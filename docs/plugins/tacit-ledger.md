# TacitLedger

**`show` reads `evolve show`'s JSON first, a prose proposal is promoted as applied to its target, and incident IDs keep their hyphens (decision changed 2026-11-22, wi_92984ac4; current; replaces "`show` reads text only", "promote of a proposal always needs current and proposed lines" and "an incident ID stops at its second hyphen", see History).** The decision that changed: `evolve show <P-id>` prints JSON, so `parseShow` tries it first and falls back to the text form; `rationale` is the root reason, `change` a new `change` field (`TacitEntryDetail.change`), `evidence` the evidence rows (IDs only); `not found: <id>` is null. Promote of a proposal with neither current nor proposed lines runs only `evolve verdict <P-id> promote --reason <r> --applied-to <target>` and writes no file, because the owner applied the change; with no target it is a `TacitRefusal` before any verdict runs (only `evolve show` has run). A proposal whose text form gives both lines applies them as before; one that gives only one is refused. `INCIDENT_ID` reads `T-20261017-de7e` whole in the `근거` line and draft lines. Not built: a backfill of IDs already cut in the owner's rules file.

**`edit` rewrites an applied class's block, `pushbacks` lists the active unclustered pushbacks and `dismiss` records one as noise (decision changed 2026-11-22, wi_ec1a534e; current; replaces "the factory writes the rules file only on promote or retire" and "a repeated field line overwrites the earlier one in `applied()`", see History).** The decision that changed: the Rules page edits an applied rule's wording, default and exception with no verdict, and lists and dismisses pushbacks before they cluster (design 09-dashboard-rules.md). The three methods are optional in the interface, like `applied`, so `none` and test fakes need no change; the UI's holder reaches them on the plugin it last built, and has `pushbacks` only while that plugin does. The `tacit show --active --unclustered` and `tacit status <T-id> noise` forms below are **assumed**: they are not yet checked against the owner's CLI (they wait for its output and `--help`).

**`show` reads each incident's optional date, the agent's proposal and its root reason, a description and a proposal's lines (decision changed 2026-11-16; current; replaces "an incident row gives only the owner's quoted words", see History).** The decision that changed: `parseShow` keeps every `- ` row under `## incidents <n>` as `evidence`, newest first (undated rows last, in the ledger's order): `- <ref> <YYYY-MM-DD>? — "<the owner's words>"` gives `ref` (the T-, L- or E- ID, or the ledger's own reference), `date` (optional; also `(YYYY-MM-DD)` or an indented `date:` line), and `quote`; indented `proposal:` / `제안:` and `root reason:` / `근본 원인:` lines under the row give that incident's `proposal` and `root_reason`. Entry-level `설명:` / `description:` (one line on the entry), `현재:` / `current:` and `변경:` / `proposed:` (a proposal's current lines and its change) are read when the ledger prints them, else absent. The plugin still runs only `evolve show <id>`, `evolve pending` and reads the rules file (`applied()`); it reads none of the owner's target files and writes nothing for this. **Related** on the Rules page is computed in the dashboard from `applied()`: an applied rule is related to an entry when its `근거` T- IDs share one with the entry's evidence or draft, or its text names the proposal's target file. Design: [09-dashboard-app.md](../design/09-dashboard-app.md).

**Promote of a proposal applies its lines, and the agents home is chosen from the known homes with a check (decision changed 2026-11-18, phase 4 of 4 of local-0ffe3059-d863-4717-b3eb-1c72a06e444e; current; replaces "promote of a proposal names the file the owner changed by hand with `--applied-to`" and "not found: put the CLIs in `<home>/bin`", see History).** The decisions that changed: **promote of a proposal (`P-` ID) changes the target file itself.** The owner's `evolve` has no apply subcommand (`evolve --help` lists learn, learnings, propose, verdict, pending, show; `evolve apply` exits with "invalid choice: 'apply'"), so the plugin applies and no evolve command is invented: `verdict(<P-id>, "promote", reason)` runs `<home>/bin/evolve show <P-id>` and reads its `target:`, `current:` and `proposed:` lines (`parseShow`). It refuses with `TacitRefusal`, writing nothing and sending no verdict, when a line is missing, the target is absolute or has a `..` segment, the target's resolved path is not a file inside the resolved home, or the current lines occur in the target other than exactly once. Otherwise it replaces them with the proposed lines, then runs `<home>/bin/evolve verdict <P-id> promote --reason <reason> --applied-to <target>`; a non-zero exit or the 30 s timeout writes the file back byte for byte and throws the CLI's error. `verdict` takes no `{ applied_to }` any more (`TacitApplication` and `appliedToError` are removed); its fourth argument is only a class's rule. Hold and reject of a proposal, and every class verdict, are unchanged. **The agents home** is still `AGENTS_HOME`, else `~/.agents`, and is never stored: `checkAgentsHome` adds `homes`, each known home (`AGENTS_HOME` when set, then `~/.agents`, each once; `knownAgentsHomes`) with its own check (the first of `bin/tacit` and `bin/evolve` missing or not executable), for the Rules page's picker; a passing `~/.agents` does not stand in for a broken `AGENTS_HOME`. **Why:** the Rules page told the owner to make the change by hand and to put the CLIs in a folder (owner answers 1 and 3: store no path, the check decides; apply after a diff and a confirm, and a failed apply writes nothing). Design: [09-dashboard-app.md](../design/09-dashboard-app.md).

**Retire of a class removes its block, and `retired()` lists the retired classes (decision changed 2026-11-14; current; replaces "retire runs `tacit verdict <C-id> retire` only", see History).** The decision that changed: a retire verdict on a class now edits the owner's rules file as promote does (block out, verdict, sync-agents, rollback on a failed verdict), and the ledger's retire verdicts are read back for the Rules page's Retired list. Design: [09-dashboard-app.md](../design/09-dashboard-app.md), [07-self-improvement.md](../design/07-self-improvement.md).

What it does: captures the owner's pushback in their own tacit-knowledge ledger, so the owner's tools can learn from it (issue #570). A `/revise`, a `/reject` and a `/verdict changes` (also a dashboard revise, reject or changes verdict) each capture one record once the command applied. The capture is an outbound intent (action `tacit_capture`, destination `tacit:ledger`), keyed by the item and the command's comment ID, so a command delivered twice, or handled by two workers, stores one intent. The process that flushes outbound runs the ledger's CLI; the command's stage change never waits on it. Design: [04-gate-commands.md](../design/04-gate-commands.md).

The interface (`src/interfaces/tacit-ledger.ts`) has `capture` (one pushback), `pending` (the entries waiting for a verdict, each with `id`, `title` and `state`, and a proposal's `kind` and `target` when listed), `show(id)` (one entry's detail, or null; since 2026-11-13), `verdict(id, decision, reason, rule?)` (the owner's verdict on an entry; `rule` is `{ wording, default, exception }` on promote of a class; promote of a proposal applies its lines first) `rules` (the promoted rules), `applied()` (the whole rules file for the Rules page's Applied group, since 2026-11-13; optional like `show`; the runtime holder delegates it) `retired()` (the retired classes, newest first, `{ id, reason, date }`, since 2026-11-14; optional; the UI's holder reads it from the plugin it last built, as `show`), and, since 2026-11-22 and optional as `retired`, `edit(id, rule)` (rewrites an applied class's block with `{ wording, default, exception }`; no verdict), `pushbacks()` (the active pushbacks in no class yet, `{ id, pushback, date? }`) and `dismiss(id)` (records pushback `T-…` as noise). `show` is optional in the interface because the runtime holder (`src/runtime/live-tacit.ts`) does not delegate it yet; the UI's holder (`uiTacit` in `src/ui/rules-api.ts`) reads it from the plugin it last built. `capture` is wired into outbound; `pending`, `show` and `verdict` serve the dashboard's Rules page and `rules` the learned rules in every prompt (design 07-self-improvement.md, 09-dashboard-app.md).

Plugins:

- `none`: `NoTacitLedger`. No ledger: nothing is captured and no outbound intent is recorded. `pending` and `rules` return nothing, `applied()` returns `{ rules: [], elsewhere: [] }`, `show` returns null, `retired()` returns nothing; `verdict` does nothing (a retire too). It has no `edit`, `pushbacks` or `dismiss`. The Rules page then shows no Applied group, so no suggestion and no Retire or Edit action, and no Pushbacks list.
  - Enable: `"plugins": { "tacit": "none", ... }`, or leave `tacit` out (the default on every platform). Secrets: none. Settings: none.
- `agents-home`: `AgentsHomeTacitLedger`. Runs the ledger's CLIs in the owner's agents home on this machine. The home is the `AGENTS_HOME` environment variable when set, else `~/.agents`; the path is found by the plugin only, never by core or controller code.
  - Enable: the Rules page's **Turn on** (below), or `"plugins": { "tacit": "agents-home", ... }`. Secrets: none. Settings: `integrations` (runtime, owner only), `AGENTS_HOME` (optional; default `~/.agents`).
  - `capture` runs `<home>/bin/tacit capture --agent software-factory` with one JSON record on stdin, never in argv: `session` (the work item ID), `proposal` (the stored summary of the item's latest finished run: its spec, change or review), `pushback` (the owner's words, verbatim), and `root_reason`, `hypothesis`, `improvement` and `rule_draft` empty (the ledger distils those itself).
  - The other calls use the owner's real CLI forms (checked 2026-11-12 with `--help`). Each value is its own argv item, nothing goes through a shell, and only `capture` uses stdin.
    - `pending` runs `<home>/bin/evolve pending`, which prints text, not JSON, and reads it (`src/impl/tacit/ledger-text.ts`): each `- P-id [kind] target — title` row under `## proposals (open)` or `## proposals (held)`, and each `- C-id title` row under `## tacit Pending` or `## tacit Held`, is one entry whose state is the heading's word in lower case (`open`, `held`, `pending`). A proposal keeps its `kind` (`promote-learning`, `edit-asset`, `new-asset`) and `target` (the asset it changes) when the row has them. Rows under any other heading are skipped. An entry with a `{"type":"verdict","class":<its id>,"ts":…,"decision":…}` line in `<home>/private/tacit/ledger.jsonl` whose `ts` is newer than `<home>/private/tacit/rule-candidates.md`'s modification time is `judged` with that decision (the daily brief rebuilds that view, which `evolve pending` reads, at 08:30; no view file: nothing is judged). Each other class gets its `draft` from `<home>/bin/evolve show <id>`, or a `draft_error`.
    - `show` runs `<home>/bin/evolve show <id>` (example: `evolve show C-037`) for a class or a proposal and reads it (`parseShow`). Its JSON form comes first (the owner's CLI for a proposal, 2026-11-22): one object with `id`, `ts`, `by`, `kind`, `target`, `title`, `rationale`, `change`, `evidence` and `state` and `verdicts`, of which `kind` and `target` are read as they are, `rationale` as `root_reason` (Why), `change` (free text) as `change`, and each `evidence` string (IDs only) as an evidence row with its `ref`, in order, their number the incident count; an empty or non-string value is absent. `not found: <id>`, which `evolve show` prints for an unknown ID, is null. Text that is not one JSON object is read in the text form, which is assumed, not yet checked against the real CLI: field lines `기본값:` / `default:` (the draft rule), `예외:` / `exceptions:`, `범위:` / `scope:`, `근본 원인:` / `root reason:`, `kind:` and `target:`, with or without a list dash, an indented line continuing one; and an `## incidents <n>` heading whose `- <ref> <YYYY-MM-DD>? — "<the owner's words>"` rows, with their indented `proposal:` and `root reason:` lines, are the incidents (`evidence`, the decision at the top; the count is `<n>`, else the rows); `설명:` / `description:`, `현재:` / `current:` and `변경:` / `proposed:` lines too. A field the text lacks is absent; an empty text is null. Any other ID throws before a CLI runs. It reads only: nothing is written to the store or the ledger.
    - `evolve show <C-id>` is read in the owner's sample form (2026-11-13): `### C-xxx <title>`, then `- 인시던트: <T-ids>`, `- 초안: 기본값: <default> / 예외: <exception>` (split on ` / 예외: `), `- 범위: <scope>`, before the `# incidents` and `# verdicts` sections. A missing part is an error, never a guess.
    - `verdict` on a class (`C-` ID) to hold or reject runs `<home>/bin/tacit verdict <id> <hold|reject> --reason <reason>`; retire is below. On a proposal (`P-` ID) it runs `<home>/bin/evolve verdict <id> <hold|reject> --reason <reason>`, and for promote it applies the proposal's lines to its target, then runs `<home>/bin/evolve verdict <id> promote --reason <reason> --applied-to <target>` (a proposal with neither current nor proposed lines, a prose change: only that verdict, no file written; the decisions at the top), never with a rule (`evolve` takes no retire). Any other ID throws before a CLI runs. The CLIs take no field for who judged, so the ledger does not record it; the dashboard's log does.
    - Promote of a class encodes the rule, as the owner did by hand. Checks come first, each a `TacitRefusal` (the Rules page's 409) with nothing written and no verdict: a rule is given; `<home>/private/tacit/rules.md` exists and its resolved path (symlinks followed) lies inside the resolved home; it has no `## <C-id>` heading yet; it has the `## 다른 곳에 인코딩된 규칙` heading; `<home>/bin/sync-agents` is executable; `evolve show <C-id>` reads as a draft. Then one block goes immediately before that heading, followed by a blank line: `## <C-id> <wording>`, `- 기본값: <default>`, `- 예외 (이럴 땐 override): <exception>`, `- 근거: 인시던트 <the draft's T-ids, joined by ", "> / 판정일 <today, YYYY-MM-DD>`, `- 범위: <the draft's scope>` (line breaks in a value become spaces). Then `<home>/bin/tacit verdict <C-id> promote --reason <reason> --rule <wording> --encoded-to private/tacit/rules.md`; if it fails the file is written back byte for byte and the CLI error is thrown. Then `<home>/bin/sync-agents`; if it fails the block stays (the verdict is recorded) and `TacitSyncFailed` is thrown. Nothing undoes a verdict or a sync that succeeded, and the file is not locked against the owner's own edits made at the same time.
    - Retire of a class removes the rule, as the owner did by hand. Checks come first, each a `TacitRefusal` (the Rules page's 409) with nothing written and no CLI run: `<home>/private/tacit/rules.md` exists and its resolved path lies inside the resolved home; it has a `## <C-id>` heading. Then the block (its heading line up to the next `#` heading or the end of the file, its trailing blank line included, so it undoes a promote's block; `withoutRuleBlock`) is removed and every other byte kept. Then `<home>/bin/tacit verdict <C-id> retire --reason <reason>`; if it fails the file is written back byte for byte and the CLI error is thrown. Then `<home>/bin/sync-agents`; if it fails the removal stays (the verdict is recorded) and `TacitSyncFailed` is thrown. A retire of a proposal throws before a CLI runs.
    - `retired()` reads `<home>/private/tacit/ledger.jsonl`: each class whose newest `{"type":"verdict","class":…,"ts":…,"decision":…}` line is a `retire` is one entry, `{ id, reason (the line's reason, else ""), date (the first ten characters of its ts) }`, newest first. A class promoted again after its retire is not listed. No file: nothing. Read-only.
    - `applied()` reads the same file for the Rules page (`parseApplied` in `src/impl/tacit/ledger-text.ts`), read-only. Each `## ` block up to the next `#` heading is one item: with a `C-xxx <name>` heading and a `- 기본값:` line it gives `id`, `name`, `default`, `exceptions` (`- 예외…`), `scope` (`- 범위:`), `incidents` (the T- IDs before `판정일` on the `- 근거: 인시던트 <T-ids> / 판정일 <YYYY-MM-DD>` line) and `judged` (that date), a part the block lacks being absent; any other block (no C- ID or no `기본값` line) is `{ raw }`, its text as written. `elsewhere` is the non-empty lines under `## 다른 곳에 인코딩된 규칙` up to the next `#` heading, as written. No file: `{ rules: [], elsewhere: [] }`, not an error. The route passes every text through the Withholder.
    - Edit of an applied class (`edit`, since 2026-11-22) changes the rule's block and sends no verdict. Checks come first, each a `TacitRefusal` (the Rules page's 409) with nothing written and no CLI run: the ID is a class; `<home>/private/tacit/rules.md` exists and its resolved path lies inside the resolved home; `<home>/bin/sync-agents` is executable; the file has a `## <C-id>` heading. Then `withEditedBlock` (`src/impl/tacit/ledger-text.ts`) rewrites only the block's heading line (`## <C-id> <wording>`, on one line) and its `기본값` and `예외` lines with their indented continuation lines: one line per line of the new value, under the label the first such line had (a repeated line is dropped, its value now in the first); a block with no `예외` line gets `- 예외 (이럴 땐 override): <exception>` after its `기본값` lines. The `근거` and `범위` lines, the line ends and every other byte stay. A failed write puts the file back byte for byte and throws the error; then `<home>/bin/sync-agents` runs, and its failure keeps the new text and throws `TacitSyncFailed` ("The rule was saved, but sync-agents failed").
    - `pushbacks` runs `<home>/bin/tacit show --active --unclustered` (**assumed form**) and reads its text (`parsePushbacks`): each `- <T-id> <YYYY-MM-DD>? — "<the owner's words>"` row is one pushback, its words unquoted (a row with no dash: the rest of the line); headings and blank lines are skipped. Text with other lines and no row throws, so a different real form shows as "could not be read" on the page, never as an empty list. Read-only.
    - `dismiss` runs `<home>/bin/tacit status <T-id> noise` (**assumed form**), which records the noise status so the pushback leaves the active list. An ID that is not `T-` followed by letters, digits, `_` or `-` throws a `TacitRefusal` before any CLI runs. Pushbacks dismissed by hand before 2026-11-22 are not backfilled.
    - `rules` reads `<home>/private/tacit/rules.md` (the CLIs have no JSON listing of it): each `## C-xxx <name>` section gives its `- 기본값:` (the rule), `- 예외` (exceptions) and `- 범위:` (scope) values as written; an indented line under one continues it. No file: no rules, not an error. `AGENTS_PRIVATE` is not honoured yet: only `<home>/private` is read.
  - Each CLI call is stopped after 30 seconds and counts as a failure; a call that exits non-zero or times out throws `<cli> <subcommand> exited <code>: <stderr>` or `<cli> <subcommand> stopped after <ms> ms` (for `show`: `evolve show exited <code>: <stderr>` or `evolve show stopped after 30000 ms`; the Rules page then says "The detail could not be read." and keeps the card). A failed capture is retried with outbound's backoff (`retry_base_ms`, `retry_max_ms`) and holds only the `tacit:ledger` destination: GitHub, Slack and the factory repo keep sending.
  - The pushback and the proposal pass the egress scanner (G5) before the CLI is called; a flagged text is replaced by the notice that names the rules.
  - The factory writes one file under the home, `<home>/private/tacit/rules.md`, and only on promote, edit or retire of a class (above); its resolved path must lie inside the resolved home, else nothing is written. Otherwise it runs the CLIs there and reads the rules file, `ledger.jsonl` and `rule-candidates.md`'s modification time. The plugin is built in the factory's processes only (the controller and worker pool, and `factory ui` for the Rules page); an agent run never gets it, and no agent environment holds the home.
  - The home is found only when `bin/tacit` and `bin/evolve` are both executable files there (`checkAgentsHome`). Otherwise the plugin behaves as `none` and startup goes on.

Not captured: a "Request changes" PR review, implicit verdicts and reverts (a follow-up issue covers the review), and pushbacks stored before the plugin was selected (no backfill). A ledger shared between people is not built (one owner, `docs/design/08-enterprise.md`).

Turn on / off (since 2026-11-12): TacitLedger is an integration (`integration: true` in `src/plugins.ts`, [selection.md](selection.md)), switched at runtime by the `integrations` setting, with no restart.

- **Turn on.** Two places turn it on, with the same picker (`web/src/views/agents-home-picker.tsx`) and the same stored value. On the Settings page's Integrations section, flipping the TacitLedger Switch while it is off opens a dialog "Turn on TacitLedger?" with the picker and its check (read once from GET /api/v1/rules); its **Turn on** posts the server's `turn_on` through POST /api/v1/settings, is disabled while the home in use is missing or the viewer is not the owner (with the same reason as on Rules), and Cancel leaves the switch off. On the Rules page, with the ledger off, the page shows an agents home picker over the known homes (`AGENTS_HOME` when set, and `~/.agents`), the home in use (`AGENTS_HOME`, else `~/.agents`) chosen first, and the chosen home's check: "bin/tacit and bin/evolve are both executable in <path>." or "<file> is missing or not executable in <path>."; a home that is not the one in use says so. The home in use found: one primary **Turn on** button stores `{ "tacit": "agents-home" }` in `integrations` through POST /api/v1/settings (the settings route's guards and the owner check), and the page then lists the rules with no reload. Choosing a home stores nothing, and no copy tells the owner where to put the CLIs. A runtime setting never names a path: the entry is only the plugin name. From a terminal: `factory settings set integrations '{"tacit":"agents-home"}'`.
- **Turn off.** The Settings page's Integrations section lists TacitLedger with its plugin and whether the setting or the config chose it; its Switch removes the entry (`settings reset integrations` when no other entry is left), so `plugins.tacit` in the config file decides again.
- **Config.** `plugins.tacit` stays the default when `integrations` has no `tacit` entry: `agents-home` (on) or `none` (off, the default when left out).
- **When it applies.** The controller and the worker pool rebuild the plugin by their next tick, `factory ui` by its next Rules request. Captures already recorded and not delivered stay in outbound until a process with the plugin on flushes them.
