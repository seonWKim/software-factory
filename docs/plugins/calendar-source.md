# CalendarSource

What it does: reads the owner's calendars, so the factory keeps a copy of their events beside the tasks (design [02-tasks.md](../design/02-tasks.md), calendar). The read never writes. A source may also offer a sync port, `sync` (decision changed 2026-11-25; current; replaces "a source only reads: the factory never creates, edits or deletes an event", see History): `label`, `writable()`, `add(copy)`, `edit(id, copy)` and `remove(id)`, which copy the owner's local events into its calendar when the owner asks, one call per add, edit or delete, a repeating event as a whole series. A failed call keeps the local change with its error on the event and is never retried on a poll. Design [02-tasks-calendar.md](../design/02-tasks-calendar.md), copy to a connected calendar.

The interface (`src/interfaces/calendar-source.ts`) has one call, `events({ from, to })`: every event that overlaps the window, each with `id` (the source's own, stable and unique within the source), `title`, `starts_at`, `ends_at` (ISO 8601 instants), `all_day`, `updated_at` (null when the source reports none) and optional `details`: the calendar's name, `location`, `description` (as written, possibly HTML; the dashboard shows it as text), `organizer` and `attendees` (name, address, answer), `conference_url` and `link` (the event's own page; http(s) only), `time_zone` (design 09-dashboard-tasks-calendar, event details). A source fills `details` only from the read it already makes. A throw is that sync's error.

**Config.** The top-level key `calendar` is a list of CalendarSource plugin names, in order, never a `plugins` key:

```jsonc
"calendar": []          // the default: no source, nothing is read
"calendar": ["google-calendar"]  // read the owner's Google calendars
```

Absent or `[]`: no source is built and no calendar data is read or stored. The runtime setting `calendar` (owner only, design [08-settings.md](../design/08-settings.md)), which connect and disconnect write, overrides the file's key and applies at the controller's next tick with no restart; with no override the file decides. A value that is not a list, a name listed twice, or a name no plugin has fails startup with an error that names `calendar` and the available plugins. `calendar` under `plugins` fails too, pointing to the top-level key. A plugin's context is the base context, the `SecretStore`, for a provider's credentials, and the `Clock`, for a provider's own time checks (google-calendar: its access token's expiry).

**Cadence.** The controller's `calendar` unit runs each poll; each configured source syncs **at most once every 5 minutes**. Its next sync time is stored per source in `calendar_sync_state` and taken by a conditional write, so every replica keeps one schedule and two never read one source in the same period. A sync asks for the window from one day back to 30 days ahead and replaces only the source's rows in `calendar_events` that overlap that window (keyed by source name and event ID); rows outside it stay (decision changed 2026-11-22; current; replaces "replaces all of the source's rows", see History). **On request:** the Calendar page's Sync and `factory calendar sync --from --to` store a request for any range of up to 62 local days, past days too; the `calendar` unit runs it on its next poll, asks each source for local midnight of the first day through local midnight after the last, replaces only the rows in that window, records the window in `calendar_synced_ranges` and leaves the source's next sync time alone ([02-tasks-calendar.md](../design/02-tasks-calendar.md)). A window that differs from the scheduled one costs `google-calendar` one full read, since its sync token is kept per window. A failed read stores its error (cut to 1000 characters) and time on the source's state row, keeps the source's last events, waits for the next due time, and is cleared by the next success. A down source never holds up the controller's other steps or a task action.

Plugins:

- `google-calendar`: Google Calendar (`src/calendar/plugins/google-calendar/`). Asks Google for the `calendar.readonly` scope, or, when connected with write access, the `calendar.events` scope only; its token exchange and refresh refuse an answer with any scope other than those two. Its sync port (label "Google Calendar") writes only when the token answer grants `calendar.events`: one events call per add (`POST`), edit (`PUT`) or delete (`DELETE`) in the first calendar it reads, a repeating event as one recurring event. Read-only, it makes no write call and the event dialog's "Also add to Google Calendar" switch is off with the note to reconnect with write access. The granted scope is never stored, and no token is logged or returned. Returns every event that overlaps the window the sync passes (decision changed 2026-11-15; current; replaces "reads today through 14 days ahead", see History): it asks Google for the whole local days that window touches, from the local midnight of the window's first day to the local midnight after its last day, in the process's time zone (as in [02-tasks.md](../design/02-tasks.md)). For the sync's window (a day back to 30 days ahead) that is yesterday's midnight to 31 days ahead; those bounds move only at local midnight, so every sync after the first on one local day reads incrementally with the sync token. Events Google answers outside the passed window are dropped. The dashboard's Calendar page counts a day as synced from the same window ([09-dashboard-app.md](../design/09-dashboard-app.md), Calendar page). Each HTTP call to Google, its body included, is given up after 30 seconds (`GOOGLE_HTTP_TIMEOUT_MS`) and throws "no answer", so a hung Google never holds up the controller's tick; the connect's token exchange takes the same limit, on the context's `Clock`, so a hung exchange fails with "no answer" and writes nothing. A failed token refresh or read throws, so the sync stores the error and keeps the last events; an error names the step and the HTTP status, never a secret value or a response body.
  - Secrets: `GOOGLE_REFRESH_TOKEN`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, read only through the `SecretStore`: an OAuth refresh token granted `calendar.readonly` (or `calendar.events`, connected with write access), and the client it was issued to (the factory's default client, or your own). The connect writes all three; you write none by hand.
  - The default client (decision changed 2026-11-14; current; replaces "the owner creates an OAuth client in Google Cloud Console first", see History): connecting needs no Google Cloud setup. When the secret file has no `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` values (an empty `KEY=` line counts as none), the connect uses the factory's own OAuth client, of type Desktop app (`src/calendar/plugins/google-calendar/default-client.ts`). Its ID is a public identifier and is the constant `DEFAULT_GOOGLE_CLIENT_ID` in source. The default client is the Desktop-app client in Google Cloud project `gongbang-514711`. Google treats a Desktop-app client's secret as not confidential (anyone can read it out of an installed app; PKCE and the loopback redirect protect the sign-in, not the secret), but this repository still holds no credential, not even gitignored ([setup](../setup.md)): the release build writes `default-client-secret.js` (exporting `DEFAULT_GOOGLE_CLIENT_SECRET`), from outside the repository, into its build output beside the compiled `default-client.js` (`dist/calendar/plugins/google-calendar/`), never into `src/`: `npm run build` with `SF_GOOGLE_DEFAULT_CLIENT_SECRET` set at build time ([setup](../setup.md), release builds) writes it into the staged `dist/` before the swap, mode 600, and writes nothing else; unset or blank, the build writes no module. A missing or unreadable module counts as no default: startup and the connect do not fail. A test checks that no tracked file holds a Google client secret and that the module's place in the build output is ignored by git. A build without that file, or with an empty ID, has no default client: the CLI then asks for your own client, and the dashboard shows no Connect (see the no-default-client state below). After a connect with the default client, the secret file holds the default pair like any other, so the sync and a later reconnect read it from there.
  - The unverified-app warning (decision changed 2026-11-19; current; replaces "the expired refresh shows as the Calendar section's last error", see History): Google may show "Google hasn't verified this app" on the consent page for either client, the default one (an unverified Google app, with the owner as its only test user) or your own; that is expected, and Continue (under Advanced on some pages) is safe. The page still asks only for read-only calendar access. A client in Testing status must be reconnected every 7 days, because Google then expires its refresh token, unless it is set to In production on the OAuth consent screen, which needs no verification for your own account. Settings → Calendar says the same in a note beside Connect, collapsed by default. When the refresh is refused with HTTP 400 and the OAuth error code `invalid_grant`, the source throws, and the sync stores, that code alone (`INVALID_GRANT`): it reads only the body's `error` field and never keeps the rest of Google's body. For that stored error the section shows "Reconnect Google Calendar" with the same note, open, in place of the "Last error" line, and keeps Connect and "Use my own client" beside Disconnect. Any other refresh failure stays "token refresh failed (HTTP <status>)".
  - Config: the optional top-level key `calendar_ids`, a list of calendar IDs (`"calendar_ids": ["work@example.com"]`). Absent or `[]`: the `primary` calendar only. Listed: those calendars instead of the primary one, each event's ID then prefixed with its calendar ID when more than one is listed. A value that is not a list of non-empty strings fails startup.
  - Cache: the access token (until it expires), and per calendar the sync token, the last answer's ETag and the last events, all in process memory, never in the store. A read sends the stored sync token and the ETag as `If-None-Match`; a `304` reuses the stored events, and a `410` clears the sync token and runs a full read in the same sync. A new local day moves the read's bounds and runs a full read. A restart, or another replica, loses the cache: that costs one full read.
  - Turn on, from the dashboard: Settings → Calendar lists each calendar plugin with a connect hook (from the registry), connected or not, with its last sync time and last error. Connect opens Google's consent page at once, in a new tab, with no dialog: the client is your own when the secret file holds both lines, else the default client; the page then polls `GET /api/v1/calendar` and shows "Connected, N events read" after the first sync. The sign-in uses the same listener on `127.0.0.1` as the CLI, so Google needs no other redirect URI; it lives in the `factory ui` process, which keeps the sign-in's state in memory only. The routes (`POST /api/v1/calendar/connect`, `/disconnect`) take the write routes' guards and the owner check.
  - No default client (decision changed 2026-11-14; current; replaces "the dashboard's Connect fails before any write and points to the own-client option", see History): the connect hook's `hasDefault()` (optional on `ConnectHook`; absent counts as true) says whether this build carries the default client, and `GET /api/v1/calendar` passes it on each plugin as `default_client`. When it is false, the Calendar section shows no one-step Connect button (it could only fail), says "This build has no default Google client. Connect with your own OAuth client.", and its main action is "Use my own client", which runs the own-client option below. `factory setup calendar google` prints the same sentence before it asks for `GOOGLE_CLIENT_ID`. A plain connect posted anyway is still refused before any write; a connect that ends before its consent page opens (a refusal, or a stop for input) keeps no attempt, so its error shows once, under the buttons, not again as a failed sign-in on the next read.
  - Turn on, from the terminal: `factory setup calendar google` (after `npm run setup`, which creates the secret file; with no secret file it stops and creates nothing) runs the same one step: your own client from the secret file when both lines are there, else the default client, and it asks for no client ID or secret. Only a build with no default client asks for them, once, with hidden input.
  - Advanced, your own client: an OAuth client of type Desktop app on your own Google Cloud project, with the Google Calendar API enabled (Google Cloud console, APIs & Services → Credentials). From the terminal, put `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in the secret file and run `factory setup calendar google`: both lines present are always used. From the dashboard, "Use my own client (advanced)" beside Connect (or "Use my own client", the main action, in a build with no default client) posts `own_client: true`; the answer names the values to ask for (`needs_input`), and only then a dialog with password fields asks for `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (those the secret file lacks); the typed values leave the page once sent, and are written only after the sign-in passes. A plain Connect sends no values; the route refuses values without `own_client: true`.
  - Both run one flow (`connectCalendar` in `src/setup.ts`, over this plugin's connect hook): the consent page asks for `https://www.googleapis.com/auth/calendar.readonly` only, or `https://www.googleapis.com/auth/calendar.events` only with write access (`write: true` on the dashboard's connect, a yes to "Allow writes" in the CLI), with a PKCE S256 challenge, a random state and a redirect to a listener on `127.0.0.1` (a port the system picks, path `/callback`) that closes after 5 minutes. It refuses a wrong state, an error from Google, a token answer that does not grant the scope asked for or grants any scope other than `calendar.readonly` or `calendar.events`, or one with no refresh token: then nothing is written (the CLI exits non-zero; the page shows why). Otherwise it writes the three secrets together to the secret file (mode 600), adds `"google-calendar"` to the live `calendar` setting (other names stay), and runs one sync. No secret, token, code or verifier is printed, returned by the dashboard, logged or stored anywhere else; the consent URL shows the client ID.
  - Off: Disconnect on the Settings page (after a confirmation dialog; nothing is written before Confirm) or `factory setup calendar google --disconnect` removes the three secret lines from the secret file (other lines stay, mode 600) and drops `"google-calendar"` from the live `calendar` setting (other names stay; the last one leaves `[]`). It does not revoke the token at Google, and the source's stored events stay until a later change removes them.

Turn on / off: connect or disconnect a plugin (above), or list plugin names in `calendar`, the file key or the live setting (on); set `[]` (off). Stored events and state rows stay until a later change removes them.

## History

- 2026-11-25: a source may offer a sync port, and `google-calendar` copies the owner's local events into Google Calendar when connected with write access (`calendar.events`, asked only then). Decision changed: "a source only reads: the factory never creates, edits or deletes an event". Before, every source only read and `google-calendar` refused any scope but `calendar.readonly`.

- 2026-11-22: a sync replaces only the source's rows that overlap its window, and the dashboard and the CLI can ask for a sync of any range of up to 62 days, run by the `calendar` unit on its next poll. Decision changed: "replaces all of the source's rows". Before, each scheduled sync deleted every stored event of the source, so a range outside one day back to 30 days ahead could not be kept.

- 2026-11-19: Settings → Calendar explains Google's unverified-app screen and the 7-day expiry of a Testing client in a note beside Connect, and an `invalid_grant` refresh is stored as that code and shown as "Reconnect Google Calendar". Decision changed: "the expired refresh shows as the Calendar section's last error". Before, the refresh failure was stored as "token refresh failed (HTTP 400)" and shown raw, with no hint to connect again.

- 2026-11-15: `google-calendar` returns every event in the window the sync passes (yesterday's midnight to 31 days ahead for the sync's window), as the interface says. Decision changed: "reads today through 14 days ahead". Before, it read today through 14 days ahead and narrowed the sync's window to that, so the stored copy held no event from yesterday or more than 14 days out.

- 2026-11-14: with no default client in the build, Settings → Calendar shows no Connect: it says so and offers "Use my own client" as the main action, from the read's new `default_client`; the CLI says the same before asking, and a refused connect leaves no failed attempt behind. Decision changed: "the dashboard's Connect fails before any write and points to the own-client option". Before, Connect stayed, always failed, and its error showed twice.

- 2026-11-14: `google-calendar` connects in one step with the factory's default OAuth client (ID in source, secret injected by the release build), from the dashboard and the CLI; the owner's own client is the advanced option. `npm run build` writes the secret module into the staged `dist/` from `SF_GOOGLE_DEFAULT_CLIENT_SECRET`. Decision changed: "the owner creates an OAuth client in Google Cloud Console first". Before, Connect and `factory setup calendar google` asked for `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` whenever the secret file lacked one.

- 2026-11-13: `google-calendar` is connected and disconnected from the dashboard too, and both the dashboard and `factory setup calendar google` write the live `calendar` setting through one flow; the token exchange is given up after 30 seconds. Before, only the terminal connected it, it wrote the file's `calendar` key after a diff and a yes, and the exchange waited on Google with no limit.

- 2026-11-12: `google-calendar` gives up an HTTP call after 30 seconds. Before, a sync waited on Google with no limit.

- 2026-11-12: `google-calendar` is turned on with `factory setup calendar google` and off with `--disconnect`. Before, the owner pasted the three secrets into the secret file and edited `calendar` by hand, and ran the OAuth consent outside the factory.

- 2026-11-12: `google-calendar` added, the first provider, with the `calendar_ids` key and the `Clock` in the plugin context. Before, no provider shipped and `calendar` could name none.

- 2026-11-12: the interface, the `calendar` config key and the sync added, with no provider. Before, the factory had no calendar.
