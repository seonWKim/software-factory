# SourceAdapter

What it does: intake. Brings in new work items and commands from a source, and posts comments back. Pull requests are not a source's: PR events, PR facts, PR comments and PR status belong to the forge (`docs/plugins/forge.md`, issue #273). `SourceAdapter` is a union on `intake` (docs/architecture.md, Intake):

- `intake: "poll"` (`PollSource`): `poll(cursor)` returns events and the next cursor; the controller calls it every `poll_interval_ms`, reads every poll source first, then polls the forge, and handles the forge's events before the sources' (so a merge that closed an issue is applied before the close). A null cursor means "start from now", not "read the history".
- `intake: "stream"` (`StreamSource`): `subscribe(signal)` returns an `AsyncIterable<PushedEvent>`, for sources that push events as they happen (e.g. Slack Socket Mode).

Both kinds have `postComment`, `markSeen` and `setStatus`. Two optional methods file new items, idempotent on a marker the source looks up first: `fileSubIssue` (a phase of a split spec, under its parent, with the intake label; only outbound calls it, for a `file_sub_issue` action, design 04-split-specs) and `fileIssue` (one standalone item, taken in for triage: the intake label, or a queued triage run; the improve run's failure patterns, design §7). The controller files through the first source in `plugins.source` order that has `fileIssue`; `slack` has neither. The controller calls `postComment` only from its outbox step (issue #282): every message is first an item thread entry with one outbox row, delivered once per entry to the item's own source, with backoff on failure (design 05-sources, "Thread first"). `silent_intake_refusal` (optional): `true` on a source whose intake label is the gate (`github-issues`), so a refused intake gets no reply; left out, the source replies once in the thread (`slack`). The controller reads this flag, never the source type.

`notifyOwner(notices)` (optional, design 12-notification-channels): sends the owner's notices of one tick as one message, one line per notice, to the channel the adapter's own config names. A notice (`SourceNotice` in `src/interfaces/source-adapter.ts`) is neutral: `kind` (`needs_you`, `finished` or `summary`), `work_item_id` (null for a summary), `title`, a one-line `reason` (a needs-you notice's fixed reason; a finished one's `merged`, `rejected` or `dropped`), `close_reason`, `thread_url` (the item's thread on this adapter's own source, else null) and `count` (for a summary). The runtime setting `notify_channels` lists the source plugins that get notices (default `[]`: none, only the dashboard and the desktop shell); the controller writes one outbox `notify` row per notice for each listed plugin whose adapter has `notifyOwner`, and none for one without it. Outbound calls it with at most 50 notices of one 60 s batch, after it egress-scanned each title and reason (a flagged batch is withheld and never retried); a failure retries the batch with backoff and holds only that adapter's notices. The controller checks that the method is present, never the source type. Only `slack` has it. The method is `notifyOwner`, not `notify`, since the test helper `FakeStreamSource` already has a private `notify`.

Plugins:

- `github-issues`: `GitHubIssueSource`. Issues with the intake label on the configured repository, their comments (commands on a PR's conversation included), closed issues, and commits on the base branch (`repo.base_branch`; one extra API call per poll, for revert tracking, design §6). It returns no PR event and reads no pull list (issue #273): selecting it selects the `github` forge (`docs/plugins/forge.md`), which reads them.
  - `setStatus(source, status, change_ref)`: shows one of eight statuses (`triaging`, `needs_approval`, `implementing`, `in_review`, `ready_to_merge`, `needs_human`, `done`, `rejected`) as a label. `change_ref` null labels the issue, which the controller calls. Non-null (the PR number as text) labels that PR (PRs share the issue labels API; converted with `prNumber`, a ref that is not a number throws): only the `github` forge calls it, from its `setPrStatus`. The source does not route PR status itself and decides nothing about which PR to label. It first compares the label state stored for the item and target (`outbound_label_states`, migration 27): the same status makes no GitHub call. Otherwise it claims the write in the store (60 s; a claim another replica holds for the same status makes the call a no-op), reads the labels, creates the label if missing (a 422 `already_exists` counts as success), adds it, removes the other seven fixed names (a 404 counts as success; no other label is touched, including other labels under the prefix), then stores the new state. A failed write stores nothing and ends its claim. Best effort: the controller logs a failure as a warning and the transition stands. Names, colours and descriptions live in one table in `src/impl/github/github-issue-source.ts`. Uses the existing Issues read/write permission; no new scope.
  - `postComment(source, body, marker)`: posts at most one comment per marker. A marker with a stored record (`outbound_deliveries`, migration 27) returns its stored URL with no call, and the comment is not edited even if the body changed (the controller logs a warning). A new marker reads the thread once, posts if the marker is not there, and stores the comment ID, URL and body hash. A failed post is counted in the store; the next try waits 1 s, 2 s, 4 s, doubling, at most 5 min, and until then the call throws without reaching GitHub, on every replica.
  - Intake and comments (issue #284; design 05-sources, "The local store is the home of the conversation"): a factory-labelled open issue is an `item_requested` event, as before (the idempotent create). Each new comment by a person is written to the store by the poll, keyed on its GitHub comment id, so a repeat poll or a second replica writes nothing more. A command goes once to the command inbox (key `github:<comment id>`, actor `github:<numeric user id>`, `args.source` the issue or PR, `args.text` the text after the command, and `args.pr` the PR (`change_ref`, its number as text) and head branch for a `/revise`, `/resolve` or `/verdict` on a PR's conversation, read once by the poll; a row queued before 2026-11-08 holds `pr_number` instead, and the reader takes either), and the controller applies it from there with provider `github`, so the GitHub auth provider decides. A comment on an issue, command or plain, goes once to its work item's thread (marker `github:<comment id>`, the comment as body, no outbox row). A plain comment is also still returned as a `plain_comment` event (`/link`, suggestions); plain comments on a PR's conversation are not written. One poll writes its comments in comment-id order. No login or display name is stored.
  - Reactions (issue #524; design 04-gate-commands, "A 👍 or 👎 on a factory message is a verdict"): inside the poll, after the comments, the comments the store records as posted on a PR of this repository in the last 7 days (`listPostedComments`) each get one conditional GET of their reactions (an unchanged list is a 304). Each new 👍 (`+1`) or 👎 (`-1`) by a person (not a bot, so not the factory's own 👀) is one `verdict_submitted` event with `reaction`, target `{ kind: "pr", change_ref }` and comment id `reaction:<reaction id>`; other emoji are passed over. The cursor keeps `reactions`: per comment still in the window, the highest reaction id delivered. Under `lowBudget()` nothing is read and the marks are kept; without a store nothing is read. Reactions on issue comments are not read.
  - `fileIssue(input)` (design §7, issue #308): files one standalone issue for a recurring failure pattern, **with** the intake label, so intake takes it in and triages it (the bot as requester: `submit_work` is open to every account no grant denies). It first looks the marker up among the newest 300 intake-labelled issues (open or closed, 3 list pages, PRs left out); an issue carrying it is returned with nothing filed, so a retry after a failure part way files no second issue. Otherwise one `POST /issues` with the body and the marker. No new scope (Issues read/write). `fileSubIssue` shares the lookup.
  - The plugin gets the store from its context, as `local` does. Without a store both calls read GitHub every time, and the poll returns each command as the event its inbox row would map to.
  - Its cursor: issues, comments (with a comment-id high-water mark), closed issues and base commits. A cursor written before issue #273 also holds the PR position (`pulls`, `start`, `reviews`): it is read without error and carried along unread; the forge takes its first cursor from it.
  - `github.history_since`: checked at startup here, used by the `github` forge (`docs/plugins/forge.md`).
  - Enable: `"plugins": { "source": "github-issues", ... }`.
  - Setup: its `setup()` hook (docs/plugins/selection.md) creates the intake label, the status labels and the PR flag labels on `repo` during `npm run setup`, reporting each as created, already exists or could not create.
  - Secrets: none of its own: it gets the process's one GitHub client (`GitHubApi`) from its context, built by the `github_auth` plugin (`GitHubCredentials`); it never sees the credentials. Settings: `repo` (including `base_branch`), `intake_label`, `branch_prefix`, `poll_interval_ms`, `status_label_prefix` (optional, default `"sf: "`; labels are the prefix plus e.g. `needs approval`. Changing it leaves labels under the old prefix in place).

- `local`: `LocalSource` (issues #199, #282). A poll source of type `local` whose surface is the store, never a forge; it makes no network call.
  - `poll(cursor)` gives no events and returns the cursor unchanged: the controller reads the CLI command log (`inbound_commands`, migration 24) itself, through its cursor `commands` (a one-time data step copied the old `intake:local` value into it, issue #467; the relay reads no other cursor), with or without this source. Each command for a local item (`args.item` the work item ID, `args.text` an optional string) is rebuilt as `/<command> <text>` and read by the same comment parser as GitHub comments (`src/core/command-inbox.ts`), so the event kinds match (`/link` is a plain comment, an unknown word an `unknown_command`; `revise` has no `pr`, `resolve` has `pr: null`, `verdict` targets the item); `comment_id` is the command's `key`, the identity provider `local` with subject the actor after `local:`. A CLI command whose item is missing or not local is skipped; rows the GitHub source wrote are read as GitHub comments (see `github-issues`).
  - The controller writes a local item's messages to its thread (`controller_item_thread`) and gives them no outbox row, so it never calls this `postComment`; it stays only because every adapter must have one. Called anyway, it stores one item message for the item with that source id, idempotent on the marker, and returns `url: null`; an id with no local item throws, naming the id. `markSeen`, `setStatus` and `closeIssue` do nothing: the store already holds the item's state. Local items' transitions run in any controller, listed or not.
  - `fileSubIssue` files the sub-tasks of a split spec (design 04, changed 2026-11-07): it returns a ref derived from the parent's source id and the phase number in the marker, `local-<id>-phase-<n>` (link `local:<that id>`), with no store read and no network call, so the same input always gives the same ref. Outbound's `local` target calls it for each `file_sub_issue` action (since 2026-11-09); the controller then creates the sub-task as an ordinary local work item keyed on that source, with `parent_id` and `phase`; a retry finds the same rows. A parent that is not local, or a marker without a phase number, throws.
  - `fileIssue(input)` (design §7, issue #308): creates one local work item for a recurring failure pattern, source id `local-filed-<16 hex of the marker's sha-256>` (link `local:<that id>`), title and body as given with the marker appended to the problem, requester `input.requester_id`, project `input.project`, and its triage run queued (key `local:<that id>:triage`) as `factory task create` queues one. Filing again finds the same item and run (the create is idempotent on the source). No network call.
  - It writes no commands, creates an item only through `fileIssue`, and emits no `item_requested`. Local identities go through the configured `AuthProvider` unchanged.
  - Enable: `"plugins": { "source": "local", ... }`, or next to GitHub: `"source": ["github-issues", "local"]`.
  - Secrets: none. Settings: none.
  - Switch back: `"source": "github-issues"` (or drop `"local"` from the list).

- `slack`: `SlackSource` (issue #109). A **stream** source of type `slack_thread`: Slack threads become work items in real time, over Socket Mode. Off unless `plugins.source` lists it.
  - In: one Socket Mode WebSocket, opened only by the replica holding the `slack_thread` listener lease (the existing stream-intake listener: store first, then ack; reconnect with backoff). No Slack SDK: `src/impl/source/slack-socket.ts` uses Node's WebSocket and `slack-api.ts` the Web API over HTTPS. Only events in a channel listed in `slack.channels` count; the bot's own messages, other bots (`bot_id`), and `subtype` events (edits, joins, deletes) are ignored and acked at once.
  - A mention of the bot (`app_mention`) starts one work item from its thread: source id `slack:<team id>:<channel id>:<thread ts>` (the message `ts` for a top-level mention), title the first line of the text, link `https://slack.com/archives/<channel>/p<ts>`. Slack sends a `message` and an `app_mention` event (two event ids) for one mention: only `app_mention` counts, and intake is idempotent on the source id. A mention whose text after the bot is a command (`@bot /approve`, or in an item's thread `@bot approve`) is that command; `@bot /link <code>` links the Slack account (`@bot link <code>` in an item's thread); any other mention in a thread that already is an item is a plain comment. A reply in an item's thread without a mention is a command or a plain comment, through the same comment parser as GitHub and the one comment event mapping in core (`src/core/comment-event.ts`), which the command inbox reader also uses. A top-level message without a mention starts nothing, and a reply in a thread that is not an item is not stored.
  - Buttons: messages that end with the command footer get a button for each listed command that takes no text (`approve`, `retry`, `resolve`, `budget`, `help`, from the command table in `src/core/commands.ts`). A press is the same event as typing the command, as the presser. Every press and typed command goes through the controller's one `AuthProvider` check, as on GitHub.
  - Spec messages (design 05-sources, "Slack spec messages"): a spec comment waiting for approval (`## Factory spec`, its footer offering approve) is posted short by `renderSpecMessage` (`slack-format.ts`): "Needs your approval: <item title>", In short (at most 3 lines), Decisions (one line each, with its proposed default), and a **Full spec** link to `<base>/app/items/<id>` when `slack.dashboard_url` is an https URL, else a **View** button (`sf_view`) as the first section's accessory (see View below). Problem, Applied defaults, Done when, scope, Files and Risk are not posted (they stay in the store and on the dashboard). Every section is at most 3000 characters; a longer one is cut with the cut note naming `factory task show <id>`. The message and its buttons are egress-scanned as one. Buttons: **Approve with defaults** (`sf_spec_approve`), **Other…** (`sf_spec_other`, only when there is a decision) and **Reject…** (`sf_spec_reject`). Approve with defaults stores the typed `/approve`'s row as the linked user, keyed `cli:slack-<team>-<user>-<action ts>`, and posts nothing. Other… opens the modal "Answer the decisions" (submit "Approve"): one optional field per decision, up to 99 (Slack's modal limit; the rest are answered with a typed `/approve`), labelled with the decision and prefilled with its proposed default; its submit (`view_submission`) stores one `/approve` with an `N: <answer>` line per non-blank field. Reject… opens "Reject spec" (submit "Reject") with one reason field; its submit stores one `/reject <reason>`. A submit runs through the same `runLocalCli` path as the typed command, keyed `cli:slack-view-<view id>`, so a repeated submit stores nothing more. A modal opens with `views.open` (bot token, no new scope) from the press itself, before the envelope is acked, after its text is egress-scanned (a blocked modal is not opened; the thread gets the withheld notice); a failed `views.open` is logged once, not retried, and stores nothing. An unlinked presser or submitter gets the one refusal and no modal; a press or submit once the spec no longer waits gets the stale reply. The spec message keeps its buttons after approval. A spec approved with no reply is posted whole, as before. No status message is posted for needs approval alone: with no status message in the thread yet, nothing is posted; a later status posts or edits the one status message.
  - View (design 05-sources, "Slack: items are viewed in Slack"; `src/impl/source/slack-modals.ts`): with no https `slack.dashboard_url`, a waiting spec message and each owner notice line carry a **View** button (value the item ID). A press by a linked account, in a listed channel or in `slack.notify_channel` (also when it is not listed), reads the store and opens one read-only modal with `views.open` (callback `sf_item`, private_metadata the item ID): the title, the state, the one-line reason it needs the owner, and the waiting spec or else the latest factory message as mrkdwn, its footer dropped; at most 45 sections of at most 3000 characters, a cut body ending with the note naming `factory task show <id>`. Buttons that apply now: **Approve** (`sf_spec_approve`), **Other…** (with a decision) and **Reject…** for a waiting spec, **Merge** (`sf_merge`) for an item waiting for a human merge. The modal is egress-scanned whole before `views.open`; a withheld one shows the withheld notice. An unlinked presser gets no modal and the press makes no other Slack call. A press inside the modal runs the thread button's path (link, state and stale checks, the same command row keyed on the press; Merge stores `merge`); Other… and Reject… open their modal with `views.push` (its private_metadata the Slack thread's source ID, or the item ID for another item). An item from a Slack thread gets its answer in the thread; any other item's command posts nothing in Slack, the controller answers in the item's own thread, and the item modal is replaced with `views.update` by one line, the result or the refusal. `views.update` and `views.push` use the bot token and need no new scope.
  - Proposal buttons (issue #584; design 04-gate-commands): the reply to a plain-language message that proposes commands is stored first, one pending `controller_command_proposals` row per command, and ends with a hidden marker naming its proposal ID and commands. From that marker `renderComment` builds, with the button builder in `slack-format.ts` (`proposalButtons`), one button per proposed command (`sf_proposal:<index>`, value `<proposal id>:<index>`), then **Confirm all** (`sf_proposal_all`) and **Cancel** (`sf_proposal_cancel`), both valued `<proposal id>`. A value carries only the proposal ID and index; the command and its args are read from the store when the press is applied. A press runs as the presser's linked factory user (`slack-commands.ts`, `runProposalPress`): an unlinked presser gets the same one refusal in the thread as a typed command, and nothing is stored. Confirm (one, or all in index order) stores one `proposal_confirm` command row keyed on the press; the controller claims each pending row once (a second confirm applies nothing and gets one reply saying it was already applied), applies it through the typed command's path and `AuthProvider` check, and a refusal at that time (the item moved on, or the presser lacks the permission) marks the row refused and gets one reply saying why, without stopping the others. Cancel marks the pending rows cancelled, stores no command and applies nothing. A reply with no stored proposal (a question) and every GitHub reply stay plain text with no buttons; the typed line works everywhere. The old Confirm and Cancel action IDs (`sf_confirm`, `sf_cancel`) are no longer drawn; a press on a message posted before them is still read as before.
  - People are Slack user IDs (provider `slack`, subject `U…`); no display name is read, stored or logged. A Slack user is a factory user only through a link: `factory link-code <user_id>`, then `@bot /link <code>` in a listed channel; the linked user's stored role decides, through the local auth plugin (design 08-permissions). An unlinked account's command is refused with one reply in the thread; an unlinked mention gets one reply saying the thread was not taken in.
  - Commands (issue #498; design 05-sources, "One command table"): the factory's commands come from the one command table, `src/core/command-table.ts`, which the CLI and the dashboard read too. In Slack, after a mention:
    - `list`, `show <id>`: reply with the text `factory task list` and `factory task show <id>` print for the same store, in a code block, in a channel or a thread.
    - `approve [notes]`, `retry [text]`, `revise <feedback>`, `reject <reason>`, `resolve [notes]` and `merge`, in an item's thread: the CLI's command row is stored (`src/impl/source/slack-commands.ts` runs the CLI's `runLocalCli`), with the linked factory user ID as actor and key `cli:slack-<event id>`, and nothing is posted; the controller applies it and answers in the thread (a role refusal is the CLI's text, once). `/approve` where approve does not apply is refused before anything is stored, with the controller's own text (`approveRefusal`, issue #528). Outside an item's thread, the slash form gets one reply naming where they work, in the form without the slash. The buttons take the same path.
    - No slash after a mention in an item's thread (issue #541): `@software-factory revise <feedback>` is `@software-factory /revise <feedback>`, and so for `approve`, `retry`, `reject`, `resolve`, `budget`, `verdict`, `standing` and `link` (`withSlash` with `THREAD_BARE_COMMANDS` in `src/core/commands.ts`); `merge` and `help` are bare anyway. The slash form after a mention still works (a leading `/` with no mention is Slack's own). Outside an item's thread a bare command word is a request in plain words. A reply in an item's thread with no mention still needs the slash.
    - `users list`, `settings list`, `settings history`: the CLI's reads. `users add|remove`, `settings set|reset` and `mode`: one reply saying Slack writes wait for edge passports (#479); nothing is written.
    - `help` or `/help`, in a channel or a thread, answered in the mention's thread: only the commands the sender may run there, by the linked user's stored role (`chatHelpReply`). Outside an item's thread: the reads, the request that starts work and `/link <code>`. In an item's thread: the reads and the commands that apply now, each in the same words as the GitHub `/help` reply for that state but without the slash (`chatForm`); its header shows the `@software-factory help` form. The hint under a factory message names `approve`, `revise <feedback>` and `help` after the mention, with no slash. An unlinked account gets one reply saying it is not linked; only `/link` and `help` are answered for it.
    - Any other words after a mention are a request in plain words: outside an item's thread a new work item (as `task create`), in an item's thread a suggested command.
    - No Slack call is made before a command is stored; a failing Slack API delays only the replies. A reply longer than the renderer's limits (3000 characters a section, 45 sections) is cut, ending with a note that names the CLI command printing the whole text and, for `show <id>`, links the item's source. The full list: SET_UP.md, Slack.
  - Reactions (issue #524): a `reaction_added` event (scope `reactions:read`) with a 👍 or 👎 (`+1`/`thumbsup`, `-1`/`thumbsdown`, any skin tone) by a person, in a configured channel, on a message the factory posted in a work item's thread, within 7 days of the message (its ts against the event's `event_ts`), is one `verdict_submitted` event with `reaction`, target `{ kind: "issue", source }` (the thread) and comment id `reaction:slack:<channel>:<message ts>:<user>:<+1|-1>`. The message is found by its ts in the store's posted-message records (`listPostedCommentsById`), which name its thread. The status message, a message with no record, a thread that is no work item, the bot's own reactions and any other emoji give no event. An app installed without the scope gets no such event; nothing else changes.
  - Dedupe keys: `event:<event_id>`, or `action:<team>:<user>:<action_ts>` for a button press, so a redelivery after a reconnect is one inbox row.
  - Out: `postComment` turns the Markdown into Slack mrkdwn (markers dropped, `PR #N` linked to GitHub, a folded `<details>` block shown as its summary in bold, since Slack has no folding), egress-scans the whole message with its buttons, and posts it in the thread with the marker's hash in Slack message metadata. It checks the store's posted-message record (`getPostedComment`) first: a recorded marker returns its stored link with no Slack call. Only a marker with no record reads the thread once, to find a message posted before the records. Each posted message is recorded (`recordPostedComment`: the message ts as the comment ID, the Slack link as the URL), so a marker is posted at most once and outbound's record check finds it too. A message the scanner blocks is never posted in any form: the thread gets one notice naming the rules, under the same marker, so it is not tried again; the notice is never recorded. `setStatus` keeps one status message per thread, its ts recorded under the marker `slack:status`, edited in place with `chat.update` and no thread read (the thread is read only when there is no record); a deleted status message (`message_not_found`) is replaced by a new one, recorded under `slack:status:after:<deleted ts>`; with a link to the PR once the item has one (built from the item's `change_ref`: text `PR #<n>`, URL `https://github.com/<owner>/<name>/pull/<n>`); a PR's own status goes to the forge. `markSeen` adds 👀 to a typed command's message (`reactions:write`); `closeIssue` does nothing (a thread cannot close: the controller's reject or close comment says it).
  - PRs and code live on the forge: implement, review and the human gate run as for an issue, and the merge closes the item through the forge's `change_merged`. `slack` may run alone or next to other sources (issue #273); without a forge no PR is read, so a factory PR never closes its item.
  - Enable: add `"slack": { "channels": ["C0123456789"] }` to factory.config.json and list it next to GitHub: `"source": ["github-issues", "local", "slack"]`. One-time Slack app setup: SET_UP.md, Slack.
  - Secrets: `SLACK_APP_TOKEN` (app-level token, `connections:write`: opens the Socket Mode connection) and `SLACK_BOT_TOKEN` (bot token: reads threads and posts in them). Read only inside `src/impl/source/slack-api.ts`, at the point of use. Settings: `slack.channels`, a non-empty list of channel IDs (`C…` or `G…`), checked at load: an unknown key in the block, a channel name instead of an ID, or a missing block while `slack` is selected fails startup. `slack.dashboard_url` (optional): an https URL, the base of a spec message's Full spec link and the notice title links; a value that is not one fails at load, naming the key. Without it no dashboard link is posted: a View button opens the item in a Slack modal instead (never a link to the local dashboard, which a phone cannot open). A format check only: the bot has no `channels:read`.
  - Owner notices (`notifyOwner`, `src/impl/source/slack-notify.ts`, design 12-notification-channels): with `"notify_channels": ["slack"]` set (`factory settings set notify_channels '["slack"]'`), the notices of one 60 s tick are posted as one top-level `chat.postMessage` in `slack.notify_channel` (a channel ID, checked at load like `slack.channels`; default the first of `slack.channels`), one line each:
    - `✅ Finished: <title> (merged)`: a close_reason of `completed` reads `merged`, `rejected` reads `rejected`, and `wont_do`, `duplicate` or `failed` read `dropped`.
    - `🙋 Needs you: <title>: <one-line reason>` (`spec to approve`, `ready to merge`, `a run failed` or `waiting on you`), followed by `(thread)` linking the item's Slack thread when it came from one.
    - `🌙 N updates during quiet hours`, linking `<dashboard>/app/`: the summary of what quiet hours held.
    The title is the main text, escaped. With an https `slack.dashboard_url` it links to `<dashboard_url>/app/items/<id>` (the summary to `<dashboard_url>/app/`) and the message is that text; without one the title stays plain text and each line is its own section with a **View** button (none on the summary), past Slack's 50 blocks the remaining lines sharing one last section with no button. No display name and no ID is shown as text. At most one message per 60 s; a backlog after an outage goes out as one message per batch. The bot posts with its existing `chat:write` scope, so it must be a member of the notices channel.
  - Switch back: drop `"slack"` from `plugins.source` (the `slack` block may stay; nothing reads it). Slack items keep their state; their replies log `no source adapter for the item's source type; skipped`.

Other sources may implement `setStatus` as a no-op.

**Several sources.** `plugins.source` takes one name or a list of names:

- `"source": "github-issues"` and `"source": ["github-issues"]` select the same thing as always.
- `"source": ["github-issues", "<other>"]` runs both. The factory builds one adapter per name. Each poll source has its own cursor (`intake:<source type>`) and each stream source its own listener and inbox cursor (`inbox:<source type>`). Each source's intake step runs on its own, so a source that fails (a poll that throws) does not stop the others in the same tick; its cursor simply does not move.
- `"source": []` selects no source (issue #282): the controller starts and runs on the store alone, with local items and commands from the command inbox. A local-only setup is better written `["local"]`; GitHub (`github-issues`) is the sync plugin. (`plugins.runner` and `plugins.llm` still fail on an empty list.)
- Fails at startup, naming `plugins.source`: an unknown name, the same name twice, or two entries that build the same source type. Any other set is accepted, one non-GitHub source alone included, and several with none of type `github_issue` (issue #273): PR events come from the forge, not from a source.
- **Per-item routing.** The controller sends each item's `postComment`, `markSeen`, `setStatus` and `closeIssue` to the adapter whose `type` matches the item's source type, so replies go back where the item came from. A command's reply goes to the source the command came from.
- **PRs live on the forge.** `setStatus` for a PR goes to the forge (`setPrStatus`), and a PR comment is an outbox row whose target is the forge's PR ref, posted with `postPrComment`, whatever the item's own source. With no forge, both go to the item's own source.
- An item whose source type is no longer listed keeps its state: its 👀, status and close calls log the warning `no source adapter for the item's source type; skipped` and do nothing, and its thread entries stay pending in the outbox until a process with the adapter delivers them. `local` items are the exception: they need no adapter.
- Commands (`/approve`, `/revise`, `/help`, unknown commands, plain comments) from any source run the same command table, the same `AuthProvider` permission check and the same replies.
- Secrets: the union of what every listed source declares.

**Writing a stream source plugin.** Implement `StreamSource` (`src/interfaces/source-adapter.ts`) with `readonly intake = "stream"` and a `type` from `SourceType`:

- `subscribe(signal)` opens **one** connection and yields a `PushedEvent` per event: the `SourceEvent`, a `dedupe_key` that is unique within the source and the same on every redelivery of that event (e.g. Slack's `envelope_id`, or better the event id), and `ack()`. The iterable completes when the connection ends and throws when it fails. Stop and complete once `signal` aborts. Do not reconnect inside `subscribe`: the listener does that, with backoff, by calling it again.
- `ack()` tells the source the event is safe. The listener calls it only after the event is committed to the store inbox, so do not ack on receipt. An event that was never acked must come back on a later connection; that is what makes a crash lose nothing.
- Do not keep state another replica would need. Only the replica holding the source's listener lease calls `subscribe`; every replica's controller handles the events from the inbox, through the same `handleEvent` as polled events, so the source's `postComment`, `markSeen` and `setStatus` are called from whichever replica handles the event.
- Credentials (e.g. a Socket Mode app token) are read by the plugin from the `SecretStore` passed in its factory context, as `slack` does, never put in events or logs (`github-issues` gets only the shared GitHub client, never the credentials).
- Register it with a `*.plugin.ts` descriptor beside it (kind `source`) and its section here, as for any plugin. Settings: `lease_ms` and `heartbeat_ms` (the listener lease reuses them), `inbox_retention_days` (optional, default 14, a positive integer or startup fails: inbox rows older than this that every reader has passed are deleted).

`fake-stream` (`FakeStreamSource`, source type `slack_thread`) is **test-only**: it lives in `tests/helpers/fakes.ts`, is added with `withPlugin` through `fakeStreamRegistry()` in tests only, and is not in `REGISTRY`, so config cannot select it.

`fake-slack-poll` (`FakeSlackPollSource`, a poll source of type `slack_thread`) is **test-only** in the same way, through `fakeSlackPollRegistry()`; tests use it as the second source next to GitHub.

Switch back / disable: `"source": "github-issues"` (or drop the other names from the list). `"source": []` runs with no source; messages for non-local items then wait in the outbox.

## History

- **Slack dashboard links on 127.0.0.1** (changed 2026-11-12, design 05-sources). Before: with no `slack.dashboard_url`, the Full spec link and the notice title links went to the local dashboard `http://127.0.0.1:<ui.port>`, which a phone cannot open; now they are View buttons that open the item in a Slack modal.
- **PR fields are `change_ref`** (changed 2026-11-08, phase 3 of the change fields). Before: `revise_requested` and `resolve_requested` named their PR as `pr: { pr_number, head_branch }`, a `/verdict` PR target had `pr_number`, and `setStatus` took `pr_number` (a number or null); all are now `change_ref`, a string. Queued command rows that still hold `args.pr.pr_number` are read as before (removal plan: design 02).
- **`notifyOwner`** (added 2026-11-12, design 12-notification-channels). Before: no source got the owner's notices; they were stored for the desktop shell only.
- **`fileIssue`** (added 2026-11-08, issue #308). Before: a source could file only the sub-issues of a split parent (`fileSubIssue`), never a standalone item.
- **`github-issues` comments in the store** (changed 2026-11-07, issue #284). Before: the poll returned every comment command as an event the controller handled at once, and wrote nothing to the item thread or the command inbox.
- **PRs move to the forge** (changed 2026-11-07, issue #273). Before: `github-issues` read every PR event (closed, merged, open, unmergeable, "Request changes" reviews) and offered `prChecks`, `prFiles`, `labelAddedBy`, `commitAuthor` and `closePr`; the controller sent PR status to the `github_issue` adapter, refused several sources without one at startup, and kept refusals silent by checking the source type.
- **Empty list and outbox** (changed 2026-11-07, issue #282). Before: an empty `plugins.source` failed at startup, the controller called `postComment` directly from each decision, and CLI commands were read by the `local` source's `poll`.
- **Several sources** (changed 2026-11-01). Before: `plugins.source` took one name and every comment, 👀, status and close went through that one adapter.
- **`local` files sub-tasks** (changed 2026-11-07). Before: `LocalSource` had no `fileSubIssue`, so `/approve` on a split spec of a local task was refused.
- **`local` tables** (changed 2026-11-07, issue #281). Before: `poll` and `postComment` read and wrote migration 21's local-only command and message tables; now they use `inbound_commands` and `controller_item_thread` through the same store methods.
- **First start of a poll source** (changed 2026-11-07, issue #341). Before: a null cursor meant "read the first page of closed PRs", so `github-issues` read the merger of every merged PR on that page and the controller flagged each as an unreviewed merge.
- **`github-issues` setStatus and postComment** (changed 2026-11-07). Before: `setStatus` read the labels on every call and `postComment` listed the whole thread on every call, and a failing post was tried again on every tick; now both check records in the store first, and a failing post backs off.
