# AgentRunner

What it does: runs one tool-using agent loop in a sandbox and returns its structured output and transcript. A runner reports a usage or rate limit as `status: "rate_limited"` (with `reset_at` if it knows it), never as a plain failure, so the factory pauses instead of spending an attempt.

Plugins:

- `claude-code`: `ClaudeCodeRunner` (`claude -p`), with a per-run HOME and a factory-owned `CLAUDE_CONFIG_DIR` under `<state_dir>/agents`, and the harness deny rules of architecture §5.
  - Enable: `"plugins": { "runner": "claude-code", ... }`.
  - Secrets: `CLAUDE_CODE_OAUTH_TOKEN` (or `ANTHROPIC_API_KEY`) from the `SecretStore`, passed to the harness only. Settings: `models` (a model name for each of `cheap`, `standard` and `strong`, all three required; shipped: `haiku`, `sonnet`, `opus`), `run_timeout_ms`; the `claude` CLI on `PATH`. Which class each run uses is `model_by` (design §4), not a plugin setting.
  - Granted tools (`exposes_tools`): a run with `tool_grants` gets one MCP server, `factory_tools`, a bridge that forwards each call over a private Unix socket to the worker process, which checks the grant and the lease, calls the broker and scans the result. Other runners refuse a run with grants.
  - Writes (design §5 Sandbox, 2026-11-07): `--tools` offers Write and Edit, but `--allowedTools` does not name them. The harness settings' `permissions.allow` holds one `Edit(//<root>/**)` rule per root: the run folder, each `writable_paths` entry (via `guardPolicy`) and the run's `TMPDIR` (`<homes>/<run_id>/tmp`); Claude Code's Edit rules cover Write too. In `-p` mode any other path is refused, the live checkout included. This is a permission check in the harness, not OS-level. Bash writes are limited at OS level by Claude Code's sandbox (the working directory, its temp folder and `sandbox.filesystem.allowWrite`). Not covered: a symlink inside the run folder that points out of it, if the harness matches the link's path; the worker's live-checkout report catches a file that lands there. `tests/claude-runner-tools.test.ts` pins the rules.
  - Sandbox network: `sandbox.network.allowLocalBinding: true`, so tests that start a local server (`listen 127.0.0.1`) pass inside the run; before, they failed with `listen EPERM` and agents finished without a green run. Only localhost: no `sandbox.network.allowedDomains` entry is set, so `registry.npmjs.org` and every other host stay denied (in `-p` mode nobody can approve one). Dependencies are installed by the factory before the run (`repo.install_command`); the prompts tell agents not to run `npm install`, `npm ci` or `npx` for a missing package, and to run tests through `npm test` (`npm test -- <file>` for one file) so vitest gets `--configLoader runner` (`docs/plugins/sandbox.md`). The harness env sets `npm_config_update_notifier=false`: npm's own update check otherwise asks the registry on every `npm` and `npx` call, which the sandbox denies and reports in every tool result. `tests/claude-runner-tools.test.ts` pins the network block. (An old test-database URL file in the state dir stays in `deny_paths`, because it can still hold a login on the owner's machine.)
  - Toolchain (design 05-sandbox.md, issue #334): only when `factory.config.json` has a `toolchain` block, whose `caches` reach the run as `AgentRunSpec.readable_paths` and its `env` as `toolchain_env`. The harness settings then add the caches to `sandbox.filesystem.allowRead` (the OS read allow list) and to `sandbox.filesystem.denyWrite`, and one `Edit(//<cache>/**)` rule to `permissions.deny`; never to `allowWrite` or `permissions.allow`. A cache overlapping a `deny_paths` entry is left out (startup already refuses it), so `allowRead` never reopens a denied folder. The agent env (`buildAgentEnv`) gets the per-run toolchain homes in its TMPDIR (`npm_config_cache`, `CARGO_HOME`, `PIP_CACHE_DIR`, `GRADLE_USER_HOME` at `<homes>/<run_id>/tmp/toolchain/<name>`), then the `toolchain.env` entries (keys checked again, G1); the runner's fixed entries always win. No block: the settings and env are exactly as before (`tests/guards.test.ts`, `tests/toolchain.test.ts`).
  - Gate hooks (design 04-pre-push-gates.md, issue #302): for a step whose spec has `gate_hooks` (the worker gives them to the implement main and fix steps only), the runner writes `<CLAUDE_CONFIG_DIR>/gate-hooks/<run id>/` (mode 0700: `hook.mjs`, `spec.json`, `blocks.jsonl`; no env and no secret value), opens a private Unix socket for it, and adds a `hooks` block to `--settings`: `PreToolUse` on `Edit|Write` (30 s timeout) refuses a path outside `allowed_paths`; `Stop` (timeout `run_timeout_ms`) sends the agent back on no commits, a diff over `max_diff_lines`/`max_diff_files` or a failing check, at most `agent_stop_checks` times per run (default 3). The script sends only the tool name and the file path, never the file content. A hook error or timeout allows. The blocks come back as `AgentRunResult.gate_blocks`; the folder and socket are removed after the step. Every other step's arguments are unchanged (`tests/claude-runner-gates.test.ts`). Tests that run the real hook script need a Unix socket and skip where the host refuses one.
  - Tool hooks (`supports_tool_hooks: true`; design 04-pre-push-gates.md, issue #494): `GateHooks.on_tool_call` holds the enabled `on_tool_call` pack checks, bound to the run. On each Edit or Write the PreToolUse host runs them first, as argv through the sandbox with the tool name and the file path appended (never the file content), then the allowed_paths check. A refusal, a crash, a timeout or the 25 s budget running out refuses the edit with the check's reason, egress-scanned first (block `pack:<name>`). With any of them enabled, the spec file says `fail_closed` and the hook script refuses an edit it cannot get an answer for. A runner without the flag (`openai-compatible`, and a fallback chain for now) makes startup refuse an enabled `on_tool_call` check, naming the check and the point.
  - Rate limits: a Claude result with `api_error_status: 429` (usage or rate limit) is reported as the general `rate_limited` status, with `reset_at` when the message gives a reset time (an `|<epoch>` suffix, or `resets 12:10pm (Area/City)`). The worker then pauses every claim until that time, or for `retry_max_ms` when there is none (design §5 Restarts). All Claude CLI text parsing stays in this runner.

- `openai-compatible`: `OpenAICompatibleRunner`, its own chat-completions tool loop against any OpenAI-style endpoint, through the shared client in `src/impl/openai/` (no vendor SDK, no harness). Not a default: chosen by name only.
  - Enable: `"plugins": { "runner": "openai-compatible", ... }` and the `openai_compatible` block, the same one the `openai-compatible` LLM uses: `"openai_compatible": { "base_url": "https://api.example.com/v1", "models": { "cheap": "...", "standard": "...", "strong": "..." } }` (plain http only for localhost). The run's model class picks the model name.
  - Secrets: `OPENAI_COMPATIBLE_API_KEY` from the `SecretStore`, read by the runner once per run and passed only to the chat client as a Bearer token. It is scrubbed from the prompt, every request body, the transcript and every tool result, and never reaches a tool's environment.
  - Tools: the request lists exactly `spec.tools`, by name, in spec order. Each call runs through the shared tool (`ToolSpec.run` with `guardPolicy`, `readable_paths` included: Read, Glob and Grep may read a declared toolchain cache, Write and Edit never write one), so a Read of a `.env` file or outside the workdir, or a Write or Edit outside the workdir and `writable_paths` (the live checkout included) or under `deny_paths`, comes back to the model as a refusal naming the path, and the run goes on. This is a tool check, not OS-level. A tool the spec does not offer is refused the same way.
  - Bash: offered when the spec offers it, but every call is refused before it runs. Bash is not path-checked and no sandbox denies reads at OS level yet (`noop` only), so a shell could read the secret file or the G6 canary. Implement and review runs therefore work without a shell (no `npm test` by the agent; the worker's own checks still run).
  - Granted tools: none (`exposes_tools` false). A run with `tool_grants` fails with `toolsNotExposedMessage` and makes no model call.
  - Limits and results: at most 25 tool rounds; a model still asking for tools after that ends `failed` (`agent_failed`). `timeout_ms` ends the run `timed_out` and the caller's AbortSignal ends it `aborted`; both cancel the in-flight request. HTTP 429 is `rate_limited`, with `reset_at` from Retry-After when it gives one; any other error is `failed`. No request is retried. A final answer that is not JSON (one surrounding code fence is allowed) or does not match `output_schema` is returned `completed` with no output, so the worker records `invalid_output`. `usage` sums input and output tokens over every call, `usage.model` is the model the response reports, `cost_usd` is null. No stall detection (`stall_ms` is ignored).
  - Switch back: `"runner": "claude-code"` (the default).

Fallback chain (design 2026-11-07, `docs/design/08-plugins.md`): list several runners, tried in order.

- Enable: `"plugins": { "runner": ["claude-code", "openai-compatible"], ... }` (Claude first, the OpenAI-style endpoint second; add more names to extend it). Every member needs its own settings and secrets as above (here the `openai_compatible` block and `OPENAI_COMPATIBLE_API_KEY`); `npm run setup` asks for and `doctor` checks each member's.
- The next member takes a run only when the previous one did no work: a rate limit, or a stall or failure with no model output (a missing secret or config fails that way). A run that completed, timed out, was aborted, or failed after output is never retried on another member. A run with `tool_grants` skips members that cannot expose tools.
- The result names its member in `served_by`; usage is summed over the members tried, the transcript joins each member's behind a `----- runner fallback: <name> -----` line, and the worker logs `runner fallback` (`from`, `to`, `reason`). If every member fails, the error lists each failure; a rate limit from the last one keeps the earliest `reset_at`.
- Switch back: a single name again, e.g. `"runner": "claude-code"` (a list of one is the same).

Capabilities (design `08-settings.md`, 2026-11-13; before: see History): the Settings page lists each registered AgentRunner plugin as one entry, `runner:<plugin>`, one per configured endpoint, enabled when `plugins.runner` selects it (each chain member). A plugin with its own config block (`openai_compatible`) shows that endpoint's host and its model names; `claude-code` shows the `models` names. Each entry lists its model per class, the classes `model_by` names, so a run's class resolves to the model of the entry that serves it; how `model_by` resolves is unchanged. An entry's roles are the agent roles (`triage`, `implement`, `review`, `resolve`); its last use is the newest stored run of those whose reported model (`usage.model`) contains one of the entry's model names. Granted tools now follow the runtime `tool_grants` setting at the next run that starts (`docs/plugins/tool-broker.md`).

A new runner reuses the shared tools in `src/core/tools` (`Read`, `Glob`, `Grep`, `Write`, `Edit`, `Bash` as `ToolSpec`s, with `guardPolicy`) instead of implementing its own file tools and deny rules, so it gets the file guards for free (architecture §5). `tests/helpers/scripted-runner.ts` is a test-only example, selected only with `withPlugin(REGISTRY, "runner", ...)` in tests and never in the registry.

Switch back / disable: `"runner": "claude-code"`. There is no "off".

## History

- **Current text names SQLite only** (decision changed 2026-11-11, issue #567). Before: the network paragraph named the file `<state_dir>/test-mysql.url`, which stays in `deny_paths` after the test database was removed on 2026-11-13 (issue #579), because it can still hold a MySQL login on the owner's machine.
- **Capabilities entries** (2026-11-13, issue #572). Before: the runners were visible only in `plugins.runner` of factory.config.json, with no page showing which are on, which models they serve or when one was last used; `AgentRunSpec.tool_grants` came from the file's `tool_grants` only.
- **Tool hooks** (2026-11-11, issue #494). Before: the PreToolUse hook checked only `allowed_paths` and failed open; no runner declared tool-hook support, and no pack check ran on an edit.
- **Toolchain** (2026-11-08, issue #334). Before: the harness settings had no read allow list and the agent env no config-declared entry, so a run could not read a home-level toolchain cache.
- **Writes** (2026-11-07). Before: `--allowedTools` named Write and Edit bare, so the native tools could write any path the host user can, the owner's live checkout included; only `.env` edits were denied.
- **Gate hooks** (2026-11-07, issue #302). Before: `--settings` held permission and sandbox rules only, no hooks, so the implementer learned of a gate failure only from the failed run.
- **Sandbox network** (2026-11-07). Before: the harness settings had no `sandbox.network` block, so sandboxed commands could not bind or connect on localhost, and every test that starts a local server failed inside the run.
- **Fallback chain** (2026-11-07). Before: `plugins.runner` took one name only.
- **Runners** (2026-11-07, issue #194): added `openai-compatible`, with Bash refused per call. Before: `claude-code` was the only runner.
- **Granted tools** (2026-11-07, issue #164). Before: the runner threw on any run with grants.
