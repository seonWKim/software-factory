# 5. Coordination: GitHub sync and adopted pull requests

- **A PR merged on the forge fast-forwards the local base** (decision changed 2026-11-25; current; replaces "only a later local merge's base push brought origin's base into the local one", see History). When the controller pushes a base (05-sources.md, Base push) and its sandbox has `pullBase`, a merged PR (a delivered `merge_pr`, or a polled `change_merged`, merged by the factory or on GitHub) stores one `pull_base` action, keyed `pull_base:<base>:<merge sha>`, on the base push's destination `git:<host id>:<base>:push`. Outbound's `local` target fetches only origin's base and, when local `<base>` is its ancestor, moves local `<base>` to it with one conditional ref update (a clean checkout of the base follows, as after a local merge). A local base ahead of origin or diverged from it moves nothing: its pending base push merges the two. A failed fetch or a base that moved meanwhile is retried by outbound. So a local merge checked on the old base finds its base moved at landing and is checked again on origin's, where a conflict starts its own resolve instead of a reconcile of main. Why: on 2026-11-25 PR merges left local main behind origin three times; once a local merge landed on the stale base and its push conflicted (wi_03aa6a45).
- **A local item's conflict starts the automatic resolve also with a forge selected** (decision changed 2026-11-12; current; replaces "with a forge selected, a local item is not merge-checked and `factory merge` on a conflict only refuses", see History). The local item rule: **a local item's branch and its base are always the factory repo's local refs, also when GitHub is selected.** The controller's sandbox fetches origin for PRs, so for a local item (source `local`, no PR) it reads the local base and branch with `localBranch` (no fetch); the merge check and `factory merge` key the automatic resolve on the local base's commit, and the resolve run takes the local route (`routeFor`: the local sandbox and the local broker), so its merge commit lands on the local branch only and nothing is pushed to origin; the base push after the local merge is unchanged. Details in 05-merge-conflict.md.
- **The local merge can run in auto mode** (decision changed 2026-11-08, issue #444; before: "never automatic: only a human's command calls it", see History). With the `mode` setting at `auto` (design 03-risk), the controller's auto-merge step, after the runs of each tick, merges a local item waiting in `merge_pending` through the same `Controller.mergeLocal` (no second path): actor `system:auto`, no person to authorize, the mode change's audit seq on the `local_merged` state change, the merge check on the merge commit first and the conditional base move as for `factory merge`. It merges only below tier 4, off the gate list, complete, and at most at `auto_merge_max_tier`; a refused or failed try is posted once per item version and the item keeps waiting for `factory merge`. After a merge the checks run again on the new base tip (red main stops auto mode). A GitHub item is never merged in auto mode: there is no forge merge to call, so it waits as in manual mode. Manual mode (the default) is unchanged.

- **One GitHub client per process.** The decision that changed: **the selected `github_auth` plugin builds the credentials and the one GitHub client over them, and every plugin and command gets that client through `Plugins`** (2026-11-08). The `token` and `app` plugins return a `GitHubAccess` (`credentials` plus `api`, src/interfaces/github-credentials.ts); `Plugins.githubAccess()` in src/compose.ts builds it once per `Plugins`, so one `build()` (and one CLI command) holds one client, its ETag cache and its call budget. `build()` hands `api` to the source, auth, grant and forge contexts and the credentials only to the broker (its `git push`); the CLI commands (`settings --project`, `migrate`, `golden add` under `src/cli/handlers/`) and `setup.ts` (doctor, setup) call `Plugins.githubApi()` and construct no client. `new GitHubClient` appears only in `token-credentials.ts` and `app-credentials.ts`. `src/plugin-api.ts` imports nothing from src/impl/github/: contexts hold the `GitHubApi` interface and `{ owner, name }`. The GitHub descriptors import their implementation inside `create()`, so discovering them loads no implementation; the `token` and `app` descriptors name `GITHUB_TOKEN` and `GITHUB_APP_ID` themselves with `secretName()`, and so sit under their own tier-4 floors (factory.config.json; floors, not exemptions, in tests/credential-floors.test.ts). The `github-issues` labels move from `setup.ts` into that plugin's `setup()` hook (docs/plugins/selection.md). With no GitHub plugin selected (Local startup) the stand-ins stay: no credential is read and doctor makes no GitHub check. Solo default (`token`) and enterprise setting (`app`, its key still read only when a token is minted) take the same path.
- **The local store is the home of the conversation.** The decision that changed: **GitHub comments and commands are written to the store, and the controller applies GitHub commands from the command inbox** (2026-11-07, issue #284). Before, each new GitHub comment was an event the controller handled at once, and nothing in the store recorded a GitHub conversation. Now the `github-issues` poll writes, through the existing store methods (no migration, no schema change): each new command once to the command inbox (`inbound_commands`), key `github:<comment id>`, actor `github:<numeric user id>` (never the login), `command` the word after `/`, `args.text` the text after it, `args.source` the issue (or PR) it was written on; and each new comment by a person on an issue (command or plain) once to its work item's thread (`controller_item_thread`), marker `github:<comment id>`, body the comment, with no outbox row (it is already on GitHub). A command on a PR's conversation (`/revise`, `/resolve`, `/verdict`) carries in `args.pr` the PR number and head branch the poll already read, and its thread entry goes to that PR's item (a factory PR by its branch, an adopted one by its source), so applying it reads nothing more from GitHub; one the poll drops today (a `/revise` on a PR that is gone, a `/resolve` or `/verdict` on a PR that is not the factory's) writes nothing. Plain comments on a PR's conversation stay unwritten. One poll's comments are written in comment-id order, whatever order GitHub lists them in, so the command step applies them in the order they were written. Dedupe is the store's: a repeat poll, a second replica polling from an older cursor, or a restart writes no second row or entry (both are idempotent on the key). The poll cursor `intake:github_issue` keeps its format, and its `last_comment_id` still decides what is new, so a controller on this code started with a cursor the old code wrote applies no command at or below it (no backfill). The command step reads these rows with the CLI's (the one inbox, by `seq`): the reader (`src/core/command-inbox.ts`) gives provider `github`, subject the numeric id, only to a row with key `github:<digits>` and actor `github:<digits>` (rows written from the CLI or the UI keep provider `local`), rebuilds the comment through the one comment event mapping (`src/core/comment-event.ts`, so GitHub has no parser copy of its own) with the PR context added, and `comment_id` is the GitHub comment id, so the 👀 and refusal replies are keyed as before. The GitHub auth provider and today's grants judge it, never the local auth plugin. A GitHub row is applied only by a process with an adapter of its source type, and a failure is logged and passed like a polled event's, so a GitHub outage never holds the local commands after it. Plain comments are still also returned as events (`/link`, suggestions); they change no state. Pushed events (`pr_open`, `pr_merged`, `pr_closed`, `pr_unmergeable`, `pr_changes_requested`, `source_closed`, `base_commit`) and new-issue intake stay on the poll path. Factory messages still reach GitHub only through the outbox (Thread first, below); the 👀 reaction and the status labels stay direct calls (moving them into the outbox is a follow-up). Without a store the source returns each command as the event its row maps to. Solo default: no GitHub source listed, nothing here runs. Enterprise setting: `github-issues` next to `local` on a shared store, each comment written once, each command applied once by any replica, with no in-process state. Not built: backfilling older comments; a thread entry for a comment read in the same poll that takes in its issue (the item does not exist yet; its command is still written and applied); a replica without the `github-issues` adapter passes GitHub rows (the cursor is shared), so in a mixed deployment every replica that runs the command step should list it; Jira comments (Slack replies: see Slack replies on the item's thread).
- **PRs through the forge.** The decision that changed: **every PR event, PR fact, PR comment and PR status goes through the forge, never through a source** (2026-11-07, issue #273, phase 2 of #172). `Forge.poll(cursor)` returns the PR events (`pr_merged`, `pr_closed`, `pr_open`, `pr_unmergeable`, `pr_changes_requested`; they left `SourceEvent`) and the next cursor, kept under `forge:<ref type>` in the existing cursor table (no schema change, no migration). The controller polls it on the poll interval under its own guard, so a forge failure never stops a source's intake. Order within a tick: every poll source is read, then the forge is polled, then the forge's events are handled, then the sources' events: a merge that closed its issue happened before the close, so the forge's read already sees it and the merge (with its `merge_sha`) is applied before the issue's `source_closed`. The forge also answers `prChecks`, `prFiles`, `labelAddedBy`, `commitAuthor` and `closePr`, and writes `postPrComment` and `setPrStatus`: a PR comment is a thread entry whose outbox row targets the forge's PR ref, and the outbox step posts it through the forge whatever source the item came from; PR status goes to `setPrStatus`. With no forge, a PR comment or status goes to the item's own source, and no PR is read. The controller names no source type: `PR_SOURCE_TYPE` is gone, startup accepts any set of sources with no two of one type (one non-GitHub source alone, or several with none of type `github_issue`), and a refused intake stays silent when the source sets `silent_intake_refusal` (GitHub; chat sources reply). Which forge: `plugins.forge` left out follows the sources, `github` when `plugins.source` lists `github-issues`, else none (derived, not a setting); `"none"` next to `github-issues` fails startup, naming `plugins.forge`; an unknown name fails naming it too. Solo default: a local source alone, no forge, no GitHub call. Enterprise: `github-issues` with the `github` forge, by the same rule. With both GitHub plugins, the source reads issues, comments, closed issues and base commits and the forge every pull list and per-PR read: one tick makes the same GitHub calls as when the source read PRs itself, each once (no list is read twice, so nothing needs handing from one to the other). Upgrade: the forge's cursor starts empty; while it is, the forge's first cursor is the GitHub source's old one (`intake:github_issue`, whose PR fields have the same names), so no merge is missed and none applied twice (a boundary PR may repeat; handling is idempotent); a fresh install starts empty and reads one page of closed PRs. Details: [docs/plugins/forge.md](../plugins/forge.md). Not built: webhooks, a forge other than GitHub, adopted PRs with a forge but no `github-issues`: an adopted item's source is its PR, of type `github_issue`, so with no adapter of that type the controller makes no transition on it (No adapter, no transition).
- **GitHub sync records.** The decision that changed: **what the GitHub source posted and labelled is recorded in the store, shared by every replica** (2026-11-07, after every controller start re-read the labels of up to 1,000 open items and every post re-read its issue's thread). SQLite migration 27 adds two tables, keyed by the item's source id:
  - **Posted comments** (`outbound_deliveries`: source id, marker, comment ID, URL, body hash, failed attempts, next attempt time). `postComment` looks up the record first: a known marker returns its stored URL with no call. Only a marker the store does not know reads the thread, once (up to 10 pages, for a post from before this change), posts if the marker is not there, and stores the comment ID, URL and a SHA-256 of the body. A repeat post with a different body is not edited: the controller logs the warning `comment already posted with another body; not edited` and returns the stored URL (editing in place would be a follow-up).
  - **Comment backoff.** A failed post is counted on its row (conditional on the stored count, so two replicas count one failure once), and the next try waits 1 s, then 2 s, 4 s, doubling, at most 5 min; until then `postComment` throws without a call, on any replica, so the caller's retry on the next 2 s tick costs nothing. A post that goes through clears the count. It lives in the GitHub source, not the controller's generic post path, so other sources (the local one) keep retrying on the next tick as before and write nothing here.
  - **Label state** (`outbound_label_states`: source id, target `issue` or `pr:<n>`, the status last written, and the claim of a write in progress). Kept per target, so a current issue label does not hide a stale PR label. `setStatus` compares with the stored state first: the same status makes no call. A different one (or none stored, an item from before this change) is claimed in the store for 60 s, written through the existing read-then-write path, stored, and the claim ended; a failed write ends the claim and stores nothing. A claim another replica holds for the same status makes the call a no-op, so two controllers starting at once write each label once. The start-up status catch-up reads every open item's label states in one batched store read and skips targets already showing their status, so a restart with unchanged labels makes no label call. A label a person removed is not put back on restart (restoring it would be a follow-up).
  - Solo default: with no GitHub source nothing writes these tables and nothing waits on GitHub. Enterprise: the rows are shared through the store, so a second replica or a restarted controller continues the same records and backoff schedule. The forge's own `GitHubIssueSource` (no store) keeps the old behaviour. Agent-side comments through the GitHub tool broker keep their own `commentOnce` path.
- **GitHub call budget.** The decision that changed: **GitHub reads are conditional and budgeted** (2026-11-07, after the App installation hit its hourly limit). GitHub is a sync plugin; the factory keeps working in local mode without it, and when it is on it spends as few calls as it can:
  - **Conditional GETs.** The shared `GitHubClient` keeps the last ETag and body of each GET URL (per Accept header) in a bounded in-memory LRU (500 entries, bodies up to 1 MB), sends `If-None-Match`, and answers a 304 (not counted by GitHub) with the kept body. This is in-process state on purpose, and the one exception to "no in-process state": it is only an optimization. GitHub decides on every call whether the body is current, so a replica with an empty cache (a new process, another machine) gets the same answers, it just pays full calls. Writes are never conditional.
  - **Rate-limit budget.** Every response's `x-ratelimit-limit`, `-remaining` and `-reset` (core resource only) are kept and exposed as `budget()`. With none left before the reset the client refuses a call with the 403 GitHub would give, without sending it, so a retry loop does not hammer the API. Under `github.min_remaining` (default 200) `lowBudget()` is true until the reset and the optional reads wait: the per-PR `mergeable` reads, the "Request changes" review reads and the base-commit read in the poll (their cursors stay put), and `prChecks` (the gate counts as pending). The intake lists (open and closed issues, comments, closed and open PRs) always run. One log line on entering that mode, one on leaving.
  - **Shared budget (decision changed 2026-11-07, issue #340).** Factories on one App installation share one hourly budget, so each process also keeps to its **share**, `github.budget_share` (default 1.0: the whole limit, the solo case). The client counts this process's counted calls (every answer but a 304) in the current window, named by its reset time; once they reach `budget_share` × the limit, `lowBudget()` is true and the optional reads wait as under `min_remaining` (both are checked). A new reset time starts the count at zero. The count is in memory, per process: replicas of one factory on one App split its share; counting in the store is a follow-up only if needed. Enterprise: one App per factory with share 1.0 (recommended), or shares summing to at most 1.0 by a documented agreement, not enforced across factories (`docs/setup.md`).
  - **Budget shared through the store (decision changed 2026-11-08; before: every replica polled GitHub, budget per process; see History).** GitHub's own numbers are one row per project and forge plugin, `outbound_forge_budget` (`project_key`, `plugin`, `remaining`, `limit`, `reset_at`, `updated_at`; SQLite migration 40). The client writes it after every response that carries the core limit, and the store keeps a write only when its `updated_at` is newer than the stored one (an older or equal write changes nothing, so replicas writing out of order keep the latest reading). The client reads the row at most once per tick (`refresh_ms` = `tick_ms`): the controller asks for it before each tick's optional reads (`refresh_forge_budget`), and a call that finds the last read older than a tick reads it first. So when one replica's response drops it under `max(github.min_remaining, 10% of the limit)`, every replica's `lowBudget()` is true on its next tick and its optional reads wait until `reset_at`: the poll's base-commit and closed-issue catch-up reads, the status catch-up, check reads (`checksStep`) and dependency reads. The intake lists of the issue poll still run, as before, and the sync lease never waits on the budget (outbox delivery may wait up to `max_wait`, 30 s, under a low budget since RFC 0015 M7: 10-event-driven.md, "Writes to the outside world leave through outbound"). `github.min_remaining` is the only setting; the 10% share is fixed. The per-process `budget_share` count is unchanged. `src/compose.ts` gives the client the store and the project key once the key is resolved, in every process that calls GitHub (`factory dev`, `factory session`); with no GitHub plugin selected there is no client and no row. Solo default: one process reads back its own writes. Enterprise setting: replicas on one store share the row; one replica syncs (05-coordination, One GitHub sync per project).
  - **Audit of inbound commands.** A comment from GitHub is kept in its item's thread with `actor` `github:<numeric id>` (`item_thread.actor`, migration 40; absent on the factory's own messages and older entries), never a login. A command's actor is the factory user its account is linked to (`src/core/authorize.ts`, links first); an account that no link and no grant names is refused through the same permission path, its comment stays in the thread under `github:<numeric id>`, and no state changes. No audit table of its own.
  - **First-start spread.** A first start's catch-up reads (each closed factory issue's full read while the source has no closed cursor, the base-commit pages while it has no commit cursor) take `GitHubClient.takeCatchUp`: at most (`budget_share` × limit) / 60 a minute, derived, no setting. When the allowance is used, the closed cursor stops at the last issue read and is marked `closed_catch_up` until the backlog is read, so it is spread over several polls; the commit cursor stays empty and the next poll reads the commits.
  - **No calls left is a wait.** A call refused locally with no calls left carries the reset as `wait_until`. The controller's loop logs `waiting for the GitHub rate-limit reset` (warn, with the step and the time), not `loop step failed`; the step runs again next poll and every other step, local work included, goes on. After each poll the controller holding the sync lease stores its process's budget (limit, remaining, reset, share, counted calls, state `ok` / `low` / `waiting`, replica id) in the cursor `github:budget`, and the status page reads it from there (design §9). No claim pause is set: the `github_rate_limit` claim pause, once it exists, is the one pause for GitHub-bound work.
  - **Fewer reads per poll.** The closed-PR list stops at the first page that reaches the cursor instead of reading up to 5 pages every poll. `setStatus` reads the labels first and writes nothing when they are already right instead of always creating the label, adding it and reading the list; with a store it first compares the stored label state (GitHub sync records above).
  - Not here: a draining child stopping its controller (issue #294). Dependency re-reads in `coordinationStep` (issue #254) are now bounded in 05-coordination.md, "Dependency reads only when the source changed".
