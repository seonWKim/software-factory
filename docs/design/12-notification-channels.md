# 12. Notification channels

- **One owner, one list of channels for the owner's notices (new decision, 2026-11-12, owner request in Slack; current).** The decision that changed: a person picked their own channels, with a per-item override, stored by user ID (see History). The factory serves one owner (`docs/design/08-enterprise.md`), so that choice is one runtime setting, and what it carries is the owner's notices (design 09-notifications): an item that needs the owner, and an item that finished.
  - **The setting.** `notify_channels` (runtime, owner `controller`, global): a list of source plugin names, default `[]`, which sends nothing beyond the dashboard and the desktop shell. `factory settings set notify_channels '["slack"]'` turns Slack on. A value that is not a list of distinct non-empty strings is refused by the core's parser; a name that is no registered source plugin is refused at set time in `src/settings-cmd.ts`, where the plugin registry is read, and so also on the settings API, which runs the same command. The core reads no registry.
  - **A capability, not a source type.** A source adapter may declare `notifyOwner(notices)` (`src/interfaces/source-adapter.ts`, `SourceNotice`). The notifications unit gives a listed channel rows only when its adapter has the method; a listed adapter without it gets none. A channel name reaches the configured adapter whose type is the name, or the name and a suffix (`slack` → `slack_thread`): `src/controller/units/notifications/notifiers.ts` reads the configured sources once, when the unit is built, and hands the pure unit only (channel, adapter type) pairs, never an adapter, so the unit can call no source. Neither the core nor the unit names a source type. The method is `notifyOwner` rather than `notify` because the test helper `FakeStreamSource` already has a private `notify`.
  - **Fan-out through the outbox.** One `notify` row per (notice, channel), keyed on both, targeted at `<adapter type>:notify`, so each channel's notices wait in their own destination. `notify` retries with backoff (`RETRIED_ACTIONS`); a Slack outage holds only Slack's notices, never local work or another destination.
  - **One message per tick.** A `<type>:notify` destination takes a fixed 60 s window with no cap (`NOTIFY_BATCHING` in `src/outbound/aggregator/batching.ts`; `outbound.batching` does not change it). Outbound hands the undelivered rows of one batch to the target's `deliverBatch` in one call (at most 50 rows a call), which calls `notifyOwner` once: one message. A batch due within 60 s of the destination's last sent one waits for the window, so at most one message goes out per 60 s, and a backlog after an outage is one message per batch, never one per notice. A row recorded delivered is skipped on a retry, so it is posted once.
  - **Egress.** Before the call, outbound scans each row's title and reason. A flagged batch is withheld: nothing of it is posted, its rows are recorded `withheld` and not retried.
  - **Slack** (`src/impl/source/slack-notify.ts`): one top-level message in `slack.notify_channel` (a channel ID, default the first of `slack.channels`), one line each: `✅ Finished: <title> (merged|rejected|dropped)`, `🙋 Needs you: <title>: <one-line reason>` with a link to the item's Slack thread when it has one, and `🌙 N updates during quiet hours` for a summary (the owner's answer), linking `<dashboard>/app/`. With an https `slack.dashboard_url` each title links to `<dashboard_url>/app/items/<id>`; without one (decision changed 2026-11-12, design 05-sources "Slack: items are viewed in Slack"; it replaces the link to the local dashboard on `ui.port`, the approver's note, see History) the title is plain text and each line carries a View button that opens the item in a Slack modal, the summary line none. No display names; no ID as main text. Both keys are checked at load.
  - **Not part of this decision.** Per-item overrides and any dashboard control for the setting; `notifyOwner` for GitHub, local or another adapter; Slack reactions, threads or buttons other than View for notices; marking notices delivered in the store; the desktop shell's text for finished notices; notices for system actions.

## History

- **Notice titles linked the local dashboard** (until 2026-11-12). Before: with no `slack.dashboard_url`, each notice title linked `http://127.0.0.1:<ui.port>/app/items/<id>`, which a phone cannot open.
- **A person picks where they are notified** (decision 2026-11-11, work item wi_811f4a45; design only, never built). Replaced 2026-11-12 by one owner's `notify_channels`. It said: a message may go to one channel or several by a setting each person owns, with an optional per-item override; the choice stored in the store by user ID (an override also by work item ID), resolved as the item's override, else the requester's choice, else the item's own source; one outbox row per chosen channel, keyed on (thread entry, channel), delivered with backoff; vendor features as optional adapter capabilities the controller checks for, never a source type; local actions never waiting on a channel; on a shared store each person's choice limited by their linked accounts and grants, and an org able to restrict the allowed channels. Per-person choice, per-item overrides and grants are dropped: the factory has one owner.
