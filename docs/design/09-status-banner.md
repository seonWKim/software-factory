# 9. Status page: factory status banner

- **Factory status banner.** Both updaters write `<state_dir>/supervisor.json` through one writer (since 2026-11-07, #352) (`SupervisorStatus`: running, building, draining, restarting, build_failed, crashed or stopped; the running and target revision; the child pid; since when) on every change, atomically. `factory ui` reads it and shows a banner at the top: while draining, that new runs are paused until the old process's N in-flight runs finish (counted from the running runs whose lease owner carries that pid), that the new revision then starts with `workers` from the config, and that code and settings changes apply when it starts. A child pid that is no longer alive reads as stopped; no file reads as stopped. A child that exits on its own is `crashed`: before exiting on an error it sends the message it prints (e.g. "schema step pending: run `npm run migrate`") over IPC, the banner shows it, and a crash loop keeps the time of its first crash (since 2026-11-02). A drained child also handles finished runs once more before it exits, so the run the drain waited on is not left unhandled until the next process. The page stays read-only.
  - **In place (`updater: none`, since 2026-11-07, #352):** `dev` writes `running` before the controller and worker start (`child_pid` is the `dev` process, `rev` its HEAD or null) and `stopped` with `child_pid: null` once they return, also when they throw. No `supervisor_pid`, so `npm run migrate` treats it as no live supervisor, as before. Solo default: one file in the state dir, written by the one process. Enterprise: one file per state dir; two `dev` processes on one state dir overwrite each other (last writer wins), as with git-worktree.
  - **Migrations (since 2026-11-07, #165):** `migration_pending` names the pending steps and says whether the old revision still runs; `migration_draining` says new runs are paused for `npm run migrate`; `migration_ready` says the steps are being applied and the new revision starts when `migrate` finishes.

## History

- **Factory status banner** (new decision, 2026-11-01). Before: the page could not tell an update drain from idle workers, so with `workers: 10` and two runs going it looked like the setting was ignored.
- **Crash message on the banner** (2026-11-02). Before: a pending migration kept the factory down for 77 min with no sign outside the log.
- **Both updaters write the status file** (2026-11-07, #352). Before: only the git-worktree updater wrote it; under `updater: none` there was no file, so the banner said "Factory stopped. No runs start." above runs that were progressing.
