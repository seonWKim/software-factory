# 4. Agents: roles, models and the human gate

| Role | Reads | Writes | Model |
|---|---|---|---|
| Triage | Slack thread, issues, code (API, no clone) | its fields, `READY` / `CLOSED` | cheap; standard on a retry after an `agent_failed` attempt |
| Manager | `READY` queue | lease, assignment | none (code) |
| Implementer | work item + pointers + previous mistakes | code on its branch, TDD tests, handoff row per commit | standard at tier 1–2, strong at tier 3–5 |
| Reviewer | pass 1: work item + diff + CI results + `worked_on` (no transcript); pass 2: intent, how_to_test | verdict (tests run only to confirm a finding), cumulative mistakes, tier recheck | standard, different if measured to help |
| Resolver (`/resolve`) | conflicting files + work item + notes | the merge resolution | standard at tier 1–2, strong at tier 3–5 |

The model column is the shipped `model_by` table (below); a retry after a review loop, or a triage retry after an `agent_failed` attempt, goes one class up.

**Model class per run kind and tier.** There are three classes, `cheap`, `standard` and `strong`; `models` in `factory.config.json` maps each to a model name (shipped: `haiku`, `sonnet`, `opus`, CLI aliases, not pinned versions) and must list all three. `model_by` maps run kind and tier to a class: one entry per run kind (`triage`, `implement`, `review`, `resolve`), each either one class for every tier or an object with a class for each of tiers `"1"` to `"5"`, plus `retry_up` (default true). Shipped, and used when `model_by` is absent:

| Run kind | Tier 1 | Tier 2 | Tier 3 | Tier 4 | Tier 5 | Retry |
|---|---|---|---|---|---|---|
| triage | cheap | cheap | cheap | cheap | cheap | one class up after an `agent_failed` attempt |
| implement | standard | standard | strong | strong | strong | one class up after a review loop |
| review | standard | standard | standard | standard | standard | not moved |
| resolve | standard | standard | strong | strong | strong | one class up after a review loop |

**Triage retry after `agent_failed` (decision changed 2026-11-08, issue #457; before: triage was never moved up, see History).** A triage run goes one class up (`cheap` → `standard` by default) when `retry_up` is on and the latest finished attempt record of the item's triage runs (`listRunAttempts`) failed with `agent_failed` (for example `error_max_structured_output_retries`), so the same cheap model does not fail the same way again. A failed triage run is retried as a new run, so the item's earlier triage runs count, and this run's own earlier claims too. An attempt that ended any other way (`lease_expired`, a network or rate-limit pause, a stall, a timeout, `paused`, `succeeded`) is not `agent_failed`, so a restart retry that never reached the model is not bumped; a later successful triage resets it. Implement and resolve runs are not bumped after `agent_failed`. The worker reads the records; `modelClassFor` takes the result as one boolean.

A review-loop retry is an implement or resolve run for an item whose `loop_count` is 1 or more (review or failed checks sent it back); it goes one class up (`cheap` → `standard` → `strong`, `strong` stays) unless `retry_up` is false. Restart retries (`/retry`, backoff) do not move `loop_count` and are not bumped by it. An item with no tier yet takes its run kind's tier-5 entry. The merge-conflict steps inside an implement run use the implement run's class. Golden reviewer replays use the review class (tier-5 entry, no bump), so they match production review. `loadConfig` checks both keys at startup: an unknown run kind or tier key, a value that is not a class, a tier object missing a tier, or `models` without one of the three classes fails loading with the key or value named. The choice is one pure function (`modelClassFor` in `src/core/model-choice.ts`). Each agent run's succeeded outcome data records `model_class` and `model` (the configured name) next to `tokens`; no schema change. Review moves from strong to standard by default, which lowers the reviewer's model: a human confirms this at merge. Out of scope: suggest, canary and setup's check stay `cheap`; stats per class; per-item overrides.

Instructions are soft; tools and permissions are hard. Credentials live only inside tool wrappers: agents never read secrets, only tools do, enforced by guards G1–G6 (architecture §5).

**The owner's message style (decision changed 2026-11-12; before: the text could change only by editing `prompts/`, see History).** One global text setting, `message_style` (default empty, at most 1000 characters), says how the factory's text should read: wording and tone only. `src/core/message-style.ts` (`withMessageStyle`) appends it, once and under a label that calls it the owner's style preference, after the role instructions of every model call that writes owner text: the triage, implement, review and resolve agent runs (`Worker.roleSpec`, after `owner-defaults` for triage), the improve run's drafts, and the interpreter's chat answers (`interpretRequest`). Each call reads it live through `LiveSettings`, so a change applies at the next model call with no restart. Empty: every system prompt and request is byte-identical to the one before the setting. It never reaches a run's own prompt, an output schema, the tools, the offered commands or a guard, and the fixed templates (command footers, button labels) never carry it. Not styled: scorer judges, the canary, `llm-check` and golden replays (golden measures the prompt alone). It changes like any settable key (`factory settings set message_style '"…"'` or the Settings page: a JSON string, audited with the actor and time), and on write the value goes through the configured egress scanner: a flagged value is refused naming the rule, and nothing is stored; with no scanner wired the write is refused. Only `message_style` is scanned on write today; the other keys are a follow-up. Why a setting and not a prompt edit: the owner tunes tone without a reviewed change to `prompts/`, and one owner means one style (no per-person or per-project style).

**Human gate (decision changed 2026-11-08; before: see History).** The human gate is the gate command set (`/approve`, `/reject <reason>`, `/retry`, `/revise`, `/resolve [notes]`), authorized locally and sent from any surface: the factory CLI or a sync plugin. A comment on the forge (an issue or a change's conversation on GitHub) is one way to send a command, not the gate itself, and with no forge selected every command still works locally. The spec is shown on each surface the item lives on; `/retry` re-runs a failed run that the factory stopped retrying (§5 Restarts); `/resolve` starts an agent resolve of a merge conflict (§5 Merge conflict). Merging the change is the merge gate. The prompts say "change", never "pull request", and name where it lives with the `{{forge}}` placeholder, filled at load with `plugins.forge` or `local`. On GitHub the factory marks each handled command (and each issue it takes in) with a 👀 reaction, and explains a refused command (no permission, or a state that cannot take it) in one reply comment (decided 2026-11-01). Agents may call read-only broker tools that `tool_grants` grants to their run kind (decision changed 2026-11-07, issue #164; how the guards hold: `docs/architecture.md` §5). Absent, a run gets none. The worker still pushes, opens the PR and posts the review through the `ToolBroker` after the agent exits.

**Given values: a request's exact values reach the spec and the implementer verbatim (decision changed 2026-11-12; before: the spec alone carried the request, see History).** `prompts/triage.md` tells triage to copy every exact value the request states (tables, hex colours, numbers, names, commands, file paths) verbatim into a "Given values" section at the end of the problem, a table as a table, never paraphrased or dropped. A pure check (`src/core/given-values.ts`) reads the request as kept at intake (`issue_text`) for three value kinds, chosen at approval: hex colours (`#` and 3, 4, 6 or 8 hex digits; one of 3 or 4 decimal digits only inside a table cell or code span, since `#570` is as likely an issue number), code spans and markdown table cells, skipping fenced blocks but for their hex colours. `missingValues` returns those the spec text (`specText`: problem, done criteria, desired output, scope, decisions, paths) does not hold verbatim; hex colours match in any letter case. When it returns any, the controller holds the spec at the gate (`spec_pending`) for a person's `/approve`: no approval without a reply applies (tier dials, auto mode, a standing rule, the improver's fix). A phase the owner's `/approve` of the split covers (`phases_auto_approve`) still starts: that approval is a person's, and a phase's request is the split's own text. The hold line above the footer names the values, and the spec comment lists them under `### Values from the request missing in the spec` before the footer. An item with no kept request (`issue_text` null) is not checked. The implement prompt puts the request below the spec under `## Original request`, fenced and labelled untrusted (`renderRequest`, `src/worker/support.ts`), or a stated fallback when none was kept; `prompts/implement.md` tells the implementer to use a request value the spec leaves out. Why: a colour table was lost between request and change twice on 2026-11-11/12. Not done: no backfill or re-check of stored specs, no new spec field, no check of the review, resolve or fix prompts.

**Owner answers bind every re-written spec (decision changed 2026-11-12; before: a re-written spec started from the request's wording, see History).** The answers stored on an approval (`spec_approved` or `split_approved`, its `answers` detail; the `N: <answer>` lines, and auto mode's defaults) reach every later triage run of the item: a spec conflict revision, a `/revise`, a re-triage, and the phase specs of a split. `ownerAnswersFor` (`src/shared/command-notes.ts`) takes the answers of the item's newest approval that stored any, so a newer answer replaces an older one and an approval with none (a standing rule, the improver's fix) keeps the earlier ones; a phase with none of its own takes its parent's newest `split_approved`. The triage run puts them in an `## Owner answers (binding)` section above the request (`renderOwnerAnswers`, `src/worker/support.ts`), fenced and labelled untrusted like the implement prompt's decisions section; with none stored the prompt is byte-identical to before. `prompts/triage.md` says an owner answer overrides the request's wording where they conflict. The controller checks each answer against the new spec (`missingAnswers`, `src/core/given-values.ts`): the whole answer must appear in the spec text with letter case and whitespace runs ignored, no fuzzy match, and the spec's own decisions do not count (a question asked again with the answer as an option is not a kept answer). A spec that drops one is held like a dropped request value: `spec_pending` for a person's `/approve`, with no tier, auto mode, standing rule or improver approval; the hold line names the decisions and the spec comment lists `Owner answer missing: N: <answer>` under `### Owner answers missing in the spec`, apart from the request values. A phase covered by `phases_auto_approve` still starts, as for a missing request value. The values check ignores the answer syntax itself (`N: <answer>`, `1: <answer>`, `N: answer`) as a value. Why: answers were lost on re-writes three times on 2026-11-12 (wi_b96d's Upcoming 7 days, wi_566a, wi_9157). Not done: no store schema change or new state, no backfill or re-check of stored specs; the implement and review prompts still read only the newest `spec_approved`'s answers (`decisionsSection`).

**Spec layout (decision changed 2026-11-07, issue #229).** After In short the spec comment reads: `### Problem`; `### Decisions for you` (the tier raise line, then triage's `decisions`: risky choices and open questions; at most 5 lines shown, the rest folded; omitted when empty); `### Done when` (the first 10 criteria, the rest in a `<details>` block; triage, the implementer and review still get all); the PR contents (`desired_output`) folded under "What the PR contains", or dropped when at least 70% of its words are already in the done criteria (`repeatsDone`); `### In scope` and `### Out of scope`; `### Files`; `### Risk`. Triage returns `in_scope` and `out_of_scope` lists instead of one `scope` text; the stored `scope` is built from them (`scopeText`), so the work item, the store and the implement prompt are unchanged. An older triage output with only `scope` still parses and renders it under `### Scope`. **`decisions` is optional (decision changed 2026-11-07):** the schema the runner sends does not list it as required, the validator reads a missing one as `[]`, and `prompts/triage.md` shows it as `"decisions": []` in an output example. Every other triage field stays required.

**In short opening.** Triage returns a required `in_short` text field: "AS-IS:" in one plain sentence or two, then "TO-BE:" in one, with no file-level detail. The spec comment is `## Factory spec`, then `### In short (AS-IS → TO-BE)` and that text; nothing comes before it. `prompts/implement.md` and `prompts/resolve.md` tell the agent that its summary (the PR description, the resolution summary) starts with the same section, before any file-level detail; the PR body's layout is below (PR body and incomplete PRs). `in_short` is not stored; a revised spec gets a new one from its triage run. Only the prompt text is tested; nothing checks that a model's reply starts with the section (a reviewer check would need a tool that reads the PR description, an open question).

**PR body and incomplete PRs (decision changed 2026-11-07, issue #229).** The worker builds the PR body (`src/core/pr-body.ts`) on every push in a fixed order: the summary's In short section, `## Before you merge`, the rest of the summary (under `## What changed` when it has no heading), `## Tests`, then `Closes #<issue>` and the work item line. Before you merge lists the implement output's `missing` entries ("Not done:"), its `deviations` ("Differs from the spec:") and "A human merges this PR (tier N)" when the tier cannot auto-merge; with none of them it says "None.". Tests holds only the factory's own pre-push check lines: a heading named Tests, Testing or Checks in the agent's summary is dropped with everything under it, so sandbox-only claims never reach the PR. `missing` and `deviations` are optional lists in the implement output (at most 10 entries of 300 characters; absent is empty). The PR delivery (`Forge.openPr` through outbound's `github-change` target since RFC 0015 M7) updates an open PR's title and body (PATCH) instead of only returning it, and takes `labels` (name → present). So a fix round's implement run rewrites the body, and an update run (base merge) or resolve run that pushed rebuilds it from the last implement run's stored notes (`pr_summary`, `missing`, `deviations` in its outcome data) and its own checks; with no stored notes (older runs, adopted PRs) the body is left alone, and a failed refresh is logged without failing the run. A non-empty `missing` sets the PR label `<status prefix>incomplete` (`sf: incomplete`; setup creates it, doctor warns when it is missing), and every later push sets or clears it. At the CI gate an incomplete PR still waits for a human merge (`merge_pending`), but its comment says it is incomplete and lists the missing work instead of the plain "A human merge is required"; `canAutoMerge` is false for it whatever the tier (auto-merge itself does not exist yet). Triage is told that a store schema change needs every store's migration, so it allows `migrations/mysql/` and `src/impl/store/mysql/migrations.ts` too (`prompts/triage.md`).

**Review routing by finding kind (decision changed 2026-11-07, issue #222).** The reviewer returns each finding as `{ kind, text }`: `code` is a defect the implementer can fix inside the spec, `spec` one that needs the spec changed (a file outside `allowed_paths`, a criterion against a repo rule). Checks it could not run go in a separate `unverified` list, which never makes the verdict `bug` and is never a finding. An older review (findings as strings, no `unverified`) still parses: each string is a `code` finding. The controller routes a review: a `bug` with only code findings loops back to implement as before (`loop_count` + 1, `review_bug`, `max_loops` applies); any spec finding, alone or with code findings, starts a spec revision on the `/revise` path: `revision_count` + 1, `spec_feedback` holds the findings, one triage run under the `:v<n>` key, no implement run, `restart_count` + 1 so the implement run after the revised spec is approved gets a new key and continues on the PR branch (the PR number is kept); `loop_count` does not change. At the revision limit (`max_loops`) no triage run starts: the item waits at the spec gate with `max_revisions` and one comment (`/approve` implements the spec as it is). The implement output has an optional `spec_conflict` reason: non-empty, the worker fails the run with it (code `spec_conflict`) before it counts commits or pushes, and the controller starts the same spec revision with the reason as feedback, so it records neither `no_commits` nor `scope_violation`. Finding text and the reason pass the egress scan before anything is stored; a flagged text stores nothing, blocks the item on a human (`run_failed:<kind>:egress_blocked`, where `/retry` and `/revise` apply) and posts one comment naming the rule. The PR review comment's header reads `pass`, `changes needed` (code findings) or `spec needs a change` (any spec finding), with unverified checks under `Not verified`. On an adopted PR every bug keeps its route: changes requested, no implement or spec revision run. The golden replay scores the verdict of the new shape; a spec finding's line is marked `(spec)`.

**Review run: cheap checks first, CI results in the prompt (decision changed 2026-11-08, issue #223; before: a review on every run, see History).** Before any agent call the worker's review run reads the PR head (`git rev-parse origin/<branch>`, the branch its folder checked out), the commits ahead of the base (`git rev-list --count origin/<base>..HEAD`) and, when there are any, the diff. No commits ahead (the branch is already on the base) or an empty diff: no agent call, the run succeeds with `no_agent: empty_diff`, and the controller blocks the item on a human with `blocked_reason` `empty_diff` and one comment keyed on the item (`empty_diff`), so a repeated run posts no other comment. A head equal to the `head_sha` of the item's latest succeeded review whose outcome holds a verdict (failed runs, `needs_human` and egress-blocked outcomes hold none and never count; a head that cannot be read never matches): no agent call, no review comment, the run succeeds with `no_agent: unchanged_head`, and the controller acknowledges it and leaves the item's state as it is. The last verdict is not replayed: it was applied when it was made. An unchanged head is never reviewed again, even after the review prompt or the reviewer model changes; only a new head starts a review. A paused review that resumes its own session is the same review and is never skipped. Every succeeded review outcome records `head_sha` in its JSON data (no store migration); outcomes stored before 2026-11-08 have none, never match, and are not backfilled. CI results: when the controller queues a review (after an implement, resolve or session finish, and on adoption) it reads each check's name and result (`passed`, `failed`, `pending`) through the forge's `prCheckResults` and puts them on the review run's input as `ci_checks` (at most 20 checks of 100 characters). The CI gate's `prChecks` is built on the same read and its results do not change. No forge selected: an empty list. A failed read: `null` (logged); the review still runs. An automatic retry keeps the run's input. The review prompt gets a `## CI results` section: one fenced line per check, labelled untrusted (names are forge text); "No CI checks ran" for an empty list; "could not be read" for a failed read or no `ci_checks` (an older run, a human `/retry`). `prompts/review.md` tells the reviewer to read the CI results and to run tests only to confirm a specific finding (no whole-suite run, no acceptance tests of its own), and that notes which are not findings (needs a human merge, not a defect) go in `summary`. Not done: failing test names from the check-run output (extra API calls per check; a follow-up). The results are read when the review is queued, so right after a push they are often pending.

## History

- **Owner answers** (decision changed 2026-11-12). Before: answers stored on an approval reached only the implement and review prompts; a spec conflict revision, a `/revise`, a re-triage or a split's phase specs started from the request's wording, nothing checked a re-written spec against the answers, and the values check flagged the answer syntax (`1: <answer>`) as a missing value.
- **Given values** (decision changed 2026-11-12). Before: triage paraphrased the request into the spec with no rule on exact values, nothing compared the spec with the request, and the implement prompt was built from the spec alone, so a table, hex colour or number the spec dropped never reached the implementer.

- **The owner's message style** (decision changed 2026-11-12). Before: prompts were read from `prompts/` once at startup and each role's system prompt was fixed there; the only way to change how the factory's text reads was to edit the prompts, and no settings write ran the egress scanner.
- **Human gate** (decision changed 2026-11-08). Before: the gate was described as the GitHub gate ("Phase 1 human gate on GitHub (D5)"): the spec was an issue comment, a user with write permission replied there, and the prompts said "pull request" or "PR" even when no forge was selected.
- **Review on every run** (decision changed 2026-11-08, issue #223). Before: the review run called the reviewer agent after every implement, resolve and session finish whatever the diff or head, so empty diffs, branches already on the base and unchanged heads all got a full LLM review; the prompt had no CI results (the forge's check read returned only the CI gate's aggregate state) and told the reviewer to run the whole test suite and its own acceptance tests, which failed in the sandbox (no MySQL, `listen EPERM`).
- **Triage `decisions` optional** (decision changed 2026-11-07). Before: `decisions` was a required schema property. The cheap model (Haiku) left the empty list out, the harness rejected each try with "must have required property 'decisions'", and 7 of 40 triage runs failed with `error_max_structured_output_retries`.
- **Review routing by finding kind** (decision changed 2026-11-07, issue #222). Before: the reviewer returned findings as plain strings, every `bug` went back to implement as a review loop (also a finding that needed a spec change, which then failed with `scope_violation` or `no_commits` and blocked on a human), "could not run the tests" was written as a finding, and the PR comment read "bugs found"; the implementer had no way to report that a criterion could not be met inside the spec.

- **PR body and incomplete PRs** (decision changed 2026-11-07, issue #229). Before: the PR body was the agent's summary, the check lines, `Closes #<issue>` and the work item line, written once when the PR opened and never updated; a gap the agent mentioned in prose (a file outside the allowed paths) left no mark, and such PRs merged as done.
- **Broker tools in agent runs** (2026-11-07, issue #164). Before: agents got no broker tools (decided 2026-10-31); the runner refused a run with grants.
- **Spec layout** (decision changed 2026-11-07, issue #229). Before: In short, "Please check" (tier raise only), What changes, Done when (every criterion), Not included (one `scope` text that also named what was in scope), Problem, Files, Risk.
- **Triage retry after `agent_failed`** (decision changed 2026-11-08, issue #457). Before: triage was not moved up on retry; only implement and resolve runs with `loop_count` ≥ 1 went one class up, so a triage run that failed with `agent_failed` was retried on the same cheap model and failed the same way again.
- **Model class per run kind and tier** (decision changed 2026-11-02, issue #137). Before: two classes, `cheap` and `strong`, hard-coded per run kind in the worker: triage cheap, implement, review and resolve strong, whatever the tier or loop, and runs did not record which model they used.
- **In short opening** (decision changed 2026-11-01). Before: the spec comment opened with the first one or two sentences of the problem, and the PR description was the implementer's summary with no plain statement of the change at the top.
