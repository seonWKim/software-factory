# 4. Agents: roles, models and the human gate

| Role | Reads | Writes | Model |
|---|---|---|---|
| Triage | Slack thread, issues, code (API, no clone) | its fields, `READY` / `CLOSED` | cheap |
| Manager | `READY` queue | lease, assignment | none (code) |
| Implementer | work item + pointers + previous mistakes | code on its branch, TDD tests, handoff row per commit | standard at tier 1–2, strong at tier 3–5 |
| Reviewer | pass 1: work item + diff + CI results + `worked_on` (no transcript); pass 2: intent, how_to_test | verdict (tests run only to confirm a finding), cumulative mistakes, tier recheck | standard, different if measured to help |
| Resolver (`/resolve`) | conflicting files + work item + notes | the merge resolution | standard at tier 1–2, strong at tier 3–5 |

The model column is the shipped `model_by` table (below); a retry after a review loop goes one class up.

**Model class per run kind and tier.** There are three classes, `cheap`, `standard` and `strong`; `models` in `factory.config.json` maps each to a model name (shipped: `haiku`, `sonnet`, `opus`, CLI aliases, not pinned versions) and must list all three. `model_by` maps run kind and tier to a class: one entry per run kind (`triage`, `implement`, `review`, `resolve`), each either one class for every tier or an object with a class for each of tiers `"1"` to `"5"`, plus `retry_up` (default true). Shipped, and used when `model_by` is absent:

| Run kind | Tier 1 | Tier 2 | Tier 3 | Tier 4 | Tier 5 | Retry after a review loop |
|---|---|---|---|---|---|---|
| triage | cheap | cheap | cheap | cheap | cheap | not moved |
| implement | standard | standard | strong | strong | strong | one class up |
| review | standard | standard | standard | standard | standard | not moved |
| resolve | standard | standard | strong | strong | strong | one class up |

A retry is an implement or resolve run for an item whose `loop_count` is 1 or more (review or failed checks sent it back); it goes one class up (`cheap` → `standard` → `strong`, `strong` stays) unless `retry_up` is false. Restart retries (`/retry`, backoff) do not move `loop_count` and are not bumped. An item with no tier yet takes its run kind's tier-5 entry. The merge-conflict steps inside an implement run use the implement run's class. Golden reviewer replays use the review class (tier-5 entry, no bump), so they match production review. `loadConfig` checks both keys at startup: an unknown run kind or tier key, a value that is not a class, a tier object missing a tier, or `models` without one of the three classes fails loading with the key or value named. The choice is one pure function (`modelClassFor` in `src/core/model-choice.ts`). Each agent run's succeeded outcome data records `model_class` and `model` (the configured name) next to `tokens`; no schema change. Review moves from strong to standard by default, which lowers the reviewer's model: a human confirms this at merge. Out of scope: suggest, canary and setup's check stay `cheap`; stats per class; per-item overrides.

Instructions are soft; tools and permissions are hard. Credentials live only inside tool wrappers: agents never read secrets, only tools do, enforced by guards G1–G6 (architecture §5).

**Human gate (decision changed 2026-11-08; before: see History).** The human gate is the gate command set (`/approve`, `/reject <reason>`, `/retry`, `/revise`, `/resolve [notes]`), authorized locally and sent from any surface: the factory CLI or a sync plugin. A comment on the forge (an issue or a change's conversation on GitHub) is one way to send a command, not the gate itself, and with no forge selected every command still works locally. The spec is shown on each surface the item lives on; `/retry` re-runs a failed run that the factory stopped retrying (§5 Restarts); `/resolve` starts an agent resolve of a merge conflict (§5 Merge conflict). Merging the change is the merge gate. The prompts say "change", never "pull request", and name where it lives with the `{{forge}}` placeholder, filled at load with `plugins.forge` or `local`. On GitHub the factory marks each handled command (and each issue it takes in) with a 👀 reaction, and explains a refused command (no permission, or a state that cannot take it) in one reply comment (decided 2026-11-01). Agents may call read-only broker tools that `tool_grants` grants to their run kind (decision changed 2026-11-07, issue #164; how the guards hold: `docs/architecture.md` §5). Absent, a run gets none. The worker still pushes, opens the PR and posts the review through the `ToolBroker` after the agent exits.

**Spec layout (decision changed 2026-11-07, issue #229).** After In short the spec comment reads: `### Problem`; `### Decisions for you` (the tier raise line, then triage's `decisions`: risky choices and open questions; at most 5 lines shown, the rest folded; omitted when empty); `### Done when` (the first 10 criteria, the rest in a `<details>` block; triage, the implementer and review still get all); the PR contents (`desired_output`) folded under "What the PR contains", or dropped when at least 70% of its words are already in the done criteria (`repeatsDone`); `### In scope` and `### Out of scope`; `### Files`; `### Risk`. Triage returns `in_scope` and `out_of_scope` lists instead of one `scope` text; the stored `scope` is built from them (`scopeText`), so the work item, the store and the implement prompt are unchanged. An older triage output with only `scope` still parses and renders it under `### Scope`. **`decisions` is optional (decision changed 2026-11-07):** the schema the runner sends does not list it as required, the validator reads a missing one as `[]`, and `prompts/triage.md` shows it as `"decisions": []` in an output example. Every other triage field stays required.

**In short opening.** Triage returns a required `in_short` text field: "AS-IS:" in one plain sentence or two, then "TO-BE:" in one, with no file-level detail. The spec comment is `## Factory spec`, then `### In short (AS-IS → TO-BE)` and that text; nothing comes before it. `prompts/implement.md` and `prompts/resolve.md` tell the agent that its summary (the PR description, the resolution summary) starts with the same section, before any file-level detail; the PR body's layout is below (PR body and incomplete PRs). `in_short` is not stored; a revised spec gets a new one from its triage run. Only the prompt text is tested; nothing checks that a model's reply starts with the section (a reviewer check would need a tool that reads the PR description, an open question).

**PR body and incomplete PRs (decision changed 2026-11-07, issue #229).** The worker builds the PR body (`src/core/pr-body.ts`) on every push in a fixed order: the summary's In short section, `## Before you merge`, the rest of the summary (under `## What changed` when it has no heading), `## Tests`, then `Closes #<issue>` and the work item line. Before you merge lists the implement output's `missing` entries ("Not done:"), its `deviations` ("Differs from the spec:") and "A human merges this PR (tier N)" when the tier cannot auto-merge; with none of them it says "None.". Tests holds only the factory's own pre-push check lines: a heading named Tests, Testing or Checks in the agent's summary is dropped with everything under it, so sandbox-only claims never reach the PR. `missing` and `deviations` are optional lists in the implement output (at most 10 entries of 300 characters; absent is empty). `github.open_pr` now updates an open PR's title and body (PATCH) instead of only returning it, and takes `labels` (name → present). So a fix round's implement run rewrites the body, and an update run (base merge) or resolve run that pushed rebuilds it from the last implement run's stored notes (`pr_summary`, `missing`, `deviations` in its outcome data) and its own checks; with no stored notes (older runs, adopted PRs) the body is left alone, and a failed refresh is logged without failing the run. A non-empty `missing` sets the PR label `<status prefix>incomplete` (`sf: incomplete`; setup creates it, doctor warns when it is missing), and every later push sets or clears it. At the CI gate an incomplete PR still waits for a human merge (`merge_pending`), but its comment says it is incomplete and lists the missing work instead of the plain "A human merge is required"; `canAutoMerge` is false for it whatever the tier (auto-merge itself does not exist yet). Triage is told that a store schema change needs every store's migration, so it allows `migrations/mysql/` and `src/impl/store/mysql/migrations.ts` too (`prompts/triage.md`).

**Review routing by finding kind (decision changed 2026-11-07, issue #222).** The reviewer returns each finding as `{ kind, text }`: `code` is a defect the implementer can fix inside the spec, `spec` one that needs the spec changed (a file outside `allowed_paths`, a criterion against a repo rule). Checks it could not run go in a separate `unverified` list, which never makes the verdict `bug` and is never a finding. An older review (findings as strings, no `unverified`) still parses: each string is a `code` finding. The controller routes a review: a `bug` with only code findings loops back to implement as before (`loop_count` + 1, `review_bug`, `max_loops` applies); any spec finding, alone or with code findings, starts a spec revision on the `/revise` path: `revision_count` + 1, `spec_feedback` holds the findings, one triage run under the `:v<n>` key, no implement run, `restart_count` + 1 so the implement run after the revised spec is approved gets a new key and continues on the PR branch (the PR number is kept); `loop_count` does not change. At the revision limit (`max_loops`) no triage run starts: the item waits at the spec gate with `max_revisions` and one comment (`/approve` implements the spec as it is). The implement output has an optional `spec_conflict` reason: non-empty, the worker fails the run with it (code `spec_conflict`) before it counts commits or pushes, and the controller starts the same spec revision with the reason as feedback, so it records neither `no_commits` nor `scope_violation`. Finding text and the reason pass the egress scan before anything is stored; a flagged text stores nothing, blocks the item on a human (`run_failed:<kind>:egress_blocked`, where `/retry` and `/revise` apply) and posts one comment naming the rule. The PR review comment's header reads `pass`, `changes needed` (code findings) or `spec needs a change` (any spec finding), with unverified checks under `Not verified`. On an adopted PR every bug keeps its route: changes requested, no implement or spec revision run. The golden replay scores the verdict of the new shape; a spec finding's line is marked `(spec)`.

**Review run: cheap checks first, CI results in the prompt (decision changed 2026-11-07, issue #223).** Before any agent call the worker's review run reads the PR head (`git rev-parse origin/<branch>`), the commits ahead of the base (`git rev-list --count origin/<base>..HEAD`) and, when there are any, the diff. No commits ahead (the branch is already on the base) or an empty diff: no agent call, the run succeeds with `no_agent: empty_diff`, and the controller blocks the item on a human with `blocked_reason` `empty_diff` and one comment keyed on the head (`empty_diff:<head>`), so a repeated run at the same head posts nothing. A head equal to the `head_sha` of the item's last succeeded review that holds a verdict (a failed review never counts; a head that cannot be read never matches): no agent call and no review comment; the run carries that verdict (`no_agent: unchanged_head`, `reused_review` = the run that produced it) and the controller routes it as before, keying the CI gate's comments on the original review, so the last verdict stands without new comments. Every succeeded review records `head_sha`. CI results: when the controller queues a review after an implement, resolve or session finish, it reads each check's name and result (`passed`, `failed`, `pending`) through the PR source's `prCheckResults` (the same read `prChecks` summarises for the CI gate, which is unchanged) and stores them as `ci_checks` (JSON, at most 20 checks of 100 characters) on that state change. The review prompt gets a `## CI results` section from the latest `ci_checks`: one fenced, untrusted line per check, "No CI checks ran" when the list is empty (also for a source without per-check results), and "did not read" when none was recorded (a read error, an adopted PR's first review). `prompts/review.md` tells the reviewer to read the CI results and run tests only to confirm a specific finding (no whole-suite run, no acceptance tests of its own), and that notes which are not findings go in `summary`. Not done: failing test names from the check-run output (extra API calls per check; a follow-up). The results are read when the review is queued, so right after a push they are often pending or not created yet.

## History

- **Human gate** (decision changed 2026-11-08). Before: the gate was described as the GitHub gate ("Phase 1 human gate on GitHub (D5)"): the spec was an issue comment, a user with write permission replied there, and the prompts said "pull request" or "PR" even when no forge was selected.
- **Review on every run** (decision changed 2026-11-07, issue #223). Before: the review run called the reviewer agent after every implement, resolve and session finish whatever the diff or head, so empty diffs, branches already on the base and unchanged heads all got a full LLM review; the prompt had no CI results and told the reviewer to run the whole test suite and its own acceptance tests, which failed in the sandbox (no MySQL, `listen EPERM`).
- **Triage `decisions` optional** (decision changed 2026-11-07). Before: `decisions` was a required schema property. The cheap model (Haiku) left the empty list out, the harness rejected each try with "must have required property 'decisions'", and 7 of 40 triage runs failed with `error_max_structured_output_retries`.
- **Review routing by finding kind** (decision changed 2026-11-07, issue #222). Before: the reviewer returned findings as plain strings, every `bug` went back to implement as a review loop (also a finding that needed a spec change, which then failed with `scope_violation` or `no_commits` and blocked on a human), "could not run the tests" was written as a finding, and the PR comment read "bugs found"; the implementer had no way to report that a criterion could not be met inside the spec.

- **PR body and incomplete PRs** (decision changed 2026-11-07, issue #229). Before: the PR body was the agent's summary, the check lines, `Closes #<issue>` and the work item line, written once when the PR opened and never updated; a gap the agent mentioned in prose (a file outside the allowed paths) left no mark, and such PRs merged as done.
- **Broker tools in agent runs** (2026-11-07, issue #164). Before: agents got no broker tools (decided 2026-10-31); the runner refused a run with grants.
- **Spec layout** (decision changed 2026-11-07, issue #229). Before: In short, "Please check" (tier raise only), What changes, Done when (every criterion), Not included (one `scope` text that also named what was in scope), Problem, Files, Risk.
- **Model class per run kind and tier** (decision changed 2026-11-02, issue #137). Before: two classes, `cheap` and `strong`, hard-coded per run kind in the worker: triage cheap, implement, review and resolve strong, whatever the tier or loop, and runs did not record which model they used.
- **In short opening** (decision changed 2026-11-01). Before: the spec comment opened with the first one or two sentences of the problem, and the PR description was the implementer's summary with no plain statement of the change at the top.
