# 9. Status page: dashboard item page

- **The item page shows labels, and the stored fields behind Details (decision changed 2026-11-19, "Plain words instead of internal names"; current; replaces the raw field names in the timeline, the run error code and the stored run status, see History).** A timeline row says its reason and each changed field by its label ("Waiting on: none → human", "Tokens: 0 → 1200"), with a `data-raw` Details holding the stored `field: from → to` lines. The Runs table shows the status in one form ("Succeeded", "Failed", "Running") and an error as its failure title, with the stored code in a Details; the closed state's reason, the token count and the transcript outcome read the same way. Times are `When` (design 09-dashboard-shell). The decision is in 09-dashboard-shell.md; this page only applies it.

- **The item and transcript pages' blocks are Cards (decision changed 2026-11-19, wi_de565ffb, "Professional polish: shared page header and cards"; current; replaces their `Section`s, see History).** Thread, Current run, Phases, Merge check, Runs, Timeline and the transcript's Steps are titled `Card`s; In short inside the decide box is a Card on the box's tint. The state fact and run statuses are the one `Badge`; no run, no thread entry and no step are `EmptyState`s.

- **The item page reads decision first: the DecisionCard, the current run, the thread collapsed after its first message, the runs, the timeline; no command prose in the body (decision changed 2026-11-19, owner request "decisions as buttons with their evidence"; current; replaces the page order and the "From a terminal" line of "A What you need to decide box and readable names" (2026-11-12) and the thread's "every entry listed open or folded" of "The item's Thread is newest first" (2026-11-13), see History).** The decision that changed: **the item page (`ItemPage`, `web/src/views/pages.tsx`) orders its parts by what the owner needs next.** Order: the breadcrumb and title, then the decision (`ItemDecision`: the `DecisionCard` while `why.next_actor` is `human`, design 09-dashboard-item-commands; else the why sentence and the "…" menu), the facts and the IDs row, **Current run** (a section only while a run is queued or running: its kind through `runKindLabel`, its status, attempt, worker, "started N ago" and its transcript link; the item query's poll keeps it live), the thread (the spec is its newest `spec` entry; the Spec comment fact links to it), the phases and merge check when there are any, the runs, the timeline. **Thread:** collapsed after its first (newest) message: the `Thread` list carries `data-collapsed` and hides every entry after the first, and one button below it, "Show N earlier messages" (`aria-expanded`), shows them ("Show only the newest message" folds them again). A URL anchor that names an earlier entry, or the DecisionCard's "Show in thread" (it fires `hashchange`), opens the list; each message's own Show more and Show less rules are unchanged. **No command prose:** the page body names no `/approve`, `/reject` or `/verdict` and has no "From a terminal" line; command buttons carry their description as a tooltip, and the command help is behind `?` and `⌘K` (design 09-dashboard-shell). Text is in `web/src/i18n/en/work.ts`; no new hex colour; no route, store or schema change.

- **The item header shows the Interactive task badge while an interactive run is running, and every run kind on the page goes through `runKindLabel` (no decision replaced).** The Runs table never prints the raw kind `interactive`; the text is the catalog entry `run.interactive`.

- **The item page lists feedback queued while implementing (decision changed 2026-11-15, design 04-gate-commands, `/revise` while implementing; current; adds to "All of it sits in one What you need to decide box", see History).** A `/revise` sent while the item implements is queued (a `revise_queued` state change) and applied when the run ends. The item page's decide box (`ItemCommands` in `web/src/views/item-commands.tsx`) lists each pending feedback's text under "Feedback (queued)", below In short, in both its forms (commands that apply, or none). `pendingFeedback` reads it from the item API's `timeline`, which already carries each state change's detail: a `revise_queued` row is pending until a `revise_applied` or `max_loops` row names its comment ID in `comment_ids`, the same rule as the controller's `pendingRevises` (`src/controller/units/commands/queued-revise.ts`). No API, store or setting change; the heading reuses the catalog's `commands.feedback` and `items.queued` texts. Feedback that stays pending after a failed or blocked run stays listed.
- **A write refused for a stale token retries once with a fresh one; a Factory work row's error has its own line (decision changed 2026-11-15; current; replaces "a stale token's 403 is shown until the owner reloads" and "a Factory work row shows a failed send in its actions", see History).** The UI process makes its CSRF token at start and keeps it in memory, and every factory update restarts it, so an open page's token dies often. Every write route's 403 for a missing or stale `x-csrf-token` (`src/ui/server.ts` writePost and `src/ui/commands.ts` commandsPost, both from `staleCsrf()`) now carries `code: "stale_csrf"` beside the unchanged message "Missing or stale x-csrf-token; reload the page."; no other 403 has a code. `postJson` in `web/src/api.ts`, under every write helper, answers that 403 by reading `GET /api/v1/session` once, putting it in the cached session query (key `[API.session]`, so later writes use the new token with no reload) and retrying the same write once with its `csrf_token`; it returns the retry's result, so a second refusal shows as before and nothing loops. Any other 403 (the origin refusal) is not retried. The refusal comes before any store write, so the retry cannot write twice. In the Tasks page's Needs you section (`NeedsList`), a row's failed send (`SendErrors`) sits on its own `basis-full` line below the row, not in the actions (`NeedActions` with `inlineErrors={false}`), and the title grows from a 16rem basis so the actions wrap below it before it truncates (`design-system/patterns.md` C-050). A waiting item's actions on a task's row (`WorkState`) keep their error in the actions cell for now. Tests: `tests/web-csrf-retry.test.ts`, `tests/ui-csrf-code.test.ts`, `tests/ui-tasks-needs.test.tsx` (Needs you section).
- **The item's Thread is newest first and shows the owner's own messages (decision changed 2026-11-13; current, except that the list is collapsed after its first message: the decision-first item page at the top; replaces "the Thread lists the item's thread entries and verdicts oldest first, each with its full body", see History).** **Order:** newest first (time, then seq), so the latest message and what it asks are at the top of the Thread, with no scrolling and no scroll-to-bottom script; the other option (open scrolled to the newest) was left out because it fights the URL anchor and a reader's own scroll. A URL anchor (`#msg-<seq>`) still wins: the page scrolls to it and that message starts expanded. **Owner entries:** the item API's `thread` rows get `role` (`factory` or `owner`). Owner rows are: the item's commands `/approve`, `/revise`, `/retry`, `/reject`, `/merge` and `/verdict` sent from the local CLI (origin `cli`) or the dashboard (origin `app`), read with the new `listItemCommands` (one `inbound_commands` read, no schema change, no remote call), each with `kind` the command's name, its text (CLI `args.text`, dashboard `args.note`) through the Withholder as `body`, its stored actor ID as `author`, and `channel` `cli` or `app`, anchor `command-<id>`, seq 0; every non-factory thread entry (a GitHub comment or Slack message, which the source already stored once with its actor ID, else `unknown`), marked `owner` instead of getting a second row from the command table (the owner's choice: GitHub-origin commands are not read from `inbound_commands`); and the item's verdicts. **Page:** owner entries are right aligned and tinted, labelled "You" with the stored ID beside it, the channel in words (`local CLI`, `dashboard`, else the source type). A factory message longer than its one-line summary (first heading, else first sentence) starts as that line with its body behind Show more (Show less folds it again); the newest message, the newest factory message (what a Needs-you reason names), every `spec` and `coordination-hold` (they ask the owner) and the anchored one start expanded. Owner entries are always shown in full. Strings are in the i18n catalog.
- **A "What you need to decide" box and readable names (decision changed 2026-11-12; current, except the page order and the terminal line: the decision-first item page at the top; replaces "the item page shows the Stage fact, In short and a Commands section after the facts, and raw IDs", see History).** **Item page** (`web/src/views/pages.tsx`, `item-commands.tsx`): a breadcrumb (`Work / <short number>`, both links in the app: `/app/items` and `/app/items/<id>`), the title, then one box headed "What you need to decide" at the top: the why sentence, In short, each open decision with its default, the note box and the buttons that apply now (labels capitalised: Approve, Revise, Reject; the command the state asks for, the first of approve, retry and resolve the viewer may send, is the page's one primary button, `Button` variant `primary`), and "From a terminal: `factory <command> <short number>`", whose Copy button copies the command with the full item ID (the CLI takes only the ID). With no command that applies, the why sentence and one line say so. The verdict's severity dropdown has a visible label, "Severity" (its accessible name stays "Verdict severity"). The facts follow the box: State is a pill (`Badge`, size `sm`) with the list's level word (the item API's `item_phase`, the list's rule; design 09-status-page, one rule for an item's phase), Source (linked only for an http(s) source), Tier, PR, Spec comment, loops, restarts, tokens, updated; then an "IDs" details row with the item ID and the source ID, each with a Copy button. **Names:** a page never shows a raw ID in running text. Items show their title (else their short source number `#N` or the 8-character local id, never `wi_…`); the viewer (the session's actor, the owner on a one-owner factory) shows as "you"; a worker as "worker N" from its slot number (decision 3); another person as their stored display name or "a person"; the factory as "the factory". Each such name opens a details element with the full ID and a Copy button (`IdDetails`, `CopyText`, `web/src/components/ui/copy.tsx`). This covers the item page (timeline, runs, host sleeps, Acting as), Needs you, Running now, Queue, Work items (tree and list), Workers, Health (host sleeps, merged by) and Failures (items by title from the items list, workers). Exempt: the Data page (decision 2: its cells are the raw table), command dialog titles (`Reject wi_1`) and an item the page's lists do not hold (its link keeps the ID). **Links:** breadcrumbs and item links point to `/app/items/<id>`; a source with no web address (a local item's `local:` link) links to the item page in the tree, Running now and Queue (`SourceLink` `itemId`, `ItemTitle` `itemPage`; `ItemTitle`'s stored-link default goes once `tests/ui-source-id.test.tsx` moves to `itemPage`). Text lives in the English catalog (`web/src/i18n/en.ts`); colours are the design token classes (`docs/design/09-brand-and-tokens.md`; the primary button is the control set's `primary` variant, accent background and on-solid text), no new hex. No route, store method, schema or migration changed.

- **A CI wait is running, and the gap after a run is queued (decision changed 2026-11-12; current; replaces "an item with `blocked_on: ci`, or with no run just after its last run finished, is stuck", see History).** An open item with `blocked_on: ci` (`checks_pending`) and no queued or running run ranks as `running` with the badge "waiting for CI": its PR's CI is running and nothing is wrong. An open item with `blocked_on: none`, no queued or running run, and a last run that finished less than one lease (`lease_ms`) ago ranks as `queued` with the badge "next run queued"; at one lease or more it is stuck as before (`stuck N min`). A running run past its lease stays stuck. No new level: `PriorityInput.last_finished_at` is filled in `src/ui/list.ts` from the runs it already reads.

- **Run transcripts in the app (new decision, 2026-11-07, issue #303; current).** A run's stored transcript opens from the item page. **Lookup:** by the worker's storage key, `transcripts/<item>/<run>.json` (a second agent step of the run: `<run>.<step>.json`, e.g. `resolve`, `fix`), never `runs.transcript_url`, which holds the external link a person gives for an interactive session (those stay out of scope). The run must belong to the item (`listRuns(item)`); no store method, schema or migration changed. **Storage:** `SharedStorage` gains `getRange(key, start, end)` → `{ bytes, size }` (only that range is read; `getRange(key, 0, 0)` gives the size), implemented by `fs` with one file handle. It is optional on the interface so an older implementation still builds; `readRange` falls back to `get` there. `UiDeps.storage` (optional; the ui command, `src/cli/handlers/ui/`, passes the configured storage plugin) is the UI's only storage dependency. **API** (`src/ui/transcript.ts`, routed from `src/ui/api.ts`): `GET`/`HEAD /api/v1/items/<id>/runs/<run>/transcript?offset=&filter=&tail=&part=` (every other method is 405, like every route). One request reads at most 64 KiB (`PAGE_BYTES`) and returns at most 64 KiB: a forward page reads from `offset - 1` so it can tell whether `offset` starts a line, leaves a line cut by the range for the next page (`next`), and skips a single line over 64 KiB with a marker; `tail=1` reads only the file's final 64 KiB and returns its last 20 steps (`earlier` says more exist). Each stream-json line (Claude Code's or the OpenAI-compatible runner's events) gives its steps (`text`, `tool_use`, `tool_result`, `result`, `system`, `error`); a line that is not a JSON event is a `plain` step, so a non-stream-json transcript shows as plain lines. `filter=edits|commands|reads` keeps only tool calls of that kind and is applied on the server, page by page. **Egress:** every step and every other text of the response (outcome code, detail, summary, worker id) passes the `EgressScanner` on the new channel `ui` before it leaves; a finding withholds the whole step (`[withheld: <rule>]`, its tool name dropped), never a cut-off part, and a clean step cut to fit the page is cut after the scan. Errors are fixed texts: 404 for an unknown run, another item's run, no stored transcript or an unknown `part`; 400 for a bad `offset` or `filter`; a storage error is a 500 whose text never includes the storage message. `/api/v1/items/:id` adds `transcripts`, run id → its stored parts (only runs with a transcript; from one `list` of the item's prefix); the run rows keep their fields, and the app's worker column is the last attempt's `worker_id`. **App:** the item page's Runs table shows kind with the run ID, attempt, status, error, worker, started, took, tokens and an Open link when a transcript is stored (a table at `sm` and up, cards below it: see "Item page, phases and narrow screens"); the view `/app/items/<id>/runs/<run>` (`web/src/views/transcript.tsx`, routed in `App.tsx`) shows the outcome first, then the steps: assistant text collapses past five lines, tool results start collapsed, errors are highlighted, a failed run offers "Jump to the last 20 steps", the step-type filter holds across "Load more" pages, and text wraps so a 375 px screen does not scroll sideways. It never polls. Out of scope: editing or re-running from a transcript, a live view, full-text search, and what the worker stores. Decision changed: "the UI reads only the store" (and the Data page's "out of scope: shared-storage transcripts") now has one storage read path, this route.
- **A deadlock claim no longer needs a person (decision changed 2026-11-11; current; replaces "an item whose current run's latest claim decision is `deadlock` is `needs_human`", see History).** The claim does not stop the run, so the factory moves the item on by itself. The level rule no longer reads it: an item whose run started past a deadlock ranks by its run (`running`), and `/api/v1/overview` `needs_you` does not count it. Its sentence (`Started past a deadlock with #92: a person checks the overlap`) stays in `why` on the rows, the item detail and the thread, with `next_actor` `factory` and `refs` naming `#92`. A person is needed only when a later conflict stops the resolve run (`blocked_on` human, `merge_conflict_pending`), which keeps its own `needs_human` level. `src/ui/priority.ts` has no deadlock input and no `deadlock` badge.
- **Why an item waits (decision changed 2026-11-07, issue #310; current, except the deadlock level above).** One pure function, `whyWaiting` (`src/ui/why.ts`, no store, no clock), turns an item's state, its queued or running run (with its queue position), the run's latest claim decision, the claim pauses in effect, the run's `not_before` (passed only while still ahead) and its phases into `{ code, text, next_actor, refs }`. **Precedence, first match wins:** closed; blocked on a person or the budget (`Ready to merge: …`, `Waiting for a person to approve the spec`, `#41 was closed without a merge: …`, a failed run, …); a deadlock claim on the current run (`Started past a deadlock with #92: a person checks the overlap`, `next_actor` `factory`); running (`Running implement`); a claim pause that stops the run's kind, by the store's claim rule (`rate_limit` and `model_stall` any kind, `forge_auth` and `preflight_access` implement and update only); a dependency (`Waiting for #A and #B to merge`, from the stored `blocked_reason`); a phase hold (`Waiting for the previous phase #N to merge`); a coordination hold (`Held behind #92, which has an open PR` / `which is running` / `which is queued ahead of it`, while the decision is `held`, not approved and on the current run); a retry's `not_before` (`Retry waits until …`); the queue position (`Queued at position N`); else `Nothing moves it: no run is queued`. `next_actor` is `human`, `factory`, `other_item` or `none`; `refs` are the same-repo `#N` numbers of the sentence (numbers only, never `owner/name#N`). **API:** `why` on each row of `/api/v1/items`, on the `item` of `/api/v1/items/:id` and on each row of `/api/v1/queue` (null for a run whose item is gone), all from the same helper (`whyOf`, `src/ui/list.ts`), so the three read the same `text`; the text passes the `Withholder`, and `ref_url` is the item's repository issue URL (from its GitHub source link; null otherwise) to append a ref to. **Levels:** a dependency blocker is `waiting_on_issue` (badge `waits on #N`) even while its run is queued, no longer `queued`. **App:** the Why column of Needs you and Work items shows the sentence; the Queue's Starts column shows it for any row that is not plainly queued or waiting out a retry (so a held run no longer reads "now"); the item page shows the full sentence under the title (no `truncate`) and no longer the raw Blocked on row; each `#N` in `refs` links to `ref_url` + N. **Reads:** only existing store reads: `getClaimPause` (four names, once per request), `listClaimDecisions` (per item with an active implement run on the item page and the Queue; this read cost is accepted for now; the Items list reads them in one `listLatestClaimDecisions` call since issue #295), `listRunsByStatus`, `getWorkItem`, and `listWorkItemsWhere` for phases only when an item is blocked upstream. No store method, interface, migration or schema changed.
- **Thread readability (decision changed 2026-11-09; current).** The decision that changed: the markdown renderer folds `<details>` and styles the spec's key sections; design only, no API change. **Markdown:** a small built-in renderer (`web/src/components/ui/markdown.tsx`, no dependency): headings, paragraphs, bullet and numbered lists, fenced code, inline code, bold, `[text](url)` links, and a `<details><summary>…</summary>` … `</details>` fold when each tag sits on a line of its own (the spec comment's form). It builds React elements, never HTML strings, so any other raw HTML shows as text; a link is drawn only for an http(s) URL, any other (`javascript:`, `data:`, relative) shows its text, plain. A section headed "In short" is a tinted summary block and one headed "Decisions for you" an amber attention block, each from its heading to the next heading of its level or higher. A paragraph "AS-IS: … TO-BE: …" shows as two lines with bold labels. **Thread:** each entry has a header bar (author, channel, kind as a badge, time on the right) apart from its body; the body is at most 75ch wide with relaxed line height.
- **Item page, phases and narrow screens (decision changed 2026-11-07, issue #313; current).** **Item API:** the `item` of `/api/v1/items/:id` adds `spec_comment_url` (through the Withholder; null before triage posts the spec), `parent_id` and `phase` (both null unless the item is a phase of a split spec) and `phases`, a split parent's phases in phase order as `{ id, phase, title, stage, source }` (title through the Withholder; empty for any other item), read with the store's existing `listPhases`; no store method, schema or migration changed. **Item page:** a phase says "Phase N of its split parent" with a link to the parent; a split parent has a Phases section linking each phase's page. The spec comment and the PR are links only when the URL is http(s); any other value (a withheld marker, a local path) shows as plain text. The Runs table's first cell is the run's kind and ID. **Timeline:** each change value is parsed from the API's JSON text and shown as words (strings unquoted, lists joined, none as `–`; a withheld marker as it is). The spec fields triage writes (`problem`, `scope`, `desired_output`, `done_criteria`, `files_to_change`, `allowed_paths`) never show inline: their row has a "spec written (show)" button that opens them, each rendered as markdown (lists as bullet lists). **Markdown:** see "Thread readability" above. **Closed facet:** the Closed option (and stage `CLOSED`) counts the closed items that match the other filters, the same rule as every other facet.
