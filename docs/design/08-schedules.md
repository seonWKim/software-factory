# 8. Operations: schedules

- **A schedule may skip a due occurrence while the factory is busy, and the feedback run starts its own sandbox (decision changed 2026-11-23, wi_c9777390927f4e03a99cd7f292d1b9fb; current; replaces "the option `only when the factory has no open work` is still to come", see History).** Evidence: on 2026-11-22 the owner paused the idle-agents loop (the loop the scheduler replaces) "until the queue is under 15", because it kept filing items while 46 builds were queued; and the owner prefers a manual setup step turned into one command (manual only for browser logins).
  - **Skip when busy.** `controller_schedules.skip_when_busy` is a nullable per-schedule option, off when unset (null or 0). `runDueSchedules` checks it when an occurrence comes due: for an idle schedule with it on, it reads the store's count of queued implement runs (`countQueuedImplementRuns`, `worker_runs` with `status = 'queued'` and `kind = 'implement'`), once per pass and only when such a schedule is due. At the threshold or over it (`SKIP_WHEN_BUSY_THRESHOLD`, 15 by default, the owner's "under 15"; a pass may be given another as `busy_threshold`) the claim's outcome is `skipped`: the same conditional UPDATE moves `next_due_at` to the next slot and leaves `running_since` unset, and the run row stores the count in `controller_schedule_runs.queued_implement_runs` (null for the other outcomes). No run is queued and the skipped slot is never run later. So with 20 queued implement runs a due occurrence is skipped; with 3 it fires. A running schedule's due occurrence is still `refused`, busy or not. One additive migration, `20261123T1000-controller-schedule-skip`, adds both nullable columns.
  - **Why queued implement runs, not open items.** Queued builds are what the owner's pause named and what a schedule's work adds to; open items include ones waiting on the owner, which a schedule cannot make longer.
  - **The feedback run starts its sandbox.** The feedback run (`scripts/idle-agents.mjs`, a local development process, not a factory feature) starts the sandbox app (`scripts/idle-agents/sandbox.mjs`, which binds a free local port) before the agent runs, passes its URL to the agent, and stops it after, also when the agent fails: `withSandbox(start, run)` in `scripts/idle-agents/schedule.mjs`, with the stop in `finally`. A schedule needs no URL and the owner starts nothing by hand.
  - **Not yet.** No designer or developer persona schedule turns `skip_when_busy` on: those personas run from the idle-agents loop, which keeps its open-items rule (`IDLE_ONLY` and `busyItems`, owner decision 1); gating them at 15 queued implement runs is a follow-up. Creating or editing schedules from the CLI, the dashboard or tasks, and the retention of `controller_schedule_runs`, are still to come.

- **A fired occurrence runs the selected ScheduleAction, and the controller's schedule unit claims on each tick (decision changed 2026-11-23, wi_9a35f49052e147d9bd48df8ecb40eb94, phase 2 of 2; current; replaces "nothing calls the scheduler yet and no action is defined", see History).** What a fired occurrence does is a plugin kind, `schedule_action` (interface `ScheduleAction`, `src/interfaces/schedule-action.ts`; [docs/plugins/schedule-action.md](../plugins/schedule-action.md)), selected by `plugins.schedule_action`. It is optional with no default: a descriptor with a `default` is refused at startup, and with the key unset no action is selected. A `*.plugin.ts` folder of that kind is discovered by the registry with no loader change. No action plugin exists yet: the owner has not named one.
  - **Action.** `run(schedule, occurrence_at)`, once per fired occurrence, with the slot it was due for. It must be safe to run twice for the same occurrence: a crash after the claim and before the run ended may hand it over again. A throw is logged (`schedule action failed`) and the run still ends, so a failing action never leaves its schedule refusing every next occurrence.
  - **Caller.** The `schedule` unit (`src/controller/units/schedule/`) has one step on the controller's `tick`. It takes the time from the tick (never a clock read) and calls the bound pass, `scheduledAction(store, action, log)` in `src/core/controller-deps.ts`: `runDueSchedules` at that time, then the action once per fired occurrence in claim order, then `endScheduleRun` for each. A second tick at the same slot claims nothing, so runs nothing.
  - **No action selected: nothing is claimed** (owner decision 2). The step returns before any read; a due occurrence stays unclaimed (its `next_due_at` and `running_since` unchanged, no run row) until an action is selected. With no schedules stored a tick changes no row, and the factory starts as before.
  - **Wiring.** Compose builds the selected action through `createPlugin` and binds it to the store, passing it to the controller as `ControllerDeps.schedule_action`. The pass lives in core and the unit imports no core code, because the dependency-direction and kinds ratchets refuse a new controller-unit import of `src/core/`, and the unit-purity ratchet refuses a unit that reaches `.d.store`. The pass runs in the step's `load` (only a load gets the tick) and the decision writes nothing; a later change can move the claims into kernel writes.
  - **Still to come.** The per-schedule skip came on 2026-11-23 (above); the retention of `controller_schedule_runs`, and creating or editing schedules from the CLI, the dashboard or tasks, are still to come.

- **A schedule is its own stored record with a cadence in its own zone; each due occurrence is claimed once by one conditional update (new decision, 2026-11-22, wi_a519d81a, phase 1 of 2; current).** This phase is the records, the cadences and the claim. Code: `src/core/schedule-cadence.ts` (cadences), `src/core/schedule.ts` (`ScheduleStore`, `addSchedule`, `runDueSchedules`), `src/impl/store/sql/schedules.ts` (`SqlScheduleStore`, which `SqlFactoryStore` extends), migration `20261122T1000-controller-schedules`.
  - **Not a task's repeat.** A plain task's `recurrence` (day, week, month, design 02-tasks) stays as it is: it makes the next task row. A schedule is a row of `controller_schedules` and creates no task; a repeating task creates no schedule.
  - **Store.** `controller_schedules`: `id` (chosen by the caller, so a retried add stores nothing more), `title`, `cadence_kind`, `cadence_spec`, `zone` (IANA name), `created_by` (a user ID, never a display name), `created_at`, `next_due_at` (null: never due again), `running_since` (null while idle). `controller_schedule_runs`: `schedule_id`, `occurrence_at`, `outcome`, `recorded_at`, unique on (`schedule_id`, `occurrence_at`). One additive migration, `CREATE TABLE IF NOT EXISTS`, no backfill.
  - **Cadences.** `interval` (`90`: every 90 minutes, counted from `created_at`, so slots stay put), `daily` (`09:00`), `weekly` (`mon,fri 09:00`) and `cron` (5 fields: minute, hour, day of month, month, day of week; `*`, lists, ranges, `/step`, month and day names, 7 for Sunday; with both day fields restricted either matches, as in cron). Daily and weekly are written as cron rules, so one parser serves three kinds; it is hand-written (no package: the sandbox has no network). The next due time is the first slot strictly after a time, on the zone's wall clock: 09:00 stays 09:00 across a daylight-saving change; a time the clocks skip runs just after the gap; a time shown twice runs once, at its first instant. `addSchedule` refuses an unknown zone or a malformed spec with the reason, storing nothing.
  - **Claim.** `runDueSchedules(store, now)` reads the schedules due by `now` and, for each, claims its occurrence with one UPDATE that moves `next_due_at` from the value read to the first slot after `now`, only while that value is still stored and the schedule is idle (`fired`, which also sets `running_since`) or running (`refused`). The run row is inserted in the same transaction. Zero rows changed means another worker claimed it first: the loser records and fires nothing. Time comes in from the caller's tick; the store stamps `recorded_at` and `running_since` with its Clock.
  - **Missed slots.** Slots missed while no worker ran make one occurrence on return, recorded against the slot it was due for (the stored `next_due_at`, owner default: slot time, not return time); `recorded_at` shows the return. So a daily schedule fires once per local day, and a restart or a missed day makes no duplicate.
  - **Running.** A due occurrence of a schedule still running is refused and stored as a `refused` run row; `next_due_at` moves on. `endScheduleRun(id, running_since)` clears `running_since` only while it still holds that value.
  - **Next phase.** The caller and the action came in phase 2 (above); the per-schedule skip when busy came on 2026-11-23 (above), as a `skipped` run row. Room was left for it: `outcome` is plain text, a new outcome is one entry in the claim's state map (`CLAIM_STATE` in `schedules.ts`; a skip moves `next_due_at` on an idle schedule without setting `running_since`), and a per-schedule condition is one nullable column. `controller_schedule_runs` grows by one row per occurrence; its retention rule (design 08-retention) comes with the caller.
