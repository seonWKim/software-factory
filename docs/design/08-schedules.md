# 8. Operations: schedules

- **A schedule is its own stored record with a cadence in its own zone; each due occurrence is claimed once by one conditional update (new decision, 2026-11-22, wi_a519d81a, phase 1 of 2; current).** Nothing calls the scheduler yet and no action is defined: this phase is the records, the cadences and the claim. Code: `src/core/schedule-cadence.ts` (cadences), `src/core/schedule.ts` (`ScheduleStore`, `addSchedule`, `runDueSchedules`), `src/impl/store/sql/schedules.ts` (`SqlScheduleStore`, which `SqlFactoryStore` extends), migration `20261122T1000-controller-schedules`.
  - **Not a task's repeat.** A plain task's `recurrence` (day, week, month, design 02-tasks) stays as it is: it makes the next task row. A schedule is a row of `controller_schedules` and creates no task; a repeating task creates no schedule.
  - **Store.** `controller_schedules`: `id` (chosen by the caller, so a retried add stores nothing more), `title`, `cadence_kind`, `cadence_spec`, `zone` (IANA name), `created_by` (a user ID, never a display name), `created_at`, `next_due_at` (null: never due again), `running_since` (null while idle). `controller_schedule_runs`: `schedule_id`, `occurrence_at`, `outcome`, `recorded_at`, unique on (`schedule_id`, `occurrence_at`). One additive migration, `CREATE TABLE IF NOT EXISTS`, no backfill.
  - **Cadences.** `interval` (`90`: every 90 minutes, counted from `created_at`, so slots stay put), `daily` (`09:00`), `weekly` (`mon,fri 09:00`) and `cron` (5 fields: minute, hour, day of month, month, day of week; `*`, lists, ranges, `/step`, month and day names, 7 for Sunday; with both day fields restricted either matches, as in cron). Daily and weekly are written as cron rules, so one parser serves three kinds; it is hand-written (no package: the sandbox has no network). The next due time is the first slot strictly after a time, on the zone's wall clock: 09:00 stays 09:00 across a daylight-saving change; a time the clocks skip runs just after the gap; a time shown twice runs once, at its first instant. `addSchedule` refuses an unknown zone or a malformed spec with the reason, storing nothing.
  - **Claim.** `runDueSchedules(store, now)` reads the schedules due by `now` and, for each, claims its occurrence with one UPDATE that moves `next_due_at` from the value read to the first slot after `now`, only while that value is still stored and the schedule is idle (`fired`, which also sets `running_since`) or running (`refused`). The run row is inserted in the same transaction. Zero rows changed means another worker claimed it first: the loser records and fires nothing. Time comes in from the caller's tick; the store stamps `recorded_at` and `running_since` with its Clock.
  - **Missed slots.** Slots missed while no worker ran make one occurrence on return, recorded against the slot it was due for (the stored `next_due_at`, owner default: slot time, not return time); `recorded_at` shows the return. So a daily schedule fires once per local day, and a restart or a missed day makes no duplicate.
  - **Running.** A due occurrence of a schedule still running is refused and stored as a `refused` run row; `next_due_at` moves on. `endScheduleRun(id, running_since)` clears `running_since` only while it still holds that value.
  - **Next phase.** A caller (a tick), the action a fired occurrence runs, and the owner's per-schedule option "only when the factory has no open work", checked at fire time, with a skipped occurrence stored as a `skipped` run row. Room is left for it: `outcome` is plain text, a new outcome is one entry in the claim's state map (`CLAIM_STATE` in `schedules.ts`; a skip moves `next_due_at` on an idle schedule without setting `running_since`), and a per-schedule condition is one nullable column. `controller_schedule_runs` grows by one row per occurrence; its retention rule (design 08-retention) comes with the caller.
