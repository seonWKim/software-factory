# 8. Operations: schedules

- **A schedule's token cap counts the runs of its period, `token_period`: `day` for a daily cadence, `lifetime` for any other (decision changed 2026-11-25, local-task-tk_33c95362 phase 2 of 4; current; replaces "Token cap. Per schedule, summed over its runs' tokens." below, see History).** Why: over all runs, a daily schedule hit the default cap in a few days and was held for good.
  - **Store.** `controller_schedules.token_period` (TEXT, nullable), migration `20261125T1001-state-controller-schedule-token-period` (additive, no backfill): null, every older schedule, counts as `lifetime`. `addSchedule` sets it from the cadence if not given; an edit keeps it.
  - **Count.** `scheduleTokensUsed(id, day?)` sums the runs whose `occurrence_at` is on that UTC date. For `day`, the claim pass, `checkpointAnswer` and `raisedCap` use the claimed or held slot's date, so the next day's occurrence starts fresh.

- **A schedule's missed-time rule, `missed_rule`, is `catch_up` or `skip`; skip drops a due occurrence claimed over one tick late or while the factory is busy (decision changed 2026-11-25, local-task-tk_57c9bfa2 phase 3, phase 1 of 2; current; replaces the skip-when-busy decision of 2026-11-23, see History).** Why: a factory that was down fired a stale slot on return; the draft decision's owner answer 1 (below) merges the two into one setting. Owner answers, verbatim: 1. "Should the Schedules dashboard switch to the missed-time setting in this item?" Answer: "Keep the page's skip checkbox, mapped to missed_rule (on means skip) (the default, accepted)". 2. "Depends on local-task-tk_57c9bfa2-462c-410a-bb98-7061aa74cc4f-phase-2? yes/no" Answer: "yes (the default, accepted)".
  - **Store.** `controller_schedules.missed_rule` (TEXT, NOT NULL, default `catch_up`). Migration `20261125T1100-controller-schedule-missed` (additive) adds it when missing and sets `skip` where `skip_when_busy = 1`, so a rerun changes nothing. `skip_when_busy` stays, unread. `updateSchedule` writes `missed_rule` only while `next_due_at` still holds the value read.
  - **Claim.** `runDueSchedules` takes `tick_ms`. For an idle `skip` schedule, a claim more than `tick_ms` after its slot is `skipped` with no queued count; else, at `SKIP_WHEN_BUSY_THRESHOLD` (15) or more queued implement runs (counted once per pass), `skipped` with the count in `controller_schedule_runs.queued_implement_runs`. Either way `next_due_at` moves on and the slot never runs later. A `catch_up` schedule fires once, late or busy, as before; a running schedule's occurrence is still `refused`. With no `tick_ms`, no claim is late. The schedule unit passes the controller's `tick_ms` to `fireDue`.
  - **Run now.** `run_now` on add sets `next_due_at` to now; the claim then sets the cadence's next slot after that run. Off: the first slot after now. Add only.
  - **CLI.** `schedule add` takes `--missed catch-up|skip` and `--run-now on|off`; `schedule edit` takes `--missed`; `--skip-when-busy` is an unexpected flag in both, the chat form included. `schedule list` prints `missed catch-up` or `missed skip`.
  - **HTTP.** The routes keep `skip_when_busy`: true stores `skip`, false `catch_up`; reads and write answers add it (true for `skip`). `/add` takes `run_now` (a boolean, else 400), `/edit` not (changed 2026-11-25, phase 4 of 4; see History).

- **A schedule is its own stored record with a cadence in its own zone; each due occurrence is claimed once by one conditional update (new decision, 2026-11-22, wi_a519d81a, phase 1 of 2; current).** This phase is the records, the cadences and the claim. Code: `src/core/schedule-cadence.ts` (cadences), `src/core/schedule.ts` (`ScheduleStore`, `addSchedule`, `runDueSchedules`), `src/impl/store/sql/schedules.ts` (`SqlScheduleStore`, which `SqlFactoryStore` extends), migration `20261122T1000-controller-schedules`.
  - **Not a task's repeat.** A plain task's `recurrence` (day, week, month, design 02-tasks) stays as it is: it makes the next task row. A schedule is a row of `controller_schedules` and creates no task; a repeating task creates no schedule.
  - **Store.** `controller_schedules`: `id` (chosen by the caller, so a retried add stores nothing more), `title`, `cadence_kind`, `cadence_spec`, `zone` (IANA name), `created_by` (a user ID, never a display name), `created_at`, `next_due_at` (null: never due again), `running_since` (null while idle). `controller_schedule_runs`: `schedule_id`, `occurrence_at`, `outcome`, `recorded_at`, unique on (`schedule_id`, `occurrence_at`). One additive migration, `CREATE TABLE IF NOT EXISTS`, no backfill.
  - **Cadences.** `interval` (`90`: every 90 minutes, counted from `created_at`, so slots stay put), `daily` (`09:00`), `weekly` (`mon,fri 09:00`) and `cron` (5 fields: minute, hour, day of month, month, day of week; `*`, lists, ranges, `/step`, month and day names, 7 for Sunday; with both day fields restricted either matches, as in cron). Daily and weekly are written as cron rules, so one parser serves three kinds; it is hand-written (no package: the sandbox has no network). The next due time is the first slot strictly after a time, on the zone's wall clock: 09:00 stays 09:00 across a daylight-saving change; a time the clocks skip runs just after the gap; a time shown twice runs once, at its first instant. `addSchedule` refuses an unknown zone or a malformed spec with the reason, storing nothing.
  - **Claim.** `runDueSchedules(store, now)` reads the schedules due by `now` and, for each, claims its occurrence with one UPDATE that moves `next_due_at` from the value read to the first slot after `now`, only while that value is still stored and the schedule is idle (`fired`, which also sets `running_since`) or running (`refused`). The run row is inserted in the same transaction. Zero rows changed means another worker claimed it first: the loser records and fires nothing. Time comes in from the caller's tick; the store stamps `recorded_at` and `running_since` with its Clock.
  - **Missed slots.** Slots missed while no worker ran make one occurrence on return, recorded against the slot it was due for (the stored `next_due_at`, owner default: slot time, not return time); `recorded_at` shows the return. So a daily schedule fires once per local day, and a restart or a missed day makes no duplicate.
  - **Running.** A due occurrence of a schedule still running is refused and stored as a `refused` run row; `next_due_at` moves on. `endScheduleRun(id, running_since)` clears `running_since` only while it still holds that value.
