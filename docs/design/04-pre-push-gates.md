# 4. Agents: scope gate, pre-push gates and sync before push

**A `checks_failed` run's failing tests that quote removed text are granted once (decision changed 2026-11-25, phase 3 of local-task-tk_8fc2206b; changes *Second failure*; see History).** After the second round fails (and the base rerun does not read it as the environment's), the worker takes the failing test files from the output (`failingTestFiles`). When there are some, none is covered by `allowed_paths` (`isCovered`), and each file's text at HEAD quotes a double-quoted string of four or more characters (the triage pin rule, `pinStrings` in `src/core/triage-pins.ts`, 04-triage) that a removed line of `git diff -U0 --no-renames <base>...HEAD` contains (`removedPins`: a line starting with `-`, not `---`), it stores them on the failed outcome as `grant_tests` (each file with the quoted text). In `retryOrBlock`, after the attempt limits and before the repeated-failure check, the controller grants them (`checksGrant`, `src/controller/units/run-results/auto-grant.ts`) when `auto_grant_test_paths` is on for the project (its own value, else the global one), every file is a test path (`testPathsOnly`) and the item had no automatic grant yet (one per item, shared with the needs-human grant): the files are widened as `/retry +paths` widens them, one comment keyed `auto-grant:<run id>` names the files, the failing check and the quoted text, and one `retry_requested` change carries `auto_grant` and the run id. The retry starts a new step, so the granted run is not counted toward `repeated_failure`. Any other case (a covered file, a file quoting nothing removed, no test file named, the switch off, a grant already used) stays `checks_failed` as before. Only double quotes count, per file, not per failing assertion; lint and typecheck failures are never granted; stored runs are not regranted.

**A done check on a missing test file says so (decision changed 2026-11-24, wi_a61fc11e; changes *Done-when checks run in the round*; before: see History).** A failed `test_file` done check whose file the committed branch lacks (`git ls-files -- tests`: the run did not create it) reads "the check names tests/X.test.ts, which does not exist", not its exit code; no base rerun. The fix prompt names the closest existing test file by name (`closestTestFile`: same suffix, most shared words, ties sorted), none when no word is shared. Triage (`checkTestFiles`, before `parseTriage`) checks each exact `tests/` file in `allowed_paths` or `files_to_change` that no done check names against its run folder's `tests/` files (a base checkout, no clone): a missing one becomes the closest everywhere, a decision naming the swap; none close, it stays (the run creates it). Never a done-check file (04-triage).

**The table-list files follow an allowed migration (decision changed 2026-11-25; extends the coverage rule below and *Scope gate*; before: see History).** `isCovered` (`src/core/policy.ts`) also covers `tests/store-contract.test.ts`, `tests/state/contract-migrations.test.ts` and `src/state/migrations/20261109T0900-state-drop-legacy-tables.migration.ts` (`TABLE_LIST_FILES` in `src/core/migration-stamps.ts`: the store contract's `DOMAIN_TABLES`, the drop-legacy `RETIRED` list) whenever an allowed path is a migration (`src/<c>/migrations/*.migration.ts`, a timestamp or `<stamp>`). A migration that adds or rebuilds a table breaks those lists; wi_457bb850, wi_4a16d8f1 and wi_7b97a829 each stopped to ask for them. Path level only (the scope machinery has no line rule): `AGENTS.md` tells the implementer and the review that the edit there is the table-name lists only.

**The scope rule covers a same-slug migration at any timestamp (decision changed 2026-11-25, wi_b9b801b3; replaces "a later same-slug migration"; changes *Scope gate*; see History).** `isCovered` (`src/core/policy.ts`) covers a path equal to an allowed path, under an allowed path ending in `/`, a ratchet list, or (`sameSlugMigrationOf`) a migration `src/<c>/migrations/<ts>-<c>-<slug>.migration.ts` or test `tests/<ts>-<c>-<slug>.test.ts` in an allowed one's folder with its component and slug, at any timestamp. The allowed path may hold a timestamp or the placeholder `<stamp>` (04-triage): the implementer takes the next free one with no stop. Another slug, component or folder is refused, and a migration test never covers a migration. A clash is caught by `tests/architecture/migration-naming.test.ts`. Overlap checks compare exact paths (`isUnder`). Triage validation, both scope gates and the edit hook share it.

**The Stop check narrows tests like the check before push** (decision changed 2026-11-23; current): moved to History, unchanged, for the size cap.

**The merge check runs in a set time zone (decision changed 2026-11-23; changes *Checks run with no database* below; before: see History).** Optional key `repo.check_tz`: an IANA zone. With it, every `merge-check` command (install, checks, UI check, base UI rerun) runs with `TZ` set to it, so a test that passes only in the machine's zone turns the merge check red before merge. Absent: off, no `TZ`, results unchanged. Validated at config load (`checkTzConfig`, `src/load-config.ts`): any other value fails startup naming `repo.check_tz`. This repo sets `UTC`. The implement run's checks and the controller's red-main check keep the machine's zone.

**Checks before push narrow tests after shadow mode (decision changed 2026-11-23; before: see History).** With `repo.test_selection` (`hubs`, `always`), each implement check round and the interactive finish select tests on the scope gate's diff (`src/core/test-selection.ts`): changed tests, tests reached by walking runtime importers (one `git grep` over `src/`, `web/src/`, `tests/`; an `import type` or `export type` line adds no edge; a hub is not walked, a `tests/helpers/` file is), tests reading a changed file, and `always`. Reads: a `tests/` file's `readFile*`, `readdir*`, `existsSync` or `glob` on a literal path (literals, `join`/`resolve`/`new URL` of them, `import.meta.dirname`, a same-file const) reaches that tracked file or all under it; logged `<test> reads <path>`. Full: a hub, `package*.json`, `tests/setup/`, `vitest.config.ts` or `tsconfig*.json` changed. Mode: the per-project learned setting `test_selection_mode`. **Shadow** (none stored): the test command runs whole; the selection is logged and kept in the run's outcome (`test_selection`: mode, full, files, reason); a failing test file outside it is a miss, kept with the diff. Clean runs count in the cursor `test_selection_clean:<project>`, a miss resets it, the 50th writes `enforce`. **Enforce**: only the `repo.test_command` check runs on the selection (`withTestFiles`), uncounted. The merge check stays full; a failing file the item's enforce selection left out (`selection_miss`) writes `shadow`, count reset. Each switch is a learned-setting change row. Counted: implement runs whose test command ran, except `checks_env`; interactive finishes that pass or miss. Test selection needs an npm `repo.test_command`: the selection names vitest test files after `npm test --`, so with `repo.test_selection` set and a test command whose first word is not `npm` (e.g. `./gradlew test`), startup fails naming `repo.test_selection`; a non-npm test command runs whole.

**The Stop check limit is a setting** (decision changed 2026-11-23; current): moved to History, unchanged, for the size cap.

**A UI failure checks the base alone (decision changed 2026-11-18; before: see History).** It reruns once on a fresh checkout of the base sha. Base fails: `why: base_red`, no change blamed (red main, 03-risk); passes: `why: checks`, back to implement. An empty tail is the reason; `merge_check_failed` keeps it.

**Merge check reruns failing test files once** (decision changed 2026-11-17; current): moved to History, unchanged, for the size cap.

**UI check at merge, not in the sandbox (decision changed 2026-11-12; before: see History).** An optional config key `repo.ui_check`: `{ "command": <gate entry>, "paths": [prefix, ...] }` (a gate entry: an argv, or `{ "dir", "argv" }` run in that folder, 04-gate-commands; decision changed 2026-11-26, wi_a4ee0778, see History) (`paths` absent: `["web/", "src/ui/"]`; a path is covered when it starts with a prefix). Absent: off, and no merge-check run runs any extra command. Validated at config load (`uiCheckConfig` in `src/core/config.ts`): a gate entry command (`gateEntryConfig`) and a non-empty list of non-empty prefixes, no other key; a bad value fails startup naming `repo.ui_check`.

- **Where it runs.** Only in the merge queue's `merge-check` run, on the merged result (the base, the entries ahead and this change), after the install command and the checks: `git diff --name-only -z --no-renames <base_sha> <merged_sha>`, and the command runs when a changed path is under one of `paths`. It runs inside the merge-check sandbox, as the other checks do, not in the implementer's agent sandbox, which cannot start Chrome (its profile and crashpad writes fail).
- **Runtime pin (decision changed 2026-11-26, wi_66d21e54: the JDK is pinned too; before: see History).** The merge check pins Node and the JDK. Install and checks run on the project's Node major from `.nvmrc`, else `package.json` engines.node, and a missing Node fails the run `checks_env`. The project's JDK major is read from `.java-version`, else the Gradle toolchain (`JavaLanguageVersion.of(N)`) in the root `build.gradle` or `build.gradle.kts`; the worker's JDK (`$JAVA_HOME/bin/java` when JAVA_HOME is set, else `java` on PATH) is probed in the sandbox, and another major or no JDK fails the run `checks_env` naming the wanted and found majors, before install. No JDK is looked up or installed, and a project naming none reads none. A compile or test failure on the right JDK stays a red check. Only the merge check reads the JDK (not the implement run's pre-push checks); no other runtime is read.
- **Not missing work.** With `repo.ui_check` set, the implement and review prompts say the UI check (naming its command) runs at merge and is not work to report as missing or as unverified: the sentence is the `{{ui_check}}` placeholder, filled at load from the config and empty without the key, so no project is told a check runs that does not. This repo sets `repo.ui_check` to `npm run -s check:responsive` on `web/` and `src/ui/` in `factory.config.json`. The implement run also drops a `missing` entry that names the check (holds the command's last argument, e.g. `check:responsive`, in any case), so an item whose only gap was the UI check is not marked incomplete and auto mode can merge it. Without `repo.ui_check` nothing is dropped.

**Pack checks in the implement run** (decision changed 2026-11-11, issue #494; current): moved to History, unchanged, for the size cap.

**Gate hooks during the agent step (decision changed 2026-11-07, issue #302; before: see History).** The implement run's main step and its fix step tell the agent about a gate failure while it can still fix it. The worker puts the values its own gates use into the run spec (`AgentRunSpec.gate_hooks`): `allowed_paths`, the run's start SHA, the base SHA (the trusted base for the main step, the merged-in base for the fix step), the project's `max_diff_lines` and `max_diff_files`, the check list (`repo.check_commands`) with the worker's tool env (no credential, no test database URL), the cap `agent_stop_checks` and the Stop blocks earlier steps of the run already used. The `claude-code` runner turns them into two Claude Code hooks (docs/plugins/agent-runner.md):

- **PreToolUse on Edit and Write** refuses a path outside `allowed_paths`, with the scope gate's coverage rule (`isCovered`, top decision; a path outside the workdir is never covered). The refusal names the allowed paths and says: "This path is outside the approved allowed_paths. If the change needs it, stop and say so in your final message so the owner can add it to the spec." Bash is not path-checked (the sandbox and the scope gate cover it); MultiEdit and NotebookEdit are not offered to the implement role.
- **Stop** sends the agent back while the worker's gates would fail the run, in the gates' order, cheapest first, stopping at the first failure: no commits since the run's start (`runCommits`, issue #261), with the no-commit reason; a diff over either size limit (`<base>...HEAD`, `diffStat`), with the size gate's own wording (`sizeDetail`); then the check list in order (narrowed: above), naming the failing command and its scanned output tail (last 2000 characters; flagged or unscanned: withheld). Checks run on the working tree as is, no test database. The Stop hook blocks at most `agent_stop_checks` times per run (default 3, a positive integer or startup fails; main and fix step share the count); the next stop is allowed, so it cannot loop.
- **Files.** Script, spec file and block record: `<CLAUDE_CONFIG_DIR>/gate-hooks/<run id>/`, outside the workdir, per step; no env or secret.
- **Advisory.** A hook that crashes, times out or cannot reach its host prints nothing and the agent goes on (except with `on_tool_call` pack checks enabled, above: then PreToolUse fails closed); a check the host cannot run allows the stop; a host that cannot start (no folder, no socket) runs the step without hooks. The worker's gates, their order, their messages and the retry policy (`NO_AUTO_RETRY`) are unchanged and still decide. Each block is one record and one log line (`gate hook sent the agent back`).

**Scope gate (decision changed 2026-11-25: coverage rule at the top; before: see History).** Before every push the worker checks the files the branch changes against the item's `allowed_paths` with `isCovered`. The diff is cumulative: `git diff --name-only -z --no-renames <base-sha>...HEAD`, where `<base-sha>` is the base sync before push (below) merged in; it must contain the base the sandbox resolved before any agent ran (`SandboxHandle.base_sha`; `untrusted_base` otherwise). A violation fails the run with `scope_violation` (a task failure, never retried automatically: the item blocks on a human with `run_failed:implement:scope_violation`, §5 Restarts), writes no handoffs, makes no push or PR, and posts the full file list on the issue. A gate: no config turns it off.

**Pre-push gates.** The worker's one pre-push step (`prePushGates` in `src/worker/runs/implement/implement-checks.ts`) runs after the implementer exits and before any handoff row or push, in this order:

1. **Scope gate**, as above.
2. **Size gate.** `git diff --numstat -z -M <base-sha>...HEAD` gives added plus deleted lines and the changed file count (`diffStat` in `src/core/diff-gate.ts`; a binary file is one file and zero lines, a rename is one file). Over `max_diff_lines` (default 1500) or `max_diff_files` (default 40) the run fails with `diff_too_large`, its detail giving both counts and both limits; exactly at a limit passes. This failure is not retried automatically: the controller comments the numbers and limits on the issue and blocks the item on a human with `run_failed:implement:diff_too_large`, so `/retry` reruns the implementer, which must make a smaller change, or `/approve <why>` approves a one-time cap (04-split-specs; changed 2026-11-24: the dashboard's over-cap Approve opens a note dialog).
   **Diff budget during the agent step (decision changed 2026-11-07, issue #217).** The implement run's prompt has a "Diff budget" section with the item's project's resolved `max_diff_lines` and `max_diff_files`, and `prompts/implement.md` tells the implementer that the run stops when the diff goes over it. While the implement agent step runs, the worker reads the committed branch diff against the base resolved before the run (`<base-sha>...HEAD`, counted by `diffStat`) every `DIFF_CHECK_MS` (30 s, a constant in `src/worker/support.ts`), waiting on the injected `Clock`. How the read is kept from the agent: History. A diff over either limit aborts the agent step before it finishes (the lease wins over it; a pause that comes at the same moment loses to it); no later agent step (merge, fix) runs, nor sync, the gates or the checks. The worker then distrusts the agent's git config as after any agent step, pushes the run's commits through the broker to its wip branch `<branch_prefix>wip/<item id>/<run id>` (§5 Restarts) and records the wip ref in the failed outcome; it does not push the PR branch and opens no PR. The run fails with `diff_too_large`, its detail in the gate's own words (both counts, both limits), so the controller's comment and suggested split are unchanged.
3. **Floor check on the real diff.** Every path the diff touches (both paths of a rename) is matched against the floor list (`floorHits`); a path under a floor whose tier is above the item's tier is a hit. Hits are not a failure: the run succeeds with the hits as data, nothing is pushed, no PR is opened, and the controller sets `blocked_on: human`, `blocked_reason: floor_tier` (stage stays `RUNNING`), records a `floor_blocked` row with the required tier, and comments each floor path with the tier it needs. `/approve` from a user with write permission raises the tier to the required tier (never lowers it), clears the block, adds one to `restart_count` so the new implement run has a new key, and records `floor_tier_approved` with the approver's user ID. `/reject` closes the item. `/retry` is refused: a floor block is not a failed run. An item already at or above the floor's tier pushes as before. The floor list itself is unchanged.

**Sync before push.** Every implement run, including a review fix on an open PR, now syncs with the base after the implementer exits and before the pre-push step (`syncBase` in `src/worker/runs/implement/implement-sync.ts`):

1. Fetch `origin/<base_branch>` and resolve it to a commit. That commit is the merged-in base: the scope gate, the size gate and the floor check all diff against it (`<base-sha>...HEAD`), so files only the base changed are not counted against the item.
2. A base already in the branch: nothing to do. Otherwise merge it with a merge commit (`git merge --no-ff`), never a rebase and never a force push. Git hooks are off for the worker's merge and commit (the agent's writable git dir could hold one).
3. On a conflict, the same run gets an agent step (the implement prompt and tools, same writable git dir) whose prompt lists the conflicting files and the base commits since the fork that touched them. The agent resolves and stages; **the worker decides**: no unmerged paths left, the merge not aborted, nothing unstaged or uncommitted, no conflict markers (`<<<<<<<` / `>>>>>>>` at a line start) in the conflicting files, then the check list passes (`repo.check_commands`) and HEAD did not move during it, then the worker commits the merge.
4. **A failed conflict step is retried once as a resolve step.** In the same run, the worker puts the branch back on the implementer's last commit (`read-tree`, `checkout -f -B`, `reset --hard`, `clean -ffd`; ignored files stay), merges the base again and runs a second agent step with the resolve prompt (`prompts/resolve.md`, runner role `resolve`, same tools and writable git dir; prompt: `renderResolvePrompt` plus what the first step failed on, with failing tests and output tail). The worker stages the conflicting files and tracked changes itself, then the same checks as step 3 apply. Its transcript is `<run>.resolve.json` beside `<run>.merge.json`.
5. Both steps failing (unmerged paths, an aborted merge, unstaged changes, markers, failing tests or a moved HEAD): the run fails with `merge_conflict` (decision changed 2026-11-18, see History: failing only on grantable test files outside `allowed_paths` asks for them, 05-merge-conflict.md), a task failure (not infra) that counts toward `max_attempts` like `scope_violation`. Nothing is pushed (an open PR is unchanged), no handoff is written, and the worker posts the conflicting files on the issue saying nothing was pushed; the controller's failure table labels the code. A retry is a new run, which syncs again.

**Scope gate and conflicting files.** The scope gate still covers the conflict resolution, as this section requires of any push path, with one exception: a file the base merge conflicted in (both sides changed it) passes whatever `allowed_paths` says (`scopeViolations(diff, allowed_paths, conflicts)` in `src/core/policy.ts`; the resolve run's gate already had this rule). A resolution that changes any other file outside `allowed_paths`, or an implementer change to an unrelated file outside them, still fails with `scope_violation` and pushes nothing. A succeeded implement run that resolved conflicts records them in its outcome (`data.conflicts`), for the conflict counts (§5 Merge conflict). Unchanged: the floor list, the size limits and the tiers.
**Gate commands and the resolve run's gates (decision changed 2026-11-26, wi_a4ee0778; replaces "argv only, run in the run folder", see History).** Gate config keys in `factory.config.json` (no shell): `repo.install_command` (default `["npm","ci"]`), `repo.install_commands` (a list of gate entries run in order in its place) and `repo.test_command` (default `["npm","test"]`, unchanged). A gate entry is an argv, run in the run folder, or `{ "dir": <folder>, "argv": [...] }`, run in that folder inside the run folder (04-gate-commands). A bad value fails at startup naming the entry. They run in the sandbox with the worker's tool env (no credential) and `run_timeout_ms`. Who runs what:

- **Update run** (§5): the check list (`repo.check_commands`), stopping at the first failure; the outcome and the PR comment name the failing command. A failure is `update_tests_failed` (no push, `merge_conflict_pending`).
- **Resolve run** (§5 Merge conflict): after the agent exits and before any push, the worker runs these checks in order. Each failure throws and nothing is pushed; the controller enqueues the next automatic attempt while under the limit, else re-blocks the item on `merge_conflict_pending` (since 2026-11-02, §5):
  1. **Scope gate (hard, worker-side).** The worker trusts none of the agent's index, refs or commits. It writes a *before* tree (a copy of the merge's index, `git add -A`, `write-tree`) before the agent starts and an *after* tree (that index reseeded from *before*, `git add -A`, `write-tree`) after it exits. Every path in `git diff --name-only -z --no-renames <before> <after>` must be one of the conflicting files or covered by `allowed_paths` (`isCovered`). Any other path fails the run with `out_of_scope`, and its detail names the files (`resolveScopeViolations` in `src/core/resolve.ts`). Scope is measured against the pre-agent merge state, not the branch against base, so files only the base changed come in with the merge without counting against the run.
  2. **Conflicts resolved.** Conflict markers (`<<<<<<<` / `>>>>>>>` at a line start) left in a conflicting file of the *after* tree fail with `unresolved_conflicts`.
  3. **The worker makes the commit.** `git commit-tree <after> -p <branch tip> -p <base sha>` (both resolved before the agent ran; no index, no hooks), so the pushed commit's tree is exactly the checked tree and the agent's own commits are dropped. The worker then resets the real index from that commit, checks the branch out on it with `-f` and runs `git clean -ffdx`, so the gate commands test what is pushed. Every git command the worker runs after the agent has `core.hooksPath=/dev/null` (the agent can write hooks into the shared git dir). If the base was already in the branch and nothing changed, the branch tip is kept.
  4. **Install, then the checks.** The install step (`repo.install_commands`, else `install_command`), then each command of the check list (`repo.check_commands`). If one exits non-zero, times out or cannot start, the run fails with `tests_failed`; its detail names the command.
  5. **HEAD unchanged.** The gate commands run repo code; if HEAD is no longer the worker's commit afterwards, the run fails with `head_moved`.
  6. Store the branch through the broker's `git.store_branch` and record a keyed `push` intent; outbound pushes it (same branch, same PR, never a force push; RFC 0015 M7, 10-event-driven.md). A refused store fails with its broker code; a forge push failure is outbound's retry.

  The implement run's pre-push step (scope against base, size, floor) does not run for a resolve, and the implement path keeps its own gate; a separate hard CI scope gate is still open (`PLAN.md`, Phase 2 step 1). **Known gap:** a resolve that touches a floor path inside `allowed_paths` is not floor-checked again. The review that follows rechecks the tier.

**Pre-push checks.** The implement run runs the repo's checks before every push, with one fix step.

- **The factory lowers shrunk ratchet counts (decision changed 2026-11-18; before: see History).** The implement run's checks set `SF_RATCHET_SHRINK=1`: the ratchet lowers fallen known-violations entries, never raises or adds; growth fails. Committed alone, then gated.

- **One check list.** `repo.check_commands` in `factory.config.json`: a list of gate entries (an argv or `{ dir, argv }`, no shell), run in order, each in its folder (`runChecks` passes it as `cwd`), stopping at the first failure. Absent: `[repo.test_command]` (`checkCommands` in `src/core/checks.ts`). A value that is not a non-empty list of valid entries fails at startup naming the entry. The same list runs everywhere a check ran before: the implement run's merge-conflict step (sync, below), the update run in place of `test_command`, and the resolve run after the install step. So checks can run twice in one implement run (conflict step, then before push).
- **Done-when checks run in the round (new decision 2026-11-22, RFC 0024 WP3 phase 2).** An item's `done_checks` (04-triage) run with the list, through the same selection, sandbox, env, timeout and output cap (`doneCheckRound`, `src/core/checks.ts`): a `test_file` check is `repo.test_command` on that file only, after the list; a `command` check is that list command, not run twice; a `manual` line runs nothing. A failing one is a failed check (fix step, `checks_failed`, base rerun as is; a missing test file: top); the fix prompt, comment and run detail name its line. Each line's result (`pass`, `fail`, `manual`, `not_run`) is in the outcome's `done_checks`; `run-results.unit.ts` copies it (JSON) to the state change. Null `done_checks`: as before.
- **Where.** After sync and the pre-push gates (scope, size, floor), before any handoff row or push. A floor block pushes nothing, so it runs no checks. The working tree is first made the committed branch (`reset --hard`, `clean -fd`, ignored files stay) when anything is uncommitted, so the checks see what is pushed.
- **One fix step.** A failing check gets one agent step in the same run: the implement prompt, write tools and the run's writable git dir (as the merge step), with the failing command, how it failed and the output tail (the last 2000 characters). The tail goes through the egress scan first; a finding drops it from the prompt. The agent commits the fix; handoff rows and the commit count include it. Then the whole list runs again, then the scope, size and floor gates again on the final diff (a fix outside `allowed_paths` fails with `scope_violation` and pushes nothing).
- **Second failure.** Unless the base rerun (next) reads it as the environment's, the run fails with `checks_failed`, a task failure (not infra) that the controller retries with backoff up to `max_attempts` (§5 Restarts), or, when its only failing test files are outside `allowed_paths` and quote text the branch removed, grants them once and runs again (top, 2026-11-25). One comment on the issue, keyed on the run (`<!-- factory:checks:<run id> -->`), names the failing command; nothing goes to the PR branch and no handoff row is written. The commits are kept on the run's wip branch (§5 Restarts), so the retry starts from them: it runs no implement agent, and its checks get their own fix step.
- **Base rerun (decision changed 2026-11-07).** On a second failure, the worker reruns only the test files the failing check's output names (`failingTestFiles`, `src/core/checks.ts`), with the same command (the files appended, after `--` for `npm`: `withTestFiles`) and the same env and timeout, in the same sandbox. It runs on a temporary detached worktree of the synced base commit, `.factory-base` inside the run folder, removed afterwards whatever the result. When every one of those files also fails there (each is named in the base run's `FAIL` lines), the run fails with `checks_env` (§5 Restarts) and one comment, keyed on the run (`<!-- factory:checks:<run id> -->`, the same key, so one comment per run), names the files; a failed post is logged and the run fails the same way. Otherwise it stays `checks_failed`.
- **PR body (decision changed 2026-11-22; before: see History).** A successful run's PR body has one "Checked before push: `<command>` passed" line per command (`(after one fix step)` when one ran), then one "Not run, a person checks it" line per `manual` done-when line, under its `## Tests` heading; the body's full layout is in `04-agents.md` (PR body and incomplete PRs).
- **Checks run with no database (decision changed 2026-11-13, issue #579; before: see History).** Check commands get the worker's tool env and its slot env (`SF_WORKER_INDEX`, `SF_TEST_WORKERS`) only (and `SF_RATCHET_SHRINK`, above; in the merge check, `TZ` from `repo.check_tz`, top), in every run. The worker makes no per-run database, redacts no database value from check output and adds no skip line to the PR body.
