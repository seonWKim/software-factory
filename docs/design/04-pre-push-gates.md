# 4. Agents: scope gate, pre-push gates and sync before push

**Gate hooks during the agent step (decision changed 2026-11-07, issue #302; before: see History).** The implement run's main step and its fix step tell the agent about a gate failure while it can still fix it. The worker puts the values its own gates use into the run spec (`AgentRunSpec.gate_hooks`): `allowed_paths`, the run's start SHA, the base SHA (the trusted base for the main step, the merged-in base for the fix step), the project's `max_diff_lines` and `max_diff_files`, the check list (`repo.check_commands`) with the worker's tool env (no credential, no test database URL), the cap `agent_stop_checks` and the Stop blocks earlier steps of the run already used. The `claude-code` runner turns them into two Claude Code hooks (docs/plugins/agent-runner.md):

- **PreToolUse on Edit and Write** refuses a path outside `allowed_paths`, with the scope gate's coverage rule (`isCovered`: an exact path, or under an allowed entry ending in `/`; a path outside the workdir is never covered). The refusal names the allowed paths and says: "This path is outside the approved allowed_paths. If the change needs it, stop and say so in your final message so the owner can add it to the spec." Bash is not path-checked (the sandbox and the scope gate cover it); MultiEdit and NotebookEdit are not offered to the implement role.
- **Stop** sends the agent back while the worker's gates would fail the run, in the gates' order, cheapest first, stopping at the first failure: no commits since the run's start (the worker's rule, `runCommits`: `<start>..HEAD`, then the non-merge commits `<base>..HEAD`, issue #261), with the no-commit reason; a diff over either size limit (`<base>...HEAD`, `diffStat`), with the size gate's own wording (`sizeDetail`); then the check list in order, with the failing command's name and output tail (the last 2000 characters). The tail goes through the egress scanner first, with the same pattern rules; a flagged tail (or a runner with no scanner) is withheld whole. The checks run on the working tree as it is (the hook never resets it) and without the test database, so MySQL runs only in the worker's gate. The Stop hook blocks at most `agent_stop_checks` times per run (default 3, a positive integer or startup fails; main and fix step share the count); the next stop is allowed, so it cannot loop.
- **Files.** The hook script, the spec file it reads and the block record sit in `<CLAUDE_CONFIG_DIR>/gate-hooks/<run id>/`, outside the workdir, made fresh for the step and removed after it. The spec file holds the check values and the path of a private Unix socket, never the env or a secret value. The script forwards the event over the socket to the runner's process, which answers with the shared code (`isCovered`, `runCommits`, `diffStat`/`sizeDetail`, `runChecks`, the scanner), so no rule is copied into the script.
- **Advisory.** A hook that crashes, times out or cannot reach its host prints nothing and the agent goes on; a check the host cannot run allows the stop; a host that cannot start (no folder, no socket) runs the step without hooks. The worker's gates, their order, their messages and the retry policy (`NO_AUTO_RETRY`) are unchanged and still decide. Each block is one record; the runner returns them (`AgentRunResult.gate_blocks`) and the worker writes one log line per block (`gate hook sent the agent back`: `run_id`, `step`, `hook`, `check`, `attempt`).
- **Not in this decision:** triage, review, resolve and update runs and the implement run's merge-conflict step get neither hook; the `openai-compatible` runner has none yet (separate issue); `prompts/implement.md` is unchanged.

**Scope gate (new decision, 2026-11-01):** before every push, the worker checks the files the branch changes against the item's `allowed_paths` with the same coverage rule triage uses for `files_to_change` (exact match, or under an allowed path ending in `/`; `isCovered` in `src/core/policy.ts`). The diff is cumulative: `git diff --name-only -z --no-renames <base-sha>...HEAD`, where `<base-sha>` is the factory repo's `origin/<base_branch>`, resolved by the sandbox before the implementer starts (`SandboxHandle.base_sha`; since 2026-11-01 not the run folder's ref, which the agent can move). `--no-renames` makes a rename a delete plus an add, so both paths are checked; the three-dot range leaves out files only base changed, so merging base in is fine, and merge commits are not skipped. A violation fails the run with `scope_violation` (a task failure, not infra; since 2026-11-02 never retried automatically: the item blocks on a human with `run_failed:implement:scope_violation`, §5 Restarts), writes no handoffs, makes no push or PR, and posts the full file list on the issue. It is a gate, not a dial: no config turns it off. Any future push path (e.g. merge-conflict resolution) must call the same check. Since sync before push (below), `<base-sha>` is the base commit fetched and merged in after the implementer exits, not the one resolved before it started. That fetched base must contain the base the sandbox resolved before any agent ran (`untrusted_base` otherwise).

**Pre-push gates.** The worker's one pre-push step (`prePushGates` in `src/worker/runs/implement/implement.run.ts`) runs after the implementer exits and before any handoff row or push, in this order:

1. **Scope gate**, as above.
2. **Size gate.** `git diff --numstat -z -M <base-sha>...HEAD` gives added plus deleted lines and the changed file count (`diffStat` in `src/core/diff-gate.ts`; a binary file is one file and zero lines, a rename is one file). Over `max_diff_lines` (default 1500) or `max_diff_files` (default 40) the run fails with `diff_too_large`, its detail giving both counts and both limits; exactly at a limit passes. This post-sync gate is unchanged and still runs before any push; when it fails, nothing is pushed and no handoff is written. This failure is not retried automatically (the same spec would likely overreach again): the controller comments the numbers and limits on the issue and blocks the item on a human with `run_failed:implement:diff_too_large`, so `/retry` reruns the implementer, which must make a smaller change. Both limits are positive integers in `factory.config.json`; a zero or non-integer value fails at startup.
   **Diff budget during the agent step (decision changed 2026-11-07, issue #217).** The implement run's prompt has a "Diff budget" section with the item's project's resolved `max_diff_lines` and `max_diff_files` (a project override included; `settingValues`, as the gate reads them), and `prompts/implement.md` tells the implementer that the run stops when the diff goes over it. While the implement agent step runs, the worker reads the committed branch diff against the base resolved before the run (`<base-sha>...HEAD`, counted by `diffStat`) every `DIFF_CHECK_MS` (30 seconds, a constant in `src/worker/support.ts`, not a config key), waiting on the injected `Clock`. The read cannot be changed by the agent's writable git folder: HEAD is resolved through the trusted git env, then the diff runs with `GIT_DIR` set to an empty bare git folder the worker makes for it (`mktemp -d`, `git init --bare --template=`), `GIT_OBJECT_DIRECTORY` the run's objects, no system or global config, and hooks off; the folder is removed after the read. A failed read is logged and tried again at the next interval. A diff over either limit aborts the agent step before it finishes (the lease wins over it; a pause that comes at the same moment loses to it); no later agent step (merge, fix) runs, nor sync, the gates or the checks. The worker then distrusts the agent's git config as after any agent step, pushes the run's commits through the broker to its wip branch `<branch_prefix>wip/<item id>/<run id>` (§5 Restarts) and records the wip ref in the failed outcome; it does not push the PR branch and opens no PR. With no commits, nothing is pushed. A failed wip push is only logged and the run fails without a wip ref. The run fails with `diff_too_large`, its detail in the gate's own words (both counts, both limits), so the controller's comment and suggested split are unchanged. It stays in `NO_AUTO_RETRY`: the item blocks with `run_failed:implement:diff_too_large` and no retry run is queued; `/retry` and `/revise` start from the base, not the wip branch (resuming from it needs a decision). Not in this decision: review and resolve runs, the limits and their defaults, the merge-conflict and fix steps (the post-sync gate covers them). Known gap: the controller's `diff_too_large` comment still says nothing was pushed, though the commits are now on the wip branch (`src/core/controller.ts` was outside this change).
3. **Floor check on the real diff.** Every path the diff touches (both paths of a rename) is matched against the floor list (`floorHits`); a path under a floor whose tier is above the item's tier is a hit. Hits are not a failure: the run succeeds with the hits as data, nothing is pushed, no PR is opened, and the controller sets `blocked_on: human`, `blocked_reason: floor_tier` (stage stays `RUNNING`), records a `floor_blocked` row with the required tier, and comments each floor path with the tier it needs. `/approve` from a user with write permission raises the tier to the required tier (never lowers it), clears the block, adds one to `restart_count` so the new implement run has a new key, and records `floor_tier_approved` with the approver's user ID. `/reject` closes the item. `/retry` is refused: a floor block is not a failed run. An item already at or above the floor's tier pushes as before. The floor list itself is unchanged.

**Sync before push.** Every implement run, including a review fix on an open PR, now syncs with the base after the implementer exits and before the pre-push step (`syncBase` in `src/worker/runs/implement/implement.run.ts`):

1. Fetch `origin/<base_branch>` and resolve it to a commit. That commit is the merged-in base: the scope gate, the size gate and the floor check all diff against it (`<base-sha>...HEAD`), so files only the base changed are not counted against the item.
2. A base already in the branch: nothing to do. Otherwise merge it with a merge commit (`git merge --no-ff`), never a rebase and never a force push. Git hooks are off for the worker's merge and commit (the agent's writable git dir could hold one).
3. On a conflict, the same run gets an agent step (the implement prompt and tools, same writable git dir) whose prompt lists the conflicting files and the base commits since the fork that touched them. The agent resolves and stages; **the worker decides**: no unmerged paths left, the merge not aborted, nothing unstaged or uncommitted, no conflict markers (`<<<<<<<` / `>>>>>>>` at a line start) in the conflicting files, then the check list passes (`repo.check_commands`, since 2026-11-03; before: `repo.test_command`) and HEAD did not move during it, then the worker commits the merge.
4. **A failed conflict step is retried once as a resolve step.** In the same run, the worker puts the branch back on the implementer's last commit (`read-tree`, `checkout -f -B`, `reset --hard`, `clean -ffd`; ignored files stay), merges the base again and runs a second agent step with the resolve prompt (`prompts/resolve.md`, runner role `resolve`, same tools and writable git dir; prompt: `renderResolvePrompt` plus what the first step failed on). The worker stages the conflicting files and tracked changes itself, then the same checks as step 3 apply. Its transcript is `<run>.resolve.json` beside `<run>.merge.json`. The issue asked for the retry "as a resolve on the pushed work"; at this point nothing is pushed and a failed run pushes nothing, so the retry stays inside the run rather than pushing unmerged work first (for the reviewer to confirm).
5. Both steps failing (unmerged paths, an aborted merge, unstaged changes, markers, failing tests or a moved HEAD): the run fails with `merge_conflict`, a task failure (not infra) that counts toward `max_attempts` like `scope_violation`. Nothing is pushed (an open PR is unchanged), no handoff is written, and the worker posts the conflicting files on the issue saying nothing was pushed; the controller's failure table labels the code. A retry is a new run, which syncs again.

**Scope gate and conflicting files.** The scope gate still covers the conflict resolution, as this section requires of any push path, with one exception: a file the base merge conflicted in (both sides changed it) passes whatever `allowed_paths` says (`scopeViolations(diff, allowed_paths, conflicts)` in `src/core/policy.ts`; the resolve run's gate already had this rule). A resolution that changes any other file outside `allowed_paths`, or an implementer change to an unrelated file outside them, still fails with `scope_violation` and pushes nothing. A succeeded implement run that resolved conflicts records them in its outcome (`data.conflicts`), for the conflict counts (§5 Merge conflict). Unchanged: the floor list, the size limits and the tiers. The implement prompt states the migration rule: when both sides add a migration with the same number, the base keeps its number and ours is renumbered to the next free number in every schema file.
**Gate commands and the resolve run's gates.** Two argv config keys in `factory.config.json` (no shell): `repo.install_command` (default `["npm","ci"]`) and `repo.test_command` (default `["npm","test"]`, unchanged). A value that is not a non-empty array of non-empty strings fails at startup. They run in the sandbox's run folder with the worker's tool env (no credential) and `run_timeout_ms`. Who runs what:

- **Update run** (§5): the check list (`repo.check_commands`, since 2026-11-03; before: `test_command` only), stopping at the first failure; the outcome and the PR comment name the failing command. A failure is `update_tests_failed` (no push, `merge_conflict_pending`).
- **Resolve run** (§5 Merge conflict): after the agent exits and before any push, the worker runs these checks in order. Each failure throws and nothing is pushed; the controller enqueues the next automatic attempt while under the limit, else re-blocks the item on `merge_conflict_pending` (since 2026-11-02, §5):
  1. **Scope gate (hard, worker-side).** The worker trusts none of the agent's index, refs or commits. Before the agent starts it copies the merge's index (written by the worker, so every tracked path is in it, `.gitignore`d or not) to a separate index file, runs `git add -A` into it and `write-tree`: the *before* tree. After the agent exits it reseeds that index from the *before* tree (`read-tree`, so no skip-worktree or assume-unchanged bit the agent set survives), runs `git add -A` again and `write-tree`: the *after* tree. Every path in `git diff --name-only -z --no-renames <before> <after>` must be one of the conflicting files or covered by `allowed_paths` (`isCovered`). Any other path fails the run with `out_of_scope`, and its detail names the files (`resolveScopeViolations` in `src/core/resolve.ts`). Scope is measured against the pre-agent merge state, not the branch against base, so files only the base changed come in with the merge without counting against the run. Untracked files that `.gitignore` matches are not in either tree, so they are never pushed.
  2. **Conflicts resolved.** Conflict markers (`<<<<<<<` / `>>>>>>>` at a line start) left in a conflicting file of the *after* tree fail with `unresolved_conflicts`.
  3. **The worker makes the commit.** `git commit-tree <after> -p <branch tip> -p <base sha>` (both resolved before the agent ran; no index, no hooks), so the pushed commit's tree is exactly the checked tree and the agent's own commits are dropped. The worker then resets the real index from that commit, checks the branch out on it with `-f` and runs `git clean -ffdx`, so the gate commands test what is pushed. Every git command the worker runs after the agent has `core.hooksPath=/dev/null` (the agent can write hooks into the shared git dir). If the base was already in the branch and nothing changed, the branch tip is kept.
  4. **Install, then the checks.** `install_command`, then each command of the check list (`repo.check_commands`, since 2026-11-03; before: `test_command`). If one exits non-zero, times out or cannot start, the run fails with `tests_failed`; its detail names the command.
  5. **HEAD unchanged.** The gate commands run repo code; if HEAD is no longer the worker's commit afterwards, the run fails with `head_moved`.
  6. Store the branch through the broker's `git.store_branch` and record a keyed `push` intent; outbound pushes it (same branch, same PR, never a force push; RFC 0015 M7, 10-event-driven.md). A refused store fails with its broker code; a forge push failure is outbound's retry.

  The implement run's pre-push step (scope against base, size, floor) does not run for a resolve, and the implement path keeps its own gate; a separate hard CI scope gate is still open (`PLAN.md`, Phase 2 step 1). **Known gap:** a resolve that touches a floor path inside `allowed_paths` is not floor-checked again. The review that follows rechecks the tier.

**Pre-push checks.** The implement run runs the repo's checks before every push, with one fix step.

- **One check list.** `repo.check_commands` in `factory.config.json`: a list of argv (no shell), run in order, stopping at the first failure. Absent: `[repo.test_command]` (`checkCommands` in `src/core/checks.ts`). A value that is not a non-empty list of non-empty argv fails at startup. This repo lists `npm run typecheck`, then `npm test`, the `run:` steps of `.github/workflows/test.yml` minus `npm ci`; `tests/check-commands.test.ts` fails when a workflow step has no entry or an entry has no step. The same list runs everywhere a check ran before: the implement run's merge-conflict step (sync, below), the update run in place of `test_command`, and the resolve run after `install_command`. So checks can run twice in one implement run (conflict step, then before push).
- **Where.** After sync and the pre-push gates (scope, size, floor), before any handoff row or push. A floor block pushes nothing, so it runs no checks. The working tree is first made the committed branch (`reset --hard`, `clean -fd`, ignored files stay) when anything is uncommitted, so the checks see what is pushed.
- **One fix step.** A failing check gets one agent step in the same run: the implement prompt, write tools and the run's writable git dir (as the merge step), with the failing command, how it failed and the output tail (the last 2000 characters). The tail goes through the egress scan first; a finding drops it from the prompt. The agent commits the fix; handoff rows and the commit count include it. Then the whole list runs again, then the scope, size and floor gates again on the final diff (a fix outside `allowed_paths` fails with `scope_violation` and pushes nothing). Transcript: `<run>.fix.json`.
- **Second failure.** Unless the base rerun (next) reads it as the environment's, the run fails with `checks_failed`, a task failure (not infra) that the controller retries with backoff up to `max_attempts` (§5 Restarts). One comment on the issue, keyed on the run (`<!-- factory:checks:<run id> -->`), names the failing command; nothing goes to the PR branch and no handoff row is written. The commits are kept on the run's wip branch (§5 Restarts), so the retry starts from them: it runs no implement agent, and its checks get their own fix step. The run code `checks_failed` is not the controller's `checks_failed` blocked reason (a failed PR check, §5 CI gate); the two never meet in one table.
- **Base rerun (decision changed 2026-11-07).** On a second failure, the worker reruns only the test files the failing check's output names (vitest's `FAIL  <file> > <name>` lines, `failingTestFiles` in `src/core/checks.ts`), with the same command (the files appended, after `--` for `npm`: `withTestFiles`) and the same env, timeout and test database, in the same sandbox. It runs on a temporary detached worktree of the synced base commit, `.factory-base` inside the run folder (`git worktree add --detach`, hooks off), never the live checkout; it is removed afterwards (`git worktree remove --force`, then `prune`), whatever the result. Lying inside the run folder, it finds the same dependencies the run folder does and writes none of them: the run folder's `node_modules` is shared and read-only (vitest's cache goes to `.vite-cache` in the checkout, `vitest.config.ts`). When every one of those files also fails there (each is named in the base run's `FAIL` lines), the run fails with `checks_env` (§5 Restarts) and one comment, keyed on the run (`<!-- factory:checks:<run id> -->`, the same key, so one comment per run), names the files; a failed post is logged and the run fails the same way. Otherwise it stays `checks_failed` as above: a file that passes or is missing on the base, a check whose output names no test file (lint, typecheck: no base run at all), and a base rerun that cannot start (the worktree cannot be made, the command cannot run or its tools are missing; logged). No `--maxWorkers` flag is added: the test processes' CPU share comes from `SF_TEST_WORKERS` (§5 Coordination).
- **PR body.** A successful run's PR body has one "Checked before push: `<command>` passed" line per command (`(after one fix step)` when one ran), and the test database's skip line when there is one, under its `## Tests` heading; the body's full layout is in `04-agents.md` (PR body and incomplete PRs).
- **Test database (new interface `TestDatabase`, docs/plugins.md).** One database per run, made the first time a check runs and dropped in a `finally` at the end of the run, also when a check failed. `mysql-local` creates `sf_test_<run id>` on a local test-only MySQL server (admin URL `TEST_MYSQL_URL` in the secret file, SET_UP.md) and sets `SF_TEST_MYSQL_URL` in each check command's environment; it refuses any name not starting with `sf_test_`. `none` (the default) sets nothing, so the MySQL tests skip themselves and the PR body says so. The URL is in no agent run's environment, prompt, outcome, comment or log: check output is redacted (the URL and its password) before it is kept. Security: a check runs code the agent wrote with the URL in its environment, so that code can read the test user's password during the checks; the test user may only create, use and drop `sf_test_*` databases on a server with no factory data. That is why this change is tier 4.
- **Not in this decision:** the post-PR CI gate (§5) and `.github/workflows/test.yml` are unchanged; the update run still runs no install; no hosted MySQL; `sf_test_*` databases a crashed run leaves behind are not swept (needs a decision). The checked-in config selects `test_database: none` until `TEST_MYSQL_URL` is added to `.env.example` (outside this change's allowed paths) and the local test user exists; then it switches to `mysql-local`.

## History

- **Gate hooks during the agent step** (decision changed 2026-11-07, issue #302). Before: every implement gate ran only after the agent had stopped. The worker failed a run with `no_commits`, `scope_violation` or `diff_too_large` in its final steps, and those go to a human rather than a retry; the mid-run diff check, which stops the agent over budget, was the only check during the run, so the agent was never told of a gate failure while it could still fix it.
- **Base rerun** (decision changed 2026-11-07). Before: every second failure of a pre-push check was `checks_failed`, a task failure, with no look at whether the failing tests also fail on the base branch, so a test that times out under load cost the item attempts and an owner `/retry`.
- **Diff budget during the agent step** (decision changed 2026-11-07, issue #217). Before: "Nothing is pushed and no handoff is written" for every `diff_too_large`; the size gate ran only in the pre-push step, after the whole agent step, the base merge and the checks, so an over-budget run spent its full agent run first, and the implementer was never told its limits. Its commits went with the run folder.

- **Sync before push** (decision changed 2026-11-01). Before: an implement run pushed its branch as it was built on the base resolved when the run started, so a base that moved during the run could open a PR that already conflicted, as #66 and #70 did; and the scope gate's `<base-sha>` was resolved before the implementer started.
- **A failed conflict step is retried once as a resolve step** (decision changed 2026-11-02). Before: the agent got one try, and a miss failed the run, whose retry rebuilt the implementation from scratch.
- **Scope gate and conflicting files** (decision changed 2026-11-02). Before: a conflicting file outside `allowed_paths` failed with `scope_violation` like any other, so a base change to a shared file stopped the run although that side of the conflict was not the item's doing.
- **Gate commands and the resolve run's gates** (new decision, 2026-11-01). Before: the only command gate was `repo.test_command` in the update run, and no gate ran the repo's install.
- **Pre-push gates** (decision changed 2026-11-01): the pre-push step now holds three checks, not only the scope gate, and the floor check now also looks at the files a branch really changes, not only at the `allowed_paths` triage listed.
- **Resolve run scope gate** (decision changed 2026-11-01 after review): the gate now measures the tree that is pushed. Before: two working-tree snapshots, with the agent's own commit pushed after them.
- **Pre-push checks** (decision changed 2026-11-03, issue #158). Before: the implement run pushed and opened its PR right after the pre-push gates, with no check command at all; `repo.test_command` ran only in the merge-conflict step and the update run, neither had a MySQL server, and the typecheck ran in no factory step, so CI found failures only after the PR existed and each cost a new implement loop or a manual fix, as #145, #151 and #154 did.
