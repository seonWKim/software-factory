# 3. Risk

- **The red-main check runs the UI check only on a change to its paths (decision changed 2026-11-27, wi_3ded861c; changes the UI check in "Red main is raised in any mode" and in the revert below, where it ran on the new base tip after every automatic merge; before: see History).** After an automatic merge the red-main check runs the install command and the checks on the new base tip, then `repo.ui_check.command` only when the tip's own change, the diff from its first parent to the tip, touches one of `repo.ui_check.paths` (the merge check's rule, `touchesUi`). The changed files come from the sandbox (`localChangedFiles`, an optional read beside `localBranch`, design `plugins/sandbox.md`; objects only, no fetch). When they cannot be read (no such read, a failed read), the UI check runs. The re-run on a reverted tip takes the same rule: the revert undoes the merge's change, so it runs the UI check when the merge did. Why: a merge that touched only backend files ran the slow browser check, and its failure there (a missing Chrome, say) counted as red main.
- **A bad automatic merge is reverted instead of stopping auto mode (decision changed 2026-11-23, wi_7454238f; changes "Stop conditions" under Auto mode below, where any red main after an automatic merge stopped auto mode and nothing reverted it; before: see History).** After each red-main check on the new base tip that passes, the tip is stored per project in `controller_green_bases` (migration `20261123T1001-controller-green-base`, no backfill: a merge with no stored green base is never reverted). When a check fails (not when the checks could not run) on the tip of a local item's merge made by `system:auto` within the last hour, whose first parent is the stored green base, the controller reverts that one merge on the local base (`revertLocal` on the sandbox, an optional capability checked at runtime, design `plugins/sandbox.md`; never pushed to origin: auto mode never merges a GitHub item) with git's own message `This reverts commit <sha>`, so the revert tracking records a `reverted` state change and implicit verdict on the item as for any revert (design 06-measurement). The item's branch gets the change back on top of the revert. The install command, the checks and the UI check (by the path rule above) run again on the reverted tip. The item reopens at implement as a loop, as a failed merge check sends it (`merge_check_failed`: CLOSED → RUNNING, `loop_count` + 1, its close and `merge_sha` cleared, detail `{ reverted, merge_sha, revert_sha, command, how, failing_tests, output_tail }`), or at `max_loops` waits in REVIEW on a person (`max_loops`); after an automatic merge the Rule of Two still holds that implement run for a person's `/approve`. Green again: the `red_main` alert on the merge is raised with a note that it was reverted, no fix item is filed and auto mode goes on. Still red: red main as today on the reverted tip (alert, fix item, auto mode back to manual), and the revert is not undone. A merge by a person, one older than an hour, a tip that moved past the merge, or a base that was already red (not the stored green base) is not blamed on the merge: no revert, no reopen, and the stop below. Every step is conditional (the base at the merge, the item still closed by it), so a second run or another replica changes nothing. Code: `src/controller/units/local-merge/red-main.ts`. Owner choices taken as proposed: a revert counts as a loop; a revert that cannot be made counts as not green.
- **Red main is raised in any mode and blames no change (decision changed 2026-11-18; changes "Stop conditions" under Auto mode below, where red main was only the checks after an automatic merge and only stopped auto mode; before: see History).** Red main is the base failing a check on its own: the merge check's UI check failing on the base alone too (`why: base_red`, design 04-pre-push-gates), or the install command, the checks or the UI check (`repo.ui_check.command`, when the merge's change touches its paths: the path rule above) failing or not running on the new base tip after an automatic merge. On red main, in manual and auto mode (`LocalMergeUnit.redMain`): one `red_main` alert keyed on the base sha (`red_main:<sha>`, the kernel's `alert` write; the same sha again within the dedupe window stores nothing), shown by `alarmText` with a fix hint naming the sha; one fix item filed through outbound (`file_fix_item`, keyed on the sha, marker `<!-- factory:red-main:<sha> -->`, by the first source in `plugins.source` order with `fileIssue`; none: a warning, no filing); and, in auto mode only, the auto mode stop below. The merge queue keeps a change checked on a red base queued (no loop, no removal, `loop_count` unchanged) and does not check it, or any queued entry behind it, again while the base tip (the local base the queue lands on, as the controller reads it) is the one it was held on. Owner answers: queued changes wait (not land with the check skipped), a red main from the UI check counts as red main for auto mode, and the alert shows in manual mode too.
  - **The red-main check keeps what failed (added 2026-11-21, wi_4b25c5c4).** After an automatic merge the check runs through the merge check's runner (`runChecks`), and the `red_main` alert's detail keeps the failing tests (at most 10, `failingTestNames`) and the output tail (at most 2000 characters) as JSON `{ text, failing_tests, output_tail }`, read back by `redMainDetail` (`src/ui/alarms.ts`). The tail is egress-scanned as run outcome text first; a flagged tail is stored as null and the names are kept. No new table or column; no backfill: an older alert, or one raised at the merge check, keeps its text alone. The overview carries them on the red_main alarm and a red_main `auto_stop` for What failed (design 09-dashboard-tasks-needs).
- **The architecture ratchets are on the gate list (decision changed 2026-11-09, owner decision; before: `tests/architecture/` was not on it, so an agent's change could grow a known-violations list or weaken a ratchet and merge without the owner, see History).** `tests/architecture/` is in `PROTECTED_PATHS.gates` (`src/core/standing.ts`) and so in `GATE_PATHS`: a change to a ratchet or its `known-violations/*.json` needs a human merge, auto mode never approves or merges it, and no standing rule approves its spec. Consequence: a spec whose allowed paths name all of `tests/` touches the gate list too (a folder that holds a gate path), so it always waits for the owner; a spec that names its test files or a narrower folder (`tests/helpers/`) does not. Solo and enterprise are the same.
- **Auto mode (decision changed 2026-11-08, issue #444; before: both gates always waited for a person and the auto-merge dial was fixed at 0, see History).** The `mode` setting is `manual` (the default, and when nothing is stored) or `auto`, read through the live settings at each decision point (`modeOf`), never cached past one tick. Manual is the behaviour before this change. In auto mode:
  - **Specs.** A spec that would wait at the spec gate is approved by the controller where it already approves one (`spec_approved`, actor `system:auto`, detail `approved_by: system:auto` and `mode_change`, the audit seq of the mode change it ran under) when it is below tier 4, none of its allowed paths touches the gate list, and every decision has a proposed default and is not owner-only (`autoApproveRefusal`). The answers taken are posted in the thread with the spec. The implement run it would start holds all three Rule of Two facts, so it waits for a person's `/approve` (`blocked_reason: rule_of_two`, since 2026-11-09; design 10-event-driven, "Run roles"). Triage writes each decision as `{ text, default, owner_only }`; a plain-text decision, or one with no flag or no default, counts as owner-only and waits. Any other spec waits for `/approve` as before, and its spec comment says why. A split spec always waits; the standing rule `spec-t1` runs first and is unchanged.
  - **Merges.** A local item waiting in `merge_pending` merges through the one local merge (`Controller.mergeLocal`, its conditional base move), actor `system:auto`, detail `mode_change`, when it is below tier 4, neither its allowed paths nor its changed files touch the gate list, it is not incomplete, its tier is at most `auto_merge_max_tier`, and its tier's merge record holds (next line) (`autoMergeRefusal`). The install command and the checks run on the merge commit first: a failure or a conflict moves nothing and leaves the item in `merge_pending`, with one reply per item version (no retry each tick). A refusal by rule is posted once and the item waits for `factory merge`. A GitHub item is never merged in auto mode (there is no forge merge to call); it waits as in manual mode, with no post.
  - **Per-tier rule and drop-back (decision changed 2026-11-22, wi_f9e6887d, phase 2 of 2 of "per-tier auto-merge drop-back"; before: a tier at most `auto_merge_max_tier` always merged, whatever its record, see History).** Under the setting, a tier merges automatically only while its merge record holds. At each auto merge the step (`autoMergeStep`) reads the merge record from the store once (`listMergeEvaluations`, in the controller reader's read list; nothing is cached across steps, so every replica reads the same record) and passes two results for the item's tier (the tier stored at merge time) to `autoMergeRefusal`: **the rule** (`tierRule`, [06-measurement.md](06-measurement.md)): the tier's last 50 merges hold at most 1 reverted or fixed-forward merge and no critical verdict; fewer than 50 merges never qualify, so a tier waits for a person until it has 50 (owner's default); and **the drop-back** (`droppedBack`, `src/core/stats.ts`, pure): 2 or more of the tier's last 20 merges reverted or fixed forward refuse it, 1 does not. With 50 merges, 2 bad in the last 20 already fail the rule; the drop-back names the cause first. The refusal names the tier and the rule (for example "tier 2 dropped back: 2 or more of its last 20 merges were reverted or fixed forward", "tier 2 does not meet the auto-merge rule: it has fewer than 50 merges") and is posted once, as any refusal above. The stored `auto_merge_max_tier` is never written: the tier merges again by itself once its record holds. `canAutoMerge` (the PR body's merge note) reads the setting only.
  - **Auto-merge tier.** `auto_merge_max_tier` is a settable key (0 to 3, default 0, so auto mode merges nothing until the owner raises it); 4 or more is refused. The file's `dials.auto_merge_max_tier` must stay 0. Tier 4 and the gate list never merge automatically, whatever it says.
  - **The gate list** is one list, `GATE_PATHS` (`src/core/improver.ts`): the merge check's owner-only paths widened with every standing-rule protected path (`PROTECTED_PATHS`, which holds `src/impl/grant/` and `src/core/tools/`). A path touches it when it is on it, under it, or a folder that holds one of its paths (`src/` holds `src/core/policy.ts`).
  - **Stop conditions (decision changed 2026-11-13, owner decision; before: any alert the alarm step stored stopped auto mode, see History; red main after an automatic merge changed 2026-11-23, see the revert decision at the top).** A red main (the decision at the top: the UI check fails on the base alone at the merge check, or the install command, the checks or the UI check fail, or cannot run, on the new base tip after an automatic merge, unless the revert of that merge makes the base green again), a child crash loop (`child_restarts`) or a budget checkpoint sets the mode back to manual at the level it is stored at: one `auto_stopped` alert (error code `red_main`, `failure_alert` or `budget_checkpoint`), keyed on the mode change it ends so a re-run or another replica stores nothing, then one `runtime_settings_changes` row by `system:auto`. A failure alarm about agent runs stops the task only and lets the owner know: its alarm is stored and open, and its new `repeated_error` alert holds the items it hit (`blocked_on: human`, `recurring_failure`, so their queued runs are not claimed) until a person lifts the hold or the filed fix merges; auto mode goes on. Why: five stops from 2026-11-08 to 2026-11-13 all came from agent-run failure alarms (`agent_stalled`, `invalid_output`, `checks_env`, `start_to_close`), the owner set auto again each time, and the hold already keeps a failing item from merging unchecked. `stopsAuto` (`src/core/alarms.ts`) holds the rule. No new budget cap. Per pattern and error code:

    | Alarm pattern / error code | Stops auto | Why |
    |---|---|---|
    | `red_main` (`auto_stopped`) | yes | Main is red. |
    | `budget_checkpoint` | yes | A budget checkpoint; unchanged. |
    | `child_restarts` | yes | A crash loop is the factory itself, not an agent run. |
    | `dead_letter` | no | Not a stop before either: the bus handler stores it outside the alarm step, and the owner's answer adds no new stop. |
    | `zero_tokens` | no | The model_stall pause already holds every claim. |
    | `repeated_error` with `agent_stalled`, `invalid_output`, `checks_env` or `start_to_close` | no | An agent-run failure: the alarm shows and its items are held. |
    | `repeated_error` with any other code | no | Owner decision: a failure alarm stops the task only (its items are held); auto mode still runs. |
    | `spend_budget` | no | It only alerts (design 06-spend); unchanged. |
  - **The last stop is shown (decision 2026-11-13).** While the newest `mode` change is a stop's (by `system:auto`), the Mode toggle on the Settings page and its line in the Needs-you notes (the system banner) say when and why ("Back to manual at 11:52: the checks failed on the base branch after a merge"), link to the stop's alarm, and show "Turn auto back on", which since 2026-11-22 asks in the shared Dialog first and on Confirm writes mode auto through the same `POST /api/v1/settings` as the toggle (design 09-dashboard-settings; before, it wrote at once, with no confirmation, see History). The stop's alarm text names its time. Read from the newest `auto_stopped` alert (`lastAutoStop`, `src/ui/alarms.ts`); the text comes from `web/src/i18n`.
  - **Solo and enterprise.** Solo: the mode is global, flipped by the local identity, which as the local owner holds `approve_merge` with no setup. Enterprise: `mode` takes `--project`, every flip of `mode` or `auto_merge_max_tier` needs `approve_merge` on the project (refused, no row written, otherwise), and every replica reads the stored row at its next tick.
- **Tier** = max(agent judgment, human floors). Rechecked at review; never lowered.
- **Floors cover every credential reader (decision changed 2026-11-07; before: see History).** A floor is a path prefix in `factory.config.json`, a folder or a single file. Besides the folders (runner, broker, egress, secrets, auth, `.claude/`), the two GitHub credential files have their own tier-4 file floors: `src/impl/github/app-credentials.ts` and `src/impl/github/token-credentials.ts`. The rest of `src/impl/github/` keeps no floor. `tests/credential-floors.test.ts` reads the floors from the checked config and fails for any src file that imports the SecretStore interface or names a secret with `secretName()` unless a tier-4 floor covers it or it is on the test's exempt list with a reason. The other secret readers (Slack, Claude and OpenAI-compatible providers, `src/setup.ts`, and the `migrate` and `setup` commands under `src/cli/handlers/`, moved from `src/main.ts` on 2026-11-08) are exempt as "follow-up" until a separate task floors them. Solo and enterprise are the same: floors change only through a reviewed PR to the checked config.
- Tier ≥ 3: human approval. Tier 5: rollout plan.
- `spec_gate_min_tier` starts fully gated; the file's `auto_merge_max_tier` dial stays 0, and the live `auto_merge_max_tier` setting (default 0) acts only in auto mode.
- **Ratchet:** moving a dial toward safety is automatic + notify. Loosening or any structural change is a human decision backed by a number.
