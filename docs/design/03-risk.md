# 3. Risk

- **The architecture ratchets are on the gate list (decision changed 2026-11-09, owner decision; before: `tests/architecture/` was not on it, so an agent's change could grow a known-violations list or weaken a ratchet and merge without the owner, see History).** `tests/architecture/` is in `PROTECTED_PATHS.gates` (`src/core/standing.ts`) and so in `GATE_PATHS`: a change to a ratchet or its `known-violations/*.json` needs a human merge, auto mode never approves or merges it, and no standing rule approves its spec. Consequence: a spec whose allowed paths name all of `tests/` touches the gate list too (a folder that holds a gate path), so it always waits for the owner; a spec that names its test files or a narrower folder (`tests/helpers/`) does not. Solo and enterprise are the same.
- **Auto mode (decision changed 2026-11-08, issue #444; before: both gates always waited for a person and the auto-merge dial was fixed at 0, see History).** The `mode` setting is `manual` (the default, and when nothing is stored) or `auto`, read through the live settings at each decision point (`modeOf`), never cached past one tick. Manual is the behaviour before this change. In auto mode:
  - **Specs.** A spec that would wait at the spec gate is approved by the controller where it already approves one (`spec_approved`, actor `system:auto`, detail `approved_by: system:auto` and `mode_change`, the audit seq of the mode change it ran under) when it is below tier 4, none of its allowed paths touches the gate list, and every decision has a proposed default and is not owner-only (`autoApproveRefusal`). The answers taken are posted in the thread with the spec. The implement run it would start holds all three Rule of Two facts, so it waits for a person's `/approve` (`blocked_reason: rule_of_two`, since 2026-11-09; design 10-event-driven, "Run roles"). Triage writes each decision as `{ text, default, owner_only }`; a plain-text decision, or one with no flag or no default, counts as owner-only and waits. Any other spec waits for `/approve` as before, and its spec comment says why. A split spec always waits; the standing rule `spec-t1` runs first and is unchanged.
  - **Merges.** A local item waiting in `merge_pending` merges through the one local merge (`Controller.mergeLocal`, its conditional base move), actor `system:auto`, detail `mode_change`, when it is below tier 4, neither its allowed paths nor its changed files touch the gate list, it is not incomplete, and its tier is at most `auto_merge_max_tier` (`autoMergeRefusal`). The install command and the checks run on the merge commit first: a failure or a conflict moves nothing and leaves the item in `merge_pending`, with one reply per item version (no retry each tick). A refusal by rule is posted once and the item waits for `factory merge`. A GitHub item is never merged in auto mode (there is no forge merge to call); it waits as in manual mode, with no post.
  - **Auto-merge tier.** `auto_merge_max_tier` is a settable key (0 to 3, default 0, so auto mode merges nothing until the owner raises it); 4 or more is refused. The file's `dials.auto_merge_max_tier` must stay 0. Tier 4 and the gate list never merge automatically, whatever it says.
  - **The gate list** is one list, `GATE_PATHS` (`src/core/improver.ts`): the merge check's owner-only paths widened with every standing-rule protected path (`PROTECTED_PATHS`, which holds `src/impl/grant/` and `src/core/tools/`). A path touches it when it is on it, under it, or a folder that holds one of its paths (`src/` holds `src/core/policy.ts`).
  - **Stop conditions (decision changed 2026-11-13, owner decision; before: any alert the alarm step stored stopped auto mode, see History).** A red main (the install command and the checks fail, or cannot run, on the new base tip after an automatic merge), a child crash loop (`child_restarts`) or a budget checkpoint sets the mode back to manual at the level it is stored at: one `auto_stopped` alert (error code `red_main`, `failure_alert` or `budget_checkpoint`), keyed on the mode change it ends so a re-run or another replica stores nothing, then one `runtime_settings_changes` row by `system:auto`. A failure alarm about agent runs stops the task only and lets the owner know: its alarm is stored and open, and its new `repeated_error` alert holds the items it hit (`blocked_on: human`, `recurring_failure`, so their queued runs are not claimed) until a person lifts the hold or the filed fix merges; auto mode goes on. Why: five stops from 2026-11-08 to 2026-11-13 all came from agent-run failure alarms (`agent_stalled`, `invalid_output`, `checks_env`, `start_to_close`), the owner set auto again each time, and the hold already keeps a failing item from merging unchecked. `stopsAuto` (`src/core/alarms.ts`) holds the rule. No new budget cap. Per pattern and error code:

    | Alarm pattern / error code | Stops auto | Why |
    |---|---|---|
    | `red_main` (`auto_stopped`) | yes | Main is red. |
    | `budget_checkpoint` | yes | A budget checkpoint; unchanged. |
    | `child_restarts` | yes | A crash loop is the factory itself, not an agent run. |
    | `dead_letter` | no | Not a stop before either: the bus handler stores it outside the alarm step, and the owner's answer adds no new stop. |
    | `zero_tokens` | no | The model_stall pause already holds every claim. |
    | `repeated_error` with `agent_stalled`, `invalid_output`, `checks_env` or `start_to_close` | no | An agent-run failure: the alarm shows and its items are held. |
    | `repeated_error` with any other code | no | Owner decision: a failure alarm stops the task only (its items are held); auto mode still runs. |
    | `spend_budget` | no | It only alerts (design 06-spend); unchanged. |
  - **The last stop is shown (decision 2026-11-13).** While the newest `mode` change is a stop's (by `system:auto`), the Mode toggle on the Settings page and its line in the Needs-you notes (the system banner) say when and why ("Back to manual at 11:52: the checks failed on the base branch after a merge"), link to the stop's alarm, and show "Turn auto back on", which writes mode auto at once, with no confirmation, through the same `POST /api/v1/settings` as the toggle. The stop's alarm text names its time. Read from the newest `auto_stopped` alert (`lastAutoStop`, `src/ui/alarms.ts`); the text comes from `web/src/i18n`.
  - **Solo and enterprise.** Solo: the mode is global, flipped by the local identity, which as the local owner holds `approve_merge` with no setup. Enterprise: `mode` takes `--project`, every flip of `mode` or `auto_merge_max_tier` needs `approve_merge` on the project (refused, no row written, otherwise), and every replica reads the stored row at its next tick.
- **Tier** = max(agent judgment, human floors). Rechecked at review; never lowered.
- **Floors cover every credential reader (decision changed 2026-11-07; before: see History).** A floor is a path prefix in `factory.config.json`, a folder or a single file. Besides the folders (runner, broker, egress, secrets, auth, `.claude/`), the two GitHub credential files have their own tier-4 file floors: `src/impl/github/app-credentials.ts` and `src/impl/github/token-credentials.ts`. The rest of `src/impl/github/` keeps no floor. `tests/credential-floors.test.ts` reads the floors from the checked config and fails for any src file that imports the SecretStore interface or names a secret with `secretName()` unless a tier-4 floor covers it or it is on the test's exempt list with a reason. The other secret readers (Slack, MySQL, Claude and OpenAI-compatible providers, `src/setup.ts`, and the `migrate` and `setup` commands under `src/cli/handlers/`, moved from `src/main.ts` on 2026-11-08) are exempt as "follow-up" until a separate task floors them. Solo and enterprise are the same: floors change only through a reviewed PR to the checked config.
- Tier ≥ 3: human approval. Tier 5: rollout plan.
- `spec_gate_min_tier` starts fully gated; the file's `auto_merge_max_tier` dial stays 0, and the live `auto_merge_max_tier` setting (default 0) acts only in auto mode.
- **Ratchet:** moving a dial toward safety is automatic + notify. Loosening or any structural change is a human decision backed by a number.

## History

- Until 2026-11-09: `tests/architecture/` was not on the gate list; a spec allowing `tests/` could be auto-approved and its change auto-merged. Changed to put the ratchets on the gate list above.
- Until 2026-11-07: floors were folders only, and no test checked that credential readers sit under one. The GitHub App and token credential files fell outside every floor, so a change to them could pass at tier 2 or 3. Changed to give each a tier-4 file floor and to add the credential-floor test.
- Until 2026-11-08 (issue #444): a spec was approved only by `/approve`, or by the standing rule at tier 1; a local change merged only through `factory merge`; `auto_merge_max_tier` was fixed at 0 by the startup check and `canAutoMerge` never allowed a merge; decisions had no owner-only marker; and nothing reacted to a red main. Changed to the `mode` setting and the auto-merge tier setting above.
- Until 2026-11-09 (owner decision, RFC 0015 M10): a spec auto mode approved started its implement run at once, with no person, although implement holds all three Rule of Two facts. Changed to hold that run for a person's `/approve` (`rule_of_two`), see the auto mode specs line above.
- Until 2026-11-13 (owner decision): any alert the alarm step stored (a repeated error of any code, a zero-token streak or a child crash loop) stopped auto mode as `failure_alert`, and the toggle showed only "manual", with the reason in an alarm row. Changed to stop on a crash loop only, hold the items an agent-run failure alarm hit, and show the last stop's time and reason beside the toggle and in the banner.
