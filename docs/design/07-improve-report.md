# 7. Self-improvement: the improve report, Run now and rule retirement

- **The improve report and Run now are only on the Rules page (decision changed 2026-11-16, phase 4 of 4 of local-task-tk_3164aaa9-e569-4086-9e6d-013b63474c69-phase-2; current; replaces "`/classic` keeps its improve section and Run now in this phase" of the Rules page decision below, see History).** The decision that changed: **`/classic` is removed (design 09-dashboard-app), so the Rules page (`/app/rules`) is the one place that shows the latest improve report and Run now.** The report's draft and filing lines are built only in `src/ui/rules-api.ts`; `improveSection`, the Health panel's Run now button and its script (`RUN_NOW_SCRIPT`) are deleted from `src/ui/health.ts`. `POST /api/v1/improve/run`, its guards and its 409 rule are unchanged.
- **The Rules page shows the improve report and Run now (decision changed 2026-11-16, phase 1 of 3 of local-task-tk_3164aaa9-e569-4086-9e6d-013b63474c69; current; replaces "the status page shows the latest improve report below Health" and "the status page's Health panel (`/classic`) shows a Run now button" of the Run now decision below, see History).** The decision that changed: **the dashboard app (`/app/rules`) shows the report and Run now, beside the rules the report's patterns feed.** GET `/api/v1/rules` (`src/ui/rules-api.ts`) gains a read field `improve`: `report`, the latest improve report (window, created_at, `runs`, `patterns`, and per failure group its `error_code`, `detail`, `runs`, `draft` as cause and fix or one note, and `filing`; null with none yet), every text through the Withholder; `run_now`, true when `runNowButton` (`src/ui/improve-api.ts`, approve_spec) allows the viewer; and `csrf_token`, the write token, only then. The field is there with the ledger on or off. The page's Improve report section sits below the rules, and above the ledger-off EmptyState with the ledger off; "no improve run has reported yet" with no report. Run now posts `{}` to POST `/api/v1/improve/run` with `x-csrf-token` and shows the queued `run_id`; a 409 shows its error and the `run_id` already queued or running, and the rules are not reloaded. The route, its guards and its 409 rule are unchanged.
- **A stall group that followed a host sleep is not filed, only shown (decision changed 2026-11-15; current; changes "File each recurring failure pattern" and "A fix spec runs unless the draft needs a person or touches a gate path" below, where every group of two or more runs was filed or sent to a person, see History).** The decision that changed: **an `agent_stalled` group one of whose runs held a recorded host sleep is not filed as a fix item in the project's repo.** A host sleep (the machine slept, `worker_host_sleeps`, design 05-restarts) is the factory's host runtime, so the repo holds no code to fix, and a spec triage drafted for it would guess its paths and wait at the spec gate.
  - **Check.** `stalledBySleep` (`src/core/improver.ts`) reads the host sleeps of each item of the group (`listHostSleeps` with `work_item_id`) and matches their run IDs against the group's runs. Only `agent_stalled` groups are checked; a sleep on an idle tick (no run) or on another run does not count. The filing step (`fileGroup`) runs it before every other check, so a matched open fix item gets no comment, and the stall hold (`recurringStalls`, design 05-restarts) reads the same rule.
  - **What it does.** No item, no claim in `controller_filed_patterns`, no triage run, nothing posted to any source. The group's filing is `skipped: host_sleep`. One information alert (pattern `repeated_error`, key `host_sleep:<key>`, detail "Host sleep: these N agent_stalled runs followed a host sleep, so no fix item was filed; …", scanned as UI text, stored without its detail when flagged), once a day per pattern. The alert holds no item and creates none.
  - **Unchanged.** A stall group with no host sleep on its runs, and every other error code, are filed, triaged and held as before. Items already filed before this decision are left as they are (no backfill). The stall watchdog, run classifier and keep-awake stay as they are; routing such a pattern to the factory's own repo is a follow-up.
- **Applied rules get retire suggestions, and the owner retires one from the Rules page (decision changed 2026-11-14; current; replaces "promoted rules only grow: retiring one is a terminal verdict and a hand edit", see History).** The decision that changed: **the factory suggests which promoted rules to retire, from data it already reads, and the owner's Retire verdict removes the rule.** It never retires one on its own.
  - **Signals.** `retireSuggestions` (`src/core/rule-retirement.ts`, pure: it imports nothing and makes no model call) gives one reason per signal a rule meets, from the rule's block in the rules file, the other applied rules, its class's incident count from `evolve show` and this repo's paths. **Stale:** judged (`판정일`) at least 30 days ago (`STALE_DAYS`, a constant, decision 1) and `evolve show`'s incident count not higher than the T- IDs on its `근거` line: "no new incident for N days since judged on <date>". No count read (a failed show) or no judged date: not stale. **Duplicate:** another applied rule's default, lower case with spaces collapsed, equals this one's or contains it, and the shorter is at least 20 characters (`DUPLICATE_MIN_CHARS`): "covered by <C-id>"; equal defaults mark both. Text overlap only, no model call (decision 3). **Gone from the repo:** its default, exceptions or scope names a path starting with `src/`, `web/`, `docs/`, `prompts/`, `tests/` or `scripts/` that this checkout lacks: "names <path>, which this repo does not have".
  - **When.** Only when the owner presses Suggest on the Rules page (decision 2), never on page load or a schedule (design 09-dashboard-app.md).
  - **Retire.** `TacitLedger.verdict(id, "retire", reason)` on a class: the plugin removes the `## <C-id>` block from the rules file, runs `tacit verdict <C-id> retire --reason <reason>` (the file put back byte for byte if it fails), then `sync-agents` as promote does (decision 4). The next run's `## Learned rules` no longer has it. Retired rules stay visible in the Rules page's Retired list, read from the ledger's retire verdicts.
  - **Not built.** A closed-project signal (free-text scopes do not name a project reliably), suggestions or retire for pack learnings (`learnings.md`), undoing a retire.
- **An improve run when failures pile up, and Run now (new decision, 2026-11-10, issue #508).** The decision that changed: **the improve run is no longer only daily or by `factory improve`**; a burst or an old failure queues one at the next controller tick, and an approver can queue one from the Rules page.
  - **Trigger rule.** Each controller tick, after the daily step, the improve unit reads the project's unreviewed failures: the failed runs (any kind but `improve`, the same runs a report groups) of the project's items that finished since its last improve run was queued (any status; all of them before the first). `improveTriggerDue` (`src/core/improver.ts`, pure) is due when **K = 10** or more of them finished in the last 24 hours, of any run kind (since 2026-11-11, issue #514, see the first entry; before, per run kind), or when the oldest is older than **3 days**. Then `triggerImprove` queues one run per project through `enqueueImprove` with key `improve:<project key>:trigger:<last improve run id, or none>` and the window [last improve run's queue time (or the oldest failure), now). Nothing is queued while any improve run of the project is queued or running, and the failures before a queued run are never counted again.
  - **Why K = 10.** Ten failures in a day since the last look is a burst worth a report the same day, not the next; fewer would queue a run, with its model calls, for ordinary noise between daily runs.
  - **Why 3 days.** The daily run normally resets the count each day, so an unreviewed failure this old means daily runs have not been queued or finished (a stopped controller, a failing improve run); three days lets a weekend pass without a burst, and no failure stays unseen longer.
  - **Constants, not settings.** K and the age are constants in `src/core/improver.ts`; `factory.config.json` has no key for them (a setting needs a reason that no one has yet).
  - **Replicas.** The rule reads store state only, no process memory: two controllers that tick together read the same last improve run and write the same key, and the store's idempotency key keeps one run.
  - **Run now.** The Rules page (`/app/rules`, the decision at the top) shows a Run now button to a user who may approve; `POST /api/v1/improve/run` (`src/ui/improve-api.ts`) queues one manual run through `enqueueImprove`, as `factory improve` does, and answers its `run_id`. It is refused (409, with the run's id) while an improve run is queued or running; the guards and owner check are in `09-dashboard-app.md`.
  - **One worker or many.** The same code with no source plugin selected, on the owner's local store.
