# 7. Self-improvement: the improve report, Run now and rule retirement

- **The improve report ranks the owner's asks and proposes standing approvals as text (decision changed 2026-11-22, wi_06476837; current; changes the report's content, which held failed runs, pushbacks, flaky tests and hot files only, see History).** The decision that changed: **the report lists the top 5 reasons the project's items asked the owner in its window, and proposes a standing approval for a reason approved unchanged 10 times in a row.** Asks are recorded as in design 06-efficiency (reason code and tier in the state change's detail; the owner's action from the next state change).
  - **Rows.** `runImprove` appends to the report's `patterns`, after the hot files: one `owner_ask` row per top reason of the asks made in the window (`detail` the reason code, `asks`, `answered`, `approved_unchanged`, its items; most asks first, then by code; `ASK_TOP` = 5), then one `ask_proposal` row per proposed reason (`detail` the code, `run_length`, `text`). They are stored in the report's existing JSON, so no migration, and are never drafted, filed or alerted. `readAskRows` (`src/core/owner-asks.ts`) reads the project's items updated in the 30 days before the window's end and their state changes; an answer after the window's end is not read.
  - **Proposal.** `standingProposals`: per reason, its answered asks by answer time; an approval unchanged adds one, a changed or rejected answer resets the run to 0, an other answer neither. A run of 10 or more (`ASK_PROPOSAL_RUN`) at the latest answer is proposed. Text only: it creates no rule; the owner applies it with the existing `/standing` command (decision 1). A reason-scoped standing rule is not built.
  - **API.** GET `/api/v1/rules` `improve.report` adds `asks` (`reason`, `asks`, `answered`, `share_unchanged`: approved unchanged ÷ answered, null with none answered) and `proposals` (`reason`, `run_length`, `text`), every text through the Withholder; `patterns` counts the other pattern rows only.
- **The improve run proposes entity file changes with golden evidence; the owner promotes, rejects or holds each (new decision, 2026-11-21, issue #496; current; its settings and the plan it replaces are in 07-self-improvement.md).** Only the repeated-failure path: golden candidate cases from the owner's pushbacks wait on #491 and #493, which are not in this repository.
  - **What is proposed.** After the report is stored (`src/worker/runs/improve/improve.run.ts`), `proposeChanges` (`src/core/proposals.ts`) takes each failure group of the report (two or more runs, one pattern key; `pushback` groups are not failures), largest first. Only one entity file: `prompts/review.md` (`PROPOSAL_FILE`), the only one a golden set covers. One plain model call (no tools, `model_class: standard`, 120 s, its usage the run's) drafts up to five exact find-and-replace edits and a reason (`PROPOSAL_SCHEMA`); the edits are applied in memory and rendered as a unified diff. A find that is missing or occurs twice, a refusal or bad output: `skipped` with `draft_failed`. The system prompt is a constant in `src/core/proposals.ts`, not a `prompts/` file, so a proposal never edits its own instructions.
  - **Evidence.** The review golden cases replay twice through the existing `runCases` (`src/golden.ts`, unchanged; the replay is built in the composition root, `src/golden-replay.ts`, and handed to the worker as `WorkerDeps.reviewReplay`, so the improve run kind imports neither `golden.ts` nor the runtime), the file before and the proposed text after, held in memory and passed as the reviewer's system prompt; each replay gets its own detached sandbox from the worker's sandbox and runner, and its results file goes under the OS temp folder. The proposal stores each case's verdict and the catch and false-alarm rates of both sides. A replay that throws: `skipped` with `replay_failed`.
  - **Limits, as settings.** `improver.max_proposals` (integer ≥ 1, default 1): proposals drafted per run, the rest `skipped` with `proposal_cap`. `improver.schedule` (`off` default, `daily`, `every_run`): which improve runs propose; `daily` only the day's slot, so a trigger or `factory improve` costs no replay. Off by default because each proposal costs two full golden replays and no shared replay budget exists yet; this repo's `factory.config.json` sets `daily`. `distill.min_cases` (integer ≥ 1, default 2): a group with fewer runs stays `watching`, recorded with no model call and no replay. File-only keys of `factory.config.json`, checked at load (`improverConfig`, `checkConfigKeys`); defaults in code. Why settings, not constants like `MAX_DRAFT_CALLS`: each proposal costs two full golden replays, and how many the owner can afford depends on the number of cases and the model. `MAX_DRAFT_CALLS` is unchanged; filed patterns have their own constant caps, `MAX_NEW_ITEMS` = 2 new items and `MAX_FILED_ISSUES` = 3 comments a run (07-self-improvement.md, 2026-11-23).
  - **Egress.** Before a proposal is stored, its item body (the diff as an unverified draft, the reason and the rates) passes the G5 scan on `comment`, and its record (diff, reason, evidence as JSON) on `run_outcome`. A flagged one is stored `withheld` with its rules only: no diff, reason or evidence.
  - **Store.** `controller_improve_proposals` (SQLite migration 45, `src/impl/store/sql/improve-proposals.ts`; no MySQL store): one row per report and pattern key (unique, so a retried run stores nothing twice and makes no second model call), its state (`watching`, `skipped`, `withheld`, `pending`, `held`, `promoted`, `rejected`), reason, diff, evidence JSON, rules, `needs_human_merge` (the file is on `GATE_PATHS`; `prompts/review.md` always is), the verdict's user ID and time, and the filed item's ref.
  - **Nothing changes before a verdict.** No repository file is written and no work item is made by a proposal. The verdict route (`POST /api/v1/proposals/verdict`, 09-dashboard-proposals.md) checks the write guards, then `approve_spec` on the project (403, nothing written), then that the proposal is that project's (404, nothing written). A verdict is one conditional update: from `pending`, or from `held` to promote or reject; any other answers `unchanged`, so the same verdict twice is safe. Reject and hold change only the state.
  - **Promote.** The controller's improve step (`fileProposals`, each tick) files one work item per promoted proposal with no item, through the first source with `fileIssue` (the same path as filed patterns): title "Proposed change to prompts/review.md: <code>", body the scanned draft body, marker `<!-- factory:proposal:<id> -->`. One caller takes each filing (`claimProposalFiling`, a conditional update; a claim with no item is another caller's for 10 minutes), and the source looks the marker up first. Nothing is applied to a file; the filed item is triaged and built like any other, and its change to `prompts/` waits for a person's merge, so promote never merges.
  - **Solo and enterprise.** The same table, route and rules. Solo: the local owner decides and promote files a local work item. Enterprise: the configured auth plugin's `approve_spec` check decides, and promote files a GitHub issue through `github-issues`. No shared model budget for replays yet (a follow-up).
- **The improve report lists the flaky tests merge checks named (decision changed 2026-11-17; current; changes the improve run's report, which held only failed runs and pushbacks, see History).** The decision that changed: **a test that failed a merge check and passed its one rerun (04-pre-push-gates.md) is listed in the project's improve report.** `flakyTests` (`src/core/failure-groups.ts`) reads each green `merge-check` run in the window whose outcome has `flaky_tests` (`file > name`): one entry per name, code `flaky_test` (`FLAKY_TEST`), detail the name as written (cut to 200 characters), with every run and item that named it, by name. `runImprove` adds them to the report's `patterns`, after the failure patterns. They are never drafted, filed, alerted or counted as failures. Why: the rerun lets such a change merge without a loop, so the report is where the owner sees the flake. Not in this decision: a flake history across runs, a comment on the work item, fixing the tests.

- **A stall group that followed a host sleep is not filed, only shown (decision changed 2026-11-15; current; changes "File each recurring failure pattern" and "A fix spec runs unless the draft needs a person or touches a gate path" below, where every group of two or more runs was filed or sent to a person, see History).** The decision that changed: **an `agent_stalled` group one of whose runs held a recorded host sleep is not filed as a fix item in the project's repo.** A host sleep (the machine slept, `worker_host_sleeps`, design 05-restarts) is the factory's host runtime, so the repo holds no code to fix, and a spec triage drafted for it would guess its paths and wait at the spec gate.
  - **Check.** `stalledBySleep` (`src/core/improver.ts`) reads the host sleeps of each item of the group (`listHostSleeps` with `work_item_id`) and matches their run IDs against the group's runs. Only `agent_stalled` groups are checked; a sleep on an idle tick (no run) or on another run does not count. The filing step (`fileGroup`) runs it before every other check, so a matched open fix item gets no comment, and the stall hold (`recurringStalls`, design 05-restarts) reads the same rule.
  - **What it does.** No item, no claim in `controller_filed_patterns`, no triage run, nothing posted to any source. The group's filing is `skipped: host_sleep`. One information alert (pattern `repeated_error`, key `host_sleep:<key>`, detail "Host sleep: these N agent_stalled runs followed a host sleep, so no fix item was filed; …", scanned as UI text, stored without its detail when flagged), once a day per pattern. The alert holds no item and creates none.
  - **Unchanged.** A stall group with no host sleep on its runs, and every other error code, are filed, triaged and held as before. Items already filed before this decision are left as they are (no backfill). The stall watchdog, run classifier and keep-awake stay as they are; routing such a pattern to the factory's own repo is a follow-up.
- **Applied rules get retire suggestions, and the owner retires one from the Rules page (decision changed 2026-11-14; current; replaces "promoted rules only grow: retiring one is a terminal verdict and a hand edit", see History).** The decision that changed: **the factory suggests which promoted rules to retire, from data it already reads, and the owner's Retire verdict removes the rule.** It never retires one on its own.
  - **Signals.** `retireSuggestions` (`src/core/rule-retirement.ts`, pure: it imports nothing and makes no model call) gives one reason per signal a rule meets, from the rule's block in the rules file, the other applied rules, its class's incident count from `evolve show` and this repo's paths. **Stale:** judged (`판정일`) at least 30 days ago (`STALE_DAYS`, a constant, decision 1) and `evolve show`'s incident count not higher than the T- IDs on its `근거` line: "no new incident for N days since judged on <date>". No count read (a failed show) or no judged date: not stale. **Duplicate:** another applied rule's default, lower case with spaces collapsed, equals this one's or contains it, and the shorter is at least 20 characters (`DUPLICATE_MIN_CHARS`): "covered by <C-id>"; equal defaults mark both. Text overlap only, no model call (decision 3). **Gone from the repo:** its default, exceptions or scope names a path starting with `src/`, `web/`, `docs/`, `prompts/`, `tests/` or `scripts/` that this checkout lacks: "names <path>, which this repo does not have".
  - **When.** Only when the owner presses Suggest on the Rules page (decision 2), never on page load or a schedule (design 09-dashboard-app.md).
  - **Retire.** `TacitLedger.verdict(id, "retire", reason)` on a class: the plugin removes the `## <C-id>` block from the rules file, runs `tacit verdict <C-id> retire --reason <reason>` (the file put back byte for byte if it fails), then `sync-agents` as promote does (decision 4). The next run's `## Learned rules` no longer has it. Retired rules stay visible in the Rules page's Retired list, read from the ledger's retire verdicts.
  - **Not built.** A closed-project signal (free-text scopes do not name a project reliably), suggestions or retire for pack learnings (`learnings.md`), undoing a retire.
- **An improve run when failures pile up, and Run now (new decision, 2026-11-10, issue #508).** The decision that changed: **the improve run is no longer only daily or by `factory improve`**; a burst or an old failure queues one at the next controller tick, and an approver can queue one from the Rules page.
  - **Trigger rule.** Each controller tick, after the daily step, the improve unit reads the project's unreviewed failures: the failed runs (any kind but `improve`, the same runs a report groups) of the project's items that finished since its last improve run was queued (any status; all of them before the first). `improveTriggerDue` (`src/core/improver.ts`, pure) is due when **K = 10** or more of them finished in the last 24 hours, of any run kind (since 2026-11-11, issue #514, see the first entry; before, per run kind), or when the oldest is older than **3 days**. Then `triggerImprove` queues one run per project through `enqueueImprove` with key `improve:<project key>:trigger:<last improve run id, or none>` and the window [last improve run's queue time (or the oldest failure), now). Nothing is queued while any improve run of the project is queued or running, and the failures before a queued run are never counted again.
  - **Why K = 10.** Ten failures in a day since the last look is a burst worth a report the same day, not the next; fewer would queue a run, with its model calls, for ordinary noise between daily runs.
  - **Why 3 days.** The daily run normally resets the count each day, so an unreviewed failure this old means daily runs have not been queued or finished (a stopped controller, a failing improve run); three days lets a weekend pass without a burst, and no failure stays unseen longer.
  - **Constants, not settings.** K and the age are constants in `src/core/improver.ts`; `factory.config.json` has no key for them (a setting needs a reason that no one has yet).
  - **Replicas.** The rule reads store state only, no process memory: two controllers that tick together read the same last improve run and write the same key, and the store's idempotency key keeps one run.
  - **Run now.** The Rules page (`/app/rules`, the decision at the top) shows a Run now button to a user who may approve; `POST /api/v1/improve/run` (`src/ui/improve-api.ts`) queues one manual run through `enqueueImprove`, as `factory improve` does, and answers its `run_id`. It is refused (409, with the run's id) while an improve run is queued or running; the guards and owner check are in `09-dashboard-app.md`.
  - **One worker or many.** The same code with no source plugin selected, on the owner's local store.
