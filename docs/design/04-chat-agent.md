# 4. Agents: the chat turn

**`chat.send`, `chat.transcript` and `chat.turns` call the chat turn, and each sent turn's outcome is stored in `controller_chat_turns`** (decision changed 2026-11-26, local-task-tk_eea9af6d phase 2, phase 1 of 2; current; replaces "No HTTP route, capability or dashboard page calls it yet", see History). The three capabilities are declared on the API registry in `src/api/capabilities/chat.ts` (design 09-api-registry), each with permission `owner`, so the dashboard, CLI and chat reach the turn through one declaration. The API version stays 1: these are additions only.

- **`chat.send`** (`POST /api/v1/chat/send`, input `session_id` optional and `text`). It runs one `chatTurn` with the Ask model (`settings.ask.llm`, the model `schedules.draft` uses) and the chat's broker over the feature map. No `session_id` starts a new session, `cs_<uuid>`. The turn id is `ct_<uuid>`, made before the turn: it keys the turn row, and `newTurnId` returns it so the spend row uses it too. It answers `turn_id`, `session_id`, `outcome` and, when the turn was answered, `reply`. `ok` answers `answered`; `withheld` answers `refused` with reason `withheld` and no reply text; `model_error`, `too_many_steps` and `seq_taken` answer `failed` with that reason; a thrown error answers `failed` with reason `error`. With no Ask model it refuses (503) and stores nothing; startup is unaffected.
- **The turn row.** `controller_chat_turns` (migration `20261126T1400-state-chat-turns`) holds one row per `chat.send` turn: `turn_id`, `session_id`, `status`, `reason` (null when answered), `created_at` and `finished_at`. `startChatTurn` writes it `running` at the turn's start; `finishChatTurn` ends only a running row, with `answered`, `refused` or `failed` and its reason, so a thrown error leaves it `failed`, never `running`. Each store method is one transaction. No backfill: no turn was recorded before.
- **`chat.transcript`** (`GET`, `session_id`) answers the session's stored messages in order; an unknown session answers none. **`chat.turns`** (`GET`, `limit` optional, default 50) answers the recent turns, newest first. Neither writes a row.
- Not built here: the dashboard page and the Runners tab that show turns (phase 2), a CLI command for chat.

**A chat turn answers from the read-only tools of the chat's own broker, scans every result and reply, stores the session and counts its spend under `chat`** (decision 2026-11-26, local-task-tk_eea9af6d phase 2 of 2; current). It builds on phase 1, which stored chat messages in `controller_chat_messages` and let the provider call carry tools (docs/plugins/llm-provider.md). The capabilities above call it.

- **The loop.** `chatTurn(deps, session_id, text)` in `src/core/chat-agent.ts` reads the session's stored messages, appends the owner's message and calls the `LLMProvider` (`model_class: "cheap"`, `data_env: "test"`, the fixed `CHAT_SYSTEM` prompt, `max_tokens` 1024) with the session so far and the offered tools. For each tool call the reply asks for, it runs the call and sends the result back as a `tool` message in the next call. It stops at a reply with no tool calls, or after `CHAT_MAX_STEPS` (6) calls, and then stores nothing (`too_many_steps`). A provider answer that does not end (`stop_reason` other than `end`) stores nothing (`model_error`).
- **Which tools.** The model is offered every tool of the chat's broker whose descriptor is `read_only` (`chatTools`), and nothing else (owner answer 2: every read-only broker tool, not a config grant list). A call naming any other tool, a write tool included, gets a `tool` message saying it is not a read-only tool and never reaches the broker. A read-only tool added to the broker is offered and callable with no chat code changed.
- **The chat's broker, and why it needs no passport.** A broker call is normally checked against a run's lease and passport (G2). A chat turn has no run, so the chat gets its own `ToolBroker`: `ChatToolBroker` in `src/core/chat-agent-tools.ts`. It is built from `ChatTool`s, whose type is read-only, and it refuses at construction any tool that is not read-only and any name given twice. It is never wrapped in the passport broker, and it holds no credential. A tool's thrown error text is not passed on (`tool_error`). The call context names the session in place of a run (`chatCallContext`: `chat:<session>`, lease token 0). The chat's guard is the read-only rule plus the egress scan below.
- **The four feature-map read tools** (owner answer 1: built here). `featureMapTools(read)` wraps the feature map (`src/api/feature-map.ts`, design 09-api-registry), so the tools come from the registry's declarations and no list of factory tools is kept by hand. `list_areas` (no input): every area with its feature ids. `list_features` (`area`): that area's features, each with its id, description, permission, method and path. `get_feature` (`id`): one feature's summary. `get_feature_schema` (`id`): its input and output JSON Schemas. A missing or empty argument answers `bad_args`, an unknown id `not_found`. core/ imports only core/ and interfaces/, so the feature map's reader is passed in: the wiring binds it to `readFeatureMap(REGISTRY, path)`. These four are the chat's tools today.
- **Egress.** The owner's message is scanned (channel `ui`) before any model call. Each tool result is scanned (channel `tool_result`) before the model sees it, and each reply text (channel `ui`) before it is stored or returned. A finding stores no message and returns nothing (`withheld`), as for chat answers (design 04-chat-commands). The feature map's text is code, not store text, so no tool returns a secret, and the scan catches any that does.
- **Storing the session.** A finished turn's messages (the owner's message, each assistant message with its tool calls, each tool result, the reply) are stored in one `appendChatMessages` batch, from the session's next seq. A turn written meanwhile by another worker at the same seq stores nothing (`seq_taken`), so a turn run twice is stored once.
- **Spend, kind `chat`.** Every turn that called the model stores one row in `controller_chat_spend` (migration `20261126T1300-state-chat-spend`): the turn's own id (`turn_id`, from the injected `newTurnId`), its session, the UTC day, the summed `cost_usd` of its calls (null, unknown, when any call reported none) and its input plus output tokens. Withheld and failed turns count too, because their model calls were spent. The key is the turn id, never a message seq: a failed turn stores no message, so the next turn takes the same seq, and a seq key would refuse that turn's spend. The key counts a turn once (`recordChatSpend` answers false); a turn run twice called the model twice and is counted twice. `listChatSpendBetween(from, to)` reads a range of UTC days. `readSpend` (`src/core/spend.ts`) adds a `chat` total (`cost_usd`, `tokens`, `turns`, `unknown`) apart from the run totals, and `GET /api/v1/spend` answers it (design 06-spend). There is no backfill, since no chat turn was counted before.
- **Eval suite.** `tests/chat-eval/owner-questions.json` holds the owner's questions (at least 10). Each has an id, the question, a `judged_answer` (what a judge grades the chat's reply against) and the chat tools it expects. The pass bar reads the file on a schedule. `tests/chat-eval.test.ts` checks only its shape and calls no model.
- Not built: the page that calls `chatTurn`; write tools in the chat; tools other than the four feature-map ones in production wiring; a cap on the session history sent per call; running the eval suite here.
