# 4. Agents: the chat turn

**A daily chat check that fails raises one Needs-you alert for its UTC day, open until the owner dismisses it** (decision changed 2026-11-27, wi_94ad6bab; current; replaces "its result is logged" as the only output of the daily run, see History). The pass bar (`CHAT_EVAL_PASS_BAR`, 8), the eval questions and the daily schedule are unchanged.

- **When.** A daily run that ends with `ok: false` (passed below the bar) or that throws. A passing run raises nothing, and an earlier day's open alert stays until dismissed: no later run clears it.
- **The alert.** `chatEvalFailedAlert` in `src/core/alarms.ts`, next to the other builders: pattern `chat_eval_failed`, key `chat_eval_failed:<UTC day>`, deduped for one day, so two failing runs on one day store one alert. Its detail names the passed count, the total, the run's own bar, the most common failure reason in plain words with its count (`failuresOf`, moved to `src/core/alarms.ts`; the words are `CHAT_FAILURE_WORDS` there, since core does not import the UI's `failureWords`) and the first provider detail, e.g. "Chat check failed today: 0 of 12 answered (needs 8). Most failures: the model did not finish (12)." A thrown run's detail is "Chat check failed today: the run stopped with an error: <message>."
- **How it is stored.** The chat-eval unit scans the detail on the `ui` channel and commits it through the kernel's `alert` write, as the coordinator's limit question is (design 06-spend); a flagged detail is stored as null. The run stays unawaited: the alert is written when it ends.
- **In Needs you.** `src/ui/alarms.ts` names it ("Alarm: the daily chat check failed; …"), points to `npm run eval:chat` and `factory alarm dismiss <id>`, keeps it open past the 6-hour alarm window with no close time (`openAlarms`, `alarmUntil`), and holds no work item with it (`alarmsFor`).
- Not built here: Slack or other delivery of the alert, and the same until-dismissed display for `coordinator_limit` alerts (a follow-up).

**The eval suite runs daily against main, and the chat passes at 8 or more passing questions** (decision changed 2026-11-27, local-task-tk_eea9af6d phase 3 of 3; current, with the failed-check alert above; replaces "Not built: running the eval suite here", see History). `src/core/chat-eval.ts` holds the run and its pass rule; it reads no file and builds no provider, so the script and the controller hand them in.

- **The run.** `runChatEval` sends each question of `tests/chat-eval/owner-questions.json` through `chatTurn` in a new session (`cs_<uuid>`) on a throwaway in-memory store, so the owner's chat sessions and store rows are never touched. Each turn gets the four feature-map tools (`featureMapTools` over `readFeatureMap(REGISTRY, path)`) and the Ask model (`settings.ask.llm`: the configured Model plugin, as `chat.send` uses). Model calls go only through `LLMProvider`.
- **The pass rule.** A question passes only when its turn answered, it called every tool the question's `tools` lists, and the judge answers yes. The judge is the same `LLMProvider`, called with `model_class: "standard"`, the fixed `JUDGE_SYSTEM` prompt, the question, its `judged_answer` and the reply; an answer starting with "yes" is a yes. A turn that failed or missed a tool is not sent to the judge.
- **The pass bar.** `CHAT_EVAL_PASS_BAR` is 8. The run prints one `PASS` or `FAIL` line per question, then the passed count out of the questions it ran, and `npm run eval:chat` (`scripts/chat-eval.mjs`, which loads `scripts/chat-eval.ts` from the TypeScript sources with no build) exits 1 below 8 and 0 at 8 or more. `npm test` does not run it: heavy tests run on a schedule. `tests/chat-eval-run.test.ts` checks the runner, the pass rule and the bar with a fake Ask model and a fake judge.
- **The schedule.** `chat_eval.schedule` in factory.config.json (`daily`, the only value; checked at load by `chatEvalProblems`) turns on the daily run; this repo sets it. Absent, compose builds no run and nothing is scheduled. Each poll the controller unit `src/controller/units/chat-eval/` claims the UTC day through the store cursor `chat_eval:daily` (a conditional advance, so replicas on one store run the day once) and starts the run on the code the controller runs, main, with no owner action. The run is not awaited, so its model calls never hold up the controller's other steps; its result is logged (`chat eval run finished`, with passed, total and the bar, and, when turns failed, `failures`, the failed turns counted by reason such as `model_error:12`, and `failure_detail`, the first failed turn's detail). The script's FAIL line names the reason and detail too. A process that stops mid-run loses that day's run; the next day runs again.
- Not built here: a Runners page line or API capability that shows the eval results (a follow-up).

**`chat.send`, `chat.transcript` and `chat.turns` call the chat turn, and each sent turn's outcome is stored in `controller_chat_turns`** (decision changed 2026-11-26, local-task-tk_eea9af6d phase 2, phase 1 of 2; current; replaces "No HTTP route, capability or dashboard page calls it yet", see History). The three capabilities are declared on the API registry in `src/api/capabilities/chat.ts` (design 09-api-registry), each with permission `owner`, so the dashboard, CLI and chat reach the turn through one declaration. The API version stays 1: these are additions only.

- **`chat.send`** (`POST /api/v1/chat/send`, input `session_id` optional and `text`). It runs one `chatTurn` with the Ask model (`settings.ask.llm`, the model `schedules.draft` uses) and the chat's broker over the feature map. No `session_id` starts a new session, `cs_<uuid>`. The turn id is `ct_<uuid>`, made before the turn: it keys the turn row, and `newTurnId` returns it so the spend row uses it too. It answers `turn_id`, `session_id`, `outcome` and, when the turn was answered, `reply`. `ok` answers `answered`; `withheld` answers `refused` with reason `withheld` and no reply text; `model_error`, `too_many_steps` and `seq_taken` answer `failed` with that reason; a thrown error answers `failed` with reason `error`. With no Ask model it refuses (503) and stores nothing; startup is unaffected.
- **The turn row.** `controller_chat_turns` (migration `20261126T1400-state-chat-turns`) holds one row per `chat.send` turn: `turn_id`, `session_id`, `status`, `reason` (null when answered), `created_at` and `finished_at`. `startChatTurn` writes it `running` at the turn's start; `finishChatTurn` ends only a running row, with `answered`, `refused` or `failed` and its reason, so a thrown error leaves it `failed`, never `running`. Each store method is one transaction. No backfill: no turn was recorded before.
- **`chat.transcript`** (`GET`, `session_id`) answers the session's stored messages in order; an unknown session answers none. **`chat.turns`** (`GET`, `limit` optional, default 50) answers the recent turns, newest first. Neither writes a row.
- Not built here: the dashboard page and the Runners tab that show turns (phase 2), a CLI command for chat.

**A chat turn answers from the read-only tools of the chat's own broker, scans every result and reply, stores the session and counts its spend under `chat`** (decision 2026-11-26, local-task-tk_eea9af6d phase 2 of 2; current). It builds on phase 1, which stored chat messages in `controller_chat_messages` and let the provider call carry tools (docs/plugins/llm-provider.md). The capabilities above call it.

- **The loop.** `chatTurn(deps, session_id, text)` in `src/core/chat-agent.ts` reads the session's stored messages, appends the owner's message and calls the `LLMProvider` (`model_class: "cheap"`, `data_env: "test"`, the fixed `CHAT_SYSTEM` prompt, `max_tokens` 1024) with the session so far and the offered tools. For each tool call the reply asks for, it runs the call and sends the result back as a `tool` message in the next call. It stops at a reply with no tool calls, or after `CHAT_MAX_STEPS` (6) calls, and then stores nothing (`too_many_steps`). A provider answer that does not end stores nothing, and its reason says what the provider did (decision changed 2026-11-27; replaces "every such answer is `model_error`", see History): `refused` is `model_refused`, `max_tokens` is `model_cut_off`, and `error` is `model_error` with `detail`, the provider's own text (a login, quota or tool problem), trimmed, capped at `CHAT_DETAIL_MAX` (300) characters and scanned (channel `ui`); a flagged or empty text gives no detail. `chat.send` answers `detail` with the reason, and a thrown error's message as the `error` reason's detail on the same terms; the Chat page shows it ("The model call failed: …"). The turn row keeps the reason only. The `claude-cli` provider carries the offered tools since the same date (docs/plugins/llm-provider.md), so the chat works on the subscription login.
- **Which tools.** The model is offered every tool of the chat's broker whose descriptor is `read_only` (`chatTools`), and nothing else (owner answer 2: every read-only broker tool, not a config grant list). A call naming any other tool, a write tool included, gets a `tool` message saying it is not a read-only tool and never reaches the broker. A read-only tool added to the broker is offered and callable with no chat code changed.
- **The chat's broker, and why it needs no passport.** A broker call is normally checked against a run's lease and passport (G2). A chat turn has no run, so the chat gets its own `ToolBroker`: `ChatToolBroker` in `src/core/chat-agent-tools.ts`. It is built from `ChatTool`s, whose type is read-only, and it refuses at construction any tool that is not read-only and any name given twice. It is never wrapped in the passport broker, and it holds no credential. A tool's thrown error text is not passed on (`tool_error`). The call context names the session in place of a run (`chatCallContext`: `chat:<session>`, lease token 0). The chat's guard is the read-only rule plus the egress scan below.
- **The four feature-map read tools** (owner answer 1: built here). `featureMapTools(read)` wraps the feature map (`src/api/feature-map.ts`, design 09-api-registry), so the tools come from the registry's declarations and no list of factory tools is kept by hand. `list_areas` (no input): every area with its feature ids. `list_features` (`area`): that area's features, each with its id, description, permission, method and path. `get_feature` (`id`): one feature's summary. `get_feature_schema` (`id`): its input and output JSON Schemas. A missing or empty argument answers `bad_args`, an unknown id `not_found`. core/ imports only core/ and interfaces/, so the feature map's reader is passed in: the wiring binds it to `readFeatureMap(REGISTRY, path)`. These four are the chat's tools today.
- **Egress.** The owner's message is scanned (channel `ui`) before any model call. Each tool result is scanned (channel `tool_result`) before the model sees it, and each reply text (channel `ui`) before it is stored or returned. A finding stores no message and returns nothing (`withheld`), as for chat answers (design 04-chat-commands). The feature map's text is code, not store text, so no tool returns a secret, and the scan catches any that does.
- **Storing the session.** A finished turn's messages (the owner's message, each assistant message with its tool calls, each tool result, the reply) are stored in one `appendChatMessages` batch, from the session's next seq. A turn written meanwhile by another worker at the same seq stores nothing (`seq_taken`), so a turn run twice is stored once.
- **Spend, kind `chat`.** Every turn that called the model stores one row in `controller_chat_spend` (migration `20261126T1300-state-chat-spend`): the turn's own id (`turn_id`, from the injected `newTurnId`), its session, the UTC day, the summed `cost_usd` of its calls (null, unknown, when any call reported none) and its input plus output tokens. Withheld and failed turns count too, because their model calls were spent. The key is the turn id, never a message seq: a failed turn stores no message, so the next turn takes the same seq, and a seq key would refuse that turn's spend. The key counts a turn once (`recordChatSpend` answers false); a turn run twice called the model twice and is counted twice. `listChatSpendBetween(from, to)` reads a range of UTC days. `readSpend` (`src/core/spend.ts`) adds a `chat` total (`cost_usd`, `tokens`, `turns`, `unknown`) apart from the run totals, and `GET /api/v1/spend` answers it (design 06-spend). There is no backfill, since no chat turn was counted before.
- **Eval suite.** `tests/chat-eval/owner-questions.json` holds the owner's questions (at least 10). Each has an id, the question, a `judged_answer` (what a judge grades the chat's reply against) and the chat tools it expects. The daily run above reads it. `tests/chat-eval.test.ts` checks only its shape and calls no model.
- Not built: the page that calls `chatTurn`; write tools in the chat; tools other than the four feature-map ones in production wiring; a cap on the session history sent per call.
