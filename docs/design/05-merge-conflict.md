# 5. Coordination: merge conflict

- **A resolve run's `out_of_scope` failure names the exact `/resolve +paths` reply, and `/retry` at a merge conflict points to it (decision changed 2026-11-26, wi_fef626be; replaces "the `out_of_scope` comment lists the files and says only `/resolve [notes]`", see History).** The decision that changed: the resolve run's `out_of_scope` detail now starts with the reply that allows the files it changed outside the conflicts and `allowed_paths` and resolves again, "Reply `/resolve +paths <files>` to allow them and resolve again." (`retryPathsReply(files, "/resolve")`, `resolveScopeDetail` in `src/worker/runs/resolve/resolve.run.ts`), then lists those files; when no single reply can (more than 10, or a name with a space or glob) it says to resolve the conflict by hand. The reply comes first so the detail's 500-character cap never cuts it; the failure comment shows the detail as before (dropped when the egress scan flags it). A `/retry` on an item at `merge_conflict_pending` is refused with `/resolve [notes]` and `/resolve +paths <path>...` (notes on the lines below) instead of "there is no failed run to retry", since a failed person's resolve run leaves the item on its conflict, not on a failed run. Unchanged: `/resolve +paths` itself (2026-11-08) and its widening, the scope gate. Why: wi_fef626be's resolve correctly carried the branch's edit of a test file main had split into a new file, failed `out_of_scope` on that new file, and the person found no reply that applied: the comment said only `/resolve [notes]` and `/retry +paths` was refused there.
- **The dashboard's Re-check clears an item's stored merge check, and its Changes tab reads the branch's diff (decision changed 2026-11-20, wi_5c4d307a, "Changes tab and fresh merge check before Merge"; replaces "the dashboard only reads the stored row", see History; the item page's side is in 09-dashboard-item.md).** **Re-check:** the item API's `merge_check.recheck` is true when the stored `checked_at` is older than the commit time of the factory repo's trusted base (`origin/<base>`, or the local branch with `local_only`); the Merge check card then shows Re-check. It posts `POST /api/v1/items/:id/merge-check/recheck`, a write route behind server.ts's guards (Origin, Content-Type, the commands CSRF token), which only deletes the item's one stored result (`FactoryStore.clearMergeCheck`): no git work, fetch or forge call in the request, and the item's stage, blocked fields and version stay. With no stored row the item reads `checking`, and the controller's next merge check step computes and stores a new result as for a first check (its base still throttled as below). How the check is computed, throttled and stored is unchanged. **Changes tab:** an item has one (`has_changes` on `GET /api/v1/items/:id`) when it has a head to read, the merge check's stored `head_sha`, else its `last_head_sha`, and the sandbox has `readChanges`; tabs Overview and Changes, kept in `?tab=changes` (`web/src/views/item-changes.tsx`). `GET /api/v1/items/:id/changes` (`src/ui/changes.ts`, read once, no polling) lists each file `git diff <base>...<head>` names with its added and removed line counts (null, shown as "binary", for a binary file); `?path=<file>` adds that file's diff, cut at 256 KiB (owner answer 1) with a Truncated note. **Data:** `Sandbox.readChanges` (optional, trusted; NoOp in `src/impl/sandbox/noop-sandbox.ts`) reads only git objects already in the factory repo against its trusted base: no fetch, no forge call, no ref, index or working tree written, no rename detection, external diff or textconv. It also gives the base's commit time for Re-check. **Egress:** every path and diff passes the EgressScanner on channel `ui`; a withheld diff shows the withheld marker in its place and its row stays. A git error answers 404 without its text. Out: editing or commenting on code from the tab, live updates, storing diffs.
- **A conflict resolution that fails only on test files it may not edit asks for them (decision changed 2026-11-18; replaces "a resolution whose checks fail always fails with `merge_conflict`", see History).** The decision that changed: in the implement run's sync step (04-pre-push-gates.md, Sync before push), when the resolve-step retry's checks fail and every test file their output names (`failingTestFiles`) is one the once-only grant may give (`auto_grant_test_paths` on for the project, and a test file by `test_globs` not on the gate list, CLAUDE.md or AGENTS.md: `LiveSettings.autoGrantable`), none is covered by `allowed_paths` (`isCovered`), and there are at most 10 of them, the run ends with a needs_human outcome naming them in `paths` instead of `merge_conflict`. Nothing is pushed and no merge-conflict comment is posted; the controller's once-only test-path grant (05-restart-asks.md, `auto_grant_test_paths`) applies to it as to the implementer's own ask, so the item runs again once with the files allowed, and a second ask waits for the owner. Any other failure (a covered or non-test failing file, no file named, the switch off, markers, unmerged paths) still fails with `merge_conflict` and the same detail. The switch decides too because the worker reaches the test-file rule only through the live settings (no new legacy import, dependency-direction ratchet), and with no grant to apply the ask would only move the wait from a retry to the owner. The retry first is kept (the owner's answer: retry first): the first step's check failure goes to the retry prompt, which now names each failing test (`file > name`) and quotes the check output tail in a fence, after the egress scan as the fix step does. Why: wi_769ffd24 failed 11 of its 12 conflicts this way (18 implement runs, about $25) while its agent named the blocking test outside the allowed paths. The logic is in `src/worker/runs/implement/conflict-ask.ts`.
- **A failed resolve run takes `/retry +paths` (decision changed 2026-11-18; replaces "`+paths` applies only to a failed implement run").** The decision that changed: a resolve run that asked for a path outside `allowed_paths` (`agent_needs_human`), or that failed without asking (`repeated_failure`), is answered with `/retry +paths <path>`: the paths are added as for an implement run (design 04-gate-commands, same limits) and one resolve run is queued with the `/retry` notes minus the `+paths` line, keeping the reviewed change and the spec. Before, the `+paths` was refused, a plain `/retry` asked again, and only `/revise` (which redoes the item) got past it. `/resolve +paths` is unchanged.

- **The resolve run no longer renumbers migration steps (decision changed 2026-11-13, #659 phase 2; before: see History).** The decision that changed: the resolve run's renumbering of a duplicate step (2026-11-08). It is removed with the update run's and the implement sync's (`docs/design/05-coordination.md`). After its `--no-commit` merge the resolve run runs the appended-line merge, snapshots, lets the agent resolve what is left, then gates and commits as before.
  - **On both paths:** removed. Neither the clean merge nor the conflict path stages any step move before the snapshot.
  - **Same skip rule:** removed with the renumbering it skipped.
  - **A failure never stops the run:** removed. The run no longer copies the index aside for a renumbering; the resolve prompt has no "Migration steps renumbered" note.
  - The resolve agent still renumbers a clashing migration by hand, as `prompts/resolve.md` says. No setting, state or schema change.
- **A local item's conflict starts the same automatic resolve, with or without a forge (decision changed 2026-11-12, twice: first for `local_only` only, then also with a forge selected; before: only items with a PR, see History).** A local item (no PR, its branch in the factory repo) waiting for a merge (`REVIEW` / `blocked_on: human` / `merge_pending`) whose branch conflicts with the local base now takes the PR path's automatic resolve, with **no update run**: the resolve run merges the base and runs the gates itself, which is the same merge with the same gates.
  - **Found by the merge check** when the local base moves: the merge check below also looks at items with no PR and stores their result per (head sha, base sha); an unchanged pair is not checked again. With no forge selected (`local_only`), the controller's sandbox reads the local base and branch in the same step as PRs (no network call). **With a forge selected** (the decision that changed: before, a local item was not checked), the sandbox's base and branch reads are origin's, so a local item (source `local`, no PR) is checked in a second pass that reads the local base and its local branch with the sandbox's `localBranch` (`MergeChecker.stepLocal`; the factory repo's own refs, no fetch, so no throttle). PRs keep the first pass and their update run. The check is `merge-tree` on the two shas it stored, the same probe `localConflicts` runs on the refs.
  - **Found by `factory merge`**: the refusal still names the conflicting files, and says an automatic resolve run started. The key's base commit is the local base: with `local_only` the sandbox's base read, with a forge selected `localBranch` on the base (the decision that changed: before, with a forge selected the refusal only named the files and started nothing).
  - **Either way** the item goes to `RUNNING` / `blocked_on: none` (`auto_resolve_started`, detail `cause`: `merge_check` or `merge_refused`, base sha, attempt) with one resolve run keyed `autoResolveKey` on the local base's commit, and **no comment** at the start. The same limit of 2 per base commit applies (`update_conflict` and `merge_conflict_pending` at the limit, comment `auto-resolve-limit:<id>:<base sha>`), the same retry, the same counts. Only an item still waiting for a merge with no PR changes, so a second call changes nothing.
  - **`/resolve` and `factory resolve`** are also accepted on a local item waiting for a merge whose branch conflicts (the local merge's `localConflicts` probe), besides `merge_conflict_pending`; each takes a new human key (`runKey` after `restart_count + 1`). A local item whose branch merges cleanly gets the usual refusal and nothing changes.
  - **The resolve run** no longer stops with `no_pr` for a local item: it runs on the local route (`routeFor`; with a forge selected compose builds it beside the forge's, a sandbox in local mode and the local broker), whose `origin/<base>` and `origin/<branch>` are the factory repo's local base and branch, merges, resolves, runs the install command and the checks, and stores the commit on the local branch through the local broker; the run folder is removed by the same route's sandbox. Nothing is pushed to a remote, also with a forge selected (the owner's answer: local branch only, local first; the base push after the local merge brings `main` to origin). Success goes to `REVIEW` (`resolved`), a review keyed `after-resolve:<run id>`, then `merge_pending`, as on the PR path.
  - **Comments** go to the item's thread (`prComment` falls back to it with no PR) and name the local branch instead of a PR. No setting, state or schema change.
  - **`factory merge` also accepts a local item held for `recurring_failure` whose last failed run is a resolve run (decision changed 2026-11-21; extends the 2026-11-20 decision below; before: refused as "not waiting for a merge").** The decision that changed: an item at `REVIEW` / `blocked_on: human` / `recurring_failure` (05-alarms) whose latest failed run has kind `resolve` (`resolveHeld`) is treated as parked on its conflict by the local merge gate, the dashboard's request gate and the controller: still conflicting is refused with the files and the hold stays; clean goes to the same fresh review (`conflict_fixed_by_hand`), which lifts the hold. Why: a resolve run that stalls twice is held for `recurring_failure` instead of parked, so `factory merge` refused the owner's hand fix (wi_c004f668, wi_bdd36b09, wi_fcf04fac). A hold after any other failed run is still refused.
  - **`factory merge` on a local item parked at `merge_conflict_pending` checks the branch as it is (decision changed 2026-11-20; extends the 2026-11-12 local conflict decision above; before: refused as "not waiting for a merge").** The decision that changed: the local merge gate (`localMergeRefusal`) also passes a local item (no PR) at `REVIEW` / `blocked_on: human` / `merge_conflict_pending` (`conflictParked`), so the controller runs the same `localConflicts` probe on its branch. **Clean** (the owner fixed it by hand): no resolve run; the item goes to `REVIEW` / `blocked_on: none` (`conflict_fixed_by_hand`, detail `head_sha`) with one fresh review keyed `<id>:review:hand-fixed:<head sha>`, and a message says to run `factory merge <id>` again once it passes (`merge_pending`), because a hand-made merge commit is new content (the owner's answer: a fresh review first; command `factory merge`, no new one). **Still conflicting:** nothing changes, no automatic resolve starts (its limit already stopped it), and the refusal lists the files and names `factory resolve <id>`. The dashboard's Merge takes the same path. The owner-only check is unchanged; PR items keep their refusal (their re-check after a hand fix is a follow-up). Found on wi_1661 (actor-app), hand merge b6d9716. No setting, state, schema change or migration.
- **`/resolve` from the local CLI, and offered in every conflict comment (decision changed 2026-11-08).** Two changes to "Agent resolve via `/resolve`" below:
  - **The local CLI accepts `factory resolve <id> [notes]`**, like `approve`, `retry`, `revise` and `reject`: it stores one `resolve` command in the command inbox (`args.text` = the notes) and changes no item state. The controller rebuilds it as the comment `/resolve <notes>` and applies it as a GitHub `/resolve`: the same `approve_spec` check (through the local auth plugin), the same states (accepted only on `REVIEW` / `blocked_on: human` / `merge_conflict_pending`, or a resolve run's `agent_needs_human`), the same refusal naming the state. The reply is an item message, read with `factory task show`.
  - **Every comment that sets `merge_conflict_pending` ends with the command footer**, so its newest footer lists `/resolve [notes]`: the automatic resolve limit comment (`update_conflict`), a failed resolve run's comment (`resolve_failed`), and a new controller comment on the PR when an update run's tests fail after a clean merge (`update-tests-failed:<run id>`, `update_tests_failed`; the worker's own comment naming the failure is unchanged). Reproduced from the store state of PRs #375, #376 and #391 on 2026-11-07 (merge_conflict_pending after a passed review, no queued run): the newest footer the owner saw was the merge_pending one, listing only `/verdict` and `/help`. The stored items are not migrated or backfilled.
- **Merge check (decision changed 2026-11-07, issue #248).** The controller checks readiness itself. On the poll interval (`poll_interval_ms`), a check step in the controller tick (`src/core/merge-check.ts`, `tickMergeCheck`) looks at every factory PR whose item waits for a human merge (`REVIEW` / `blocked_on: human` / `merge_pending`, factory branch only, never an adopted PR; other states are not checked). Through the sandbox (the same instance `src/compose.ts` passes to the worker pool), it fetches only the base branch (`updateBase`) and the item's branch (`fetchBranch`, into `refs/remotes/origin/<branch>` of the factory repo), then runs `git merge-tree --write-tree --name-only` (`mergeCheck`) in the factory repo's object store. No checkout, worktree or index is used, so the person's working checkout (HEAD, index, working tree) is untouched. The base is fetched at most once per `poll_interval_ms` however often the step runs (an in-process throttle; another replica fetches for itself), and an item's head at the same fetch. The git check runs once per (item, head sha, base sha): the stored result is the cache.
  - **Stored result:** one latest row per item in `controller_merge_checks` (SQLite migration 25): `mergeable`, the conflicting files (sorted, each once), `head_sha`, `base_sha` and `checked_at`. Every replica and the dashboard read the same row (`getMergeCheck`, `listMergeChecks`).
  - **A conflict starts the update run at once,** in the same step, through the same decision and the same key as the GitHub path (`<id>:update:<pr>:<head sha>:<base sha>`), so the local check and a later (or earlier) `pr_unmergeable` for the same pair enqueue one run between them. The run is enqueued before the result is stored, so a crash in between checks again rather than losing it. A step with unchanged shas enqueues nothing and cancels nothing.
  - It works with no GitHub source configured. A sandbox without `fetchBranch` and `mergeCheck` turns the check off; `pr_unmergeable` from GitHub still works as below.
  - The dashboard only reads the stored result (design §9); nothing runs git on a request.
- Merge conflict: when the local merge check above finds a conflict, or GitHub reports an open factory PR as unmergeable (`mergeable === false`, the source's `pr_unmergeable` event), and its item waits for a human merge (`REVIEW` / `merge_pending`), the controller enqueues one **`update` run** per (head sha, base sha). The worker runs no agent for it: it merges `origin/<base_branch>` into the PR branch in a fresh run folder (merge only, never a rebase or force push), runs `repo.test_command` (argv in `factory.config.json`, default `["npm","test"]`) with the worker's tool env, and **pushes only if the merge is clean and the tests pass** (`update_pushed`; the item stays `merge_pending`). Otherwise it pushes nothing and comments on the PR (the conflicting files one per line, or that the tests failed on the updated branch). Failing tests after a clean merge: the controller sets `blocked_on: human` / `merge_conflict_pending` (`update_tests_failed`); the stage stays `REVIEW`. A conflict starts an automatic resolve (below). A base already contained in the branch is a no-op. A git or push error fails the run (`run_failed:update:<code>`), and `/retry` re-enqueues it.
  - **Automatic resolve.** An update run whose merge conflicts makes the controller enqueue a `resolve` run in the same transition, with no `/resolve`: the item goes to `RUNNING` / `blocked_on: none` (`auto_resolve_started`, detail = update run id, base sha, attempt) and the run's key is `<id>:resolve:auto:<base sha>:<attempt>` (`autoResolveKey` in `src/core/policy.ts`), with empty notes. The run is the same resolve run with the same gates as a human's (below).
    - **Limit: 2 automatic resolve runs per base commit** (`AUTO_RESOLVE_LIMIT`, a constant; config can come later). The count is derived from the item's resolve run keys for that base sha (`autoResolveAttempts`), not stored, so there is no migration. A failed automatic run under the limit enqueues the next attempt at once (`auto_resolve_retry`, key from the failed run's key plus one; a rate limit waits for its reset, and counts); the item stays `RUNNING` and no comment is posted. At the limit, the item goes back to `REVIEW` / `blocked_on: human` / `merge_conflict_pending` (`resolve_failed`). An update run that conflicts with a base that already had 2 attempts starts no run and sets `merge_conflict_pending` (`update_conflict`, detail = `auto_resolve_attempts`), with a comment on the PR. A new base commit gets its own 2 attempts. The update run's ack fences it and the failed run's ack fences the retry, so applying either twice enqueues one resolve run.
    - **A human `/resolve` is unchanged:** it is accepted on any item waiting on `merge_conflict_pending`, whatever the automatic count, and does not count toward the limit (its key is `runKey`, not an automatic key). A failed human resolve still waits for the next `/resolve`.
    - **Counts (derived, no schema change):** "resolved automatically" is each succeeded automatic resolve run that pushed a merge with conflicts, plus each succeeded implement run that pushed after resolving conflicts in its sync step (`data.conflicts`, §4 Sync before push); "needed a person" is each state change that set `merge_conflict_pending` (`conflictCounts` in `src/core/resolve.ts`). An automatic resolve's comments go to the PR: on success (`auto-resolved:<run id>`: pushed, a fresh review runs next) and on the final failure (`run-failed:<run id>`, attempt 2 of 2), and the limit comment of an update run (`auto-resolve-limit:<run id>`). Each ends with both counts. The status page shows the same two counts in a `conflicts` column of each item row (empty when both are 0) and on the item page.
    - **Fixed rules in `prompts/resolve.md`** (they apply to the human, the automatic and the implement-retry resolve alike; project-neutral since 2026-11-07, issue #335): keep both sides' sections in documents with sections; when both sides added a migration with the same number, the base keeps its number and the branch's migration is renumbered to the next free number in every file that lists migrations; keep both sides' entries in lists and tables; run the configured checks (`{{check_commands}}`, filled at load). This repo's own merge rules (keep both sides' sections of `docs/design.md`, `docs/design/*.md`, `docs/plugins/*.md`, `docs/settings.md` and `SET_UP.md`, with two current decisions ordered newest first by date and two edits of one decision combined into one, keeping both History lines (decision changed 2026-11-11: the doc folders added, see History)) live in `AGENTS.md`, which reaches agents through `CLAUDE.md`.
  - **Agent resolve via `/resolve`.** A human starts it (and, since 2026-11-02, the factory itself on an update conflict, above): a user with write permission comments `/resolve [notes]` (first line `/resolve`; the notes are the rest of the comment, trimmed) on the issue, or on the factory PR's conversation. The source maps a PR comment to the work item by the head branch `factory/<id>`, as `pr_merged` does, and the 👀 and any refusal go to the PR. The permission check reuses the `approve_spec` action (no new `AuthAction`). A non-writer, or an item that is not `REVIEW` / `blocked_on: human` / `merge_conflict_pending`, gets the usual refusal reply (it names the state by its label, §4 Gate commands), and nothing changes.
    - **Accepted:** the item goes to `RUNNING` / `blocked_on: none` / `blocked_reason: null` and a `resolve` run is enqueued in the same transition (`resolve_requested`, actor = the commenter's user ID). Its key is `runKey` after `restart_count + 1`, bumped like `/retry`, so every `/resolve` gets a key no earlier run of the item has. The notes are stored on the run (`runs.input`, migration 11, SQLite) for the worker. They are untrusted: the prompt puts them in a marked section, below the conflicts and the spec.
    - **The run:** the sandbox starts from the factory branch (it must exist on origin) and runs `git merge --no-ff --no-commit origin/<base_branch>`, leaving the conflicts in the tree. The agent (`prompts/resolve.md`, the resolve class of `model_by` (§4), write tools, the git dir writable; it does not need to commit, the worker commits the checked tree) gets each conflicting file's conflict hunks with both sides, the item's problem, done criteria, scope and `allowed_paths`, the notes, and the instruction to keep both sides' intent and add no new features. **What it may touch:** the conflicting files and `allowed_paths`, nothing else, enforced by the resolve gates in §4. A clean merge (no conflicts) runs no agent and goes straight to the gates.
    - **Success:** the worker pushes the merge to the same branch (no new PR). The controller moves the item to `REVIEW` (`resolved`; `pr_number` unchanged, block cleared) and enqueues a review whose key is `<id>:review:after-resolve:<resolve run id>`, so it never collides with an earlier review key. The usual review outcomes follow (`merge_pending`, or a bug loop), and `pr_merged` closes the item as before.
    - **Failure** (any code: agent, `out_of_scope`, `unresolved_conflicts`, `tests_failed`, `head_moved`, push, egress, rate limit, lease loss): a human's run is not retried automatically (an automatic run under its limit is, above). The item goes back to `REVIEW` / `blocked_on: human` / `merge_conflict_pending` (`resolve_failed`, detail = run id and error code), not `run_failed:*`. One comment, marked `run-failed:<run id>`, names the code and its detail (the detail is dropped if the egress scan flags it; an `out_of_scope` detail starts with the `/resolve +paths` reply for its files, 2026-11-26) and says `/resolve` can be sent again. The next `/resolve` is accepted under a new key.
