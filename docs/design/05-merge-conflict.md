# 5. Coordination: merge conflict

- **The resolve run renumbers a duplicate MySQL step too (decision changed 2026-11-08; before: only the update run and the implement sync renumbered, see History).** Found on PR #417: the branch added `migrations/mysql/0039-sync-lease.sql` while main took 0039 with `0039-implicit-verdicts.sql`. The merge is clean (different file names), so the resolve run had no conflict to work on and went straight to its checks, which the duplicate-number check of the MySQL steps failed. Now the resolve run, after its `--no-commit` merge (and the appended-line merge) and **before its snapshot**, plans and applies the same renumbering as the update run (`renumberPlan`, `applyRenumbering` in `src/core/mechanical.ts`, through the worker's `stageRenumbering`): the branch's new steps move to the next numbers after the base's highest (`git mv`), and literal references to the old names in the files the branch changes (index against the base) are rewritten, all **staged in the index with no commit**. The run's own merge commit (`commit-tree` of the checked tree) carries the moves, then the install command and the checks run. The update run and the implement sync keep their separate renumber commit.
  - **On both paths:** the clean merge (no agent) and the conflict path. Because the moves are staged before the snapshot the scope gate compares against, they are never counted as the agent's changes.
  - **Files it cannot rewrite:** a file still in conflict has no merged text to rewrite. When a conflicting file still names an old step, the resolve prompt gets a "Migration steps renumbered" section after the notes, naming the moves and those files (`staleStepRefs`), so the agent uses the new name. `prompts/resolve.md` is unchanged.
  - **Same skip rule:** no renumbering when the branch changes a SQLite schema file (SQLite's list is append-only, with no step numbers in file names). Inline steps (`INLINE_STEPS` in `src/impl/store/mysql/migrations.ts`) are not renumbered; the resolve agent handles them.
  - **A failure never stops the run:** the worker copies the index aside first; if the renumbering throws, it copies the index back, checks out the tracked files from it (`checkout-index -a -f`, which leaves conflicted files alone), removes any moved step file (`clean -fdq -- migrations/mysql/`), logs `migration renumbering failed`, and the run goes on as it did before this decision.
  - Solo and enterprise alike: no setting, no schema change.
- **`/resolve` from the local CLI, and offered in every conflict comment (decision changed 2026-11-08).** Two changes to "Agent resolve via `/resolve`" below:
  - **The local CLI accepts `factory resolve <id> [notes]`**, like `approve`, `retry`, `revise` and `reject`: it stores one `resolve` command in the command inbox (`args.text` = the notes) and changes no item state. The controller rebuilds it as the comment `/resolve <notes>` and applies it as a GitHub `/resolve`: the same `approve_spec` check (through the local auth plugin), the same states (accepted only on `REVIEW` / `blocked_on: human` / `merge_conflict_pending`, or a resolve run's `agent_needs_human`), the same refusal naming the state. The reply is an item message, read with `factory task show`.
  - **Every comment that sets `merge_conflict_pending` ends with the command footer**, so its newest footer lists `/resolve [notes]`: the automatic resolve limit comment (`update_conflict`), a failed resolve run's comment (`resolve_failed`), and a new controller comment on the PR when an update run's tests fail after a clean merge (`update-tests-failed:<run id>`, `update_tests_failed`; the worker's own comment naming the failure is unchanged). Reproduced from the store state of PRs #375, #376 and #391 on 2026-11-07 (merge_conflict_pending after a passed review, no queued run): the newest footer the owner saw was the merge_pending one, listing only `/verdict` and `/help`. The stored items are not migrated or backfilled.
- **Merge check (decision changed 2026-11-07, issue #248).** The controller checks readiness itself. On the poll interval (`poll_interval_ms`), a check step in the controller tick (`src/core/merge-check.ts`, `tickMergeCheck`) looks at every factory PR whose item waits for a human merge (`REVIEW` / `blocked_on: human` / `merge_pending`, factory branch only, never an adopted PR; other states are not checked). Through the sandbox (the same instance `src/compose.ts` passes to the worker pool), it fetches only the base branch (`updateBase`) and the item's branch (`fetchBranch`, into `refs/remotes/origin/<branch>` of the factory repo), then runs `git merge-tree --write-tree --name-only` (`mergeCheck`) in the factory repo's object store. No checkout, worktree or index is used, so the person's working checkout (HEAD, index, working tree) is untouched. The base is fetched at most once per `poll_interval_ms` however often the step runs (an in-process throttle; another replica fetches for itself), and an item's head at the same fetch. The git check runs once per (item, head sha, base sha): the stored result is the cache.
  - **Stored result:** one latest row per item in `merge_checks` (SQLite migration 25, MySQL step 0025): `mergeable`, the conflicting files (sorted, each once), `head_sha`, `base_sha` and `checked_at`. Every replica and the dashboard read the same row (`getMergeCheck`, `listMergeChecks`).
  - **A conflict starts the update run at once,** in the same step, through the same decision and the same key as the GitHub path (`<id>:update:<pr>:<head sha>:<base sha>`), so the local check and a later (or earlier) `pr_unmergeable` for the same pair enqueue one run between them. The run is enqueued before the result is stored, so a crash in between checks again rather than losing it. A step with unchanged shas enqueues nothing and cancels nothing.
  - It works with no GitHub source configured. A sandbox without `fetchBranch` and `mergeCheck` turns the check off; `pr_unmergeable` from GitHub still works as below.
  - The dashboard only reads the stored result (design §9); nothing runs git on a request.
- Merge conflict: when the local merge check above finds a conflict, or GitHub reports an open factory PR as unmergeable (`mergeable === false`, the source's `pr_unmergeable` event), and its item waits for a human merge (`REVIEW` / `merge_pending`), the controller enqueues one **`update` run** per (head sha, base sha). The worker runs no agent for it: it merges `origin/<base_branch>` into the PR branch in a fresh run folder (merge only, never a rebase or force push), runs `repo.test_command` (argv in `factory.config.json`, default `["npm","test"]`) with the worker's tool env, and **pushes only if the merge is clean and the tests pass** (`update_pushed`; the item stays `merge_pending`). Otherwise it pushes nothing and comments on the PR (the conflicting files one per line, or that the tests failed on the updated branch). Failing tests after a clean merge: the controller sets `blocked_on: human` / `merge_conflict_pending` (`update_tests_failed`); the stage stays `REVIEW`. A conflict starts an automatic resolve (below). A base already contained in the branch is a no-op. A git or push error fails the run (`run_failed:update:<code>`), and `/retry` re-enqueues it.
  - **Automatic resolve.** An update run whose merge conflicts makes the controller enqueue a `resolve` run in the same transition, with no `/resolve`: the item goes to `RUNNING` / `blocked_on: none` (`auto_resolve_started`, detail = update run id, base sha, attempt) and the run's key is `<id>:resolve:auto:<base sha>:<attempt>` (`autoResolveKey` in `src/core/policy.ts`), with empty notes. The run is the same resolve run with the same gates as a human's (below).
    - **Limit: 2 automatic resolve runs per base commit** (`AUTO_RESOLVE_LIMIT`, a constant; config can come later). The count is derived from the item's resolve run keys for that base sha (`autoResolveAttempts`), not stored, so there is no migration. A failed automatic run under the limit enqueues the next attempt at once (`auto_resolve_retry`, key from the failed run's key plus one; a rate limit waits for its reset, and counts); the item stays `RUNNING` and no comment is posted. At the limit, the item goes back to `REVIEW` / `blocked_on: human` / `merge_conflict_pending` (`resolve_failed`). An update run that conflicts with a base that already had 2 attempts starts no run and sets `merge_conflict_pending` (`update_conflict`, detail = `auto_resolve_attempts`), with a comment on the PR. A new base commit gets its own 2 attempts. The update run's ack fences it and the failed run's ack fences the retry, so applying either twice enqueues one resolve run.
    - **A human `/resolve` is unchanged:** it is accepted on any item waiting on `merge_conflict_pending`, whatever the automatic count, and does not count toward the limit (its key is `runKey`, not an automatic key). A failed human resolve still waits for the next `/resolve`.
    - **Counts (derived, no schema change):** "resolved automatically" is each succeeded automatic resolve run that pushed a merge with conflicts, plus each succeeded implement run that pushed after resolving conflicts in its sync step (`data.conflicts`, §4 Sync before push); "needed a person" is each state change that set `merge_conflict_pending` (`conflictCounts` in `src/core/resolve.ts`). An automatic resolve's comments go to the PR: on success (`auto-resolved:<run id>`: pushed, a fresh review runs next) and on the final failure (`run-failed:<run id>`, attempt 2 of 2), and the limit comment of an update run (`auto-resolve-limit:<run id>`). Each ends with both counts. The status page shows the same two counts in a `conflicts` column of each item row (empty when both are 0) and on the item page.
    - **Fixed rules in `prompts/resolve.md`** (they apply to the human, the automatic and the implement-retry resolve alike; project-neutral since 2026-11-07, issue #335): keep both sides' sections in documents with sections; when both sides added a migration with the same number, the base keeps its number and the branch's migration is renumbered to the next free number in every file that lists migrations; keep both sides' entries in lists and tables; run the configured checks (`{{check_commands}}`, filled at load). This repo's own merge rules (keep both sides' sections of `docs/design.md` and `SET_UP.md`; renumber in both the SQLite and MySQL schema lists) live in `AGENTS.md`, which reaches agents through `CLAUDE.md`.
  - **Agent resolve via `/resolve`.** A human starts it (and, since 2026-11-02, the factory itself on an update conflict, above): a user with write permission comments `/resolve [notes]` (first line `/resolve`; the notes are the rest of the comment, trimmed) on the issue, or on the factory PR's conversation. The source maps a PR comment to the work item by the head branch `factory/<id>`, as `pr_merged` does, and the 👀 and any refusal go to the PR. The permission check reuses the `approve_spec` action (no new `AuthAction`). A non-writer, or an item that is not `REVIEW` / `blocked_on: human` / `merge_conflict_pending`, gets the usual refusal reply (it names the state by its label, §4 Gate commands), and nothing changes.
    - **Accepted:** the item goes to `RUNNING` / `blocked_on: none` / `blocked_reason: null` and a `resolve` run is enqueued in the same transition (`resolve_requested`, actor = the commenter's user ID). Its key is `runKey` after `restart_count + 1`, bumped like `/retry`, so every `/resolve` gets a key no earlier run of the item has. The notes are stored on the run (`runs.input`, migration 11, SQLite and MySQL) for the worker. They are untrusted: the prompt puts them in a marked section, below the conflicts and the spec.
    - **The run:** the sandbox starts from the factory branch (it must exist on origin) and runs `git merge --no-ff --no-commit origin/<base_branch>`, leaving the conflicts in the tree. The agent (`prompts/resolve.md`, the resolve class of `model_by` (§4), write tools, the git dir writable; it does not need to commit, the worker commits the checked tree) gets each conflicting file's conflict hunks with both sides, the item's problem, done criteria, scope and `allowed_paths`, the notes, and the instruction to keep both sides' intent and add no new features. **What it may touch:** the conflicting files and `allowed_paths`, nothing else, enforced by the resolve gates in §4. A clean merge (no conflicts) runs no agent and goes straight to the gates.
    - **Success:** the worker pushes the merge to the same branch (no new PR). The controller moves the item to `REVIEW` (`resolved`; `pr_number` unchanged, block cleared) and enqueues a review whose key is `<id>:review:after-resolve:<resolve run id>`, so it never collides with an earlier review key. The usual review outcomes follow (`merge_pending`, or a bug loop), and `pr_merged` closes the item as before.
    - **Failure** (any code: agent, `out_of_scope`, `unresolved_conflicts`, `tests_failed`, `head_moved`, push, egress, rate limit, lease loss): a human's run is not retried automatically (an automatic run under its limit is, above). The item goes back to `REVIEW` / `blocked_on: human` / `merge_conflict_pending` (`resolve_failed`, detail = run id and error code), not `run_failed:*`. One comment, marked `run-failed:<run id>`, names the code and its detail (the detail is dropped if the egress scan flags it) and says `/resolve` can be sent again. The next `/resolve` is accepted under a new key.

## History

- **The resolve run renumbers a duplicate MySQL step too** (decision changed 2026-11-08). Before: migration renumbering ran on the update path only (the update run and the implement sync, after a committed merge, issue #297); the resolve run never renumbered, so a clean merge with a step number both sides took failed its checks.
- **`/resolve` from the local CLI, and offered in every conflict comment** (decision changed 2026-11-08). Before: `/resolve` came only as a comment on the issue or on the factory PR; the local CLI had no `resolve` verb, so a local item could not send it. The comments that set `merge_conflict_pending` carried no command footer, and an update run whose tests failed got no controller comment, so the item's newest footer was the merge_pending one (`/verdict`, `/help`).
- **Resolve prompt rules** (decision changed 2026-11-07, issue #335). Before: `prompts/resolve.md` named `docs/design.md` and `SET_UP.md` for the keep-both-sections rule, the SQLite and MySQL schema lists for the migration rule, and `npm test` and the `npx` rule for running tests.

- **Merge check** (decision changed 2026-11-07, issue #248). Before: the controller learned that a factory PR could not merge only from GitHub's mergeable flag (`pr_unmergeable` on the poll); nothing checked readiness locally, so a ready-to-merge item showed "Ready to merge" even when its branch conflicted with a newer base.
- **Automatic resolve** (decision changed 2026-11-02, issue #119). Before: an update run that conflicted set `merge_conflict_pending` at once and waited for a human's `/resolve`, a failed resolve run waited for another `/resolve`, and only a human started a resolve.

- **Merge conflict** (decision changed 2026-11-01). Before: "→ `READY` / `blocked_on: human` / `merge_conflict_pending`; human instructs, factory resolves".
