# 8. Operations: schedule actions

Split from [08-schedules.md](08-schedules.md) (2026-11-25, moved text, no decision changed).

- **A schedule's action may be `summary`, which posts the owner's summary of what merged, what waits for a decision, what failed and what was unusual, at the morning and evening times; only setup adds one (decision 2026-11-26, local-task-tk_267bcd58 phase 1 of 2; current; a new kind, no decision replaced).** Why: nothing told the owner once a day what the factory did. Owner answers: both time settings are read on each run, so a change moves the next post (1); the summary posts to the owner's chat from wi_805e (2); a window with only spend to show posts nothing (3).
  - **Slots.** `summary_morning_time` (`08:30`) and `summary_evening_time` (`22:00`), HH:MM in the machine's zone, runtime settings read through the live settings on each run. An occurrence takes the latest slot at or before its own time; its window runs from the slot before it. The setup schedules (below) fire every 15 minutes, so each slot is reached within 15 minutes of its time.
  - **Text.** `buildSummary` (`src/core/summary.ts`) reads only what the dashboard reads (`listWorkItemsWhere` for merges and waiting items, `listRunsFinishedSince` and `getWorkItem` for failures, `listSchedules` and `listScheduleRuns` for paused schedules and skipped or refused slots) and writes fixed wording: Merged, Waiting for your decision (each with its first command as a button), Failed (each with `/retry` as a button when it waits for one), Unusual. No model call. Nothing in any section: no summary, and the run records "nothing to report".
  - **Post.** `summaryAction` (`plugins/summary/`) over the port `SummaryDeps` (`plugins/ports.ts`), bound by compose with `summaryDeps`. The text is egress-scanned first: a finding throws, so nothing is posted or stored. Then one outbound delivery keyed `summary:<local date>:<morning|evening>`: a key already stored posts nothing new. With the channel down the run stores the text on its run row and ends normally, so the schedule keeps running. Until wi_805e builds the owner's chat, compose binds `NO_OWNER_CHAT`, a channel that is always down.
  - **Not written by the CLI.** `summary` is in `SCHEDULE_ACTION_KINDS`; `schedule add`, `schedule edit` and the HTTP routes refuse it with a reason that names setup, as they refuse `improve`.
  - **Setup (added 2026-11-26, local-task-tk_267bcd58 phase 2 of 2; extends this decision, replaces none).** A step of `npm run setup` (`addSummarySchedules`, `src/cli/handlers/setup/guided.ts`) adds `summary-morning` (Morning summary) and `summary-evening` (Evening summary), each with action `summary`, an interval cadence of 15 minutes (spec `15`), the machine's zone (`Intl`) and the owner's user ID as creator, whatever `improver.daily_trigger` says. It adds each only when its ID is not stored, so a second run adds none. An interval, not a daily time, because the action picks its slot from the live settings on each run (owner answer 1): a changed summary time moves the next post with no schedule edit. The improve step and this one add through one helper (`addSetupSchedule`: ID, title, action, cadence; skip a stored ID, need an owner, warn naming `plugins.schedule_action` when it is not routed and still add).

- **Every action the factory takes on its own writes one `controller_activity` row with its actor ID, kind, subject, outcome, reason, a transcript or log reference and its time, in the transaction of its change; a schedule run row stores its `reason` and `ref` too (decision changed 2026-11-26, local-task-tk_9a6d93d9 phase 1 of 3; current; replaces "a schedule run row keeps its outcome and output only, and the reaper, retention, cleanup, auto-grant, restarts and migrations write no record a page reads", see History).** Why: the owner could not see in one place why the factory acted on its own. Owner answers (binding): Activity entries are kept 30 days; the Activity page (phase 3) has an Actors card and an About card; a factory alert is dismissed with a Clear button (phase 3).
  - **Jobs.** `src/controller/background-jobs.ts` (`BACKGROUND_JOBS`) lists each background job with its Activity kind, its system actor ID (an ID, never a display name) and where it writes: reaper `lease_expiry`, retention `retention`, cleanup `cleanup`, auto-grant `auto_grant`, schedule `schedule_run`, supervisor `restart`, migrations `migration`. The guard test (phase 2) reads it. The store may not import the controller, so `src/impl/store/sql/activity.ts` keeps `STORE_ACTORS`, typed against the list.
  - **Same transaction.** `expireLeases` writes one row per run it moved (its transcript as `ref`); each retention batch that deleted rows writes one row with its counts (`prunedWithActivity`); a schedule claim writes the run row's `reason` and `ref` (its schedule's run list) and its row; an auto-grant's transition carries its row (`TransitionInput.activity`), so a lost version writes none; a stored supervised restart (`recordChildRestart`) writes its row once. A cleanup pass changes disk, not the store, so it writes its row after the pass (`recordActivity`), only when it removed or failed on something.
  - **Migrations.** A migration applied on an open or by `npm run migrate` writes one row after the migrations commit. A fresh database writes none, and past actions are not backfilled.
  - **Retention.** The retention pass's history class deletes rows older than 30 days (`ACTIVITY_RETENTION_DAYS`).
  - **Not yet.** The guard test (phase 2) and the Activity page (phase 3).

- **A Check a page schedule (`action_kind` `check_page`) is the only routine: the schedule claim pass runs it with the routine planner, and the routine HTTP routes and page are gone (decision changed 2026-11-25, local-task-tk_3ec69bb2 phase 3 of 3; current; replaces the routine decisions, routes and page, see History).** Why: GET `/api/v1/schedules` and the Schedules page show the rows; every GET or POST under `/api/v1/routines` answers 404 (not the shell's 405, so a stale script sees the routes are gone). Owner answer, verbatim: 1. "On an On each merge schedule, should Run now be disabled or hidden?" Answer: "Disabled (the default, accepted)".
  - **Rows.** Migrations `20261124T1100` and `20261125T1000` copied every routine and suggestion (same IDs) into `controller_schedules` (with `trigger_kind`, a nullable cadence and the routine columns) and `controller_schedule_suggestions`. The routine store (`src/impl/store/sql/routines.ts`) touches only those rows; the due list leaves them out.
  - **Claim.** After `runDueSchedules`, `scheduledAction` runs `runDueCheckPages` (`src/core/check-page.ts`): `planRoutine` plans each due row (the On merge trigger; the USD caps), and a fire claims the slot with `claimCheckPage`, one conditional transaction that moves the marks and stores the run row: `fired`, or `checkpoint` over its token cap (`check_page` calls a model). It never sets `running_since`.
  - **Caps.** In USD, from each run's cost. A finished run over `run_cap_usd` pauses its schedule. A due run that would take the UTC day's spend past `daily_cap_usd` is held on a local item (`blocked_on: human`, `blocked_reason: routine_cap`). The shared `/approve` and `/reject` answer it: `/approve` raises the cap for that UTC day by the last run's cost, once per hold item, and the next tick runs the slot; `/reject` skips it.
  - **Action.** `checkPageAction` (`plugins/check-page/`) over the port `RoutineQueue`, which compose binds (`routineQueue`, `src/core/controller-deps.ts`): a `routine` run on the carrier item keyed `routine:<id>:<slot>`. Its tokens and cost go on its slot's run row once; its findings become the schedule's suggestions.
  - **Removal plan for the routine tables.** `controller_routines` and `controller_routine_suggestions` have no reader or writer. 1. Now: they stay so a downgrade finds its rows. 2. A later item adds a breaking migration that first checks every `controller_routines` row has a `check_page` schedule row with its ID and every suggestion its `controller_schedule_suggestions` row (it refuses, dropping nothing, when one is missing), then drops both tables and their `src/controller/table-docs.ts` entries. 3. Their migrations (`20261120T1001`, `20261124T1100`, `20261125T1000`) and tests stay.
  - **Not yet.** Triggers other than merge; dropping the routine tables.

- **A schedule's token cap counts the runs of its period, `token_period`: `day` for a daily cadence, `lifetime` for any other (decision changed 2026-11-25, local-task-tk_33c95362 phase 2 of 4; current; replaces "Token cap. Per schedule, summed over its runs' tokens." below, see History).** Why: over all runs, a daily schedule hit the default cap in a few days and was held for good.
  - **Store.** `controller_schedules.token_period` (TEXT, nullable), migration `20261125T1001-state-controller-schedule-token-period` (additive, no backfill). Null, every older schedule, resolves from its cadence like a new one: `day` for a daily cadence, `lifetime` for any other (changed 2026-11-27: a null daily schedule was counted over all its runs and held for good; see [history/08-schedules.md](history/08-schedules.md)). `tokenPeriod` in `src/core/schedule.ts` is that one rule, read where the cap is summed and by `addSchedule`, which stores it if not given; an edit keeps it.
  - **Count.** `scheduleTokensUsed(id, day?)` sums the runs whose `occurrence_at` is on that UTC date. For `day`, the claim pass, `checkpointAnswer` and `raisedCap` use the claimed or held slot's date, so the next day's occurrence starts fresh.
  - **Not yet.** Setting it from the CLI or HTTP; the page showing it.

- **A schedule's action may be `improve`, which queues the daily improve run of its slot's UTC day; only setup adds one (decision changed 2026-11-24, local-task-tk_33c95362 phase 1 of 4; current; replaces "a schedule's action is build, agent or feedback" in the action decision below, see History).** Why: the owner wants the daily improve run to be a schedule that shows and is owned like the others, so `improver.daily_trigger` off turns off the controller's daily step (design 07-self-improvement) and a schedule queues the run instead. Owner answer 4: one run per UTC day, under the daily run's key.
  - **Action.** `src/controller/units/schedule/plugins/improve/` (`improveAction`) over the port `DailyImproveQueue` (`plugins/ports.ts`); compose passes it as `routes.improve`, bound to `enqueueImprove(…, { slot })`. An occurrence queues the run keyed `improve:<project key>:daily:<YYYY-MM-DD>` for its slot's UTC day (not the time it ran), the controller's daily key, so a second occurrence that day, a rerun or the controller's own daily step queues none. It records `queued` or `already queued` with the run's ID and key; no model call, tokens 0, so the token cap never holds it.
  - **Stored and routed, not written by the CLI.** `SCHEDULE_ACTION_KINDS` (what `addSchedule` stores and `routed` runs) includes `improve`; `SCHEDULE_WRITE_WORDS`, what `schedule add`, `schedule edit` and the HTTP routes accept (`scheduleActionOf`), is build, agent, feedback and check-page (since 2026-11-25, local-task-tk_3ec69bb2 phase 2 of 3; the replaced wording is in History) but never `improve` (owner answer 2 of 2026-11-24, below): an `improve` action there is refused with a reason that names setup.
  - **Setup.** A step of `npm run setup` (`addImproveSchedule`, `src/cli/handlers/setup/guided.ts`) adds, with `improver.daily_trigger` off, the schedule ID `improve-daily`, title Daily improve run, action `improve`, cadence daily at 09:00 in the machine's zone (`Intl`), created by the owner's user ID. It adds nothing when that ID is stored or the flag is on or unset. A schedule runs only when `plugins.schedule_action` is routed, so a fresh install with the flag off and no routed action runs no daily improve (decision 1): setup then warns, naming `plugins.schedule_action`, and still adds the schedule.
  - **Not yet.** Adding the schedule to installs that already run the daily run; the feedback grants and the Schedules page card that shows them (later phases).

- **The Gongbang personas run as feedback schedules, one per persona, and the idle-agents loop is gone (decision changed 2026-11-24, local-task-tk_0ae5a8e9 phase 4 of 4; current; replaces "the feedback run starts its sandbox" and the idle-loop gate in the 2026-11-23 skip decision, see History).** Owner answers: the "only when the factory is idle" gate for the designer and developer personas is dropped, so every persona runs on its cadence (answer 1); the owner starts the sandbox Gongbang (`scripts/idle-agents/sandbox.mjs`) by hand and the schedule names its URL (answer 2). A local development process of this repository, not a factory feature.
  - **Setup.** `node scripts/personas-schedules.mjs [--sandbox-url <url>]` reads the owner's git-ignored `.factory/idle-agents/projects.json`. The roster is the four built-in agents (`gongbang-user-en`, `gongbang-user-ko`, `gongbang-designer`, `gongbang-developer`) plus every agent key in that file, as the loop had it; on the owner's file that is seven. Each persona gets one schedule through `npm run -s factory -- schedule add`: ID `persona-<agent>`, action `feedback`, cadence daily at 09:00, zone the machine's (`Intl`), token cap at its default. An ID that `schedule list` already shows is skipped, so a second run adds nothing; with no projects.json it adds none and exits 0. The definitions come from a pure exported function (`personaSchedules`), tested with a fake CLI (`tests/personas-schedules.test.ts`).
  - **Prompt.** Each prompt tells the persona to read its file under `.claude/agents/` and `scripts/idle-agents/feedback.md` and follow both; with `--sandbox-url` it names that URL. Without a browser grant a persona has no Browse tool and reads code only; with one it opens only that URL (changed 2026-11-25, local-task-tk_33c95362 phase 3 of 4: the feedback grants decision in [08-schedules.md](08-schedules.md); the replaced text is in [history/08-schedules-actions.md](history/08-schedules-actions.md)).

  - **Removed.** `scripts/idle-agents.mjs` (the timer loop, its open-items gate `IDLE_ONLY`/`busyItems`, its own sandbox start), its helper `scripts/idle-agents/schedule.mjs` (`withSandbox` and the once-a-day pick), `tests/idle-agents.test.ts` and the `idle-agents` package script.

- **A schedule's action is build, agent, feedback or (since 2026-11-24, above) improve, run by the `routed` ScheduleAction, and a per-schedule token cap holds a model-calling occurrence at a checkpoint answered by the common `/approve` and `/reject` (decision changed 2026-11-23, wi_af086ea57ce54b0b8f9297f88bfaa146, phase 2 of 4; current; replaces "no action plugin exists yet: the owner has not named one", see History).** Owner answers this phase builds on: a task's repeat stays separate and a build schedule is its own record; each schedule keeps its own IANA zone. The answers on the persona idle gate (dropped), the sandbox the feedback schedules click through (started by hand, its URL named by the schedule) and the Schedules page are for later phases: this one adds no persona schedule, no browser tool and no page, and the idle-agents feedback run's own sandbox start (below) is unchanged. Given values: one work item per build occurrence; Read, Glob and Grep only; at most 3 evidence-backed tasks per feedback occurrence; 200000 tokens per schedule; `/approve` raises the cap, `/reject` ends the run.
  - **Record.** `controller_schedules.action_kind` (`build`, `agent`, `feedback`, `improve`; null: no action, and `routed` refuses the occurrence), `action_settings` (JSON: build `title`, `body`; agent `prompt`; feedback `prompt`, `max_tasks`) and `token_cap` (null: `SCHEDULE_TOKEN_CAP`, 200000). `controller_schedule_runs.output` (the action's result, egress-scanned), `tokens` and `cost_usd` (what its model calls used, added on each run of the occurrence, so a rerun counts). `addSchedule` refuses an unknown kind, settings that are not an object and a cap below 1. One additive migration, `20261123T1100-state-controller-schedule-actions` (under `src/state/migrations/`, which may alter any owner's table), adds the six nullable columns.
  - **Actions.** Three folders under `src/controller/units/schedule/plugins/` (`build/`, `agent/`, `feedback/`), each a `ScheduleActionRoute` over typed ports (`plugins/ports.ts`: `fileItem`, `ask`, `record`). The one selected descriptor is `routed` (`src/impl/schedule-action/routed.plugin.ts`, not a default): it binds the ports to the store, the runner, the sandbox and the scanner and calls the route of the schedule's kind. The folders import nothing outside the controller and the descriptor does not import them: compose passes them in the plugin's context, so the dependency-direction (302) and kinds ratchets do not grow. Build files one local work item, `schedule-<id>-<slot>`, with its triage run queued: a second run of the occurrence gets the same item and files nothing. Agent runs its prompt once in a fresh detached checkout with exactly Read, Glob and Grep (each checked to be capability `read`), `deny_paths`, no writable path, no broker tool and an empty env, and stores the answer and its cost. Feedback asks the same agent for tasks with evidence (path, line, quote) against a schema, files at most 3 evidence-backed ones as local items `schedule-<id>-<slot>-<n>` (so a rerun files none twice and never more than 3 for one occurrence) and records the rest on the run (`over_cap`, `no_evidence`, `no_title`, `withheld`). Every answer is scanned before it is stored or filed (G5). No test calls a model: the fake runner (`tests/helpers/fakes/runner.ts`) stands in.
  - **Token cap.** Per schedule, over the runs of its period (2026-11-25, above). `runDueSchedules` checks it (`overBudget`) when an agent or feedback occurrence comes due on an idle schedule, after the busy skip: over it, the claim is a `checkpoint`: `next_due_at` moves on, `running_since` stays unset, no model is called. A build never calls a model, so the cap never holds it.
  - **Checkpoint answer.** The claim pass (`scheduledAction`) reads the held runs each pass. For each, `checkpointAnswer` (`src/core/schedule.ts`) reads its local item, source `schedule-checkpoint-<id>-<slot>`, filed on the first pass that sees the run (idempotent on the source) with the tokens used, the cap and the cap an approve sets, and moved to wait for a person (`blocked_on: human`, `blocked_reason: schedule_checkpoint`). The common `/approve` on it (`approveCheck`, and `approveRefusal` for `factory approve`) closes it as completed (`schedule_checkpoint_approved`); the next pass then moves the run to `fired`, sets the cap to the larger of the cap and the tokens its period used plus 200000, marks the schedule running and runs the action, all conditional on the run still being held and the schedule idle (else the next pass tries again). The common `/reject` closes the item as rejected; the next pass moves the run to `rejected`. No new command, and the state lives in the store only.
  - **Not yet.** The Schedules page (owner answer 5), the feedback run clicking through the sandbox URL (no browser tool, so feedback reads code only), the dashboard's Approve button on a checkpoint item (its phase is `other_blocked`, so the page lists only `/reject`; the comment, chat and `factory approve` paths take `/approve`), creating or editing schedules from the dashboard, and the retention of `controller_schedule_runs`.
