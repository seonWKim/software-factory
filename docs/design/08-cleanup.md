# 8. Operations: cleanup of closed items

- **A closed item's run folders, merged local branch and the processes still running in its folders are removed once `cleanup.keep_hours` passed since the close, by a close callback each poll and a daily sweep (new decision, 2026-11-23, local-task-tk_c8475295; current; replaces none).** Found 2026-11-20: closing an item cleaned up nothing. 25 run folders (11 GB, about 530 MB each), 11 of them for closed items, and 370 local `factory/*` branches; only the manual `factory teardown` removed anything, and never a closed item's folder. Code: `src/cleanup/` (the pass, handler discovery, the safety helper, three handlers), the `cleanup` controller unit (`src/controller/units/cleanup/`), ticked by the controller role, and the `factory cleanup` command.
  - **Watch the stored state, not the call sites.** Closes are written by several units (closes, local-merge, phases, pr-events, commands, request-transition). The cleanup reads the stored `CLOSED` stage and the close's state change instead of hooking each. It adds no table and no migration: it reads the store and this host's git and folders.
  - **Handlers, one folder each.** Every `src/cleanup/handlers/<name>/<name>.cleanup.ts` is discovered (its default export is `defineCleanupHandler`). A handler lists this host's resources of its kind, each with the item it belongs to, and gives `accepts(resource)`, `keep(resource)` (why it must stay beyond the in-use guard, or none) and `cleanup(resource)` (removes it, returns the bytes freed or none). The pass (`src/cleanup/sweep.ts`) names no resource kind, and nothing in `src/core` or `src/interfaces` does. Handlers run in their `order`: a process stops before its folder goes.
    - **Run folders** (`run-folder`): each `sbx_<8 hex>` clone in this host's worktrees folder. Its item is the one whose branch (`factory/<id>`) it has checked out. A detached folder (a triage run) belongs to no item and stays, listed with its reason (decision 3 of the work item). It goes only when the shared safety check passes. The history line gives its size (`du -sk`).
    - **Local branch** (`branch`): each local `refs/heads/factory/<id>`. The branch decision (decision 1): only a branch merged into the base branch (local or origin's) goes, and never one checked out in a worktree. It is deleted at the sha it was listed at, so a branch that moved since stays. Remote branches are never touched. No size.
    - **Processes** (`process`): nothing records which dev server or browser a run starts, so a process belongs to the run folder its working folder is inside (decision 2; `lsof -d cwd`). It is stopped (SIGTERM) only in a pass that also removes that folder, so a process outside any removable run folder is never touched. No size.
  - **The in-use guard, shared by every handler.** A resource stays when its item is not `CLOSED`, closed less than `keep_hours` ago (the close is its latest state change to `CLOSED`), or has an open interactive session, a running run, or a run holding a live lease. Then the handler's own check.
  - **One safety helper.** The run-folder checks (no uncommitted changes, no commits the repository lacks) and the merged-branch rule are `folderUnsafe` and `mergedRule` in `src/cleanup/removal-safety.ts`. `factory teardown` imports the same helper; what teardown removes is unchanged (design 08-teardown).
  - **History and failures.** Each removal writes one state change on the item (reason `cleanup_removed`, actor `system:cleanup`, no field changed), whose detail names what went (`removed`, `kind`) and, for a folder, `bytes_freed`. A failed removal is logged (`cleanup removal failed`), never stops the close or the other removals, and stays for the next pass to try again.
  - **When it runs.** The controller role ticks the `cleanup` step each poll interval. The close callback reads the items closed within the last `keep_hours` plus a day and handles those whose keep passed; none due, it lists nothing. A process caches the items it handled (a cache only; a restart reads them again). Then the daily sweep, over every resource of this host, at most once per UTC day under the store lease `cleanup:<host id>` with the day it finished in the store cursor of the same name, as the retention pass does (design 08-retention). The lease and mark are per host: each host sweeps the folders it made, and never another host's. The sweep catches what a callback missed: a crash, and items closed before this change.
  - **`factory cleanup`.** Runs the sweep now and prints what it removed (with sizes and the total freed), what it kept and why, and what failed. `--dry-run` prints each resource that would go and each kept one with its reason, and changes no file, branch or history.
  - **Settings: `cleanup.enabled` and `cleanup.keep_hours`.** `factory.config.json` takes a `cleanup` block: `enabled` (default `true`) and `keep_hours` (default 24, so a failed merge can still be inspected). With `enabled` false neither the close callback nor the sweep removes anything. `keep_hours` must be an integer of 0 or more; anything else, or an unknown key under `cleanup`, fails config load naming the key. The block is file-only like `retention`: a shorter keep changes only by a reviewed PR.
  - **Not covered.** A dashboard view or button (a CLI-only gap, a follow-up). Another host's folders and branches. Remote branches. How runs keep a folder for a pause, a stopped-run retry or an interactive session is unchanged; such a folder's run is queued or running, and its item is not closed. The file watcher (FSEvents) running at a full core, found with this, is a separate follow-up.

- Replaced decisions of this topic: none (a new topic, 2026-11-23).
