# 9. Status page

**Three levels for what waits: Needs you, Needs triage, Blocked by another task (decision changed 2026-11-12; replaces the one "Needs a human" level and "Waiting on another issue").** The list's levels are now: ready to merge, needs approval, Needs you (`needs_you`), Needs triage (`needs_triage`), stuck, running, queued, Blocked by another task (`blocked_by_task`), closed. `levelOf` (`src/ui/priority.ts`) reads two more inputs that `src/ui/list.ts` fills: `held` (the item's queued run has an unapproved `held` claim decision, a coordination hold) and `asked_by` (the kind of the run behind an `agent_needs_human` block, `blockingRunKind`).
- **Blocked by another task:** a coordination hold, a deadlock claim, a dependency hold (`blocked_on: dependency`, also while its run is queued) and a phase or upstream hold. The badge names the item it waits on: `waits on #N` (a coordination or deadlock holder's number from its `holder_ref`, a dependency's or phase's number), `deadlock with #N`, else fixed words. Held work no longer looks like work that needs a decision.
- **Needs triage:** an item whose latest agent ask came from a triage run. The row shows the agent's question and an Answer link to the ask comment. Triage cannot ask yet (its output has no `needs_human`, a follow-up), so this level stays empty until then.
- **Needs you:** every other person's or budget block: merge pending and spec approval keep their own levels inside the Needs-you group; failed run, max loops, merge conflict, budget, Rule of Two, dependency closed, implement/review/resolve asks and unknown reasons are `needs_you`. A row never shows an empty reason or "no reason": a null block reason reads "waiting for a person"; an agent's ask reads its question.
- **Counts and filters.** The `needs` filter ("Needs you": server `src/ui/filters.ts` `NEEDS_YOU`, the web app's `NEEDS_YOU_LEVELS`) is the Needs-you group plus Needs triage, never Blocked by another task. The `needs_you` level is no filter option of its own (`state=needs_you` is a 400): it would share the group's label, and the group shows it. The overview `needs_you` counts items blocked on a person or the budget plus system actions; a deadlock claim is in Blocked by another task, is no system action and is not counted (its run goes on). The old ids `needs_human` and `waiting_on_issue` are gone: a request with one gets 400.
- **Colours** reuse the existing tones: Needs you red, Needs triage amber, Blocked by another task neutral zinc (web); warn for both person levels on `/classic`.

**A verdict from Needs you (decision changed 2026-11-11, issue #513; replaces "a Needs-you row offers only the commands that change the item's state, so a waiting item has no verdict there").** A Needs-you row in the app lists `verdict` after its state-changing commands wherever it applies (an open item with a PR, or a local item with or without one), with a one-line text form; sending it stores the same app request as the item page's note box. The server-rendered `/classic` page is unchanged. Details in [09-dashboard-app.md](09-dashboard-app.md).

**Read-only status page (new decision, 2026-11-01).** `npm run factory -- ui` serves two pages from `node:http` on `127.0.0.1:<ui.port>` (`factory.config.json`, default 4310; there is no host option): `/` (Needs you, see below; Running now, highlighted when the last heartbeat is older than `lease_ms`; Queue, oldest first; All work items, `?stage=` filter, CLOSED hidden unless `?closed=1`; Totals: items per stage, runs succeeded and failed and tokens in the last 24 h) and `/items/<id>` (state_changes timeline and runs). No actions (approve, retry, merge stay on GitHub), no login, no remote access.
- **A surface, not a plugin.** Like the CLI it reads `FactoryStore` and has no plugin interface or `docs/plugins.md` entry. It is built through `Plugins` (store, secrets, scanner), not `build()`, so it runs no controller or worker.
- **Withhold, not mask.** Free text from the store (titles, blocked reasons, state-change values and reasons, run errors) is egress-scanned before rendering. `EgressScanner.scan` returns rules, not spans, so a field with any finding is replaced whole by `[withheld: <rule>]`. Span-level masking would need a new `EgressScanner` method; that is a separate tier-4 change if wanted.
- **Request guards.** GET and HEAD only (405 with `Allow: GET, HEAD` otherwise) except the two write routes, `POST /api/v1/settings` and, since issue #291, `POST /api/v1/pauses/resume` (each behind the Origin, Content-Type and CSRF guards; the resume route also checks the owner, see [09-dashboard-app.md](09-dashboard-app.md)), unknown paths 404, and a Host header other than `127.0.0.1` or `localhost` (any port) gets 403, against DNS rebinding: the page exposes store data to any local browser tab. Responses carry a CSP with `default-src 'none'`.
- **New nullable columns** (migration 3, SQLite and MySQL): `work_items.title` (written at intake; `problem` is unchanged, since triage overwrites `problem` with the spec), `runs.started_at` (set on every claim, so it is the latest attempt's start) and `runs.finished_at` (set when a run succeeds or fails, by the worker or the reaper; a reaper requeue leaves it null). Rows from before the migration read as null: an item without a title shows its source id, a run without `started_at` shows an unknown duration. `title` is store-owned, not in `WorkItemPatch`.
- **New read methods** on `FactoryStore`, implemented once in `SqlFactoryStore`: `listWorkItemsWhere` (stage, blocked_on, exclude closed), `countWorkItemsWhere` (the same filter, no limit), `countWorkItemsByStage`, `listRunsByStatus`, `listRunsFinishedWithin(window_ms)` (the window is measured on the store's clock, so no "now" argument).
- **Needs you (no decision changed, 2026-11-01).** The top of `/` is "Needs you (N)", and the page `<title>` carries the same N. N is `countWorkItemsWhere({ blocked_on: "human", exclude_closed: true })`, an exact count however many there are; the rows are at most 200 of them (the most recently updated). One row per item, oldest wait first, where the wait starts at the latest state change that set the current `blocked_on` or `blocked_reason` (not `updated_at`). A row shows the issue number, the title, how long it has waited, the reason in plain words, a link to where to act and the command to type: `spec_pending` → "spec ready", the spec comment, `/approve or /reject <reason>`; `merge_pending` → "ready to merge", the PR, "merge the PR"; `run_failed:<kind>:<code>` → "failed: <code>", the failure comment, `/retry`; `max_attempts` and `max_restart` → "failed: <code>" with the code of the item's latest failed run, the failure comment, `/retry`; anything else (`max_loops`, `merge_conflict_pending`, unknown reasons) → the reason in plain words, the issue, no command. A missing stored link falls back to the issue. Still no forms or buttons.
- **Comment links** (migration 8, SQLite and MySQL): nullable `work_items.spec_comment_url` and `work_items.failure_comment_url`, in `WorkItemPatch`. `SourceAdapter.postComment` and `GitHubClient.commentOnce` return the comment's URL, also when the marker comment already exists, so a re-applied decision stores the same link. The controller stores the spec URL in the transition that sets READY + `spec_pending`, and the failure URL in the transition that blocks on a failed run (`run_failed:*`, `max_attempts`, `max_restart`); when the egress scan withholds the last-attempt comment, or no comment is posted, it stores null. Outbound's delivery records the URL (`DeliveryCompleted`). Older items read null and link to the issue.

- **"Last 24 h"** counts runs by `finished_at`. Tokens are summed in app code over every finished run, failed included, with the same full count the controller adds to `token_cost` (see §6 "What tokens counts", [06-token-budget.md](06-token-budget.md)). A **Cost** section below Totals shows USD per UTC day for the last 7 days by run kind, unknown costs shown as unknown.
- **Dashboard UX.** `/` is one list in priority order (`src/ui/priority.ts`, pure): ready to merge, needs approval, needs a human for another reason, stuck (a running run past `lease_ms`, or an open item nobody moves), running, queued, waiting on another issue, closed (hidden by default). Within a level: more dependents first, then the oldest wait, then the higher tier. Each row has fixed-word reason badges; rows that wait on a person show the old Needs-you reason, link and command in a "next step" column. The `<title>` count is unchanged (exact human-blocked count). Filters (`src/ui/filters.ts`, pure) come from the query string on the server render, so they work without JavaScript: `state` (`needs` or one level), `stage`, `tier`, `kind`, `unblocks=1`, `closed=1`, `q`; any unknown value is a 400. Each option shows how many rows it would give with the other filters kept. Choices: (a) "oldest wait" is when the current block was set (the latest state change that set `blocked_on`/`blocked_reason`) for human- or budget-blocked items, else `updated_at`; no new store method. (b) Run kind is the kind named in a `run_failed:<kind>:` reason, else the kind of the item's running (or else queued) run. (c) Dependency input is empty until #49: the waiting level and `unblocks` stay empty. (d) Search covers the issue number and the title as the page shows it, after withholding, so a withheld title can't be found (and gets no `title` attribute).
- **Refresh and CSP.** No meta refresh. One constant inline script fetches the same URL every 5 s while the tab is visible (`visibilitychange` stops and restarts it), parses it with `DOMParser`, and replaces only the `<main>` sections whose HTML changed, restoring scroll, open `<details>`, form values, focus and selection; rows whose `data-sig` (version, level, run status) changed get an opacity flash of 180 ms, none under `prefers-reduced-motion`. A manual refresh button (`aria-label`) shows only with JavaScript; `<noscript>` has a Refresh link. The CSP is now `default-src 'none'; script-src '<sha256 of the script>'; style-src '<sha256 of the style>'; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`. Both hashes are computed from the constants in `src/ui/html.ts`; there is no `style=` attribute and nothing loads from another origin. Styling: colour, spacing and radius tokens on `:root` with a dark theme via `prefers-color-scheme`, tabular numbers, titles cut with an ellipsis (full text in `title`), tables in their own horizontal scroll box so the page fits 375 px.

- **Section order and waiting items (decision changed 2026-11-07).** `/` puts what the operator acts on first and background last: the factory banner, Running now, Queue, Paused, the filters and the ranked work-item list, Health, then Totals, Merges and Cost (Merges since 2026-11-11). An item blocked on `upstream` or `dependency` ranks as waiting on another issue, never as stuck. A held split phase (`phase_hold`) shows `waits on #N`, the phase before it; a split parent (`phases_open`) shows `waits on N issues`, its open phases (`#N` when only one is open). Both are worked out from the listed items' `parent_id` and `phase`; the badge holds only fixed words and numbers.
- **Merges digest (new decision, 2026-11-11, issue #512).** The classic page `/` shows a "Merges (last 7 days)" section between Totals and Cost. It shows the counts of merged, reverted and fixed-forward merges, the verdicts by kind and the tokens. Below the counts are the newest 20 merges: the item, when it merged, its tier and tokens, what happened after it (reverted, fixed forward, or "nothing yet") and its verdicts. It reads `listMergeEvaluations` once and sums with `digestMerges` ([06-measurement.md](06-measurement.md), per-merge evaluation), in `src/ui/merge-digest.ts`. No sync plugin is read, so the section renders the same with none configured or during an outage. **Empty state:** with no evaluation in the window it says "No merge in the last 7 days" and that merges from before evaluations were stored are not counted. **Free text:** the only free text is the item title, which goes through the Withholder. A title with a finding is replaced whole by `[withheld: <rule>]`. The digest is not posted to GitHub, Slack or Jira. The dashboard app does not render it yet.
- **System actions no longer list a deadlock (decision changed 2026-11-11; current; replaces the deadlock entry of "System actions in Needs you", see History).** There is no `claim_deadlock` system action and `SystemAction` has no `work_item_id`: a deadlock claim does not stop the run, so no person is needed (design 09-dashboard-app). The order is: migration, token, claim pauses, worker pauses, alarms, revisions. `needs_you` = the human-blocked items + `system_actions.length`; the Floor's Needs you count is the table's rows + the system actions, with no item-row exception.
- **System actions in Needs you (new decision, 2026-11-07, issue #311; the deadlock entry is replaced, see above).** Needs you also lists what the factory needs from the operator besides a work item, each with the command that clears it, in this order: a pending migration (the store's `schemaVersion()` behind the code, a store that refuses to open with `migration_pending`, or the supervisor's `migration_pending` state) → `npm run migrate`; a GitHub token with fewer than 3 days left → `npm run setup -- --rotate-github`; each claim pause in effect with its end time (`model_stall`: the next probe) → `factory resume <name>`; worker pauses in effect → `factory workers resume`; each item whose current run's latest claim decision is a deadlock, listed until the run is resolved → `factory status <id>`; and a revision mismatch → `reload / restart \`factory ui\`` (the dashboard sends its built-in revision as `?rev=`, compared with the server's) or `restart \`factory ui\`` (the UI server runs another revision than the running factory). `GET /api/v1/overview` returns them as `system_actions: [{ code, text, command, until, work_item_id }]` (text through the Withholder) and `needs_you` = the human-blocked items + `system_actions.length` (a deadlock was already counted; it now counts as its system action). **Reads:** store reads only (`schemaVersion`, `getClaimPause`, `listWorkerPauses`, `listClaimDecisions`), the supervisor's status file and in-process values: the token's days come from this UI process's last health run (`LastChecks`, `src/ui/system-actions.ts`), so a poll makes no GitHub request; a replica with no health run yet returns `github_token_days: "unknown"` and lists no token action. The app's Floor shows them at the top of Needs you (an item shown in the table counts once), and the browser tab title leads with the count: `(4) Floor · software-factory`, no prefix at 0. `/classic` keeps its own count.
- **Alarms in Needs you and the why-it-waits sentence (new decision, 2026-11-08; extends System actions in Needs you).** An alarm is an alert the alarm step stored (design 05-alarms). It is **open** while its pattern key's newest alert is less than the alarm step's dedupe window old (`ALERT_DEDUPE_MS`, 6 hours): a pattern that still holds alerts again then, one that stopped is **resolved** and drops out. There is no resolve command or button. **Needs you:** each open alarm is a system action with code `alarm`, after the deadlocks and before the revisions: its sentence (`Alarm: <code> failed <n> runs on several items`, `Alarm: <n> agent runs in a row used no tokens`, `Alarm: the factory restarted <n> times in 30 minutes`), `: <detail>` when the scanned detail was stored, where to look (`Failures page (/app/failures)`, `factory llm-check`, `factory doctor`) as its command, and `until`, when it closes by itself. It counts in `needs_you`, and the app's Floor lists it at the top of Needs you like any system action. `/classic` shows the same rows in a "Needs you: open alarms (N)" section under the factory banner; its title count is unchanged. **Affected items:** an open item is affected by a repeated-error alarm when its latest finished run failed with the alarm's code, by a zero-token alarm when its latest finished run is an agent run that used no tokens (both only for a run finished at most 6 hours before the alert, or after it), and by a crash-loop alarm when it has a queued or running run. The why-it-waits sentence of an affected item names each such alarm after the sentence (`Queued at position 1. Alarm: …`, `withAlarms` in `src/ui/why.ts`), whichever rule gave it, so Work items, the item page and the Queue (and the Floor's Needs you table) show it; `/classic` adds it to the item's row and to its item page facts. **Reads:** `listAlerts` once per request (at most 100) and the item's `listRuns` only while an alarm is open (the list reads them already). Pure helpers in `src/ui/alarms.ts`. No store method, schema or migration for this part.
- **Claim pauses on the Floor page (new decision, 2026-11-07, issue #291).** The app's Floor page shows a "Claim pauses" section right after the factory banner while any claim pause is in effect: each pause's name, what it stops and when it ends, with a "Resume now" button (`POST /api/v1/pauses/resume`); the endpoint's error shows next to that button. Nothing shows while no pause is in effect. The server-rendered page at `/classic` is unchanged and has no button.
- **GitHub budget (new decision, 2026-11-07, issue #340).** The classic page shows a "GitHub API" section after the factory banner, and `GET /api/v1/overview` returns `github_budget`: GitHub's limit and remaining calls, the reset time, this process's `budget_share`, its share in calls and its counted calls in the window, the state (`ok`, `low`, `waiting`), the replica that stored it, and `wait_reason` (`waiting for the GitHub rate-limit reset at <time>` while no calls are left). It is read from the store cursor `github:budget` the controller writes after each poll (05-sources.md, GitHub call budget), so the page makes no GitHub call. A wait is not an error and not a system action: once the stored reset has passed the state is `ok` and the count 0. Null when nothing is stored (GitHub not in use, or no poll yet). The dashboard app does not render it yet.

## History

- **Levels for what waits** (decision changed 2026-11-12). Before: one "Needs a human" level (`needs_human`) held every `blocked_on: human` item, every budget block and every deadlock claim; coordination holds were "Queued" and dependency holds "Waiting on another issue" (`waiting_on_issue`); the overview's `needs_you` counted only human blocks, and a null reason read "no reason".
- **A verdict from Needs you** (decision changed 2026-11-11, issue #513). Before: Needs you offered only commands that change the item's state; a verdict was sent from the item page's note box only.
- **Merges digest** (new decision, 2026-11-11, issue #512). Before: the page had no digest of what the loop merged or what happened after each merge. **Section order** changed with it: Totals and Cost became Totals, Merges and Cost.
- **Alarms in Needs you and the why-it-waits sentence** (new decision, 2026-11-08). Before: alerts were stored and readable through `listAlerts`, but no view showed them: Needs you, the why-it-waits sentence, the item list and the item page said nothing of an open alarm.
- **GitHub budget** (new decision, 2026-11-07, issue #340). Before: the page showed no GitHub rate limit, so a factory at 0 calls looked idle or failing.

- **System actions in Needs you** (new decision, 2026-11-07, issue #311). Before: Needs you counted only items blocked on a person (and, since issue #310, deadlocked items), so a pending migration, an expiring token, a claim pause and a stale UI were not listed, and the tab title had no count.
- **Claim pauses on the Floor page** (new decision, 2026-11-07, issue #291). Before: the Floor page showed no claim pause, so the operator saw runs not starting with no reason and no way to end the pause but a database edit.
- **"Last 24 h" tokens** (decision changed 2026-11-02, issue #136). Before: succeeded runs only, input + output.
- **Refresh and CSP** (decision changed 2026-11-01). Before: meta refresh every 5 s and no JavaScript; the CSP had `style-src 'unsafe-inline'`, `form-action 'none'`, no script.
- **Read-only status page** (first decided 2026-11-01): meta refresh every 5 s, no JavaScript, no front-end dependency. Replaced by Refresh and CSP, and by the dashboard app ([09-dashboard-app.md](09-dashboard-app.md)).
- **Dashboard UX** (decision changed 2026-11-01, issue #64). Supersedes "no JavaScript, meta refresh" and the fixed Needs you / All work items sections.
- **Needs you** (2026-11-01). It replaces the "Waiting for you" list.
- **Section order and waiting items** (decision changed 2026-11-07). Before: Totals and Cost came first, Running now and Queue came after the list and Health, and a split phase or parent waiting on other phases showed as "stuck N min".
- **A deadlock listed as a system action** (decision changed 2026-11-11). Before: each item whose current run's latest claim decision was a deadlock was a `claim_deadlock` system action (`factory status <id>`, `work_item_id` set), counted once in the Floor when its row was also shown. Now it is not listed.
