# 5. Coordination: restarts

- **Restart history is kept in the store, one row per restart (new decision, 2026-11-08; changes where the restart alarm's history lives).** Each unexpected child exit the supervisor records (`restarts: [{ at, reason }]` in `<state_dir>/supervisor.json`, design 05-alarms) is also stored as one row of `child_restarts` (`restart_key`, `at`, `reason`, `recorded_at`; SQLite migration 38, MySQL step `0038-child-restarts.sql`). The controller's alarm step writes it: before it counts, it stores each restart of this host's list with `FactoryStore.recordChildRestart`, one conditional insert keyed on the restart's time and a hash of its reason, so the same restart read again on the next poll, or by another replica, leaves one row (`created: false`), and the write is safe to run twice. `listChildRestartsWithin(window_ms)` reads them oldest first on the store's clock. A process with its own restart list counts that list, as before; a process without one (in-place or `none` updater, a controller on a host with no supervisor) counts the store's restarts of every host. So the restart alarm's count and its 30-minute window read the same after the factory or the store restarts. Solo default: the one SQLite store, the same rows. Enterprise: replicas on the shared MySQL store run the same conditional insert and the same step number. **No backfill:** restarts from before this change were never stored and are not reconstructed; existing items and alerts keep their data, and the migration only adds the empty table. Item restarts are unchanged: an infra failure or `/retry` still only bumps `restart_count` on the item, and the retry, backoff and block rules below are untouched.
- **A dead network pauses claims, not runs (new decision, 2026-11-07; also changes the stall pause's probe and its early end).** A git call (fetch, push, the sandbox's base fetch), the GitHub preflight or a model request through the shared chat client that fails on DNS or connect (`Could not resolve host`, `Failed to connect to`, `getaddrinfo ENOTFOUND`, `ECONNREFUSED` and the like; `unreachableHost` in `src/core/policy.ts`) is `network_unavailable`: the broker returns it for a push and for the preflight's GETs, the openai-compatible runner reports it as the error `network_unavailable: could not reach <host>`, and the worker turns a `git_failed`, `push_failed`, `preflight_failed`, `preflight_access` or `exception` whose text is such an error into it (`classifyNetwork`). Every other `git_failed` and `push_failed` keeps its code. Its detail is `could not reach <host>`, the host name only, never git's text, a URL, a credential or a response body. It is not a failure of the run: the worker sets the `network` claim pause (first probe 30 s later), then puts the run back in the queue with `pauseRun` and nothing to resume (`paused_by: system:network`), so it has no outcome, its attempt is unchanged at the next claim, and it never counts toward `max_restart` or `max_attempts`, never meets the repeated-failure rule and never reaches a dead letter. The run's folder is not kept: an implement run whose push failed on the network runs its agent again. While the pause holds, `claimRun` returns null for every kind, triage and review included; the pause is global, as the rate limit is. The `network` pause is a probe pause like `model_stall`, one store code path for both (rows `network`, `network_since`, `network_answered` in `claim_pauses`; no migration): in effect past its time until a probe passes. **One probe schedule for both probe pauses:** once a probe is due, the controller replica whose conditional update moves the row from the due time to the next probe time (`FactoryStore.claimProbe`) probes, and no other replica; a pass ends the pause through `endClaimPause`, which moves the pause row and its answered row to the earlier of the probe time and now (the stall pause's rule, below, now for both); a failure keeps the pause and moves the next probe its delay after the failed probe. The stall's next probe is `probe_interval_ms` later, as before; the network's is 30 s, 30 s, 1, 2, 4 min, then 5 min (`networkProbeDelayMs`, retryDelayMs over the probes made). The network probe is the `NetworkProbe` interface, default plugin `http` (docs/plugins/network-probe.md): one HEAD to each endpoint of the selected plugins, GitHub only when a GitHub plugin is selected. Solo default and enterprise setting are the same, with no new setting. Logs: one warn when the pause starts (`network unavailable: all runs paused, first probe at <time>`, field `host`), info per failed probe, one info when claims resume (`network reachable again: claims resume`). `factory status` and the Health panel show `agents paused: network not reachable since <time>; runs start again once a probe passes`. Not in this decision: the dashboard's why-it-waits sentence (`src/ui/why.ts`) and `factory resume network`, which need files outside this change; the Claude CLI's own network failure text.
- **A GitHub rate limit waits for its reset; it is not a refused credential (decision changed 2026-11-07).** The REST client reads `retry-after`, `x-ratelimit-remaining` and `x-ratelimit-reset` on every refused call. A 429, or a 403 with `retry-after`, with `x-ratelimit-remaining: 0`, or whose body names the primary (`API rate limit exceeded`) or the secondary limit, throws a `GitHubRateLimitError` with `reset_at`: `retry-after` first, then `x-ratelimit-reset`, else one minute from now. A call the client refuses itself (no calls left before the last reset) throws the same error. The broker returns `github_rate_limited` for it from the preflight, `open_pr` and `comment`, never `forge_auth` and never an exception; its message carries the check or tool and the reset time, never a header or body. The push keeps `forge_auth` (git's stderr is not read for a rate limit; a follow-up). A plain 403 with none of these signals is still `forge_auth`: the forge-auth rule is not widened. The worker, before it stores the outcome, sets the `github_rate_limit` row of `claim_pauses` to the reset (only ever moved later; one log line when a pause starts); it does not touch the model `rate_limit` row or the `forge_auth` row. While the row is in effect `claimRun` skips implement, update and review runs (all three call GitHub on their way) for every worker and replica and still claims triage and resolve, and the controller skips its GitHub source poll with no log line per skipped poll. A run that fails with it spends no attempt and no restart (`failureClass` is `rate_limited`, update runs included); its retry's `not_before` is the later of its backoff and the pause end (`retryNotBefore` in `src/core/policy.ts`). An `open_pr` rate limit keeps the run's commits on its wip branch through the same path as any failed PR (below), so the retry runs no agent. The permission lookup throws on a rate limit until the reset, never "none"; no stored grant stands in for it, and local actions use local auth. No owner comment, no migration (the table takes any name), and no new GitHub call; solo and enterprise behave the same, and on a shared store every replica waits. Known gaps: the pause is not in `factory resume`'s list or the Floor/Health pause list yet, and a controller poll that hits the limit does not set the pause itself.
- **Checks that fail on the base too are `checks_env` (decision changed 2026-11-07).** An implement run whose pre-push check fails twice, and whose failing test files fail on a clean checkout of the base commit too (§4 Pre-push gates, base rerun), fails with `checks_env` (`CHECKS_ENV` in `src/core/policy.ts`), its own failure class: it spends no `max_attempts` and no `max_restart`, adds nothing to `restart_count` and never triggers `repeated_failure`. The controller requeues it from the kept commits (the wip branch) with the usual retry key and backoff, reason `run_retry_scheduled`. The cap is `CHECKS_ENV_LIMIT` = 2 per item, counted from the item's whole run history in the store (every acknowledged `checks_env` run, plus this one), so every replica counts the same: the third `checks_env` on an item blocks it on a human with `run_failed:implement:checks_env` (reason `checks_env`), queues nothing, and posts the last-attempt comment, keyed `run-failed:<run id>`, with the failing tests; `/retry` works as for any `run_failed:*`, and since the count is per item, a further `checks_env` after it blocks again at once. A real bug that also fails on the base (a broken base) is read the same way: each item is requeued up to twice, then blocks. The worker's own comment for each `checks_env` run names the flaky test files (§4). Solo and enterprise use the same path. Not in this decision: filing a factory issue for a test file that is flaky three times in 24 hours.
- **Failure details keep the cause; `provider_setup` is not retried (decision changed 2026-11-07).** A failed check's detail names the failing tests: `checks_failed` appends `failing tests: <file> > <name>, ...` (vitest's `FAIL` lines in the output tail, at most 10, `failingTests` in `src/core/output-summary.ts`); the output tail is kept as before. A rate limit keeps its reset text: the claude-code runner's `rate_limited` error is the CLI's result text (e.g. `You've hit your 5-hour limit · resets 6:30pm`), capped at 500 characters, or `rate_limited` when the CLI gave none; `reset_at` is read as before. The shared OpenAI-style chat client reads the error body of every non-2xx reply, a 429 included: `error.code` (or `error.type`) `insufficient_quota`, `invalid_api_key` or `model_not_found`, at any HTTP status, is `provider_setup`, with the provider's message (key redacted, then capped at 300 characters); any other 429 stays `rate_limited` and keeps the message too. A runner reports it as a `failed` result with `code: provider_setup`. A fallback chain moves to its next member on it (no output was made); only when no member is left does the run fail with it. The worker records the code `provider_setup` (a task failure), sets no claim pause and never reports it as `rate_limited`. The controller does not retry it, for any run kind: the item blocks on a human with `run_failed:<kind>:provider_setup` and one comment, keyed `run-failed:<run id>`, says to check the quota or billing, the API key and the model names, then `/retry` (an automatic resolve run goes back to waiting on the conflict instead of its next attempt). Every new detail is in the outcome, so the worker's whole-outcome egress scan covers it: a flagged detail makes the run `egress_blocked`, as before. For `provider_setup` only, the worker scans the provider's message first and, if flagged (OpenAI's `invalid_api_key` message can echo part of the key), keeps the code and drops the message and the output tail. `llm-check` prints the provider's message on its FAIL line, after its own scan. Not in this decision: the improver (#304) and the failures view (#312), which read these details later.
- **An owner can end a claim pause early (decision changed 2026-11-07, issue #291).** `FactoryStore.endClaimPause(name)`, implemented once in the shared SQL store (SQLite and MySQL), ends `rate_limit`, `forge_auth`, `preflight_access` or `model_stall` now. For the three timed pauses it is one conditional update, `resume_at = now WHERE resume_at > now`, so a second end, or an end with no pause in effect, changes no row. `model_stall` ends only when `model_answered` is at or after the probe time, so its end moves both rows to the earlier of the probe time and now (under the claim lock; since 2026-11-07, see the stalled runs and the network pause), as an answered probe does; `model_stall_since` then reads null too. `pauseClaims` still only moves a pause later, and when a pause starts or how long it lasts is unchanged; a pause ended early is "not in effect", so the next failure starts a new one (`started`). Two ways in: `factory resume` (`rate_limit`), `factory resume <name>` or `factory resume --all` (all four), which prints what it ended or `no pause in effect`, exits 0, and exits 1 with no write for an unknown name (`model_stall_since` and `model_answered` are not names); and the dashboard's "Resume now" button (`POST /api/v1/pauses/resume`, design 09-dashboard-app.md). Each end writes one log line, `claim pause ended` (or `claim pause resume: none in effect`) with the pause and the actor ID: `local:<login>` on the CLI, the factory user ID in the UI, never a display name. No comment is posted on the item or the PR. No migration or schema change: the rows are those of migration 4.
- **A drain stops the controller at once (decision changed 2026-11-07, issue #294).** When a supervised `dev` child gets the drain message, its controller loop and its stream listeners stop at once: it starts no new pass (no intake, reaper, checks, app commands, run outcomes or model probe), and a pass already running finishes. Only the worker's running runs finish, under the old child's worker, which claims nothing more. The old child runs no final pass over finished runs: the new child's controller, already started (start-then-drain, `docs/design/08-self-update.md`), applies their outcomes on its next pass. The old child logs one line, `controller stopped on drain`, then acknowledges the drain once its runs finished. SIGINT/SIGTERM still stops both loops of every child at once. Handlers stay safe to run twice, and several replicas stay allowed.
- **Which failures pause and which block (decision changed 2026-11-07, issue #216).** Two codes pause implement and update claims for every worker and replica, each in its own `claim_pauses` row, with one owner comment and one log line per pause: `forge_auth` (a forge 401 or 403, unchanged) and `preflight_access` (a push_access or pr_api preflight check that failed any other way). Both are task failures, and their retry waits for the pause. One rule blocks at once: an infra failure whose previous run in the step failed with the same infra code and the same detail, both runs finished within 60 seconds of their start, blocks with `repeated_failure` (below). Everything else is retried as before.
- **Restarts.** Now a failed triage, implement or review run is retried by the factory. Update runs keep the old rule (block, `/retry`).
  - Each retry is a **new run row** enqueued by the controller in the same conditional transition that acks the failed run. Its key is the failed run's key plus `:a<n>` (`retryKey` in `src/core/policy.ts`), derived from the failed run alone, so applying the same run twice asks for the same key and the ack fences the second apply: one retry, never two. The item stays `blocked_on: none` while it waits.
  - **Backoff:** the retry's earliest start, `runs.not_before`, is `finished_at + retry_base_ms × 2^(n−1)` where n counts the step's failed attempts, capped at `retry_max_ms`. Every claim checks it in the store, so every worker and replica waits. The reaper gives an expired lease the same wait: it requeues the run with `not_before` set (by its claim count), not at once.
  - **Infra vs task:** a lease loss, a timeout, an exception or an expired lease is an infra failure: it counts toward `max_restart` and adds one to `restart_count`. Anything else (agent error, invalid output, a preflight failure, a forge 401/403, a failed push) is a task failure and counts toward `max_attempts`; `restart_count` stays. Counts are per step (the first run and its automatic retries), read from the run history.
  - **No automatic retry for deterministic implement failures.** An implement run that fails with `no_commits`, `scope_violation`, `egress_blocked` or `diff_too_large` (`NO_AUTO_RETRY` in `src/core/policy.ts`) is never retried by the factory: the controller blocks the item on a human with `run_failed:implement:<code>` (reason `run_failed`) and posts one comment keyed `run-failed:<run id>` that names the code, its detail (dropped if the egress scan flags it) and `/retry` / `/revise <feedback>` (the size gate keeps its own text with the limits). `/retry` starts a new implement run (restart_count + 1), as for any `run_failed:*`. The scope gate's own comment with the file list is unchanged. **`diff_too_large` keeps its commits on a wip branch (decision changed 2026-11-07, issue #217):** a run the mid-run diff check stopped (§4 Pre-push gates) pushes its commits to `<branch_prefix>wip/<item id>/<run id>` and records the wip ref in its failed outcome, never the PR branch and no PR; since it is not retried automatically, nothing reads that ref yet, and `/retry` or `/revise` starts from the base. A `diff_too_large` from the post-sync size gate still pushes nothing. Triage and review runs that fail with `egress_blocked` are still retried.
  - **Implement preflight.** Before the agent starts, the implement run checks, in order: push access (`push_access`) and the PR API (`pr_api`) through the broker's read-only tool `github.preflight` (one GET of the repository, which must answer, and one GET of the branch's open PRs). Its `permissions.push` is only reported. The push itself is the push check, and its 401/403 pauses (`forge_auth`), then the base fetch (`base_fetch`: the sandbox's trusted `updateBase` and the fetch of `origin/<base>` into the run folder). A failed push_access or pr_api check fails the run with `preflight_access` (a 401 or 403: `forge_auth`, below); a failed base fetch with `preflight_failed`. The detail starts with the check's name. It is a task failure, so `max_attempts` bounds it, and it spends no agent tokens. A resumed run (below) runs the preflight too.
  - **Forge-auth pause.** The broker maps a forge 401 or 403 that is not a GitHub rate limit (first decision above) in the preflight, the push (git's `returned error: 401/403`, `Authentication failed`, `Permission … denied`) or `open_pr` to the error code `forge_auth` (other `open_pr` errors still throw). A run that fails with it is a task failure, and the worker, before it stores the outcome, sets a second named row of the existing `claim_pauses` table, `forge_auth`, to now + `auth_pause_ms` (default `retry_max_ms`, 30 min; only ever moved later). While it is in effect `claimRun` skips implement-type runs (`implement` and `update`, both push the branch; the issue asked for implement only) for every worker and replica; triage, review and resolve are claimed as before. The rate-limit row (`rate_limit`) and its all-claims pause are unchanged. No schema change: the table exists on both backends since migration 4. The retry's `not_before` is the later of its backoff and the pause end. A pause that was not in effect when the run failed is a new pause. Which run started it is decided by the store's conditional write itself (`pauseClaims` returns `started` for `forge_auth`: the insert of the row, or the update of a row whose end has passed), never by a read before the write, so of two workers refused at the same moment exactly one starts it. That worker logs one line (`forge auth refused: implement and update runs paused until …`) and the outcome carries `pause_started`, from which the controller posts one comment on that item, keyed `forge-auth:<pause end>`, naming the code and the time only. A run that fails during a pause moves the end later but posts and logs nothing. The broker's messages carry the check name and the HTTP status, never a response header, body or credential.
  - **Preflight-access pause (issue #216).** When the push_access or pr_api check fails with anything but a 401 or 403 (a 404, a 5xx, GitHub not answering), the broker returns `preflight_access`. The worker, before it stores the outcome, sets the `preflight_access` row of `claim_pauses` (not the `forge_auth` row) to now + `auth_pause_ms`, only ever moved later; `claimRun` skips implement and update runs while either row is in effect, and still claims triage, review and resolve. As for forge_auth, `pauseClaims` returns `started` from the store's conditional write: the worker that started the pause logs one line (`preflight access failed (<check>): implement and update runs paused until …`) and the outcome carries `pause_started`, from which the controller posts one comment on that item, keyed `preflight-access:<pause end>`, naming the check and the time, never the forge's answer. A failure during the pause moves the end later and posts and logs nothing. The retry's `not_before` is the later of its backoff and the pause end. A `preflight_access` failure never triggers `repeated_failure`. A GitHub 5xx on these checks pauses too (the issue asked for it); the pause key is `auth_pause_ms`, so it inherits the compose gap below.
  - **wip branch and resume.** When the push or the PR fails (a failed result or a thrown error) after the agent step and the pre-push gates passed, the worker pushes the branch head through the broker to `<branch_prefix>wip/<item id>/<run id>` on the forge (the forge, not a local ref, since the retry can run on another host) before the run fails with its original code. The failed outcome records `wip`: branch, head sha, commit count, the agent's summary and next steps (for the PR body and any new handoff row) and the files the base merge conflicted in. The controller's automatic retry carries it in the new run's `input` (`runs.input`, no schema change). The retry runs the preflight, then, if `origin/<wip branch>` is exactly the recorded head, puts the PR branch on it and runs no agent; then sync before push, the gates, push and PR as usual. It adds handoff rows only for commits not yet recorded, so it pushes the same commit SHAs as the failed run (unless the base moved and a new merge commit is added). On a resumed run a base merge conflict fails with `merge_conflict` at once, with no agent step. A wip branch that is gone or moved is not trusted: the retry runs the agent as before. A resumed run that fails its push again names the same wip branch and pushes no new one. If the wip push itself fails, the run fails with its original code and no `wip`, and is retried as before, with a new agent run. Not in this decision: deleting wip branches (they stay after success), keeping commits as bundles in shared storage.
  - **Stopped runs keep their work (decision changed 2026-11-07).** An implement run whose agent step ends `rate_limited`, `agent_stalled` or `agent_timed_out` (and whose lease holds) keeps its work the way the diff-budget stop does: after the agent stopped, its git config is distrusted, the worktree's changes become one WIP commit (`wip: stopped run <run id> (<code>)`), and when the run has commits since its start the worker pushes them through the broker to `<branch_prefix>wip/<item id>/<run id>`, never the PR branch and no PR, and records the wip ref in the failed outcome, marked `continue: true`. The controller's retry carries it in `runs.input` as for a failed push (no schema change; the flag and the session below live on the wip ref inside the input, since `RunInput` itself is unchanged). The retry runs the preflight, checks the wip head out, and **runs the agent on it** (a push retry still runs none), then sync, gates, push and PR as usual; its commits start where the stopped run's did, so the PR holds the earlier ones. **Session resume, same host only:** when the sandbox can reattach folders and the runner stores sessions, the stopped run keeps its run folder (a sandbox clone, never the live checkout) and its agent session, and the wip ref names them (`session`: id, host, folder, start, base sha). A retry on that host whose folder is still there, whose session the runner still has and whose folder HEAD is the wip head resumes it with `--resume` in that folder; otherwise it removes the kept folder and starts a new session on the wip head in a new folder. A retry on another host starts a new session from `origin/<wip branch>`, which must be the recorded head (else, as before, the agent starts from the branch as it is). The kept session is removed when the retry ends. A run with no commits and no changes pushes nothing and retries fresh with no wip, as before; a failed wip push fails the run with its original code and no wip ref, keeps nothing, and retries fresh. Codes, pauses and their timing are unchanged. **Runner side:** a killed claude-code run prints no result event, so its usage is the per-message usage of its stream's `assistant` events, counted once per message id (the last event of a message counts), with a null cost; it may differ from the CLI's own final total. Every runner result may carry `did_work` (claude-code: any `tool_use` of a write or exec tool). A fallback chain does not fall over on a stall that did work, so no next member gets a half-edited workdir; a runner that does not report the flag keeps the zero-output-tokens rule, and a rate limit still falls over. `runs.session_tokens` is unchanged (a follow-up decides it). Rollout: stop every old worker first; an old worker reads a `continue` wip ref as a push retry and would push the half-done branch with no agent run. Known gaps: a folder and session kept for a retry that then runs on another host, or whose outcome the egress scan replaces, stay on the first host until removed by hand; wip branches are not deleted.
  - **Rate limits:** a runner that reports `rate_limited` (claude-code: a result with `api_error_status: 429`; the openai-compatible runner: a 429 that is not `provider_setup`, above) spends no attempt and no restart. The worker stores a claim pause in the store (`claim_pauses`, only ever moved later) before it stores the outcome, so **no worker claims any run, for any item, until the reset time**, or for `retry_max_ms` when the runner gave none. The worker whose call moved the pause logs one line saying when work resumes. The retry run's `not_before` is the reset time.
  - **Stalled runs (issue #176; stall rule changed 2026-11-07, issue #215):** the claude-code runner reads the CLI's streamed events (`--output-format stream-json`). Only model output restarts the stall clock: an `assistant` event, a `thinking_tokens` system event (the model thinking) or a `tool_result` block. Other system events (init, API retries) do not count. A run with no model output within `first_output_ms` of its start (default 180000; `factory.config.json` top level, a positive integer or startup fails; settable live, applied at the next run that starts) ends as `stalled`, and the error names `first_output_ms`. After the first model output, a run with no further model output for `stall_ms` (default 300000) while no tool call is open ends as `stalled`. Before the first model output the shorter of the two limits applies, counted from the start. A running tool call stops the clock, and the run timeout still applies. The worker passes both limits on the run spec. A first-output stall is handled exactly like a silence stall (below). Known risk: a model that is slow to its first token for a real reason (a very large prompt) counts as stalled after `first_output_ms` and pauses all claims through `model_stall`. The worker records `agent_stalled` (not infra) and sets the `model_stall` claim pause to now + `probe_interval_ms` (default 600000). A stall spends no attempt and no restart, gets no backoff and never reaches a dead letter: the controller requeues `retryKey(key)` with reason `run_stalled`. While the pause holds, `claimRun` returns null for every kind. **Who probes (decision changed 2026-11-07; before: see History):** one probe schedule for both probe pauses (see the network pause above). Any live controller probes a due pause, not only the one in the process that set it (a drained child no longer leaves the pause unprobed). Once the probe time has passed, a controller first takes the probe with `claimProbe("model_stall", due, now + probe_interval_ms)` (`takeStallProbe(due, next)`, its old model_stall form, is deprecated: no source file calls it; removal plan: the next change allowed to edit `tests/store-contract.test.ts` moves its two `takeStallProbe` contract tests to `claimProbe("model_stall", …)` and deletes `takeStallProbe` from `FactoryStore` and the SQL store in the same change), a conditional move of the probe time under the claim lock: among replicas that read the same due time exactly one moves it, and only that one sends the short prompt on the cheap model class (`data_env: test`, timeout `stall_ms`). Solo: one process, the same path. Enterprise: several replicas on a shared store, one LLM call per due time. An answer ends the pause exactly as `endClaimPause("model_stall")` does (`model_answered` and the probe time move to the earlier of the probe time and now, never a future time, so a stall right after starts a new pause), so claims resume; no answer or an error keeps the pause and moves the probe `probe_interval_ms` after the failed probe. No `not_before` is cleared: a stalled run's retry is queued with `not_before` = the stall time, never the probe time, so nothing holds it once the pause ends (tested). `factory status` and the dashboard's Health panel show `agents paused: model not answering since <time>, next probe at <time>`. No migration: the pause lives in `claim_pauses` rows (`model_stall`, `model_stall_since`, `model_answered`). The stall path is no longer the only one that sets this pause (decision changed 2026-11-07): the alarm step (`05-alarms.md`) starts it the same way, `pauseClaims(now + probe_interval_ms, "model_stall")`, when it stores a new zero-token alert (`alarm_repeat_count` agent runs in a row with no tokens). The probe ends it the same way.
  - **Missing toolchain (issue #229):** when the first failing pre-push check could not start its tools (a `node_modules` path not found, `tsc`/`vitest`/`npx`/`node` not found; `toolchainMissing` in `src/core/checks.ts`), the run ends as `toolchain_missing`, an infra failure: no fix step runs and the work in progress is kept. A code error such as `Cannot find module 'pkg'` with no `node_modules` path stays a check failure.
  - **Failure comments (issue #229):** the dead-letter and last-attempt comments strip terminal colour codes, then name the first error line and up to five failing tests (`src/core/output-summary.ts`); the output tail goes under a collapsed `<details>`.
  - **Agent asks a human (issue #167):** an implement, review or resolve run may return `needs_human` with a short `reason` and one `question`. The controller blocks the item on `blocked_on: human` with `agent_needs_human`, posts the reason and question once, keyed on the run, and starts no retry; nothing is pushed. `/retry`, `/revise` or `/reject` answer it.
  - **Same failure twice (issue #167):** two task failures in a row in one step with the same code and the same detail line block the item with `repeated_failure` and queue no third run. One comment names the code and line; the line is dropped if the egress scan flags it. `/retry` starts the step afresh. A `preflight_access` failure is never compared. The rule is on by default; `repeated_failure_rule: false` on the controller turns it and the infra rule below off (tests that pin `max_attempts` do).
  - **Same infra failure twice, fast (issue #216):** an infra failure is blocked at once, `blocked_on: human` with `repeated_failure`, when the step's previous run also failed as infra with the same `error_code` and the same (non-empty) detail, and both runs finished within 60 seconds of their start (`repeatsFastInfraFailure`, `FAST_FAILURE_MS` in `src/core/policy.ts`). `restart_count` goes up by one, as for any infra failure, and no retry run is queued. Task failures, rate limits, stalls and `preflight_access` never trigger it; a different detail, or a run that took 60 seconds or more, retries as before up to `max_restart`. One comment, keyed `run-failed:<run id>`, names the code, the detail and the tail of the last run's output, as the max_restart dead letter does; if the egress scan flags it, the detail is dropped, then the tail. `/retry` is accepted on it, and the status page lists it under failed with the last error code, as for `max_restart`.
  - **Abandoned attempts (issue #210):** when the reaper expires a running run's lease, the same conditional update that moves it to queued, failed or cancelled decides its end: only a run that update actually changed gets one `run abandoned` warn line (the existing `lease expired` line still fires), so a second reaper pass on the same lease writes nothing. The line carries run id, work item id, attempt, status `abandoned`, reason `lease_expired`, `started_at`, `ended_at` (the run's last heartbeat: its `updated_at` read before the reaper's write) and `duration_ms` (end minus start; null when `started_at` is missing). `expireLeases` passes each one to an optional callback after its transaction commits; its returned run ids are unchanged. The reason is always `lease_expired`: the reaper cannot tell a crash from a host sleep, so `process_exit` is not set. No migration; it reads existing `runs` columns. The attempt-record table (#207) will fill the same end when it lands.
  - **Dead letter:** when a step's task failures reach `max_attempts` or its infra failures reach `max_restart`, the item goes to `blocked_on: human` with `blocked_reason` `max_attempts` or `max_restart`. One comment says in plain words what failed, the error code, and the tail of the last run's output. It goes through the `EgressScanner` first; if the scan blocks it, nothing is posted, a warning is logged, and the item still blocks.
  - `/retry` on an item blocked by a failed run (`max_attempts`, `max_restart`, `repeated_failure`, or an older `run_failed:*`) enqueues the run at once (`not_before` null) with `restart_count + 1`, which starts a new step and a fresh budget. It does not lift a rate-limit pause. On an item with no failed run it is refused as before.
  - Config: `max_attempts` (default 3, unchanged), `max_restart` (default 3), `retry_base_ms` (default 60000), `retry_max_ms` (default 1800000), `auth_pause_ms` (default `retry_max_ms`; since 2026-11-02) in `factory.config.json`. Schema: migration 4 adds `runs.not_before` and the `claim_pauses` table (SQLite and MySQL). Known gap: `src/compose.ts` does not pass `auth_pause_ms` through to the core config yet, so until it does the pause lasts `retry_max_ms` whatever the file says (the key is accepted, and the checked-in value equals the default).
  - Rollout: an old worker ignores `not_before` and the pause, so stop every worker before the first new controller starts, then migrate and start the new code everywhere. **Rollout of the 2026-11-02 changes (preflight, forge-auth pause, wip resume, no automatic retry of the four codes):** stop every old worker first, then start the new code everywhere. An old worker ignores the `forge_auth` pause row (it would claim implement and update runs during a pause) and ignores a retry's `wip` input (it would run the agent again). No migration is needed.

## History

- **Restart history is kept in the store** (new decision, 2026-11-08). Before: restarts lived only in the item's `restart_count` and in each host's `supervisor.json` (the last 10), so the store could not give a restart's time or the alarm's count and window, and a replica on another host never saw them.
- **A dead network pauses claims, not runs** (new decision, 2026-11-07). Before: a git fetch or sandbox step that failed on DNS was `git_failed` (infra, counted toward `max_restart`), a push that did was `push_failed` (a task failure, counted toward `max_attempts`), an unreachable GitHub in the preflight was `preflight_access` (pausing implement claims but spending an attempt), and the chat client's `network_error` mapped to no pause, so one outage could block every queued item. The stall pause's probe schedule (one replica per due time, see the entry below) was its own store call, `takeStallProbe`, now the model_stall form of `claimProbe`.
- **A GitHub rate limit waits for its reset** (decision changed 2026-11-07). Replaces the forge-auth rule for a 403: the broker mapped every 401 and 403 from the preflight and `open_pr` to `forge_auth`, so a rate-limit 403 paused implement and update claims for `auth_pause_ms` (30 minutes) whatever the reset, spent an attempt, and was reported as refused credentials; a rate limit on a review comment threw; the client's own refusal was a plain 403; the permission lookup read a rate-limit 403 as "none", so a collaborator could look like one with no access; and nothing waited for the reset.
- **Checks that fail on the base too are `checks_env`** (decision changed 2026-11-07). Before: a pre-push check that failed twice was always `checks_failed`, a task failure counted toward `max_attempts`, even when its tests failed the same way on the base branch (an environment problem such as a 5 s test timeout under load).
- **Stall probe ownership and the next probe time** (decision changed 2026-11-07). Before: each tick every controller that read a due `model_stall` pause called the model, so several replicas made one call each for the same due time; an answer wrote `model_answered` = now through `pauseClaims`, and `endClaimPause("model_stall")` wrote it at the probe time even when that was still ahead, so a stall before it started no pause; and the health line showed only the start time (`since <time>`), not the next probe.
- **Failure details keep the cause; `provider_setup` is not retried** (decision changed 2026-11-07). Before: a failed check's detail named only the command and its exit (`npm test` exited 1), a claude-code rate limit's error was the literal `rate_limited` (the CLI's reset text was dropped), and the chat client dropped the body of a 429, so an `insufficient_quota` reply was treated as a rate limit that paused claims for every worker for the retry window, and other quota, key and model errors were retried until `max_attempts`.
- **An owner can end a claim pause early** (decision changed 2026-11-07, issue #291). Before: a claim pause only ever moved later and had no early end; the only way out of one was a manual database edit, and the dashboard showed no pauses.
- **Stopped runs keep their work** (decision changed 2026-11-07). Replaces the part of **wip branch and resume** that kept commits only when the push or PR failed (and of the 2026-11-07 `diff_too_large` decision that only that stop kept them): a run that ended `rate_limited`, `agent_stalled` or `agent_timed_out` lost its run folder and agent sessions, so its retry started from the base; a killed run recorded zero tokens; and the fallback chain fell over on a stall with zero output tokens even after edits.

- **A drain stops the controller at once** (decision changed 2026-11-07, issue #294). Before: the drained child's controller kept polling sources and running passes until its worker drained, then ran one final pass over finished runs, so the old and the new child's controllers ran side by side and could both apply the same comments.
- **`diff_too_large` keeps its commits on a wip branch** (decision changed 2026-11-07, issue #217). Before: a `diff_too_large` run pushed nothing, so its commits went with the run folder when the run ended; the wip branch was kept only when the push or PR failed, or the checks failed.

- **Which failures pause and which block** (decision changed 2026-11-07, issue #216). Before: a push_access or pr_api check that failed other than with a 401/403 was a plain `preflight_failed` task failure, so one revoked permission cost every queued item its `max_attempts` with no alert; and an infra failure such as `git_failed` that repeated with the same code and detail within seconds was retried up to `max_restart`.
- **Missing toolchain and failure comments** (2026-11-07, issue #229). Before: a run folder without its tools failed as `checks_failed`, ran a fix step that could not help and spent an attempt; failure comments pasted the raw output tail with colour codes.
- **Agent asks a human; same failure twice** (2026-11-07, issue #167). Before: an agent that could not go on had to fail, and identical task failures used every attempt up to `max_attempts`.
- **Restarts** (decision changed 2026-11-01). Before: any failed run set `blocked_on: human` / `run_failed:<kind>:<code>` at once and waited for `/retry`, and the reaper requeued an expired lease with no wait.
- **No automatic retry for deterministic implement failures** (decision changed 2026-11-02, issue #135). Before: only `diff_too_large` blocked at once, and `no_commits`, `scope_violation` and `egress_blocked` were retried up to `max_attempts`, each retry a full agent run that failed the same way.
- **Implement preflight** (new decision, 2026-11-02, issue #135). Before: the agent ran first and a missing push permission showed only at the push, after a full agent run, repeated on every retry.
- **Forge-auth pause** (new decision, 2026-11-02, issue #135). Before: a 401/403 on the push was a plain `push_failed`, on `open_pr` an uncaught `exception`, and both were retried with a full agent run while every other implement run hit the same wall.
- **wip branch and resume** (new decision, 2026-11-02, issue #135). Before: the run folder was destroyed after every run, so the commits of a finished agent step were lost when the push or PR failed, and the retry ran the agent again.
- **Implement preflight, `permissions.push`** (decision changed 2026-11-02). Before: `push: false` failed the check, and a GitHub App installation token reports `push: false` even with contents: write, so every implement run failed the preflight while pushes worked.
- **The alarm step also sets `model_stall`** (decision changed 2026-11-07, design 05-alarms). Before: only a stalled run set the pause.
- **Stalled runs** (new decision, 2026-11-03, issue #176). Before: a CLI that waited without printing held the worker for the whole `run_timeout_ms`, was recorded as `agent_timed_out` (infra, counted toward `max_restart`), and its retry blocked the worker again (2026-11-02: every run from about 15:00 to 23:20 ended this way).
- **Stall rule: only model output restarts the clock** (decision changed 2026-11-07, issue #215). Before: every stdout chunk, system events included, restarted the `stall_ms` clock, and there was no first-output limit, so a run whose model never answered while the CLI printed API retries ended only at `run_timeout_ms` (runs with zero tokens took about 50 minutes each).
- **Abandoned attempts** (new decision, 2026-11-07, issue #210). Before: the reaper logged only `lease expired` with the run id, so a cut-off attempt had a start (`run start`) and no end.
