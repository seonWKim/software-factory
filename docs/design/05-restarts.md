# 5. Coordination: restarts

- **A drain stops the controller at once (decision changed 2026-11-07, issue #294).** When a supervised `dev` child gets the drain message, its controller loop and its stream listeners stop at once: it starts no new pass (no intake, reaper, checks, app commands, run outcomes or model probe), and a pass already running finishes. Only the worker's running runs finish, under the old child's worker, which claims nothing more. The old child runs no final pass over finished runs: the new child's controller, already started (start-then-drain, `docs/design/08-self-update.md`), applies their outcomes on its next pass. The old child logs one line, `controller stopped on drain`, then acknowledges the drain once its runs finished. SIGINT/SIGTERM still stops both loops of every child at once. Handlers stay safe to run twice, and several replicas stay allowed.
- **Which failures pause and which block (decision changed 2026-11-07, issue #216).** Two codes pause implement and update claims for every worker and replica, each in its own `claim_pauses` row, with one owner comment and one log line per pause: `forge_auth` (a forge 401 or 403, unchanged) and `preflight_access` (a push_access or pr_api preflight check that failed any other way). Both are task failures, and their retry waits for the pause. One rule blocks at once: an infra failure whose previous run in the step failed with the same infra code and the same detail, both runs finished within 60 seconds of their start, blocks with `repeated_failure` (below). Everything else is retried as before.
- **Restarts.** Now a failed triage, implement or review run is retried by the factory. Update runs keep the old rule (block, `/retry`).
  - Each retry is a **new run row** enqueued by the controller in the same conditional transition that acks the failed run. Its key is the failed run's key plus `:a<n>` (`retryKey` in `src/core/policy.ts`), derived from the failed run alone, so applying the same run twice asks for the same key and the ack fences the second apply: one retry, never two. The item stays `blocked_on: none` while it waits.
  - **Backoff:** the retry's earliest start, `runs.not_before`, is `finished_at + retry_base_ms × 2^(n−1)` where n counts the step's failed attempts, capped at `retry_max_ms`. Every claim checks it in the store, so every worker and replica waits. The reaper gives an expired lease the same wait: it requeues the run with `not_before` set (by its claim count), not at once.
  - **Infra vs task:** a lease loss, a timeout, an exception or an expired lease is an infra failure: it counts toward `max_restart` and adds one to `restart_count`. Anything else (agent error, invalid output, a preflight failure, a forge 401/403, a failed push) is a task failure and counts toward `max_attempts`; `restart_count` stays. Counts are per step (the first run and its automatic retries), read from the run history.
  - **No automatic retry for deterministic implement failures.** An implement run that fails with `no_commits`, `scope_violation`, `egress_blocked` or `diff_too_large` (`NO_AUTO_RETRY` in `src/core/policy.ts`) is never retried by the factory: the controller blocks the item on a human with `run_failed:implement:<code>` (reason `run_failed`) and posts one comment keyed `run-failed:<run id>` that names the code, its detail (dropped if the egress scan flags it) and `/retry` / `/revise <feedback>` (the size gate keeps its own text with the limits). `/retry` starts a new implement run (restart_count + 1), as for any `run_failed:*`. The scope gate's own comment with the file list is unchanged. **`diff_too_large` keeps its commits on a wip branch (decision changed 2026-11-07, issue #217):** a run the mid-run diff check stopped (§4 Pre-push gates) pushes its commits to `<branch_prefix>wip/<item id>/<run id>` and records the wip ref in its failed outcome, never the PR branch and no PR; since it is not retried automatically, nothing reads that ref yet, and `/retry` or `/revise` starts from the base. A `diff_too_large` from the post-sync size gate still pushes nothing. Triage and review runs that fail with `egress_blocked` are still retried.
  - **Implement preflight.** Before the agent starts, the implement run checks, in order: push access (`push_access`) and the PR API (`pr_api`) through the broker's read-only tool `github.preflight` (one GET of the repository, which must answer, and one GET of the branch's open PRs). Its `permissions.push` is only reported. The push itself is the push check, and its 401/403 pauses (`forge_auth`), then the base fetch (`base_fetch`: the sandbox's trusted `updateBase` and the fetch of `origin/<base>` into the run folder). A failed push_access or pr_api check fails the run with `preflight_access` (a 401 or 403: `forge_auth`, below); a failed base fetch with `preflight_failed`. The detail starts with the check's name. It is a task failure, so `max_attempts` bounds it, and it spends no agent tokens. A resumed run (below) runs the preflight too.
  - **Forge-auth pause.** The broker maps a forge 401 or 403 in the preflight, the push (git's `returned error: 401/403`, `Authentication failed`, `Permission … denied`) or `open_pr` to the error code `forge_auth` (other `open_pr` errors still throw). A run that fails with it is a task failure, and the worker, before it stores the outcome, sets a second named row of the existing `claim_pauses` table, `forge_auth`, to now + `auth_pause_ms` (default `retry_max_ms`, 30 min; only ever moved later). While it is in effect `claimRun` skips implement-type runs (`implement` and `update`, both push the branch; the issue asked for implement only) for every worker and replica; triage, review and resolve are claimed as before. The rate-limit row (`rate_limit`) and its all-claims pause are unchanged. No schema change: the table exists on both backends since migration 4. The retry's `not_before` is the later of its backoff and the pause end. A pause that was not in effect when the run failed is a new pause. Which run started it is decided by the store's conditional write itself (`pauseClaims` returns `started` for `forge_auth`: the insert of the row, or the update of a row whose end has passed), never by a read before the write, so of two workers refused at the same moment exactly one starts it. That worker logs one line (`forge auth refused: implement and update runs paused until …`) and the outcome carries `pause_started`, from which the controller posts one comment on that item, keyed `forge-auth:<pause end>`, naming the code and the time only. A run that fails during a pause moves the end later but posts and logs nothing. The broker's messages carry the check name and the HTTP status, never a response header, body or credential.
  - **Preflight-access pause (issue #216).** When the push_access or pr_api check fails with anything but a 401 or 403 (a 404, a 5xx, GitHub not answering), the broker returns `preflight_access`. The worker, before it stores the outcome, sets the `preflight_access` row of `claim_pauses` (not the `forge_auth` row) to now + `auth_pause_ms`, only ever moved later; `claimRun` skips implement and update runs while either row is in effect, and still claims triage, review and resolve. As for forge_auth, `pauseClaims` returns `started` from the store's conditional write: the worker that started the pause logs one line (`preflight access failed (<check>): implement and update runs paused until …`) and the outcome carries `pause_started`, from which the controller posts one comment on that item, keyed `preflight-access:<pause end>`, naming the check and the time, never the forge's answer. A failure during the pause moves the end later and posts and logs nothing. The retry's `not_before` is the later of its backoff and the pause end. A `preflight_access` failure never triggers `repeated_failure`. A GitHub 5xx on these checks pauses too (the issue asked for it); the pause key is `auth_pause_ms`, so it inherits the compose gap below.
  - **wip branch and resume.** When the push or the PR fails (a failed result or a thrown error) after the agent step and the pre-push gates passed, the worker pushes the branch head through the broker to `<branch_prefix>wip/<item id>/<run id>` on the forge (the forge, not a local ref, since the retry can run on another host) before the run fails with its original code. The failed outcome records `wip`: branch, head sha, commit count, the agent's summary and next steps (for the PR body and any new handoff row) and the files the base merge conflicted in. The controller's automatic retry carries it in the new run's `input` (`runs.input`, no schema change). The retry runs the preflight, then, if `origin/<wip branch>` is exactly the recorded head, puts the PR branch on it and runs no agent; then sync before push, the gates, push and PR as usual. It adds handoff rows only for commits not yet recorded, so it pushes the same commit SHAs as the failed run (unless the base moved and a new merge commit is added). On a resumed run a base merge conflict fails with `merge_conflict` at once, with no agent step. A wip branch that is gone or moved is not trusted: the retry runs the agent as before. A resumed run that fails its push again names the same wip branch and pushes no new one. If the wip push itself fails, the run fails with its original code and no `wip`, and is retried as before, with a new agent run. Not in this decision: deleting wip branches (they stay after success), keeping commits as bundles in shared storage.
  - **Rate limits:** a runner that reports `rate_limited` (claude-code: a result with `api_error_status: 429`) spends no attempt and no restart. The worker stores a claim pause in the store (`claim_pauses`, only ever moved later) before it stores the outcome, so **no worker claims any run, for any item, until the reset time**, or for `retry_max_ms` when the runner gave none. The worker whose call moved the pause logs one line saying when work resumes. The retry run's `not_before` is the reset time.
  - **Stalled runs (issue #176; stall rule changed 2026-11-07, issue #215):** the claude-code runner reads the CLI's streamed events (`--output-format stream-json`). Only model output restarts the stall clock: an `assistant` event, a `thinking_tokens` system event (the model thinking) or a `tool_result` block. Other system events (init, API retries) do not count. A run with no model output within `first_output_ms` of its start (default 180000; `factory.config.json` top level, a positive integer or startup fails; settable live, applied at the next run that starts) ends as `stalled`, and the error names `first_output_ms`. After the first model output, a run with no further model output for `stall_ms` (default 300000) while no tool call is open ends as `stalled`. Before the first model output the shorter of the two limits applies, counted from the start. A running tool call stops the clock, and the run timeout still applies. The worker passes both limits on the run spec. A first-output stall is handled exactly like a silence stall (below). Known risk: a model that is slow to its first token for a real reason (a very large prompt) counts as stalled after `first_output_ms` and pauses all claims through `model_stall`. The worker records `agent_stalled` (not infra) and sets the `model_stall` claim pause to now + `probe_interval_ms` (default 600000). A stall spends no attempt and no restart, gets no backoff and never reaches a dead letter: the controller requeues `retryKey(key)` with reason `run_stalled`. While the pause holds, `claimRun` returns null for every kind. Each tick, once the probe time has passed, the controller sends one short prompt on the cheap model class (`data_env: test`, timeout `stall_ms`): an answer writes `model_answered` and ends the pause; no answer or an error moves the probe `probe_interval_ms` later. Both writes only move times later, so replicas probing at once agree. `factory status` and the dashboard's Health panel show `agents paused: model not answering since <time>`. No migration: the pause lives in `claim_pauses` rows (`model_stall`, `model_stall_since`, `model_answered`).
  - **Missing toolchain (issue #229):** when the first failing pre-push check could not start its tools (a `node_modules` path not found, `tsc`/`vitest`/`npx`/`node` not found; `toolchainMissing` in `src/core/checks.ts`), the run ends as `toolchain_missing`, an infra failure: no fix step runs and the work in progress is kept. A code error such as `Cannot find module 'pkg'` with no `node_modules` path stays a check failure.
  - **Failure comments (issue #229):** the dead-letter and last-attempt comments strip terminal colour codes, then name the first error line and up to five failing tests (`src/core/output-summary.ts`); the output tail goes under a collapsed `<details>`.
  - **Agent asks a human (issue #167):** an implement, review or resolve run may return `needs_human` with a short `reason` and one `question`. The controller blocks the item on `blocked_on: human` with `agent_needs_human`, posts the reason and question once, keyed on the run, and starts no retry; nothing is pushed. `/retry`, `/revise` or `/reject` answer it.
  - **Same failure twice (issue #167):** two task failures in a row in one step with the same code and the same detail line block the item with `repeated_failure` and queue no third run. One comment names the code and line; the line is dropped if the egress scan flags it. `/retry` starts the step afresh. A `preflight_access` failure is never compared. The rule is on by default; `repeated_failure_rule: false` on the controller turns it and the infra rule below off (tests that pin `max_attempts` do).
  - **Same infra failure twice, fast (issue #216):** an infra failure is blocked at once, `blocked_on: human` with `repeated_failure`, when the step's previous run also failed as infra with the same `error_code` and the same (non-empty) detail, and both runs finished within 60 seconds of their start (`repeatsFastInfraFailure`, `FAST_FAILURE_MS` in `src/core/policy.ts`). `restart_count` goes up by one, as for any infra failure, and no retry run is queued. Task failures, rate limits, stalls and `preflight_access` never trigger it; a different detail, or a run that took 60 seconds or more, retries as before up to `max_restart`. One comment, keyed `run-failed:<run id>`, names the code, the detail and the tail of the last run's output, as the max_restart dead letter does; if the egress scan flags it, the detail is dropped, then the tail. `/retry` is accepted on it, and the status page lists it under failed with the last error code, as for `max_restart`.
  - **Abandoned attempts (issue #210):** when the reaper expires a running run's lease, the same conditional update that moves it to queued, failed or cancelled decides its end: only a run that update actually changed gets one `run abandoned` warn line (the existing `lease expired` line still fires), so a second reaper pass on the same lease writes nothing. The line carries run id, work item id, attempt, status `abandoned`, reason `lease_expired`, `started_at`, `ended_at` (the run's last heartbeat: its `updated_at` read before the reaper's write) and `duration_ms` (end minus start; null when `started_at` is missing). `expireLeases` passes each one to an optional callback after its transaction commits; its returned run ids are unchanged. The reason is always `lease_expired`: the reaper cannot tell a crash from a host sleep, so `process_exit` is not set. No migration; it reads existing `runs` columns. The attempt-record table (#207) will fill the same end when it lands.
  - **Dead letter:** when a step's task failures reach `max_attempts` or its infra failures reach `max_restart`, the item goes to `blocked_on: human` with `blocked_reason` `max_attempts` or `max_restart`. One comment says in plain words what failed, the error code, and the tail of the last run's output. It goes through the `EgressScanner` first; if the scan blocks it, nothing is posted, a warning is logged, and the item still blocks.
  - `/retry` on an item blocked by a failed run (`max_attempts`, `max_restart`, `repeated_failure`, or an older `run_failed:*`) enqueues the run at once (`not_before` null) with `restart_count + 1`, which starts a new step and a fresh budget. It does not lift a rate-limit pause. On an item with no failed run it is refused as before.
  - Config: `max_attempts` (default 3, unchanged), `max_restart` (default 3), `retry_base_ms` (default 60000), `retry_max_ms` (default 1800000), `auth_pause_ms` (default `retry_max_ms`; since 2026-11-02) in `factory.config.json`. Schema: migration 4 adds `runs.not_before` and the `claim_pauses` table (SQLite and MySQL). Known gap: `src/compose.ts` does not pass `auth_pause_ms` through to the core config yet, so until it does the pause lasts `retry_max_ms` whatever the file says (the key is accepted, and the checked-in value equals the default).
  - Rollout: an old worker ignores `not_before` and the pause, so stop every worker before the first new controller starts, then migrate and start the new code everywhere. **Rollout of the 2026-11-02 changes (preflight, forge-auth pause, wip resume, no automatic retry of the four codes):** stop every old worker first, then start the new code everywhere. An old worker ignores the `forge_auth` pause row (it would claim implement and update runs during a pause) and ignores a retry's `wip` input (it would run the agent again). No migration is needed.

## History

- **A drain stops the controller at once** (decision changed 2026-11-07, issue #294). Before: the drained child's controller kept polling sources and running passes until its worker drained, then ran one final pass over finished runs, so the old and the new child's controllers ran side by side and could both apply the same comments.
- **`diff_too_large` keeps its commits on a wip branch** (decision changed 2026-11-07, issue #217). Before: a `diff_too_large` run pushed nothing, so its commits went with the run folder when the run ended; the wip branch was kept only when the push or PR failed, or the checks failed.

- **Which failures pause and which block** (decision changed 2026-11-07, issue #216). Before: a push_access or pr_api check that failed other than with a 401/403 was a plain `preflight_failed` task failure, so one revoked permission cost every queued item its `max_attempts` with no alert; and an infra failure such as `git_failed` that repeated with the same code and detail within seconds was retried up to `max_restart`.
- **Missing toolchain and failure comments** (2026-11-07, issue #229). Before: a run folder without its tools failed as `checks_failed`, ran a fix step that could not help and spent an attempt; failure comments pasted the raw output tail with colour codes.
- **Agent asks a human; same failure twice** (2026-11-07, issue #167). Before: an agent that could not go on had to fail, and identical task failures used every attempt up to `max_attempts`.
- **Restarts** (decision changed 2026-11-01). Before: any failed run set `blocked_on: human` / `run_failed:<kind>:<code>` at once and waited for `/retry`, and the reaper requeued an expired lease with no wait.
- **No automatic retry for deterministic implement failures** (decision changed 2026-11-02, issue #135). Before: only `diff_too_large` blocked at once, and `no_commits`, `scope_violation` and `egress_blocked` were retried up to `max_attempts`, each retry a full agent run that failed the same way.
- **Implement preflight** (new decision, 2026-11-02, issue #135). Before: the agent ran first and a missing push permission showed only at the push, after a full agent run, repeated on every retry.
- **Forge-auth pause** (new decision, 2026-11-02, issue #135). Before: a 401/403 on the push was a plain `push_failed`, on `open_pr` an uncaught `exception`, and both were retried with a full agent run while every other implement run hit the same wall.
- **wip branch and resume** (new decision, 2026-11-02, issue #135). Before: the run folder was destroyed after every run, so the commits of a finished agent step were lost when the push or PR failed, and the retry ran the agent again.
- **Implement preflight, `permissions.push`** (decision changed 2026-11-02). Before: `push: false` failed the check, and a GitHub App installation token reports `push: false` even with contents: write, so every implement run failed the preflight while pushes worked.
- **Stalled runs** (new decision, 2026-11-03, issue #176). Before: a CLI that waited without printing held the worker for the whole `run_timeout_ms`, was recorded as `agent_timed_out` (infra, counted toward `max_restart`), and its retry blocked the worker again (2026-11-02: every run from about 15:00 to 23:20 ended this way).
- **Stall rule: only model output restarts the clock** (decision changed 2026-11-07, issue #215). Before: every stdout chunk, system events included, restarted the `stall_ms` clock, and there was no first-output limit, so a run whose model never answered while the CLI printed API retries ended only at `run_timeout_ms` (runs with zero tokens took about 50 minutes each).
- **Abandoned attempts** (new decision, 2026-11-07, issue #210). Before: the reaper logged only `lease expired` with the run id, so a cut-off attempt had a start (`run start`) and no end.
