# 5. Coordination: sandbox and agent tools

- **The warmed Gradle wrapper is copied into each run's own home (decision changed 2026-11-14; changes *A writable home per run* under the toolchain caches below; before: see History).** With a `toolchain` block, before each agent step of a run whose folder has `gradlew`, the worker names the owner's `<HOME>/.gradle/wrapper/dists` (HOME from its tool env; the folder the warm step fills) as `AgentRunSpec.toolchain_seeds` when it exists, and the runner copies it with a local recursive copy into the run's `<TMPDIR>/toolchain/gradle/wrapper/dists`, the per-run `GRADLE_USER_HOME`. The copy's folders are owner-writable, so the wrapper writes its lock file there and `./gradlew build --offline` finds its distribution without the network; files already copied by an earlier step stay. The source is only read: never linked (a hardlink would let the agent write the owner's files through the shared inode), never made writable, never added to `toolchain.caches`, the read allow list or a write root. Like a cache, the source may not be, hold or lie inside a `deny_paths` entry: an overlap fails worker startup naming both paths. The path is fixed, like `TOOLCHAIN_HOMES`: no config key. A missing source, no `gradlew` or no HOME: no copy, and the run goes on. No block: no check, no `toolchain_seeds`, and the spec and env are as before (`tests/toolchain.test.ts`). The dependency cache keeps its read-only path (`toolchain.env`, e.g. `GRADLE_RO_DEP_CACHE`). Not in this change: Maven, Cargo or npm wrapper distributions, caches shared or writable across runs.
- **Read-only input folders for agents (new decision, 2026-11-14; before: see History).** A project may add a top-level `read_only_inputs` list to `factory.config.json`: absolute folders (a leading `~` is the owner's HOME) holding source data outside its repo, which its agents read and never write, e.g. `["~/data/resume"]`. They follow the toolchain caches' rules below through the same code path, not a second one: one parser for both lists (normalized, absolute or `~/`), one overlap check (a folder that is, holds or lies inside a `deny_paths` entry fails startup naming both paths), one read allow list (`readable_paths`: the caches first, then the inputs), so the harness settings put each in `sandbox.filesystem.allowRead` and `denyWrite` with an `Edit(//<folder>/**)` deny rule, never in `allowWrite` or `permissions.allow`, and the shared Write and Edit refuse them. `factory doctor` lists each as `read-only input <folder>`: ok when it exists, a warn when it does not (no warm step fills it), a FAIL per denied path it overlaps. An input folder adds no warm step, no env entry and no prompt sentence. No key: no input folder, and every run, doctor report and prompt is exactly as before (`tests/toolchain.test.ts`). The reason for a second key: a project's input data is not a cache, and naming it one hid what the folder is. Not in this change: writable inputs, a remote or network source, any copy or sync of the folder.
- **Toolchain caches are read-only for agents (decision changed 2026-11-08, issue #334; before: see History).** A project may add a `toolchain` block to `factory.config.json`: `caches` (folders), `env` (non-secret entries) and `warm_command` (argv). It is a PR-only key, and on a shared store it comes only from the checked-in file. No block: no warm step, no readable cache, no extra env, and the prompts, harness settings and worker steps are exactly as before (`tests/toolchain.test.ts`). The rules, and the frontier harness each one follows:
  - *Read allow list, deny list wins (Claude Code's sandbox: `sandbox.filesystem.denyRead` with `allowRead`, and its permission rules where deny beats allow).* Declared caches go into the read allow list only: the Claude Code harness settings get `sandbox.filesystem.allowRead`, and the shared file tools let Read, Glob and Grep read under them (`GuardPolicy.readable_paths`; a read tool only, see `defineTool`). Secrets and the owner's config stay on the read denylist whatever the cache list says: a cache that is, lies inside or holds a `deny_paths` entry (the secret file's folder, `~/.ssh`, `~/.gitconfig`, `~/.claude` …) fails startup naming both paths, the runner drops one anyway, and `factory doctor` reports it as a FAIL. A link inside a cache to a denied file is refused by its resolved name, as everywhere.
  - *Write allowlist, read-only elsewhere (Codex's `workspace-write` mode: writable roots, read-only everywhere else; Claude Code's `sandbox.filesystem.allowWrite`).* Caches are never write roots: not in `allowWrite` or `permissions.allow`; the harness adds them to `sandbox.filesystem.denyWrite` and an `Edit(//<cache>/**)` deny rule, and the shared Write and Edit refuse them. Sandbox writes do not widen.
  - *A writable home per run (Codex's `workspace-write`, whose writable roots include the run's temp folder).* With a block, each run's toolchain homes point into its own TMPDIR, which it may already write: `npm_config_cache`, `CARGO_HOME`, `PIP_CACHE_DIR` and `GRADLE_USER_HOME` at `<homes>/<run_id>/tmp/toolchain/<name>` (`TOOLCHAIN_HOMES`). A `toolchain.env` entry may point one elsewhere, e.g. Gradle's read-only `GRADLE_RO_DEP_CACHE` at a declared cache. The Gradle home starts with a copy of the warmed wrapper distribution (the decision at the top).
  - *No network for the agent (Claude Code's sandbox: network off unless a host is allowed or a proxy is set; Codex's `workspace-write`: no network).* Unchanged: localhost only. The prompts' check sentence says the configured checks (`repo.check_commands`, else `test_command`) run offline from the read-only caches (`{{toolchain}}` in `prompts/implement.md`, `review.md` and `resolve.md`; empty without a block).
  - *Setup with the network, agent without (Codex cloud's environment setup script, which runs before the agent with internet access).* Before the first agent step of an implement, review or resolve run, the worker runs `warm_command` (absent: `repo.install_command`) in the run folder with its own tool env (the owner's HOME, so the real caches fill) and the slot env, never a credential or the test database. A failure ends the run `warm_failed` before any agent starts, naming the command (an infra failure, retried). Triage only reads and warms nothing. This is the only new network call, and only with a block.
  - *This repo's warm step fetches the Electron binary (2026-11-11, issue #573).* Electron 45 (a devDependency since #574) has no install script and downloads its binary on first use, which the offline agent cannot do. This repo's `factory.config.json` sets `toolchain.warm_command` to `["sh", "-c", "npm ci && if [ -f node_modules/electron/install.js ]; then node node_modules/electron/install.js; fi"]`: the install, then Electron's own download into `node_modules/electron/dist`, only when the branch has electron. The download goes through Electron's cache in the owner's HOME (`~/Library/Caches/electron` on macOS, `~/.cache/electron` on Linux; the warm step runs with the owner's HOME), so after the first run it only unpacks (about 3 s), with no `ELECTRON_CACHE` setting.
  - *Non-secret env only (Codex's `shell_environment_policy`, whose default excludes drop `*KEY*`, `*SECRET*`, `*TOKEN*`).* A `toolchain.env` key matching `FORBIDDEN_ENV`, or one the factory sets itself (`PATH`, `HOME`, `TMPDIR`, `CLAUDE_*`, `ANTHROPIC_*`, `GIT_*`, `SF_*`), fails at load; each value goes through the configured egress scanner at startup (known secret values and patterns), and a hit fails startup naming the entry, never the value. The runner checks the keys again, and its own entries always win.
  - *Solo default and enterprise.* Solo: the caches are the owner's own home folders, read-only, warmed by the worker on the same machine. Enterprise: each worker host warms its own caches with its own worker; there is no shared cache across hosts in this change. Not in this change (follow-ups): writable shared caches, a network proxy for installs, per-language presets (a project's pack, #305).
- **Agent writes stay out of the live checkout (decision changed 2026-11-07).** An agent run may write only under its run folder, its `writable_paths` and the temp folder its runner declares (Claude Code: the run's `TMPDIR`, `<homes>/<run_id>/tmp`). The owner's live checkout (`repo.path`) is never one of them, though `noop` run folders sit inside it (`.worktrees/`). This is a rule of the Sandbox interface, so every sandbox plugin meets it; today only `noop` exists. How each part is enforced:
  - *Claude Code native Write and Edit: a harness permission check (not OS-level).* `--allowedTools` no longer names `Write` or `Edit`; the harness settings carry one `Edit(//<root>/**)` allow rule per root (Claude Code's Edit rules cover Write too). In `-p` mode a call no rule allows is refused, so a Write with an absolute path to the live checkout, or a relative path climbing out of the run folder, never runs.
  - *Claude Code Bash: OS-level.* Claude Code's OS sandbox (Seatbelt on macOS, bubblewrap on Linux) allows writes to the working directory (the run folder), its temp folder and `sandbox.filesystem.allowWrite` (`writable_paths`), with `allowUnsandboxedCommands: false`. Unchanged.
  - *Every other runner: a tool check through the shared guard policy.* The shared `Write` and `Edit` refuse any path whose resolved form is outside the workdir and `writable_paths` (`guardPolicy`); the refusal names the path and nothing is written. `openai-compatible` refuses every Bash call.
  - *`noop` itself adds no OS rule.* It relies on the two above. Accepted for the solo default, not a loosening: on a host where Claude Code's OS sandbox is off, Bash writes under `noop` are not limited. Enterprise uses a container sandbox plugin, which must enforce the same rule at OS level.
  - *Worker check (detection, not enforcement).* Before and after each agent step the worker lists the untracked, not ignored files in the live checkout (`git -C <repo.path> ls-files --others --exclude-standard -z`, trusted git env, through `Sandbox.exec`). Files that are new after the step are logged as `files appeared in the live checkout during an agent step` with `run_id`, `step`, `checkout`, `paths` (at most 20) and `count`. Files already there before the step are not reported. The report never fails the run: the file may be the owner's or another parallel run's. A sandbox that cannot see the host checkout (git fails) skips the check. Not seen: ignored paths (such as `node_modules/`), and writes to tracked files. No transcript parsing.
  - Why: on 2026-11-07 an untracked `placeholder` file appeared at the root of the live checkout. Native Write and Edit had no path rule (only `.env` edits were denied), the OS `allowWrite` covered Bash only, and the worker's untracked-file check looked only inside the run folder, so nothing stopped or noticed it.
- **A run's tool grants: broker tools, and pack entries that are granted and approved (new decision, 2026-11-11, issue #589).** Where the worker builds an agent step's grants (`src/worker/runner.ts`), it splits the run kind's `tool_grants` with `checkPackGrants` (`src/packs/pack-grants.ts`): broker tool names go on as before (read-only, checked against the broker at startup), and each `pack:tool:<name>` or `pack:mcp_server:<name>` is checked against the store: `no_entry`, `not_approved` (its current description_hash has no approval, 11-packs.md), or `not_started` (both checks pass; pack tools start in a later phase). Any pack grant fails the run with `pack_tool_refused` before its agent starts, naming each grant and its reason; no process starts and no tool is called. Startup accepts a pack grant without asking the broker, and refuses a `pack:` name of any other form.
- **Sandbox** interface: `create(spec) -> handle`, `exec(handle, cmd)`, `copy_in/out`, `destroy(handle)`. Impls: `NoOpSandbox` (local dev, now: runs in its own clone on the host, no isolation), Docker, gVisor, Kata / Firecracker, hosted sandboxes. Swapping never touches agents.
  - *With `NoOpSandbox`, an agent has the host user's access. Keep the local factory on the test environment only (prod connections refused) and per-worker ports / test DB via the interfaces.*
  - **Own git folder per run.** Every run's worktree was a `git worktree` of the owner's checkout, and implement runs got the owner's `.git` as a writable path, so an agent could change the owner's branches, index and config, or plant a hook that later ran outside the sandbox (on 2026-11-01 an agent created a local branch and staged the owner's files). Now `NoOpSandbox` gives each run its own clone: its git folder is inside the run folder, objects are borrowed from the factory repo through an alternates link, `core.hooksPath` points to an empty read-only folder outside every run folder, and destroy removes the folder. Implement runs get no writable path outside the run folder. The worker's and the broker's git calls in a run folder ignore agent-written config: they run with `TRUSTED_GIT_ENV` (hooks, fsmonitor and signing off, no replace refs or grafts), the worker strips every non-data config key and checks the git folder after the agent exits, and the broker refuses a folder that still has such a key. The base commit for the scope gate, size gate, floor check and the broker's diff and egress scan comes from the factory repo's `origin/<base>` (`SandboxHandle.base_sha`), and the broker pushes to the factory repo's `origin` URL, not to the run folder's `origin`. Rule: architecture §5. Not changed: what the agent may read (it can read the factory's objects), the updater's own worktree in the state dir, and old worktree entries left in the factory `.git` by earlier runs.
  - **File and shell tools carry their own guards (new decision, 2026-11-01; part 1 of 3 for #58).** `src/core/tools/` defines `Read`, `Glob`, `Grep`, `Write`, `Edit` and `Bash` once, as `ToolSpec`s that reach the run folder only through `Sandbox.exec` (paths are argv entries, never spliced into a shell string). One pure function, `guardPolicy(workdir, deny_paths, writable_paths, env_allowlist)`, gives the policy they enforce: the file tools refuse any path whose written or symlink-resolved form is under a `deny_paths` entry or a `.env`/`.env.*` file, or whose resolved form is outside the workdir and `writable_paths` (reads too); Glob and Grep list only regular files and drop denied ones; Bash gets only `PATH` plus `env_allowlist` and refuses a secret-looking key. Results are `{ok:true, content, truncated?} | {ok:false, error}`, cut at 64 KiB; no tool throws. The guards do not depend on the runner, so any runner can reuse them. Wired in by part 2 (#89) and part 3 (#90) below. Not covered: Bash is not path-checked (only an OS-level sandbox can stop a shell from reading a denied file), and a symlink swapped in between the check and the operation is not caught. Egress scanning of tool output stays with the caller (G5).
  - **The run spec carries tool specs; the runner shares the guard policy (new decision, 2026-11-01; part 2 of 3 for #58, issue #89).** `AgentRunSpec.tools` holds `ToolSpec`s from `src/core/tools`, each with its capability. The worker picks `READ_TOOLS` (Read, Glob, Grep: read only) for triage and `WRITE_TOOLS` (Bash, Read, Edit, Write, Glob, Grep) for the other roles; canary and golden keep their own name lists, resolved with `toolsNamed`. The Claude Code runner passes exactly `spec.tools` names to `--tools` and `--allowedTools` and adds none, takes `deny_paths`/`writable_paths` through `guardPolicy` (the same policy the tools enforce) and the env pattern from `FORBIDDEN_ENV`. Its output for the same input is unchanged (`tests/claude-runner-tools.test.ts` pins it). Still runner-only: the web denies (WebFetch, WebSearch). The Bash command denies are now also in the shared Bash tool (next point). Rule: architecture §5.
  - **The shared Bash tool refuses denied command names (decision changed 2026-11-07, issue #191).** Before running anything, `Bash` in `src/core/tools/bash.ts` splits the command on `;`, `&`, `|` and newlines, skips leading `VAR=value` words in each segment, and refuses the call if a segment starts with `gh`, `security`, `git push`, `git credential`, `printenv` or `env`. Names match whole words only, so `envsubst` and `ghost` run. The refusal is a tool result (`ok:false`, the error names the matched command); nothing reaches the sandbox, and the run goes on. These are the same names the Claude Code runner denies through its harness settings, which stay as they are. The check is name-based, not a shell parser. Limits, not caught: `/usr/bin/env` (a path, not the bare name), `sh -c "..."`, `eval`, subshells (`$(...)`, backticks, `( ... )`), and quoting tricks such as `"g"h`. Only an OS-level sandbox and the broker's own tools close those. Rule: architecture §5.
  - **Runners reuse the shared tools for their guards (new decision, 2026-11-01; part 3 of 3 for #58, issue #90).** A runner without a harness builds `guardPolicy` from its `AgentRunSpec` and calls every file tool through `ToolSpec.run` from `src/core/tools`; a refusal reaches the model as a tool result, and the run goes on. A test-only runner (`tests/helpers/scripted-runner.ts`, driven by a scripted fake LLM, selected only through `withPlugin` in tests, not in `src/impl/` or `REGISTRY`) shows it: a Grep-then-Read task completes, and a Read of a `deny_paths` file is refused without its contents reaching the output or the transcript. Not in this decision: a production API-based runner, and path checks for Bash (G3 still needs an OS-level sandbox). Rule: architecture §5.
  - **Transcript scan: a pattern hit alone keeps the transcript out of storage (decision changed 2026-11-07, issue #167).** Every agent call's transcript is G5-scanned (channel `log`) before it is stored. A `known_secret` or `factory_canary` finding fails the run with `egress_blocked`. Any other finding (a secret pattern, such as a token-shaped test fixture that a failing test printed) does not fail the run: the transcript is not stored, a warning names the rules, and the run goes on. The commit, PR, comment, handoff and run-outcome scans are unchanged, so that text still cannot leave.
  - **Agents can run the test suite inside the Claude Code sandbox (decision changed 2026-11-07).** Implement runs ended `checks_failed` because the agent never saw a green run in its sandbox: tests that start a local server failed with `listen EPERM 127.0.0.1`, direct `npx vitest` calls failed writing `node_modules/.vite-temp`, and every `npm`/`npx` call reported a denied `registry.npmjs.org`. Now the Claude Code harness settings set `sandbox.network.allowLocalBinding: true` (bind and connect on localhost only; no `allowedDomains` entry, so every other host stays denied) and `npm_config_update_notifier=false` (npm's update check, the source of most registry denials). The implement, resolve and review prompts say to run tests through `npm test` (`npm test -- <file>` for one file, which carries `--configLoader runner`) and not to install packages. Unchanged: filesystem `denyRead` and `allowWrite`, every permission deny rule, `allowUnsandboxedCommands: false`, the credential env denies, the broker and the egress scans. Accepted: a run can connect to any local port. The files holding the factory's logins are in `deny_paths`; the local UI pages are read-only and egress-scanned, and its settings API refuses writes without its CSRF token; any other local service on the host is reachable as it is to the host user. Details: `docs/plugins/agent-runner.md`.

## History

- **A run's tool grants** (new decision, 2026-11-11, issue #589). Before: a run's grants were the run kind's `tool_grants` broker tools only, every one checked against the broker at startup; a pack entry could not be granted.

- **Own git folder per run** (decision changed 2026-11-01). Before: worktrees shared the owner's git folder and agents could write to it.
- **File and shell tools carry their own guards** (new decision, 2026-11-01; part 1 of 3 for #58). Before: the guards existed only as Claude Code settings strings built by the runner.
- **The run spec carries tool specs; the runner shares the guard policy** (new decision, 2026-11-01; part 2 of 3 for #58, issue #89). Before: `AgentRunSpec.harness_tools` was a bare list of names copied by hand in the worker, and the Claude Code runner built its allow list and path deny rules on its own, so nothing tied a role's tools to the rules that limit them.
- **Runners reuse the shared tools for their guards** (new decision, 2026-11-01; part 3 of 3 for #58, issue #90). Before: each runner implemented its own tools and guards, so a runner with no built-in harness would have had to rebuild them.
- **The shared Bash tool refuses denied command names** (decision changed 2026-11-07, issue #191). Changes the "Still runner-only" part of *The run spec carries tool specs*. Before: "Still runner-only: the Bash command and web denies (`gh`, `git push`, `printenv`, `mysql`, WebFetch, WebSearch), because the shared Bash tool checks no commands."
- **Transcript scan** (decision changed 2026-11-07, issue #167). Before: any finding in a transcript failed the run with `egress_blocked`, so an implement run whose fix step ran tests that printed a fake `ghp_` fixture lost all its work.
- **Agents can run the test suite inside the Claude Code sandbox** (decision changed 2026-11-07). Before: the harness settings had no network block, so sandboxed commands could neither bind nor connect on localhost, and agents were told only "run `npm test`", so they also called vitest directly and tried to install packages.
- **Agent writes stay out of the live checkout** (decision changed 2026-11-07). Changes the claim in *Own git folder per run* that implement runs get no writable path outside the run folder: that held for `writable_paths` and Bash, not for Claude Code's native tools. Before: `--allowedTools` named `Write` and `Edit` bare, so they could write any path the host user can (only `.env` edits were denied), and no check looked at the live checkout after a run.
- **Toolchain caches are read-only for agents** (decision changed 2026-11-08, issue #334). Changes *File and shell tools carry their own guards* (the file tools read only under the workdir and `writable_paths`) and the G1 agent environment (only the fixed entries, the git identity and the slot env). Before: an agent could read no folder outside its run, and nothing in config could add an env entry or a readable path, so a Gradle, Maven or Cargo build inside the agent found an empty home-level cache and, with no network, could not download; only the worker's own install and check commands, run with the real HOME and the network, worked.
- **This repo's warm step fetches the Electron binary** (new decision, 2026-11-11, issue #573). Before: this repo's `factory.config.json` had no `toolchain` block, so no warm step ran and an agent could not launch Electron.
- **MySQL text removed from the current decisions** (decision changed 2026-11-11, issue #567). Before: the Bash tool refused "`printenv`, `env`, `mysql`, `mysqldump` or `mysqladmin`" and said "`envsubst`, `ghost` and `mysqldumpx` run"; the test-suite decision said "`<state_dir>/test-mysql.url` joins `deny_paths`, since a run can now reach the local MySQL." and accepted "MySQL needs a login, and the files holding the factory's logins are in `deny_paths`".
- **Read-only input folders for agents** (new decision, 2026-11-14). Uses the rules of *Toolchain caches are read-only for agents* for a second, separately named list. Before: `toolchain.caches` was the only config that put a folder on the agents' read allow list, so a project whose source data sat outside its repo had to call that folder a cache or copy it into the repo.
- **The warmed Gradle wrapper is copied into each run's own home** (decision changed 2026-11-14). Changes *A writable home per run* in *Toolchain caches are read-only for agents*. Before: each run's `GRADLE_USER_HOME` started as an empty folder in its TMPDIR, so `./gradlew` tried to download its distribution and failed offline; the owner's warmed `~/.gradle/wrapper/dists` could not be used in place, since the wrapper writes a lock file beside it and that folder is read-only to the agent.
