# 9. Status page: dashboard item page, failed items, timeline, Runs and live transcript

Part of the item page ([09-dashboard-item.md](09-dashboard-item.md)).

- **A run waiting for a host test slot says so: its Runs status badge and its `task show` line read "waiting for a test slot" (decision changed 2026-11-29, phase 3 of 3 of local-28caa30d, "Show the wait"; current; replaces "Status: Waiting, Running, Done, Failed or Stopped, `item.result.<status>`" of the Runs-row decision below for a waiting run, see History).** A run waiting for a slot keeps status `running` (design 04-pre-push-gates), so it looked like a stuck run. The wait is read from the store only: the run's live `waiting:<run id>` row in `worker_test_slots` (phase 2), through the store read `listTestSlotWaits` (`TestSlotReads`, wrapping `readTestSlots` in `src/impl/store/sql/test-slots.ts`), so every worker shows the same wait; no table, column, setting, migration or route is added. **Item detail:** each run of `GET /api/v1/items/<id>` carries `waiting_for_slot` (true while its waiting row is live), read in the same request. **Run page:** the row's own `StatusBadge` keeps the run's status tone and `data-status` and shows `item.result.waitingForSlot` ("waiting for a test slot") instead of "Running". **CLI:** `task show` ends a waiting run's line with "waiting for a test slot" (`id kind status attempt  waiting for a test slot`). A run that is not waiting reads as before. Display only: slot take, release, lease, cap, polling and the Stop check are unchanged; the Runners and Work pages show no wait. Tests: `tests/test-slot-display.test.ts`.

- **The Runs table fits the window: its title cell wraps anywhere (decision changed 2026-11-24, "Item page Runs: actions inside the window"; current; replaces the title cell's `break-words` of the Runs-row decision below, see History).** Of the three design-system ways to keep a table's actions in sight (hide low-value columns below a breakpoint, cards at more widths, shorten or wrap cells) the Runs table wraps cells: every column carries what the owner reads (state, run, detail, worker, start, Open and "⋯"), and the Table already turns into cards below `sm`. In `ItemTable`'s table layout (`web/src/views/item-row.tsx`, shared with Work's Running now and Runners) the title and its second line use `wrap-anywhere`, not `break-words`: a table column is never narrower than its longest unbreakable word, so an unbroken identifier in a title or in a failed run's open Details held the title column at its `max-w-md` cap (448 px) and pushed the last column past the right edge at 768 to 1024 px. With `wrap-anywhere` the column shrinks to its `min-w-40` floor and the table fits its card at every `check:responsive` size; Work's Running now table, which failed the same way at 800 and 1024 px, is fixed by the same change. Display only. Tests: `tests/ui-item-row.test.tsx` ("ItemTable fits its box").

- **The Runs rows are `ItemRow`s (decision changed 2026-11-22, wi_37bb601c, "One ItemRow for every list of work items"; current, except the title cell's wrapping: the fits-the-window decision above; replaces the Runs table of the transcripts and plain-words decisions below and the short run ID of the 2026-11-23 no-internal-name decision, see History).** The shared row is in 09-dashboard-tasks.md (`web/src/views/item-row.tsx`), `compact` in an `ItemTable` (a Table at `sm` and up, cards below it): Status (Waiting, Running, Done, Failed or Stopped, `item.result.<status>`), Run (the title: kind and attempt, "Implement #2", plain text), Detail ("3 tries · took 3m · 1.5k tokens": consecutive cancelled runs of one kind fold into the newest, tokens summed), Worker, Started, then Open (the stored transcript) as the action and Copy ID (the run's ID) in "⋯". A failed run's second line is its code's sentence (`item.error.<code>`, `term.<code>`, the failure title, else "Failed"), the code and full text behind Details. Each row carries `data-item-id` and `data-run`; no ID is row text. Tests: `tests/item-page.test.tsx`, `tests/ui-transcript.test.tsx`.

- **A failed item's page shows no internal name: short run IDs, thread kinds and channels in words, run-failed comments in plain English (decision changed 2026-11-23, issue #758; current, except Runs: the Runs-row decision above; replaces the full run ID in the Runs Step cell of the plain-words decision below, the thread's kind badge and source-type channel shown as stored of the Thread decision below, and the error code in the sentence of the factory's run-failed comment, see History).** **Runs:** no run ID is row text (the Runs-row decision above; the short ID it replaced is in History). **Thread:** the kind badge is a word from `thread.kind.<kind>` (`web/src/i18n/en/work.ts`; `run-failed` reads "Run failed"), the channel too (`thread.channel.<type>`; `github_issue` reads "GitHub"); an unknown snake_case or kebab-case value reads the generic "Factory message", "Message" or "its source", never the code; a plain one-word value stays as it is. The body stays text as stored (`data-raw`). **Run-failed comments** (`src/controller/units/run-results/run-results.unit.ts`: the repeated failure, repeated infrastructure failure, no-auto-retry, size check, provider setup, resolve failed and last attempt comments) name the failure in words ("The triage run failed twice in a row the same way: the worker hit an unexpected error.") and put the error code under a `<details><summary>Details</summary>` fold as code ("Error code: `exception`"), which the thread's Markdown renders as a Disclosure. **Why and alarms:** every blocked reason and error code shown to the owner has an English sentence (`src/ui/why.ts`, `src/ui/alarms.ts`, `web/src/i18n/en/work.ts`); repeated failure reads "Triage failed twice the same way. Decide what happens next."; an unknown code reads a generic sentence, never the code. `tests/owner-text.test.ts` renders /app/tasks, /app/items and a failed item's page and fails on any `/[a-z]+_[a-z]+/` or kebab-case token outside `<code>` inside a disclosure and outside text shown as stored, and on a code in the run-failed comment's sentence. Display and wording only: no failure logic, retry or state change.

- **The timeline and the Runs table read as sentences, with the stored names behind Details (decision changed 2026-11-20, wi_7ed794a4, "Item timeline and Runs table in plain words"; current, except Runs: the Runs-row decision at the top; replaces the labelled `field: from → to` timeline line, the status word and the full error text of "The item page shows labels" below, see History).** Display only: no stored timeline or run data, reason code or migration changes. **Timeline:** each row is one sentence from the catalog key `timeline.<reason>` (`web/src/i18n/en/work.ts`), with the actor in it: the viewer is "You" ("You asked for a retry", "You took over in a terminal", "Created by you"), the factory "The factory", a worker "Worker N", any other person "A person" (never a name). A reason with no key reads "Changed". Every reason the controller's units write has a key (`tests/item-page.test.tsx` scans `src/controller/units` for them). The reason code, the actor ID and every changed field (`blocked_on: human → none`) sit only in the row's `data-raw` Details; the spec toggle keeps "spec written (show)". **Runs:** the Runs-row decision at the top (it replaced this part, see History).

- **A running run's transcript is live (decision changed 2026-11-20, wi_65a10426, "Live view of a running implement"; current; replaces "the transcript page never polls; a live view is out of scope" of "Run transcripts in the app" (2026-11-07), see History).** The decision that changed: **a queued or running run's transcript page shows its steps so far and polls until the run ends**, so a long run can be told from a stuck one. **Worker** (`src/worker/live-transcript.ts`, called from `Worker.agent`): while an agent step runs, `LiveTranscript` writes the step's output so far to its usual key (`transcripts/<item>/<run>.json`, a second step `<run>.<step>.json`), at most once per 5 s (owner answer 3) and only when the text grew; only whole lines are written, so no page shows a cut event. Every partial write passes G5 on channel `log` first: a pattern-only hit skips that write and the run goes on; a known secret or the canary aborts the agent and fails the run with `egress_blocked`, as the end-of-step check does. The end-of-step write and its scan are unchanged and replace the last partial file; a finished run's stored transcript is never rewritten. Its throttle state is that step's writer's only. **Runner contract:** `AgentRunSpec.live` (optional) receives the output so far as text; the Claude Code runner accumulates its stdout next to the stall watch and calls it; the fallback chain passes the spec, so only the member running now streams (earlier members appear when the step ends); the OpenAI-compatible runner does not stream yet (owner answer 1: later). **API:** for a queued or running run with no stored part yet, `GET /api/v1/items/<id>/runs/<run>/transcript` answers 200 with `steps: []`, `parts: []`, `part: ""`, `format: null`, `size: 0`, `next: null`; after the first write it reads the partial file like any other. Unknown runs, another item's run and a finished run with no stored transcript stay 404. **App:** Current run links its transcript for a queued or running run whether or not a part is stored yet (the block's link style). The transcript page refetches every `POLL_MS` (3 s, owner answer 2) only while the run is queued or running, reads the next page on its own while live (as an empty filter page does), shows "Waiting for the agent's first output" while there are no steps, and stops polling once the run ends. Out of scope: interactive sessions, live output to any remote service, store schema changes. Tests: `tests/live-transcript.test.ts`.

- **The item page shows labels, and the stored fields behind Details (decision changed 2026-11-19, "Plain words instead of internal names"; current except its timeline line, Runs status and error cell: the plain-words decision above; replaces the raw field names in the timeline, the run error code and the stored run status, see History).** A timeline row says its reason and each changed field by its label ("Waiting on: none → human", "Tokens: 0 → 1200"), with a `data-raw` Details holding the stored `field: from → to` lines. The Runs table shows the status in one form ("Succeeded", "Failed", "Running") and an error as its failure title, with the stored code in a Details; the closed state's reason, the token count and the transcript outcome read the same way. Times are `When` (design 09-dashboard-shell). The decision is in 09-dashboard-shell.md; this page only applies it.
