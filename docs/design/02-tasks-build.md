# 2. Plain tasks: Build this, the description and the merge close

- **A task follows its item's replacement when the item closes as rejected (decision changed 2026-11-24, local-task-tk_0a313675, "Tasks follow their item when it is refiled"; current; replaces "a rejected close leaves the linked task open" in the 2026-11-19 close decision below, see History).** The decision that changed: **when an item closes as `rejected` and a replacement is known, the store moves the item's open linked tasks to the replacement in the close's own transaction, so they close when it completes; with no replacement the task stays open and its row says `Not built: <reason>`.** On 2026-11-24 the owner's Tasks list had 26 open tasks whose items were refiled, split or covered by another item, all really finished and closed by hand.
  - **Replacement.** The store's close transition (`applyTransition` in `src/impl/store/sql/sql-factory-store.ts`, the first move to `CLOSED`) calls `onItemClosed` (`src/impl/store/sql/tasks.ts`). On `rejected` it reads the reject reason (`spec_feedback`, where `/reject` stores it) as it is: the first `wi_` id in it that names one stored item other than the item itself (the full id, or a prefix that matches exactly one item) is the replacement. Else, for a split parent (items whose `parent_id` is it): every phase closed completes the task, as `task done` does; a phase still open takes it, the highest-numbered open one (owner answer 2). Else there is none.
  - **Move.** The task's `work_item_id` becomes the replacement and `link_note` stores `Moved from <old wi_ id>`; each write is conditional on the task being open and still linked to the closed item, so a repeat changes nothing. A task moved to an item already closed as completed is completed at once. The existing completed-close path then closes it.
  - **Store.** Migration `20261124T1002-controller-tasks-link-note` adds the nullable `link_note TEXT` to `controller_tasks` (owner answer 1): additive, rerun-safe, no backfill, so the 26 tasks closed by hand and every other existing task keep their state.
  - **Tasks API and row.** `GET /api/v1/tasks` returns each task's `link_note` (else null) and `reject_reason`: on an open task still linked to an item closed as rejected, the item's reject reason through the Withholder, `no reason given` when it is empty; else null. The Tasks row of such a task shows `Not built: <reason>` (`tasks.notBuilt`) in its details line in place of `Rejected`, and keeps its checkbox so the owner decides. A moved open task's row shows its `link_note`.
  - **Not in this decision.** `wont_do` and `duplicate` closes move nothing; Build this, reopen, the completed close, `/reject` and the source close paths are unchanged; no CLI command shows the note or the reason.
  - Tests: `tests/task-merge-close.test.ts` (refile and complete, short id, an already completed replacement, no replacement, wont_do, split parent with all phases closed and with one open), `tests/20261124T1001-controller-tasks-link-note.test.ts`, `tests/ui-tasks-done.test.tsx` (the Not built and moved rows).
- **Promote of a proposal on the Rules page stores a plain task with a body (decision changed 2026-11-20, local-task-tk_3b38699c, "Promote proposals that need building"; current; changes "who writes a task's `body`" in the description decision below, see History).** The decision that changed: **`addTask` also writes `body` for a task the Rules page creates**: promoting a proposal whose change is prose (no Now and Proposed lines) stores a plain task, ID `tk_` and the proposal ID in lower case (a retry adds nothing), title the proposal's title, `body` its rationale, change, target, evidence IDs and proposal ID (design 09-dashboard-rules). No new column or migration: it is the description decision's nullable `body` (no backfill; none stays NULL). Not built; in no project. Tests: `tests/tasks.test.ts` (body written and read, else NULL), `tests/rules-page.test.ts`.
- **`task create --depends-on <id>` holds the new item until another merges (decision changed 2026-11-20; current; replaces "`task create` takes only `--title`, `--body-file` and `--project`", see History).** One wi_ ID (or a unique prefix, `wi_` optional) or tk_ id; it writes `Depends on: <id>` after the body (`withDependsOn`), as design 05-dependencies reads it, and records the edge at once (2026-11-27, design 05-dependencies); an id naming no local item (`localItemOf`), or several, is refused with exit 1. In `--help` and the command table.
- **A plain task has an optional description that Build this sends to triage (decision changed 2026-11-19, wi_6fee2cb6, "Plain tasks get a description"; current; replaces "a plain task carries only its title, and `task create --project`'s body goes to the work item only", see History).** The decision that changed: **each task stores an optional description, `body`, edited in a dialog opened by clicking the task's title on the Tasks page, and Build this and `factory task build` put it below the title in the work item's problem (`<title>`, a blank line, the description), which triage reads.** Found by the dogfood review of 2026-11-19 (F14): Build this sent the agent the title alone.
  - **Store.** Migration `20261119T1000-controller-tasks-body` adds the nullable `body TEXT` to `controller_tasks`: additive, rerun-safe, no backfill (an existing task has none). `setTaskBody(id, body)` (`src/impl/store/sql/tasks.ts`) writes it conditional on the task being open (`done_at` unset); an unknown or done task writes nothing. A recurring task's next occurrence copies it, as it copies the title.
  - **Route.** `POST /api/v1/tasks/body` with `{ "id": "<task id>", "body": "<text>" }` is one of `TASK_WRITES`, so it takes the write routes' guards. The text is trimmed; empty after trimming is stored as NULL (cleared); over 20,000 characters (`MAX_TASK_BODY`, `taskBody` in `src/core/tasks.ts`) is 400. 404 for an unknown task, 409 for a done one, 503 with no actor; every refusal writes nothing. `GET /api/v1/tasks` returns each task's `body`, through the Withholder as the title is.
  - **Build.** `buildTask` (`src/core/task-build.ts`) reads the stored description and takes no body argument; a task with none builds exactly as before (the problem is the title). A built task keeps the text it was built with: a later edit changes the task, not the work item. `createProjectTask` (`task create --project`, `POST /api/v1/tasks/create`) stores its body on the new task (trimmed, empty as none, over 20,000 refused with nothing written) and builds from it.
  - **Not in this decision.** A CLI command to set a description (owner answer 2: a follow-up issue), syncing a later edit into a built item, and showing the description on the row or the item page. A sub-task uses the same column and dialog.
  - Tests: `tests/tasks-api.test.ts` (save, clear, the limit, 404 and 409 with nothing written, the read), `tests/task-build.test.ts` (the problem with and without a description, a later edit, `create --project`), `tests/20261119T1000-controller-tasks-body.test.ts` (the migration on an existing database), `tests/ui-tasks-page.test.tsx` (the dialog).
- **A linked task is done when its item closes as completed; a rejected or wont_do close leaves it open and its row says why (since 2026-11-24 a rejected close with a known replacement moves the task, the decision at the top; decision changed 2026-11-19, local-task-tk_71bf2922; current; replaces "every close of a work item completes its linked tasks", from 2026-11-18, see History).** The decision that changed: **only a close with `close_reason` `completed`, merged or not, completes the item's linked open tasks; an item closed as `rejected` or `wont_do` leaves its task open, and the Tasks page shows the reason on the open row.** The owner's request: "A task is done when its item closes as completed, not only on merge"; an item closed as completed without its own merge (a plan item, work that landed through other commits, the owner's close) had left its task open, while a rejected item's task must stay open for the owner to close or rebuild.
  - **Store.** The store's close transition (`applyTransition` in `src/impl/store/sql/sql-factory-store.ts`, the first move of an item to `CLOSED`) calls `completeLinkedTasks` (`src/impl/store/sql/tasks.ts`) in the same transaction only when the item's `close_reason` is `completed`, so each merge path, a source close as completed and any other completed close (a plan item, the owner's close) complete the task, as `task done` does (a recurring one gets its next occurrence once). `/reject`, a budget-checkpoint reject, a source close as not planned (`wont_do`) and a PR closed unmerged (`rejected`) leave it open. Conditional on `done_at` unset, and only the first move to `CLOSED` calls it, so a repeated close does not move `done_at`. A task with no link is never changed. `closeLinkedTasks` stays for the local merge, which then finds none open.
  - **Close reason on the row (owner answer 2: the reason only).** Nothing new is stored on the task: `GET /api/v1/tasks` reads each linked task's item, open or done, and adds `close_reason`, the item's close reason when it closed without a merge (`merge_sha` unset), else null. The Tasks page shows it in the row's details line (no new column), on open and done rows: `Rejected`, `Not planned` (`wont_do`), or `Closed` (any other reason). An open row keeps its checkbox, Build this is not offered (it has a link) and no reopen-style action is added. A merged item's row keeps its Merged state badge instead. Strings: `tasks.closedRejected`, `tasks.closedNotPlanned`, `tasks.closedOther` in `web/src/i18n/en/tasks.ts`.
  - **No backfill.** No migration and no task is changed: tasks done by a rejected or wont_do close under the 2026-11-18 rule stay done (their rows keep the reason beside the done time), and tasks of items closed as completed before it stay open until `task done`. The CLI `task list` still shows open tasks only.
  - Tests: `tests/task-merge-close.test.ts` (each close path, completed with no merge, repeat, unlinked task, the Tasks read's `close_reason` on open rows), `tests/ui-tasks-done.test.tsx` (the reason on open and done rows).

- **Date views, Build this and the merge close (decision changed 2026-11-12, issue #607, phase 2 of 2 of #591; current; replaces "dashboard views and linking a task to an item are not part of this decision", from the #606 decision in design 02-tasks, see History).** The decision that changed: **a task can be seen by its due date on the dashboard, sent to intake once as a work item that it stays linked to, and is completed when that item closes as completed.**
  - **Link.** `controller_tasks.work_item_id`, nullable, added by the timestamped migration `src/controller/migrations/20261112T1500-controller-tasks-work-item.migration.ts` (TEXT; additive, rerun-safe, no backfill: existing tasks stay unlinked). Set once: `linkTask` writes it only where it is unset. A recurring task's next occurrence is never linked.
  - **Build.** `buildTask` (`src/core/task-build.ts`), behind `factory task build <task_id>` (chat `task build <task_id>`) and the Tasks page's Build this (`POST /api/v1/tasks/build` with `{ "id": "<task id>" }`). It makes one local work item in intake with its triage run queued, through the same `createLocalItem` as `task create`, with source ID `local-task-<task id>`, title the task's title, requester the caller's user ID, then stores the link. A second build answers the linked item and writes nothing; a retry after a crash between the two writes finds the same item (createWorkItem is idempotent on the source) and sets the link. Refused with nothing written: an unknown task, a done task, and no stored project key (the CLI's stored key; the page's `settings.resolveProject`; chat has none, so a chat build is refused until it does).
  - **Merge close.** When the item closes as completed, every open task linked to it is completed, as `task done` does (a recurring one gets its next occurrence once). Since 2026-11-19 the store's close transition does it for every close as completed, merged or not, and a rejected or wont_do close leaves the task open (the close decision at the top). Conditional on `done_at` unset, so a repeated event or delivery closes nothing more. A task with no link is never changed. Changes merged before this decision close nothing.
  - **Views.** `taskViews` (`src/core/tasks.ts`, pure) places each open task by its due date against the injected Clock's calendar date in the process's time zone, so the day ends at local midnight: Inbox (no due date), Today (overdue, due before today, first; then due today), Upcoming (due in the 7 days after today, one group per day that has a task), Project (every open task under its `#list`, unlabelled last). Within a group: due date, then due time (untimed last), then priority, then age. `GET /api/v1/tasks` (`src/ui/tasks-api.ts`) answers them with the page's CSRF token and whether Build this is on (a commands actor).
  - **Solo and enterprise.** The same: SQLite applies the migration when the store opens. Due-date alerts, and linking a task to a repository or a pull request, are still not part of any decision; reminders are in the schedule a task decision in design 02-tasks-calendar.
