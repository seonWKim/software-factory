# 9. Status page: the macOS desktop app

- **The app is Gongbang (decision changed 2026-11-12, brand phase 3; current).** The decision that changed: **the bundle was "Software Factory.app" with Electron's icon, and every name in the shell was a literal "Software Factory"; now `desktop/package.json` `productName` ("Gongbang") is the one name.** The build reads it and writes `desktop/out/Gongbang.app` with `CFBundleName` and `CFBundleDisplayName` set to it; it renders the mark (`scripts/build-icons.mjs`, `docs/design/09-brand-and-tokens.md`) and puts `icon.icns` in `Contents/Resources/` in place of `electron.icns`, with `CFBundleIconFile` pointing at it (off macOS there is no `icon.icns` and Electron's icon stays). In the shell, `desktop/electron/common/product.js` reads the same `productName`: the window title, the tray tooltip (`Gongbang: <state>`), the menu's "Quit Gongbang" and the startup error dialog ("Gongbang could not start") all use it. The menu bar title is `Gb <n>`. The app data folder keeps its name, `~/Library/Application Support/software-factory/`, so an existing config is kept. Installing the app into `~/Applications` is not built: SET_UP.md still says to move it by hand.
- **A quick-add box on a global shortcut (new decision, 2026-11-12; current).** The decision that changed: **the shell is no longer only a window on the dashboard: it also stores plain tasks, through one new route.** A system-wide shortcut, `app.quick_add_shortcut` in the shell's `config.json` (default `Alt+Space`; a config without the key takes the default and starts as usual), opens a frameless box with one text field and the parsed fields as chips. Enter sends one `POST /api/v1/tasks` (design 02-tasks) from the shell's main process, never from the box's page, with the dashboard's Origin and the per-process CSRF token from `GET /api/v1/session`, as the dashboard sends them; the route parses the words with the #606 parser and stores the task under the ID the box chose, so a resend stores one task. Esc, or clicking elsewhere, closes the box and posts nothing. A refusal (words the parser refuses, an unreachable factory) shows its reason in the box and keeps it open with the same task ID.
  - **AppShell gains `registerShortcut` and `unregisterShortcut`** (`src/interfaces/app-shell.ts`, `docs/plugins/app-shell.md`). The macOS shell implements them with Electron's `globalShortcut`; `register` answers false when another app holds the accelerator and throws on a string that is not one, and both come back as false. Every shortcut is released on quit. `desktop/electron/macos/shortcut.js` holds the shortcut logic over AppShell, and `main.js` runs it once the shell has started: it registers the configured one (refused: a message, a line in the supervisor log, and the shell runs on with none held) and changes it by registering the new one before the old one is released, so a refused accelerator keeps the previous one.
  - **A native settings view changes the shortcut.** The menu bar menu's "Quick-add shortcut…" opens a small window that records a key combination; Save registers it, writes it to `config.json` (keeping every other key) and releases the old one, or shows why it was refused. There is no dashboard Settings section for it: the setting belongs to the shell, which runs before any factory config is read.
  - **The box opens at once.** Its window is made hidden at start, so the shortcut only shows and focuses it and tells the page to empty and focus the field; the 300 ms target is checked by hand on macOS, not by a test. "Quick add…" in the menu bar menu opens it too.
  - **Static pages in `desktop/electron/macos/`** (`quick-add.html`, `settings.html`, their scripts and `panel.css`), loaded from the app bundle, with a CSP of their own files only. They use macOS system colours (`Canvas`, `CanvasText`, `GrayText`, `Field`, `AccentColor`) and the system font, light and dark, and name no colour value: the dashboard's tokens are not in the bundle. Both windows run sandboxed with context isolation and no Node, refuse navigation and new windows, and share one preload, `panel-preload.cjs`, which exposes only the panel channels; the main process answers only its own windows. That preload and `main.js` are the only files that import `electron`.
  - **Chips from the checkout's own parser.** The chips come from `dist/core/quick-add.js` of the chosen checkout (pure, no imports), loaded once by `main.js`, so the box shows what the route will store without a second parser. Without `dist/` the box shows no chips; the route still parses. This is the one checkout file the shell loads besides `.factory/supervisor.json`.
  - **Who stores the task.** The route stores the task as the dashboard's commands actor (`ui.user_id`, else the CLI identity on loopback), as the page's other writes act; without an actor it answers 503 and stores nothing.
  - Solo and multi-worker: the same; one shell per machine, one shortcut per shell. Windows and Linux shortcuts, editing or deleting a task from the box, and a dashboard quick-add form are not part of this decision.
- **A macOS app around the running factory (new decision, 2026-11-11, issue #573; current).** `npm run build:desktop:macos` builds an unsigned "Gongbang.app" (the decision above) in the git-ignored `desktop/out/`. It is a thin shell: it starts the factory, shows the dashboard and drains the factory on Quit. It adds no store state and no change to the supervisor, the updater or the dashboard; its one route, for the quick-add box, is the decision above.
  - **Plain ES modules, no compile step.** `desktop/electron/common/` holds the pure modules, each taking its effects (fs, spawn, fetch, timers) as arguments: the supervisor child and its restart (`supervisor.js`), the status count (`status.js`), the app data folder and config (`app-data.js`), the Quit drain (`quit-drain.js`) and the wiring (`run-shell.js`). `desktop/electron/macos/` holds the Electron main file, the preloads, the macOS AppShell and the quick-add panels. Only `main.js` and the panels' sandboxed preload import `electron`; the tests pass a mock, so `npm test` and `npm run typecheck` pass without Electron in `node_modules` and no test starts it. The `.d.ts` files beside the modules are for the tests' typecheck only and are not copied into the app.
  - **AppShell is wired directly, not a registry plugin (decision 1).** `src/interfaces/app-shell.ts` holds the interface (open the window, show the status, set the Quit drain, quit) so another platform plugs in the same way, but the desktop entry builds its shell itself: the shell runs before any factory config is read, and a shell picked in `factory.config.json` would have to be read by the shell it picks. The contract test runs against a fake and the macOS shell with Electron mocked. Docs: [`docs/plugins/app-shell.md`](../plugins/app-shell.md).
  - **The build.** It copies `node_modules/electron/dist/Electron.app` (the pinned `electron` devDependency) to `desktop/out/Gongbang.app`, sets its bundle name and icon, removes Electron's default app and puts the shell in `Contents/Resources/app/`: `desktop/electron/` and a `package.json` that names the checkout the build ran in. Nothing else: no factory source and no `node_modules`. Without `node_modules/electron/dist` it exits 1 with a message naming `electron@<version>` and the missing folder; it never runs `npm install`. Installing Electron in the factory's warm step is a separate change.
  - **The shell attaches to a factory that already runs (changed 2026-11-11, fix/desktop-attach; see History).** Before it starts anything it checks the checkout: `<checkout>/.factory/supervisor.json` names a live `supervisor_pid` (the git-worktree updater) or `child_pid` (the none updater), or `GET /api/v1/overview` on `ui_port` answers within 2 s. Either one: the shell starts no supervisor, shows that factory's dashboard and count, and its Quit leaves that factory running; the log says `[shell] attached ...`. Two supervisors on one state folder would claim the same work and fight over the UI port. A factory that stops later is not taken over: quit and start the app again. A `state_dir` other than `.factory` is caught by the dashboard probe only.
  - **The supervisor is the shell's child when none runs.** The shell runs `dist/main.js dev` from the chosen checkout with its own runtime as Node (`ELECTRON_RUN_AS_NODE=1`), its output appended to `state/supervisor.log`. When it exits it starts again after 5 s. `dist/` must be built (`npm run build`, or one `npm run factory -- dev`).
  - **No top-level `await` in `main.js`.** Electron emits `ready` only after the ESM entry has finished loading, so `await app.whenReady()` at the top level hangs the app with no window (seen with Electron 45). `main.js` uses `app.whenReady().then(...)`; a test fails on a top-level `await` there.
  - **Quit drains (decision 3) the supervisor the shell started.** Cmd+Q, the app menu's Quit and the menu bar's Quit send SIGTERM to the supervisor (which stops its children as on Ctrl-C) and wait for it to exit; after 60 s it gets SIGKILL. The shell exits after that. No restart follows a Quit.
  - **Closing the window keeps the factory running (on by default).** The window hides; the menu bar item stays and the supervisor keeps working. `keep_running_when_closed: false` in the shell's config makes closing the window a Quit. The Dock icon or the menu's "Open dashboard" shows the window again.
  - **The window.** `contextIsolation` on, `nodeIntegration` off, `sandbox` on, a preload that exposes nothing. It loads only `http://127.0.0.1:<ui_port>/app/`: other navigations are refused and new windows denied. While the dashboard does not answer (the supervisor is starting) it loads again every 2 s.
  - **The menu bar.** `Gb <n>` (`SF <n>` before the decision above), where `n` is `needs_you` from `GET /api/v1/overview`, read at start and every 15 seconds; its menu shows the factory state (`factory.state`, `stopped` when the API says the supervisor is stopped, `not reachable` while the API does not answer) and the count. A dash while the count is unknown.
  - **The app data folder.** `~/Library/Application Support/software-factory/` is the macOS shell's alone: `config.json` (`checkout`, default the folder the app was built from; `ui_port`, default 4310, set it when `factory.config.json` sets another `ui.port`; `keep_running_when_closed`, default true; `app.quick_add_shortcut`, default `Alt+Space`, the decision above), written with the defaults on first start, and `state/` (the supervisor log, Electron's own data and `notices-shown.json`, the owner notices the shell has shown). The child gets the folder as `SF_HOME`; core does not read it in this change. The shell writes only this folder; of the checkout it reads only `.factory/supervisor.json` (the attach check) and loads only the built parser `dist/core/quick-add.js` (the box's chips), and never a secrets file (`~/.config/software-factory/.env`); a test records every file it touches.
  - **No platform code in core.** `tests/boundaries.test.ts` fails on `process.platform`, `homedir()`, platform names or OS paths in `src/core`, `src/interfaces`, `src/ui` and `web/`. Platform code lives in a plugin (KeepAwake) or the desktop shell. The known exemptions, each with its reason in the test (decision 2): the KeepAwake plugins, the registry's per-platform default (`src/plugins.ts`), the env-file SecretStore's path (`src/impl/secrets/`) and setup's `open`/`xdg-open` (`src/setup.ts`; a follow-up moves it).
  - Solo default and multi-worker setting are the same: one shell per machine (a second copy quits at once), supervising one checkout; workers on other machines are unaffected.
  - The child gets the shell's own environment. Started from Finder, that has macOS's short `PATH`, so tools outside it (`claude`) may not be found; passing the login shell's `PATH` is a follow-up.
  - Not yet (slice 2): launch at login, a first-launch repo picker and clone, code signing and notarization, auto-update of the shell, Windows and Linux builds.
