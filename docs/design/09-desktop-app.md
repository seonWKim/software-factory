# 9. Status page: the macOS desktop app

- **A macOS app around the running factory (new decision, 2026-11-11, issue #573; current).** `npm run build:desktop:macos` builds an unsigned "Software Factory.app" in the git-ignored `desktop/out/`. It is a thin shell: it starts the factory, shows the dashboard and drains the factory on Quit. It adds no route, no store state and no change to the supervisor, the updater, the dashboard or the API.
  - **Plain ES modules, no compile step.** `desktop/electron/common/` holds the pure modules, each taking its effects (fs, spawn, fetch, timers) as arguments: the supervisor child and its restart (`supervisor.js`), the status count (`status.js`), the app data folder and config (`app-data.js`), the Quit drain (`quit-drain.js`) and the wiring (`run-shell.js`). `desktop/electron/macos/` holds the Electron main file, a preload and the macOS AppShell. Only `main.js` imports `electron`; the tests pass a mock, so `npm test` and `npm run typecheck` pass without Electron in `node_modules` and no test starts it. The `.d.ts` files beside the modules are for the tests' typecheck only and are not copied into the app.
  - **AppShell is wired directly, not a registry plugin (decision 1).** `src/interfaces/app-shell.ts` holds the interface (open the window, show the status, set the Quit drain, quit) so another platform plugs in the same way, but the desktop entry builds its shell itself: the shell runs before any factory config is read, and a shell picked in `factory.config.json` would have to be read by the shell it picks. The contract test runs against a fake and the macOS shell with Electron mocked. Docs: [`docs/plugins/app-shell.md`](../plugins/app-shell.md).
  - **The build.** It copies `node_modules/electron/dist/Electron.app` (the pinned `electron` devDependency) to `desktop/out/Software Factory.app`, sets its bundle name, removes Electron's default app and puts the shell in `Contents/Resources/app/`: `desktop/electron/` and a `package.json` that names the checkout the build ran in. Nothing else: no factory source and no `node_modules`. Without `node_modules/electron/dist` it exits 1 with a message naming `electron@<version>` and the missing folder; it never runs `npm install`. Installing Electron in the factory's warm step is a separate change.
  - **The supervisor is the shell's child.** The shell runs `dist/main.js dev` from the chosen checkout with its own runtime as Node (`ELECTRON_RUN_AS_NODE=1`), its output appended to `state/supervisor.log`. When it exits it starts again after 5 s. `dist/` must be built (`npm run build`, or one `npm run factory -- dev`).
  - **Quit drains (decision 3).** Cmd+Q, the app menu's Quit and the menu bar's Quit send SIGTERM to the supervisor (which stops its children as on Ctrl-C) and wait for it to exit; after 60 s it gets SIGKILL. The shell exits after that. No restart follows a Quit.
  - **Closing the window keeps the factory running (on by default).** The window hides; the menu bar item stays and the supervisor keeps working. `keep_running_when_closed: false` in the shell's config makes closing the window a Quit. The Dock icon or the menu's "Open dashboard" shows the window again.
  - **The window.** `contextIsolation` on, `nodeIntegration` off, `sandbox` on, a preload that exposes nothing. It loads only `http://127.0.0.1:<ui_port>/app/`: other navigations are refused and new windows denied. While the dashboard does not answer (the supervisor is starting) it loads again every 2 s.
  - **The menu bar.** `SF <n>`, where `n` is `needs_you` from `GET /api/v1/overview`, read at start and every 15 seconds; its menu shows the factory state (`factory.state`, `stopped` when the API says the supervisor is stopped, `not reachable` while the API does not answer) and the count. A dash while the count is unknown.
  - **The app data folder.** `~/Library/Application Support/software-factory/` is the macOS shell's alone: `config.json` (`checkout`, default the folder the app was built from; `ui_port`, default 4310, set it when `factory.config.json` sets another `ui.port`; `keep_running_when_closed`, default true), written with the defaults on first start, and `state/` (the supervisor log and Electron's own data). The child gets the folder as `SF_HOME`; core does not read it in this change. The shell reads and writes only this folder: never the checkout's files and never a secrets file (`~/.config/software-factory/.env`); a test records every file it touches.
  - **No platform code in core.** `tests/boundaries.test.ts` fails on `process.platform`, `homedir()`, platform names or OS paths in `src/core`, `src/interfaces`, `src/ui` and `web/`. Platform code lives in a plugin (KeepAwake) or the desktop shell. The known exemptions, each with its reason in the test (decision 2): the KeepAwake plugins, the registry's per-platform default (`src/plugins.ts`), the env-file SecretStore's path (`src/impl/secrets/`) and setup's `open`/`xdg-open` (`src/setup.ts`; a follow-up moves it).
  - Solo default and multi-worker setting are the same: one shell per machine (a second copy quits at once), supervising one checkout; workers on other machines are unaffected.
  - The child gets the shell's own environment. Started from Finder, that has macOS's short `PATH`, so tools outside it (`claude`) may not be found; passing the login shell's `PATH` is a follow-up.
  - Not yet (slice 2): launch at login, a notification per newly needed item, a first-launch repo picker and clone, code signing and notarization, auto-update of the shell, Windows and Linux builds.
