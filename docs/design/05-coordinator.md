# 5. Coordination: the coordinator back end

- **A cycle calls the agent only when an item waits for a merge and the coordinator's daily limit is not reached (decision changed 2026-11-27, local-task-tk_f8e0e9d6 phase 2 of 3; current; replaces "one call per cycle" in the Agent bullet below, see History).** The decision that changed: **when a due cycle calls the agent.** Two gates run after the cycle has claimed its due time (so the due time always moves on by 15 minutes) and before the agent call, in `src/coordinator/cycle.ts`. With no item waiting for a merge, the cycle stores one `skipped` row, command `cycle`, reason "nothing to do: no item is waiting for a merge", and calls nothing. With today's coordinator spend at or over `spend.coordinator_daily_usd`, it stores one `skipped` `cycle` row naming the limit, calls nothing, and raises the day's one owner question, answered with the common `approve <usd>` or `reject` (design [06-spend](06-spend.md)). A cycle that calls the agent stores one `coordinator` spend row and one Activity record (job `coordinator`, actor `system:coordinator`) with its cost in the reason; the agent's answer carries the runner's reported cost and tokens. Why: a cycle with nothing to merge spends money for no result, and the coordinator runs on its own, so its spend needs a ceiling the owner controls.

- **A coordinator cycle runs every 15 minutes while the `coordinator` setting is on; it merges only local items of tier 1 or 2, checked in code (decided 2026-11-26, phase 2 of local-task-tk_dd036ba7).** New; it replaces no decision.
  - **Switch.** The boolean setting `coordinator` (`src/controller/settings/coordinator.setting.ts`), off by default, settable at runtime (`factory settings set coordinator true`). The controller's `coordinator` unit reads it from the live settings at each tick, as the worker reads `worker_kinds` at each claim: off starts no new cycle, on resumes them. A cycle already running finishes.
  - **Cadence.** A cycle is due every 15 minutes (owner answer 3) on the injected Clock. The due time is one row of `controller_coordinator_due`, so every replica reads the same time; the replica that runs the cycle moves it on by 15 minutes with one conditional update (`due_at` still the time it read), so no two replicas run the same cycle.
  - **One cycle at a time.** The cycle holds the store lease `coordinator`, a row of the existing sync leases (`StoreLease` over `syncLeaseOps`, `src/core/lease.ts`): no new lease table. While another replica holds it, a tick starts no cycle. The lease lasts `run_timeout_ms` plus 5 minutes, so it outlasts one agent call; a replica that stopped mid-cycle is taken over once it expires. The cycle renews it after the agent answers and carries out no merge once it is lost.
  - **Agent.** One call per cycle that passes the gates above, through the selected agent runner (`plugins.runner`), in a fresh read-only checkout with Read, Glob and Grep only, as the schedule's agent action runs (`readOnlyTools`). Its system prompt is `prompts/coordinator.md` (standing instructions, no private path), its prompt the items waiting for a merge (id, title, source type, tier, stage), its answer a JSON list of `merge` or `skip` actions with a reason each. The transcript is egress-scanned and stored at `transcripts/coordinator/<cycle>.json`; its link is `storage:<key>`, null when the scan flagged it.
  - **Merge gate in code.** Whatever the agent answers, the cycle (`mergeRefusal`, `src/coordinator/cycle.ts`) merges only an item that is waiting for a merge, from the local source, of tier 1 or 2 (owner answer 2), and of a tier no higher than `auto_merge_max_tier`. A tier 3 or 4 item and a GitHub item are refused. An allowed merge goes through the existing local merge (`mergeLocal`, as auto mode calls it, under the controller's service passport), so the merge queue and its checks still decide whether it lands. Any other command is refused.
  - **Records.** `controller_coordinator_actions`: one row per action, keyed on the cycle and the action's place in it, with the item, the command, the outcome (`requested`, `refused`, `skipped`, `failed`), the reason and the transcript link. A cycle whose agent call failed stores one `failed` row. No backfill.
  - Not in it: the Work page's Coordinator card (owner answer 1: above the work list, for the phase that builds the page), a read API for the records, any command other than `merge`, GitHub items, tiers 3 and 4.
  - Why a setting and a table: the owner turns the coordinator on and off without a restart, and every replica needs the same due time; `controller_coordinator_due` holds that one time.
