- **Page commands act as the CLI identity on loopback (decision changed 2026-11-08; current).** Without `ui.user_id`, the page's item commands act as the identity the CLI resolves on the same machine, through the same function (`cliIdentity`: `cli_user`, then `local:<git user.email>`, then `local:<OS user>`, then `local:anonymous`), so a solo setup sends commands with no config. `uiCommandsActor` (`src/compose.ts`) decides: `ui.user_id` when set (source `config`, the enterprise override); else, when the server binds a loopback address (`127.0.0.1`, `::1`, `localhost`), the CLI identity (source `environment`, or `config` when it is `cli_user`); else no actor, and a POST answers 503 "Commands are off: this server is not on loopback, so it needs ui.user_id. Settings (/app/settings#page-commands) says what to set." (an environment identity fits only a one-person local server; a shared server needs `ui.user_id` or real auth). The server binds only `127.0.0.1` today (`BIND`, `src/ui/server.ts`; no host option), so the 503 is for a future bind option. Authorization: the controller judges the request with the owner check (08-permissions), so the owner approves and adds verdicts, and anyone else, `local:anonymous` among them, is refused with "only the owner may send this command". `GET /api/v1/session` adds `actor` and `actor_source` (`config` | `environment` | null); the item page shows "Acting as <actor> (from <source>)", and `factory ui` prints it at startup. The item page's "Commands are off" notice links to the Settings page's "Commands from the page" section (`/app/settings#page-commands`), which shows who commands act as and says what to set: `ui.user_id` in `factory.config.json`, then restart `factory ui`. `ui.user_id` stays a config-file key, not a settable one: making it settable is #445.
  - **Item commands from the page (decision changed 2026-11-07, issue #227).** A second write route, `POST /api/v1/items/:id/commands` (`src/ui/commands.ts`), records one app command request (`inbound_app_requests`, design §4 app requests) for the controller to apply on its next tick; the route itself applies no command but Approve and Merge (since 2026-11-15, the decision at the top). Body: JSON `{ command, note? }`; `command` is any item command but `help` and the account command `link` (`approve`, `reject`, `revise`, `retry`, `resolve`, `budget`, `verdict`); `note` is optional, at most 2000 characters, trimmed, and required (non-blank) for `reject` and `revise`. The row's actor is `ui.user_id` from `factory.config.json` (a factory user ID, optional, unset in the checked-in config; an empty or non-string value stops startup naming the key), or without it the CLI identity (see "Page commands act as the CLI identity on loopback"), so the controller's permission check is that user's; args are `{ work_item_id, note? }` and the key is `app:<random UUID>`. **Token:** one random token per UI process (32 bytes, base64url), made at startup in `buildUiParts`, shared with the Settings write, held only in memory (never in a file, the store or a log) and new after every restart; the page reads it from `GET /api/v1/session` (`{ as_of, csrf_token, commands_enabled, actor, actor_source }`; 404 when the route is not wired), which is behind the same Host guard as every route, and sends it in `x-csrf-token`. **Checks, in order, each before any store write:** a Host other than `127.0.0.1`/`localhost` 403; an Origin missing or not `http://<Host>` 403; a Content-Type other than `application/json` 415; a missing or wrong token 403; no actor (a non-loopback server without `ui.user_id`) 503; a body over 16 KB 413; a body that is not JSON 400; an unknown command, an unknown or ill-typed field, a note over 2000 characters, or `reject`/`revise` without text 400; an unknown item id 404. Success is 202 `{ request_id, seq, command, work_item_id }` (Approve and Merge add `outcome`, `state` and `refusal`). The controller applies `approve`, `reject`, `revise` (since 2026-11-11, issue #527), `retry` and `resolve` (since 2026-11-11, issue #453), `verdict` and `merge` and refuses the rest with one reply (design 04-gate-commands, App requests); **a dashboard reject closes the item's open PR** as `/reject` does (decision changed 2026-11-09, issue #452; before: a dashboard reject was refused, and a reject left the PR open): one comment quoting the reason, then the PR closed without a merge, a merged PR left alone. A POST to any other path (settings excepted) is a 405 with a JSON `{ error }` body and `allow: GET, HEAD`, whatever the area; every other method keeps its area's 405. **Item API:** `/api/v1/items/:id` adds `commands` (`{ name, usage, description }` for each command that applies in the item's current state, from the same table and rule as the comment footer, `commandsFor`, `/help` last) and `replies` (the item's stored requests, oldest first, the newest 50: `{ seq, command, created_at, handled_at, refusal }`; `command` and `refusal` pass the `Withholder`; the note is never returned). They read a new store method, `listAppCommandRequestsForItem` (no schema change). Every other GET response is unchanged. The server still binds only `127.0.0.1`.
