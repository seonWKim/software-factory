# 5. Coordination: intake sources and pull requests

- **Slack intake and source routing** (2026-11-01, issue #109). The decisions that changed: **Slack intake** (Slack threads are a source, through the `slack` stream plugin) and **source routing** (each item's actions go to the adapter of its source type, so Slack runs beside GitHub). A mention of the bot in a channel listed in the `slack` config block (channel IDs only, checked at startup, no other key) creates one item for its thread, source id `slack:<team id>:<channel id>:<thread ts>`, deduplicated on Slack's event id. Replies in the thread and button presses are the same command events as GitHub comments; every one goes through `AuthProvider.authorize` before it acts, `/help` included outside GitHub, and an unknown account gets a refusal in the thread. Buttons are only for commands that take no text (approve, retry, resolve, budget, help), read from the command footer the command table builds; a plain-language suggestion gets Confirm and Cancel, and nothing runs before Confirm. Everything posted passes the `EgressScanner`; a blocked message is never posted or retried in any form, and the thread gets one fixed withheld notice with the same marker, so a repeat posts nothing. The plugin reads only `SLACK_APP_TOKEN` and `SLACK_BOT_TOKEN`, never a GitHub credential. Routing: no new plugin kind; the list-valued `plugins.source` and the per-item routing of "Several sources" carry it, and the controller now also posts the PR's link once in a non-GitHub item's thread. PRs, review and the merge stay on GitHub, unchanged. No Slack SDK: Socket Mode over Node's `WebSocket`, the Web API over `fetch`. Not built: DMs, reactions, private-channel scopes, closing a thread. Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md), `slack`.
- **CLI intake.** The decision that changed: **local work items and their commands are written from the CLI** (issue #200). `factory task create --title <t> --body-file <f>` creates one local work item in the store (source type `local`, id `local-<random>`, requester `cli_user`) with its triage run queued, in one `createWorkItem`, and prints its ID; the project key comes from the store (`storeProjectResolver`), so it makes no GitHub call, and it fails while no project is stored. `factory task list` and `factory task show <id>` only read (state, spec, runs, item messages). `factory approve|retry|revise|reject <id> [text]` append one row to the CLI command log (`command_inbox`: random key, actor `cli_user`, `args.item`, optional `args.text`) and change no item state; the `local` source reads it and the controller applies it like the same GitHub comment: the same `authorize` check through `AuthProvider` (identity provider `local`, subject `cli_user`) and the same refusal replies, stored as item messages. Every command acts as `cli_user` from factory.config.json (a factory user ID such as `github:12345`, read by `cliUserConfig` in src/core/config.ts); with none each prints an error and exits 1. The command table in src/core/local-cli.ts builds the usage text, one `/help` line and the SET_UP.md list (a test compares them). No new table and no new permission path. Not built: a CLI command that links the local account (with `auth: github` the identity resolves only through a link, so until one exists CLI commands are refused as not linked), `verdict`, `budget`, `resolve` from the CLI, a dashboard view.
- **Local intake.** The decision that changed: **local intake and item messages live in the store.** The `local` poll source (issue #199) reads the CLI command log (`command_inbox`) by `seq`, at most 100 per poll, cursor = last `seq` read (`intake:local`), and turns each command for a local item (`args.item` = work item ID, optional `args.text`) into the event the same comment gives on GitHub, by rebuilding `/<command> <text>` and parsing it with the same comment parser; `comment_id` is the command key, the identity is provider `local`, subject the actor after `local:`. Commands for missing or non-local items are skipped and the cursor passes them. Its replies are stored as item messages (`item_thread`, one per marker); `markSeen`, `setStatus` and `closeIssue` are no-ops because the store already holds the item's state. Source plugins get the store in their context for this. Writing commands and creating local items: see CLI intake above. Not built: linking local accounts to factory users. Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Item thread and command inbox.** The decision that changed: **an item's messages and the CLI commands live in two general tables** (issue #281). The store keeps every item's messages in `item_thread` (one per item and marker) and the commands in `command_inbox` (read by `seq`, `command_key` the idempotency key). SQLite migration 24 and MySQL step `0024` create both and copy the rows of migration 21's message and command tables with their `seq`, so a saved `intake:local` cursor still points at the same next command; the copy skips rows already copied, so it is safe to run again. The old tables stay in place, and nothing reads or writes them. Store method names, arguments and results are unchanged, and GitHub items still write nothing there.
- **Stream intake.** `SourceAdapter` is now a union on `intake`: `"poll"` sources keep `poll(cursor)` (GitHub, unchanged); `"stream"` sources have `subscribe(signal)` yielding `PushedEvent`s (event, `dedupe_key` unique within the source, `ack()`). A pushed event is written to a store inbox (`source_inbox`, migration 10) before it is acked, and a duplicate `dedupe_key` is a no-op that is still acked; a failed write is not acked. Controllers read the inbox through the cursor `inbox:<source type>` and the same `handleEvent` as polled events, so any replica handles them. One listener per stream source across replicas, decided by a store lease (`listener_leases`, migration 10: owner, token, expiry; conditional updates only; the inbox write checks the token in its transaction). It reuses `lease_ms` / `heartbeat_ms`, runs inside the controller process (started by `Controller.run`), reconnects with backoff and logs on state changes only. Cleanup on the poll interval deletes rows older than `inbox_retention_days` (optional, default 14) that are at or below the cursor; no cursor, no deletion. What it changes: a new intake path and two tables; GitHub intake, `SourceType` and the registry are unchanged (the only stream source was the test-only `fake-stream`; `slack` came later, see Slack intake above). Not built: webhook endpoints. Details: architecture §4 Intake.
- **Several sources.** The decision that changed: **one source becomes a list of sources.** `plugins.source` takes a string (unchanged: a list of one, the same selection as before) or a list of registered names; an empty list, an unknown name, or the same name twice fails at startup naming `plugins.source`. `build()` makes one adapter per name and hands them all to the controller, which refuses at startup two adapters of one source type, or several with none of type `github_issue` (PR merge, close and unmergeable events come only from GitHub, so without it factory PRs would never close their items). Routing: each item's `postComment`, `markSeen`, `setStatus` and `closeIssue` go to the adapter whose `type` matches the item's `source.type`; `setStatus` for a PR (non-null `pr_number`) goes to the `github_issue` adapter whatever the item's source, because PRs live on GitHub (a single non-GitHub source alone keeps the old behaviour: everything to it). An item whose source type has no configured adapter keeps its state; its calls log a warning and are skipped. Intake: every poll source has its own cursor `intake:<type>` and every stream source its own listener (the lease was already per type) and inbox cursor; each source's step runs under its own guard, so one source failing does not stop the others in the same tick. Commands from any source go through the same command table, the same `AuthProvider` check and the same replies; resolving non-GitHub identities is left to the provider work (#107, #109). Not built: new `SourceType` values (the Slack adapter came with Slack intake above). Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Pull requests a person opens, and a person's pushes.** Now every change to the repository passes through the controller:
  - **Adoption.** The `github-issues` source reports `pr_open` on every poll for each open PR against the base branch from this repository: every factory-branch PR, and every other PR that is not a draft (a draft is adopted on a later poll, once it is ready). A PR the store does not know (not a factory branch, no item with that PR as its source) is adopted: one item, origin `adopted`, source = the PR (`owner/repo#N`, link `/pull/N`; comments and the status label go on the PR, labelled once), title = PR title, problem = title and body, requester = the author's user ID, `done_criteria` null, `allowed_paths` = the files the PR changes (`prFiles`, both sides of a rename, read only for a PR the store does not know), tier = the floor tier of those files, stage `REVIEW` with `pr_number` and `head_branch` set, and one review run, all in one `createWorkItem` (idempotent on the source; state change `pr_adopted`). An author that does not resolve to a user is not adopted (its merge is then an unreviewed merge). Forks are not adopted.
  - **Review of an adopted PR.** The worker checks out the item's `head_branch` (it fails if `origin/<branch>` is missing) and the prompt has the PR's title and body (untrusted), its files and the diff, and says there is no spec. The review comment goes on the PR as for factory PRs. The review sets the tier (max of judgment, floor, previous). A pass goes through the same CI gate to `merge_pending`, and auto-merge stays at 0, so a human still merges. The factory never pushes to a person's branch: bugs block on a human with `changes_requested`, failed checks with `checks_failed` (both `blocked_on: human`; no implement run). `/verdict` and `/resolve` still map PRs by factory branch only.
  - **`factory: skip`.** A PR with this label, added (latest `labeled` event in the issue timeline) by a user with the existing `approve_spec` permission, gets no item. A label added by anyone else is ignored with a warning, and the PR is adopted. It is checked at adoption only: on an adopted PR the label does nothing.
  - **Merges.** Every merged or closed PR is reported now, not only factory ones. A factory branch maps to its item as before; any other PR to its adopted item by number; a merge closes it as `CLOSED` / `completed` with `merge_sha`, the merger as actor (approver of record), and a close without merge as `rejected`. A merged PR with no item (skipped, a fork, never adopted, or merged before the first poll that would have adopted it) writes one `unreviewed_merges` row (project, PR number, merge sha, merger's user ID or null; idempotent on project and PR number) and a warning. On a fresh install the first poll reads one page of closed PRs, so older merges there are recorded too.
  - **A person's push.** Every run that pushes (implement, update, resolve) records the head it pushed as the item's `last_head_sha`, under its lease (`recordPushedHead`); adoption records the PR's head. On each poll the controller compares an open factory or adopted PR's head with it. A different head is a person's push: one run of kind `manual`, written already `succeeded` and acknowledged (never queued, so no worker claims it and the controller applies nothing), with `actor`, `from_sha`, `to_sha` and `pr_number` in its outcome, and `last_head_sha` moved to the new head, in one transaction (`recordPrHead`, conditional on the old head, so a repeat writes nothing). It changes no stage, blocked field or version, and nothing is re-queued or re-reviewed: a later review covers it. GitHub does not name who pushed, so the actor is the author of the head commit resolved through auth; if that does not resolve, `system:pr-sync` and a warning. While any run of the item is running, the head is not looked at (that run may be pushing); an item with no recorded head (from before this) only takes the current head as a baseline.
  - **Schema:** migration 12 adds `work_items.origin` (`factory` default), `head_branch`, `last_head_sha` (all store-owned, not in `WorkItemPatch`) and the `unreviewed_merges` table. SQLite builds it on open; MySQL gets it from the step file `migrations/mysql/0012-adopted-prs.sql` through `npm run migrate` (the table has a `seq` column like every MySQL table, which the store orders ties by). A MySQL store refuses to start until that step is applied.
  - Not built: re-review after a person's push, adopting a PR again after it reopens with a new number, showing unreviewed merges in stats. The Health section and the Floor line of the app show them (see `09-dashboard-app.md`).

## History

- **Stream intake** (new decision, 2026-11-01). Before: every source was polled on a timer, so a source that pushes events, like Slack Socket Mode, had to be forced into polling.
- **Several sources** (decision changed 2026-11-01). Before: `plugins.source` named one plugin and the controller sent every comment, 👀, status and close through that one adapter, so a second source such as Slack could not run next to GitHub, and its items would have been answered through GitHub.
- **Pull requests a person opens, and a person's pushes** (decision changed 2026-11-01, issue #113). Before: only factory PRs were tracked: the GitHub source read pull requests on factory branches only, so a PR a person opened could merge with no review run, no scope or size check and no record, and a push a person made to a factory branch was invisible to the factory.
- **Local intake** (decision changed 2026-11-07, issue #199). Before: polled intake was GitHub only, nothing read the CLI command log and nothing stored item messages; now local intake and item messages live in the store, through the `local` source.
- **CLI intake** (decision changed 2026-11-07, issue #200). Before: the `local` source could read the CLI command log, but nothing wrote to it and nothing created a local work item, so human commands from the CLI had no entry point and the local flow was untested end to end.
- **Item thread and command inbox** (decision changed 2026-11-07, issue #281). Before: local item messages and CLI commands lived in two tables from migration 21 named for the local source only, so the store had no single place for an item's conversation.
- **Slack intake and source routing** (decision changed 2026-11-01, issue #109). Before: no real stream source existed, so work could start only from a GitHub issue (or the CLI), and the routing had only test fakes as a second source; a Slack thread could not start, answer or approve an item.
