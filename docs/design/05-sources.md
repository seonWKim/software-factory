# 5. Coordination: intake sources and pull requests

- **Short IDs in the CLI** (decision changed 2026-11-21, wi_8c693a8b, "Dashboard IDs work in every command"; current; replaces "`task show`, the item commands and `help` take only the full `wi_…` ID", see History). The decision that changed: **one token rule names an item.** `resolveItemId` (src/core/local-cli.ts), used by `task show`, every item command (`approve`, `retry`, `revise`, `reject`, `resolve`, `verdict`, `merge`) and `help <id>`: the token, `wi_` optional, is a prefix of the work item ID, so the full ID, the short ID (`shortItemId`: the 8 hex characters after `wi_`, as the dashboard shows it, design 09-dashboard-item) and any unique prefix of either work. A token with no hex characters after `wi_` reads nothing. The store's `findWorkItemIds(prefix)` reads the matching IDs as a primary key range, no list scan. One match runs the command with the full ID (the stored command carries it, the local handler's hints name it); none keeps the refusal `no work item <token>`; several exit 1 with each full ID and its short ID listed, and nothing is written. `task create` prints the full ID first (scripts read it), the short ID on line 2, then the lines below; `task list` prints `<id>`, `<short id>`, title, stage and blocked reason; its Tasks section is unchanged. Not changed: the old source short ID (`f77945b7` of `local-f77945b7-…`) is no token; dashboard search; the chat's own item lookups. Why: the dashboard showed an ID that no command accepted.
- **CLI hints name the installed command, and `task create` prints the item's link and next step** (decision changed 2026-11-19, dogfood-review F19; current; replaces "the CLI's hints always say `factory` and `task create` prints only the item ID", see History). The decision that changed: **the CLI's hints start with the command the owner runs.** A project's wrapper (`gb`, say) runs the same code, so it exports its own name in `FACTORY_CLI_NAME`; `cliName` (src/core/local-cli.ts) reads it, one word trimmed, and falls back to `factory` when it is absent, empty or more than one word. src/main.ts reads it for the sentence form (`<name> confirm <proposal-id>`, `<name> task create …`, the usage error) and the local handler (src/cli/handlers/local/local.command.ts) for the line after a stored approve, revise, reject, retry, resolve or merge (`see \`<name> task show <id>\``, `<name> merge`), the refusal hint (`refusalHint`) and `<name> confirm`. It reaches runLocalCli and runSentence as the optional `cli` dep, which the chat callers (src/impl/source/slack-commands.ts) leave out, so chat replies and the shared `/help` text still say `factory`. `task create` prints the new item's ID first (scripts read it), its short ID (Short IDs, above), then `task <id> in +<slug>` with `--project`, then the item's page `http://127.0.0.1:<ui.port>/app/items/<id>` (`ui.port` from the loaded config, which `loadConfig` already checked, default 4310; it opens on this machine while `factory ui` runs), then `triage queued; you'll be asked to approve the spec`; a caller with no `ui` dep (chat) prints no link. Not changed: hints in other CLI handlers (`resume`, `mode`, `ui`), Slack and GitHub replies. Why: a project's owner was told to run `factory task show …`, a command they did not have, and `task create` gave no link and no next step.
- **Replies under a Slack notice act on its items** (decision changed 2026-11-12; current; replaces "a notice is linked to no item, so a mention under it is a request, and the Slack source reads only `slack.channels`", see History). The decision that changed: **each Slack notice is recorded with the work items its lines name, and a reply in its thread acts on them; it never creates a work item.** When a notice posts, the Slack source's `notifyOwner` stores one record (`controller_notice_messages`: channel, the message ts, the IDs its lines name in line order; a summary line names none) in the SQLite store (timestamped controller migration `20261112T2100-controller-notice-messages`). A failed record is logged, not thrown, so outbound does not post the notice twice. A reply in a notice's thread after a mention, or with a slash, is read as in an item's own thread (bare command words, the fixed phrase `go ahead and merge` as `merge`, design 04-gate-commands) and runs as the linked factory user: a notice naming one item runs the command on it; one naming several posts one question in the notice's thread with one button per item (value the item ID), the reply's words stored (`controller_notice_questions`, keyed on the reply's event ID) until a press runs them on the chosen item as the presser; one naming none (a summary, or a notice with no record) gets one reply saying so. An unlinked account gets the usual refusal and nothing is stored; words with no command get one reply naming the commands each item takes now, with no model call. Answers post in the notice's thread: the source's own, and the controller's for a Slack item, since the reply's ID (and so its stored command's key, `cli:slack-notice-<channel>-<ts>-<event id>`) carries the notice, and `postComment` posts a marker with that key there. The notices channel (`slack.notify_channel`) is read for these replies even when it is not in `slack.channels`, owner only; other messages there are not read, and there a thread with no record counts as a notice posted before the records. A mention in a thread that is neither an item nor a notice still makes an item from the thread. Not built: the plain-words reader under a notice (a reply with no mention and no slash is not read), records for notices posted before this change, expiry of the records, and the controller's answer for a local or GitHub item, which stays on that item's own surface. TargetDeps and the outbound notify target are unchanged. Why: the owner's "go ahead and merge" under a "ready to merge" notice made a new work item instead of merging the item it named.
- **Local items: the base push, the owner's checkout, and PR-era items.** The decisions that changed (2026-11-08, issue #433; before: see History): **a local merge with a forge selected queues one push of the base to origin; a checkout of the base no longer refuses the merge; a local item that already has a PR keeps the PR path.**
  - **The local forge pushes the base too** (decision changed 2026-11-16; current; replaces "only the `github` forge pushes a base, so with no forge a local merge never reaches origin", see History). The owner wants local work on the remote with no GitHub plugin. `merge_queue.push_base` (default `false`) gives the `local` forge `pushBase` when the factory repo names an origin; with no forge selected, compose then makes it the controller's forge, and the base push below runs unchanged (the same `push_base` action, retries and base reconcile). The git push is one shared function (`src/impl/git/base-push.ts`) both forges call. Off (the default) or no origin: no push row and no remote call. Only the base branch is pushed, never item branches.
  - **Base push** (decision changed 2026-11-09, RFC 0015 M8: an outbound delivery; see History and 10-event-driven.md "The merge queue"). When the forge can push a base (`Forge.pushBase`, built by the `github` forge, and by the `local` forge with `merge_queue.push_base`) and the sandbox can sync one (`syncBase`), the delivered merge stores one keyed `push_base` action (`push_base:<item>:<merge sha>`) to the base push's own destination `git:<host id>:<base>:push` (not the merges', so a failing push holds no later merge; 10-event-driven.md "Git destinations"), before the item's close. The item closes before anything remote runs. Outbound's `local` target delivers it; its batch claim makes two replicas push once; the sandbox fetches only origin's base; when it already contains the merge the row finishes with no push; when it moved and is not an ancestor of the local base it is merged into the local base first (merge-tree, commit-tree, one conditional ref update; no check runs on it, both sides were checked where they were made); then the forge pushes from the factory repo with `--force-with-lease` on the remote sha the sandbox read and `--no-verify`, so a base that moved again is never overwritten. Any failure (an outage, a rate limit) is a delivery failure: outbound retries the batch, `retry_base_ms` doubling up to `retry_max_ms`, keeping the error; the item never changes. A remote base that conflicts is delivered as a conflict, which files a reconcile item (Base reconcile, below). The push uses the factory repo's own git configuration for origin, as its fetches do.
  - **Base reconcile: a remote base conflict files one reconcile item per origin sha** (decision changed 2026-11-23, wi_2f7e8217; current; replaces "one Needs-you row asking the owner to merge `origin/<base>` by hand", see History). The pushed item stays closed and the `push_base` row finishes as `conflict`, now with origin's sha (`remote`, which the sandbox's `syncBase` returns with the conflicting paths). With a forge that pushes a base, `basePushDelivered` has the intake unit file one local work item, source id `base-reconcile:<base>:<origin sha>` (`reconcileSourceId`), so a second conflict on that sha files nothing; with no origin (the solo default) nothing is filed, and a conflict stored before this change (no `remote`) files nothing either (no backfill). The item skips triage and spec approval: it moves from NEW to RUNNING with one resolve run (`<item>:reconcile:<sha>`). Its resolve run asks the sandbox to `startReconcile`: fetch only origin's base, and make the item's branch from local `<base>` when it is missing (never from origin; a retry keeps it); it merges origin's commit as fetched, not local `<base>`, into that branch, resolves, and runs the install and check commands as any resolve run; the result is committed on the local branch only. A green result goes to merge_pending and enters the merge queue with no person (`system:controller`, keyed on the run), so local `<base>` moves only through its merge check, with the same checks; the landing then queues the base push, which now finds origin an ancestor. A red check moves nothing and sends no implement run (the item has no spec): it returns to merge_pending. A failed resolve run waits on a person as any resolve run does. Needs you shows its `base_push_conflict` row, "The reconcile of local main with origin failed" (or another base's name), only while that base's newest push conflicts and a reconcile item of that base is blocked on a person; the detail names the conflicting files, the local merges waiting, the item, and the hand merge. No new table, column, stage or setting. Why: a conflict with origin is recoverable after the fact, so the factory reconciles it itself and asks the owner only when that fails.
  - **The owner's checkout.** The refusal for a base checked out in a worktree is gone. A checkout of the base with no uncommitted tracked changes is fast-forwarded with the base (`read-tree -m -u`, hooks off: HEAD, index and files move together, status stays clean). One with uncommitted changes keeps its HEAD commit, index and status: its HEAD is detached where it was before the base moves (re-attached if the move fails), the close's state change gets `checkout_not_updated` (the path), the merge message says so, and the item page shows a "local checkout: not updated" fact. The item page also shows the base push (pending with its failed tries, pushed, or a conflict).
  - **PR-era local items.** `routeFor` (src/core/worker-deps.ts) gives the local route only to a local item with no PR (`change_ref` null). A local item that opened a PR before #427 takes the forge's broker and sandbox like a GitHub item, so its update run reads `origin/<branch>` again instead of failing with `git rev-parse:` (PR #429). This reverses #333's rule that routing is by source type only.
  - **Compose, worker, session.** Unchanged otherwise: `Plugins.localRoute` builds the `local` broker and the selected sandbox in local mode beside the selected ones; `git.store_branch` goes through `routeFor`, as do preflight and comments (the push and the PR are outbound deliveries since RFC 0015 M7, 10-event-driven.md). A session with no local route refuses a local item before any call.
  - **Merge (decision changed 2026-11-08, issue #451; before: see History).** A local item with no PR merges only through the `local-merge` unit's `mergeLocal` (the sandbox's `mergeLocal`), reached by `factory merge <id>` and by the Merge button (an app `merge` request, `09-dashboard-app.md`); a GitHub item at `merge_pending`, and a PR-era local item that has a PR, merges from the same Merge button through the forge's `mergePr` at the head the review passed (the `pr-events` unit's `requestPrMerge`, a keyed `merge_pr` action outbound's `github-change` target delivers, RFC 0015 M7; a merge commit), never from the CLI: `factory merge` stays local-only. For a local item, the install command and the checks run on the merge commit in a temporary detached worktree, hooks off, removed after; a failure moves nothing and the item stays in `merge_pending`.
  - **Two replicas.** One conditional `update-ref` moves the base, one conditional transition closes the item and writes the push row (unique per item), and one conditional claim takes the row, so two merges of one change give one merge commit, one closed item and one push.
  - Solo default: no forge selected (a forge implies a remote): the local merge moves the local base and nothing else; no push row is written and no remote call is made. Enterprise setting: a forge selected, on the shared store: one push row per merge in the close transaction, pushed once by any replica with backoff. Not built: backfilling pushes for items merged before this change; pushing with the forge's App credentials instead of the repo's git configuration. The merge check for local items while GitHub is selected: built 2026-11-12, see the first decision above.
- **Local startup.** The decision that changed: **the factory starts, builds, reviews and merges with no GitHub plugin selected** (2026-11-07). One rule, by plugin selection and never by whether the repo has a remote: config selects no GitHub plugin when no source is `github-issues`, neither `auth` origin is `github`, the broker is not `github`, no forge is selected and `permissions.grants` has no `github-permission` (`selectsGitHub` in src/compose.ts, which sets `local_only` in the loaded config). Then:
  - **Startup.** No GitHub credential is read (the `github_auth` plugin is not built; plugins get a GitHub client and credentials that refuse every call) and no repository lookup is made. The project key is `local:local:<first 32 hex of the SHA-256 of owner/name>`, labelled `local/<owner>/<name>`, stored as #350's key of the configured repo, so the CLI and the next start read it. No forge ID: a rename starts a new project. Switching a store back to GitHub keeps the stored local key until GitHub's background read stores the GitHub key for the next start (the existing "another repository ID" warning).
  - **Base and fetches.** Nothing fetches origin: the sandbox's trusted base is the factory repo's local `refs/heads/<base_branch>`, a run folder's `refs/remotes/origin/*` are the factory repo's local branches (so the worker's `origin/<base>` and `origin/<branch>` read them unchanged), the worker's base fetch copies the local branch, and the git-worktree updater builds the local base branch with no fetch and no fast-forward of the main checkout.
  - **Broker.** The `local` ToolBroker (docs/plugins/tool-broker.md) commits a run's branch to the local branch `refs/heads/factory/<id>` of the factory repo, never to a remote, behind the same lease, prefix, trusted-git and egress checks as the GitHub broker (one helper, `src/impl/broker/trusted-git.ts`). It has no PR, preflight or comment tool, so the worker skips the PR open, the preflight's forge checks and PR comments, and the implement outcome has no `pr_number`.
  - **A run's comments are thread entries** (decision changed 2026-11-09, RFC 0015 M7, worker half; see History). The worker's merge-conflict, failed-checks, checks-env and scope-violation messages, its review comment and its update comment are entries on the item's thread (`Worker.comment`, once per marker), delivered by outbound like every controller message (10-event-driven.md, "Writes to the outside world leave through outbound"). A local item's thread is its surface: nothing leaves it, also with GitHub selected. Any other item's gate comments go to its own source (`threadDelivery`, src/core/local-merge.ts); the review and update comments go to its PR through the forge (`WorkerDeps.prRef`, the forge's `prRef`), and with no PR or no forge to its own source, as the controller's PR comments do. The run never waits on the delivery and never fails on it: a delivery failure is retried by outbound. The broker has no `github.comment` tool any more. Solo default: a local item never calls GitHub for a comment. Enterprise setting: a GitHub item keeps its comments, markers and bodies unchanged; an item of another source (e.g. Slack) now gets its gate comments in its own thread, where before it got none. Not built: the rest of a local item with GitHub selected (preflight, push, PR open, checks) stays with #333.
  - **Review and gate.** The item enters `REVIEW` with no `pr_number`; the review reads the local branch's diff against the local base, and a pass reaches `merge_pending` the same way a PR does (no PR, so no checks to wait for). Its message names `factory merge <id>`.
  - **Merge** (decision changed 2026-11-08, RFC 0015 M8; see History and 10-event-driven.md "The merge queue"). `factory merge <id>` stores a `merge` command in the command inbox; the controller's one local merge function (`mergeLocal` in the `local-merge` unit; #333 and #246 call it, no second path) authorizes it through the owner check for `approve_merge` (anyone else is refused as `not_owner`), refuses an item not waiting for a merge or whose branch conflicts with the base, and puts the change in the merge queue. A `merge-check` run checks its merged result on a worker; only a green one lands, as an outbound delivery whose `local` target merges through the sandbox, so core runs no git; a red one is refused on the item with the reason and nothing moves. The sandbox writes the merge commit with `git merge-tree` and `git commit-tree` (objects only, no checkout, no index, no hook) and moves `refs/heads/<base>` conditionally on the base it merged; the push to origin, with a forge selected, is the base push's. A conflict moves nothing, replies with the conflicting files and starts the automatic resolve (05-merge-conflict.md; since 2026-11-12 also with a forge selected); a checkout of the base is fast-forwarded or left as it was (see Local items: the base push, the owner's checkout). A merge closes the item (`completed`, `merge_sha`, the approver as actor, reason `local_merged`) and releases the items waiting on it; a repeat finds the branch merged and moves nothing. In auto mode the controller calls the same function itself (see the first decision above).
  - Solo default: `plugins.source: ["local"]`, `plugins.broker: "local"`, `"auth": "local"`, `permissions.grants: ["static"]`. Enterprise setting: the GitHub source, GitHub auth and the GitHub broker, unchanged, with no local broker. No new table, column or state. Not built (follow-ups): degraded mode and forge state, the outbox for GitHub writes and CLI mirror comments, the `factory status` line for GitHub; `factory session` with the local broker. Local items while GitHub is selected: see Local items: the base push, the owner's checkout, and PR-era items.
- **Thread first, then the outbox.** The decision that changed: **every factory message is written to the item thread before any source is called, and only the outbox step posts it** (2026-11-07, issue #282). The controller's one message helper writes the message to `controller_item_thread` (one per item and marker), and for an item whose source is not `local` it adds, in the same transaction, one `outbound_intents` row (SQLite migration 29): the source type, the target, the item field the URL fills (`spec_comment_url` or `failure_comment_url`), the attempts and the next try. An entry goes only to its item's own source: a PR comment (the PR is a target of the same type) goes to the PR, and for a non-GitHub item it goes to the item's own source instead. The outbox step runs last in every tick (and after each public tick step): it lists pending rows of the source types this process has adapters for, claims each one for `lease_ms` with a conditional update (a token only a claim bumps), calls that adapter's `postComment` (the only call of it, apart from a `/link` reply on an issue that is no work item, which has no thread), and marks the row delivered under the claim; a marker the store already has a posted record of (GitHub sync records below) is marked delivered with its stored URL and no call, a changed body only logged. So each entry is posted once, also when two replicas run the step at once. A failed post counts an attempt, keeps the error, releases the claim and waits `retry_base_ms` doubling per attempt up to `retry_max_ms`; it never touches the item's stage, blocked fields or version, and a failed post no longer stops the transition that wrote it. The URL of a delivered comment fills the item's link field when no newer entry names the same field (no version change, no state change); the transition itself stores the link only when the entry was already delivered (a re-decide), so links appear once the outbox delivers. Entries of a source type with no adapter here stay pending for a process that has one. `local` items need no adapter: the thread is their surface, so they get no outbox rows and their transitions run in any process. The controller reads CLI and app commands from the command inbox itself (design 04-gate-commands, "Commands from the command inbox"), so `plugins.source` may be an empty list: the factory then runs on the store alone, with local items. A local-only setup is still `"source": ["local"]`; GitHub (`github-issues`) is the sync plugin. Solo default: no source, only the local command inbox and item thread (no outbox rows, no external call). Enterprise setting: linked sources on a shared store, each outbox row claimed by the conditional update above, so one replica posts it. This outbox is the one queue for every source write: later work (degraded mode, the sync lease, CLI mirror comments) adds to it, not a second queue. The comment-to-event mapping has one copy, in core (`src/core/comment-event.ts`): the command inbox reader and the Slack source import it; the `src/impl/source` copy is gone. Not built: retiring `inbound_app_requests`, a Slack adapter, webhook endpoints.
- **One command table, and the factory's commands in Slack** (new decision, 2026-11-09, issue #498; current). The decision that changed: **every CLI command is one entry of one table in `src/core/command-table.ts`, and Slack runs the same commands as the linked factory user**; before, the command list lived in three places (the item commands in src/core/commands.ts, `task`, `merge` and `users` in src/core/local-cli.ts, `settings` and `mode` as usage text in src/settings-cmd.ts) and Slack took item commands only. Each entry gives its name, its CLI arguments, who may run it (`anyone`, `submit_work`, `approve_spec`, `approve_merge`, the local owner), what it does and prints, and its chat form (typed after a mention of the bot). The CLI's top words, usage and parsers, the dashboard's command list (`APP_COMMANDS`: the item commands, then the table's other item commands such as `merge`), the chat parser (`parseChatCommand`) and the two SET_UP.md lists read it; tests/command-table.test.ts fails when an entry has no CLI form, no chat form or, for an item command, no dashboard command. The item commands' phases and replies stay in src/core/commands.ts.
  - **Slack forms.** `list` and `show <id>` (anywhere), `settings list`, `settings history`, `help`; `approve`, `retry`, `revise`, `reject`, `resolve` and `merge` in an item's thread, which names the item, with or without the slash (see "Slack commands need no slash after a mention in an item's thread"); a mention with any other words is a request in plain words (outside an item's thread it is answered with the offer to make it a task, whose press starts a work item as `task create` does; in an item's thread the factory suggests a command). A form's words match whole and in any case, a form shown without `/` takes an optional one, and its arguments must fit (`list` takes none, `show` one ID), so "list the open bugs" is a request. A reply in an item's thread without a mention is a command only with its `/`. Buttons (Approve, Retry, Resolve, Help, Confirm) take the same path.
  - **Who.** The Slack account must be linked (`factory link-code <user_id>`, then `/link <code>`); the linked factory user's stored role decides, through the local auth plugin, as for the CLI (design 08-permissions). An unlinked account gets one reply in the thread saying it is not linked; only `/link` and `help` are answered for it. Solo: the owner's Slack account is linked to the local owner. Enterprise: each person's account is linked to their own factory user. One code path; audit rows carry the factory user ID.
  - **How.** The Slack source (src/impl/source/slack-commands.ts) runs a command through the CLI's own code (`runLocalCli`), as the linked user: a read replies with the lines the CLI prints for the same store, in a code block; an item command or `merge` stores the CLI's command row (key `cli:slack-<event id>`, so a redelivery stores it once; actor the linked user ID; not mirrored, since the thread already shows it) and posts nothing: the controller applies it from the command inbox with the same result and answers in the thread (a refusal is the owner check's text, once). The source makes no Slack call before the row is stored; a failing Slack API delays only the replies. `help` lists only what the sender may run there: the owner (or anyone while no owner is stored) everything, anyone else reads and requests (the owner lookup, `getOwner`). `settings list` and `settings history` read the config file and the store as the CLI does.
  - **Writes wait for #479.** `settings set|reset` and `mode` from Slack get one reply saying they wait for edge passports on chat commands (#479); they write nothing. Reads still work.
  - **Cut chat replies.** A reply longer than the Slack renderer's limits (src/impl/source/slack-format.ts: 3000 characters a section, 45 sections) keeps the sections that fit and ends with one note, `(reply cut to Slack's limits; the whole text: <command> or <link|the item>)`: the CLI command that prints the whole text (e.g. `factory task show <id>`), and for `show <id>` a link to the item's source (its issue or Slack thread) when that is a web address. The command is always there because the CLI reads the same store and the solo default has no dashboard address to link; the link is added when the item has one (decision changed 2026-11-09, review of #498; before: the note named the command only, with no link).
  - **Not built here:** #481 to #486 (`/revise` on a PR from Slack, 👀 on commands, private channels, edge passports and auth origin for Slack), a Slack form for `standing`.
- **CLI intake.** The decision that changed: **`factory approve|retry|revise|reject` work for an item of any source, and a command on a GitHub item is mirrored to its issue, best effort** (2026-11-08; the owner's answer of 2026-11-07: local auth decides). The CLI stores the command for any item it finds (the old refusal "is not a local work item: reply on its issue instead" is gone) and still makes no GitHub call. The controller applies it from the command inbox through the same transition the same GitHub comment gives, with the CLI identity as actor, judged by the owner check: the owner needs no GitHub write access, and the transition never waits on GitHub (labels, 👀 and replies stay best effort; a CLI command has no comment to react to, so it gets no 👀). The mirror: a command on an item of a sync source is stored with `mirror` (`command_inbox.mirror` = 1, SQLite migration 37); the controller's mirror step writes it once to the item's thread under marker `<!-- factory:cli:<command_key> -->`, so the outbox posts one comment on the issue with its retries and backoff, and marks the command mirrored (`mirrored_at`, `markCliCommandMirrored`) only once that post was delivered. A failed or rate-limited post leaves it unmirrored for a later tick. The mirror text names the command in backticks and quotes the note (left out when the egress scan flags it), so it never starts with `/` and the GitHub poll reads it as a plain comment. Solo: nothing to configure, the environment user is the owner on the first command. `task list` stays local-only. The decision before it, still in force: **a CLI command acts as the environment's identity and is authorized by the local auth plugin** (issue #318). Who: `cli_user` from factory.config.json when set (now optional), else `local:<git user.email>` (in the repo, lowercased), else `local:<OS user name>`, else `local:anonymous` (`cliIdentity` in src/core/local-cli.ts; `cliEnvironment` in src/cli/support.ts reads git and the OS; git's `user.name` is skipped as a display name).
