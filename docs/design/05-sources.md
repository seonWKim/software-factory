# 5. Coordination: intake sources and pull requests

- **Local startup.** The decision that changed: **the factory starts, builds, reviews and merges with no GitHub plugin selected** (2026-11-07). One rule, by plugin selection and never by whether the repo has a remote: config selects no GitHub plugin when no source is `github-issues`, neither `auth` origin is `github`, the broker is not `github`, no forge is selected and `permissions.grants` has no `github-permission` (`selectsGitHub` in src/compose.ts, which sets `local_only` in the loaded config). Then:
  - **Startup.** No GitHub credential is read (the `github_auth` plugin is not built; plugins get a GitHub client and credentials that refuse every call) and no repository lookup is made. The project key is `local:local:<first 32 hex of the SHA-256 of owner/name>`, labelled `local/<owner>/<name>`, stored as #350's key of the configured repo, so the CLI and the next start read it. No forge ID: a rename starts a new project. Switching a store back to GitHub keeps the stored local key until GitHub's background read stores the GitHub key for the next start (the existing "another repository ID" warning).
  - **Base and fetches.** Nothing fetches origin: the sandbox's trusted base is the factory repo's local `refs/heads/<base_branch>`, a run folder's `refs/remotes/origin/*` are the factory repo's local branches (so the worker's `origin/<base>` and `origin/<branch>` read them unchanged), the worker's base fetch copies the local branch, and the git-worktree updater builds the local base branch with no fetch and no fast-forward of the main checkout.
  - **Broker.** The `local` ToolBroker (docs/plugins/tool-broker.md) commits a run's branch to the local branch `refs/heads/factory/<id>` of the factory repo, never to a remote, behind the same lease, prefix, trusted-git and egress checks as the GitHub broker (one helper, `src/impl/broker/trusted-git.ts`). It has no PR, preflight or comment tool, so the worker skips the PR open, the preflight's forge checks and PR comments, and the implement outcome has no `pr_number`.
  - **A local item's gate comments with GitHub selected.** The decision that changed: **a local item makes no forge comment, also when the GitHub broker is selected** (2026-11-08, issue #421; local first). Its merge-conflict, failed-checks, checks-env and scope-violation messages stay in its item thread; only an item of the GitHub source posts them on its issue. The issue number comes from one helper, `issueNumber` in src/core/change-ref.ts: the `<digits>` of an `owner/repo#<digits>` source id, null for a local item and for any other id (core names no forge, so it reads the id's shape, not the `github_issue` type). The worker's one comment helper (`forgeComment`) makes no broker call for a null number and succeeds, so the run fails with its own gate code; a review or update with no PR is the same. The broker's `github.comment` checks its `number` (agent-supplied args reach it) and refuses a value that is not a positive integer with `invalid_args`, making no request. Solo default: a local item never calls GitHub for a comment. Enterprise setting: a GitHub item keeps its comments, markers and bodies unchanged. Not built: the rest of a local item with GitHub selected (preflight, push, PR open, checks) stays with #333.
  - **Review and gate.** The item enters `REVIEW` with no `pr_number`; the review reads the local branch's diff against the local base, and a pass reaches `merge_pending` the same way a PR does (no PR, so no checks to wait for). Its message names `factory merge <id>`.
  - **Merge.** `factory merge <id>` stores a `merge` command in the command inbox; the controller's one local merge function (`Controller.mergeLocal`; #333 and #246 call it, no second path) authorizes it through the local auth plugin for `approve_merge` (the approver role; a requester's refusal names `factory users add`), refuses an item not waiting for a merge, and merges through the sandbox the controller already holds, as the merge check does, so core runs no git. The sandbox writes the merge commit with `git merge-tree` and `git commit-tree` (objects only, no checkout, no index, no hook) and moves `refs/heads/<base>` conditionally on the base it merged, with no push. A conflict moves nothing, leaves the item in `merge_pending` and replies with the conflicting files; a base branch checked out in any worktree is refused, since moving it would change that checkout. A merge closes the item (`completed`, `merge_sha`, the approver as actor, reason `local_merged`) and releases the items waiting on it; a repeat finds the branch merged and moves nothing. Never automatic: `auto_merge_max_tier` stays 0.
  - Solo default: `plugins.source: ["local"]`, `plugins.broker: "local"`, `"auth": "local"`, `permissions.grants: ["static"]`. Enterprise setting: the GitHub source, GitHub auth and the GitHub broker, unchanged, with no local broker. No new table, column or state. Not built (follow-ups): degraded mode and forge state, the outbox for GitHub writes and CLI mirror comments, the `factory status` line for GitHub; `factory session` with the local broker; local items while GitHub is selected (#333).
- **The local store is the home of the conversation.** The decision that changed: **GitHub comments and commands are written to the store, and the controller applies GitHub commands from the command inbox** (2026-11-07, issue #284). Before, each new GitHub comment was an event the controller handled at once, and nothing in the store recorded a GitHub conversation. Now the `github-issues` poll writes, through the existing store methods (no migration, no schema change): each new command once to the command inbox (`command_inbox`), key `github:<comment id>`, actor `github:<numeric user id>` (never the login), `command` the word after `/`, `args.text` the text after it, `args.source` the issue (or PR) it was written on; and each new comment by a person on an issue (command or plain) once to its work item's thread (`item_thread`), marker `github:<comment id>`, body the comment, with no outbox row (it is already on GitHub). A command on a PR's conversation (`/revise`, `/resolve`, `/verdict`) carries in `args.pr` the PR number and head branch the poll already read, and its thread entry goes to that PR's item (a factory PR by its branch, an adopted one by its source), so applying it reads nothing more from GitHub; one the poll drops today (a `/revise` on a PR that is gone, a `/resolve` or `/verdict` on a PR that is not the factory's) writes nothing. Plain comments on a PR's conversation stay unwritten. One poll's comments are written in comment-id order, whatever order GitHub lists them in, so the command step applies them in the order they were written. Dedupe is the store's: a repeat poll, a second replica polling from an older cursor, or a restart writes no second row or entry (both are idempotent on the key). The poll cursor `intake:github_issue` keeps its format, and its `last_comment_id` still decides what is new, so a controller on this code started with a cursor the old code wrote applies no command at or below it (no backfill). The command step reads these rows with the CLI's (the one inbox, by `seq`): the reader (`src/core/command-inbox.ts`) gives provider `github`, subject the numeric id, only to a row with key `github:<digits>` and actor `github:<digits>` (rows written from the CLI or the UI keep provider `local`), rebuilds the comment through the one comment event mapping (`src/core/comment-event.ts`, so GitHub has no parser copy of its own) with the PR context added, and `comment_id` is the GitHub comment id, so the 👀 and refusal replies are keyed as before. The GitHub auth provider and today's grants judge it, never the local auth plugin. A GitHub row is applied only by a process with an adapter of its source type, and a failure is logged and passed like a polled event's, so a GitHub outage never holds the local commands after it. Plain comments are still also returned as events (`/link`, suggestions); they change no state. Pushed events (`pr_open`, `pr_merged`, `pr_closed`, `pr_unmergeable`, `pr_changes_requested`, `source_closed`, `base_commit`) and new-issue intake stay on the poll path. Factory messages still reach GitHub only through the outbox (Thread first, below); the 👀 reaction and the status labels stay direct calls (moving them into the outbox is a follow-up). Without a store the source returns each command as the event its row maps to. Solo default: no GitHub source listed, nothing here runs. Enterprise setting: `github-issues` next to `local` on a shared store, each comment written once, each command applied once by any replica, with no in-process state. Not built: backfilling older comments; a thread entry for a comment read in the same poll that takes in its issue (the item does not exist yet; its command is still written and applied); a replica without the `github-issues` adapter passes GitHub rows (the cursor is shared), so in a mixed deployment every replica that runs the command step should list it; Slack and Jira comments.
- **PRs through the forge.** The decision that changed: **every PR event, PR fact, PR comment and PR status goes through the forge, never through a source** (2026-11-07, issue #273, phase 2 of #172). `Forge.poll(cursor)` returns the PR events (`pr_merged`, `pr_closed`, `pr_open`, `pr_unmergeable`, `pr_changes_requested`; they left `SourceEvent`) and the next cursor, kept under `forge:<ref type>` in the existing cursor table (no schema change, no migration). The controller polls it on the poll interval under its own guard, so a forge failure never stops a source's intake. Order within a tick: every poll source is read, then the forge is polled, then the forge's events are handled, then the sources' events: a merge that closed its issue happened before the close, so the forge's read already sees it and the merge (with its `merge_sha`) is applied before the issue's `source_closed`. The forge also answers `prChecks`, `prFiles`, `labelAddedBy`, `commitAuthor` and `closePr`, and writes `postPrComment` and `setPrStatus`: a PR comment is a thread entry whose outbox row targets the forge's PR ref, and the outbox step posts it through the forge whatever source the item came from; PR status goes to `setPrStatus`. With no forge, a PR comment or status goes to the item's own source, and no PR is read. The controller names no source type: `PR_SOURCE_TYPE` is gone, startup accepts any set of sources with no two of one type (one non-GitHub source alone, or several with none of type `github_issue`), and a refused intake stays silent when the source sets `silent_intake_refusal` (GitHub; chat sources reply). Which forge: `plugins.forge` left out follows the sources, `github` when `plugins.source` lists `github-issues`, else none (derived, not a setting); `"none"` next to `github-issues` fails startup, naming `plugins.forge`; an unknown name fails naming it too. Solo default: a local source alone, no forge, no GitHub call. Enterprise: `github-issues` with the `github` forge, by the same rule. With both GitHub plugins, the source reads issues, comments, closed issues and base commits and the forge every pull list and per-PR read: one tick makes the same GitHub calls as when the source read PRs itself, each once (no list is read twice, so nothing needs handing from one to the other). Upgrade: the forge's cursor starts empty; while it is, the forge's first cursor is the GitHub source's old one (`intake:github_issue`, whose PR fields have the same names), so no merge is missed and none applied twice (a boundary PR may repeat; handling is idempotent); a fresh install starts empty and reads one page of closed PRs. Details: [docs/plugins/forge.md](../plugins/forge.md). Not built: webhooks, a forge other than GitHub, adopted PRs with a forge but no `github-issues`: an adopted item's source is its PR, of type `github_issue`, so with no adapter of that type the controller makes no transition on it (No adapter, no transition).
- **Thread first, then the outbox.** The decision that changed: **every factory message is written to the item thread before any source is called, and only the outbox step posts it** (2026-11-07, issue #282). The controller's one message helper writes the message to `item_thread` (one per item and marker), and for an item whose source is not `local` it adds, in the same transaction, one `thread_outbox` row (SQLite migration 29, MySQL step `0029-thread-outbox.sql`): the source type, the target, the item field the URL fills (`spec_comment_url` or `failure_comment_url`), the attempts and the next try. An entry goes only to its item's own source: a PR comment (the PR is a target of the same type) goes to the PR, and for a non-GitHub item it goes to the item's own source instead. The outbox step runs last in every tick (and after each public tick step): it lists pending rows of the source types this process has adapters for, claims each one for `lease_ms` with a conditional update (a token only a claim bumps), calls that adapter's `postComment` (the only call of it, apart from a `/link` reply on an issue that is no work item, which has no thread), and marks the row delivered under the claim; a marker the store already has a posted record of (GitHub sync records below) is marked delivered with its stored URL and no call, a changed body only logged. So each entry is posted once, also when two replicas run the step at once. A failed post counts an attempt, keeps the error, releases the claim and waits `retry_base_ms` doubling per attempt up to `retry_max_ms`; it never touches the item's stage, blocked fields or version, and a failed post no longer stops the transition that wrote it. The URL of a delivered comment fills the item's link field when no newer entry names the same field (no version change, no state change); the transition itself stores the link only when the entry was already delivered (a re-decide), so links appear once the outbox delivers. Entries of a source type with no adapter here stay pending for a process that has one. `local` items need no adapter: the thread is their surface, so they get no outbox rows and their transitions run in any process. The controller reads CLI and app commands from the command inbox itself (design 04-gate-commands, "Commands from the command inbox"), so `plugins.source` may be an empty list: the factory then runs on the store alone, with local items. A local-only setup is still `"source": ["local"]`; GitHub (`github-issues`) is the sync plugin. Solo default: no source, only the local command inbox and item thread (no outbox rows, no external call). Enterprise setting: linked sources on a shared store, each outbox row claimed by the conditional update above, so one replica posts it. This outbox is the one queue for every source write: later work (degraded mode, the sync lease, CLI mirror comments) adds to it, not a second queue. The comment-to-event mapping has one copy, in core (`src/core/comment-event.ts`): the command inbox reader and the Slack source import it; the `src/impl/source` copy is gone. Not built: retiring `app_command_requests`, a Slack adapter, webhook endpoints.
- **GitHub sync records.** The decision that changed: **what the GitHub source posted and labelled is recorded in the store, shared by every replica** (2026-11-07, after every controller start re-read the labels of up to 1,000 open items and every post re-read its issue's thread). SQLite migration 27 and MySQL step `0027` add two tables, keyed by the item's source id:
  - **Posted comments** (`posted_comments`: source id, marker, comment ID, URL, body hash, failed attempts, next attempt time). `postComment` looks up the record first: a known marker returns its stored URL with no call. Only a marker the store does not know reads the thread, once (up to 10 pages, for a post from before this change), posts if the marker is not there, and stores the comment ID, URL and a SHA-256 of the body. A repeat post with a different body is not edited: the controller logs the warning `comment already posted with another body; not edited` and returns the stored URL (editing in place would be a follow-up).
  - **Comment backoff.** A failed post is counted on its row (conditional on the stored count, so two replicas count one failure once), and the next try waits 1 s, then 2 s, 4 s, doubling, at most 5 min; until then `postComment` throws without a call, on any replica, so the caller's retry on the next 2 s tick costs nothing. A post that goes through clears the count. It lives in the GitHub source, not the controller's generic post path, so other sources (the local one) keep retrying on the next tick as before and write nothing here.
  - **Label state** (`label_states`: source id, target `issue` or `pr:<n>`, the status last written, and the claim of a write in progress). Kept per target, so a current issue label does not hide a stale PR label. `setStatus` compares with the stored state first: the same status makes no call. A different one (or none stored, an item from before this change) is claimed in the store for 60 s, written through the existing read-then-write path, stored, and the claim ended; a failed write ends the claim and stores nothing. A claim another replica holds for the same status makes the call a no-op, so two controllers starting at once write each label once. The start-up status catch-up reads every open item's label states in one batched store read and skips targets already showing their status, so a restart with unchanged labels makes no label call. A label a person removed is not put back on restart (restoring it would be a follow-up).
  - Solo default: with no GitHub source nothing writes these tables and nothing waits on GitHub. Enterprise: the rows are shared through the store, so a second replica or a restarted controller continues the same records and backoff schedule. The forge's own `GitHubIssueSource` (no store) keeps the old behaviour. Agent-side comments through the GitHub tool broker keep their own `commentOnce` path.
- **GitHub call budget.** The decision that changed: **GitHub reads are conditional and budgeted** (2026-11-07, after the App installation hit its hourly limit). GitHub is a sync plugin; the factory keeps working in local mode without it, and when it is on it spends as few calls as it can:
  - **Conditional GETs.** The shared `GitHubClient` keeps the last ETag and body of each GET URL (per Accept header) in a bounded in-memory LRU (500 entries, bodies up to 1 MB), sends `If-None-Match`, and answers a 304 (not counted by GitHub) with the kept body. This is in-process state on purpose, and the one exception to "no in-process state": it is only an optimization. GitHub decides on every call whether the body is current, so a replica with an empty cache (a new process, another machine) gets the same answers, it just pays full calls. Writes are never conditional.
  - **Rate-limit budget.** Every response's `x-ratelimit-limit`, `-remaining` and `-reset` (core resource only) are kept and exposed as `budget()`. With none left before the reset the client refuses a call with the 403 GitHub would give, without sending it, so a retry loop does not hammer the API. Under `github.min_remaining` (default 200) `lowBudget()` is true until the reset and the optional reads wait: the per-PR `mergeable` reads, the "Request changes" review reads and the base-commit read in the poll (their cursors stay put), and `prChecks` (the gate counts as pending). The intake lists (open and closed issues, comments, closed and open PRs) always run. One log line on entering that mode, one on leaving.
  - **Shared budget (decision changed 2026-11-07, issue #340).** Factories on one App installation share one hourly budget, so each process also keeps to its **share**, `github.budget_share` (default 1.0: the whole limit, the solo case). The client counts this process's counted calls (every answer but a 304) in the current window, named by its reset time; once they reach `budget_share` × the limit, `lowBudget()` is true and the optional reads wait as under `min_remaining` (both are checked). A new reset time starts the count at zero. The count is in memory, per process: replicas of one factory on one App split its share; counting in the store is a follow-up only if needed. Enterprise: one App per factory with share 1.0 (recommended), or shares summing to at most 1.0 by a documented agreement, not enforced across factories (`docs/setup.md`).
  - **Budget shared through the store (decision changed 2026-11-08; before: every replica polled GitHub, budget per process; see History).** GitHub's own numbers are one row per project and forge plugin, `forge_budget` (`project_key`, `plugin`, `remaining`, `limit`, `reset_at`, `updated_at`; SQLite migration 40, MySQL step 0040). The client writes it after every response that carries the core limit, and the store keeps a write only when its `updated_at` is newer than the stored one (an older or equal write changes nothing, so replicas writing out of order keep the latest reading). The client reads the row at most once per tick (`refresh_ms` = `tick_ms`): the controller asks for it before each tick's optional reads (`refresh_forge_budget`), and a call that finds the last read older than a tick reads it first. So when one replica's response drops it under `max(github.min_remaining, 10% of the limit)`, every replica's `lowBudget()` is true on its next tick and its optional reads wait until `reset_at`: the poll's base-commit and closed-issue catch-up reads, the status catch-up, check reads (`checksStep`) and dependency reads. The intake lists of the issue poll still run, as before, and outbox delivery and the sync lease never wait on the budget. `github.min_remaining` is the only setting; the 10% share is fixed. The per-process `budget_share` count is unchanged. `src/compose.ts` gives the client the store and the project key once the key is resolved, in every process that calls GitHub (`factory dev`, `factory session`); with no GitHub plugin selected there is no client and no row. Solo default: one process reads back its own writes. Enterprise setting: replicas on one MySQL store share the row; one replica syncs (05-coordination, One GitHub sync per project).
  - **Audit of inbound commands.** A comment from GitHub is kept in its item's thread with `actor` `github:<numeric id>` (`item_thread.actor`, migration 40; absent on the factory's own messages and older entries), never a login. A command's actor is the factory user its account is linked to (`src/core/authorize.ts`, links first); an account that no link and no grant names is refused through the same permission path, its comment stays in the thread under `github:<numeric id>`, and no state changes. No audit table of its own.
  - **First-start spread.** A first start's catch-up reads (each closed factory issue's full read while the source has no closed cursor, the base-commit pages while it has no commit cursor) take `GitHubClient.takeCatchUp`: at most (`budget_share` × limit) / 60 a minute, derived, no setting. When the allowance is used, the closed cursor stops at the last issue read and is marked `closed_catch_up` until the backlog is read, so it is spread over several polls; the commit cursor stays empty and the next poll reads the commits.
  - **No calls left is a wait.** A call refused locally with no calls left carries the reset as `wait_until`. The controller's loop logs `waiting for the GitHub rate-limit reset` (warn, with the step and the time), not `loop step failed`; the step runs again next poll and every other step, local work included, goes on. After each poll the controller holding the sync lease stores its process's budget (limit, remaining, reset, share, counted calls, state `ok` / `low` / `waiting`, replica id) in the cursor `github:budget`, and the status page reads it from there (design §9). No claim pause is set: the `github_rate_limit` claim pause, once it exists, is the one pause for GitHub-bound work.
  - **Fewer reads per poll.** The closed-PR list stops at the first page that reaches the cursor instead of reading up to 5 pages every poll. `setStatus` reads the labels first and writes nothing when they are already right instead of always creating the label, adding it and reading the list; with a store it first compares the stored label state (GitHub sync records above).
  - Not here: a draining child stopping its controller (issue #294). Dependency re-reads in `coordinationStep` (issue #254) are now bounded in 05-coordination.md, "Dependency reads only when the source changed".
- **CLI intake.** The decision that changed: **`factory approve|retry|revise|reject` work for an item of any source, and a command on a GitHub item is mirrored to its issue, best effort** (2026-11-08; the owner's answer of 2026-11-07: local auth decides). The CLI stores the command for any item it finds (the old refusal "is not a local work item: reply on its issue instead" is gone) and still makes no GitHub call. The controller applies it from the command inbox through the same transition the same GitHub comment gives, with the CLI identity as actor, judged by the local auth plugin: a local approver needs no GitHub write access, and the transition never waits on GitHub (labels, 👀 and replies stay best effort; a CLI command has no comment to react to, so it gets no 👀). The mirror: a command on an item of a sync source is stored with `mirror` (`command_inbox.mirror` = 1, SQLite migration 37, MySQL step `migrations/mysql/0037-command-mirror.sql`); the controller's mirror step writes it once to the item's thread under marker `<!-- factory:cli:<command_key> -->`, so the outbox posts one comment on the issue with its retries and backoff, and marks the command mirrored (`mirrored_at`, `markCliCommandMirrored`) only once that post was delivered. A failed or rate-limited post leaves it unmirrored for a later tick. The mirror text names the command in backticks and quotes the note (left out when the egress scan flags it), so it never starts with `/` and the GitHub poll reads it as a plain comment. Solo: nothing to configure, the environment user is the owner on the first command. Enterprise: an `approver` from `factory users add` may approve GitHub items too, a `requester` may not. `task list` stays local-only. The decision before it, still in force: **a CLI command acts as the environment's identity and is authorized by the local auth plugin** (issue #318). Who: `cli_user` from factory.config.json when set (now optional), else `local:<git user.email>` (in the repo, lowercased), else `local:<OS user name>`, else `local:anonymous` (`cliIdentity` in src/core/local-cli.ts; main.ts reads git and the OS; git's `user.name` is skipped as a display name). The local UI acts as the same identity. No command fails for lack of `cli_user`. Who may: the auth plugin for origin `local` (default `local`, whatever `auth` selects for GitHub; [08-permissions.md](08-permissions.md), "Local commands are authorized locally"): the first identity to run a writing command becomes the local owner, the owner grants `approver` or `requester` with `factory users add`, and `anonymous` reads and creates only. `factory task create --title <t> --body-file <f>` creates one local work item in the store (source type `local`, id `local-<random>`, requester = the CLI identity) with its triage run queued, in one `createWorkItem`, and prints its ID; the project key comes from the store (`storeProjectResolver`), and it fails while no project is stored. `factory task list` and `factory task show <id>` only read (state, spec, runs, item messages). `factory approve|retry|revise|reject <id> [text]` append one row to the CLI command log (`command_inbox`: random key, actor = the CLI identity, `args.item`, optional `args.text`) and change no item state; the controller reads it from the command inbox (since issue #282; before, through the `local` source) and applies it like the same GitHub comment, with the same `authorize` check through the local auth plugin (identity provider `local`, subject the actor after `local:`) and the same replies, stored as item messages; a role refusal names the `factory users add` command. The CLI itself makes no GitHub call; the mirror goes through the outbox. The command table in src/core/local-cli.ts builds the usage text, one `/help` line and the SET_UP.md list (a test compares them). Not built: `factory link` (an optional GitHub link for audit), `verdict`, `budget`, `resolve` from the CLI, a dashboard view.
- **Local intake.** The decision that changed: **local intake and item messages live in the store.** Until issue #282 the `local` poll source read the CLI command log (`command_inbox`) by `seq`, at most 100 per poll, cursor = last `seq` read (`intake:local`); the controller now does that itself (cursor `commands`, starting from `intake:local`), and turns each command for a local item (`args.item` = work item ID, optional `args.text`) into the event the same comment gives on GitHub, by rebuilding `/<command> <text>` and parsing it with the same comment parser; `comment_id` is the command key, the identity is provider `local`, subject the actor after `local:`. CLI commands for missing items are skipped and the cursor passes them; a non-local item's command is applied too, see CLI intake (GitHub rows: see The local store is the home of the conversation). Its replies are item thread entries (`item_thread`, one per marker), written by the controller; `markSeen`, `setStatus` and `closeIssue` are no-ops because the store already holds the item's state. Source plugins get the store in their context for this. Writing commands, creating local items and who may send them: see CLI intake above. Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Item thread and command inbox.** The decision that changed: **an item's messages and the CLI commands live in two general tables** (issue #281). The store keeps every item's messages in `item_thread` (one per item and marker) and the commands in `command_inbox` (read by `seq`, `command_key` the idempotency key). SQLite migration 24 and MySQL step `0024` create both and copy the rows of migration 21's message and command tables with their `seq`, so a saved `intake:local` cursor still points at the same next command; the copy skips rows already copied, so it is safe to run again. The old tables stay in place, and nothing reads or writes them. Store method names, arguments and results are unchanged. GitHub items write their comments and commands there too since issue #284 (The local store is the home of the conversation, above).
- **Stream intake.** `SourceAdapter` is now a union on `intake`: `"poll"` sources keep `poll(cursor)` (GitHub, unchanged); `"stream"` sources have `subscribe(signal)` yielding `PushedEvent`s (event, `dedupe_key` unique within the source, `ack()`). A pushed event is written to a store inbox (`source_inbox`, migration 10) before it is acked, and a duplicate `dedupe_key` is a no-op that is still acked; a failed write is not acked. Controllers read the inbox through the cursor `inbox:<source type>` and the same `handleEvent` as polled events, so any replica handles them. One listener per stream source across replicas, decided by a store lease (`listener_leases`, migration 10: owner, token, expiry; conditional updates only; the inbox write checks the token in its transaction). It reuses `lease_ms` / `heartbeat_ms`, runs inside the controller process (started by `Controller.run`), reconnects with backoff and logs on state changes only. Cleanup on the poll interval deletes rows older than `inbox_retention_days` (optional, default 14) that are at or below the cursor; no cursor, no deletion. What it changes: a new intake path and two tables; GitHub intake, `SourceType` and the registry are unchanged (the only stream source is the test-only `fake-stream`). Not built: webhook endpoints. The Slack plugin: see Slack intake and source routing. Details: architecture §4 Intake.
- **Several sources.** The decision that changed: **one source becomes a list of sources.** `plugins.source` takes a string (unchanged: a list of one, the same selection as before) or a list of registered names; an unknown name or the same name twice fails at startup naming `plugins.source` (an empty list is allowed since 2026-11-07: see Thread first). `build()` makes one adapter per name and hands them all to the controller, which refuses at startup two adapters of one source type (since issue #273 any other set is accepted: PRs come from the forge, see PRs through the forge). Routing: each item's `postComment`, `markSeen`, `setStatus` and `closeIssue` go to the adapter whose `type` matches the item's `source.type`; status and comments on a PR go to the forge. An item whose source type has no configured adapter keeps its state: the controller makes no transition on it (changed 2026-11-07; `local` items excepted since issue #282, the store being their surface), and its outbox entries stay pending, so a finished run of it stays unacknowledged for a process that has the adapter, such as the new version next to an older one still draining with an older `plugins.source`; its calls outside a transition log a warning and are skipped. Intake: every poll source has its own cursor `intake:<type>` and every stream source its own listener (the lease was already per type) and inbox cursor; each source's step runs under its own guard, so one source failing does not stop the others in the same tick. Commands from any source go through the same command table, the same `AuthProvider` check and the same replies; resolving non-GitHub identities is left to the provider work (#107, #109). Not built: new `SourceType` values. The Slack adapter: see Slack intake and source routing. Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Slack intake and source routing.** The decision that changed (2026-11-01 decision, built 2026-11-07, issue #109): **Slack threads are a real-time source**, the `slack` stream plugin, next to GitHub through the existing per-type routing. A mention of the bot (`app_mention`) in a channel listed in the `slack` block of factory.config.json (`channels`: channel IDs, checked at load; an unknown key, a name instead of an ID, or a missing block while selected fails startup) starts one work item from its thread, source id `slack:<team>:<channel>:<thread ts>`; `createWorkItem` is idempotent on it, so the `message` + `app_mention` pair Slack sends for one mention, and any redelivery, is one item. Only `app_mention` starts or commands with a mention; a thread reply without one is a command or a plain comment for an item thread; top-level messages without a mention, the bot's own messages, other bots and `subtype` events are ignored. Inbox dedupe is on Slack's `event_id` (a button press: team, user, `action_ts`). People are Slack user IDs (provider `slack`), linked to factory users with `/link`; an unlinked account's command is refused with one reply, and an unlinked mention gets one reply instead of the silence a GitHub issue gets (the label is GitHub's gate; Slack has none). Replies: the controller's comments, converted to mrkdwn, with a button for each footer command that takes no text (`approve`, `retry`, `resolve`, `budget`, `help`; reject, revise, verdict stay typed) and Confirm/Cancel under a suggestion; a press is the typed command by the presser, through the same `authorize`. Each post carries its marker's hash in Slack message metadata and the thread is read first, so a marker is posted once. Everything posted is egress-scanned in the plugin; a blocked message is replaced, under the same marker, by one notice naming the rules, and is never retried in any form. Status is one thread message edited in place, with the PR link once there is one. No Slack SDK (spec decision 5 changed): the listener already owns reconnects and the ack-after-store rule, so the plugin uses Node's WebSocket and the Web API over `fetch`, with no new dependency. `SUGGEST_MIN_CONFIDENCE` is 0.85 (was 0.7). Not built: DMs, reactions (no `reactions:write` scope, so `markSeen` does nothing), a channel check against the API (no `channels:read`), Slack token patterns in the egress scanner (the known-value check covers the configured tokens). Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Pull requests a person opens, and a person's pushes.** Now every change to the repository passes through the controller:
  - **Adoption.** The forge (`github`) reports `pr_open` on every poll for each open PR against the base branch from this repository: every factory-branch PR, and every other PR that is not a draft (a draft is adopted on a later poll, once it is ready). A PR the store does not know (not a factory branch, no item with that PR as its source) is adopted: one item, origin `adopted`, source = the PR (`owner/repo#N`, link `/pull/N`; comments and the status label go on the PR, labelled once), title = PR title, problem = title and body, requester = the author's user ID, `done_criteria` null, `allowed_paths` = the files the PR changes (`prFiles`, both sides of a rename, read only for a PR the store does not know), tier = the floor tier of those files, stage `REVIEW` with `pr_number` and `head_branch` set, and one review run, all in one `createWorkItem` (idempotent on the source; state change `pr_adopted`). An author that does not resolve to a user is not adopted (its merge is then an unreviewed merge). Forks are not adopted.
  - **Review of an adopted PR.** The worker checks out the item's `head_branch` (it fails if `origin/<branch>` is missing) and the prompt has the PR's title and body (untrusted), its files and the diff, and says there is no spec. The review comment goes on the PR as for factory PRs. The review sets the tier (max of judgment, floor, previous). A pass goes through the same CI gate to `merge_pending`, and auto-merge stays at 0, so a human still merges. The factory never pushes to a person's branch: bugs block on a human with `changes_requested`, failed checks with `checks_failed` (both `blocked_on: human`; no implement run). `/verdict` and `/resolve` still map PRs by factory branch only.
  - **`factory: skip`.** A PR with this label, added (latest `labeled` event in the issue timeline) by a user with the existing `approve_spec` permission, gets no item. A label added by anyone else is ignored with a warning, and the PR is adopted. It is checked at adoption only: on an adopted PR the label does nothing.
  - **Merges.** Every merged or closed PR is reported now, not only factory ones. A factory branch maps to its item as before; any other PR to its adopted item by number; a merge closes it as `CLOSED` / `completed` with `merge_sha`, the merger as actor (approver of record), and a close without merge as `rejected`. A merged PR with no item (skipped, a fork, never adopted, or merged after the first start but before the poll that would have adopted it) writes one `unreviewed_merges` row (project, PR number, merge sha, merger's user ID or null; idempotent on project and PR number) and a warning. **First start (decision changed 2026-11-07, issue #341):** the first poll stores a starting point in the forge's JSON cursor (the GitHub source's until issue #273) (`start`, from the Clock in GitHub's UTC format; no new table, written through the store's conditional cursor update so replicas agree), even with no closed PR. A PR merged before it gets no merger read and no event, so a factory started on an old repository flags no past merge and reads only the closed-PR list. Upgrade: a cursor from before this keeps its place (its closed-PR time becomes the start), so a running install reads no history. `github.history_since` checks older merges on purpose: older than the start, it moves the start back once (that poll reads at most 5 pages of closed PRs, one GET per merged PR; the cursor records the value so a restart does not repeat it); a newer value is ignored with one warning naming the setting. Solo and enterprise follow the same rule. Paging history across polls is not built.
  - **A person's push.** Every run that pushes (implement, update, resolve) records the head it pushed as the item's `last_head_sha`, under its lease (`recordPushedHead`); adoption records the PR's head. On each poll the controller compares an open factory or adopted PR's head with it. A different head is a person's push: one run of kind `manual`, written already `succeeded` and acknowledged (never queued, so no worker claims it and the controller applies nothing), with `actor`, `from_sha`, `to_sha` and `pr_number` in its outcome, and `last_head_sha` moved to the new head, in one transaction (`recordPrHead`, conditional on the old head, so a repeat writes nothing). It changes no stage, blocked field or version, and nothing is re-queued or re-reviewed: a later review covers it. GitHub does not name who pushed, so the actor is the author of the head commit resolved through auth; if that does not resolve, `system:pr-sync` and a warning. While any run of the item is running, the head is not looked at (that run may be pushing); an item with no recorded head (from before this) only takes the current head as a baseline.
  - **Schema:** migration 12 adds `work_items.origin` (`factory` default), `head_branch`, `last_head_sha` (all store-owned, not in `WorkItemPatch`) and the `unreviewed_merges` table. SQLite builds it on open; MySQL gets it from the step file `migrations/mysql/0012-adopted-prs.sql` through `npm run migrate` (the table has a `seq` column like every MySQL table, which the store orders ties by). A MySQL store refuses to start until that step is applied.
  - Not built: re-review after a person's push, adopting a PR again after it reopens with a new number, showing unreviewed merges in stats. The Health section and the Floor line of the app show them (see `09-dashboard-app.md`).

## History

- **GitHub call budget: shared through the store** (decision changed 2026-11-08). Before: every replica polled GitHub, budget per process: each GitHub client kept GitHub's rate limit from its own responses only, in memory, so a replica that had made no call yet did not know another one had used the budget, and its optional reads went on.
- **A local item's gate comments with GitHub selected** (decision changed 2026-11-08, issue #421). Before: the worker took the issue number as `Number(source id after "#")`, so with the GitHub broker selected a local item's merge-conflict, failed-checks, checks-env and scope-violation comments were sent to `issues/NaN/comments`, the checks-env one through a direct broker call, and a review or update comment with no PR was sent with a null number.
- **Local startup** (decision changed 2026-11-07). Before: every start needed GitHub: build() read the GitHub credentials and made a GitHub client for every config, a first start resolved the project key through GitHub, the only broker pushed to GitHub and opened PRs, and the sandbox and the updater fetched origin and read the base from `origin/<base>`, so a local task had no path to a merge.
- **CLI intake** (decision changed 2026-11-08). Before: the CLI refused `approve|retry|revise|reject` for any non-local item ("is not a local work item: reply `/<command>` on its issue instead") and the controller skipped CLI commands for non-local items, so a local approver could act on a GitHub item only through a GitHub account with write access.
- **GitHub issues are the home of the conversation** (decision changed 2026-11-07, issue #284). Before: the GitHub source turned each new comment into an event the controller handled at once; nothing wrote a GitHub comment to the item thread or the command inbox, the inbox reader built only local identities and skipped every item that was not local, and dedupe relied only on the poll cursor's `last_comment_id`.
- **PRs through the forge** (decision changed 2026-11-07, issue #273). Before: the `github-issues` source read every PR event and PR fact, the controller sent PR comments and PR status to whichever adapter had the `github_issue` type (`PR_SOURCE_TYPE`), refused several sources without one at startup, and kept a refused intake silent by checking that type; the forge plugin was loaded but never called.
- **First start of the GitHub source** (decision changed 2026-11-07, issue #341). Before: a fresh install's first poll read one page of closed PRs and the merger of each merged one, so every past merge there was recorded as an unreviewed merge with a warning.
- **Thread first, then the outbox** (decision changed 2026-11-07, issue #282). Before: the controller posted each message through a helper that called the source adapter directly, so nothing in the store recorded what reached a GitHub item's source, a failed post made the whole transition retry, CLI commands were read only through the `local` source, and an empty `plugins.source` failed at startup.
- **Stream intake** (new decision, 2026-11-01). Before: every source was polled on a timer, so a source that pushes events, like Slack Socket Mode, had to be forced into polling.
- **Several sources** (decision changed 2026-11-01). Before: `plugins.source` named one plugin and the controller sent every comment, 👀, status and close through that one adapter, so a second source such as Slack could not run next to GitHub, and its items would have been answered through GitHub.
- **Pull requests a person opens, and a person's pushes** (decision changed 2026-11-01, issue #113). Before: only factory PRs were tracked: the GitHub source read pull requests on factory branches only, so a PR a person opened could merge with no review run, no scope or size check and no record, and a push a person made to a factory branch was invisible to the factory.
- **Local intake** (decision changed 2026-11-07, issue #199). Before: polled intake was GitHub only, nothing read the CLI command log and nothing stored item messages; now local intake and item messages live in the store, through the `local` source.
- **CLI intake** (decision changed 2026-11-07, issue #318). Before: every CLI command acted as `cli_user` and failed without it, and the one global `auth` plugin judged it: with `auth: github` the local account resolved only through a link no command created, so CLI commands were refused as not linked and local items stuck at spec approval.
- **CLI intake** (decision changed 2026-11-07, issue #200). Before: the `local` source could read the CLI command log, but nothing wrote to it and nothing created a local work item, so human commands from the CLI had no entry point and the local flow was untested end to end.
- **Item thread and command inbox** (decision changed 2026-11-07, issue #281). Before: local item messages and CLI commands lived in two tables from migration 21 named for the local source only, so the store had no single place for an item's conversation.
- **GitHub call budget: shared budget** (decision changed 2026-11-07, issue #340). Before: the client stopped optional reads only under `min_remaining`, so one factory could use most of a limit other factories on the same App draw from; a first start read every closed item and 500 base commits in one poll; and a call refused at 0 remaining was logged as a failed loop step.
- **GitHub call budget** (decision changed 2026-11-07). Before: every GitHub GET was a full call counted against the hourly limit, even when nothing had changed; the closed-PR list read every page up to 5 on each poll; `setStatus` made at least three calls each time; and nothing read the rate-limit headers, so a retry loop kept calling after the limit was spent.
- **No adapter, no transition** (decision changed 2026-11-07). Before: a controller without the item's source adapter still applied the item's transitions and only skipped the calls, so an older process draining after `local` was added to `plugins.source` applied local items' triage and dropped their spec comments and replies.
- **GitHub sync records** (decision changed 2026-11-07). Before: nothing about posts or labels was stored: every controller start re-applied the status of up to 1,000 open items, each a label read that the in-process ETag cache could not save after a restart; every post listed the issue's whole thread (up to 10 pages) to find its marker, repeats included; and a failed post was called again on every 2 s tick, with no stored attempt count.
- **Slack intake and source routing** (decision changed 2026-11-01, built 2026-11-07, issue #109). Before: no source used stream intake, so a request in Slack had to be copied into a GitHub issue by hand; the routing by source type existed but only test sources used it.
