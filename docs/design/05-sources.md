# 5. Coordination: intake sources and pull requests

- **Slack spec messages: short, with decision buttons** (decision changed 2026-11-12; current; replaces "a spec is posted whole to Slack, after a separate `Status: needs approval` message", see History). The decision that changed: **in Slack, a spec waiting for approval is one short message whose decisions are answered with buttons.** The Slack source reads the spec comment by its headings (`## Factory spec`, `### In short (AS-IS → TO-BE)`, `### Decisions for you`, whose lines carry their `Proposed default:`) and posts: "Needs your approval: <item title>" (the title from the store), In short (at most 3 lines), Decisions (one line each with its proposed default), and a Full spec link to `<base>/app/items/<id>`, the base `slack.dashboard_url` when set, else the local dashboard `http://127.0.0.1:<ui.port>` (only the owner's machine opens it). Problem, Applied defaults, Done when and the rest stay in the store and on the dashboard. Buttons: Approve with defaults, Other… (when there is a decision: a modal with one field per decision, up to Slack's 99, prefilled with its default; its submit stores one `/approve` with an `N: <answer>` line per non-blank field) and Reject… (a modal with one reason field; its submit stores one `/reject <reason>`). Presses and submits follow the proposal press rules: the linked user, stored first as the typed command's row (keyed on the press or the view ID), applied through the controller's `AuthProvider` check; an unlinked account gets the one refusal, a spec no longer waiting the stale reply, and neither opens a modal. A modal opens from the press itself, before the ack (a `trigger_id` lasts about 3 seconds), after the egress scan; a failed `views.open` is logged once and not retried. The spec message keeps its buttons after approval (a press then gets the stale reply). No status message is posted just to say a spec needs approval: a thread with no status message yet gets none then, and a later status posts or edits the one message in place. A spec approved with no reply (auto mode) is still posted whole. Why: on a phone, the whole spec was a wall of text with the decisions, the one thing to act on, in its middle; one message per spec now carries the ask and the answers. Core, the controller, the other sources and the spec text are unchanged.
- **Slack: no mention needed in a thread the factory owns** (decision changed 2026-11-12, issue #585; current; replaces "a reply in an item's thread with no mention still needs the slash", from the #541 decision below, see History). The decision that changed: **in a Slack thread that is a work item's (the factory owns it), a person's reply with no mention is read; in any other thread it is not.** In an owned thread a reply with no mention is kept on the item's thread, as before; a command typed with its slash is that command; any other reply, a bare command word included, is a plain comment that the plain-words reader reads (04-gate-commands): it answers once with proposed commands stored as pending, with a button each, Confirm all and Cancel, and changes no state until a press or a typed command. In a thread the factory does not own, a reply with no mention is other people's conversation: not stored, no model call, no reply; a mention there still works. No code change: the Slack source already did this (`fromEventsApi`), and tests/slack-source.test.ts now holds both halves. Why: the line that said a plain reply needs the slash no longer matched the reader, and the owner should not have to mention the bot in their own item's thread. Solo and enterprise are the same: one code path; the reply's author needs `approve_spec`, as before.
- **A Slack top-level mention becomes an item only on a press** (decision changed 2026-11-12; current; replaces "a top-level mention read as a request, or not read, is taken in at once", see History). The Slack source marks the `item_requested` of a top-level mention (one outside any thread) with `classify`; a mention inside a thread that is not an item, and every other source (local CLI, GitHub), are taken in as before. The intake unit answers a classified message in its own thread and never creates an item for it: a chat message gets one answer; a request, an unsure message, and one it does not read (no model, a requester without `approve_spec`, too long, a failed or malformed answer) get a short reply with a **Make this a task** button; an empty one gets `I couldn't read that.` and one the egress scan flags gets one fixed line, both with no button. The button's press is an `item_requested` from the presser, marked `offered` (only the press sets it), keyed on the message's source id: it creates the item, posts one `Task created: <title>` line, and a second press changes nothing (04-gate-commands.md, "A mention creates an item only on a press", has the replies, the egress scan, the reply key and the button). No schema change, no new state; solo and enterprise run the same path on their store.
- **The sources read reactions on the factory's messages** (decision changed 2026-11-11, issue #524; current; replaces "a source reads comments and adds 👀, and reads no reactions", see History). What each reaction means is design 04-gate-commands ("A 👍 or 👎 on a factory message is a verdict"). **GitHub:** GitHub has no batched reaction read, so inside its poll the GitHub source lists the comments the store records as posted on a PR of its repository in the last 7 days (`listPostedComments`: the posted-message record's URL names `/pull/`) and reads each one's reactions with one GET per poll; every GET is conditional, so an unchanged list is a 304 that GitHub does not count. The cursor keeps, per comment still in the window, the highest reaction id delivered, so a reaction is delivered once. Under `lowBudget()` no reaction is read and the marks are kept; with no store there are no records and nothing is read. **Slack:** the app needs `reactions:read` and the `reaction_added` event (slack/manifest.json; an installed app must be reinstalled to get them). A reaction event names the message ts but not its thread, so the source finds the message in the store's posted-message records by its ts (`listPostedCommentsById`), which name the thread; the status message, a message with no record, a thread that is no work item, a channel not configured and a message older than 7 days (message ts against `event_ts`) mean nothing. Without the scope no such event arrives and nothing else changes; GitHub reactions are read whether Slack is on or not. **No schema change:** the two store reads are read-only, on the existing records (`outbound_deliveries`, whose `updated_at` is the post time once a comment is recorded), in the SQL store shared by SQLite and MySQL (`src/impl/store/sql/posted-comments.ts`; the interface is `PostedCommentReads` in `src/core/reaction-verdict.ts`, which `FactoryStore` extends).
- **Slack buttons follow the item's state** (decision changed 2026-11-11, issue #586; current; replaces "a message's buttons are built once from the command footer the controller wrote when it posted the message, and never change", see History). On each status write (one per state change, delivered by outbound) the Slack source also edits each earlier factory message of the item's thread whose footer buttons no longer all apply (`settle` in `src/impl/source/slack-source.ts`): one `chat.update` that keeps only the buttons that still apply, drops the footer's command list and ends with the Done line (`Done: <what happened> by <actor ID> at <time>. The item is now <phase>.`). It reads the store only: the thread entries' bodies give each message's buttons, the posted-message records its ts. Each update is recorded under `slack:done:<ts>:<buttons kept>` in the same posted-message records, so running it again makes no second call, and a later change that drops more buttons edits once more. A message posted before the records, a deleted one, or one the egress scan blocks is left as it is; Slack messages posted before this change are not backfilled. A press of a button that no longer applies gets one reply saying what already happened, with the current buttons (04-gate-commands.md). **Order:** the spec comment of a transition is stored before the transition commits and its status after; one announce lists thread entries before actions, and outbound sends a destination's batches one at a time in intent order, so the status is never posted before that spec is delivered (a failing spec delivery holds it). No schema change, no new state; solo and enterprise run the same path on their store.
- **Where intake runs** (since 2026-11-08, RFC 0015 M4): the polls, cursors, stream relay and command reads below now run in `src/inbound/` and reach the controller over the bus; the order and dedupe rules below are unchanged. See 10-event-driven.md, "Intake runs in inbound, on the bus".

- **Slack commands need no slash after a mention in an item's thread** (decision changed 2026-11-11, issue #541; current; replaces "after a mention, only `approve` works without its slash (issue #528); every other command needs it", see History). Slack takes a message that starts with `/` for its own slash commands, so the factory's commands follow a mention. In an item's thread, a mention whose first word is a command word with no slash is that command, with the same text: `@software-factory revise <feedback>` stores and applies exactly what `@software-factory /revise <feedback>` does, through the same role check, keyed once on the Slack event ID. It covers every command the Slack source takes with a slash after a mention: `approve`, `retry`, `revise`, `reject`, `resolve`, `budget`, `verdict`, `standing`, `link`, and `merge` (bare already). The Slack source adds the `/` (`withSlash` with `THREAD_BARE_COMMANDS`, src/core/commands.ts) before the same parsers read it; `help` is read bare anywhere, as before. The slash form after a mention keeps working. Outside an item's thread nothing changes: a bare command word is a request in plain words (`@software-factory reject duplicate emails` is answered with the offer to make it a task), and the slash form of an item command gets the reply naming where it works. A reply in an item's thread with no mention is read by the plain-words reader (see the no-mention rule above); its bare command word is never applied by itself. What Slack shows: the hint under a factory message, the `help` reply in a thread and the refusal outside a thread name each command without its slash (`chatForm`); SET_UP.md's Slack list does too. Outside an item's thread `link` keeps its slash in `help` and the unlinked reply, since a bare `link <code>` there is a request. GitHub's parser, footers, the shared refusal text and the dashboard are unchanged. Why: Slack users type the bare word; storing it as a plain comment did nothing. Solo and enterprise are the same: one code path, the linked user's stored role decides.

- **The command cursor starts at `commands` only** (decision changed 2026-11-11, issue #467; current; before: the relay read `intake:local` whenever `commands` was missing, see History). The command relay reads one cursor, `commands`; no row means it starts at seq 0. A one-time data step copied the old `intake:local` value into `commands` when `commands` was missing (one guarded INSERT, never an overwrite; `intake:local` itself is left as it was). Solo (SQLite): the inbound migration `20261111T1200-inbound-commands-cursor` runs once when the store opens, after the cursor table rename, in the same transaction as the other steps. Enterprise (MySQL): step `0042-commands-cursor` runs through `npm run migrate` (it finds the table as `inbound_cursors`, or `cursors` before the rename; `--dry-run` lists the row it would write); the factory refuses to start while it is pending, so no replica runs the relay without it, and it is safe to run again. Why: the fallback cost a second cursor read on every tick until a store's first command was relayed, and was a second way to start the same cursor that only an upgrade needed.

- **Slack replies on the item's thread** (new decision, 2026-11-10, issue #480; current). The decision that changed: **a person's reply in a Slack work item's thread is stored on the item's thread**, as the GitHub source stores a comment; before, the Slack source held the store read-only and a reply was only an event the controller used for `/link` and commands, so the item page showed only the factory's messages for a Slack thread. The Slack source (src/impl/source/slack-source.ts) now holds `getWorkItemBySource` and `recordItemMessage`. A reply in an item's thread (a plain `message` reply, or an `app_mention` in the thread), a command included, is written with `recordItemMessage` before its event is returned or its command runs: marker `slack:<message ts>`, actor `slack:<Slack user ID>` (never a display or real name), body the reply text with the bot mention removed, and no delivery, so no outbox row (it is already in Slack). The command still runs once, as before. The store ignores a repeat marker, so a redelivered envelope or a restarted listener stores nothing more. A failed write throws: the envelope yields no event and is not acked, so Slack sends it again (ack after store). Not stored: a reply in a thread that is not a work item, the mention that creates an item (its request text is the item's body), an empty reply, button presses. Entries keep the order the store received them in, which is the order Slack sent them. No migration, no schema change. Solo default: the entry goes to the local store. Enterprise setting: the same call on the shared store, so every replica sees it. Not built: backfilling replies received before this change, following Slack edits and deletes of a stored reply.

- **The local merge can run in auto mode** (decision changed 2026-11-08, issue #444; before: "never automatic: only a human's command calls it", see History). With the `mode` setting at `auto` (design 03-risk), the controller's auto-merge step, after the runs of each tick, merges a local item waiting in `merge_pending` through the same `Controller.mergeLocal` (no second path): actor `system:auto`, no person to authorize, the mode change's audit seq on the `local_merged` state change, the merge check on the merge commit first and the conditional base move as for `factory merge`. It merges only below tier 4, off the gate list, complete, and at most at `auto_merge_max_tier`; a refused or failed try is posted once per item version and the item keeps waiting for `factory merge`. After a merge the checks run again on the new base tip (red main stops auto mode). A GitHub item is never merged in auto mode: there is no forge merge to call, so it waits as in manual mode. Manual mode (the default) is unchanged.

- **Local items: the base push, the owner's checkout, and PR-era items.** The decisions that changed (2026-11-08, issue #433; before: see History): **a local merge with a forge selected queues one push of the base to origin; a checkout of the base no longer refuses the merge; a local item that already has a PR keeps the PR path.**
  - **Base push** (decision changed 2026-11-09, RFC 0015 M8: an outbound delivery; see History and 10-event-driven.md "The merge queue"). When the selected forge can push a base (`Forge.pushBase`, built by the `github` forge) and the sandbox can sync one (`syncBase`), the delivered merge stores one keyed `push_base` action (`push_base:<item>:<merge sha>`) to the base push's own destination `git:<host id>:<base>:push` (not the merges', so a failing push holds no later merge; 10-event-driven.md "Git destinations"), before the item's close. The item closes before anything remote runs. Outbound's `local` target delivers it; its batch claim makes two replicas push once; the sandbox fetches only origin's base; when it already contains the merge the row finishes with no push; when it moved and is not an ancestor of the local base it is merged into the local base first (merge-tree, commit-tree, one conditional ref update; no check runs on it, both sides were checked where they were made); then the forge pushes from the factory repo with `--force-with-lease` on the remote sha the sandbox read and `--no-verify`, so a base that moved again is never overwritten. Any failure (an outage, a rate limit) is a delivery failure: outbound retries the batch, `retry_base_ms` doubling up to `retry_max_ms`, keeping the error; the item never changes. A remote base that conflicts is delivered as a conflict and posts one message on the closed item. The push uses the factory repo's own git configuration for origin, as its fetches do.
  - **Remote base conflict: the item stays closed** (the owner's decision point; chosen: no reopen, since the merge already happened and no new state is needed). The row finishes as `conflict`, and one message on the item names the conflicting files and says to merge `origin/<base>` into `<base>` and push by hand. Nothing moves.
  - **The owner's checkout.** The refusal for a base checked out in a worktree is gone. A checkout of the base with no uncommitted tracked changes is fast-forwarded with the base (`read-tree -m -u`, hooks off: HEAD, index and files move together, status stays clean). One with uncommitted changes keeps its HEAD commit, index and status: its HEAD is detached where it was before the base moves (re-attached if the move fails), the close's state change gets `checkout_not_updated` (the path), the merge message says so, and the item page shows a "local checkout: not updated" fact. The item page also shows the base push (pending with its failed tries, pushed, or a conflict).
  - **PR-era local items.** `routeFor` (src/core/worker-deps.ts) gives the local route only to a local item with no PR (`change_ref` null). A local item that opened a PR before #427 takes the forge's broker and sandbox like a GitHub item, so its update run reads `origin/<branch>` again instead of failing with `git rev-parse:` (PR #429). This reverses #333's rule that routing is by source type only.
  - **Compose, worker, session.** Unchanged otherwise: `Plugins.localRoute` builds the `local` broker and the selected sandbox in local mode beside the selected ones; `git.store_branch` goes through `routeFor`, as do preflight and comments (the push and the PR are outbound deliveries since RFC 0015 M7, 10-event-driven.md). A session with no local route refuses a local item before any call.
  - **Merge (decision changed 2026-11-08, issue #451; before: see History).** A local item with no PR merges only through the `local-merge` unit's `mergeLocal` (the sandbox's `mergeLocal`), reached by `factory merge <id>` and by the Merge button (an app `merge` request, `09-dashboard-app.md`); a GitHub item at `merge_pending`, and a PR-era local item that has a PR, merges from the same Merge button through the forge's `mergePr` at the head the review passed (the `pr-events` unit's `requestPrMerge`, a keyed `merge_pr` action outbound's `github-change` target delivers, RFC 0015 M7; a merge commit), never from the CLI: `factory merge` stays local-only. For a local item, the install command and the checks run on the merge commit in a temporary detached worktree, hooks off, removed after; a failure moves nothing and the item stays in `merge_pending`.
  - **Two replicas.** One conditional `update-ref` moves the base, one conditional transition closes the item and writes the push row (unique per item), and one conditional claim takes the row, so two merges of one change give one merge commit, one closed item and one push.
  - Solo default: no forge selected (a forge implies a remote): the local merge moves the local base and nothing else; no push row is written and no remote call is made. Enterprise setting: a forge selected, on the shared store: one push row per merge in the close transaction, pushed once by any replica with backoff. Not built: backfilling pushes for items merged before this change; pushing with the forge's App credentials instead of the repo's git configuration; the merge check for local items while GitHub is selected.
- **Local startup.** The decision that changed: **the factory starts, builds, reviews and merges with no GitHub plugin selected** (2026-11-07). One rule, by plugin selection and never by whether the repo has a remote: config selects no GitHub plugin when no source is `github-issues`, neither `auth` origin is `github`, the broker is not `github`, no forge is selected and `permissions.grants` has no `github-permission` (`selectsGitHub` in src/compose.ts, which sets `local_only` in the loaded config). Then:
  - **Startup.** No GitHub credential is read (the `github_auth` plugin is not built; plugins get a GitHub client and credentials that refuse every call) and no repository lookup is made. The project key is `local:local:<first 32 hex of the SHA-256 of owner/name>`, labelled `local/<owner>/<name>`, stored as #350's key of the configured repo, so the CLI and the next start read it. No forge ID: a rename starts a new project. Switching a store back to GitHub keeps the stored local key until GitHub's background read stores the GitHub key for the next start (the existing "another repository ID" warning).
  - **Base and fetches.** Nothing fetches origin: the sandbox's trusted base is the factory repo's local `refs/heads/<base_branch>`, a run folder's `refs/remotes/origin/*` are the factory repo's local branches (so the worker's `origin/<base>` and `origin/<branch>` read them unchanged), the worker's base fetch copies the local branch, and the git-worktree updater builds the local base branch with no fetch and no fast-forward of the main checkout.
  - **Broker.** The `local` ToolBroker (docs/plugins/tool-broker.md) commits a run's branch to the local branch `refs/heads/factory/<id>` of the factory repo, never to a remote, behind the same lease, prefix, trusted-git and egress checks as the GitHub broker (one helper, `src/impl/broker/trusted-git.ts`). It has no PR, preflight or comment tool, so the worker skips the PR open, the preflight's forge checks and PR comments, and the implement outcome has no `pr_number`.
  - **A run's comments are thread entries** (decision changed 2026-11-09, RFC 0015 M7, worker half; see History). The worker's merge-conflict, failed-checks, checks-env and scope-violation messages, its review comment and its update comment are entries on the item's thread (`Worker.comment`, once per marker), delivered by outbound like every controller message (10-event-driven.md, "Writes to the outside world leave through outbound"). A local item's thread is its surface: nothing leaves it, also with GitHub selected. Any other item's gate comments go to its own source (`threadDelivery`, src/core/local-merge.ts); the review and update comments go to its PR through the forge (`WorkerDeps.prRef`, the forge's `prRef`), and with no PR or no forge to its own source, as the controller's PR comments do. The run never waits on the delivery and never fails on it: a delivery failure is retried by outbound. The broker has no `github.comment` tool any more. Solo default: a local item never calls GitHub for a comment. Enterprise setting: a GitHub item keeps its comments, markers and bodies unchanged; an item of another source (e.g. Slack) now gets its gate comments in its own thread, where before it got none. Not built: the rest of a local item with GitHub selected (preflight, push, PR open, checks) stays with #333.
  - **Review and gate.** The item enters `REVIEW` with no `pr_number`; the review reads the local branch's diff against the local base, and a pass reaches `merge_pending` the same way a PR does (no PR, so no checks to wait for). Its message names `factory merge <id>`.
  - **Merge** (decision changed 2026-11-08, RFC 0015 M8; see History and 10-event-driven.md "The merge queue"). `factory merge <id>` stores a `merge` command in the command inbox; the controller's one local merge function (`mergeLocal` in the `local-merge` unit; #333 and #246 call it, no second path) authorizes it through the local auth plugin for `approve_merge` (the approver role; a requester's refusal names `factory users add`), refuses an item not waiting for a merge or whose branch conflicts with the base, and puts the change in the merge queue. A `merge-check` run checks its merged result on a worker; only a green one lands, as an outbound delivery whose `local` target merges through the sandbox, so core runs no git; a red one is refused on the item with the reason and nothing moves. The sandbox writes the merge commit with `git merge-tree` and `git commit-tree` (objects only, no checkout, no index, no hook) and moves `refs/heads/<base>` conditionally on the base it merged; the push to origin, with a forge selected, is the base push's. A conflict moves nothing, leaves the item in `merge_pending` and replies with the conflicting files; a checkout of the base is fast-forwarded or left as it was (see Local items: the base push, the owner's checkout). A merge closes the item (`completed`, `merge_sha`, the approver as actor, reason `local_merged`) and releases the items waiting on it; a repeat finds the branch merged and moves nothing. In auto mode the controller calls the same function itself (see the first decision above).
  - Solo default: `plugins.source: ["local"]`, `plugins.broker: "local"`, `"auth": "local"`, `permissions.grants: ["static"]`. Enterprise setting: the GitHub source, GitHub auth and the GitHub broker, unchanged, with no local broker. No new table, column or state. Not built (follow-ups): degraded mode and forge state, the outbox for GitHub writes and CLI mirror comments, the `factory status` line for GitHub; `factory session` with the local broker. Local items while GitHub is selected: see Local items: the base push, the owner's checkout, and PR-era items.
- **One GitHub client per process.** The decision that changed: **the selected `github_auth` plugin builds the credentials and the one GitHub client over them, and every plugin and command gets that client through `Plugins`** (2026-11-08). The `token` and `app` plugins return a `GitHubAccess` (`credentials` plus `api`, src/interfaces/github-credentials.ts); `Plugins.githubAccess()` in src/compose.ts builds it once per `Plugins`, so one `build()` (and one CLI command) holds one client, its ETag cache and its call budget. `build()` hands `api` to the source, auth, grant and forge contexts and the credentials only to the broker (its `git push`); the CLI commands (`settings --project`, `migrate`, `golden add` under `src/cli/handlers/`), `issue-cmd.ts` (`issueDeps`) and `setup.ts` (doctor, setup) call `Plugins.githubApi()` and construct no client. `new GitHubClient` appears only in `token-credentials.ts` and `app-credentials.ts`. `src/plugin-api.ts` imports nothing from src/impl/github/: contexts hold the `GitHubApi` interface and `{ owner, name }`. The GitHub descriptors import their implementation inside `create()`, so discovering them loads no implementation; the `token` and `app` descriptors name `GITHUB_TOKEN` and `GITHUB_APP_ID` themselves with `secretName()`, and so sit under their own tier-4 floors (factory.config.json; floors, not exemptions, in tests/credential-floors.test.ts). The `github-issues` labels move from `setup.ts` into that plugin's `setup()` hook (docs/plugins/selection.md). With no GitHub plugin selected (Local startup) the stand-ins stay: no credential is read and doctor makes no GitHub check. Solo default (`token`) and enterprise setting (`app`, its key still read only when a token is minted) take the same path.
- **The local store is the home of the conversation.** The decision that changed: **GitHub comments and commands are written to the store, and the controller applies GitHub commands from the command inbox** (2026-11-07, issue #284). Before, each new GitHub comment was an event the controller handled at once, and nothing in the store recorded a GitHub conversation. Now the `github-issues` poll writes, through the existing store methods (no migration, no schema change): each new command once to the command inbox (`inbound_commands`), key `github:<comment id>`, actor `github:<numeric user id>` (never the login), `command` the word after `/`, `args.text` the text after it, `args.source` the issue (or PR) it was written on; and each new comment by a person on an issue (command or plain) once to its work item's thread (`controller_item_thread`), marker `github:<comment id>`, body the comment, with no outbox row (it is already on GitHub). A command on a PR's conversation (`/revise`, `/resolve`, `/verdict`) carries in `args.pr` the PR number and head branch the poll already read, and its thread entry goes to that PR's item (a factory PR by its branch, an adopted one by its source), so applying it reads nothing more from GitHub; one the poll drops today (a `/revise` on a PR that is gone, a `/resolve` or `/verdict` on a PR that is not the factory's) writes nothing. Plain comments on a PR's conversation stay unwritten. One poll's comments are written in comment-id order, whatever order GitHub lists them in, so the command step applies them in the order they were written. Dedupe is the store's: a repeat poll, a second replica polling from an older cursor, or a restart writes no second row or entry (both are idempotent on the key). The poll cursor `intake:github_issue` keeps its format, and its `last_comment_id` still decides what is new, so a controller on this code started with a cursor the old code wrote applies no command at or below it (no backfill). The command step reads these rows with the CLI's (the one inbox, by `seq`): the reader (`src/core/command-inbox.ts`) gives provider `github`, subject the numeric id, only to a row with key `github:<digits>` and actor `github:<digits>` (rows written from the CLI or the UI keep provider `local`), rebuilds the comment through the one comment event mapping (`src/core/comment-event.ts`, so GitHub has no parser copy of its own) with the PR context added, and `comment_id` is the GitHub comment id, so the 👀 and refusal replies are keyed as before. The GitHub auth provider and today's grants judge it, never the local auth plugin. A GitHub row is applied only by a process with an adapter of its source type, and a failure is logged and passed like a polled event's, so a GitHub outage never holds the local commands after it. Plain comments are still also returned as events (`/link`, suggestions); they change no state. Pushed events (`pr_open`, `pr_merged`, `pr_closed`, `pr_unmergeable`, `pr_changes_requested`, `source_closed`, `base_commit`) and new-issue intake stay on the poll path. Factory messages still reach GitHub only through the outbox (Thread first, below); the 👀 reaction and the status labels stay direct calls (moving them into the outbox is a follow-up). Without a store the source returns each command as the event its row maps to. Solo default: no GitHub source listed, nothing here runs. Enterprise setting: `github-issues` next to `local` on a shared store, each comment written once, each command applied once by any replica, with no in-process state. Not built: backfilling older comments; a thread entry for a comment read in the same poll that takes in its issue (the item does not exist yet; its command is still written and applied); a replica without the `github-issues` adapter passes GitHub rows (the cursor is shared), so in a mixed deployment every replica that runs the command step should list it; Jira comments (Slack replies: see Slack replies on the item's thread).

- **GitHub call budget.** The decision that changed: **GitHub reads are conditional and budgeted** (2026-11-07, after the App installation hit its hourly limit). GitHub is a sync plugin; the factory keeps working in local mode without it, and when it is on it spends as few calls as it can:
  - **Conditional GETs.** The shared `GitHubClient` keeps the last ETag and body of each GET URL (per Accept header) in a bounded in-memory LRU (500 entries, bodies up to 1 MB), sends `If-None-Match`, and answers a 304 (not counted by GitHub) with the kept body. This is in-process state on purpose, and the one exception to "no in-process state": it is only an optimization. GitHub decides on every call whether the body is current, so a replica with an empty cache (a new process, another machine) gets the same answers, it just pays full calls. Writes are never conditional.
  - **Rate-limit budget.** Every response's `x-ratelimit-limit`, `-remaining` and `-reset` (core resource only) are kept and exposed as `budget()`. With none left before the reset the client refuses a call with the 403 GitHub would give, without sending it, so a retry loop does not hammer the API. Under `github.min_remaining` (default 200) `lowBudget()` is true until the reset and the optional reads wait: the per-PR `mergeable` reads, the "Request changes" review reads and the base-commit read in the poll (their cursors stay put), and `prChecks` (the gate counts as pending). The intake lists (open and closed issues, comments, closed and open PRs) always run. One log line on entering that mode, one on leaving.

The client counts this process's counted calls (every answer but a 304) in the current window, named by its reset time; once they reach `budget_share` × the limit, `lowBudget()` is true and the optional reads wait as under `min_remaining` (both are checked). A new reset time starts the count at zero. The count is in memory, per process: replicas of one factory on one App split its share; counting in the store is a follow-up only if needed. Enterprise: one App per factory with share 1.0 (recommended), or shares summing to at most 1.0 by a documented agreement, not enforced across factories (`docs/setup.md`).

The client reads the row at most once per tick (`refresh_ms` = `tick_ms`): the controller asks for it before each tick's optional reads (`refresh_forge_budget`), and a call that finds the last read older than a tick reads it first. So when one replica's response drops it under `max(github.min_remaining, 10% of the limit)`, every replica's `lowBudget()` is true on its next tick and its optional reads wait until `reset_at`: the poll's base-commit and closed-issue catch-up reads, the status catch-up, check reads (`checksStep`) and dependency reads. The intake lists of the issue poll still run, as before, and the sync lease never waits on the budget (outbox delivery may wait up to `max_wait`, 30 s, under a low budget since RFC 0015 M7: 10-event-driven.md, "Writes to the outside world leave through outbound"). `github.min_remaining` is the only setting; the 10% share is fixed. The per-process `budget_share` count is unchanged. `src/compose.ts` gives the client the store and the project key once the key is resolved, in every process that calls GitHub (`factory dev`, `factory session`); with no GitHub plugin selected there is no client and no row. Solo default: one process reads back its own writes. Enterprise setting: replicas on one MySQL store share the row; one replica syncs (05-coordination, One GitHub sync per project).

A command's actor is the factory user its account is linked to (`src/core/authorize.ts`, links first); an account that no link and no grant names is refused through the same permission path, its comment stays in the thread under `github:<numeric id>`, and no state changes. Replies: the controller's comments, converted to mrkdwn, with a button for each footer command that takes no text (`approve`, `retry`, `resolve`, `budget`, `help`; reject, revise, verdict stay typed) and Confirm/Cancel under a suggestion; a press is the typed command by the presser, through the same `authorize`. Each post carries its marker's hash in Slack message metadata, and the store's posted-message record is checked first (decision changed 2026-11-11, issue #484; before: the thread was read first, see History): the Slack source writes the same `outbound_deliveries` record the GitHub source writes (`recordPostedComment`: the message ts as the comment ID, the Slack link as the URL), so a recorded marker returns its link with no Slack call. Only a marker with no record reads the thread once (`conversations.replies`), to find a message posted before the records; what it finds is recorded. So a marker is posted once. Everything posted is egress-scanned in the plugin; a blocked message is replaced, under the same marker, by one notice naming the rules, and is never retried in any form. Status is one thread message edited in place, with the PR link once there is one; its ts is recorded under the marker `slack:status`, so each later status is one `chat.update` and no thread read (the first status with no record reads the thread once, and records a status message posted before this change). A status message someone deleted (`message_not_found`) is replaced by a new one, recorded under `slack:status:after:<deleted ts>`, because a stored record keeps its first ts and no store method may change it; the source follows that chain with store reads only. A status or message the egress scan blocks is not posted or edited and leaves no record (a withheld notice is marked in its metadata and never recorded). Solo default: the records are in the local store, with no setting. Enterprise setting: they are in the shared store, so a second replica reads no thread for them. No new table, column, migration or store method. A repeated status with the same text still sends its `chat.update`. Not built: backfilling records for messages posted before this change (each is recorded the first time its thread is read). No Slack SDK (spec decision 5 changed): the listener already owns reconnects and the ack-after-store rule, so the plugin uses Node's WebSocket and the Web API over `fetch`, with no new dependency. `SUGGEST_MIN_CONFIDENCE` is 0.85 (was 0.7). Not built: DMs, reactions (no `reactions:write` scope, so `markSeen` does nothing), a channel check against the API (no `channels:read`), Slack token patterns in the egress scanner (the known-value check covers the configured tokens). Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Pull requests a person opens, and a person's pushes.** Now every change to the repository passes through the controller:
  - **Adoption.** The forge (`github`) reports `pr_open` on every poll for each open PR against the base branch from this repository: every factory-branch PR, and every other PR that is not a draft (a draft is adopted on a later poll, once it is ready). A PR the store does not know (not a factory branch, no item with that PR as its source) is adopted: one item, origin `adopted`, source = the PR (`owner/repo#N`, link `/pull/N`; comments and the status label go on the PR, labelled once), title = PR title, problem = title and body, requester = the author's user ID, `done_criteria` null, `allowed_paths` = the files the PR changes (`prFiles`, both sides of a rename, read only for a PR the store does not know), tier = the floor tier of those files, stage `REVIEW` with `pr_number` and `head_branch` set, and one review run, all in one `createWorkItem` (idempotent on the source; state change `pr_adopted`). An author that does not resolve to a user is not adopted (its merge is then an unreviewed merge). Forks are not adopted.
  - **Review of an adopted PR.** The worker checks out the item's `head_branch` (it fails if `origin/<branch>` is missing) and the prompt has the PR's title and body (untrusted), its files and the diff, and says there is no spec. The review comment goes on the PR as for factory PRs. The review sets the tier (max of judgment, floor, previous). A pass goes through the same CI gate to `merge_pending`, and auto-merge stays at 0, so a human still merges. The factory never pushes to a person's branch: bugs block on a human with `changes_requested`, failed checks with `checks_failed` (both `blocked_on: human`; no implement run). `/verdict` and `/resolve` still map PRs by factory branch only.
  - **`factory: skip`.** A PR with this label, added (latest `labeled` event in the issue timeline) by a user with the existing `approve_spec` permission, gets no item. A label added by anyone else is ignored with a warning, and the PR is adopted. It is checked at adoption only: on an adopted PR the label does nothing.
  - **Merges.** Every merged or closed PR is reported now, not only factory ones. A factory branch maps to its item as before; any other PR to its adopted item by number; a merge closes it as `CLOSED` / `completed` with `merge_sha`, the merger as actor (approver of record), and a close without merge as `rejected`. A merged PR with no item (skipped, a fork, never adopted, or merged after the first start but before the poll that would have adopted it) writes one `controller_unreviewed_merges` row (project, PR number, merge sha, merger's user ID or null; idempotent on project and PR number) and a warning. **First start (decision changed 2026-11-07, issue #341):** the first poll stores a starting point in the forge's JSON cursor (the GitHub source's until issue #273) (`start`, from the Clock in GitHub's UTC format; no new table, written through the store's conditional cursor update so replicas agree), even with no closed PR. A PR merged before it gets no merger read and no event, so a factory started on an old repository flags no past merge and reads only the closed-PR list. Upgrade: a cursor from before this keeps its place (its closed-PR time becomes the start), so a running install reads no history. `github.history_since` checks older merges on purpose: older than the start, it moves the start back once (that poll reads at most 5 pages of closed PRs, one GET per merged PR; the cursor records the value so a restart does not repeat it); a newer value is ignored with one warning naming the setting. Solo and enterprise follow the same rule. Paging history across polls is not built.
  - **A person's push.** Every run that pushes (implement, update, resolve) records the head it pushed as the item's `last_head_sha`, under its lease (`recordPushedHead`); adoption records the PR's head. On each poll the controller compares an open factory or adopted PR's head with it. A different head is a person's push: one run of kind `manual`, written already `succeeded` and acknowledged (never queued, so no worker claims it and the controller applies nothing), with `actor`, `from_sha`, `to_sha` and `pr_number` in its outcome, and `last_head_sha` moved to the new head, in one transaction (`recordPrHead`, conditional on the old head, so a repeat writes nothing). It changes no stage, blocked field or version, and nothing is re-queued or re-reviewed: a later review covers it. GitHub does not name who pushed, so the actor is the author of the head commit resolved through auth; if that does not resolve, `system:pr-sync` and a warning. While any run of the item is running, the head is not looked at (that run may be pushing); an item with no recorded head (from before this) only takes the current head as a baseline.
  - **Schema:** migration 12 adds `work_items.origin` (`factory` default), `head_branch`, `last_head_sha` (all store-owned, not in `WorkItemPatch`) and the `controller_unreviewed_merges` table. SQLite builds it on open; MySQL gets it from the step file `migrations/mysql/0012-adopted-prs.sql` through `npm run migrate` (the table has a `seq` column like every MySQL table, which the store orders ties by). A MySQL store refuses to start until that step is applied.
  - Not built: re-review after a person's push, adopting a PR again after it reopens with a new number, showing unreviewed merges in stats. The Health section and the Floor line of the app show them (see `09-dashboard-app.md`).

## History

- **A spec was posted whole to Slack, after a separate status message** (until 2026-11-12). Before: the Slack source posted `Status: *needs approval*` as its own message, then the whole spec comment as one message (In short, Problem, Decisions, Applied defaults, Done when, scope, Files, Risk), with Approve and Help buttons from its footer; decisions were answered only by typing `/approve` with `N: <answer>` lines.
- **A plain reply in an item's thread needed the slash** (until 2026-11-12, issue #585; set 2026-11-11, issue #541). Before: this file said a reply in an item's thread with no mention still needed the slash, so a sentence there was never a command by accident; the reader's proposals (2026-11-11) already answered such a reply, and nothing said that a reply in a thread the factory does not own is never read.
- **A top-level mention read as a request, or not read, was taken in at once** (until 2026-11-12; set 2026-11-11, the chat answer). Before: the intake unit read a top-level mention only for a requester with `approve_spec`, a model, and a clean message of 1 to 1000 characters; a `request` answer, a failed or malformed answer and every message it did not read became a work item at once, with no reply, so a question to the bot got an item and a full spec. Only an unsure answer got the Make this a task button.
- **Every top-level Slack mention was a work request** (until 2026-11-11, the chat answer). Before: the Slack source turned any mention outside an item's thread into an `item_requested`, and intake created a work item for it without reading the message, so "can you receive natural inputs?" became a work item.
- **No source read reactions** (until 2026-11-11, issue #524). Before: the GitHub source read comments and added 👀 but never listed a comment's reactions; the Slack app had `reactions:write` only (no `reactions:read`, no `reaction_added` event); and the store had no read of a posted message by its comment ID or of the posted comments in a time window.
- **Slack buttons never changed** (until 2026-11-11, issue #586). Before: each message's buttons were built once from the command footer it was posted with and never edited, so an Approve stayed under a spec after the item moved on, and pressing it reached the command handler's `was not applied` refusal.
- **Only `approve` worked without its slash after a mention** (until 2026-11-11, issue #541; set 2026-11-11, issue #528). Before: in an item's thread the Slack source read a bare `approve` after a mention as `/approve` and nothing else, so `@software-factory revise <feedback>` was stored as a plain comment and did nothing; the hint, the `help` reply and the refusal outside a thread showed the slash form, and SET_UP.md listed `@bot /approve [notes]` and the other item commands with their slash.
- **The command cursor fell back to `intake:local`** (until 2026-11-11, issue #467). Before: while the `commands` cursor row was missing, the command relay read the old `intake:local` cursor as its start, two cursor reads on every tick until the first command was relayed.
- **Slack messages: thread first** (until 2026-11-11, issue #484). Before: the Slack source read the whole thread (`conversations.replies`, up to 20 pages) before every `postComment` and every `setStatus` to find its own earlier message by marker hash or by status metadata, and wrote no posted-message record, so outbound's record check always missed for Slack. Now the store's record is checked first and the thread is read only when there is none.
- **Slack replies were not saved** (until 2026-11-10, issue #480). Before: the Slack source held the store read-only; a person's reply in an item's thread became a plain-comment event used only for `/link` and command handling and was never stored, so the item page showed only the factory's messages for a Slack thread. "The local store is the home of the conversation" listed Slack comments as not built, and "One command table" listed #480 (people's replies on the item page) as not built here.

- **One command table, and the factory's commands in Slack** (new decision, 2026-11-09, issue #498).
