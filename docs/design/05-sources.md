# 5. Coordination: intake sources and pull requests

- **Thread first, then the outbox.** The decision that changed: **every factory message is written to the item thread before any source is called, and only the outbox step posts it** (2026-11-07, issue #282). The controller's one message helper writes the message to `item_thread` (one per item and marker), and for an item whose source is not `local` it adds, in the same transaction, one `thread_outbox` row (SQLite migration 27, MySQL step `0027-thread-outbox.sql`): the source type, the target, the item field the URL fills (`spec_comment_url` or `failure_comment_url`), the attempts and the next try. An entry goes only to its item's own source: a PR comment (the PR is a target of the same type) goes to the PR, and for a non-GitHub item it goes to the item's own source instead. The outbox step runs last in every tick (and after each public tick step): it lists pending rows of the source types this process has adapters for, claims each one for `lease_ms` with a conditional update (a token only a claim bumps), calls that adapter's `postComment` (the only call of it, apart from a `/link` reply on an issue that is no work item, which has no thread), and marks the row delivered under the claim. So each entry is posted once, also when two replicas run the step at once. A failed post counts an attempt, keeps the error, releases the claim and waits `retry_base_ms` doubling per attempt up to `retry_max_ms`; it never touches the item's stage, blocked fields or version, and a failed post no longer stops the transition that wrote it. The URL of a delivered comment fills the item's link field when no newer entry names the same field (no version change, no state change); the transition itself stores the link only when the entry was already delivered (a re-decide), so links appear once the outbox delivers. Entries of a source type with no adapter here stay pending for a process that has one. `local` items need no adapter: the thread is their surface, so they get no outbox rows and their transitions run in any process. The controller reads CLI and app commands from the command inbox itself (design 04-gate-commands, "Commands from the command inbox"), so `plugins.source` may be an empty list: the factory then runs on the store alone, with local items. A local-only setup is still `"source": ["local"]`; GitHub (`github-issues`) is the sync plugin. Not built: retiring `app_command_requests`, a Slack adapter, webhook endpoints.
- **GitHub call budget.** The decision that changed: **GitHub reads are conditional and budgeted** (2026-11-07, after the App installation hit its hourly limit). GitHub is a sync plugin; the factory keeps working in local mode without it, and when it is on it spends as few calls as it can:
  - **Conditional GETs.** The shared `GitHubClient` keeps the last ETag and body of each GET URL (per Accept header) in a bounded in-memory LRU (500 entries, bodies up to 1 MB), sends `If-None-Match`, and answers a 304 (not counted by GitHub) with the kept body. This is in-process state on purpose, and the one exception to "no in-process state": it is only an optimization. GitHub decides on every call whether the body is current, so a replica with an empty cache (a new process, another machine) gets the same answers, it just pays full calls. Writes are never conditional.
  - **Rate-limit budget.** Every response's `x-ratelimit-limit`, `-remaining` and `-reset` (core resource only) are kept and exposed as `budget()`. With none left before the reset the client refuses a call with the 403 GitHub would give, without sending it, so a retry loop does not hammer the API. Under `github.min_remaining` (default 200) `lowBudget()` is true until the reset and the optional reads wait: the per-PR `mergeable` reads, the "Request changes" review reads and the base-commit read in the poll (their cursors stay put), and `prChecks` (the gate counts as pending). The intake lists (open and closed issues, comments, closed and open PRs) always run. One log line on entering that mode, one on leaving.
  - **Fewer reads per poll.** The closed-PR list stops at the first page that reaches the cursor instead of reading up to 5 pages every poll. `setStatus` reads the labels first and writes nothing when they are already right (one GET, a 304 when unchanged) instead of always creating the label, adding it and reading the list.
  - Not here: dependency re-reads in `coordinationStep` (issue #254; it can use `lowBudget()`), and a draining child stopping its controller (issue #294).
- **CLI intake.** The decision that changed: **a CLI command acts as the environment's identity and is authorized by the local auth plugin** (issue #318). Who: `cli_user` from factory.config.json when set (now optional), else `local:<git user.email>` (in the repo, lowercased), else `local:<OS user name>`, else `local:anonymous` (`cliIdentity` in src/core/local-cli.ts; main.ts reads git and the OS; git's `user.name` is skipped as a display name). The local UI acts as the same identity. No command fails for lack of `cli_user`. Who may: the auth plugin for origin `local` (default `local`, whatever `auth` selects for GitHub; [08-permissions.md](08-permissions.md), "Local commands are authorized locally"): the first identity to run a writing command becomes the local owner, the owner grants `approver` or `requester` with `factory users add`, and `anonymous` reads and creates only. `factory task create --title <t> --body-file <f>` creates one local work item in the store (source type `local`, id `local-<random>`, requester = the CLI identity) with its triage run queued, in one `createWorkItem`, and prints its ID; the project key comes from the store (`storeProjectResolver`), and it fails while no project is stored. `factory task list` and `factory task show <id>` only read (state, spec, runs, item messages). `factory approve|retry|revise|reject <id> [text]` append one row to the CLI command log (`command_inbox`: random key, actor = the CLI identity, `args.item`, optional `args.text`) and change no item state; the controller reads it from the command inbox (since issue #282; before, through the `local` source) and applies it like the same GitHub comment, with the same `authorize` check through the local auth plugin (identity provider `local`, subject the actor after `local:`) and the same replies, stored as item messages; a role refusal names the `factory users add` command. No GitHub call on this path. The command table in src/core/local-cli.ts builds the usage text, one `/help` line and the SET_UP.md list (a test compares them). Not built: `factory link` (an optional GitHub link for audit), `verdict`, `budget`, `resolve` from the CLI, a dashboard view.
- **Local intake.** The decision that changed: **local intake and item messages live in the store.** Until issue #282 the `local` poll source read the CLI command log (`command_inbox`) by `seq`, at most 100 per poll, cursor = last `seq` read (`intake:local`); the controller now does that itself (cursor `commands`, starting from `intake:local`), and turns each command for a local item (`args.item` = work item ID, optional `args.text`) into the event the same comment gives on GitHub, by rebuilding `/<command> <text>` and parsing it with the same comment parser; `comment_id` is the command key, the identity is provider `local`, subject the actor after `local:`. Commands for missing or non-local items are skipped and the cursor passes them. Its replies are item thread entries (`item_thread`, one per marker), written by the controller; `markSeen`, `setStatus` and `closeIssue` are no-ops because the store already holds the item's state. Source plugins get the store in their context for this. Writing commands, creating local items and who may send them: see CLI intake above. Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Item thread and command inbox.** The decision that changed: **an item's messages and the CLI commands live in two general tables** (issue #281). The store keeps every item's messages in `item_thread` (one per item and marker) and the commands in `command_inbox` (read by `seq`, `command_key` the idempotency key). SQLite migration 24 and MySQL step `0024` create both and copy the rows of migration 21's message and command tables with their `seq`, so a saved `intake:local` cursor still points at the same next command; the copy skips rows already copied, so it is safe to run again. The old tables stay in place, and nothing reads or writes them. Store method names, arguments and results are unchanged, and GitHub items still write nothing there.
- **Stream intake.** `SourceAdapter` is now a union on `intake`: `"poll"` sources keep `poll(cursor)` (GitHub, unchanged); `"stream"` sources have `subscribe(signal)` yielding `PushedEvent`s (event, `dedupe_key` unique within the source, `ack()`). A pushed event is written to a store inbox (`source_inbox`, migration 10) before it is acked, and a duplicate `dedupe_key` is a no-op that is still acked; a failed write is not acked. Controllers read the inbox through the cursor `inbox:<source type>` and the same `handleEvent` as polled events, so any replica handles them. One listener per stream source across replicas, decided by a store lease (`listener_leases`, migration 10: owner, token, expiry; conditional updates only; the inbox write checks the token in its transaction). It reuses `lease_ms` / `heartbeat_ms`, runs inside the controller process (started by `Controller.run`), reconnects with backoff and logs on state changes only. Cleanup on the poll interval deletes rows older than `inbox_retention_days` (optional, default 14) that are at or below the cursor; no cursor, no deletion. What it changes: a new intake path and two tables; GitHub intake, `SourceType` and the registry are unchanged (the only stream source is the test-only `fake-stream`). Not built: a Slack plugin, webhook endpoints. Details: architecture §4 Intake.
- **Several sources.** The decision that changed: **one source becomes a list of sources.** `plugins.source` takes a string (unchanged: a list of one, the same selection as before) or a list of registered names; an unknown name or the same name twice fails at startup naming `plugins.source` (an empty list is allowed since 2026-11-07: see Thread first). `build()` makes one adapter per name and hands them all to the controller, which refuses at startup two adapters of one source type, or several with none of type `github_issue` (PR merge, close and unmergeable events come only from GitHub, so without it factory PRs would never close their items). Routing: each item's `postComment`, `markSeen`, `setStatus` and `closeIssue` go to the adapter whose `type` matches the item's `source.type`; `setStatus` for a PR (non-null `pr_number`) goes to the `github_issue` adapter whatever the item's source, because PRs live on GitHub (a single non-GitHub source alone keeps the old behaviour: everything to it). An item whose source type has no configured adapter keeps its state: the controller makes no transition on it (changed 2026-11-07; `local` items excepted since issue #282, the store being their surface), and its outbox entries stay pending, so a finished run of it stays unacknowledged for a process that has the adapter, such as the new version next to an older one still draining with an older `plugins.source`; its calls outside a transition log a warning and are skipped. Intake: every poll source has its own cursor `intake:<type>` and every stream source its own listener (the lease was already per type) and inbox cursor; each source's step runs under its own guard, so one source failing does not stop the others in the same tick. Commands from any source go through the same command table, the same `AuthProvider` check and the same replies; resolving non-GitHub identities is left to the provider work (#107, #109). Not built: a Slack adapter (#109), new `SourceType` values. Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Pull requests a person opens, and a person's pushes.** Now every change to the repository passes through the controller:
  - **Adoption.** The `github-issues` source reports `pr_open` on every poll for each open PR against the base branch from this repository: every factory-branch PR, and every other PR that is not a draft (a draft is adopted on a later poll, once it is ready). A PR the store does not know (not a factory branch, no item with that PR as its source) is adopted: one item, origin `adopted`, source = the PR (`owner/repo#N`, link `/pull/N`; comments and the status label go on the PR, labelled once), title = PR title, problem = title and body, requester = the author's user ID, `done_criteria` null, `allowed_paths` = the files the PR changes (`prFiles`, both sides of a rename, read only for a PR the store does not know), tier = the floor tier of those files, stage `REVIEW` with `pr_number` and `head_branch` set, and one review run, all in one `createWorkItem` (idempotent on the source; state change `pr_adopted`). An author that does not resolve to a user is not adopted (its merge is then an unreviewed merge). Forks are not adopted.
  - **Review of an adopted PR.** The worker checks out the item's `head_branch` (it fails if `origin/<branch>` is missing) and the prompt has the PR's title and body (untrusted), its files and the diff, and says there is no spec. The review comment goes on the PR as for factory PRs. The review sets the tier (max of judgment, floor, previous). A pass goes through the same CI gate to `merge_pending`, and auto-merge stays at 0, so a human still merges. The factory never pushes to a person's branch: bugs block on a human with `changes_requested`, failed checks with `checks_failed` (both `blocked_on: human`; no implement run). `/verdict` and `/resolve` still map PRs by factory branch only.
  - **`factory: skip`.** A PR with this label, added (latest `labeled` event in the issue timeline) by a user with the existing `approve_spec` permission, gets no item. A label added by anyone else is ignored with a warning, and the PR is adopted. It is checked at adoption only: on an adopted PR the label does nothing.
  - **Merges.** Every merged or closed PR is reported now, not only factory ones. A factory branch maps to its item as before; any other PR to its adopted item by number; a merge closes it as `CLOSED` / `completed` with `merge_sha`, the merger as actor (approver of record), and a close without merge as `rejected`. A merged PR with no item (skipped, a fork, never adopted, or merged before the first poll that would have adopted it) writes one `unreviewed_merges` row (project, PR number, merge sha, merger's user ID or null; idempotent on project and PR number) and a warning. On a fresh install the first poll reads one page of closed PRs, so older merges there are recorded too.
  - **A person's push.** Every run that pushes (implement, update, resolve) records the head it pushed as the item's `last_head_sha`, under its lease (`recordPushedHead`); adoption records the PR's head. On each poll the controller compares an open factory or adopted PR's head with it. A different head is a person's push: one run of kind `manual`, written already `succeeded` and acknowledged (never queued, so no worker claims it and the controller applies nothing), with `actor`, `from_sha`, `to_sha` and `pr_number` in its outcome, and `last_head_sha` moved to the new head, in one transaction (`recordPrHead`, conditional on the old head, so a repeat writes nothing). It changes no stage, blocked field or version, and nothing is re-queued or re-reviewed: a later review covers it. GitHub does not name who pushed, so the actor is the author of the head commit resolved through auth; if that does not resolve, `system:pr-sync` and a warning. While any run of the item is running, the head is not looked at (that run may be pushing); an item with no recorded head (from before this) only takes the current head as a baseline.
  - **Schema:** migration 12 adds `work_items.origin` (`factory` default), `head_branch`, `last_head_sha` (all store-owned, not in `WorkItemPatch`) and the `unreviewed_merges` table. SQLite builds it on open; MySQL gets it from the step file `migrations/mysql/0012-adopted-prs.sql` through `npm run migrate` (the table has a `seq` column like every MySQL table, which the store orders ties by). A MySQL store refuses to start until that step is applied.
  - Not built: re-review after a person's push, adopting a PR again after it reopens with a new number, showing unreviewed merges in stats. The Health section and the Floor line of the app show them (see `09-dashboard-app.md`).

## History

- **Thread first, then the outbox** (decision changed 2026-11-07, issue #282). Before: the controller posted each message through a helper that called the source adapter directly, so nothing in the store recorded what reached a GitHub item's source, a failed post made the whole transition retry, CLI commands were read only through the `local` source, and an empty `plugins.source` failed at startup.
- **Stream intake** (new decision, 2026-11-01). Before: every source was polled on a timer, so a source that pushes events, like Slack Socket Mode, had to be forced into polling.
- **Several sources** (decision changed 2026-11-01). Before: `plugins.source` named one plugin and the controller sent every comment, 👀, status and close through that one adapter, so a second source such as Slack could not run next to GitHub, and its items would have been answered through GitHub.
- **Pull requests a person opens, and a person's pushes** (decision changed 2026-11-01, issue #113). Before: only factory PRs were tracked: the GitHub source read pull requests on factory branches only, so a PR a person opened could merge with no review run, no scope or size check and no record, and a push a person made to a factory branch was invisible to the factory.
- **Local intake** (decision changed 2026-11-07, issue #199). Before: polled intake was GitHub only, nothing read the CLI command log and nothing stored item messages; now local intake and item messages live in the store, through the `local` source.
- **CLI intake** (decision changed 2026-11-07, issue #318). Before: every CLI command acted as `cli_user` and failed without it, and the one global `auth` plugin judged it: with `auth: github` the local account resolved only through a link no command created, so CLI commands were refused as not linked and local items stuck at spec approval.
- **CLI intake** (decision changed 2026-11-07, issue #200). Before: the `local` source could read the CLI command log, but nothing wrote to it and nothing created a local work item, so human commands from the CLI had no entry point and the local flow was untested end to end.
- **Item thread and command inbox** (decision changed 2026-11-07, issue #281). Before: local item messages and CLI commands lived in two tables from migration 21 named for the local source only, so the store had no single place for an item's conversation.
- **GitHub call budget** (decision changed 2026-11-07). Before: every GitHub GET was a full call counted against the hourly limit, even when nothing had changed; the closed-PR list read every page up to 5 on each poll; `setStatus` made at least three calls each time; and nothing read the rate-limit headers, so a retry loop kept calling after the limit was spent.
- **No adapter, no transition** (decision changed 2026-11-07). Before: a controller without the item's source adapter still applied the item's transitions and only skipped the calls, so an older process draining after `local` was added to `plugins.source` applied local items' triage and dropped their spec comments and replies.
