# 11. Plugin import: skills and MCP servers from Claude Code and Codex user configs

- **The Tools tab lists the tools of each approved imported MCP server, which a worker starts once per request with an empty env and no credential (decision changed 2026-11-16, phase 3 of 3 of local-84b269e4-38be-439c-983e-10f9675881fa; current; replaces "an imported server's tools are not listed", see History).** Owner answer 3 is built; owner answer 1 still holds.
  - **Which servers.** An imported MCP server (an `ext_packs_entries` row of kind `mcp_server` whose descriptor's `source` is `claude` or `codex`) whose current description has an approve row in `ext_packs_approvals`. A waiting, off or changed one starts nothing, gets no request and shows no row. Pack MCP servers are not listed here.
  - **Request** (`src/import/mcp-tool-lists.ts`, `requestMcpToolLists`). `GET /api/v1/plugins` (`src/ui/plugins-api.ts`), with a factory user (`UiPauses.principal`), writes one `requested` `ext_mcp_tool_lists` row per such server with no row for its current `description_hash` (the ID follows from name and hash, so a second read or a second process adds nothing; a `not_approved` row is asked again once the description is approved again). With no factory user nothing is asked. The UI process never starts a server; it reads the result from the store. `factory plugins list --kind tool` shows the same rows (the shared builder; it writes nothing).
  - **Listing** (`listRequestedMcpTools`). The worker pool runs it each tick, one at a time per process (`list_mcp_tools`, injected from `src/compose.ts`, so no file under `src/worker/` imports `src/import/` or `src/impl/`). It claims a row by a conditional update (`requested` to `running`, `claimed_by` the process ID), so two workers never both start the server; a `running` row not finished in 10 minutes (a stopped worker's) may be claimed again the same way. It reads the approval again: gone or changed ends the row `not_approved` with no process. A descriptor with no stdio `command` (URL based) ends `not_stdio`. Else `startPackMcpServer` starts it with `env: {}` and no credential, sends only `initialize` and `tools/list`, keeps the tool names and stops it: `listed`. A server that does not start or answer ends `did_not_start`.
  - **Stored** (`ext_mcp_tool_lists`, migration `src/state/migrations/20261116T1200-state-ext-mcp-tool-lists`, additive): `id`, `name`, `description_hash`, `status`, `tools` (a JSON list of names only), `requested_by` (a user ID), `claimed_by`, `created_at`, `updated_at`, unique on (`name`, `description_hash`). No tool description and no error text is stored. The listing writes no `ext_packs_approvals` or `ext_packs_entries` row.
  - **Tools tab.** Each listed tool is a row `mcp:<server>:<tool>`, origin MCP, described "From MCP server <server>"; a server with no names yet is one row `mcp:<server>` saying "listing its tools", "did not start" or "not a stdio server". No approve or revoke control on the Tools tab; the server is approved on the MCP tab.
  - **Owner answer 1.** An imported MCP server granted to a run is refused as `not_started` before the agent starts (`importedMcpRefusals`, passed to the workers from `src/compose.ts`); no secret value reaches any server process.
  - **Not done:** `web/src/api.ts` still types a tool's `origin` as `broker | pack` and the row texts come from the server in English (the i18n catalog and the API types were outside this change's paths).
  - Tests: `tests/import-plugins.test.ts` (a fake stdio MCP server: the empty env, no `tools/call`, the names only; waiting, off and changed servers; one request; the claim of two workers; a stale claim; the approval read again; `not_stdio`; `did_not_start` with no error text; the run refusal; the pool's tick) and `tests/import-plugins-ui.test.ts` (the request row and its user, no start in the UI process, the rows of each result, the page's MCP origin).
- **The dashboard imports too: each Plugins tab (MCP, Skills, Tools) has an Import button that opens a checkbox dialog over the same scan and the same stores as `factory plugins import` (decision changed 2026-11-16, phase 2 of 3 of local-84b269e4-38be-439c-983e-10f9675881fa; current; replaces "CLI only in this phase: no dashboard change", see History).** The owner can import what Claude Code and Codex already hold without leaving the Plugins page.
  - **Read.** `GET /api/v1/plugins/import` (`src/ui/plugins-import-api.ts`) runs `scanUserConfigs` over both sources and kinds under the OS home folder and returns, per found item, `kind`, `source`, `name`, a skill's `path`, an MCP server's `env_keys` and `header_keys` (names only), `imported` (a skill: its `ext_skill_refs` row with the same source, path and SHA-256 exists; an MCP server: its `ext_packs_entries` row with the same name and description hash exists) and `refused` (the rules of the three `pack add` scans it fails), plus each source whose config did not parse. It writes nothing. A missing config gives no items from that source and status 200. Every string leaves through the Withholder.
  - **Write.** `POST /api/v1/plugins/import` with `{ "items": [{ "kind", "source", "name" }] }` (1 to 500) scans again and stores the named items through `SkillRefsStore` and `PackEntriesStore.insert` after `scanDescriptor`, the CLI's stores and rules. The browser names items only: their descriptors come from the server's own scan, so no descriptor, env value or header value is ever sent or returned. Each item's outcome is `stored`, `already_added`, `refused` (with its rules; nothing stored) or `not_found` (the configs no longer hold it), with the CLI's line. An imported MCP server stays `pending`: nothing is started, approved or granted.
  - **added_by** is the page's factory user (`UiPauses.principal`, as the pack approvals route); with none the POST is a 403 and writes nothing.
  - **Guards** (`src/ui/server.ts`). The POST is a write route: Host, Origin, Content-Type, CSRF token, body size and JSON, then the body check and the factory user, all before any store write. The GET reads the user's own config files, so after the Host check it also needs the page's CSRF token in `x-csrf-token` (a same-origin GET carries no Origin and no Content-Type, so those two guards cannot apply to it). Both are wired only when the pause routes are (`ApiDeps.pauses`); without them the GET is a 404 and the POST a 405.
  - **Dialog** (`web/src/views/plugins.tsx`). The Import button sits beside each tab's search box; it is off, with the CLI command in its tooltip, when the Plugins read carries no CSRF token. The Skills tab's dialog lists skills; the MCP and Tools tabs' list MCP servers (tools come from MCP servers; an approved imported server's tools are listed on the Tools tab, the decision above). It is the shared `Dialog` with one checkbox per item (the shared `Button` with `role="checkbox"`, as on the Tasks page: `components/ui` has no checkbox). An imported item shows checked, disabled and badged Imported; a refused one is disabled and names its rules; an MCP server shows its env key names. Import posts the checked items, reloads the Plugins read and closes with a status line; a refused or vanished item keeps the dialog open with its line.
  - Tests: `tests/import-plugins-ui.test.ts` (read, imported flag, missing config, the guards of both routes, the 403 without a factory user, refusal, idempotency, the sentinel env and header values in no body and no row, and the page's Import buttons and dialog).
- **`factory plugins import` finds the skills and MCP servers in the user-level Claude Code and Codex configs and stores them as skill references and pending pack entries, with no env value anywhere (new decision, 2026-11-15, phase 1 of 3 of local-84b269e4-38be-439c-983e-10f9675881fa).** Before, the factory could not see the skills and MCP servers a user keeps in those configs. The dashboard import is the decision above.
  - **Command.** `factory plugins import [--dry-run] [--kind skill|mcp_server|all] [--from claude|codex]` (`src/cli/handlers/plugins/plugins.command.ts`). `--kind` defaults to `all`, `--from` to both sources; each limits the scan to its kind or source. `--kind=x` and `--kind x` both work. An unknown flag or value prints the usage and exits 1.
  - **What is read** (`src/import/scan.ts`, reads only), under the OS home folder:
    - Claude Code: `~/.claude.json`, its top-level `mcpServers` (user scope only; the `projects` entries and project `.mcp.json` files are not read), and `~/.claude/skills/<name>/SKILL.md`.
    - Codex: `~/.codex/config.toml`, its `[mcp_servers.<name>]` tables, and `~/.codex/skills/<name>/SKILL.md`. The TOML is read by a small reader in `src/import/toml.ts` (no new dependency).
  - **No env value leaves the scanner.** An MCP server's stored descriptor is built from an allow-list: `name`, `description` ("Imported from the … user config"), `source`, and, when present, `type`, `command`, `args` (a list of strings) and `url` with its user, password, query and fragment removed. `env_keys` holds the key names of `env`, and Codex's `env_vars` and `bearer_token_env_var` names; `header_keys` holds the key names of `headers`, `http_headers` and `env_http_headers`. Every other field is dropped. A parse error names the file, and the TOML line number, never the text there.
  - **Dry run.** `--dry-run` prints one `found <kind> <name> from <source>` line per item and `dry run: N found, nothing stored`. It never loads the config's store: no store row, no file and no state folder is written.
  - **MCP servers** go through the three scans `factory pack add` runs (`scanDescriptor`, 11-packs.md), then `PackEntriesStore.insert` as a `pending` `ext_packs_entries` row of kind `mcp_server`, `credential_name` null, `module_hash` null, `description_hash` the descriptor-only hash. A refused server is named with its rules and not stored; the command then exits 1.
  - **Skills** go to `ext_skill_refs` (migration `src/state/migrations/20261115T1200-state-ext-skill-refs`, additive): `id`, `source` (`claude` | `codex`), `name` (the folder name), `path` (the absolute SKILL.md path), `sha256` (of the file's bytes), `added_by`, `created_at`, unique on (`source`, `path`, `sha256`). The file's text is never stored. A changed file is a new row.
  - **Idempotent.** Both inserts skip a row already stored (the ID follows from the unique key), so a second run prints `already added …` for each item and stores nothing new; a second worker makes the same rows.
  - **Missing or malformed configs.** A missing config file finds no MCP servers from that source and exits 0. A config that does not parse stops its whole source (its skills too) with one error line naming the file; nothing from that source is stored, the other source still runs, and the command exits 1.
  - **added_by:** the CLI identity (`cli_user`, else git `user.email`, else the OS user, else `anonymous`), as `factory pack add`.
  - **Nothing is started, approved or granted** in this phase: each imported MCP server stays `pending` until the owner runs `factory pack approve`.
  - **Owner answers (binding, kept verbatim):**
    1. Imported MCP servers that name env keys: may the factory pass the referenced secret values to the server process? Answer: keep not_started until a later change (the default, accepted).
    2. Where are imported skill references stored? Answer: a new store table ext_skill_refs (the default, accepted).
    3. Does the Tools tab start an approved imported MCP server to list its tools? Answer: yes, once in the worker with an empty env (the default, accepted).
    The answers to 1 and 3 apply to later phases.
  - **Architecture ratchet.** The command imports `src/import/` (a legacy folder), which adds two `component-imports-legacy` lines for `cli/handlers/plugins/plugins.command.ts` to `tests/architecture/known-violations/dependency-direction.json`; that change needs the owner's merge.
  - **Not done:** `args` are stored as found, so a secret written into an argument (not into `env`) is caught only by the egress and credential-leak scans; listing or using the imported skill references.
  - Tests: `tests/import-plugins.test.ts` (dry run, idempotency, the sentinel env value in both formats, the skill reference, the filters, missing and malformed configs, the TOML reader).
