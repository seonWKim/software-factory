# 8. Enterprise: permissions and size limits

- **Local user changes are audited, and the dashboard manages them (new decision, 2026-11-08, issue #445; current).** The decision that changed: **every add, role change and removal of a local user writes one row to `identity_local_user_changes`** (`seq`, `user_id`, `action` `add` | `change` | `remove`, `old_role`, `new_role`, `actor`, `at`), an Identity table: the additive migration `src/identity/migrations/20261109T1300-identity-local-user-changes.migration.ts` (SQLite on open, MySQL through `npm run migrate`; the numbered lists stay frozen at 41). The row is written by Identity's `recordLocalUserChange` (`src/identity/local-users/changes.ts`). The store's `setLocalUserRole` and `removeLocalUser` write it in the same transaction as the change, so `factory users add|remove` and the dashboard's Users page (`POST /api/v1/users`, 09-dashboard-app) write the same row; a refused write (non-owner, the owner's row, a missing user) and a set to the role a user already has write none. The actor is `added_by` for an add or change and the owner for a remove (only the owner may remove; the store interface is unchanged). Removing a user still deletes its `identity_local_users` row; the audit row keeps the record. The page reuses the CLI's `users` actions (`runLocalCli`), so the owner rule, the first-writer-is-owner claim (never `anonymous`), the user ID check and the refusal to make `anonymous` an approver are the CLI's. Solo: rows in the SQLite file; enterprise: rows in the shared MySQL store, each with the person's own actor ID. Not shown on the page yet (follow-up).
- **Guided setup and display names** (decision changed 2026-11-08, owner decision; before: `factory setup` asked only for secrets, needed a terminal, and stored no name for anyone, see History).
  - **Guided flow.** `factory setup` asks, in order: store (`sqlite` | `mysql`), plugins (GitHub sync yes/no, Slack threads yes/no plus channel IDs), mode and `auto_merge_max_tier`; then the unchanged secret file, model credential, GitHub token, database steps; then "You and the mode"; then the other secrets, plugin setup hooks, checks and canary. Each question shows its default and Enter takes it. The default is the file's current choice, and the solo default (SQLite, local only, no Slack) when the file lists no sources yet, so a rerun changes nothing. `--yes` takes every default without reading the terminal (scripts, tests): a missing secret is reported, never asked, and the MySQL root password is not asked. `--rotate-github|claude|mysql` work as before. Code: `src/cli/handlers/setup/` (`guided.ts`, `ask.ts`, `config-edit.ts`, `me.ts`); the secret steps stay in `src/setup.ts` (`setupSecrets`, `setupFinish`).
  - **Shared choices go to factory.config.json**, shown first as a `-`/`+` diff of the top-level keys that change (`store`, `plugins`, `auth`, `permissions`, `slack`), then written after a yes (`--yes` writes). Only those keys' text changes; every other line stays as written. The file is reloaded through the config check, and put back if the check refuses it. Local only means `plugins.source: ["local"]`, `plugins.broker: "local"`, `auth: "local"` and `permissions.grants` without `github-permission` (`["static"]` when nothing is left), so `selectsGitHub` is false. `mode` and `auto_merge_max_tier` are runtime settings, not file keys (08-settings): setup sets a changed one through `factory settings set`, with its approve_merge check and audit row, and prints the command to run later when that is refused (no project key stored yet).
  - **Your identity.** The ID is unchanged: `cli_user`, else `local:<git user.email>`, else `local:<OS user>`, else `local:anonymous` (05-sources, CLI intake). Setup asks for a display name, prefilled from the stored one, else git `user.name`. Git's `user.name` is only this default and is never an ID. The name is stored **once**, in Identity's `identity_profiles` (user ID, display name, source `self` or the provider, updated at; migration `src/identity/migrations/20261108T2345-identity-profiles`). Every other table keeps IDs only. The CLI and the UI look a name up at the edge: `factory users list` shows `ID (name)`; the status page shows `name (ID)` where it showed an ID (item timeline actor, pause holders), and the API adds `actor.name` and `merged_by_name` beside the IDs (`src/ui/names.ts`; M9 wiring, 2026-11-08). A table of its own, not a `display_name` column on `identity_local_users` (the target schema has no profile table): that table lists role holders (a row means a role, and `users remove` deletes it), but a person with no role yet and an enterprise user (`github:`, `oidc:`) with no local row also have a name. `local:anonymous` stores no name.
  - **Many users.** `factory setup --me` only registers the current person (ID and display name), touching neither factory.config.json nor the secret file. The first person to register, or to run a writing command, becomes the owner, as before (`claimLocalOwner`). Anyone later has no role (read and create only, like `anonymous`) until the owner runs `factory users add <id> --role approver|requester`; setup prints that command.
  - **Enterprise.** An `AuthProvider` may implement `displayName(identity)`: `authenticate` then stores the name it returns against the principal (source = the provider). A name the person chose (`self`) is never replaced by a provider's. No provider implements it yet (OIDC and GitHub will supply the name at login).
  - **`narrow` stays internal.** `PassportService.narrow` is called only from `src/worker/` (run passports) and `src/identity/`; it is never a tool, an HTTP route or a CLI command. `tests/architecture/passport.test.ts` enforces it, with a negative fixture, and has no exemption list.

- **Passports in the running factory** (decision changed 2026-11-09, RFC 0015 M9 follow-up: commands are decided under their passport and auto mode under the controller's service passport; before: the auth plugins decided alone and the audit row said `none`, see History). Every factory process starts Identity (`startIdentity`, `src/identity/runtime/`).
  - **Runs (G2).** At run start the worker narrows its service passport to a run passport (`src/worker/passports/run-passports.ts`): `actions = [use_tool]`, the item's project, the item, the run, the run's branch (`factory/<item>` or the item's head branch), the run kind's broker tools (the forge tools the worker itself calls for implement, update and resolve; none for review, triage and improve, whose comments outbound delivers since RFC 0015 M7) plus that kind's `tool_grants`, and `audience = tool-broker`. The token stays in the worker process, keyed by run id with the lease token of the claim that minted it, and is dropped when that claim ends; a slot that lost the run cannot drop the passport of the claim that took it over (decision changed 2026-11-09, worker review finding 5). It never reaches the agent, a prompt or the store. `PassportToolBroker` (`src/impl/broker/passport-broker.ts`) wraps every broker the worker pool or an agent's granted tools reach, and checks the token on every call (`check`, offline, audited) before the inner broker sees it: a run with no passport (`passport_missing`), a revoked or expired passport or parent, and a tool, run, item or branch outside it (`passport_denied`) are refused. A tool call that names no branch is checked on the run's own branch. It only adds refusals: the inner broker still checks the lease, the branch prefix and egress. Paths are not a caveat yet: the broker sees no file list, and the worker's scope gate still checks `allowed_paths`. Tier is not a caveat either.
  - **Service passports.** The controller, the worker and outbound act as `service:<name>`, each limited by an `actions` caveat (`controller`: approve_spec, approve_merge; `worker` and `outbound`: use_tool). Only the built-in `service` provider resolves a `service:` principal; a person's proof that resolves to one is refused. A service passport lasts 24 h and is reissued at half-life or once revoked, so a run passport always has 12 h or more ahead. Revoking a service passport ends every run passport narrowed from it; the next run gets a fresh one (to stop a service for good, deny its principal). The worker's and the controller's are used: auto mode's spec approvals and merges are authorized under `service:controller` (`controllerServiceAuth`, `src/impl/auth/audited-auth.ts`) and audited under it; a refusal holds the spec for `/approve` or leaves the change unmerged, with the reason. Outbound gets its own when it acts as itself (M7 follow-up).
  - **Edge** (decision changed 2026-11-09, issue #479: Slack commands are minted at relay too; before: only command rows got a passport, see History). A CLI command row and a UI request row carry the actor's person passport (`inbound_commands.passport_id`). A comment command a poll stored gets one when inbound relays it: its row's `github:<id>` actor resolves through the selected auth plugin's own mapping (`PluginIdentityProvider`, store only, no forge call). A Slack command the listener stored as a stream record (an `/approve` in a thread reply) gets one the same way when inbound relays the record: its actor `slack:<user id>`, origin `slack`. A Slack plain comment and an item request get none. An actor no provider resolves gets none, and the plugin decides alone. `CommandReceived` and `SourceEventReceived` inherit the passport id from `InboundReceived`; the controller puts a Slack command's on the event's actor, checked for expiry at the record's received time. Solo: no Slack account is linked to a factory user unless the owner links it, so Slack commands get no passport. Enterprise: a Slack account linked through the selected auth plugin gets one, and its commands are audited under it.
  - **Commands are decided under their passport.** The command inbox puts a row's passport on the command's identity (`commandIdentity`, `src/core/command-inbox.ts`; an app request's from its row), and the controller's `auth` unit passes it on. `AuditedAuthProvider` wraps each auth plugin (controller and UI): with a passport, Identity's `authorize(passport_id, action, resource, roles)` checks the chain, expiry, revocation and caveats, and that the passport names the principal the plugin resolved (`passport_principal_mismatch` otherwise); the plugin chosen by the command's origin then decides the role with its own grants, as before, so solo needs no setup. One `authz_audit` row holds the decision under the passport. With none (a row from before M9, an actor no provider resolves, the UI's own checks), the plugin decides and the row says `none`. A command's passport is checked for expiry at the time its row was recorded (`CommandPassport.at`, the store's clock) and for revocation now, so a command that waits in its stream longer than the passport's 1 h (a failing command before it, an outage) is still decided under it; a passport revoked meanwhile refuses it. Run passport checks are audited by Identity itself.
  - **Revocation** applies at once in the process that revokes, and on another replica's next `revocations` tick (10 s).
  - **Key.** Solo: one random 32-byte key in the state folder (`passport.key`, mode 0600, created on first use with an exclusive create so concurrent processes agree), on agents' `deny_paths`. Enterprise: a shared rotated key from the SecretStore (`SF_PASSPORT_KEY`) is the plan; not wired yet, so replicas on several hosts need the same file until then.

- **Passports** (2026-11-08, RFC 0015 M9). The service in `src/identity/`; how the running factory uses it is the decision above.
  - **Edge.** An adapter hands Identity a proof once (`authenticate`: provider and stable subject, resolved by an `AuthProvider`). It gets a passport: an id plus an HMAC chain (macaroon style, `node:crypto`) of principal, provider, origin, kind, issue and expiry times, and caveats. Only the token's hash is stored.
  - **Checks.** `authorize(passport_id, action, resource)` checks the chain, its expiry and the deny list (`identity_revocations`). It then checks every link's caveats: project, item, run, branch, paths, tools, audience and actions. A caveat on a field the resource does not name refuses. Last come the `GrantSource` roles, with the legacy rule (any deny wins, `submit_work` is open, local sources first). Every decision goes to `authz_audit`. Authorize by id re-signs the stored chain, so an edited row is refused as `tampered`.
  - **Narrowing.** `narrow` mints run and per-call passports. They can only add caveats and never outlive the parent. The ToolBroker calls `PassportChecker.check(token, ...)`, which verifies the token offline.
  - **Keys and time.** The key comes from a keyring over an injected secret provider (current plus previous keys, for rotation); the passport service never reads a file for it (the solo provider is the key file above). Time is Identity's `revocations` tick (10s), which also reloads the deny list. A passport is accepted up to one tick past its expiry, and another replica's revocation applies on that replica's next tick.
  - **Solo:** the local identity (git `user.email`, else the OS user, else `anonymous`; never `user.name`, which is only the default of the display name setup stores in `identity_profiles`) and `OwnerGrant` (the owner has every role, `anonymous` none). **Enterprise:** any `AuthProvider` (OIDC, SSO) and grant sources, and a shared rotated key in the SecretStore.
- **Chat accounts act as their linked factory user, with its stored role** (decision changed 2026-11-09, issue #498; current). The decision that changed: **a Slack account is judged by the local auth plugin, not the forge's**: its link (`user_links`) gives the factory user, and that user's stored role (`identity_local_users`, plus `static` grants) decides, the same rule and the same refusal text as the CLI ("`<user>` has no role that allows it (`no_role`); the local owner can grant one with `factory users add`"). An unlinked account is refused as not linked. The controller's auth unit sends identities of provider `local` and `slack` to the local plugin and every forge identity to the forge's. Commands typed in Slack and stored as CLI rows act as the linked user ID itself ([05-sources.md](05-sources.md), One command table); other Slack commands (`/budget`, `/verdict`, `/standing`) resolve the link at apply time. Solo: the owner links their Slack account to the local owner and needs nothing else. Enterprise: each person links their own account; the owner grants roles with `factory users add`. Audit rows carry the factory user ID in both. Until #479, Slack writes to users, settings and the mode are refused.
- **Local commands are authorized locally, on any item.** The decision that changed: **a local command on an item of any source, GitHub items included, is judged by the local auth plugin** (2026-11-08; the owner's answer of 2026-11-07). A local owner or approver authorizes `factory approve|retry|revise|reject` on a GitHub item without GitHub write access of their own; a requester or `anonymous` is refused with the local wording ("`<user>` has no role that allows it (`no_role`); the local owner can grant one with `factory users add`"). GitHub is never asked; the bot mirrors the command to the issue through the outbox, best effort ([05-sources.md](05-sources.md), CLI intake). Before it, and still in force: **the auth plugin is chosen per command origin, and local commands never depend on GitHub** (issue #318). Commands from the local CLI (identity provider `local`) and the local UI (app requests) go to the auth plugin for origin `local`; GitHub comments, and every other origin, go to the one for `github_issue`. Config: `auth` stays a string (the plugin for GitHub comments; local commands then use `local`) or becomes `{ "github_issue": "<plugin>", "local": "<plugin>" }` (`github_issue` required, `local` default `local`; any other key fails at startup). The controller holds both (`auth`, `local_auth`); merger, closer and author lookups stay on `auth`.
  - **The `local` plugin** (`LocalAuthProvider`): a local identity `local:<x>`, or a `cli_user` that is already a user ID such as `github:1`, is its own factory user (links still read first); a linked chat account (provider `slack`) resolves to its linked user; other unlinked accounts resolve to no user. Roles come from the store's local users (`LocalUsersGrant`) plus the configured grants that make no remote call (`static`, so its denies still refuse); remote grants (`github-permission`) are never asked, so a GitHub outage or rate limit does not stop a local approval.
  - **Local users**: table `identity_local_users` (user ID, role `owner` | `approver` | `requester`, added by, created at; SQLite migration 26, MySQL step `migrations/mysql/0026-local-users.sql` through `npm run migrate`). `owner_slot` (1 on the owner's row, NULL elsewhere, unique) keeps one owner whatever terminals or replicas race. The first identity to run a writing CLI command, or to be authorized by the local plugin while no owner exists, becomes the owner (`claimLocalOwner`); `local:anonymous` never does. Owner and approver approve; a requester, or a user with no row, only submits work and reads. `factory users list | add <user_id> --role approver|requester | remove <user_id>` (owner only) manage the rows; the owner's row cannot be changed or removed, and `anonymous` cannot be made an approver.
  - **Two setups, one rule.** Solo: zero setup, you are the owner on your first command. Team on a shared store: the first person is the owner and grants others. The identity comes from each person's environment (`cli_user`, git `user.email`, the OS user; docs/design/05-sources.md, CLI intake), which anyone who can run the CLI can set: the terminal and the store's credentials are the trust boundary, as for every other store row. Not built: transferring the owner, linking a local identity to a GitHub account to merge one person's identities for audit (`factory link` with the `gh` ID proof), a Slack origin.
- **Permissions in the factory.** Now:
  - **Factory users and links.** A factory user ID can have several linked provider accounts: table `user_links(provider, subject, user_id)`, unique on provider and subject (SQLite migration 14, MySQL step `migrations/mysql/0014-identity-links.sql`). `resolve` returns the linked user, found by provider and subject only, so a changed display name never changes the user. GitHub user IDs stay `github:<numeric id>`, so existing history keeps its approvers with no rewrite; an unlinked GitHub account still resolves to that ID but has no role unless a grant gives one. An unlinked account of any other provider (Slack, once a Slack source exists) resolves to no user, and its command gets one reply saying the account is not linked, with no store change.
  - **Linking by one-time code.** `factory link-code <user_id>` stores a random 10-character code (50 bits) as its SHA-256 hash in `identity_link_codes` and prints it once. The other account posts `/link <code>`. A code works once and for 10 minutes. A wrong, expired, used or locked code is a failed attempt that links nothing and adds one to every live code's failure count; a code with 5 failures is locked. The code never appears in the store, logs or replies. A redelivered `/link` from the account that used the code reports the same link and changes nothing; an account already linked to another user is refused and the code stays live. `/link` is an account command: listed by `/help` and in SET_UP.md, never in an item footer, and read on any issue. The GitHub source passes it on as a plain comment (it emits events only for item commands), so today it works on issue comments, not on PR conversations.
  - **Grants and one check.** Roles per project (`requester`: `submit_work`; `approver`: every gate action) map onto the existing `AuthAction` values. Grant plugins (kind `grant`, `*.grant.ts` descriptors, selected by the list `permissions.grants`, default `github-permission`) give roles: `github-permission` (write, maintain or admin → approver; triage or read → requester) and `static` (roles per user ID and project in config, plus explicit denies). Grants sit outside the one-per-interface registry because several are selected at once. One shared check, `authorize` in `src/core/authorize.ts`, takes the union of roles minus denies (any deny wins) for the work item's project, with the factory user ID; every command path reaches it through the controller's one `authorize` helper, and only the `github-permission` grant asks GitHub for a permission (tests/grants.test.ts checks both). Local grants are asked before remote ones and the first covering role stops the search, so a static grant costs no GitHub call. `submit_work` stays open to any resolved user unless denied: the intake label remains its gate. Refusals keep today's wording ("needs write permission", with the reason `no_role` or `denied`).
  - **Raised size limits.** The checked-in `max_diff_lines` and `max_diff_files` in `factory.config.json` are 5000 lines and 80 files. The human raised them after eight implement runs failed the 1500/40 gate at 1,666 to 3,364 lines and up to 49 files. Raising a gate is a loosening, so it needs a human merge. The built-in defaults in `src/core/diff-gate.ts` stay 1500 and 40. The split threshold (85% of the caps) moves with them, to 4250 lines or 68 files. The running controller reads the config from the merged main, so it must hold the new numbers before an implement run that needs them, or that PR is blocked by `diff_too_large`.
  - **Not in this change:** links for existing users (none needed while GitHub IDs stay `github:<id>`), a Slack source, OIDC, and a UI for links.

## History

- **Chat accounts act as their linked factory user, with its stored role** (decision changed 2026-11-09, issue #498). Before: Slack accounts were judged by the forge's auth plugin (with `auth: github`, through `github-permission` or `static` grants on the linked user), while the CLI's users and roles lived in the store, so one person could hold two different rights.

- **Local user changes are audited** (decision changed 2026-11-08, issue #445). Before: `factory users` (owner only) was the only way to change local roles, and a removal deleted the `local_users` row with no record of the change, who made it or the old role.
- **Guided setup and display names** (decision changed 2026-11-08). Before: `factory setup` needed a terminal and asked only for secrets (store and plugins were edited by hand in factory.config.json, the mode only through `factory mode`), and no display name was stored anywhere: git `user.name` was not used at all.
- **Passports in the running factory** (decision changed 2026-11-09, M9 follow-up). Before: the auth plugins decided every command and `AuditedAuthProvider` recorded it under passport `none`; auto mode's approvals and merges were checked by nothing.
- **Passports in the running factory** (decision changed 2026-11-08, RFC 0015 M9 wiring). Before: the passport service existed but nothing used it: the ToolBroker checked only the lease, command rows had no passport, nothing was audited to `authz_audit`, and the UI showed user ids only.
- **Passports** (new decision 2026-11-08, RFC 0015 M9). Before: a command's user id went straight to `authorize`, with no signed token, no narrowing for runs, no revocation and no audit of decisions.
- **Local commands are authorized locally, on any item** (decision changed 2026-11-08). Before: local commands were authorized locally but accepted for local items only; on a GitHub item the CLI refused and only a GitHub comment, judged by the GitHub auth plugin, could act.
- **Local commands are authorized locally** (new decision, 2026-11-07, issue #318). Before: one `auth` plugin authorized every origin, so with `auth: github` a CLI command resolved only through a link that no command created, and local items stuck at spec approval while GitHub was the only judge.
- **Permissions in the factory** (decision changed 2026-11-01, issue #107). Before: permissions were GitHub write access only, checked inside the `github` AuthProvider, so a Slack user had no way in and one person's GitHub and Slack accounts were two strangers.
- **Raised size limits** (decision changed 2026-11-01, issue #107). The checked-in limits went from 1500 and 40 to 3000 and 60. The human set them from the size of that change (estimated 1,500 to 2,500 lines in 30 to 45 files).
- **Raised again** (decision changed 2026-11-02). Before: 3000 and 60.
- **Command passport expiry** (decision changed 2026-11-09, review of RFC 0015 M9). Before: a command's passport was checked for expiry when the controller handled the command, so a command that waited over an hour in its stream was refused as `expired`.
- **Edge passports for Slack commands** (decision changed 2026-11-09, issue #479). Before: only command rows got an edge passport; a Slack command the listener stored as a stream record was relayed with none, so the auth plugin alone decided it and the audit row said `none`.
- **Ending a run passport** (decision changed 2026-11-09, worker review finding 5). Before: `end(run)` dropped the run's passport whoever had minted it, so a slot that lost the run in the same process dropped the passport of the claim that took it over, and that claim's broker calls failed `passport_missing`.
