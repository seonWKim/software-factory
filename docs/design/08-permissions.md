# 8. Enterprise: permissions and size limits

- **The auth plugins and the grants are deleted (decision changed 2026-11-13, issue #669, phase B of #575; current).** The decision that changed: **the owner check is the only AuthProvider, and nothing decides roles from grants**, instead of the unused `github`, `local` and `none` auth plugins and the `github-permission` and `static` grants staying in the tree, unselected. The plugin registry has no auth kind and no grant descriptors; `selectPlugins` takes no auth name; the Slack source's taps build `OwnerAuth` itself. Identity decides its own role half without grant sources: a `service:` principal holds the owner role (its passport's `actions` caveat limits it), and an `owner` option, unset in a running factory, gives one principal the owner role in Identity's own tests. Behaviour does not change: commands take the owner check, service principals their passport checks ([auth-provider.md](../plugins/auth-provider.md)).
- **One owner check decides every command (decision changed 2026-11-13, issue #668, phase A of #575; current).** The decision that changed: **every person's command, whatever its origin, passes one owner check** (`authorizeOwner` and `OwnerAuth`, `src/core/authorize.ts`), instead of an auth plugin chosen by the command's origin (`auth`, `local_auth`, `slack_auth`) deciding roles from GitHub write access, `permissions.grants` and the store's local users.
  - **The check.** The caller's identity resolves to a factory user: its linked user first (`user_links`, by provider and subject), else a local identity's own ID (`cli_user`, `local:<git user.email>`, `local:<OS user>`), else `<provider>:<subject>`. That user must be the store's local owner (`identity_local_users`, role `owner`); anyone else is refused with reason `not_owner` and the reply "only the owner may send this command". `local:anonymous` is refused and never claims the owner. A local user ID asked while the store has no owner claims it (`claimLocalOwner`), so solo needs no setup; an account of another provider never claims it. `submit_work` stays open (a work request is not a command; the intake label is its gate), except to an unlinked chat account (`slack:`, `oidc:`), since a chat source has no intake label.
  - **Every caller.** The controller's `auth` unit (comment, Slack, CLI and app-request commands, intake, verdicts, standing rules, PR events, local merges), the command inbox, the local CLI, the dashboard's command checks and pause route, `factory settings`/`factory mode` (approve_merge), `factory session`, and `approve_tool` (`factory pack approve|revoke` and the packs route) all take `OwnerAuth`; approve_tool has no owner-action path of its own. compose builds no auth or grant plugin: `ControllerDeps` has one `auth` (the owner check behind `AuditedAuthProvider`) and no `local_auth` or `slack_auth`. The Slack source's Good, Bad and Feedback taps build `OwnerAuth` too, so they take the same check.
  - **No edge passport.** CLI command rows and dashboard requests carry no `passport_id`, inbound mints none at the relay, and the controller hands Identity none; each gate decision writes one `authz_audit` row with passport `none`. No store migration: the `passport_id` column stays, old rows are not backfilled and their passports are ignored.
  - **Service principals unchanged.** The controller's auto-mode spec approvals and merges (`service:controller`), the worker's run passports and outbound's deliveries (`service:worker`, `service:outbound`) keep their passport checks and never reach the owner check.
  - **Config.** `auth` and `permissions` are no longer settings (`src/config-keys.ts`, the settings catalog, `docs/settings.md`, `PR_ONLY_KEYS`): a file that still has one loads and logs one warning naming it, and `factory setup` removes them. Phase B (#669, the decision above) deleted the auth plugins (`github`, `local`, `none`) and the grant plugins (`github-permission`, `static`); roles and `factory users add|remove` remain for a later change. The Users page lists local users only, with no static rows and no permissions config.
- **`approve_tool`: approving a pack tool is the owner's action (new decision, 2026-11-11, issue #589; current).** The decision that changed: **the actions are `submit_work`, `approve_spec`, `approve_merge`, `record_verdict`, `use_tool` and `approve_tool`**, instead of the first five only. `approve_tool` approves or revokes one description of a pack tool or MCP server (11-packs.md); it is in `AuthAction`, in Identity's `Action` and `ACTIONS`, and so in the `owner` role, and in no other role. Since 2026-11-13 it takes the one owner check above, as every command does: only the store's local owner is allowed, anyone else is refused as `not_owner`. Solo: the CLI identity or the page's user, no external account. The approval row stores the approver's user ID. No per-person approvers are added (One owner, below).
- **One owner (new decision, 2026-11-11, owner decision; current).** The decision that changed: **the factory has one person, its owner, and no roles for anyone else**, instead of a team on a shared store where the first person is the owner and grants roles to others ([08-enterprise.md](08-enterprise.md), One owner, many workers). Identity comes from the environment (`cli_user`, git `user.email`, the OS user); the owner is the person whose identity that is, on one worker or many. Deprecated, to be removed by follow-up issues (numbers added when filed): local users other than the owner and `factory users add|remove`, roles (`approver`, `requester`), grants and the auth plugins `github`, `local` and `none` (deleted 2026-11-13 by phase B of #575, [auth-provider.md](../plugins/auth-provider.md)), and linked accounts for other people. Kept: run passports and the ToolBroker check (they guard a process, not a person), service passports, the owner's own linked accounts, the audit of decisions, and the checked-in size limits. The decisions below still describe the code until the removals land.
- **Local user changes are audited, and the dashboard manages them (new decision, 2026-11-08, issue #445; current).** The decision that changed: **every add, role change and removal of a local user writes one row to `identity_local_user_changes`** (`seq`, `user_id`, `action` `add` | `change` | `remove`, `old_role`, `new_role`, `actor`, `at`), an Identity table: the additive migration `src/identity/migrations/20261109T1300-identity-local-user-changes.migration.ts` (SQLite on open, MySQL through `npm run migrate`; the numbered lists stay frozen at 41). The row is written by Identity's `recordLocalUserChange` (`src/identity/local-users/changes.ts`). The store's `setLocalUserRole` and `removeLocalUser` write it in the same transaction as the change, so `factory users add|remove` and the dashboard's Users page (`POST /api/v1/users`, 09-dashboard-app) write the same row; a refused write (non-owner, the owner's row, a missing user) and a set to the role a user already has write none. The actor is `added_by` for an add or change and the owner for a remove (only the owner may remove; the store interface is unchanged). Removing a user still deletes its `identity_local_users` row; the audit row keeps the record. The page reuses the CLI's `users` actions (`runLocalCli`), so the owner rule, the first-writer-is-owner claim (never `anonymous`), the user ID check and the refusal to make `anonymous` an approver are the CLI's. Solo: rows in the SQLite file; enterprise: rows in the shared MySQL store, each with the person's own actor ID. Not shown on the page yet (follow-up).
- **Setup steps share one frame and can resume** (decision changed 2026-11-10, issue #501; current). The decision that changed: **every `npm run setup` step runs through one step runner** (`runStep`, `src/setup.ts`) instead of some steps asking with a default and others only printing, and **an interrupted run continues where it stopped** instead of starting at step 1.
  - **The frame.** Each step prints `N. Title`, one line on why, its question with the default (Enter takes it), then one `✓` or `✗` result line. A step that ends `✓` without asking anything is a bug, and the runner throws. The steps, in order (`SETUP_STEPS`, `src/cli/handlers/setup/guided.ts`): Store, Plugins, Secret file, Secrets, Database, You, Mode, Setup of the selected plugins, Checks, Canary. Each step's number is its place in that list, so it is the same on every run. A step result may say `stop` (the secret file not written, no database, a FAIL check, a failed canary): setup ends there with exit code 1.
  - **Secrets only when declared.** One Secrets step asks for every secret the selected plugins declare that is missing (or named by `--rotate-*`), in the same run, with hidden input. A `oneOf` group (the model credential) is asked once, for its first member (CLAUDE_CODE_OAUTH_TOKEN), and only when no member is set. MYSQL_PASSWORD is never asked: the Database step generates it. With GitHub off, the `github_auth` plugin's secret (GITHUB_APP_ID or GITHUB_TOKEN) is neither asked nor checked. GitHub off means `local_only`, or the Plugins step's answer `no` when the config diff was declined: the answer is kept in the setup state, and `neededSecrets` and `doctorChecks` take it. Before, a declined diff left GitHub selected in the file, so GITHUB_APP_ID was still asked.
  - **`--yes`** builds no terminal reader at all: every question takes its default, and the hidden prompt refuses. The Secrets step's question defaults to no there, so a missing secret is reported on the `✗` line, never asked.
  - **Progress record.** After each `✓` step, setup writes `<state_dir>/setup-progress.json` (mode 600): `{ "done": [step names], "github": <the GitHub answer> }`, never a secret value. The next run, when the record names a finished step, prints which step the last run stopped before and asks `Continue from step N? [yes] / start over`. `yes` runs from step N (with the recorded GitHub answer); `start over` deletes the record and runs from step 1. A run where every step ended `✓` deletes the record. A run that ends with a `✗` keeps it and says which step to continue from. Code: `src/cli/handlers/setup/progress.ts`. No new setting and no store change: the record is a local file, per machine, for both solo and team (each person runs setup on their own machine).
  - **Check lines.** Each doctor and setup check line says what it checks, and each FAIL says how to fix it, in its text (`(run: …)`) or, when the text is outside text reported as it came (an error, a version), in the check's `fix` (`claude CLI: not found (fix: install Claude Code …)`). Doctor marks lines `ok`/`warn`/`FAIL`; setup's Checks step marks them `✓`/`!`/`✗` (`markedLine`). The ANTHROPIC_API_KEY line reads `ANTHROPIC_API_KEY not set (good: agents use CLAUDE_CODE_OAUTH_TOKEN)`, and when set, a FAIL that says to run `unset ANTHROPIC_API_KEY`. The status page shows the same text, without the `fix` part.
- **Guided setup and display names** (decision changed 2026-11-08, owner decision; before: `factory setup` asked only for secrets, needed a terminal, and stored no name for anyone, see History). The step order, the secret steps and the progress record changed on 2026-11-10 (above).
  - **Guided flow.** `factory setup` asks for the store (`sqlite` | `mysql`) and the plugins (GitHub sync yes/no, Slack threads yes/no plus channel IDs) first, then the steps listed above. Each question shows its default and Enter takes it. The default is the file's current choice, and the solo default (SQLite, local only, no Slack) when the file lists no sources yet, so a rerun changes nothing. `--yes` takes every default without reading the terminal (scripts, tests): a missing secret is reported, never asked, and the MySQL root password is not asked. `--rotate-github|claude|mysql` work as before. Code: `src/cli/handlers/setup/` (`guided.ts`, `ask.ts`, `config-edit.ts`, `me.ts`, `progress.ts`); the runner and the secret file, plugin setup, checks and canary steps are in `src/setup.ts`.
  - **Shared choices go to factory.config.json**, shown first as a `-`/`+` diff of the top-level keys that change (`store`, `plugins`, `slack`, and the removal of a leftover `auth` or `permissions`), then written after a yes (`--yes` writes). Only those keys' text changes; every other line stays as written. The file is reloaded through the config check, and put back if the check refuses it. Local only means `plugins.source: ["local"]` and `plugins.broker: "local"`, so `selectsGitHub` is false. `mode` and `auto_merge_max_tier` are runtime settings, not file keys (08-settings): setup sets a changed one through `factory settings set`, with its approve_merge check and audit row, and prints the command to run later when that is refused (no project key stored yet).
  - **Your identity.** The ID is unchanged: `cli_user`, else `local:<git user.email>`, else `local:<OS user>`, else `local:anonymous` (05-sources, CLI intake). Setup asks for a display name, prefilled from the stored one, else git `user.name`. Git's `user.name` is only this default and is never an ID. The name is stored **once**, in Identity's `identity_profiles` (user ID, display name, source `self` or the provider, updated at; migration `src/identity/migrations/20261108T2345-identity-profiles`). Every other table keeps IDs only. The CLI and the UI look a name up at the edge: `factory users list` shows `ID (name)`; the status page shows `name (ID)` where it showed an ID (item timeline actor, pause holders), and the API adds `actor.name` and `merged_by_name` beside the IDs (`src/ui/names.ts`; M9 wiring, 2026-11-08). A table of its own, not a `display_name` column on `identity_local_users` (the target schema has no profile table): that table lists role holders (a row means a role, and `users remove` deletes it), but a person with no role yet and an enterprise user (`github:`, `oidc:`) with no local row also have a name. `local:anonymous` stores no name.
  - **Many users.** `factory setup --me` only registers the current person (ID and display name), touching neither factory.config.json nor the secret file. The first person to register, or to run a writing command, becomes the owner, as before (`claimLocalOwner`). Anyone later has no role (read and create only, like `anonymous`) until the owner runs `factory users add <id> --role approver|requester`; setup prints that command.
  - **Enterprise.** An `AuthProvider` may implement `displayName(identity)`: `authenticate` then stores the name it returns against the principal (source = the provider). A name the person chose (`self`) is never replaced by a provider's. No provider implements it yet (OIDC and GitHub will supply the name at login).
  - **`narrow` stays internal.** `PassportService.narrow` is called only from `src/worker/` (run passports) and `src/identity/`; it is never a tool, an HTTP route or a CLI command. `tests/architecture/passport.test.ts` enforces it, with a negative fixture, and has no exemption list.

- **Passports in the running factory** (decision changed 2026-11-09, RFC 0015 M9 follow-up: commands are decided under their passport and auto mode under the controller's service passport; before: the auth plugins decided alone and the audit row said `none`, see History). Every factory process starts Identity (`startIdentity`, `src/identity/runtime/`).
  - **Runs (G2).** At run start the worker narrows its service passport to a run passport (`src/worker/passports/run-passports.ts`): `actions = [use_tool]`, the item's project, the item, the run, the run's branch (`factory/<item>` or the item's head branch), the run kind's broker tools (the forge tools the worker itself calls for implement, update and resolve; none for review, triage and improve, whose comments outbound delivers since RFC 0015 M7) plus that kind's `tool_grants`, and `audience = tool-broker`. The token stays in the worker process, keyed by run id with the lease token of the claim that minted it, and is dropped when that claim ends; a slot that lost the run cannot drop the passport of the claim that took it over (decision changed 2026-11-09, worker review finding 5). It never reaches the agent, a prompt or the store. `PassportToolBroker` (`src/impl/broker/passport-broker.ts`) wraps every broker the worker pool or an agent's granted tools reach, and checks the token on every call (`check`, offline, audited) before the inner broker sees it: a run with no passport (`passport_missing`), a revoked or expired passport or parent, and a tool, run, item or branch outside it (`passport_denied`) are refused. A tool call that names no branch is checked on the run's own branch. It only adds refusals: the inner broker still checks the lease, the branch prefix and egress. Paths are not a caveat yet: the broker sees no file list, and the worker's scope gate still checks `allowed_paths`. Tier is not a caveat either.
  - **Service passports.** The controller, the worker and outbound act as `service:<name>`, each limited by an `actions` caveat (`controller`: approve_spec, approve_merge; `worker` and `outbound`: use_tool). Only the built-in `service` provider resolves a `service:` principal; a person's proof that resolves to one is refused. A service passport lasts 24 h and is reissued at half-life or once revoked, so a run passport always has 12 h or more ahead. Revoking a service passport ends every run passport narrowed from it; the next run gets a fresh one (to stop a service for good, deny its principal). The worker's and the controller's are used: auto mode's spec approvals and merges are authorized under `service:controller` (`controllerServiceAuth`, `src/impl/auth/audited-auth.ts`) and audited under it; a refusal holds the spec for `/approve` or leaves the change unmerged, with the reason. Outbound gets its own when it acts as itself (M7 follow-up).
  - **Edge and commands** (decision changed 2026-11-13: no edge passport; see the owner check above and History). Commands carry no person passport: `AuditedAuthProvider` wraps the owner check and writes one `authz_audit` row per decision with passport `none`. Run passport checks are audited by Identity itself.
  - **Revocation** applies at once in the process that revokes, and on another replica's next `revocations` tick (10 s).
  - **Key.** Solo: one random 32-byte key in the state folder (`passport.key`, mode 0600, created on first use with an exclusive create so concurrent processes agree), on agents' `deny_paths`. Enterprise: a shared rotated key from the SecretStore (`SF_PASSPORT_KEY`) is the plan; not wired yet, so replicas on several hosts need the same file until then.

- **Passports** (2026-11-08, RFC 0015 M9). The service in `src/identity/`; how the running factory uses it is the decision above.
  - **Edge.** An adapter hands Identity a proof once (`authenticate`: provider and stable subject, resolved by an `AuthProvider`). It gets a passport: an id plus an HMAC chain (macaroon style, `node:crypto`) of principal, provider, origin, kind, issue and expiry times, and caveats. Only the token's hash is stored.
  - **Checks.** `authorize(passport_id, action, resource)` checks the chain, its expiry and the deny list (`identity_revocations`). It then checks every link's caveats: project, item, run, branch, paths, tools, audience and actions. A caveat on a field the resource does not name refuses. Last comes the role: `submit_work` is open; any other action needs the owner role, which a `service:` principal holds (and, in Identity's own tests, the principal its `owner` option names). Every decision goes to `authz_audit`. Authorize by id re-signs the stored chain, so an edited row is refused as `tampered`.
  - **Narrowing.** `narrow` mints run and per-call passports. They can only add caveats and never outlive the parent. The ToolBroker calls `PassportChecker.check(token, ...)`, which verifies the token offline.
  - **Keys and time.** The key comes from a keyring over an injected secret provider (current plus previous keys, for rotation); the passport service never reads a file for it (the solo provider is the key file above). Time is Identity's `revocations` tick (10s), which also reloads the deny list. A passport is accepted up to one tick past its expiry, and another replica's revocation applies on that replica's next tick.
  - **Solo:** the local identity (git `user.email`, else the OS user, else `anonymous`; never `user.name`, which is only the default of the display name setup stores in `identity_profiles`) and the `owner` option (that principal has every role, `anonymous` none). **Enterprise:** any `AuthProvider` (OIDC, SSO) and a shared rotated key in the SecretStore.
- **Local users and links** (kept until phase B of #575; who may act is the owner check above).
  - **Local users**: table `identity_local_users` (user ID, role `owner` | `approver` | `requester`, added by, created at; SQLite migration 26, MySQL step `migrations/mysql/0026-local-users.sql` through `npm run migrate`). `owner_slot` (1 on the owner's row, NULL elsewhere, unique) keeps one owner whatever terminals or replicas race. The first local identity to run a writing CLI command, or to be asked by the owner check while no owner exists, becomes the owner (`claimLocalOwner`); `local:anonymous` never does. Since 2026-11-13 only the owner approves; an approver or requester row allows nothing more than no row (the owner check above). `factory users list | add <user_id> --role approver|requester | remove <user_id>` (owner only) manage the rows; the owner's row cannot be changed or removed, and `anonymous` cannot be made an approver.
  - **One owner.** Zero setup: you are the owner on your first command, on one worker or many. The identity comes from the environment (`cli_user`, git `user.email`, the OS user; docs/design/05-sources.md, CLI intake), which anyone who can run the CLI can set: the terminal and the store's credentials are the trust boundary, as for every other store row. Not built: transferring the owner, linking a local identity to a GitHub account (`factory link` with the `gh` ID proof), a Slack origin.
- **Permissions in the factory.** Now:
  - **Factory users and links.** A factory user ID can have several linked provider accounts: table `user_links(provider, subject, user_id)`, unique on provider and subject (SQLite migration 14, MySQL step `migrations/mysql/0014-identity-links.sql`). `resolve` returns the linked user, found by provider and subject only, so a changed display name never changes the user. GitHub user IDs stay `github:<numeric id>`, so existing history keeps its approvers with no rewrite; an unlinked GitHub account still resolves to that ID but has no role unless a grant gives one. An unlinked account of any other provider (Slack, once a Slack source exists) resolves to no user, and its command gets one reply saying the account is not linked, with no store change.
  - **Linking by one-time code.** `factory link-code <user_id>` stores a random 10-character code (50 bits) as its SHA-256 hash in `identity_link_codes` and prints it once. The other account posts `/link <code>`. A code works once and for 10 minutes. A wrong, expired, used or locked code is a failed attempt that links nothing and adds one to every live code's failure count; a code with 5 failures is locked. The code never appears in the store, logs or replies. A redelivered `/link` from the account that used the code reports the same link and changes nothing; an account already linked to another user is refused and the code stays live. `/link` is an account command: listed by `/help` and in SET_UP.md, never in an item footer, and read on any issue. The GitHub source passes it on as a plain comment (it emits events only for item commands), so today it works on issue comments, not on PR conversations.
  - **Grants** (`github-permission`, `static`, selected by `permissions.grants`) were deleted on 2026-11-13: the owner check above replaced them (History).
  - **Raised size limits.** The checked-in `max_diff_lines` and `max_diff_files` in `factory.config.json` are 5000 lines and 80 files. The human raised them after eight implement runs failed the 1500/40 gate at 1,666 to 3,364 lines and up to 49 files. Raising a gate is a loosening, so it needs a human merge. The built-in defaults in `src/core/diff-gate.ts` stay 1500 and 40. The split threshold (85% of the caps) moves with them, to 4250 lines or 68 files. The running controller reads the config from the merged main, so it must hold the new numbers before an implement run that needs them, or that PR is blocked by `diff_too_large`.
  - **Not in this change:** links for existing users (none needed while GitHub IDs stay `github:<id>`), a Slack source, OIDC, and a UI for links.
