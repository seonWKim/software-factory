# 8. Enterprise: permissions and size limits

- **Local user changes are audited, and the dashboard manages them (new decision, 2026-11-08, issue #445; current).** The decision that changed: **every add, role change and removal of a local user writes one row to `local_user_changes`** (`seq`, `user_id`, `action` `add` | `change` | `remove`, `old_role`, `new_role`, `actor`, `at`; SQLite migration 42, MySQL step `migrations/mysql/0042-local-user-changes.sql`). The store's `setLocalUserRole` and `removeLocalUser` write it in the same transaction as the change, so `factory users add|remove` and the dashboard's Users page (`POST /api/v1/users`, 09-dashboard-app) write the same row; a refused write (non-owner, the owner's row, a missing user) and a set to the role a user already has write none. The actor is `added_by` for an add or change and the owner for a remove (only the owner may remove; the store interface is unchanged). Removing a user still deletes its `local_users` row; the audit row keeps the record. The page reuses the CLI's `users` actions (`runLocalCli`), so the owner rule, the first-writer-is-owner claim (never `anonymous`), the user ID check and the refusal to make `anonymous` an approver are the CLI's. Solo: rows in the SQLite file; enterprise: rows in the shared MySQL store, each with the person's own actor ID. Not shown on the page yet (follow-up).
- **Local commands are authorized locally, on any item.** The decision that changed: **a local command on an item of any source, GitHub items included, is judged by the local auth plugin** (2026-11-08; the owner's answer of 2026-11-07). A local owner or approver authorizes `factory approve|retry|revise|reject` on a GitHub item without GitHub write access of their own; a requester or `anonymous` is refused with the local wording ("`<user>` has no role that allows it (`no_role`); the local owner can grant one with `factory users add`"). GitHub is never asked; the bot mirrors the command to the issue through the outbox, best effort ([05-sources.md](05-sources.md), CLI intake). Before it, and still in force: **the auth plugin is chosen per command origin, and local commands never depend on GitHub** (issue #318). Commands from the local CLI (identity provider `local`) and the local UI (app requests) go to the auth plugin for origin `local`; GitHub comments, and every other origin, go to the one for `github_issue`. Config: `auth` stays a string (the plugin for GitHub comments; local commands then use `local`) or becomes `{ "github_issue": "<plugin>", "local": "<plugin>" }` (`github_issue` required, `local` default `local`; any other key fails at startup). The controller holds both (`auth`, `local_auth`); merger, closer and author lookups stay on `auth`.
  - **The `local` plugin** (`LocalAuthProvider`): a local identity `local:<x>`, or a `cli_user` that is already a user ID such as `github:1`, is its own factory user (links still read first); other providers resolve to no user. Roles come from the store's local users (`LocalUsersGrant`) plus the configured grants that make no remote call (`static`, so its denies still refuse); remote grants (`github-permission`) are never asked, so a GitHub outage or rate limit does not stop a local approval.
  - **Local users**: table `local_users` (user ID, role `owner` | `approver` | `requester`, added by, created at; SQLite migration 26, MySQL step `migrations/mysql/0026-local-users.sql` through `npm run migrate`). `owner_slot` (1 on the owner's row, NULL elsewhere, unique) keeps one owner whatever terminals or replicas race. The first identity to run a writing CLI command, or to be authorized by the local plugin while no owner exists, becomes the owner (`claimLocalOwner`); `local:anonymous` never does. Owner and approver approve; a requester, or a user with no row, only submits work and reads. `factory users list | add <user_id> --role approver|requester | remove <user_id>` (owner only) manage the rows; the owner's row cannot be changed or removed, and `anonymous` cannot be made an approver.
  - **Two setups, one rule.** Solo: zero setup, you are the owner on your first command. Team on a shared store: the first person is the owner and grants others. The identity comes from each person's environment (`cli_user`, git `user.email`, the OS user; docs/design/05-sources.md, CLI intake), which anyone who can run the CLI can set: the terminal and the store's credentials are the trust boundary, as for every other store row. Not built: transferring the owner, linking a local identity to a GitHub account to merge one person's identities for audit (`factory link` with the `gh` ID proof), a Slack origin.
- **Permissions in the factory.** Now:
  - **Factory users and links.** A factory user ID can have several linked provider accounts: table `user_links(provider, subject, user_id)`, unique on provider and subject (SQLite migration 14, MySQL step `migrations/mysql/0014-identity-links.sql`). `resolve` returns the linked user, found by provider and subject only, so a changed display name never changes the user. GitHub user IDs stay `github:<numeric id>`, so existing history keeps its approvers with no rewrite; an unlinked GitHub account still resolves to that ID but has no role unless a grant gives one. An unlinked account of any other provider (Slack, once a Slack source exists) resolves to no user, and its command gets one reply saying the account is not linked, with no store change.
  - **Linking by one-time code.** `factory link-code <user_id>` stores a random 10-character code (50 bits) as its SHA-256 hash in `link_codes` and prints it once. The other account posts `/link <code>`. A code works once and for 10 minutes. A wrong, expired, used or locked code is a failed attempt that links nothing and adds one to every live code's failure count; a code with 5 failures is locked. The code never appears in the store, logs or replies. A redelivered `/link` from the account that used the code reports the same link and changes nothing; an account already linked to another user is refused and the code stays live. `/link` is an account command: listed by `/help` and in SET_UP.md, never in an item footer, and read on any issue. The GitHub source passes it on as a plain comment (it emits events only for item commands), so today it works on issue comments, not on PR conversations.
  - **Grants and one check.** Roles per project (`requester`: `submit_work`; `approver`: every gate action) map onto the existing `AuthAction` values. Grant plugins (kind `grant`, `*.grant.ts` descriptors, selected by the list `permissions.grants`, default `github-permission`) give roles: `github-permission` (write, maintain or admin → approver; triage or read → requester) and `static` (roles per user ID and project in config, plus explicit denies). Grants sit outside the one-per-interface registry because several are selected at once. One shared check, `authorize` in `src/core/authorize.ts`, takes the union of roles minus denies (any deny wins) for the work item's project, with the factory user ID; every command path reaches it through the controller's one `authorize` helper, and only the `github-permission` grant asks GitHub for a permission (tests/grants.test.ts checks both). Local grants are asked before remote ones and the first covering role stops the search, so a static grant costs no GitHub call. `submit_work` stays open to any resolved user unless denied: the intake label remains its gate. Refusals keep today's wording ("needs write permission", with the reason `no_role` or `denied`).
  - **Raised size limits.** The checked-in `max_diff_lines` and `max_diff_files` in `factory.config.json` are 5000 lines and 80 files. The human raised them after eight implement runs failed the 1500/40 gate at 1,666 to 3,364 lines and up to 49 files. Raising a gate is a loosening, so it needs a human merge. The built-in defaults in `src/core/diff-gate.ts` stay 1500 and 40. The split threshold (85% of the caps) moves with them, to 4250 lines or 68 files. The running controller reads the config from the merged main, so it must hold the new numbers before an implement run that needs them, or that PR is blocked by `diff_too_large`.
  - **Not in this change:** links for existing users (none needed while GitHub IDs stay `github:<id>`), a Slack source, OIDC, and a UI for links.

## History

- **Local user changes are audited** (decision changed 2026-11-08, issue #445). Before: `factory users` (owner only) was the only way to change local roles, and a removal deleted the `local_users` row with no record of the change, who made it or the old role.
- **Local commands are authorized locally, on any item** (decision changed 2026-11-08). Before: local commands were authorized locally but accepted for local items only; on a GitHub item the CLI refused and only a GitHub comment, judged by the GitHub auth plugin, could act.
- **Local commands are authorized locally** (new decision, 2026-11-07, issue #318). Before: one `auth` plugin authorized every origin, so with `auth: github` a CLI command resolved only through a link that no command created, and local items stuck at spec approval while GitHub was the only judge.
- **Permissions in the factory** (decision changed 2026-11-01, issue #107). Before: permissions were GitHub write access only, checked inside the `github` AuthProvider, so a Slack user had no way in and one person's GitHub and Slack accounts were two strangers.
- **Raised size limits** (decision changed 2026-11-01, issue #107). The checked-in limits went from 1500 and 40 to 3000 and 60. The human set them from the size of that change (estimated 1,500 to 2,500 lines in 30 to 45 files).
- **Raised again** (decision changed 2026-11-02). Before: 3000 and 60.
