# 8. Operations: routines

- **Routine runs are planned only by the schedule path; the routine tables have a removal plan (decision changed 2026-11-25, local-task-tk_3ec69bb2 phase 3 of 3; current; replaces "the kernel reads each due routine's plan (`routinePlans`)" in Runs and Run now below, see [History](#history)).** A routine is a Check a page schedule row (design [08-schedules](08-schedules.md)), so the schedule unit's claim pass (`runDueCheckPages`, `src/core/routines.ts`) plans each due routine with `planRoutine` and the `routed` action's `check_page` route queues its run. The kernel's `routinePlans` and its `routine_fire` and `routine_hold` writes are removed, and the routines unit has no step; it keeps its operations (findings, the hold answers, suggestion answers). The routine store, API, CLI and page and their responses are unchanged.
  - **Caps.** As before: a run over `run_cap_usd` pauses the routine; a due run past `daily_cap_usd` is held on a local item for `/approve` or `/reject`. New: the schedule row's token cap holds an occurrence at a checkpoint, as for agent and feedback schedules, and a finished run's tokens and cost go on its slot's schedule run row.
  - **Needs the action.** A routine runs only when `plugins.schedule_action` is `routed` (the repo's config selects it), as every schedule does.
  - **Removal plan for the routine tables.** `controller_routines` and `controller_routine_suggestions` have had no reader or writer since phase 2 (only their migrations and `table-docs.ts` name them). 1. This change: nothing reads or writes them; they stay so a downgrade to a release before phase 2 still finds its rows. 2. A later item adds a breaking migration that first checks every `controller_routines` row has a `check_page` schedule row with its ID and every suggestion its `controller_schedule_suggestions` row (it refuses, dropping nothing, when one is missing), then drops both tables, and removes their entries from `src/controller/table-docs.ts`. 3. The migrations that made and copied them (`20261120T1001`, `20261124T1100`, `20261125T1000`) and their tests stay, as every applied migration does.
- **The routine API and the Routines page are built (decision changed 2026-11-24, local-task-tk_956892cd phase 3, phase 4 of 4; current; replaces "suggestions and Run now are not on the page yet", see [History](#history)).** The page is described in [09-dashboard-routines.md](09-dashboard-routines.md): a table with a detail card, a paused-routine Notice, and New, Edit and Delete in a Dialog. Its row menu has Run now, Edit, Pause or Resume, and Delete; its detail card shows next run, last run, the instruction, page, time zone, the caps and the routine's suggestions (read only: text and state). Accept, dismiss and snooze of a suggestion, and Run now for trigger routines, are not on the page. The API: `src/ui/routines-api.ts`, shaped as the schedules API (design [08-schedules](08-schedules.md)) and reached through the route tables (`src/ui/read-routes.ts`, `src/ui/write-routes.ts`), so `src/ui/server.ts` has no line for it.
  - **Reads.** `GET /api/v1/routines`: every routine, oldest first. `GET /api/v1/routines/suggestions?routine=<id>`: that routine's suggestions; 400 without the parameter, 404 for an unknown ID.
  - **Writes.** `POST /api/v1/routines/add`, `/edit`, `/pause`, `/resume`, `/delete` and `/run` take a JSON body with `id` and, for add and edit, the routine's fields (`name`, `instruction`, `url`, `schedule` as `{ kind, spec }`, `zone`, `trigger`, `run_cap_usd`, `daily_cap_usd`; an add without `zone` is in UTC). After the write guards, a body that is not an object, or has an unknown or wrongly typed field, is a 400 before any store call; anyone but the owner a 403; a refusal of the core (`writeRoutine`, `src/core/routines.ts`) a 409 with its reason; else 200 with the routine (as it was, for a delete).
  - **Decisions.** Each write reads the routine and writes once, conditional on the marks it read (`updateRoutine`, or `editRoutine` for the fields). An ID already stored refuses an add; an unknown ID refuses every other write (`no routine <id>`). An edit merges the fields given and must still pass `routineProblem`; a changed schedule, zone or trigger on an unpaused routine moves `next_due_at` to its first slot after now (none for a trigger routine), and a paused routine stays paused. Pause refuses a paused routine; resume refuses one that is not paused and moves a scheduled routine's slot to its first after now. Delete removes the routine and its suggestions in one transaction (`deleteRoutine`); its runs stay on its carrier item.
  - **Run now.** It sets a scheduled routine's `next_due_at` to now, and nothing else: the schedule claim pass (`dueSlot`, `runDueCheckPages`) fires it on the next tick and `afterSlot` moves the regular slot on, so there is no second path. A paused routine refuses it, and so does a trigger routine, which has no next slot to move.
  - Not built: closing a deleted routine's open cap-hold item, a Run now for trigger routines.
- **A routine runs an owner's instruction on a schedule or a trigger, and its findings come back as suggestions (decided 2026-11-24, local-task-tk_956892cd phase 2 of 3; current; a new decision, none replaced).** A routine is an owner-set instruction (and an optional http(s) page) that the factory runs as a read-only `routine` run. This phase is the store, the scheduler, the suggestions and the caps.
  - **Tables.** One additive migration (`src/controller/migrations/20261120T1001-controller-routines.migration.ts`; 20261120T1000 was taken by attachments, so it moved to the next free minute, design 04-triage): `controller_routines` (one row per routine: form, caps, today's cap raise, marks `next_due_at` and `last_run_at`, `paused`) and `controller_routine_suggestions` (one row per finding, unique on `(routine_id, fingerprint)`). No backfill and no row created. States are plain text, so a later state adds no migration. The store methods are on `RoutineStore` (`src/core/routines.ts`), built in `src/impl/store/sql/routines.ts`.
  - **Form.** A routine has a schedule (a cadence in a zone, `src/core/schedule-cadence.ts`) or a trigger, never both and never neither: `routineProblem` refuses either, and nothing is stored. The only trigger is `merge`: a change merged into the base branch since the routine's last run (or, before any, since it was made), read from the merge evaluations. Why only one: it is the only event the owner's request named; another adds a value to `ROUTINE_TRIGGERS`.
  - **Time.** Every slot and mark is computed by pure functions in `src/core/routines.ts` (`firstDue`, `dueSlot`, `afterSlot`, `planRoutine`) from a time passed in, which the caller reads from the injected `Clock`; tests drive each form with a fake clock.
  - **Runs.** The schedule claim pass plans each unpaused due routine (since 2026-11-25, above). A fire queues one run on the routine's carrier item (a local system item no stage moves), keyed `routine:<id>:<slot>`, so a second fire of one slot queues nothing. Routine runs count in spend (design [06-spend](06-spend.md)).
  - **Caps.** In USD, from each run's harness cost. A finished run that cost more than `run_cap_usd` pauses its routine. A due run that would take the routine's spend for the UTC day past `daily_cap_usd` is held: the claim pass files a local hold item, keyed on routine and slot, that waits for the owner (`blocked_on: human`, `blocked_reason: routine_cap`) with today's spend, the last run's cost and the cap. A held slot waits for its answer even across a UTC day boundary.
  - **`/approve` and `/reject` on a held item.** The shared commands answer it, with no per-cap command (the owner's rule: a factory limit holds the work and asks through `/approve` and `/reject`). `/approve` raises the routine's cap for the current UTC day by the last run's cost, once per hold item, and the next tick runs the held slot. `/reject` skips the slot. Either way the cap still holds: a later slot over it is held again. Any other command on a hold item is refused with what it takes.
  - **Suggestions.** Each finding of a finished run passes the G5 egress scan before it is stored; a flagged finding is withheld (logged as a count), with no override. A clean finding is stored as a `pending` suggestion. Its fingerprint is its text lowercased, whitespace collapsed and end punctuation dropped, hashed; a finding whose fingerprint the routine already holds is a duplicate: skipped and counted on the stored row. A run's findings are recorded once, so a handler run twice adds nothing.
  - **Answers.** Accept files the suggestion through the first configured source that can file (`fileIssue`, the kernel's `filingSource`), scanned (G5) first and keyed on its marker, and stores the filed ref; with no source that can file, it stays pending. Dismiss closes it. Snooze hides it for 14 days (`SNOOZE_MS`); then it is pending again.
  - Not built: `factory approve <id>` on a hold item (the CLI's own pre-check refuses it; a comment or inbox `/approve` works), triggers other than `merge`.
