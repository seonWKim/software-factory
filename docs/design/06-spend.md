# 6. Measurement: spend and spend budgets

- **A coordinator cycle stores its spend and stops at the daily limit with one owner question (decision changed 2026-11-27, local-task-tk_f8e0e9d6 phase 2 of 3; current; replaces "no code records a `coordinator` row yet, and no cycle reads the limit" in the kind decision below, see History).** The decision that changed: **whether the coordinator's spend is recorded and its limit enforced.** Each cycle that calls the agent stores exactly one `controller_chat_spend` row of kind `coordinator` (`CoordinatorStore.recordSpend`, `src/coordinator/store.ts`): `turn_id` the cycle id, `session_id` `coordinator`, the UTC day, the cost from the runner's own report (`usage.cost_usd`, null when it gave none or the call failed) and the tokens; keyed on the cycle id, so a rerun stores nothing more. Each such cycle also stores one Activity record (job `coordinator`, actor `system:coordinator`, `src/controller/background-jobs.ts`; `CoordinatorStore.recordActivity` writes it over the same SQL database as the spend row, only when the spend row was new, so the controller unit reaches no store) whose reason gives the cost and today's coordinator spend against the limit. Today's spend (`spendOn`) adds only known costs; rows with no cost add nothing and are named in the Activity reason. Before the agent call, the cycle compares today's spend with `spend.coordinator_daily_usd`: at or over it, the cycle stores one skipped `cycle` row naming the limit, calls no agent, and, on the UTC day's first such stop only, raises the owner question. The question is raised before the stop row is stored, so a failure between the two writes raises it again on the next stop (the store's one-day dedupe on the key adds nothing twice). **The question** is one Needs-you alert (built by `coordinatorLimitAlert`, `src/core/alarms.ts`; the coordinator unit scans its text and stores it through the kernel's `alert` write), pattern `coordinator_limit`, key `coordinator_limit:<UTC day>`, so exactly one per UTC day, answered or not (an answer dismisses it, which would lift the store's dedupe, so the cycle counts the day's earlier limit stops instead); its text gives the day's spend, the current limit and the proposed limit (twice the current one). **The answer** uses the common commands, with no limit-specific one: `approve <usd>` and `reject` with no item ID (`factory approve 10`, `factory reject`) answer only the question of the current UTC day (`coordinatorLimitAnswer`, `src/core/spend.ts`), while it is not dismissed; an earlier day's question takes no answer, and a bare `approve` with no amount settles a held skill version first (design 07), else is refused naming the amount it needs. The CLI checks the amount and the owner, then stores one command row naming the question's key; the controller's commands unit (`answerLimit`) checks the owner as `/approve` does (the auth unit's `approve_spec`) and the question again, then commits one `coordinator_limit_answer` write: `approve` sets `spend.coordinator_daily_usd` through the settings path (`setSettingOverride` with the owner as actor, one audit row), so cycles run again once today's spend is below the new limit; `reject` changes no setting, so cycles stay stopped until the UTC day ends. Either answer dismisses the alert by the owner, so the decision and its result stay on the alert. Not built: an API capability for the answer (it is CLI-only, as the held skill version's answer is). Not built: the Spend page, the budget alerts and `GET /api/v1/spend` still do not show coordinator spend; no backfill. Why: the coordinator calls the model on its own, so its cost must be counted, and a limit reached needs the owner's word, not a silent stop.

- **Spend rows have a kind, `chat` or `coordinator`, and the coordinator has a daily limit setting (decision changed 2026-11-27, local-task-tk_f8e0e9d6 phase 1 of 3; current; extends "Chat turns are counted apart, under `chat`" below, see History).** The decision that changed: **what a `controller_chat_spend` row is.** It was always a chat turn; it now carries `kind`, `chat` (a chat turn) or `coordinator` (a coordinator cycle's model calls); the column's check refuses any other kind. The migration `20261127T1000-state-coordinator-spend` is additive: the column defaults to `chat`, so every stored row reads `chat` with no backfill. The chat totals (`listChatSpendBetween`, so `readSpend`'s `chat` total) read only `chat` rows. `spend.coordinator_daily_usd` (type `usd`, owner controller, set at runtime, global, default 5) is the coordinator's daily limit in dollars per UTC day: unset it reads 5, it takes a positive amount, and it refuses null, zero and negative amounts (a limit, never "no budget"). It sits next to the spend budgets in the Limits group of Settings > Advanced. Since phase 2 (above) each cycle that calls the agent records its row and every cycle reads the limit; the Spend page, the budget alerts and `GET /api/v1/spend` do not show coordinator spend. Why: the coordinator calls the model on its own every cycle, and its spend needs a place apart from chat and a limit of its own.

- **The daily chart explains each day and filters the tasks (decision changed 2026-11-16; current; replaces "one daily bar chart" with a native title per bar and the most costly day's amount as the middle x-axis label, see History).** The decision that changed: **the chart's bars, axes and what a bar does.** Why: the owner's screenshot (2026-11-15) showed a small "2026-11-07: $568.79" box over the x-axis and "$568.79" between two dates, which read like a date.
  - **Tooltip.** Hover or keyboard focus on a bar shows a tooltip above it (the shared `Tooltip`, `web/src/components/ui/menu.tsx`): the date, cost, number of runs, tokens, the runs with no cost when there are any, and the day's top 3 items by known cost, each with its title linking to its item page. The Tooltip stays open while the pointer or focus is inside it, so its links work; Esc closes it. Bars near the chart's edges align it to that edge so it stays on the page.
  - **Top items per day.** `GET /api/v1/spend` gives each day `top`: at most 3 items (`SPEND_DAY_TOP` in `src/core/spend.ts`) ranked by their known cost that day, then by ID, each `work_item_id`, `title` (through the Withholder) and `cost_usd`. A run with no stored cost adds nothing there, and an item with only such runs that day is not listed. Built from the runs `readSpend` already reads; titles are read once per item for the table and the days together.
  - **Axes.** The y-axis shows 3 cost labels (the most a day cost at the top, half of it, $0), each with a dashed gridline across the chart; only $0 when nothing cost anything. The x-axis shows only the first and last dates of the range, never a cost.
  - **Click filter.** A bar is a `Button` (ghost); clicking it, or Enter or Space, picks the day and loads `GET /api/v1/spend?from=<day>&to=<day>` for the "Tasks by cost" table only; totals and the chart keep the 30-day read. Clicking the picked bar again, or "Show all days", shows all days again. The pick stays in the browser (no URL or store state).
  - **Colours.** Token classes only (`bg-accent`, `border-border`, the Tooltip's `bg-text-1`/`text-surface`, links in the text colour, underlined); the design system has no chart or dataviz tokens, so none were added.

- **Chat turns are counted apart, under `chat` (decision changed 2026-11-26, local-task-tk_eea9af6d phase 2 of 2; current; replaces "no table of its own" and "not built: the LLM provider's own calls" in the Source and Not built bullets below, see History).** The decision that changed: **where spend is read from.** Runs still come from their stored outcomes. A chat turn is no run, so each turn stores one `controller_chat_spend` row (turn id, session, UTC day, cost or null for unknown, tokens; design [04-chat-agent](04-chat-agent.md)). `readSpend` adds a `chat` total (`cost_usd`, `tokens`, `turns`, `unknown`) over the range, and `GET /api/v1/spend` answers it next to, never inside, the run totals, days and items. Budgets and the page do not read it yet. Why: chat turns call the model, and their cost would otherwise go uncounted.

- **Routine runs are counted (decision changed 2026-11-24, local-task-tk_956892cd phase 2 of 3; current; replaces the counted kinds in the Source bullet below, see History).** The decision that changed: **which run kinds spend counts.** `SPEND_KINDS` in `src/core/spend.ts` is now triage, implement, review, resolve, update and routine. Why: a routine (now a Check a page schedule, design [08-schedules-actions](08-schedules-actions.md)) is a model-calling run with a harness cost, and its daily cap reads that cost; leaving it out would hide it from the Spend page and from the budgets.

- **Spend is read from the stored run outcomes; budgets alert once per period and threshold and stop nothing (decision 2026-11-13, wi_199b; current; new).**
  - **Source.** Each run's cost is the agent CLI's own figure, stored on its outcome (`usage.cost_usd`, design 06-token-budget) and read with `outcomeCost` (`src/core/types.ts`); tokens are `runTokenCount`. No new table, column or migration, and no price computed here. Counted runs are the agent kinds the status page's cost table counts (`SPEND_KINDS` in `src/core/spend.ts`: triage, implement, review, resolve, update, routine; routine since 2026-11-24, see above), by the UTC day of `finished_at`.
  - **Unknown cost.** A run with no stored cost (the CLI reported none, or a row from before costs were stored) is counted apart as `unknown`, never added as $0, in every total, day and item. Runs stored before this change are not backfilled.
  - **Periods.** A day is a UTC day (00:00 to 24:00 UTC). A week is the ISO week, from Monday 00:00 UTC.
  - **Read model and route.** `readSpend` in `src/core/spend.ts` (one `listRunsFinishedBetween` read) gives the totals, every UTC day of the range (zero where nothing ran) and each item (cost, tokens, runs, unknown, kinds), items by cost. `GET /api/v1/spend?from=&to=` (`src/ui/spend.ts`): `from` and `to` are UTC days (`YYYY-MM-DD`, both inclusive, at most 366 days); left out, the last 30 days to today. It also names `today` and the week's Monday (`week_start`), lists at most 200 items with their titles through the Withholder, and is read-only (a POST gets 405).
  - **Budgets.** `spend.daily_budget_usd` and `spend.weekly_budget_usd`, settable at runtime (`factory settings set`, the Settings page), each set or reset one audit row. Type `usd`: a positive decimal dollar amount such as 12.50, not cents; the default is none (null: no budget, no alert). Why a new setting type: the number field took only whole steps, so 12.50 was refused; the Settings page's number field now takes any fraction (`step="any"`), and the server still checks every key.
  - **Alerts.** The alarm step (`spendStep` in `src/core/alarms.ts`, design 05-alarms) compares the known cost of the current day and week with each budget set. Passing 80% and 100% each stores one `spend_budget` alert through `recordAlert`, keyed `spend:<daily|weekly>:<period start>:<threshold>` (`spend:daily:2026-11-13:80`). The key names the period and threshold, so repeated steps, several replicas and a controller restarted on the same store alert once per period and threshold; a new period alerts again. Unknown-cost runs add nothing toward a budget and are named in the alert's detail. The alerts show in Needs you through the alert record, with the Spend page as the place to look; no Slack or other external call (the macOS notifications task will show them later).
  - **No stop.** A spend alert never stops, pauses or holds a run, auto mode included: `isFailureAlert` leaves `spend_budget` out of the failure alarms that set auto mode back to manual (design 03-risk).
  - **Page.** Health's Spend tab (`/app/health?tab=spend` since 2026-11-22, design 09-health; `/app/spend` redirects there) shows today, this week and the last 30 days, one daily bar chart (see the chart decision above) and the tasks by cost. Each of the Today and This week tiles also shows its budget ("$4.10 of $20 today", cents kept only when the budget has them) or "No budget set."; a note under the totals says an alert appears in Needs you at 80% and 100% and no work stops, with a "Change in Settings" link. `GET /api/v1/spend` answers `budgets: { daily_usd, weekly_usd }` (number or null, read with `effectiveGlobal`). No setting key is shown (decision changed 2026-11-20: the tiles showed no budget).
  - Not built: per-item or per-tier money budgets (token budgets stay per tier, design 06-token-budget), the LLM provider's own calls, checking cost against the bill, notification channels.
