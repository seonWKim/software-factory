# 6. Measurement: spend and spend budgets

- **Spend is read from the stored run outcomes; budgets alert once per period and threshold and stop nothing (decision 2026-11-13, wi_199b; current; new).**
  - **Source.** Each run's cost is the agent CLI's own figure, stored on its outcome (`usage.cost_usd`, design 06-token-budget) and read with `outcomeCost` (`src/core/types.ts`); tokens are `runTokenCount`. No new table, column or migration, and no price computed here. Counted runs are the agent kinds the status page's cost table counts (`SPEND_KINDS` in `src/core/spend.ts`: triage, implement, review, resolve, update), by the UTC day of `finished_at`.
  - **Unknown cost.** A run with no stored cost (the CLI reported none, or a row from before costs were stored) is counted apart as `unknown`, never added as $0, in every total, day and item. Runs stored before this change are not backfilled.
  - **Periods.** A day is a UTC day (00:00 to 24:00 UTC). A week is the ISO week, from Monday 00:00 UTC.
  - **Read model and route.** `readSpend` in `src/core/spend.ts` (one `listRunsFinishedBetween` read) gives the totals, every UTC day of the range (zero where nothing ran) and each item (cost, tokens, runs, unknown, kinds), items by cost. `GET /api/v1/spend?from=&to=` (`src/ui/spend.ts`): `from` and `to` are UTC days (`YYYY-MM-DD`, both inclusive, at most 366 days); left out, the last 30 days to today. It also names `today` and the week's Monday (`week_start`), lists at most 200 items with their titles through the Withholder, and is read-only (a POST gets 405).
  - **Budgets.** `spend.daily_budget_usd` and `spend.weekly_budget_usd`, settable at runtime (`factory settings set`, the Settings page), each set or reset one audit row. Type `usd`: a positive decimal dollar amount such as 12.50, not cents; the default is none (null: no budget, no alert). Why a new setting type: the number field took only whole steps, so 12.50 was refused; the Settings page's number field now takes any fraction (`step="any"`), and the server still checks every key.
  - **Alerts.** The alarm step (`spendStep` in `src/core/alarms.ts`, design 05-alarms) compares the known cost of the current day and week with each budget set. Passing 80% and 100% each stores one `spend_budget` alert through `recordAlert`, keyed `spend:<daily|weekly>:<period start>:<threshold>` (`spend:daily:2026-11-13:80`). The key names the period and threshold, so repeated steps, several replicas and a controller restarted on the same store alert once per period and threshold; a new period alerts again. Unknown-cost runs add nothing toward a budget and are named in the alert's detail. The alerts show in Needs you through the alert record, with the Spend page as the place to look; no Slack or other external call (the macOS notifications task will show them later).
  - **No stop.** A spend alert never stops, pauses or holds a run, auto mode included: `isFailureAlert` leaves `spend_budget` out of the failure alarms that set auto mode back to manual (design 03-risk).
  - **Page.** The Spend page (`/app/spend`, design 09-dashboard-app) shows today, this week and the last 30 days, one daily bar chart and the tasks by cost.
  - Not built: per-item or per-tier money budgets (token budgets stay per tier, design 06-token-budget), the LLM provider's own calls, checking cost against the bill, notification channels.
