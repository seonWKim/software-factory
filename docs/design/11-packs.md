# 11. Packs: layered prompts, skills, plugins and checks

- **A pack tool's approval is pinned to its descriptor and its module's bytes, and its credential may not be a built-in plugin's secret (decision changed 2026-11-11; current; replaces "the approval is pinned to the description only").** The decision that changed: editing a tool's `tools/<file>.tool.js` no longer keeps the old approval.
  - **The hash.** A tool's `module_hash` is the SHA-256 of its `.tool.js` bytes. Its `description_hash` is the SHA-256 of the canonical descriptor JSON followed by `\nmodule_hash:<module_hash>` (`descriptionHash` in `src/packs/pack-entries.store.ts`), so the same descriptor with another module is a new entry. A tool with no module, and every MCP server, keeps the descriptor-only hash: the same value as before, so their stored entries and approvals are unchanged.
  - **pack add** reads the module beside each `tools/*.json` and stores its hash in `ext_packs_entries.module_hash` (nullable; migration `src/state/migrations/20261111T2000-state-ext-packs-entries-module-hash`, additive, both dialects, no backfill). The add line and the approve/revoke line show `module_hash <12 hex>` beside the `description_hash`; a tool with no module shows none. No list command (decision 2).
  - **Startup** hashes the module bytes it imports (the import URL carries the hash, so a restart in the same process loads those bytes) and keeps the module file and its hash on the `PackTool`.
  - **Every call** (`PackToolBroker`), after the approval and description_hash checks and before the credential is read, re-reads and re-hashes the module file; a different or missing file is `not_approved` and the call function is never reached. To serve a changed module: `factory pack add`, approve the new hash, restart the worker.
  - **Existing approvals** of tools with a module stop applying; the owner re-approves each one (decision 1; no pack tool was approved yet).
  - **Credential refusal.** `withPackTools` checks each descriptor's `credential` against every secret the built-in registry (`REGISTRY`, before pack plugins join; compose passes it) declares, such as the GitHub App key or the Slack tokens. A match fails startup, naming the secret, the plugin that declares it and the descriptor file. Reason: a pack tool would otherwise receive a credential the owner never gave it. Pack plugin secrets and MCP servers are out of scope.
  - **Not done:** scanning the module's code for egress, credential or poisoning patterns (a follow-up).
- **Packs (new decision, 2026-11-11, issue #489).** A pack is a folder with any of `prompts/`, `skills/` and `plugins/`. A user customizes the factory in a pack instead of editing engine files, so a later `git pull` of the engine does not conflict with the change. `src/packs/packs.ts` finds the layers at each config load (`loadConfig`); nothing is cached between loads.
  - **Layers, in the default order:**
    - `base`: the code root's own `prompts/` and `skills/` (the updater's runtime copy under `git-worktree`). No prompt file moved. Base is always on.
    - `org`: the folder at `packs.org`, resolved from the config file's folder. Absent key: the layer is off.
    - `project`: `.factory/` in the configured repo's **main checkout**. A `repo.path` that is a git worktree is followed to its main checkout (its `.git` file's git dir and `commondir`), so a worktree's own copy of `.factory/` is never read.
    - `learned`: `learned/` under the state dir. Read-only: no code writes to it. Its writer (self-improvement) is a later change.
  - **Off, never an error.** A missing layer folder, a missing file in it, or no `packs` key turns that part off. With no org path, no `.factory/` and no `learned/`, prompts, skills and the plugin registry are exactly the base-only result (the registry is the built-in `REGISTRY` object itself).
  - **`packs` config key:** `{ "order": [...], "org": "<path>" }`, both optional. `order` must list every layer once, `base` first and `learned` last, so only `org` and `project` can swap; an unknown layer, a missing or repeated layer, base not first or learned not last fails startup, naming `packs.order`. Unknown keys under `packs` fail like any other config key. Default order: base, org, project, learned. Reason for the setting: an org that wants its rules to win over every project's sets `["base", "project", "org", "learned"]`.
  - **Prompts.** Each prompt (`triage`, `implement`, `review`, and the optional `resolve`, `improve`, `owner-defaults`) is read through the layers in order. The first layer that has `prompts/<name>.md` gives the text. Each later layer's file is cut at its `## ` headings (outside code fences): a section whose heading matches a section of the text so far replaces it, one that matches none is added at the end, and every other section keeps its text. A later file's text before its first `## ` heading is not used. Placeholders (`{{check_commands}}`, `{{forge}}`, `{{toolchain}}`) are filled after the merge; `owner-defaults` is still appended to triage after both are merged.
  - **Skills.** Every layer's `skills/<name>.md` is a capability of kind `skill`. A base skill keeps its code-root ID (`skills/<name>.md`); any other layer's ID is its absolute path, which an agent can Read. `build()` hands every layer's skills to the capability plugin's context, so `list-all` lists them. `Bm25CapabilitySearch` takes the non-base layers' `skills/` folders as extra roots (kind `skill`).
  - **Plugins.** Every `plugins/**/*.plugin.js` of every layer is imported at load, checked like a built-in descriptor, and added to a copy of the registry for this load (`withPackPlugins` in `src/plugins.ts`); the built-in `REGISTRY` never changes. A pack plugin is selected only by name in `factory.config.json` and built through the same `createPlugin` path. Startup fails, naming the file, when a pack plugin (in any layer, base included) declares a guard (`SecretStore`, `EgressScanner`, `ToolBroker`, named in the error), claims a `default`, or reuses a name its kind already has.
  - **Checks (decision changed 2026-11-11, issue #494; before: see History).** Every layer's `checks/<name>.json` is a pack check, run only when its name is listed in `hooks`, at one of the implement run's four pack check points (`before_agent`, `on_tool_call`, `before_finish`, `after_agent`), as argv in the run's sandbox with the worker's tool env. Its format, order, timeouts, retries, audit and startup refusals are in 04-pre-push-gates.md. A name in two layers fails startup, naming it.
  - **Solo default:** base, plus `.factory/` in the repo's main checkout and an optional `learned/` under the state dir. No org path, so the org layer is off. Any layer may add plugins and checks.
  - **With an org pack:** the same, plus an org pack at the path set in the reviewed config. `packs` is a reviewed key: it comes only from the checked-in config under the code root, so a replica's own file cannot point at another org pack. A project pack's plugin or enabled check is refused at startup, naming the file (a project's `.factory/` is not reviewed by the org); an org pack's plugin or check is allowed.
  - **Not in packs yet:** roles, rules, signals and settings; pack install, versioning, distribution, or a command to list packs. Tools and MCP servers are added by `factory pack add` and approved by `factory pack approve`, below; an approved pack tool is served by the pack tool broker, and an approved stdio MCP server with no credential is started for each run that is granted it.
- **Approved pack MCP servers with no credential are started for a granted run, and their results pass the egress scan and the output cap (decision changed 2026-11-11, issue #596; current; replaces "no MCP server is started yet: a granted, approved MCP server fails the run as `not_started`").** A run kind that grants an approved `pack:mcp_server:<name>` gets that server's tools; the agent reaches them only through the factory's bridge, never by starting the server itself.
  - **The descriptor.** `mcp_servers/<file>.json` needs `name`, `description` and `command` (a non-empty string); `args` is optional, a list of strings; `type` is optional and only `"stdio"` is allowed (decision 2: no remote servers). An `env` field is never read: the server always starts with an empty env. `packMcpServer` in `src/packs/pack-grants.ts` reads these fields.
  - **The grant check** (`checkPackGrants`) returns each approved, granted server as `{ name, command, args }`, and the worker passes them to the runner in `AgentRunSpec.mcp_servers`. Still refused, as `not_started`, before the agent starts, and no process starts: a server whose descriptor names a `credential` (a server that needs a factory secret is out of scope), one that is not a stdio server with a `command`, and every server on a runner without `runs_mcp_servers` (the openai-compatible runner, a fallback chain, a claude runner with no broker). An unapproved or changed description is `not_approved` as for a tool (the pin, below); an ungranted server is in no spec and no `--mcp-config`.
  - **Guarded route (decision 1).** The claude runner starts each server itself, in the worker process (`src/impl/runner/pack-mcp-client.ts`): the descriptor's `command` and `args`, an empty env, the run's home folder as working folder, stderr dropped unread. It speaks MCP to it (`initialize`, `tools/list`, `tools/call`, newline-delimited JSON-RPC on stdio) and stops it when the run ends. A server that does not start or answer fails the run, naming the server only. The agent's `--mcp-config` gets one entry per server, `pack_<name>`, which is the factory's bridge (`node <bridge script> <socket> <name>`, env `{}`), and `--allowedTools` lists each tool the server listed at start as `mcp__pack_<name>__<tool>`, so a headless run never waits on a permission prompt. Every call goes through `ToolGate.callServer`: the tool must be one the server listed, then the run's lease, the call, the egress scan (a flagged result is withheld as `egress_blocked`), and the 64 KiB output cap, the same as a broker tool. Reason: Claude Code starting the server itself would hand its results to the agent with no scan and no cap.
  - **Where the server runs.** In the worker's host, outside the agent's sandbox, with no credential in its env; the owner's approval of its pinned description is what lets it run. The captured `--mcp-config` and agent env hold no credential value (tests/tool-bridge.test.ts).
  - **Solo and enterprise:** one owner, so no difference; no schema change.
- **Pack tools are served through the pack tool broker, with an approval check on every call and an output cap (decision changed 2026-11-11, issue #592; current; replaces "nothing starts a pack tool: a granted, approved pack tool fails the run as `not_started`").** A run kind that grants an approved `pack:tool:<name>` gets it as one of its broker tools. MCP servers: see issue #596, above.
  - **Implementation.** A layer's `tools/<file>.json` is the descriptor `factory pack add` stores and the owner approves; `tools/<file>.tool.js` beside it is the code, `export default async function (args, credential)`. `loadConfig` imports every such module, in layer order, into the worker only (`src/impl/broker/pack-tools.ts`); the agent's sandbox never loads it. A bad module, a name in two layers, or a `pack:tool:` grant with no module or not `"read_only": true` fails startup, naming the file or grant. With an org pack, a project pack's tool module fails startup, like its plugins.
  - **Broker gate** (`src/impl/broker/pack-tool-broker.ts`, a wrapper, not a registered plugin, so no descriptor). compose wraps the selected broker and the local items' broker in it, inside the run passport check. Every call checks, in order: the run's lease, then the store's approval of the entry's current description (`approvedEntry`, a read only, so a retried check gives the same answer and writes nothing), then that the approved description_hash is the one the loaded module runs. Only then is the credential read from the `SecretStore` and the tool's call function reached; a refusal (`not_approved`, `no_credential`) never reaches it. Any other tool name goes to the wrapped broker.
  - **Credentials.** A descriptor's `credential` is declared as a secret of the selected broker, so the `SecretStore` loads and scans it and setup asks for it. Its value is handed only to the call function, in the worker: never to the agent's environment, prompt, logs or store rows. A thrown error reaches the agent as `tool_error` with no text, and a result that holds the credential is withheld (`credential_in_result`).
  - **Output cap** (`src/impl/runner/tool-bridge.ts`, `ToolGate`, after the egress scan). Every granted tool's result, pack tool or not, whose text is over 64 KiB (`RESULT_CAP_BYTES`, the shared tools' `OUTPUT_CAP`) is written whole to `.factory-tool-results/` in the run folder (with a `.gitignore` of `*`, so it is never committed), and the agent gets `{ truncated, path, bytes, preview }`: the file's path and its first 2 KB, cut back to a UTF-8 character boundary. Reason: a large result no longer enters the agent's context in full. No paging or streaming.
  - **Solo and enterprise:** one owner, so the approval is the single latest row in `ext_packs_approvals`, with no per-person grants; no schema change.
- **Pack tools and MCP servers need a grant and an approval (decision changed 2026-11-11, issue #589; replaces "stored entries are data only: nothing reads an approval, and no entry can be granted").** A pack entry reaches a run only when both hold: the run kind's `tool_grants` names it, as `pack:tool:<name>` or `pack:mcp_server:<name>`, and its **current description** is approved. A refused grant fails the run before its agent with `pack_tool_refused` and its reason; a pack tool that passes both is served (issue #592, above), and an MCP server that passes both is started when it has no credential (issue #596, above). An entry no run kind grants is never listed, approved or not.
  - **Approval** (`src/packs/pack-approvals.store.ts`). `factory pack approve|revoke <tool|mcp_server> <name> [<description_hash prefix>]` and the dashboard's `POST /api/v1/packs/approvals` (`src/ui/packs-api.ts`, behind the page's write-route guards) both call `changeApproval`: first `AuthProvider.authorize` with the `approve_tool` action on resource `tool` `pack:<kind>:<name>` (08-permissions.md), then the stored description (absent prefix: the current one), then one row. A refused change writes nothing.
  - **One table, `ext_packs_approvals`** (migration `src/state/migrations/20261111T1600-state-ext-packs-approvals`, additive, both dialects): `seq`, `kind`, `name`, `description_hash`, `action` (`approve` | `revoke`), `user_id` (the approver's user ID, never a display name), `at` (the injected Clock). Every approve or revoke appends one row, so the table is the change and its audit at once; the latest row of a (kind, name, description_hash) decides whether that description is approved.
  - **The pin.** An approval holds for one description_hash (for a tool with a module, the descriptor and the module's bytes: the decision above). The current description of a name is the entry `pack add` stored last; a changed descriptor is a new entry with a new hash, so the name is off for every run (`not_approved`) until the owner approves the new hash. Approving an older hash again changes nothing for the current one.
  - **`packs.auto_approve_read_only`** (setting `src/worker/settings/packs-auto-approve-read-only.setting.ts`: worker, boolean, default `false`, review only, tighten-only). On, an entry whose descriptor says `"read_only": true` and that has no `credential_name` counts as approved at the grant check; it writes no row, so turning the setting off turns those entries off again. An entry with a credential, or without `read_only: true`, always needs the owner's approval. Reason for the setting: a team with many read-only doc and search tools skips one approval per description change. Solo default and enterprise: off.
  - **Solo:** the CLI identity (`cli_user`, else git `user.email`, else the OS user, else `anonymous`) or the page's user approves through the local auth plugin's owner check, with no external account; the first local identity is the owner. **Enterprise:** the configured auth plugin decides `approve_tool` through `AuthProvider.authorize` (the page's `AuditedAuthProvider` audits the decision too), and the approval row carries the approver's user ID. No per-person approvers or roles (one owner, 08-enterprise.md).
- **Pack tools and MCP servers are stored as pending entries (decision changed 2026-11-11, issue #588; replaces "tools and MCP servers are not in packs yet").** `factory pack add <path>` reads the pack's `tools/*.json` (kind `tool`) and `mcp_servers/*.json` (kind `mcp_server`), one descriptor per file with a non-empty `name`. Each descriptor goes through three scans; one that passes all three is stored as `pending`, one that fails any is refused, its line names every failed rule, and nothing is stored for it. The command prints one line per entry (stored, already added, or refused with the rule names) and exits 1 when any entry was refused, else 0. Nothing starts: no process, no tool call; approving, granting and starting an entry are later phases. Startup, the capability list and the tool list do not read the entries.
  - **One table, `ext_packs_entries`** (migration `src/state/migrations/20261111T1201-state-ext-packs-entries`, additive, both dialects): `id`, `kind`, `name`, `description_hash`, `descriptor` (the scanned canonical JSON: keys sorted, no spaces), `credential_name` (the name of the environment variable a tool reads, never its value; null without one), `status` (`pending` only), `added_by`, `created_at`, `updated_at` (from the injected Clock). Unique key (kind, name, description_hash); `description_hash` is the SHA-256 of the canonical JSON, so a change to any field is a new entry and the same descriptor again stores nothing and prints `already added`. The code is `src/packs/pack-entries.store.ts`; the command `src/cli/handlers/pack/pack.command.ts` names no table.
  - **The three scans** (`src/packs/pack-scans.ts`):
    - **egress:** the configured `EgressScanner` on channel `tool_result`, over the canonical JSON; the rule is the scanner's own finding. Its patterns are not copied.
    - **credential-leak:** `credential_value` refuses a non-empty string under a key named `token`, `secret`, `password`, `api_key`, `apikey` or `authorization` (any case, any depth); `credential_name` refuses a `credential` field that is not an environment variable name (`^[A-Z][A-Z0-9_]*$`).
    - **tool-poisoning,** on the description and every other string field: `override_instructions` (ignore, disregard or forget near previous, prior, above or system and instructions, rules or prompt), `concealment` (do not or never near tell, inform, mention or reveal and user), `secret_file_access` (`.ssh/`, `id_rsa`, `.env`, `.aws/credentials`, `/etc/passwd`), `invisible_text` (zero-width and bidi control characters).
    - A file that is not a JSON object with a `name` is refused as `invalid_descriptor`. A refused entry is named by its file, so no descriptor text is printed.
  - **added_by:** the CLI identity, the same user ID other CLI commands store (`cli_user`, else git `user.email`, else the OS user, else `anonymous`), on every store: one owner (08-enterprise.md).

## History

- **Current text names SQLite only** (decision changed 2026-11-11, issue #567). Before: the org pack layer was described as "Enterprise (shared store, `store.type` `mysql`)", and a project pack's tool module failed startup "on a shared store (`mysql`)"; both now hang on the org pack.
- **Pack tool approval pinned to the module too** (decision changed 2026-11-11). Before: the approval was pinned to the description only: `description_hash` was the SHA-256 of the descriptor JSON, so editing a tool's `.tool.js` kept the old approval; startup only checked that a credential was a secret name, so a pack tool could name a built-in plugin's secret.
- **Pack MCP servers started for a granted run** (decision changed 2026-11-11, issue #596). Before: no MCP server was started yet; a granted MCP server that passed the grant and the approval failed the run before its agent with `pack_tool_refused`, reason `not_started`, and no process started.
- **Pack tools served through the pack tool broker** (decision changed 2026-11-11, issue #592). Before: nothing started or called a pack tool; a run granted an approved pack tool failed before its agent with `pack_tool_refused`, reason `not_started`, and granted tool results had no size cap.
- **Pack entries need a grant and an approval** (decision changed 2026-11-11, issue #589). Before: entries were stored as `pending` and nothing read an approval, so no entry could be approved, pinned to its description_hash or granted to a run kind; `tool_grants` named broker tools only.

- **Tools and MCP servers not in packs** (decision changed 2026-11-11, issue #588). Before: "Not in packs yet: roles, rules, checks, tools, MCP servers, signals and settings"; no table held a tool or MCP server and no command added one.
- **Checks** (decision changed 2026-11-11, issue #494). Before: checks were not in packs; no code read a layer's `checks/` folder.
