# 9. Status page: dashboard chat (the Chat page and the Runners Chat Card)

- **The composer takes images: paste, drop or the attach button; your message shows them above its text (decision changed 2026-11-27, owner "image upload to chat isn't working", then "build it now", spec chat-images; current; replaces "the composer is a text box with a send button inside it", see History).** The chat page's composer (`web/src/views/chat-page.tsx`, its image parts in `web/src/views/chat-images.tsx`) takes up to 5 images per message, sent with `chat.send`'s `images` (design 04-chat-agent).
  - **Adding.** Paste an image into the text box (the clipboard's image files; a paste with none is the text's), drop files onto the composer (it shows the `focus` ring while files are dragged over it), or press the paperclip, a ghost icon Button (`FilePicker`, named "Add images") inside the text box's left edge, which opens the system picker for png, jpeg, gif and webp. Each image becomes an `ImageThumb` in a row above the text box with a round Remove button on its corner, a spinner while its bytes are read, and an error state for a file the server would refuse: another type, over 5 MB, or past the fifth, each said in a line under the row that names the file and says to remove it ("“notes.pdf” can’t be sent: only png, jpeg, gif and webp images can. Remove it to go on."). A refused image is never sent.
  - **Sending.** Send is on with text or at least one read image, once no image is still being read. The message sends the read images in their order, with or without text (the item context line is added only to text), and the composer empties. Try again sends the same images again. The server's refusal (a type, size or count it checks again) shows as a failed send, its words naming the file.
  - **Your message.** Its images sit above its bubble at the right, as `ImageThumb` buttons ("Open <name>"); a click opens the image larger in the shared `ModalPanel`, titled with the file name. A message of images only has no bubble and no Copy.
  - **An image not sent.** When `chat.send` names `images_withheld` (an image that held something like a key), the reply starts with a plain `text-2` line: "Not sent to the chat: “key.png”. It looked like it held a password or key, so it stayed here." When nothing was left to send, the failed send says it in the same words.
  - **Runners transcript.** The Transcript dialog shows a stored message's images as thumbnails above its text, each read once through `chat.image`.
  - Pictures are `blob:` URLs from bytes the page holds (09-brand-and-tokens, CSP). Tests: `tests/ui-chat.test.tsx` (paste, drop and the attach button each add a thumbnail; Remove; Send with only an image; a refused file named), `tests/web-ui-components.test.tsx` (ImageThumb, FilePicker).

- **The Chat page has a New chat Button and a Recent list of earlier sessions (decision added 2026-11-27, schedule chat-vs-top-llm-apps-review; current; replaces none, the page had neither).** The spec asked for New chat in the side panel's `PageHeader`, before its close icon Button; this base has no panel and no close Button (Chat became a page, decision below), and the page draws no title and no `PageHeader` (owner, 2026-11-28, Layout below), so a secondary New chat Button sits alone in the page's action row at the top right, where a header's actions would be: it clears the messages, the typed text and the session, so the next send carries no `session_id`. On the empty page a `Card` titled Recent sits above the composer and lists up to 10 sessions, newest first. It is one `chat.turns` read with limit 50 under the query key `["chat", "recent"]` (not the Chat Card's `["chat", "turns"]`, which keeps its limit of 10), made when the empty page mounts and never polled, grouped by `session_id` in the page (no `chat.sessions` capability: owner answer). Each row is a `ListRow`: the relative time of the session's latest turn as its title, an outcome `Badge` and the reason in plain words as its details, and a menu with one Open entry; no turn, session or item ID shows. Open reads `chat.transcript` for that session into the conversation in order (your messages and the replies only, the context line taken off, through the same reply rendering) and the next send carries that `session_id`. A pending read shows a `Loading` placeholder, no sessions an `EmptyState`, a failed read an `ErrorNote` in plain words. So after a reload the earlier sessions are one Open away; the conversation itself is still not stored anywhere but the server. Tests: `tests/ui-chat-panel.test.tsx`.

- **Every reply, your own message and every fenced code block has a Copy icon Button, and "Copied" is announced (decision added 2026-11-27, schedule chat-vs-top-llm-apps-review; current; replaces none, nothing offered Copy).** A reply ends with a `ButtonRow` holding a Copy icon Button named "Copy reply" that writes the reply's stored text, on the Chat page and in the Runners transcript dialog; each of your messages on the page has "Copy your message", which writes what you typed without the context line; each fenced code block, in a reply and in the shared `Markdown` component (so on the item, thread and rules pages too), has "Copy code" under it that writes the code without its fence lines. All are one `CopyIcon` (`web/src/components/ui/copy.tsx`: a ghost, `icon` Button with the lucide Copy icon over `copyToClipboard`); after a copy "Copied" shows beside it for 1.5 s in an always-present `aria-live="polite"` element, and with no clipboard nothing shows and the text stays selectable. Send stays the page's one primary Button. Copy runs in the browser only: no fetch, no route. Edit and resend of your last message was offered and not built (owner answer: Copy only). Tests: `tests/ui-copy.test.tsx`, `tests/ui-chat.test.tsx`.

- **Chat is a page of its own, in the sidebar, laid out as one centred conversation column (decision changed 2026-11-27, owner design feedback: "Chat should be extracted as a menu + it should resemble chat GPT UI … for slickness"; current; replaces the side panel and its Chat button in the top bar, see History).** `PAGES` (`web/src/pages.ts`) has `chat` (label Chat, icon MessageSquare, group `tasks`) first in the sidebar, above Tasks (since 2026-11-27, [09-dashboard-shell.md](09-dashboard-shell.md)), so `/app/chat` routes to `ChatPage` (`web/src/views/chat-page.tsx`); the top bar has no Chat button and there is no side panel, so the page is the one chat surface ([09-dashboard-shell.md](09-dashboard-shell.md)). The page calls the generated typed client (`web/src/api/generated.ts`: `chatSend`, `itemsList`) and nothing else: no hand-written `fetch`, no new route (`tests/ui-chat.test.tsx` reads the source). It only answers: it creates no item and runs no command. Texts in `web/src/i18n/en/chat.ts` (key prefix `chat.`). Only the layout pattern follows the familiar chat apps; no other product's name, mark or words.

- **Layout.** The page marks itself `data-page-fill`, and `<main>` (`web/src/App.tsx`) then grows to the content column's height, so the page is window-high. Inside, one column centred in the page, at most 48rem (768px) wide (`max-w-[48rem]`: a reading column inside the page, like a prose width, not a page width; `<main>` stays `--page-wide`): the conversation, then the composer. The page draws no title (decision changed 2026-11-28, owner: remove the "Chat" title; the sidebar already names the page): no `PageHeader`, only an `sr-only` h1 "Chat" for screen readers, which `one-h1` in `scripts/responsive/rules.mjs` accepts in place of a shown one. Your message is a right-aligned `surface-2` bubble (`rounded-card`, at most 85% of the column, kept as written in `[data-raw]`); a reply is plain left-aligned text with no bubble. Messages are 32px apart. While the chat answers, the shared `TypingDots` (design-system/components.md; its `typing` keyframes at the top level of `web/src/index.css`) sits in the reply's place: three `text-2` dots that rise and brighten one after the other in a 1.2s loop, still with reduced motion, a live `role=status` read as "Thinking…" (decision changed 2026-11-27, owner "fix the ... to be more dynamic": the three grey dots looked static; see History).

- **Composer.** (Images: the decision at the top.) A `Textarea` (`rounded-card`, `shadow-sm`) starts one line high and grows with its text up to 8 lines, then scrolls; the paperclip (`FilePicker`, "Add images") sits inside its left edge and the send icon Button (primary, round, arrow up, named Send) inside its right edge; Send is on with text or at least one read image, once no image is still being read. While an answer is pending, Send is gone and Stop takes its place under the composer (the next decision); you can type the next message meanwhile, and the paperclip is off. Enter sends; Shift+Enter makes a new line; an Enter that ends an input method's composition (Korean, Japanese) does neither. A one-line hint under it says so. The composer is `sticky` at the bottom of the scrolling content column, on the page colour faded in above it, with the safe-area inset below it, so it stays in view while the conversation scrolls.

- **While an answer is pending, Stop takes Send's place and the wait is counted (decision added 2026-11-27, nightly chat review; current; replaces nothing, the composer had no way to cancel).** The page keeps the send's `AbortController` and start time in the conversation (`pending`). Under the composer, a secondary md `Button` "Stop" replaces the Send icon, with a plain `text-sm text-text-2` line beside it (no ID, no live role): "Answering…" for the first 5 s, then "Answering… N s", N the whole seconds since the send, updated once a second. Stop aborts the `chat.send` request (the generated `chatSend` takes an optional `AbortSignal` that `postJson` passes to fetch, as does every POST wrapper), ends the wait at once and adds "Stopped. The chat may still finish its answer; it is not shown here." to the conversation; a reply that arrives later is not shown. Stop pressed before the items list is read or the request starts sends nothing. The server is not changed: the turn runs on as today; recording it as Failed 'stopped' is a follow-up. Tests: `tests/ui-chat.test.tsx` ("Stop and the elapsed line").

- **Empty page and scrolling.** With nothing asked, a short greeting and four example questions in plain words (What needs me today?, and three more) as round secondary Buttons; a click puts the question in the composer and focuses it, and sends nothing. The column follows each new message and the answering mark to the end, unless you scrolled up more than 80px from it.

- **A failed send reads as the chat's turn, at the left (decision changed 2026-11-27, owner screenshot at 767px: the red error sat right-aligned under the bubble and the column ran past the right edge; current; replaces "errors sit under the failed message", see History).** A send that fails (chat off with no model: "Add one in Plugins, then try again"; a refused or failed turn, its reason in plain words; a lost connection) adds a `data-from="chat"` row where the answer would be: its words in the `failed` colour (the danger token, as the `danger` Button; `role=alert`) and a Try again Button beside them that sends the same message again in its place, so it never shows twice. The words break anywhere (`wrap-anywhere`, `min-w-0`: an error can hold one long request id or path), and Try again wraps under them when the row runs out of room. Every level of the column (`data-page-fill`, the list, each row) is `min-w-0`, so nothing in a turn widens the column: it fits 320 to 1920px with the 16px gutter. Tests: `tests/ui-chat.test.tsx` (the row's place), `npm run check:responsive`'s `chat-error` page (no horizontal overflow at every viewport).

- **The conversation outlives the page, not a reload.** It is kept in the query cache (key `chat`/`conversation`, never refetched, never collected): going to another page and back keeps the messages and the session (`chat.send` continues it with `session_id`), and an answer that comes while the page is away still lands. A reload starts a new conversation; the earlier sessions are listed under Recent and Open continues one.

- **An optional item context.** `/app/chat?item=<id>` names one item: each message then starts with "About item: “<title>”, state <state label>, stage <stage>." from the stored items list (`itemsList`, read once per 10 s at send), so "What is this?" is about that item. Without it the message is sent as typed. Nothing links there yet. A shown transcript takes the line (or an older "Open page: …" line) off again.

- **A reply is readable markdown.** `replyParts` splits a reply; its paragraphs, lists and fenced code blocks render through the shared `Markdown` component (code in its `surface-2` mono block, scrolling sideways inside the column), a pipe table as a `DataTable` (cards below `sm`).

- **The Runners tab's Chat Card shows the chat's autonomous work (design-system `patterns.md`, "Autonomous work is visible").** `ChatCard` (`web/src/views/chat-card.tsx`, in `RunnersTab`, [09-dashboard-runners.md](09-dashboard-runners.md)) reads `chat.turns` (10, polled every 3 s while visible): the current activity ("Answering 2 questions now." or none), then a table of recent turns with when, outcome (Answered, Held back, Failed, Answering: one `Badge`), the reason in plain words (never the stored code) and a Transcript Button that opens that turn's stored messages (`chat.transcript`) in a `ModalPanel`. No turn, session or item ID shows anywhere on the panel, the Card or the dialog.
