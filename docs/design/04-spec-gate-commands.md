# 4. Agents: commands at the spec gate and after a run

**`/approve` applies at `too_large`, with a note** (decision changed 2026-11-24, phase 3 of local-task-tk_8bb1417c; replaces "accepted there but not listed", see History; full decision in 04-split-specs). `too_large` is one of `/approve`'s phases, so footers, `/help`, `SET_UP.md` and the dashboard list it; over the cap it needs a note (`/approve <why>`, `factory approve <id> <why>`) and is refused without one. The dashboard's over-cap Approve opens a note dialog and sends the same note.

**`/revise` on a New or in-triage item adds context, queued for one re-triage** (decision changed 2026-11-23, wi_c3c370c8; replaces "`/revise` is refused while the item is triaging", see History; full decision in design 02-attachments). At `triaging` it is a `revise_queued` row with `at: triage` (same empty-text refusal and egress scan, a "queued" reply); when the triage run ends, `applyQueued` starts exactly one more triage run, which reads the filed and the added text. `revision_count` stays.

**`/revise` goes back through triage after a failed implement run, and in REVIEW after a `bug` verdict** (decision changed 2026-11-23, wi_bdd36b09; adds the `bug` verdict case to the "`/revise` after a failed implement run" decision, whose text is in History). It applies at `too_large` (the `run_failed:implement:diff_too_large` block, label "blocked: the change was too large"), at `failed_implement` (any other implement failure blocked on a human: `max_attempts` or `max_restart` at `RUNNING`, or `run_failed:implement:*`; label "blocked by a failed implement run"; `failed_run` keeps failed triage and update runs, `failed_review` a failed review run's), and, new, on an item in `REVIEW` on a factory branch (not adopted) whose latest review with a verdict found a `bug` (`lastVerdict`, checks-gate unit), in any phase of `REVIEW`, `failed_review` included (at `max_loops` the loop-limit `/revise` below). `/revise <feedback>` (`reviseAfterFailure`) sends the item back to `NEW` (`spec_revision_requested`, the user as actor, detail `previous_blocked_reason`), clears the block, adds one to `revision_count` and to `restart_count`, stores the feedback, clears `failure_comment_url` and queues triage under the spec-gate revision key (`…:v<n>`, the restart count before the bump); `loop_count` stays. As `restart_count` moved, the next `/approve` queues an implement run under a new key; a remote branch from the earlier attempt is resumed. At the revision limit (`max_loops`) nothing changes: the reply names it and offers `/retry` or `/reject <reason>`. Empty feedback gets the spec-gate refusal; `/retry` and `/reject` apply as before. `/revise` on the issue stays refused at a floor block, a budget checkpoint, a failed triage or update run and in `REVIEW` after a passing verdict; there, at the merge wait and `failed_review`, the refusal points to the PR (Feedback on a pull request, below). The size-check comment names `/revise <feedback>` next to `/retry`. Why the `bug` case: an item an unchanged head left in `REVIEW` (design 05-ci-gate, 2026-11-23) had no command but `/reject`. Not changed: the REVIEW footer and `/help` text (a follow-up).

**Commands at the review loop limit** (decision changed 2026-11-23, wi_971653ce; replaces the 2026-11-08 decision, see History). At `max_loops` (label "review loop limit reached"), from the issue or the CLI: `/retry [notes]` starts one implement run (`RUNNING`, `loop_count` 0, `restart_count` + 1, key `…:implement:l0:r<n>`; `+paths` as after a failed implement run); `/revise <feedback>` goes back to `NEW` (`reviseAfterFailure`, `loop_count` 0, an open PR stays; empty feedback refused); `/reject <reason>` closes as at the spec gate. **After a failed merge check** (a local item whose latest `max_loops` change carries the queue `entry_id`: `mergeCheckStopped`; implement loops carry none), `/retry` is refused (`mergeCheckRetryRefusal`, naming `factory merge <id>`, `/revise` and `/reject`), and the local merge gate (`localMergeRefusal`, `held`) passes the owner's `factory merge <id>`: one `merge_check_again` change (the owner as actor, back to `merge_pending`), then the merge queue as usual. The loop count is not checked and stays: a pass merges, a failed check stops it at `max_loops` again. `CommandState.merge_check` makes `/help` mark `factory merge <id>`, not `/retry`, and chat help list `merge`. At a `max_loops` from implement loops `factory merge` is still refused ("not waiting for a merge"). Unchanged: the limit, PR items, the dashboard Merge button (off at `max_loops`) and `factory help <id>` (it reads no state changes).

**`factory approve` reads its decision answers at intake** (decision changed 2026-11-20; replaces the decision in History). After `approveRefusal` (below), the CLI and Slack's `approve` run `splitAnswers` on the text against the item's `latestSpec`, passed in as the required `LocalCliDeps.answers` (`src/core` cannot import `src/shared`). A bad line exits 1 with its refusal and stores nothing. Otherwise the text is stored as typed, and after the `stored` line each decision prints as `N. <question> → <answer> (default taken)`, `(your answer)` or `→ (no answer and no default)`; no decisions, no lines.

**`/retry` after a released session** (decision 2026-11-22, wi_33b7e450). Phase `session_released` (`RUNNING`, blocked on a human): `/retry [+paths]` queues the implement run as after a failed one, for `interactive start` to take over; no `/revise` or `/approve`.

**An approval whose answer needs a path outside the allowed paths is refused until `+paths`** (decision changed 2026-11-21, wi_80ba9d05; replaces the decision in History). Owner answer: warn and wait for `+paths`; nothing widens on its own. `approveCheck` in `src/core/request-transition.ts`, after `splitAnswers` and before the transition, reads each non-default answer's option change (design 04-triage, `option_changes`) and keeps its `extra_paths` that the item's `allowed_paths` plus the approval's own `+paths` do not cover (`uncoveredOptionPaths`, `isCovered`). Any left: the approval is refused with one reply (`optionPathsRefusal`) naming each path, the decision, and the `/approve +paths <path>` reply to send with the same answers (`retryPathsReply`); nothing is queued, no implement run starts and `allowed_paths` stay as they were. It is the same gate for a comment, Slack, `factory approve` and the dashboard (whose request carries no `+paths`, so it is refused too; its dialog warns first, design 09-dashboard-item-commands). An approval whose `+paths` covers the paths widens `allowed_paths` and starts the implement run as before. A default answer needs no extra path. Split specs are not checked here: their phases have their own allowed paths. Done-when changes are shown, never checked against the other lines; the owner decides. Existing approvals are not re-checked.

**A spec's premise is checked: a spec that changes no file is never approved, and an old item's `/retry` re-triages first** (decision changed 2026-11-20, wi_66612b38; replaces parts of Gate commands and Auto mode below and the old `/retry`, see History). Triage has no clone, so `parseTriage` still accepts an empty `files_to_change`. Such a spec (not a split) changes no file in this repo:
- **Its spec comment** says so in the one refusal text (`NO_FILES_REFUSAL`, `src/core/commands.ts`), naming `/revise` and `/reject`; its footer has no `/approve`.
- **Every approval is refused** with that one reply, and nothing changes: a `/approve` comment, a stored `factory approve` (the commands unit's `noFilesRefusal`) and the dashboard's Approve (the commands route).
- **Nothing approves it without a person:** auto mode, a standing rule, a recurring failure's fix and `phases_auto_approve` leave it at the gate.

**`/retry` on an item whose last state change is over 24 hours old** (the `Clock`; `premise-recheck.ts`), when it would start a run: one `retry_requested` change to `NEW`, block cleared, `restart_count` + 1, `loop_count` 0 at `max_loops`, and one triage run keyed `<runKey>:recheck`, no implement run; the new spec waits at the gate. `/retry +paths` there is refused (`RECHECK_PATHS_REFUSAL`).

**`/hold <id>`: hold until <id> merges, at a local stop for a human** (decision changed 2026-11-20; replaces the decision in History). For a local item with no PR whose implement run asked for a human (`asked_by: ["implement"]`, now checked by `applies`); its footer lists it only when the reason names a local item not closed yet (`namesUnmerged`). The coordination unit (`holdCommand`, design 05-dependencies) writes the `Depends on: <id>` line, `blocked_on: dependency` and a queued implement run in one transition, or refuses with the reason: no such local item, the item itself, a closed item, a missing or second id, another phase. CLI, chat and dashboard forms go through the commands unit; an inbox refusal is posted once. Not changed: `/hold` on a GitHub issue, dashboard buttons.

**One refusal and help text on every surface** (decision changed 2026-11-11, issue #528; replaces the decision in History). The refusal and help texts are built once, in `src/core/commands.ts`, and every surface uses them: the controller's reply to an issue comment or a Slack thread command (`refusalText`, `CLOSED_REFUSAL`, `CHECKPOINT_REFUSAL`, `dependencyHoldRefusal`, `specNotWaiting`), the dashboard's stored reply (the app-requests unit), the CLI and Slack's item commands (which run through the CLI's code). **`factory approve <id>`** first runs the controller's own phase check from the item's fields (`approveRefusal`) and, where approve does not apply, prints that refusal and exits 1 before any store write (no command row, no local owner claimed); the controller's later reply would have been the same text. An implement run held by coordination cost (RUNNING, not blocked) and a split parent's states are left to the controller, since the hold is in no field; so `factory approve` is still stored there. The other item commands are stored in any state as before. **Help:** `factory help [<id>]` prints `helpReply`, the issue's `/help` reply: with an item, its state's commands marked **(now)**, without one every command with nothing marked. Slack's help (`chatHelpReply`) lists, in an item's thread, the commands that apply now in the same `- \`usage\`: description.` lines as the issue footer and `/help`; outside one, the reads, the request that starts work and `/link <code>`. Its header shows the `@software-factory /help` form; when `/approve` is listed, a last line says that `approve` with no slash works too after the mention. **Bare approve:** after a mention in an item's thread, `approve` (any case, with its notes) is `/approve` (`BARE_COMMANDS`, `withSlash`); outside an item's thread the same word is a request in plain words, as before. Other bare words (`retry`, `reject`, ...) stay plain words. The controller's authorize check is unchanged. Solo default: no grants needed, the first identity is the local owner and may run everything. Enterprise: the stored grants decide what the dashboard shows (design 09-dashboard-app) and what the controller applies.

**The spec comment says how to answer its decisions** (decision changed 2026-11-11, issue #527; replaces the decision in History). When triage named decisions, the comment's "Decisions for you" section ends, after the folded list, with an answer block (`answerBlock` in `src/core/spec-comment.ts`): one line saying to reply `/approve` with one `N: <answer>` line per decision and that a decision not answered takes its default, then a code block of `/approve` with one `N: <answer>` line per decision. A section with only a tier raise has no block. The reply goes through the one parser below ("Answers to the spec's decisions"), so a GitHub comment, a Slack thread `/approve` (after a mention, the lines below it), the dashboard's approve and `factory approve` store the same `answers`, with the approver's user ID as actor. A `/revise` from Slack or GitHub whose text has `### <Section>` lines (the dashboard's Revise form sends that shape, design 09-dashboard-app) is stored as typed, as any `/revise` text: there is no section reader.

**Answers to the spec's decisions** (decision changed 2026-11-10, issue #526; replaces the decision in History). An approval answers the spec's numbered decisions (design 04-triage) with `N: <answer>` lines in its note:

- **One parser.** `splitAnswers` in `src/shared/command-notes.ts` (imports nothing outside `src/shared/`) runs in the command unit's `spec_approved` branch, after the note's egress scan and `+paths` split, so `/approve` in a comment, a chat thread, the dashboard's approve and `factory approve` all go through it. The spec's decisions come from the latest applied triage run's stored output (`latestSpec` in `src/core/commands.ts`). With no decisions the note is kept whole. A line whose N names no decision, a repeated N or an empty answer refuses the approval with one reply and stores nothing; other lines remain the note. Options are not enforced: a free answer is always accepted.
- **Stored.** The `spec_approved` state change's detail gets `answers`: JSON of one entry per decision, `{ question, answer, accepted_default }`. A decision with no line takes its default (accepted); an answer equal to the default is accepted too; a decision with no default and no answer is stored with `answer: null` and the approval still goes ahead. The detail is flat values, so the list is a JSON string, as `added_paths` is; no schema change. The actor is the approver's user ID: the owner's ID (the local identity, `local:<name>`, or a linked account's ID), never a display name. A split's answers go on its approval's tag and are not carried to the phases.
- **Auto mode.** Its `spec_approved` detail is built by `autoApprovalDetail` (same module): `approved_by`, `mode_change`, the numeric `decisions` count as before, and `answers` with each default taken as accepted.
- **The runs.** The implement and review prompts add a "Decisions for the spec" section after the approver's notes (`decisionsSection`, fenced with the worker's `fenced`): each question, its answer, and whether the default was accepted, labelled untrusted. It is absent when the latest approval has no answers.

**`/revise` on a local item at the merge wait is feedback on its local branch** (decision changed 2026-11-11, issue #563; replaces the decision in History). A local item (`CommandState.local`, from the item's source) with no PR (`change_ref` null) that waits for its merge takes `/revise <feedback>` (`factory revise <id> <feedback>`, the item page, its own thread) as feedback for the implementer. The command table entry has `local_phases` (the merge wait only) and a `local_description`; `appliesLocally()` in `src/core/commands.ts` decides it, so `applies()`, the footer, `/help` (marked **(now)**, with the local description and no PR text), the item API's `commands` (the same `approve_spec` check as approve) and the SET_UP.md table all read it from one place. The controller's `command()` sends it to the existing `prFeedback` with `change_ref` null: the same egress scan, cap, empty-feedback refusal, `pr_revise_requested` state change (the CLI user as actor, the feedback in its detail, no `pr_number`) keyed on the command (a redelivery starts no second run), and one implement run on the local branch (`RUNNING`, `loop_count` + 1) whose prompt gets the feedback section; the review follows on the local branch and a pass returns the item to the merge wait with its merge comment. At the loop limit it blocks with `max_loops`, and the comment says "The feedback would start loop …", not "PR feedback". Unchanged: every other phase of a local item (`failed_review` included, a follow-up) refuses `revise` as before; a GitHub item's issue `/revise` at the merge wait keeps its refusal pointing to PR #N, and PR feedback is as it was.

**`/revise` in a Slack thread is PR feedback** (decision changed 2026-11-09, issue #481; replaces the decision in History). A Slack thread has no PR conversation, so on a Slack-sourced item (`slack_thread`) that has a PR (`change_ref`) and is in a phase that takes PR feedback (`commandSpec("revise").pr_phases`: the merge wait and `failed_review`), a `/revise <feedback>` in the item's thread goes to `prFeedback` with the item's own `change_ref` as the PR: the same scan, cap, empty-feedback refusal, `max_loops` stop, `pr_revise_requested` state change keyed on the comment id (a redelivery starts no second run) and one implement run on the PR branch (`RUNNING`, `loop_count` + 1). At the spec gate and after a failed implement run, a thread `/revise` revises the spec as before; in any other phase it is refused with one reply in the thread that names the phase and gives no "reply on PR #N" hint. In Slack the command goes after a mention (`@factory /revise <feedback>`), because Slack takes a message that starts with `/` as its own slash command; it is a chat command, stored in the command log as the linked factory user and applied by the controller's command step with the item's thread as its source, keyed on the Slack event (a redelivery appends no second row). Unchanged: `/revise` on the PR, and a `/revise` on a GitHub issue in the merge wait, which keeps its refusal pointing to the PR.

**Auto mode answers the spec gate** (decision changed 2026-11-08, issue #444; replaces the decision in History). With the `mode` setting at `auto` (design 03-risk), a spec below tier 4 whose allowed paths touch no gate path and whose decisions all have a proposed default and none is owner-only is approved with no reply: `spec_approved`, actor `system:auto`, `approved_by: system:auto` and the mode change's audit seq in its detail, and the spec comment lists each decision with the default taken. Any other spec waits at the gate as before and its comment says why. The commands themselves are unchanged; `/revise` and `/reject` still apply to an item auto mode approved, as to any approved item. In manual mode (the default) nothing changes. `factory mode auto|manual` is a CLI command, not a comment command (design 08-settings).

**`/resolve +paths` and `/resolve` notes** (decision changed 2026-11-08; current): its text moved to History, unchanged, to keep this file under its size cap.

**Standing approvals at the spec gate** (decision changed 2026-11-07, issue #299, phase 2 of #293). The rule `spec-t1`, the approval it gives, its protected paths, its turn-off by `/revise` or `/reject` and who may set it are in `05-standing-approvals.md`. **`/standing [accept|decline <rule>]`** is in the command table: with no arguments it shows the rule's state; it gets 👀 and one reply keyed on the comment, and none when the rule is already in the asked state. It is a factory command, about the rules and not the item, so `/help` and the `SET_UP.md` table list it and no footer does (like `/link`). It is parsed in the one comment parser (`src/core/commands.ts`), turned into a `standing_requested` event by `commentEvent` (`src/core/comment-event.ts`, so the command inbox and Slack get it) and by the GitHub issue source, and answered on a work item only.

**Widening allowed paths from a command** (decision changed 2026-11-07, issue #280). `/approve +paths <path>...` and `/retry +paths <path>...` add paths to the item's `allowed_paths` in the same store transition that queues the implement run; the scope gate, the floor check and the implement prompt all read the widened list, since the run loads the item fresh. `+paths` starts the first line of the command's text; the paths are the rest of that line (whitespace-separated, a path may be in backticks, a leading `./` is dropped) and the lines below are the note. At most 10 paths per command; a path that is empty, absolute, has `..` or has a glob is refused with one reply and nothing changes (the whole text is egress-scanned first, so a refusal never quotes a flagged path). Paths already covered by `allowed_paths` (the scope gate's rule, `isCovered`, which also always covers the ratchet lists under `tests/architecture/known-violations/`) are not added again; with none left, the command applies with the paths unchanged and one reply on the comment (keyed on it) says so: "`/retry` was applied; its `+paths` added nothing to the allowed paths, already allowed: <paths>" (since 2026-11-16, design 05-restarts). The same for `/approve +paths` and `/resolve +paths`. With some new paths, only those are added and no such reply is posted. Added paths under a floor raise the tier to the highest such floor, as triage does, and never lower it; on a floor block that combines with the block's tier. The state change (`spec_approved`, `floor_tier_approved` or `retry_requested`) has the user as actor, the old and new `allowed_paths` (and tier) in `changes`, and `detail.added_paths` (a JSON list). `/approve +paths` applies where `/approve` applies to a spec or a floor block (spec waiting, max revisions, floor block). It is refused on a split spec (that approval files sub-issues), on an implement run held by coordination cost (the run is already queued), and from app requests (`args.note` is a note, never parsed for paths). `/retry +paths` applies only when the failed run is an implement run; on a triage, review, update or resolve run it is refused with one reply and nothing changes. **`/retry` takes notes** on the same line or below: scanned and capped at 2000 characters like `/approve` notes, stored as `detail.note` on `retry_requested`, and shown in the implement and review prompts in the "Notes from the approver" section (after the latest approval's note, labelled "After `/retry`:"); a retried resolve run also gets it as its notes. Triage prompts do not show it. **The reply is given, never applied by an agent.** An implement run's `needs_human` may carry `paths` (at most 10); the comment then gives the exact `/retry +paths ...` reply for the ones not yet covered, and a `scope_violation` comment does the same for its files (when no single reply can, more than 10 or a name with a space or glob, it points to `/revise`). Agent output never changes `allowed_paths`; only the owner's command does.

**Gate commands.** On a spec waiting for approval (`READY` / `spec_pending`), a user with write permission replies one of:
- `/approve`: implementation starts, as before.
- `/reject <reason>`: the item closes (`close_reason: rejected`). It is recorded first, as `CLOSED` with `blocked_on: upstream` / `blocked_reason: source_close_pending` and the reason in `spec_feedback`; then the controller posts one comment quoting the reason (marker `rejected:<item id>`, so never twice), closes the GitHub issue as "not planned" (`SourceAdapter.closeIssue`), and clears the mark (`source_closed`). **An open PR is closed too** (decision changed 2026-11-09, issue #452, see History): on an item with a PR and a forge, the mark moves to `pr_close_pending` instead, and outbound delivers one keyed `close_pr` action, one comment on the PR quoting the reason (marker `pr-closed:<item id>`), then the PR closed without a merge; the mark clears when outbound reports it done. A PR already merged or closed gets no comment and no close. A failed PR close keeps the mark and is retried (outbound's backoff, and each intake tick records the same keyed action again), and the marker keeps a retry from posting a second comment. A `/reject` at a budget checkpoint still leaves the PR as it is. A local item's close needs no source adapter: its comment is a thread entry and nothing waits on a sync plugin. If the factory stops in between, every intake tick finishes items still marked. With no reason, the item and the issue still close.
- `/revise <feedback>`: the item stays open and goes back to `NEW` (`spec_revision_requested`, actor: that user) with a new triage run keyed `<item>:triage:l<loop>:r<restart>:v<n>`, which differs from the intake key and from every earlier revision. The run's prompt has the original issue text (`issue_text`), the previous spec, and the feedback under a heading that labels it untrusted, in a fence it cannot close. The new spec is a new comment and waits for the same three commands. With no feedback text the command is refused with a reply and nothing changes. The first `max_loops` revisions each run triage; the next `/revise` sets `blocked_on: human` / `blocked_reason: max_revisions`, posts one comment, and starts no run. `/approve` and `/reject` still apply there, so a human always has a way out; a further `/revise` is refused.

All three need write permission, and on an item in any other state they are refused with one reply. **Refusals name the state by its label.** Every refusal and every `/help` reply describes the item's state with the same label as the command table (`phaseLabel` in `src/core/commands.ts`, e.g. "implementing", "waiting for a human merge"), never `NEW`, `READY`, `RUNNING`, `REVIEW` or `CLOSED` and never a `blocked_on` / `blocked_reason` value; a test checks every state. A new item's PR is titled with the issue title in full, with no prefix (decision changed 2026-11-07, issue #229); items with no stored title (from before titles were kept) keep the old rule. Schema: migration 6 adds `issue_text`, `revision_count` and `spec_feedback` (SQLite); old rows have `issue_text` null, and their revision prompt points at the source link instead.

**Feedback on a pull request.** On a PR waiting for a human merge, or whose review run failed (`failed_review`), a writer's `/revise <feedback>` comment on the PR, or a writer's GitHub review with "Request changes", sends that feedback to one implement run on the PR branch, followed by a fresh review. This covers factory and adopted PRs. The GitHub source reads `/revise` on a PR's conversation (with the PR's head, through `pullHead`) and, on the open PRs it already reports, `CHANGES_REQUESTED` reviews by a person, with their line comments (path, line, text); approvals, plain comments, dismissed and pending reviews start nothing, and reviews from before the source first read them are skipped. The controller (`prFeedback`) refuses outside the two states (naming the state's label), refuses empty feedback and feedback the egress scanner flags, and caps it at 8000 characters. Each round adds one to `loop_count`: at `max_loops` the item blocks with `max_loops` and one comment, and no run starts. Otherwise the item goes to `RUNNING` and one implement run is keyed `runKey(next)` with the feedback as its input; the state change (`pr_revise_requested` or `pr_changes_requested`) records the comment or review id, so a redelivered event changes nothing. The implement prompt gets a "Feedback on the pull request" section, labelled untrusted and fenced like the approver's note; an automatic retry reads it from that state change. A reviewer without write permission is ignored; a writer's review in a state that cannot take it gets one reply on the PR. Footers on a PR start with "On the pull request, you can reply with:" when `/revise` applies there.

**Approval notes, `/help`, unknown commands and footers.** One table in `src/core/commands.ts` lists every command (name, usage, one-line description, the item states where it applies, whether it needs a PR) and holds the parser. A command is the comment's first line: `/` plus letters (any case), then whitespace, the end of the line or one of `.,:;!?`; anything else (`/`, `/ x`, `/src/x.ts`, `/approve2`) is not a command, and `/rejectfoo` is an unknown command, not `/reject`. The text after the command word, same line and following lines joined by a newline and trimmed, is the command's text.
- `/approve [notes]` on a spec or a floor block: the note is untrusted. After the permission check (a non-writer's note is never stored), the whole note goes through the `EgressScanner`; a finding refuses the approval with one reply naming the rule, stores nothing and leaves the stage. Otherwise the note, capped at 2000 characters, goes on the approval's `controller_state_changes` row as `detail.note` (`spec_approved` or `floor_tier_approved`; no schema change). The implement and review prompts get a "Notes from the approver" section, labelled untrusted and fenced, holding the note of the item's latest approval that has one; with none the section is absent. Prompt files are unchanged; the section is added in code.
- An unknown command on a work item gets 👀 and one reply (`Unknown command "/xyz".`, then the commands for the item's current state, then `/help`), keyed on the comment id. `/help` gets one reply listing every command and marking the ones that apply now; it names the current state by its label, not the phase id. On an issue that is not a work item, both get no reply and no 👀. Neither needs write permission: they change nothing.
- Every comment that waits for a human (spec, max revisions, floor block, failed run, dead letter, diff too large, failed update, max loops, merge waiting) ends with a footer built from the same table, for the state the item will be in after the transition (these comments are posted before it). Where no listed command changes the state (merge waiting), a last line says so. A test runs every command in every state through the controller and checks that the footer lists exactly the accepted ones; another fails when the command table in `SET_UP.md` differs from the code. A known command in the wrong state keeps its existing refusal reply.
