- **Health reads answer from the stored report; no timer (decision changed 2026-11-23, wi_926cad13; current; replaces "the first read waits, a timer runs while the page is in use", see History).** The UI server's `GET /api/health` and `GET /api/v1/health` return the same stored report at once (`HealthMonitor.serveStored`, over `BackgroundSnapshot` in `src/ui/background-refresh.ts`, the one helper for this). Before the first run ends they answer `pending: true` with `checked_at: null` and no checks, and the page keeps its placeholder (the shared `Loading`, label "Health checks") and reads again each second. `checked_at` is when the stored run finished. A read starts a background run only when the stored run is `HEALTH_MIN_INTERVAL_MS` (60 s) old or a successful write (POST) marked it stale; a write also starts the next run at once. The read that starts a run never waits for it, one run at a time per process, and `refreshing: true` says one is going. There is no timer: with no reads and no writes no check runs. A run that throws keeps the last good report and its time; with no good run the report is the one FAIL row (retried when the next run is due). A `HealthMonitor` the server did not set to serve stored (tests calling `respond` directly, `factory doctor`'s callers) keeps the on-demand behaviour: at most one run per 60 s, concurrent requests share it. The checks are unchanged; the report adds `pending` and `refreshing`.

- **No store check (decision changed 2026-11-11, issues #590 and #567; before: doctor and the Health panel had a store check over `schemaVersion()`, see History).** The store is SQLite only (`05-coordination.md`), so `doctorChecks` opens no store: no store reachability or schema line, no store password check, and no `storeErrorCheck`. - **Health report (new decision, 2026-11-01; the server-rendered panel is removed, see the top).** `GET /api/health` returns `{ checked_at, checks: [{ status: "ok" | "warn" | "fail", msg }] }`: the same checks, order, results and messages as `factory doctor`, because both call the one `doctorChecks` (`src/setup.ts`); the UI holds no check logic, and the ui command (`src/cli/handlers/ui/`) hands `doctorChecks` to the UI's `HealthMonitor`. The `--llm` line is not in the report, so a read makes no model call. Checks run at most once per 60 s per UI process, measured between run starts; every read of the report counts, and requests that arrive during a run wait for that run. The limit is in-process state on purpose: it throttles a read-only probe per process and nothing else depends on it. Every message goes through the `Withholder` before it leaves (GitHub error text can carry a secret), so a flagged message shows `[withheld: <rule>]`. A run that throws (doctor would stop) shows as one FAIL. Same request guards as every other path: GET and HEAD only, Host check.
- **Host sleeps on the Health API (new decision, 2026-11-07, issue #218).** `GET /api/v1/health` returns the same report as `GET /api/health` plus `sleeps`: the 10 newest host sleeps (design §5 Host sleep), newest first (`woke_at`, then worker id), each `{ worker_id, woke_at, gap_ms, run_id }`, and an empty list when there are none. Ids, timestamps and numbers only: no free text reaches the response (the worker id passes the Withholder like every id). The read is a report, never a gate: when it fails (e.g. a database without step 0028) `sleeps` is empty and the checks still answer. `GET /api/v1/items/<id>` adds `sleeps`: those recorded during one of the item's runs (by `run_id`). The app's Health page lists them as "host slept N min" (N = `gap_ms` in whole minutes, at least 1) with the wake time, or "No host sleep recorded."; the item page's timeline shows each as "host slept N min" among the state changes, by time. `GET /api/health` keeps its shape.

The route, its guards and the owner check are in [09-dashboard-app.md](09-dashboard-app.md); the store method in [05-restarts.md](05-restarts.md).
- **Thresholds: token expiry and a pending schema step (decision changed 2026-11-07, issue #311; before: see History).** The GitHub token check counts whole days left, rounded down (`tokenExpiryCheck`, `src/setup.ts`, from the repository GET's expiry header; App sign-in is below): **0 days or less is a FAIL**, **1 or 2 days a warn** (both say `(run: npm run setup -- --rotate-github)`), **3 days or more ok** (`… (recommended ≤ 30 when shared)`); a token that never expires stays a warn. The check carries `token_days`, so Needs you reads the last run's value (design §9 Status page) without a GitHub call. **A schema behind the code is a FAIL:** "reachable, schema at version X of Y (run: npm run migrate)", because every command refuses to start until `npm run migrate` ran; a schema newer than the code stays a warn.
- **App sign-in has no token-expiry threshold (decision changed 2026-11-08, issue #434).** When the credentials plugin gives a grant (GitHub App), `tokenExpiryCheck` is ok, "GitHub App token minted (renewed automatically)", reads neither the grant's expiry nor GitHub, and carries no `token_days`, so Needs you shows no token item. The factory mints a new token on each use, so the mint's one-hour expiry is not a warning and rotating does nothing. A failed mint stays a FAIL in the credentials check.
- **Ok rows fold behind a count (new decision, 2026-11-07, issue #311).** The app's Health page shows the fail and warn rows (fail first) and folds the ok rows into one closed `<details>` whose summary is their count ("22 ok"). `GET /api/health` and `GET /api/v1/health` still list every check.
- **Read-only schema probe.** `FactoryStore.schemaVersion()` returns `{ applied, latest }` with one read and no lock, table creation or migration (SQLite reads `sqlite_master` first). Since 2026-11-11 no doctor check calls it (the store check is gone, above); no check on the health path writes to the store.
