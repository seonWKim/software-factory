# 9. Status page: health panel and schema probe

- **Health panel (new decision, 2026-11-01).** `/` has a Health section and `GET /api/health` returns `{ checked_at, checks: [{ status: "ok" | "warn" | "fail", msg }] }`: the same checks, order, results and messages as `factory doctor`, because both call the one `doctorChecks` (`src/setup.ts`); the UI holds no check logic, and `main.ts` hands `doctorChecks` to the UI's `HealthMonitor`. The `--llm` line is not on the panel, so opening the page makes no model call. Checks run at most once per 60 s per UI process, measured between run starts; page loads (including the 5 s meta refresh), the panel's refresh link (`/?health=refresh`) and the API all count, the refresh link never bypasses the limit, and requests that arrive during a run wait for that run. The limit is in-process state on purpose: it throttles a read-only probe per process and nothing else depends on it. Every message goes through the `Withholder` before the API or the page (MySQL and GitHub error text can carry a secret), so a flagged message shows `[withheld: <rule>]`. A run that throws (doctor would stop) shows as one FAIL. Same request guards as every other path: GET and HEAD only, Host check.
- **Host sleeps on the Health API (new decision, 2026-11-07, issue #218).** `GET /api/v1/health` returns the same report as `GET /api/health` plus `sleeps`: the 10 newest host sleeps (design §5 Host sleep), newest first (`woke_at`, then worker id), each `{ worker_id, woke_at, gap_ms, run_id }`, and an empty list when there are none. Ids, timestamps and numbers only: no free text reaches the response (the worker id passes the Withholder like every id). The read is a report, never a gate: when it fails (e.g. a MySQL database without step 0027) `sleeps` is empty and the checks still answer. `GET /api/v1/items/<id>` adds `sleeps`: those recorded during one of the item's runs (by `run_id`). The app's Health page lists them as "host slept N min" (N = `gap_ms` in whole minutes, at least 1) with the wake time, or "No host sleep recorded."; the item page's timeline shows each as "host slept N min" among the state changes, by time. `GET /api/health` and the classic page keep their shape.
- **Claim pauses on the Health page (new decision, 2026-11-07, issue #291).** The app's Health page lists each claim pause in effect above the checks (name, what it stops, when it ends; the `model_stall` row's time is the next probe) with a "Resume now" button that calls `POST /api/v1/pauses/resume`; an error from the endpoint shows next to that button. The checks themselves are unchanged: the `agents paused: model not answering since …` row still comes first while a stall pause holds, and the checks still write nothing. The route, its guards and the owner check are in [09-dashboard-app.md](09-dashboard-app.md); the store method in [05-restarts.md](05-restarts.md).
- **Read-only schema probe.** `FactoryStore.schemaVersion()` returns `{ applied, latest }` with one read and no lock, table creation or migration (SQLite reads `sqlite_master` first; MySQL treats a missing `schema_migrations` as version 0). doctor's MySQL check and the health path both use it (option (a) of issue #106): up to date stays "reachable, schema up to date"; a schema behind the code is a warn ("schema at version X of Y (the factory migrates it when it starts)"), not a FAIL, because `build()` migrates on start; a schema newer than the code is a warn too. No check on the health path writes to the store.

## History

- **Claim pauses on the Health page** (new decision, 2026-11-07, issue #291). Before: the Health page showed only the checks, so a timed pause (`rate_limit`, `forge_auth`, `preflight_access`) was not visible and could not be ended from the app.
- **Read-only schema probe** (decision changed, 2026-11-01). Before: doctor's MySQL check ran `store.migrate()`, so doctor, and `setup` through it, created or upgraded the schema.
