# 9. Status page: health panel and schema probe

- **No store check (decision changed 2026-11-11, issues #590 and #567; before: doctor and the Health panel had a MySQL check over `schemaVersion()`, see History).** The store is SQLite only (`05-coordination.md`), so `doctorChecks` opens no store: no store reachability or schema line, no store password check, and no `storeErrorCheck`. The health path makes no store call at all (`tests/health.test.ts`).
- **Health panel (new decision, 2026-11-01).** `/` has a Health section and `GET /api/health` returns `{ checked_at, checks: [{ status: "ok" | "warn" | "fail", msg }] }`: the same checks, order, results and messages as `factory doctor`, because both call the one `doctorChecks` (`src/setup.ts`); the UI holds no check logic, and the ui command (`src/cli/handlers/ui/`) hands `doctorChecks` to the UI's `HealthMonitor`. The `--llm` line is not on the panel, so opening the page makes no model call. Checks run at most once per 60 s per UI process, measured between run starts; page loads (including the 5 s meta refresh), the panel's refresh link (`/?health=refresh`) and the API all count, the refresh link never bypasses the limit, and requests that arrive during a run wait for that run. The limit is in-process state on purpose: it throttles a read-only probe per process and nothing else depends on it. Every message goes through the `Withholder` before the API or the page (GitHub error text can carry a secret), so a flagged message shows `[withheld: <rule>]`. A run that throws (doctor would stop) shows as one FAIL. Same request guards as every other path: GET and HEAD only, Host check.
- **Host sleeps on the Health API (new decision, 2026-11-07, issue #218).** `GET /api/v1/health` returns the same report as `GET /api/health` plus `sleeps`: the 10 newest host sleeps (design §5 Host sleep), newest first (`woke_at`, then worker id), each `{ worker_id, woke_at, gap_ms, run_id }`, and an empty list when there are none. Ids, timestamps and numbers only: no free text reaches the response (the worker id passes the Withholder like every id). The read is a report, never a gate: when it fails (e.g. a database without step 0028) `sleeps` is empty and the checks still answer. `GET /api/v1/items/<id>` adds `sleeps`: those recorded during one of the item's runs (by `run_id`). The app's Health page lists them as "host slept N min" (N = `gap_ms` in whole minutes, at least 1) with the wake time, or "No host sleep recorded."; the item page's timeline shows each as "host slept N min" among the state changes, by time. `GET /api/health` and the classic page keep their shape.
- **Claim pauses on the Health page (new decision, 2026-11-07, issue #291).** The app's Health page lists each claim pause in effect above the checks (name, what it stops, when it ends; the `model_stall` row's time is the next probe) with a "Resume now" button that calls `POST /api/v1/pauses/resume`; an error from the endpoint shows next to that button. The checks themselves are unchanged: the `agents paused: model not answering since …` row still comes first while a stall pause holds, and the checks still write nothing. The route, its guards and the owner check are in [09-dashboard-app.md](09-dashboard-app.md); the store method in [05-restarts.md](05-restarts.md).
- **Thresholds: token expiry and a pending schema step (decision changed 2026-11-07, issue #311; before: see History).** The GitHub token check counts whole days left, rounded down (`tokenExpiryCheck`, `src/setup.ts`, from the repository GET's expiry header; App sign-in is below): **0 days or less is a FAIL**, **1 or 2 days a warn** (both say `(run: npm run setup -- --rotate-github)`), **3 days or more ok** (`… (recommended ≤ 30 when shared)`); a token that never expires stays a warn. The check carries `token_days`, so Needs you reads the last run's value (design §9 Status page) without a GitHub call. **A schema behind the code is a FAIL:** "reachable, schema at version X of Y (run: npm run migrate)", because every command refuses to start until `npm run migrate` ran; a schema newer than the code stays a warn.
- **App sign-in has no token-expiry threshold (decision changed 2026-11-08, issue #434).** When the credentials plugin gives a grant (GitHub App), `tokenExpiryCheck` is ok, "GitHub App token minted (renewed automatically)", reads neither the grant's expiry nor GitHub, and carries no `token_days`, so Needs you shows no token item. The factory mints a new token on each use, so the mint's one-hour expiry is not a warning and rotating does nothing. A failed mint stays a FAIL in the credentials check.
- **Ok rows fold behind a count (new decision, 2026-11-07, issue #311).** The app's Health page shows the fail and warn rows (fail first) and folds the ok rows into one closed `<details>` whose summary is their count ("22 ok"). `GET /api/health`, `GET /api/v1/health` and `/classic` still list every check.
- **Read-only schema probe.** `FactoryStore.schemaVersion()` returns `{ applied, latest }` with one read and no lock, table creation or migration (SQLite reads `sqlite_master` first). Since 2026-11-11 no doctor check calls it (the store check is gone, above); no check on the health path writes to the store.

## History

- **Current text names SQLite only** (decision changed 2026-11-11, issue #567). Before: the first decision was titled "No MySQL check"; the Host sleeps paragraph named a MySQL database without step 0028; the schema probe said MySQL treated a missing `schema_migrations` as version 0 and that the MySQL check was gone.
- **MySQL check** (decision changed 2026-11-11, issue #590). Before: with a MySQL store, doctor read `schemaVersion()` and printed "MySQL <user>@<host>:<port>/<db> reachable, schema up to date" (or behind: FAIL with `npm run migrate`; unreachable: FAIL with the connection fix from `storeErrorCheck`).
- **App token expiry** (decision changed 2026-11-08, issue #434). Before: an App token's expiry came from its mint response and went through the same day thresholds, so the hour-long expiry failed on every App factory and told the owner to run the rotate command.

- **Thresholds** (decision changed 2026-11-07, issue #311). Before: the token check warned only above 30 days (rounded to the nearest day), so a token expiring in 2 days showed ok; a schema behind the code was a warn, "schema at version X of Y (the factory migrates it when it starts)".
- **Claim pauses on the Health page** (new decision, 2026-11-07, issue #291). Before: the Health page showed only the checks, so a timed pause (`rate_limit`, `forge_auth`, `preflight_access`) was not visible and could not be ended from the app.
- **Read-only schema probe** (decision changed, 2026-11-01). Before: doctor's MySQL check ran `store.migrate()`, so doctor, and `setup` through it, created or upgraded the schema.
