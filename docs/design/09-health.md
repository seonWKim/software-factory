# 9. Status page: health panel and schema probe

- **Health reads answer from a background snapshot (decision changed 2026-11-19, local-task-tk_b2bfa355; current; replaces the on-request checks, see History).** The UI server's `GET /api/health` and `GET /api/v1/health` return the last run at once (`HealthMonitor.start`, over `BackgroundSnapshot` in `src/ui/background-refresh.ts`); `checked_at` is that run's time. The first read after start waits for the first run only. While started, a run happens every `HEALTH_MIN_INTERVAL_MS` (60 s) only if either route was read in the last 10 minutes (an idle owner's page makes no GitHub call), after each successful write (POST) in the background, and once when the first read after an idle spell returns the last result. A run that throws keeps the last good report and its time; with no good run yet the report is the one FAIL row as before. `startUi` starts it and closing the server stops it. A `HealthMonitor` that is not started (tests calling `respond` directly, `factory doctor`'s callers) keeps the on-demand behaviour: at most one run per 60 s, concurrent requests share it. The checks and the report shape are unchanged.
- **The checks are read only through the API (decision changed 2026-11-16, phase 4 of 4 of local-task-tk_3164aaa9-e569-4086-9e6d-013b63474c69-phase-2; current; replaces "`/` has a Health section" and its refresh link `/?health=refresh` of the Health panel decision below, see History).** The decision that changed: **`/classic` and its Health panel are removed (design 09-dashboard-app), and `HealthMonitor.section` with them.** `GET /api/health`, `GET /api/v1/health` and the app's Health page read `HealthMonitor.report` (`src/ui/health.ts`), and the overview's GitHub sync line comes from `syncChecks`; both are unchanged. The 60 s limit stays: every read of the report counts.
- **The Health page has tabs, one row per sleep, plain "you" (new decision, 2026-11-15; changes "Host sleeps on the Health API" (list), "Claim pauses on the Health page" (placement) and "Ok rows fold behind a count" (kept, inside a tab)).** The app's Health page keeps the code-revision line above the shared underline `Tabs`: Checks (default), Claim pauses (only while a pause holds), Host sleeps, Merged without review. The selected tab is the `tab` query parameter, read and written in place (no history entry) by `useUrlParam` (`web/src/lib/url-param.ts`, also used by Plugins and the Tasks project tabs); no parameter or an unknown one selects Checks, and with no window (server rendering) it reads as none. Each label shows its count (all checks, pauses in effect, grouped sleep rows, merges); the Checks label carries "⚠ failing" while any check is a fail, a warn does not. The Checks tab lists fail rows, then warn rows, and folds the ok rows behind their count. Host sleeps shows one row per sleep event: API entries with the same `woke_at` become one row, "host slept N min" (N from the largest `gap_ms`), the wake time and the workers as one text ("workers 0–4" from their slot numbers; "workers 0, 2" when not consecutive). The API and its 10-entry cap are unchanged, so a sleep that hit many workers leaves fewer than 10 rows. Merged by is plain text: "you" for the viewer, "a person" otherwise, the user ID as the cell's `title`; no disclosure, no Copy button (`PersonName` and `IdDetails` are unchanged for other pages).
- **No store check (decision changed 2026-11-11, issues #590 and #567; before: doctor and the Health panel had a store check over `schemaVersion()`, see History).** The store is SQLite only (`05-coordination.md`), so `doctorChecks` opens no store: no store reachability or schema line, no store password check, and no `storeErrorCheck`. The health path makes no store call at all (`tests/health.test.ts`).
- **Health report (new decision, 2026-11-01; the server-rendered panel is removed, see the top).** `GET /api/health` returns `{ checked_at, checks: [{ status: "ok" | "warn" | "fail", msg }] }`: the same checks, order, results and messages as `factory doctor`, because both call the one `doctorChecks` (`src/setup.ts`); the UI holds no check logic, and the ui command (`src/cli/handlers/ui/`) hands `doctorChecks` to the UI's `HealthMonitor`. The `--llm` line is not in the report, so a read makes no model call. Checks run at most once per 60 s per UI process, measured between run starts; every read of the report counts, and requests that arrive during a run wait for that run. The limit is in-process state on purpose: it throttles a read-only probe per process and nothing else depends on it. Every message goes through the `Withholder` before it leaves (GitHub error text can carry a secret), so a flagged message shows `[withheld: <rule>]`. A run that throws (doctor would stop) shows as one FAIL. Same request guards as every other path: GET and HEAD only, Host check.
- **Host sleeps on the Health API (new decision, 2026-11-07, issue #218).** `GET /api/v1/health` returns the same report as `GET /api/health` plus `sleeps`: the 10 newest host sleeps (design §5 Host sleep), newest first (`woke_at`, then worker id), each `{ worker_id, woke_at, gap_ms, run_id }`, and an empty list when there are none. Ids, timestamps and numbers only: no free text reaches the response (the worker id passes the Withholder like every id). The read is a report, never a gate: when it fails (e.g. a database without step 0028) `sleeps` is empty and the checks still answer. `GET /api/v1/items/<id>` adds `sleeps`: those recorded during one of the item's runs (by `run_id`). The app's Health page lists them as "host slept N min" (N = `gap_ms` in whole minutes, at least 1) with the wake time, or "No host sleep recorded."; the item page's timeline shows each as "host slept N min" among the state changes, by time. `GET /api/health` keeps its shape.
- **Claim pauses on the Health page (new decision, 2026-11-07, issue #291).** The app's Health page lists each claim pause in effect above the checks (name, what it stops, when it ends; the `model_stall` row's time is the next probe) with a "Resume now" button that calls `POST /api/v1/pauses/resume`; an error from the endpoint shows next to that button. The checks themselves are unchanged: the `agents paused: model not answering since …` row still comes first while a stall pause holds, and the checks still write nothing. The route, its guards and the owner check are in [09-dashboard-app.md](09-dashboard-app.md); the store method in [05-restarts.md](05-restarts.md).
- **Thresholds: token expiry and a pending schema step (decision changed 2026-11-07, issue #311; before: see History).** The GitHub token check counts whole days left, rounded down (`tokenExpiryCheck`, `src/setup.ts`, from the repository GET's expiry header; App sign-in is below): **0 days or less is a FAIL**, **1 or 2 days a warn** (both say `(run: npm run setup -- --rotate-github)`), **3 days or more ok** (`… (recommended ≤ 30 when shared)`); a token that never expires stays a warn. The check carries `token_days`, so Needs you reads the last run's value (design §9 Status page) without a GitHub call. **A schema behind the code is a FAIL:** "reachable, schema at version X of Y (run: npm run migrate)", because every command refuses to start until `npm run migrate` ran; a schema newer than the code stays a warn.
- **App sign-in has no token-expiry threshold (decision changed 2026-11-08, issue #434).** When the credentials plugin gives a grant (GitHub App), `tokenExpiryCheck` is ok, "GitHub App token minted (renewed automatically)", reads neither the grant's expiry nor GitHub, and carries no `token_days`, so Needs you shows no token item. The factory mints a new token on each use, so the mint's one-hour expiry is not a warning and rotating does nothing. A failed mint stays a FAIL in the credentials check.
- **Ok rows fold behind a count (new decision, 2026-11-07, issue #311).** The app's Health page shows the fail and warn rows (fail first) and folds the ok rows into one closed `<details>` whose summary is their count ("22 ok"). `GET /api/health` and `GET /api/v1/health` still list every check.
- **Read-only schema probe.** `FactoryStore.schemaVersion()` returns `{ applied, latest }` with one read and no lock, table creation or migration (SQLite reads `sqlite_master` first). Since 2026-11-11 no doctor check calls it (the store check is gone, above); no check on the health path writes to the store.
