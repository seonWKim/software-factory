# 9. Status page: dashboard item page, the Thread and queued feedback

Part of the item page ([09-dashboard-item.md](09-dashboard-item.md)).

- **An owner command row shows the permission mode it ran under (decision changed 2026-11-28, phase 2 of local-task-tk_cad55672; current; adds to the owner entries of the Thread decision below).** `threadRows` (`src/ui/thread.ts`) copies the command row's stored `permission_mode` (`ask_all`, `ask_irreversible`, `full`) onto the thread row; `Thread` shows it in the row's header as the mode's Settings label (`data-permission-mode`). A command stored before the mode was recorded has no field and shows no mode; no migration or backfill. Read-only: no gate logic, no store change.

- **A thread message's headings start at h3 (decision changed 2026-11-21; current; replaces Markdown's fixed h(N+2) mapping in the thread, see History).** `Markdown` takes `renumberHeadings` (default false); `Thread` sets it. A message's shallowest heading is h3 and each deeper level steps down one (h4, h5, h6), skipping none (axe `heading-order`).

- **The item page lists feedback queued while implementing (decision changed 2026-11-15, design 04-gate-commands, `/revise` while implementing; current; adds to "All of it sits in one What you need to decide box", see History).** A `/revise` sent while the item implements is queued (a `revise_queued` state change) and applied when the run ends. The item page's decide box (`ItemCommands` in `web/src/views/item-commands.tsx`) lists each pending feedback's text under "Feedback (queued)", below In short, in both its forms (commands that apply, or none). `pendingFeedback` reads it from the item API's `timeline`, which already carries each state change's detail: a `revise_queued` row is pending until a `revise_applied` or `max_loops` row names its comment ID in `comment_ids`, the same rule as the controller's `pendingRevises` (`src/controller/units/commands/queued-revise.ts`). No API, store or setting change; the heading reuses the catalog's `commands.feedback` and `items.queued` texts. Feedback that stays pending after a failed or blocked run stays listed.

- **The item's Thread is newest first and shows the owner's own messages (decision changed 2026-11-13; current, except that the list is collapsed after its first message: the decision-first item page at the top; replaces "the Thread lists the item's thread entries and verdicts oldest first, each with its full body", see History).** **Order:** newest first (time, then seq), so the latest message and what it asks are at the top of the Thread, with no scrolling and no scroll-to-bottom script. A URL anchor (`#msg-<seq>`) still wins: the page scrolls to it and that message starts expanded. **Owner entries:** the item API's `thread` rows get `role` (`factory` or `owner`). Owner rows are: the item's commands `/approve`, `/revise`, `/retry`, `/reject`, `/merge` and `/verdict` sent from the local CLI (origin `cli`) or the dashboard (origin `app`), read with the new `listItemCommands` (one `inbound_commands` read, no schema change, no remote call), each with `kind` the command's name, its text (CLI `args.text`, dashboard `args.note`) through the Withholder as `body`, its stored actor ID as `author`, and `channel` `cli` or `app`, anchor `command-<id>`, seq 0; every non-factory thread entry (a GitHub comment or Slack message, which the source already stored once with its actor ID, else `unknown`), marked `owner` instead of getting a second row from the command table (the owner's choice: GitHub-origin commands are not read from `inbound_commands`); and the item's verdicts. **Page:** owner entries are right aligned and tinted, labelled "You" with the stored ID beside it, the channel in words (`local CLI`, `dashboard`, else the source type). A factory message longer than its one-line summary (first heading, else first sentence) starts as that line with its body behind Show more (Show less folds it again); the newest message, the newest factory message (what a Needs-you reason names), every `spec` and `coordination-hold` (they ask the owner) and the anchored one start expanded. Owner entries are always shown in full. Strings are in the i18n catalog.
