# 4. Agents: gate commands

**Commands from the command inbox** (decision changed 2026-11-07, issue #282). The controller reads every command that does not come in a forge comment from one store table, the command inbox (`command_inbox`), in `seq` order through its own cursor `commands`, every tick and with no source configured. The cursor starts where the `local` source's `intake:local` cursor stopped, so a command it already read is not applied again. A CLI command (`factory approve|retry|revise|reject <id> [text]` on a local item) is rebuilt as `/<command> <text>` and read by the same comment parser as a GitHub comment (`src/core/command-inbox.ts`), then handled as that comment: the same `authorize` check through `AuthProvider` (identity provider `local`, subject the actor, so an account with no link is refused with the not-linked reply), the same command table, the same refusal wording. An app request is written to the inbox too, in the same transaction as its own row (key `app:<seq>`, `args.app_request`), and applied as before (below); SQLite migration 28 (MySQL step `0028-thread-outbox.sql`) copies the requests still pending. The `app_command_requests` table stays only for the request's status (`getAppCommandRequest`, the item API's replies); its pending-request read is removed. Removal plan: once the item API reads a request's status from the command inbox and the thread, the table and its store methods go in one change with its migration. A command whose handling throws (a store error) holds the cursor before it, so it and the ones after it are tried again next tick. Every reply is a thread entry, delivered by the outbox (design 05-sources, "Thread first"), so a failed post no longer keeps a request pending: the refusal is stored on the row at once and the outbox retries the post. No change to the authorize rule, the command table or the refusal wording.

**Widening allowed paths from a command** (decision changed 2026-11-07, issue #280). `/approve +paths <path>...` and `/retry +paths <path>...` add paths to the item's `allowed_paths` in the same store transition that queues the implement run; the scope gate, the floor check and the implement prompt all read the widened list, since the run loads the item fresh. `+paths` starts the first line of the command's text; the paths are the rest of that line (whitespace-separated, a path may be in backticks, a leading `./` is dropped) and the lines below are the note. At most 10 paths per command; a path that is empty, absolute, has `..` or has a glob is refused with one reply and nothing changes (the whole text is egress-scanned first, so a refusal never quotes a flagged path). Paths already covered by `allowed_paths` (the scope gate's rule, `isCovered`) are not added again; with none left, the command applies with the paths unchanged. Added paths under a floor raise the tier to the highest such floor, as triage does, and never lower it; on a floor block that combines with the block's tier. The state change (`spec_approved`, `floor_tier_approved` or `retry_requested`) has the user as actor, the old and new `allowed_paths` (and tier) in `changes`, and `detail.added_paths` (a JSON list). `/approve +paths` applies where `/approve` applies to a spec or a floor block (spec waiting, max revisions, floor block). It is refused on a split spec (that approval files sub-issues), on an implement run held by coordination cost (the run is already queued), and from app requests (`args.note` is a note, never parsed for paths). `/retry +paths` applies only when the failed run is an implement run; on a triage, review, update or resolve run it is refused with one reply and nothing changes. **`/retry` takes notes** on the same line or below: scanned and capped at 2000 characters like `/approve` notes, stored as `detail.note` on `retry_requested`, and shown in the implement and review prompts in the "Notes from the approver" section (after the latest approval's note, labelled "After `/retry`:"); a retried resolve run also gets it as its notes. Triage prompts do not show it. **The reply is given, never applied by an agent.** An implement run's `needs_human` may carry `paths` (at most 10); the comment then gives the exact `/retry +paths ...` reply for the ones not yet covered, and a `scope_violation` comment does the same for its files (when no single reply can, more than 10 or a name with a space or glob, it points to `/revise`). Agent output never changes `allowed_paths`; only the owner's command does.

**Gate commands.** On a spec waiting for approval (`READY` / `spec_pending`), a user with write permission replies one of:
- `/approve`: implementation starts, as before.
- `/reject <reason>`: the item closes (`close_reason: rejected`). It is recorded first, as `CLOSED` with `blocked_on: upstream` / `blocked_reason: source_close_pending` and the reason in `spec_feedback`; then the controller posts one comment quoting the reason (marker `rejected:<item id>`, so never twice), closes the GitHub issue as "not planned" (`SourceAdapter.closeIssue`), and clears the mark (`source_closed`). If the factory stops in between, every intake tick finishes items still marked. With no reason, the item and the issue still close.
- `/revise <feedback>`: the item stays open and goes back to `NEW` (`spec_revision_requested`, actor: that user) with a new triage run keyed `<item>:triage:l<loop>:r<restart>:v<n>`, which differs from the intake key and from every earlier revision. The run's prompt has the original issue text (`issue_text`), the previous spec, and the feedback under a heading that labels it untrusted, in a fence it cannot close. The new spec is a new comment and waits for the same three commands. With no feedback text the command is refused with a reply and nothing changes. The first `max_loops` revisions each run triage; the next `/revise` sets `blocked_on: human` / `blocked_reason: max_revisions`, posts one comment, and starts no run. `/approve` and `/reject` still apply there, so a human always has a way out; a further `/revise` is refused.

**`/revise` after a failed implement run.** Two command phases split out of "blocked by a failed run": `too_large` (the `run_failed:implement:diff_too_large` block, label "blocked: the change was too large") and `failed_implement` (any other implement failure blocked on a human: `max_attempts` or `max_restart` at `RUNNING`, or `run_failed:implement:*`; label "blocked by a failed implement run"). `failed_run` ("blocked by a failed run") keeps failed triage and update runs; a failed review run is its own phase, `failed_review` ("blocked by a failed review run", since 2026-11-04), where `/retry` applies as before. At both new phases `/retry` applies as before, and `/revise <feedback>` sends the item back to `NEW` (`spec_revision_requested`, detail `previous_blocked_reason`), clears the block, adds one to `revision_count` and to `restart_count`, stores the feedback and clears `failure_comment_url`, and queues triage under the spec-gate revision key (`…:v<n>`, the restart count before the bump). Triage writes a new spec with the feedback, which waits at the spec gate; because `restart_count` moved, the next `/approve` queues an implement run under a new key (without the bump it would match the failed run's key and never start). An existing remote branch from the failed attempt is resumed, as `/retry` does. The revision counter and `max_loops` apply as at the spec gate, but at the limit nothing changes: the reply names the limit and offers `/retry` or `/reject <reason>`, and the item keeps its block. `/reject <reason>` also applies at both phases (same close as at the spec gate), so that offer always works. An empty `/revise` gets the same refusal as at the spec gate. `/revise` on the issue stays refused at a floor block, a budget checkpoint and a failed triage, review or update run; at the merge wait and `failed_review` the refusal points to the PR, where `/revise` applies (Feedback on a pull request, below). The size-check comment names `/revise <feedback>` next to `/retry`.

All three need write permission, and on an item in any other state they are refused with one reply. **Refusals name the state by its label.** Every refusal and every `/help` reply describes the item's state with the same label as the command table (`phaseLabel` in `src/core/commands.ts`, e.g. "implementing", "waiting for a human merge"), never `NEW`, `READY`, `RUNNING`, `REVIEW` or `CLOSED` and never a `blocked_on` / `blocked_reason` value; a test checks every state. A new item's PR is titled with the issue title in full, with no prefix (decision changed 2026-11-07, issue #229); items with no stored title (from before titles were kept) keep the old rule. Schema: migration 6 adds `issue_text`, `revision_count` and `spec_feedback` (SQLite and MySQL); old rows have `issue_text` null, and their revision prompt points at the source link instead.

**Feedback on a pull request.** On a PR waiting for a human merge, or whose review run failed (`failed_review`), a writer's `/revise <feedback>` comment on the PR, or a writer's GitHub review with "Request changes", sends that feedback to one implement run on the PR branch, followed by a fresh review. This covers factory and adopted PRs. The GitHub source reads `/revise` on a PR's conversation (with the PR's head, through `pullHead`) and, on the open PRs it already reports, `CHANGES_REQUESTED` reviews by a person, with their line comments (path, line, text); approvals, plain comments, dismissed and pending reviews start nothing, and reviews from before the source first read them are skipped. The controller (`prFeedback`) refuses outside the two states (naming the state's label), refuses empty feedback and feedback the egress scanner flags, and caps it at 8000 characters. Each round adds one to `loop_count`: at `max_loops` the item blocks with `max_loops` and one comment, and no run starts. Otherwise the item goes to `RUNNING` and one implement run is keyed `runKey(next)` with the feedback as its input; the state change (`pr_revise_requested` or `pr_changes_requested`) records the comment or review id, so a redelivered event changes nothing. The implement prompt gets a "Feedback on the pull request" section, labelled untrusted and fenced like the approver's note; an automatic retry reads it from that state change. A reviewer without write permission is ignored; a writer's review in a state that cannot take it gets one reply on the PR. Footers on a PR start with "On the pull request, you can reply with:" when `/revise` applies there.

**Approval notes, `/help`, unknown commands and footers.** One table in `src/core/commands.ts` lists every command (name, usage, one-line description, the item states where it applies, whether it needs a PR) and holds the parser. A command is the comment's first line: `/` plus letters (any case), then whitespace, the end of the line or one of `.,:;!?`; anything else (`/`, `/ x`, `/src/x.ts`, `/approve2`) is not a command, and `/rejectfoo` is an unknown command, not `/reject`. The text after the command word, same line and following lines joined by a newline and trimmed, is the command's text.
- `/approve [notes]` on a spec or a floor block: the note is untrusted. After the permission check (a non-writer's note is never stored), the whole note goes through the `EgressScanner`; a finding refuses the approval with one reply naming the rule, stores nothing and leaves the stage. Otherwise the note, capped at 2000 characters, goes on the approval's `state_changes` row as `detail.note` (`spec_approved` or `floor_tier_approved`; no schema change). The implement and review prompts get a "Notes from the approver" section, labelled untrusted and fenced, holding the note of the item's latest approval that has one; with none the section is absent. Prompt files are unchanged; the section is added in code.
- An unknown command on a work item gets 👀 and one reply (`Unknown command "/xyz".`, then the commands for the item's current state, then `/help`), keyed on the comment id. `/help` gets one reply listing every command and marking the ones that apply now; it names the current state by its label, not the phase id. On an issue that is not a work item, both get no reply and no 👀. Neither needs write permission: they change nothing.
- Every comment that waits for a human (spec, max revisions, floor block, failed run, dead letter, diff too large, failed update, max loops, merge waiting) ends with a footer built from the same table, for the state the item will be in after the transition (these comments are posted before it). Where no listed command changes the state (max loops, merge waiting), a last line says so. A test runs every command in every state through the controller and checks that the footer lists exactly the accepted ones; another fails when the command table in `SET_UP.md` differs from the code. A known command in the wrong state keeps its existing refusal reply.

**Command suggestions for plain-language replies.** The GitHub source now emits a `plain_comment` event (author, comment id, whole body) for each non-bot issue comment that is not a command; PR conversation comments are left alone. The controller, in this order: finds the work item (none: ignored); checks the commenter's write permission with the action the gate commands use (`approve_spec`), and without it makes no model call and posts nothing; skips comments over 300 characters, empty ones and `CLOSED` items; then calls `suggestCommand(text, state, llm)` (`src/core/suggest.ts`). That is one `LLMProvider` call, `model_class: "cheap"`, `data_env: "test"` (the comment is factory input of the same kind as the issue text triage reads). The prompt lists only the commands `commandsFor` allows in the item's state, with their usage lines, never `/verdict` (structured args), and holds the person's text once, in a fenced section labelled untrusted that the text cannot close; the model answers JSON `{command, args, confidence}` with one command name from the list or `none`. Malformed output, any stop reason but `end`, a confidence below 0.7, `none`, extra keys, a command not in the list, or one that does not apply in the state gives no suggestion. Args: `/revise` carries the feedback and `/reject` the reason (the person's text when the model gives none), `/approve` no note, `/budget` only a whole number. Non-empty args go through the `EgressScanner`; a finding drops the suggestion. The reply is one comment keyed on the comment id (`factory:suggest:<comment id>`, so a redelivery posts nothing new): the suggested command in a code block to type, or, with no suggestion, the command list for the state. **The rule: a suggestion never changes state** (no `state_changes` row, no stage or block change, no run, no stored pending suggestion); the person confirms by typing the command, which goes through the normal command path and its permission check. The controller takes the LLM as an optional dependency (`compose.ts` wires the configured one); without it plain comments get no reply. Not built: Slack Confirm/Cancel buttons, suggestions on PR conversations, a per-command permission model (#107 would replace the `approve_spec` check).

**App requests** (issue #245). A request stored in `app_command_requests` (request key, the factory user's id, command, JSON args) is a new entry point to the same command path as a comment, not a new command path. Each controller tick, outside the poll interval, reads them from the command inbox in order (see "Commands from the command inbox"; until 2026-11-07, up to 20 pending rows of the request table). `approve` with `args.work_item_id` (and an optional `args.note`) gets the `/approve` permission check (`approve_spec` on the item, for the request's user), the same note scan and the same transition: on a spec waiting for approval, `spec_approved` with that user as actor and one implement run under the comment path's key. The state change also carries `detail.app_request` (the request's seq), so a request applied but not marked (a crash, another replica) is found and marked applied, with no second change and no refusal. Any other command is refused (`only \`approve\` is applied from an app request`). A refusal reads exactly as the comment path's (`` `/approve` was not applied: <reason>. ``), is written once to the item's thread with the marker `factory:refused:app-<seq>` (the outbox posts it), and is then stored on the row; a request naming no known item stores its refusal and posts nothing. Each request is marked once by a conditional update (`handled_at`, `refusal`; migration 23 on SQLite, step `0023-app-command-handling.sql` on MySQL). Nothing creates requests yet: no endpoint, UI or CLI.

**Verdict command:** a user with write permission (auth action `record_verdict`, separate from `approve_spec`) records a structured verdict with `/verdict accept|changes|reject <severity> <reason>`, on the work item's issue or on its PR. Severity is one of `none`, `minor`, `major`, `critical`. The reason is the text after the severity, following lines included; `accept` may omit it, `changes` and `reject` may not. **A verdict does not change `stage`, `blocked_on` or `blocked_reason`:** it bumps the version and stores a `state_changes` row (reason `human_verdict`, actor = the user's id, `changes` = {}) plus a linked `verdicts` row (verdict, severity, reason, comment id, target `issue`/`pr`). `verdicts.comment_id` is unique, so a redelivered comment stores nothing and gets no second reply. A bad format, an unknown severity, a missing reason, no write permission, a `CLOSED` item, or an item with no PR yet is refused with one reply on the issue, keyed on the comment id, and nothing is stored. A PR comment maps to its item by the PR's head branch. Verdicts are the input for the weighted human-feedback rate that gates auto-merge (§6); computing it is not built yet.

## History

- **Commands from the command inbox** (decision changed 2026-11-07, issue #282). Before: CLI commands reached the controller only through the `local` source's poll, so only when `local` was listed in `plugins.source`; app requests were read straight from their own table each tick; and a refusal reply that failed to post kept an app request pending.
- **Widening allowed paths from a command** (decision changed 2026-11-07, issue #280). Before: allowed paths were set once by triage; `/approve` text was only a note and `/retry` took no text, so a run that needed one more file was refused by the scope gate every time, and the only fix was a `/revise` that ran triage again. No comment told the owner which reply would help.
- **PR titles** (decision changed 2026-11-07, issue #229). Before: `factory: <issue title>`; the prefix pushed titles past 50 characters, and the bot author and the `factory/` branch already mark the PR.
- **Gate commands** (decision changed 2026-11-01). Before: the spec gate took only `/approve` and `/reject <reason>`, a reject dropped its reason and left the issue open, and PR titles were the spec's first line cut at 80 characters.
- **`/revise` after a failed implement run** (decision changed 2026-11-01, issue #91). Before: a failed implement run or a `diff_too_large` block took only `/retry`, which runs the same spec again, so an owner whose change was too big could not change the spec.
- **Refusals name the state by its label** (decision changed 2026-11-01, issue #91). Before: refusals printed the raw stage, and the `/resolve` refusal also printed `blocked_on` and `blocked_reason`, which the owner cannot act on.
- **Approval notes, `/help`, unknown commands and footers** (decision changed 2026-11-01). Before: a note after `/approve` was dropped, `/approve some note` was not even an approval, a mistyped command such as `/aprove` got no reply, and no comment listed the commands that work on an item.
- **Command suggestions for plain-language replies** (decision changed 2026-11-01). Before: the GitHub source dropped every comment that was not a command before the controller saw it, so "ship it" on a spec got no answer and the person could not tell whether the factory understood.
- **Verdict command** (new decision, 2026-11-01). Before: the gate commands were only `/approve`, `/reject` and `/retry`, read only on the issue, and human feedback on a PR was free-form text.
- **App requests** (new decision, 2026-11-07, issue #245). Before: commands came only from comments on the issue or the PR; the `app_command_requests` table (migration 22) was read by nothing.
- **Feedback on a pull request** (decision changed 2026-11-04, issue #178). Before: once a PR existed, `/revise` worked only on the issue at the spec gate or after a failed implement run; `/revise` on the PR found no item, and the GitHub source never read PR reviews, so "Request changes" was lost. `failed_run` also covered failed review runs.
