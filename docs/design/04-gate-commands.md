# 4. Agents: gate commands

**Plain-language messages: proposals for any open item** (decision changed 2026-11-11, issue #583; replaces "a plain comment gets at most one suggested command, for the item it was written on, chosen from the commands of that item's state, and Slack draws Confirm and Cancel under it"). The controller answers a `plain_comment` (the GitHub source's non-command issue comment, a Slack thread's plain reply) in this order: finds the work item (none: ignored); checks the commenter with the action the gate commands use (`approve_spec`; solo default: the local owner, who may run everything; enterprise: the stored grants), and without it makes no model call and posts nothing; skips empty messages, messages over 1000 characters (`INTERPRET_MAX_CHARS`, raised from 300 so one message can name several items) and `CLOSED` items; runs the message through the `EgressScanner` (a finding: no model call, nothing stored, nothing posted). Then `interpret(text, items, llm)` (`src/core/interpret.ts`) makes one `LLMProvider` call, `model_class: "cheap"`, `data_env: "test"`. Its input is only the message and the open-item list, at most 200 items, each with its ID, issue number (null for a local item or a chat thread), title and state label, in fenced sections labelled untrusted that the text cannot close; the system prompt lists the commands a proposal may name (`approve`, `reject`, `revise`, `retry`, `resolve`, `budget`; never `/verdict`, `/standing`, `/link` or `/help`). The model answers JSON `{kind, entries: [{item, command, args}]}` with `kind` one of:
- `commands`: zero or more proposals, each for any listed item (by ID or number). An entry naming an unlisted item, a command that is not proposable or does not apply in the item's state, or `/revise` or `/reject` with no text is dropped. Args are capped at 300 characters on one line; `/budget` keeps only a whole number.
- `show`: a read such as "show 566". The reply is a direct answer built from the stored item (number, title, state label, link), and proposes no command.
- `question`: the message is unclear. The reply is one question that lists its readings (two or more, checked like proposals) as typed lines, and no command.
- `none`, malformed output, a stop reason but `end`, or no entry left after the checks: the reply says no command was found and lists the commands for the item's state (the footer), as before.

Every proposed argument goes through the `EgressScanner`; a finding stores nothing and posts nothing. **The rule: the model's output is never applied** (no `controller_state_changes` row, no stage or block change, no run, no stored pending proposal). The reply is one plain-text comment keyed on the triggering comment id (`factory:suggest:<comment id>`, the marker kept from the suggestion so a comment answered before the change is not answered again; a redelivery posts nothing new). Each proposal shows its item and a fenced line to type on that item (`/approve`, `/approve <note>`, ...), which then goes through the normal command path and its permission check. **Slack and GitHub show a proposal as plain text**: Slack draws no Confirm or Cancel buttons (`suggestedCommand` is gone from `slack-format.ts`; the Slack source still reads a press on a message posted before). Not built: buttons or Confirm and Cancel controls for proposals (a later phase), applying a proposal automatically, a store table for pending proposals, Slack plain-message intake outside an item's thread.

**One refusal and help text on every surface** (decision changed 2026-11-11, issue #528; replaces "each surface reads the command table its own way: the dashboard lists every command of the item's phase, the CLI keeps its own list with no help, `factory approve` stores a row in any state and the refusal comes later from the controller, and in Slack a bare `approve` is no command and `/help` outside an item's thread has no request or `/link` line"). The refusal and help texts are built once, in `src/core/commands.ts`, and every surface uses them: the controller's reply to an issue comment or a Slack thread command (`refusalText`, `CLOSED_REFUSAL`, `CHECKPOINT_REFUSAL`, `dependencyHoldRefusal`, `specNotWaiting`), the dashboard's stored reply (the app-requests unit), the CLI and Slack's item commands (which run through the CLI's code). The wording of every stored refusal is unchanged. **`factory approve <id>`** first runs the controller's own phase check from the item's fields (`approveRefusal`) and, where approve does not apply, prints that refusal and exits 1 before any store write (no command row, no local owner claimed); the controller's later reply would have been the same text. An implement run held by coordination cost (RUNNING, not blocked) and a split parent's states are left to the controller, since the hold is in no field; so `factory approve` is still stored there. The other item commands are stored in any state as before. **Help:** `factory help [<id>]` prints `helpReply`, the issue's `/help` reply: with an item, its state's commands marked **(now)**, without one every command with nothing marked. Slack's help (`chatHelpReply`) lists, in an item's thread, the commands that apply now in the same `- \`usage\`: description.` lines as the issue footer and `/help`; outside one, the reads, the request that starts work and `/link <code>`. Its header shows the `@software-factory /help` form; when `/approve` is listed, a last line says that `approve` with no slash works too after the mention. **Bare approve:** after a mention in an item's thread, `approve` (any case, with its notes) is `/approve` (`BARE_COMMANDS`, `withSlash`); outside an item's thread the same word is a request in plain words, as before. Other bare words (`retry`, `reject`, ...) stay plain words. The controller's authorize check is unchanged. Solo default: no grants needed, the first identity is the local owner and may run everything. Enterprise: the stored grants decide what the dashboard shows (design 09-dashboard-app) and what the controller applies.

**The spec comment says how to answer its decisions** (decision changed 2026-11-11, issue #527; replaces "the spec comment numbers its decisions but does not say how to answer them"). When triage named decisions, the comment's "Decisions for you" section ends, after the folded list, with an answer block (`answerBlock` in `src/core/spec-comment.ts`): one line saying to reply `/approve` with one `N: <answer>` line per decision and that a decision not answered takes its default, then a code block of `/approve` with one `N: <answer>` line per decision. A section with only a tier raise has no block. The reply goes through the one parser below ("Answers to the spec's decisions"), so a GitHub comment, a Slack thread `/approve` (after a mention, the lines below it), the dashboard's approve and `factory approve` store the same `answers`, with the approver's user ID as actor. A `/revise` from Slack or GitHub whose text has `### <Section>` lines (the dashboard's Revise form sends that shape, design 09-dashboard-app) is stored as typed, as any `/revise` text: there is no section reader. No parser, role check, schema or store change; solo and enterprise behave the same.

**Answers to the spec's decisions** (decision changed 2026-11-10, issue #526; replaces "the approve note reaches the implement and review runs as plain text, and auto mode's approval stores only a count of decisions"). An approval answers the spec's numbered decisions (design 04-triage) with `N: <answer>` lines in its note:

- **One parser.** `splitAnswers` in `src/shared/command-notes.ts` (imports nothing outside `src/shared/`) runs in the command unit's `spec_approved` branch, after the note's egress scan and `+paths` split, so `/approve` in a comment, a chat thread, the dashboard's approve and `factory approve` all go through it. The spec's decisions come from the latest applied triage run's stored output (`latestSpec` in `src/core/commands.ts`). With no decisions the note is kept whole. A line whose N names no decision, a repeated N or an empty answer refuses the approval with one reply and stores nothing; other lines remain the note. Options are not enforced: a free answer is always accepted.
- **Stored.** The `spec_approved` state change's detail gets `answers`: JSON of one entry per decision, `{ question, answer, accepted_default }`. A decision with no line takes its default (accepted); an answer equal to the default is accepted too; a decision with no default and no answer is stored with `answer: null` and the approval still goes ahead. The detail is flat values, so the list is a JSON string, as `added_paths` is; no schema change. The actor is the approver's user ID: the local identity in solo (`local:<name>`), the user's ID in a team, never a display name. A split's answers go on its approval's tag and are not carried to the phases.
- **Auto mode.** Its `spec_approved` detail is built by `autoApprovalDetail` (same module): `approved_by`, `mode_change`, the numeric `decisions` count as before, and `answers` with each default taken as accepted.
- **The runs.** The implement and review prompts add a "Decisions for the spec" section after the approver's notes (`decisionsSection`, fenced with the worker's `fenced`): each question, its answer, and whether the default was accepted, labelled untrusted. It is absent when the latest approval has no answers.

**`/revise` in a Slack thread is PR feedback** (decision changed 2026-11-09, issue #481; replaces "a `/revise` is PR feedback only when it comes from the PR's conversation"). A Slack thread has no PR conversation, so on a Slack-sourced item (`slack_thread`) that has a PR (`change_ref`) and is in a phase that takes PR feedback (`commandSpec("revise").pr_phases`: the merge wait and `failed_review`), a `/revise <feedback>` in the item's thread goes to `prFeedback` with the item's own `change_ref` as the PR: the same scan, cap, empty-feedback refusal, `max_loops` stop, `pr_revise_requested` state change keyed on the comment id (a redelivery starts no second run) and one implement run on the PR branch (`RUNNING`, `loop_count` + 1). At the spec gate and after a failed implement run, a thread `/revise` revises the spec as before; in any other phase it is refused with one reply in the thread that names the phase and gives no "reply on PR #N" hint. In Slack the command goes after a mention (`@factory /revise <feedback>`), because Slack takes a message that starts with `/` as its own slash command; it is a chat command, stored in the command log as the linked factory user and applied by the controller's command step with the item's thread as its source, keyed on the Slack event (a redelivery appends no second row). Unchanged: `/revise` on the PR, and a `/revise` on a GitHub issue in the merge wait, which keeps its refusal pointing to the PR. No setting, state or schema change; solo and enterprise behave the same.

**Auto mode answers the spec gate** (decision changed 2026-11-08, issue #444; replaces "a spec at the gate waits for `/approve`, `/reject` or `/revise`, or the standing rule at tier 1"). With the `mode` setting at `auto` (design 03-risk), a spec below tier 4 whose allowed paths touch no gate path and whose decisions all have a proposed default and none is owner-only is approved with no reply: `spec_approved`, actor `system:auto`, `approved_by: system:auto` and the mode change's audit seq in its detail, and the spec comment lists each decision with the default taken. Any other spec waits at the gate as before and its comment says why. The commands themselves are unchanged; `/revise` and `/reject` still apply to an item auto mode approved, as to any approved item. In manual mode (the default) nothing changes. `factory mode auto|manual` is a CLI command, not a comment command (design 08-settings).

**`/resolve +paths` and `/resolve` notes** (decision changed 2026-11-08; replaces "`/resolve` takes its whole text as the run's notes, unscanned, and never widens `allowed_paths`"). `/resolve` now reads its text as `/retry` does: the whole text is egress-scanned first (a finding refuses the `/resolve` with one reply and stores nothing), then `parseCommandPaths` splits a `+paths <path>...` first line off, and the notes are the lines below (empty when there are none), capped at 2000 characters. The `+paths` rules are those of `/retry +paths`: at most 10 paths, no `..`, no glob, no absolute path, a refused path changes nothing and gets one reply, and paths already covered by `allowed_paths` are not added again. The widening (the same `widen` helper, so a path under a higher floor raises the tier) lands in the `resolve_requested` transition that queues the resolve run, with `detail.added_paths` and the old and new `allowed_paths` in `changes`; the resolve run's scope gate reads the widened list. It applies where `/resolve` applies: an item waiting on a merge conflict, or one whose resolve run asked for a human (`agent_needs_human`); anywhere else it is refused and nothing changes. Why: a resolve run may change only the conflicting files and the allowed paths, so when the base needs one more file (a test that imports a file the PR moved) the run failed with `out_of_scope` every time, and the item stayed at `merge_conflict_pending`. Unchanged: `/resolve` without `+paths` (same run input, no change to `allowed_paths`), `/retry +paths` on a failed resolve run (still refused), the `factory resolve` CLI usage, automatic resolve notes, the resolve prompt and the scope gate. No schema change. Solo and enterprise behave the same.

**Commands at the review loop limit** (decision changed 2026-11-08; replaces "at `max_loops` no command changes the state"). An item blocked on a human with `max_loops` (command phase `max_loops`, label "review loop limit reached") now takes the three existing commands, from the issue and from the CLI, with or without a PR. `/retry [notes]` starts one implement run: the item goes to `RUNNING`, unblocked, with `loop_count` back at 0 and `restart_count` + 1, and the run key uses the reset count (`…:implement:l0:r<n>`); `+paths` widens `allowed_paths` exactly as after a failed implement run (at most 10, no `..`, no glob, covered paths not added again). `/revise <feedback>` takes the after-failure path (`reviseAfterFailure`): back to `NEW` with a triage run and the feedback stored, `loop_count` 0 (only at `max_loops`); the open PR and its branch stay. With no feedback it is refused with one reply and nothing changes. `/reject <reason>` closes the item as at the spec gate (`rejected`, the issue closed as not planned). A human chose to try again, so the loop count restarts (and the model bump that follows it may drop). The max-loops comment's footer lists the three commands and `/help`, so it no longer ends with "No command changes this item's state now." Unchanged: the limit itself, the review loop, `/retry` on the other phases (a failed triage, review or update run still refuses `+paths`) and commands on the PR conversation at `max_loops` (none). No schema change. Solo and enterprise behave the same.

**Implicit verdicts and the lenient `/verdict`** (decision changed 2026-11-08, issue #316; replaces "only `/verdict` writes verdicts, and every kind but `accept` needs a severity"). The factory records a verdict on its own from three PR events of a **factory** item (origin `factory`; adopted PRs, Slack items and local items get none here): a merge whose merger resolves to a user and with no `manual` run on the item (no person pushed) is one `accept`, severity `none`, for the merged head (`last_head_sha`), the merger as actor, stored just before the `pr_merged` transition; a person's push (the `manual` run of design 05-sources) is one `changes`, severity `minor`, for the pushed head, the pusher (or `system:pr-sync`) as actor, its reason naming the commit count from `Forge.commitsBetween` (`a person pushed 3 commits to the PR`) or saying the count is unknown; a revert of a merged item (CLOSED / `completed`) is one `reverted`, severity `major`, per reverting commit, as `system:links`, with no PR head. A merge whose merger does not resolve writes no verdict and logs why. **Implicit verdicts never change `stage`, `blocked_on` or `blocked_reason`:** like `/verdict`, each bumps the version and adds one `controller_state_changes` row, reason `implicit_verdict`, `changes` = {}. A `controller_verdicts` row now has `implicit` (0/1) and `pr_head` (SQLite migration 39, MySQL step 0039, which also widens `comment_id` to 128); an implicit verdict keeps its event key in `comment_id` (`implicit:<merged|pushed|reverted>:<item>:<sha>`), so a redelivered event or a second run of the merge handler stores nothing. **One verdict per PR head:** an implicit verdict for a head that already has one is a no-op, so a person's push then a merge ends with that head's `changes` and no `accept`; an explicit `/verdict` is stored for the item's current head and deletes that head's implicit verdict (its `controller_state_changes` row stays). The parser now takes `/verdict accept` alone (severity `none`), `accept <reason>` without a severity, and `yes` and `ok` as `accept`; an unknown word gets the usage line and stores nothing. `/verdict` also applies to a merged item (command phase `merged`); a closed item whose PR was not merged is refused with one reply. Solo default: no forge, so no PR events and no implicit verdicts. Enterprise: the GitHub forge, implicit verdicts from its PR events, on the shared store with both migrations applied.

**Standing approvals at the spec gate** (decision changed 2026-11-07, issue #299, phase 2 of #293). A tier 1 spec that waits at the spec gate is approved without a reply when the standing rule `spec-t1` is on and none of its allowed paths is protected (see `05-standing-approvals.md`). The state change is `standing_approved` with actor `standing:spec-t1` and the owner's user ID (`owner_id`, the rule's `set_by`) in its detail, and the spec comment says which rule approved it and how to turn it off. The rule acts only where `dials.spec_gate_min_tier` already sends a spec to the gate (that dial is unchanged); a spec the dial lets through, a split spec, a spec above tier 1 and a protected one go on as before. **`/standing [accept|decline <rule>]`** is a new command in the table: with no arguments it shows the rule's state, `accept` turns it on and `decline` turns it off (or declines its proposal). It needs the same permission check as `/approve` (`approve_spec`), records the user ID as `set_by`, and gets 👀 and one reply keyed on the comment; a rule already in the asked state is left alone with no reply, so a second accept or a redelivery posts nothing new. It is a factory command, about the rules and not the item, so `/help` and the `SET_UP.md` table list it and no footer does (like `/link`). It is parsed in the one comment parser (`src/core/commands.ts`), turned into a `standing_requested` event by `commentEvent` (`src/core/comment-event.ts`, so the command inbox and Slack get it) and by the GitHub issue source, and answered on a work item only. A `/revise` or `/reject` applied on an item a rule approved turns that rule off, with one reply that says so (marker `standing-off:<comment id>`).

**Commands from the command inbox** (decision changed 2026-11-07, issue #282). The controller reads every command that does not come in a forge comment from one store table, the command inbox (`inbound_commands`), in `seq` order through its own cursor `commands`, every tick and with no source configured. The cursor started where the `local` source's `intake:local` cursor stopped, copied once by a data step (since 2026-11-11, issue #467: the relay reads only `commands` now; design 05-sources), so a command it already read is not applied again. A CLI command (`factory approve|retry|revise|reject <id> [text]` on a local item) is rebuilt as `/<command> <text>` and read by the same comment parser as a GitHub comment (`src/core/command-inbox.ts`), then handled as that comment: the same `authorize` check through `AuthProvider` (identity provider `local`, subject the actor, so an account with no link is refused with the not-linked reply), the same command table, the same refusal wording. An app request is written to the inbox too, in the same transaction as its own row (key `app:<seq>`, `args.app_request`), and applied as before (below); SQLite migration 29 (MySQL step `0029-thread-outbox.sql`) copies the requests still pending. The `inbound_app_requests` table stays only for the request's status (`getAppCommandRequest`, the item API's replies); its pending-request read is removed. Removal plan: once the item API reads a request's status from the command inbox and the thread, the table and its store methods go in one change with its migration. A command whose handling throws (a store error) holds the cursor before it, so it and the ones after it are tried again next tick. Every reply is a thread entry, delivered by the outbox (design 05-sources, "Thread first"), so a failed post no longer keeps a request pending: the refusal is stored on the row at once and the outbox retries the post. No change to the authorize rule, the command table or the refusal wording.

**Widening allowed paths from a command** (decision changed 2026-11-07, issue #280). `/approve +paths <path>...` and `/retry +paths <path>...` add paths to the item's `allowed_paths` in the same store transition that queues the implement run; the scope gate, the floor check and the implement prompt all read the widened list, since the run loads the item fresh. `+paths` starts the first line of the command's text; the paths are the rest of that line (whitespace-separated, a path may be in backticks, a leading `./` is dropped) and the lines below are the note. At most 10 paths per command; a path that is empty, absolute, has `..` or has a glob is refused with one reply and nothing changes (the whole text is egress-scanned first, so a refusal never quotes a flagged path). Paths already covered by `allowed_paths` (the scope gate's rule, `isCovered`) are not added again; with none left, the command applies with the paths unchanged. Added paths under a floor raise the tier to the highest such floor, as triage does, and never lower it; on a floor block that combines with the block's tier. The state change (`spec_approved`, `floor_tier_approved` or `retry_requested`) has the user as actor, the old and new `allowed_paths` (and tier) in `changes`, and `detail.added_paths` (a JSON list). `/approve +paths` applies where `/approve` applies to a spec or a floor block (spec waiting, max revisions, floor block). It is refused on a split spec (that approval files sub-issues), on an implement run held by coordination cost (the run is already queued), and from app requests (`args.note` is a note, never parsed for paths). `/retry +paths` applies only when the failed run is an implement run; on a triage, review, update or resolve run it is refused with one reply and nothing changes. **`/retry` takes notes** on the same line or below: scanned and capped at 2000 characters like `/approve` notes, stored as `detail.note` on `retry_requested`, and shown in the implement and review prompts in the "Notes from the approver" section (after the latest approval's note, labelled "After `/retry`:"); a retried resolve run also gets it as its notes. Triage prompts do not show it. **The reply is given, never applied by an agent.** An implement run's `needs_human` may carry `paths` (at most 10); the comment then gives the exact `/retry +paths ...` reply for the ones not yet covered, and a `scope_violation` comment does the same for its files (when no single reply can, more than 10 or a name with a space or glob, it points to `/revise`). Agent output never changes `allowed_paths`; only the owner's command does.

**Gate commands.** On a spec waiting for approval (`READY` / `spec_pending`), a user with write permission replies one of:
- `/approve`: implementation starts, as before.
- `/reject <reason>`: the item closes (`close_reason: rejected`). It is recorded first, as `CLOSED` with `blocked_on: upstream` / `blocked_reason: source_close_pending` and the reason in `spec_feedback`; then the controller posts one comment quoting the reason (marker `rejected:<item id>`, so never twice), closes the GitHub issue as "not planned" (`SourceAdapter.closeIssue`), and clears the mark (`source_closed`). **An open PR is closed too** (decision changed 2026-11-09, issue #452; before: a reject closed only the issue and left its PR open): on an item with a PR and a forge, the mark moves to `pr_close_pending` instead, and outbound delivers one keyed `close_pr` action, one comment on the PR quoting the reason (marker `pr-closed:<item id>`), then the PR closed without a merge; the mark clears when outbound reports it done. A PR already merged or closed gets no comment and no close. A failed PR close keeps the mark and is retried (outbound's backoff, and each intake tick records the same keyed action again), and the marker keeps a retry from posting a second comment. A `/reject` at a budget checkpoint still leaves the PR as it is. A local item's close needs no source adapter: its comment is a thread entry and nothing waits on a sync plugin. If the factory stops in between, every intake tick finishes items still marked. With no reason, the item and the issue still close.
- `/revise <feedback>`: the item stays open and goes back to `NEW` (`spec_revision_requested`, actor: that user) with a new triage run keyed `<item>:triage:l<loop>:r<restart>:v<n>`, which differs from the intake key and from every earlier revision. The run's prompt has the original issue text (`issue_text`), the previous spec, and the feedback under a heading that labels it untrusted, in a fence it cannot close. The new spec is a new comment and waits for the same three commands. With no feedback text the command is refused with a reply and nothing changes. The first `max_loops` revisions each run triage; the next `/revise` sets `blocked_on: human` / `blocked_reason: max_revisions`, posts one comment, and starts no run. `/approve` and `/reject` still apply there, so a human always has a way out; a further `/revise` is refused.

**`/revise` after a failed implement run.** Two command phases split out of "blocked by a failed run": `too_large` (the `run_failed:implement:diff_too_large` block, label "blocked: the change was too large") and `failed_implement` (any other implement failure blocked on a human: `max_attempts` or `max_restart` at `RUNNING`, or `run_failed:implement:*`; label "blocked by a failed implement run"). `failed_run` ("blocked by a failed run") keeps failed triage and update runs; a failed review run is its own phase, `failed_review` ("blocked by a failed review run", since 2026-11-04), where `/retry` applies as before. At both new phases `/retry` applies as before, and `/revise <feedback>` sends the item back to `NEW` (`spec_revision_requested`, detail `previous_blocked_reason`), clears the block, adds one to `revision_count` and to `restart_count`, stores the feedback and clears `failure_comment_url`, and queues triage under the spec-gate revision key (`…:v<n>`, the restart count before the bump). Triage writes a new spec with the feedback, which waits at the spec gate; because `restart_count` moved, the next `/approve` queues an implement run under a new key (without the bump it would match the failed run's key and never start). An existing remote branch from the failed attempt is resumed, as `/retry` does. The revision counter and `max_loops` apply as at the spec gate, but at the limit nothing changes: the reply names the limit and offers `/retry` or `/reject <reason>`, and the item keeps its block. `/reject <reason>` also applies at both phases (same close as at the spec gate), so that offer always works. An empty `/revise` gets the same refusal as at the spec gate. `/revise` on the issue stays refused at a floor block, a budget checkpoint and a failed triage, review or update run; at the merge wait and `failed_review` the refusal points to the PR, where `/revise` applies (Feedback on a pull request, below). The size-check comment names `/revise <feedback>` next to `/retry`.

All three need write permission, and on an item in any other state they are refused with one reply. **Refusals name the state by its label.** Every refusal and every `/help` reply describes the item's state with the same label as the command table (`phaseLabel` in `src/core/commands.ts`, e.g. "implementing", "waiting for a human merge"), never `NEW`, `READY`, `RUNNING`, `REVIEW` or `CLOSED` and never a `blocked_on` / `blocked_reason` value; a test checks every state. A new item's PR is titled with the issue title in full, with no prefix (decision changed 2026-11-07, issue #229); items with no stored title (from before titles were kept) keep the old rule. Schema: migration 6 adds `issue_text`, `revision_count` and `spec_feedback` (SQLite and MySQL); old rows have `issue_text` null, and their revision prompt points at the source link instead.

**Feedback on a pull request.** On a PR waiting for a human merge, or whose review run failed (`failed_review`), a writer's `/revise <feedback>` comment on the PR, or a writer's GitHub review with "Request changes", sends that feedback to one implement run on the PR branch, followed by a fresh review. This covers factory and adopted PRs. The GitHub source reads `/revise` on a PR's conversation (with the PR's head, through `pullHead`) and, on the open PRs it already reports, `CHANGES_REQUESTED` reviews by a person, with their line comments (path, line, text); approvals, plain comments, dismissed and pending reviews start nothing, and reviews from before the source first read them are skipped. The controller (`prFeedback`) refuses outside the two states (naming the state's label), refuses empty feedback and feedback the egress scanner flags, and caps it at 8000 characters. Each round adds one to `loop_count`: at `max_loops` the item blocks with `max_loops` and one comment, and no run starts. Otherwise the item goes to `RUNNING` and one implement run is keyed `runKey(next)` with the feedback as its input; the state change (`pr_revise_requested` or `pr_changes_requested`) records the comment or review id, so a redelivered event changes nothing. The implement prompt gets a "Feedback on the pull request" section, labelled untrusted and fenced like the approver's note; an automatic retry reads it from that state change. A reviewer without write permission is ignored; a writer's review in a state that cannot take it gets one reply on the PR. Footers on a PR start with "On the pull request, you can reply with:" when `/revise` applies there.

**Approval notes, `/help`, unknown commands and footers.** One table in `src/core/commands.ts` lists every command (name, usage, one-line description, the item states where it applies, whether it needs a PR) and holds the parser. A command is the comment's first line: `/` plus letters (any case), then whitespace, the end of the line or one of `.,:;!?`; anything else (`/`, `/ x`, `/src/x.ts`, `/approve2`) is not a command, and `/rejectfoo` is an unknown command, not `/reject`. The text after the command word, same line and following lines joined by a newline and trimmed, is the command's text.
- `/approve [notes]` on a spec or a floor block: the note is untrusted. After the permission check (a non-writer's note is never stored), the whole note goes through the `EgressScanner`; a finding refuses the approval with one reply naming the rule, stores nothing and leaves the stage. Otherwise the note, capped at 2000 characters, goes on the approval's `controller_state_changes` row as `detail.note` (`spec_approved` or `floor_tier_approved`; no schema change). The implement and review prompts get a "Notes from the approver" section, labelled untrusted and fenced, holding the note of the item's latest approval that has one; with none the section is absent. Prompt files are unchanged; the section is added in code.
- An unknown command on a work item gets 👀 and one reply (`Unknown command "/xyz".`, then the commands for the item's current state, then `/help`), keyed on the comment id. `/help` gets one reply listing every command and marking the ones that apply now; it names the current state by its label, not the phase id. On an issue that is not a work item, both get no reply and no 👀. Neither needs write permission: they change nothing.
- Every comment that waits for a human (spec, max revisions, floor block, failed run, dead letter, diff too large, failed update, max loops, merge waiting) ends with a footer built from the same table, for the state the item will be in after the transition (these comments are posted before it). Where no listed command changes the state (merge waiting), a last line says so. A test runs every command in every state through the controller and checks that the footer lists exactly the accepted ones; another fails when the command table in `SET_UP.md` differs from the code. A known command in the wrong state keeps its existing refusal reply.

**App requests** (decision changed 2026-11-11, issue #453; replaces "only `approve`, `merge`, `reject`, `revise` and `verdict` are applied from an app request, and `approve`, `reject` and `revise` have their own copy of the comment's check and transition"). A request stored in `inbound_app_requests` (request key, the factory user's id, command, JSON args) is a new entry point to the same command path as a comment, not a new command path. Each controller tick, outside the poll interval, reads them from the command inbox in order (see "Commands from the command inbox"; until 2026-11-07, up to 20 pending rows of the request table). Seven commands are applied, each with `args.work_item_id` and an optional `args.note`, and each puts the request's seq on its state change as `detail.app_request` (a verdict: in its comment id), so a request applied but not marked (a crash, another replica) is found and marked applied, with no second change and no refusal:
- **The gate commands `approve`, `reject`, `revise`, `retry` and `resolve`** go to the comment's own handler (`CommandsUnit.gateCommand`), the one a `/approve`, `/reject`, `/revise`, `/retry` or `/resolve` comment goes to, so there is one copy of the check and the transition. The handler takes who sent the command: a comment's identity (resolved by its origin's auth plugin), or the request's factory user with the request's edge passport (`passport_id` and the time the request was recorded), checked by the local auth plugin. The check is `approve_spec` on the item for that user; without it the request is refused and nothing is written. Then the same note scan, the same transition with the user as actor and `detail.app_request` set to the seq, the same standing-rule follow-up (a `revise` or `reject` on an item a standing rule approved turns the rule off, with the same reply, keyed `standing-off:app-<seq>`) and a reject's same close (its issue and its open PR). The handler returns its refusal; the app path posts it under its own marker, the comment path under the comment's (and only the comment path adds 👀). From the page: the note is the note (the approve's or retry's note, the resolve's notes, the reject's reason, the revise's feedback), never parsed for `+paths`; a reject's reason and a revise's feedback also pass the egress scan first, since the page's text is new text the factory would publish (a finding refuses it and stores nothing). A revise is the issue's `/revise`, never PR feedback, and a resolve is the issue's `/resolve`.
- `verdict` gets the `/verdict` check (`record_verdict`), parser and store: one `controller_verdicts` row with comment id `app-<seq>`, target `issue`, and one `human_verdict` state change; the stage and block do not change. A malformed note gets the usage line and stores nothing.
- `merge`: the Merge button (design 09-dashboard-app).

Any other command (`budget` among them: a follow-up) is refused (`only \`approve\`, \`merge\`, \`reject\`, \`resolve\`, \`retry\`, \`revise\` and \`verdict\` are applied from an app request`, then `reply \`/<command>\` on the issue instead` for a known command). A refusal reads exactly as the comment path's (`` `/<command>` was not applied: <reason>. ``), is written once to the item's thread with the marker `factory:refused:app-<seq>` (the outbox posts it), and is then stored on the row; a request naming no known item stores its refusal and posts nothing. Each request is marked once by a conditional update (`handled_at`, `refusal`; migration 23 on SQLite, step `0023-app-command-handling.sql` on MySQL). Requests come from the page's POST (design 09-dashboard-app). No schema change; solo and enterprise behave the same.

**Verdict command:** a user with write permission (auth action `record_verdict`, separate from `approve_spec`) records a structured verdict with `/verdict accept|changes|reject <severity> <reason>`, on the work item's issue or on its PR. Severity is one of `none`, `minor`, `major`, `critical`. The reason is the text after the severity, following lines included; `accept` may omit the severity (then `none`) and the reason, `changes` and `reject` may not; `yes` and `ok` mean `accept` (since 2026-11-08, above). **A verdict does not change `stage`, `blocked_on` or `blocked_reason`:** it bumps the version and stores a `controller_state_changes` row (reason `human_verdict`, actor = the user's id, `changes` = {}) plus a linked `controller_verdicts` row (verdict, severity, reason, comment id, target `issue`/`pr`, `implicit` 0, `pr_head` = the item's current head). `verdicts.comment_id` is unique, so a redelivered comment stores nothing and gets no second reply. A bad format, an unknown severity, a missing reason, no write permission, a `CLOSED` item whose PR was not merged, or an item with no PR yet (a local item excepted since 2026-11-09, issue #452: an open or merged local item with no PR takes a verdict with no `pr_head`; a closed local item that was not merged is refused as `the work item is closed`; see "App requests") is refused with one reply on the issue, keyed on the comment id, and nothing is stored. A PR comment maps to its item by the PR's head branch. Verdicts are the input for the weighted human-feedback rate that gates auto-merge (§6); computing it is not built yet.

## History

- **Command suggestions for plain-language replies** (decision changed 2026-11-11, issue #583). Before: `suggestCommand` (`src/core/suggest.ts`) saw only the comment and the current item's state and returned at most one command for that item at confidence 0.85 or more; comments over 300 characters were skipped; args that failed the egress scan gave the command list instead; and Slack drew Confirm and Cancel buttons under the suggestion, parsed from the reply by `suggestedCommand`. A message naming several items, asking to see one, or unclear got no useful answer.
- **App requests** (decision changed 2026-11-11, issue #453). Before: only `approve`, `merge`, `reject`, `revise` and `verdict` were applied from an app request (a dashboard `retry` or `resolve` got the refusal `only \`approve\`, \`merge\`, \`reject\`, \`revise\` and \`verdict\` are applied from an app request; reply \`/retry\` on the issue instead`), and the app path had its own copy of the `approve_spec` check and the approve, reject and revise transitions beside the comment's handler, which returned nothing and posted its own refusal.
- **Each surface reads the command table its own way** (decision changed 2026-11-11, issue #528). Before: the dashboard listed every command that applied in the item's state whatever the viewer's grants; the CLI had its own list and no help command; `factory approve` stored a command row in any state and only the controller refused it later; in Slack a bare `approve` after the mention was a plain comment, and help outside an item's thread named neither the request nor `/link`.
- **The spec comment says how to answer its decisions** (decision changed 2026-11-11, issue #527). Before: the comment listed its decisions as a numbered list and ended with the command footer, but did not say that `/approve` takes one `N: <answer>` line per decision or what an unanswered decision takes, although the parser already read those lines from any source.
- **App requests** (decision changed 2026-11-11, issue #527). Before: only `approve`, `merge`, `reject` and `verdict` were applied from an app request; a dashboard `revise` was recorded and then refused (`only \`approve\`, \`merge\`, \`reject\` and \`verdict\` are applied from an app request; reply \`/revise\` on the issue instead`).
- **`/revise` in a Slack thread is PR feedback** (decision changed 2026-11-09, issue #481). Before: only a `/revise` carrying a PR (from GitHub's PR-conversation poll) was PR feedback; a Slack thread `/revise` on an item with a PR fell through to the spec-revision path and was refused with "reply `/revise <feedback>` on PR #N", a PR conversation the Slack user may not use.
- **Auto mode answers the spec gate** (decision changed 2026-11-08, issue #444). Before: only `/approve` or the standing rule `spec-t1` approved a spec waiting at the gate.
- **`/resolve +paths` and `/resolve` notes** (decision changed 2026-11-08). Before: `/resolve` passed its raw text as the resolve run's notes, with no egress scan and no length cap, and `+paths` was not split off, so a resolve that needed a file outside the conflicts and the allowed paths could only fail `out_of_scope` (PR #416).
- **Commands at the review loop limit** (decision changed 2026-11-08). Before: `max_loops` had no command in the table; its footer ended with "No command changes this item's state now.", `/retry` was refused as "no failed run to retry", and `/revise` and `/reject` were refused because no spec was waiting, so the item could only be closed or changed by hand.
- **Implicit verdicts and the lenient `/verdict`** (decision changed 2026-11-08, issue #316). Before: only `/verdict` wrote verdicts; `/verdict accept` alone and `/verdict yes` were refused (a severity was required for every kind), so every owner `/verdict` on record was refused; merges, pushes and reverts wrote no verdict; a `/verdict` on a merged item was refused as closed.
- **Standing approvals at the spec gate** (decision changed 2026-11-07, issue #299). Before: every spec at or above `dials.spec_gate_min_tier` waited in `spec_pending` for a human `/approve`, `/reject` or `/revise`; no command accepted or declined a standing rule, and nothing acted on one.
- **Commands from the command inbox** (decision changed 2026-11-07, issue #282). Before: CLI commands reached the controller only through the `local` source's poll, so only when `local` was listed in `plugins.source`; app requests were read straight from their own table each tick; and a refusal reply that failed to post kept an app request pending.
- **Widening allowed paths from a command** (decision changed 2026-11-07, issue #280). Before: allowed paths were set once by triage; `/approve` text was only a note and `/retry` took no text, so a run that needed one more file was refused by the scope gate every time, and the only fix was a `/revise` that ran triage again. No comment told the owner which reply would help.
- **PR titles** (decision changed 2026-11-07, issue #229). Before: `factory: <issue title>`; the prefix pushed titles past 50 characters, and the bot author and the `factory/` branch already mark the PR.
- **Gate commands** (decision changed 2026-11-01). Before: the spec gate took only `/approve` and `/reject <reason>`, a reject dropped its reason and left the issue open, and PR titles were the spec's first line cut at 80 characters.
- **`/revise` after a failed implement run** (decision changed 2026-11-01, issue #91). Before: a failed implement run or a `diff_too_large` block took only `/retry`, which runs the same spec again, so an owner whose change was too big could not change the spec.
- **Refusals name the state by its label** (decision changed 2026-11-01, issue #91). Before: refusals printed the raw stage, and the `/resolve` refusal also printed `blocked_on` and `blocked_reason`, which the owner cannot act on.
- **Approval notes, `/help`, unknown commands and footers** (decision changed 2026-11-01). Before: a note after `/approve` was dropped, `/approve some note` was not even an approval, a mistyped command such as `/aprove` got no reply, and no comment listed the commands that work on an item.
- **Command suggestions for plain-language replies** (decision changed 2026-11-01). Before: the GitHub source dropped every comment that was not a command before the controller saw it, so "ship it" on a spec got no answer and the person could not tell whether the factory understood.
- **Verdict command** (new decision, 2026-11-01). Before: the gate commands were only `/approve`, `/reject` and `/retry`, read only on the issue, and human feedback on a PR was free-form text.
- **App requests** (new decision, 2026-11-07, issue #245). Before: commands came only from comments on the issue or the PR; the `inbound_app_requests` table (migration 22) was read by nothing.
- **App requests** (decision changed 2026-11-09, issue #452). Before: only `approve` and `merge` were applied from an app request (a dashboard `reject` or `verdict` got the refusal `only \`approve\` and \`merge\` are applied from an app request`); a `/verdict` was refused on every item with no PR (`the work item has no PR yet`), local items included; and `/reject` closed only the source issue, leaving an open PR open.
- **Feedback on a pull request** (decision changed 2026-11-04, issue #178). Before: once a PR existed, `/revise` worked only on the issue at the spec gate or after a failed implement run; `/revise` on the PR found no item, and the GitHub source never read PR reviews, so "Request changes" was lost. `failed_run` also covered failed review runs.
- **Answers to the spec's decisions** (decision changed 2026-11-10, issue #526). Before: an approval note reached the implement and review runs as one plain text, so an agent could not tell which answer belonged to which decision, and auto mode's `spec_approved` stored only `decisions`, a count.
