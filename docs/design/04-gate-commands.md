# 4. Agents: gate commands

**A mistyped CLI command name gets "did you mean" and no model call** (decision changed 2026-11-16; replaces "any first word no CLI command claims runs the sentence form"). The decision that changed: **`factory <word> ...` where `<word>` is no command but has at least 4 letters and is within 2 edits of a command name in the loaded command map prints `unknown command <word>, did you mean <name>?` and exits 1; it never reaches the sentence form, so it makes no model call and opens no store.** Before, `factory stauts wi_1` was two words, so the sentence form sent it to the model and printed a confusing answer.
- **Where.** `resolveCommand` in src/cli/index.ts, before its fallback to the sentence form (`mistypedName`, `TYPO_MIN_LENGTH` 4, `TYPO_MAX_EDITS` 2). Only real command names match (every name of every command, aliases included); there is no top-level `status` alias of `workers status`.
- **The distance.** Optimal string alignment (`editDistance`): an insertion, a deletion, a substitution, or a swap of two neighbouring letters is one edit each, so a swapped pair is one typo. On a tie the name closest in length to the word wins (`stauts` is `status`, not `stats`).
- **Unchanged.** A word with fewer than 4 letters, or further than 2 edits from every name, still runs the sentence form as before, and a flag still prints the usage. How the sentence form reads a sentence of two or more words is unchanged.

**A mistyped `+paths` is refused with the corrected command, and an agent's own reply line is withheld** (decision changed 2026-11-16; replaces "without the `+paths` keyword the whole text is the note" and "the agent's reason and question are quoted as written"). The decision that changed: **on `/retry`, `/approve` and `/resolve`, a first line with no `+paths` keyword but a `+` word that has a `/` or `.` (`/retry +tests/a.json +tests/b.json`) is refused with one reply and nothing changes**, where before the whole text was stored as the note, no path was added, and the run failed the same way again (three items lost a run this way on 2026-11-16).
- **What counts as a path.** A first-line word that starts with `+` and has a `/` or `.` after it; `+1` or `+ok` stays a note, as do `+` words on the lines below. The `+paths` form, its limits (at most 10, no `..`, no glob, no absolute path) and its other refusals are unchanged.
- **The refusal.** `parseCommandPaths` (src/core/commands.ts) builds it with `retryPathsReply` from the words without their `+`, under the command name typed: "a path on the first line needs `+paths` before it, so nothing changed; did you mean `/retry +paths tests/a.json tests/b.json`?". When `retryPathsReply` returns null (a glob, more than 10), it gives the usage `` `/retry +paths <path>...` `` and no corrected line. Like the other `+paths` refusals it changes nothing and gets one reply. App requests are not parsed for paths, so they are unchanged.
- **The agent's reply line.** A needs_human comment quotes the agent's reason and question without any line that holds `/retry +`, `/approve +` or `/resolve +` (`withholdReplyLines`), so a wrong form the agent wrote never reaches the owner; the reply to copy is only the controller's own `retryPathsReply` line. A text that was nothing but such lines shows "(withheld: a reply command the agent wrote)".

**`/revise` while implementing is queued and applied when the run ends** (decision changed 2026-11-15; replaces "`/revise` during an implement run is refused with `specNotWaiting`"). The decision that changed: **`/revise <feedback>` on an item in the `implementing` phase (`RUNNING`, `blocked_on: none`), from a comment, a Slack thread, `factory revise` or the dashboard, is stored, not refused, and applied as one implement revise run right after the current run ends, before review.**
- **Why queued, not live.** No agent runner takes a message while its session runs (`AgentRunner` has only `run`, `hasSession` and `removeSession`), so every runner takes the queued path. The reply names it: `` `/revise` queued: applies when this run ends. `` (`REVISE_QUEUED_PATH` in `src/controller/units/commands/queued-revise.ts`, which holds the whole queued path), one thread entry keyed `revise-queued:<comment id>`. The live path ("sent to the running implementer") is a follow-up for when a runner can take a message mid-run.
- **Stored.** `queueRevise`: one `revise_queued` state change with no field change, the user as actor, `detail.comment_id` and `detail.feedback` (trimmed, capped at 8000 characters). The same comment again stores nothing. Empty feedback gets the existing feedback-required refusal, and feedback the egress scan flags the existing leak-scanner refusal (`feedbackScan`, shared with `prFeedback`); neither stores anything. No schema change: the state changes are the queue.
- **Applied.** When an implement run (or a session finish) would queue its review (the direct implement result, the PR-pending path through `prDelivered` or `prPending`), `applyQueued` reads the pending feedback (`pendingRevises`: each `revise_queued` row whose comment ID no `revise_applied` or `max_loops` row names) and, in the same conditional transition that acknowledges the run, starts one implement run instead of the review: `RUNNING`, `loop_count` + 1, reason `revise_applied`, `detail.comment_ids` (JSON, oldest first) and `detail.feedback`, run key `runKey(next)` plus `:revise-<first comment id>`, all pending feedback joined in order as its notes. The worker reads `revise_applied` as a loop start (`LOOP_STARTS`), so the implementer's "Feedback on the change" section has the text, also on an automatic retry. The review follows that run as after any loop.
- **Two workers.** The apply is the run's acknowledgement transition, conditional on the item's version and on the run not yet acknowledged; a second worker on the same run end re-reads, finds the `revise_applied` row (no feedback pending) and its transition is refused, so the feedback is applied once.
- **A run that fails or blocks** keeps the feedback pending (decision 1 at approval): nothing is applied or dropped, and the next successful implement run end applies it.
- **The loop limit.** When `loop_count + 1` reaches `max_loops`, the item blocks with `max_loops` (no run starts, its `comment_ids` settle the feedback) and one comment says the feedback queued while implementing would start loop N, as `prFeedback` does.
- **Where it shows.** The command table lists `implementing` among `/revise`'s phases, with its own `implementing_description` (shown there instead of "Get a new spec written"), so the footer, `/help`, the item API's commands and the SET_UP.md table offer it there; the item page lists pending feedback until it is applied (design 09-dashboard-app). Unchanged: `/revise` in review, at the merge wait before review, on the PR while implementing, and in every other phase.

**`/reject` closes an item at any open phase** (decision changed 2026-11-13; replaces "a reject applies only while the spec waits for approval"). The decision that changed: **`/reject <reason>` (and `factory reject <id> <reason>`, a dashboard Reject, a Slack `reject` in the item's thread) closes an open item at any command phase without a merge**: triaging, implementing, held by coordination cost, held for the previous phase of a split (`phase_hold`), in review, at the merge wait and every block. Before, the controller refused it outside the spec gate and the failure blocks with "the spec is not waiting for approval (the item is implementing)", and the refusal reached only its log for a CLI command, while the CLI had already printed "stored `/reject` ... the controller applies it on its next poll". On 2026-11-12 two rejects (wi_4bb6, wi_b0a9) were dropped that way, and wi_4bb6 then shipped a PR. They are not reopened or closed by this change.
- **The close.** One transition (`CommandsUnit.reject`): `CLOSED`, `close_reason: rejected`, the reason in `spec_feedback`, `blocked_on: upstream` / `source_close_pending`, and, as a source close does, `cancel_queued_runs` and `cancel_running_runs`, so no run of the item is left queued and a running one gets `lease_lost` on its next heartbeat, completion or tool call and pushes nothing. The rest is the existing reject close (`finishReject`): one comment quoting the reason, the issue closed as not planned, and an open PR closed with one comment (decision 2: at the merge wait too, as at the spec gate). The floor block, a Rule of Two hold and a budget checkpoint keep their own reject transitions.
- **The exception.** An item whose change is merged (`merge_sha` set) or in the merge queue (a live entry: queued, checking, passed, merging; the closes unit's `rejectRefusal`) is refused, and the reply says it cannot be rejected now and why: a merged change is undone by a new change that reverts it, and the queue lands a change once its merged result passes the checks, or removes it, after which `/reject` applies again. Nothing changes.
- **The sender sees every refusal.** The controller answers a refused command in the item's thread, as before: a reply on the GitHub issue, in the Slack thread, and the dashboard's request row. For the CLI (decision 1), `factory task show <id>` ends with a "Last refused command" section: the item's latest refusal with its reason, read from the thread entry the controller already stores (marker `factory:refused:<key>`), so no table or column is added. `factory reject` (and every item command) prints where that refusal shows.
- **Help and the table.** `/reject` applies at every open phase (`OPEN_PHASES` in `src/core/commands.ts`), so every open item's footer lists it, `/help` marks it **(now)** there, and the SET_UP.md table says "any open item". The description names the exception.

**One-tap verdicts: Good, Bad and Feedback on result messages** (decision changed 2026-11-12; replaces "a person's verdict on a result is typed (`/verdict`), a 👍 or 👎, or the dashboard's Accept, Changes and Reject, and every verdict is a new row"). The decision that changed: **each spec, finished-run and merge message the factory posts to a Slack-sourced item ends with Good, Bad and Feedback buttons; a tap stores one verdict per message, and a second tap changes that verdict instead of adding one.**

- **Which messages** (decision 2): a result message is one posted under a spec marker (`spec:<run>`), the ready-to-merge message of a finished review run (`merge:<run>`) or a merge (`pr-merged:`, `local-merged:`) (`resultMarker` in src/impl/source/slack-format.ts). Status, refusal, reply, chat and failure messages get no verdict buttons, and messages posted before this change are not backfilled. GitHub keeps reactions and `/verdict`.
- **What a tap stores** (decisions 1 and 4; `buttonVerdict` in src/core/verdict.ts): Good is `accept`/`none`; Bad is `changes`/`minor` with no reason (the button asks for none); Feedback opens a Slack modal (`views.open`), and its submit stores `changes`/`none` with the text as the reason. The actor is the linked factory user ID, never a display name; target `issue`; `pr_head` the item's head when it has a PR.
- **One verdict per message.** The key is `button:<channel>:<message ts>`, with `:<run ID>` when the message reports a run (`buttonVerdictKey`), so the verdict names its run. It goes through `recordVerdict` with `replace` (src/impl/store/sql/verdicts.ts): a different verdict under the key updates that one `controller_verdicts` row (kind, severity, reason, `at`, and a new `human_verdict` state change for the actor); the same verdict again, a redelivered press included, is a duplicate that changes nothing. No schema change, no migration.
- **Who.** The Slack source runs the `record_verdict` check through the account's linked factory user (the local auth plugin's check, which judges Slack by default, issue #498). An unlinked account, or one whose user lacks the permission, stores nothing, opens no modal and gets no reply. An item closed without a merge takes none. Unlike a typed `/verdict` from Slack, a tap needs no PR: the verdict is about that message.
- **Feedback safety.** The text is egress-scanned (G5) before anything is stored; a finding stores nothing and posts one notice in the thread (keyed on the modal's view ID), without the text. The submit is acked, which closes the modal, only after the store write.
- **The message shows it.** After a verdict is stored the message is edited (`chat.update`) to end with `Verdict: <Good|Bad|Feedback> by <user ID> at <time>.` and to offer only the other buttons; the edit is recorded under `slack:verdict:<ts>:<state change ID>`, so the same verdict shown again makes no Slack call. A later state change's edit (05-sources, "Slack buttons follow the item's state") keeps the verdict line and buttons; its Done line skips verdict state changes.
- **Pushback.** Bad and Feedback are `changes` rows in `controller_verdicts`, so `listVerdictsSince`, the verdict signal's read, returns them; no new counter. A tap does not call the tacit capture that a typed `/verdict changes` does (that call is the controller's; a tap is stored by the Slack source).
- **Reactions stay** (decision 3): 👍 and 👎 work as before beside the buttons. **Style** (decision 5): the buttons have no colour style until the `design-system/` folder exists in this repository.
- **The dashboard** (09-dashboard-app): the item page offers Good, Bad and Feedback through the existing verdict app request (one new row per click: the item has no message there), and its thread shows every verdict. A local item takes them with no Slack call.
- **Solo and enterprise** run the same path on their store; the conditional verdict write and the key keep one row however many replicas take the press.

**A mention creates an item only on a press** (decision changed 2026-11-12; replaces "a top-level Slack mention the interpreter reads as `request`, or does not read, is taken in as a work item at once"). The decision that changed: **a top-level Slack mention never becomes a work item by itself. The factory answers it in its own thread, and when the message may be work it offers a Make this a task button; only a press creates the item.** The local CLI sentence form and GitHub intake are unchanged.

- **The replies** (the intake unit, `answered`; one reply per message, keyed `factory:chat-answer:<source id>`, so a redelivery posts nothing more):
  - an empty mention: `I couldn't read that.`, with no button;
  - a message the egress scan flags: `I can't use that message: it looks like it holds a secret. Remove it and mention me again.`, with no button. The intake unit scans the message before any model call, so the button's marker, which carries the message, never holds a flagged text. (`readMessage` scans it once more; that second scan is accepted);
  - no model configured, a sender who is not the owner (no model call in either case), a message over 1000 characters, or a `none` answer (a failed call, a stop reason but `end`, malformed output, a `request` with empty text): `I couldn't read that. Make it a task?`, then the button;
  - `request`: the model's own 1 to 3 plain sentences on what it understood and what a task would do (e.g. "I can make this a task: send a Slack message when a task finishes or needs you."), then the button. The interpreter's `request` kind now carries `text` and the `message`, and its prompt asks for the text;
  - `unsure`, `chat`, `commands`, `show` and `question`: as before.
  A model answer the egress scan flags posts nothing and creates nothing.
- **The press.** The button is the existing Make this a task (`factory:make-task:<base64url of the message>`). Its press is an `item_requested` from the presser with `offered` set (only that press sets it; `src/interfaces/source-adapter.ts`), keyed on the message's source id. Intake checks the presser's `submit_work`, creates the item titled from the message, and, only when it created it, posts one line `Task created: <title>` before the status and spec follow as before. A second press finds the item and posts nothing.
- **Why.** A mention that only asked something (on 2026-11-12 "report when tasks finish or when you need my decision") became an item and a full spec in the owner's thread. A press costs one click and makes the intent explicit; no request is dropped, since every unread case gets the button.
- **Not changed.** Replies inside an item's thread, the `submit_work` refusal reply, the button's layout, items created from earlier mentions (no backfill), the store (no schema change), one model call per message.

**A 👍 or 👎 on a factory message is a verdict** (decision changed 2026-11-11, issue #524; replaces "reactions are ignored: only a typed `/verdict`, `factory verdict` and the app's verdict request record a person's verdict"). The decision that changed: **a reaction by a person on the factory's PR comment (GitHub) or on its message in a work item's Slack thread is read and maps onto the `/verdict` path.**

- **The mapping** (`src/core/reaction-verdict.ts`, pure): 👍 (`+1`, Slack `thumbsup`, any skin tone) is `accept` with severity `none`; 👎 (`-1`, `thumbsdown`) asks for the severity first; any other emoji, and any bot's reaction (the factory's own 👀 included), means nothing. Reactions are read up to 7 days after the message (`REACTION_WINDOW_MS`); older ones are not, and there is no backfill.
- **The event.** Each new reaction is one `verdict_submitted` event with `reaction` set, `verdict` the mapped verdict (`reactionVerdict`; null for 👎), built by the source with `reactionEvent`, and comment id `reaction:<reaction id>` (a GitHub reaction's id; on Slack `slack:<channel>:<message ts>:<user>:<+1|-1>`). It keeps the `/verdict` kind, so the verdicts unit takes it (the controller's list of event kinds needs no new entry), but a refusal gets no reply and no 👀 is added. Its target is the PR by change ref (GitHub) or the item by its thread (Slack).
- **👍** is stored through `recordVerdict`, as a typed `/verdict accept` would be: one `controller_verdicts` row keyed on the reaction, target `pr` (GitHub) or `issue` (Slack), and `pr_head` the item's current head (`last_head_sha`) when it has a PR. A redelivered reaction finds the key and stores nothing. **Open decision 3** (an item with no PR): a Slack or GitHub item with no PR takes no reaction verdict, as with `/verdict`; a local item has no factory message to react to. A refusal (closed unmerged, no PR) is logged, not answered.
- **👎** stores nothing by itself. It gets one follow-up, keyed on the reaction (`severity-reaction:<id>`), a thread entry delivered by outbound: on the PR for a GitHub reaction, in the thread for a Slack one. Its text is fixed (`SEVERITY_FOLLOW_UP` in the verdicts unit) and quotes nothing the person wrote: reply `/verdict changes <severity> <reason>`. That reply is an ordinary `/verdict`, stored or refused as before (an unknown severity gets the usage refusal). A 👎 with no reply stores nothing; a 👎 on an item that takes no verdict gets no follow-up.
- **Who.** The reacting account must resolve to a factory user with `record_verdict`, the `/verdict` check. An unlinked account, or a linked one without the permission, stores nothing and gets no reply: a reaction is too light to answer.
- **Not changed.** Removing a reaction, or changing it, does not remove or change its verdict. Reactions on issue comments and on the factory's Slack status message are not read. `/verdict` syntax and refusals are unchanged.
- **Solo and enterprise.** Solo default: no GitHub or Slack, so no reactions; nothing changes. Enterprise setting: the same mapping on the shared store; the grants decide `record_verdict`.

**Commands from the command inbox** (decision changed 2026-11-07, issue #282). The controller reads every command that does not come in a forge comment from one store table, the command inbox (`inbound_commands`), in `seq` order through its own cursor `commands`, every tick and with no source configured. The cursor started where the `local` source's `intake:local` cursor stopped, copied once by a data step (since 2026-11-11, issue #467: the relay reads only `commands` now; design 05-sources), so a command it already read is not applied again. A CLI command (`factory approve|retry|revise|reject <id> [text]` on a local item) is rebuilt as `/<command> <text>` and read by the same comment parser as a GitHub comment (`src/core/command-inbox.ts`), then handled as that comment: the same `authorize` check through `AuthProvider` (identity provider `local`, subject the actor, so an account with no link is refused with the not-linked reply), the same command table, the same refusal wording. An app request is written to the inbox too, in the same transaction as its own row (key `app:<seq>`, `args.app_request`), and applied as before (below); SQLite migration 29 copies the requests still pending. The `inbound_app_requests` table stays only for the request's status (`getAppCommandRequest`, the item API's replies); its pending-request read is removed. Removal plan: once the item API reads a request's status from the command inbox and the thread, the table and its store methods go in one change with its migration. A command whose handling throws (a store error) holds the cursor before it, so it and the ones after it are tried again next tick. Every reply is a thread entry, delivered by the outbox (design 05-sources, "Thread first"), so a failed post no longer keeps a request pending: the refusal is stored on the row at once and the outbox retries the post. No change to the authorize rule, the command table or the refusal wording.

**App requests** (decision changed 2026-11-11, issue #453; replaces "only `approve`, `merge`, `reject`, `revise` and `verdict` are applied from an app request, and `approve`, `reject` and `revise` have their own copy of the comment's check and transition"). A request stored in `inbound_app_requests` (request key, the factory user's id, command, JSON args) is a new entry point to the same command path as a comment, not a new command path. Each controller tick, outside the poll interval, reads them from the command inbox in order (see "Commands from the command inbox"; until 2026-11-07, up to 20 pending rows of the request table). Seven commands are applied, each with `args.work_item_id` and an optional `args.note`, and each puts the request's seq on its state change as `detail.app_request` (a verdict: in its comment id), so a request applied but not marked (a crash, another replica) is found and marked applied, with no second change and no refusal:
- **The gate commands `approve`, `reject`, `revise`, `retry` and `resolve`** go to the comment's own handler (`CommandsUnit.gateCommand`), the one a `/approve`, `/reject`, `/revise`, `/retry` or `/resolve` comment goes to, so there is one copy of the check and the transition. The handler takes who sent the command: a comment's identity (resolved by its origin's auth plugin), or the request's factory user with the request's edge passport (`passport_id` and the time the request was recorded), checked by the local auth plugin. The check is `approve_spec` on the item for that user; without it the request is refused and nothing is written. Then the same note scan, the same transition with the user as actor and `detail.app_request` set to the seq, the same standing-rule follow-up (a `revise` or `reject` on an item a standing rule approved turns the rule off, with the same reply, keyed `standing-off:app-<seq>`) and a reject's same close (its issue and its open PR). The handler returns its refusal; the app path posts it under its own marker, the comment path under the comment's (and only the comment path adds 👀). From the page: the note is the note (the approve's or retry's note, the resolve's notes, the reject's reason, the revise's feedback), never parsed for `+paths`; a reject's reason and a revise's feedback also pass the egress scan first, since the page's text is new text the factory would publish (a finding refuses it and stores nothing). A revise is the issue's `/revise`, never PR feedback, and a resolve is the issue's `/resolve`.
- `verdict` gets the `/verdict` check (`record_verdict`), parser and store: one `controller_verdicts` row with comment id `app-<seq>`, target `issue`, and one `human_verdict` state change; the stage and block do not change. A malformed note gets the usage line and stores nothing.
- `merge`: the Merge button (design 09-dashboard-app).

Any other command (`budget` among them: a follow-up) is refused (`only \`approve\`, \`merge\`, \`reject\`, \`resolve\`, \`retry\`, \`revise\` and \`verdict\` are applied from an app request`, then `reply \`/<command>\` on the issue instead` for a known command). A refusal reads exactly as the comment path's (`` `/<command>` was not applied: <reason>. ``), is written once to the item's thread with the marker `factory:refused:app-<seq>` (the outbox posts it), and is then stored on the row; a request naming no known item stores its refusal and posts nothing. Each request is marked once by a conditional update (`handled_at`, `refusal`; migration 23 on SQLite). Requests come from the page's POST (design 09-dashboard-app). No schema change; solo and enterprise behave the same.
