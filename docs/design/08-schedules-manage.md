- **A Check a page schedule is written by `factory schedule add`/`edit` and the schedule routes, may run on each merge, is deleted with its suggestions, and `factory routine` is an alias (decision changed 2026-11-25, local-task-tk_3ec69bb2 phase 2 of 3; current; replaces "`check_page` is not written by `schedule add`/`edit`" of the Check a page decision and "deletes the `controller_schedules` row" of the delete decision, see History).** Owner answers, verbatim: 1. "Keep factory routine as an alias, or remove it?" Answer: "Alias: keep factory routine, printing the schedule equivalent (the default, accepted)". 2. "Keep Delete for Check a page schedules?" Answer: "Keep: add schedule delete to the CLI, the API and the row menu (the default, accepted)".
  - **Fields.** `--action check-page` needs an http(s) `--url` and `--instruction` (`--body` fills the same); `--run-cap`/`--daily-cap` set its USD caps (`none` clears; a non-positive or non-numeric value is refused). Stored in the row's columns of those names (`run_cap_usd`, `daily_cap_usd`); HTTP takes the same names, null clearing a cap.
  - **On merge.** `--cadence on-merge` is check-page only, takes no `--spec`, zone UTC by default (as routines), `trigger_kind` merge, no next due time; `schedule list` prints `on each merge`, `schedule run` refuses it. Edit changes no check-page schedule's cadence, zone or trigger, and no action to or from check-page. A refusal stores nothing.
  - **Lists.** `schedule list` shows check-page rows (`listSchedules({ check_pages: true })`); GET `/api/v1/schedules` lists them too, as stored with `skip_when_busy` (changed 2026-11-25, phase 1 of 3; see History; page: [09-dashboard-schedules](09-dashboard-schedules.md)). GET `/api/v1/schedules/suggestions?schedule=<id>` reads the routine store's list (400 without it, 404 unknown).
  - **Delete.** `deleteSchedule` also deletes the row's `controller_schedule_suggestions` in its one transaction, owner only.
  - **Alias.** `factory routine` prints its `factory schedule` equivalent (or why there is none) on stderr, then acts on the same row; the `/api/v1/routines` routes are removed (see History).
  - **Not yet.** The row menu's Delete (a `web/` follow-up); triggers other than merge.

- **A schedule can be drafted from the owner's words and its text improved by the configured model: `factory schedule draft <words…> [--yes]`, `factory schedule improve <id> [--yes]`, `POST /api/v1/schedules/draft` and `/improve`; the dashboard follows in phase 2 (new decision, 2026-11-25, local-task-tk_57c9bfa2 phase 1 of 4; current).** No decision is replaced. Owner answers, verbatim: 1. "Merge skip-when-busy and the missed-time rule into one per-schedule setting?" Answer: "Merge into one setting, migrate skip_when_busy (the default, accepted)" (a later phase; this one leaves `skip_when_busy` as it is). 2. "How does factory schedule draft confirm before it adds the schedule?" Answer: "Ask y/N in the terminal; --yes skips the ask (the default, accepted)".
  - **Core.** `src/core/schedule-draft.ts`: `draftSchedule(words, deps)` and `improveSchedule(id, deps)` each return a proposal or a reason and store nothing. One `standard` model call through the llm plugin, JSON only (`output_schema`), the owner's words or the schedule's text fenced as untrusted data, as `interpretRequest` fences a chat message. A failed call (error, refused, cut off, unparsable answer) is a reason.
  - **Draft.** The model answers title, cadence kind and spec, zone, action kind and its text. The core runs the checks `schedule add` runs (`cadenceProblem`, `scheduleActionOf`, the zone) and refuses a failing proposal with that reason. The ID is `sch_` plus the CLI's `newId`, so the words never choose it. The zone is the machine's (Intl), as the persona schedules use, unless the words name the zone the model gave.
  - **Improve.** Reads the schedule's text (a build's body, an agent's or feedback's prompt) and answers the old and the revised text.
  - **Egress.** The words, or the schedule's text, are scanned before the model call, and the model's text before it is returned; a finding refuses it and names only the rule, never the text.
  - **CLI.** Both print the proposal, or the old and new text, then ask y/N on the terminal (an `ask` the CLI handler passes only while stdin is a TTY; it prints the proposal before its question, so the owner sees what they approve). y adds it through `createSchedule`, or edits it through `editSchedule`; n stores nothing. `--yes`, the last word, skips the ask, for improve too. No terminal and no `--yes` is refused and stores nothing. The command table gives both `no_chat`: the confirmation needs a terminal.
  - **HTTP.** `src/ui/schedules-api.ts` through `write-routes.ts`: the write guards (Origin, JSON, CSRF token), a 400 for a bad body (`{ words }` or `{ id }`), the owner check (403), all before any model call; no model is a 503, a refusal of the core a 409, else 200 with `{ proposal }`. Stores nothing. The model is the Data page's Ask model (`settings.ask.llm`, the Model plugin compose.ts builds), so the UI process has one way to get it.
  - **Off.** No model (plugins.llm cannot be built) turns both off; the CLI and routes say so, and nothing else changes.
  - **Not yet.** The dashboard's Draft and Improve buttons and New schedule form (phase 2).

- **A schedule can be deleted: `factory schedule delete <id>` and `POST /api/v1/schedules/delete` (decision changed 2026-11-24, owner screenshot #93 "we should support removing schedules"; current; replaces "no delete: a schedule can only be paused" of the CLI and HTTP decision below; full text in [history/08-schedules.md](history/08-schedules.md), moved for the size cap).** `deleteSchedule` (`src/core/schedule.ts`, owner only; refused `no schedule <id>`, a 404 over HTTP) deletes the row and its suggestions (since 2026-11-25, above) and ends its held checkpoints as `rejected` in one transaction; other run rows, items and runs stay, and a run in flight finishes.

- **Schedules are managed from the CLI and the HTTP routes; the dashboard page follows in phase 2 (new decision, 2026-11-24, wi_945d62c472fa4b37943a1f1ce11a3d48, phase 1 of 2; current).** Owner answers: pause clears the next due time, so no migration (answer 1); `schedule add` creates build, agent and feedback actions only (answer 2). No decision is replaced.
  - **Commands.** `factory schedule …`, group `schedule` of the command table (`src/core/command-table.ts`), so in the CLI usage, SET_UP.md and chat; `local-cli.ts` hands the word to `parseScheduleArgs` and `runScheduleCommand` (`src/core/schedule.ts`). The table gives each flag. `--body` is a build's item body and an agent's or feedback's prompt (`scheduleActionOf`, shared with the routes). Full text in History.
  - **Writes.** `pauseSchedule`, `resumeSchedule`, `runSchedule` and `editSchedule` read the schedule, decide, then write once through `ScheduleStore.updateSchedule(id, read, patch)`: one UPDATE of only the patch's fields, conditional on `next_due_at` still being the value read (IS NULL when null). A lost condition is refused `changed by another worker, try again` and writes nothing; so a pause made between a claim's read and its write makes that claim fire nothing, and a claim made since a write's read makes the write change nothing. Pause sets `next_due_at` to null (refused `already paused`), so a paused schedule is never listed due and its slots never fire; resume sets the first slot after now (refused `not paused`, or `never falls due`); run sets now, so the next tick claims it once, as `refused` while it runs (refused `paused`, writing nothing). An edit refuses no field and a bad cadence, zone, action or token cap; a changed cadence or zone on an unpaused schedule sets its first slot after now, and a paused one stays paused. `add` refuses an ID already stored. The CLI decides at the store's Clock's time (`scheduleNow`), as it has no Clock of its own. No migration and no backfill: a paused schedule is one with a null `next_due_at`, as one whose cadence never falls due again.
  - **Owner only.** Every write is the owner's: the CLI claims the owner first, as every write does, and refuses anyone else; the routes check the owner (`ownerOf`). Reads print for anyone.
  - **HTTP.** `src/ui/schedules-api.ts`: GET `/api/v1/schedules` and `/runs?schedule=<id>` (400 without it, 404 unknown); POST `/add`, `/edit`, `/pause`, `/resume`, `/run` with `id` and, for add and edit, the CLI's fields. A bad body is a 400 before any store call, not the owner a 403, a core refusal a 409, else 200 with the schedule. Full text in History.
  - **Not yet.** The Schedules page and its New schedule form (phase 2), and the retention of `controller_schedule_runs`.
