# 8. Enterprise: retention

- **Every table that grows has a rule: the daily pass prunes more tables, a page's allowed check is not audited, raw records keep 7 days, and three lookups use indexes (decision changed 2026-11-16, local-task-tk_b699b800; current).** The decision that changed: **the daily pass deletes from every operational table that grows**, instead of three classes over `outbound_intents`, `inbound_commands` and three record tables while `authz_audit`, the outbound action and batch tables, passports, claim pauses and the controller inbox grew forever (the live store was 428 MB after 7 days: `authz_audit` 89k rows, about 12k a day, 99.99% "allow"; each outbound table +1.3–1.5k rows a day; 2,184 of 2,577 passports expired; 653 controller inbox rows with no expiry; `inbound_raw_records` 208 MB). Code: the `retention` unit (`src/controller/units/retention/`), ticked by the controller role; the store's `pruneDeliveredOutbox`, `pruneHandledCommands` and `pruneHistory` (`src/impl/store/sql/retention.ts`); inbound's `records` tick for raw records.
  - **Three classes, one period each, plus raw records.** `factory.config.json` takes a `retention` block: `outbox_days` (default 30), `commands_days` (default 30), `records_days` (default 90) and `raw_records_days` (default 7). An absent block or key takes its default. A value must be an integer of 0 or more; anything else fails startup with a message naming the key, and an unknown key under `retention` fails load with a suggestion. `0` keeps that class forever: the pass skips it entirely. The block is file-only, not a runtime setting (`factory settings`): a shorter period deletes history, so it changes by a reviewed PR. Every worker gets the same defaults.
    - **Outbox** (`outbox_days`): a thread entry (`outbound_intents`) or an action (`outbound_actions`) with `delivered_at` set and created more than `outbox_days` ago; an undelivered row is never deleted. Each item's newest `push_base` action stays at any age: `getBasePush` reads it and its batch's tries. Then the batch rows no kept intent uses: an `outbound_batch_intents` row whose intent (`act_<seq>`, `int_<seq>`) is gone and whose batch is sent or gone, and a sent `outbound_batches` row sent before the cutoff with no intent row left. `outbound_deliveries` (one row per posted comment, read by reactions and edits) is never deleted (decision 2 of the work item: keep deliveries).
    - **Commands** (`commands_days`): unchanged. A row of `inbound_commands` created more than `commands_days` ago, whose seq is at or below the `commands` cursor (inbound announced it), and that is not waiting for the CLI mirror (`mirror` = 1 with `mirrored_at` NULL stays). An app request also needs `handled_at`. A request recorded before the two tables merged (`legacy_table` `app_command_requests`) also waits until its `app:<seq>` command row is gone; a request recorded since is its own command row.
    - **History** (`records_days`, the store's `pruneHistory`, renamed from `pruneRecords` so it is not mistaken for inbound's own `pruneRecords`): claim decisions (`controller_claim_decisions`, by `at`), host sleeps (`worker_host_sleeps`, by `woke_at`), alerts (`controller_alerts`, by `created_at`), authorization decisions (`authz_audit`, by `at`; decision 1: 90 days, the records period) and claim pauses (`worker_claim_pauses`, by `resume_at`) older than `records_days`. In the same call, by the store's clock and not by `records_days`: passports past `expires_at` (`identity_passports`) and revocations past theirs (`identity_revocations`).
    - **Raw records** (`raw_records_days`, inbound's `records` tick, not the daily pass): `inbound_raw_records` received more than `raw_records_days` ago. A polled snapshot goes at the cutoff (its message went out with it); a stream row only once its source's inbox cursor passed it, as before. Default 7 (decision 3), instead of 14: polled snapshots were most of the 208 MB.
  - **`inbox_retention_days` is deprecated.** It set the raw record period (default 14). It is still read: when `retention.raw_records_days` is absent, a positive integer there sets it, and the config loads with a warning naming the new key; when both are set, `retention.raw_records_days` wins (and the warning says so). Removal plan: once no config in use sets it (the startup warning shows which do), a later change refuses the key at load with a message naming `retention.raw_records_days`, then drops it from the known keys and from `FileConfig`.
  - **Kept tables.** `controller_state_changes`, `controller_verdicts` and `worker_runs` are never deleted: they are the audit trail and the measurement history. `outbound_deliveries` is kept too (above). No retention call names them. Tables the work item does not name (`controller_handoffs`, alert patterns, posted comments, the item thread) and transcripts (waiting for the signal ledger, #305) are out of scope.
  - **Guards.**
    - **Claim decisions.** A claim decision whose run is `queued` or `running` stays at any age: `approveClaimHold` reads it, and the hold timer counts from its `held_since`, so a long hold must keep its row. Only decisions of finished runs (or runs gone) age out.
    - **Alerts.** An alert counts as open while it is inside the alarm dedupe window (`ALERT_DEDUPE_MS`, 6 hours, design 05-alarms). The cutoff for alerts is the older of `records_days` and that window, so no retention above 0 removes an open alert.
    - **Claim pauses.** A pause in effect has `resume_at` in the future, so it is never older than the cutoff. A probe pause (`model_stall`, `network`) is in effect while its row is after its `_answered` row, whatever the clock says: its three rows (`<name>`, `<name>_since`, `<name>_answered`) stay until a probe answered it. A pause started again after its row was deleted is a new row, read as any other.
    - **Passports.** An expired passport that is the parent (or any ancestor) of a passport still valid stays, so no live passport loses a link of its chain; it goes once that child expires.
  - **The controller inbox expires (decision 4).** The controller's bus gives a message that carries no key TTL (`idempotency_key_ttl_ms` null) an inbox row expiring 14 days after the message (`CONTROLLER_INBOX_TTL_MS`), raised to its topic's maximum redelivery when that is longer, so a redelivery is still deduped; the bus's own `prune` tick deletes expired rows, as for any TTL. A dead-letter notice keeps no expiry. Other components' inboxes are unchanged, and rows written before this change keep their NULL expiry (no backfill).
  - **Authorization audit of page checks.** A dashboard page asks the owner check whether to offer a command (approve_spec, approve_merge) on every load. That read-only check (`OwnerAuth.check`) writes an `authz_audit` row only when it refuses; a command decision, allowed or refused, still writes one (design 08-permissions, Audit).
  - **Indexes.** Three hot lookups scanned whole tables. Additive migrations add `outbound_actions_item` on `outbound_actions (work_item_id, action, seq)` (getBasePush), `controller_handoffs_item` on `controller_handoffs (work_item_id, at)` (an item's handoffs) and `outbound_deliveries_comment` on `outbound_deliveries (comment_id)` (a reaction's posted comment). A store test checks each query's plan uses its index.
  - **VACUUM.** A deleted row frees pages inside the file but does not shrink it. `npm run migrate` (apply mode) runs `VACUUM` after the migrations and the data step, and prints the bytes freed (page count times page size, before minus after). The factory never runs it on its own: VACUUM rewrites the whole file and holds the write lock while it does.
  - **The dead base push table.** `outbound_base_pushes` is read by nothing; its contract drop (`20261109T1215-outbound-drop-base-pushes`) and the legacy drop run only when the owner runs `npm run migrate -- --contract`, 14 days after the migrations they follow; `npm run migrate -- --contract --dry-run` lists both first. This change runs neither.
  - **Bounded batches.** Each store call deletes at most a batch (500) per table: it selects the keys of matching rows, ordered, then deletes those keys with the guards checked again (SQLite has no `DELETE ... LIMIT`); a guard that reads its own table (the newest push_base, the passport chain, a probe pause) is checked in the select only. Cutoffs come from the store's clock. The pass calls a class again while a batch comes back full, up to 200 batches; past that the day stays unmarked and the next tick goes on. Every delete is conditional, so a pass run twice, or two at once, deletes nothing more and does not fail.
  - **Once per UTC day, under a lease, with a day mark.** The controller role ticks the step each poll interval. The step takes the store sync lease named `retention` (`inbound_sync_leases`, `acquireSyncLease`; owner the replica id, or `controller` solo); a replica that cannot take it does nothing. It reads the store cursor `retention` (`inbound_cursors`), which holds the last UTC day a pass finished; when that is today it does nothing, else it prunes and moves the cursor to today with `advanceCursor` (conditional on the value it read). Then it releases the lease. A process also caches the day it finished, so later ticks that day make no store call; the cache is not shared state, and a restart or another replica reads the cursor. A pass that outlives the lease is still safe: a second holder's deletes are conditional and its cursor move is conditional too.
  - **Why a store port in the unit.** The unit-purity ratchet forbids a unit to reach `.d.store`, and the kernel has no prune write. The role hands the step the store's retention calls (`RetentionStore`, a `Pick` of the store); a later change can move the deletes into kernel writes.
