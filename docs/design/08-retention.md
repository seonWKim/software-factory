# 8. Enterprise: retention

- **The controller deletes old operational rows once a day, in three classes, under a store lease (new decision, 2026-11-11, issue #462; current).** The inbox cleanup (`inbox_retention_days`, inbound's `records` tick, `docs/architecture.md` Intake) stays as it was. Code: the `retention` unit (`src/controller/units/retention/`), ticked by the controller role; the store's `pruneDeliveredOutbox`, `pruneHandledCommands` and `pruneRecords`.
  - **Three classes, one period each.** `factory.config.json` takes a `retention` block: `outbox_days` (default 30), `commands_days` (default 30) and `records_days` (default 90). An absent block or key takes its default. A value must be an integer of 0 or more; anything else fails startup with a message naming the key, and an unknown key under `retention` fails load with a suggestion. `0` keeps that class forever: the pass skips it entirely. The block is file-only, not a runtime setting (`factory settings`): a shorter period deletes history, so it changes by a reviewed PR. Every worker gets the same defaults.
    - **Outbox** (`outbound_intents`, the thread outbox): a row with `delivered_at` set and created more than `outbox_days` ago. An undelivered row is never deleted.
    - **Commands** (`inbound_commands`, the command inbox and the app requests merged into it): a row created more than `commands_days` ago, whose seq is at or below the `commands` cursor (inbound announced it), and that is not waiting for the CLI mirror (`mirror` = 1 with `mirrored_at` NULL stays). An app request also needs `handled_at`. A request recorded before the two tables merged (`legacy_table` `app_command_requests`) also waits until its `app:<seq>` command row is gone; a request recorded since is its own command row.
    - **Records:** claim decisions (`controller_claim_decisions`, by `at`), host sleeps (`worker_host_sleeps`, by `woke_at`) and alerts (`controller_alerts`, by `created_at`) older than `records_days`.
  - **Kept tables.** `controller_state_changes`, `controller_verdicts` and `worker_runs` are never deleted: they are the audit trail and the measurement history. No retention call names them. Tables the issue does not name (alert patterns, posted comments, the item thread) and transcripts (waiting for the signal ledger, #305) are out of scope.
  - **The claim-decision guard.** A claim decision whose run is `queued` or `running` stays at any age: `approveClaimHold` reads it, and the hold timer counts from its `held_since`, so a long hold must keep its row. Only decisions of finished runs (or runs gone) age out.
  - **The alert guard.** An alert counts as open while it is inside the alarm dedupe window (`ALERT_DEDUPE_MS`, 6 hours, design 05-alarms). The cutoff for alerts is the older of `records_days` and that window, so no retention above 0 removes an open alert.
  - **Bounded batches.** Each store call deletes at most a batch (500) per table: it selects the keys of matching rows, ordered, then deletes those keys with the guards checked again (SQLite has no `DELETE ... LIMIT`). Cutoffs come from the store's clock. The pass calls a class again while a batch comes back full, up to 200 batches; past that the day stays unmarked and the next tick goes on. Every delete is conditional, so a pass run twice, or two at once, deletes nothing more and does not fail.
  - **Once per UTC day, under a lease, with a day mark.** The controller role ticks the step each poll interval. The step takes the store sync lease named `retention` (`inbound_sync_leases`, `acquireSyncLease`; owner the replica id, or `controller` solo); a replica that cannot take it does nothing. It reads the store cursor `retention` (`inbound_cursors`), which holds the last UTC day a pass finished; when that is today it does nothing, else it prunes and moves the cursor to today with `advanceCursor` (conditional on the value it read). Then it releases the lease. A process also caches the day it finished, so later ticks that day make no store call; the cache is not shared state, and a restart or another replica reads the cursor. A pass that outlives the lease is still safe: a second holder's deletes are conditional and its cursor move is conditional too.
  - **No schema change.** The lease and the cursor reuse existing tables; no migration, table or column was added.
  - **Why a store port in the unit.** The unit-purity ratchet forbids a unit to reach `.d.store`, and the kernel has no prune write. The role hands the step the store's retention calls (`RetentionStore`, a `Pick` of the store); a later change can move the deletes into kernel writes.
