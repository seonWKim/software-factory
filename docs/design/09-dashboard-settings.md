# 9. Status page: dashboard Settings and Plugins pages

- **The Settings page has three tabs, every key reads as words, and the approval queues sit on the Rules page (decision changed 2026-11-16, local-task-tk_ff159996-481f-42e1-af0d-64216fec6817; current; replaces "one column of sections with a raw key as each row's name", and the Settings placement of Pending proposals, Standing approvals and Providers, see History).** The decisions that changed:
  - **Tabs.** `SettingsPage` (`web/src/views/settings.tsx`) shows the shared underline `Tabs` (design 09-brand-and-tokens), the selected one in the `tab` query parameter (`useUrlParam`; General when it is absent or unknown, so a reload keeps it). **General:** Mode and Notices. **Integrations:** Integrations and Calendar (the Calendar page's empty-state link goes to `/app/settings?tab=integrations#calendar`). **Advanced:** Settable keys, the file keys ("Change on a local branch"), the PR-only keys, History, Commands from the page and Ignored overrides (owner answer: Commands and Ignored overrides go to Advanced).
  - **Labels.** A key's primary text is its human label and description from `web/src/i18n/en.ts` (`key.<name>.label`, `key.<name>.help`, read through `web/src/lib/key-label.ts`; a key with no entry reads as itself). Every settable key has both; the file, read-only and PR-only keys have a label. A row's key name, Source, File value and Applies at sit behind one Details toggle (`KeyNameDetails` for the rows without a Source). Save and Reset buttons and field labels name the label, never the key. The intro names no CLI command.
  - **Approvals on Rules.** `ApprovalsSection` (`web/src/views/standing.tsx`) is the "Approvals" heading of the Rules page (existing surface, owner answer): the pending proposals, then the standing rules, from one `GET /api/v1/standing` read. Each part is hidden when it has no items, and the heading when both are empty, so no empty box asks for a decision. The standing rule facts no longer print the `standing_approvals.threshold` key.
  - **Models on Plugins.** The Providers table moved from Settings to a Models tab of the Plugins page (`ModelsTab`, `web/src/views/plugins-models.tsx`, from `GET /api/v1/settings/capabilities`, provider entries only); the Settings "see Plugins page" link is gone. The endpoints and what any setting does are unchanged.
- **The Health page has a GitHub budget tab, shown only while a budget is stored, and the Rules page shows the improve report (decision changed 2026-11-16, phase 1 of 3 of local-task-tk_3164aaa9-e569-4086-9e6d-013b63474c69; current; replaces "the GitHub budget shows only on `/classic`" of the 2026-11-07 GitHub budget decision in 09-status-page.md, see History).** The decision that changed: **the app shows the GitHub budget and the improve report itself.** `HealthPage` (`web/src/views/pages.tsx`) adds a "GitHub budget" tab (`?tab=github`) after the others only when `overview.github_budget` is non-null (GitHub selected and polled); with it null the tab is not drawn, even for `?tab=github`. The tab reads only the overview, no GitHub call: remaining of limit until `reset_at`, the calls this process counted (and its share when `share_limit` is set), a warn `Notice` with the wait reason while `waiting` or "budget low" while `low`, and `github_token_days` when not null ("not checked yet" for `unknown`). The Overview type carries `github_budget` and `github_token_days`. The Rules page's improve report and Run now are in 07-self-improvement.md (the same date).

The read-only keys show value and reason only (`settings.file.readOnlyLine` is removed); `settings.file.intro` names no file; `settings.noProjectLabel` points to the label control. A Project label `Field` (`Input`, Save, the shared `Outcome`) sits at the top of the Settable keys section beside the per-project lines (`web/src/views/settings.tsx`, `settings.projectLabel*`), and posts the `project-label` write (design 08-settings). No new component or colour. The PR-only table and its title still name factory.config.json: those keys change only by a reviewed PR.
- **The Plugins page adds, imports and approves from the page, and edits the skill folders (decision changed 2026-11-16; current; replaces the "empty states name `factory pack add <path>` and `capabilities.skill_folders`" and "with no approvals route the page names `factory pack approve mcp_server <name>`" parts of the 2026-11-15 Plugins page decision below, see History).** The decision that changed: **the page does what the CLI does for agent capabilities; no Plugins text names a CLI command or the config file.** The CLI commands (`factory pack add|approve|revoke`, `factory plugins import|list`) are unchanged.
  - **Import and Add on every tab.** Each tab shows Import and Add above its list, or in its empty state when the tab has nothing. Import opens the import `Dialog` of 11-plugin-import.md: it reads GET `/api/v1/plugins/import`, lists the found skills (Skills tab) or MCP servers (MCP and Tools tabs) with a checkbox each, and posts the checked ones to POST `/api/v1/plugins/import`, as `factory plugins import`. Add opens a `Dialog` with one path field: on MCP and Tools a pack folder, or one `.json` file of a pack's `tools/` or `mcp_servers/` folder (that file alone), stored as pending (`{ "action": "add", "path" }`, as `factory pack add`); on Skills a skill folder, or a skill file whose folder is taken (`<folder>/<name>/SKILL.md` or `<folder>/<name>.md`). The path is typed: a browser file picker gives no server path. Add on MCP and Tools rides the pack approvals route, since the server's write routes are one per path (`src/ui/packs-api.ts`); a page with no factory user is refused before any write.
  - **Approve and Revoke on every row.** Every MCP server row and every pack tool row on the Tools tab has Approve, or Revoke once approved (`kind` `mcp_server` or `tool`); a broker tool has none (it is granted through `tool_grants`). The read adds `tool_status` (each pack tool's status by row name) for this. With no approvals route the buttons, Import and Add are off, with the reason in their tooltip; no fallback line is shown.
  - **Skill folders.** The Skills tab lists the configured skill folders (`skill_folders` of the read, as the file holds them; an empty list and no error when none is set), each with Remove. Add and Remove send the whole new list as `edit-file` of `capabilities.skill_folders` to POST `/api/v1/settings` with the read's `settings_token` (null, and Add and Remove off, without the config file writer); the writer puts it on a local branch and the page shows that item's Merge button (design 08-settings).
- **A Plugins page, in its own sidebar group above System (decision changed 2026-11-15; current; replaces "the sidebar groups are Tasks, Factory, System and the Settings row" and "capabilities are a section of Settings", see History).** "Plugins" on this page means what the agents can use (MCP servers, skills, tools), never the factory's implementation plugins of `docs/plugins.md`.

  - **Tabs.** `web/src/views/plugins.tsx`: the shared `Tabs`, MCP, Skills and Tools.   - **Search and empty states.** One search box over name and description (every word, any case), cleared on a tab change. An empty tab says how to add one, with Import and Add (since 2026-11-16, the decision above); a search that matches nothing says so.
  - **The read.** `GET /api/v1/plugins` (`src/ui/plugins-api.ts`, served from `src/ui/server.ts` beside the notices so `api.ts` stays in its size budget) returns `{ as_of, csrf_token, mcp, skills, tools }`, every string through the `Withholder`; a 404 without the Settings wiring. `csrf_token` is the pack approvals route's token, null when that route is not wired (the buttons are then off; since 2026-11-16 the read also carries `tool_status`, `skill_folders` and `settings_token`, the decision above).   - **Settings page layout and object values (decision changed 2026-11-10, owner feedback; before: the pending proposals sat inside "Standing approvals" near the bottom, the PR-only keys were headed "Changes by PR only" with a "changes by PR only" note per row, and an object value showed as one JSON line, see History).** The page opens with "Pending proposals" (its own section, the one part of the page that waits for an answer), then Mode, Commands from the page, Settable keys, Standing approvals, the PR-only keys and History.   - **Claim pauses and "Resume now" (decision changed 2026-11-07, issue #291; design §5 Restarts).** `GET /api/v1/pauses` (`src/ui/pause-api.ts`, store reads only) returns `pauses`, each claim pause in effect (`rate_limit`, `forge_auth`, `preflight_access`, `model_stall`, in that order) with `name` and `ends_at` (for `model_stall` the next probe time), and `csrf_token` (the Settings token; null when the resume route is not wired). `POST /api/v1/pauses/resume` with `{ "name": <pause> }` ends one through `endClaimPause`, the same code `factory resume <name>` runs, and answers `{ name, ended, pauses }`; a second resume answers `ended: false`. Guards, in order, all before any store write: Host, Origin equal to the Host's own origin, Content-Type `application/json`, the CSRF token in `x-csrf-token`, the body size, JSON, a known pause name (400 otherwise), then the owner check: the page's factory user (a `local` account linked to a user, else `cli_user`; none is a 403) must be allowed `approve_spec` on the configured project (403 otherwise, nothing written). The UI process still makes no forge call: the check runs the configured auth plugin over the local grants only (a remote grant such as `github-permission` is left out there, so grant the role in `permissions.static` or use `factory resume`). Each resume writes one log line with the factory user ID. **App:** the Floor and Health pages show a "Claim pauses" section above their other sections while any pause is in effect: each pause's name, what it stops and when it ends, and a "Resume now" button that posts with the token; the endpoint's error shows next to that button, and a resumed pause leaves the list. No section while none is in effect.
  - **Standing approvals on the Settings page (decision changed 2026-11-08, issue #300, phase 3 of #293; see `05-standing-approvals.md`).** `GET /api/v1/standing` (`src/ui/standing-api.ts`, store reads only) returns `rules`, each rule a person can turn on (only `spec-t1`) with `rule`, `gate`, `tier`, `threshold` (the effective `standing_approvals.threshold`: file, override or default, the Settings resolve), `enabled` (off when no row is stored), `set_by` (a user ID), `created_at`, `updated_at` and `last_used_at` (always null: not recorded in this phase, the page shows "not recorded"); `proposals`, the pending ones (`id`, `rule`, `run_length`, `threshold`, `created_at`): stored, its rule not on, and the rule not written since the proposal was stored; and `csrf_token` (null when the write is not wired). Every text value passes the Withholder. `POST /api/v1/standing` with `{ rule, enabled, proposal? }` writes the rule with `putStandingRule` (`set_by` = the page's factory user ID) and one log line (`standing rule on|off`, rule, user ID, proposal), and answers `{ changed, ...the read model }`. Guards, in order, all before any store write, the same as the resume route: Host, Origin equal to the Host's own origin, Content-Type `application/json`, the CSRF token in `x-csrf-token`, the body size, JSON; then the body (400: not `{ rule, enabled, proposal? }`, a rule other than `spec-t1`, or a proposal not stored for that rule); then the owner check, the resume route's own principal and `approve_spec` authorize (403, nothing written). A rule already in the asked state is not written (`changed: false`; no row stored counts as off), unless the body names a pending proposal: then the answer is written so the proposal leaves the list. The route is wired with the pause routes (absent: a POST is a 405). No audit row (a stored per-person audit record is a follow-up). **App:** the Settings page shows a "Standing approvals" section: a switch per rule with its gate, tier, threshold, who set it, created and last used, and Accept and Decline per pending proposal; a refusal shows beside its item.
