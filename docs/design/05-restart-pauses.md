# 5. Coordination: claim pauses, rate limits and failure details

- **A missing model credential is one setup state: no agent run is claimed until it exists (new decision, 2026-11-21, RFC 0024 WP1; changes the infra rule of 05-restarts.md for it and the env-file store's single read, see History).** Before each claim the worker asks `WorkerDeps.modelCredential` (compose wires it when every selected runner declares the `model credential` secret group: doctor's check of it, presence only, no value leaves the store). With none, the tick claims no agent run (`MODEL_RUN_KINDS`: triage, implement, review, resolve; update, merge-check and improve still claim) and sets the store-wide claim pause `model_credential` (`MODEL_CREDENTIAL` in `src/core/policy.ts`, its row a far-future time; the worker whose write started it logs one warning). Any worker whose check finds the credential ends it on its next tick, and the queued runs are claimed as they are: no `/retry`, no restart. The env-file secret store reads its file again, at most once per 5 s, when a declared name has no value or the last read failed; every value it ever read stays in the scan. A runner that finds no credential after a claim (a race) throws `SetupMissing`: the worker classifies it `setup_missing` (never `exception`), and with a check wired puts the agent run back in the queue as the network pause does (`paused_by` `system:setup_missing`): no outcome, retry, count or alarm. The pause is not resumable (`RESUMABLE_PAUSES` is unchanged), queued agent runs say "Waiting for a model credential", and Needs you shows one row, "Add a model credential: run `npm run setup`" (09-status-page). `factory dev` prints doctor's line once at start. Out of scope: the OpenAI-compatible runner and its `provider_setup` path.

- **Stop all agents and resume: `factory stop`, `factory resume owner`, the dashboard's Stop all agents, and `workers` 0 (new decision, 2026-11-21, wi_0f56f105; current; changes the `workers` rule (1 or more) and the "no worker pause or resume control on the dashboard" line of the decision below, see History).** The decision: **one owner action stops every agent, and one starts them again; it reuses the worker pause, so there is one pause mechanism.** `factory stop` (`src/cli/handlers/resume/`, the command that also takes `resume`) and Stop all agents (POST /api/v1/agents/stop, `stopAllAgents` in `src/ui/pause-api.ts`) start the *owner pause*: the all-workers row of `worker_pauses` (`worker_id` `*`), the row `factory workers pause --all` writes, with `paused_by` the actor's ID and `paused_at` the time (`stopAgents` in `src/resume-cmd.ts`; no new table, column or migration). While it holds, `claimRun` gives no worker a run, and each worker stops its running implement and review runs within one `tick_ms` and puts them back in the queue with `pauseRun`: attempt unchanged, folder and commits kept (§5 Pause, unchanged). Triage, resolve, update and other runs finish their current step first; interactive sessions keep running; the factory process and its supervisor keep running. A second stop keeps the first row. `factory resume owner` and Resume now on its Needs-you row end it through `endPause`, which for `owner` clears every worker pause, as `factory workers resume` does (hand-set `workers pause <n>` rows included). `factory resume --all` includes `owner`; `factory resume` with no name still ends only `rate_limit`. Both commands run the owner check (`approve_spec`) and act as the CLI identity; a refusal prints `not changed: <reason>` or `not resumed: <reason>`, exits 1 and writes nothing; the dashboard route answers 403 with nothing written. Stop and resume each write one log line with the actor's ID (the logger adds the time): `agents stopped` (`pause: owner`, `actor`, `since`) and `claim pause ended` (`pause: owner`, `actor`). GET /api/v1/pauses lists the owner pause last, as `{ name: "owner", ends_at: null, since }`: it has no end time, only when it began. Needs you shows it as a `claim_pause` row, "Agents stopped by you at 16:03" (local time) with Resume now (`PauseCheckRow`); the `worker_pause` row now counts only the per-worker rows, which keep their CLI hint. **`workers` takes 0** in `factory.config.json` and in `factory settings set workers`: an integer of 0 or more (`workerCount`, `src/core/settings.ts`). At 0 the pool runs no loop (`WorkerPool.loops()`), so no worker claims; a loop that holds a run finishes it, as any loop above `workers` does. With 0 in the file and no `max_workers` the process has no slots, so raising `workers` live needs `max_workers`. Why: the owner asked for "a way to stop all agents"; `workers pause --all` already stopped claims and runs but had no dashboard control and no name in `factory resume`. The Health page's pause list names it "Agents stopped" with how long ago; the other gaps of that list stay a follow-up.

- **`factory resume` and `factory workers` run the owner check and act as the CLI identity; `--by` is removed (decision changed 2026-11-16; changes "An owner can end a claim pause early" below and the worker pause command).** The decision that changed: **before `factory resume` ends a pause, and before `factory workers pause <n>`, `pause --all` or `resume` writes, the command asks the owner check for `approve_spec` on the configured project (`ownerRefusal` in src/compose.ts, the same helper the sentence form and `factory settings` use), as the dashboard's "Resume now" does. A refusal prints `not resumed: <reason>` or `not changed: <reason>`, exits 1 and ends or writes nothing.** Both record the CLI identity's user (`ctx.identity()`: `cli_user`, else `local:<git user.email>`, else `local:<OS user>`, else `local:anonymous`): `resume` in its log line's `actor`, `workers` in `paused_by`. `factory workers status` only reads and asks no check. `factory workers … --by <id>` is refused with the usage: the actor is no longer a flag, so no one can record a pause as another ID. Stored `paused_by` values of older pauses (`system:cli`, a `--by` value) are kept as they are. The dashboard has no worker pause or resume control yet, so the worker-pause hint on the Status page keeps its CLI text (a follow-up); the claim-pause hint and the "Resume now" refusal name Resume now on the Status page (`/app/`) first and `factory resume <name>` as the fallback.
- **Restart history is kept in the store, one row per restart (new decision, 2026-11-08; changes where the restart alarm's history lives).** Each unexpected child exit the supervisor records (`restarts: [{ at, reason }]` in `<state_dir>/supervisor.json`, design 05-alarms) is also stored as one row of `runtime_child_restarts` (`restart_key`, `at`, `reason`; SQLite migration 38). **The row has no `recorded_at` (decision changed 2026-11-09, issue #461; changes the columns of this decision):** nothing read it, so `recordChildRestart` writes only the three columns and the breaking migration `src/runtime/migrations/20261109T1401-runtime-drop-restart-recorded-at` drops the column. The runner archives the table first, and the migration's verify fails if any row's `at` or `reason` changed. A new database gets the schema on open, an existing one through `npm run migrate`, which drains the writers first, since code from before still writes the column. The controller's alarm step writes it: before it counts, it stores each restart of this host's list with `FactoryStore.recordChildRestart`, one conditional insert keyed on the restart's time and a hash of its reason, so the same restart read again on the next poll, or by another replica, leaves one row (`created: false`), and the write is safe to run twice. `listChildRestartsWithin(window_ms)` reads them oldest first on the store's clock. A process with its own restart list counts that list, as before; a process without one (in-place or `none` updater, a controller on a host with no supervisor) counts the store's restarts of every host. So the restart alarm's count and its 30-minute window read the same after the factory or the store restarts. Solo default: the one SQLite store, the same rows. **No backfill:** restarts from before this change were never stored and are not reconstructed; existing items and alerts keep their data, and the migration only adds the empty table. Item restarts are unchanged: an infra failure or `/retry` still only bumps `restart_count` on the item, and the retry, backoff and block rules below are untouched.
- **A dead network pauses claims, not runs (new decision, 2026-11-07; also changes the stall pause's probe and its early end).** A git call (fetch, push, the sandbox's base fetch), the GitHub preflight or a model request through the shared chat client that fails on DNS or connect (`Could not resolve host`, `Failed to connect to`, `getaddrinfo ENOTFOUND`, `ECONNREFUSED` and the like; `unreachableHost` in `src/core/policy.ts`) is `network_unavailable`: the broker returns it for a push and for the preflight's GETs, the openai-compatible runner reports it as the error `network_unavailable: could not reach <host>`, and the worker turns a `git_failed`, `push_failed`, `preflight_failed`, `preflight_access` or `exception` whose text is such an error into it (`classifyNetwork`). Every other `git_failed` and `push_failed` keeps its code. Its detail is `could not reach <host>`, the host name only, never git's text, a URL, a credential or a response body. It is not a failure of the run: the worker sets the `network` claim pause (first probe 30 s later), then puts the run back in the queue with `pauseRun` and nothing to resume (`paused_by: system:network`), so it has no outcome, its attempt is unchanged at the next claim, and it never counts toward `max_restart` or `max_attempts`, never meets the repeated-failure rule and never reaches a dead letter. The run's folder is not kept: an implement run whose push failed on the network runs its agent again. While the pause holds, `claimRun` returns null for every kind, triage and review included; the pause is global, as the rate limit is. The `network` pause is a probe pause like `model_stall`, one store code path for both (rows `network`, `network_since`, `network_answered` in `worker_claim_pauses`; no migration): in effect past its time until a probe passes. **One probe schedule for both probe pauses:** once a probe is due, the controller replica whose conditional update moves the row from the due time to the next probe time (`FactoryStore.claimProbe`) probes, and no other replica; a pass ends the pause through `endClaimPause`, which moves the pause row and its answered row to the earlier of the probe time and now (the stall pause's rule, below, now for both); a failure keeps the pause and moves the next probe its delay after the failed probe. The stall's next probe is `probe_interval_ms` later, as before; the network's is 30 s, 30 s, 1, 2, 4 min, then 5 min (`networkProbeDelayMs`, retryDelayMs over the probes made). The network probe is the `NetworkProbe` interface, default plugin `http` (docs/plugins/network-probe.md): one HEAD to each endpoint of the selected plugins, GitHub only when a GitHub plugin is selected. Solo default and enterprise setting are the same, with no new setting. Logs: one warn when the pause starts (`network unavailable: all runs paused, first probe at <time>`, field `host`), info per failed probe, one info when claims resume (`network reachable again: claims resume`). `factory status` and the Health panel show `agents paused: network not reachable since <time>; runs start again once a probe passes`. Not in this decision: the dashboard's why-it-waits sentence (`src/ui/why.ts`) and `factory resume network`, which need files outside this change; the Claude CLI's own network failure text.
- **A GitHub rate limit waits for its reset; it is not a refused credential (decision changed 2026-11-07).** The REST client reads `retry-after`, `x-ratelimit-remaining` and `x-ratelimit-reset` on every refused call. A 429, or a 403 with `retry-after`, with `x-ratelimit-remaining: 0`, or whose body names the primary (`API rate limit exceeded`) or the secondary limit, throws a `GitHubRateLimitError` with `reset_at`: `retry-after` first, then `x-ratelimit-reset`, else one minute from now. A call the client refuses itself (no calls left before the last reset) throws the same error. The broker returns `github_rate_limited` for it from the preflight, `open_pr` and `comment`, never `forge_auth` and never an exception; its message carries the check or tool and the reset time, never a header or body. The push keeps `forge_auth` (git's stderr is not read for a rate limit; a follow-up). A plain 403 with none of these signals is still `forge_auth`: the forge-auth rule is not widened. The worker, before it stores the outcome, sets the `github_rate_limit` row of `worker_claim_pauses` to the reset (only ever moved later; one log line when a pause starts); it does not touch the model `rate_limit` row or the `forge_auth` row. While the row is in effect `claimRun` skips implement, update and review runs (all three call GitHub on their way) for every worker and replica and still claims triage and resolve, and the controller skips its GitHub source poll with no log line per skipped poll. A run that fails with it spends no attempt and no restart (`failureClass` is `rate_limited`, update runs included); its retry's `not_before` is the later of its backoff and the pause end (`retryNotBefore` in `src/core/policy.ts`). An `open_pr` rate limit keeps the run's commits on its wip branch through the same path as any failed PR (below), so the retry runs no agent. The permission lookup throws on a rate limit until the reset, never "none"; no stored grant stands in for it, and local actions use local auth. No owner comment, no migration (the table takes any name), and no new GitHub call; solo and enterprise behave the same, and on a shared store every replica waits. Known gaps: the pause is not in `factory resume`'s list or the Floor/Health pause list yet, and a controller poll that hits the limit does not set the pause itself.
- **Checks that fail on the base too are `checks_env` (decision changed 2026-11-07).** An implement run whose pre-push check fails twice, and whose failing test files fail on a clean checkout of the base commit too (§4 Pre-push gates, base rerun), fails with `checks_env` (`CHECKS_ENV` in `src/core/policy.ts`), its own failure class: it spends no `max_attempts` and no `max_restart`, adds nothing to `restart_count` and never triggers `repeated_failure`. The controller requeues it from the kept commits (the wip branch) with the usual retry key and backoff, reason `run_retry_scheduled`. The cap is `CHECKS_ENV_LIMIT` = 2 per item, counted from the item's whole run history in the store (every acknowledged `checks_env` run, plus this one), so every replica counts the same: the third `checks_env` on an item blocks it on a human with `run_failed:implement:checks_env` (reason `checks_env`), queues nothing, and posts the last-attempt comment, keyed `run-failed:<run id>`, with the failing tests; `/retry` works as for any `run_failed:*`, and since the count is per item, a further `checks_env` after it blocks again at once. A real bug that also fails on the base (a broken base) is read the same way: each item is requeued up to twice, then blocks. The worker's own comment for each `checks_env` run names the flaky test files (§4). Solo and enterprise use the same path. Not in this decision: filing a factory issue for a test file that is flaky three times in 24 hours.
- **Failure details keep the cause; `provider_setup` is not retried (decision changed 2026-11-07).** A failed check's detail names the failing tests: `checks_failed` appends `failing tests: <file> > <name>, ...` (vitest's `FAIL` lines in the output tail, at most 10, `failingTests` in `src/core/output-summary.ts`); the output tail is kept as before. A rate limit keeps its reset text: the claude-code runner's `rate_limited` error is the CLI's result text (e.g. `You've hit your 5-hour limit · resets 6:30pm`), capped at 500 characters, or `rate_limited` when the CLI gave none; `reset_at` is read as before. The shared OpenAI-style chat client reads the error body of every non-2xx reply, a 429 included: `error.code` (or `error.type`) `insufficient_quota`, `invalid_api_key` or `model_not_found`, at any HTTP status, is `provider_setup`, with the provider's message (key redacted, then capped at 300 characters); any other 429 stays `rate_limited` and keeps the message too. A runner reports it as a `failed` result with `code: provider_setup`. A fallback chain moves to its next member on it (no output was made); only when no member is left does the run fail with it. The worker records the code `provider_setup` (a task failure), sets no claim pause and never reports it as `rate_limited`. The controller does not retry it, for any run kind: the item blocks on a human with `run_failed:<kind>:provider_setup` and one comment, keyed `run-failed:<run id>`, says to check the quota or billing, the API key and the model names, then `/retry` (an automatic resolve run goes back to waiting on the conflict instead of its next attempt). Every new detail is in the outcome, so the worker's whole-outcome egress scan covers it: a flagged detail makes the run `egress_blocked`, as before. For `provider_setup` only, the worker scans the provider's message first and, if flagged (OpenAI's `invalid_api_key` message can echo part of the key), keeps the code and drops the message and the output tail. `llm-check` prints the provider's message on its FAIL line, after its own scan. Not in this decision: the improver (#304) and the failures view (#312), which read these details later.
- **An owner can end a claim pause early (decision changed 2026-11-07, issue #291).** `FactoryStore.endClaimPause(name)`, implemented once in the shared SQL store, ends `rate_limit`, `forge_auth`, `preflight_access` or `model_stall` now. For the three timed pauses it is one conditional update, `resume_at = now WHERE resume_at > now`, so a second end, or an end with no pause in effect, changes no row. `model_stall` ends only when `model_answered` is at or after the probe time, so its end moves both rows to the earlier of the probe time and now (under the claim lock; since 2026-11-07, see the stalled runs and the network pause), as an answered probe does; `model_stall_since` then reads null too. `pauseClaims` still only moves a pause later, and when a pause starts or how long it lasts is unchanged; a pause ended early is "not in effect", so the next failure starts a new one (`started`). Two ways in: `factory resume` (`rate_limit`), `factory resume <name>` or `factory resume --all` (all four), which prints what it ended or `no pause in effect`, exits 0, and exits 1 with no write for an unknown name (`model_stall_since` and `model_answered` are not names); and the dashboard's "Resume now" button (`POST /api/v1/pauses/resume`, design 09-dashboard-app.md). Each end writes one log line, `claim pause ended` (or `claim pause resume: none in effect`) with the pause and the actor ID: the CLI identity's user on the CLI (since 2026-11-16, after the owner check; see the top), the factory user ID in the UI, never a display name. No comment is posted on the item or the PR. No migration or schema change: the rows are those of migration 4.
- **A drain stops the controller at once (decision changed 2026-11-07, issue #294).** When a supervised `dev` child gets the drain message, its controller loop and its stream listeners stop at once: it starts no new pass (no intake, reaper, checks, app commands, run outcomes or model probe), and a pass already running finishes. Only the worker's running runs finish, under the old child's worker, which claims nothing more. The old child runs no final pass over finished runs: the new child's controller, already started (start-then-drain, `docs/design/08-self-update.md`), applies their outcomes on its next pass. The old child logs one line, `controller stopped on drain`, then acknowledges the drain once its runs finished. SIGINT/SIGTERM still stops both loops of every child at once. Handlers stay safe to run twice, and several replicas stay allowed.
