# 9. Status page: dashboard evals page

- **A held version is a Card at the top of the page with "Keep the current version" and "Use this version" (decision changed 2026-11-26, local-task-tk_fa5469ab; current; adds a card before Versions to the order in the versions decision below; before: see History).** The decision: **each version of this skill that the new-version gate holds ([07-self-improvement.md](07-self-improvement.md)) is a `Card` "Version N is waiting for your decision" above the Versions `Card`: its pass rate against the current version's ("Pass rate 40%, down from 80% on version 3"), "Cases that got worse" (each case's input on one line, cut with an ellipsis, or "Case N" when its input is not text; "No single case got worse" when none did), then a `ButtonRow` with "Keep the current version" (secondary) and "Use this version" (primary, last).** Read: `held` of `GET /api/v1/evals` (`useHeldVersions`, `web/src/views/evals.tsx`, polled), filtered to this skill. Use this version posts `{ op: "version.settle", ref, version, decision: "approve" }` to `POST /api/v1/evals/write` with the session's CSRF token; Keep the current version opens a `Dialog` ("Keep the current version of <skill>?", a consequence line and an optional "Reason" `Textarea`, which is not sent or stored, decision 1 of the spec) whose confirm posts `decision: "reject"`. After either, every read is fetched again: the card leaves and the Versions list marks the right version Current. A refusal shows in the Dialog, or for Use this version on its own line under the buttons. The held card and Versions sit in one wrapper, so the gap between them is the Card's own 24px top margin, as between the page's other cards. The held-version alarm in Needs you uses the same `HeldVersionActions` (09-dashboard-tasks-needs.md).

- **Run now starts one run from the page header (decision changed 2026-11-24, local-task-tk_3c92ecdb phase 3; current; replaces "there is no Run now" in the decision below; before: see History).** The decision: **the `PageHeader`'s one primary action is Run now, a primary `Button` that opens a `Dialog`; confirming posts one run to `POST /api/v1/evals/<skill>/runs`, which runs the skill's suite once through `runSkillEval` and answers when the run is stored.** The `factory eval run` gap is closed: the page and the CLI start a run through the same checks.
  - **The Dialog.** Title "Run the tests of <skill name>", a one-line consequence, then three `Field`s: Model (a `Select` of the model classes as stored, cheap, standard, strong, starting on standard; never a model ID, owner answer 2), Judge model (a disabled `Select` that shows the judge class of the chosen model, strong for cheap and standard, standard for strong, as `judgeClass` in `src/core/scorer.ts`; the run is posted with that class) and Replays per case (an `Input` of type number, starting at 1). The footer is the Dialog's `ButtonRow`, Cancel then the primary Run last. A refusal's reason (403 from the owner check, 409 from a refused run) shows in the Dialog, which stays open; a stored run closes it and every read is fetched again. The button shows for every user: hiding it from a user without `approve_spec` is not done, the 403 reason says why.
  - **The route** (`src/ui/evals-run-api.ts`). In `WRITE_ROUTES` with its name in `POST_ONLY`, so it passes the Host, Origin, Content-Type, CSRF and body-size guards first; then the owner check `ownerOf` (`src/ui/rules-api.ts`: `approve_spec`, then the store's owner), whose refusal is a 403 with its reason. The body is `{ model_class?, judge_model_class?, replays? }`, `eval run`'s `--model`, `--judge-model` and `--replays`; a wrong type is a 400. The run is `UiEvals.run`, wired by `factory ui` to the CLI's `skillEvalRun`: `runSkillEvalFor` refuses before anything is written (no suite, a model class not stored, a judge class not the model's, replays other than 1), which is a 409 with its reason and stores no run. The run's `created_by` and its log line carry the acting user's ID, never a display name; the answer is `{ run_id, status }`, each through the Withholder. The `GET` of the same path is the runs read, unchanged. Without a run function wired the POST is a 405.
  - **Out of scope.** The run is not queued: the request waits for it. One replay per case (the engine stores one verdict per case); no cancel and no per-case detail.

Reads: `GET /api/v1/evals/<skill>/versions` and `/diff?a=<folder hash>&b=<folder hash>` ([06-measurement.md](06-measurement.md)), typed in `web/src/api/evals.ts` (`useSkillVersions`, polled every 30 seconds; `useSkillDiff`, read only while both versions are picked). No server route changed.
  - **Versions.** One `ListRow` per version, newest first: "Version N", a `Badge` "Current" on the newest, then the details line "Pass rate 90%", the change since the previous version as "+30 points since the version before" or "−10 points since…" (decision 1; "no change to show" when either version has no rate) and "Saved Nov 22". A version with no run linked to it shows "no pass rate". Under each row a `Disclosure` "Details" (lazy) holds the folder hash (as eval runs store it now, owner answer 4) and the run ID: these are the only places either shows. No versions: an `EmptyState`; a failed read: an `ErrorNote` in the card, the rest of the page unchanged.
  - **Compare.** The Compare `Button` (off with a title when the skill has fewer than two versions) opens a `ModalPanel` "Compare versions" with two `Select`s, First version and Second version (the second the newest and the first the one before, to start), then the `DiffView` ([design-system/components.md](../../design-system/components.md) "DiffView") of the two SKILL.md texts, one column (owner answer 2: unified), each line marked − or +, then a `DataTable` of each case's result in each version ("Case 1": Passed, Failed, Could not judge, or "no result"); cases are numbered, never shown by ID.
  - **Plain words.** All new text is in `web/src/i18n/en/evals.ts`.

- **A skill's evals page shows Trend, Grid and Compare, read only (new decision, 2026-11-23, local-task-tk_3c92ecdb phase 1; current).** The decision: **a page at `/app/evals/<skill>`, where `<skill>` is the suite's `skill_ref`, URL-encoded, that shows how the skill did run by run.** The page is not in the sidebar; the Plugins page's Skills tab links to it (phase 2, decision changed 2026-11-24, see History). `evalsRoute` (`web/src/pages.ts`) parses the path and `App.tsx` renders `EvalsPage` (`web/src/views/evals.tsx`) as it does the transcript; the sidebar marks no page as current. The reads are the existing `GET /api/v1/evals/<skill>/runs`, `/grid` and `/compare?a=&b=` ([06-measurement.md](06-measurement.md)), typed in `web/src/api/evals.ts`, polled every 30 seconds (compare is read only while both runs are picked). The Trend, Grid and Compare cards write nothing; the header's Run now (below, phase 3, decision changed 2026-11-24, see History) is the one control that starts a run.
  - **Layout.** One `PageHeader` (the skill's name, its folder name from the `skill_ref`: `skills/review-plan/SKILL.md` shows "review-plan"; width `wide`), then three `Card`s in one flex column with `gap-6`, in this order: Trend, Grid, Compare. Loading shows `Loading`, a failed read `ErrorNote` with a fixed sentence (its default text would carry the skill's URL), no runs `EmptyState` ("No runs yet").
  - **Trend.** "Pass rate over time": the new `Chart` (`web/src/components/ui/chart.tsx`, [design-system/components.md](../../design-system/components.md) "Chart") with one bar per run, oldest first, height the pass rate over 1. A run with no pass rate is skipped. Every bar is also a sentence ("Nov 20, 12:00: 90%").
  - **Grid.** "Latest run per version and model class": a `DataTable`, one row per skill version, one column per model class (cheap, standard, strong, then others by name). A cell is the newest run of that pair: a `Badge` with its pass rate (tone from its status, `succeeded` or `failed`) and its date. A pair with no run shows the text "no run". A skill version is a hash, so it is named by age: the first version the skill had is "Version 1", the next "Version 2"; a run with no recorded version is "Version not recorded".
  - **Compare (replaced 2026-11-25, see the first decision above).** "Compare two runs": two `Select`s (First run, Second run) and one `DataTable` with the run date, model class and pass rate of both, then the gap (second minus first, in points), the noise band and whether the gap is within noise (Yes or No). Without two pass rates the table says "Not enough replays to say". The pickers list the runs that have a pass rate, as "date, model class, pass rate"; the run ID is only the option's value. It starts on the two newest runs with a pass rate, the older as First run. With fewer than two such runs the card says so and shows no picker.
  - **Plain words.** The page shows the skill's name, run dates, model classes and pass rates. No run, suite or skill ID, hash or snake_case name appears in its text; its text is in `web/src/i18n/en/evals.ts`.
