# 9. Status page: the API registry

- **Each capability is declared once, and its route, OpenAPI document, typed client and feature map come from that declaration (new decision, 2026-11-26, phase 1 of 3 of local-task-tk_c6ba6e00-9024-4701-b9b6-24adb4fb8cdb; current).** Before, every dashboard route had its own hand-written handler, wired by hand in `src/ui/read-routes.ts` and `src/ui/write-routes.ts`, and the page's routes and client were kept by hand in `web/src/api.ts` and `web/src/api/`. That stays for every existing route in this phase: no route, page or client call moves, and only a test fixture is declared.
  - **Declaration** (`src/api/registry.ts` `declare`): an id (`<area>.<name>`), its area, a description, a permission (`read` or `owner`), a method (`GET` or `POST`), a path under `/api/v1/` (outside the feature map's), an input and an output schema, and its run. A run returns its answer or `refuse(status, error)`. The permission is declared only in this phase: the existing guards are the only ones enforced.
  - **Schemas** (`src/api/schema.ts`, owner answer 1): an in-repo helper, no schema library and no new dependency. `string`, `integer`, `number`, `boolean`, `oneOf`, `array`, `object`, `nullable`, `optional` and `jsonObject`; each gives the input check, the output render, the JSON Schema and the TypeScript type. An object refuses an undeclared input field and leaves an undeclared output field out. A nested object may be typed only as a JSON object (owner answer 3): the items output schema (`src/api/schemas/items.ts`) types the answer's and each row's top-level fields and every nested object as a JSON object.
  - **Finding the declarations** (owner answer 2): a checked-in index, `src/api/index.ts`, imports every declaration file in `src/api/capabilities/` (none yet). `tests/api-registry.test.ts` fails while a file is not imported or an import has no file.
  - **Routes.** One `READ_ROUTES` entry, after the others and before `api.ts`'s paths, answers the feature map and every GET capability (input from the query parameters); one `WRITE_ROUTES` entry, last, answers every POST capability (input from the JSON body) behind the same guards as every write route, in the table's order: Origin, Content-Type, CSRF token (the pauses token: the owner's writes), body size, then the capability. `POST_ONLY` names the registry's routes. A bad input is a 400 before the run; an answer that does not match its output schema is a 500. Every string a capability answers, nested JSON objects and a refusal's text too, goes through the `Withholder`; a `oneOf` word, the code's own, does not.
  - **Feature map** (`src/api/feature-map.ts`): `GET /api/v1/feature-map/areas` (each area with its capability ids), `/api/v1/feature-map/capabilities` (id, area, description, permission, method, path) and `/api/v1/feature-map/capabilities/<id>` (one, with its input and output JSON Schemas; 404 for an unknown id). Its text is the declarations', so it needs no Withholder.
  - **Generated files.** `npm run gen:api` (`scripts/gen-api.mjs`, Node's type stripping, no build) writes `docs/api/openapi.json` (OpenAPI 3.1; no capabilities in this phase) and `web/src/api/generated.ts` (per capability its input and output types and one call through `web/src/api/client.ts`). `tests/api-openapi.test.ts` and `tests/api-registry.test.ts` fail while either differs from what the declarations generate, so a schema changed without regenerating fails; the generated client is typechecked by `npm run typecheck` and, for the fixture, in the test.
  - **Headless first** (`AGENTS.md`): a feature is declared as a capability first, and the dashboard, chat and CLI call that API. A page-only or CLI-only behaviour and a hand-written route count as gaps. Counting unregistered page paths in the same ratchet (owner answer 4) comes in a later phase, with its list file.
