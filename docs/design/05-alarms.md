# 5. Coordination: alarms

- **`/retry +paths` on a recurring_failure hold widens the paths and starts a fresh implement run (decision changed 2026-11-26; changes "`/retry` lifts a hold" under the 2026-11-11 entry below, where `+paths` was refused; see History).** Before, `/retry +paths` on an item held for `recurring_failure` was refused ("no failed run to widen"). But the most common task failure that recurs is a `checks_failed` caused by a file outside the allowed paths (a new table's column that needs a line in another file), so the person could not widen the scope on the state where it is most needed. Now, when the item's last failed run is an implement run, `/retry +paths <path>...` adds the paths with the same validation and tier raise as any `+paths` grant (`widen`), lifts the hold, adds one to `restart_count`, cancels the held queued runs and queues a fresh implement run under the new step key, handed the newest kept wip ref (`retryWip`, design 05-restarts), so the saved work goes on. A run cancelled with no outcome is acknowledged as `run_ignored`, never retried, so the cancelled held retry queues nothing. `+paths` on a hold whose last failed run is another kind (or with none) is still refused; plain `/retry` still only lifts the hold. `repeated_failure` already took `+paths` after a failed implement run (its retry kind is the last failed run's) and is unchanged. No schema change, no config key.
- **The owner can dismiss an alarm (decision changed 2026-11-24, local-task-tk_44b73f2b phase 2; changes "One alert per pattern per 6 hours" below, under which an alarm stayed open until its dedupe window ended; see History).** `factory alarm dismiss <id>` and `POST /api/v1/alarms/dismiss` (`{ "alert_id": <id> }`) dismiss the pattern of one alert. The route passes the request guards and the owner check of `POST /api/v1/pauses/resume` (Origin, Content-Type, CSRF token, then `approve_spec` for the page's factory user); the command passes the same owner check for the CLI identity. Both call `FactoryStore.dismissAlert(alert_id, actor)`.
  - **Store.** Migration `20261123T1201-state-alert-dismissals` adds nullable `dismissed_at` and `dismissed_by` to `controller_alert_patterns`, with no backfill (the spec's `T1200` was taken by `20261123T1200-controller-skill-eval-version`). The dismissal records the store clock's time and the actor's user ID, never a display name. It is conditional: a pattern already dismissed since its last alert keeps the first dismissal, so a second dismiss or a replica writes nothing. `listAlerts` returns each alert with its pattern's `dismissed_at`; `listAlertDismissals(since)` lists the dismissed patterns for the alarm step. The SQL lives in `src/impl/store/sql/alerts.ts`.
  - **Hidden.** `openAlarms` (`src/ui/alarms.ts`) hides an alarm whose pattern was dismissed at or after the alarm was raised, so it leaves Needs you. Overview alarm rows carry `alert_id`, the id a Dismiss posts. The dashboard button is phase 3.
  - **Counts start again.** A dismissed pattern counts only the runs that finished after its dismissal: the repeated-error check, the zero-token streak, the child-restart count, the pack-grant refusal alert and the re-raise (which counts from the newest of its last re-raise, its first known time and the dismissal of its `recurring:` or `repeated_error:` key). A failure that goes on brings the alarm back once `alarm_repeat_count` new runs fail.
  - **Stored at once.** `recordAlert` also stores a new alert when the pattern's dismissal is at or after its last alert (and that alert is older than now), so the returning alarm does not wait for the 6-hour window. The winning write moves `last_alert_at` past the dismissal, so replicas store one alert.
  - **Spend.** A dismissed spend threshold (`spend:<period>:<start>:<pct>`) does not alert again in its period; the next period has its own key.
  - **Not changed.** Dismissing holds nothing and lifts no hold: held items stay held until `/retry` or their fix merges. Alerts recorded outside the alarm step (the improver's `needs_person:` alerts, `auto_stopped`, `red_main`, `dead_letter`) are not changed; one of them recorded again after a dismissal is stored at once. No delivery change, no config key.
- **A stall that followed a host sleep, an abandoned interactive run and a pushback group raise no repeated-error alert (decision changed 2026-11-23; changes "Repeated error" under "The alarm step looks across items" below, and which runs the re-raise and the filed-pattern hold count; see History).** Before, the repeated-error check counted every failed run but improve runs, and the improver stored a `host_sleep:<key>` information alert for a stall group that followed a host sleep and a `needs_person:<key>` alert for every group that needs a person, pushback groups included. None of these is a failure a person must act on: the machine slept, the owner abandoned the session themselves, or the owner's own words are the pattern.
  - **Left out of the count.** The new repeated-error alert, the re-raise and the filed-pattern hold leave out a failed `agent_stalled` run that has a host sleep recorded with its run ID, and a failed `interactive` run with error code `abandoned` (`SESSION_ABANDONED`). Each such run is left out on its own; the rest of its pattern still counts at the same `alarm_repeat_count`. A stall with no host sleep on it, an `abandoned` failure of another run kind, and every other error code alert, re-raise and hold as before.
  - **One rule, read sparingly.** The sleep rule is the improver's (`sleptRuns` in `src/core/improver.ts`: the group's items' host sleeps, matched by run ID). The alarm step (`sleptStalls` in `src/core/alarms.ts`) reads host sleeps only for an `agent_stalled` pattern with at least `alarm_repeat_count` runs in the step's runs, so a poll with no such pattern reads none.
  - **The improver stores neither alert.** A stall group that followed a host sleep is still `skipped: host_sleep` in the improve report, and a pushback group that needs a person is still `skipped: needs_person` there; neither stores an alert. Other groups that need a person keep their `needs_person:<key>` alert (design 07-improve-report).
  - **Unchanged.** The stall rate in a stall alert's detail still counts every stall in the window, slept or not; the zero-token check and the child-restart check are unchanged. Stored `host_sleep` and `needs_person` alerts are left as they are (no backfill). Filing an improve pattern of abandoned runs is not changed here. No schema change, no config key.
- **A stall pattern alerts with its stall rate and holds no item (decision changed 2026-11-23; changes "Hold" under the re-raise, the filed-pattern hold and "Repeated error" below; see History).** Before, a repeated `agent_stalled` pattern held its items like any other: its new alert, its re-raise and its open filed item each held every item it hit, so one pattern held six items at once on 2026-11-22. A stall is now an infra failure that its own item's retry rules handle (design 05-restarts: backoff, and a hold only after three stalls in a row on that item). So a stall pattern's new repeated-error alert, its re-raise and its filed pattern hold no item; the alert and the re-raise are still stored, and the re-raise still comments on the filed item. The repeated-error alert of an `agent_stalled` pattern adds the stall rate to its detail: `<normalized detail>; stall rate: <stalls> of <agent runs> agent runs in the last <alarm_window_minutes> minutes stalled`, counting every stall and every finished agent run (`triage`, `implement`, `review`, `resolve`) in the alarm window (`stallRate` in `src/core/alarms.ts`). Its key stays `repeated_error:<pattern key>`. No schema change, no config key.
- **A run the pack grant check refused holds its item and alerts (new decision 2026-11-18; replaces none, adds a pattern to "The alarm step looks across items" below).** A run that the pack grant check refuses already fails with `pack_tool_refused`, and its message names each refused grant (`pack tools refused: <grant> <reason>`, design 11-packs). Until now nothing else reacted to it: it alerted only once `alarm_repeat_count` items hit it, so one unattended run that could not reach its tools looked like a silent no-op.
  - **Hold.** Each alarm step holds, at its first run, the item of every failed run of the last hour with `pack_tool_refused`, of any run kind (spec decision 1: every refused run, not only the controller's own). It is the existing hold (`blocked_on: human`, `blocked_reason: recurring_failure`, the improver's pattern key in the state change), so `/retry` lifts it, a lifted hold is not put back by the same run, and a second step writes no second hold. No fix item is filed for it, so the release never lifts it; only `/retry` does.
  - **Alert.** Each pattern stores one `repeated_error` alert, key `grant_refused:<pattern key>`, through `recordAlert` with the one-hour re-raise window (`RERAISE_WINDOW_MS`), so two steps store one. Its detail is the newest run's, scanned on the `ui` channel first; a flagged detail is stored as NULL.
  - Reads: the store and the injected Clock only; no model, forge or sandbox call. No schema change, no config key, no new alert pattern.
  - Not built: owner pre-approval of scoped grants per job (owner answer 1: hold and alert only); any change to the worker's refusal or to how an agent handles a `not_granted` tool result; retiring a scheduled job whose target is gone (no scheduled-job record exists yet; owner answer 2, propose retirement and approve with `/approve`, binds that follow-up).
- **A held item names its failure and whether a retry is enough (decision changed 2026-11-15; changes what "A filed pattern holds an item at its first matching run, for a person" below shows, not when it holds or releases).** Before, an item held as `recurring_failure` explained itself as "Waiting for a person: recurring_failure" and its decision box said "recurring failure" with no command. Now the explanation (`why.ts`) and the decision box and Needs-you reason (`need.ts`) read the item's last failed run and give one text (`heldFailureText`): the failure in the failures page's plain words (`FAILURE_DESCRIPTIONS`, the raw code when it has none) with its detail through the Withholder (run-outcome channel), then one sentence on retry. A stall, a usage or rate limit, or an infra failure (`retryClears` in `src/core/policy.ts`, on `failureClass`) says a plain retry is likely enough; any other failure is the task's own and says a plain retry will likely fail again, so something must change first. A held item with no failed run names no failure and says a person retries or rejects it. The command shown is `/retry`. The run list is read only for held items; no schema change.
- **The alarm step also checks the spend budgets (decision 2026-11-13, wi_199b; adds a pattern to "The alarm step looks across items" below, changes nothing else).** After its failure patterns, the step compares the day's and the week's known cost with `spend.daily_budget_usd` and `spend.weekly_budget_usd` and stores one `spend_budget` alert per period and threshold (80%, 100%), keyed with the period, so it never repeats in a period. A spend alert holds, pauses and stops nothing, and is not a failure alarm for auto mode (`isFailureAlert`). Design 06-spend holds the decision.
- **A filed item counts as open only while intake can still take it in, and `/retry` lifts a hold (decision changed 2026-11-11, issue #511 follow-up; changes "Hold" and "Release" in the entry below and "Release" under the re-raise).** Before, a filed item not in the store counted as open forever ("filed and not started yet"), and no command lifted a hold. On 2026-11-11 a pattern whose filed issue (#432) was filed without the intake label and closed by a person three days earlier, never taken in, held a new item, and only a merged fix could release it, so it stayed held.
  - **Open filed item.** In the store and not closed, or not in the store and filed less than `FILED_INTAKE_MS` (one hour, a constant in `src/core/alarms.ts`) ago. Intake takes a filed item in at its next poll, so one still missing after an hour never will be: filed without the intake label, refused, or closed before intake read it. The bound reads only the filing's time: no forge call, no new column. Why not record the source's close on the filed pattern: the GitHub source reports closes only of issues that carry the intake label, so an unlabelled filed issue's close never arrives, and a local filed item is in the store at once. A filed item closed within its first hour, before intake, can still hold items in that hour; `/retry` lifts those.
  - **`/retry` lifts a hold.** On an item held with `recurring_failure` (command phase `recurring_failure`, "held: its run failed like a known recurring failure"), `/retry`, `factory retry` and the dashboard's retry set `blocked_on: none`, state change `retry_requested`, and queue no run: the item's queued runs are claimed again. `+paths` is accepted after a failed implement run since 2026-11-26 (the first entry above). Every other command is refused, as at any phase it is not listed for; `/help` and the footers list `/retry` there from the command table.
  - **Once per run, for the re-raise too.** The re-raise now holds only the items whose failed runs no hold of the pattern took after they finished, as the first-run hold already did, so a lifted hold is not put back by the same run through either path. A new failed run of the pattern holds the item again.
  - Store: no schema change. Solo and enterprise use the same path on their one store; no config key.
- **A filed pattern holds an item at its first matching run, for a person (decision changed 2026-11-11, issue #511; changes "Hold" and "Release" under the re-raise below).** Before, a filed pattern's items kept running until the re-raise, after `alarm_repeat_count` new failures, and were held `blocked_on: upstream`. Now each alarm step (every controller poll), after the re-raise, holds the item of every failed run of the last hour whose pattern (the improver's `patternKey`) has an open filed item (in the store and not closed, or filed and not started yet: within an hour of filing since the first entry) and that finished after the filing: `blocked_on: human`, `blocked_reason: recurring_failure`, the pattern key in the state change detail. Every hold, this one and the re-raise's, is now for a person, so it shows in Needs you beside the re-raise alert, whose key `recurring:<key>` names the same pattern key.
  - **Once per run.** The hold is a conditional transition of an item nothing else blocks, so a second step, a retry or a second replica writes no second state change. A run whose item already had a hold of this pattern after the run finished holds nothing again, so a hold a person cleared is not put back by the same run.
  - **Release.** Unchanged: once the fix item closes with a merge sha its held items return to `blocked_on: none`. The release reads held items by `blocked_reason` (`listWorkItemsWhere` gained a `blocked_reason` filter), so holds stored as `upstream` before this change are released too. A filed item closed any other way holds nothing new, and nor does one not taken in within an hour of filing (see the first entry); its held items wait for `/retry`. An item filed as a fix is never held.
  - Store: no schema change for the hold; it reads `getFiledPattern`, `getWorkItemBySource` and the run's item's state changes, only for runs of a filed pattern. Solo and enterprise use the same path on their one store; no config key.
- **A recurring pattern re-raises and holds its items (decision changed 2026-11-10, issue #504; changes "Pause" and "Delivery" below).** Before, a pattern alerted once per 6 hours and nothing acted on it after that: on 2026-11-09 one pattern failed 36 runs over about four hours. Now each alarm step first re-raises every failure pattern that is already known, by its repeated-error alert or by its filed item (design §7, `controller_filed_patterns`), and that failed `alarm_repeat_count` more runs within the last hour (`RERAISE_WINDOW_MS`), counted after its last re-raise, else after it was first known. The pattern key is the improver's (`patternKey`: a hash of the code and normalized detail), so the alert, the filed item and the re-raise name one pattern.
  - **At most once an hour.** The re-raise is an alert (pattern `repeated_error`, key `recurring:<key>`, the count of new runs, the scanned detail) stored through `recordAlert` with a one-hour dedupe, so of two steps or replicas on a shared store exactly one stores it. Only that one acts on it. It shows in Needs you as any alert does, and stops auto mode as any failure alert does.
  - **Comment on the filed item.** When the pattern has a filed item, one comment, scanned (`comment` channel) first, says how many runs failed with it since filing and how many in the last hour, and that its items are held until the fix merges. It goes through the item's thread when the store holds the item, else straight to its source (the improver's path), marker `factory:recurring:<key>:<alert id>`, so a retry posts nothing twice.
  - **Hold.** Every open item the pattern hit in the last hour that nothing else blocks gets `blocked_on: human` (`upstream` until 2026-11-11, see the #511 entry above), `blocked_reason: recurring_failure`, the pattern key in the state change (a blocked reason, not a stage). `claimRun` skips queued runs of an item with that reason, so other items keep running. A held item still takes its runs' results: a failure queues its retry, which waits. An item filed as a fix is never held.
  - **Release.** Each alarm step reads the held items; one whose pattern's fix item is closed with a merge sha goes back to `blocked_on: none`, so its queued runs are claimed again for a retry. One conditional transition per item; safe to run twice. A pattern with no fix item (its draft needs a person, design §7) keeps its items held until a person acts on them: `/retry` lifts the hold (since 2026-11-11, see the first entry).
  - Store: no schema step and no new table. A pattern's last alert and last re-raise come from the newest 100 alerts (`listAlerts`, read once per step and only when some pattern is a candidate), its filing from `getFiledPattern`; `claimRun` reads the held item's `blocked_reason` in its claim query. Solo and enterprise use the same path on their one store.
- **The alarm step looks across items (new decision, 2026-11-07).** The controller handles each run's outcome on its own, and its retry and block rules see one item's step. The alarm step counts across items, so a burst gets noticed within one poll instead of waiting for the daily improve run (§7). It runs once per poll interval in the controller loop (`tickAlarms` for one step). It reads two things: the store's runs finished inside the window (`listRunsFinishedWithin`), and this host's supervisor status file. It calls no forge, LLM or sandbox. `detectAlarms` in `src/core/alarms.ts` is pure and finds three patterns:
  - **Repeated error.** Failed runs inside `alarm_window_minutes` that share an error code and a normalized detail (`normalizeDetail` from the improver: digit runs as `#`, hex ids as `<id>`, lower case), on at least `alarm_repeat_count` distinct items. Improve runs, stalls that followed a host sleep and abandoned interactive runs are left out (the 2026-11-23 decision at the top). The alert's count is the number of matching runs, and its detail is the normalized detail.
  - **Zero-token runs.** The newest `alarm_repeat_count` or more finished agent runs (`triage`, `implement`, `review`, `resolve`) inside the window all used no tokens (`runTokenCount`). One run with tokens breaks the streak. Update, improve, manual and interactive runs do not count.
  - **Child restarts.** At least `alarm_restart_count` unexpected child exits within 30 minutes, from the restart list in the supervisor status file. The alert's detail is the last exit reason.
- **One alert per pattern per 6 hours.** `FactoryStore.recordAlert(alert, 6 h)` runs in one transaction. It inserts the pattern's `controller_alert_patterns` row, or updates it only `WHERE last_alert_at <= now − 6 h` or the pattern was dismissed since its last alert (the 2026-11-24 entry at the top), and inserts the `controller_alerts` row only when one of those writes took effect. Two alarm steps at once, on one replica or several on a shared store, store one alert. The step is safe to run twice. The dedupe key (`pattern_key`) is the pattern plus a hash of the code and normalized detail, so it never holds the detail. Tables: SQLite migration 36. `listAlerts({ limit })` reads the newest alerts first.
- **Egress.** An alert's detail is scanned on the `ui` channel before it is stored (G5). If the scanner flags it, the alert keeps the code and count and stores `detail: NULL`. If the scanner throws, nothing is stored, so a detail is never stored unscanned. The log line names the pattern, the alert ID, the code and the count, never the detail.
- **Pause: only the existing `model_stall` pause.** A re-raise pauses nothing: it holds only its pattern's items (above). A new zero-token alert calls `pauseClaims(now + probe_interval_ms, "model_stall")`, the stall pause of `05-restarts.md`. The model probe then ends it when the cheap model answers. A deduped repeat starts no pause, so a probe that ended the pause is not undone every poll. The other two patterns pause nothing. There is no per-run-kind pause, and the alarm makes no automatic fix (no raised timeouts or retried runs).
- **Delivery: local, plus the filed item.** Alerts live in the store for the local UI to read through `listAlerts`; a re-raise also comments on the pattern's filed item (above). Slack and other GitHub delivery are follow-ups (no Slack plugin exists), and so is the digest (RFC 0019 P3). The alarm step has no UI view of its own: the Needs you and why-it-waits surfaces (#360, #368) are where alerts are meant to show, and that wiring is a follow-up change in `src/ui/`.
- **Restart history is host-local.** The git-worktree updater writes the last 10 unexpected child exits (`restarts: [{ at, reason }]`, oldest first; reason: the child's error, else `exit code N`) into `<state_dir>/supervisor.json`. The controller reads that file on its own host (`readRestarts` in `src/compose.ts`; no file or no list means no restarts). Solo default: the one host's file is the whole picture. Enterprise gap: a replica on another host does not see this host's restarts, so a crash loop alerts only on its own host. A follow-up is to keep restart history in the store. In in-place or `none` updater mode no list is written and the restart alarm never fires.
- **Three settings, settable live.** `alarm_repeat_count` (default 3), `alarm_window_minutes` (default 60) and `alarm_restart_count` (default 5). They are top-level `factory.config.json` keys (positive integers, or startup fails) and `factory settings set` keys, applied at the next alarm step with no restart (see `08-settings.md`). Why settings and not constants: the right threshold depends on the item rate. A busy enterprise factory sees 3 matching failures on 3 items in an hour as normal noise, while a solo developer may want 2. A crash loop during an update differs per host. The 6-hour dedupe and the 30-minute restart window stay constants (`ALERT_DEDUPE_MS`, `RESTART_WINDOW_MS`), since nothing so far calls for tuning them. No learned or automatic thresholds.
