# 5. Coordination: alarms

- **A filed pattern holds an item at its first matching run, for a person (decision changed 2026-11-11, issue #511; changes "Hold" and "Release" under the re-raise below).** Before, a filed pattern's items kept running until the re-raise, after `alarm_repeat_count` new failures, and were held `blocked_on: upstream`. Now each alarm step (every controller poll), after the re-raise, holds the item of every failed run of the last hour whose pattern (the improver's `patternKey`) has an open filed item (in the store and not closed, or filed and not started yet) and that finished after the filing: `blocked_on: human`, `blocked_reason: recurring_failure`, the pattern key in the state change detail. Every hold, this one and the re-raise's, is now for a person, so it shows in Needs you beside the re-raise alert, whose key `recurring:<key>` names the same pattern key.
  - **Once per run.** The hold is a conditional transition of an item nothing else blocks, so a second step, a retry or a second replica writes no second state change. A run whose item already had a hold of this pattern after the run finished holds nothing again, so a hold a person cleared is not put back by the same run.
  - **Release.** Unchanged: once the fix item closes with a merge sha its held items return to `blocked_on: none`. The release reads held items by `blocked_reason` (`listWorkItemsWhere` gained a `blocked_reason` filter), so holds stored as `upstream` before this change are released too. A filed item closed any other way holds nothing new. An item filed as a fix is never held.
  - Store: no schema change for the hold; it reads `getFiledPattern`, `getWorkItemBySource` and the run's item's state changes, only for runs of a filed pattern. Solo and enterprise use the same path on their one store; no config key.
- **A recurring pattern re-raises and holds its items (decision changed 2026-11-10, issue #504; changes "Pause" and "Delivery" below).** Before, a pattern alerted once per 6 hours and nothing acted on it after that: on 2026-11-09 one pattern failed 36 runs over about four hours. Now each alarm step first re-raises every failure pattern that is already known, by its repeated-error alert or by its filed item (design §7, `controller_filed_patterns`), and that failed `alarm_repeat_count` more runs within the last hour (`RERAISE_WINDOW_MS`), counted after its last re-raise, else after it was first known. The pattern key is the improver's (`patternKey`: a hash of the code and normalized detail), so the alert, the filed item and the re-raise name one pattern.
  - **At most once an hour.** The re-raise is an alert (pattern `repeated_error`, key `recurring:<key>`, the count of new runs, the scanned detail) stored through `recordAlert` with a one-hour dedupe, so of two steps or replicas on a shared store exactly one stores it. Only that one acts on it. It shows in Needs you as any alert does, and stops auto mode as any failure alert does.
  - **Comment on the filed item.** When the pattern has a filed item, one comment, scanned (`comment` channel) first, says how many runs failed with it since filing and how many in the last hour, and that its items are held until the fix merges. It goes through the item's thread when the store holds the item, else straight to its source (the improver's path), marker `factory:recurring:<key>:<alert id>`, so a retry posts nothing twice.
  - **Hold.** Every open item the pattern hit in the last hour that nothing else blocks gets `blocked_on: human` (`upstream` until 2026-11-11, see the first entry), `blocked_reason: recurring_failure`, the pattern key in the state change (a blocked reason, not a stage). `claimRun` skips queued runs of an item with that reason, so other items keep running. A held item still takes its runs' results: a failure queues its retry, which waits. An item filed as a fix is never held.
  - **Release.** Each alarm step reads the held items; one whose pattern's fix item is closed with a merge sha goes back to `blocked_on: none`, so its queued runs are claimed again for a retry. One conditional transition per item; safe to run twice. A pattern with no fix item (its draft needs a person, design §7) keeps its items held until a person acts on them: no command lifts the hold yet (a follow-up in `src/core/commands.ts`).
  - Store: no schema step and no new table. A pattern's last alert and last re-raise come from the newest 100 alerts (`listAlerts`, read once per step and only when some pattern is a candidate), its filing from `getFiledPattern`; `claimRun` reads the held item's `blocked_reason` in its claim query. Solo and enterprise use the same path on their one store.
- **The alarm step looks across items (new decision, 2026-11-07).** The controller handles each run's outcome on its own, and its retry and block rules see one item's step. The alarm step counts across items, so a burst gets noticed within one poll instead of waiting for the daily improve run (§7). It runs once per poll interval in the controller loop (`tickAlarms` for one step). It reads two things: the store's runs finished inside the window (`listRunsFinishedWithin`), and this host's supervisor status file. It calls no forge, LLM or sandbox. `detectAlarms` in `src/core/alarms.ts` is pure and finds three patterns:
  - **Repeated error.** Failed runs inside `alarm_window_minutes` that share an error code and a normalized detail (`normalizeDetail` from the improver: digit runs as `#`, hex ids as `<id>`, lower case), on at least `alarm_repeat_count` distinct items. Improve runs are left out. The alert's count is the number of matching runs, and its detail is the normalized detail.
  - **Zero-token runs.** The newest `alarm_repeat_count` or more finished agent runs (`triage`, `implement`, `review`, `resolve`) inside the window all used no tokens (`runTokenCount`). One run with tokens breaks the streak. Update, improve, manual and interactive runs do not count.
  - **Child restarts.** At least `alarm_restart_count` unexpected child exits within 30 minutes, from the restart list in the supervisor status file. The alert's detail is the last exit reason.
- **One alert per pattern per 6 hours.** `FactoryStore.recordAlert(alert, 6 h)` runs in one transaction. It inserts the pattern's `controller_alert_patterns` row, or updates it only `WHERE last_alert_at <= now − 6 h`, and inserts the `controller_alerts` row only when one of those writes took effect. Two alarm steps at once, on one replica or several on a shared store, store one alert. The step is safe to run twice. The dedupe key (`pattern_key`) is the pattern plus a hash of the code and normalized detail, so it never holds the detail. Tables: SQLite migration 36 and MySQL step `0036-alarms.sql` (0025 to 0035 were taken when this landed). `listAlerts({ limit })` reads the newest alerts first.
- **Egress.** An alert's detail is scanned on the `ui` channel before it is stored (G5). If the scanner flags it, the alert keeps the code and count and stores `detail: NULL`. If the scanner throws, nothing is stored, so a detail is never stored unscanned. The log line names the pattern, the alert ID, the code and the count, never the detail.
- **Pause: only the existing `model_stall` pause.** A re-raise pauses nothing: it holds only its pattern's items (above). A new zero-token alert calls `pauseClaims(now + probe_interval_ms, "model_stall")`, the stall pause of `05-restarts.md`. The model probe then ends it when the cheap model answers. A deduped repeat starts no pause, so a probe that ended the pause is not undone every poll. The other two patterns pause nothing. There is no per-run-kind pause, and the alarm makes no automatic fix (no raised timeouts or retried runs).
- **Delivery: local, plus the filed item.** Alerts live in the store for the local UI to read through `listAlerts`; a re-raise also comments on the pattern's filed item (above). Slack and other GitHub delivery are follow-ups (no Slack plugin exists), and so is the digest (RFC 0019 P3). The alarm step has no UI view of its own: the Needs you and why-it-waits surfaces (#360, #368) are where alerts are meant to show, and that wiring is a follow-up change in `src/ui/`.
- **Restart history is host-local.** The git-worktree updater writes the last 10 unexpected child exits (`restarts: [{ at, reason }]`, oldest first; reason: the child's error, else `exit code N`) into `<state_dir>/supervisor.json`. The controller reads that file on its own host (`readRestarts` in `src/compose.ts`; no file or no list means no restarts). Solo default: the one host's file is the whole picture. Enterprise gap: a replica on another host does not see this host's restarts, so a crash loop alerts only on its own host. A follow-up is to keep restart history in the store. In in-place or `none` updater mode no list is written and the restart alarm never fires.
- **Three settings, settable live.** `alarm_repeat_count` (default 3), `alarm_window_minutes` (default 60) and `alarm_restart_count` (default 5). They are top-level `factory.config.json` keys (positive integers, or startup fails) and `factory settings set` keys, applied at the next alarm step with no restart (see `08-settings.md`). Why settings and not constants: the right threshold depends on the item rate. A busy enterprise factory sees 3 matching failures on 3 items in an hour as normal noise, while a solo developer may want 2. A crash loop during an update differs per host. The 6-hour dedupe and the 30-minute restart window stay constants (`ALERT_DEDUPE_MS`, `RESTART_WINDOW_MS`), since nothing so far calls for tuning them. No learned or automatic thresholds.

## History

- **Hold at the first matching run, for a person** (decision changed 2026-11-11, issue #511). Before: a filed pattern's items were held only by the re-raise, after `alarm_repeat_count` new failures within the hour, and every hold was `blocked_on: upstream`, so it did not ask a person; the release read `blocked_on: upstream` items.
- **Re-raise and hold** (decision changed 2026-11-10, issue #504). Before: a pattern stored one alert per 6 hours and nothing else; no alert re-raised a pattern that kept failing, nothing commented on its filed item, the items it hit kept being retried, and delivery was local only.
- **Alarm step** (new decision, 2026-11-07). Before: nothing looked across items. Repeated error codes, zero-token runs and child crash loops were not counted anywhere. The supervisor status file showed only the current child state, and only the daily improve run grouped failures, a day late.
