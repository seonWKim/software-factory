# 9. Status page: dashboard app and read API

- **Dashboard app and read API (new decision, 2026-11-02, issue #124; steps 1 and 2 of the dashboard plan).** The status UI moves to a client app. **Stack:** Vite, React, TypeScript, Tailwind, shadcn/ui (components copied into `web/` as plain files, not a dependency), lucide icons and TanStack Query; the system font stack, nothing from a CDN. The app lives in `web/`, `npm run build` removes `web/dist/` (git-ignored) and builds the app into it after the server, so `/app/` serves the shell (it answers 503 only when the app is not built), and `isCodePath` counts `web/` as code so the updater rebuilds on a change there. Once the server-rendered pages are retired (step 6, `src/ui/html.ts` and `src/ui/pages.ts`), the app supersedes them; until step 3 it is served at `/app/` and the old pages stay at `/` and `/items/<id>` unchanged (same HTML, same CSP).
  - **Read-only JSON API** (`src/ui/api.ts`), `GET`/`HEAD` only, the same Host guard, `cache-control: no-store` and security headers as the page, errors as JSON `{ error }` (404 for an unknown path or item id, 400 for an unknown filter value): `/api/v1/overview` (items per stage, human-blocked count, running and queued run counts, runs succeeded and failed and tokens in the last 24 h: the page's numbers), `/api/v1/items` (the page's ranked list with the same filters `state`, `stage`, `tier`, `kind`, `unblocks`, `closed`, `q`, plus the facet counts; the ranking moved to `src/ui/list.ts` so the page and the API share it), `/api/v1/items/:id` (facts, timeline, runs; each run has an `attempts` array, see below), `/api/v1/runs` (running then queued runs: kind, item id, attempt, owner, last heartbeat, start, lease expiry; never the fencing token), `/api/v1/queue` (queued runs, oldest first), `/api/v1/workers` (`workers`: each current lease owner once, by ID, with its running count; history is step 5. `processes`, since 2026-11-07: one entry per live worker process, see below) and `/api/v1/health` (the same `HealthMonitor.report` as `/api/health`, which keeps its response). Every free-text value (titles, blocked reasons, state-change values and reasons, actor and owner ids, run errors) passes through the `Withholder` as plain text or `[withheld: <rule>]`. The API calls only store read methods; no store method, interface, migration or schema changed. Orphaned-run rules (heartbeat older than 2 × `heartbeat_ms`, or lease expired) belong to the floor view (step 3), which applies them to the raw owner, heartbeat and lease expiry returned here.
  - **Run attempts in the item API (decision changed 2026-11-07, issue #207).** Each entry of `runs` in `/api/v1/items/:id` keeps its fields and values and adds `attempts`: the run's attempt records (§6, one per claim) in attempt order, each `{ attempt, worker_id, status, started_at, finished_at, error_code, failure_class, tokens }`. `worker_id` and `error_code` pass the `Withholder`; the claim's lease token is never returned. Attempts are listed under their run row, not grouped by retry step. `/api/v1/runs` and every other route are unchanged. The API still calls only store read methods; the new one is `listRunAttempts`.
  - **`processes` on `/api/v1/workers` (new field, 2026-11-07, issue #209; design §5 Worker slots reported per process).** One entry per worker process whose store row is at most `lease_ms` old, idle processes included, ordered by host then pid: `process_id` (`<host>:<pid>`), `pid`, `host`, `slots` (the live count; 0 while draining), `max_slots`, `busy` (slots holding a run), `idle` (`slots - busy`, at least 0), `index_base`, `started_at`, `reported_at`, and `runs`: the running runs whose lease owner is one of its worker loops (`id`, `kind`, `work_item_id`, `worker_id`, `started_at`). `process_id`, `host` and `worker_id` pass through the `Withholder`. The `workers` array is unchanged. The field reads `listWorkerProcesses`, a new store read; this replaces "no store method changed" for this route only. It is on `/api/v1/workers`, not `/api/health`, because health is doctor output. The read is a report, never a gate: when it fails (a MySQL database without step 19, say) the route still answers 200 with `workers` as usual, `processes: []` and `processes_error` (the error text, through the `Withholder`).
  - **Serving `/app/`** (`src/ui/app.ts`): files from `web/dist`; any other path gets `index.html` (client routing), except a missing file under `assets/`, which is a 404. A path that decodes to `.`/`..`, a slash, a backslash or a NUL, a dotfile, or a file whose real path is outside `web/dist` is a 404. No built app: 503 "run npm run build", and `/` keeps working. Its own CSP: `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'` (no `unsafe-inline`, no hash; so no inline `style=` attributes in the app either). Same Host and method guards (errors as text). The app's fetches go only to `/api/v1/*`; it polls every 3 s while the document is visible, and its light/dark choice stays in the browser.
  - **App shell (step 2, issue #160; 2026-11-07).** `web/` holds the app: `web/vite.config.ts` (base `/app/`, no module-preload polyfill, nothing inlined), `web/tsconfig.json` (DOM and JSX; `npm run typecheck` runs it after the server's), one root `package.json` and `node_modules`. The shell: a sidebar (Floor, Work items, Workers, Queue, Health, Settings; every page but the shell is a placeholder naming the step that brings it), a top bar with "Needs you (N)" from `/api/v1/overview`, "updated Ns ago", Refresh and a light/dark toggle (the choice in `localStorage` key `sf-theme`, else the system preference). TanStack Query polls every 3 s and not in a hidden tab; nothing animates under `prefers-reduced-motion`. shadcn's Button is a plain file (`web/src/components/ui/button.tsx`) without class-variance-authority. Web tests are `tests/*.test.tsx` with `@vitest-environment jsdom` in the file, so every other test keeps the node environment. Decision changed: none; this builds the recorded stack.

  - **The app is the default (steps 3–5, 2026-11-07).** `/` answers 302 to `/app/`; the server-rendered page moved to `/classic` (its own links and filter form point there; `/items/<id>` is unchanged) and stays until the app covers everything it shows. Pages: **Floor** (the supervisor banner, then Needs you (ready to merge, needs approval, needs a human, stuck), Running now, the first 10 queued runs, then the last-24-h numbers), **Work items** (the API's ranked list with the state filter and search; an item page under `/app/items/<id>` with its facts, runs with their errors and the timeline), **Workers** (lease owners with runs, and the running runs), **Queue** (every queued run in claim order, with when it may start), **Health** (the doctor checks, failing first; read every 30 s, not 3 s) and **Settings** (read-only: points at `factory settings`). `/api/v1/overview` now also returns `factory`, the supervisor status the banner shows (absent without a status function, null when stopped). Client routing is `history.pushState` under `/app/` (`web/src/nav.tsx`), no router dependency. Commands (approve, revise, retry, …) are not in the app yet: they stay on the source until local-first commands land (a separate issue).

  - **Data page and raw table reads (new decision, 2026-11-07, issue #239).** A read-only debugging view of every store table, so what the factory did no longer needs a hand-written query. **Store:** two new `FactoryStore` reads, implemented once in `SqlFactoryStore` for SQLite and MySQL: `listTables()` (every table of the backend's schema from the database's own catalog: `sqlite_master` with `pragma_table_info`, or `information_schema` on MySQL; each with its row count, columns, primary key and `order_by`) and `listTableRows({ table, limit, offset, filter })` (one page, newest first, with the total after the filter; `limit` defaults to 50 and is capped at 200; null, with no row read, for a table or filter column the catalog lacks). Order: the first of `created_at`, `at`, `started_at`, `updated_at` the table has, then its primary key, all descending; a table with neither keeps the database's order. Names reach SQL only after they are found in the catalog (and match a plain identifier); the filter value is always a bound parameter. No migration, schema or write path changed. **API** (`src/ui/data.ts`, routed from `src/ui/api.ts`, `GET`/`HEAD` only like every route): `/api/v1/data/tables` (`name`, `rows`, `columns`, `hidden`) and `/api/v1/data/tables/:name?page=&limit=&col=&val=` (`rows`, `total`, `page`, `limit`, `columns`, `hidden`, `order_by`, `filter`, and `run_items`: run id → owning item for the run ids on the page). The allow-list is the store's catalog: the route reads `listTables` first, so an unknown table or column is a 404 before any row is read; 400 for a bad `page`/`limit` or `col` without `val`. **Hidden columns**, listed once in `HIDDEN_COLUMNS` (`src/ui/data.ts`): `runs.lease_token`, `listener_leases.token`, `run_attempts.lease_token`, `link_codes.code_hash`. They leave only as `[hidden]`, and a `col=` naming one is a 404 with no store call, so a hidden value cannot be probed by filtering. Every text cell (and the echoed filter value) passes the API's `Withholder` on the same channel as the other routes; numbers and nulls pass as they are. **Page** (`web/src/views/data.tsx`): a "Data" entry in its own Tools group of the sidebar, after Settings (the Pages group is unchanged); the table list with row counts on the left, one page of rows on the right with a sticky header and horizontal scroll, an exact-value filter, Previous/Next, `wi_…` values linked to the item and `run_…` values to the item that owns the run, Copy row as JSON (the values the API gave, markers included, never a raw value), and cells over 300 characters cut on the page with "Show all" for that cell (the API returns the full text, so no second read). It never polls: no interval, no refetch on focus; only the top bar's Refresh reads again. Out of scope: editing or exporting rows, free-form SQL, shared-storage transcripts. Residual risk: the Withholder catches only what the egress scanner detects, so free-form JSON such as run input can show prompt text that is not secret-like. Decision changed: "the API calls only store read methods; no store method changed" now has two more reads, `listTables` and `listTableRows`, used by the data routes only.

## History

- **Run attempts in the item API** (decision changed 2026-11-07, issue #207). Replaces: "`/api/v1/items/:id` (facts, timeline, runs)" with one row per run and no record of its earlier claims, and "no store method, interface, migration or schema changed" (the item route now also reads `listRunAttempts`).
- **`/api/v1/workers`** (field added 2026-11-07, issue #209). Before: it returned only `workers`, the lease owners of running runs, so an idle process did not appear and no slot count was shown.
- **Where `/` goes** (changed 2026-11-07). Before: `/` served the server-rendered page and the app was only at `/app/`, with placeholder pages.
- **Store reads behind the API** (changed 2026-11-07, issue #239). Before: the API had only curated views, and tables such as `claim_decisions`, `file_conflicts` and `run_attempts` had no view at all; the store had no generic table read.
