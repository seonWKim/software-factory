# 9. Status page: dashboard app and read API

- **Dashboard app and read API (new decision, 2026-11-02, issue #124; steps 1 and 2 of the dashboard plan).** The status UI moves to a client app. **Stack:** Vite, React, TypeScript, Tailwind, shadcn/ui (components copied into `web/` as plain files, not a dependency), lucide icons and TanStack Query; the system font stack, nothing from a CDN. The app lives in `web/`, `npm run build` builds the app into `web/dist/` (git-ignored) after the server, through a staging folder swapped in at the end (`08-self-update.md`), so `/app/` serves the shell (it answers 503 only when the app is not built), and `isCodePath` counts `web/` as code so the updater rebuilds on a change there. Once the server-rendered pages are retired (step 6, `src/ui/html.ts` and `src/ui/pages.ts`), the app supersedes them; until step 3 it is served at `/app/` and the old pages stay at `/` and `/items/<id>` unchanged (same HTML, same CSP).
  - **JSON API** (`src/ui/api.ts`), `GET`/`HEAD` on every route, plus three writes, `POST /api/v1/settings`, `POST /api/v1/items/:id/commands` and `POST /api/v1/pauses/resume` (below); the same Host guard, `cache-control: no-store` and security headers as the page, errors as JSON `{ error }` (404 for an unknown path or item id, 400 for an unknown filter value): `/api/v1/overview` (items per stage, human-blocked count, running and queued run counts, runs succeeded and failed and tokens in the last 24 h: the page's numbers), `/api/v1/items` (the page's ranked list with the same filters `state`, `stage`, `tier`, `kind`, `unblocks`, `closed`, `q`, plus the facet counts; the ranking moved to `src/ui/list.ts` so the page and the API share it), `/api/v1/items/:id` (facts, timeline, runs; each run has an `attempts` array, see below), `/api/v1/runs` (running then queued runs: kind, item id, attempt, owner, last heartbeat, start, lease expiry; never the fencing token), `/api/v1/queue` (queued runs, oldest first), `/api/v1/settings` (the Settings page's read model and the per-process CSRF token; see `08-settings.md`), `/api/v1/workers` (`workers`: each current lease owner once, by ID, with its running count; history is step 5. `processes`, since 2026-11-07: one entry per live worker process, see below) and `/api/v1/health` (the same `HealthMonitor.report` as `/api/health`, which keeps its response). Every free-text value (titles, blocked reasons, state-change values and reasons, actor and owner ids, run errors) passes through the `Withholder` as plain text or `[withheld: <rule>]`. The API calls only store read methods; no store method, interface, migration or schema changed. Orphaned-run rules (heartbeat older than 2 × `heartbeat_ms`, or lease expired) belong to the floor view (step 3), which applies them to the raw owner, heartbeat and lease expiry returned here.
  - **Run attempts in the item API (decision changed 2026-11-07, issue #207).** Each entry of `runs` in `/api/v1/items/:id` keeps its fields and values and adds `attempts`: the run's attempt records (§6, one per claim) in attempt order, each `{ attempt, worker_id, status, started_at, finished_at, error_code, failure_class, tokens }`. `worker_id` and `error_code` pass the `Withholder`; the claim's lease token is never returned. Attempts are listed under their run row, not grouped by retry step. `/api/v1/runs` and every other route are unchanged. The API still calls only store read methods; the new one is `listRunAttempts`.
  - **`processes` on `/api/v1/workers` (new field, 2026-11-07, issue #209; design §5 Worker slots reported per process).** One entry per worker process whose store row is at most `lease_ms` old, idle processes included, ordered by host then pid: `process_id` (`<host>:<pid>`), `pid`, `host`, `slots` (the live count; 0 while draining), `max_slots`, `busy` (slots holding a run), `idle` (`slots - busy`, at least 0), `index_base`, `started_at`, `reported_at`, and `runs`: the running runs whose lease owner is one of its worker loops (`id`, `kind`, `work_item_id`, `worker_id`, `started_at`). `process_id`, `host` and `worker_id` pass through the `Withholder`. The `workers` array is unchanged. The field reads `listWorkerProcesses`, a new store read; this replaces "no store method changed" for this route only. It is on `/api/v1/workers`, not `/api/health`, because health is doctor output. The read is a report, never a gate: when it fails (a MySQL database without step 19, say) the route still answers 200 with `workers` as usual, `processes: []` and `processes_error` (the error text, through the `Withholder`).
  - **Serving `/app/`** (`src/ui/app.ts`): files from `web/dist`; any other path gets `index.html` (client routing), except a missing file under `assets/`, which is a 404. A path that decodes to `.`/`..`, a slash, a backslash or a NUL, a dotfile, or a file whose real path is outside `web/dist` is a 404. No built app: 503 "run npm run build", and `/` keeps working. Its own CSP: `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'` (no `unsafe-inline`, no hash; so no inline `style=` attributes in the app either). Same Host and method guards (errors as text). The app's fetches go only to `/api/v1/*`; it polls every 3 s while the document is visible, and its light/dark choice stays in the browser.
  - **App shell (step 2, issue #160; 2026-11-07).** `web/` holds the app: `web/vite.config.ts` (base `/app/`, no module-preload polyfill, nothing inlined), `web/tsconfig.json` (DOM and JSX; `npm run typecheck` runs it after the server's), one root `package.json` and `node_modules`. The shell: a sidebar (Floor, Work items, Workers, Queue, Health, Settings; every page but the shell is a placeholder naming the step that brings it), a top bar with "Needs you (N)" from `/api/v1/overview`, "updated Ns ago", Refresh and a light/dark toggle (the choice in `localStorage` key `sf-theme`, else the system preference). TanStack Query polls every 3 s and not in a hidden tab; nothing animates under `prefers-reduced-motion`. shadcn's Button is a plain file (`web/src/components/ui/button.tsx`) without class-variance-authority. Web tests are `tests/*.test.tsx` with `@vitest-environment jsdom` in the file, so every other test keeps the node environment. Decision changed: none; this builds the recorded stack.

  - **The app is the default (steps 3–5, 2026-11-07).** `/` answers 302 to `/app/`; the server-rendered page moved to `/classic` (its own links and filter form point there; `/items/<id>` is unchanged) and stays until the app covers everything it shows. Pages: **Floor** (the supervisor banner, then Needs you (ready to merge, needs approval, needs a human, stuck), Running now, the first 10 queued runs, then the last-24-h numbers), **Work items** (the API's ranked list with the state filter and search; an item page under `/app/items/<id>` with its facts, runs with their errors and the timeline), **Workers** (lease owners with runs, and the running runs), **Queue** (every queued run in claim order, with when it may start), **Health** (the doctor checks, failing first; read every 30 s, not 3 s) and **Settings** (see below). `/api/v1/overview` now also returns `factory`, the supervisor status the banner shows (absent without a status function, null when stopped). Client routing is `history.pushState` under `/app/` (`web/src/nav.tsx`), no router dependency. The item page also has the item's command buttons (below, issue #228).

  - **Settings page writes (decision changed 2026-11-07, issue #236).** The Settings page (`web/src/views/settings.tsx`) shows a row per settable key with its value, source, file value and "applies at", a number field, a switch (a plain button with `role=switch`, `web/src/components/ui/switch.tsx`, no new dependency), a text field per tier for `models` (no model picker: the factory has no model list) or a JSON field for `model_by`, a reset button when an override exists, and for `max_attempts`, `max_diff_lines` and `max_diff_files` a row for the configured repo.   - **Claim pauses and "Resume now" (decision changed 2026-11-07, issue #291; design §5 Restarts).** `GET /api/v1/pauses` (`src/ui/pause-api.ts`, store reads only) returns `pauses`, each claim pause in effect (`rate_limit`, `forge_auth`, `preflight_access`, `model_stall`, in that order) with `name` and `ends_at` (for `model_stall` the next probe time), and `csrf_token` (the Settings token; null when the resume route is not wired). `POST /api/v1/pauses/resume` with `{ "name": <pause> }` ends one through `endClaimPause`, the same code `factory resume <name>` runs, and answers `{ name, ended, pauses }`; a second resume answers `ended: false`. Guards, in order, all before any store write: Host, Origin equal to the Host's own origin, Content-Type `application/json`, the CSRF token in `x-csrf-token`, the body size, JSON, a known pause name (400 otherwise), then the owner check: the page's factory user (a `local` account linked to a user, else `cli_user`; none is a 403) must be allowed `approve_spec` on the configured project (403 otherwise, nothing written). The UI process still makes no forge call: the check runs the configured auth plugin over the local grants only (a remote grant such as `github-permission` is left out there, so grant the role in `permissions.static` or use `factory resume`). Each resume writes one log line with the factory user ID. **App:** the Floor and Health pages show a "Claim pauses" section above their other sections while any pause is in effect: each pause's name, what it stops and when it ends, and a "Resume now" button that posts with the token; the endpoint's error shows next to that button, and a resumed pause leaves the list. No section while none is in effect. `/classic` is unchanged.

  - **Data page and raw table reads (new decision, 2026-11-07, issue #239).** A read-only debugging view of every store table, so what the factory did no longer needs a hand-written query. **Store:** two new `FactoryStore` reads, implemented once in `SqlFactoryStore` for SQLite and MySQL: `listTables()` (every table of the backend's schema from the database's own catalog: `sqlite_master` with `pragma_table_info`, or `information_schema` on MySQL; each with its row count, columns, primary key and `order_by`) and `listTableRows({ table, limit, offset, filter })` (one page, newest first, with the total after the filter; `limit` defaults to 50 and is capped at 200; null, with no row read, for a table or filter column the catalog lacks). Order: the first of `created_at`, `at`, `started_at`, `updated_at` the table has, then its primary key, all descending; a table with neither keeps the database's order. Names reach SQL only after they are found in the catalog (and match a plain identifier); the filter value is always a bound parameter. No migration, schema or write path changed. **API** (`src/ui/data.ts`, routed from `src/ui/api.ts`, `GET`/`HEAD` only like every route): `/api/v1/data/tables` (`name`, `rows`, `columns`, `hidden`) and `/api/v1/data/tables/:name?page=&limit=&col=&val=` (`rows`, `total`, `page`, `limit`, `columns`, `hidden`, `order_by`, `filter`, and `run_items`: run id → owning item for the run ids on the page). The allow-list is the store's catalog: the route reads `listTables` first, so an unknown table or column is a 404 before any row is read; 400 for a bad `page`/`limit` or `col` without `val`. **Hidden columns**, listed once in `HIDDEN_COLUMNS` (`src/ui/data.ts`): `runs.lease_token`, `listener_leases.token`, `run_attempts.lease_token`, `link_codes.code_hash`. They leave only as `[hidden]`, and a `col=` naming one is a 404 with no store call, so a hidden value cannot be probed by filtering. Every text cell (and the echoed filter value) passes the API's `Withholder` on the same channel as the other routes; numbers and nulls pass as they are. **Page** (`web/src/views/data.tsx`): a "Data" entry in its own Tools group of the sidebar, after Settings (the Pages group is unchanged); the table list with row counts on the left, one page of rows on the right with a sticky header and horizontal scroll, an exact-value filter, Previous/Next, `wi_…` values linked to the item and `run_…` values to the item that owns the run, Copy row as JSON (the values the API gave, markers included, never a raw value), and cells over 300 characters cut on the page with "Show all" for that cell (the API returns the full text, so no second read). It never polls: no interval, no refetch on focus; only the top bar's Refresh reads again. Out of scope: editing or exporting rows, free-form SQL, shared-storage transcripts. Residual risk: the Withholder catches only what the egress scanner detects, so free-form JSON such as run input can show prompt text that is not secret-like. Decision changed: "the API calls only store read methods; no store method changed" now has two more reads, `listTables` and `listTableRows`, used by the data routes only.

  - **Item tables: plugins, issue and PR links (new decision, 2026-11-07, issue #240).** `/api/v1/overview` returns `plugins: { issues, prs }`, each `"github"` or `null`: `issues` is `"github"` when the `github-issues` source is selected (`main.ts` passes it in the optional `UiDeps.plugins`, default both null), and `prs` follows the same condition because PRs are read only through that adapter today (no separate PR host setting). Each row of `/api/v1/items` has `issue: { number, url }`, or `null` for an adopted PR (recognised on the server from a `/pull/` source link). `pr_url` (items and item routes) is built from the project's stored label (`github.com/owner/name`), never the key; with no stored label it is `null` and the app shows the number without a link. In Needs you and Work items the title links to `/app/items/<id>` (the item id when there is no title) and the Item cell has no GitHub link; the Issue and PR columns (`#N` linked, or a dash) show only when the matching plugin is `"github"`, so with no GitHub source no link in those tables points to github.com. Running now and Queue keep their title component and its GitHub link on the source id. `/classic` is unchanged.
  - **Unreviewed merges in the app (new decision, 2026-11-07, issue #268).** `GET /api/v1/unreviewed-merges?limit=N` returns the stored `unreviewed_merges` rows, newest first: default 50, at most 200 (a larger value is capped, a non-numeric or zero one is 400). Each row: `project` (the stored label, `unknown project` when none; never the key), `pr_number`, `pr_url`, `merge_sha` (first 7 characters), `merged_by` (the stored user ID, `unknown` when null; no display name) and `recorded_at`. `pr_url` is `https://<label>/pull/<n>` only when `plugins.prs` is `"github"` and a label is stored, else `null` and the app shows the number alone. Every string passes the `Withholder`; the sha is scanned whole, then shortened. `/api/v1/overview` adds `unreviewed_merges_7d`, the count of rows recorded in the last 7 days, from the new store read `countUnreviewedMergesSince(since)` (SQL store only). The Floor shows "N PRs merged without review in the last 7 days" with a link to Health, hidden at 0; the Health page has a "Merged without review" table (PR, merged by, merge commit, when), newest first. Read-only: no schema, migration or recording change; no way to mark a merge reviewed. `/classic` and factory stats are unchanged.

  - **Item commands from the page (decision changed 2026-11-07, issue #227).** A second write route, `POST /api/v1/items/:id/commands` (`src/ui/commands.ts`), records one app command request (`app_command_requests`, design §4 app requests) for the controller to apply on its next tick; the route itself never applies a command. Body: JSON `{ command, note? }`; `command` is any item command but `help` and the account command `link` (`approve`, `reject`, `revise`, `retry`, `resolve`, `budget`, `verdict`); `note` is optional, at most 2000 characters, trimmed, and required (non-blank) for `reject` and `revise`. The row's actor is `ui.user_id` from `factory.config.json` (a factory user ID, optional, unset in the checked-in config; an empty or non-string value stops startup naming the key), so the controller's permission check is that user's; args are `{ work_item_id, note? }` and the key is `app:<random UUID>`. **Token:** one random token per UI process (32 bytes, base64url), made at startup in `buildUiParts`, shared with the Settings write, held only in memory (never in a file, the store or a log) and new after every restart; the page reads it from `GET /api/v1/session` (`{ as_of, csrf_token, commands_enabled }`; 404 when the route is not wired), which is behind the same Host guard as every route, and sends it in `x-csrf-token`. **Checks, in order, each before any store write:** a Host other than `127.0.0.1`/`localhost` 403; an Origin missing or not `http://<Host>` 403; a Content-Type other than `application/json` 415; a missing or wrong token 403; no `ui.user_id` 503; a body over 16 KB 413; a body that is not JSON 400; an unknown command, an unknown or ill-typed field, a note over 2000 characters, or `reject`/`revise` without text 400; an unknown item id 404. Success is 202 `{ request_id, seq, command, work_item_id }`. A POST to any other path (settings excepted) is a 405 with a JSON `{ error }` body and `allow: GET, HEAD`, whatever the area; every other method keeps its area's 405. **Item API:** `/api/v1/items/:id` adds `commands` (`{ name, usage, description }` for each command that applies in the item's current state, from the same table and rule as the comment footer, `commandsFor`, `/help` last) and `replies` (the item's stored requests, oldest first, the newest 50: `{ seq, command, created_at, handled_at, refusal }`; `command` and `refusal` pass the `Withholder`; the note is never returned). They read a new store method, `listAppCommandRequestsForItem` (no schema change). Every other GET response is unchanged. The server still binds only `127.0.0.1`.
  - **Command buttons on the item page (decision changed 2026-11-07, issue #228).** The item page (`web/src/views/item-commands.tsx`) shows one button per entry of the item API's `commands`, in the API's order, labelled with the command name, and one text box that is the note of every send: the reason for reject, the feedback for revise, tokens for budget, `accept|changes|reject <severity> <reason>` for verdict, and an optional note for approve, retry and resolve. A send is `postCommand` (`web/src/api.ts`): `POST /api/v1/items/:id/commands` with JSON `{ command, note }` (`note` only when the box has text, trimmed) and the token from `GET /api/v1/session` in `x-csrf-token`; the session is read once per page load, not polled. Revise and reject stay disabled while the box is blank. Reject asks first with an inline "Confirm reject" / "Cancel"; nothing is posted before Confirm. No other command asks. Next to each button: the error text of a failed send (a non-2xx answer), "sent" at once after a 202 until a reply as new as it arrives, else the item's latest request for that command from `replies`: its refusal, "sent" while it has no handled time, "Done" when handled with no refusal. When the session says `commands_enabled` is false, or the session cannot be read, every button is disabled and the page says commands are off. Outcomes update with the 3 s poll; request notes and the full reply history are not shown. No server route, store or command changed.
  - **Merge check fields (new fields, 2026-11-07, issue #248; design §5 Merge check).** Each row of `/api/v1/items` and the `item` of `/api/v1/items/:id` have `merge_check`: `null` for an item that is not ready to merge, else `{ state, conflicts, head_sha, base_sha, checked_at }`. `state` is `mergeable` or `conflicts` from the item's stored result, or `checking` while it has none or while the result is for an older head than the item's recorded `last_head_sha`. `conflicts` are the conflicting file names, each through the `Withholder`. - **Work items tree (decision changed 2026-11-08, issue #295; current).** The Work items page defaults to a tree (`web/src/views/tree.tsx`, `react-aria-components` `Tree`: treegrid roles, arrow keys move focus, right expands, left collapses). A split parent holds its phases in phase order; every other item is a top-level row, in the API's ranked order. - **Run transcripts in the app (new decision, 2026-11-07, issue #303; current).** A run's stored transcript opens from the item page. **Lookup:** by the worker's storage key, `transcripts/<item>/<run>.json` (a second agent step of the run: `<run>.<step>.json`, e.g. `resolve`, `fix`), never `runs.transcript_url`, which holds the external link a person gives for an interactive session (those stay out of scope). The run must belong to the item (`listRuns(item)`); no store method, schema or migration changed. **Storage:** `SharedStorage` gains `getRange(key, start, end)` → `{ bytes, size }` (only that range is read; `getRange(key, 0, 0)` gives the size), implemented by `fs` with one file handle. It is optional on the interface so an older implementation still builds; `readRange` falls back to `get` there. `UiDeps.storage` (optional; `main.ts` passes the configured storage plugin) is the UI's only storage dependency. **API** (`src/ui/transcript.ts`, routed from `src/ui/api.ts`): `GET`/`HEAD /api/v1/items/<id>/runs/<run>/transcript?offset=&filter=&tail=&part=` (every other method is 405, like every route). One request reads at most 64 KiB (`PAGE_BYTES`) and returns at most 64 KiB: a forward page reads from `offset - 1` so it can tell whether `offset` starts a line, leaves a line cut by the range for the next page (`next`), and skips a single line over 64 KiB with a marker; `tail=1` reads only the file's final 64 KiB and returns its last 20 steps (`earlier` says more exist). Each stream-json line (Claude Code's or the OpenAI-compatible runner's events) gives its steps (`text`, `tool_use`, `tool_result`, `result`, `system`, `error`); a line that is not a JSON event is a `plain` step, so a non-stream-json transcript shows as plain lines. `filter=edits|commands|reads` keeps only tool calls of that kind and is applied on the server, page by page. **Egress:** every step and every other text of the response (outcome code, detail, summary, worker id) passes the `EgressScanner` on the new channel `ui` before it leaves; a finding withholds the whole step (`[withheld: <rule>]`, its tool name dropped), never a cut-off part, and a clean step cut to fit the page is cut after the scan. Errors are fixed texts: 404 for an unknown run, another item's run, no stored transcript or an unknown `part`; 400 for a bad `offset` or `filter`; a storage error is a 500 whose text never includes the storage message. `/api/v1/items/:id` adds `transcripts`, run id → its stored parts (only runs with a transcript; from one `list` of the item's prefix); the run rows keep their fields, and the app's worker column is the last attempt's `worker_id`. **App:** the item page's Runs table shows kind with the run ID, attempt, status, error, worker, started, took, tokens and an Open link when a transcript is stored (a table at `sm` and up, cards below it: see "Item page, phases and narrow screens"); the view `/app/items/<id>/runs/<run>` (`web/src/views/transcript.tsx`, routed in `App.tsx`) shows the outcome first, then the steps: assistant text collapses past five lines, tool results start collapsed, errors are highlighted, a failed run offers "Jump to the last 20 steps", the step-type filter holds across "Load more" pages, and text wraps so a 375 px screen does not scroll sideways. It never polls. Out of scope: editing or re-running from a transcript, a live view, full-text search, and what the worker stores. Decision changed: "the UI reads only the store" (and the Data page's "out of scope: shared-storage transcripts") now has one storage read path, this route.
- **Why an item waits (decision changed 2026-11-07, issue #310; current).** One pure function, `whyWaiting` (`src/ui/why.ts`, no store, no clock), turns an item's state, its queued or running run (with its queue position), the run's latest claim decision, the claim pauses in effect, the run's `not_before` (passed only while still ahead) and its phases into `{ code, text, next_actor, refs }`. **Precedence, first match wins:** closed; blocked on a person or the budget (`Ready to merge: …`, `Waiting for a person to approve the spec`, `#41 was closed without a merge: …`, a failed run, …); a deadlock claim on the current run (`Started past a deadlock with #92: a person checks the overlap`); running (`Running implement`); a claim pause that stops the run's kind, by the store's claim rule (`rate_limit` and `model_stall` any kind, `forge_auth` and `preflight_access` implement and update only); a dependency (`Waiting for #A and #B to merge`, from the stored `blocked_reason`); a phase hold (`Waiting for the previous phase #N to merge`); a coordination hold (`Held behind #92, which has an open PR` / `which is running` / `which is queued ahead of it`, while the decision is `held`, not approved and on the current run); a retry's `not_before` (`Retry waits until …`); the queue position (`Queued at position N`); else `Nothing moves it: no run is queued`. `next_actor` is `human`, `factory`, `other_item` or `none`; `refs` are the same-repo `#N` numbers of the sentence (numbers only, never `owner/name#N`). **API:** `why` on each row of `/api/v1/items`, on the `item` of `/api/v1/items/:id` and on each row of `/api/v1/queue` (null for a run whose item is gone), all from the same helper (`whyOf`, `src/ui/list.ts`), so the three read the same `text`; the text passes the `Withholder`, and `ref_url` is the item's repository issue URL (from its GitHub source link; null otherwise) to append a ref to. **Levels:** a dependency blocker is `waiting_on_issue` (badge `waits on #N`) even while its run is queued, no longer `queued`; an item whose current run's latest claim decision is `deadlock` is `needs_human` (badge `deadlock`), so it is in Needs you, and `/api/v1/overview` `needs_you` counts it besides the human-blocked items. **App:** the Why column of Needs you and Work items shows the sentence; the Queue's Starts column shows it for any row that is not plainly queued or waiting out a retry (so a held run no longer reads "now"); the item page shows the full sentence under the title (no `truncate`) and no longer the raw Blocked on row; each `#N` in `refs` links to `ref_url` + N. **Reads:** only existing store reads: `getClaimPause` (four names, once per request), `listClaimDecisions` (per item with an active implement run; this read cost is accepted for now), `listRunsByStatus`, `getWorkItem`, and `listWorkItemsWhere` for phases only when an item is blocked upstream. No store method, interface, migration or schema changed. `/classic` keeps its own text.
- **Item page, phases and narrow screens (decision changed 2026-11-07, issue #313; current).** **Item API:** the `item` of `/api/v1/items/:id` adds `spec_comment_url` (through the Withholder; null before triage posts the spec), `parent_id` and `phase` (both null unless the item is a phase of a split spec) and `phases`, a split parent's phases in phase order as `{ id, phase, title, stage, source }` (title through the Withholder; empty for any other item), read with the store's existing `listPhases`; no store method, schema or migration changed. **Item page:** a phase says "Phase N of its split parent" with a link to the parent; a split parent has a Phases section linking each phase's page. The spec comment and the PR are links only when the URL is http(s); any other value (a withheld marker, a local path) shows as plain text. The Runs table's first cell is the run's kind and ID. **Timeline:** each change value is parsed from the API's JSON text and shown as words (strings unquoted, lists joined, none as `–`; a withheld marker as it is). The spec fields triage writes (`problem`, `scope`, `desired_output`, `done_criteria`, `files_to_change`, `allowed_paths`) never show inline: their row has a "spec written (show)" button that opens them, each rendered as markdown (lists as bullet lists). **Markdown:** a small built-in renderer (`web/src/components/ui/markdown.tsx`, no dependency): headings, paragraphs, bullet and numbered lists, fenced code, inline code, bold and `[text](url)` links. It builds React elements, never HTML strings, so raw HTML shows as text; a link is drawn only for an http(s) URL, any other (`javascript:`, `data:`, relative) shows its text, plain. **Closed facet:** the Closed option (and stage `CLOSED`) counts the closed items that match the other filters, the same rule as every other facet. When the filters leave closed items out of the list, `/api/v1/items` reads them for the counts only: one `listWorkItemsWhere({ stage: "CLOSED" })` read (at most `LIST_LIMIT` items), no per-item reads (a closed item's level is always `closed`, its kind comes from its blocked reason, its search keys from its withheld title). The classic page at `/classic` keeps its own counts. **Tables:** every `Table` in the app (not the Data page's own table, which keeps its horizontal scroll) is a table at `sm` (640 px) and up and a list of cards below it, with no horizontal scroll: the first cell is the card's title, the next two sit under it, the rest are listed with their column names. Rows are `Tr`, cells `Td` (`web/src/components/ui/parts.tsx`); the width is read from the window, so a component test at 390 px sees the cards. **Sidebar:** in the icon-only layout below `sm` each link keeps a `title` and an accessible name (`aria-label`, its page label). **Settings:** each `_ms` key shows its value as a duration with units under its field (5400000 as `1h 30m`, 1800000 as `30m`), its description unchanged.
- **Revisions, system actions and the tab title (decision changed 2026-11-07, issue #311; current).** **Revisions:** `/api/v1/overview` adds `server_rev`, the git revision the UI server runs (`git rev-parse HEAD` of its code root, read once at start; null when git cannot say), beside `factory.rev`, which stays the supervisor's. The app has its own revision built in through Vite `define` (`__FACTORY_REV__` from `git rev-parse HEAD` at build time, `web/vite.config.ts`; `WEB_REV` in `web/src/api.ts`, null in tests) and sends it on each overview poll as `?rev=`. When both are known and differ, a banner under the top bar says "Dashboard out of date: reload / restart `factory ui`" (`web/src/views/system-banner.tsx`); equal or unknown revisions show none. It says only that they differ, never which is newer. Under `git-worktree` the supervisor restarts the page on each new revision ([08-self-update.md](08-self-update.md)). **System actions:** the overview adds `system_actions` and counts them in `needs_you` ([09-status-page.md](09-status-page.md)); the Floor lists them at the top of Needs you, each with its command. **Tab title:** `(N) <page> · software-factory` with N the overview's `needs_you`, no prefix at 0. **Health:** ok rows fold behind their count ([09-health.md](09-health.md)). No store method, schema or migration changed.
- **Workers, Failures and the effective worker count (decision changed 2026-11-07, issue #312; current).** **Workers page:** one row per entry of `processes` on `/api/v1/workers`: host, pid, start time, busy and idle slots (idle is slots minus busy, never below 0), current and max slots, the process's runs, and a "draining" badge when `slots` is 0. It shows the effective worker count once, as "Worker setting: N (override | config file | default)"; the factory banner no longer states a count. **Overview:** `factory.workers` is the effective `workers` setting (`effectiveWorkers`, `src/ui/settings-api.ts`: the Settings page's resolve of file, override and default, capped at `max_workers`) with `factory.workers_source`; without the Settings wiring it falls back to the status file's value with source `file`. **Failures:** `GET /api/v1/failures?window=24h|7d` (`src/ui/failures.ts`, default 24h, any other value 400) returns the failed runs of the window grouped by error code: `{ window, cap, total, capped, groups: [{ code, description, count, last_seen, items, runs: [{ id, work_item_id, kind, attempt, detail, worker, finished_at }] }] }`, largest group first. It reads only `listRunsFinishedWithin` and `listRunAttempts` (the worker of the run's claim), at most the newest 500 failed runs per window; `capped` says when more failed, and the page states the cap. Codes, details and workers pass the Withholder (run-outcome channel). `description` comes from one server-side table (`FAILURE_DESCRIPTIONS`) of the codes the code base names; any other code shows raw with `description: null`. - **Needs-you Why column (decision changed 2026-11-07).** A Needs-you row's Why shows what to do, from `needOf` (`src/ui/need.ts`), the one function the classic status page also uses; `GET /api/v1/items` returns it as `need: { reason, command }` on those rows only. ## History

- **Work items tree** (decision changed 2026-11-08, issue #295). Before: the Work items page was one flat table of `/api/v1/items` rows (item, state, why, since, issue, PR) with no parent, phase, worker, queue position or claim decision on a row, filtered by the server's `state` and `q`. It stays as the List toggle.
- **Revisions, system actions and the tab title** (decision changed 2026-11-07, issue #311). Before: the overview returned only the supervisor's revision (`factory.rev`), the web build had no revision built in, so a tab or a page server on old code was not shown; `needs_you` counted only human-blocked and deadlocked items; the tab title had no count.
- **Item page, phases and narrow screens** (decision changed 2026-11-07, issue #313). Before: the item API had no `spec_comment_url`, `parent_id`, `phase` or `phases`; the timeline printed each change as `field: <from JSON> → <to JSON>`, so a spec showed escaped newlines and arrays; the Runs table showed only the kind ("the item page's Runs table shows kind, attempt, status, error, worker, started, took, tokens and an Open link when a transcript is stored, scrolling inside its own box"); every table kept its full width in a scroll box on a phone; the sidebar links below `sm` had no title; the Closed facet read 0 because closed items were loaded only when a filter asked for them; and Settings showed `_ms` keys as plain milliseconds.
- **Why an item waits** (decision changed 2026-11-07, issue #310). Before: the level returned `queued` before it checked dependency blockers, so an item waiting on another item's merge showed Queued; a deadlock claim decision was not in Needs you or `needs_you`; the Queue's Starts column read only the run's `not_before`, so a coordination hold showed "now"; and the item page showed the raw `blocked_on: blocked_reason`, cut off, with `#N` not linked.
- **The dashboard's only write is Settings** (decision changed 2026-11-07, issue #291). Before: `POST /api/v1/settings` was the one write route besides item commands (#227) and the app showed no claim pauses. Now `POST /api/v1/pauses/resume` is another write, behind the same guards plus the owner check.
- **No command buttons in the app** (decision changed 2026-11-07, issue #228). Before: commands could be posted to `/api/v1/items/:id/commands` but the app had no buttons for them ("Out of scope here: buttons in the app that send commands", and "Commands … are not in the app yet" on the item page); now the item page sends them.
- **The dashboard is read-only but for Settings** (decision changed 2026-11-07, issue #227; the read-only decision of #236 changed again). Before: `POST /api/v1/settings` was the dashboard's only write, every other POST answered 405 in its area's format (HTML on the pages), commands stayed on the source, and the item API had no `commands` or `replies`. Now item commands can be posted to `/api/v1/items/:id/commands`, and every other POST is a JSON 405.

- **Run attempts in the item API** (decision changed 2026-11-07, issue #207). Replaces: "`/api/v1/items/:id` (facts, timeline, runs)" with one row per run and no record of its earlier claims, and "no store method, interface, migration or schema changed" (the item route now also reads `listRunAttempts`).
- **`/api/v1/workers`** (field added 2026-11-07, issue #209). Before: it returned only `workers`, the lease owners of running runs, so an idle process did not appear and no slot count was shown.
- **Where `/` goes** (changed 2026-11-07). Before: `/` served the server-rendered page and the app was only at `/app/`, with placeholder pages.
- **The dashboard is read-only** (decision changed 2026-11-07, issue #236). Before: the JSON API answered only `GET`/`HEAD` ("Read-only JSON API"), and the Settings page was read-only, pointing at `factory settings`. Now `POST /api/v1/settings` is the one write route and the Settings page edits and resets settable keys.

- **PR link in the API** (decision changed 2026-11-07, issue #240). Before: `pr_url` was built from the stored project key (`github:host:id`), giving a malformed host; now it is built from the stored label, as the classic page already did.

- **Run transcripts in the app** (new decision 2026-11-07, issue #303). Replaces: the UI had no storage dependency and only read the store; the worker stored transcripts that nothing read back, the item page had no worker column or transcript link, and the Data page listed shared-storage transcripts as out of scope.
- **Workers, Failures and the effective worker count** (decision changed 2026-11-07, issue #312). Before: the Workers page listed lease owners and "Running now" and ignored `processes`, so draining processes and idle slots were invisible; the factory banner showed the status file's `workers` (the file value, which could disagree with an override or the `max_workers` cap); the Floor's failed count was plain text, and no route grouped failed runs by error code.
