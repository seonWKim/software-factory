# 7. Self-improvement: design learnings from owner corrections

- **Owner corrections to UI changes become learnings lines, and repeated kinds are counted for one proposal each (new decision, 2026-11-20, wi_5f097420; current).** The decision: **the design system learns from the owner's corrections in two tracks, as the factory's own rules do.** The automatic track stores and writes every correction with no gate; the owner-gated track counts lines of one kind and drafts one proposal per kind. Before, the improver learned only from failed runs and pushback words (07-self-improvement.md): a correction such as "the checkbox is too big" was fixed once and lost.
  - **What is captured.** On an item whose change touches `web/` (its PR's files, else the spec's files to change, else its allowed paths, `touchesWeb` in `src/core/design-learnings.ts`): a `/revise` or `/reject` with words (`pushback`, captured beside the tacit ledger's capture in the commands unit), an explicit `changes` verdict with a reason (`verdict`, in the verdicts unit), and each design-system finding of a finished review run (`review`: a `code` finding naming `design-system/`, `patterns.md`, `components.md` or a decision rule, from prompts/review.md step 7, in the run-results unit). The improve unit's `captureCorrection` and `captureReview` store it; a failure is logged and never stops the command it follows.
  - **A line.** What was built (the item's title, 120 characters), what the owner said (one line, 300 characters, through the G5 scan first: a flagged text stores nothing), which page (the first `web/src/pages/<page>` the change touches, else `web`), the date and the item ID. File form: `- L<n> · <date> · <item> · page: <page> · built: <title> · owner: <words>`.
  - **Store.** `controller_design_learnings` (migration `20261120T1200-controller-design-learnings`): one row per line, `capture_key` unique (`pushback:<item>:<comment>`, `verdict:<item>:<comment>`, `review:<run>:<finding index>`, `supersede:<line>`), so a retried or redelivered capture stores nothing more. `kind`, `batch` and `superseded_by` are each set once by a conditional update; two replicas or a retry write each once.
  - **Kind.** The improve run (worker) tags each active untagged line with one plain model call (`cheap`, no tools, one word back) from a closed list: `control_size`, `spacing_layout`, `component_choice`, `shown_data`, `wording`, `colour_token`, `interaction`, `other`. An answer off the list is `other`; a failed call leaves the line for the next run; at most 20 calls per run (`MAX_TAG_CALLS`). Owner answer: one call per line, `other` never counts.
  - **The file.** `design-system/learnings.md` is append-only: a line is never edited or removed. After each improve run's report is filed, the improve unit appends every line not written yet in one commit to the local base: one `append_lines` outbound action (key `design_learnings:<improve run>-<first line>-<last line>-<count>`, so a report filed again after newer lines arrived stores its own action) to the base's git destination, delivered by the `local` target (`appendLines` in `src/outbound/targets/local-git.ts`: the file read from objects, one commit on a new branch from the base, merged into the base conditionally on it; a moved base throws and outbound retries). A line the file already holds is not appended again, so a retry or a crash between the action and marking the lines adds nothing twice. No PR, no push: the commit stays local (owner answer). A sandbox that cannot commit to a local branch leaves the lines in the store.
  - **Supersede.** A line turned into a rule gets a new line naming it (`supersedeDesignLearning`, source `supersede`: `- L<n> · … · supersedes L<m> · turned into a rule by <item>`), and the store sets the old row's `superseded_by`. Superseded lines no longer count and leave the agents' read.
  - **The agents' read.** AGENTS.md tells agents to read the last 40 active lines of `design-system/learnings.md` with the other design-system files before a `web/` change (`recentActive`: a line a later `supersedes` line names, and the supersede lines, are left out). Owner answer: through AGENTS.md only, not the triage or implement prompts.
  - **Counting.** `planProposals` (pure) groups the active tagged lines by kind, all of them, no time window. A kind with two or more lines and no open proposal is due one proposal with every such line as evidence; a kind with an open proposal only adds its new lines to that proposal's evidence, never a second proposal; one line of a kind (a one-off) stays a learning only; `other` and untagged lines never count. The improve run's outcome lists the proposals due (`design.due`).
  - **The proposal.** What it proposes: a rule for `design-system/patterns.md`, a row in the "Which component for what" table, a new component, or a design-system test that blocks the mistake. It is pending on the proposals page and changes nothing in `design-system/` by itself; the owner promotes, rejects or holds it, and a promoted proposal is built as a normal item that changes `design-system/` through the normal path, whose merge supersedes its evidence lines. Owner answer: filing waits until the entity proposals mechanism (wi_30e2e40b) merges; until then the counting runs and its result is in the run's outcome, and nothing is filed.
  - **Not in this decision.** Backfilling past corrections; adding learnings to the triage or implement prompts; any change to `patterns.md`, components or tokens beyond the learnings file; pushing the commit to a remote.
