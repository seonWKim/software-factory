# 8. Enterprise: self-update

- **The supervisor runs the status page and swaps it on each new revision (decision changed 2026-11-07, issue #311; before: see History).** Under `git-worktree`, `factory dev` also runs `factory ui` as a child (`serveUi`, `src/impl/updater/git-worktree.ts`; `runDev` turns it on), from the claiming child's version folder, with `SOFTWARE_FACTORY_CODE_ROOT`, `SOFTWARE_FACTORY_SUPERVISED=1` and the external config like the dev child (no worker index block). When a new revision's child starts, the status page **drains and swaps**: the old `ui` child gets SIGTERM and has exited (its port is free; SIGKILL after the drain timeout) before the new one starts from the new folder, so the page serves the new API with no manual restart; the gap is the time one process takes to stop and bind. The page does not stop for a docs-only change, a failed build or a waiting migration (it only reads the store). One that exits by itself starts again on the next poll (logged as a warning), as the dev child does; so a `factory ui` started by hand on the same port makes the child fail each poll until the hand-started one stops (below): under `git-worktree`, open the page `factory dev` serves instead. The child exits when the supervisor's IPC channel closes, never as an orphan; supervisor shutdown stops it with the other children. Under `none` (in place) `factory ui` is still started by hand. **A hand-started page never serves code older than the factory's (decision changed 2026-11-08; before: see History).** A `factory ui` that is not the supervisor's child compares its own revision with `rev` in `supervisor.json`, at start and every 30 s (a local file read and, only when they differ, one `git merge-base --is-ancestor` in its code root). When the factory runs a newer commit of the same line, it refuses to start, or stops, with exit code 1 and the message to open the page `factory dev` serves (under `git-worktree`) or to rebuild and start it again (under `none`); its port is then free for the supervisor's `ui` child. A page on a newer or unrelated commit (a branch under development) keeps serving and only shows the banner. It refuses rather than restarting itself: a hand-started page runs from a checkout no updater rebuilds. A supervisor started before issue #311 has no `ui` child, since the supervisor process itself never updates: restart `factory dev` once. The overview's `server_rev` is the `ui` process's own `git rev-parse HEAD` (its code root), and the app has the revision built in through Vite `define` (`__FACTORY_REV__`, `web/vite.config.ts`), so a tab or a page server left on old code shows "Dashboard out of date: reload / restart `factory ui`" (design §9 dashboard app).

- **Self-update with an external config (decided 2026-11-07, issue #336).** `--config <path>` / `FACTORY_CONFIG` (docs/plugins/selection.md) replaces the code root's `factory.config.json`. The supervisor passes the absolute path it was started with to every child and every `migrate --status --json` / `migrate --no-drain` call as `FACTORY_CONFIG`, so a new version keeps using the same file; prompts and code still come from the version folder. Each child's worker index block is sized from that same file's `workers` and `max_workers` (the file the child reads), and `state_dir` / `worktrees_dir` resolve from its folder. Without an external config nothing changes: each child reads its own folder's `factory.config.json`. On a shared (MySQL) store the reviewed keys (`dials`, `floors`, `plugins`, `permissions`, `auth`) still come from the version folder's checked-in file, so a reviewed PR stays the only way to change them. The updater still follows the factory checkout's `origin/<base_branch>`.

- **Self-update (D7, decided 2026-11-01):** the factory runs from a runtime copy of `origin/<base_branch>` (`<state_dir>/runtime`, a detached git worktree), not from the checkout it was started in. State stays in the main checkout: `state_dir`, `worktrees_dir`, `repo.path`, the database, shared storage and the secret file; only code, `factory.config.json` and `prompts/` come from the runtime copy (`loadConfig` takes the code root explicitly; the supervisor passes it as `SOFTWARE_FACTORY_CODE_ROOT`). `dev` is a supervisor behind a new `Updater` plugin (`git-worktree` default, `none` = run in place as before). The new commit is built beside the running child first: a failed build must leave the old version running. Consequence: under `git-worktree`, uncommitted local edits, local branches and unpushed merges no longer affect `dev`. The main checkout is only fast-forwarded, and only when it is on the base branch and clean. (The single `runtime` copy and the drain order were replaced the same day; see start-then-drain below.)
  - **Self-update: start-then-drain.** Now the new child starts in the same poll step as its successful build, and only then is every older child asked to drain (the same IPC message). The old child's controller stops at once (no new pass; a pass already running finishes), its worker stops claiming and finishes its in-flight runs from its own folder, and the child exits by itself; the new child's controller applies those runs' outcomes (`docs/design/05-restarts.md`, issue #294); poll never waits for it. It is hard-stopped (SIGKILL, logged as an error) only if it has not exited `run_timeout_ms` plus 60 s after the drain request, each child on its own timer. A draining child that exits is not a crash. This is safe because claims and state changes already go through the store with leases: during the overlap only the new child's controller runs passes, and both versions' workers complete and claim runs through the same conditional updates.
    - **Folders:** each version runs from its own detached worktree, `<state_dir>/versions/<short-rev>` (12 characters; `-2`, `-3`... if that name is still held). The child's entry and `SOFTWARE_FACTORY_CODE_ROOT` point at its folder for its whole life, so a new version never changes files under a running one. A docs-only change fast-forwards only the newest folder. When a child starts, the supervisor writes its pid to `.factory-pid` in the folder.
    - **Installs:** `node_modules` lives in `<state_dir>/deps/<hash of package-lock.json>/node_modules`; each folder's `node_modules` is a link to the install for its lock file. A new lock hash runs `npm ci` in the new folder and moves the result into `deps/` through a temp name, so `deps/` only holds complete installs and a failed `npm ci` leaves nothing there. Old folders keep their install.
    - **Worker index ranges:** each child gets `SF_WORKER_INDEX_BASE`, the lowest block of `max_workers` indexes (absent: `workers`; read from the file the child reads: the external config, else the new folder's `factory.config.json`) that no live child uses; the worker pool numbers its workers from it, so `SF_WORKER_INDEX` never collides between an old and a new child. Blocks are kept in supervisor memory: one supervisor per state directory is assumed and not guarded.
    - **Code version** (added 2026-11-08, RFC 0015 M6 leftovers): each child also gets `SF_CODE_VERSION`, the revision its folder was built from. Its workers stamp it on every run they execute (`worker_runs.code_version`), so a run journaled by the old child is resumed only by code that can resume that revision (design 10-event-driven). An unsupervised `dev` has none and stamps `dev`.
    - **Cleanup:** kept folders are those with a live child, plus the newest folder (or, while the newest has a live child, the newest built folder not already kept). Others are removed once their process has exited and no kept folder links into them: `git worktree remove --force`, then plain deletion if needed, then `git worktree prune`. An install is removed when no kept folder links to it. A failed build's folder is removed at once. On supervisor start, every folder whose pid file is missing or names a dead process is removed, except the newest one when its build matches `origin/<base_branch>` (a restart does not rebuild); a live pid keeps its folder. A reused pid makes an orphan look alive, so its folder stays until a later start (accepted). The first start under this layout removes the legacy `runtime/` and `runtime-next/` worktrees, once the sweep finds no live child.
    - **Shutdown:** SIGINT/SIGTERM to the supervisor sends SIGTERM to every live child, old and new (SIGKILL after the drain timeout), and returns only after all have exited.
    - **Rollout:** this change ships through the drain-based supervisor; start-then-drain takes effect from the next merge after it.

- **SQLite: a breaking migration waits for `npm run migrate` (decision changed 2026-11-09, runtime review H1/H2; before: see History).** Of the two safe options, drain the old child inside the update or refuse the update until the owner migrates, the update is refused: a breaking migration renames tables, takes a backup and is verified, and the owner should see that happen (`--dry-run` first). So on SQLite `migrate --status --json` reports every pending breaking timestamped migration (`<id> (breaking)`, `sqlitePendingSteps` in `src/impl/store/sqlite/rehearse.ts`), and the update takes the waiting path below: the old child keeps running, nothing migrates, and `npm run migrate` (or `updater.auto_migrate`) drains every child before it applies. Additive migrations are not reported: the new child applies them on open, safe beside old code (RFC 0015 §12 D1). Every other open of a database that holds data (a child, `factory status` from a newer checkout) refuses a pending breaking migration with `migration_pending` and names `npm run migrate`, as MySQL does; a new database is still built at the latest schema on first open, so solo zero setup is unchanged. `npm run migrate -- --status` and `--dry-run` on SQLite only read: they list the pending baseline steps and migrations and change nothing (no `migrate()`, no topic tables); only apply migrates, after the drain, with breaking migrations backed up first. `--rehearse` applies them to its copy.

- **Self-update: migrate before the drain (decided 2026-11-07, issue #165).** After a successful build the supervisor asks the new folder's code which `npm run migrate` steps (schema or data) are still pending against the store (`node <folder>/dist/main.js migrate --status --json`). If any are pending it starts, drains and kills nothing: the old child keeps claiming with its settings, `supervisor.json` says `migration_pending` with the step names, and each poll checks again (no restart loop). Once the steps are gone (applied elsewhere), the next poll starts the new revision and drains the old one as usual. A newer commit replaces a waiting target (built and checked instead).
  - **`npm run migrate` while `dev` runs:** it sees a live supervisor (`supervisor.json`'s `supervisor_pid`) and writes `<state_dir>/supervisor-request.json` (`drain`). The supervisor reads and removes it on its next poll and drains every child; no child starts (`migration_draining`). Once none is live it reports `migration_ready`; only then does `migrate` apply the steps, and it writes `start` (or `cancel` if a step failed: the old revision starts again, the target keeps waiting). It gives up after `run_timeout_ms` plus the drain margin, with a `cancel` and nothing applied. A drain request with no update waiting migrates the running revision and starts it again. `--no-drain` applies without asking (the supervisor's own call). No live supervisor: it applies at once, as before.
  - **Crash fallback:** a child whose store refuses to open because steps are pending exits with the error code `migration_pending` (sent over IPC with its message). The supervisor treats that as a waiting migration on that revision, not a crash, and does not restart it until `npm run migrate` finishes.
  - **`updater.auto_migrate`** (in `factory.config.json`, default `false`): the supervisor drains every child, applies the steps itself (`migrate --no-drain`) once none is live, then starts the new revision. A failed apply starts the old revision again and is not retried automatically for that target.
  - **Status page:** banner states `migration_pending` ("Update to X waits for `npm run migrate` (pending: …). Still running Y with its settings."), `migration_draining` and `migration_ready`.

- **Build in place without breaking running processes (decided 2026-11-07).** `npm run build` (`scripts/build.mjs`, no dependency) compiles into fresh staging folders beside the targets, `dist.build-<pid>-<n>` and `web/dist.build-<pid>-<n>` (same depth, so source map paths stay right): `tsc -p tsconfig.json` and `tsc -p tsconfig.migrations.json` with `--outDir` set to the staged `dist`, and `vite build --outDir <staged web/dist> --emptyOutDir`. Only when all three succeed does it take a short lock (`dist.swap-lock/`, made with `mkdir`, holder pid inside; a dead holder's lock is taken over) and swap each folder in: the live folder is renamed aside (`*.old-<pid>-<n>`), the staged one renamed to its name, then the old one deleted. So a failed build leaves the previous `dist/` and `web/dist/` untouched, and a live folder is missing only between two renames (no file is ever half-written). Concurrent builds (several `npm run factory -- <cmd>` at once) compile side by side and the last swap wins. Each build first removes staging and old folders whose pid is dead. A fresh staging folder per build keeps the guarantee that a deleted `*.plugin.ts` leaves no stale descriptor (`08-plugins.md`). `npm run factory`, `migrate` and `setup` still build first; a running `factory ui` keeps serving `web/dist` (same path, new files) and the supervisor's children run from their own version folders. The updater's version builds and the tests' `--outDir` builds to temp folders are unchanged; the updater counts `scripts/build.mjs` as code, so a change to it rebuilds.

## History

- **Hand-started status page on old code** (changed 2026-11-08). Before: a `factory ui` started by hand was never checked against the factory's revision, so it kept serving old code and the old API (a 404 on `/api/v1/failures`) after every update, with only the banner to say so.
- **Status page restarts** (changed 2026-11-07, issue #311). Before: `factory ui` was started by hand and the supervisor never restarted it, so after an update it kept serving the old code and the old API.
- **Self-update** (D7, decided 2026-11-01). Order on a code change: build the new commit beside the running child first, then drain (IPC; the worker stops claiming and finishes its in-flight run), fast-forward, swap in the build, restart. This deliberately differs from "drain, update, build, restart": a failed build must leave the old version running. The drain-then-start order and the single `runtime` copy were replaced the same day.
- **Self-update: start-then-drain** (D7 changed 2026-11-01, issue #120). Before: drain-then-start. After a successful build the supervisor drained the running child and waited for it to exit before fast-forwarding `<state_dir>/runtime` and starting the new version, so one long run, up to `run_timeout_ms` (45 minutes), held every other worker idle after each merge.
- **Self-update: a new revision that needs `npm run migrate`** (changed 2026-11-07, issue #165). Before: it started at once like any build; its store refused to open, the child exited and the supervisor restarted it every poll (a crash loop) while the old child was already drained. `npm run migrate` had to be run with `dev` stopped.
- **Self-update: the drain stops the controller too** (changed 2026-11-07, issue #294). Before: a drain stopped only the old child's claiming; its controller kept running intake and the reaper until its worker drained, then ran one final pass.
- **Build in place** (changed 2026-11-07). Before: `npm run build` began by deleting `dist/` and `web/dist/`, then compiled into them. Every `npm run factory -- <cmd>` did so in the main checkout, so two CLI calls at once crashed each other (`Cannot find module dist/main.js`), a running `factory ui` lost `web/dist` mid-serve, and the supervisor could fail to start a child during a build.
- **Self-update: worker block size source** (changed 2026-11-07, issue #336). Before: the block size was always read from the new version folder's `factory.config.json`, and children and migrate calls got no config path, so an external config was ignored under `git-worktree`.
- **SQLite breaking migrations** (changed 2026-11-09, runtime review H1/H2). Before: the supervisor's `migrate --status --json` reported only the project-key data step on SQLite, so an update with a breaking migration took the plain swap: the new child renamed `runs`, `work_items` and the rest on open while the old child still wrote them. `npm run migrate -- --status` and `--dry-run` also opened the store with `migrate()`, so they applied every pending migration, breaking ones included, with no drain.
