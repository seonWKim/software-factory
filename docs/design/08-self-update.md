# 8. Enterprise: self-update

- **The status file names the revision a new child replaced (new decision, 2026-11-19, wi_fcf04fac; current; replaces none).** The decision: **`supervisor.json` carries `previous_rev`**, so an open dashboard can say what an update brought ([09-dashboard-shell.md](09-dashboard-shell.md), the update note). `GitWorktreeUpdater.startChild` sets it to the running revision when a child on another revision starts; a crash restart of the same revision keeps it; it is null until a child replaced another, and since it lives in the supervisor process, a supervisor restart starts it at null again. The `none` updater writes no file. The UI server reads it (`readFactoryStatus`, `src/ui/factory-status.ts`) and, when it is set, runs `git rev-list --count previous_rev..rev` (`revListCount`, the helper `CodeOrigin.behind` uses, `src/impl/updater/code-origin.ts`) and `git log --format=%s --max-count=20` over the same range in the code root (the updater's runtime copy, else the cwd), cached per revision pair (`updateChanges`), so the 3 s poll runs git once per update. Local git only, no fetch. `/api/v1/overview`'s `factory` adds `previous_rev` and `changes` (`{ count, subjects }`; subjects pass the Withholder; `count` null when git fails; `changes` null without `previous_rev`).

- **SQLite: a breaking migration applies on its own once nothing runs (decision changed 2026-11-17, local-task-tk_dac45611; current; replaces "a breaking migration waits for `npm run migrate`", see History).** The decision that changed: **after an update the factory drains and applies pending breaking migrations itself; no owner command is needed** (owner answers: auto-apply after the drain; the CLI fails fast). Seen 2026-11-17: after the dashboard on 4312 updated, `gb task list` exited 1 with the raw refusal naming `npm run migrate`, which a role agent allowed only `gb` commands cannot run. Now:
  - **Supervisor:** a step that `migrate --status --json` names `<id> (breaking)` (`breakingStep`, `src/interfaces/updater.ts`) takes the `updater.auto_migrate` path whatever that key says: every child drains, the steps apply (`migrate --no-drain`) once none is live, then the new revision starts. `auto_migrate` (default `false`) now decides only for the other steps (the project-key data step). A failed apply starts the old revision again and is not retried for that target, as before.
  - **Open:** the SQLite plugin opens with a drain check (`factoryRunning`, `src/migrate-drain.ts`): when `supervisor.json` names no live supervisor or child other than the opening process, nothing runs that a drain would have to stop, so the open applies the breaking migrations itself (an in-place `dev` naming itself, a CLI with the factory stopped). While one runs, the open refuses with `migration_pending` and one line, "The factory is draining or migrating: breaking migrations … apply once every factory process has stopped; try again in a minute", which the CLI prints as its whole error and exits 1 (fail fast, no wait). A supervised child sees its supervisor and refuses, so the supervisor's crash fallback below still holds.
  - **Never half-applied:** the open applies every pending migration in one transaction, one migration at a time; one that fails rolls all of them back and the error names it (`migration <id> failed; nothing was applied: …`). Breaking migrations still back up their tables first. A driver opened without a drain check (tests, tools) still refuses with the old message naming `npm run migrate`.
  - **Unchanged:** additive migrations apply on open beside old code (RFC 0015 §12 D1); a new database is built at the latest schema; `npm run migrate` (with its drain), `--status`, `--dry-run` and `--rehearse` work as before. Not covered: the supervisor's status page child is not drained before a migration (it only reads the store), and the in-place `none` updater has no supervisor to apply them while it runs: its next start applies them on open.

- **The dashboard files the supervisor requests: Migrate now, Start and Restart now (decision changed 2026-11-16, phase 3 of 4 of local-0ffe3059-d863-4717-b3eb-1c72a06e444e; current; replaces "only `npm run migrate` files a supervisor request, and the supervisor has no restart action", see History).** The decision that changed: **the status page runs `npm run migrate`'s handshake itself and adds two requests** (owner answer 4: a supervisor request like the migrate request, behind a confirm). `src/ui/migrate-api.ts` serves `GET /api/v1/supervisor` (which of the three the page may offer, and why not in plain words), `POST /api/v1/migrate` and `POST /api/v1/supervisor`. **Migrate now** without `confirm` is the dry run (`sqlitePendingSteps`, then `migrateSqlite` in dry-run mode: the pending steps and each row the project-key step would change; nothing written); with `confirm: true` it runs `withDrain` (`src/migrate-drain.ts`) in the background: a `drain` request, a wait for `migration_ready`, the steps (as `npm run migrate` applies them), then `start` on success or `cancel` on a failure or a thrown step. A page that filed only `drain` would leave the factory drained with nothing applied, so the page never files `drain` alone. **Start** files `start`; it is offered only when a supervisor is live and no child claims (a crash loop, a build that failed). **Restart now** files the new `restart` action (`SupervisorRequest` in `src/interfaces/updater.ts`), the same `{ action, at }` body; it is offered only while a child claims. The supervisor (`readRequest`, `src/impl/updater/git-worktree.ts`) acts on `start` with no migration under way only when no child is live (it clears a failed build of the newest folder's head and starts a child), ignores a `start` while a child claims, and on `restart` starts a child from its current (built) version folder, then drains the old one as any start-then-drain does; a `restart` while a migration waits is ignored. Each route sits behind the write guards (Host, Origin, Content-Type, CSRF token), the resume route's owner check (`approve_spec`) and a confirm; every refusal writes no file. A request needs a live supervisor to read it (`supervisor_pid` alive in `supervisor.json`), so with none all three are refused and the page says to start the factory from a terminal with `factory dev`; starting a stopped factory from the page is not covered, nor is the `none` updater (it writes no `supervisor_pid`, so nothing is offered). The parts come from `buildUiParts` (`src/compose.ts`: the state dir, clock, `run_timeout_ms`, the topic-table step and the project-key resolver, which builds the GitHub client only when owner/name rows are left) through the `ui` command. The banner texts and the Needs-you migration row no longer name `npm run`.
  - **In place (none updater):** the `none` updater writes no `supervisor_pid` and names itself as `child_pid`; with a live child and no supervisor, `supervisorOffers` gives all three offers the reason "Updates from this page are off while the factory runs from your checkout. To update, stop it, pull the latest code and start it again." (and the POSTs refuse with it), never the start message, which stays for when no factory process runs.

- **`factory dev` is the only way to run the loops (decision changed 2026-11-16, phase 1 of 2 of local-task-tk_f99d69ea; current; replaces "the controller and the worker can also run alone", see History).** The decision that changed: **the `factory controller` and `factory worker` commands are removed**, with their Makefile targets; the controller and the worker run only together, under `factory dev` and its supervisor (updater, drain, status page). `runLoops` in `src/cli/support.ts` takes no mode and always runs both. So `npm run migrate`'s drain reaches every loop process, and no hand-started process that skips the supervisor can write during a migration. `npm run factory -- controller` or `worker` is now an unknown command.

- **A separate code checkout follows its own origin/main on a slower interval (decision changed 2026-11-15; current; replaces "local mode follows the local base branch", see History).** The decision that changed: **the git-worktree updater's local mode (follow the code checkout's local `refs/heads/<repo.base_branch>`, never fetch) applies only when self-hosting**, and self-hosting means the code checkout's path equals the resolved `repo.path` (owner answer, 2026-11-15). In a project install the code checkout is a separate clone of software-factory and `factory merge` moves the project's repository, not that clone, so its branch never moved and installs kept their first version (seen 2026-11-15: two installs a day behind main; a hand fast-forward rolled both forward cleanly). A separate clone, with the local source or the GitHub source alike (decision 1 of the spec), follows `origin/main` of the code checkout (`CODE_BASE_BRANCH`: the factory's own base branch, never the project's `repo.base_branch`). It fetches at most once per `updater.code_update_interval_ms` (default 15 minutes; a config-file key, not a runtime setting: few external calls), and each poll in between reads only the local origin ref. A failed fetch is logged and tried again one interval later; the child keeps running (local first). A new commit then takes the usual start-then-drain path below. `supervisor.json` carries `behind`, the commits the running revision is behind origin/main as of the last successful fetch (`null` before one; absent when self-hosting), and Health and Runners show the running revision with it, so a stuck install is visible. Self-hosting is unchanged: local mode with the local source, a fetch of `origin/<base_branch>` every poll with GitHub. Not covered: the supervisor process itself still never updates.

- **The CLI skips the build when nothing changed (decision changed 2026-11-14; current; replaces "the CLI always rebuilds", see History).** The decision that changed: **`npm run factory -- <cmd>` builds only when a build input changed since the last successful build.** The `factory` script runs `npm run --silent build -- --if-stale`; with that flag the script first compares the modification times of the build inputs (`src/`, `web/src/`, `package.json`, `tsconfig.json`, `web/vite.config.ts`, `web/index.html`, walked recursively, folders included) with the freshness marker `dist.fresh` (beside `dist/`, git-ignored like the staging folders, so `dist/` holds only build output), which holds the start time of the last successful build. Nothing at or after that time: no `tsc` or `vite` runs and the command starts at once. Any input changed, added or removed (adding or removing an entry changes its folder's time), a missing input, a missing marker, `dist/` or `web/dist/`: the build runs exactly as `npm run build` does. The marker is written under the swap lock only after both `dist/` and `web/dist/` are swapped in, so a failed build (non-zero exit, its output on stderr, the CLI command does not run) leaves the old marker and the next call tries again. The marker holds the build's start time, not its end, so a file edited during a build is newer than it. Why mtime and not a content hash: reading only times is cheap (about 600 entries, tens of milliseconds) and an extra rebuild from a touched but unchanged file is harmless. `npm run build`, `check:responsive`, `migrate` and `setup` still build every time. Not covered: a change outside the listed inputs (a dependency upgrade without a `package.json` change, `scripts/build.mjs` itself) needs `npm run build`; a docs-only commit keeps the build stamp of the last build, as the server revision decision below intends.

- **Server revision = build stamp in dist/ (decision changed 2026-11-13; current; replaces "server revision = folder git HEAD", see History).** The decision that changed: **the revision a UI server reports as `server_rev` is the one its build was made from**, not its folder's git HEAD. `npm run build` (`scripts/build.mjs`) writes the checkout's HEAD into the staged `dist/revision` after both compile steps and before the swap, so a failed build leaves the previous stamp in place; `factory ui` reads it at start (`serverRevision`, `src/ui/system-actions.ts`), null when there is none (a build from before this change; the folder gets one on its next build, none are backfilled). The app's own revision (`__FACTORY_REV__`, `web/vite.config.ts`) is the same HEAD, read in the same build. Why: a docs-only update moves the newest folder's checkout without a build (above), so its HEAD named a commit the running code was never built from, and the "Dashboard out of date" banner fired with advice (reload, restart `factory ui`) that could not clear it. The other option, restamping on a docs-only move, would keep the server's revision tied to a git HEAD the build never saw. What did not change: when the updater builds, the hand-started page's refusal (it still compares its folder's git HEAD with `rev` in `supervisor.json`), and the "UI server and factory differ" check.

- **The supervisor runs the status page and swaps it on each new revision (decision changed 2026-11-07, issue #311; before: see History).** Under `git-worktree`, `factory dev` also runs `factory ui` as a child (`serveUi`, `src/impl/updater/git-worktree.ts`; `runDev` turns it on), from the claiming child's version folder, with `SOFTWARE_FACTORY_CODE_ROOT`, `SOFTWARE_FACTORY_SUPERVISED=1` and the external config like the dev child (no worker index block). When a new revision's child starts, the status page **drains and swaps**: the old `ui` child gets SIGTERM and has exited (its port is free; SIGKILL after the drain timeout) before the new one starts from the new folder, so the page serves the new API with no manual restart; the gap is the time one process takes to stop and bind. The page does not stop for a docs-only change, a failed build or a waiting migration (it only reads the store). One that exits by itself starts again on the next poll (logged as a warning), as the dev child does; so a `factory ui` started by hand on the same port makes the child fail each poll until the hand-started one stops (below): under `git-worktree`, open the page `factory dev` serves instead. The child exits when the supervisor's IPC channel closes, never as an orphan; supervisor shutdown stops it with the other children. Under `none` (in place) `factory ui` is still started by hand. **A hand-started page never serves code older than the factory's (decision changed 2026-11-08; before: see History).** A `factory ui` that is not the supervisor's child compares its own revision with `rev` in `supervisor.json`, at start and every 30 s (a local file read and, only when they differ, one `git merge-base --is-ancestor` in its code root). When the factory runs a newer commit of the same line, it refuses to start, or stops, with exit code 1 and the message to open the page `factory dev` serves (under `git-worktree`) or to rebuild and start it again (under `none`); its port is then free for the supervisor's `ui` child. A page on a newer or unrelated commit (a branch under development) keeps serving and only shows the banner. It refuses rather than restarting itself: a hand-started page runs from a checkout no updater rebuilds. A supervisor started before issue #311 has no `ui` child, since the supervisor process itself never updates: restart `factory dev` once. The overview's `server_rev` is the `ui` process's own `git rev-parse HEAD` (its code root), and the app has the revision built in through Vite `define` (`__FACTORY_REV__`, `web/vite.config.ts`), so a tab or a page server left on old code shows "Dashboard out of date: reload / restart `factory ui`" (design §9 dashboard app).

- **Self-update with an external config (decided 2026-11-07, issue #336).** `--config <path>` / `FACTORY_CONFIG` (docs/plugins/selection.md) replaces the code root's `factory.config.json`. The supervisor passes the absolute path it was started with to every child and every `migrate --status --json` / `migrate --no-drain` call as `FACTORY_CONFIG`, so a new version keeps using the same file; prompts and code still come from the version folder. Each child's worker index block is sized from that same file's `workers` and `max_workers` (the file the child reads), and `state_dir` / `worktrees_dir` resolve from its folder. Without an external config nothing changes: each child reads its own folder's `factory.config.json`. The updater still follows the factory checkout's `origin/<base_branch>`.

- **Self-update (D7, decided 2026-11-01):** the factory runs from a runtime copy of `origin/<base_branch>` (`<state_dir>/runtime`, a detached git worktree), not from the checkout it was started in. State stays in the main checkout: `state_dir`, `worktrees_dir`, `repo.path`, the database, shared storage and the secret file; only code, `factory.config.json` and `prompts/` come from the runtime copy (`loadConfig` takes the code root explicitly; the supervisor passes it as `SOFTWARE_FACTORY_CODE_ROOT`). `dev` is a supervisor behind a new `Updater` plugin (`git-worktree` default, `none` = run in place as before). The new commit is built beside the running child first: a failed build must leave the old version running. Consequence: under `git-worktree`, uncommitted local edits, local branches and unpushed merges no longer affect `dev`. The main checkout is only fast-forwarded, and only when it is on the base branch and clean. (The single `runtime` copy and the drain order were replaced the same day; see start-then-drain below.)
  - **Self-update: start-then-drain.** Now the new child starts in the same poll step as its successful build, and only then is every older child asked to drain (the same IPC message). The old child's controller stops at once (no new pass; a pass already running finishes), its worker stops claiming and finishes its in-flight runs from its own folder, and the child exits by itself; the new child's controller applies those runs' outcomes (`docs/design/05-restarts.md`, issue #294); poll never waits for it. It is hard-stopped (SIGKILL, logged as an error) only if it has not exited `run_timeout_ms` plus 60 s after the drain request, each child on its own timer. A draining child that exits is not a crash. This is safe because claims and state changes already go through the store with leases: during the overlap only the new child's controller runs passes, and both versions' workers complete and claim runs through the same conditional updates.
    - **Folders:** each version runs from its own detached worktree, `<state_dir>/versions/<short-rev>` (12 characters; `-2`, `-3`... if that name is still held). The child's entry and `SOFTWARE_FACTORY_CODE_ROOT` point at its folder for its whole life, so a new version never changes files under a running one. A docs-only change fast-forwards only the newest folder. When a child starts, the supervisor writes its pid to `.factory-pid` in the folder.
    - **Installs:** `node_modules` lives in `<state_dir>/deps/<hash of package-lock.json>/node_modules`; each folder's `node_modules` is a link to the install for its lock file. A new lock hash runs `npm ci` in the new folder and moves the result into `deps/` through a temp name, so `deps/` only holds complete installs and a failed `npm ci` leaves nothing there. Old folders keep their install.
    - **Worker index ranges:** each child gets `SF_WORKER_INDEX_BASE`, the lowest block of `max_workers` indexes (absent: `workers`; read from the file the child reads: the external config, else the new folder's `factory.config.json`) that no live child uses; the worker pool numbers its workers from it, so `SF_WORKER_INDEX` never collides between an old and a new child. Blocks are kept in supervisor memory: one supervisor per state directory is assumed and not guarded.
    - **Code version** (added 2026-11-08, RFC 0015 M6 leftovers): each child also gets `SF_CODE_VERSION`, the revision its folder was built from. Its workers stamp it on every run they execute (`worker_runs.code_version`), so a run journaled by the old child is resumed only by code that can resume that revision (design 10-event-driven). An unsupervised `dev` has none and stamps `dev`.
    - **Cleanup:** kept folders are those with a live child, plus the newest folder (or, while the newest has a live child, the newest built folder not already kept). Others are removed once their process has exited and no kept folder links into them: `git worktree remove --force`, then plain deletion if needed, then `git worktree prune`. An install is removed when no kept folder links to it. A failed build's folder is removed at once. On supervisor start, every folder whose pid file is missing or names a dead process is removed, except the newest one when its build matches `origin/<base_branch>` (a restart does not rebuild); a live pid keeps its folder. A reused pid makes an orphan look alive, so its folder stays until a later start (accepted). The supervisor no longer looks for the legacy `runtime/` and `runtime-next/` worktrees (decision changed 2026-11-09, issue #466; before: see History); `versions/` and `deps/` sit in `state_dir`.
    - **Shutdown:** SIGINT/SIGTERM to the supervisor sends SIGTERM to every live child, old and new (SIGKILL after the drain timeout), and returns only after all have exited.
    - **Rollout:** this change ships through the drain-based supervisor; start-then-drain takes effect from the next merge after it.

- **Self-update: migrate before the drain (decided 2026-11-07, issue #165).** After a successful build the supervisor asks the new folder's code which `npm run migrate` steps (schema or data) are still pending against the store (`node <folder>/dist/main.js migrate --status --json`). If any are pending it starts, drains and kills nothing: the old child keeps claiming with its settings, `supervisor.json` says `migration_pending` with the step names, and each poll checks again (no restart loop). Once the steps are gone (applied elsewhere), the next poll starts the new revision and drains the old one as usual. A newer commit replaces a waiting target (built and checked instead).
  - **`npm run migrate` while `dev` runs:** it sees a live supervisor (`supervisor.json`'s `supervisor_pid`) and writes `<state_dir>/supervisor-request.json` (`drain`). The supervisor reads and removes it on its next poll and drains every child; no child starts (`migration_draining`). Once none is live it reports `migration_ready`; only then does `migrate` apply the steps, and it writes `start` (or `cancel` if a step failed: the old revision starts again, the target keeps waiting). It gives up after `run_timeout_ms` plus the drain margin, with a `cancel` and nothing applied. A drain request with no update waiting migrates the running revision and starts it again. `--no-drain` applies without asking (the supervisor's own call). No live supervisor: it applies at once, as before.
  - **Crash fallback:** a child whose store refuses to open because steps are pending exits with the error code `migration_pending` (sent over IPC with its message). The supervisor treats that as a waiting migration on that revision, not a crash, and does not restart it until `npm run migrate` finishes.
  - **`updater.auto_migrate`** (in `factory.config.json`, default `false`): the supervisor drains every child, applies the steps itself (`migrate --no-drain`) once none is live, then starts the new revision. A failed apply starts the old revision again and is not retried automatically for that target. A breaking step always takes this path (decision of 2026-11-17 above).
  - **Status page:** banner states `migration_pending` ("Update to X waits for `npm run migrate` (pending: …). Still running Y with its settings."), `migration_draining` and `migration_ready`.

- **Build in place without breaking running processes (decided 2026-11-07; output rule changed 2026-11-14).** `npm run build` (`scripts/build.mjs`, no dependency) compiles into fresh staging folders beside the targets, `dist.build-<pid>-<n>` and `web/dist.build-<pid>-<n>` (same depth, so source map paths stay right): `tsc -p tsconfig.json` and `tsc -p tsconfig.migrations.json` with `--outDir` set to the staged `dist`, and `vite build --outDir <staged web/dist> --emptyOutDir`. Only when all three succeed does it take a short lock (`dist.swap-lock/`, made with `mkdir`, holder pid inside; a dead holder's lock is taken over) and swap each folder in: the live folder is renamed aside (`*.old-<pid>-<n>`), the staged one renamed to its name, then the old one deleted. So a failed build leaves the previous `dist/` and `web/dist/` untouched, and a live folder is missing only between two renames (no file is ever half-written). Concurrent builds (several `npm run factory -- <cmd>` at once) compile side by side and the last swap wins. Each build first removes staging and old folders whose pid is dead. A fresh staging folder per build keeps the guarantee that a deleted `*.plugin.ts` leaves no stale descriptor (`08-plugins.md`). `npm run factory` (when a build input changed), `migrate` and `setup` build first; a running `factory ui` keeps serving `web/dist` (same path, new files) and the supervisor's children run from their own version folders. The updater's version builds and the tests' `--outDir` builds to temp folders are unchanged; the updater counts `scripts/build.mjs` as code, so a change to it rebuilds. **Build output is shown only on failure (decision changed 2026-11-14):** each `tsc` and `vite` step runs with its output captured, so a successful build prints nothing (Vite's "chunks larger than 500 kB" warning no longer lands in front of every `npm run factory -- <cmd>` result, such as the id `task create` prints); a failed step prints its captured output to stderr, then the build exits non-zero. The chunk limit is unchanged. Whether the CLI builds at all is the freshness check above.
