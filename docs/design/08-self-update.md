# 8. Enterprise: self-update

- **Self-update (D7, decided 2026-11-01):** the factory runs from a runtime copy of `origin/<base_branch>` (`<state_dir>/runtime`, a detached git worktree), not from the checkout it was started in. State stays in the main checkout: `state_dir`, `worktrees_dir`, `repo.path`, the database, shared storage and the secret file; only code, `factory.config.json` and `prompts/` come from the runtime copy (`loadConfig` takes the code root explicitly; the supervisor passes it as `SOFTWARE_FACTORY_CODE_ROOT`). `dev` is a supervisor behind a new `Updater` plugin (`git-worktree` default, `none` = run in place as before). The new commit is built beside the running child first: a failed build must leave the old version running. Consequence: under `git-worktree`, uncommitted local edits, local branches and unpushed merges no longer affect `dev`. The main checkout is only fast-forwarded, and only when it is on the base branch and clean. (The single `runtime` copy and the drain order were replaced the same day; see start-then-drain below.)
  - **Self-update: start-then-drain.** Now the new child starts in the same poll step as its successful build, and only then is every older child asked to drain (the same IPC message). The old child stops claiming, finishes its in-flight runs from its own folder and exits by itself; poll never waits for it. It is hard-stopped (SIGKILL, logged as an error) only if it has not exited `run_timeout_ms` plus 60 s after the drain request, each child on its own timer. A draining child that exits is not a crash. This is safe because claims and state changes already go through the store with leases: during the overlap the old child's controller keeps running intake and the reaper until its worker drains, and both versions' workers claim through the same conditional updates.
    - **Folders:** each version runs from its own detached worktree, `<state_dir>/versions/<short-rev>` (12 characters; `-2`, `-3`... if that name is still held). The child's entry and `SOFTWARE_FACTORY_CODE_ROOT` point at its folder for its whole life, so a new version never changes files under a running one. A docs-only change fast-forwards only the newest folder. When a child starts, the supervisor writes its pid to `.factory-pid` in the folder.
    - **Installs:** `node_modules` lives in `<state_dir>/deps/<hash of package-lock.json>/node_modules`; each folder's `node_modules` is a link to the install for its lock file. A new lock hash runs `npm ci` in the new folder and moves the result into `deps/` through a temp name, so `deps/` only holds complete installs and a failed `npm ci` leaves nothing there. Old folders keep their install.
    - **Worker index ranges:** each child gets `SF_WORKER_INDEX_BASE`, the lowest block of `workers` indexes (read from the new folder's `factory.config.json`, the file the child reads) that no live child uses; the worker pool numbers its workers from it, so `SF_WORKER_INDEX` never collides between an old and a new child. Blocks are kept in supervisor memory: one supervisor per state directory is assumed and not guarded.
    - **Cleanup:** kept folders are those with a live child, plus the newest folder (or, while the newest has a live child, the newest built folder not already kept). Others are removed once their process has exited and no kept folder links into them: `git worktree remove --force`, then plain deletion if needed, then `git worktree prune`. An install is removed when no kept folder links to it. A failed build's folder is removed at once. On supervisor start, every folder whose pid file is missing or names a dead process is removed, except the newest one when its build matches `origin/<base_branch>` (a restart does not rebuild); a live pid keeps its folder. A reused pid makes an orphan look alive, so its folder stays until a later start (accepted). The first start under this layout removes the legacy `runtime/` and `runtime-next/` worktrees, once the sweep finds no live child.
    - **Shutdown:** SIGINT/SIGTERM to the supervisor sends SIGTERM to every live child, old and new (SIGKILL after the drain timeout), and returns only after all have exited.
    - **Rollout:** this change ships through the drain-based supervisor; start-then-drain takes effect from the next merge after it.

## History

- **Self-update** (D7, decided 2026-11-01). Order on a code change: build the new commit beside the running child first, then drain (IPC; the worker stops claiming and finishes its in-flight run), fast-forward, swap in the build, restart. This deliberately differs from "drain, update, build, restart": a failed build must leave the old version running. The drain-then-start order and the single `runtime` copy were replaced the same day.
- **Self-update: start-then-drain** (D7 changed 2026-11-01, issue #120). Before: drain-then-start. After a successful build the supervisor drained the running child and waited for it to exit before fast-forwarding `<state_dir>/runtime` and starting the new version, so one long run, up to `run_timeout_ms` (45 minutes), held every other worker idle after each merge.
