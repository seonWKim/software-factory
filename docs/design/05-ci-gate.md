# 5. Coordination: CI gate

- **Failed checks on an unchanged head loop again; a conflicting PR is updated first (decision changed 2026-11-08; before: see History).** Two changes to the Failed case below:
  - **Unchanged head.** A review the worker skips because the head is the one the last verdict was for (`no_agent: unchanged_head`) reads the PR's checks when that verdict passed. Failed: the same path as any failed checks (`checks_failed`, `loop_count + 1`, `RUNNING`, a new implement run; at `max_loops` a block on a human with `max_loops` and no run), with `unchanged_head: true` in the state change detail. The next implement prompt's "Failing CI checks to fix" section then adds `The previous attempt pushed no commit`. Pending or passed: only the ack, no field changes, as before. After a `bug` verdict nothing changes: a review_bug loop that pushes nothing still stops in `REVIEW` (follow-up issue). Items already stalled this way are swept by the periodic pass (decision changed 2026-11-08; before: not repaired, see History): `tickChecks` also lists up to 50 `REVIEW` items with `blocked_on: none`, skips any with a `blocked_reason` or a run that is queued, running or not yet applied, and when the last verdict before the latest succeeded review passed and the checks failed, applies the same failed-checks path (loop, `max_loops`, or the update first) through a conditional transition. Pending or passed checks change nothing, so a pending stalled item is read again on each tick, like an item waiting on CI.
  - **Conflict first.** When the checks failed on a factory PR whose stored merge check (§5 Merge check) is not mergeable for the reviewed head, no implement run starts yet: one update run is enqueued with the merge check's key (`<item>:update:<pr>:<head>:<base>`, `update_started`), and the item waits in `REVIEW` with `blocked_on: ci`, `blocked_reason: checks_failed_update` (a blocked reason, no new stage). The update counts no loop. Pushed: a review runs on the new head (`<item>:review:after-update:<run>`), and the gate applies again from there. Already up to date: the gate applies again to the same review, and since that update key has run, the failed checks start the implement run. A conflict or failing tests go the usual update ways (automatic resolve, `merge_conflict_pending`). No stored check, or one for another head: implement as before; the factory runs no new merge check for this. Solo and enterprise are the same.

- **CI gate.** Two parts:
  - **Workflow:** `.github/workflows/test.yml` runs on every pull request and every push to `main`: job `test` (`npm ci`, `npm run typecheck`, `npm test`) and job `test-mysql` (a `mysql:8` service, `npm test` with `SF_TEST_MYSQL_URL`). No secrets, `contents: read`. Branch protection on `main` requires the `test` check (SET_UP.md); that is a manual repository setting.
  - **Check gate in the controller:** when a review passes, the controller reads the PR's checks through the new optional `SourceAdapter.prChecks(pr_number)` → `pending` | `passed` | `failed` (with the failed names) before it decides. GitHub (`GitHubIssueSource`): the head commit's check runs (latest per name) and commit statuses; a conclusion other than success / neutral / skipped, or a status `failure` / `error`, is failed; anything unfinished is pending; no checks at all is passed, so a repository without CI is not held. A source without `prChecks` counts as passed.
    - **Passed:** `merge_pending` as before (`review_passed`, the merge comment keyed on the review run).
    - **Pending, or the source failed to answer:** the item stays in `REVIEW` with `blocked_on: ci`, `blocked_reason: checks_pending` (`checks_pending`; no new stage). `tickChecks` runs every `poll_interval_ms` on any replica, re-reads each waiting item and applies the gate again with the latest succeeded review run's id; still pending changes nothing.
    - **Failed:** treated like a review bug: `loop_count + 1`, `RUNNING`, an implement run keyed by `runKey` (`checks_failed`, detail `failed_checks` = JSON array of up to 20 names, each up to 100 characters, and `review_run_id`). At `max_loops` the item blocks on a human with `max_loops` instead. One comment, keyed on the review run, names the checks (G5-scanned; the names are dropped if the scan flags them). The next implement prompt gets a "Failing CI checks to fix" section, fenced as untrusted text, when the item's latest loop-starting change is `checks_failed`.
  - **Known gaps:** the status label for `blocked_on: ci` is `needs human` until `status-label.ts` maps it to `in review`; `setup` does not yet ask for the token's Checks and Commit statuses read permissions (SET_UP.md says to add them by hand). A push after the item reached `merge_pending` is not re-gated; branch protection covers it.
  - **No golden workflow; the golden replay is local only (new decision, 2026-11-08, issue #338).** No workflow replays the reviewer when a prompt changes, and no model credential goes into GitHub Actions secrets: `test.yml` is the only workflow and it still has no secret. The replay is `npm run factory -- golden compare --base <file>` on the developer's machine (§6, [06-measurement.md](06-measurement.md)), with the same inputs and exit codes everywhere: 1 when the comparison fails, 0 on a pass or a skip. Solo default and enterprise setting are the same: the person changing a prompt runs it before the merge; making it a required check is not possible without a CI credential, so it stays a reviewer's ask.
  - **Checks before push.** The same commands as the workflow's `run:` steps now run in the worker before the push (§4 Pre-push checks), so most failures are fixed before the PR exists. The CI gate itself is unchanged and still decides after the PR: it is the only place the MySQL tests run when `plugins.test_database` is `none`, and it covers pushes the factory did not make. `repo.check_commands` and the workflow's `run:` steps must match; `tests/check-commands.test.ts` fails on drift either way.

## History

- **Stalled items swept** (decision changed 2026-11-08). Before: "Items already stalled this way are not repaired." PR #399 stayed in `REVIEW` with failed checks and nothing polling it.
- **Failed checks on an unchanged head** (decision changed 2026-11-08). Before: a review that skipped an unchanged head was only acked, so an implement run of a failed-checks loop that pushed nothing left the item in `REVIEW` with no block and nothing polling it (PR #399); and the loop never looked at whether the PR conflicted with its base before implementing.
- **No golden workflow** (new decision, 2026-11-08, issue #338). Before: the issue proposed `.github/workflows/golden.yml` on pull requests touching `prompts/**`, with the model key as an Actions secret; the owner decided (2026-11-07) the replay runs locally only.

- **CI gate** (new decision, 2026-11-01). Before: a PR that passed review went straight to `merge_pending`, and GitHub ran no tests on PRs, so PR #51 merged with a failing test and nothing showed it.
- **Checks before push** (decision changed 2026-11-03, issue #158). Before: CI was the first place any check ran on an implement run's change.
