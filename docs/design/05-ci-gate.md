# 5. Coordination: CI gate

- **Red main per failing test: tests that fail on main too are main's; only the others count against the item (decision changed 2026-11-23; changes step 2 "Red main" of the 2026-11-16 decision below; before: see History).** Source: wi_c3cba3a9 (#772), seen 2026-11-22: its only failure was `tests/ui-health-page.test.tsx`, red on main since about 04:00Z and fixed by wi_74ef152e, and the check-name rule could not tell the item's own failures from main's inside the one `test` check. Red main now takes, in order:
  1. **Check names first:** the base head (`Forge.baseChecks`) must be failed and every failed PR check name must fail there too, as before; otherwise the normal path.
  2. **Then tests:** the gate reads the PR head's failed job log (`Forge.failedJobLog(head_sha)`) and the base head's (`Forge.failedJobLog` on `baseChecks`' `head_sha`) and compares their vitest `FAIL` tests (`failingTestDetails`). Every PR failing test also failing on main: the item waits on `main is red: <check>` (`main_red`, comment `main-red:<run>`) as before, no run and no loop. Any PR failing test that passes on main: not red; the item takes the rerun-once step and, failing again, goes back to implement (`checks_failed`), with the comment (`checks-failed:<run>`) and `ci_failing_tests` naming only its own failing tests.
  3. **Fallback:** a log that is not read (no `failedJobLog`, no head, or a read that throws, logged) or that names no test leaves the check names to decide, as before (owner answer 1).
  - **Reads:** the PR log is read at most once per decision, the base log at most once per `tickChecks` step, shared by every item that step decides like the base checks read; a review applied outside the step reads it once for its own decision. No new check run and no write to main: once main is green the gate goes on as before (rerun once, then merge or implement).
  - **Not changed:** rerun once, the unchanged-head and `max_loops` paths, merge-check runs, adopted PRs; items already blocked are not backfilled.

- **Rerun once: a head's first failure reruns its failed jobs; a second failure sends the failing tests to implement (decision changed 2026-11-18; changes step 4 "Otherwise" of the 2026-11-16 decision below and the Not detected line under it; before: see History).** Source: since 2026-11-11 failed checks sent items back to implement 8 times on 7 items with the check names only; wi_88435e43 (PR #699) stopped for a human to read a log whose failure was a flaky test that passed on a rerun. Failed PR checks on a factory PR now take a new step 3, between "Red main" and "Unchanged head" (those become 4 and 5); conflict first and red main still run before it, so a failure that takes either path is not rerun:
  3. **Rerun once:** when the forge has `rerunFailedJobs` and the review knows its head (`head_sha`), the first failure on that head reruns only the failed jobs, once, on the same head. The item waits in `REVIEW` with `blocked_on: ci`, `blocked_reason: checks_rerun` (a blocked reason, no new stage; `tickChecks` reads it like `checks_pending`). No run starts and `loop_count` does not move; one comment keyed on the review run (`checks-rerun:<run>`, G5-scanned) says so. Passed afterwards: `merge_pending` as if they had passed. Pending: it keeps waiting. Failed again on the same head: the next step, and back to implement as before. The rerun is recorded in the store with the item, as the `checks_rerun` state change whose detail `rerun_head` is the head, so a restart or another replica never reruns that head again; a new head gets its own single rerun. The rerun is the one forge write the kernel's reader allows (`ControllerReader.forge`).
  - **Failing tests to implement:** back to implement after that rerun, the implement run's input carries `ci_failing_tests`: the failed jobs' log (`Forge.failedJobLog`), cut to the vitest `FAIL` lines with each test's first error line (`failingTestDetails`), at most 10 tests and 4,000 characters (whole tests only), every name and message the egress scan flags redacted. The implement prompt shows it in the "Failing CI checks to fix" section, fenced as untrusted text. The state change and comment still name the checks.
  - **Today's path kept:** a forge without `rerunFailedJobs`, a review with no head, or a rerun that throws (logged; e.g. a token without the Actions write permission, or only a commit status failed, which has no job) takes the path as before: `checks_failed` with the names only, and no rerun is recorded. A forge without `failedJobLog`, or a log read that throws (e.g. a token without Actions read), sends the item back with the names only. No setting turns the rerun off: the optional forge methods decide it (owner answer 1).
  - **Not changed:** a merge-check run (design 05-merge-queue) and an adopted PR (it blocks on its author before any of these steps; owner answer 2). The status label for `blocked_on: ci` stays `needs human`. Two replicas deciding the same item at the same moment can both call the rerun before the record lands; the conditional transition keeps one decision, and the other re-decides with the record in place.
  - Not detected: failing tests outside the diff on a check that is not red on base, beyond what the failed job's log says.

- **A red base waits and an unchanged head blocks on a human; neither counts a loop (decision changed 2026-11-16; changes "Unchanged head" of the 2026-11-08 decision below; before: see History).** Source: work item wi_4baead09 (#369 golden cases), green locally, failed CI on a test it never touched because the base itself was red, and used four loops to reach `max_loops`. Failed PR checks on a factory PR now take the first of these that applies:
  1. **Conflict first:** the update run below, unchanged.
  2. **Red main** (changed 2026-11-23 above: per failing test)**:** when every failed PR check also fails on the base branch's head commit (`Forge.baseChecks`, the same summary rule as `prChecks`), the item stays in `REVIEW` with `blocked_on: ci` and `blocked_reason: main is red: <test>`, `<test>` the first failed name (`main_red`; detail `failed_checks`, `review_run_id`). No run starts and `loop_count` does not move; one comment keyed on the review run (`main-red:<run>`, G5-scanned) says why. `tickChecks` reads the item again each tick like `checks_pending`: still red changes nothing; base no longer red takes the normal failed-checks path (`loop_count + 1`, one implement run, or `max_loops`); checks passed go to `merge_pending`. Only some failed checks red on base: the normal path. The base is read only when PR checks failed, at most once per `tickChecks` step: every item that step decides shares the one read (items on one base head sha), held in memory for that step only; the store holds the wait itself. A review applied outside the step reads it once for its own decision. A base read that is pending, fails (logged), or a forge without `baseChecks`: not red, the normal path (owner decision, 2026-11-16).
  3. **Unchanged head:** a review the worker skipped because the head is the one the last verdict was for (`no_agent: unchanged_head`) with failed checks blocks on a human with `blocked_reason: unchanged_head` (`unchanged_head`; the state change keeps `unchanged_head: true`). No run starts and `loop_count` does not move, so an implement run that pushes nothing never loops to `max_loops`; one comment keyed `unchanged-head:<run>` asks a human to decide. The stall sweep below applies this path too.
  4. **Otherwise:** `loop_count + 1` and an implement run, or `max_loops`, as before.
  - The status label for the new wait stays `needs human` (`blocked_on: ci`). Step 4 "Otherwise" and its Not detected line changed 2026-11-18 (Rerun once, above).

- **Failed checks on an unchanged head; a conflicting PR is updated first (decision changed 2026-11-08; its "Unchanged head" part changed 2026-11-16 above).** Two changes to the Failed case below:
  - **Unchanged head.** A review the worker skips because the head is the one the last verdict was for (`no_agent: unchanged_head`) reads the PR's checks when that verdict passed. Failed: the red-main and unchanged-head paths above (changed 2026-11-16). Pending or passed: only the ack, no field changes, as before. After a `bug` verdict nothing changes: a review_bug loop that pushes nothing still stops in `REVIEW` (follow-up issue). Items already stalled this way are swept by the periodic pass (decision changed 2026-11-08; before: not repaired, see History): `tickChecks` also lists up to 50 `REVIEW` items with `blocked_on: none`, skips any with a `blocked_reason` or a run that is queued, running or not yet applied, and when the last verdict before the latest succeeded review passed and the checks failed, applies the same failed-checks rule (the update first, red main, or the unchanged-head block) through a conditional transition. Pending or passed checks change nothing, so a pending stalled item is read again on each tick, like an item waiting on CI.
  - **Conflict first.** When the checks failed on a factory PR whose stored merge check (§5 Merge check) is not mergeable for the reviewed head, no implement run starts yet: one update run is enqueued with the merge check's key (`<item>:update:<pr>:<head>:<base>`, `update_started`), and the item waits in `REVIEW` with `blocked_on: ci`, `blocked_reason: checks_failed_update` (a blocked reason, no new stage). The update counts no loop. Pushed: a review runs on the new head (`<item>:review:after-update:<run>`), and the gate applies again from there. Already up to date: the gate applies again to the same review, and since that update key has run, the failed checks start the implement run. A conflict or failing tests go the usual update ways (automatic resolve, `merge_conflict_pending`). No stored check, or one for another head: implement as before; the factory runs no new merge check for this. Solo and enterprise are the same.

- **Slowest test files on main (new decision, 2026-11-09, issue #469).** On a push to `main`, job `test` runs `npm test` with vitest's JSON reporter added (`--reporter=default --reporter=json --outputFile.json=<runner temp>/test-report.json`), then a step `node scripts/slowest-files.mjs <report>` that prints the 10 slowest test files, ranked by duration (`endTime - startTime` per file). The step runs with `if: always()`, so a failed test run still shows it, and it exits 0 when the report is missing or unreadable: it only informs, it never fails the job. A pull request runs the plain `npm test` step and no report, so the PR check costs nothing more and `tests/check-commands.test.ts` still matches that `run:` line against `repo.check_commands`. The push-to-main run is the periodic one; there is no scheduled workflow. Solo default and enterprise setting are the same; locally, run `npm test -- --reporter=json --outputFile.json=r.json`, then `node scripts/slowest-files.mjs r.json`. Why: nothing ranked the slow files, so the git-heavy ones (issue #469) went unnoticed.

- **CI gate.** Two parts:
  - **Workflow:** `.github/workflows/test.yml` runs on every pull request and every push to `main`: job `test` (`npm ci`, `npm run typecheck`, `npm test`; on a push to `main` with the JSON report and the slowest-files step above). No secrets, `contents: read`. Branch protection on `main` requires the `test` check (SET_UP.md); that is a manual repository setting.
  - **Check gate in the controller:** when a review passes, the controller reads the PR's checks through the new optional `SourceAdapter.prChecks(pr_number)` → `pending` | `passed` | `failed` (with the failed names) before it decides. GitHub (`GitHubIssueSource`): the head commit's check runs (latest per name) and commit statuses; a conclusion other than success / neutral / skipped, or a status `failure` / `error`, is failed; anything unfinished is pending; no checks at all is passed, so a repository without CI is not held. A source without `prChecks` counts as passed.
    - **Passed:** `merge_pending` as before (`review_passed`, the merge comment keyed on the review run).
    - **Pending, or the source failed to answer:** the item stays in `REVIEW` with `blocked_on: ci`, `blocked_reason: checks_pending` (`checks_pending`; no new stage). `tickChecks` runs every `poll_interval_ms` on any replica, re-reads each waiting item and applies the gate again with the latest succeeded review run's id; still pending changes nothing.
    - **Failed:** treated like a review bug: `loop_count + 1`, `RUNNING`, an implement run keyed by `runKey` (`checks_failed`, detail `failed_checks` = JSON array of up to 20 names, each up to 100 characters, and `review_run_id`). At `max_loops` the item blocks on a human with `max_loops` instead. One comment, keyed on the review run, names the checks (G5-scanned; the names are dropped if the scan flags them). The next implement prompt gets a "Failing CI checks to fix" section, fenced as untrusted text, when the item's latest loop-starting change is `checks_failed`.
  - **Known gaps:** the status label for `blocked_on: ci` is `needs human` until `status-label.ts` maps it to `in review`; `setup` does not yet ask for the token's Checks and Commit statuses read permissions (SET_UP.md says to add them by hand). A push after the item reached `merge_pending` is not re-gated; branch protection covers it.
  - **No golden workflow; the golden replay is local only (new decision, 2026-11-08, issue #338).** No workflow replays the reviewer when a prompt changes, and no model credential goes into GitHub Actions secrets: `test.yml` is the only workflow and it still has no secret. The replay is `npm run factory -- golden compare --base <file>` on the developer's machine (§6, [06-measurement.md](06-measurement.md)), with the same inputs and exit codes everywhere: 1 when the comparison fails, 0 on a pass or a skip. Solo default and enterprise setting are the same: the person changing a prompt runs it before the merge; making it a required check is not possible without a CI credential, so it stays a reviewer's ask.
  - **Checks before push.** The same commands as the workflow's `run:` steps now run in the worker before the push (§4 Pre-push checks), so most failures are fixed before the PR exists. The CI gate itself is unchanged and still decides after the PR: it covers pushes the factory did not make. `repo.check_commands` and the workflow's `run:` steps must match; `tests/check-commands.test.ts` fails on drift either way.
