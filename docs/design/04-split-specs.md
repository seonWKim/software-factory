# 4. Agents: split specs

**A phase already done on the base closes as completed with no merge sha (decision changed 2026-11-28, wi_0bab8381; see History).** A phase's implement run with no commits that answers `already_done` and passes the checks on the base closes the phase `CLOSED` / `completed`, `merge_sha` null (04-pre-push-gates). Nothing else changes: completed releases the next held phase, the last phase closing completed closes the parent (`closeSplitIfDone`, merge sha null), the linked task completes (`sql/tasks.ts`), and a goal split queues no judge for a phase with no merge sha.

**The one-time cap lives only in the `size_cap_approved` record; the `size_cap` column is gone (decision changed 2026-11-24, phase 4 of local-task-tk_8bb1417c; replaces "the item's `size_cap`, a new nullable JSON column" in the decision below, see History).** Before it, an over-cap approval also wrote the cap to `controller_work_items.size_cap` (migration `20261124T1100-controller-size-cap`), duplicating its record. Now `overCapApproval` sets no field; `sizeCaps` (`src/core/size-cap.ts`) takes the item's state changes and uses the `one_time_cap` of its latest `size_cap_approved` record, else the project caps. Every size reader reads them so, including `overCap`. The migration is removed; a database that has the column keeps it unused, and items approved before keep their cap from their record, with no backfill.

**The dashboard's over-cap Approve asks for the note, and `/approve` lists `too_large` (decision changed 2026-11-24, phase 3 of local-task-tk_8bb1417c; replaces "`/approve` at `too_large` is accepted but is not one of its listed phases" in the decision below, see History).** Before it, a Needs you Approve on an over-cap item sent at once with no note, and the controller refused it in the thread, so the owner typed it again; at `too_large`, `/help`, the footers, the `SET_UP.md` table and the dashboard left Approve out. Now `too_large` is one of `/approve`'s phases (`src/core/commands.ts`), so every surface lists it; its `SET_UP.md` row adds that an over-cap `/approve <why>` needs a note and that the dashboard's Approve opens a dialog for it (`table_note`: the help replies keep the shorter text, as Slack's first section is full). The item API's Approve row carries `over_cap` (the size, the caps in force and the proposed one-time cap, `OverCapSizes`) only when `overCap` finds the item over its caps; the Needs you Approve then opens a note dialog (design 09-dashboard-item-commands) and sends the note as `factory approve <id> <why>` does. The controller, the size cap logic and the refusal text are unchanged. Not changed: the item page's own Approve (a follow-up).

**An over-cap `/approve` needs a note and stores a one-time size cap with its `size_cap_approved` record (decision changed 2026-11-24, phase 2 of local-task-tk_8bb1417c; replaces "Nothing writes a one-time cap yet" and "`/approve` implements it as one change" in the 85% threshold below, see History).** Before it, `/approve` at the size checkpoint started the implement run on the project's caps and stored nothing about who approved the size or why, and at `too_large` only `/retry` (same caps) or `/revise` applied. Now an `/approve` over the item's caps (`overCap` in `src/core/split.ts`: at the spec gate a spec at its size checkpoint, sized by its estimate; at `too_large` the blocked diff, sized from its run's failure detail) proposes a one-time cap. At the spec gate it is the estimate itself (`estimateCap`), each cap never below the cap in force: the estimate is the size the owner approves, and the floor keeps a count the estimate is under (often the files) from being lowered. At `too_large` it is `proposedCap`: each cap raised just enough that the blocked diff is within 85% of it, never below the cap in force, since a rerun's diff differs from the blocked one and needs room. With no note it is refused in one reply naming the size, the caps and the proposed cap, and nothing is stored (`overCapNoteRequired`, `src/core/size-cap.ts`); at `too_large` a run that recorded no size is refused too, since no cap can be proposed. With a note, `overCapApproval` (`src/core/size-cap.ts`) adds to the approval's own transition the detail `size_cap_approved`, JSON of the actor, the sizes, the project cap, the one-time cap and the note. At the spec gate that transition is `spec_approved`; at `too_large` it is `/retry`'s (`retry_requested`, the implement run keyed as `/retry`'s, restart_count + 1). Later size readers get the one-time cap from that record through `sizeCaps` (the decision above). The size checkpoint note and the too_large comment (its size section, `suggestedSplit`) name `/approve <why>` with the size, the caps and the proposed cap. `/approve` at `too_large` is one of its listed phases (the decision above). `factory approve <id>` runs the same check before storing anything, with the same refusal text, reading the caps as the controller does (`storedProjectCaps`: the file's layers, the stored overrides, the learned layer); the dashboard's Approve leaves an over-cap approval to the controller instead of applying it at request time, and its Needs you Approve asks for the note first (the decision above). One command for every limit: no per-limit command. Solo and enterprise: no new column or table, no network call.

**A judge's `fix` files a fix phase under the goal, up to 2 before the owner decides (decided 2026-11-23, phase 3 of the goal split; a new decision, none replaced).** Before it, a `fix` verdict stopped the goal as a goal question and nothing filed the fix. The owner's answers: fix phases are local tasks (1); a judge that cannot tell whether a goal line holds answers `fix`, as `prompts/judge.md` says (2); the cap is 2 (3); `/approve` at the cap or on a question files the proposed fix phase (4); `next` on the last recorded phase asks the owner (5). Now a `fix` verdict (`judgeDecision`, `src/controller/units/phases/phases.unit.ts`) files the fix as a new phase row under the parent: a local task (`<parent source id>-phase-<n>`, no network call), the next phase number after the last recorded phase, held after that phase (`phase_hold`), its title, problem, done criteria and allowed paths the judge's. The parent records one `goal_phase_added` state change (detail: the judged phase, the verdict and reason, `applied: fix`, the `fix_*` fields, `added_phase`, `sub_issue`: the new row's source id) and stays `READY` / `phases_open`; `recordedPhases` and `closeSplitIfDone` read the recorded phases as the last `split_approved`'s `sub_issues` followed by each later `goal_phase_added`'s `sub_issue`. A `fix` lets the goal go on past the judged phase, so a phase still held after it starts as after `next`, and the fix phase starts once the phase before it closes completed and is judged; it is judged like any phase, so a fix on the last phase never closes the goal. Each goal files at most 2 fix phases on its own (`FIX_PHASE_CAP`, counted from its `goal_phase_added` changes): a third `fix` records the verdict (`applied: goal_limit`, its `fix_*` fields kept) and sets the parent to `blocked_on: human`, `blocked_reason: goal_limit` with one comment stating the fix phases filed so far, the cap and the proposed fix phase's title. `/approve` on `goal_limit` or `goal_question` (`approveGoal`, called from the commands unit before the spec gate) reads the latest `judge_verdict` or `judge_failed` change: with a fix (`fix_*`) it files that fix phase as above, past the cap too, under the owner as actor; with none it records a `judge_verdict` with `applied: next` on the judged phase, so the next held phase starts, and on the last recorded phase it is refused with a reply naming `/reject <reason>`. `/reject` there closes the goal rejected, as at any open phase. An `ask` stays a goal question, since only the owner can decide it. Every verdict is a message in the goal's thread: `next` and `done` get one comment each (keyed `goal-verdict:<parent>:<phase>`), each fix phase one (`goal-phase:<parent>:<n>`), and a question or the cap one (`goal-question`, `goal-limit`). Every step re-reads the store, the row is keyed on its derived ref and each comment on its key, so a second pass or replica files nothing twice. Solo and enterprise: no new table, setting or migration.

**A judge checks a goal split after each merged phase (decision changed 2026-11-23, phase 2 of the goal split; replaces the goal-lines decision's "Not built yet: a judge" clause, see History).** Before it, nothing read a split's goal lines: `closeSplitIfDone` closed a goal split as completed once its last recorded phase closed completed with a merge sha, and each held phase started once the phase before it closed completed. Now, on a split whose `split_approved` stores `goal_done_when`, the phase tick (`judgePhases`, `src/controller/units/phases/phases.unit.ts`) queues one `judge` run on the parent for each recorded phase that closed completed with a merge sha, keyed `judge:<parent id>:<phase>`, in a conditional transition (`judge_queued`, detail: the phase and its merge sha) that re-reads the parent's runs first, so a second pass or replica queues nothing for that phase and an automatic retry (`:a<n>`) counts as its run. The run's input holds the goal lines, the phase's title, problem and done criteria, its merge sha and the recorded phases' titles in order. The `judge` run kind (`src/worker/runs/judge/`) runs the `judge` role (`src/worker/roles/judge.role.ts`): `prompts/judge.md`, read-only tools (`Read`, `Glob`, `Grep`), no kept session, a folder at the base (the phase is merged there), and it proposes only a verdict. The runner pins it to `strong` whatever the tier, since `model_by` lists only the four agent kinds and stays as it is. Its answer is `{ verdict, reason, fix? }`: verdict one of `next`, `fix`, `done`, `ask`; a `fix` needs a title, a problem, at least one done criterion and at least one allowed path (`JUDGE_SCHEMA` beside the run, `parseJudge` in `src/core/outputs.ts`). The controller applies it (`judgeResult`), acked in the same transition and its tokens added to the parent's `token_cost`, and records one `judge_verdict` state change on the parent with the phase, the verdict, the reason and the verdict as `applied`. `next` on a phase before the last: no phase row is added and the tick releases the next held phase, which on a goal split waits for this verdict. `done` on a phase before the last is applied as `next`, so the goal never closes early. `done` on the last recorded phase: `closeSplitIfDone` closes the parent completed with that phase's merge sha, and its close comment says the judge found the goal's lines met (detail `goal_met`). `fix`: a fix phase is filed, as the decision above says. `ask` on any phase, or `next` on the last: the parent waits on the owner (`blocked_on: human`, `blocked_reason: goal_question`) with one comment keyed per phase, no phase row is added, the next phase stays held and nothing closes. An answer that fails `parseJudge`, and any failed judge run, is retried as an invalid triage answer is (`retryOrBlock`, `invalid_output`, the retry keeping the run's input); the phase stays closed. A judge run that reaches a retry limit (`max_attempts`, a repeated or recurring failure) does not block the parent as a dead run, which would drop it out of `phases_open` where no tick or `/retry` reaches it: the parent records `judge_failed` (the phase, the limit, the last error) and stops as a goal question (`blocked_on: human`, `goal_question`) with the same one comment per phase, so the owner's answer on the goal lifts it. A split without goal lines queues no judge and closes as before. A goal split with no `prompts/judge.md` in any pack: its judge run fails with `prompt_missing` before any agent runs, the parent records `judge_skipped` for that phase, and the split goes on and closes as before; the controller is not handed the prompts, so the run is queued and asks no model. The judge's state lives only in the store (the run key and the parent's state changes); every handler re-reads it and is safe to run twice. Not built yet: showing the verdict on the spec comment or the item page, and backfilling phases closed before this change. Solo and enterprise: one new run kind on the existing runs table, no new table or migration, no network call.

**A split spec may carry goal lines, stored on its approval and listed in its split comment (decided 2026-11-22, wi_fe05f6b9; a new decision, none replaced).** Before it, triage's answer had no goal field, and the approval recorded only the phase ids on the parent's `split_approved` detail (`sub_issues`), so what the whole split was for was not kept. Triage's answer now takes an optional `goal_done_when`: a list of non-empty lines saying what the whole split must do once every phase merged, in order. It is read only on a split spec: absent or empty is no goal, and a non-empty list on an answer without phases is an invalid answer (`parseTriage`, `parseGoalLines` in `src/core/split.ts`), retried like any `invalid_output`; tool-call markup in a line is refused as in every other field. The approval's end (`advanceSplit`) reads the lines from the same triage run that holds the phases, stores them on `split_approved` under `goal_done_when` as a JSON array in order (left out when there are none), and the split comment on the parent lists them in order after the phase list, under "The whole split is done when:" (for local tasks, after the line listing them). A split without goal lines behaves exactly as before. Not built yet: showing the lines in the spec comment at the gate, and backfilling splits approved before this change. Solo and enterprise: the same detail on the store, no new table, no migration, no network call.

**A split parent closes once every recorded phase is closed, whatever each phase's close reason; the last phase decides how (decision changed 2026-11-18; replaces "the parent closes only when every recorded phase is `CLOSED` / `completed`; a phase closed any other way keeps the parent open", see History).** The decision that changed: the parent's close in "The phase hold" below. Found 2026-11-18: wi_34339813 (#317) sat at `phases_open` from 2026-11-07 because its phase 3 was rejected (its work landed as #369) while phases 1, 2 and 4 merged, so the three items waiting on it in a chain never started. On every poll `tickPhases` runs `closeSplitIfDone` on each `phases_open` parent; once every phase its approval recorded exists and is `CLOSED`, the last recorded phase (the highest phase number, `lastPhase`) decides: closed `completed`, the parent gets one comment starting "Closed because", its issue is closed as completed, and it goes `CLOSED` / `completed` with that phase's `merge_sha` (null when the phase has none; state change `split_completed`, detail `phases`, `completed`); closed any other way, the comment says the last phase closed without a merge, the issue is closed as not planned, as a rejected item's is, and the parent goes `CLOSED` / `rejected` (`split_rejected`). Either way its dependents are re-checked from the store in the same pass (design 05-dependencies): they are released when it closed completed, and get the `dependency_closed` hold when it closed rejected. A parent already at `phases_open` needs no migration: the next poll applies the rule. Unchanged: a phase after a rejected phase is still released only by a human `/retry`, and no phase is merged automatically.

**A split spec is approved on an item from any source (decision changed 2026-11-12; replaces "a source with no `fileSubIssue` refuses the approval" and "Not built: Slack" below).** When the parent's source cannot file sub-issues (a Slack thread, or no adapter for its type in this process), `/approve` no longer refuses ("this source cannot file sub-issues, so a split spec cannot be approved here" is gone): the phases are filed as local tasks. The claim records `filing: local` in its detail, so every pass and replica files the same way; `advanceSplit` then takes each phase in at once, with no outbound action and no network call, as a local work item whose source id is derived like `LocalSource.fileSubIssue` derives it (`<parent source id>-phase-<n>`), linked to the parent through `parent_id` and `phase`, held after the first (`phase_hold`). A retry derives the same ids, so it finds the rows already taken in. The parent's thread gets no "filing is queued" reply, only one line listing the local tasks in phase order, written as a thread message like any comment, so outbound posts it to Slack. The phase chain, the hold, `phases_auto_approve` and the parent's close as completed are unchanged. Sources with `fileSubIssue` (GitHub, local) file as before. Solo: no account beyond the parent's source. Enterprise: the same rows on the shared store, read by every replica.

**Phases are filed through outbound (decision changed 2026-11-09, RFC 0015 M7; see History).** `/approve` on a split spec claims the filing (`split_filing`, below), replies that the filing is queued ("`/approve` was applied: the factory is filing the N phases of this split as sub-issues of this issue, one at a time ..."), and records phase 1 as an outbound action `file_sub_issue` to the parent's source (title, body, marker, phase number), keyed `file_sub_issue:<parent>:<phase>:<approving comment id>`, so it is stored once. Outbound files it through the parent's source (`github-issue` for GitHub, the `local` target through `LocalSource.fileSubIssue`, `source` for another adapter), under its service passport, egress-scanned (a flagged title or body is filed as the withheld notice, keeping its marker), and records the filed item's id and link on the action (`delivered_ref`, `delivered_url`). Phase N+1's body names phase N's ref, so it is recorded only on phase N's `DeliveryCompleted`: the phases unit (`advanceSplit`) takes phase N in as a work item (held after the first, as below) and records the next filing. With every phase taken in, the parent gets the split comment listing them and waits on them (`split_approved`, `phases_open`). `advanceSplit` works only from the store (the parent's phases, the claim, the keyed actions), so it is safe to repeat: the phase tick runs it for a parent still at `split_filing`, which resumes a filing whose step was lost (a crash after the claim, a lost `DeliveryCompleted`). Never filed twice: the key stores each phase's filing once per approval, and a retry after a lost response finds the issue by its marker (GitHub: the parent's sub-issues, then the newest labelled issues; local: the ref is derived from the marker). A failure (an outage, a rate limit) is outbound's retry with backoff, no longer a refused `/approve`; the parent's later messages wait behind it in its destination order. A filing the source refuses for good (an HTTP 4xx such as a locked or deleted parent) is given up on its third attempt: outbound raises its dead-letter alarm (Needs you), and the parent goes to `blocked_on: human`, `blocked_reason: delivery_failed` (state change `delivery_failed`, detail `action`, `phase`, `phases`, `error`) with one comment saying how many phases were filed. The parent then waits like a spec at the gate (`/revise` and `/reject` apply too), and `/approve` claims the filing again under its own comment id: the phases already taken in are kept, the rest are filed under new keys, none twice. `/approve` while a filing is queued is refused ("an earlier `/approve` queued this split's phases for filing"); the stale-claim takeover is gone, since a stopped process leaves its filing to outbound and the phase tick. Solo: the `local` source alone; outbound's `local` target files with no network call. Enterprise: the same, with the actions on the shared store; any replica's outbound with the source adapter delivers them.

**Local tasks split too** (decision changed 2026-11-07; current): its text moved to History, unchanged, to keep this file under its size cap.

**One approval files a split** (decision changed 2026-11-07; current): its text moved to History, unchanged, to keep this file under its size cap.

**Only recorded phases count (decision changed 2026-11-07).** Releasing the next phase and closing the parent read only the phases its approval recorded (`sub_issues` of the last `split_approved`). A duplicate sub-issue linked to the same parent, filed by a racing approval and closed by hand, neither holds the next phase nor keeps the parent open.

**Phase issues read first (decision changed 2026-11-07, issue #229).** A phase issue's title is `Phase N/M: <title>`, and a leading "Phase N:" (or "Phase N/M:") the model already wrote is dropped, so it never repeats. Its body opens with `## In short` (the phase number and the first sentence of its problem), then `Part of #<parent>` and the phase it waits for as `#<n>`, then Problem, Done when and Allowed paths. A factory close posts one line that starts with "Closed because" (a rejected spec, a budget-checkpoint `/reject`, all phases of a split done).

**Split specs.** Four decisions changed:
- **Triage output.** Triage now returns `estimated_lines` and `estimated_files` (required integers, 0 or more; an answer without them is `invalid_output` and is retried like any invalid answer, which includes runs started before this change) and an optional `phases` list: 2 to 4 phases in merge order, each with a title, a problem, at least one done criterion and at least one allowed path. An empty list means no split. The estimate is the agent's, made before any code exists, so it can be off; code checks only that the phases are there and well formed.
- **The 85% threshold.** An estimate over 85% of either cap (`SPLIT_PERCENT` in `src/core/split.ts`, the one place it is defined, computed from the item's configured `max_diff_lines` and `max_diff_files`: with the defaults, over 1275 lines or over 34 files) with no phases waits at the spec gate, at its size checkpoint (decision changed 2026-11-23, phase 1 of local-task-tk_8bb1417c; replaces "is rejected unless it has 2 to 4 phases", see History). The controller applies it when it reads the triage outcome (`atSizeCheckpoint` in `src/core/split.ts`, in the triage branch of `run-results.unit.ts`): the spec is posted with a note above its footer (`sizeCheckpointNote`: the estimate, the threshold, the caps) saying `/approve <why>` implements it as one change under a one-time cap (decision changed 2026-11-24, see the first decision of this file) and `/revise <feedback>` asks for 2 to 4 phases. It waits whatever its tier, and `phases_auto_approve` never approves it. A spec with 1 phase or more than 4 is still refused (`parseTriage` with the caps); the worker checks the shape only. The caps are the item's size caps, read through one function, `sizeCaps` in `src/core/size-cap.ts`: the one-time cap of the item's latest `size_cap_approved` record when it has one, else the project's `max_diff_lines` and `max_diff_files`. Every size reader of one item calls it: the session's diff gates, the implement run's limits and pre-push gate, and the triage check and size-checkpoint text in run-results. Only an over-cap `/approve` writes a one-time cap (that record, since 2026-11-24); every other item uses the project settings. A spec under the threshold without phases renders exactly as before; a spec with phases adds a "Split into phases" section (each phase's title, problem, done criteria and allowed paths, in order) before the command footer. A split spec always waits at the spec gate, whatever its tier, because its `/approve` files issues.
- **`/approve` on a split spec.** It files one sub-issue per phase, in order, through `SourceAdapter.fileSubIssue` (GitHub: an issue with the intake label, its body naming the parent and the phase it waits for, linked under the parent with the sub-issues API), and takes each in as a work item at once, requested by the approver, with a `detail` on its `intake` row (`parent_work_item_id`, `phase`, `phases`, `depends_on`: the previous phase's source id). Each filed issue carries a marker per (parent, phase), `<!-- factory:phase:<parent id>:<n> -->`; filing looks it up first (the parent's sub-issues, then the newest factory-labelled issues), and intake is keyed on the source, so a retry files no duplicates. A failure is outbound's retry (see the first decision above). Intake ignores an issue whose body carries a phase marker: the split takes it in, so the bot's own issues never start un-held. On success the parent gets one comment listing the phases and waits in `READY` with `blocked_on: upstream` / `blocked_reason: phases_open` (state change `split_approved`, detail `sub_issues`: the phases' source ids in order). The parent is never implemented. Each phase is an ordinary work item with its own triage spec and its own `/approve`. `/revise` on a split spec runs triage again; the new spec may or may not be a split.
- **`phases_auto_approve` (decided 2026-11-07).** A live setting (`npm run factory -- settings set phases_auto_approve true`, or the top-level file key; default `false`). When on, the owner's `/approve` of the split covers its phases: a phase whose parent still waits on its phases (`phases_open`) goes from triage straight to implement (`triaged_phase_approved`, detail `parent_work_item_id`). Its spec is still posted, with a line saying why no `/approve` is needed. A phase already waiting at `spec_pending` when the setting is turned on is approved on the next `tickPhases` (`phase_spec_auto_approved`). A phase whose own spec is a split, a phase whose spec waits at its own size checkpoint (over 85% of a cap with no phases; decision changed 2026-11-23, see the 85% threshold above; checked in `approvedByParent`, so in the triage branch and in the phase tick alike), an item that is not a phase, and a phase whose parent is no longer `phases_open` still wait for a human. The split comment on the parent says which way the phases go. Only spec approval changes: the merge gate and the tier floors stay as they are.
- **The phase hold.** **`/retry` releases a held phase whose previous phase closed without a merge (decision changed 2026-11-12; replaces "a phase closed any other way keeps the next phase held" with no command to lift it; see History).** A held phase is its own command phase (`phase_hold`, "held: waiting for the previous phase of its split"), where `/retry` applies. `/retry` there releases the phase into triage (state change `retry_requested`, detail `released: phase_hold`, `parent_work_item_id`, `phase`, `depends_on`: the previous phase's source id, `close_reason`: its close reason, and the note if any; triage queued under the intake key) when the previous phase is `CLOSED` any way: rejected, won't do, or completed before the pass ran. While the previous phase is still open, `/retry` changes nothing and replies that it must close as completed first. The automatic release below is unchanged: only a human `/retry` releases a phase after a previous phase closed without a merge, since the owner decides whether the rest of the split still applies. Phases already held when this shipped need no data change. The first phase is queued for triage at once. Each later phase starts `NEW` with `blocked_on: upstream` / `blocked_reason: phase_hold` and no run (no new stage). On every poll, after its closes are applied, the controller (`tickPhases`) releases a held phase whose previous phase is `CLOSED` / `completed` (`phase_released`, triage queued under the intake key) and closes a `phases_open` parent whose recorded phases are all `CLOSED`, as the first decision of this file says (since 2026-11-18). A phase closed any other way keeps the next phase held. The bot closing the parent as completed is a new outward action. Both steps re-read the store and are safe to repeat on any replica. Ordering beyond "wait for the previous phase" is out of scope.

Store: one migration, SQLite 13 (`work-item-phases`): `work_items.parent_id` and `phase`, with an index on both. A phase is created with its parent's id and its place in merge order (`NewWorkItem.parent`; store-owned, never changed by a transition), and `FactoryStore.listPhases(parent)` returns a parent's phases in phase order. The controller finds a held phase's previous phase and a parent's phases through it; the `intake` and `split_approved` details stay as the audit trail, and the `split_approved` detail says how many phases the approval filed. The hold is in `blocked_on` / `blocked_reason`; `createWorkItem` takes an optional `hold` and an intake `detail`. Status labels: a held phase and a `phases_open` parent show "needs human", the label for any non-human blocker; a label of their own is not in this change.

The size checkpoint now suggests a split: after `diff_too_large`, the comment adds "Suggested split", 2 to 4 phases built from the diff size (the counts in the size gate's detail) and the item's allowed paths, grouped by folder, never the code. It is computed in the controller (`suggestSplit` in `src/core/split.ts`), so it runs no agent and costs no tokens. The work item asked for a short triage-role step reading the changed paths; that needs the worker to put the changed paths in the failed outcome (and to run the step), and `src/core/worker.ts` and `src/core/diff-gate.ts` were outside this change's allowed paths. Until then the suggestion groups the item's allowed paths, the only paths the controller has. A reviewer can use the suggestion as the phases of a split spec through `/revise`. Not changed: the caps, floors, tiers, the human merge gate, Slack intake (GitHub only), splitting an item that is already running, and merging any phase automatically.
