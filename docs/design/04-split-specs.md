# 4. Agents: split specs

**A split spec is approved on an item from any source (decision changed 2026-11-12; replaces "a source with no `fileSubIssue` refuses the approval" and "Not built: Slack" below).** When the parent's source cannot file sub-issues (a Slack thread, or no adapter for its type in this process), `/approve` no longer refuses ("this source cannot file sub-issues, so a split spec cannot be approved here" is gone): the phases are filed as local tasks. The claim records `filing: local` in its detail, so every pass and replica files the same way; `advanceSplit` then takes each phase in at once, with no outbound action and no network call, as a local work item whose source id is derived like `LocalSource.fileSubIssue` derives it (`<parent source id>-phase-<n>`), linked to the parent through `parent_id` and `phase`, held after the first (`phase_hold`). A retry derives the same ids, so it finds the rows already taken in. The parent's thread gets no "filing is queued" reply, only one line listing the local tasks in phase order, written as a thread message like any comment, so outbound posts it to Slack. The phase chain, the hold, `phases_auto_approve` and the parent's close as completed are unchanged. Sources with `fileSubIssue` (GitHub, local) file as before. Solo: no account beyond the parent's source. Enterprise: the same rows on the shared store, read by every replica.

**Phases are filed through outbound (decision changed 2026-11-09, RFC 0015 M7; see History).** `/approve` on a split spec claims the filing (`split_filing`, below), replies that the filing is queued ("`/approve` was applied: the factory is filing the N phases of this split as sub-issues of this issue, one at a time ..."), and records phase 1 as an outbound action `file_sub_issue` to the parent's source (title, body, marker, phase number), keyed `file_sub_issue:<parent>:<phase>:<approving comment id>`, so it is stored once. Outbound files it through the parent's source (`github-issue` for GitHub, the `local` target through `LocalSource.fileSubIssue`, `source` for another adapter), under its service passport, egress-scanned (a flagged title or body is filed as the withheld notice, keeping its marker), and records the filed item's id and link on the action (`delivered_ref`, `delivered_url`). Phase N+1's body names phase N's ref, so it is recorded only on phase N's `DeliveryCompleted`: the phases unit (`advanceSplit`) takes phase N in as a work item (held after the first, as below) and records the next filing. With every phase taken in, the parent gets the split comment listing them and waits on them (`split_approved`, `phases_open`). `advanceSplit` works only from the store (the parent's phases, the claim, the keyed actions), so it is safe to repeat: the phase tick runs it for a parent still at `split_filing`, which resumes a filing whose step was lost (a crash after the claim, a lost `DeliveryCompleted`). Never filed twice: the key stores each phase's filing once per approval, and a retry after a lost response finds the issue by its marker (GitHub: the parent's sub-issues, then the newest labelled issues; local: the ref is derived from the marker). A failure (an outage, a rate limit) is outbound's retry with backoff, no longer a refused `/approve`; the parent's later messages wait behind it in its destination order. A filing the source refuses for good (an HTTP 4xx such as a locked or deleted parent) is given up on its third attempt: outbound raises its dead-letter alarm (Needs you), and the parent goes to `blocked_on: human`, `blocked_reason: delivery_failed` (state change `delivery_failed`, detail `action`, `phase`, `phases`, `error`) with one comment saying how many phases were filed. The parent then waits like a spec at the gate (`/revise` and `/reject` apply too), and `/approve` claims the filing again under its own comment id: the phases already taken in are kept, the rest are filed under new keys, none twice. `/approve` while a filing is queued is refused ("an earlier `/approve` queued this split's phases for filing"); the stale-claim takeover is gone, since a stopped process leaves its filing to outbound and the phase tick. Solo: the `local` source alone; outbound's `local` target files with no network call. Enterprise: the same, with the actions on the shared store; any replica's outbound with the source adapter delivers them.

**Local tasks split too (decision changed 2026-11-07).** With only the `local` source, `factory approve <parent>` on a split spec files each phase through `LocalSource.fileSubIssue` (outbound's `local` target since 2026-11-09), which derives the sub-task's source id `<parent source id>-phase-<n>` from the parent and the phase marker, with no network call. The controller's split path is unchanged: it creates each phase as an ordinary local work item keyed on that source, with `parent_id` and `phase`, holds the later ones (`phase_hold`), stores the split comment as an item message, and the parent waits on `phases_open` until the last recorded phase closes as completed; its "Closed because" comment is an item message too. A retry after a failure derives the same ids, so it finds the rows already filed. `factory task show <id>` and the item page list a task's sub-tasks in phase order (ID, title, stage, blocked reason; the page links each to its own page; "(none)" without any). No table and no migration: the store's `parent_id`, `phase` and `listPhases` are enough. Solo: `source: local` alone, no account. Enterprise: the same rows on the shared store, read by every replica. Not built: nested sub-tasks, adding a sub-task by hand. (Slack: since 2026-11-12, a Slack thread's phases are local tasks, see the first decision.)

**One approval files a split (decision changed 2026-11-07).** `/approve` on a split spec first claims the filing with a conditional transition of the parent to `READY` / `blocked_on: upstream` / `blocked_reason: split_filing` (state change `split_filing`, detail `comment_id` and `phases`). Only the pass whose transition wins files the phases; a pass that loses to the same command does nothing and posts nothing, and one that loses to another `/approve` is refused. Filing reuses a phase that already has a work item under the parent (`listPhases`) before the marker lookup, and the claim ends with `split_approved` (`phases_open`), conditional on the claim, or with `delivery_failed` (above). Cause: #172 and #252 each had phases 2..N filed twice because the old process, while draining after a code change, kept polling next to its successor; both applied the same `/approve` at once, and the marker lookup (the parent's sub-issues, then labelled issues) did not see the issue the other pass had filed moments before.

**Only recorded phases count (decision changed 2026-11-07).** Releasing the next phase and closing the parent read only the phases its approval recorded (`sub_issues` of the last `split_approved`). A duplicate sub-issue linked to the same parent, filed by a racing approval and closed by hand, neither holds the next phase nor keeps the parent open.

**Phase issues read first (decision changed 2026-11-07, issue #229).** A phase issue's title is `Phase N/M: <title>`, and a leading "Phase N:" (or "Phase N/M:") the model already wrote is dropped, so it never repeats. Its body opens with `## In short` (the phase number and the first sentence of its problem), then `Part of #<parent>` and the phase it waits for as `#<n>`, then Problem, Done when and Allowed paths. A factory close posts one line that starts with "Closed because" (a rejected spec, a budget-checkpoint `/reject`, all phases of a split done).

**Split specs.** Four decisions changed:
- **Triage output.** Triage now returns `estimated_lines` and `estimated_files` (required integers, 0 or more; an answer without them is `invalid_output` and is retried like any invalid answer, which includes runs started before this change) and an optional `phases` list: 2 to 4 phases in merge order, each with a title, a problem, at least one done criterion and at least one allowed path. An empty list means no split. The estimate is the agent's, made before any code exists, so it can be off; code checks only that the phases are there and well formed.
- **The 85% threshold.** An estimate over 85% of either cap (`SPLIT_PERCENT` in `src/core/split.ts`, the one place it is defined, computed from the item's configured `max_diff_lines` and `max_diff_files`: with the defaults, over 1275 lines or over 34 files) is rejected unless it has 2 to 4 phases. The controller applies it when it reads the triage outcome (`parseTriage` with the caps); the worker checks the shape only. A spec under the threshold without phases renders exactly as before; a spec with phases adds a "Split into phases" section (each phase's title, problem, done criteria and allowed paths, in order) before the command footer. A split spec always waits at the spec gate, whatever its tier, because its `/approve` files issues.
- **`/approve` on a split spec.** It files one sub-issue per phase, in order, through `SourceAdapter.fileSubIssue` (GitHub: an issue with the intake label, its body naming the parent and the phase it waits for, linked under the parent with the sub-issues API), and takes each in as a work item at once, requested by the approver, with a `detail` on its `intake` row (`parent_work_item_id`, `phase`, `phases`, `depends_on`: the previous phase's source id). Each filed issue carries a marker per (parent, phase), `<!-- factory:phase:<parent id>:<n> -->`; filing looks it up first (the parent's sub-issues, then the newest factory-labelled issues), and intake is keyed on the source, so a retry files no duplicates. A failure is outbound's retry (see the first decision above). Intake ignores an issue whose body carries a phase marker: the split takes it in, so the bot's own issues never start un-held. On success the parent gets one comment listing the phases and waits in `READY` with `blocked_on: upstream` / `blocked_reason: phases_open` (state change `split_approved`, detail `sub_issues`: the phases' source ids in order). The parent is never implemented. Each phase is an ordinary work item with its own triage spec and its own `/approve`. `/revise` on a split spec runs triage again; the new spec may or may not be a split.
- **`phases_auto_approve` (decided 2026-11-07).** A live setting (`npm run factory -- settings set phases_auto_approve true`, or the top-level file key; default `false`). When on, the owner's `/approve` of the split covers its phases: a phase whose parent still waits on its phases (`phases_open`) goes from triage straight to implement (`triaged_phase_approved`, detail `parent_work_item_id`). Its spec is still posted, with a line saying why no `/approve` is needed. A phase already waiting at `spec_pending` when the setting is turned on is approved on the next `tickPhases` (`phase_spec_auto_approved`). A phase whose own spec is a split, an item that is not a phase, and a phase whose parent is no longer `phases_open` still wait for a human. The split comment on the parent says which way the phases go. Only spec approval changes: the merge gate and the tier floors stay as they are.
- **The phase hold.** **`/retry` releases a held phase whose previous phase closed without a merge (decision changed 2026-11-12; replaces "a phase closed any other way keeps the next phase held" with no command to lift it; see History).** A held phase is its own command phase (`phase_hold`, "held: waiting for the previous phase of its split"), where `/retry` applies. `/retry` there releases the phase into triage (state change `retry_requested`, detail `released: phase_hold`, `parent_work_item_id`, `phase`, `depends_on`: the previous phase's source id, `close_reason`: its close reason, and the note if any; triage queued under the intake key) when the previous phase is `CLOSED` any way: rejected, won't do, or completed before the pass ran. While the previous phase is still open, `/retry` changes nothing and replies that it must close as completed first. The automatic release below is unchanged: only a human `/retry` releases a phase after a previous phase closed without a merge, since the owner decides whether the rest of the split still applies. Phases already held when this shipped need no data change. The first phase is queued for triage at once. Each later phase starts `NEW` with `blocked_on: upstream` / `blocked_reason: phase_hold` and no run (no new stage). On every poll, after its closes are applied, the controller (`tickPhases`) releases a held phase whose previous phase is `CLOSED` / `completed` (`phase_released`, triage queued under the intake key) and closes a `phases_open` parent whose phases are all `CLOSED` / `completed`: one comment, then the parent issue closed as completed (`closeIssue(source, "completed")`, alongside the existing not-planned close), then `CLOSED` / `completed` (`split_completed`). A phase closed any other way keeps the next phase held and the parent open. The bot closing the parent as completed is a new outward action. Both steps re-read the store and are safe to repeat on any replica. Ordering beyond "wait for the previous phase" is out of scope.

Store: one migration, SQLite 13 (`work-item-phases`): `work_items.parent_id` and `phase`, with an index on both. A phase is created with its parent's id and its place in merge order (`NewWorkItem.parent`; store-owned, never changed by a transition), and `FactoryStore.listPhases(parent)` returns a parent's phases in phase order. The controller finds a held phase's previous phase and a parent's phases through it; the `intake` and `split_approved` details stay as the audit trail, and the `split_approved` detail says how many phases the approval filed. The hold is in `blocked_on` / `blocked_reason`; `createWorkItem` takes an optional `hold` and an intake `detail`. Status labels: a held phase and a `phases_open` parent show "needs human", the label for any non-human blocker; a label of their own is not in this change.

The size checkpoint now suggests a split: after `diff_too_large`, the comment adds "Suggested split", 2 to 4 phases built from the diff size (the counts in the size gate's detail) and the item's allowed paths, grouped by folder, never the code. It is computed in the controller (`suggestSplit` in `src/core/split.ts`), so it runs no agent and costs no tokens. The work item asked for a short triage-role step reading the changed paths; that needs the worker to put the changed paths in the failed outcome (and to run the step), and `src/core/worker.ts` and `src/core/diff-gate.ts` were outside this change's allowed paths. Until then the suggestion groups the item's allowed paths, the only paths the controller has. A reviewer can use the suggestion as the phases of a split spec through `/revise`. Not changed: the caps, floors, tiers, the human merge gate, Slack intake (GitHub only), splitting an item that is already running, and merging any phase automatically.

## History

- **`/retry` releases a held phase** (2026-11-12). Before: a held phase fell under the generic "other blocked" command phase, so `/retry` did nothing on it, and a phase whose previous phase closed without a merge (rejected as superseded by other work) stayed held forever and had to be refiled by hand (#598, phase 3 of #569 after #595 was rejected).

- **A split spec is approved on an item from any source** (2026-11-12). Before: `/approve` on a split spec whose parent's source had no `fileSubIssue` (a Slack thread) was refused ("this source cannot file sub-issues, so a split spec cannot be approved here; reply `/revise <feedback>` to get a spec without phases"), and "Local tasks split too" listed Slack as not built, so a large Slack ask had to be refiled by hand as local tasks.

- **Phases are filed through outbound** (2026-11-09, RFC 0015 M7). Before: `/approve` filed every phase inline (the phases unit called `fileSubIssue`, the last entry of the `forge-writes` ratchet), in one pass; a failure refused the approval (`split_filing_failed`, back at the spec gate, "filing stopped after k of N; reply `/approve` again"), and a claim older than 10 minutes (`SPLIT_FILING_STALE_MS`), left by a process that stopped mid-filing, could be taken over by `/approve`.

- **Local tasks split too** (2026-11-07). Before: only the GitHub source offered `fileSubIssue`, so `/approve` on a local task's split spec was refused (`local-d8e25824`), and neither `task show` nor the item page listed sub-tasks.

- **One approval files a split** (2026-11-07). Before: every pass that read the spec at the gate filed the phases and only the final transition was conditional, so two controllers applying one `/approve` (a draining process and its successor) filed phases 2..N twice when the marker lookup missed.

- **Only recorded phases count** (2026-11-07). Before: every work item linked to the parent counted, so a duplicate phase closed as not planned kept the parent open forever (#172 and #252 got duplicate phases from two approvals racing).

- **Phase issues** (2026-11-07, issue #229). Before: the title could read "Phase 2/4: Phase 2: …", and the body opened with "Phase N of M of owner/repo#163 (https://…)" and had no In short.

- **Split specs** (decision changed 2026-11-01, issue #102). Before: triage returned no size estimate and one spec for the whole issue, so a change too big to review was found only by the size gate after an implement run had spent its tokens, and the size-check comment asked for a smaller spec without saying how.
- **Phase spec approval** (changed 2026-11-07). Before: each phase always waited for its own `/approve`, though the owner had already approved the split on the parent. It still does by default; `phases_auto_approve` turns that off.
- **MySQL text removed from the current decisions** (decision changed 2026-11-11, issue #567). Before: local task sub-tasks were read on "the shared MySQL store"; the phases store was "one migration, SQLite 13 and MySQL step 13 (`work-item-phases`)", followed by: "MySQL step 13 is an inline step (`INLINE_STEPS` in `src/impl/store/mysql/migrations.ts`), not a file in `migrations/mysql/`, because that folder was outside this change's allowed paths. It is numbered, checked for gaps and duplicates, and applied by `npm run migrate` exactly like a `0013-work-item-phases.sql` file, so moving it into that file later changes nothing for a database that already ran it."
