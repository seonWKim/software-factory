# 5. Coordination: status labels

- **Status labels (new decision, 2026-11-01):** a pure mapping (`src/core/status-label.ts`) turns `stage`, `blocked_on`, `blocked_reason` and `close_reason` into exactly one of eight statuses: `NEW` → triaging; `READY`/`spec_pending` → needs approval; `RUNNING` → implementing; `REVIEW` → in review; `REVIEW`/`merge_pending` → ready to merge; `CLOSED`/`completed` → done; `CLOSED` with any other `close_reason` → rejected (`duplicate` and `failed` have no producer today); anything else blocked (failed runs, `max_loops`, `merge_conflict_pending`, an unknown reason, or a `blocked_on` other than `human`) → needs human. The source shows it through a new `SourceAdapter.setStatus(source, status, pr_number)`: on GitHub, one label `<status_label_prefix><name>` (default prefix `sf: `). The PR is addressed through the same call with a non-null `pr_number`, not a separate PR `SourceRef`, because PRs share the issue labels API. Only the eight fixed names under the current prefix are ever removed, so a human-made `sf: …` label survives. The controller calls it after each committed transition whose patch touches `stage`, `blocked_on`, `blocked_reason`, `close_reason` or `pr_number` (issue, then PR once `pr_number` is set), after an intake that created the item, and for every non-`CLOSED` item when `Controller.run` starts (catch-up via `listWorkItems(1000)`, a warning when the cap is hit; no new store method). Ack-only transitions (empty patch) write nothing. Every call is best effort, like the 👀: a failure is a warning and the transition stands. Labels are output only; the factory never reads them. **Known limitation:** with several controller replicas, two near-simultaneous transitions of one item can write labels in the wrong order; the next transition or the next start-up catch-up corrects it.
