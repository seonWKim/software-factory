## History

- **Only a base push brought origin's base into the local one** (until 2026-11-25, the "A PR merged on the forge fast-forwards the local base" decision in 05-github-sync.md). Before: a PR merged on GitHub (the Merge button's `merge_pr` or a merge on GitHub) moved only origin's base; local `<base>` stayed behind until the next local merge's `push_base` merged origin into it, so a local merge checked meanwhile was checked on, and landed on, the stale base and could conflict at its push, filing a reconcile item.
- **A local item's conflict starts the automatic resolve also with a forge selected** (decision changed 2026-11-12). Before: with a forge selected the controller read only origin's base, so a local item was not merge-checked, `factory merge` on a conflict refused with the files and started nothing, and two local items in this repo were resolved by hand on 2026-11-12.
- **Slack replies were not saved** (until 2026-11-10, issue #480). Before: the Slack source held the store read-only; a person's reply in an item's thread became a plain-comment event used only for `/link` and command handling and was never stored, so the item page showed only the factory's messages for a Slack thread. "The local store is the home of the conversation" listed Slack comments as not built, and "One command table" listed #480 (people's replies on the item page) as not built here.
- **The local merge can run in auto mode** (decision changed 2026-11-08, issue #444). Before: the local merge was never automatic; only `factory merge` or the Merge button called it, and `auto_merge_max_tier` stayed 0.
- **One GitHub client per process** (decision changed 2026-11-08). Before: build() made a GitHubClient from the credentials it got from the `github_auth` plugin, and `main.ts`, `setup.ts` and `issue-cmd.ts` each made their own, so one run could hold several clients with separate budgets; `src/plugin-api.ts` typed contexts with the GitHubClient class; the GitHub descriptors imported their implementations at top level, and `setup.ts` created the labels itself.
- **GitHub call budget: shared through the store** (decision changed 2026-11-08). Before: every replica polled GitHub, budget per process: each GitHub client kept GitHub's rate limit from its own responses only, in memory, so a replica that had made no call yet did not know another one had used the budget, and its optional reads went on.
- **GitHub issues are the home of the conversation** (decision changed 2026-11-07, issue #284). Before: the GitHub source turned each new comment into an event the controller handled at once; nothing wrote a GitHub comment to the item thread or the command inbox, the inbox reader built only local identities and skipped every item that was not local, and dedupe relied only on the poll cursor's `last_comment_id`.
- **PRs through the forge** (decision changed 2026-11-07, issue #273). Before: the `github-issues` source read every PR event and PR fact, the controller sent PR comments and PR status to whichever adapter had the `github_issue` type (`PR_SOURCE_TYPE`), refused several sources without one at startup, and kept a refused intake silent by checking that type; the forge plugin was loaded but never called.
- **GitHub call budget: shared budget** (decision changed 2026-11-07, issue #340). Before: the client stopped optional reads only under `min_remaining`, so one factory could use most of a limit other factories on the same App draw from; a first start read every closed item and 500 base commits in one poll; and a call refused at 0 remaining was logged as a failed loop step.
- **GitHub call budget** (decision changed 2026-11-07). Before: every GitHub GET was a full call counted against the hourly limit, even when nothing had changed; the closed-PR list read every page up to 5 on each poll; `setStatus` made at least three calls each time; and nothing read the rate-limit headers, so a retry loop kept calling after the limit was spent.
- **GitHub sync records** (decision changed 2026-11-07). Before: nothing about posts or labels was stored: every controller start re-applied the status of up to 1,000 open items, each a label read that the in-process ETag cache could not save after a restart; every post listed the issue's whole thread (up to 10 pages) to find its marker, repeats included; and a failed post was called again on every 2 s tick, with no stored attempt count.
- **MySQL text removed from the current decisions** (decision changed 2026-11-11, issue #567). Before: the notice records said "(timestamped controller migration `20261112T2100-controller-notice-messages`; the MySQL store is gone, so there is no MySQL step)"; the reaction reads ran "in the SQL store shared by SQLite and MySQL"; the command cursor decision added "Enterprise (MySQL): step `0042-commands-cursor` runs through `npm run migrate` (it finds the table as `inbound_cursors`, or `cursors` before the rename; `--dry-run` lists the row it would write); the factory refuses to start while it is pending, so no replica runs the relay without it, and it is safe to run again."; the outbox rows were "SQLite migration 29, MySQL step `0029-thread-outbox.sql`"; the GitHub sync records were "SQLite migration 27 and MySQL step `0027`"; the budget row was "SQLite migration 40, MySQL step 0040" and "Enterprise setting: replicas on one MySQL store share the row"; the CLI mirror was "SQLite migration 37, MySQL step `migrations/mysql/0037-command-mirror.sql`"; the thread tables were "SQLite migration 24 and MySQL step `0024`"; and migration 12 read "SQLite builds it on open; MySQL gets it from the step file `migrations/mysql/0012-adopted-prs.sql` through `npm run migrate` (the table has a `seq` column like every MySQL table, which the store orders ties by). A MySQL store refuses to start until that step is applied."
- **One GitHub client per process: `issue-cmd.ts` among its callers** (until 2026-11-16, when the `factory issue` command was removed). Before: the callers of `Plugins.githubApi()` were the CLI commands (`settings --project`, `migrate`, `golden add`), `issue-cmd.ts` (`issueDeps`) and `setup.ts` (doctor, setup).
