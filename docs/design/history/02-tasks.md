## History

- **No calendar** (until 2026-11-12, the calendar decision above). The factory read no calendar and had no table for one.
- **The dashboard has no quick-add form** (until 2026-11-12). The route's callers were the desktop quick-add box only, and the Tasks page told the owner to use `factory task add <words>`. The Tasks page now has a quick-add form.
- **No route stored a task** (until 2026-11-12): only `factory task add` and the chat command did. The desktop quick-add box needed one, so `POST /api/v1/tasks` was added beside them.
- **Plain tasks** (new decision, 2026-11-11, issue #606). Before: `factory task` meant work items only (create, list, show), and a plain to-do could only be stored as a work item that triage would read.
- **MySQL text removed from the task decisions** (decision changed 2026-11-11, issue #567). Before: the schedule migration said "No MySQL step: the MySQL store was removed on 2026-11-12 (#654)."; the calendar migration held "SQLite and MySQL DDL"; the sub-tasks column was "TEXT on SQLite, `VARCHAR(191) NULL` with its key on MySQL, the width of a task ID"; the link column was "TEXT on SQLite, `VARCHAR(64) NULL` on MySQL, the work item ID's width"; the tasks table migration "holds the SQLite and the MySQL DDL; no numbered SQLite or MySQL step (those lists are frozen)"; and each Solo and enterprise bullet added "MySQL applies its DDL in `npm run migrate`" (for the tasks table: "MySQL applies the same migration's MySQL DDL in `npm run migrate`").
