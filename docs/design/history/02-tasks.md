## History

- **Today's timeline with drag-to-schedule** (until 2026-11-16, the no timeline decision at the top). `GET /api/v1/tasks` returned `timeline`: today's open timed tasks and timed events as blocks (`planDay`, a task with no stored duration drawn as `DEFAULT_DURATION_MINUTES`, 30), each with its start, end, offset from midnight and length, cut at midnight. The Tasks page showed it above the list, collapsed behind a "Show timeline" control: half-hour slots, each a drop target, with the task blocks drawn over them. A task row dragged onto a slot posted `POST /api/v1/tasks/schedule` `{ id, date, time }` (and an optional `duration_minutes`), which set the due date (today), due time and duration through `updateTask` (400 bad body, 404 unknown, 409 done, nothing written).
- **`#label` is ASCII letters, digits, `_` and `-`** (until 2026-11-16, the any-script `#label` decision at the top). The tag rule was `/^#[\w-]+$/`, so a Hangul or other non-ASCII tag such as `#집` stayed in the title and set no list. The Tasks page placeholder read "e.g. rent friday p1 #home, then {key}".
- **`every` anywhere starts a repeat, and any other `every` form is refused** (until 2026-11-15, the quick-add repeat decision at the top). `every` followed by `day`, `week` or `month` was the recurrence wherever it stood in the words, and `every` followed by anything else was refused with "unknown recurrence: every <word>", so "Design rules checked on every UI review" could not be added.
- **`task create` makes a work item only** (until 2026-11-15, the create under a project decision at the top). `factory task create --title <t> --body-file <f>` wrote no task, so its item showed under no project; the owner ran `task add "<title> +slug"` and linked the item by hand. No dashboard route created a work item.
- **The Tasks page had three views: Today, Upcoming and All** (until 2026-11-15, the one list decision at the top). A SegmentedControl chose Today (overdue, then due today, then the timeline; the undated tasks added today since 2026-11-15, the added today decision at the top), Upcoming (the dated open tasks due tomorrow through 7 days ahead, one group per day) or All (every open task under its `#list`, undated last), Today on load, each rendering all its rows at once. Replaced by one paginated list. Its other parts stand: the five-tab and Done decisions below it, the server placement and the done window.
- **Today: overdue first, then due today** (until 2026-11-15, the added today decision at the top). Today's `due` held only the tasks whose due date was today; a task added with no due date was in no Today group, only in All under its list, unlabelled last, often off the first screen.
- **Done tasks are behind All's Show done** (until 2026-11-15, the done tasks stay decision at the top). A Show done switch at the foot of All, off on load, showed a separate done list read from `GET /api/v1/tasks/done`: the tasks done in the last 30 days, most recently done first, one flat list with each row's list label and done time, Show older for the 30 days before, and Reopen; a done task left Today, Upcoming and All, and the done read was not filtered by the project tabs.
- **The Done tab decision** (decision of 2026-11-14, removed 2026-11-15 by the done tasks stay decision at the top). The Tasks page had a Done tab (later All's Show done list): `GET /api/v1/tasks/done` (`readDoneTasks`) with `?before=` for Show older, `{ as_of, tasks, older, next_before }`; the store's `listDoneTasks(window)` with `older`; each row's Reopen posting `POST /api/v1/tasks/reopen`, its refusal above the list; the read's query key under the tasks' key (`useDoneTasks`), not polled. The store read, the 30-day window and Reopen stay; the tab, the list, Show older and the route are gone.
- **The project row was the tabs alone** (until 2026-11-15, the "+" button decision at the top). A project was created in a task row's Projects… dialog (which also links the task) or with `factory project create`; the Projects… dialog keeps working as before.
- **Five tabs: Inbox, Today, Upcoming, List and Done** (until 2026-11-14, the three views decision at the top). The Tasks page's Task view control had Inbox (open tasks with no due date, `inbox` of `GET /api/v1/tasks`), Today, Upcoming (today through 7 days ahead), List (every open task under its `#list`) and Done.
- **The Done tab** (until 2026-11-14, the three views decision at the top). Done was a fifth tab after List; its list, window, Show older and Reopen now sit behind All's Show done switch, unchanged.
- **The List tab** (until 2026-11-14, the three views decision at the top). The fourth tab grouped every open task by its `#list`; All does the same.
- **Inbox's timeline** (until 2026-11-14, the three views decision at the top). The Inbox and Today tabs both ended with today's timeline, so an undated task could be dragged from Inbox onto a slot; the timeline is on Today only.
- **Events beside the tasks in Today and Upcoming** (decision changed 2026-11-14, the calendar events decision at the top). Before: the Tasks page listed each day's events with its tasks, drew them on the timeline and showed the stale-sync notice above Today and Upcoming.
- **The Tasks page's #list tab is named Project** (until 2026-11-14, phase 3 of local-d91d27e8; design 09-dashboard-app holds the switcher and List tab decision). The tab that groups the open tasks by `#list` was named Project; it is now List, and Project names the task project switcher.
- **`task project` takes one `+slug` or `-slug` per call** (until 2026-11-15, the move decision at the top). Moving a task between projects needed two calls, `-<from>` then `+<to>`, and a failure between them left the task in neither or in both.
- **A task belongs to no project** (until 2026-11-14, the task projects decision above). The #606 decision said: "`list` is a free label (`#home`), never a repository key: a task belongs to no project." A task had one free `#label` and no command listed tasks by a named group.
- **Enter adds the task** (until 2026-11-14, the quick-add key decision above). The Tasks page quick-add field was a form: Enter submitted it, as the Add button did, and no setting chose another key.
- **The Tasks page shows open tasks only, so a done task leaves every view** (until 2026-11-14, the Done tab decision, now under History). Every tab read `GET /api/v1/tasks`, which lists open tasks only; a done task and its done time could be seen only in the CLI's history, and reopened from the page only by ⌘Z in the same page session.
- **Completing a task is final** (until 2026-11-13, the undo a completion decision above). Done set `done_at` once and nothing cleared it: no store method, command, route or key reopened a task, so a task marked done by mistake had to be added again.
- **Reminders are not part of any decision** (until 2026-11-13, the schedule a task and reminder channels decisions above; said in the edit, delete and sub-tasks decision). No reminder fired at a task's time.
- **The reminder is a desktop notice only, sent up to a day late** (until 2026-11-13, the reminder channels decision above; owner answer 3 of #598). The `task-reminders` unit wrote no outbox intent, so a reminder never reached Slack or another `notify_channels` adapter, and `REMINDER_LOOKBACK_MS` was one day.
- **A task has a due date and an optional `HH:MM` time, no duration, no timeline and no reminder** (until 2026-11-13, the schedule a task decision above). Quick add read only `HH:MM`, nothing stored how long a task takes, the Tasks page had no hour-by-hour view, and no reminder fired at a task's time.
- **A calendar read had no time limit** (until 2026-11-12, the Google call timeout decision above). A Google that accepted the connection and never answered held the controller's tick until the process restarted.
- **Editing and deleting a task are not part of any decision for the dashboard** (until 2026-11-12, the Tasks page decision above). The Tasks page could list, quick-add and Build this only; a task was edited, completed, deleted or given a sub-task through the CLI or chat.
- **Upcoming started tomorrow, and no view showed events** (until 2026-11-12, the calendar views decision above). Upcoming listed tasks due in the 7 days after today, so today's tasks were only in Today; the calendar component synced events that no view read.
- **Editing and deleting a task are not commands yet** (until 2026-11-12, the edit, delete and sub-tasks decision above). The #606 decision had `task add`, `task done` (later `task build`) and `task list` only; a task could not be changed or removed, and had no sub-tasks.
- **No calendar** (until 2026-11-12, the calendar decision above). The factory read no calendar and had no table for one.
- **The dashboard has no quick-add form** (until 2026-11-12). The route's callers were the desktop quick-add box only, and the Tasks page told the owner to use `factory task add <words>`. The Tasks page now has a quick-add form.
- **No views, no link to an item, no merge close** (until 2026-11-12, issue #607). The #606 decision said: "Reminders, due-date alerts, dashboard and status page views, and linking a task to a repository, an item or a pull request are not part of this decision." A task could only be listed by `task list`, never sent to intake, and stayed open when the change made for it merged.
- **No route stored a task** (until 2026-11-12): only `factory task add` and the chat command did. The desktop quick-add box needed one, so `POST /api/v1/tasks` was added beside them.

- **Plain tasks** (new decision, 2026-11-11, issue #606). Before: `factory task` meant work items only (create, list, show), and a plain to-do could only be stored as a work item that triage would read.
- **MySQL text removed from the task decisions** (decision changed 2026-11-11, issue #567). Before: the schedule migration said "No MySQL step: the MySQL store was removed on 2026-11-12 (#654)."; the calendar migration held "SQLite and MySQL DDL"; the sub-tasks column was "TEXT on SQLite, `VARCHAR(191) NULL` with its key on MySQL, the width of a task ID"; the link column was "TEXT on SQLite, `VARCHAR(64) NULL` on MySQL, the work item ID's width"; the tasks table migration "holds the SQLite and the MySQL DDL; no numbered SQLite or MySQL step (those lists are frozen)"; and each Solo and enterprise bullet added "MySQL applies its DDL in `npm run migrate`" (for the tasks table: "MySQL applies the same migration's MySQL DDL in `npm run migrate`").
