## History

- **The Plugins page sat in its own sidebar group above System** (until 2026-11-18, the bottom-group decision at the top). Before: `PAGES` gave Plugins the group `plugins`, drawn as its own untitled block between Tasks and System.
- **The Settings page was one column of 13 sections with raw keys as row names** (until 2026-11-16, the Settings tabs decision at the top). Before: Pending proposals, Mode, Notices, Integrations, Providers, Calendar, Commands, Settable keys, Ignored overrides, Standing approvals, file keys, PR-only keys and History followed one another; a row read its config key (`max_attempts`) with Source, File value and Applies at as columns, and Save read "Save repo.install_command"; the intro named `factory settings`; the empty Pending proposals box opened the page; Providers stayed there with a link to the Plugins page.
- **The GitHub budget and the improve report only on `/classic`** (decision changed 2026-11-16, the GitHub budget tab decision at the top). Before: `overview.github_budget` and `github_token_days` were in the overview but no app page read them, and the improve report and Run now were drawn only by the classic page.
- **The Settings page saved non-danger file-only keys at once and named the file** (until 2026-11-16, the Settings confirm decision at the top). Before: Save on a file-only key that was no guard, floor, permission or dial posted `edit-file` with no Dialog; the section intro named factory.config.json, each read-only key ended with "Edit factory.config.json to change this.", the page had no project label control, and its no-label line said to use `factory settings --project` on the command line.
- **The Plugins page sent the owner to the CLI** (until 2026-11-16, the Import, Add and skill folders decision at the top). Before: the empty states said to run `factory pack add <path>` or to list folders under `capabilities.skill_folders` in the config file; with no approvals route the page showed "This page cannot approve here" with `factory pack approve mcp_server <name>` and each button's tooltip read "Approve from the CLI"; pack tools had no Approve; nothing could be imported, added or put in the skill folder list from the page.
- **The sidebar had no Plugins group; capabilities were a Settings section** (until 2026-11-15, the Plugins page decision at the top). Before: the sidebar groups were Tasks, Factory, System and the Settings row; skills, tools and providers were one read-only table on the Settings page, and pack MCP servers were shown on no page.
- **PR-only copy: edit factory.config.json in a pull request** (decision changed 2026-11-13, phase 3 of "Settings without editing factory.config.json"). Before: the PR-only section listed every PR-only key, file-only ones included, under the line "These keys set the guards, secrets, permissions, plugins and what agents may read, so a person must review every change: this page and `factory settings set` refuse them. To change one, edit it in factory.config.json in a pull request and merge it after review."; the page had no control for a file-only key.
- **No Tasks page** (new decision, 2026-11-12, issue #607). Before: plain tasks were listed only by `factory task list`; the dashboard had no page, no read route and no button for them.
- **Settings page layout and object values** (decision changed 2026-11-10, owner feedback). Before: the pending proposals were the last part of "Standing approvals"; the PR-only keys were headed "Changes by PR only" with that note on every row and no reason; an object value was one JSON line (`break-all` in the file value column), and the `json` field a four-row textarea of the same line.
- **Standing approvals on the Settings page** (decision changed 2026-11-08, issue #300). Before: rules and proposals were shown and changed only through `/standing` and the CLI; the API had no standing route and `POST /api/v1/pauses/resume` was the last of three write routes.
- **The dashboard's only write is Settings** (decision changed 2026-11-07, issue #291). Before: `POST /api/v1/settings` was the one write route besides item commands (#227) and the app showed no claim pauses. Now `POST /api/v1/pauses/resume` is another write, behind the same guards plus the owner check.
