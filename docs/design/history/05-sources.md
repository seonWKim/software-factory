## History

- **Slack button presses were commands or proposal presses only** (until 2026-11-12, one-tap verdicts). Before: every Slack button press was a command button (an inbox event, or a chat command's stored row), a proposal press or Make this a task; the source never stored a verdict itself and never opened a modal.

- **A local item's conflict starts the automatic resolve also with a forge selected** (decision changed 2026-11-12). Before: with a forge selected the controller read only origin's base, so a local item was not merge-checked, `factory merge` on a conflict refused with the files and started nothing, and two local items in this repo were resolved by hand on 2026-11-12.

- **A notice was linked to no item** (until 2026-11-12). Before: the Slack source posted each notice and kept nothing of it, so a mention in its thread was read like one in any thread that is no item: a request that made a work item from the thread (the owner's "go ahead and merge" under a "ready to merge" notice became an item titled so); and a notices channel outside `slack.channels` was never read.
- **Slack links went to 127.0.0.1 with no dashboard URL** (until 2026-11-12). Before: with no `slack.dashboard_url`, a spec message's Full spec link and each notice title linked `http://127.0.0.1:<ui.port>/app/items/<id>`, which only the owner's machine could open; on a phone the link went nowhere.
- **A spec was posted whole to Slack, after a separate status message** (until 2026-11-12). Before: the Slack source posted `Status: *needs approval*` as its own message, then the whole spec comment as one message (In short, Problem, Decisions, Applied defaults, Done when, scope, Files, Risk), with Approve and Help buttons from its footer; decisions were answered only by typing `/approve` with `N: <answer>` lines.
- **A plain reply in an item's thread needed the slash** (until 2026-11-12, issue #585; set 2026-11-11, issue #541). Before: this file said a reply in an item's thread with no mention still needed the slash, so a sentence there was never a command by accident; the reader's proposals (2026-11-11) already answered such a reply, and nothing said that a reply in a thread the factory does not own is never read.
- **A top-level mention read as a request, or not read, was taken in at once** (until 2026-11-12; set 2026-11-11, the chat answer). Before: the intake unit read a top-level mention only for a requester with `approve_spec`, a model, and a clean message of 1 to 1000 characters; a `request` answer, a failed or malformed answer and every message it did not read became a work item at once, with no reply, so a question to the bot got an item and a full spec. Only an unsure answer got the Make this a task button.
- **Every top-level Slack mention was a work request** (until 2026-11-11, the chat answer). Before: the Slack source turned any mention outside an item's thread into an `item_requested`, and intake created a work item for it without reading the message, so "can you receive natural inputs?" became a work item.
- **No source read reactions** (until 2026-11-11, issue #524). Before: the GitHub source read comments and added 👀 but never listed a comment's reactions; the Slack app had `reactions:write` only (no `reactions:read`, no `reaction_added` event); and the store had no read of a posted message by its comment ID or of the posted comments in a time window.
- **Slack buttons never changed** (until 2026-11-11, issue #586). Before: each message's buttons were built once from the command footer it was posted with and never edited, so an Approve stayed under a spec after the item moved on, and pressing it reached the command handler's `was not applied` refusal.
- **Only `approve` worked without its slash after a mention** (until 2026-11-11, issue #541; set 2026-11-11, issue #528). Before: in an item's thread the Slack source read a bare `approve` after a mention as `/approve` and nothing else, so `@software-factory revise <feedback>` was stored as a plain comment and did nothing; the hint, the `help` reply and the refusal outside a thread showed the slash form, and SET_UP.md listed `@bot /approve [notes]` and the other item commands with their slash.
- **The command cursor fell back to `intake:local`** (until 2026-11-11, issue #467). Before: while the `commands` cursor row was missing, the command relay read the old `intake:local` cursor as its start, two cursor reads on every tick until the first command was relayed.
- **Slack messages: thread first** (until 2026-11-11, issue #484). Before: the Slack source read the whole thread (`conversations.replies`, up to 20 pages) before every `postComment` and every `setStatus` to find its own earlier message by marker hash or by status metadata, and wrote no posted-message record, so outbound's record check always missed for Slack. Now the store's record is checked first and the thread is read only when there is none.
- **Slack replies were not saved** (until 2026-11-10, issue #480). Before: the Slack source held the store read-only; a person's reply in an item's thread became a plain-comment event used only for `/link` and command handling and was never stored, so the item page showed only the factory's messages for a Slack thread. "The local store is the home of the conversation" listed Slack comments as not built, and "One command table" listed #480 (people's replies on the item page) as not built here.
- **Cut chat replies named only a CLI command** (2026-11-09, review of #498). Before: a cut reply's note named the command that prints the whole text, with no link; now it also links the shown item's source.
- **One command table, and the factory's commands in Slack** (new decision, 2026-11-09, issue #498). Before: the item commands were listed in src/core/commands.ts, `task`, `merge` and `users` in src/core/local-cli.ts, and `settings` and `mode` only as usage text in src/settings-cmd.ts; Slack took only item commands, in an item's thread, judged by the forge's auth plugin; a `help` or another command outside an item's thread got no reply.

- **Base push as a claimed row** (2026-11-08, issue #433, replaced 2026-11-09 by RFC 0015 M8). Before: the local merge's close transition wrote one `outbound_base_pushes` row, and the controller's outbox step claimed it by a conditional update, pushed, and retried a failure with its own backoff.
- **A local item's gate comments with GitHub selected** (2026-11-08, issue #421, replaced 2026-11-09 by RFC 0015 M7). The worker posted its gate, review and update comments itself through the broker's `github.comment` (`forgeComment`), on the number `issueNumber` or `prNumber` gave; a null number (a local item, any non-GitHub id, a review or update with no PR) posted nothing. The broker refused a `number` that was not a positive integer with `invalid_args`.

- **Merge** (decision changed 2026-11-08, RFC 0015 M8). Before: the local merge ran the install command and the checks on the merge commit in a temporary worktree of the controller's sandbox and moved the base at once; no queue ordered two approved changes.

- **The local merge can run in auto mode** (decision changed 2026-11-08, issue #444). Before: the local merge was never automatic; only `factory merge` or the Merge button called it, and `auto_merge_max_tier` stayed 0.
- **Local items: the base push, the owner's checkout, and PR-era items** (decision changed 2026-11-08, issue #433). Before: a local merge moved only the local base and never pushed, so on a repo with a remote the merged work never reached origin; a base checked out in any worktree (the owner's usual checkout) refused the merge; and routing was by source type only, so a local item that opened a PR before #427 took the local route and its update run failed with `git rev-parse:`.
- **One GitHub client per process** (decision changed 2026-11-08). Before: build() made a GitHubClient from the credentials it got from the `github_auth` plugin, and `main.ts`, `setup.ts` and `issue-cmd.ts` each made their own, so one run could hold several clients with separate budgets; `src/plugin-api.ts` typed contexts with the GitHubClient class; the GitHub descriptors imported their implementations at top level, and `setup.ts` created the labels itself.
- **Merge** (decision changed 2026-11-08, issue #451). Before: "Still only `Controller.mergeLocal` (the sandbox's `mergeLocal`), reached by `factory merge <id>` and, since issue #438, by the item page's Merge button as an app `merge` request"; a GitHub item was merged only by a person on GitHub.
- **Local items, by source type** (decision changed 2026-11-08, issue #333). Before: the worker and `factory session` sent every item to the one selected broker and sandbox, so with GitHub selected a local item pushed to origin and opened a PR, and the local merge moved the base with no test run on the merge commit.
- **GitHub call budget: shared through the store** (decision changed 2026-11-08). Before: every replica polled GitHub, budget per process: each GitHub client kept GitHub's rate limit from its own responses only, in memory, so a replica that had made no call yet did not know another one had used the budget, and its optional reads went on.
- **A local item's gate comments with GitHub selected** (decision changed 2026-11-08, issue #421). Before: the worker took the issue number as `Number(source id after "#")`, so with the GitHub broker selected a local item's merge-conflict, failed-checks, checks-env and scope-violation comments were sent to `issues/NaN/comments`, the checks-env one through a direct broker call, and a review or update comment with no PR was sent with a null number.
- **Local startup** (decision changed 2026-11-07). Before: every start needed GitHub: build() read the GitHub credentials and made a GitHub client for every config, a first start resolved the project key through GitHub, the only broker pushed to GitHub and opened PRs, and the sandbox and the updater fetched origin and read the base from `origin/<base>`, so a local task had no path to a merge.
- **CLI intake** (decision changed 2026-11-08). Before: the CLI refused `approve|retry|revise|reject` for any non-local item ("is not a local work item: reply `/<command>` on its issue instead") and the controller skipped CLI commands for non-local items, so a local approver could act on a GitHub item only through a GitHub account with write access.
- **GitHub issues are the home of the conversation** (decision changed 2026-11-07, issue #284). Before: the GitHub source turned each new comment into an event the controller handled at once; nothing wrote a GitHub comment to the item thread or the command inbox, the inbox reader built only local identities and skipped every item that was not local, and dedupe relied only on the poll cursor's `last_comment_id`.
- **PRs through the forge** (decision changed 2026-11-07, issue #273). Before: the `github-issues` source read every PR event and PR fact, the controller sent PR comments and PR status to whichever adapter had the `github_issue` type (`PR_SOURCE_TYPE`), refused several sources without one at startup, and kept a refused intake silent by checking that type; the forge plugin was loaded but never called.
- **First start of the GitHub source** (decision changed 2026-11-07, issue #341). Before: a fresh install's first poll read one page of closed PRs and the merger of each merged one, so every past merge there was recorded as an unreviewed merge with a warning.
- **Thread first, then the outbox** (decision changed 2026-11-07, issue #282). Before: the controller posted each message through a helper that called the source adapter directly, so nothing in the store recorded what reached a GitHub item's source, a failed post made the whole transition retry, CLI commands were read only through the `local` source, and an empty `plugins.source` failed at startup.
- **Stream intake** (new decision, 2026-11-01). Before: every source was polled on a timer, so a source that pushes events, like Slack Socket Mode, had to be forced into polling.
- **Several sources** (decision changed 2026-11-01). Before: `plugins.source` named one plugin and the controller sent every comment, 👀, status and close through that one adapter, so a second source such as Slack could not run next to GitHub, and its items would have been answered through GitHub.
- **Pull requests a person opens, and a person's pushes** (decision changed 2026-11-01, issue #113). Before: only factory PRs were tracked: the GitHub source read pull requests on factory branches only, so a PR a person opened could merge with no review run, no scope or size check and no record, and a push a person made to a factory branch was invisible to the factory.
- **Local intake** (decision changed 2026-11-07, issue #199). Before: polled intake was GitHub only, nothing read the CLI command log and nothing stored item messages; now local intake and item messages live in the store, through the `local` source.
- **CLI intake** (decision changed 2026-11-07, issue #318). Before: every CLI command acted as `cli_user` and failed without it, and the one global `auth` plugin judged it: with `auth: github` the local account resolved only through a link no command created, so CLI commands were refused as not linked and local items stuck at spec approval.
- **CLI intake** (decision changed 2026-11-07, issue #200). Before: the `local` source could read the CLI command log, but nothing wrote to it and nothing created a local work item, so human commands from the CLI had no entry point and the local flow was untested end to end.
- **Item thread and command inbox** (decision changed 2026-11-07, issue #281). Before: local item messages and CLI commands lived in two tables from migration 21 named for the local source only, so the store had no single place for an item's conversation.
- **GitHub call budget: shared budget** (decision changed 2026-11-07, issue #340). Before: the client stopped optional reads only under `min_remaining`, so one factory could use most of a limit other factories on the same App draw from; a first start read every closed item and 500 base commits in one poll; and a call refused at 0 remaining was logged as a failed loop step.
- **GitHub call budget** (decision changed 2026-11-07). Before: every GitHub GET was a full call counted against the hourly limit, even when nothing had changed; the closed-PR list read every page up to 5 on each poll; `setStatus` made at least three calls each time; and nothing read the rate-limit headers, so a retry loop kept calling after the limit was spent.
- **No adapter, no transition** (decision changed 2026-11-07). Before: a controller without the item's source adapter still applied the item's transitions and only skipped the calls, so an older process draining after `local` was added to `plugins.source` applied local items' triage and dropped their spec comments and replies.
- **GitHub sync records** (decision changed 2026-11-07). Before: nothing about posts or labels was stored: every controller start re-applied the status of up to 1,000 open items, each a label read that the in-process ETag cache could not save after a restart; every post listed the issue's whole thread (up to 10 pages) to find its marker, repeats included; and a failed post was called again on every 2 s tick, with no stored attempt count.
- **Slack intake and source routing** (decision changed 2026-11-01, built 2026-11-07, issue #109). Before: no source used stream intake, so a request in Slack had to be copied into a GitHub issue by hand; the routing by source type existed but only test sources used it.
- **MySQL text removed from the current decisions** (decision changed 2026-11-11, issue #567). Before: the notice records said "(timestamped controller migration `20261112T2100-controller-notice-messages`; the MySQL store is gone, so there is no MySQL step)"; the reaction reads ran "in the SQL store shared by SQLite and MySQL"; the command cursor decision added "Enterprise (MySQL): step `0042-commands-cursor` runs through `npm run migrate` (it finds the table as `inbound_cursors`, or `cursors` before the rename; `--dry-run` lists the row it would write); the factory refuses to start while it is pending, so no replica runs the relay without it, and it is safe to run again."; the outbox rows were "SQLite migration 29, MySQL step `0029-thread-outbox.sql`"; the GitHub sync records were "SQLite migration 27 and MySQL step `0027`"; the budget row was "SQLite migration 40, MySQL step 0040" and "Enterprise setting: replicas on one MySQL store share the row"; the CLI mirror was "SQLite migration 37, MySQL step `migrations/mysql/0037-command-mirror.sql`"; the thread tables were "SQLite migration 24 and MySQL step `0024`"; and migration 12 read "SQLite builds it on open; MySQL gets it from the step file `migrations/mysql/0012-adopted-prs.sql` through `npm run migrate` (the table has a `seq` column like every MySQL table, which the store orders ties by). A MySQL store refuses to start until that step is applied."
