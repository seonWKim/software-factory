## History

- **Parallel workers: every run got the even CPU share** (decision changed 2026-11-26). Before: a merge-check run's `SF_TEST_WORKERS` was the same as any run's, the host's CPUs over the runs running on the host at claim, rounded down (`testWorkerShare(cpus, runs)`), so with five runs on 10 CPUs the serial merge check got 2 vitest workers.
- **Dependency edges re-read only when the issue changed, in full** (2026-11-26: the topic now keeps a short form; the decision is unchanged). Before, in full: **Dependency edges re-read only when the issue changed (decision changed 2026-11-07, issue #254; replaces the in-memory 30-minute link refresh of the same day, and before that edges re-read from the forge on every poll; see History).** Coordination reads an item's dependency edges from the store. They are read from the forge again only when the issue's `updated_at` moved past the time they were read at. The open-issue intake poll reports edits: `item_requested` carries the issue's `updated_at`. For an item the store already has, the controller compares it with the item's read time (`work_items.edges_source_updated_at`). When it is newer, or there is no read time, the controller reads the links once (issue body, sub-issues, blocked-by) and stores them. Every edge and the item keep that `updated_at` (`dependency_edges.source_updated_at`, so an issue with no links has a read time too). The same or an older time (the poll's `since` is inclusive, so the newest issue comes back every poll) reads nothing. A new item's links are read at intake, as before, with its `updated_at`. A failed read clears the item's read time, and so does an item from before this change. The next coordination pass then reads the links once and records the store time; after a failed read, that pass waits 10 minutes, so links that keep failing (a 403 or 5xx outage) cost one read per item per 10 minutes, not one per poll. A failed read stops no coordination: it is logged (`dependency links not read` / `dependency state not read`) and the stored edges and states apply; a failed outside-state read is not tried again for 10 minutes. A `/retry` at `dependency_closed` reads the links and every edge's state again at once (see Split parents above). Items with a PR or closed are not re-read. There is no timed link refresh: a sub-issue or blocked-by link added without the issue counting as updated is read on the issue's next edit or `/retry`. The factory's own label and comment writes also move an issue's `updated_at`, so they cost one read each, not one per poll. A dependency the store does not track is read from the forge at most once per 10 minutes (`DEPENDENCY_STATE_TTL_MS`). This is an in-process cache, like the ETag cache (design §5 Sources): a replica without it asks once. A dependency that is a factory item is still read from the store each pass. **Request budget:** while a source reports `lowBudget()`, the optional reads wait for the reset. Those are the forge state of untracked dependencies (the stored state stays), the coordination re-read of unread links, and the start-up status catch-up, which runs on the first tick whose budget is back. GitHub's `lowBudget()` is now also true under 10% of the reported limit, not only under `github.min_remaining`. It still logs one line on entering and one on leaving, and the budget is per process, in memory. Schema: SQLite migrations 33 (`dependency_edges.source_updated_at`) and 34 (`work_items.edges_source_updated_at`). Not in this decision: webhooks as a trigger for edge reads, a store-backed budget shared between processes, and a draining process stopping its controller (#294).
- **A split's phases had no `Depends on:` line; only a full wi_ ID resolved; `/hold` only at an implement stop** (decision changed 2026-11-26). Before: `takeIn` built a phase's problem from its title and phase body alone, so a parent filed with `task create --depends-on wi_X` (whose own implement never runs) gave its phases no edge, and they started without waiting for wi_X. `localItemOf` and the local source read a wi_ ID only as a full ID. `/hold <id>` applied only to a local item whose implement run asked for a human (`agent_needs_human`); on an item with a queued or running implement run it was refused with "the item is implementing; `/hold <id>` applies only to a local item whose implement run asked for a human".
- **A held run was re-checked against whatever overlapped it now; `hold_policy` defaulted to `{"mode":"hold"}`** (decision changed 2026-11-23, "Overlap holds go oldest first"). Before: each claim re-checked a held implement run against the current running items and open PRs, so an item that started after the hold began held it when the first blocker merged, and a newer queued run that overlapped only a held queued run was claimed by the deadlock rule ahead of it; the default `{"mode":"hold"}` never timed out, so such a run waited for `/approve` (wi_fec72464 20 hours behind #779, tk_efa4d88b and tk_586ba492; wi_088d528a 13 hours). Now the order rule holds a held run only behind work ahead of it, newer runs wait behind an older held run, and the default is `{"mode":"run_after_minutes","minutes":120}`.
- **Hold policy as written 2026-11-07** (decision changed 2026-11-23, "Overlap holds go oldest first"; the topic now keeps a short form). Before, in full: **Hold policy: a cost hold may time out or be allowed (decision changed 2026-11-07, issue #314; before: a cost hold kept the run queued until `/approve`, see History).** What changed: a run the cost rule holds (`held`: a running item or an open PR at or above `max_coordination_cost`) now follows `hold_policy`, read by the claim inside the same `worker_claim_locks` transaction. Modes: `{ "mode": "hold" }` (the run waits for `/approve` or for the holder to merge; the default until 2026-11-23, see "Overlap holds go oldest first" above); `{ "mode": "run_after_minutes", "minutes": 120 }` (the default since 2026-11-23: the run is claimed once it has been held `minutes`, a positive integer, default 120, 20 before; decision `timed_out`); `{ "mode": "run" }` (claimed at once; decision `overlap_allowed`). Both new decisions keep the holder, shared paths, cost and threshold, as `held` does, so a person can see what ran side by side. The timer counts from `claim_decisions.held_since`: set when a run is first held, kept while it stays `held` whichever holder the decision names (the row's `at` still moves on every change), so a holder change never restarts it; a row from before the column has none and counts from its `at`. `hotspot_mode`: `policy` (default) lets a hold that shares a hotspot follow `hold_policy`; `hold` keeps any hold where a running item or open PR shares a hotspot path held under every mode (any shared hotspot counts, with no weight rule). Not changed: dependency holds (never time out or become `overlap_allowed`: the dependency check comes first), the deadlock rule, `/approve` and its refusals (it still lifts a `held` decision under any mode), the hold comment text, cycle handling. **Config and setting:** `hold_policy` and `hotspot_mode` are top-level keys of `factory.config.json`, checked at load by `coordinationProblems` (an unknown mode, `minutes` that is not a positive integer, a key a mode does not take, an unknown `hotspot_mode` fail startup) and passed by `src/compose.ts` into `FactoryConfig.coordination` with the other coordination keys. `hold_policy` is also a settable key (`factory settings set hold_policy '{"mode":"run"}'`, design 08-settings.md), refused with the same messages and applied at the next claim with no restart: `LiveSettings` puts the effective value into the claim's coordination settings. `hotspot_mode` changes by PR only. One global value until per-project settings (#99). One worker or many: the default keeps every run held until the owner acts; an owner who prefers throughput sets a timer. **Schema:** SQLite migration 30 adds `claim_decisions.held_since` (NULL on older rows). Not in this decision: showing on the Queue and Items pages when a held run will start (a follow-up issue), per-project hold settings (#99).

- **Parallel workers: CPU share for tests counts the running runs** (decision changed 2026-11-18). Before: each run's `SF_TEST_WORKERS` was the host's CPUs divided by the live claiming slot count (`workers`, capped at `max_workers`), rounded down, at least 1, read on each call; ten slots on a 10-CPU host gave 1 each, and with `workers: 3` every run got 3 of 10 CPUs however many runs were going. Why the change: the share over slots gave 3 of 10 CPUs whatever ran, while 0 or 1 slot was busy 58% of the last 10 hours; measured on main (2026-11-18, Node 22, 416 test files), `npm test` took 220 s at `SF_TEST_WORKERS=3` and 137 s at 9, same results.
- **A split parent counts as merged when its last recorded phase closed `completed`** (decision changed 2026-11-18). Before: a split parent closed `completed` with no merge sha counted as merged only when every recorded phase closed `completed` (`itemMerged`), the rule that then closed the parent; a parent with a rejected phase never closed, so its dependents waited forever.
- **Learned weights count only conflicts inside `conflict_window_days`** (decision changed 2026-11-18). Found 2026-11-18: `docs/design/09-dashboard-app.md` still weighed 4.0 from 70 old conflicts, though its sections moved to per-page files that day; counting only the last 3 days would have freed 23 of 127 hold decisions in 48h (~625 wait-minutes).

The decision that changed: Dependencies, "Not in this decision: sources other than GitHub". - **Migration lock per database** (decision changed 2026-11-10). - **Hold policy** (decision changed 2026-11-07, issue #314). - **A held run names the holder that decides** (decision changed 2026-11-07). - **Dependency edges re-read only when the issue changed** (decision changed 2026-11-07, issue #254). Before: the read times were in the controller's memory (`EDGES_REFRESH_MS`, `DEPENDENCY_STATE_REFRESH_MS`): links were re-read on every delivery of an open item without a PR, and again by the coordination step once this process's last read was 30 minutes old, so a restart or another replica read every item's links again after 30 minutes; the 30-minute refresh and the outside-state reads ran under `lowBudget()` too.
- **Dependency reads only when the source changed** (decision changed 2026-11-07, issue #254). Before: edges re-read from the forge on every poll: each poll, for each item with a queued implement run or a dependency hold (up to 50 each), the controller read the issue body, its `sub_issues` and its `blocked_by` (three GETs), plus one GET per dependency outside the factory, so about 40 calls a poll with ten such items; on 2026-11-07 this used up the GitHub App's hourly limit, which also kept `/approve` and `/retry` comments from being read. A failed read failed the whole item's coordination pass, so stored edges did not apply during an outage.
