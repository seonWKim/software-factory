## History

- **The resolve run's `out_of_scope` comment listed the files and offered only `/resolve [notes]`** (until 2026-11-26, wi_fef626be; replaced by the decision at the top of 05-merge-conflict.md). Before: the detail was "changed files outside the conflicts and allowed_paths: <files>", and a `/retry` (with or without `+paths`) on the item at `merge_conflict_pending` was refused with "there is no failed run to retry", so the person did not learn that `/resolve +paths <files>` was the reply that applied.
- **`factory merge` also accepts a local item held for `recurring_failure` whose last failed run is a resolve run** (decision changed 2026-11-21). Before: the local merge gate accepted `merge_pending` and `merge_conflict_pending` only, so an item held after its resolve runs stalled was refused with "is not waiting for a merge (REVIEW, recurring_failure)" even when the owner had fixed the branch by hand.
- **The dashboard only read the stored merge check and showed no diff** (until 2026-11-20, wi_5c4d307a; replaced by the Re-check and Changes tab decision at the top of 05-merge-conflict.md). Before: every replica and the dashboard read the same row, and only the controller's merge check step wrote it, so after the base moved a stored result ("Mergeable against base 76eb55, checked 1d ago") could stay old with no way to refresh it from the dashboard; the UI had no sandbox read, so an item's changed files showed only as the timeline's raw `pr_files` row.
- **`factory merge` on a local item parked at `merge_conflict_pending` checks the branch as it is** (decision changed 2026-11-20). Before: the local merge gate accepted only `merge_pending`, so `factory merge` refused a parked item with "is not waiting for a merge (REVIEW, merge_conflict_pending); `factory merge` applies once its review passed (merge_pending)" before any conflict probe, and a branch fixed by hand needed another `/resolve` run.
- **A conflict resolution that fails only on test files it may not edit asks for them** (decision changed 2026-11-18). Before: in the implement run's sync step, a resolution whose checks failed after the resolve-step retry always failed with `merge_conflict` (`tests failed after the resolution (npm test exited 1)`), which never reached the once-only path grant; the retry prompt got only that sentence, with no failing test names and no output.
- **The resolve run no longer renumbers MySQL steps** (decision changed 2026-11-13, #659 phase 2). Before, this decision stood:
  - > **The resolve run renumbers a duplicate MySQL step too (decision changed 2026-11-08; before: only the update run and the implement sync renumbered, see History).** Found on PR #417: the branch added `migrations/mysql/0039-sync-lease.sql` while main took 0039 with `0039-implicit-verdicts.sql`. The merge is clean (different file names), so the resolve run had no conflict to work on and went straight to its checks, which the duplicate-number check of the MySQL steps failed. Now the resolve run, after its `--no-commit` merge (and the appended-line merge) and **before its snapshot**, plans and applies the same renumbering as the update run (`renumberPlan`, `applyRenumbering` in `src/core/mechanical.ts`, through the worker's `stageRenumbering`): the branch's new steps move to the next numbers after the base's highest (`git mv`), and literal references to the old names in the files the branch changes (index against the base) are rewritten, all **staged in the index with no commit**. The run's own merge commit (`commit-tree` of the checked tree) carries the moves, then the install command and the checks run. The update run and the implement sync keep their separate renumber commit.
  - > **On both paths:** the clean merge (no agent) and the conflict path. Because the moves are staged before the snapshot the scope gate compares against, they are never counted as the agent's changes.
  - > **Files it cannot rewrite:** a file still in conflict has no merged text to rewrite. When a conflicting file still names an old step, the resolve prompt gets a "Migration steps renumbered" section after the notes, naming the moves and those files (`staleStepRefs`), so the agent uses the new name. `prompts/resolve.md` is unchanged.
  - > **Same skip rule:** no renumbering when the branch changes a SQLite schema file (SQLite's list is append-only, with no step numbers in file names). Inline steps (`INLINE_STEPS` in `src/impl/store/mysql/migrations.ts`) are not renumbered; the resolve agent handles them.
  - > **A failure never stops the run:** the worker copies the index aside first; if the renumbering throws, it copies the index back, checks out the tracked files from it (`checkout-index -a -f`, which leaves conflicted files alone), removes any moved step file (`clean -fdq -- migrations/mysql/`), logs `migration renumbering failed`, and the run goes on as it did before this decision.
  - > Solo and enterprise alike: no setting, no schema change.
