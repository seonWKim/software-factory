## History

- **The re-export hub and the command table were in `src/core/commands.ts`** (changed 2026-11-27, refactor, no behaviour change). Before: the core helpers the controller units reach through `src/core/commands.ts` were re-exported by `export { … } from` statements packed several to a line in that file, and the `CommandSpec` table (`COMMANDS`, `CommandPhase`, `CommandState`, `commandSpec`) sat there too, so the file stood at 599 of its 600-line budget. Now the hub is `src/core/commands-reexports.ts` (one export a line, each with its consumer) and the table is `src/core/command-specs.ts`; `src/core/commands.ts` re-exports both, so every import and the names it exports are unchanged.
- **Every install, check and UI check command was one argv run in the run folder** (decision changed 2026-11-26, wi_a4ee0778, "A gate entry can name its folder, and `repo.install_commands` lists several installs"). Before: `repo.install_command` was the only install (one argv), and each `repo.check_commands` entry and `repo.ui_check.command` was a plain argv with no folder; `runChecks` took one `cwd` for every command, so a repo with a Gradle `backend/` and an npm `frontend/` could not install both or run `npm test` in `frontend/` without a shell workaround.
- **Change notes moved here 2026-11-26, wi_a4ee0778** (to keep the topic file under its size cap; the decisions still hold). From "`/revise` while implementing is queued" (2026-11-15): "**Two workers.** The apply is the run's acknowledgement transition, conditional on the item's version and on the run not yet acknowledged; a second worker on the same run end re-reads, finds the `revise_applied` row (no feedback pending) and its transition is refused, so the feedback is applied once." "**A run that fails or blocks** keeps the feedback pending (decision 1 at approval): nothing is applied or dropped, and the next successful implement run end applies it." "**The loop limit.** When `loop_count + 1` reaches `max_loops`, the item blocks with `max_loops` (no run starts, its `comment_ids` settle the feedback) and one comment says the feedback queued while implementing would start loop N, as `prFeedback` does." "**Where it shows.** The command table lists `implementing` among `/revise`'s phases, with its own `implementing_description` (shown there instead of 'Get a new spec written'), so the footer, `/help`, the item API's commands and the SET_UP.md table offer it there; the item page lists pending feedback until it is applied (design 09-dashboard-app)." From "One-tap verdicts" (2026-11-12): "**Pushback.** Bad and Feedback are `changes` rows in `controller_verdicts`, so `listVerdictsSince`, the verdict signal's read, returns them; no new counter. A tap does not call the tacit capture that a typed `/verdict changes` does (that call is the controller's; a tap is stored by the Slack source)." "**Reactions stay** (decision 3): 👍 and 👎 work as before beside the buttons. **Style** (decision 5): the buttons have no colour style until the `design-system/` folder exists in this repository." "**The dashboard** (09-dashboard-app): the item page offers Good, Bad and Feedback through the existing verdict app request (one new row per click: the item has no message there), and its thread shows every verdict. A local item takes them with no Slack call."

Seen 2026-11-22 on wi_d4d15050 (queue entry mqe_23a5859d, merge_requested v7, merge_returned v8).

- **A `/merge` row found its item by the commented issue only, and `factory merge` refused a non-local item** (decision changed 2026-11-18, `/merge` works on a PR whatever its item's source). Before: the forge poll read no PR for a `/merge`, so `mergeComment` looked the item up by the comment's issue alone and a PR of a Slack-sourced item matched nothing (inbound command 1070, PR #692); an unmatched `/merge` was ignored with no reply; and `factory merge <id>` on a non-local item was refused in the CLI ("not a local work item: merge its change on the forge instead") before any row was stored.
- **A merge row from the command inbox went through the comment mapping, and `factory merge` acted only on local items** (decision changed 2026-11-18, a merge command row on a non-local item merges its PR or posts why not). Before: `handleInboxCommand` dispatched a GitHub `/merge` row's comment event, which `commentEvent` maps to null (no `merge` case), so the row was dropped with no action and no reply; `factory merge <id>` on a non-local item returned with nothing done.
- **`/retry +paths` applied only to a failed implement run** (decision changed 2026-11-18, `/retry +paths` widens a failed resolve run). Before: on a failed resolve run it was refused, and a plain `/retry` re-ran the resolve without the path.
- **Every app request was applied by the controller on its next tick** (decision changed 2026-11-15, Approve and Merge from the dashboard at the top). Before: the dashboard's `POST /api/v1/items/:id/commands` stored only the request row and answered 202; the controller applied Approve through the comment command path and Merge through `mergeLocal` or `requestPrMerge` on its next pass (`tick_ms` 2000, some steps each `poll_interval_ms` 30000), so the row kept its old button until then. The approve and merge checks lived in `commands.unit.ts`, `transitions.unit.ts` (the Rule of Two approval), local-merge and pr-events.
- **Every unknown first word went to the sentence form** (decision changed 2026-11-16, the typo reply). Before: `resolveCommand` sent any first word no command claimed, unless it was a flag, to the sentence form; with two or more words that made a model call, so a mistyped command name (`factory stauts wi_1`) paid for one and printed the model's answer.
- **A mistyped `+paths` was a note, and the agent's reply lines were quoted** (decision changed 2026-11-16, mistyped `+paths` refused). Before: `+paths` was read only when the keyword started the first line, and any other first line was the whole note, so `/retry +tests/a.json` retried with no path added; and a needs_human comment quoted the agent's reason and question as written, including a hand-written "Reply: /retry +tests/..." in the wrong form.
