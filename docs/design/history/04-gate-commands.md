## History

- **Every app request was applied by the controller on its next tick** (decision changed 2026-11-15, Approve and Merge from the dashboard at the top). Before: the dashboard's `POST /api/v1/items/:id/commands` stored only the request row and answered 202; the controller applied Approve through the comment command path and Merge through `mergeLocal` or `requestPrMerge` on its next pass (`tick_ms` 2000, some steps each `poll_interval_ms` 30000), so the row kept its old button until then. The approve and merge checks lived in `commands.unit.ts`, `transitions.unit.ts` (the Rule of Two approval), local-merge and pr-events.
- **Every unknown first word went to the sentence form** (decision changed 2026-11-16, the typo reply). Before: `resolveCommand` sent any first word no command claimed, unless it was a flag, to the sentence form; with two or more words that made a model call, so a mistyped command name (`factory stauts wi_1`) paid for one and printed the model's answer.
- **A mistyped `+paths` was a note, and the agent's reply lines were quoted** (decision changed 2026-11-16, mistyped `+paths` refused). Before: `+paths` was read only when the keyword started the first line, and any other first line was the whole note, so `/retry +tests/a.json` retried with no path added; and a needs_human comment quoted the agent's reason and question as written, including a hand-written "Reply: /retry +tests/..." in the wrong form.
- **`/revise` was refused during an implement run** (decision changed 2026-11-15, `/revise` while implementing). Before: `/revise` applied only at the spec gate, after a failed implement run, at the loop limit or at a merge wait; during an implement run the controller refused it with `specNotWaiting` ("the spec is not waiting for approval (the item is implementing)"), shown only under "Last refused command", and the owner resent the feedback by hand once the run ended.
- **The single interpreter read every plain message** (decision changed 2026-11-13, the plain/command classifier). Before: one interpreter call decided both whether a plain message was a command and what it meant, so a plain sentence (a question that named an item or used a command word) could come back as command proposals.
- **A reject applied only while the spec waited for approval** (decision changed 2026-11-13). Before: `/reject` applied at the spec gate, the revision limit, the floor block, a Rule of Two hold, a budget checkpoint and the failure blocks (too large, failed implement, agent asked, repeated failure, review loop limit); at any other open phase (implementing, held by coordination, `phase_hold`, review, the merge wait) the controller refused it with "the spec is not waiting for approval (the item is …)", a CLI sender saw that refusal only in the item's messages, and the help text "Close the item without a merge" promised more than the code did.
- **Every verdict was a new row, and Slack results had no verdict buttons** (decision changed 2026-11-12, one-tap verdicts). Before: a verdict on a result was a typed `/verdict`, a 👍 (or 👎 then `/verdict changes`), or the dashboard's Accept, Changes and Reject; a stored comment ID was always a duplicate, so a person could not change a verdict on the same message.
- **Only a command word was a command after a mention** (decision changed 2026-11-12). Before: `go ahead and merge` after a mention in an item's thread was a plain comment the plain-words reader read, and under a notice a request that made a new item.
- **A top-level mention read as `request`, or not read, was taken in at once** (decision changed 2026-11-12). Before: the intake unit created a work item for a `request` answer, a `none` answer, a requester without `approve_spec`, no model, and an empty, long or flagged message, with no reply, so triage posted a full spec in the owner's thread even when the owner was only asking; only `unsure` got the Make this a task button, and its press posted no line of its own.
- **A plain task never reached intake** (decision changed 2026-11-12, issue #607). Before: `task add` and `task done` were the only task commands; to have the factory build a to-do the owner had to retype it as `task create`, and nothing tied the two.
- **Only a Slack press confirmed a proposal** (decision changed 2026-11-12, issue #585). Before: a plain-language reply's proposals were stored and confirmable only by a Slack button; the CLI had no sentence form and no `factory confirm`, and the dashboard showed only the typed command buttons, so outside Slack a proposal was applied only by typing its line.
- **A pushback stayed in the factory's store** (decision changed 2026-11-11, issue #570). Before: `/revise` and `/reject` were applied in the commands unit and a `/verdict` stored in the verdicts unit, and neither called anything outside the store, so a pushback left no trace the owner's ledger could read.
- **A plain reply with no command got a fixed line; every top-level Slack mention was an item** (decision changed 2026-11-11, the chat answer). Before: the interpreter knew only `commands`, `show`, `question` and `none`, and saw only the message and the open-item list (ID, number, title, state), so it could not answer how an item was doing; `none` was answered with "The factory did not find a command in your comment, so nothing changed." and the command list. A top-level Slack mention became an `item_requested` and the intake step created a work item for it without reading what it meant, so a question to the bot became a work item.
- **Reactions were ignored** (decision changed 2026-11-11, issue #524). Before: the GitHub source added 👀 but never read reactions, and the Slack app had no `reactions:read` scope or `reaction_added` event, so a 👍 or 👎 on a factory message recorded nothing; only a typed `/verdict`, `factory verdict` and the app's verdict request did.
- **Proposals were plain text only, with no store table** (decision changed 2026-11-11, issue #584). Before: a plain-language reply showed its proposed commands as typed lines on every surface, nothing stored them (so a proposal did not survive a restart or reach another replica), and Slack drew no buttons for them; the Confirm and Cancel action IDs in `slack-format.ts` were wired to nothing new.
- **`/revise` on a local item at the merge wait** (decision changed 2026-11-11, issue #563). Before: a local item had no PR, so its `/revise` at the merge wait fell through to the spec path and was refused as "the spec is not waiting for approval"; the command table listed `revise` for local items only at the spec gate and after failures, so `/help`, the footer and the item page did not offer it there.
- **An approved spec kept the spec gate's answer block; a stale button got the refusal** (decision changed 2026-11-11, issue #586). Before: a spec auto mode approved still said to reply `/approve` with `N: <answer>` lines, its approval was a note above the plain footer, and a press of a button whose command no longer applied reached the command handler, which answered with the shared `was not applied` text.
- **No verdict in Needs you** (decision changed 2026-11-11, issue #513). Before: a Needs-you row offered only commands that change state, so a waiting item offered no verdict there; a verdict was sent from the item page.
- **Command suggestions for plain-language replies** (decision changed 2026-11-11, issue #583). Before: `suggestCommand` (`src/core/suggest.ts`) saw only the comment and the current item's state and returned at most one command for that item at confidence 0.85 or more; comments over 300 characters were skipped; args that failed the egress scan gave the command list instead; and Slack drew Confirm and Cancel buttons under the suggestion, parsed from the reply by `suggestedCommand`. A message naming several items, asking to see one, or unclear got no useful answer.
- **A verdict needs a PR on every surface but the controller** (decision changed 2026-11-11, issue #523). Before: the controller recorded a verdict on a local item with no PR, but `applies()` required a PR, so the item API, `/help`, the footers and the SET_UP.md table did not offer `/verdict` there; `factory verdict` was an unknown command; the item page had only the note box; and the closed-item refusal text lived only in the verdict unit.
- **App requests** (decision changed 2026-11-11, issue #453). Before: only `approve`, `merge`, `reject`, `revise` and `verdict` were applied from an app request (a dashboard `retry` or `resolve` got the refusal `only \`approve\`, \`merge\`, \`reject\`, \`revise\` and \`verdict\` are applied from an app request; reply \`/retry\` on the issue instead`), and the app path had its own copy of the `approve_spec` check and the approve, reject and revise transitions beside the comment's handler, which returned nothing and posted its own refusal.
- **Each surface reads the command table its own way** (decision changed 2026-11-11, issue #528). Before: the dashboard listed every command that applied in the item's state whatever the viewer's grants; the CLI had its own list and no help command; `factory approve` stored a command row in any state and only the controller refused it later; in Slack a bare `approve` after the mention was a plain comment, and help outside an item's thread named neither the request nor `/link`.
- **The spec comment says how to answer its decisions** (decision changed 2026-11-11, issue #527). Before: the comment listed its decisions as a numbered list and ended with the command footer, but did not say that `/approve` takes one `N: <answer>` line per decision or what an unanswered decision takes, although the parser already read those lines from any source.
- **App requests** (decision changed 2026-11-11, issue #527). Before: only `approve`, `merge`, `reject` and `verdict` were applied from an app request; a dashboard `revise` was recorded and then refused (`only \`approve\`, \`merge\`, \`reject\` and \`verdict\` are applied from an app request; reply \`/revise\` on the issue instead`).
- **`/revise` in a Slack thread is PR feedback** (decision changed 2026-11-09, issue #481). Before: only a `/revise` carrying a PR (from GitHub's PR-conversation poll) was PR feedback; a Slack thread `/revise` on an item with a PR fell through to the spec-revision path and was refused with "reply `/revise <feedback>` on PR #N", a PR conversation the Slack user may not use.
- **Auto mode answers the spec gate** (decision changed 2026-11-08, issue #444). Before: only `/approve` or the standing rule `spec-t1` approved a spec waiting at the gate.
- **`/resolve +paths` and `/resolve` notes** (decision changed 2026-11-08). Before: `/resolve` passed its raw text as the resolve run's notes, with no egress scan and no length cap, and `+paths` was not split off, so a resolve that needed a file outside the conflicts and the allowed paths could only fail `out_of_scope` (PR #416).
- **Commands at the review loop limit** (decision changed 2026-11-08). Before: `max_loops` had no command in the table; its footer ended with "No command changes this item's state now.", `/retry` was refused as "no failed run to retry", and `/revise` and `/reject` were refused because no spec was waiting, so the item could only be closed or changed by hand.
- **Implicit verdicts and the lenient `/verdict`** (decision changed 2026-11-08, issue #316). Before: only `/verdict` wrote verdicts; `/verdict accept` alone and `/verdict yes` were refused (a severity was required for every kind), so every owner `/verdict` on record was refused; merges, pushes and reverts wrote no verdict; a `/verdict` on a merged item was refused as closed.
- **Standing approvals at the spec gate** (decision changed 2026-11-07, issue #299). Before: every spec at or above `dials.spec_gate_min_tier` waited in `spec_pending` for a human `/approve`, `/reject` or `/revise`; no command accepted or declined a standing rule, and nothing acted on one.
- **Commands from the command inbox** (decision changed 2026-11-07, issue #282). Before: CLI commands reached the controller only through the `local` source's poll, so only when `local` was listed in `plugins.source`; app requests were read straight from their own table each tick; and a refusal reply that failed to post kept an app request pending.
- **Widening allowed paths from a command** (decision changed 2026-11-07, issue #280). Before: allowed paths were set once by triage; `/approve` text was only a note and `/retry` took no text, so a run that needed one more file was refused by the scope gate every time, and the only fix was a `/revise` that ran triage again. No comment told the owner which reply would help.
- **PR titles** (decision changed 2026-11-07, issue #229). Before: `factory: <issue title>`; the prefix pushed titles past 50 characters, and the bot author and the `factory/` branch already mark the PR.
- **Gate commands** (decision changed 2026-11-01). Before: the spec gate took only `/approve` and `/reject <reason>`, a reject dropped its reason and left the issue open, and PR titles were the spec's first line cut at 80 characters.
- **`/revise` after a failed implement run** (decision changed 2026-11-01, issue #91). Before: a failed implement run or a `diff_too_large` block took only `/retry`, which runs the same spec again, so an owner whose change was too big could not change the spec.
- **Refusals name the state by its label** (decision changed 2026-11-01, issue #91). Before: refusals printed the raw stage, and the `/resolve` refusal also printed `blocked_on` and `blocked_reason`, which the owner cannot act on.
- **Approval notes, `/help`, unknown commands and footers** (decision changed 2026-11-01). Before: a note after `/approve` was dropped, `/approve some note` was not even an approval, a mistyped command such as `/aprove` got no reply, and no comment listed the commands that work on an item.
- **Command suggestions for plain-language replies** (decision changed 2026-11-01). Before: the GitHub source dropped every comment that was not a command before the controller saw it, so "ship it" on a spec got no answer and the person could not tell whether the factory understood.
- **Verdict command** (new decision, 2026-11-01). Before: the gate commands were only `/approve`, `/reject` and `/retry`, read only on the issue, and human feedback on a PR was free-form text.
- **App requests** (new decision, 2026-11-07, issue #245). Before: commands came only from comments on the issue or the PR; the `inbound_app_requests` table (migration 22) was read by nothing.
- **App requests** (decision changed 2026-11-09, issue #452). Before: only `approve` and `merge` were applied from an app request (a dashboard `reject` or `verdict` got the refusal `only \`approve\` and \`merge\` are applied from an app request`); a `/verdict` was refused on every item with no PR (`the work item has no PR yet`), local items included; and `/reject` closed only the source issue, leaving an open PR open.
- **Feedback on a pull request** (decision changed 2026-11-04, issue #178). Before: once a PR existed, `/revise` worked only on the issue at the spec gate or after a failed implement run; `/revise` on the PR found no item, and the GitHub source never read PR reviews, so "Request changes" was lost. `failed_run` also covered failed review runs.
- **Answers to the spec's decisions** (decision changed 2026-11-10, issue #526). Before: an approval note reached the implement and review runs as one plain text, so an agent could not tell which answer belonged to which decision, and auto mode's `spec_approved` stored only `decisions`, a count.
- **MySQL text removed from the current decisions** (decision changed 2026-11-11, issue #567). Before: the proposals table was "SQLite migration 43, MySQL step `0044-command-proposals.sql`, since 0043 is merge-evaluations"; the verdict columns came from "SQLite migration 39, MySQL step 0039" and the implicit-verdict paragraph ended "Enterprise: the GitHub forge, implicit verdicts from its PR events, on the shared store with both migrations applied"; the command inbox copied pending requests with "SQLite migration 29 (MySQL step `0029-thread-outbox.sql`)"; migration 6 was "(SQLite and MySQL)"; and the app request handling was "migration 23 on SQLite, step `0023-app-command-handling.sql` on MySQL".
