## History

- **The approver's notes were only the approval's and the `/retry` note** (decision changed 2026-11-23, `/note`). Before: the "Notes from the approver" section held the note on the latest approval that had one and the latest `/retry` note; an owner's later comment or an interactive session's notes were not read, so an item already queued or in review could get no reason from its owner.
- **Change notes moved here 2026-11-23** (to keep the topic file under its size cap; the decisions still hold). From "A mention creates an item only on a press" (2026-11-12): "Not changed. Replies inside an item's thread, the `submit_work` refusal reply, the button's layout, items created from earlier mentions (no backfill), the store (no schema change), one model call per message." From "Commands from the command inbox" (2026-11-07): the `inbound_app_requests` table's "pending-request read is removed", and "No change to the authorize rule, the command table or the refusal wording." From "App requests" (2026-11-11): until 2026-11-07 the controller read "up to 20 pending rows of the request table". From "A mistyped CLI command name gets \"did you mean\"" (2026-11-16): "**Unchanged.** A word with fewer than 4 letters, or further than 2 edits from every name, still runs the sentence form as before, and a flag still prints the usage. How the sentence form reads a sentence of two or more words is unchanged."
- **A `restart` app request was refused as an unknown command** (decision changed 2026-11-20, `restart`). Before: the factory had no run command; a merged item offered nothing to run its result, and the local merge reply said nothing about it.
- **One-time steps of the command inbox** (moved here 2026-11-20 from the 2026-11-07 decision, which still holds). The `commands` cursor started where the `local` source's `intake:local` cursor stopped, copied once by a data step (since 2026-11-11, issue #467: the relay reads only `commands`; design 05-sources), so a command it already read was not applied again; SQLite migration 29 copied the app requests still pending into the inbox.
- **Replaced by the app requests decision** (decision changed 2026-11-11, issue #453): "only `approve`, `merge`, `reject`, `revise` and `verdict` are applied from an app request, and `approve`, `reject` and `revise` have their own copy of the comment's check and transition".
- **Replaced by one-tap verdicts** (decision changed 2026-11-12): "a person's verdict on a result is typed (`/verdict`), a 👍 or 👎, or the dashboard's Accept, Changes and Reject, and every verdict is a new row".
- **A `/merge` row found its item by the commented issue only, and `factory merge` refused a non-local item** (decision changed 2026-11-18, `/merge` works on a PR whatever its item's source). Before: the forge poll read no PR for a `/merge`, so `mergeComment` looked the item up by the comment's issue alone and a PR of a Slack-sourced item matched nothing (inbound command 1070, PR #692); an unmatched `/merge` was ignored with no reply; and `factory merge <id>` on a non-local item was refused in the CLI ("not a local work item: merge its change on the forge instead") before any row was stored.
- **A merge row from the command inbox went through the comment mapping, and `factory merge` acted only on local items** (decision changed 2026-11-18, a merge command row on a non-local item merges its PR or posts why not). Before: `handleInboxCommand` dispatched a GitHub `/merge` row's comment event, which `commentEvent` maps to null (no `merge` case), so the row was dropped with no action and no reply; `factory merge <id>` on a non-local item returned with nothing done.
- **`/retry +paths` applied only to a failed implement run** (decision changed 2026-11-18, `/retry +paths` widens a failed resolve run). Before: on a failed resolve run it was refused, and a plain `/retry` re-ran the resolve without the path.
- **Every app request was applied by the controller on its next tick** (decision changed 2026-11-15, Approve and Merge from the dashboard at the top). Before: the dashboard's `POST /api/v1/items/:id/commands` stored only the request row and answered 202; the controller applied Approve through the comment command path and Merge through `mergeLocal` or `requestPrMerge` on its next pass (`tick_ms` 2000, some steps each `poll_interval_ms` 30000), so the row kept its old button until then. The approve and merge checks lived in `commands.unit.ts`, `transitions.unit.ts` (the Rule of Two approval), local-merge and pr-events.
- **Every unknown first word went to the sentence form** (decision changed 2026-11-16, the typo reply). Before: `resolveCommand` sent any first word no command claimed, unless it was a flag, to the sentence form; with two or more words that made a model call, so a mistyped command name (`factory stauts wi_1`) paid for one and printed the model's answer.
- **A mistyped `+paths` was a note, and the agent's reply lines were quoted** (decision changed 2026-11-16, mistyped `+paths` refused). Before: `+paths` was read only when the keyword started the first line, and any other first line was the whole note, so `/retry +tests/a.json` retried with no path added; and a needs_human comment quoted the agent's reason and question as written, including a hand-written "Reply: /retry +tests/..." in the wrong form.
- **App requests** (decision changed 2026-11-11, issue #453). Before: only `approve`, `merge`, `reject`, `revise` and `verdict` were applied from an app request (a dashboard `retry` or `resolve` got the refusal `only \`approve\`, \`merge\`, \`reject\`, \`revise\` and \`verdict\` are applied from an app request; reply \`/retry\` on the issue instead`), and the app path had its own copy of the `approve_spec` check and the approve, reject and revise transitions beside the comment's handler, which returned nothing and posted its own refusal.
- **App requests** (decision changed 2026-11-11, issue #527). Before: only `approve`, `merge`, `reject` and `verdict` were applied from an app request; a dashboard `revise` was recorded and then refused (`only \`approve\`, \`merge\`, \`reject\` and \`verdict\` are applied from an app request; reply \`/revise\` on the issue instead`).
- **Commands from the command inbox** (decision changed 2026-11-07, issue #282). Before: CLI commands reached the controller only through the `local` source's poll, so only when `local` was listed in `plugins.source`; app requests were read straight from their own table each tick; and a refusal reply that failed to post kept an app request pending.
- **App requests** (new decision, 2026-11-07, issue #245). Before: commands came only from comments on the issue or the PR; the `inbound_app_requests` table (migration 22) was read by nothing.
- **App requests** (decision changed 2026-11-09, issue #452). Before: only `approve` and `merge` were applied from an app request (a dashboard `reject` or `verdict` got the refusal `only \`approve\` and \`merge\` are applied from an app request`); a `/verdict` was refused on every item with no PR (`the work item has no PR yet`), local items included; and `/reject` closed only the source issue, leaving an open PR open.
