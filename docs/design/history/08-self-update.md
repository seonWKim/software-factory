## History

- **SQLite: a breaking migration waits for `npm run migrate`** (changed 2026-11-17, local-task-tk_dac45611). Before (decided 2026-11-09, runtime review H1/H2): an update with a pending breaking migration took the waiting path until the owner ran `npm run migrate` (or set `updater.auto_migrate`), and every other open of a database holding data (a child, the CLI) refused with `migration_pending` and the message naming `npm run migrate`, so a project's `gb` commands stayed blocked after an update.
- **Only `npm run migrate` files a supervisor request; the supervisor has no restart action** (changed 2026-11-16). Before: `supervisor-request.json` took `drain`, `start` and `cancel`, all from `npm run migrate`; a `start` with no migration under way was ignored; the status page filed nothing and its banners told the owner to run `npm run migrate` or `npm run factory -- dev`.
- **The controller and the worker can also run alone** (changed 2026-11-16). Before: `factory controller` and `factory worker` (and `make controller` / `make worker`) ran one loop each outside the supervisor, through a mode argument of `runLoops`; `npm run migrate` did not drain them, so SET_UP.md told the owner to stop them by hand first.
- **Local mode follows the local base branch** (changed 2026-11-15). Before: with no GitHub plugin selected, the updater always followed the code checkout's local `refs/heads/<repo.base_branch>` and never fetched, whether or not the code checkout was the repository `factory merge` moves; with the GitHub source a separate clone followed `origin/<repo.base_branch>`, fetched every poll.

- **The CLI always rebuilds** (changed 2026-11-14). Before: the `factory` script ran `npm run --silent build` before every command, so each `npm run factory -- <cmd>` (`task list`, `status`) paid a full `tsc` and Vite build even when no source had changed.
- **Build output always shown** (changed 2026-11-14). Before: `scripts/build.mjs` ran `tsc` and `vite` with inherited output, so every successful build printed Vite's chunk size warning (4 lines) to the stdout of the CLI command that triggered it, before the command's own output.
- **Current text names SQLite only** (decision changed 2026-11-11, issue #567). Before: with an external config, on a shared (MySQL) store the reviewed keys (`dials`, `floors`, `plugins`, `permissions`, `auth`) still came from the version folder's checked-in file; and a database that holds data refused a pending breaking migration with `migration_pending` "as MySQL does".
- **Server revision = folder git HEAD** (changed 2026-11-13). Before: `factory ui` reported `git rev-parse HEAD` of its code root as `server_rev`. After a docs-only update moved the checkout without a build, the page (built at the old commit) and the server differed, and the "Dashboard out of date" banner showed although nothing was out of date.
- **Hand-started status page on old code** (changed 2026-11-08). Before: a `factory ui` started by hand was never checked against the factory's revision, so it kept serving old code and the old API (a 404 on `/api/v1/failures`) after every update, with only the banner to say so.
- **Status page restarts** (changed 2026-11-07, issue #311). Before: `factory ui` was started by hand and the supervisor never restarted it, so after an update it kept serving the old code and the old API.
- **Self-update** (D7, decided 2026-11-01). Order on a code change: build the new commit beside the running child first, then drain (IPC; the worker stops claiming and finishes its in-flight run), fast-forward, swap in the build, restart. This deliberately differs from "drain, update, build, restart": a failed build must leave the old version running. The drain-then-start order and the single `runtime` copy were replaced the same day.
- **Self-update: start-then-drain** (D7 changed 2026-11-01, issue #120). Before: drain-then-start. After a successful build the supervisor drained the running child and waited for it to exit before fast-forwarding `<state_dir>/runtime` and starting the new version, so one long run, up to `run_timeout_ms` (45 minutes), held every other worker idle after each merge.
- **Self-update: a new revision that needs `npm run migrate`** (changed 2026-11-07, issue #165). Before: it started at once like any build; its store refused to open, the child exited and the supervisor restarted it every poll (a crash loop) while the old child was already drained. `npm run migrate` had to be run with `dev` stopped.
- **Self-update: the drain stops the controller too** (changed 2026-11-07, issue #294). Before: a drain stopped only the old child's claiming; its controller kept running intake and the reaper until its worker drained, then ran one final pass.
- **Build in place** (changed 2026-11-07). Before: `npm run build` began by deleting `dist/` and `web/dist/`, then compiled into them. Every `npm run factory -- <cmd>` did so in the main checkout, so two CLI calls at once crashed each other (`Cannot find module dist/main.js`), a running `factory ui` lost `web/dist` mid-serve, and the supervisor could fail to start a child during a build.
- **Self-update: legacy runtime cleanup** (removed 2026-11-09, issue #466). Before: the first start under `versions/` removed the legacy `<state_dir>/runtime` and `runtime-next` worktrees once the sweep found no live child, and the updater took both paths as options. Removed because every install has used `versions/` since 2026-11-01, so the cleanup never found anything; leftover folders on old installs are not deleted.
- **Self-update: worker block size source** (changed 2026-11-07, issue #336). Before: the block size was always read from the new version folder's `factory.config.json`, and children and migrate calls got no config path, so an external config was ignored under `git-worktree`.
- **SQLite breaking migrations** (changed 2026-11-09, runtime review H1/H2). Before: the supervisor's `migrate --status --json` reported only the project-key data step on SQLite, so an update with a breaking migration took the plain swap: the new child renamed `runs`, `work_items` and the rest on open while the old child still wrote them. `npm run migrate -- --status` and `--dry-run` also opened the store with `migrate()`, so they applied every pending migration, breaking ones included, with no drain.
- **Self-update: in-place reason text** (changed 2026-11-29, issue #917). Before: the in-place reason was "Running from your checkout. To update, stop `factory dev`, pull, and start it again." It showed literal backticks and led with a command; Now: one plain sentence saying updates from the page are off because the factory runs from the checkout, and what to do.
