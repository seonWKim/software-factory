# 9. Status page: dashboard Work, Workers, Spend and Data pages

- **The Failures page speaks plain words, and Work uses the shared controls (decision changed 2026-11-16; current; replaces the Work tree's summary line and the raw error code heading of the 2026-11-07 Failures decision, see History).** The decision that changed: **each failure group is titled in plain words, and Work has no summary line.** `web/src/views/failures.tsx` titles a group with the code's `failure.<code>.title` from `web/src/i18n/en.ts`, then its one-line meaning and next step (`.meaning`, `.next`); the raw code is small secondary text under the title. A code with no copy shows the raw code as its title and a generic line. Every code of `FAILURE_DESCRIPTIONS` (`src/ui/failures.ts`) plus `spec_conflict`, `checks_failed` and `agent_timed_out` has copy, and a test enforces it. The failures read no longer sends `description`; the copy lives in the catalog (`FAILURE_DESCRIPTIONS` stays for the why text). Each group links to Work as `/app/items?ids=<item ids>`: the page filters its rows to those items in the browser (closed ones too), says so in a Notice with Show all, and the server is unchanged. The 24h / 7d switch is a `SegmentedControl`; the run table is a `DataTable`. **Work:** Tree / List is a `SegmentedControl`, the state filter is `Tabs` (each tab carries its count), the summary line is removed, and the rate limit shows as a `Notice` only while its pause is set. Health merges, the running, queue and items tables and the settings tables are `DataTable`s; `DataTable` takes `dataKey` to put each row's key in `data-key`, and a column may set `className`. The Plugins Import button, when off, says in a visible `Notice` that import runs with `factory plugins import`; a dashboard import is a follow-up. A test (`tests/web-i18n-text.test.ts`) fails on an `en.ts` key with no literal use in `web/src`, except keys built from the listed template prefixes.
- **The Queue page is removed; Work's Queued filter shows the queued runs (decision changed 2026-11-14; current; replaces "Work's Queued filter is item-based" in the 2026-11-13 sidebar decision's Queued paragraph and the Queue page, see History).** The decision that changed: **there is no Queue page or menu entry**, and **Work's Queued filter (tree and list) shows the queued runs from `GET /api/v1/queue`** through `QueueTable` (`web/src/views/common.tsx`; table label and Section title `queue.title`, "Queued runs"): position, item, run, attempt, queued and starts, in the server's order, from the one helper `useQueuedRuns` (`web/src/views/pages.tsx`). The summary's "N queued", the Queued filter button's count and the list's header count are all the length of that read, the same number as `overview.queued`. The list view does not send `state` or `q` to `GET /api/v1/items` while Queued is on, so every queued run's item is in the title lookup. **Work's initial filter** comes from the `state` query parameter (an unknown value is no filter). **Old route:** `/app/queue` redirects in place to `/app/items?state=queued` (`REDIRECTS`, `redirectFor`; `routeFor` ignores the redirect's query); the app shows nothing while the address is swapped, so Work starts with the query. `GET /api/v1/queue`, `overview.queued` and the item-based `state=queued` filter of `GET /api/v1/items` are unchanged. `page.queue` is deleted. No server, store or schema change.
- **The Data page says what each table holds and answers plain-text questions (decision changed 2026-11-14; current; replaces "the Data page lists tables by name only, and free-form SQL is out of scope", from the 2026-11-07 Data page decision below, see History).** The decision that changed: **each table has a line, an owner and column meanings, and the owner can ask a question that becomes one read-only query.**
  - **Table docs.** Each component keeps a `table-docs.ts` beside its migrations (`src/<component>/table-docs.ts`: bus, calendar, controller, identity, inbound, outbound, runtime, state, worker): `TABLE_DOCS`, one line per table it declares (key `table`) and a meaning for a column whose name does not say (key `table.column`). State describes `schema_migrations` and the extension pack tables; a `legacy_` copy gets no line (changed 2026-11-15 with the legacy contract, design 10-event-driven; see History): every value of a table no component describes shows as `[hidden]`, so `HIDDEN_COLUMNS` lists no `legacy_` copy, and the test skips `legacy_` tables; the bus describes its run-time topic tables by suffix. `src/ui/data.ts` gathers them (`TABLE_DOCS`, `tableDoc`); one source, no list in `web/`. `tests/data-table-docs.test.ts` fails when a table of a freshly migrated SQLite store has no line, or a line names a table or column the store lacks. `GET /api/v1/data/tables` adds `description`, `owner` and `column_docs` per table (null and `{}` for a table no component describes; a hidden column gets no meaning) and `csrf_token` (the Settings token; null when the Ask route is not wired). No table, column or migration was added.
  - **Ask route.** `POST /api/v1/data/ask` with `{ question }` (1 to 1000 characters; `src/ui/data-ask.ts`), wired through `UiSettings.ask` (`buildUiParts` builds the Model plugin, `plugins.llm`, in the UI process; null when it cannot be built). Guards in order: Host, Origin, Content-Type, the CSRF token, the body size, JSON, then the owner check (`ownerOf`, 403 for anyone else) before any model call; then the question (400). A store with no read-only query answers 409. No model: 503 with a message; a model error or no query: 502 with a message; no query runs in either case, and the table list still loads.
  - **Model input.** One `LLMProvider.complete` call (`standard` class, JSON output `{ sql }`): the instruction, the question, today's UTC date (the Spend page's day), and each table's and column's name with its line and meanings. Hidden columns and tables no component describes (the `legacy_` copies until the contract migration) are left out; no row value and no row count is sent. The request passes the egress scan (`log` channel) first; a flagged request is not sent (400). A single-value answer line is built by code from the one result cell (`<column>: <value>`), never by a second model call.
  - **Query checks and connection** (`FactoryStore.readOnlyQuery`, `src/impl/store/sqlite/readonly-query.ts`). Before running: one statement (one trailing `;` allowed) that begins with `SELECT` or `WITH` and has a `SELECT`; ATTACH, DETACH, PRAGMA and every write or transaction word anywhere in the code (comments and string literals blanked) is refused, each with its reason (422 with the query and `refused`). A query that names a hidden column (`HIDDEN_COLUMNS`, quoted or not) is refused the same way; a result column with a hidden column's name shows `[hidden]`, and the query's reads of hidden columns give NULL. The query runs in a child process (`readonly-query-worker.ts`) on its own connection, opened read-only (`readOnly`, SQLITE_OPEN_READONLY) with `query_only` on and, on Node 24.10 and later, an authorizer that allows only reads; each of the three refuses a write alone. On an older Node (22.13 to 24.9, as on CI) no authorizer runs: an ATTACH or `PRAGMA query_only = OFF` still leaves nothing writable (attached databases open read-only), and a query whose plan (EXPLAIN) reads a hidden column, or opens an index holding one, is refused instead of reading NULL, since the name check alone misses a hidden column read under another name (a renamed CTE column) (decision changed 2026-11-14: hidden-column reads are refused, not NULL, where no authorizer runs). At most 500 rows (`truncated` when cut); past 5 seconds the child is killed and the query refused with a time-limit message. Why a process: `node:sqlite` cannot interrupt a running statement, a process can be killed.
  - **Results.** Every text cell, the query text and the column names pass the Withholder (`[withheld: <rule>]`). The response: `{ as_of, sql, columns, rows (arrays, in column order), truncated, answer }`.
  - **Cost.** Each model call writes one `data ask: model call` log record (model class, provider, input and output tokens, `cost_usd`) through the page's logger. It is not in the Spend totals: spend counts run outcomes only (06-spend), and the Ask has no run and no table of its own.
  - **Page.** Below the Autonomy line, an "Ask" section (shown when `csrf_token` is set): a `Field` with a `Textarea`, a primary Ask button, then the query, the one-line answer, a cut notice and the result table; a refusal is a `warn` `Notice` under the query, a message alone a `bad` one. The table list shows each table's owner and line under its name; the table card shows the line, `Owner: <component>`, and the column meanings (also as the column header's title). Strings are `data.*` keys in `web/src/i18n/en.ts`.
  - Not built: typed SQL when the model is off, saved questions, charts, any write.
- **The Spend page (decision 2026-11-13, wi_199b; current; new page, replaces nothing).** `/app/spend` sits in the System group of the sidebar right after Failures (`web/src/views/spend.tsx`, `page.spend` and its strings in `web/src/i18n/en.ts`). It reads `GET /api/v1/spend` (the last 30 UTC days) and shows: three totals, Today, This week (from Monday UTC) and Last 30 days, each with cost and tokens; one bar chart of cost per UTC day, plain list elements in the `accent` token colour scaled to the day that cost most, each bar named with its day and cost for screen readers, no chart dependency; the tasks by cost in a `DataTable` (item title linking to the item page, cost, tokens, runs, kinds, and a No cost column only when some task has runs with no stored cost); and the count of runs with no stored cost, said apart, never shown as $0. The Settings page's number field takes fractions (`step="any"`) so a dollar budget such as 12.50 can be typed, and an unset value (null) shows an empty field. Design 06-spend holds the read model and the budgets.
  - **`processes` on `/api/v1/workers` (new field, 2026-11-07, issue #209; design §5 Worker slots reported per process).** One entry per worker process whose store row is at most `lease_ms` old, idle processes included, ordered by host then pid: `process_id` (`<host>:<pid>`), `pid`, `host`, `slots` (the live count; 0 while draining), `max_slots`, `busy` (slots holding a run), `idle` (`slots - busy`, at least 0), `index_base`, `started_at`, `reported_at`, and `worker_runs`: the running runs whose lease owner is one of its worker loops (`id`, `kind`, `work_item_id`, `worker_id`, `started_at`). `process_id`, `host` and `worker_id` pass through the `Withholder`. The `workers` array is unchanged. The field reads `listWorkerProcesses`, a new store read; this replaces "no store method changed" for this route only. It is on `/api/v1/workers`, not `/api/health`, because health is doctor output. The read is a report, never a gate: when it fails (a database without step 19, say) the route still answers 200 with `workers` as usual, `processes: []` and `processes_error` (the error text, through the `Withholder`).
  - **Data page and raw table reads (new decision, 2026-11-07, issue #239).** A read-only debugging view of every store table, so what the factory did no longer needs a hand-written query. **Store:** two new `FactoryStore` reads, implemented once in `SqlFactoryStore` for SQLite: `listTables()` (every table of the backend's schema from the database's own catalog: `sqlite_master` with `pragma_table_info`; each with its row count, columns, primary key and `order_by`) and `listTableRows({ table, limit, offset, filter })` (one page, newest first, with the total after the filter; `limit` defaults to 50 and is capped at 200; null, with no row read, for a table or filter column the catalog lacks). Order: the first of `created_at`, `at`, `started_at`, `updated_at` the table has, then its primary key, all descending; a table with neither keeps the database's order. Names reach SQL only after they are found in the catalog (and match a plain identifier); the filter value is always a bound parameter. No migration, schema or write path changed. **API** (`src/ui/data.ts`, routed from `src/ui/api.ts`, `GET`/`HEAD` only like every route): `/api/v1/data/tables` (`name`, `rows`, `columns`, `hidden`) and `/api/v1/data/tables/:name?page=&limit=&col=&val=` (`rows`, `total`, `page`, `limit`, `columns`, `hidden`, `order_by`, `filter`, and `run_items`: run id → owning item for the run ids on the page). The allow-list is the store's catalog: the route reads `listTables` first, so an unknown table or column is a 404 before any row is read; 400 for a bad `page`/`limit` or `col` without `val`. **Hidden columns**, listed once in `HIDDEN_COLUMNS` (`src/ui/data.ts`): `runs.lease_token`, `listener_leases.token`, `run_attempts.lease_token`, `link_codes.code_hash`. They leave only as `[hidden]`, and a `col=` naming one is a 404 with no store call, so a hidden value cannot be probed by filtering. Every text cell (and the echoed filter value) passes the API's `Withholder` on the same channel as the other routes; numbers and nulls pass as they are. **Page** (`web/src/views/data.tsx`): a "Data" entry in its own Tools group of the sidebar, after Settings (the Pages group is unchanged); the table list with row counts on the left, one page of rows on the right with a sticky header and horizontal scroll, an exact-value filter, Previous/Next, `wi_…` values linked to the item and `run_…` values to the item that owns the run, Copy row as JSON (the values the API gave, markers included, never a raw value), and cells over 300 characters cut on the page with "Show all" for that cell (the API returns the full text, so no second read). It never polls: no interval, no refetch on focus; only the top bar's Refresh reads again. Out of scope: editing or exporting rows, shared-storage transcripts (free-form questions: the Ask decision of 2026-11-14 at the top). Residual risk: the Withholder catches only what the egress scanner detects, so free-form JSON such as run input can show prompt text that is not secret-like. Decision changed: "the API calls only store read methods; no store method changed" now has two more reads, `listTables` and `listTableRows`, used by the data routes only. **Autonomy line (new decision, 2026-11-11, issue #522):** `GET /api/v1/data/autonomy` (`dataAutonomy`, `src/ui/data.ts`) returns `{ as_of, merged, with_push, autonomy }` from `collectAutonomy`, the function `factory stats` uses ([06-measurement.md](06-measurement.md) Autonomy), so both give the same numbers for the same store; one `listStatsRecords` read, no write. The Data page shows one line above the tables, `Autonomy: 0.75 (3 of 4 merged factory items with no person's push)`, or `Autonomy: not enough data` when no factory item merged; it reads like the rest of the page, only on load and Refresh.

  - **Unreviewed merges in the app (new decision, 2026-11-07, issue #268).** `GET /api/v1/unreviewed-merges?limit=N` returns the stored `controller_unreviewed_merges` rows, newest first: default 50, at most 200 (a larger value is capped, a non-numeric or zero one is 400). Each row: `project` (the stored label, `unknown project` when none; never the key), `change_ref` (the PR number as text), `change_url`, `merge_sha` (first 7 characters), `merged_by` (the stored user ID, `unknown` when null; no display name) and `recorded_at`. `change_url` is always `null` (decision changed 2026-11-08): the store keeps no link for an unreviewed merge yet, so the app shows `#<change_ref>` as text; storing one is a follow-up. Every string passes the `Withholder`; the sha is scanned whole, then shortened. `/api/v1/overview` adds `unreviewed_merges_7d`, the count of rows recorded in the last 7 days, from the new store read `countUnreviewedMergesSince(since)` (SQL store only). The Floor shows "N PRs merged without review in the last 7 days" with a link to Health, hidden at 0; the Health page has a "Merged without review" table (PR, merged by, merge commit, when), newest first. Read-only: no schema, migration or recording change; no way to mark a merge reviewed. Factory stats are unchanged.

- **Work items tree (decision changed 2026-11-08, issue #295; current).** The Work items page defaults to a tree (`web/src/views/tree.tsx`, `react-aria-components` `Tree`: treegrid roles, arrow keys move focus, right expands, left collapses). A split parent holds its phases in phase order; every other item is a top-level row, in the API's ranked order. Each item shows once: a held item stays where its parent puts it and is never moved under the item it waits for; it carries a "waits for #N" chip linking to that item (a phase hold: the previous phase; a dependency blocker: the named issue; a coordination hold: the holder from the latest claim decision). A row shows `#N` and title, the state badge, the wait reason and the running run's worker ID (on a second line at phone width), the run kind and attempt (queue position when queued, run time when running), the PR link and the last update. **CI is not shown:** the store holds no CI result (it comes from GitHub at check time); a follow-up issue covers storing it. **List toggle:** keeps the flat table unchanged (same server `state` and `q` query); the choice is saved in `localStorage` (`sf.items.view`), the tree is the default. **One request per poll:** the tree reads `GET /api/v1/items?closed=1` once and filters in the page (state, search, held); the list sends its server filters as before. **Filters in the tree:** closed items are hidden unless "Show closed" (or the Closed filter) is on, so a parent whose phases are all closed is one row; a match shows its parents for context; the state filter ("held": a held claim or a phase waiting for its previous phase) is a row of tabs with counts (the summary line was removed 2026-11-16, see the first decision). Expanded rows are saved per browser (`sf.items.expanded`); "Expand all" and "Collapse all" set them; the default is every parent with an open phase expanded. **API:** each row of `/api/v1/items` adds `parent_id`, `phase`, `waiting_on_number`, `run` (`kind`, `status`, `attempt`, `worker_id`, `started_at`, `position` when queued) and `claim` (the latest claim decision of the current implement run, null when it is from an earlier run: `decision`, `holder`, `holder_id`, `approved`, `cost`, `threshold`); existing fields keep their names and values. `worker_id` and `holder` pass the Withholder. The decisions come from one batched store read, `listLatestClaimDecisions(ids)` (read-only, no schema change). Out of scope: CI per PR row, commands from this page.
- **Workers, Failures and the effective worker count (decision changed 2026-11-07, issue #312; current).** **Workers page:** one row per entry of `processes` on `/api/v1/workers`: host, pid, start time, busy and idle slots (idle is slots minus busy, never below 0), current and max slots, the process's runs, and a "draining" badge when `slots` is 0. It shows the effective worker count once, as "Worker setting: N (override | config file | default)"; the factory banner no longer states a count. **Overview:** `factory.workers` is the effective `workers` setting (`effectiveGlobal`, `src/ui/settings-api.ts`: the Settings page's resolve of file, override and default, capped at `max_workers`) with `factory.workers_source`; without the Settings wiring it falls back to the status file's value with source `file`. **Failures:** `GET /api/v1/failures?window=24h|7d` (`src/ui/failures.ts`, default 24h, any other value 400) returns the failed runs of the window grouped by error code: `{ window, cap, total, capped, groups: [{ code, description, count, last_seen, items, runs: [{ id, work_item_id, kind, attempt, detail, worker, finished_at }] }] }`, largest group first. It reads only `listRunsFinishedWithin` and `listRunAttempts` (the worker of the run's claim), at most the newest 500 failed runs per window; `capped` says when more failed, and the page states the cap. Codes, details and workers pass the Withholder (run-outcome channel). `description` comes from one server-side table (`FAILURE_DESCRIPTIONS`) of the codes the code base names; any other code shows raw with `description: null`. The Failures page is a sidebar entry after Health; its groups expand to their runs, each item linked to its page. The Floor's "Runs failed" count links to `/app/failures?window=24h`. Out of scope: transcript links per run (#303), write actions, a history of worker processes.
