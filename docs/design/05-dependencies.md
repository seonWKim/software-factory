# 5. Coordination: parallel workers, holds and dependencies

- **A split's phases inherit the parent's `Depends on:` line; `--depends-on` and `/hold` take a short wi_ ID; `/hold` also applies to a queued implement run (decision changed 2026-11-26; before: phases got no line, only a full ID resolved, `/hold` only at an implement stop, see History).** Found 2026-11-26: items filed with `task create --depends-on wi_…` were split, their phases had no line, so `controller_dependency_edges` had no row and every phase's implement run started at once. (1) `takeIn` (`phases.unit.ts`) appends each `Depends on:` wi_/tk_ id of the parent's problem and filed text to every local phase's problem (so also its `issue_text`, which `writeDependsOn` restores after the phase's own triage); phase 1 then holds on the parent's dependency and the later phases wait for it through the phase chain. (2) `localItemOf` resolves a wi_ ID exactly, else as the prefix of exactly one item's ID (the 11-char short ID `wi_bbd7d1c8`); the line written names the full wi_ ID (a tk_ id as given), and the local source resolves lines the same way. An ID that names nothing, or several items, is refused with nothing written. (3) `/hold <id>` (`factory hold <item> <id>`) on a local item implementing with no PR and nothing blocking it, whose implement run is queued and none running, writes the line alone (`hold_requested`, no new run), then reads its links at once, so the same queued run is held (`blocked_on: dependency`) until the dependency merges. While an implement run is running it is refused ("applies once the run ends"); a running run is never stopped. The stop at `agent_needs_human` is unchanged. No schema change. Not in it: GitHub sub-issue phases (their `#N` lines), a queued run claimed between approval and the next coordination pass.
- **Overlap holds go oldest first; a cost hold starts after 2 h by default (decision changed 2026-11-23; before: a held run was re-checked against whatever overlapped it now, and `hold_policy` defaulted to `{"mode":"hold"}`, see History).** Found 2026-11-22: wi_fec72464 waited 20 hours (#779, then tk_efa4d88b, tk_586ba492), wi_088d528a 13. The order rule (`aheadOf`, `claimDecision`, the store's `coordinate`):
  1. A running item or open PR holds a run already held only if its item's first implement run started before the hold began (`held_since`) or was queued before the held run. A PR with no recorded run counts as started before any hold. A first hold starts now.
  2. A queued run that is itself held (stored `held`, or held earlier in the same claim) holds every newer queued run it overlaps (`held`, `holder_kind: waiting`). One not held keeps the deadlock rule.
  3. So when a blocker merges, the oldest held run starts; newer overlapping runs wait for it.
  4. A run held longer than the limit starts anyway: `hold_policy` defaults to `{"mode":"run_after_minutes","minutes":120}` (owner answer: 2 h). Its decision is `timed_out`; the worker's `run start` log line carries `hold_decision` and, for `timed_out`, `hold_limit_minutes`. `{"mode":"hold"}` still waits for `/approve`.
  - Unchanged: dependency holds, `/approve`, `hotspot_mode`, the weights, and the 2026-11-07 rule that a closed holder stops holding at once; its `held` decisions turn `released` (unread), keeping `held_since`. No schema change or backfill. Not in it: start times on the Queue and Items pages, #99, fairness across run kinds.
- **Plans over about 15 files split into linked items; shared indexes count only when named (decision changed 2026-11-20; before: see History).** Found 2026-11-20: the two indexes below made most waits; one item claimed 39 files.
  - **Split by size** (owner answer 1). `prompts/triage.md` splits a plan of over about 15 files into phases linked by Depends on, each claiming its own files.
  - **Shared indexes** (owner answer 2). `coordinationCost` drops a shared `UNCLAIMED_INDEXES` path (`docs/design.md`, `web/src/i18n/en.ts`) unless both runs' lists name it, so different pages' text changes run side by side.
  - **Sessions too** (2026-11-21). A session start and a claim beside a session use this cost (`sessionHold`, design 05-interactive-sessions).
- **Three entry points write a local item's `Depends on: wi_…` line (decision changed 2026-11-20; before: only a typed line, see History).** The edge is still that line in the problem (`dependsOnLine`); no schema change. (1) The coordination pass, before it reads the links, writes a yes to triage's "Depends on wi_X? yes/no" (design 04-triage) on the newest approval with answers, and each `Depends on:` line of `issue_text` (e.g. `task create --depends-on`, design 02-tasks-build) the spec dropped (`writeDependsOn`, `depends_on_written`); a no writes nothing, and only unread links or a newer approval are written: no backfill. (2) `/hold <id>` (design 04-spec-gate-commands) appends the line, sets `blocked_on: dependency` and queues an implement run in one transition (`hold_requested`), refusing an unknown local id, the item itself or a closed item. Hold and release are unchanged. Not in it: ids not existing yet, `dependency-stop.ts`, the dashboard.
- **A split parent counts as merged when it closed `completed` and its last recorded phase closed `completed` (decision changed 2026-11-18; before: only when every recorded phase closed `completed`, see History).** The decision that changed: "Split parents count as merged" (1), below. `itemMerged` counts a dependency that is a factory item as merged only when it is closed `completed` and either has a `merge_sha` or its last recorded phase (the highest phase number) closed `completed`. It follows the new split close rule (design 04-split-specs, 2026-11-18): a parent whose phases are all closed closes `completed` with the last phase's merge sha when that phase merged, so a dependent waiting for it is released even if an earlier phase was rejected; it closes `rejected` when the last phase closed without a merge, and its dependents get the `dependency_closed` hold as for any dependency closed unmerged. Dependency rules for items that are not split parents are unchanged.
- **Local items honour `Depends on:` lines naming wi_ or tk_ ids (decision changed 2026-11-18; before: dependencies came only from the GitHub source, so a local item had no edges and never held, see History).** Now the `local` source is a dependency source: its `dependencyLinks` reads the item's problem text, takes each `Depends on:` line (the same line rule as `#N`, `dependsOnLines` in `src/core/coordination.ts`, which `parseDependsOn` also uses), and resolves every `wi_…` (work item) id and every `tk_…` (task) id, through the task's linked work item, to the source id of the local item it names. Store reads only, no network call. An id that names no local item, or an item that is not local, gives no edge (no hold, no comment). Edges stay keyed by the source id, because `releaseDependents` matches on it; the hold names the item by its wi_ id, which the source gives as each edge's label (`dependencyLabel`, read from the store), so the blocked_reason reads `waiting for wi_X to merge`, `dependency_closed:wi_X` when it closes without a merge, and the dashboard's why reads "Waiting for wi_X to merge". The rest is the coordination path GitHub items use: `blocked_on: dependency`, `dependency_hold`, released (`dependency_released`) when the local merge closes the item, `blocked_on: human` with queued runs cancelled when it closes unmerged, cycles refused. GitHub `Depends on: #N` edges and their text are unchanged. A local item's lines are read once, on the first coordination pass of its implement run (its links were never read with a time, so an item filed before this change still implementing without a PR is read then too), and again only on `/retry` at `dependency_closed`. Not in this decision: rewriting the stored data of existing items, holding on an id that does not exist yet, a local item named as `#N`, a GitHub item named by its wi_ id, and the implement run's dependency stop (`run-results/dependency-stop.ts`), which still matches only a stop reason naming the edge's `shortRef`.
- **`max_coordination_cost`, `hotspot_weight` and `mechanical_weight` are settable live (decision changed 2026-11-12, phase 1 of "Settings without editing factory.config.json"; before: all three were `factory.config.json` keys only, read once at startup, see History).** Each is a `factory settings set` key (and a Settings page key), global only, checked with the config loader's own message (`coordinationProblems`) and applied at the next claim with no restart: `LiveSettings` puts the effective values into `FactoryConfig.coordination`, which each worker passes to `claimRun`. They are tighten-only in the direction that holds more runs: a lower `max_coordination_cost` or a higher `hotspot_weight` or `mechanical_weight` needs no grant; a loosening asks `approve_merge` (`08-settings.md`). The file value still applies when no override is stored, and the defaults (2.5, 3.0, 0.25) when neither sets them. `hotspot_paths`, `mechanical_paths` and `hotspot_mode` still change by PR only.
- **Default hotspots no longer list `docs/design.md` (decision changed 2026-11-22, issue #753; before: the default and checked-in `hotspot_paths` listed it, see History).** The default `hotspot_paths` (`DEFAULT_HOTSPOTS`, `src/core/coordination.ts`) is the schema file, `src/controller/`, `src/worker/` and `SET_UP.md`; every file under a folder entry weighs `hotspot_weight` (3.0). `docs/design.md` is a mechanical path, never a hotspot, weighing `mechanical_weight` (0.25), so its entry did nothing; it is gone from the default and from `factory.config.json`, and `mechanical_paths`, `mechanical_weight` and `UNCLAIMED_INDEXES` are unchanged. `tests/coordination.test.ts` fails when a default hotspot or mechanical path names nothing that exists, or when either hotspot list names `docs/design.md`. A config that sets `hotspot_paths` is unchanged.
- **Parallel workers (decision changed 2026-11-26: a merge-check run gets at least half the CPUs for tests; before: every run got the even share, see History).** **The slot cap is per factory, not per process (decision changed 2026-11-20):** the claim counts every running run in the store except interactive runs, under the claim lock, and every Worker passes the live `workers`, lone ones too; a process draining after a merge keeps its slots, so the new one no longer claims a full `workers` on top. The decision that changed: CPU share for tests. `workers` in `factory.config.json` (integer ≥ 1, default 1, anything else fails at startup) sets how many worker loops `factory dev` and `factory worker` run in one process (`WorkerPool`). Each has its id `<host>:<pid>:<n>` and passes `SF_WORKER_INDEX=n` to the agent and to the gate commands of the update and resolve runs and the check list. **CPU share for tests:** each loop also passes `SF_TEST_WORKERS` there, the host's CPUs (`os.availableParallelism()`) divided by the number of runs running on this host when the run is claimed, this one included, rounded down, at most CPUs - 1 and at least 1 (`testWorkerShare(cpus, runs, kind)` in `src/worker/support.ts`): a lone run on a 10-CPU host gets 9, three running runs get floor(10 / 3) = 3 each. A merge-check run gets the larger of that share and half the CPUs rounded up, still at most CPUs - 1: with five runs on 10 CPUs it gets 5, the others 2. Why: merge checks run one at a time and every finished item waits for one; on 2026-11-26 with five runs a check got 2 workers and took 27-34 min (4-16 min before), while implement runs mostly wait on the model. The count is the pool's busy slots plus the busy slots of the other worker processes on the same host, read from their `worker_processes` rows fresh within `lease_ms` (`WorkerPool.hostRuns`, `WorkerDeps.hostRuns`; a lone Worker counts 1); those rows are at most one tick old, so the count can lag briefly. The share is computed once at claim and kept for the run: a run that starts while others run gets the smaller share, and nothing is resized mid-run. This repo's `vitest.config.ts` uses it as `maxWorkers`; unset (a developer's `npm test`, solo or enterprise) vitest keeps its default. Derived, not a setting: no new config key. Another repo's test command uses it only if its test runner reads it. Each host computes its own share from its own CPUs and running runs, so replicas on several hosts need nothing shared; two processes on one host while an old one drains can briefly oversubscribe. They share one counted `KeepAwake` (held while any run is in progress) and one drain (no claims after it, acknowledged after the last in-flight run). **One branch writer per item:** a claim skips an implement-type run (`implement`, including a review fix, and `update`) only while the same item has one running. Overlapping paths no longer hold runs back; their conflicts are handled at merge (sync before push, the update run, `/resolve`). Triage and review are never skipped. The check and the claim are one store transaction that first takes the lock row in `worker_claim_locks` (migration 7), so two claimers cannot both start one item's run; a skipped run stays queued and is claimed after its item's run completes. **Claim order:** a claim takes queued runs by kind rank, then `created_at`, then insertion order. The rank is review, triage, update, implement, resolve: runs that lead to a human decision first (review takes a PR toward ready-to-merge, triage gives the owner a spec to approve), then the branch writers, and `resolve`, a long branch-writing agent run, last. Within one kind the oldest run still goes first. A held run (its item has a branch writer running, or its `not_before` has not passed) blocks nothing behind it. Retry backoff, the rate-limit pause and the one-branch-writer rule are unchanged. Not in this change: aging or fairness, so a steady stream of review and triage runs can delay implement runs. Not in this decision: pausing every worker on a usage limit across processes (after #41), a status page panel of which worker runs what (the data is in `/api/v1/workers`, see Worker slots reported per process), splitting one item across workers, automatic scaling, and an index unique across processes or hosts.
- **Hold policy: a cost hold may time out or be allowed (decision changed 2026-11-07, issue #314; default changed 2026-11-23, see "Overlap holds go oldest first" above; before: see History).** A `held` run (a running item, an open PR or an older held run at or above `max_coordination_cost`) follows `hold_policy`, read by the claim under the claim lock: `{"mode":"hold"}` waits for `/approve` or the holder to merge; `{"mode":"run_after_minutes","minutes":120}` (the default; `minutes` a positive integer, 120 when left out) is claimed once held `minutes` (decision `timed_out`); `{"mode":"run"}` is claimed at once (`overlap_allowed`). Both keep holder, paths, cost and threshold. The timer counts from `claim_decisions.held_since` (SQLite migration 30), kept while the run stays `held` whichever holder is named; a row without it counts from `at`. `hotspot_mode: hold` keeps a hold where a running item or open PR shares a hotspot held under every mode (default `policy`). Dependency holds never time out; `/approve` lifts a `held` decision under any mode. Both keys are `factory.config.json` keys checked at load (`coordinationProblems`); `hold_policy` is also settable live (08-settings.md). One global value until #99.
- **Mechanical paths and mechanical merges (decision changed 2026-11-07, issue #297; before: every shared path weighed at least 1.0, see History).** What changed: a new class of paths, `mechanical_paths`, that two items usually change only by adding lines or new files: `docs/design/`, `docs/design.md`, `docs/plugins.md`, `docs/plugins/` (the default). A shared path that equals one or lies under a mechanical folder weighs `mechanical_weight` (**0.25**) and is never a hotspot, even when `hotspot_paths` lists it (so `docs/design.md` no longer weighs 3.0); a learned weight wins when higher (from two recorded conflicts, which only real resolutions add). A folder that merely holds mechanical files (`docs/`) is not mechanical. So two items that each add a History line in the same topic file and an index line cost 0.5 and run side by side; two items that both change a file under `src/controller/` (before 2026-11-09, `src/core/controller.ts`) still cost 3.0 or more and are held. Hold reasons and the stored claim decision (`claim_decisions.shared`, `mechanical: true`) name each mechanical path with its weight: `docs/design.md (mechanical, 0.25)`.
  - **Appended-line merge, in code** (`src/core/mechanical.ts`). When a base merge conflicts and every conflicting file has, on both sides, only lines added to the common ancestor (index stages 1, 2, 3; regular files only), the worker merges each file as the base's added lines, then the branch's, at each place (one copy when both added the same lines), writes it through git (blob, index entry, `checkout-index`; never through a working-tree path), and goes on with no model call. All or nothing: one file with a removed or changed line, a file added on both sides or deleted on one, keeps the old path for every file (an agent step in the implement sync; the automatic resolve run after an update). It runs in the implement sync before push (then the merge commit, the scope gate, the size gate and the check list, before any push), in the update run (merge commit, then the check list; a failure is `tests_failed` as before) and in the resolve run (no agent step; the marker check, the worker's commit and the gates still run). A file merged this way is not recorded with `recordConflicts`, so it adds no learned weight.
  - **Migration renumbering is removed (decision changed 2026-11-13, #659 phase 2; before: see History).** The decision that changed: Migration renumbering, in code. Its code (`renumberSteps`, `stageRenumbering` and the helpers in `src/core/mechanical.ts`), its tests and the resolve run's renumbering are removed. The implement sync, the update run and the resolve run keep only the appended-line merge. An agent still renumbers a clashing migration by hand, as `prompts/implement.md` and `prompts/resolve.md` say. A SQLite schema collision is a real conflict: SQLite numbers its migrations in `schema.ts`, and the gates report it.
  - **Config:** `mechanical_paths` (a list of non-empty paths) and `mechanical_weight` (a number above 0 and below 1.0, else startup fails), in `factory.config.json` and checked by `checkConfigKeys`; `mechanical_weight` is also settable live since 2026-11-12 (above). `src/compose.ts` now passes all five coordination keys into `FactoryConfig.coordination` (closing the known gap below). One global value until per-project settings (#99).
  - Not in this decision: SQLite migration renumbering, the resolve prompt, renumbering in the resolve run, references beyond a literal step name, hand-resolution weights (#113).
- **A held run names the holder that decides; a closed holder stops holding at once (decision changed 2026-11-07; before: the stored decision named the highest-cost holder, and a closed holder stayed named until the next claim, see History).** What changed: (1) In a claim's holds, running items and open PRs come first, then queued runs, each group highest cost first (`holdsOn`), so a `held` decision names a running item or PR, the one that keeps the run queued, even when a queued run shares more files. The rule itself is unchanged: a queued run cannot make progress before it is claimed, so it never holds on its own; a run held only by queued runs is claimed in claim order (the oldest of a group that holds each other goes first), and only a running item or an open PR keeps a run queued (since 2026-11-23 also an older held run, see above). (2) When an item closes (the merge path's `pr_merged` / `pr_closed` transition, or any other close), the same transaction deletes the claim decisions of queued runs that name it as holder and have no approval, so no comment, `/approve` refusal or status page names a merged PR from that commit on, even while claims are paused; the next claim records what holds each run now. No new forge read: the merge path is still the poll that sees the merge.
- **Split parents count as merged; `/retry` re-checks a closed dependency (decision changed 2026-11-07, issue #246; before: a factory item counted as merged only with a merge sha, and nothing lifted `dependency_closed`, see History).** What changed: (1) A dependency that is a factory item counts as merged when it is closed `completed` with a merge sha, **or** when it is a split parent closed `completed` whose last recorded phase closed `completed` (the rule as changed 2026-11-18, the first decision of this file). When the split closes, its dependents are re-checked from the store in the same pass, as after a PR merge. A dependency outside the factory is unchanged: an issue closed as completed or a merged PR is merged; a PR closed unmerged and an issue closed as not planned stay `closed_unmerged`. (2) `/retry` (new command phase `dependency_closed`, "blocked: a dependency was closed without a merge") on an item blocked `dependency_closed:#N` reads its links and the states of the dependencies outside the factory from the forge at once, whatever the refresh intervals (one read per edge, only on a human command), and stores them. A dependency still closed unmerged, or a cycle, refuses it with a reply naming it, and nothing changes. Otherwise the block is lifted with the human as actor (state change `retry_requested`, detail `released: dependency_closed:#N`) and a new implement run is queued (restart_count + 1, since the block cancelled the old run); a dependency still open then holds it as usual (`blocked_on: dependency`). `/retry` fits because, as at a failed run, it starts the step the block stopped; `/approve` keeps its meaning (the spec or the floor) and still never lifts a dependency hold. `+paths` is refused there. A dependency cycle still needs a human to edit or close the item.
- **Dependency edges re-read only when the issue changed (decision changed 2026-11-07, issue #254; the topic now keeps a short form, the full text is in History).** Coordination reads an item's edges from the store; the forge is read again only when the issue's `updated_at` moved past the read time (`work_items.edges_source_updated_at`, `dependency_edges.source_updated_at`), or there is none (a new item, a failed read: the next pass reads once, at most once per 10 minutes after a failure). A failed read stops nothing: stored edges and states apply. An untracked dependency's state is cached 10 minutes (`DEPENDENCY_STATE_TTL_MS`); while `lowBudget()`, the optional reads wait. A `/retry` at `dependency_closed` reads again at once.
- **Coordination: dependencies and a cost threshold (decision changed 2026-11-03, issue #115; before: the claim held an implement-type run only while its own item had one running, so a dependent item could start before the work it needs merged, overlapping items always ran side by side, open PRs held nothing, and a file that conflicted again and again weighed the same as any other).** What changed: a claim now also holds an `implement` run (it stays queued, with a stored reason) for two reasons, both read from the store inside the same `worker_claim_locks` transaction, never from the network.
  - **Dependencies.** An item depends on every issue named on a `Depends on: #N` line of its issue, on its GitHub sub-issues (a parent waits for its sub-issues) and on its blocked-by links (the GitHub source reads all three; a list GitHub has switched off gives none). Edges are stored per item (`controller_dependency_edges`, with the source id even for an issue outside the factory) at intake and again only when the issue changed (see Dependency edges re-read only when the issue changed above). The controller writes each edge's state outside the claim lock: from the store for a factory item (merged = closed `completed` with a merge sha, or a split parent whose phases closed `completed`; see Split parents above), else from the forge (an issue closed as completed or a merged PR is merged). Open: the item gets `blocked_on: dependency` and a `blocked_reason` naming the items (`waiting for #92 to merge`, one comment), stage `RUNNING`, status label "implementing". Merged: when the dependency's PR merges, the controller clears the hold in the same event, and the next claim takes the run (for an item outside the factory, on the first poll after its state is read again, at most 10 minutes later). Closed without a merge: `blocked_on: human`, `dependency_closed:#N`, queued runs cancelled, one comment; `/retry` re-checks it (see Split parents above). A cycle: refused, `blocked_on: human`, `dependency_cycle: #a → #b → #a`, queued runs cancelled, one comment keyed `dependency-cycle:<id>`. `/approve` never lifts a dependency hold; its refusal says so (new command phase `dependency_hold`, "waiting for a dependency to merge").
  - **Cost.** For an item without a PR, the cost of running it next to another item is the sum of the weights of the paths both change (the shared-path test is the scope gate's `isCovered`): 1.0 per shared path (a mechanical path 0.25, see Mechanical paths above); a file with two or more recorded conflicts 1.0 + 0.5 per conflict, at most 4.0; a hotspot (`hotspot_paths`: the schema file, `src/controller/`, `src/worker/`, `SET_UP.md`; see Default hotspots above) the fixed `hotspot_weight` 3.0 (a higher learned weight wins). A cost at or above `max_coordination_cost` (**2.5**, raised from the 1.5 first proposed) holds the run. Holders: items with an implement-type run running, items with an open PR even with no run (its stored diff file list `pr_files`; a PR opened before this change has none and falls back to `allowed_paths`, and the comment says so), and other claimable queued implement runs. Each side's files: `pr_files`, else triage's `files_to_change` (now stored), else `allowed_paths`. **This replaces the plain overlap view:** one or two ordinary shared files (1.0 or 2.0) run in parallel, a hotspot or a file with three or more recorded conflicts serializes. Deadlock rule: a run held only by other queued runs is claimed in claim order, so the oldest of a group that holds each other goes first. (See A held run names the holder that decides, above, for which holder a decision names.) Each decision is stored per run (`controller_claim_decisions`: shared paths with weights, total cost, threshold, holder item or PR, whether the holder fell back to `allowed_paths`), rewritten only when it changes. A cost hold keeps `blocked_on: none` (status "implementing"); the controller posts one comment per (run, holder) on the poll: `The implement run is held: waiting for #92 to merge: both change src/worker/runner.ts (conflicted 6 times), cost 4.0 > 2.5.` `/approve` on such an item records `coordination_approved` (the approver's user ID as actor) and the next claim takes the run.
  - **Never held:** triage, review, update and resolve runs, and implement runs of an item that already has a PR (review fixes: their conflicts are the PR's, handled at merge).
  - **Learned weights:** **the claim counts only conflicts recorded in the last `conflict_window_days` (decision changed 2026-11-18; before: every recorded conflict of the project counted, with no time limit, see History).** The decision that changed: Learned weights. Now the claim reads `controller_file_conflicts` rows with `at` at or after the claim time minus `conflict_window_days` (`conflictCounts(project, since)`, `conflictWindowStart`); older rows stay in the table (pruning is design 08-retention) and add no learned weight. `conflict_window_days` is a `factory.config.json` key (a positive integer, default 3, anything else fails at startup with the other coordination keys), not a live setting. A same-file overlap whose cost still reaches `max_coordination_cost` (a hotspot, or a file with 3 or more recent conflicts) still holds; only the extra weight from old history decays. The improver's 7-day hotspot count (design 07) keeps its own window. The worker records one conflict per file at each base merge that conflicts and is not merged in code (sync before push, the update run, the resolve run), keyed by item and base sha, so an update and its automatic resolve on one base count once (`controller_file_conflicts`, `recordConflicts`). A later hand-resolution record (#113) can use the same call.
  - **Config:** `max_coordination_cost` (number above 0, default 2.5), `hotspot_weight` (default 3.0), `hotspot_paths` in `factory.config.json` (the first two also settable live since 2026-11-12, above); a zero or non-numeric value fails at load (`checkConfigKeys`). One global value until per-project settings (#99). `src/compose.ts` passes them into `FactoryConfig.coordination` since 2026-11-07 (issue #297); before, the worker used the defaults, which equal the checked-in values.
  - **Schema:** migration 16 (SQLite) adds `work_items.files_to_change` and `pr_files` and the tables `controller_dependency_edges`, `controller_file_conflicts`, `controller_claim_decisions`. No shipped migration changed.
  - Not in this decision: per-project thresholds (#99), a command to resume an item blocked by a cycle (a human closes or edits it), showing a cost hold on the status page (it shows `blocked_on` and `blocked_reason`, and a cost hold keeps both clear).
