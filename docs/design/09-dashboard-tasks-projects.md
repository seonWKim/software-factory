# 9. Status page: dashboard Project switcher and projects

- **Factory work follows the Project switcher (decision changed 2026-11-14; current; replaces "the Factory work section is to follow the project scope once the switcher merges, and lists every project's items for now", see History).** The decision that changed: **with a project picked on the Tasks page, Factory work lists only the open items that need the owner and were built from a task in that project; with All projects, every such item, as before.** A work item has no project field: it takes the active projects of its source task, the task whose `controller_tasks.work_item_id` is the item's ID (set by Build this), as `controller_task_projects` links them. An item from a task in two projects shows under each; an item with no source task, or whose task is in no active project, shows under All projects only. Archived projects do not count (the owner's answer: active projects only), so an item whose task's only project is archived also shows under All projects only. **Read:** `GET /api/v1/items?project=<slug>` keeps the listed rows whose source task is in that project, from one store read for all of them (`listWorkItemProjectSlugs`, one query over `controller_tasks`, `controller_task_projects` and `controller_projects`), never a read per item; the facets are unchanged. The parameter is refused as `GET /api/v1/tasks` refuses it, with the same messages (`projectFilterRefusal` in `src/ui/tasks-api.ts`): 400 for a value that is not a slug or an archived project, 404 for an unknown one. Without it the read is unchanged. No table, column or migration. **Page:** the Needs you section (`NeedsYou`, called `FactoryWork` until 2026-11-15) takes the page's `project` and reads through `useItems` (`web/src/api.ts`), whose query key is `["/api/v1/items", "project", slug]`, so a command's reload of `["/api/v1/items"]` reloads it whatever the filter. Work, Activity and Failures keep the unfiltered read. **Why:** picking "Wonderful AI demo" still listed this repository's work.
- **The Tasks page has a Project switcher kept in `?project=`, its #list tab is named List, and each open row has Projects… (decision changed 2026-11-14, phase 3 of 3 of local-d91d27e8; current; replaces "the Tasks page's fourth tab is Project, grouping by #list, and the dashboard cannot create a task project, set a task's projects or filter by one", see History).** The decision that changed: **the word Project names the task project switcher, and the dashboard creates task projects and sets a task's projects.**
  - **Project tabs.** The `Tabs` component (`web/src/components/ui/tabs.tsx`, underline tabs, tablist labelled Project, arrow keys select as they move) in its own row under the title, above Quick add: All projects first, then the active projects (`active_projects` of `GET /api/v1/tasks`, by slug); archived projects are not listed. The Add project "+" (an icon-only ghost Button, accessible name Add project) is Tabs' `action`: it sits at the end of the tab row inside its bottom border, is not a tab and is skipped by the arrow keys; it opens the Add project dialog as before (since 2026-11-15; it was a bordered button beside the row, see History). Its value is the page's `project` query parameter, read on load and written on change with `history.replaceState` (no new history entry), so a filtered view can be shared and reloaded; All projects removes the parameter. A slug the URL names that is not active stays listed by its slug as a tab, and the read's refusal shows as the page's error. The choice filters Inbox, Today, Upcoming and List through `GET /api/v1/tasks?project=<slug>`; Done keeps its own unfiltered read (`GET /api/v1/tasks/done`). The read's query key is `["/api/v1/tasks", "open", project]`, so a row action's reload of `["/api/v1/tasks"]` reloads it whatever the filter.
  - **List tab.** The fourth tab, formerly Project, is List (`tasks.list`); it still groups every open task by its `#list` (design 02-tasks, the `#list` removal plan). `tasks.project` ("Project") is now the project tablist's label.
  - **Read.** `GET /api/v1/tasks` adds `active_projects` (`{ slug, name }`, names through the Withholder) and `projects` on each task row (the slugs of its active projects, one `listTaskProjectSlugs` read). The views' existing `projects` field keeps its meaning (the List tab's groups by `#list`), so the new list is named `active_projects`, not `projects`. With `?project=` the open tasks are filtered to that project before `taskViews` runs: 400 for a value that is not a slug as `projectSlug` makes it or an archived project, 404 for an unknown one. It reads only.
  - **Routes** (`src/ui/projects-api.ts`, both in `TASK_WRITES`, so they take the task routes' guards: Host, Origin, Content-Type, the commands actor's CSRF token, body size, JSON). `POST /api/v1/projects` with `{ id, name }` (`id`: `pj_` and 8 to 64 URL-safe characters, chosen by the page): 503 with no commands actor, 400 with `projectName`'s reason, 409 naming the project that holds the slug (`project "<slug>" exists already`, with that project), else 200 with the project; a resend under the same ID answers the stored project and writes nothing. `POST /api/v1/tasks/project` with `{ id, project, add }`: 400 for another body or a `project` that is not a slug, 404 for an unknown task or project, 400 with the archived reason when `add` names an archived project (a remove from one is allowed), else 200 with `{ task_id, project, changed }`. Every refusal comes before the store write.
  - **Row and dialog.** An open task row's overflow menu has Projects… (after Add sub-task, before Delete); a Done row has no menu. It opens the project dialog, the shared `Dialog` rendered into `document.body`, so the row's height does not change: a checkbox per active project (the shared `Button` with `role="checkbox"`, as the row's complete control), each change posted at once and announced; a New project `Field` whose Create project (the dialog's confirm, also Enter) creates the project under an ID kept for that name, so a retry stores one project, then adds the task to it. The secondary button reads Close (`Dialog`'s new `cancelLabel`), since nothing waits for a confirm. A refusal stays in the dialog with its reason. The dialog lives in `web/src/views/tasks/dialogs.tsx`: a new exported component under `web/src/components/ui/` needs its section in `design-system/components.md`, which this phase could not change; it moves there with that section when a second page uses it.
  - **Not part of this decision.** Renaming, archiving, restoring or deleting projects on the dashboard, project pages, a projects column, filtering Done, and showing archived projects in the switcher.
