# 9. Owner notices

- **One stored notice per wait on the owner (new decision, 2026-11-12, phase 1 of the owner notices).** Before, an item that needed the owner showed up only in the status page's Needs-you count: nothing stored the moment it started waiting, so nothing could tell the owner. Now the controller's `notifications` unit (`src/controller/units/notifications/`) stores one `controller_notices` row per wait. Showing a notice, sending it and marking it delivered are phase 2 (the Mac shell); Slack, GitHub and other channels stay with `12-notification-channels.md`; notices for system actions (a pending migration, an expiring token, a claim pause, an alarm) are not part of this decision.
  - **A wait.** An item waits on the owner from the state change that set its `blocked_on` to `human` until one sets it to anything else. That state change's ID is the wait key. A change that keeps `blocked_on: human` (a new `blocked_reason`) is the same wait; leaving and re-entering Needs you is a new one. So an item is noticed once per wait, and again only after it left and came back.
  - **Table.** `controller_notices` (`work_item_id`, `wait_key`, `kind`, `created_at`, `held_until`, `delivered_at`, `count`), primary key (`work_item_id`, `wait_key`), indexed on (`delivered_at`, `held_until`). Created by the timestamped migration `src/controller/migrations/20261112T0900-controller-notices.migration.ts` for SQLite and MySQL; no numbered MySQL step (that list is frozen). The store methods are in `src/impl/store/sql/notices.ts` (`NoticeStore` in `src/core/notifications.ts`), not in `sql-factory-store.ts`, which is over its line budget.
  - **Kinds.** From the item's `blocked_reason`: `spec` (`spec_pending`), `merge` (`merge_pending`), `failure` (`run_failed:*`, `max_attempts`, `max_restart`, `max_loops`, `repeated_failure`, `recurring_failure`) and `other` (anything else). The runtime setting `notice_kinds` lists the kinds that raise a notice (default: all four). A wait of a kind left out stores nothing while the kind is off; turned on again while the item still waits, it is noticed then.
  - **Quiet hours.** The runtime setting `quiet_hours` is a local-time window, `HH:MM-HH:MM` (it may cross midnight; empty: off). A notice decided inside it is stored with `held_until` set to the window's end and is not pending. Once that time has passed, the next pass stores one summary for the held notices of that window: `kind` `summary`, an empty `work_item_id` (it covers several items), wait key `quiet:<held_until>`, `count` the number it covers. A held notice is shown only through its summary.
  - **Backfill.** The migration stores every item already waiting on the owner as notified: its current wait's row with `kind` `backfill` and `created_at` and `delivered_at` both the wait's own time (the migration reads no clock). So turning this on raises no notice for what the Needs-you list already shows.
  - **Pure and idempotent.** `decideNotices` in `src/core/notifications.ts` takes the waiting items' state changes, the stored notices, the time (the tick's) and the two settings, and returns the notices to write. The unit's `load` reads the items with `blocked_on: human`, their stored notices, the summaries and the held notices, and the state changes only of an item updated since its newest notice (else its wait is unchanged); the router commits each notice through the kernel as an insert that skips a stored (`work_item_id`, `wait_key`). A second pass, a reopened store or a second replica adds nothing.
  - **Local read.** `GET /api/v1/notices` (`src/ui/notices-api.ts`) lists the pending notices, oldest first: undelivered and not held, a summary's `work_item_id` as null. IDs, kinds, counts and times only, so no egress scan. Every other method answers the existing 405.
