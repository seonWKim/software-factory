# 2. Plain tasks: edit, delete and sub-tasks

- **Edit, delete and one level of sub-tasks (decision changed 2026-11-12; current; replaces "Editing and deleting a task are not commands yet", from the #606 decision in design 02-tasks, see History).** The decision that changed: **a plain task can be edited with quick-add words, deleted for good, and given sub-tasks one level deep, from the CLI and chat.** Work item sub-tasks (from split specs) are a different thing and are unchanged.
  - **Commands.** `factory task edit <task_id> <words>`, `factory task delete <task_id>` and `factory task sub <parent_id> <words>`, entries of the command table with permission `submit_work`, so they also exist in chat as `task edit`, `task delete` and `task sub`.
  - **Edit.** `parseQuickEdit` (`src/core/quick-add.ts`) reads the same words as quick-add, with the same refusals, and names only the fields they give; words with no title keep the title, and no words at all are refused. The store sets only those fields, conditional on `done_at` unset, as quick-add would store them: a time alone on an undated task makes it due today, and a recurrence with no due date (stored or given) is refused. Refused with nothing written: an unknown task, a done task, words the parser refuses.
  - **Delete.** A hard delete of the row, no undo and no soft delete. With `with_sub_tasks` (decision changed 2026-11-20, wi_0e5a2dd31a2440128cff38acf7f3cdb4; current; the dashboard's "Delete with sub-tasks", design 02-tasks-page) every sub-task, open and done, is deleted with it, with its project links, in the same transaction. Without it (the CLI and a plain `{ id }`) it is refused, with nothing written and the open sub-tasks named, while the task has an open sub-task, and its done sub-tasks are detached (`parent_task_id` set to NULL) in the same transaction, so they become plain tasks. A second delete answers "no task". A linked work item is not changed, and a later merge of it finds no deleted task to complete. Replaced: "a delete is always refused while a sub-task is open", see [History](history/02-tasks-edit.md).
  - **Sub-tasks.** `controller_tasks.parent_task_id`, nullable and indexed (`controller_tasks_sub_tasks`), added by the timestamped migration `src/controller/migrations/20261112T1800-controller-sub-tasks.migration.ts` (TEXT; additive, rerun-safe, no backfill: existing tasks stay top-level). Not `parent_id`, which keeps its recurrence meaning and its unique key. One level: a sub-task under a sub-task is refused with nothing written. Completing a parent completes no sub-task and completing a sub-task does not complete its parent; a recurring sub-task's next occurrence stays under the same parent. `task list` shows a sub-task's parent ID at the end of its line (`sub of <id>`).
  - **Store methods.** `updateTask(id, edit)`, `deleteTask(id, { with_sub_tasks? })` and `addSubTask(parent_task_id, task)` on `TaskStore` (`src/core/tasks.ts`, implemented in `src/impl/store/sql/tasks.ts`) take plain arguments and hold no CLI or chat logic, so the dashboard's Tasks page calls them from its HTTP routes (the Tasks page decision in design 02-tasks-page).
  - **Solo and enterprise.** The same: SQLite applies the migration when the store opens.
