# 4. Agents: verdict commands and pushback capture

**A pushback is captured in the owner's tacit ledger** (decision changed 2026-11-11, issue #570; replaces "a `/revise`, a `/reject` and a `changes` verdict are stored only in the factory's store"). The decision that changed: **once a `/revise`, a `/reject` or a `/verdict changes` applied, the controller records one capture for the owner's ledger (`plugins.tacit`, [tacit-ledger.md](../plugins/tacit-ledger.md)); outbound delivers it.**

- **Where.** The hooks sit after a successful apply: `gateCommand` in the commands unit for `/revise` and `/reject` (a comment, the CLI or a dashboard request), `recordVerdict` in the verdicts unit for a `changes` verdict. A refused command, an `accept` verdict, a "Request changes" PR review, implicit verdicts and reverts capture nothing (the review is a follow-up issue).
- **How.** The capture is an outbound action (`tacit_capture`) in the existing `outbound_actions` table (no schema change), destination `tacit:ledger`, keyed `tacit:<item>:<comment ID>`: the same command delivered twice, or handled by two workers on one store, stores one intent. The command's stage change commits without waiting for it.
- **Delivery.** Outbound's `tacit` target, in the process that flushes and holds the plugin (the controller; never an agent run), calls the ledger. The pushback and the proposal pass the egress scanner (G5) first; a flagged text becomes the notice naming the rules. A failure is retried with outbound's backoff and holds only `tacit:ledger`; GitHub, Slack and the factory repo keep sending.
- **What.** `session` is the item ID, `proposal` the stored summary of the item's latest finished run, `pushback` the owner's words verbatim; the ledger's own fields stay empty.
- **Default `none`:** nothing is captured and no intent is recorded. Pushbacks stored before the plugin was selected are not backfilled.
- **Solo and enterprise.** Solo default: `none`; with `agents-home`, the home is on the owner's machine. Enterprise (one owner's replicas on one store): the comment-ID key keeps each capture once; a ledger shared between people is not built.

**A verdict from the CLI, the item page and a local item with no PR** (decision changed 2026-11-11, issue #523; replaces "a verdict needs a PR: the item API, `/help`, the footers and the SET_UP.md table offer `/verdict` only once the item has a PR, the CLI has no `verdict`, and the item page has only the note box"). The decision that changed: **a local item takes a verdict with no PR on every surface**, not only in the controller.

- **The rule.** `applies()` (`src/core/commands.ts`) lets `/verdict` apply to a local item (`CommandState.local`, from the item's source) with or without a PR, in any open or merged phase; any other item still needs its PR. `whenText` says "once it has a PR (a local item needs none)". So the item API lists `verdict` for a local item with no PR, and still not for a GitHub or Slack item with none.
- **One refusal.** `verdictRefusal(item)` in `src/core/verdict.ts` is the closed-item reason: `the work item is closed`, or `... and its PR was not merged` when it had one; a merged item takes a verdict. The verdict unit calls it and keeps no copy of the text; `factory verdict` calls it before any write.
- **The CLI.** `factory verdict <id> <accept|changes|reject> [<severity> <reason>]` is a command table entry (`src/core/command-table.ts`, group `item`, who: the owner). The text after the ID is checked with `parseVerdict` (a malformed one prints the `/verdict` usage line) and with `verdictRefusal`; a refused call stores nothing. Otherwise it stores one command row, as `/verdict <text>`, which the controller applies as a `/verdict` comment on the item: one `controller_verdicts` row, target `issue`, `implicit` 0, `pr_head` null with no PR; no stage, `blocked_on` or `blocked_reason` change. A verdict row on an item of a sync source is not mirrored to it: it changes no state, so there is nothing to show there.
- **Slack keeps its comment path.** The entry's chat form is `comment` (`ChatArgs`): the chat parser leaves it to the comment parser, so `/verdict` (or a bare `verdict` in an item's thread) in Slack is read as before, a `verdict_submitted` event on the thread.
- **The item page.** For `verdict` it shows a severity choice and Accept, Changes and Reject buttons; a click sends the verdict app request with the note `<kind> <severity> <reason>` (`verdictNote` in `web/src/views/item-commands.tsx`), the reason from the note box. Changes and Reject wait for a reason.
- **Needs you** (decision changed 2026-11-11, issue #513; replaces "Needs you keeps only state commands, so it shows no verdict buttons"). A Needs-you row also lists `verdict` where the command rules apply it (an open item with a PR, or a local item with or without one), with a one-line text form, as typed after `/verdict`; a send is the same app request as the item page's note box, so the controller stores the same verdict, and a malformed one is refused with the usage line. Details in design 09-dashboard-app. `auto_merge_max_tier` and its setting path are unchanged.
- **Solo and enterprise.** No account; the local identity and the owner check decide whether the buttons are enabled (`record_verdict`), and the controller runs the same check when it applies the request or the CLI row.

**Implicit verdicts and the lenient `/verdict`** (decision changed 2026-11-08, issue #316; replaces "only `/verdict` writes verdicts, and every kind but `accept` needs a severity"). The factory records a verdict on its own from three PR events of a **factory** item (origin `factory`; adopted PRs, Slack items and local items get none here): a merge whose merger resolves to a user and with no `manual` run on the item (no person pushed) is one `accept`, severity `none`, for the merged head (`last_head_sha`), the merger as actor, stored just before the `pr_merged` transition; a person's push (the `manual` run of design 05-sources) is one `changes`, severity `minor`, for the pushed head, the pusher (or `system:pr-sync`) as actor, its reason naming the commit count from `Forge.commitsBetween` (`a person pushed 3 commits to the PR`) or saying the count is unknown; a revert of a merged item (CLOSED / `completed`) is one `reverted`, severity `major`, per reverting commit, as `system:links`, with no PR head. A merge whose merger does not resolve writes no verdict and logs why. **Implicit verdicts never change `stage`, `blocked_on` or `blocked_reason`:** like `/verdict`, each bumps the version and adds one `controller_state_changes` row, reason `implicit_verdict`, `changes` = {}. A `controller_verdicts` row now has `implicit` (0/1) and `pr_head` (SQLite migration 39, which also widens `comment_id` to 128); an implicit verdict keeps its event key in `comment_id` (`implicit:<merged|pushed|reverted>:<item>:<sha>`), so a redelivered event or a second run of the merge handler stores nothing. **One verdict per PR head:** an implicit verdict for a head that already has one is a no-op, so a person's push then a merge ends with that head's `changes` and no `accept`; an explicit `/verdict` is stored for the item's current head and deletes that head's implicit verdict (its `controller_state_changes` row stays). The parser now takes `/verdict accept` alone (severity `none`), `accept <reason>` without a severity, and `yes` and `ok` as `accept`; an unknown word gets the usage line and stores nothing. `/verdict` also applies to a merged item (command phase `merged`); a closed item whose PR was not merged is refused with one reply. Solo default: no forge, so no PR events and no implicit verdicts. Enterprise: the GitHub forge, implicit verdicts from its PR events.

**Verdict command:** a user with write permission (auth action `record_verdict`, separate from `approve_spec`) records a structured verdict with `/verdict accept|changes|reject <severity> <reason>`, on the work item's issue or on its PR. Severity is one of `none`, `minor`, `major`, `critical`. The reason is the text after the severity, following lines included; `accept` may omit the severity (then `none`) and the reason, `changes` and `reject` may not; `yes` and `ok` mean `accept` (since 2026-11-08, above). **A verdict does not change `stage`, `blocked_on` or `blocked_reason`:** it bumps the version and stores a `controller_state_changes` row (reason `human_verdict`, actor = the user's id, `changes` = {}) plus a linked `controller_verdicts` row (verdict, severity, reason, comment id, target `issue`/`pr`, `implicit` 0, `pr_head` = the item's current head). `verdicts.comment_id` is unique, so a redelivered comment stores nothing and gets no second reply. A bad format, an unknown severity, a missing reason, no write permission, a `CLOSED` item whose PR was not merged, or an item with no PR yet (a local item excepted since 2026-11-09, issue #452: an open or merged local item with no PR takes a verdict with no `pr_head`; a closed local item that was not merged is refused as `the work item is closed`; see "App requests") is refused with one reply on the issue, keyed on the comment id, and nothing is stored. A PR comment maps to its item by the PR's head branch. Verdicts are the input for the weighted human-feedback rate that gates auto-merge (§6); computing it is not built yet.
