# 4. Agents: commands in plain words and proposals

**A Needs-you decision is answered in the dashboard chat** (decision added 2026-11-28, phase 3 of local-task-tk_cad55672; replaces "the dashboard's command box and Confirm all are on the item page only"). The decision that changed: **the Chat page opened on an item (`?item=`) shows its Needs-you decision, and its buttons, its reply and its Confirm all and Cancel are sent through the same item command path as the item page and the typed command.** Three capabilities in `src/api/capabilities/chat.ts`: `chat.decision` (GET, `?item=`) reads the item detail (`src/ui/api.ts`) and answers whether the owner is next, the why, In short, the newest factory message, the commands and the pending proposals' typed lines; `chat.command` (POST, `item` with `command` and an optional `note` or `proposal`) calls `itemCommandSend` (`src/ui/commands.ts`), which `commandsPost` now ends in after its own guards, so one app request row is stored with the page's actor and Approve and Merge pass the same owner check (`approve_spec`) and transition; `chat.mode` (GET) reads the stored `permission_mode` (one owner setting, default `ask_irreversible`). A reply is a `sentence` app request: the controller reads it as a plain comment on the item and stores its proposals as pending, as the command box's sentence; Confirm all (`proposal_confirm`) applies each pending row through the confirm path and its own check, Cancel (`proposal_cancel`) marks them cancelled and applies nothing, and `factory confirm <id>` still confirms the same proposal. Not changed: the interpreter's prompt, the command table, the store schema. Tests: `tests/chat-decisions.test.ts`.

**A top-level work request creates one item** (decision changed 2026-11-26, phase 1 of local-task-tk_dd036ba7; replaces "a top-level `request` answer is posted with a Make this a task button and creates no item"). The decision that changed: **on a top-level Slack mention, a `request` answer makes the work item at once, and the thread gets one reply naming it by ID and title.** The intake unit (`answered` in `src/controller/units/intake/intake.unit.ts`) reads the message once through the commands unit's `readMessage`, in the same order as before (empty, egress scan, `approve_spec`, then the model); for `request` it posts nothing of the model's text and goes on to the `createWorkItem` call a press of Make this a task makes (keyed on the message's source id, the problem holding the message text, the requester's `submit_work`), then posts `Task created: <item ID> <title>` (the ID in code font) keyed `factory:task-created:<source id>`. A redelivery finds the item before any model call, so it makes no second item and no second reply. A pasted image is not fetched (Slack events carry no files); the item is made from the text. Unchanged: `chat` gets its answer, `unsure` its reply and button, no model, a sender without `approve_spec`, a long message or `none` the unread line and button, a flagged message the fixed line, a flagged model answer nothing, all with no item; the button, its press (no model call) and its marker. Not built: attachments on the item, multi-step plans, a merge report in the thread.

**"go ahead and merge" is `merge` in Slack** (decision changed 2026-11-12; replaces "only a command word is a command after a mention in an item's thread"). The decision that changed: **after a mention, the whole reply `go ahead and merge` (any case, an optional `.` or `!`) is read as `merge`, in an item's own thread and under a notice (design 05-sources, "Replies under a Slack notice act on its items").** It is a fixed phrase, not the plain-words reader: no model call, the same `merge` path and checks (a local item's merge row is stored; any other item gets the CLI's "merge its change on the forge" refusal). Any other wording keeps today's reading (`go ahead and merge it` is a plain comment in an item's thread). `threadWords` in `src/impl/source/slack-notice-replies.ts` reads it before the bare command words. Why: the owner typed the phrase under a "ready to merge" notice and it was taken as a request.

**`task build` sends a plain task to intake (decision changed 2026-11-12, issue #607; replaces "a plain task never reaches intake: only `task create` makes a local work item").** The command table has `factory task build <task_id>` (chat `task build <task_id>`, who: anyone who may submit work), and the dashboard's Tasks page has Build this, which posts to `POST /api/v1/tasks/build` behind the same guards as the item commands route (Host, Origin, `application/json`, the per-process `x-csrf-token`, body size, JSON) and acts as the page's commands actor. Both run `buildTask` (design 02-tasks-build): one local work item per task, the link stored on the task, a second build writing nothing; a done task, an unknown task or no stored project key is refused with nothing written (CLI exit 1, route 409; no actor: 503). It is not an item command: it takes a task ID and stores no command row, since the item it makes starts in intake like any `task create` item.

**A command in your own words from the CLI and the dashboard, and a confirm by proposal ID** (decision changed 2026-11-12, issue #585; replaces "a stored proposal is confirmed only by a Slack button press; the CLI has no sentence form and no confirm command, and the dashboard no command box"). The decision that changed: **the CLI and the dashboard read a sentence with the same plain-words reader and store its proposals as pending, and `factory confirm <proposal-id>` and the dashboard's Confirm all apply them through the same confirm path as a Slack press.**

- **The CLI sentence form.** `factory "<words>"`: any first word no CLI command claims (`resolveCommand` in src/cli/index.ts; a flag still prints the usage, and since 2026-11-16 a word near a command name gets the typo reply above) runs the sentence form, the one command src/main.ts defines itself, since it is no command word: its logic is `runSentence` in src/core/local-cli.ts, and it needs at least two words. It checks `approve_spec` for the CLI identity through the local auth plugin (as a plain reply's author is checked), scans the words, calls `interpret` once over the open items as a top-level message, scans the answer, and for a `commands` answer stores one pending row per command under a new proposal ID (`prop_<random>`, author the CLI identity) and prints each as `<item>\t<typed line>` under a line naming the ID and `factory confirm <id>`. Any other answer is printed as its plain reply; nothing is stored. No item changes state. The table entry is `"<words>"` in a new command group, `sentence` (it is no CLI top word); its chat form is the plain reply (`<command in your own words>`, never parsed).
- **`factory confirm <proposal-id>`.** A command table entry in group `item` (not an item command: it takes a proposal ID, never an item ID), claimed by the local handler; chat form `confirm <proposal-id>`. It reads the proposal's rows: an unknown ID fails; one with nothing pending stores nothing and prints what already happened to each command; otherwise it appends one `proposal_confirm` row as the CLI identity (with its edge passport), `item` the first pending command's item, whose thread gets any reply. The controller applies it as a press's row (`confirmProposal`, which the dashboard's Confirm all also takes): each pending row once, through the typed path and its check, a refusal marked and answered once, a confirm that finds nothing pending answered once.
- **The dashboard** (09-dashboard-app): the command box sends a `sentence` app request, which the controller (`appProposal` in proposals.ts, reached from the app-requests unit through the commands unit) answers as a plain reply on the item (`approve_spec` first, as the page's user with its passport), through `answerPlain`, the one answer a plain comment gets too; Confirm all sends `proposal_confirm` and Cancel `proposal_cancel`, each with the proposal ID only.
- **Not changed.** The interpreter's prompt, the commands it may propose and their arguments; GitHub stays plain text; no expiry; the old `sf_confirm` press path; no confirm by index from the CLI or the dashboard; no store schema change.
- **Solo and enterprise** behave the same: the confirmer's own check decides each command, wherever it is pressed or typed.

**A thin classifier labels a plain message `plain` or `command` before the interpreter** (decision changed 2026-11-13; replaces "the single interpreter call reads every plain message and decides both whether it is a command and what it means"). The decision that changed: **a plain message is plain input unless a small, separate model call labels it `command`; only then may the interpreter's command proposals reach the reply.**

- **The call.** `classifyMessage` (`src/core/classify-message.ts`) makes one `LLMProvider` call, `model_class: "cheap"`, `data_env: "test"`, with a short fixed system prompt (`CLASSIFY_SYSTEM`), no output schema and `max_tokens: 5`: the answer is one word, `plain` or `command` (any case, an optional trailing `.`). The message is its only input, fenced and labelled untrusted. It runs after the existing length cap (`INTERPRET_MAX_CHARS`) and egress scan, so a flagged or over-long message still makes no model call.
- **Precision first.** A failed call, a stop reason but `end`, an unknown word or malformed output is `plain`; the prompt says to answer `plain` when unsure, and that naming an item or a command word is not enough. Nothing is applied on a doubtful reading.
- **What each label gets.** `interpretMessage` (`src/core/interpret.ts`) runs the classifier, then `interpret` unchanged (same prompt, kinds, checks and proposal storage). For `plain`, a `commands` or `question` answer becomes `none`: no proposal, no stored proposal row, no item change; the message gets the chat (or show, request, unsure) answer as before, or the existing fixed reply for `none`. For `command`, the interpreter's answer is used as it was.
- **Where.** All three entry points read through it: a plain reply in an item's thread or on a GitHub issue and a top-level Slack mention before intake (both through the commands unit's `readMessage`), and the CLI sentence form (`runSentence`). Each keeps its permission check order; the classifier runs after it.
- **Not changed.** Proposals still apply only when typed or confirmed. No setting, store table, migration, plugin or interface: the classifier uses the existing `LLMProvider`. A message now makes two cheap calls (the label, then the interpreter); the label's is a few tokens.

**Plain messages get a chat answer, and a top-level Slack mention is read before intake** (decision changed 2026-11-11; replaces "a plain reply the interpreter finds no command in gets the fixed line `did not find a command in your comment`" and "every top-level Slack mention is a work request, taken in without reading it"). The decision that changed: **the interpreter answers in plain words when a message is not a command, and on a top-level Slack mention it also decides whether the message is a work request at all.**

- **The kinds.** `interpret` (`src/core/interpret.ts`) gains `chat` (a plain-words answer in `text`), and, for a top-level message only, `request` (a work request) and `unsure` (the model cannot tell; `text` says so). The output schema is `{kind, entries, text}`; the model's `none` kind is gone. `none` is now only what the code returns for a failed call, a stop reason but `end`, malformed output or entries that all fail the checks. The answer is capped at 1500 characters (`MAX_CHAT_CHARS`). The system prompt tells the model the facts given are all it knows and to say plainly when they do not answer the question, never to guess.
- **The facts.** A reply on an item sends, besides the message and the open-item list, that item's state label and block reason as read-only facts in their own fenced, untrusted section. Recent runs are not sent (deferred).
- **A reply in an item's thread** (`handlePlainComment`): a `chat` answer is posted in place of the fixed line, ending with the item's name and its state label from the store (`<item> is <state>. Nothing has changed.`); on an item, a `request` or `unsure` answer with text is read as chat. The fixed line and the command list stay only for `none` (a failed or malformed answer). Same order, same permission (`approve_spec`), same marker (`factory:suggest:<comment id>`), one reply.
- **A top-level Slack mention** (`classify` on its `item_requested`, set by the Slack source; 05-sources.md). The intake unit checks `submit_work` as before, then reads the message before creating anything. One call decides and answers: `chat` is posted in the message's own thread and creates no item; `commands`, `show` and `question` answers are posted there as typed lines for open items (not stored as proposals: the thread has no item); `unsure` is posted with a **Make this a task** button and creates no item. `request` creates its item (2026-11-26, "A top-level work request creates one item" above); `none` and the messages not read get the unread line and the button (04-gate-commands, "A mention creates an item only on a press").
- **Make this a task.** The unsure reply ends with a hidden marker that carries the message text (`<!-- factory:make-task:<base64url> -->`); Slack's `renderComment` draws one button whose value is that text (decision 1: no schema change). Slack takes at most 2000 characters in a value; a longer message gets no button and the reply says why (with the 1000-character limit before the model call it does not happen today). A press is an `item_requested` from the presser (their `submit_work` check), keyed on the message's source id, through the existing intake path: the first press creates the item, a second press finds it and changes nothing, and a press makes no model call.
- **Safety.** Every chat answer and offer goes through the `EgressScanner` before it is posted; a finding posts nothing and stores nothing (and on a top-level message creates no item either). A chat answer changes no item state: no stage, block or version change, no state change row, no run. The top-level reply is keyed on the message's source id (`factory:chat-answer:<source id>`), so a redelivery posts no second reply.
- **Solo and enterprise** run the same code path on the store each uses; the permission checks are unchanged: replies need `approve_spec`, top-level requests `submit_work`. Not built: classifying local CLI or GitHub intake, recent runs as a fact, a second model call per message, following Slack edits or deletes after the reply, backfill.

**Proposals are stored and Slack draws a button per proposed command** (decision changed 2026-11-11, issue #584; replaces "a proposal is plain text on every surface, applied only by typing its line, and no store table holds it"). The decision that changed: **a plain-language reply's proposals are stored, one row per command, and in Slack each gets a button, plus Confirm all and Cancel; a press applies the stored command through the typed command's path, as the presser.**

- **The table.** `controller_command_proposals` (SQLite migration 43): one row per proposed command, keyed by (`proposal_id`, `idx`), with the work item, command, args, author ID (`slack:<id>` for a Slack user; never a display name), `status` (`pending`, `applied`, `refused`, `cancelled`), `answered_by` (the factory user ID) and `refusal`. The proposal ID is a hash of the item and the triggering comment id, so storing the same reply again (a redelivery, another replica) writes nothing new. The store methods (`recordCommandProposals`, `listCommandProposals`, the conditional `answerCommandProposal`) are implemented once, in `src/impl/store/sql/command-proposals.ts`. Only `commands` replies are stored; a question's readings are not. No backfill.
- **The buttons.** The stored reply ends with a hidden marker (`<!-- factory:proposal:<id>:<commands> -->`). Slack's `renderComment` builds from it, with the button builder in `slack-format.ts`, one button per command, Confirm all and Cancel; each value carries only the proposal ID and index. GitHub, and any reply with no marker, stay plain text with no buttons.
- **The confirm path** (`src/controller/units/commands/proposals.ts`). A press is stored as one `proposal_confirm` command row by the presser's linked factory user (an unlinked presser gets the one refusal a typed command gets). The controller reads the rows from the store, claims each pending row (pending → applied, conditional), and applies it through `gateCommand`, the typed command's path: the same `AuthProvider` check (`approve_spec`), note scan and state checks. A refusal then (the item moved on, the presser lacks the permission) marks the row refused and gets one reply saying why; Confirm all goes on in index order. A confirm that finds nothing pending applies nothing and gets one reply saying it was already applied. Cancel marks the pending rows cancelled and stores no command. A stop between the claim and the apply leaves the row applied with nothing applied; the reply's typed line still works.
- **Solo and enterprise.** Solo default: the presser is a linked Slack account and the local owner may run everything. Enterprise setting: the stored grants decide through the same check; the buttons do not change who may do what.
- **Why a table:** a proposal must survive a restart and be confirmable on any replica; the press carries no command text, so a forged value cannot run anything the row does not hold. The old Confirm press path (`sf_confirm`, its value the command text) is unchanged for messages posted before.

**A spec approved with no reply offers no `/approve`; a stale button press gets a kind reply** (decision changed 2026-11-11, issue #586; replaces "an approved spec keeps the spec gate's answer block, auto mode's approval is a note above the plain footer, and a press of a button whose command no longer applies gets the shared `was not applied` refusal"). The decision that changed: **an auto-approved spec names its approval in its footer and lists no `/approve` anywhere, and only a stale button press (never a typed command) is answered with what already happened.**

- **The spec.** `renderSpec(..., { approved: true })` (`src/core/spec-comment.ts`) drops the answer block on every spec approved without a reply (auto mode, a standing rule, the factory's own fix, a phase approved by its parent's split). Auto mode's footer is `autoApprovedFooter` (same file; `commandFooter` with `/approve` left out): `Approved automatically (auto mode, tier N) at <YYYY-MM-DD HH:MM UTC>.`, then the footer of the state after the approval with `/approve` left out, so GitHub shows no `/approve` and Slack draws no Approve button. The answers auto mode took are still listed above it. Where the Approve came from: the spec comment's answer block asked for `/approve`, and the Rule of Two hold right after an auto approval posts its own comment whose footer lists `/approve` (that one is a real ask and stays).
- **A stale button press.** The Slack source checks a pressed command button against the item's state (`buttonApplies` in `src/impl/source/slack-format.ts`: the item's phase is one the command applies in; the phase only, since a coordination-cost hold is in no field). A press that no longer applies stores nothing and sends no event: one reply in the thread, keyed on the press, says it did nothing, then the Done line (`doneLine`: `Done: <last state change's reason> by <actor ID> at <time>. The item is now <phase>.`) and the footer of the current state, so its buttons are the current ones. A typed command, from any source, keeps the shared refusal; the command table, the authorize check and the refusal wording are unchanged.
- **The dashboard** already builds its actions from the item's current state (`itemCommands`); a test keeps it so.
- **Solo and enterprise** behave the same: one code path; the store holds the same records.

**Plain-language messages: proposals for any open item** (decision changed 2026-11-11, issue #583; replaces "a plain comment gets at most one suggested command, for the item it was written on, chosen from the commands of that item's state, and Slack draws Confirm and Cancel under it"). The controller answers a `plain_comment` (the GitHub source's non-command issue comment, a Slack thread's plain reply) in this order: finds the work item (none: ignored); checks the commenter with the action the gate commands use (`approve_spec`; solo default: the local owner, who may run everything; enterprise: the stored grants), and without it makes no model call and posts nothing; skips empty messages, messages over 1000 characters (`INTERPRET_MAX_CHARS`, raised from 300 so one message can name several items) and `CLOSED` items; runs the message through the `EgressScanner` (a finding: no model call, nothing stored, nothing posted). Then `interpret(text, items, llm)` (`src/core/interpret.ts`) makes one `LLMProvider` call, `model_class: "cheap"`, `data_env: "test"`. Its input is only the message and the open-item list, at most 200 items, each with its ID, issue number (null for a local item or a chat thread), title and state label, in fenced sections labelled untrusted that the text cannot close; the system prompt lists the commands a proposal may name (`approve`, `reject`, `revise`, `retry`, `resolve`, `budget`; never `/verdict`, `/standing`, `/link` or `/help`). The model answers JSON `{kind, entries: [{item, command, args}]}` with `kind` one of:
- `commands`: zero or more proposals, each for any listed item (by ID or number). An entry naming an unlisted item, a command that is not proposable or does not apply in the item's state, or `/revise` or `/reject` with no text is dropped. Args are capped at 300 characters on one line; `/budget` keeps only a whole number.
- `show`: a read such as "show 566". The reply is a direct answer built from the stored item (number, title, state label, link), and proposes no command.
- `question`: the message is unclear. The reply is one question that lists its readings (two or more, checked like proposals) as typed lines, and no command.
- `none`, malformed output, a stop reason but `end`, or no entry left after the checks: the reply says no command was found and lists the commands for the item's state (the footer), as before. Since the chat answer (above), a plain answer is `chat` and this fixed line is only for a failed or malformed answer.

Every proposed argument goes through the `EgressScanner`; a finding stores nothing and posts nothing. **The rule: the model's output is never applied by itself** (no `controller_state_changes` row, no stage or block change, no run); a `commands` reply's proposals are stored as pending rows (issue #584, above) and apply only when typed or confirmed by a press. The reply is one plain-text comment keyed on the triggering comment id (`factory:suggest:<comment id>`, the marker kept from the suggestion so a comment answered before the change is not answered again; a redelivery posts nothing new). Each proposal shows its item and a fenced line to type on that item (`/approve`, `/approve <note>`, ...), which then goes through the normal command path and its permission check. **GitHub shows a proposal as plain text; Slack adds a button per proposed command, Confirm all and Cancel** (issue #584, above). Not built: buttons or a confirm for GitHub replies, applying a proposal automatically, expiry of pending proposals, removing the old Confirm press path, Slack plain-message intake outside an item's thread.
