# 4. Screenshots of changed pages before merge

- **A passing review of a UI change is followed by a screenshot run and a screenshot review; the owner sees the screenshots on the item's Changes tab before Merge (new decision, 2026-11-23, local-task-tk_e9edb2f4, "Screenshots of changed pages before merge"; current).** Before it, a UI change was reviewed from its diff alone, and the owner first saw the page after merging. No step below changes a stage, `blocked_on` or `blocked_reason`, holds the item, or touches the merge queue, the merge check or the approval gate; the merge-time UI check (`repo.ui_check`) still gates as before.
  - **Trigger** (`src/controller/units/run-results/screenshots.ts`, called by the run-results unit before it applies a review). A succeeded review whose verdict is `pass` with no `spec` finding, on an item the review still applies to, whose `pr_files` touch one of `repo.ui_check.paths` (default `web/` and `src/ui/`), queues one run of kind `screenshot`, keyed `<item>:screenshot:<review run>`, with `review_run_id` in its input. A `bug` verdict, a spec finding, no `repo.ui_check`, no `pr_files`, or files outside those paths queue none. The run is queued by a plain transition (empty patch, reason `screenshots_queued`), not through `decide`: a look at stored images is never held by the token budget or the Rule of Two, which would block the item.
  - **Run** (`src/worker/runs/screenshot/screenshot.run.ts`; `screenshot` is in `RunKind`, `WORKER_KINDS`, the `worker_kinds` default and `CLAIM_ORDER`, ranked after `review`; no schema change: the kind is text and the result is the run outcome). No agent, no push. In a run folder on the item's branch: the install command (run-side install cache), then the dashboard's build (`npm run --silent build`), then the capture. The capture is fixed: every sidebar page `web/src/pages.ts` lists, the fixture's item page and its run's transcript page, each at 390px (844px high) and 1280px (800px high), in light and dark (`src/shared/screenshots.ts`). There is no width or theme setting.
  - **Browser** (`ScreenshotBrowser` in `src/shared/screenshots.ts`; Chrome in `src/shared/chrome-browser.ts`; tests hand a fake). The Chrome browser runs the checkout's `scripts/responsive/capture.mjs` as a child process with only `PATH`, `HOME`, the temp folders, `LANG`, `CHROME_PATH` and `CI` in its env (no token, no secret). The script seeds the same throwaway fixture store as `npm run check:responsive` (`scripts/responsive/fixture.mjs`: never the item's own data), serves it with the checkout's built UI server and drives headless Chrome through the check's driver (`scripts/responsive/cdp.mjs`); each PNG goes back on stdout, one JSON line per shot. The driver stays in `scripts/responsive/`: the worker never imports it, and its timers could not live in `src/shared/` (the no-clock rule).
  - **Storage.** Each PNG is put in shared storage as soon as it is taken, under `<item id>/<run id>/<page>-<width>-<theme>.png`. Nothing is written in the repository or under `.playwright-mcp/`. The outcome is `{ captures: [{ page, width, theme, key }], reason, review_run_id }`.
  - **Failure.** No Chrome, no capture script in the checkout, a failed install or build, or a capture that fails ends the run with the captures it has and a `reason`: a result, never a run failure. A run that fails anyway (a lost lease) is not retried.
  - **Screenshot review.** After the screenshot run ends, captured or not, one review run is queued (reason `screenshot_review_queued`), keyed `<item>:review:screenshots:<screenshot run>`, with input `screenshot_review: true`, `screenshot_run_id` and `screenshots` (the captures, or the reason; a failed run's reason names its error code). The review run (`src/worker/runs/review/review.run.ts`) copies the stored images into its run folder (`.factory-screenshots/`) and asks the reviewer, on `prompts/review.md` step 7, to check each against `design-system/patterns.md`: each broken rule is a finding of kind `code` naming the rule by its number. A capture that did not happen is the unverified line `screenshots not captured: <reason>`, added by the worker; with no image, no agent runs, and the run is not counted in the zero-token alarm's streak (`src/core/alarms.ts`), so a worker with no Chrome never pauses claims. Its outcome is `screenshot_review` (findings, unverified, summary), never `review`, so no verdict route, unchanged-head check, merge gate or later review reads it. Its result posts one comment (findings, then "Not verified") and acknowledges the run (reason `screenshot_reviewed`): no stage, `blocked_on` or `blocked_reason` changes, and a finding never sends the item back to implement (owner answer to the spec's decision 1).
  - **First review.** The first review has no screenshots in its input; step 7 tells it to list none under `unverified`.
  - **Item API and page.** `GET /api/v1/items/<id>` adds `screenshots` (the newest screenshot run: `run_id`, `status`, `captures`, `reason`; null with none) and `screenshot_review` (the newest screenshot review: `status`, `findings`, `unverified`, `summary`; null with none), each text through the Withholder (`src/ui/item-screenshots.ts`). `GET /api/v1/screenshot?item=&run=&page=&width=&theme=` returns one image as a PNG data URL, only one that run's outcome lists. The item page's Changes tab shows them (design 09-dashboard-item).
  - **Scope.** The capture is the factory's own dashboard on its fixture store: a project without `repo.ui_check` queues no screenshot run. Out of scope: the item's own data, a diff view, visual diffs against an earlier screenshot, and changes to `scripts/responsive-check.mjs`'s layout check.
