# 4. Screenshots of changed pages before merge

- **The screenshot run also captures every non-default tab of each tabbed page, and the Evals dialog open (decision changed 2026-11-24, local-task-tk_25b34361, "Merge screenshots open the changed tab or dialog"; current; replaces the default-URL-only page list, see History).** Two merges on 2026-11-24 could not be checked: a Settings Integrations change and a Plugins Skills "Evals does nothing" change were captured on General and MCP only. Tabs are chosen by `?tab=`, so a default-URL capture never shows another tab.
  - **List** (`capturePages` in `src/shared/screenshots.ts`). Every sidebar page and the item and transcript pages keep their names, widths, themes and order. After them, one capture per non-default tab, named `<page>-<tab>` with the path `<page>?tab=<tab>`: `settings-integrations`, `settings-advanced`, `plugins-skills`, `plugins-tools`, `plugins-models`, `health-runs`, `health-cost`, `health-review`; a page the checkout's sidebar does not list has none. Then, last, the dialog captures: `routines-new-routine` (the Routines page's New routine Dialog; a dialog with no tab is named `<page>-<dialog>` with the path `<page>`, added 2026-11-24), `schedules-new-schedule` (the Schedules page's New schedule Dialog, added 2026-11-24 after owner report #82) and `plugins-skills-evals`. Each is at 390px and 1280px, light and dark. The list is fixed: the run starts before the screenshot review, so it cannot read which tab a change touches. The names are what the review writes as `page` in `changed_pages`. Out of scope: the item page's Changes tab, the Tasks files view and any dialog but these three.
  - **Open step.** A shot may carry `open`, the value of a `data-capture-open` attribute (`ScreenshotPage.open`, sent on the shot's stdin line). After the page is drawn, `scripts/responsive/capture.mjs` clicks the enabled button with that attribute (the first one: the first skill row's Evals button in `web/src/views/plugins.tsx`), waits for a `dialog[open]` and for the page's reads to settle, then measures and captures the full page as before. When no button is found or no dialog opens within five seconds, the shot fails with "the <name> dialog did not open"; as for any failed capture, the run ends with the captures it has and that reason.
  - **Fixture.** `scripts/responsive/fixture.mjs` (also behind `npm run check:responsive`) seeds one imported skill (`fixture-review`: a `SKILL.md` in the fixture's temp dir and its `ext_skill_refs` row, the only kind of skill row whose Evals is on) and one eval suite for it, so the Skills tab has a row with Evals. It also seeds three routines (a long name on a weekly schedule, a paused interval one, one on the merge trigger), so the Routines table, its row menu and its paused Notice are drawn.
- **Each screenshot is the whole page, the fixture shows every section a changed page can show, and the screenshot review says per changed page whether its changed section appeared (decision changed 2026-11-24, local-task-tk_d8cec779, "Merge screenshots show the changed section"; current; replaces the first-screen capture and the per-run result only, see History).** Two examples from 2026-11-24 ("Rules page: Waiting for you first, compact In effect rows" and "Phase 3/3: Dismiss button on each alarm row in Needs you") showed only "Rules are off" or no alarm row, so the owner could not check the change from them.
  - **Full page** (`scripts/responsive/capture.mjs`). Each shot is laid out at its fixed height from `SCREENSHOT_SIZES` (390px wide at 844px, 1280px wide at 800px), then the capture measures the content's full height: the dashboard's shell is one window high and its content column (`[data-scroll-root]`) scrolls, so it is the window less that column's box plus all the column scrolls (or the document's height, if taller). When that is taller than the fixed height, the window grows to it and the capture takes all of it (a `Page.captureScreenshot` clip of the full height). Widths, themes and the page list are unchanged; there is no cap on an image's height.
  - **Fixture** (`scripts/responsive/fixture.mjs`, also behind `npm run check:responsive`). Rules are on: a throwaway agents home in the fixture's temp dir, wired as `scripts/idle-agents/sandbox.mjs` wires a real one, holds the rules file (two applied rules, one rule encoded elsewhere) and stub `tacit`, `evolve` and `sync-agents` that print fixed text for the forms the page reads (one rule candidate and one structure proposal waiting) and change nothing; `AGENTS_HOME` is set only in the CLIs' env. One standing approval (`spec-t1`) is on and approved three items in the last 7 days, more than the two its row names before "+N more". The two seeded alerts stay, so the Tasks page's Needs you Check group has alarm rows. The fixture has no owner check, so the Rules page shows its read-only notice; the idle agents' sandbox still replaces `tacit` and adds `pauses`.
  - **Per-page result.** The screenshot review's answer adds `changed_pages` to the review schema (`CHANGED_PAGES_SCHEMA` in `src/shared/screenshots.ts`): one entry per page the change touches, with the section it changes and `shown`, whether that section appears in at least one of its images (`prompts/review.md` step 7). The run stores them as `pages` in `screenshot_review`; each section not shown is also the unverified line `changed section not in the screenshots: <page>: <section>`. The comment lists them under "Changed pages:" ("shown in the screenshots" or "not shown in the screenshots"), before "Not verified". A section not shown never changes the verdict or the item. Out of scope: showing `pages` on the item's Changes tab (a follow-up).
- **A passing review of a UI change is followed by a screenshot run and a screenshot review; the owner sees the screenshots on the item's Changes tab before Merge (new decision, 2026-11-23, local-task-tk_e9edb2f4, "Screenshots of changed pages before merge"; current).** Before it, a UI change was reviewed from its diff alone, and the owner first saw the page after merging. No step below changes a stage, `blocked_on` or `blocked_reason`, holds the item, or touches the merge queue, the merge check or the approval gate; the merge-time UI check (`repo.ui_check`) still gates as before.
  - **Trigger** (`src/controller/units/run-results/screenshots.ts`, called by the run-results unit before it applies a review). A succeeded review whose verdict is `pass` with no `spec` finding, on an item the review still applies to, whose `pr_files` touch one of `repo.ui_check.paths` (default `web/` and `src/ui/`), queues one run of kind `screenshot`, keyed `<item>:screenshot:<review run>`, with `review_run_id` in its input. A `bug` verdict, a spec finding, no `repo.ui_check`, no `pr_files`, or files outside those paths queue none. The run is queued by a plain transition (empty patch, reason `screenshots_queued`), not through `decide`: a look at stored images is never held by the token budget or the Rule of Two, which would block the item.
  - **Run** (`src/worker/runs/screenshot/screenshot.run.ts`; `screenshot` is in `RunKind`, `WORKER_KINDS`, the `worker_kinds` default and `CLAIM_ORDER`, ranked after `review`; no schema change: the kind is text and the result is the run outcome). No agent, no push. In a run folder on the item's branch: the install command (run-side install cache), then the dashboard's build (`npm run --silent build`), then the capture. The capture is fixed: every sidebar page `web/src/pages.ts` lists, the fixture's item page and its run's transcript page, each at 390px and 1280px, in light and dark, as the whole page (`src/shared/screenshots.ts`; the full-page decision above). There is no width or theme setting.
  - **Browser** (`ScreenshotBrowser` in `src/shared/screenshots.ts`; Chrome in `src/shared/chrome-browser.ts`; tests hand a fake). The Chrome browser runs every command through the run's sandbox (`Sandbox.exec` on the run folder's handle, bound by the run as `RunExec`), never as a host process, so code written on the item's branch runs only where its other commands run. It reads `web/src/pages.ts`, then runs the checkout's `scripts/responsive/capture.mjs` once, with the fixed list of shots on stdin (the item and transcript paths hold `:item` and `:run`, which the script fills with its fixture's IDs) and only `PATH`, `HOME`, the temp folders, `LANG`, `CHROME_PATH` and `CI` in its env (no token, no secret). The script seeds the same throwaway fixture store as `npm run check:responsive` (`scripts/responsive/fixture.mjs`: never the item's own data), serves it with the checkout's built UI server and drives headless Chrome through the check's driver (`scripts/responsive/cdp.mjs`); each PNG goes back on stdout, one JSON line per shot, in order. The driver stays in `scripts/responsive/`: the worker never imports it, and its timers could not live in `src/shared/` (the no-clock rule).
  - **Storage.** Each PNG is put in shared storage by the worker once the capture returns it, under `<item id>/<run id>/<page>-<width>-<theme>.png`. Nothing is written in the repository or under `.playwright-mcp/`. The outcome is `{ captures: [{ page, width, theme, key }], reason, review_run_id }`.
  - **Failure.** No Chrome, no capture script in the checkout, a failed install or build, or a capture that fails ends the run with the captures it has and a `reason`: a result, never a run failure. A run that fails anyway (a lost lease) is not retried.
  - **Screenshot review.** After the screenshot run ends, captured or not, one review run is queued (reason `screenshot_review_queued`), keyed `<item>:review:screenshots:<screenshot run>`, with input `screenshot_review: true`, `screenshot_run_id` and `screenshots` (the captures, or the reason; a failed run's reason names its error code). The review run (`src/worker/runs/review/review.run.ts`) copies the stored images into its run folder (`.factory-screenshots/`) and asks the reviewer, on `prompts/review.md` step 7, to check each against `design-system/patterns.md`: each broken rule is a finding of kind `code` naming the rule by its number. A capture that did not happen is the unverified line `screenshots not captured: <reason>`, added by the worker; with no image, no agent runs, and the run is not counted in the zero-token alarm's streak (`src/core/alarms.ts`), so a worker with no Chrome never pauses claims. Its outcome is `screenshot_review` (findings, unverified, summary, and `pages` since 2026-11-24), never `review`, so no verdict route, unchanged-head check, merge gate or later review reads it. Its result posts one comment (findings, then "Not verified") and acknowledges the run (reason `screenshot_reviewed`): no stage, `blocked_on` or `blocked_reason` changes, and a finding never sends the item back to implement (owner answer to the spec's decision 1).
  - **First review.** The first review has no screenshots in its input; step 7 tells it to list none under `unverified`.
  - **Item API and page.** `GET /api/v1/items/<id>` adds `screenshots` (the newest screenshot run: `run_id`, `status`, `captures`, `reason`; null with none) and `screenshot_review` (the newest screenshot review: `status`, `findings`, `unverified`, `summary`; null with none), each text through the Withholder (`src/ui/item-screenshots.ts`). `GET /api/v1/screenshot?item=&run=&page=&width=&theme=` returns one image as a PNG data URL, only one that run's outcome lists. The item page's Changes tab shows them (design 09-dashboard-item).
  - **Scope.** The capture is the factory's own dashboard on its fixture store: a project without `repo.ui_check` queues no screenshot run. Out of scope: the item's own data, a diff view, visual diffs against an earlier screenshot, and changes to `scripts/responsive-check.mjs`'s layout check.
