# 7. Self-improvement

- **A fix spec runs unless the draft needs a person or touches a gate path (decision changed 2026-11-10, issue #504; changes "The factory triages them" below).** The draft gains `needs_person` (the model's answer, required in `IMPROVE_SCHEMA` and `prompts/improve.md`: true when no change to the repository can fix it, such as an owner decision, a credential, a quota or an outside service). Filing then takes one of two paths:
  - **No person.** A group whose draft is not `needs_person` and whose fix touches no `GATE_PATHS` (or that has no draft) is filed as one fix item, as before (one per pattern: the `controller_filed_patterns` claim, so two replicas file once). When its triage run succeeds, the controller approves its spec without a person, whatever the tier or mode (reason `fix_spec_approved`, the pattern key in the detail, the spec comment says so), and it is implemented and reviewed like any approved item. The fix item is found by its source ref in `controller_filed_patterns`, never by the marker in its body, so an issue that copies the marker is not one. Its merge follows the usual rules: a change whose spec touches the gate list waits for a person's merge, auto merge refuses it (03-risk), and a GitHub PR always waits for a person; the spec comment names the gate path.
  - **A person.** A group whose draft says `needs_person`, or whose fix touches the gate list (`touches_prompts_or_gate`, withheld drafts included), is not filed: no item, no triage or fix run. Needs you shows it as an alert (pattern `repeated_error`, key `needs_person:<key>`, detail "Needs a person: …" with the draft's cause, scanned as UI text), stored once a day per pattern; the group's filing is `skipped: needs_person`.
  - When the fix item merges, the items its pattern held (design 05-alarms) return to the queue for retry. Solo and enterprise use the same path; the fix runs on the same store. Out of scope: an automatic merge of a fix touching a gate path, prompt, permission or tool, and automatic fixes for needs-person drafts.
- **File each recurring failure pattern (new decision, 2026-11-08, issue #308; phase 3 of the self-improvement plan).** After a succeeded improve run, before acknowledging it, the controller files the report's groups of two or more runs (`fileReport`, `src/core/improver.ts`). One-run patterns stay in the report only, never filed or commented.
  - **Where.** Through the first source in `plugins.source` order that has `SourceAdapter.fileIssue`. Solo default: `local` files a local work item (source id `local-filed-<hash of the marker>`, requester `system:improver`), no external account. Enterprise: `github-issues` files a GitHub issue. No source that can file: each group is `skipped: no_source`.
  - **The factory triages them (decision changed 2026-11-09, owner: "I want this to be automatically triaged"; since 2026-11-10 only drafts that need no person and touch no gate path are filed, and their spec is approved without a person, see the first entry).** A filed item is triaged with no person starting it. `github-issues` files the issue with the intake label (`github.intake_label`), so the next poll takes it in like any labelled issue; its requester is the bot's account (`submit_work` is open to every account no grant denies, so no permission changes). `local` queues the item's triage run when it creates it, as `factory task create` does (key `local:<source id>:triage`), requester `system:improver`. The human-merge rule is kept by the gates, not by withholding triage: a spec whose allowed paths touch `GATE_PATHS` waits for `/approve` and its change for a person's merge even in auto mode (03-risk), and a GitHub item's PR always waits for a person. The body lists the group's runs and items, the normalized detail, the draft (marked unverified), when the fix touches `GATE_PATHS` that it needs a human merge, and that the factory triages it.
  - **Pattern key and marker.** The key is a short stable hash (cyrb53) of the error code and normalized detail. Each filing is claimed in `controller_filed_patterns` (unique per project and key) before the source call, and the body carries `<!-- factory:improve:<key>:<claiming report id> -->`. The source looks the marker up before filing (`github-issues`: the newest 300 intake-labelled issues; `local`: the source id derived from it), so a retry after a failure part way never files a second item. A claim left with no item is finished by the next improve run that sees the pattern.
  - **Matching.** A group whose key has a filed item that is open (or not in the store: filed, nobody started it) gets one comment naming its runs not linked there yet, marker `factory:improve-comment:<key>:<report id>`; no new run: `linked`, nothing posted. A run is linked when an earlier report filed or commented it on that item; the reports since the window's start cover every run of the window. An item closed in the last 30 days (by its `updated_at`) also matches: `skipped: recently_closed`, nothing sent. An item closed longer ago does not: the pattern is filed again and the claim moves to the new report. A comment on an item in the store goes through its thread (and the outbox); on one nobody started, straight to its source, once per marker.
  - **Caps.** At most `MAX_FILED_ISSUES` = 3 new items and 3 comments per run (largest groups first); the rest are `skipped` with `issue_cap` or `comment_cap`. A constant like `MAX_DRAFT_CALLS`, not a config key: one number solo and enterprise share; comments are writes through the shared account.
  - **Egress.** Every body and comment passes the G5 scan (`comment` channel) before it is sent. A flagged one is not sent and nothing is claimed; the group is recorded `withheld` with its rules only.
  - **Record.** Each group's outcome is stored on it in the report (`filing`: `filed`, `commented` with the new run IDs, `linked`, `skipped` with its reason, `withheld` with its rules, `failed` when the source call threw). No schema step: `controller_filed_patterns` (migration 31) as it is, in SQLite and MySQL. A fault is logged and the run acknowledged anyway: a sync plugin's outage never holds local work.
  - **Health page.** The status page shows the latest improve report below Health: window, group and pattern counts, each group's draft cause and fix and its filing, skipped and withheld ones with their reason or rules. Every text passes the Withholder.
- **Draft cause and fix per failure group (new decision, 2026-11-07, issue #307; phase 2 of the self-improvement plan).** The improve run now makes one plain model call per group of two or more runs. A one-run pattern gets none.
  - **Call.** `LLMProvider.complete` with only system (`prompts/improve.md`), one user message, `max_tokens`, `output_schema` (`cause`, `fix`, `touches`), `model_class: standard`, `data_env: test` and the run's signal, bounded by a 120 s timeout. No tools, no tool grants, no sandbox, no agent runner. Its usage counts toward the run's. Solo: the checked-in `plugins.llm` default, no new setup. Enterprise: the same named chain; no shared budget yet (a follow-up). No new config key.
  - **Cap.** At most 5 calls per run (`MAX_DRAFT_CALLS`), largest groups first; each group past the cap is marked `draft: { status: skipped, reason: call_cap }`, so the report lists what it skipped. A constant, not a setting: one number solo and enterprise share until budgets exist.
  - **Tails.** For each called group, the transcript tails (last 4 000 bytes of `transcripts/<item>/<run>.json`) of its 3 latest runs pass the G5 scan on the `log` channel before the call. A flagged tail is left out of the prompt and recorded `withheld` with its rules, never its text. A run with no stored transcript (none, or one the scan kept out of storage) is recorded `missing`.
  - **Output.** Checked against the schema. Invalid output, a refusal, an error or a max-tokens stop marks the group's draft `failed` with that reason; the run still completes with its report. A valid draft passes the G5 scan (`log`) before it is stored; a flagged one is stored `withheld` with its rules only.
  - **`touches_prompts_or_gate`.** Set by the factory, never the model: true when a path in `touches` is on `GATE_PATHS` (`src/core/improver.ts`), the owner-only list: `prompts/`, `src/impl/broker/`, `src/impl/egress/`, `src/impl/secrets/`, `src/impl/sandbox/`, `src/impl/auth/`, `src/core/checks.ts`, `src/core/policy.ts`, `.claude/`, `factory.config.json`. One constant, so the merge check can reuse it.
  - **Storage.** Drafts and tail markers live on each group in the existing `failure_groups` JSON; no schema step. A retry of a run whose report exists returns it with no model call.
  - **Wiring.** `WorkerDeps.llm` is optional; compose always passes the `plugins.llm` chain. Without it (or without the improve prompt) the run is phase 1's: groups carry no draft.
- **Daily improve run and its report (decision 2026-11-07, issue #306; phase 1 of the self-improvement plan).** A new run kind, `improve`, looks back at failed runs once a day. It runs no agent.
  - **Schedule.** Each controller tick queues the improve run of the current UTC calendar day, key `improve:<project key>:daily:<YYYY-MM-DD>`, so a second tick, a restart or another replica that day queues nothing (the controller keeps the day it saw queued in process, only to skip the store write). `factory improve` queues one run now through the same enqueue, key `improve:<project key>:manual:<ISO time>`: never the day's slot, not gated. No config key sets the time or the window.
  - **Window.** Fixed at enqueue in the run's input (`input.improve`), so a retry reports the same runs: the daily run of day D covers the previous full UTC day, [D−1 00:00, D 00:00); a manual run the 24 hours before it was queued. A run finished outside the window is not counted.
  - **System work item.** The runs table needs a work item, so each project has one system work item that carries its improve runs: source `local`, id `system:improve:<project key>`, made on first use, `NEW` with `blocked_on: upstream`, `blocked_reason: system_item` for good (a blocked reason, not a new stage). Nothing triages, implements or releases it; the controller acknowledges an improve run with no field change (`improve_done` / `improve_failed`).
  - **Claim and work.** Workers claim `improve` through the same `claimRun` as every kind, ranked after the listed kinds. It needs no sandbox: the worker reads the window's finished runs, groups the failed ones (improve runs left out) by error code and normalized detail (lower case, digit runs → `#`, hex ids of 7+ characters → `<id>`, whitespace collapsed, 200 characters), and stores one report per run (keyed by run, so a retry keeps the first). Groups of two or more runs come first by size, then by key; one-run patterns by key; run IDs in finish order. The same input runs give an identical grouping. The outcome names the report and its counts.
  - **Tables.** `controller_improve_reports` (window, `failure_groups` and `patterns` as JSON: run IDs and item IDs, never raw detail) and `controller_filed_patterns` (one row per pattern filed from a report, unique per project and pattern key): SQLite migration 31, MySQL step 0031. Phase 3 (#308) writes `controller_filed_patterns`.
  - **Not yet.** Opening PRs or fixing the failures. Solo and enterprise are the same: one system item per project on the shared store.
- Behavior changes only through what agents read or may do: all files in the factory-definition repo.
- Additive learnings: planned to be automatic, **not built yet** (2026-11-07): no code or doc writes learnings today. Prompt / gate / permission / tool changes: improver PR with replay evidence → human.
- Recurring failure class → hard fix (gate, permission), not a softer prompt.
- Progressive disclosure: index → body → references; `CapabilitySearch` (BM25, vector, hybrid) finds skills/tools/MCP. Finding ≠ permission.
  - **Doc index in the prompt (new decision, 2026-11-01):** the worker takes an optional `CapabilitySearch` and appends the top 8 results to the triage, implement and review prompts as a short index (path, name, ≤200-character snippet); agents read full text on demand with `Read`, which they already have. The index grants nothing: tools, `deny_paths` and grants are unchanged. BM25 comes first (`bm25` plugin: `*.md` under `docs/` and `skills/`, headings boosted, rebuilt from files when they change, per process); vector and hybrid stay later. `Capability.kind` gains `doc` for markdown docs (`skill` for `skills/`). The checked-in config selects `bm25` (2026-11-07), so every triage, implement and review prompt gets the index; `list-all`, which finds nothing, is the fallback.

## History

- **A fix spec runs without a person** (decision changed 2026-11-10, issue #504). Before (2026-11-09): every group was filed and triaged, and its spec waited at the spec gate like any item's (`/approve`, or auto mode below tier 4 with no gate path); a draft had no `needs_person`, and a draft that touched the gate list was filed too, with a note that it needs a human merge.
- **Filed items are triaged by the factory** (decision changed 2026-11-09). Before (2026-11-08, #308): a person started them. Filed items carried no intake label and got no triage run, so filing the factory's own fixes never went ahead without a human; the body said "Filed for a person to start".
- **File each recurring failure pattern** (new decision, 2026-11-08, issue #308). Before (phases 1 and 2): nothing was filed or posted; `controller_filed_patterns` stayed empty, filing and posting to a source were listed under Not yet, and the status page did not show the report.
- **Draft cause and fix per failure group** (new decision, 2026-11-07, issue #307). Before (phase 1, #306): the improve run called no model; its report grouped failed runs but named no cause or fix, and "reading or summarising failures with a model" was listed under Not yet.
- **Daily improve run** (new decision, 2026-11-07, issue #306). Before: no run looked back at failed runs; they could be read by time window (the status page), but nothing grouped them or stored a report.
- **Doc index in the prompt** (new decision, 2026-11-01). Before this, no agent received any capability list (`list-all` existed but nothing built it).
- **Checked-in `CapabilitySearch` default** (changed 2026-11-07). Before: the default stayed `list-all`, which finds nothing, so no prompt got a doc index. Now: `bm25`.
- **Additive learnings** (corrected 2026-11-07). Before: "additive learnings: automatic", though nothing wrote them. Now: marked planned, not built yet.
