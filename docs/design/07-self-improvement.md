# 7. Self-improvement

- **Promoted rules reach every prompt, and the owner's pushbacks count beside run failures (decision changed 2026-11-12, issue #571; current; changes "Rules, learnings and skills reach every agent prompt" below, where promoting rules was "still later", and "Claim and work" under the daily improve run, which grouped failed runs only, see History). Its learned-rules read, scope and verdict path changed again on 2026-11-12 to the owner's real `tacit` and `evolve` forms (replaces `TacitLedger.list` and the verdict as JSON on stdin, see History).**
  - **Learned rules in the prompt.** At each run start `LearnedRules` (`src/core/learned-rules.ts`) reads the owner's promoted rules with `TacitLedger.rules()`, through the `plugins.tacit` plugin only: the module opens no file and names no path (a test reads its imports). The `agents-home` plugin reads them from `<home>/private/tacit/rules.md`, one `## C-xxx <name>` section per rule (docs/plugins/tacit-ledger.md). The worker appends them as their own `## Learned rules` section after the packs' `## Rules and learnings` and before the doc index (`joinGuidance` in `src/compose.ts`), in the file's order: one bullet per rule, its default (`기본값`), then an `Except:` line with its exceptions (`예외`) and a `Scope:` line with its scope (`범위`) when it has them. A rule with no default is left out. With the plugin `none`, no rules file or no rule, or a failed read (a warning), there is no section and the prompt is as before. Cap: 4000 characters (`LEARNED_RULES_MAX`, about 1000 tokens), a constant; text past it is dropped with a warning.
  - **Scope.** A rule's scope is the owner's own words (`범위`), not domain tags, so the factory no longer drops a rule by scope: it puts the scope under the rule and the agent applies it. `RUN_DOMAIN` and the tag filter are gone.
  - **Promote, reject, hold.** Only from the dashboard's Rules page (09-dashboard-app.md), through `TacitLedger.verdict(id, decision, reason, rule?)`. The `agents-home` plugin runs `<home>/bin/tacit verdict <id> <decision> --reason <reason>` for a candidate class (`C-` ID), with `--rule <the owner's wording>` on promote only, and `<home>/bin/evolve verdict <id> <decision> --reason <reason>` for a structure proposal (`P-` ID), never with a rule; each value is its own argv item, never through a shell. The CLIs take no field for who judged, so the ledger does not record it; the owner check stays, and the dashboard's log names the owner's user ID. The ledger schema and the terminal `/evolve` are unchanged, and nothing is written to the owner's agent instruction files.
  - **Pushbacks as signals.** `runImprove` also reads the project's pushbacks made inside its window: each `/reject` and `/revise` with words (`spec_feedback` on its `spec_rejected` or `spec_revision_requested` state change) and each explicit `changes` verdict with a reason (`listStateChangesSince`, `listVerdictsSince`, then one run list per item). Each counts once, on the item's latest run that succeeded before it (the output pushed back on); one with no such run is not counted. Its words pass the G5 scan (`log`) first; a flagged one is not counted. `groupFailures` groups them under the error code `pushback` by their normalized words, as a failure's detail. So two pushbacks with the same words make a group of two: one draft call and one filed proposal, exactly as two failed runs with one error; a one-off pushback stays a one-run pattern. The trigger rule still counts failed runs only.
  - **Solo and enterprise.** The same code. Solo: the local ledger in the owner's agents home, the owner the only user. Enterprise: one owner still (RFC 0020, after #568 no roles), so the verdict check is the owner check; the log line of a verdict carries the owner's user ID, never a display name.
- **Scorer grades for succeeded runs, and an improve run as soon as failures pile up in 24 hours (decision changed 2026-11-11, issue #514; changes "Trigger rule" and "Why K = 10" under "An improve run when failures pile up" below, and replaces the schedule-only start of the daily improve run, see History).**
  - **Grades.** Each succeeded agent run (triage, implement, review, resolve) is graded before its outcome is stored: `gradeRun` (`src/worker/runs/improve/improve.run.ts`, called from the worker's run step) asks every judge of the scorer (`src/core/scorer.ts`, the `Judge` interface) and stores their grades in the outcome's data as `grades: [{ judge, score, reason }]`, score 1 to 5. Failed runs and runs with no agent (improve, update, merge-check) get none. A judge that fails, refuses, times out (60 s) or answers out of schema gives no grade; grading never fails a run. The usage of each judge call counts toward the run's.
  - **Independent judges.** A judge is never the call that produced the run: it is its own plain `LLMProvider.complete` (no tools, no session, no sandbox, no agent runner), on another model class than the producer's (`judgeClass`: `strong` for a `cheap` or `standard` run, `standard` for a `strong` one), with its own system prompt, and it reads only the item's title and the run's stored output (its data as JSON, cut to 6000 characters), never the producer's prompt or transcript. So a grade does not carry the producing call's bias. The output passes the G5 scan (`log`) before a judge reads it, and each grade's reason before it is kept; a flagged one is left out.
  - **The judges' prompt.** The `## Grading a run` section of `prompts/improve.md` is the judges' system prompt and names the output format; the text before it stays the draft call's system prompt, byte for byte as before (`improvePrompts`).
  - **Scorers off.** With no LLMProvider in the worker (`WorkerDeps.llm` absent), or no `## Grading a run` section, the scorer is `NO_SCORER`: no judge, no grade, no model call, nothing logged at startup. Compose passes the `plugins.llm` chain, and the checked-in default selects one, so a factory with a model has grades.
  - **Trigger by count in 24 hours.** `improveTriggerDue` (`src/core/improver.ts`) is now due when **10** failed runs of the project, of any run kind but `improve`, finished in the last **24 hours** (`TRIGGER_FAILURES`, `TRIGGER_WINDOW_MS`) and since its last improve run was queued; the 3-day age rule is unchanged. Before, it counted per run kind, so ten failures spread over triage, implement and review queued nothing. Why 24 hours: the daily run's window, so a burst that the next daily run would only see tomorrow gets its report today. Constants, not settings.
  - **One run across replicas, in the store.** The controller's improve step calls `triggerImprove` each tick, as before. Its dedupe is store state, not process memory: the key `improve:<project key>:trigger:<last improve run id, or none>` is the same for every replica that sees the same failures, and `enqueueRun`'s conditional insert on that unique key keeps one run. `factory improve`, Run now and the trigger all queue through `enqueueImprove`, so a manual run writes the same system work item and run shape as a triggered one. No schema change: the run's idempotency key is the stored dedupe, and grades live in the outcome's JSON.
  - **Solo and enterprise.** The same code: one store, the worker's own `plugins.llm` chain, no config key.
- **Improve reports are per project, and the daily run learns a tighter `max_diff_lines` (decision changed 2026-11-11, issue #497; changes "Claim and work" under the daily improve run below, where the report grouped the window's failed runs of every project, see History).**
  - **Per project.** `runImprove` counts only the failed runs whose work item is in the improve run's project (decision 3 of #497), the same filter the trigger rule uses (one item read per item in the window). Two projects on one store get two reports that share no run.
  - **The learner.** After the daily run stores its report, `learnFromReport` (`src/core/learned-settings.ts`, called from `src/worker/runs/improve/improve.run.ts`) reads the report's `diff_too_large` runs. With 3 or more it writes one learned `max_diff_lines` for the project and window: 80% of the value in force, rounded down, never below 1, only when tighter. One audit row names the evidence run IDs. A manual or triggered run learns nothing (decision 2 of #497). The store, the conditional write, the check in `settingsFor` and the reset are in 08-settings.md.
  - **Solo and enterprise.** The same: the learned value and its audit are store rows, so every worker and controller on the store reads it at its next settings refresh; a retry or a second worker on the same window writes nothing.
- **A filed pattern holds its items for a person and records whether its fix held (decision changed 2026-11-11, issue #511; changes "When the fix item merges" under the fix-spec entry and "Record" under filing below).** Before, a filed pattern's items kept running after it was filed until the alarm step's re-raise held them, after `alarm_repeat_count` new failures, as `blocked_on: upstream`; and nothing checked whether a merged fix held, so `controller_filed_patterns` had no outcome.
  - **Hold.** In the alarm step (every controller poll, design 05-alarms), not the improve run, which is daily or triggered and would hold late: the first failed run whose pattern key matches a filed pattern with an open item holds that run's item, `blocked_on: human`, `blocked_reason: recurring_failure`, the pattern key in the state change detail. A conditional transition, once per run. The release when the fix merges is unchanged.
  - **Outcome.** Each controller tick the improve unit (`settleOutcomes`, `src/core/improver.ts`) reads the project's filed patterns with an item and no outcome (`listFiledPatternsWithoutOutcome`). One whose fix item closed as `completed` at least **7 days** ago (`OUTCOME_WAIT_MS`; the close time is the state change that set `CLOSED`) gets `regressed` when a failed run of its pattern finished in the 7 days after the close, else `holds`, and `outcome_at`. The write is `setFiledPatternOutcome`, a conditional update `WHERE outcome IS NULL`, so a retry or a second replica writes once. An item still open, not in the store, or closed as `failed`, `rejected`, `duplicate` or `wont_do` gets no outcome. A refiled pattern (its item closed over 30 days ago) starts again with no outcome.
  - **Why 7 days.** Long enough for a daily improve run and a week of ordinary traffic to hit the pattern again, short enough to judge a fix while it is still fresh. A constant, not a setting.
  - **Store.** Nullable `outcome` and `outcome_at` on `controller_filed_patterns`, the timestamped migration `src/controller/migrations/20261111T1500-controller-filed-pattern-outcome` (no numbered step: the numbered list is frozen). Rows filed before keep no outcome: no backfill. The stored report is not rewritten, and the status page does not show outcomes yet (a follow-up). Solo and enterprise are the same: one store, no config key.
- **Rules, learnings and skills reach every agent prompt (decision changed 2026-11-11, issue #490; replaces "additive learnings: not built yet").** Reading is built; writing learnings is still later. Promoting rules: since 2026-11-12, see the first entry (#571).
  - **Where they live.** Each pack layer (design 11-packs.md, in `packs.order`: base is the code root, then org, project, learned) may hold `rules/*.md` and a `learnings.md`. Learnings are the file's `## ` sections (outside code fences; text before the first is a title, not an entry). An entry with a line `status: retired` is left out.
  - **In the prompt.** `PackGuidance` (`src/impl/capability/project-guidance.ts`) reads them at each run: every layer's rules in full (files by name), then every layer's unretired learnings, as a `## Rules and learnings` section. The worker appends it to the triage, implement, review and resolve prompts before the `## Available docs (index)` section (`WorkerDeps.guidance`, wired in `src/compose.ts`). No rules and no learnings: no section, so the prompt is byte for byte what it was.
  - **Cap.** Rules and learnings together are at most 8000 characters per prompt (fixed; rules first, so learnings are cut first). Text past the cap is dropped and a warning with the dropped count is logged. Why 8000: about 2000 tokens, small beside the prompt, large enough for a page of rules.
  - **Best effort.** A missing folder or file is none. Any other read failure is a warning; the run goes on without rules and learnings, as a failed index search does.
  - **Kept out of the doc index.** The `bm25` index skips every `learnings.md`, so a retired entry is never found there. Skills: an Agent Skills `skills/<name>/SKILL.md` is indexed with its frontmatter `name` and `description` as name and snippet, in the code root and in every pack layer's `skills/`.
  - **Solo and enterprise.** The same: each worker reads the layers of its own process's checkout (base) and its pack folders; nothing is stored or shared, no config key, no store state.
- **A fix spec runs unless the draft needs a person or touches a gate path (decision changed 2026-11-10, issue #504; changes "The factory triages them" below).** The draft gains `needs_person` (the model's answer, required in `IMPROVE_SCHEMA` and `prompts/improve.md`: true when no change to the repository can fix it, such as an owner decision, a credential, a quota or an outside service). Filing then takes one of two paths:
  - **No person.** A group whose draft is not `needs_person` and whose fix touches no `GATE_PATHS` (or that has no draft) is filed as one fix item, as before (one per pattern: the `controller_filed_patterns` claim, so two replicas file once). When its triage run succeeds, the controller approves its spec without a person, whatever the tier or mode (reason `fix_spec_approved`, the pattern key in the detail, the spec comment says so), and it is implemented and reviewed like any approved item. The fix item is found from the marker in its filed body (`markerKey`), or, after a spec revision replaced the body, from its earlier `fix_spec_approved` change; the pattern's stored item (`controller_filed_patterns.filed_ref`) must be this item, so an issue that copies a marker is not one. Its merge follows the usual rules: a change whose spec touches the gate list waits for a person's merge, auto merge refuses it (03-risk), and a GitHub PR always waits for a person; the spec comment names the gate path.
  - **A person.** A group whose draft says `needs_person`, or whose fix touches the gate list (`touches_prompts_or_gate`, withheld drafts included), is not filed: no item, no triage or fix run. Needs you shows it as an alert (pattern `repeated_error`, key `needs_person:<key>`, detail "Needs a person: …" with the draft's cause, scanned as UI text), stored once a day per pattern; the group's filing is `skipped: needs_person`.
  - When the fix item merges, the items its pattern held (design 05-alarms; from its first matching run since 2026-11-11, see the first entry) return to the queue for retry. Solo and enterprise use the same path; the fix runs on the same store. Out of scope: an automatic merge of a fix touching a gate path, prompt, permission or tool, and automatic fixes for needs-person drafts.
- **An improve run when failures pile up, and Run now (new decision, 2026-11-10, issue #508).** The decision that changed: **the improve run is no longer only daily or by `factory improve`**; a burst or an old failure queues one at the next controller tick, and an approver can queue one from the status page.
  - **Trigger rule.** Each controller tick, after the daily step, the improve unit reads the project's unreviewed failures: the failed runs (any kind but `improve`, the same runs a report groups) of the project's items that finished since its last improve run was queued (any status; all of them before the first). `improveTriggerDue` (`src/core/improver.ts`, pure) is due when **K = 10** or more of them finished in the last 24 hours, of any run kind (since 2026-11-11, issue #514, see the first entry; before, per run kind), or when the oldest is older than **3 days**. Then `triggerImprove` queues one run per project through `enqueueImprove` with key `improve:<project key>:trigger:<last improve run id, or none>` and the window [last improve run's queue time (or the oldest failure), now). Nothing is queued while any improve run of the project is queued or running, and the failures before a queued run are never counted again.
  - **Why K = 10.** Ten failures in a day since the last look is a burst worth a report the same day, not the next; fewer would queue a run, with its model calls, for ordinary noise between daily runs.
  - **Why 3 days.** The daily run normally resets the count each day, so an unreviewed failure this old means daily runs have not been queued or finished (a stopped controller, a failing improve run); three days lets a weekend pass without a burst, and no failure stays unseen longer.
  - **Constants, not settings.** K and the age are constants in `src/core/improver.ts`; `factory.config.json` has no key for them (a setting needs a reason that no one has yet).
  - **Replicas.** The rule reads store state only, no process memory: two controllers that tick together read the same last improve run and write the same key, and the store's idempotency key keeps one run.
  - **Run now.** The status page's Health panel (`/classic`) shows a Run now button to a user who may approve; `POST /api/v1/improve/run` (`src/ui/improve-api.ts`) queues one manual run through `enqueueImprove`, as `factory improve` does, and answers its `run_id`. It is refused (409, with the run's id) while an improve run is queued or running; the guards and owner check are in `09-dashboard-app.md`.
  - **Solo and team.** The same code with no source plugin selected on the local store (solo) and on the shared store (team); only the store differs.
- **File each recurring failure pattern (new decision, 2026-11-08, issue #308; phase 3 of the self-improvement plan).** After a succeeded improve run, before acknowledging it, the controller files the report's groups of two or more runs (`fileReport`, `src/core/improver.ts`). One-run patterns stay in the report only, never filed or commented.
  - **Where.** Through the first source in `plugins.source` order that has `SourceAdapter.fileIssue`. Solo default: `local` files a local work item (source id `local-filed-<hash of the marker>`, requester `system:improver`), no external account. Enterprise: `github-issues` files a GitHub issue. No source that can file: each group is `skipped: no_source`.
  - **The factory triages them (decision changed 2026-11-09, owner: "I want this to be automatically triaged"; since 2026-11-10 only drafts that need no person and touch no gate path are filed, and their spec is approved without a person, see the first entry).** A filed item is triaged with no person starting it. `github-issues` files the issue with the intake label (`github.intake_label`), so the next poll takes it in like any labelled issue; its requester is the bot's account (`submit_work` is open to every account no grant denies, so no permission changes). `local` queues the item's triage run when it creates it, as `factory task create` does (key `local:<source id>:triage`), requester `system:improver`. The human-merge rule is kept by the gates, not by withholding triage: a change whose spec touches `GATE_PATHS` waits for a person's merge even in auto mode (03-risk), and a GitHub item's PR always waits for a person. The body lists the group's runs and items, the normalized detail, the draft (marked unverified), and that the factory triages, implements and reviews it without a person, a gate-path change still waiting for a person's merge.
  - **Pattern key and marker.** The key is a short stable hash (cyrb53) of the error code and normalized detail. Each filing is claimed in `controller_filed_patterns` (unique per project and key) before the source call, and the body carries `<!-- factory:improve:<key>:<claiming report id> -->`. The source looks the marker up before filing (`github-issues`: the newest 300 intake-labelled issues; `local`: the source id derived from it), so a retry after a failure part way never files a second item. A claim left with no item is finished by the next improve run that sees the pattern.
  - **Matching.** A group whose key has a filed item that is open (or not in the store: filed, nobody started it) gets one comment naming its runs not linked there yet, marker `factory:improve-comment:<key>:<report id>`; no new run: `linked`, nothing posted. A run is linked when an earlier report filed or commented it on that item; the reports since the window's start cover every run of the window. An item closed in the last 30 days (by its `updated_at`) also matches: `skipped: recently_closed`, nothing sent. An item closed longer ago does not: the pattern is filed again and the claim moves to the new report. A comment on an item in the store goes through its thread (and the outbox); on one nobody started, straight to its source, once per marker.
  - **Caps.** At most `MAX_FILED_ISSUES` = 3 new items and 3 comments per run (largest groups first); the rest are `skipped` with `issue_cap` or `comment_cap`. A constant like `MAX_DRAFT_CALLS`, not a config key: one number solo and enterprise share; comments are writes through the shared account.
  - **Egress.** Every body and comment passes the G5 scan (`comment` channel) before it is sent. A flagged one is not sent and nothing is claimed; the group is recorded `withheld` with its rules only.
  - **Record.** Each group's outcome is stored on it in the report (`filing`: `filed`, `commented` with the new run IDs, `linked`, `skipped` with its reason, `withheld` with its rules, `failed` when the source call threw). No schema step: `controller_filed_patterns` (migration 31) as it is. A fault is logged and the run acknowledged anyway: a sync plugin's outage never holds local work.
  - **Health page.** The status page shows the latest improve report below Health: window, group and pattern counts, each group's draft cause and fix and its filing, skipped and withheld ones with their reason or rules. Every text passes the Withholder.
- **Draft cause and fix per failure group (new decision, 2026-11-07, issue #307; phase 2 of the self-improvement plan).** The improve run now makes one plain model call per group of two or more runs. A one-run pattern gets none.
  - **Call.** `LLMProvider.complete` with only system (`prompts/improve.md`), one user message, `max_tokens`, `output_schema` (`cause`, `fix`, `touches`), `model_class: standard`, `data_env: test` and the run's signal, bounded by a 120 s timeout. No tools, no tool grants, no sandbox, no agent runner. Its usage counts toward the run's. Solo: the checked-in `plugins.llm` default, no new setup. Enterprise: the same named chain; no shared budget yet (a follow-up). No new config key.
  - **Cap.** At most 5 calls per run (`MAX_DRAFT_CALLS`), largest groups first; each group past the cap is marked `draft: { status: skipped, reason: call_cap }`, so the report lists what it skipped. A constant, not a setting: one number solo and enterprise share until budgets exist.
  - **Tails.** For each called group, the transcript tails (last 4 000 bytes of `transcripts/<item>/<run>.json`) of its 3 latest runs pass the G5 scan on the `log` channel before the call. A flagged tail is left out of the prompt and recorded `withheld` with its rules, never its text. A run with no stored transcript (none, or one the scan kept out of storage) is recorded `missing`.
  - **Output.** Checked against the schema. Invalid output, a refusal, an error or a max-tokens stop marks the group's draft `failed` with that reason; the run still completes with its report. A valid draft passes the G5 scan (`log`) before it is stored; a flagged one is stored `withheld` with its rules only.
  - **`touches_prompts_or_gate`.** Set by the factory, never the model: true when a path in `touches` is on `GATE_PATHS` (`src/core/improver.ts`), the owner-only list: `prompts/`, `src/impl/broker/`, `src/impl/egress/`, `src/impl/secrets/`, `src/impl/sandbox/`, `src/impl/auth/`, `src/core/checks.ts`, `src/core/policy.ts`, `.claude/`, `factory.config.json`. One constant, so the merge check can reuse it.
  - **Storage.** Drafts and tail markers live on each group in the existing `failure_groups` JSON; no schema step. A retry of a run whose report exists returns it with no model call.
  - **Wiring.** `WorkerDeps.llm` is optional; compose always passes the `plugins.llm` chain. Without it (or without the improve prompt) the run is phase 1's: groups carry no draft.
- **Daily improve run and its report (decision 2026-11-07, issue #306; phase 1 of the self-improvement plan).** A new run kind, `improve`, looks back at failed runs once a day. It runs no agent.
  - **Schedule.** Each controller tick queues the improve run of the current UTC calendar day, key `improve:<project key>:daily:<YYYY-MM-DD>`, so a second tick, a restart or another replica that day queues nothing (the controller keeps the day it saw queued in process, only to skip the store write). `factory improve` queues one run now through the same enqueue, key `improve:<project key>:manual:<ISO time>`: never the day's slot, not gated. No config key sets the time or the window.
  - **Window.** Fixed at enqueue in the run's input (`input.improve`), so a retry reports the same runs: the daily run of day D covers the previous full UTC day, [D−1 00:00, D 00:00); a manual run the 24 hours before it was queued. A run finished outside the window is not counted.
  - **System work item.** The runs table needs a work item, so each project has one system work item that carries its improve runs: source `local`, id `system:improve:<project key>`, made on first use, `NEW` with `blocked_on: upstream`, `blocked_reason: system_item` for good (a blocked reason, not a new stage). Nothing triages, implements or releases it; the controller acknowledges an improve run with no field change (`improve_done` / `improve_failed`).
  - **Claim and work.** Workers claim `improve` through the same `claimRun` as every kind, ranked after the listed kinds. It needs no sandbox: the worker reads the window's finished runs, groups the failed ones (improve runs left out) by error code and normalized detail (lower case, digit runs → `#`, hex ids of 7+ characters → `<id>`, whitespace collapsed, 200 characters), and stores one report per run (keyed by run, so a retry keeps the first). Groups of two or more runs come first by size, then by key; one-run patterns by key; run IDs in finish order. The same input runs give an identical grouping. The outcome names the report and its counts.
  - **Tables.** `controller_improve_reports` (window, `failure_groups` and `patterns` as JSON: run IDs and item IDs, never raw detail) and `controller_filed_patterns` (one row per pattern filed from a report, unique per project and pattern key): SQLite migration 31. Phase 3 (#308) writes `controller_filed_patterns`.
  - **Not yet.** Opening PRs or fixing the failures. Solo and enterprise are the same: one system item per project on the shared store.
- Behavior changes only through what agents read or may do: all files in the factory-definition repo.
- Additive learnings: read into every prompt (above); writing them automatically is still planned, not built. Prompt / gate / permission / tool changes: improver PR with replay evidence → human.
- Recurring failure class → hard fix (gate, permission), not a softer prompt.
- Progressive disclosure: index → body → references; `CapabilitySearch` (BM25, vector, hybrid) finds skills/tools/MCP. Finding ≠ permission.
  - **Doc index in the prompt (new decision, 2026-11-01):** the worker takes an optional `CapabilitySearch` and appends the top 8 results to the triage, implement and review prompts as a short index (path, name, ≤200-character snippet); agents read full text on demand with `Read`, which they already have. The index grants nothing: tools, `deny_paths` and grants are unchanged. BM25 comes first (`bm25` plugin: `*.md` under `docs/` and `skills/`, headings boosted, rebuilt from files when they change, per process); vector and hybrid stay later. `Capability.kind` gains `doc` for markdown docs (`skill` for `skills/`). The checked-in config selects `bm25` (2026-11-07), so every triage, implement and review prompt gets the index; `list-all`, which finds nothing, is the fallback.

## History

- **Learned rules and verdicts through the real CLIs** (decision changed 2026-11-12). Before: `LearnedRules` read `TacitLedger.list("promoted")` (`tacit list --agent software-factory --state promoted --json`), a rule's text was the owner's wording stored with its promote verdict, else the entry's `rule_draft`, and a rule whose `scope` tags did not include `software` (`RUN_DOMAIN`) was left out; a verdict sent `{ id, verdict, reason, by, text? }` as JSON on stdin to `evolve verdict --agent software-factory`, and the ledger kept its draft beside the owner's wording. The real CLIs have neither form, so no rule was read and every verdict failed.
- **Learned rules and pushback signals** (decision changed 2026-11-12, issue #571). Before: a rule promoted with the terminal `/evolve` was written only to the owner's own agent instruction files, so no run's prompt saw it, and promoting rules from the factory was "still later"; the improve run grouped failed runs only, so the owner's pushbacks carried no weight in a report.
- **Scorer grades and the 24-hour failure count** (decision changed 2026-11-11, issue #514). Before: no run was graded, so the factory had no quality signal on its own output; the trigger counted unreviewed failures per run kind, with no 24-hour window. Before #508 the improve run started only on its daily schedule (and by `factory improve`), so a burst of failures waited up to a day for a report.
- **Per-project improve reports and the learner** (decision changed 2026-11-11, issue #497). Before: an improve run's report grouped the failed runs of every project in its window, and no step acted on a group, so a project that kept failing with `diff_too_large` kept the same `max_diff_lines`.
