# 7. Self-improvement

- **`improver.daily_trigger` off stops the controller's daily improve run (changed 2026-11-24, tk_33c95362 phase 1; see History).** Why: the owner wants it shown and owned as a schedule. Boolean, unset is on; failure trigger stays.
- **A proposed skill draft and its verdict also go to the owner's tacit ledger when it is on (decided 2026-11-24, local-task-tk_90fd7e80 phase 4; a new decision, none replaced).** Only with `enabled` true, after the store holds it: a draft stored `proposed` goes to `changeProposal` once; a hold, reject or promote the store accepts on a proposed draft goes to `verdictRecord`. A failure is only logged. The improve run and the skill verdict route pass the ledger (docs/plugins/tacit-ledger.md).
- **The improve run drafts a skill change when its eval score drops or stalls, measures it in scratch and stores it for a verdict (decision changed 2026-11-24, local-task-tk_90fd7e80 phase 2; current; replaces "Nothing reads them yet" in the entry below, see History).** `improveSkills` (`src/core/skill-improve.ts`, re-exported by `src/core/improver.ts`) runs in every improve run after `learnFromReport`, with the run's metered `plugins.llm` provider, the injected Clock and `WorkerDeps.skillImprove`, which the composition root builds in `src/skill-evals.ts` (`skillImproveWiring`).
  - **Off.** With `capabilities.skill_folders` absent or empty, or no model: no draft, no question; startup does not fail.
  - **Seeded skills.** Suites whose `skill_ref` folder is inside a skill folder. **Measured runs**: finished, with a pass rate, not a scratch run (`skill_version` `draft:<id>`), newest first.
  - **Trigger.** The newest measured run is below `skill_improve_target` and either more than `skill_improve_drop_margin` below the run before it (`drop`), or the newest of its last `skill_improve_stall_runs` measured runs is no more than `skill_improve_noise` above the oldest of them (`stall`). Exactly a margin is within it.
  - **One draft per skill version.** The draft's id is a hash of project, `skill_ref` and the folder's version: a later improve run for the same version finds it and drafts nothing. `skill_drafts_per_day` 0: no draft and no question. Else `takeSkillDraftSlot` takes a slot first; at the cap, no draft, and one owner question a project and UTC day (alert pattern `skill_draft_limit`, key per limit, project and day) names the value and the proposed change (`skill_drafts_per_day 3 → 4`). The run still succeeds; acting on a reply is a later phase.
  - **The draft call.** One plain `complete`, `standard`, no tools, 120 s, system prompt `prompts/skill-improve.md`; the message holds the current SKILL.md and the names of the checks the newest measured run failed, never a replay output, transcript, judge reason or run ID. Its answer is the whole new SKILL.md. Its input plus output tokens are the draft's `tokens`; past `skill_draft_token_budget` the draft is stored `held` (`reason: token_budget`), not measured, with one owner question a day the same way. The text passes the G5 scan (`log`) first: flagged, `tried` with reason `withheld` and the rules only.
  - **Scratch measurement.** The skill's suite replayed with the draft text as the skill's system prompt (`scratchRunFor`), judged with `prompts/skill-judge.md`, stored as an eval run with its figures under `skill_version` `draft:<id>`, on the newest measured run's model class. No file under a skill folder changes.
  - **Proposed or tried.** A scratch pass rate more than `skill_improve_noise` above the current version's latest run of the same model class: `proposed`. Otherwise `tried`, `reason` one of `failed_call`, `failed_replay` (it threw, ran nothing or has no pass rate), `no_baseline`, `no_gain`. The detail holds scores, check names, the draft text and the reason; never a transcript.
  - **Verdicts (changed 2026-11-24, phase 3; replaces "nothing calls them yet", see History).** `promoteSkillDraft`, `holdSkillDraft` and `rejectSkillDraft`; the Rules page and `factory improve skill <id> <verdict>` call them through one owner-only function (09-dashboard-rules-waiting.md). Promote (from proposed or held) refuses a skill outside the skill folders before anything is written; else stores the old SKILL.md text in the detail (a conditional update on the state), writes the draft to SKILL.md, re-runs the suite (an ordinary stored eval run) and sets the draft `promoted` with that run. Hold: proposed → held; reject: proposed or held → rejected. Each is conditional on the state: a second verdict changes nothing. Nothing promotes on its own.
  - **Solo and enterprise.** The same: the drafts, the day slots and the questions are store rows; no new key.
- **Skill improvement has six config-file keys and a draft store (decided 2026-11-24, local-task-tk_90fd7e80 phase 1; a new decision, none replaced).** Keys (`src/core/skill-improve-config.ts`, re-exported by `src/core/config.ts`; top-level, not settable): `skill_improve_drop_margin` (0 to 1, default 0.05: a score drop past it marks a skill worse), `skill_improve_stall_runs` (integer ≥ 1, default 3: runs with no gain before a skill counts as stalled), `skill_improve_target` (0 to 1, default 0.9: the pass rate that needs no draft), `skill_improve_noise` (0 to 1, default 0.02: changes within it are neither gain nor drop), `skill_drafts_per_day` (integer ≥ 0, default 3; 0 means no drafts) and `skill_draft_token_budget` (integer ≥ 1, default 50000 tokens a draft may spend). Why: drafting a skill change spends model tokens on the owner's account, so each project's daily drafts and each draft's spend are capped, and a score change only counts past the noise and drop margins, so the factory drafts for real regressions and stalls, not for jitter. Absent, a key takes its default; a wrong value fails the config load naming the key. Skill folders are `capabilities.skill_folders`, no new key. Store: `controller_skill_drafts` (states tried, proposed, promoted, rejected, held; any other refused; `detail` is JSON, never a transcript) and `controller_skill_draft_days` (one row per project and UTC day; `takeSkillDraftSlot` raises it only below the cap in one conditional statement, so replicas cannot pass it), migration `20261123T1300-controller-skill-improve`. The improve run reads and writes them since phase 2 (the entry above).
- **Entity proposals for the owner's verdict (decision changed 2026-11-21, #496; current; replaces the prompt-change plan and the daily run's "Not yet", see History).** Settings: `improver.max_proposals` (default 1; the rest `proposal_cap`); `improver.schedule` (`off` default; `daily`, this repo's; `every_run`); `distill.min_cases` (default 2), below it: `watching`. Details: 07-improve-report.md.
- **Filed patterns are ranked and capped at 2 new items a run; a rejected one waits for doubled evidence; `factory stats` counts filings per kind (decision changed 2026-11-23, issue #775; current; changes "Caps" and "Matching" under "File each recurring failure pattern" below, see History).**
  - **Rank, then cap.** `fileReport` takes the report's failure groups and hot files together, largest evidence first (`evidenceOf`: its runs, plus its held items for a hot file; report order on a tie), then files at most `MAX_NEW_ITEMS` = **2** new items a run. The rest are `skipped` with `issue_cap` and their `count` (the evidence). Comments keep `MAX_FILED_ISSUES` = 3 (`comment_cap`). A constant, not a setting (decision 1 of #775). The estimate is the evidence count, not item-hours held (decision 3).
  - **A rejected filing.** The claim stores the pattern's evidence at filing (`controller_filed_patterns.evidence`). A pattern whose filed item closed as `rejected` in the last 30 days is filed again only when its evidence is at least double the stored one; otherwise `skipped: recently_closed`, as before. After 30 days it is filed again whatever its evidence. Any other close reason keeps the 30-day rule. A row filed before the column (evidence null) waits the 30 days (decision 2).
  - **Stats.** `factory stats` prints filed, done and rejected per kind over the last 30 days (`collectFilings`, `src/core/stats.ts`): `hotspot` and `failure pattern` from the filed patterns of every project claimed in the window (`listFiledPatternsWithin`, the store clock's window), `proposal` from promoted proposals with a filed item decided in it. Done and rejected read each filed item's `close_reason` now. A refiled pattern's row holds only its latest filing, so an earlier filing of the same key is not counted. The base branch's red-main fix item ("Fix the base branch at <sha>", the outbound `file_fix_item`) is not filed through `controller_filed_patterns`, so it is not counted.
  - **Store.** Nullable `evidence` (integer) on `controller_filed_patterns`, the timestamped migration `src/controller/migrations/20261122T1201-controller-filed-pattern-evidence`; no backfill. Solo and enterprise are the same: one store, no config key.
  - **Not yet (follow-ups).** The expected effect in the filed body and its outcome check; stopping a kind whose 30-day rejection share passes 40% over at least 5 closed; per-kind counts and a "not filed, below the cap" label on the improve report (its web label for `issue_cap` still reads "daily limit of new issues").
- **One caller files a pattern; a hot file with an open item of its title is skipped (decision changed 2026-11-18; current; changes "Pattern key and marker" below, see History).** `fileGroup` files only when `takeFiledPattern` says `taken`: the one call that inserted, replaced or restarted the claim. A claim with no item under 10 minutes old (`FILING_WAIT_MS`) is `skipped: in_flight`, no source call. A `hotspot` row is `skipped: open_item` while the store holds an item not `CLOSED` titled "Reduce conflicts on <file>"; GitHub is not searched by title.
- **A failure pattern is filed at 3 runs on 2 items, outside model-stall and network pauses (decision changed 2026-11-18; current; changes "File each recurring failure pattern" below, see History).** After the unchanged host-sleep check, `fileReport` leaves out a group's failed runs that finished in a `model_stall` or `network` pause (start inclusive, end exclusive, an open pause included): none left is `skipped` with `pause`; under 3 runs or 2 items left, no filing, report only. Constants, no config key; `hotspot` rows keep their own rule. The store appends each ended probe pause to `controller_pause_history` (name, since row, end; unique, never pruned), read through `pauseAt` by every replica.
- **Scorer grades for succeeded runs, and an improve run as soon as failures pile up in 24 hours (decision changed 2026-11-11, issue #514; changes "Trigger rule" and "Why K = 10" under "An improve run when failures pile up" below, and replaces the schedule-only start of the daily improve run, see History).**
  - **Grades.** Each succeeded agent run (triage, implement, review, resolve) is graded before its outcome is stored: `gradeRun` (`src/worker/runs/improve/improve.run.ts`, called from the worker's run step) asks every judge of the scorer (`src/core/scorer.ts`, the `Judge` interface) and stores their grades in the outcome's data as `grades: [{ judge, score, reason }]`, score 1 to 5. Failed runs and runs with no agent (improve, update, merge-check) get none. A judge that fails, refuses, times out (60 s) or answers out of schema gives no grade; grading never fails a run. The usage of each judge call counts toward the run's.
  - **Independent judges.** A judge is never the call that produced the run: it is its own plain `LLMProvider.complete` (no tools, no session, no sandbox, no agent runner), on another model class than the producer's (`judgeClass`: `strong` for a `cheap` or `standard` run, `standard` for a `strong` one), with its own system prompt, and it reads only the item's title and the run's stored output (its data as JSON, cut to 6000 characters), never the producer's prompt or transcript. So a grade does not carry the producing call's bias. The output passes the G5 scan (`log`) before a judge reads it, and each grade's reason before it is kept; a flagged one is left out.
  - **The judges' prompt.** The `## Grading a run` section of `prompts/improve.md` is the judges' system prompt and names the output format; the text before it stays the draft call's system prompt, byte for byte as before (`improvePrompts`).
  - **Scorers off.** With no LLMProvider in the worker (`WorkerDeps.llm` absent), or no `## Grading a run` section, the scorer is `NO_SCORER`: no judge, no grade, no model call, nothing logged at startup. Compose passes the `plugins.llm` chain, and the checked-in default selects one, so a factory with a model has grades.
  - **Trigger by count in 24 hours.** `improveTriggerDue` (`src/core/improver.ts`) is now due when **10** failed runs of the project, of any run kind but `improve`, finished in the last **24 hours** (`TRIGGER_FAILURES`, `TRIGGER_WINDOW_MS`) and since its last improve run was queued; the 3-day age rule is unchanged. Why 24 hours: the daily run's window, so a burst that the next daily run would only see tomorrow gets its report today. Constants, not settings.
  - **One run across replicas, in the store.** The controller's improve step calls `triggerImprove` each tick, as before. Its dedupe is store state, not process memory: the key `improve:<project key>:trigger:<last improve run id, or none>` is the same for every replica that sees the same failures, and `enqueueRun`'s conditional insert on that unique key keeps one run. `factory improve`, Run now and the trigger all queue through `enqueueImprove`, so a manual run writes the same system work item and run shape as a triggered one. No schema change: the run's idempotency key is the stored dedupe, and grades live in the outcome's JSON.
  - **Solo and enterprise.** The same code: one store, the worker's own `plugins.llm` chain, no config key.
- **Improve reports are per project, and the daily run learns a tighter `max_diff_lines` (decision changed 2026-11-11, issue #497; changes "Claim and work" under the daily improve run below, see History).**
  - **Per project.** `runImprove` counts only the failed runs whose work item is in the improve run's project (decision 3 of #497), the same filter the trigger rule uses (one item read per item in the window). Two projects on one store get two reports that share no run.
  - **The learner.** After the daily run stores its report, `learnFromReport` (`src/core/learned-settings.ts`, called from `src/worker/runs/improve/improve.run.ts`) reads the report's `diff_too_large` runs. With 3 or more it writes one learned `max_diff_lines` for the project and window: 80% of the value in force, rounded down, never below 1, only when tighter. One audit row names the evidence run IDs. A manual or triggered run learns nothing (decision 2 of #497). The store, the conditional write, the check in `settingsFor` and the reset are in 08-settings.md.
  - **Solo and enterprise.** The same: the learned value and its audit are store rows, so every worker and controller on the store reads it at its next settings refresh; a retry or a second worker on the same window writes nothing.
- **A filed pattern holds its items for a person and records whether its fix held (decision changed 2026-11-11, issue #511; changes "When the fix item merges" under the fix-spec entry and "Record" under filing below).** Before, a filed pattern's items kept running after it was filed until the alarm step's re-raise held them, after `alarm_repeat_count` new failures, as `blocked_on: upstream`; and nothing checked whether a merged fix held, so `controller_filed_patterns` had no outcome.
  - **Hold.** In the alarm step (every controller poll, design 05-alarms), not the improve run, which is daily or triggered and would hold late: the first failed run whose pattern key matches a filed pattern with an open item holds that run's item, `blocked_on: human`, `blocked_reason: recurring_failure`, the pattern key in the state change detail. A conditional transition, once per run. The release when the fix merges is unchanged.
  - **Outcome.** Each controller tick the improve unit (`settleOutcomes`, `src/core/improver.ts`) reads the project's filed patterns with an item and no outcome (`listFiledPatternsWithoutOutcome`). One whose fix item closed as `completed` at least **7 days** ago (`OUTCOME_WAIT_MS`; the close time is the state change that set `CLOSED`) gets `regressed` when a failed run of its pattern finished in the 7 days after the close, else `holds`, and `outcome_at`. The write is `setFiledPatternOutcome`, a conditional update `WHERE outcome IS NULL`, so a retry or a second replica writes once. An item still open, not in the store, or closed as `failed`, `rejected`, `duplicate` or `wont_do` gets no outcome. A refiled pattern (its item closed over 30 days ago, or rejected and its evidence doubled) starts again with no outcome.
  - **Why 7 days.** Long enough for a daily improve run and a week of ordinary traffic to hit the pattern again, short enough to judge a fix while it is still fresh. A constant, not a setting.
  - **Store.** Nullable `outcome` and `outcome_at` on `controller_filed_patterns`, the timestamped migration `src/controller/migrations/20261111T1500-controller-filed-pattern-outcome` (no numbered step: the numbered list is frozen). Rows filed before keep no outcome: no backfill. The stored report is not rewritten, and the status page does not show outcomes yet (a follow-up). Solo and enterprise are the same: one store, no config key.
- **A fix spec runs unless the draft needs a person or touches a gate path (decision changed 2026-11-10, issue #504; changes "The factory triages them" below).** The draft gains `needs_person` (the model's answer, required in `IMPROVE_SCHEMA` and `prompts/improve.md`: true when no change to the repository can fix it, such as an owner decision, a credential, a quota or an outside service). Filing then takes one of two paths:
  - **No person.** A group whose draft is not `needs_person` and whose fix touches no `GATE_PATHS` (or that has no draft) is filed as one fix item, as before (one per pattern: the `controller_filed_patterns` claim, so two replicas file once). When its triage run succeeds, the controller approves its spec without a person, whatever the tier or mode (reason `fix_spec_approved`, the pattern key in the detail, the spec comment says so), and it is implemented and reviewed like any approved item. The fix item is found from the marker in its filed body (`markerKey`), or, after a spec revision replaced the body, from its earlier `fix_spec_approved` change; the pattern's stored item (`controller_filed_patterns.filed_ref`) must be this item, so an issue that copies a marker is not one. Its merge follows the usual rules: a change whose spec touches the gate list waits for a person's merge, auto merge refuses it (03-risk), and a GitHub PR always waits for a person; the spec comment names the gate path.
  - **A person.** A group whose draft says `needs_person`, or whose fix touches the gate list (`touches_prompts_or_gate`, withheld drafts included), is not filed: no item, no triage or fix run. Needs you shows it as an alert (pattern `repeated_error`, key `needs_person:<key>`, detail "Needs a person: …" with the draft's cause, scanned as UI text), stored once a day per pattern; the group's filing is `skipped: needs_person`.
  - When the fix item merges, the items its pattern held (design 05-alarms; from its first matching run since 2026-11-11, see the first entry) return to the queue for retry. Solo and enterprise use the same path; the fix runs on the same store. Out of scope: an automatic merge of a fix touching a gate path, prompt, permission or tool, and automatic fixes for needs-person drafts.
- **File each recurring failure pattern (new decision, 2026-11-08, issue #308; phase 3 of the self-improvement plan).** After a succeeded improve run, before acknowledging it, the controller files the report's groups of two or more runs (`fileReport`, `src/core/improver.ts`). One-run patterns stay in the report only, never filed or commented.
  - **Where.** Through the first source in `plugins.source` order that has `SourceAdapter.fileIssue`. Solo default: `local` files a local work item (source id `local-filed-<hash of the marker>`, requester `system:improver`), no external account. Enterprise: `github-issues` files a GitHub issue. No source that can file: each group is `skipped: no_source`.
  - **The factory triages them (decision changed 2026-11-09, owner: "I want this to be automatically triaged"; since 2026-11-10 only drafts that need no person and touch no gate path are filed, and their spec is approved without a person, see the first entry).** A filed item is triaged with no person starting it. `github-issues` files the issue with the intake label (`github.intake_label`), so the next poll takes it in like any labelled issue; its requester is the bot's account (`submit_work` is open to every account no grant denies, so no permission changes). `local` queues the item's triage run when it creates it, as `factory task create` does (key `local:<source id>:triage`), requester `system:improver`. The human-merge rule is kept by the gates, not by withholding triage (see "No person" above). The body lists the group's runs and items, the normalized detail, the draft (marked unverified), and that the factory triages, implements and reviews it without a person, a gate-path change still waiting for a person's merge.
  - **Pattern key and marker.** The key is a cyrb53 of the error code and normalized detail. One caller takes each filing in `controller_filed_patterns` (unique per project and key) before the source call; the body carries `<!-- factory:improve:<key>:<claiming report id> -->`, looked up by the source before every create (`github-issues`: the newest 300 intake-labelled issues; `local`: its derived source id). A claim left with no item is taken up again under its marker after the 10-minute wait.
  - **Matching.** A group whose key has a filed item that is open (or not in the store: filed, nobody started it) gets one comment naming its runs not linked there yet, marker `factory:improve-comment:<key>:<report id>`; no new run: `linked`, nothing posted. A run is linked when an earlier report filed or commented it on that item; the reports since the window's start cover every run of the window. An item closed in the last 30 days (by its `updated_at`) also matches: `skipped: recently_closed`, nothing sent; since 2026-11-23 one closed as `rejected` stops matching once the pattern's evidence doubles (see the first entry). An item closed longer ago does not: the pattern is filed again and the claim moves to the new report. A comment on an item in the store goes through its thread (and the outbox); on one nobody started, straight to its source, once per marker.
  - **Caps.** At most `MAX_NEW_ITEMS` = 2 new items (since 2026-11-23, groups and hot files ranked together by evidence, see the first entry) and `MAX_FILED_ISSUES` = 3 comments per run; the rest are `skipped` with `issue_cap` or `comment_cap`. A constant like `MAX_DRAFT_CALLS`, not a config key: one number solo and enterprise share; comments are writes through the shared account.
  - **Egress.** Every body and comment passes the G5 scan (`comment` channel) before it is sent. A flagged one is not sent and nothing is claimed; the group is recorded `withheld` with its rules only.
  - **Record.** Each group's outcome is stored on it in the report (`filing`: `filed`, `commented` with the new run IDs, `linked`, `skipped` with its reason, `withheld` with its rules, `failed` when the source call threw). No schema step: `controller_filed_patterns` (migration 31) as it is. A fault is logged and the run acknowledged anyway: a sync plugin's outage never holds local work.
- **Draft cause and fix per failure group (new decision, 2026-11-07, issue #307; phase 2 of the self-improvement plan).** The improve run now makes one plain model call per group of two or more runs. A one-run pattern gets none.
  - **Call.** `LLMProvider.complete` with only system (`prompts/improve.md`), one user message, `max_tokens`, `output_schema` (`cause`, `fix`, `touches`), `model_class: standard`, `data_env: test` and the run's signal, bounded by a 120 s timeout. No tools, no tool grants, no sandbox, no agent runner. Its usage counts toward the run's. Solo: the checked-in `plugins.llm` default, no new setup. Enterprise: the same named chain; no shared budget yet (a follow-up). No new config key.
  - **Cap.** At most 5 calls per run (`MAX_DRAFT_CALLS`), largest groups first; each group past the cap is marked `draft: { status: skipped, reason: call_cap }`, so the report lists what it skipped. A constant, not a setting: one number solo and enterprise share until budgets exist.
  - **Tails.** For each called group, the transcript tails (last 4 000 bytes of `transcripts/<item>/<run>.json`) of its 3 latest runs pass the G5 scan on the `log` channel before the call. A flagged tail is left out of the prompt and recorded `withheld` with its rules, never its text. A run with no stored transcript (none, or one the scan kept out of storage) is recorded `missing`.
  - **Output.** Checked against the schema. Invalid output, a refusal, an error or a max-tokens stop marks the group's draft `failed` with that reason; the run still completes with its report. A valid draft passes the G5 scan (`log`) before it is stored; a flagged one is stored `withheld` with its rules only.
  - **`touches_prompts_or_gate`.** Set by the factory, never the model: true when a path in `touches` is on `GATE_PATHS` (`src/core/improver.ts`), the owner-only list: `prompts/`, `src/impl/broker/`, `src/impl/egress/`, `src/impl/secrets/`, `src/impl/sandbox/`, `src/impl/auth/`, `src/core/checks.ts`, `src/core/policy.ts`, `.claude/`, `factory.config.json`. One constant, so the merge check can reuse it.
  - **Storage.** Drafts and tail markers live on each group in the existing `failure_groups` JSON; no schema step. A retry of a run whose report exists returns it with no model call.
  - **Wiring.** `WorkerDeps.llm` is optional; compose always passes the `plugins.llm` chain. Without it (or without the improve prompt) the run is phase 1's: groups carry no draft.
- **Daily improve run and its report (decision 2026-11-07, issue #306; phase 1 of the self-improvement plan).** A new run kind, `improve`, looks back at failed runs once a day. It runs no agent.
  - **Schedule.** With `improver.daily_trigger` on, each tick queues the UTC day's run, key `improve:<project key>:daily:<YYYY-MM-DD>`; an `improve` schedule uses it too. `factory improve` queues one now (`:manual:<ISO time>`), not gated. No key sets time or window.
  - **Window.** Fixed at enqueue in the run's input (`input.improve`), so a retry reports the same runs: the daily run of day D covers the previous full UTC day, [D−1 00:00, D 00:00); a manual run the 24 hours before it was queued. A run finished outside the window is not counted.
  - **System work item.** The runs table needs a work item, so each project has one system work item that carries its improve runs: source `local`, id `system:improve:<project key>`, made on first use, `NEW` with `blocked_on: upstream`, `blocked_reason: system_item` for good (a blocked reason, not a new stage). Nothing triages, implements or releases it; the controller acknowledges an improve run with no field change (`improve_done` / `improve_failed`).
  - **Claim and work.** Workers claim `improve` through the same `claimRun` as every kind, ranked after the listed kinds. It needs no sandbox: the worker reads the window's finished runs, groups the failed ones (improve runs left out) by error code and normalized detail (lower case, digit runs → `#`, hex ids of 7+ characters → `<id>`, whitespace collapsed, 200 characters), and stores one report per run (keyed by run, so a retry keeps the first). Groups of two or more runs come first by size, then by key; one-run patterns by key; run IDs in finish order. The same input runs give an identical grouping. The outcome names the report and its counts.
  - **Tables.** `controller_improve_reports` (window, `failure_groups` and `patterns` as JSON: run IDs and item IDs, never raw detail) and `controller_filed_patterns` (one row per pattern filed from a report, unique per project and pattern key): SQLite migration 31. Phase 3 (#308) writes `controller_filed_patterns`.
  - **Solo and enterprise.** One system item per project on the shared store.
