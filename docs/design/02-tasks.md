# 2. Plain tasks

- **Calendar events leave the Tasks views (decision changed 2026-11-14; current; replaces "Today and Upcoming list calendar events beside the tasks", from the calendar views decision below, see History).** The decision that changed: **Inbox, Today, Upcoming, List and Done show tasks only; the events, with the stale-sync notice, are on the Calendar page (design 09-dashboard-app).** `GET /api/v1/tasks` is unchanged and still places events in the Today and Upcoming rows and the timeline; the Tasks page drops them, the Calendar page reads them from the same response.
- **A task can be in task projects: `+slug` in quick add and task edit, `factory project …`, and `task list`'s projects column (decision changed 2026-11-14, phase 2 of 3 of local-d91d27e8; current; replaces "a task belongs to no project", from the #606 plain tasks decision below, see History).** The decision that changed: **a plain task may belong to one or more named task projects, which the owner creates, lists, renames, archives, restores and deletes, and lists tasks by.** A task project is not a repository: `src/core/project.ts` is the repository key, and the settings commands' `--project <owner/name>` still names a repository.
  - **Store.** Phase 1 added `controller_projects` and `controller_task_projects`, the name and slug rules (`projectName`, `projectSlug` in `src/core/projects.ts`) and `ProjectStore` (`src/impl/store/sql/projects.ts`). This phase adds no table and no migration, and backfills nothing: an existing task is in no project. `addTask`, `addSubTask` and `updateTask` take `projects`, the slugs, and link the task to each in the same transaction as the row (`linkTaskProjects`); an unknown or archived project throws `ProjectRefused` inside it, so no task row, link or edit is written. Callers that pass no projects are unchanged. `getProjectBySlug` and `listTaskProjectSlugs` (one read for a whole list, active projects only) are the reads.
  - **Refusals.** `no project "<slug>"` for an unknown slug and `project "<slug>" is archived; restore it first` for an archived one (`projectRefusal` in `src/core/tasks.ts`), on the CLI (exit 1), in chat and on the dashboard's add, edit and sub-task routes (400).
  - **Quick add and edit.** `+slug` reads the word after `+` through `projectSlug`, so `+Home-Repairs` names `home-repairs`; several may be given, each once. A `+` with no letter or digit after it is refused with a reason and nothing stored. In `task edit`, `+slug` adds the task to that project with the edit; it never takes the task out of one.
  - **Commands.** Seven entries of the command table, each for anyone who may submit work (`submit_work`), so each is also a chat command: `project create <name>`, `project list [--archived]`, `project rename <slug> <name>`, `project archive <slug>`, `project restore <slug>`, `project delete <slug>` and `task project <task_id> +<slug>|-<slug>` (add, or take out). A slug as typed is read through `projectSlug`. `task list` prints a projects column after the list column, `-` or `+a,+b` with the slugs sorted, and `task list --project <project_slug>` lists only the open tasks in that project; an unknown name exits 1 with `no project "<name>"`, an archived one with the archived refusal. Chat `list` takes no `--project`.
  - **`#list` removal plan.** `#label` keeps working in this phase, beside `+slug`: quick add still stores it, `task list` still prints its column, and the Tasks page's List tab (named Project until phase 3, design 09-dashboard-app) still groups by it. A later phase (after phase 3, the dashboard's project pages) removes `#label` from quick add, the list column and the Project tab, once the owner has moved their labels to projects; that phase records the removal here and keeps the `list` column's stored values readable until it is dropped.
  - **Not part of this decision.** Project pages, project filters and a projects column on the dashboard (phase 3), editing project names or slugs on the dashboard, `--project` or `+slug` in chat `list`, and removing `#label`.
  - Tests: `tests/quick-add.test.ts`, `tests/projects.test.ts` (CLI), `tests/store-contract.test.ts`, `tests/tasks-api.test.ts`, `tests/command-table.test.ts`, `tests/tasks.test.ts` and `tests/task-edit.test.ts`.

- **The Tasks page quick-add field adds on the owner's chosen key: Enter or ⌘Enter (decision changed 2026-11-14; current; replaces "Enter adds the task", from the dashboard quick-add form of the plain tasks decision below, see History).** The decision that changed: **the key that adds a task from the Tasks page quick-add field is the owner's `tasks_add_key` setting, `enter` (the default, as before) or `cmd-enter`.**
  - With `cmd-enter`, ⌘Enter (Meta only: no Ctrl, Alt or Shift) adds the task and plain Enter adds nothing (owner answer 2). The Add button adds the task under both choices, and a refused add still shows its reason beside the field and keeps the words.
  - `tasks_add_key` is a dashboard setting: its descriptor is `src/runtime/settings/tasks-add-key.setting.ts` (choices `TASKS_ADD_KEYS`), it is listed in `docs/settings.md`, and only `GET /api/v1/tasks` reads it, as `add_key`: the stored global override when it is one of the choices, else `enter`. The page reads no config file. It is not in `SETTABLE_KEYS` (src/core/settings.ts), so the resolver does not read it; `tests/settings-catalog.test.ts` names it among the dashboard keys.
  - The field's placeholder names the submit key ("…, then Enter" or "…, then ⌘Enter") and its `aria-keyshortcuts` says it, so the field keeps its size and layout under both choices. The shortcuts help keeps `q` (focus the field). Key matching is `isQuickAddSubmit` in `web/src/keys.ts`.
  - The desktop quick-add box and its global shortcut are unchanged (owner answer 3). Tests: `tests/ui-tasks-page.test.tsx` (both choices), `tests/tasks-api.test.ts` (`add_key` in the read), `tests/ui-shortcuts.test.tsx` (the key match), `tests/settings-catalog.test.ts`.
- **The Tasks page has a Done tab: the tasks done in the last 30 days, each with a Reopen button (decision changed 2026-11-14; current; extends the 2026-11-13 undo a completion decision below, which it does not replace; replaces "the Tasks page shows open tasks only, so a done task leaves every view", from the #607 date views decision below, see History).** The decision that changed: **the owner can see a done task and when it was done on the Tasks page, and reopen it from there**, not only through ⌘Z for completions made in the same page session.
  - **Tab.** A fifth tab, Done, after Project in the Task view control (owner answer 1). If the combined view of tasks and work (wi_7458) lands, the tab moves into it as its done section; no second combined view is built here. One flat list across all lists, each row with its list label (`#list`, or "No list"), its title and the date and time it was done, in the `YYYY-MM-DD HH:MM` form the page uses for due dates, in the viewer's time zone (owner answer 3). No counts, search or filters; calendar events are not shown.
  - **Window.** The last 30 days first (`DONE_WINDOW_DAYS`, `doneWindow` in `src/core/tasks.ts`, against the server's Clock); Show older loads the 30 days before the oldest row shown, or before the window's start when it showed none (owner answer 2). Show older is hidden when the response says no task was done before the window. No limit inside a window: one owner's done tasks of 30 days are a small read.
  - **Store.** `listDoneTasks(window)` on `TaskStore`, implemented in `src/impl/store/sql/tasks.ts` (SQLite) and delegated by the SQL `FactoryStore`: the tasks with `from <= done_at < before` (no upper bound on the first read), most recently done first (`done_at` descending, then ID), and `older`, whether a task was done before `from`. Read-only; no schema change, no migration, no backfill: old done tasks show as they are.
  - **Route.** `GET /api/v1/tasks/done` (`readDoneTasks` in `src/ui/tasks-api.ts`, wired in `src/ui/server.ts`), with `?before=<ISO time>` for Show older (400 when it is not a time): `{ as_of, tasks, older, next_before }`, titles through the Withholder. It reads the stored copy only, writes nothing and calls no source. The same path's POST still completes a task.
  - **Reopen.** Each row's Reopen posts the existing `POST /api/v1/tasks/reopen` `{ id }` (the store's `reopenTask`); there is no second reopen path. The recurring rule is the undo decision's: an open next occurrence is removed (`removed_next`); a done one answers 409 with nothing written, and the page shows the refusal above the Done list. On success the tasks are reloaded, so the row leaves Done and shows open again.
  - **Freshness.** The Done read's query key starts with the tasks' key (`useDoneTasks` in `web/src/api.ts`), so every row action that reloads the tasks (a checkbox completion, a reopen, ⌘Z) reloads Done too: a task completed on the page shows in Done once its route answers, with no page reload. The Done read is not polled.
  - **Not part of this decision.** Reopening a closed work item, redo, editing, deleting, scheduling or building from the Done tab, the CLI's history output, and the MySQL store (removed 2026-11-12).
  - Tests: `tests/task-done-view.test.ts` (FakeClock: order, the 30-day window, Show older, read-only, reopen and the recurring rule), `tests/tasks-api.test.ts` and `tests/ui-tasks-page.test.tsx`.

- **A task's completion can be undone: `task reopen` and ⌘Z on the Tasks page (decision changed 2026-11-13; current; replaces "completing a task is final", from the #606 decision below, see History).** The decision that changed: **a plain task marked done can be reopened, from the CLI, chat and the dashboard, and ⌘Z on the Tasks page undoes the completions made there.** Work items are unchanged: a CLOSED work item stays final (design 04-gate-commands), and nothing here reopens one.
  - **Store.** `reopenTask(id)` on `TaskStore` (`src/core/tasks.ts`, implemented in `src/impl/store/sql/tasks.ts`), in one transaction: sets `done_at` to NULL only where it is set, and answers the stored task and whether it reopened. A task that is not done writes nothing and answers `reopened` false; an unknown ID answers `not_found`. No schema change: `done_at` and `parent_id` already exist.
  - **Recurring.** The completion inserted the next occurrence (`parent_id` this task). While that occurrence is open, the reopen deletes it in the same transaction (its sub-tasks, if any, move under the reopened task, the same series), so a later completion inserts one again. When it is done, the reopen is refused with `next_done` and nothing is written: undo that one first (owner answer 3).
  - **Commands.** `factory task reopen <task_id>` and chat `task reopen <task_id>`, an entry of the command table with the permission of `task done` (`submit_work`).
  - **Route.** `POST /api/v1/tasks/reopen` `{ id }` in `TASK_WRITES` (`src/ui/tasks-api.ts`), with the guards of `/done` in the same order (Host, Origin, `application/json`, `x-csrf-token`, body size, JSON); 503 with no commands actor, 404 for an unknown task, 409 for `next_done`, else 200 with `reopened` and `removed_next`.
  - **⌘Z.** The Tasks page keeps, in memory only, the tasks its checkboxes completed this page session (owner answer 2: a reload clears them). ⌘Z (metaKey only, no Ctrl, Alt or Shift; `isUndo` in `web/src/keys.ts`) outside a field reopens the newest one through the route, then reloads the Tasks query so the task shows open again; with none kept it does nothing and sends nothing. In an input, textarea, select or contenteditable the browser keeps its own undo. It reverses completions only, never an edit or a delete, and has no redo. A refusal shows beside the quick-add field. Listed as ⌘Z in the shortcut help.
  - **Not part of this decision.** Reopening a closed work item (owner answer 1: plain tasks only), undoing an edit or a delete, redo (⌘⇧Z), a stored undo log reaching completions from before the page session, and the merge close of linked tasks.
  - Tests: `tests/task-reopen.test.ts` (store with FakeClock, CLI), `tests/tasks-api.test.ts`, `tests/ui-shortcuts.test.tsx` and `tests/ui-tasks-page.test.tsx`.

- **A task's reminder goes out on every `notify_channels` channel, within a 5-minute poll window (decision changed 2026-11-13, refiled #598; current; replaces "the reminder is a desktop notice only, sent up to a day late", from the schedule a task decision below, see History).** The decision that changed: **a reminder reaches the owner where the other notices do (owner answer 1), and only near the task's time.**
  - **Path.** The `task-reminders` unit writes, for each due task, one outbox `notify` intent per `notify_channels` adapter that has `notifyOwner` (Slack today), through the notifications unit's `notifiers`, before its `task_reminder` write (the conditional `reminded_at` update and the desktop notice, one transaction). Each intent is keyed `notify:<task>:task:<date>T<time>:<channel>`, so a second poll or replica stores none twice, and a crash between the intents and the marker resends nothing. The line reads as a needs-you line, the task's title and `task due at HH:MM`, with no work item ID: a task is no item, so the line links no item page and a reply under it acts on no item. No provider name or API is in the unit; outbound and the adapter render and send it. Quiet hours do not hold a reminder: its time is one the owner chose.
  - **Window.** `REMINDER_LOOKBACK_MS` is 5 minutes (the poll window): a task whose time passed longer ago when a poll reads it, such as one overdue when the controller starts, gets no reminder.
  - **Known gap.** A task done in the instant between the read and the write can still get its channel intent (the marker and desktop notice are refused). Kept: the intents come first so a crash never loses a reminder.
  - Tests: `tests/task-reminders.test.ts` (FakeClock, a fake Slack adapter: one intent per channel, none on a second poll or replica, none past the window).

- **Schedule a task: a duration, today's timeline, a typed time and a reminder at the task's time (decision changed 2026-11-13, issue #598, phase 3 of 3 of #569; current; replaces "a task has a due date and an optional `HH:MM` time, no duration, no timeline and no reminder", from the #606 and #607 decisions below, see History).** The decision that changed: **a task can be placed on a day's hours and reminds the owner at its time.**
  - **Duration.** `controller_tasks.duration_minutes` (nullable): how long the task takes, 1 to 1440 minutes. None stored: the task is planned and drawn as 30 minutes (`DEFAULT_DURATION_MINUTES`, `taskDuration` in `src/core/tasks.ts`), so no row is backfilled. Quick add and the edit words read `45m`, `1h`, `1h30m` (each at most once; `0m` or more than a day is refused with a reason and nothing written), so the duration is edited from the Tasks page's row edit and from `factory task edit` with the same parser.
  - **Typed time.** Quick add reads `3pm`, `3:30pm`, `12am` (midnight) and `12pm` (noon) beside `HH:MM`; `at` is read only right before a time (`at 3pm`), and anywhere else stays a title word (`meet at home`). `13pm`, `12:61pm`, `0am` and `at 13pm` are refused with "not a time" and nothing stored.
  - **Timeline.** `GET /api/v1/tasks` adds `timeline`: today's timed tasks and timed events as blocks (`planDay`), each with its start, end, offset from midnight and length, cut at midnight; all-day events and untimed tasks are left out. The Inbox and Today tabs end with it: half-hour slots, each a drop target, with the blocks drawn over them at their time and length; events are read-only. A task row dragged onto a slot posts `POST /api/v1/tasks/schedule` `{ id, date, time }` (and an optional `duration_minutes`), which sets the due date (today), due time and duration through `updateTask`, with the guards and refusals of the other row routes (400 bad body, 404 unknown, 409 done, nothing written). From the keyboard, the row's edit takes `3pm` or `45m`. No week or month timeline, no overlap check, and calendar events are not moved.
  - **Reminder.** The `task-reminders` controller unit (`src/controller/units/task-reminders/`), each poll, reads through `listDueReminders` the open, timed tasks with no `reminded_at` whose time, in the process's time zone, has come at the tick's time (the injected Clock's) at most `REMINDER_LOOKBACK_MS` ago (the reminder decision above). For each it writes one `task_reminder`: in one transaction, the conditional update of `reminded_at` (where the task is open, unreminded and still at that date and time), then a `controller_notices` row of kind `task`, its `work_item_id` the task's ID and its wait key `task:<date>T<time>`. A second poll or replica, or a task done, deleted or moved since the read, changes no row and stores no notice. A new due date or time clears `reminded_at`, so a moved task is reminded at its new time; a recurring task's next occurrence keeps its due time and duration, starts unreminded, and its date is still counted from the old due date (owner answer 1).
  - **Desktop.** The desktop shell lists the notice through `GET /api/v1/notices` and shows "A task is due now" (no title or ID: the route carries no free text), opening the Tasks page (`desktop/electron/common/notices.js`). When the app is not running there is no OS notification there; the notice stays pending and the app shows it once on its next start. The channels are in the reminder decision above.
  - **Store.** The timestamped SQLite migration `src/controller/migrations/20261113T0900-controller-task-schedule.migration.ts` adds `duration_minutes INTEGER` and `reminded_at TEXT`, both nullable: additive, no backfill, safe to rerun; `schema/sqlite.sql` matches it.
  - Tests: `tests/quick-add.test.ts`, `tests/tasks.test.ts`, `tests/task-edit.test.ts`, `tests/tasks-api.test.ts`, `tests/task-reminders.test.ts` (FakeClock), `tests/desktop/notices.test.ts`, `tests/ui-tasks-page.test.tsx` and `tests/store-contract.test.ts`.

- **A Google call with no answer within 30 seconds fails that sync (decision changed 2026-11-12, issue #595; current; replaces "a failed read stores its error per source", which waited on a read for as long as it took, from the calendar component decision below, see History).** The decision that changed: **a calendar outage never blocks a task action, also when the provider hangs.** The `google-calendar` plugin's HTTP client (`timedFetch` in `src/calendar/plugins/google-calendar/google-calendar.plugin.ts`) aborts each call to Google, its body included, after `GOOGLE_HTTP_TIMEOUT_MS` (30 seconds, well inside the 5-minute period). The source then throws "no answer", so the sync stores the error, keeps the last events and moves on to the next source, and the controller's tick goes on to its other steps. The limit sits in the plugin's transport, not in the component's sync, because component code sets no timer (RFC 0015 §9 no-clock). Task actions never wait on the sync: they write `controller_tasks` only, and the sync's transaction starts after a read answers. Tests: `tests/calendar/calendar-outage.test.ts` (every task action while a source fails or Google hangs), the refresh token's absence from agent environments, logs and the store in `tests/calendar/google-calendar.test.ts`, and Today's and Upcoming's events on the page in `tests/ui-tasks-page.test.tsx`.

- **The Tasks page edits, completes, deletes and nests a task (decision changed 2026-11-12; current; replaces "editing and deleting a task are not part of any decision" for the dashboard, see History).** The decision that changed: **each row on the dashboard's Tasks page has the actions the CLI has, and each one calls the same store method as its CLI command, so the page and the CLI cannot diverge.**
  - **Routes.** `POST /api/v1/tasks/edit` `{ id, words }` calls `updateTask` (as `factory task edit`); `/done` `{ id }` calls `completeTask` (`task done`); `/delete` `{ id }` calls `deleteTask` (`task delete`); `/sub` `{ parent, id, words }` calls `addSubTask` (`task sub`), under a `tk_` ID the page chose, so a resend stores one sub-task. Code: `src/ui/tasks-api.ts` (`TASK_WRITES`, wired in `src/ui/server.ts`). Each is a dashboard write route with the same guards in the same order as quick add (Host, Origin, `application/json`, the per-process `x-csrf-token`, body size, JSON), then the body, and needs the commands actor (503 without one). Every refusal answers 4xx with its reason and writes nothing: 400 for a body that is not one or words the parser refuses, 404 for an unknown task or parent, 409 for a done task's edit, a delete while sub-tasks are open (their titles named) and a sub-task under a sub-task.
  - **Edit.** In place on the row, opened by `e` on the focused row; the field starts with the title. The words go through `parseQuickEdit`: the title, and the quick-add words for date and time, priority and `#project`; a field the words leave out keeps its stored value. Recurrence words are refused with a reason: the page does not edit a recurrence. Enter (or Save) saves; Esc (or Cancel) closes it with no write; the title unchanged writes nothing.
  - **Complete.** A checkbox at the start of each row (the shared `Button` with `role=checkbox`: `components/ui` has no checkbox, and no raw input is used outside it); the task leaves the views once the route answers.
  - **Delete.** "Delete" in the row's overflow menu, or Delete on the focused row, opens the shared Dialog with `danger` set; only its confirm posts. A refusal (open sub-tasks) stays in the dialog with the reason; Cancel or Esc writes nothing. The store detaches the task's done sub-tasks (above); the approver's answer was to delete them with the parent, which is a follow-up item, not a change of the store here.
  - **Sub-tasks.** "Add sub-task" in the overflow menu of a top-level task only opens a quick-add field under the row (Enter saves, Esc cancels). A sub-task shows indented right under its parent when both are in the same list, one level; one whose parent is in another list stays in place and names its parent.
  - **Keys and look.** `j`/`k` select and focus a row; `e` and Delete act on the focused row and are listed in the shortcut help. The controls are `Input`, `Button`, `Dialog` and `OverflowMenu` from `web/src/components/ui`, colours from the design tokens, and every string on the rows in `web/src/i18n/en.ts`.

- **Calendar events in Today and Upcoming, and Upcoming starts today (decision changed 2026-11-12, phase 3 of 3 of local-a3dfbb03; current; replaces "Upcoming: due in the 7 days after today" and "views of events are not part of this decision", from the date views and calendar decisions below, see History).** The decision that changed: **Today and Upcoming show the calendar events stored by the last syncs beside the tasks, and Upcoming runs from today through 7 days ahead.**
  - **Read path.** `readCalendar` (`src/calendar/calendar-read.ts`, exported by the component's `index.ts`) reads every stored event and every source's sync state (`synced_at`, and whether `error_at` is set) in two queries. It calls no source and writes no row, so a page request works the same while a source is down or rate-limited. `GET /api/v1/tasks` (`src/ui/tasks-api.ts`) reads it through the store's SQL driver, as the packs route does, and passes event titles through the Withholder like task titles.
  - **Placement.** `taskViews(open, now, events)` (`src/core/tasks.ts`, pure, no calendar import) places each event on every local day it overlaps. Each day of Today and Upcoming lists all-day events first, then timed tasks and events in time order (a task before an event at the same minute; an event that began on an earlier day counts from 00:00), then the untimed tasks in their usual order (priority, then age). An event is an entry with `kind: "event"`, its `source`, its `time` that day (null all day); the arrays keep their names (`today.due`, `upcoming[].tasks`). Today's overdue tasks stay first and are tasks only. Upcoming: today through 7 days after today, one group per day with a task or an event.
  - **Sync state.** The response's `calendar` lists each source's last sync time and whether its last sync failed. When it failed, the views keep showing the last stored events, and the Tasks page names the source with its last sync time above Today and Upcoming. The stored error text is not shown.
  - **No source.** With no `calendar` source configured the tables stay empty: Today and Upcoming show tasks only, `calendar` is `[]`, and no error shows. A source removed from config keeps its last stored rows (the sync never deletes them), so they still show until a cleanup exists.
  - **Not part of this decision.** Events in Inbox and Project, creating, editing or deleting events, linking events to tasks, items or pull requests, showing the sync error text, any provider, and reminders or due-date alerts.

- **A calendar component that syncs configured calendar sources, with no provider (new decision, 2026-11-12, phase 1 of 3 of local-a3dfbb03; current).** Until now the factory had no calendar. The decision: **the factory keeps a copy of the events of each calendar source the owner configures, synced at most once every 5 minutes per source; no provider ships in this phase, so with the default config nothing is read.**
  - **Interface.** `CalendarSource` (`src/interfaces/calendar-source.ts`), a neutral read: `events({ from, to })` answers the events that overlap the window (`id`, `title`, `starts_at`, `ends_at`, `all_day`, `updated_at`). Registered as the optional plugin kind `calendar` with no default plugin and no plugin (docs/plugins/calendar-source.md).
  - **Config.** The top-level key `calendar`, a list of plugin names, default `[]`. Checked at startup: an unknown name, a repeated one or a value that is not a list fails, naming `calendar` and the available plugins. A top-level key, not `plugins.calendar`, because several calendars are listed at once and none is a default.
  - **Component.** `src/calendar/` owns the `calendar_` tables and their SQL: `calendar_events` (one row per source name and event ID, with the time it was synced) and `calendar_sync_state` (one row per source: `next_sync_at`, `synced_at`, `error`, `error_at`), created by the timestamped migration `src/calendar/migrations/20261112T1700-calendar-events.migration.ts` (additive, no backfill: the tables start empty).
  - **Sync.** The controller unit `calendar` (`src/controller/units/calendar/`) runs each poll and calls the component, which reads the due times in one query and syncs each due source. The due time is stored, never held in memory, and claimed by a conditional write (an insert for a first sync, else an update where `next_sync_at` has passed), so every replica keeps one schedule and a source is read at most once per 5 minutes. A sync asks for one day back to 30 days ahead and replaces the source's events in one transaction. A failed read stores its error per source, keeps the last events and waits for the next due time; the next success clears it. With no source configured the step returns before any read or write. Time comes from the controller's Clock (a FakeClock in tests).
  - **Not part of this decision.** Any provider (Google, Outlook, iCal or another), views of events (dashboard, CLI, chat), creating, editing or deleting events, linking events to tasks, items or pull requests, and redacting a provider's error text.

- **Edit, delete and one level of sub-tasks (decision changed 2026-11-12; current; replaces "Editing and deleting a task are not commands yet", from the #606 decision below, see History).** The decision that changed: **a plain task can be edited with quick-add words, deleted for good, and given sub-tasks one level deep, from the CLI and chat.** Work item sub-tasks (from split specs) are a different thing and are unchanged.
  - **Commands.** `factory task edit <task_id> <words>`, `factory task delete <task_id>` and `factory task sub <parent_id> <words>`, entries of the command table with permission `submit_work`, so they also exist in chat as `task edit`, `task delete` and `task sub`.
  - **Edit.** `parseQuickEdit` (`src/core/quick-add.ts`) reads the same words as quick-add, with the same refusals, and names only the fields they give; words with no title keep the title, and no words at all are refused. The store sets only those fields, conditional on `done_at` unset, as quick-add would store them: a time alone on an undated task makes it due today, and a recurrence with no due date (stored or given) is refused. Refused with nothing written: an unknown task, a done task, words the parser refuses.
  - **Delete.** A hard delete of the row, no undo and no soft delete. Refused, with nothing written and the open sub-tasks named, while the task has an open sub-task. Its done sub-tasks are detached (`parent_task_id` set to NULL) in the same transaction, so they become plain tasks. A second delete answers "no task". A linked work item is not changed, and a later merge of it finds no deleted task to complete.
  - **Sub-tasks.** `controller_tasks.parent_task_id`, nullable and indexed (`controller_tasks_sub_tasks`), added by the timestamped migration `src/controller/migrations/20261112T1800-controller-sub-tasks.migration.ts` (TEXT; additive, rerun-safe, no backfill: existing tasks stay top-level). Not `parent_id`, which keeps its recurrence meaning and its unique key. One level: a sub-task under a sub-task is refused with nothing written. Completing a parent completes no sub-task and completing a sub-task does not complete its parent; a recurring sub-task's next occurrence stays under the same parent. `task list` shows a sub-task's parent ID at the end of its line (`sub of <id>`).
  - **Store methods.** `updateTask(id, edit)`, `deleteTask(id)` and `addSubTask(parent_task_id, task)` on `TaskStore` (`src/core/tasks.ts`, implemented in `src/impl/store/sql/tasks.ts`) take plain arguments and hold no CLI or chat logic, so the dashboard's Tasks page calls them from its HTTP routes (the Tasks page decision above).
  - **Solo and enterprise.** The same: SQLite applies the migration when the store opens.

- **Date views, Build this and the merge close (decision changed 2026-11-12, issue #607, phase 2 of 2 of #591; current; replaces "dashboard views and linking a task to an item are not part of this decision", from the #606 decision below, see History).** The decision that changed: **a task can be seen by its due date on the dashboard, sent to intake once as a work item that it stays linked to, and is completed when that item's change merges.**
  - **Link.** `controller_tasks.work_item_id`, nullable, added by the timestamped migration `src/controller/migrations/20261112T1500-controller-tasks-work-item.migration.ts` (TEXT; additive, rerun-safe, no backfill: existing tasks stay unlinked). Set once: `linkTask` writes it only where it is unset. A recurring task's next occurrence is never linked.
  - **Build.** `buildTask` (`src/core/task-build.ts`), behind `factory task build <task_id>` (chat `task build <task_id>`) and the Tasks page's Build this (`POST /api/v1/tasks/build` with `{ "id": "<task id>" }`). It makes one local work item in intake with its triage run queued, through the same `createLocalItem` as `task create`, with source ID `local-task-<task id>`, title the task's title, requester the caller's user ID, then stores the link. A second build answers the linked item and writes nothing; a retry after a crash between the two writes finds the same item (createWorkItem is idempotent on the source) and sets the link. Refused with nothing written: an unknown task, a done task, and no stored project key (the CLI's stored key; the page's `settings.resolveProject`; chat has none, so a chat build is refused until it does).
  - **Merge close.** When a change merges, `closeLinkedTasks(work_item_id)` completes every open task linked to the item, as `task done` does (a recurring one gets its next occurrence once). Called through the pr-events unit's `closeLinkedTasks` (the controller units' one store call for it) on each merge path after its close is confirmed: the local merge (`local-merge.unit.ts merged`), the Merge button's PR merge (`pr-events.unit.ts prMergeDelivered`) and a PR merged on the forge (`prFinished`, only for `change_merged` with the item closed as completed at that merge sha). Conditional on `done_at` unset, so a repeated event or delivery closes nothing more. A task with no link is never read by a merge. Changes merged before this decision close nothing.
  - **Views.** `taskViews` (`src/core/tasks.ts`, pure) places each open task by its due date against the injected Clock's calendar date in the process's time zone, so the day ends at local midnight: Inbox (no due date), Today (overdue, due before today, first; then due today), Upcoming (due in the 7 days after today, one group per day that has a task), Project (every open task under its `#list`, unlabelled last). Within a group: due date, then due time (untimed last), then priority, then age. `GET /api/v1/tasks` (`src/ui/tasks-api.ts`) answers them with the page's CSRF token and whether Build this is on (a commands actor).
  - **Solo and enterprise.** The same: SQLite applies the migration when the store opens. Due-date alerts, and linking a task to a repository or a pull request, are still not part of any decision; reminders are in the schedule a task decision above.

- **Plain tasks beside the work items, never work items (new decision, 2026-11-11, issue #606, phase 1 of 2 of #591).** Until now the work item was the only entity, so a plain to-do ("pay rent", "call the bank") could only be stored as a work item, which triage would read and spec. Now `factory task add <words>` stores a task in its own table, which triage, implement, review and the status page never read.
  - **Table.** `controller_tasks` (`id`, `title`, `list`, `priority`, `due_date`, `due_time`, `recurrence`, `created_by`, `created_at`, `done_at`, `parent_id`), unique on `parent_id`, indexed on (`done_at`, `created_at`). It carries the controller's prefix, as the table-ownership rule requires, and stays apart from `controller_work_items`, so no work-item query can return a task. Created by the timestamped migration `src/controller/migrations/20261111T1610-controller-tasks.migration.ts`, which holds the DDL; no numbered SQLite step (that list is frozen).
  - **Fields.** `list` is a free label (`#home`), never a repository key: a task belongs to no project. `priority` is 1 to 3, 1 the highest. `due_date` is `YYYY-MM-DD`, `due_time` `HH:MM`, 24-hour. `recurrence` is `day`, `week` or `month`. `created_by` is the CLI identity's user ID (`cli_user`, else `local:<git user.email>`, else the OS user, else `local:anonymous`; a chat command's linked factory user), never a display name. `parent_id` names the task a recurring occurrence came from.
  - **Quick-add.** `src/core/quick-add.ts` is a pure parser (no clock, no I/O, no import from outside `src/core`). It picks out, in any order: `today`, `tomorrow`, `YYYY-MM-DD` (the due day); `HH:MM` (the due time; alone, due today); `!1` to `!3`; `#label`; `every day`, `every week`, `every month`. The words left are the title. It refuses, with a reason and nothing stored: a date or a time that does not exist (`2026-13-01`, `25:00`), a priority outside 1 to 3, any other `every` form (`every fortnight`), a field given twice, a recurrence with no due day, and an empty title.
  - **Today and tomorrow** are kept as "0 or 1 days from today" by the parser and resolved by the store with its injected Clock, as the calendar date in the process's time zone, so a test's FakeClock decides them and the system clock never does.
  - **Commands.** `factory task add <words>` and `factory task done <task_id>` are entries of the one command table (`src/core/command-table.ts`), with the same permission as `task create` (anyone who may submit work), so they also exist in chat as `task add <words>` and `task done <task_id>`. `task list` shows the open tasks in a "Tasks" section after the local work items, only when there is one. Editing, deleting and sub-tasks: see the 2026-11-12 decision above.
  - **Writes.** Every write is conditional on the row's current state, so a retry, a redelivered chat message or a second worker changes nothing more. Add inserts with the ID the caller chose (`tk_<random>`, the chat message's ID in chat) and skips a stored one. Done sets `done_at` only where it is unset. A recurring task's completion, in the same transaction, inserts its next occurrence (`parent_id` this task, due a day, a week or a month later, on the month's last day when the month is shorter); the unique `parent_id` keeps a second completion from inserting another.
  - **Route (2026-11-12, the desktop quick-add box).** `POST /api/v1/tasks` with `{ "id": "tk_<8 to 64 URL-safe characters>", "words": "<quick-add words>" }` stores a task through the same parser and `addTask`, under the caller's ID (a resend stores one task), created by the dashboard's commands actor, and answers 200 with the stored task. It is one of the dashboard's write routes and takes their guards in order (Host, Origin equal to the Host's own, `application/json`, the per-process `x-csrf-token`, body size, JSON), then the body; every refusal stores nothing: 400 with the parser's reason, 503 with no actor, 405 when the commands route is not wired. Its callers are the macOS shell's quick-add box (design 09-desktop-app) and the Tasks page's quick-add form (below). Code: `src/ui/tasks-api.ts`.
  - **Dashboard quick-add form (2026-11-12).** The Tasks page has a text field and an Add button at the top, calling that route through `postTaskAdd` (`web/src/api.ts`). Enter (since 2026-11-14 the owner's chosen key, see the quick-add key decision above) or Add posts the words under a `tk_` ID the page chose (`tk_` and 32 hex characters); the page keeps that ID for those words until the add succeeds, so a retry after an error or a network failure stores one task. On success the field clears, keeps focus and the Tasks query reloads; on a refusal `role=alert` shows the server's message beside the field and the text stays. Esc clears the field; `q` focuses it when no field has focus, on the Tasks page only. No server change. The old hint "Add a task with `factory task add`" is gone; "Build this sends a task to the factory." stays.
  - **Solo and enterprise.** The same: SQLite applies the migration when the store opens. Views, the link to an item and the merge close: see the 2026-11-12 decision above.
