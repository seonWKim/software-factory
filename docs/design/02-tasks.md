# 2. Plain tasks

- **Plain tasks beside the work items, never work items (new decision, 2026-11-11, issue #606, phase 1 of 2 of #591).** Until now the work item was the only entity, so a plain to-do ("pay rent", "call the bank") could only be stored as a work item, which triage would read and spec. Now `factory task add <words>` stores a task in its own table, which triage, implement, review and the status page never read.
  - **Table.** `controller_tasks` (`id`, `title`, `list`, `priority`, `due_date`, `due_time`, `recurrence`, `created_by`, `created_at`, `done_at`, `parent_id`), unique on `parent_id`, indexed on (`done_at`, `created_at`). It carries the controller's prefix, as the table-ownership rule requires, and stays apart from `controller_work_items`, so no work-item query can return a task. Created by the timestamped migration `src/controller/migrations/20261111T1610-controller-tasks.migration.ts`, which holds the SQLite and the MySQL DDL; no numbered SQLite or MySQL step (those lists are frozen).
  - **Fields.** `list` is a free label (`#home`), never a repository key: a task belongs to no project. `priority` is 1 to 3, 1 the highest. `due_date` is `YYYY-MM-DD`, `due_time` `HH:MM`, 24-hour. `recurrence` is `day`, `week` or `month`. `created_by` is the CLI identity's user ID (`cli_user`, else `local:<git user.email>`, else the OS user, else `local:anonymous`; a chat command's linked factory user), never a display name. `parent_id` names the task a recurring occurrence came from.
  - **Quick-add.** `src/core/quick-add.ts` is a pure parser (no clock, no I/O, no import from outside `src/core`). It picks out, in any order: `today`, `tomorrow`, `YYYY-MM-DD` (the due day); `HH:MM` (the due time; alone, due today); `!1` to `!3`; `#label`; `every day`, `every week`, `every month`. The words left are the title. It refuses, with a reason and nothing stored: a date or a time that does not exist (`2026-13-01`, `25:00`), a priority outside 1 to 3, any other `every` form (`every fortnight`), a field given twice, a recurrence with no due day, and an empty title.
  - **Today and tomorrow** are kept as "0 or 1 days from today" by the parser and resolved by the store with its injected Clock, as the calendar date in the process's time zone, so a test's FakeClock decides them and the system clock never does.
  - **Commands.** `factory task add <words>` and `factory task done <task_id>` are entries of the one command table (`src/core/command-table.ts`), with the same permission as `task create` (anyone who may submit work), so they also exist in chat as `task add <words>` and `task done <task_id>`. `task list` shows the open tasks in a "Tasks" section after the local work items, only when there is one. Editing and deleting a task are not commands yet.
  - **Writes.** Every write is conditional on the row's current state, so a retry, a redelivered chat message or a second worker changes nothing more. Add inserts with the ID the caller chose (`tk_<random>`, the chat message's ID in chat) and skips a stored one. Done sets `done_at` only where it is unset. A recurring task's completion, in the same transaction, inserts its next occurrence (`parent_id` this task, due a day, a week or a month later, on the month's last day when the month is shorter); the unique `parent_id` keeps a second completion from inserting another.
  - **Route (2026-11-12, the desktop quick-add box).** `POST /api/v1/tasks` with `{ "id": "tk_<8 to 64 URL-safe characters>", "words": "<quick-add words>" }` stores a task through the same parser and `addTask`, under the caller's ID (a resend stores one task), created by the dashboard's commands actor, and answers 200 with the stored task. It is one of the dashboard's write routes and takes their guards in order (Host, Origin equal to the Host's own, `application/json`, the per-process `x-csrf-token`, body size, JSON), then the body; every refusal stores nothing: 400 with the parser's reason, 503 with no actor, 405 when the commands route is not wired. Its caller is the macOS shell's quick-add box (design 09-desktop-app); the dashboard has no quick-add form. Code: `src/ui/tasks-api.ts`.
  - **Solo and enterprise.** The same: SQLite applies the migration when the store opens; MySQL applies the same migration's MySQL DDL in `npm run migrate`. Reminders, due-date alerts, dashboard and status page views, and linking a task to a repository, an item or a pull request are not part of this decision.

## History

- **No route stored a task** (until 2026-11-12): only `factory task add` and the chat command did. The desktop quick-add box needed one, so `POST /api/v1/tasks` was added beside them.

- **Plain tasks** (new decision, 2026-11-11, issue #606). Before: `factory task` meant work items only (create, list, show), and a plain to-do could only be stored as a work item that triage would read.
