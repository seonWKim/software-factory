# 4. Agents: closing the source issue and `/reject`

**`/reject` closes an item at any open phase** (decision changed 2026-11-13; replaces "a reject applies only while the spec waits for approval"). The decision that changed: **`/reject <reason>` (and `factory reject <id> <reason>`, a dashboard Reject, a Slack `reject` in the item's thread) closes an open item at any command phase without a merge**: triaging, implementing, held by coordination cost, held for the previous phase of a split (`phase_hold`), in review, at the merge wait and every block. Before, the controller refused it outside the spec gate and the failure blocks with "the spec is not waiting for approval (the item is implementing)", and the refusal reached only its log for a CLI command, while the CLI had already printed "stored `/reject` ... the controller applies it on its next poll". On 2026-11-12 two rejects (wi_4bb6, wi_b0a9) were dropped that way, and wi_4bb6 then shipped a PR. They are not reopened or closed by this change.
- **The close.** One transition (`CommandsUnit.reject`): `CLOSED`, `close_reason: rejected`, the reason in `spec_feedback`, `blocked_on: upstream` / `source_close_pending`, and, as a source close does, `cancel_queued_runs` and `cancel_running_runs`, so no run of the item is left queued and a running one gets `lease_lost` on its next heartbeat, completion or tool call and pushes nothing. The rest is the existing reject close (`finishReject`): one comment quoting the reason, the issue closed as not planned, and an open PR closed with one comment (decision 2: at the merge wait too, as at the spec gate). The floor block, a Rule of Two hold and a budget checkpoint keep their own reject transitions.
- **The exception.** An item whose change is merged (`merge_sha` set) or in the merge queue (a live entry: queued, checking, passed, merging; the closes unit's `rejectRefusal`) is refused, and the reply says it cannot be rejected now and why: a merged change is undone by a new change that reverts it, and the queue lands a change once its merged result passes the checks, or removes it, after which `/reject` applies again. Nothing changes.
- **The sender sees every refusal.** The controller answers a refused command in the item's thread, as before: a reply on the GitHub issue, in the Slack thread, and the dashboard's request row. For the CLI (decision 1), `factory task show <id>` ends with a "Last refused command" section: the item's latest refusal with its reason, read from the thread entry the controller already stores (marker `factory:refused:<key>`), so no table or column is added. `factory reject` (and every item command) prints where that refusal shows.
- **Help and the table.** `/reject` applies at every open phase (`OPEN_PHASES` in `src/core/commands.ts`), so every open item's footer lists it, `/help` marks it **(now)** there, and the SET_UP.md table says "any open item". The description names the exception.

**Closing the source issue.** Intake now also reads closed factory-labelled issues on every poll (`issues?state=closed&labels=<intake_label>`, its own `closed` cursor inside the same intake cursor, `since` inclusive, the issue numbers at the boundary time skipped; pull requests in the list are skipped). Each becomes a `source_closed` event carrying the closer from the single-issue endpoint's `closed_by`, or null, and GitHub's `state_reason` (`completed`, `not_planned`, or null for none or any other value). The rule: **closing the issue stops the item.** If the item exists and is not already `CLOSED`, one conditional transition sets `CLOSED` with `close_reason` `completed` when the state_reason is `completed` and `wont_do` otherwise (no `merge_sha` is written), writes one `controller_state_changes` row with reason `source_closed` and the closer's user id as actor, and in the same transaction cancels the item's `queued` runs (triage, or a retry waiting on backoff; `TransitionInput.cancel_queued_runs`) and stops its `running` runs of any kind (`TransitionInput.cancel_running_runs`: status `cancelled`, lease cleared, no outcome). A stopped run's worker gets `lease_lost` on its next heartbeat, its handoff writes and its completion are refused (its outcome is not stored), and the tool broker refuses its calls with `lease_lost`, so nothing is pushed after the close. Cancelled runs go through the normal ack path and are recorded as `run_ignored`; the controller posts nothing for them. The reaper cancels, rather than requeues, an expired run whose item is `CLOSED`. Store first, no login check: an item already `CLOSED` (by `/reject`, a merge, or an earlier delivery of the same close) gets no row, so repeats and the factory's own close are no-ops. A closer GitHub does not name, or who maps to no user, is recorded as the system actor (`system:intake`) with a warning. No comment is posted on the closed issue; its status label moves to `done` for `completed` and `rejected` for `wont_do`. **The item's PR:** an item with a `pr_number` is closed as `CLOSED` with `blocked_on: upstream` / `blocked_reason: pr_close_pending` in the same transition. The controller then asks the source to close that PR without merging (`SourceAdapter.closePr`), after one comment on it, keyed on marker `pr-closed:<item id>`: "Closed because the issue was closed by @<login>.", or "Closed because the issue was closed." when GitHub names no closer (the source reads `closed_by` again, so no login is stored). A PR already merged or closed is left alone, with no comment. Then the mark is cleared (`pr_closed_for_source`). If the comment or the close fails, the item stays `CLOSED` and marked, a warning is logged, and every intake tick tries again; the comment goes first and carries its marker, so it is never posted twice. The `pr_closed` event GitHub then sends finds the item `CLOSED` and changes nothing. Closes are delivered after the poll's PR events, so a merged PR whose `Closes #N` closed the issue is recorded as `completed` first. Reopening the issue or re-adding the label does not restart a closed item: intake returns the existing item, so a human files a new issue. Known gaps: an issue whose factory label was removed before it closed is not seen; an item closed as `completed` with no merge still counts as merged in budget stats (§6), left for its own item. `/reject` still leaves the PR open.
