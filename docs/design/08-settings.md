# 8. Enterprise: settings in layers

- **Every setting is a discovered descriptor (decision changed 2026-11-08, RFC 0015 M10; before: the key lists, descriptions and "applies at" texts lived only in `src/core/settings.ts`, see History).** Each settable and PR-only key is one `src/<owner>/settings/<key>.setting.ts` file (`defineSetting`, `src/shared/setting.ts`): key, owner component, type, default, description, when a change applies, `direction` (`tighten-only` or `free`, with the order that is tighter), `changed_by` (`runtime` or `review`), `scope`, and `guard` or `dial` with the grant a runtime change needs. The catalog page `docs/settings.md` is generated from them (`npm run settings:catalog`). The resolver (`resolveSettings`) still types its values by the key lists in `src/core/settings.ts`; `tests/settings-catalog.test.ts` holds both equal until that file moves into the runtime. Every settings folder is on the gate list (`PROTECTED_PATHS.guard_settings`).
  - **Settings only tighten (`tests/architecture/settings-monotonic.test.ts`).** The levels are owner → org → project → pack → user (`resolveLevels`, `src/runtime/settings/monotonic.ts`): the owner's reviewed config may set any value; a lower level's value that loosens the one in force is ignored with its reason. A guard (`secrets`, `egress`, `broker`, `deny_paths`) is set by the owner's config only. A dial changes by review only, or at runtime with its grant (`mode`, `auto_merge_max_tier`: `approve_merge`). Today's runtime overrides map onto the levels unchanged: a global override is the owner's live value, a project override the project level. Solo and enterprise are the same; the org, pack and user levels have no writer yet.

- **`mode` and `auto_merge_max_tier` are settable (decision changed 2026-11-08, issue #444; before: twenty-two settable keys, the auto-merge dial fixed at 0 in the file, and no mode, see History).** `mode` (`"manual"` or `"auto"`, default `"manual"`) decides whether the factory may approve specs and merge local changes itself (design 03-risk); `auto_merge_max_tier` (a whole number from 0 to 3, default 0) is the highest tier auto mode merges at. Neither is a `factory.config.json` key; the file's `dials.auto_merge_max_tier` must stay 0. No migration: each is one row in the existing override table, audited like every set.
  - **Per project.** `mode` takes `--project` (the configured repo's `owner/name`), the first per-project key that is no gate: a project's mode stands on its own, with no tighten-only check, outside the per-project layers. `GATE_SETTABLE_KEYS` holds the three gates; `PROJECT_SETTABLE_KEYS` is them plus `mode`. `auto_merge_max_tier` is global.
  - **Who may change them.** A set or reset of either needs `approve_merge` on the configured project (`APPROVE_MERGE_KEYS`, `SettingsDeps.mayApproveMerge`): the CLI asks the local auth plugin over the local grants, the Settings page the page's own approve_merge check (as its Merge button), both with no forge call. A refusal writes no override and no audit row. Solo: the first local identity is the owner and holds `approve_merge` with no setup. Enterprise: an approver or the owner; a requester is refused.
  - **`factory mode auto|manual [--project <owner/name>]`** is `factory settings set mode <mode>`, the same checks and one audit row naming the actor and the time. `factory settings` now writes as the CLI identity (`cli_user`, else `local:<git user.email>`, else the OS user), the identity the approve_merge check asks about and the one the page writes as.
  - **Read live.** The controller reads both through `LiveSettings` at each decision (refreshed each tick), so a flip on one replica applies on every replica at its next tick, with no restart. A stop condition (03-risk) writes `mode` back to `"manual"` as `system:auto`, at the level the auto mode was stored at.

- **Settings resolve in layers.** The per-project keys are exactly `max_attempts`, `max_diff_lines`, `max_diff_files`, `budgets` and `floors`. Each resolves in this order, first hit wins: learned value → project override (`projects["owner/name"]`) → `defaults` → built-in default (3, 1500, 40, no budgets, no floors). `settingsFor(project, layers, learned?)` in `src/core/settings.ts` is pure and returns each key's value and the layer it came from; the controller and worker read these keys only through it (`tests/settings.test.ts` fails on any other read of them from a config object).
  - **Config shape.** `defaults` holds the global values; the same keys at top level still load as before (the checked-in config is unchanged), and setting one key in both places fails at startup. `projects` is keyed by project ID in the store's form, `owner/name` (`WorkItem.project`), not `github.com/owner/repo`: #98 (project IDs) has not landed, so this uses the ID the store already has. A project ID other than the configured repo's fails at startup; running several repositories at once is a separate issue.
  - **Tighten only.** Every per-project key is a gate, so a project may not loosen it past the global value (`defaults`, else built-in): a number above it fails at startup; `budgets` is the whole map, so a tier above the global value, or a global tier left out (no limit), fails; `floors` is the whole list, so it may add entries and raise a tier, but leaving out a global prefix or lowering its tier fails. Equal or tighter passes.
  - **Unknown keys.** `defaults` and each project accept only the per-project keys. `auto_merge_max_tier`, `dials`, `plugins`, `repo` (so `test_command` and `install_command`: a no-op command would loosen the test gate and two commands cannot be compared), `budget_min_sample` (not a gate) and every guard setting are unknown keys there, reported in the same format as top-level unknown keys (#84), with the project in the path (`projects["owner/name"].key`) and a suggestion when one is close.
  - **Learned layer.** `LearnedSettingsSource` is an optional dependency of the controller and worker. Nothing writes learned values yet and the composition root passes none. A learned value that would loosen a gate past the global value is ignored, so the layer can never weaken a human check.
  - **Display.** `factory doctor` prints one `ok` line per project and per-project key with its effective value and layer (`setting for owner/name: max_attempts = 3 (defaults)`). The status page's Health panel shows the same lines, since it runs the same `doctorChecks`. No store change and no migration.

- **`toolchain` is a PR-only key (decision changed 2026-11-08, issue #334; before: twelve PR-only keys, see History).** The `toolchain` block (`caches`, `env`, `warm_command`; `05-sandbox.md`) decides what agents may read and the env they get, so it changes only by a reviewed PR: `factory settings set toolchain …` (and the Settings page) is refused with "changes by PR only", and the page lists it with the other PR-only keys and its description. On a shared store (MySQL) it is one of the keys taken only from the checked-in file, like `dials`, `floors`, `plugins`, `permissions` and `auth`. It is not a per-project key: `defaults` and `projects` blocks refuse it as an unknown key.

- **`standing_approvals.threshold` is settable (decision changed 2026-11-07, issue #299; before: eighteen settable keys, none for standing approvals, see History).** `factory settings set standing_approvals.threshold <n>` (and the Settings page) sets how many unchanged spec approvals in a row propose a standing rule. Global only, default 10, a positive whole number (anything else is refused on set and ignored, with the file value kept, when the stored overrides load), audited like every set, and read at the controller's next spec approval with no restart (`LiveSettings.values()`). It is not a `factory.config.json` key: a `standing_approvals` block in the file is an unknown key. See `05-standing-approvals.md`.

- **`hold_policy` is settable (decision changed 2026-11-07, issue #314; before: seventeen settable keys, none for coordination, see History).** `factory settings set hold_policy <json>` (and the Settings page) sets what a run held by coordination cost does: `{"mode":"hold"}` (default), `{"mode":"run_after_minutes","minutes":20}` or `{"mode":"run"}`. It is global only (no `--project`, until #99), checked with the config loader's message (`parseHoldPolicy` in `src/core/coordination.ts`), and applies at the next claim: `LiveSettings` puts the effective value into `FactoryConfig.coordination`, which each worker passes to `claimRun`. The other coordination keys (`max_coordination_cost`, `hotspot_paths`, `hotspot_weight`, `mechanical_paths`, `mechanical_weight`, `hotspot_mode`) stay file-only, outside the allow-list. The settable-keys table below lists it. See `05-coordination.md` Hold policy.

- **The alarm keys are settable (decision changed 2026-11-07; before: nineteen settable keys, see History).** `alarm_repeat_count` (default 3), `alarm_window_minutes` (default 60) and `alarm_restart_count` (default 5) are top-level `factory.config.json` keys (positive integers, or startup fails) and `factory settings set` keys. They are global only (no `--project`) and apply at the next alarm step, which runs on each poll, with no restart. `LiveSettings` puts the effective values into the controller's config view. Why each is a setting and not a constant is in `05-alarms.md`. The settable-keys table below lists them.

- **Settings change from the dashboard too (decision changed 2026-11-07, issue #236).** The Settings page of the dashboard app (§9) is a second front end for `factory settings`: `GET /api/v1/settings` reads, `POST /api/v1/settings` writes, and every write runs `runSettings` (`src/settings-cmd.ts`), so the page accepts, refuses and stores exactly what the CLI does, with the CLI's messages. The settable keys, checks, storage and audit rows ("Settings change at runtime", under History) are unchanged; no store method and no migration was added.
  - **Read.** `GET /api/v1/settings` (`src/ui/settings-api.ts`) returns each settable key with its effective value (JSON text), source (`override`, `file`, `default`), the file value, the built-in default, the project values with their source, "applies at", and for `workers` its `max_workers` limit; the PR-only keys, each marked "changes by PR only" with no write control; the ignored overrides; and the last 50 audit rows, the rows `settings history` shows. Project labels, actor IDs, values and messages pass the `Withholder`; a project key is never returned.
  - **Descriptions (issue #269; moved 2026-11-08, RFC 0015 M10).** Each settable key and each PR-only key has a one-sentence description of what it controls, in its `*.setting.ts` file (`description`, beside `applies`), read through the settings catalog (`loadSettingCatalog`, `src/runtime/`). `tests/settings-catalog.test.ts` fails when a settable or PR-only key has no setting file. `GET /api/v1/settings` returns it as `description` on each entry of `keys` and `pr_only`, through the `Withholder` like the other strings, and the page shows it under the key name. The web code holds no description text, and `factory settings` prints none.
  - **Write.** The body is `{ action: "set" | "reset", key, value?, project? }`; `value` is JSON text, as the CLI takes it. Success: 200 with the CLI's lines. A refusal from the shared checks (heartbeat × 2 < lease, retry order, a PR-only key or a guard, workers above `max_workers`, a project value looser than the global one, a reset with no override): 422 with the CLI's `refused: …` line in `error`, and nothing stored. A body that is not a set or reset: 400.
  - **Guards, in order.** Host must be 127.0.0.1 or localhost (the existing guard, 403); `Origin` must equal the Host's own `http://` origin, and a missing one is refused (403); `Content-Type` must be `application/json` (415); the `x-csrf-token` header must equal the per-process token (403). The token is 32 random bytes made when the UI process starts, held only in memory (never in the store, on disk or in the HTML), and returned by `GET /api/v1/settings`; a restart invalidates it and a page reload fetches the new one. Bodies over 64 KiB: 413. Every other method on every other path still answers 405.
  - **Project writes without the forge.** The UI process builds no GitHub client and reads no forge credential. For `project` it finds the configured repo's project key from the stored project label (`storeProjectResolver`: the project keys of stored overrides and recent work items, the first whose label ends in `/owner/name`). With no stored label the write is refused with a pointer to `factory settings … --project` on the command line. This is the one place the page differs from the CLI, which asks the forge.
  - **Actor.** A page write stores `local:<OS login>` of the user running `factory ui`, never a display name, as the CLI does.

## History

- **Settings as descriptors** (decision changed 2026-11-08, RFC 0015 M10). Before: `SETTING_DESCRIPTIONS`, `PR_ONLY_DESCRIPTIONS` and `SETTING_APPLIES` in `src/core/settings.ts`, typed by their key lists, and no statement of which way each key may move.
- **`mode` and `auto_merge_max_tier` are settable** (decision changed 2026-11-08, issue #444). Before: twenty-two settable keys, `--project` only for the three gates, `auto_merge_max_tier` only the file dial fixed at 0, and `factory settings` wrote as `local:<OS login>`.
- **`toolchain` is a PR-only key** (decision changed 2026-11-08, issue #334). Before: twelve PR-only keys and no `toolchain` key.
- **The alarm keys are settable** (decision changed 2026-11-07, design 05-alarms). Before: nineteen settable keys, and no alarm existed.
- **`standing_approvals.threshold` is settable** (decision changed 2026-11-07, issue #299). Before: eighteen settable keys; the standing-approval threshold was named as a config key, not wired.
- **`hold_policy` is settable** (decision changed 2026-11-07, issue #314). Before: seventeen settable keys, and no coordination setting could change at runtime.
- **Settings resolve in layers** (decision changed 2026-11-01, issue #99). Before: every setting had one top-level value in `factory.config.json` for the whole factory, read straight from config by the controller, worker and budget code. This changes the single-value config of the §3 floors, the §4 size gate (`max_diff_lines`, `max_diff_files`), §5 Restarts (`max_attempts`) and the §6 Budgets "Config" decision.
- **Settings change at runtime (decision changed 2026-11-03, issue #157; before: config was parsed once at startup and handed to the controller and worker pool as a frozen object, the pool built its loops once, so changing any setting needed a PR, a merge and a restart).** Seventeen keys can be changed while the factory runs with `factory settings set <key> <value>`; every other key still changes only by PR.
  - **One effective value.** `resolveSettings` in `src/core/settings.ts` gives each settable key's value: the stored override if set, else the `factory.config.json` value, else the built-in default. The controller, the worker pool and the `factory settings` commands all read through it. Precedence with the layers above: a global override sits above the file's top-level (or `defaults`) value, a project override above the file's `projects` block, and the learned layer stays on top.
  - **Storage.** Two tables, both with a `project_key` column ('' for global, else a project key; not named `project`, so the owner/name project-key step never reads them): `settings_overrides(setting_key, project_key, value_json, set_by, set_at)` and the audit trail `settings_changes(seq, setting_key, project_key, old_value, new_value, actor, at)`. Values are JSON text. SQLite migration 17; MySQL step 0017 (an inline step in `src/impl/store/mysql/migrations.ts`, since 0013 was already taken by the inline phases step and 0014 by identity links; the issue named it 0013). Each set and reset is one transaction with its audit row: if the audit insert fails, the override is unchanged. Concurrent sets: last writer wins and the audit rows keep commit order. The actor is an ID, `local:<OS login>`, never a display name. The settings commands refuse on MySQL while steps are pending, as the other commands do.
  - **Live reads.** One `LiveSettings` per process (a cache of the file values plus the stored rows; no replica needs it) is refreshed by the controller at the start of each tick and each public tick step, by the worker pool each tick, and by a worker before each claim and each lease renewal. A worker reads the values once at its claim and keeps them for that run. A stored override that fails a check (bad JSON or value, heartbeat × 2 ≥ lease, base above max, a project value looser than the global value, a global value tighter than a project's file value) is ignored and logged once; the process keeps the file value and keeps running.
  - **Worker pool (decision changed 2026-11-07).** The pool has `max_workers` slots: a file-only key, an integer of at least `workers`, absent meaning `workers`. Each tick it starts the slots below the effective `workers` and stops the rest: a stopped slot claims nothing more, finishes its run and ends; it starts again when `workers` rises. So `settings set workers <n>` raises or lowers the count live, anywhere from 1 to `max_workers`, with no PR and no restart. `max_workers` sizes the supervisor's index block, so `settings set workers` above it is refused and a stored value above it is read as `max_workers`. The file's `workers` is the count before any override.
  - **The settable keys and when each applies** (no restart for any):

    | Key | `--project` | Applies at |
    |---|---|---|
    | `max_attempts` | yes | the controller's next decision |
    | `max_loops`, `max_restart`, `retry_base_ms`, `retry_max_ms` | no | the controller's next decision |
    | `max_diff_lines`, `max_diff_files` | yes | the next run that starts |
    | `run_timeout_ms`, `first_output_ms`, `models`, `model_by` | no | the next run that starts (`first_output_ms`: a positive integer, default 180000; see `05-restarts.md`) |
    | `poll_interval_ms`, `tick_ms` | no | the next tick |
    | `heartbeat_ms`, `lease_ms` | no | the next lease renewal (`lease_ms` also the next claim) |
    | `workers` | no | the worker pool's next tick; at most the file's `max_workers` (absent: its `workers`) |
    | `phases_auto_approve` | no | the next phase spec triage writes, and the next phase tick for a phase spec already waiting (`true`/`false`; default `false`; see `04-split-specs.md`) |
    | `hold_policy` | no | the next claim (`{"mode":"hold"}` default, `{"mode":"run_after_minutes","minutes":20}` or `{"mode":"run"}`; added 2026-11-07, issue #314; see `05-coordination.md` Hold policy) |
    | `alarm_repeat_count`, `alarm_window_minutes`, `alarm_restart_count` | no | the next alarm step, each poll (3, 60 and 5 by default; added 2026-11-07; see `05-alarms.md`) |
    | `standing_approvals.threshold` | no | the controller's next spec approval (a positive whole number; default 10; added 2026-11-07, issue #299; see `05-standing-approvals.md`) |
    | `mode` | yes | the controller's next spec approval or merge (`"manual"` default, or `"auto"`; needs approve_merge; added 2026-11-08, issue #444; see `03-risk.md`) |
    | `auto_merge_max_tier` | no | the controller's next merge (0 to 3; default 0; needs approve_merge; added 2026-11-08, issue #444; see `03-risk.md`) |
  - **Refused.** PR-only keys are refused with "changes by PR only": `plugins`, `repo`, `store`, `floors`, `dials`, `auth`, `permissions`, the guards (`secrets`, `egress`, `broker`), `deny_paths`, `env`, `toolchain` (added 2026-11-08, issue #334). It is an allow-list, so every key not in the table is refused as not settable, among them `budgets`, `inbox_retention_days`, `stats`, `ui`, `intake_label` and `branch_prefix` (until the owner decides), and `auth_pause_ms`. A refused command writes no override and no audit row.
  - **Checks on set.** A value is checked with the config loader's own message for that key. `heartbeat_ms` and `lease_ms` are checked together (heartbeat × 2 < lease) using the other key's effective value, and so are `retry_base_ms` ≤ `retry_max_ms`. `--project` takes only `max_attempts`, `max_diff_lines`, `max_diff_files`, and only the configured repo's `owner/name`; a project value may only tighten its gate against the global value, and a global value that would leave any project's value looser is refused with the project named. Nothing is clamped silently. A set to the current value still writes an audit row. `settings reset` on a key with no override is refused with no audit row; resetting a project override needs `--project`; a reset that would break the heartbeat or retry check is refused.
  - **Not covered.** The update run's own timeout in the updater keeps the file value until restart. (Its "no dashboard write path" is replaced: see "No dashboard write path" below.)
- **Worker pool** (decision changed 2026-11-07). Before: the pool had the file's `workers` slots, so the live `workers` setting could only lower the count; raising it took a PR and a restart.
- **No dashboard write path** (decision changed 2026-11-07, issue #236). Before: settings changed only through `factory settings` on the command line; the dashboard was read-only and its Settings page pointed at the command (#131, #124). Now the page writes through the same `runSettings`.
