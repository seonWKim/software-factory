# 8. Enterprise: settings in layers

- **The Settings page lists capabilities, and the per-role tool grants change at runtime (decision changed 2026-11-13, issue #572; current; replaces "tool grants change in factory.config.json only", see History).** The decision that changed: **`tool_grants` is a settable key (tighten-only, so a new grant needs `approve_merge`), and a Capabilities section on the Settings page lists what the agents may use.**
  - **The list.** `GET /api/v1/settings/capabilities` (`src/ui/capabilities-api.ts`) returns one entry per skill, tool and provider, each with `enabled`, the `roles` (run kinds) that may use it and `last_used`. The registry is `src/runtime/capabilities/capabilities.ts`. MCP servers join when packs carry them (#495, #568); this change adds none.
    - **Skills.** Each skill in the folders listed in `capabilities.skill_folders` (new optional key in factory.config.json, default none; a leading `~` is the owner's HOME, a relative path is taken from the factory root): a subfolder with a `SKILL.md`, or a top-level `<name>.md`. With no folder the list has no skill and nothing fails; a missing folder lists none. A skill is enabled when it is listed. No role grant exists for skills yet, so a skill names no role. Solo: the owner adds their agents home's `agent-skills` and `~/.claude/skills`.
    - **Tools.** The selected ToolBroker's tools (its descriptor table, `allTools()`) and the pack layers' tools (`pack:tool:<name>`). A tool is enabled when a role is granted it in the `tool_grants` in force; a tool that is not read-only is never granted and says so.
    - **Providers.** One entry per registered AgentRunner (`runner:<plugin>`) and LLMProvider (`llm:<plugin>`) plugin, enabled when `plugins` selects it. A plugin with its own config block (`openai_compatible` for `openai-compatible`) is that endpoint: its host and its own model names; any other uses the `models` setting. A runner entry serves the agent roles (`triage`, `implement`, `review`, `resolve`), an LLM entry the improve run. Each entry lists its model per class: `model_by` names classes, so a run's class resolves to the model of the entry that serves it. How `model_by` resolves is unchanged.
    - **Last used, from stored runs only.** Runs finished in the last 30 days, newest first, at most 100 (`USAGE_RUNS`): a provider entry's is the newest run of one of its roles whose reported model (`usage.model`) contains one of the entry's model names; a tool's or skill's is the newest run whose stored transcript (at most 1 MiB per part) calls it (`mcp__factory_tools__<tool>`, or a Skill call with `"skill":"<name>"`). No tool call writes anything new, and no table was added. The page reads the list once when it opens, never on the poll.
    - **Names only.** The sources are folder listings, tool descriptors and plugin names; an endpoint is shown as its host (never its path, query or user info); every string leaves through the `Withholder`, so a value the SecretStore holds is withheld. The UI process builds the selected broker only to read its descriptor table: its forge client, credentials, secrets and scanner are stand-ins that throw if touched, and nothing calls a tool. The sources come from the loaded config through the Settings file writer (`configWriter`, `src/ui/settings-api.ts`), read again on each request, so `compose.ts` did not change.
  - **`tool_grants` at runtime.** One descriptor, `src/runtime/settings/tool-grants.setting.ts`: runtime, global, default `{}`, applies at the next run that starts. The value is the file key's shape: run kind → tool names (a pack entry as `pack:tool:<name>` or `pack:mcp_server:<name>`), checked on set by `toolGrantsShape` (`src/core/config.ts`); a stored value of another shape is ignored and the file's grants stay. The file's `tool_grants` is the base value; an override replaces it whole. The worker reads the grants in force at its claim (`LiveSettings` puts them into the config view), and they reach the run passport and the run's tool gate as before.
    - **Tighten-only, so loosening asks (the 2026-11-09 rule).** A value that grants any role a tool the value in force does not grant it is a loosening and needs `approve_merge`; a refusal stores no override and writes no audit row. Removing a grant, or keeping the same grants, needs none. A reset back to the file's grants asks when it loosens. Solo: the owner holds `approve_merge`. Enterprise: an approver or the owner; a requester may tighten but not loosen.
    - **Checked against the broker at use, not on set.** The broker is built only in the worker, so a set does not check a name against it; a name the broker does not list, or a tool that is not read-only, reaches no agent, because the run's tool gate lists and calls only granted read-only tools the broker serves. Startup still checks the file's `tool_grants` against the broker as before.
  - **Guards unchanged.** A tool still runs only through the ToolBroker, behind the run passport (G2) and the tool gate; no new call path reaches a tool, and G1 to G6 are as they were.
- **`calendar` is a live owner setting that connect and disconnect write (decision changed 2026-11-13, "Connect Google Calendar from the dashboard"; current; replaces "`calendar` is a file key the CLI's connect writes after a diff", see History).** The decision that changed: **which calendars the factory reads is the runtime key `calendar`, read live by each process like `integrations`, not only the top-level key in factory.config.json.**
  - **The key.** `calendar` (runtime, global, `free`, default `[]`; `src/runtime/settings/calendar.setting.ts`) is a list of calendar plugin names, each once. An override wins over the file's top-level `calendar` key; with none the file decides as before, so a config that lists calendars keeps working. It is an owner-only key (`OWNER_KEYS`): the Settings route and the calendar routes ask the page's owner check; `factory settings set calendar …` and `factory setup calendar …`, run by the owner on their machine, ask none.
  - **Why live, not the file writer (decision 1).** The file-only key writer puts a change on a local branch the owner merges, then a restart picks it up: a connect from the dashboard would end with the calendar still off. A live setting applies at the controller's next tick, as `integrations` does, and its audit row names who changed it.
  - **One flow, CLI and dashboard (approver's note).** `connectCalendar` (`src/setup.ts`) runs the plugin's connect hook, writes its secrets through the setup writer (`setSecret` / `removeSecret`, mode 600; decision 3), then lists or drops the plugin in the live `calendar` setting (other names kept; no override when nothing changes), and on connect runs one sync. `factory setup calendar <command>` (`--disconnect`) and `POST /api/v1/calendar/connect` and `/disconnect` (`src/ui/calendar-api.ts`) both call it, so they cannot disagree. The CLI no longer edits factory.config.json for `calendar` and asks no diff question.
  - **Read live.** Each process's `LiveSettings` hands the effective list to its `LiveCalendars` holder (`src/calendar/live-calendars.ts`) after every refresh; the controller's sync reads the holder's feeds. A name that joins is built then, its secrets read afresh from the secret file (the process's own SecretStore loaded only the plugins selected at start); a name that leaves is dropped. The first list is startup's: a plugin that fails to build there (a bad `calendar_ids`) fails startup as before; later a name that fails to build is logged once and skipped.
  - **Owner only (decision 2).** The calendar routes take the write routes' guards (Host, Origin, Content-Type, CSRF token) and then the store's local owner (`rules-api.ts` `ownerOf`), before the flow runs.
- **The Settings page edits the file-only keys in a typed form (decision changed 2026-11-13, phase 3 of 3 of "Settings without editing factory.config.json"; current; replaces "the page lists the file-only keys read-only in the PR-only table", see History).** The decision that changed: **every writer key except the read-only ones below has a typed control on the Settings page, saved through the phase-2 writer onto a local branch the owner merges from the page.**
  - **Editable keys.** `plugins` (with the guards `plugins.secrets`, `plugins.egress`, `plugins.broker`), `models`, `model_by`, `slack`, `repo.install_command`, `repo.test_command`, `repo.check_commands`, `repo.path`, `toolchain`, `dials`, `floors`, `permissions`, `hotspot_paths`, `mechanical_paths`, `path_companions`. The writer's `FILE_ONLY_KEYS` gained the three path lists (decision 1 of the phase-3 spec), so the page can write them.
  - **Read-only keys (owner answer: keep these seven).** Each shows its value and "Edit factory.config.json to change this.", with no write control: `store` (moving it moves where the factory keeps its state), `env` (decides whether the factory runs locally or in the cloud), `state_dir` (where the state files live; moving it strands them), `worktrees_dir` (where run worktrees live), `ui` (the port is bound at start), `outbound.batching` (a nested map per destination kind with five fields; too free-form for one control), `cli_user` (the identity the page and CLI act as; changing it changes who `approve_merge` is checked against). `state_dir` and `worktrees_dir` stay writer keys for `factory settings edit-file`.
  - **Not a file key.** `deny_paths` is built at load (`src/compose.ts`) and gets no control (decision 2); `auth`, `merge_queue.depth`, `hooks`, `packs.auto_approve_read_only` and `outbound.batching` are not writer keys. They stay in the PR-only table with their descriptions.
  - **Read.** `GET /api/v1/settings` returns `file_keys` (null when the process has no file writer): each editable key's value in the file as this process loaded it, the read-only keys' values (both as JSON text through the `Withholder`), and each interface under `plugins` with its registered plugin names, whether it is a guard and the plugin in force. `configWriter` (`src/ui/settings-api.ts`) builds it from the loaded config (`fileKeysOf`) beside the writer, so `compose.ts` does not change. A value merged since start shows after a restart.
  - **Write.** Save sends `{ "action": "edit-file", key, value, confirm }`; the answer adds the filed `item` and `branch`. A change to a guard, `floors`, `permissions` or (decision 3) `dials` asks first in the danger Dialog, and only Confirm sends `confirm: true`. The plugin selects list only registered names, so no option turns a guard off.
- **File-only keys change through a local branch the owner merges (decision changed 2026-11-13, phase 2 of 3 of "Settings without editing factory.config.json"; replaces "changes by PR only" for these keys, see History).** `factory settings edit-file <key> <json> [--confirm]` and the Settings write route (`POST /api/v1/settings` with `"action": "edit-file"`, `"confirm": true`) run one writer, `editConfigFile` (`src/core/config-writer.ts`). `factory settings set` still refuses these keys: they are not runtime settings, and factory.config.json stays the one store of their values.
  - **Keys.** `plugins` (and `plugins.secrets`, `plugins.egress`, `plugins.broker`), `models`, `model_by`, `slack`, the repo commands (`repo.install_command`, `repo.test_command`, `repo.check_commands`), `toolchain`, the paths (`state_dir`, `worktrees_dir`, `repo.path`), `floors`, `dials`, `permissions`, and since phase 3 the path lists `hotspot_paths`, `mechanical_paths` and `path_companions`. Any other key is refused by name. A dotted key edits one member of an object. `models` and `model_by` are also runtime settings: the writer edits only the file value, and a runtime override still wins over it.
  - **Loosening-sensitive (owner answer).** An edit to a guard (`secrets`, `egress`, `broker`, `deny_paths`), `floors` or `permissions`, or a `plugins` edit that changes a guard, is refused unless the request carries the confirm flag. `deny_paths` is built at load, never a file key, so with the flag it is refused as not file-only.
  - **Checked before any write.** The writer reads the file from the local base branch, sets the one value in the text (`setConfigKey`, `src/core/config-text.ts`; every other byte stays) and runs `checkConfigKeys`, then `loadConfig`, on the whole new text. A refusal writes no file, branch, audit row or item.
  - **A local branch, never the checkout.** The sandbox (`commitNewBranch`, NoOpSandbox) writes one commit from objects only: the parent is the base's commit, and the tree is the parent's with only the config file changed. It then creates `refs/heads/<branch_prefix><id>` (`factory/<id>`) by a conditional ref update that fails when the branch exists. The base ref, HEAD, the index and the working tree are never touched. Core runs no git.
  - **Filed for the owner's merge.** One local work item, created at REVIEW waiting for the merge (blocked on human, `merge_pending`, no change_ref, tier 4, so auto mode never merges it), and one row in `runtime_config_file_changes` (actor ID, key, old and new value as JSON text, branch), in one transaction. The table comes from one SQLite migration (`src/state/migrations/20261113T1200-state-config-file-changes`). There is no MySQL migration, since the MySQL store is being removed. No other table holds the value. No review run is added (owner answer): the owner wrote the edit, the loader checked it and the confirm flag guards loosening. `factory merge <id>` lands it through the merge queue, whose checks run on the merged commit first.
  - **Ratchets.** The audit store is its own class over the store's database (`ConfigFileChangesSql`), and the writer's parts are built in `src/ui/settings-api.ts` (`configWriter`), so `SqlFactoryStore` and `compose.ts` do not grow. `factory setup` keeps its own top-level text edit (`src/cli/handlers/setup/config-edit.ts`) until the cli component may import core.
- **The timing, coordination and intake label keys are settable (decision changed 2026-11-12, phase 1 of 3 of "Settings without editing factory.config.json"; replaces the "Refused" list of "Settings change at runtime" and the file-only coordination keys of "`hold_policy` is settable", see History).** Seven file-only keys join the allow-list, each with one `*.setting.ts` descriptor under the component that reads it, and change with `factory settings set <key> <value>` (and the Settings page) with no restart. Phase 2 (a writer that puts a file-only key on a local branch) and phase 3 (a typed Settings form) are separate items.
  - **New settable keys** (global only, no `--project`):

    | Key | Direction | Applies at | Default with no override and no file value |
    |---|---|---|---|
    | `stall_ms` | free | the next run that starts | 300000 (`STALL_DEFAULTS`) |
    | `probe_interval_ms` | free | the next stall pause or probe | 600000 (`STALL_DEFAULTS`) |
    | `auth_pause_ms` | free | the next forge auth pause | the effective `retry_max_ms`, and it follows a change to it |
    | `max_coordination_cost` | tighten-only, lower is tighter | the next claim | 2.5 (`DEFAULT_COORDINATION`) |
    | `hotspot_weight` | tighten-only, higher is tighter | the next claim | 3.0 (`DEFAULT_COORDINATION`) |
    | `mechanical_weight` | tighten-only, higher is tighter | the next claim | 0.25 (`DEFAULT_COORDINATION`) |
    | `intake_label` | free | the next item taken in | none: the file's value applies |
  - **Checks.** Each value gets the config loader's own message: the timing keys a positive integer (`stallConfig`, `retryConfig`); `max_coordination_cost` and `hotspot_weight` a number above 0, `mechanical_weight` above 0 and below 1.0 (`coordinationProblems`); `intake_label` a non-empty string (`intakeLabel`, which the loader now runs too). A refusal writes no override and no audit row.
  - **Grants.** The timing keys and `intake_label` are `free`: any value, no grant. The coordination keys are tighten-only in the direction that holds more runs: a lower `max_coordination_cost` or a higher weight needs no grant; a loosening asks `approve_merge` (the 2026-11-09 rule below).
  - **Read live.** `LiveSettings` puts the timing keys into the config view and the coordination keys into `FactoryConfig.coordination`, so a worker's next claim and the controller's next tick use them. The GitHub source reads the stored `intake_label` override (else the file's) when it lists open issues and files a new one: a new item is taken in under the label in force; an open item keeps the label its issue carries, and nothing is relabelled or backfilled.
  - **Refused.** PR-only keys are refused with "changes by PR only": `plugins`, `repo`, `store`, `floors`, `dials`, `auth`, `permissions`, the guards (`secrets`, `egress`, `broker`), `deny_paths`, `env`, `toolchain`, `outbound.batching`, `merge_queue.depth`, `hooks`, `packs.auto_approve_read_only`. Every other key outside the allow-list is refused as not settable, among them `budgets`, `inbox_retention_days`, `stats`, `ui`, `hotspot_paths`, `mechanical_paths`, `hotspot_mode` and `branch_prefix`. `branch_prefix` stays file-only (owner answer): it sets the tool broker's push namespace, a guard input, and open items derive their branch from it.
- **Integrations switch at runtime with `integrations` (decision changed 2026-11-12; current; replaces "`plugins` is review-only" for the interfaces marked `integration`, see History).** A plugin interface whose kind row in `src/plugins.ts` carries `integration: true` is an integration; only `tacit` (TacitLedger) is marked, and a guard (SecretStore, EgressScanner, ToolBroker) never is (`src/plugins.ts` refuses it at load, `tests/plugins.test.ts` keeps an allow-list). The new settable key `integrations` (runtime, global, `free`, default `{}`) maps an integration interface to a plugin name, e.g. `{ "tacit": "agents-home" }`; it overrides that interface's `plugins` key in factory.config.json, and with no entry the config decides as before. `plugins` itself stays review-only for every interface.
  - **Why a new key.** The owner turns their own ledger on from the dashboard in one click; a reviewed PR and a restart for a plugin that only reads the owner's own CLIs was the slowest path and the Rules page had to explain it. The same key serves later integrations (the calendar sources).
  - **Owner only, free.** A set or reset of an owner-only key (`OWNER_KEYS` in `src/core/settings.ts`) asks `SettingsDeps.mayOwn`: the Settings route's POST runs the page's owner check (`rules-api.ts` `ownerOf`: the store's local owner), and refuses when no owner check is wired. No grant beyond that (`approve_merge` is not asked); either direction is allowed. The CLI (`factory settings set integrations …`), run by the owner on their machine, asks no owner check.
  - **Checked against the registry.** A set naming a guard, any interface not marked `integration`, an unknown interface or a plugin name the registry does not hold for the interface is refused (`checkIntegrations`); a refused set writes no override and no audit row. The stored value is a plugin name only, never a path: the agents home stays `AGENTS_HOME` or `~/.agents`, so a runtime setting never names an executable.
  - **No restart.** Each process holds the integration's plugin behind a live holder (`src/runtime/live-tacit.ts`): `LiveSettings.refresh` (its `integrations` option) hands it the resolved entry after each read, and it rebuilds the plugin when the name changes. The controller and the worker pool switch by their next tick; `factory ui` builds its own holder and LiveSettings (`uiTacit` in `src/ui/rules-api.ts`) and refreshes them before each Rules request. No process keeps a second copy of the entry; a stored name that no longer builds keeps the plugin in use and is logged once.
- **Sessions and the Settings page read the learned layer (decision changed 2026-11-11; replaces "Read" and "Reset" of the learned decision below, where only the controller and worker pool read the layer, the Settings page resolved overrides only, and every learned reset asked `approve_merge`, see History).**
  - **Sessions.** `buildSessionParts` (`src/compose.ts`) builds a `StoredLearnedSettings`, refreshes it with the session's `LiveSettings`, and hands it out as `SessionParts.learned`; `sessionDeps` (`src/session-cmd.ts`) gives it to `Sessions`, so a session's split check and pre-push size gate use the learned `max_diff_lines` of its project, as a run's do.
  - **Settings API.** `GET /api/v1/settings` returns, per per-project gate key, each stored learned value with its project label, its value, `source` (the layer `settingsFor` resolves for that project: `learned` while in force, else the tighter layer), `evidence_run_ids` and `set_at`. The evidence is the newest audit row that wrote the stored value; the set time is the stored row's `updated_at`. `LearnedSettingsSource` gained an optional `record(project, key)` for these; the gates still need only `get`.
  - **Page.** Each per-project key on the Settings page shows the configured project's learned value next to its file and override values: in force or ignored, set how long ago, its evidence runs, and a "Reset learned" button (`POST` with `learned: true`).
  - **Reset rule.** `factory settings reset <key> --project <owner/name> --learned` and the page's reset run one check (`resetLearned` in `src/settings-cmd.ts`, reached through `runSettings`): it asks `approve_merge` only when the reset loosens the value in force (the learned value is in force and the layer below it is looser). A learned value already out of force clears with no grant. A refusal has the same message on both and writes no audit row. One owner: the owner holds `approve_merge`.
  - **Not changed.** Nothing new writes learned values and no migration is added; the learner (#497) is as below.
- **The daily improve run learns a tighter `max_diff_lines` (decision changed 2026-11-11, issue #497; replaces "Learned layer" under "Settings resolve in layers", where nothing wrote learned values and a learned value was checked only against the global value, see History).**
  - **When.** Only in the daily improve run (decision 2 of #497), after its report is stored (`src/worker/runs/improve/improve.run.ts` calls `learnFromReport`, `src/core/learned-settings.ts`). A manual or triggered improve run learns nothing. The report holds only the project's runs (07-self-improvement).
  - **What.** When the report has 3 or more `diff_too_large` runs (its groups and one-run patterns), the learner writes `max_diff_lines` = 80% of the value in force (decision 1 of #497), rounded down, never below 1, and only when that is tighter. The value in force is `settingsFor` with the stored learned value. No other key is learned and nothing is ever loosened from evidence. Why 3: one or two oversized changes are usually one big item, three in a day is a pattern.
  - **Store.** `runtime_learned_settings` (project, key, JSON value, updated_at) and the audit `runtime_learned_setting_changes` (old and new value, the evidence run IDs as JSON, the window end, the actor `system:improver`, the time; unique on project, key and window end), one timestamped migration `src/runtime/migrations/20261111T1400-runtime-learned-settings` for SQLite and MySQL. The write is conditional on the stored value the learner read and on no audit row for the window, with the audit row in the same transaction: a retry, a rerun of the same window or a second worker writes nothing.
  - **Check.** `settingsFor` takes a learned value only when it is at or under the project override, else the global value (before: the global value only). So a project override or a global value lowered below it puts the learned value out of force, without deleting it.
  - **Read.** `StoredLearnedSettings` caches the stored rows so `settingsFor` stays synchronous; `LiveSettings.refresh` refreshes it (each tick, each claim). `src/compose.ts` builds one per process and gives it to the controller, the worker pool and (above) sessions.
  - **Reset.** `factory settings reset max_diff_lines --project <owner/name> --learned` clears the learned value with one audit row; who may run it is the "Reset rule" above.
- **A loosening `factory settings` change needs `approve_merge` (decision changed 2026-11-09, owner decision; before: only `mode` and `auto_merge_max_tier` asked, so any CLI user could loosen a tighten-only key, see History).** A set or reset that leaves a `tighten-only` key (the catalog's `direction`, compared with `loosens` in `src/shared/setting.ts`) looser than its effective value before the change (`phases_auto_approve true`, a higher `max_diff_lines`, a reset of a tighter override) asks `SettingsDeps.mayApproveMerge`, the same check `mode` uses; a refusal writes no override and no audit row. Tightening and `free` keys are not asked. The CLI and the Settings page both run it (`runSettings`). Solo: the local owner holds `approve_merge` with no setup, so nothing changes. Enterprise: a requester may tighten but not loosen.
- **Every setting is a discovered descriptor (decision changed 2026-11-08, RFC 0015 M10; before: the key lists, descriptions and "applies at" texts lived only in `src/core/settings.ts`, see History).** Each settable and PR-only key is one `src/<owner>/settings/<key>.setting.ts` file (`defineSetting`, `src/shared/setting.ts`): key, owner component, type, default, description, when a change applies, `direction` (`tighten-only` or `free`, with the order that is tighter), `changed_by` (`runtime` or `review`), `scope`, and `guard` or `dial` with the grant a runtime change needs. The catalog page `docs/settings.md` is generated from them (`npm run settings:catalog`). The resolver (`resolveSettings`) still types its values by the key lists in `src/core/settings.ts`; `tests/settings-catalog.test.ts` holds both equal until that file moves into the runtime. Every settings folder is on the gate list (`PROTECTED_PATHS.guard_settings`).
  - **Settings only tighten (`tests/architecture/settings-monotonic.test.ts`).** The levels are owner → org → project → pack → user (`resolveLevels`, `src/runtime/settings/monotonic.ts`): the owner's reviewed config may set any value; a lower level's value that loosens the one in force is ignored with its reason. A guard (`secrets`, `egress`, `broker`, `deny_paths`) is set by the owner's config only. A dial changes by review only, or at runtime with its grant (`mode`, `auto_merge_max_tier`: `approve_merge`). Today's runtime overrides map onto the levels unchanged: a global override is the owner's live value, a project override the project level. Solo and enterprise are the same; the org, pack and user levels have no writer yet.

- **`mode` and `auto_merge_max_tier` are settable (decision changed 2026-11-08, issue #444; before: twenty-two settable keys, the auto-merge dial fixed at 0 in the file, and no mode, see History).** `mode` (`"manual"` or `"auto"`, default `"manual"`) decides whether the factory may approve specs and merge local changes itself (design 03-risk); `auto_merge_max_tier` (a whole number from 0 to 3, default 0) is the highest tier auto mode merges at. Neither is a `factory.config.json` key; the file's `dials.auto_merge_max_tier` must stay 0. No migration: each is one row in the existing override table, audited like every set.
  - **Per project.** `mode` takes `--project` (the configured repo's `owner/name`), the first per-project key that is no gate: a project's mode stands on its own, with no tighten-only check, outside the per-project layers (`mode` stays `free`, owner confirmed 2026-11-09: #444 lets a project choose auto under a global manual, with `approve_merge`). `GATE_SETTABLE_KEYS` holds the three gates; `PROJECT_SETTABLE_KEYS` is them plus `mode`. `auto_merge_max_tier` is global.
  - **Who may change them.** A set or reset of either needs `approve_merge` on the configured project (`APPROVE_MERGE_KEYS`, `SettingsDeps.mayApproveMerge`): the CLI asks the local auth plugin over the local grants, the Settings page the page's own approve_merge check (as its Merge button), both with no forge call. A refusal writes no override and no audit row. Solo: the first local identity is the owner and holds `approve_merge` with no setup. Enterprise: an approver or the owner; a requester is refused.
  - **`factory mode auto|manual [--project <owner/name>]`** is `factory settings set mode <mode>`, the same checks and one audit row naming the actor and the time. `factory settings` now writes as the CLI identity (`cli_user`, else `local:<git user.email>`, else the OS user), the identity the approve_merge check asks about and the one the page writes as.
  - **Read live.** The controller reads both through `LiveSettings` at each decision (refreshed each tick), so a flip on one replica applies on every replica at its next tick, with no restart. A stop condition (03-risk) writes `mode` back to `"manual"` as `system:auto`, at the level the auto mode was stored at.

- **Settings resolve in layers.** The per-project keys are exactly `max_attempts`, `max_diff_lines`, `max_diff_files`, `budgets` and `floors`. Each resolves in this order, first hit wins: learned value → project override (`projects["owner/name"]`) → `defaults` → built-in default (3, 1500, 40, no budgets, no floors). `settingsFor(project, layers, learned?)` in `src/core/settings.ts` is pure and returns each key's value and the layer it came from; the controller and worker read these keys only through it (`tests/settings.test.ts` fails on any other read of them from a config object).
  - **Config shape.** `defaults` holds the global values; the same keys at top level still load as before (the checked-in config is unchanged), and setting one key in both places fails at startup. `projects` is keyed by project ID in the store's form, `owner/name` (`WorkItem.project`), not `github.com/owner/repo`: #98 (project IDs) has not landed, so this uses the ID the store already has. A project ID other than the configured repo's fails at startup; running several repositories at once is a separate issue.
  - **Tighten only.** Every per-project key is a gate, so a project may not loosen it past the global value (`defaults`, else built-in): a number above it fails at startup; `budgets` is the whole map, so a tier above the global value, or a global tier left out (no limit), fails; `floors` is the whole list, so it may add entries and raise a tier, but leaving out a global prefix or lowering its tier fails. Equal or tighter passes.
  - **Unknown keys.** `defaults` and each project accept only the per-project keys. `auto_merge_max_tier`, `dials`, `plugins`, `repo` (so `test_command` and `install_command`: a no-op command would loosen the test gate and two commands cannot be compared), `budget_min_sample` (not a gate) and every guard setting are unknown keys there, reported in the same format as top-level unknown keys (#84), with the project in the path (`projects["owner/name"].key`) and a suggestion when one is close.
  - **Learned layer.** Written only by the daily improve run's learner, for `max_diff_lines` (see "The daily improve run learns a tighter `max_diff_lines`" above). A learned value that is not at or under the project override, else the global value, is ignored, so the layer can never weaken a human check.
  - **Display.** `factory doctor` prints one `ok` line per project and per-project key with its effective value and layer (`setting for owner/name: max_attempts = 3 (defaults)`). The status page's Health panel shows the same lines, since it runs the same `doctorChecks`. No store change and no migration.

- **`toolchain` is a PR-only key (decision changed 2026-11-08, issue #334; before: twelve PR-only keys, see History).** The `toolchain` block (`caches`, `env`, `warm_command`; `05-sandbox.md`) decides what agents may read and the env they get, so it changes only by a reviewed PR: `factory settings set toolchain …` (and the Settings page) is refused with "changes by PR only", and the page lists it with the other PR-only keys and its description. On a shared store (MySQL) it is one of the keys taken only from the checked-in file, like `dials`, `floors`, `plugins`, `permissions` and `auth`. It is not a per-project key: `defaults` and `projects` blocks refuse it as an unknown key.

- **`standing_approvals.threshold` is settable (decision changed 2026-11-07, issue #299; before: eighteen settable keys, none for standing approvals, see History).** `factory settings set standing_approvals.threshold <n>` (and the Settings page) sets how many unchanged spec approvals in a row propose a standing rule. Global only, default 10, a positive whole number (anything else is refused on set and ignored, with the file value kept, when the stored overrides load), audited like every set, and read at the controller's next spec approval with no restart (`LiveSettings.values()`). It is not a `factory.config.json` key: a `standing_approvals` block in the file is an unknown key. See `05-standing-approvals.md`.

- **`hold_policy` is settable (decision changed 2026-11-07, issue #314; before: seventeen settable keys, none for coordination, see History).** `factory settings set hold_policy <json>` (and the Settings page) sets what a run held by coordination cost does: `{"mode":"hold"}` (default), `{"mode":"run_after_minutes","minutes":20}` or `{"mode":"run"}`. It is global only (no `--project`, until #99), checked with the config loader's message (`parseHoldPolicy` in `src/core/coordination.ts`), and applies at the next claim: `LiveSettings` puts the effective value into `FactoryConfig.coordination`, which each worker passes to `claimRun`. `hotspot_paths`, `mechanical_paths` and `hotspot_mode` stay file-only; `max_coordination_cost`, `hotspot_weight` and `mechanical_weight` are settable since 2026-11-12 (above). The settable-keys table below lists it. See `05-coordination.md` Hold policy.

- **The alarm keys are settable (decision changed 2026-11-07; before: nineteen settable keys, see History).** `alarm_repeat_count` (default 3), `alarm_window_minutes` (default 60) and `alarm_restart_count` (default 5) are top-level `factory.config.json` keys (positive integers, or startup fails) and `factory settings set` keys. They are global only (no `--project`) and apply at the next alarm step, which runs on each poll, with no restart. `LiveSettings` puts the effective values into the controller's config view. Why each is a setting and not a constant is in `05-alarms.md`. The settable-keys table below lists them.

- **Settings change from the dashboard too (decision changed 2026-11-07, issue #236).** The Settings page of the dashboard app (§9) is a second front end for `factory settings`: `GET /api/v1/settings` reads, `POST /api/v1/settings` writes, and every write runs `runSettings` (`src/settings-cmd.ts`), so the page accepts, refuses and stores exactly what the CLI does, with the CLI's messages. The settable keys, checks, storage and audit rows ("Settings change at runtime", under History) are unchanged; no store method and no migration was added.
  - **Read.** `GET /api/v1/settings` (`src/ui/settings-api.ts`) returns each settable key with its effective value (JSON text), source (`override`, `file`, `default`), the file value, the built-in default, the project values with their source, "applies at", and for `workers` its `max_workers` limit; the PR-only keys with their descriptions and no write control (no per-row note since 2026-11-10: the page heading says they change only in `factory.config.json` by a reviewed PR, design 09); the ignored overrides; and the last 50 audit rows, the rows `settings history` shows. Project labels, actor IDs, values and messages pass the `Withholder`; a project key is never returned.
  - **Descriptions (issue #269; moved 2026-11-08, RFC 0015 M10).** Each settable key and each PR-only key has a one-sentence description of what it controls, in its `*.setting.ts` file (`description`, beside `applies`), read through the settings catalog (`loadSettingCatalog`, `src/runtime/`). `tests/settings-catalog.test.ts` fails when a settable or PR-only key has no setting file. `GET /api/v1/settings` returns it as `description` on each entry of `keys` and `pr_only`, through the `Withholder` like the other strings, and the page shows it under the key name. The web code holds no description text, and `factory settings` prints none.
  - **Write.** The body is `{ action: "set" | "reset", key, value?, project?, learned? }`; `value` is JSON text, as the CLI takes it; `learned: true` (a reset with a project only) is `settings reset --learned`. Success: 200 with the CLI's lines. A refusal from the shared checks (heartbeat × 2 < lease, retry order, a PR-only key or a guard, workers above `max_workers`, a project value looser than the global one, a reset with no override): 422 with the CLI's `refused: …` line in `error`, and nothing stored. A body that is not a set or reset: 400.
  - **Guards, in order.** Host must be 127.0.0.1 or localhost (the existing guard, 403); `Origin` must equal the Host's own `http://` origin, and a missing one is refused (403); `Content-Type` must be `application/json` (415); the `x-csrf-token` header must equal the per-process token (403). The token is 32 random bytes made when the UI process starts, held only in memory (never in the store, on disk or in the HTML), and returned by `GET /api/v1/settings`; a restart invalidates it and a page reload fetches the new one. Bodies over 64 KiB: 413. Every other method on every other path still answers 405.
  - **Project writes without the forge.** The UI process builds no GitHub client and reads no forge credential. For `project` it finds the configured repo's project key from the stored project label (`storeProjectResolver`: the project keys of stored overrides and recent work items, the first whose label ends in `/owner/name`). With no stored label the write is refused with a pointer to `factory settings … --project` on the command line. This is the one place the page differs from the CLI, which asks the forge.
  - **Actor.** A page write stores `local:<OS login>` of the user running `factory ui`, never a display name, as the CLI does.
