# 8. Enterprise: settings in layers

- **Settings resolve in layers.** The per-project keys are exactly `max_attempts`, `max_diff_lines`, `max_diff_files`, `budgets` and `floors`. Each resolves in this order, first hit wins: learned value → project override (`projects["owner/name"]`) → `defaults` → built-in default (3, 1500, 40, no budgets, no floors). `settingsFor(project, layers, learned?)` in `src/core/settings.ts` is pure and returns each key's value and the layer it came from; the controller and worker read these keys only through it (`tests/settings.test.ts` fails on any other read of them from a config object).
  - **Config shape.** `defaults` holds the global values; the same keys at top level still load as before (the checked-in config is unchanged), and setting one key in both places fails at startup. `projects` is keyed by project ID in the store's form, `owner/name` (`WorkItem.project`), not `github.com/owner/repo`: #98 (project IDs) has not landed, so this uses the ID the store already has. A project ID other than the configured repo's fails at startup; running several repositories at once is a separate issue.
  - **Tighten only.** Every per-project key is a gate, so a project may not loosen it past the global value (`defaults`, else built-in): a number above it fails at startup; `budgets` is the whole map, so a tier above the global value, or a global tier left out (no limit), fails; `floors` is the whole list, so it may add entries and raise a tier, but leaving out a global prefix or lowering its tier fails. Equal or tighter passes.
  - **Unknown keys.** `defaults` and each project accept only the per-project keys. `auto_merge_max_tier`, `dials`, `plugins`, `repo` (so `test_command` and `install_command`: a no-op command would loosen the test gate and two commands cannot be compared), `budget_min_sample` (not a gate) and every guard setting are unknown keys there, reported in the same format as top-level unknown keys (#84), with the project in the path (`projects["owner/name"].key`) and a suggestion when one is close.
  - **Learned layer.** `LearnedSettingsSource` is an optional dependency of the controller and worker. Nothing writes learned values yet and the composition root passes none. A learned value that would loosen a gate past the global value is ignored, so the layer can never weaken a human check.
  - **Display.** `factory doctor` prints one `ok` line per project and per-project key with its effective value and layer (`setting for owner/name: max_attempts = 3 (defaults)`). The status page's Health panel shows the same lines, since it runs the same `doctorChecks`. No store change and no migration.

## History

- **Settings resolve in layers** (decision changed 2026-11-01, issue #99). Before: every setting had one top-level value in `factory.config.json` for the whole factory, read straight from config by the controller, worker and budget code. This changes the single-value config of the §3 floors, the §4 size gate (`max_diff_lines`, `max_diff_files`), §5 Restarts (`max_attempts`) and the §6 Budgets "Config" decision.
- **Settings change at runtime (decision changed 2026-11-03, issue #157; before: config was parsed once at startup and handed to the controller and worker pool as a frozen object, the pool built its loops once, so changing any setting needed a PR, a merge and a restart).** Fifteen keys can be changed while the factory runs with `factory settings set <key> <value>`; every other key still changes only by PR.
  - **One effective value.** `resolveSettings` in `src/core/settings.ts` gives each settable key's value: the stored override if set, else the `factory.config.json` value, else the built-in default. The controller, the worker pool and the `factory settings` commands all read through it. Precedence with the layers above: a global override sits above the file's top-level (or `defaults`) value, a project override above the file's `projects` block, and the learned layer stays on top.
  - **Storage.** Two tables, both with a `project_key` column ('' for global, else a project key; not named `project`, so the owner/name project-key step never reads them): `settings_overrides(setting_key, project_key, value_json, set_by, set_at)` and the audit trail `settings_changes(seq, setting_key, project_key, old_value, new_value, actor, at)`. Values are JSON text. SQLite migration 15; MySQL step 0015 (an inline step in `src/impl/store/mysql/migrations.ts`, since 0013 was already taken by the inline phases step and 0014 by identity links; the issue named it 0013). Each set and reset is one transaction with its audit row: if the audit insert fails, the override is unchanged. Concurrent sets: last writer wins and the audit rows keep commit order. The actor is an ID, `local:<OS login>`, never a display name. The settings commands refuse on MySQL while steps are pending, as the other commands do.
  - **Live reads.** One `LiveSettings` per process (a cache of the file values plus the stored rows; no replica needs it) is refreshed by the controller at the start of each tick and each public tick step, by the worker pool each tick, and by a worker before each claim and each lease renewal. A worker reads the values once at its claim and keeps them for that run. A stored override that fails a check (bad JSON or value, heartbeat × 2 ≥ lease, base above max, a project value looser than the global value, a global value tighter than a project's file value) is ignored and logged once; the process keeps the file value and keeps running.
  - **Worker pool.** The pool has the file's `workers` slots. Each tick it starts the slots below the effective `workers` and stops the rest: a stopped slot claims nothing more, finishes its run and ends; it starts again when `workers` rises. The file's `workers` sizes the supervisor's index block, so `settings set workers` above it is refused and a stored value above it is read as the file's value.
  - **The settable keys and when each applies** (no restart for any):

    | Key | `--project` | Applies at |
    |---|---|---|
    | `max_attempts` | yes | the controller's next decision |
    | `max_loops`, `max_restart`, `retry_base_ms`, `retry_max_ms` | no | the controller's next decision |
    | `max_diff_lines`, `max_diff_files` | yes | the next run that starts |
    | `run_timeout_ms`, `models`, `model_by` | no | the next run that starts |
    | `poll_interval_ms`, `tick_ms` | no | the next tick |
    | `heartbeat_ms`, `lease_ms` | no | the next lease renewal (`lease_ms` also the next claim) |
    | `workers` | no | the worker pool's next tick; at most the file's `workers` |
  - **Refused.** PR-only keys are refused with "changes by PR only": `plugins`, `repo`, `store`, `floors`, `dials`, `auth`, `permissions`, the guards (`secrets`, `egress`, `broker`), `deny_paths`, `env`. It is an allow-list, so every key not in the table is refused as not settable, among them `budgets`, `inbox_retention_days`, `stats`, `ui`, `intake_label` and `branch_prefix` (until the owner decides), and `auth_pause_ms`. A refused command writes no override and no audit row.
  - **Checks on set.** A value is checked with the config loader's own message for that key. `heartbeat_ms` and `lease_ms` are checked together (heartbeat × 2 < lease) using the other key's effective value, and so are `retry_base_ms` ≤ `retry_max_ms`. `--project` takes only `max_attempts`, `max_diff_lines`, `max_diff_files`, and only the configured repo's `owner/name`; a project value may only tighten its gate against the global value, and a global value that would leave any project's value looser is refused with the project named. Nothing is clamped silently. A set to the current value still writes an audit row. `settings reset` on a key with no override is refused with no audit row; resetting a project override needs `--project`; a reset that would break the heartbeat or retry check is refused.
  - **Not covered.** The update run's own timeout in the updater keeps the file value until restart. No dashboard write path (#131, #124).
