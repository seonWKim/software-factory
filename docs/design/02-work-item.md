# 2. Work item (one shape, all sources)

`source{type, link}`, `requester_id`, `problem`, `resources` (pointers), `done_criteria` (frozen after confirm), `desired_output`, `scope` + *`allowed_paths`*, `tier 1–5`, `stage NEW|READY|RUNNING|REVIEW|CLOSED`, `blocked_on none|human|upstream|ci|budget` + `blocked_reason`, `close_reason completed|duplicate|wont_do|failed|rejected`, `loop_count`, `restart_count`, `token_cost`, `project`, `pr_number`, `merge_sha`, *`fixes_pr`*, `issue_text` (the issue as received at intake; triage overwrites `problem`, so a revision reads this), `revision_count` (`/revise` commands that started a triage run; not `loop_count`, which counts review loops), `spec_feedback` (text of the latest `/revise` or `/reject`; untrusted), `origin factory|adopted`, `head_branch` (an adopted PR's own branch), `last_head_sha` (the PR head the factory last recorded; §5, pull requests a person opens). Every change → `state_changes` row (IDs only, never names).

**Projects are keyed by the forge's repository ID.** A renamed or transferred repository split its items between the old and new path, and the path could not tell apart repositories on different hosts or providers. Now every project column (`work_items.project`, `unreviewed_merges.project`) and every lookup by project holds the **key** `<provider>:<host>:<repository id>`; for GitHub, `github:github.com:<repo node id>` (e.g. `github:github.com:R_kgDOabc123`). The node ID never changes with a rename or a transfer, so lookups by key still find the items created before one. The readable path is only a **label**, `<host>/<owner>/<name>` (e.g. `github.com/seonWKim/software-factory`), kept in the store (a `cursors` row `project_label:<key>`) so the status page shows it without calling GitHub.

**Startup reads the project key from the store, never waits on GitHub once it is known (2026-11-07).** GitHub resolves the configured `repo` (`GET /repos/{owner}/{name}`: `node_id` and the current `full_name`) once; the key is stored as the `cursors` row `project_key:<owner>/<name>` beside the label. Every later start (`build()`, `factory session`, `settings --project`, `golden add`) reads the key from the store first; a store written before this row finds the key from the stored label (as the Settings page does) and writes the row. A start with the key stored makes one background GitHub read to refresh the label (a rename); if GitHub fails or is rate limited, that read logs a warn and the stored key and label stay in use. If GitHub reports another node ID for the path, the new key is stored and the next start uses it. Only a first start (no key stored) waits for GitHub: a rate limit, an outage or a network error is logged and retried after 30 s, doubling up to 10 min, until it resolves or the process is stopped; nothing local can be waiting then, since every item, command and run carries the key. A 401 or 404 on a first start still stops it with a message naming the configured repo and the reason. The status page's Health panel warns while the key is not stored, and its GitHub API line shows GitHub's error. Solo: the SQLite store holds the row. Enterprise: replicas share it on MySQL, so a replica started during a GitHub outage reads the key the others stored; the row is written with a conditional set. The status page, comments and log lines show the label, never the key. The store refuses a project value that is not a key, and refuses to open while any row still holds `owner/name`. `npm run migrate` rewrites existing rows (SQLite and MySQL), resolving each `owner/name` through GitHub first and writing nothing if one fails; `--dry-run` lists the rows and changes nothing, a second run changes nothing. Rollout: run `npm run migrate` after stopping the old controllers and before starting the new ones. `factory.config.json` still names per-project settings by `owner/name`; they are re-keyed at startup. Only GitHub is implemented; the format leaves room for other providers and hosts. `source.id` values (`owner/repo#12`) are unchanged.

## History

- **Startup reads the project key from the store** (decision changed 2026-11-07). Before: every start resolved the configured repo through GitHub and stopped if it could not, so a rate-limited GitHub App installation (403) kept a new `factory dev` child from starting.
- **Projects are keyed by the forge's repository ID** (decision changed 2026-11-01). Before: `project` was the repository's path, `owner/name`, e.g. `seonWKim/software-factory`.
