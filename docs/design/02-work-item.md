# 2. Work item (one shape, all sources)

`source{type, link}`, `requester_id`, `problem`, `resources` (pointers), `done_criteria` (frozen after confirm), `desired_output`, `scope` + *`allowed_paths`*, `tier 1–5`, `stage NEW|READY|RUNNING|REVIEW|CLOSED`, `blocked_on none|human|upstream|ci|budget` + `blocked_reason`, `close_reason completed|duplicate|wont_do|failed|rejected`, `loop_count`, `restart_count`, `token_cost`, `project`, `change_ref` + `change_url` (the PR number as text and the PR link; returned on every read), `merge_sha`, *`fixes_pr`*, `issue_text` (the issue as received at intake; triage overwrites `problem`, so a revision reads this), `revision_count` (`/revise` commands that started a triage run; not `loop_count`, which counts review loops), `spec_feedback` (text of the latest `/revise` or `/reject`; untrusted), `origin factory|adopted`, `head_branch` (an adopted PR's own branch), `last_head_sha` (the PR head the factory last recorded; §5, pull requests a person opens). Every change → `controller_state_changes` row (IDs only, never names).

**A local work item may be built from a plain task, and its merge completes that task (decision changed 2026-11-12, issue #607; replaces "a merge closes only the work item").** `factory task build <task_id>` and the dashboard's Build this (design 02-tasks) create a local work item with source ID `local-task-<task id>` (link `local:local-task-<task id>`), title and problem the task's title, in intake with its triage run queued, and store the item's ID on the task (`controller_tasks.work_item_id`). The item's own shape and stages are unchanged; the link lives on the task, never on the item. When the item closes as completed by a merge (the local merge, the Merge button's PR merge, or a PR merged on the forge), the controller completes every open task linked to it, conditional on the task still being open, so a repeated event changes nothing. Any other close (rejected, failed, a closed PR) leaves the task open. Solo and enterprise behave the same.

**The PR is `change_ref`; `change_url` is the forge's own link (decision changed 2026-11-12: `pr_number` removed; before that 2026-11-08: where `change_url` comes from).** The core reads an item's PR from `change_ref` and converts it to a number only for a forge call, through one helper (`prNumber`, `src/core/change-ref.ts`); forge methods keep taking numbers (their parameter is `pr`). The store takes `change_ref` (a string) wherever it took a PR number: the lookup by PR, the adopted-PR input, the manual-push input, the unreviewed-merge input, and the item patch, whose PR field is `change_ref` (string or null) with an optional `change_url`. There is no `pr_number` column or field: the breaking migration `20261112T1200-controller-change-ref-only` (`src/controller/migrations/`) rebuilds `controller_work_items` and `controller_unreviewed_merges` without it, keeping every row, the `(project, change_ref)` indexes and the unique `(project, change_ref)` key of unreviewed merges under new index names (`<table>_by_<what>`), and points the work item's child tables back at the new table. The old tables stay as `legacy_controller_work_items` and `legacy_controller_unreviewed_merges` until a contract migration removes them (a follow-up issue). An unreviewed merge's `change_ref` no longer has to be a PR number. Run-outcome data keys and log fields named `pr_number` are not the column and keep their names. **`change_url` rule:** a PR the worker or an interactive session opens stores the `url` of outbound's `pr` delivery (`Forge.openPr`, RFC 0015 M7), recorded on the action and applied to the item on `DeliveryCompleted`. When no URL is given (an adopted PR, an older outcome, a broker with no URL), the store derives `https://<label>/pull/<n>` for a GitHub project with a stored label, else null. A later patch never overwrites a stored `change_url` (`COALESCE`). The state change records `change_ref`, the patched field. The lookup by PR matches `change_ref` only (migration 35 backfilled it from `pr_number`).

**Forge and source events name the PR as `change_ref` (decision changed 2026-11-08, phase 3: the event and source fields).** The forge's events are `change_open`, `change_merged`, `change_closed` and `change_unmergeable`, and each carries `change_ref`, a string like the store's; `pr_changes_requested` keeps its kind name with a `change_ref` field. The source events' PR (`revise_requested` and `resolve_requested` `pr`, a `/verdict` PR target) and `SourceAdapter.setStatus`'s PR argument are `change_ref` too. The controller compares an event's `change_ref` with the item's directly and converts with `prNumber` only for a forge call; the GitHub forge builds `change_ref` as the PR number as text and converts back only at a GitHub API call. The Slack status link is built from the item's `change_ref`. Stored state-change reasons (`pr_merged`, `pr_closed_unmerged`, `pr_closed_for_source`) keep their names and values. **Legacy command rows:** a GitHub command row's `args.pr` is written as `{ change_ref, head_branch }`; the reader still takes a row queued earlier with `{ pr_number, head_branch }` and maps it to the same event. Removal plan: drop the `pr_number` read once no controller older than this change is running and every command row queued before it is applied (the command step applies rows in seq order on every tick, so one release after this one is enough); the same change deletes its test. Solo and enterprise behave the same: a shared store may hold rows from an older replica during a rolling upgrade, which is why the fallback stays for a release.

**PR log and state-change keys are `change_ref` (decision changed 2026-11-12, phase 1 follow-up: the controller log and detail keys).** The unreviewed-merge log line, the PR feedback state-change detail and the budget checkpoint text (`CheckpointText`) name the PR as `change_ref`, the string ref (or null), not `pr_number`. The checkpoint comment still reads `PR #<n>` with a PR and `no PR yet` without one. Stored state-change and log rows are not rewritten: an older row keeps its `pr_number` key.

**Projects are keyed by the forge's repository ID.** A renamed or transferred repository split its items between the old and new path, and the path could not tell apart repositories on different hosts or providers. Now every project column (`work_items.project`, `unreviewed_merges.project`) and every lookup by project holds the **key** `<provider>:<host>:<repository id>`; for GitHub, `github:github.com:<repo node id>` (e.g. `github:github.com:R_kgDOabc123`). The node ID never changes with a rename or a transfer, so lookups by key still find the items created before one. The readable path is only a **label**, `<host>/<owner>/<name>` (e.g. `github.com/seonWKim/software-factory`), kept in the store (a `inbound_cursors` row `project_label:<key>`) so the status page shows it without calling GitHub.

**Startup reads the project key from the store, never waits on GitHub once it is known (2026-11-07).** GitHub resolves the configured `repo` (`GET /repos/{owner}/{name}`: `node_id` and the current `full_name`) once; the key is stored as the `inbound_cursors` row `project_key:<owner>/<name>` beside the label. Every later start (`build()`, `factory session`, `settings --project`, `golden add`) reads the key from the store first; a store written before this row finds the key from the stored label (as the Settings page does) and writes the row. A start with the key stored makes one background GitHub read to refresh the label (a rename); if GitHub fails or is rate limited, that read logs a warn and the stored key and label stay in use. If GitHub reports another node ID for the path, the new key is stored and the next start uses it. Only a first start (no key stored) waits for GitHub: a rate limit, an outage or a network error is logged and retried after 30 s, doubling up to 10 min, until it resolves or the process is stopped; nothing local can be waiting then, since every item, command and run carries the key. A 401 or 404 on a first start still stops it with a message naming the configured repo and the reason. The status page's Health panel warns while the key is not stored, and its GitHub API line shows GitHub's error. The SQLite store holds the row, written with a conditional set. The status page, comments and log lines show the label, never the key. The store refuses a project value that is not a key, and refuses to open while any row still holds `owner/name`. `npm run migrate` rewrites existing rows, resolving each `owner/name` through GitHub first and writing nothing if one fails; `--dry-run` lists the rows and changes nothing, a second run changes nothing. Rollout: run `npm run migrate` after stopping the old controllers and before starting the new ones. `factory.config.json` still names per-project settings by `owner/name`; they are re-keyed at startup. Only GitHub is implemented; the format leaves room for other providers and hosts. `source.id` values (`owner/repo#12`) are unchanged.

## History

- **A merge closes only the work item** (decision changed 2026-11-12, issue #607). Before: no work item had a link to a plain task, so the merge paths closed the item and released its dependents, and a task the change was made for stayed open.
- **`pr_number` removed** (decision changed 2026-11-12, the change fields phase 4). Before: the store wrote `pr_number` from `change_ref` on `controller_work_items` and `controller_unreviewed_merges`, `WorkItem` and `UnreviewedMerge` carried it, an unreviewed merge's `change_ref` had to be a PR number (its mirror column was NOT NULL), and the lookup by PR fell back to `pr_number` for a row with `change_ref` NULL.
- **PR log and state-change keys are `change_ref`** (decision changed 2026-11-12). Before: the unreviewed-merge log line, the PR feedback state-change detail and `CheckpointText` kept the key `pr_number` (a number); log fields and state-change details kept their names.
- **Forge and source events name the PR as `change_ref`** (decision changed 2026-11-08). Before: the forge events were `pr_open`, `pr_merged`, `pr_closed` and `pr_unmergeable` with `pr_number` (a number), the source events' PR and `setStatus` took `pr_number`, command rows stored `args.pr.pr_number`, and the Slack status link was built from `pr_number`.
- **`change_url` comes from the forge's open result** (decision changed 2026-11-08). Before: the store wrote `change_ref` and `change_url` beside a patched `pr_number`, `change_url` always derived from the project label (`https://<label>/pull/<n>`), and the core read `pr_number`; neither was patched directly.
- **Work items carry `change_ref` and `change_url`** (decision changed 2026-11-08). Before: the store wrote both columns (migration 35) but the work item shape listed only `pr_number`, so no read returned them and the item intake returned for an adopted PR did not match its stored row.
- **Startup reads the project key from the store** (decision changed 2026-11-07). Before: every start resolved the configured repo through GitHub and stopped if it could not, so a rate-limited GitHub App installation (403) kept a new `factory dev` child from starting.
- **Projects are keyed by the forge's repository ID** (decision changed 2026-11-01). Before: `project` was the repository's path, `owner/name`, e.g. `seonWKim/software-factory`.
- **MySQL text removed from the current decisions** (decision changed 2026-11-11, issue #567). Before: the `change_ref` migration rebuilt the tables "on SQLite and MySQL"; the lookup by PR was backfilled by "migration 35 and MySQL step 0035", ending "Solo (SQLite) and enterprise (MySQL) behave the same"; the project-key paragraph said "Enterprise: replicas share it on MySQL, so a replica started during a GitHub outage reads the key the others stored; the row is written with a conditional set" and that `npm run migrate` rewrote rows "(SQLite and MySQL)".
