# 11. Signal ledger

- **One ledger of the signals the store already holds, tagged by the entity they are about (new decision, 2026-11-11, issue #491).** Gate decisions, revision and retry requests, verdicts, review findings, failed runs, reverts and fix-forwards were each stored in their own table and nothing gathered them or said which role or standing rule a signal was about. Now the controller's `signals` unit (`src/controller/units/signals/`) writes one `controller_signals` row per such record, so a later step can route a signal to the entity that should change. Routing, stats and any learning step that reads the ledger are not part of this decision.
  - **Table.** `controller_signals` (`id`, `source`, `source_ref`, `kind`, `work_item_id`, `role`, `rule`, `at`), unique on (`source`, `source_ref`), indexed on (`source`, `at`) and (`work_item_id`, `at`). Created by the timestamped migration `src/controller/migrations/20261111T1210-controller-signals.migration.ts`; no numbered MySQL step (that list is frozen).
  - **Sources.** Each source is one `src/controller/signals/<name>.signal.ts` (`defineSignal`), found by discovery (`*.signal.ts`, a `signal` entry in the registry's descriptor patterns). It names the kinds it writes (a fixed list) and reads its records through the controller's read-only store accessors. Adding a source changes no unit code. The initial four:
    - `state_changes`: one row per state change whose reason is a gate decision (`spec_approved`, `spec_rejected`, `floor_tier_approved`, `rule_of_two_approved`, `standing_approved`; the actor is a person, `system:auto` or the standing rule), a revision or retry request (`spec_revision_requested`, `retry_requested`, `pr_revise_requested`, `pr_changes_requested`), a revert or a fix-forward (`reverted`, `fixed_forward`). Key: the state change ID; kind: its reason.
    - `verdicts`: one row per verdict row, `human_verdict` for a `/verdict`, `implicit_verdict` for one read from a PR event (a merge, a person's push to a factory PR, a revert). Key: the verdict ID.
    - `failed_runs`: one row per run that ended `failed`, kind `run_failed`. Key: the run ID.
    - `review_findings`: one row per finding of a finished review run, `review_finding_code` or `review_finding_spec` by the finding's kind. Key: `<run ID>:<finding index>`. Only the finding's kind is read, never its text.
  - **Tags.** `work_item_id` and `at` come from the source record (a run's finish time, or `updated_at` on an older row with none). `role` is the run kind's role (`triage`, `implement`, `review`, `resolve`; a fixed list) for a run-related signal, else null. `rule` is the standing rule ID (`spec-t1`) when a standing rule approved the item (its `standing_approved` state change), else null. A record of a kind or role its source does not list is left out with a warning. Skill and doc-index tags wait until a run's loaded skills are stored.
  - **IDs only.** A row holds IDs, enum codes and times: no text, no display name, no transcript. A run's transcript is referenced by the run ID alone, and no source reads a file. So the ledger needs no egress scan.
  - **Idempotency.** Each row is an insert that skips a stored (`source`, `source_ref`), so a second tick, a crash between writes, or a second replica adds nothing. The unit holds nothing in memory: on each poll, each source reads from the newest stored `at` of its own source, less a 10-minute overlap (`OVERLAP_MS`), so a record stored a little late is still read. A record stored with a time older than that is not.
  - **Pure.** The unit is split into `load` (the reads: the sources, the cursor, the standing approvals) and `decide` (the rows); the router commits them. It writes no state change, verdict, run, outbound intent or item field.
  - **Backfill.** A source with no stored row reads every record it has, so the first tick after the migration writes the signals already stored, once, with the same keys as later ones.
  - **Solo and enterprise.** Solo: SQLite, the migration runs when the store opens. Enterprise: MySQL, the same migration runs in `npm run migrate`; the table is shared, and the unique key keeps several replicas from writing a signal twice.
