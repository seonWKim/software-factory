# 5. Interactive sessions

**Decided 2026-11-01 (issue #112).** A person's own LLM session on an item is a new run kind, `interactive`: written running with a lease by `factory session start`, with the person's user ID as its actor, never claimed by a worker, and counted as the item's branch writer, so implement and update runs wait while their item overlaps an open session and a session does not start over a running one. Gates at `session finish`: the scope gate, the size gate (the same `max_diff_lines` and `max_diff_files`), the floor check (a hit refuses the finish; no tier is raised) and `repo.test_command`; push and PR only through the broker. A finished session moves the item to REVIEW with a review run. An abandoned session (`abandoned`), or one whose lease expired (the reaper writes `session_lost` and never requeues it), releases the item: RUNNING, `blocked_on: human`, `blocked_reason: session_released`, nothing queued. Exception: the session's LLM runs as the owner with the owner's access, outside the run-folder rule (architecture §5); the gates at finish are the factory's check, not a sandbox.

- **The finish gates diff against the base the session absorbed (decision changed 2026-11-21, wi_866cdd08; current; changes "Gates at `session finish`" above, which diffed against the base the session started on, see [History](history/05-interactive-sessions.md)).** Found 2026-11-21: wi_7391c26f merged main into its run folder to re-record a ratchet, and every file other items had changed on main (14, from dfb9ba3d) counted as outside `allowed_paths`, so its finish was refused until it was abandoned and refiled. Now `finish` picks its gate base (`gateBase` in `src/core/session.ts`) by the implement run's rule (`syncBase`, design 04-pre-push-gates): it fetches the base branch from the factory repo as the worker does (`sandbox.updateBase`, then `baseRefspec` from `src/core/worker-deps.ts`, the implement run's refspec rule, into the run folder's `origin/<base>`: the local `refs/heads/<base>` for a local item or `local_only`, else the factory repo's `origin/<base>`), and when that tip moved forward from the session's start base and HEAD contains it (the session merged or rebased onto it), the commit count, the scope, size and floor gates and the test selection diff against it. Otherwise, and when the fetch fails (local first), they diff against the start base, as before. Either way the gates see the tree HEAD has against one base commit, so only the item's own changes count, and an edit made inside the merge commit itself (a resolution touching an out-of-scope file) is still caught. A session that merged an older main than the tip is still refused for that main's files: merge or rebase onto the tip.
- **Workers claim only the run kinds in `worker_kinds`; the others wait for a session (decision changed 2026-11-21, wi_c1197be3; current; replaces "every worker claims every run kind", see [History](history/05-interactive-sessions.md)).** `worker_kinds` (src/worker/settings/worker-kinds.setting.ts) is a runtime, global, free list setting: the run kinds a worker claims, default all eight in this order, `triage, review, merge-check, update, restart, improve, implement, resolve` (`WORKER_KINDS` in src/core/settings.ts, the one list, since core cannot import the worker). The worker's claim passes the live value to `claimRun` at each tick, so a change applies at the next claim with no restart; one value for the whole store, no per-worker list. `factory settings set worker_kinds` and POST /api/v1/settings refuse an unknown kind, a repeated kind or an empty list with the same message, naming `worker_kinds` (to stop every claim, `workers pause`). With implement and resolve left out, those runs stay queued for an interactive session (its takeover of a queued implement run is unchanged), while reviews, merge checks and the other kinds keep flowing. An item whose queued run is of a kind left out says so on its state line ("Waits for a session: workers do not take implement runs", reason `waits_session`), derived from the setting at each read, with nothing stored on the item. Runs already queued or running are not changed. Why: a worker took the next queued implement run within seconds and held its paths, so the owner's session was refused, and `workers pause --all`, the only stop, also halted reviews and merges.
- **A session and the work beside it use the workers' coordination cost (decision changed 2026-11-21, wi_a1d21531; current; replaces "implement and update runs wait while their item overlaps an open session and a session does not start over a running one" above, where any shared allowed path counted, see [History](history/05-interactive-sessions.md)).** Found 2026-11-19: worker runs already weighed the design files as mechanical (0.25), but `session start` refused on any shared allowed path, so items whose plans all listed `docs/design.md` and `web/src/i18n/en.ts` were started one at a time. Now `startSession` (and a claim next to an open session) asks `sessionHold` in `src/core/coordination.ts`: the workers' `holdsOn` over each side's `files_to_change` (else `allowed_paths`), same project only, with the run's `coordination` settings (`StartSessionInput.coordination`; the session passes `config.coordination`, absent: `DEFAULT_COORDINATION`). It refuses (or a `--wait` start waits) only when the cost against one running run of another item is at or above `max_coordination_cost`; the refusal names the paths, the cost and the threshold (`overlaps at cost 3 (max_coordination_cost 2.5): src/worker/x.ts`). `hold_policy` does not apply: a session never starts over a hold. So mechanical paths, the unclaimed indexes (design 05-dependencies) and one or two ordinary shared files no longer hold a session.
- **A session keeps the machine awake while it holds its lease, and `session_lost` names the last heartbeat (decision changed 2026-11-21; current; changes "one whose lease expired (the reaper writes `session_lost` and never requeues it)" above, which kept no keep-awake and gave the bare detail "the session's lease expired", see [History](history/05-interactive-sessions.md)).** Once `factory session start` has its task, it holds the keep-awake plugin selected in `plugins.awake` (built as the worker's: the platform default when the key is missing, `caffeinate -w <pid>` on macOS) until its heartbeat stops (the task ended, or Ctrl-C), then releases it; a crash ends caffeinate with the process. A hold or release that throws is logged as a warning and the session goes on. The reaper still fails a lapsed interactive run with `session_lost` and never requeues it; its detail now reads `the session's lease expired; last heartbeat at <ISO 8601>`, the run's `updated_at` before the reaper's write. Why: three sessions ended `session_lost` with no evidence; a host sleep longer than `lease_ms` fits, and the session alone held no keep-awake. Lid-close sleep and the root cause of those three are not covered.
- **A start acts as the CLI identity; GitHub is asked only for `--as` with the GitHub source on (decision changed 2026-11-21; current; replaces "the person is the GitHub account of `--as <login>`, default `repo.owner`, looked up on every start", see [History](history/05-interactive-sessions.md)).** With no `--as`, `session start` takes the person from the CLI identity with no network call: `cli_user` from factory.config.json, else `local:<git user.email>`, else `local:<OS user>`, else `local:anonymous` (`cliIdentity`; the command supplies the environment to `sessionDeps`). A `github:<id>` cli_user stands for that GitHub account, as a lookup would give; any other ID is a local identity. `OwnerAuth` maps it to the factory user and the owner check decides, as before. `--as <login>` with the GitHub source on (`plugins.source` lists `github-issues`) calls `GET /users/<login>` and uses the account's numeric id as the subject; an unknown login or a failed call is refused naming the fix (check the login, or start without `--as`). `--as` with the GitHub source off is refused naming the fix (turn the source on, or drop `--as`). Why: a failed lookup (rate limit, offline, GitHub off) refused every start, and on 2026-11-20 two waiting starts failed this way; local first says a local action never waits on a sync plugin.
- **A waiting start reserves its NEW item (decision changed 2026-11-21; current; changes "a session does not start over a running one" above for `--wait`; replaces "nothing waits: a start over another item's running run is refused", see [History](history/05-interactive-sessions.md)).** `factory session start <id> --spec <file> --wait` on a NEW item nothing blocks reserves the item for the waiting session, in the store under the claim lock: one `worker_claim_pauses` row named `session_reserved:<item id>:<owner>` (the session's lease owner), `resume_at` its expiry, so no schema step, the item's version and stage are unchanged, and nothing is sent to a sync plugin. While it holds, `claimRun` claims none of the item's runs (its queued triage run stays queued) for any worker, and `startSession` refuses any other owner with `reserved`, which the CLI names (owner and expiry). The waiting CLI tries the start every 15 seconds on the injected Clock with the item as it is then (the same `startSession` overlap check), keeping one run folder for the whole wait; only running runs block, as before. The reservation ends when the session starts (in the same transaction), when the owner stops the wait (Ctrl-C releases it at once), when a check finds the item no longer NEW, or 2 hours after it was made (`RESERVATION_MS`, a constant, no setting): the claim reads the expiry, deletes the expired row and triage claims the item as usual. A wait does not resume after the CLI exits; the reservation then ends at its expiry. `--wait` without `--spec`, or on an item that is not NEW, is refused with the message a start without it gets. No `session reserve` command and no dashboard control: the dashboard gap is a follow-up.
- **A start takes over a queued implement or update run; a running one still refuses (decision changed 2026-11-19; current; replaces "a session refuses to start over a queued or running implement or update run", see [History](history/05-interactive-sessions.md)).** A start on an item whose implement or update run is only queued cancels those queued runs in one transition (reason `interactive_takeover`, the run ids in its detail), then the interactive task starts. A running implement or update run, or an open interactive task, still refuses with nothing changed.
- **Interactive tasks (new decision, 2026-11-19).** People call it an interactive task: `factory interactive start | status | note | finish | abandon`, with `factory session` as the same command. It works for local tasks: `sessionDeps` passes the local route, so a local item gets the local broker and sandbox, and `finish` commits the local branch and moves the item to REVIEW. The dashboard reads the run kind `interactive` as "Interactive task" (one helper for the runs table, the runners list, the tree and the transcript title) and shows that badge on a Work row whose current run is a running interactive one, and in the item page header while one is running. The store, API and run kind keep the name `interactive`.
- **Commands:** `factory interactive start | status | note | finish | abandon`, or the same under `factory session` (flags in `SET_UP.md`).
- **Schema:** migration 18 (SQLite) adds the run columns `actor_id` (the person's user ID, never a display name), `transcript_url` and `session_tokens`. Every other run, old rows included, keeps them NULL. A session's notes and its last `finish` attempt are kept in the run's `input`. `session_tokens` is added to the item's `token_cost` once, when the run ends.
