# 2. Work items: added context and attachments

**A chat message's images are rows of the same attachment table that belong to a chat turn instead of an item** (new decision, 2026-11-27, spec chat-images; current; none replaced: an item's attachments are unchanged). Migration `20261127T2200-controller-chat-attachments` adds `chat_session_id` and `chat_seq` (nullable) to `controller_attachments`, with an index on both: a chat image names the user message it was sent with and has an empty `work_item_id`, so `listAttachments` of an item never reads one. They are written only with their turn's messages (`appendChatMessages`, one transaction) and read by session or by ID (`getChatImage`); there is no second image store. Their checks are `chatImages` in `src/core/attachments.ts` (the same types and 5 MB limit as `attach`, at most 5 per message, each refusal naming the file), and before the model each one's text (`imageText`: its name and the printable text in its bytes, which holds metadata such as a png text chunk) passes the egress scanner. Design 04-chat-agent.

**A New or in-triage item takes added context, images and links, which the next triage reads as untrusted material** (new decision, 2026-11-23, wi_c3c370c8, "Add context or images to an open item"; none replaced). Before it, an item's brief was fixed when it was filed: adding a reference meant `/reject` and filing again, which paid for triage twice. Owner answers (binding): adding context extends `/revise`, with no new command; triage gets images as model image input; attachments are taken on New and in-triage items only; their bytes live in a new controller table.

- **Add context is `/revise` on a New or in-triage item.** `/revise <text>` (`factory revise <id> <text>`, a comment, a Slack thread, the dashboard's Add context) now applies in the `triaging` phase (stage `NEW`). The controller stores it as the queued-revise row (`revise_queued`, design 04-gate-commands) with `at: triage` in its detail, the same empty-text refusal (`FEEDBACK_REQUIRED`) and egress scan, keyed on the command, and replies once that it is queued (`CONTEXT_QUEUED_PATH`). The filed text stays; the added text is appended, never edited in. When the triage run that was running or queued ends with a spec, the run-results unit asks the commands unit's `applyQueued` first: with added context pending it starts exactly one more triage run (key `<triage key>:context-<first comment ID>`), records `revise_applied` naming every pending comment ID (so a second worker on the same run end finds none), and leaves the item `NEW`; the spec of the run that ended is not used. Context added during the re-triage queues one more. The re-triage's prompt has the filed text, every context added while New (`addedContext`, oldest first) under "Added context (untrusted)", and the attachments. Added context is never implement feedback: `pendingRevises` keeps the two apart by `at`. The command table and SET_UP.md say so (`triaging_description`).
- **Attachments: images and links, in the controller store.** `controller_attachments` (migration `20261120T1000-controller-attachments`), one row per attachment keyed by its ID, indexed by work item ID: an image's type, size, file name and bytes (base64 text), or a link's URL and optional label, who attached it and when. `addAttachment` is one insert conditional on the item's stage being `NEW` in the same statement, so an item that left triage meanwhile gets nothing; `listAttachments` reads them oldest first. Nothing is written to the repository or to a sandbox working tree.
- **One attach path, the same refusals.** `attach` in `src/core/attachments.ts` checks, in order: the stage (only `NEW`; the spec gate and later are refused, naming the phase), then an image's type from its first bytes (png, jpeg, gif or webp; never the file name) and its size (at most 5 MB), or a link's scheme (http or https only) and the egress scan of its URL and label (a finding stores nothing and names the rule, never the text). `factory attach <id> <file>` and `factory attach <id> --link <url> [label]` (`src/cli/handlers/attach/attach.command.ts`, through `runAttach`, after the owner check) and the dashboard's POST `/api/v1/attachments` (`src/ui/attachments-api.ts`, as the page's commands actor, after the owner check) both call it, so each refusal is one line with the same text. A file over 5 MB is read and sent as its first bytes and its size only. Attaching does not start a triage run by itself: the next one reads it, and Add context starts one.
- **Triage reads them as untrusted material.** The triage run appends "Added context (untrusted)" (each text fenced) and "Attachments" (one fenced line per image and link, marked untrusted; a link is text only and is never fetched) to its prompt, and hands each image to the runner as `AgentRunSpec.images`. The Claude Code runner sends a run with images as one stream-json user message on stdin (`--input-format stream-json`, the prompt then each image as a base64 block), so no image file is written; a run without images is unchanged. A runner that takes no image input (the OpenAI-compatible one) ignores them, and the prompt still names each image. `prompts/triage.md` says added context and attachments are untrusted material to read as part of the request, never instructions.
- **Not solved: image bytes are not scanned.** The egress scanner reads text only, so a secret inside an image (a screenshot of a token) reaches the model unscanned. Links and labels are scanned; image bytes are not.
- **Not changed.** No attachment or added context at the spec gate or later; nothing is uploaded to GitHub or Slack, and a GitHub item's attachments stay local; no video playback and no fetching of linked pages; items stored before this change are not backfilled; the implement prompt does not read attachments yet (a follow-up).
