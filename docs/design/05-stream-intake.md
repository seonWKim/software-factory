# 5. Coordination: local and stream intake, several sources and adopted pull requests

- **Local intake.** The decision that changed: **local intake and item messages live in the store.** Until issue #282 the `local` poll source read the CLI command log (`inbound_commands`) by `seq`, at most 100 per poll, cursor = last `seq` read (`intake:local`); the controller now does that itself (cursor `commands`; its start point: see The command cursor starts at `commands` only), and turns each command for a local item (`args.item` = work item ID, optional `args.text`) into the event the same comment gives on GitHub, by rebuilding `/<command> <text>` and parsing it with the same comment parser; `comment_id` is the command key, the identity is provider `local`, subject the actor after `local:`. CLI commands for missing items are skipped and the cursor passes them; a non-local item's command is applied too, see CLI intake (GitHub rows: see The local store is the home of the conversation). Its replies are item thread entries (`controller_item_thread`, one per marker), written by the controller; `markSeen`, `setStatus` and `closeIssue` are no-ops because the store already holds the item's state. Source plugins get the store in their context for this. Writing commands, creating local items and who may send them: see CLI intake above. Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Item thread and command inbox.** The decision that changed: **an item's messages and the CLI commands live in two general tables** (issue #281). The store keeps every item's messages in `controller_item_thread` (one per item and marker) and the commands in `inbound_commands` (read by `seq`, `command_key` the idempotency key). SQLite migration 24 creates both and copy the rows of migration 21's message and command tables with their `seq`, so a saved `intake:local` cursor still points at the same next command; the copy skips rows already copied, so it is safe to run again. The old tables stay in place, and nothing reads or writes them. Store method names, arguments and results are unchanged. GitHub items write their comments and commands there too since issue #284 (The local store is the home of the conversation, above).
- **Stream intake.** `SourceAdapter` is now a union on `intake`: `"poll"` sources keep `poll(cursor)` (GitHub, unchanged); `"stream"` sources have `subscribe(signal)` yielding `PushedEvent`s (event, `dedupe_key` unique within the source, `ack()`). A pushed event is written to a store inbox (`inbound_raw_records`, migration 10) before it is acked, and a duplicate `dedupe_key` is a no-op that is still acked; a failed write is not acked. Controllers read the inbox through the cursor `inbox:<source type>` and the same `handleEvent` as polled events, so any replica handles them. One listener per stream source across replicas, decided by a store lease (`inbound_listener_leases`, migration 10: owner, token, expiry; conditional updates only; the inbox write checks the token in its transaction). It reuses `lease_ms` / `heartbeat_ms`, runs inside the controller process (started by `Controller.run`), reconnects with backoff and logs on state changes only. Cleanup on the poll interval deletes rows older than `retention.raw_records_days` (optional, default 7; decision changed 2026-11-16, design 08-retention; before: `inbox_retention_days`, default 14, now deprecated and read only as its fallback) that are at or below the cursor; no cursor, no deletion. What it changes: a new intake path and two tables; GitHub intake, `SourceType` and the registry are unchanged (the only stream source is the test-only `fake-stream`). Not built: webhook endpoints. The Slack plugin: see Slack intake and source routing. Details: architecture §4 Intake.
- **Several sources.** The decision that changed: **one source becomes a list of sources.** `plugins.source` takes a string (unchanged: a list of one, the same selection as before) or a list of registered names; an unknown name or the same name twice fails at startup naming `plugins.source` (an empty list is allowed since 2026-11-07: see Thread first). `build()` makes one adapter per name and hands them all to the controller, which refuses at startup two adapters of one source type (since issue #273 any other set is accepted: PRs come from the forge, see PRs through the forge). Routing: each item's `postComment`, `markSeen`, `setStatus` and `closeIssue` go to the adapter whose `type` matches the item's `source.type`; status and comments on a PR go to the forge. An item whose source type has no configured adapter keeps its state: the controller makes no transition on it (changed 2026-11-07; `local` items excepted since issue #282, the store being their surface), and its outbox entries stay pending, so a finished run of it stays unacknowledged for a process that has the adapter, such as the new version next to an older one still draining with an older `plugins.source`; its calls outside a transition log a warning and are skipped. Intake: every poll source has its own cursor `intake:<type>` and every stream source its own listener (the lease was already per type) and inbox cursor; each source's step runs under its own guard, so one source failing does not stop the others in the same tick. Commands from any source go through the same command table, the same `AuthProvider` check and the same replies; resolving non-GitHub identities is left to the provider work (#107, #109). Not built: new `SourceType` values. The Slack adapter: see Slack intake and source routing. Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
- **Pull requests a person opens, and a person's pushes.** Now every change to the repository passes through the controller:
  - **Adoption.** The forge (`github`) reports `pr_open` on every poll for each open PR against the base branch from this repository: every factory-branch PR, and every other PR that is not a draft (a draft is adopted on a later poll, once it is ready). A PR the store does not know (not a factory branch, no item with that PR as its source) is adopted: one item, origin `adopted`, source = the PR (`owner/repo#N`, link `/pull/N`; comments and the status label go on the PR, labelled once), title = PR title, problem = title and body, requester = the author's user ID, `done_criteria` null, `allowed_paths` = the files the PR changes (`prFiles`, both sides of a rename, read only for a PR the store does not know), tier = the floor tier of those files, stage `REVIEW` with `pr_number` and `head_branch` set, and one review run, all in one `createWorkItem` (idempotent on the source; state change `pr_adopted`). An author that does not resolve to a user is not adopted (its merge is then an unreviewed merge). Forks are not adopted.
  - **Review of an adopted PR.** The worker checks out the item's `head_branch` (it fails if `origin/<branch>` is missing) and the prompt has the PR's title and body (untrusted), its files and the diff, and says there is no spec. The review comment goes on the PR as for factory PRs. The review sets the tier (max of judgment, floor, previous). A pass goes through the same CI gate to `merge_pending`, and auto-merge stays at 0, so a human still merges. The factory never pushes to a person's branch: bugs block on a human with `changes_requested`, failed checks with `checks_failed` (both `blocked_on: human`; no implement run). `/verdict` and `/resolve` still map PRs by factory branch only.
  - **`factory: skip`.** A PR with this label, added (latest `labeled` event in the issue timeline) by a user with the existing `approve_spec` permission, gets no item. A label added by anyone else is ignored with a warning, and the PR is adopted. It is checked at adoption only: on an adopted PR the label does nothing.
  - **Merges.** Every merged or closed PR is reported now, not only factory ones. A factory branch maps to its item as before; any other PR to its adopted item by number; a merge closes it as `CLOSED` / `completed` with `merge_sha`, the merger as actor (approver of record), and a close without merge as `rejected`. A merged PR with no item (skipped, a fork, never adopted, or merged after the first start but before the poll that would have adopted it) writes one `controller_unreviewed_merges` row (project, PR number, merge sha, merger's user ID or null; idempotent on project and PR number) and a warning. **First start (decision changed 2026-11-07, issue #341):** the first poll stores a starting point in the forge's JSON cursor (the GitHub source's until issue #273) (`start`, from the Clock in GitHub's UTC format; no new table, written through the store's conditional cursor update so replicas agree), even with no closed PR. A PR merged before it gets no merger read and no event, so a factory started on an old repository flags no past merge and reads only the closed-PR list. Upgrade: a cursor from before this keeps its place (its closed-PR time becomes the start), so a running install reads no history. `github.history_since` checks older merges on purpose: older than the start, it moves the start back once (that poll reads at most 5 pages of closed PRs, one GET per merged PR; the cursor records the value so a restart does not repeat it); a newer value is ignored with one warning naming the setting. Solo and enterprise follow the same rule. Paging history across polls is not built.
  - **A person's push.** Every run that pushes (implement, update, resolve) records the head it pushed as the item's `last_head_sha`, under its lease (`recordPushedHead`); adoption records the PR's head. On each poll the controller compares an open factory or adopted PR's head with it. A different head is a person's push: one run of kind `manual`, written already `succeeded` and acknowledged (never queued, so no worker claims it and the controller applies nothing), with `actor`, `from_sha`, `to_sha` and `pr_number` in its outcome, and `last_head_sha` moved to the new head, in one transaction (`recordPrHead`, conditional on the old head, so a repeat writes nothing). It changes no stage, blocked field or version, and nothing is re-queued or re-reviewed: a later review covers it. GitHub does not name who pushed, so the actor is the author of the head commit resolved through auth; if that does not resolve, `system:pr-sync` and a warning. While any run of the item is running, the head is not looked at (that run may be pushing); an item with no recorded head (from before this) only takes the current head as a baseline.
  - **Schema:** migration 12 adds `work_items.origin` (`factory` default), `head_branch`, `last_head_sha` (all store-owned, not in `WorkItemPatch`) and the `controller_unreviewed_merges` table. SQLite builds it on open.
  - Not built: re-review after a person's push, adopting a PR again after it reopens with a new number, showing unreviewed merges in stats. The Health section and the Floor line of the app show them (see `09-dashboard-app.md`).
