# 6. Measurement

- Raise auto-merge: severity-weighted human feedback rate < per-tier threshold over a per-tier min sample.
- Keep it raised: revert rate, fix-forward links, *sampled human audits*. Lower automatically when escapes cross the threshold.
- **Revert and fix-forward tracking (new decision, 2026-11-01):** reverts are found by polling base-branch commits, not by webhook. The `github-issues` source reads `origin/<base_branch>` commits (cursor: commit date, `since` inclusive; the first poll reads at most the newest 500, and a window over 500 drops the oldest) and emits `base_commit` {sha, message}. The controller (matchers in `src/core/links.ts`) records a `reverted` state_changes row on a factory item when a commit body says `This reverts commit <merge_sha>`, or when a subject starting with `Revert` names its PR `#N` (the squash suffix `(#M)` at the end is the reverting PR, not a candidate). A new issue whose title or body says `Fixes #N` or `Follow-up to #N`, N a factory PR, gets `fixes_pr = N` (row reason `fixes_pr_linked`) and the item with PR N gets a `fixed_forward` row. Only factory PRs are linked; other numbers are ignored. These rows change no field: `reverted` and `fixed_forward` are state_changes reasons only, not stages or close reasons, and nothing about gates or auto-merge changes. What the reason code cannot hold goes in the new nullable `state_changes.detail` (JSON, IDs and shas only): `reverted` → `{reverting_commit, reverting_pr}`, `fixed_forward` → `{fix_work_item_id}`, `fixes_pr_linked` → `{original_work_item_id}`. Dedupe key (checked inside the conditional transition, so a conflict re-reads): (item, `reverted`, reverting commit), so two commits that revert the same merge are two rows; (original item, `fixed_forward`, fix item). Rows written before the column existed have `detail` NULL. Stats over these rows are not built yet.
- **`factory stats`:** `npm run factory -- stats` prints one row per tier 1–5 plus `untiered` (`tier` null) over **CLOSED** items (merged, rejected or otherwise closed; the item's current tier): `items`, the feedback weight sum (the configured weight of every `/verdict` severity on those items), `rate` = weight sum ÷ items, `/reject` (applied `spec_rejected` state changes), `/retry` (applied `retry_requested` state changes) and total `token_cost`. A refused command writes no state change, so it is not counted; a `/reject` on a floor block (`floor_rejected`) is not counted as `/reject` either. `--json` prints the same numbers plus the config used as one object, with no IDs or display names. Config: a required `stats` key in `factory.config.json`, `weights` {`none`, `minor`, `major`, `critical`} (each a number ≥ 0; checked-in 0 / 1 / 3 / 10) and `min_sample` (integer ≥ 1, default 10); anything else fails startup. There are no weights in code. A tier with fewer than `min_sample` items shows `not enough data` instead of the rate (JSON: `rate` null, `sufficient` false); its counts still print. **Read-only:** it reads through one new store method, `listStatsRecords(reasons)` (every item's tier, stage and `token_cost`, its state-change reasons from that list and its verdict severities, with no cap), and is built through `buildStatsStore`, which never calls `migrate()` (unlike `build()`) and never calls `transition`. **Stats changes no dial:** `auto_merge_max_tier` stays 0, and moving a dial on these numbers stays a human decision. **Adopted row (decision changed 2026-11-01, issue #113):** adopted items (§5, [05-sources.md](05-sources.md)) are left out of the tier rows and counted in one more row, `adopted` (CLOSED adopted items of any tier, same columns; `adopted` in `--json`).
- Compare agents: golden PRs (bad + good) → catch rate up without false-alarm rate up → shadow mode → human decides on cost.
- **Golden set for the reviewer.** `src/golden.ts`, two CLI commands:
  - `factory golden add <pr> [--expect should_flag|should_pass] [--force]` writes `golden/cases/<pr>/` in the repo: `diff.patch` (the PR's unified diff from GitHub, one read-only GET), `spec.md` (the work item spec, in the worker's review layout) and `case.json` (`expect`, `outcome`, `human_verdict` {reason, actor_id, record_id}, `revert_reason` {reason, record_id, detail}, `source_record_ids`; IDs only). The outcome is read through the store APIs (`getWorkItemByPr`, `listStateChanges`): `rejected` (closed with `close_reason: rejected`), `reverted` / `fixed_forward` (merged, then the §6 revert-tracking row), `clean_merge` (merged, neither row), `held` (anything else). A `should_pass` case comes only from a clean merge and only with an explicit `--expect should_pass`; a clean merge is never `should_flag`. Without `--expect`, rejected, reverted and fixed-forward PRs default to `should_flag`; a held PR must say which. An existing case directory is refused without `--force`. Every file is G5-scanned (channel `commit`) before anything is written; any finding writes nothing and prints rule names only. The human verdict form (severity + reason, BACKLOG #3) is not built yet: `human_verdict` is the human's merge or close row until it is. Choosing which PRs become cases is a human decision; none are seeded.
  - `factory golden run --agent reviewer` (only `reviewer` is accepted) replays every case through the `runner` plugin in a fresh detached sandbox (`branch: null`) with the worker's review system prompt, `REVIEW_SCHEMA`, the same harness tools, and the stored spec plus diff as the prompt (no doc index, so a replay does not depend on the docs). It builds no `ToolBroker`, opens no store, pushes nothing and posts nothing. With the `noop` sandbox the agent has the host user's access, so run it in the test environment only (§5).
  - **Rates:** a case is flagged when the parsed review has `verdict: "bug"`. `catch_rate` = flagged / completed `should_flag` runs; `false_alarm_rate` = flagged / completed `should_pass` runs; each is printed with numerator and denominator, and a zero denominator prints `n/a`. **Errored runs** (any runner status other than `completed`, or output that fails `parseReview`) are counted and shown separately and excluded from both rates.
  - **Results** go to `<state_dir>/golden/results/<timestamp>.json`, not the store: case IDs, expect, verdicts, findings, counts and rates only. The file is G5-scanned (channel `run_outcome`) first; a finding writes nothing. Not yet: comparing two agents automatically, shadow mode.
