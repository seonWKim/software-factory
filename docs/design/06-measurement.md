# 6. Measurement

- Raise auto-merge: severity-weighted human feedback rate < per-tier threshold over a per-tier min sample.
- Keep it raised: revert rate, fix-forward links, *sampled human audits*. Lower automatically when escapes cross the threshold.
- **Revert and fix-forward tracking (new decision, 2026-11-01):** reverts are found by polling base-branch commits, not by webhook. The `github-issues` source reads `origin/<base_branch>` commits (cursor: commit date, `since` inclusive; the first poll reads at most the newest 500, and a window over 500 drops the oldest) and emits `base_commit` {sha, message}. The controller (matchers in `src/core/links.ts`) records a `reverted` state_changes row on a factory item when a commit body says `This reverts commit <merge_sha>`, or when a subject starting with `Revert` names its PR `#N` (the squash suffix `(#M)` at the end is the reverting PR, not a candidate). A new issue whose title or body says `Fixes #N` or `Follow-up to #N`, N a factory PR, gets `fixes_pr = N` (row reason `fixes_pr_linked`) and the item with PR N gets a `fixed_forward` row. Only factory PRs are linked; other numbers are ignored. These rows change no field: `reverted` and `fixed_forward` are state_changes reasons only, not stages or close reasons, and nothing about gates or auto-merge changes. What the reason code cannot hold goes in the new nullable `state_changes.detail` (JSON, IDs and shas only): `reverted` → `{reverting_commit, reverting_pr}`, `fixed_forward` → `{fix_work_item_id}`, `fixes_pr_linked` → `{original_work_item_id}`. Dedupe key (checked inside the conditional transition, so a conflict re-reads): (item, `reverted`, reverting commit), so two commits that revert the same merge are two rows; (original item, `fixed_forward`, fix item). Rows written before the column existed have `detail` NULL. Stats over these rows are not built yet.
- **Implicit verdicts in the numbers (decision changed 2026-11-08, issue #316):** a merge with no commits by people, a person's push and a revert of a factory PR each store an implicit verdict ([04-gate-commands.md](04-gate-commands.md)), one per PR head. `listStatsRecords` returns each item's explicit severities and its implicit count apart, and `factory stats` shows the two counts in their own columns (`explicit`, `implicit`; the same keys in `--json`). The feedback weight and the rate still read explicit verdicts only: the weighted rate that gates auto-merge, and how implicit verdicts weigh in it, are a later decision. No weight or `min_sample` changed.
- **`factory stats`:** `npm run factory -- stats` prints one row per tier 1–5 plus `untiered` (`tier` null) over **CLOSED** items (merged, rejected or otherwise closed; the item's current tier): `items`, `explicit` and `implicit` (the counts of `/verdict` verdicts and of implicit verdicts on those items, since 2026-11-08), the feedback weight sum (the configured weight of every explicit `/verdict` severity on those items; implicit verdicts weigh nothing yet), `rate` = weight sum ÷ items, `/reject` (applied `spec_rejected` state changes), `/retry` (applied `retry_requested` state changes) and total `token_cost`. A refused command writes no state change, so it is not counted; a `/reject` on a floor block (`floor_rejected`) is not counted as `/reject` either. `--json` prints the same numbers plus the config used as one object, with no IDs or display names. Config: a required `stats` key in `factory.config.json`, `weights` {`none`, `minor`, `major`, `critical`} (each a number ≥ 0; checked-in 0 / 1 / 3 / 10) and `min_sample` (integer ≥ 1, default 10); anything else fails startup. There are no weights in code. A tier with fewer than `min_sample` items shows `not enough data` instead of the rate (JSON: `rate` null, `sufficient` false); its counts still print. **Read-only:** it reads through one new store method, `listStatsRecords(reasons)` (every item's tier, stage and `token_cost`, its state-change reasons from that list and its verdict severities, with no cap), and is built through `buildStatsStore`, which never calls `migrate()` (unlike `build()`) and never calls `transition`. **Stats changes no dial:** `auto_merge_max_tier` stays 0, and moving a dial on these numbers stays a human decision. **Adopted row (decision changed 2026-11-01, issue #113):** adopted items (§5, [05-sources.md](05-sources.md)) are left out of the tier rows and counted in one more row, `adopted` (CLOSED adopted items of any tier, same columns; `adopted` in `--json`).
- **Run attempts (new decision, 2026-11-07, issue #207):** every claim of a run writes one record in `worker_run_attempts`, in the claim's transaction: run id, attempt number, worker id, start, status `running`, and the claim's lease token (kept in the store, never returned). Attempt numbers count the run's claims (1, 2, 3 …), so the claim that resumes a paused run gets its own record; `Run.attempt` keeps its meaning (a resume adds nothing to it). The record is closed once, by what ends the claim: `completeRun` (conditional on the same lease token) as `succeeded` or `failed`, with the failed outcome's error code, `failureClass()` (`task`, `infra`, `rate_limited`, `stalled`) and `outcomeTokens()`; `pauseRun` as `paused`; a close with `cancel_running_runs` as `cancelled`; the reaper (`expireLeases`, whether it requeues, fails or cancels the run) as `lease_expired`, error code `lease_expired`, failure class `infra`, tokens 0, except an expired interactive session, which closes as `failed` with `session_lost` (§5 Interactive sessions). `session start` opens the session run's one record, like a claim. Succeeded, paused and cancelled records have no error code and no failure class; records closed with no outcome have tokens 0. Read through `listRunAttempts(item)` (runs in `listRuns` order, attempts in order). Retries, `max_attempts`, backoff and run statuses are unchanged: a factory retry is still a new run row (§5 Restarts), so a step that failed twice and then succeeded shows three runs with one attempt each. **Backfill:** SQLite migration 20 (applied on open) and MySQL step `migrations/mysql/0020-run-attempts.sql` (`npm run migrate`; `CREATE TABLE IF NOT EXISTS` and `INSERT IGNORE`, so a rerun adds nothing) gives every run with attempt ≥ 1 one record numbered by its `attempt`, from the run row: status (a queued run with attempt ≥ 1 is `paused` when `paused_at` is set, else `lease_expired`), `started_at`, `finished_at` (else `paused_at`, else `updated_at`; null while running), the lease owner as worker id (null once the lease was cleared), error code, failure class and tokens as above. Queued runs with attempt 0 and manual runs get none. **Rollout:** stop old workers before the new code starts: a claim by old code writes no record.
- Compare agents: golden PRs (bad + good) → catch rate up without false-alarm rate up → shadow mode → human decides on cost.
- **Golden set for the reviewer.** `src/golden.ts`, two CLI commands:
  - `factory golden add <pr> [--expect should_flag|should_pass] [--force]` writes `golden/cases/<pr>/` in the repo: `diff.patch` (the PR's unified diff from GitHub, one read-only GET), `spec.md` (the work item spec, in the worker's review layout) and `case.json` (`expect`, `outcome`, `human_verdict` {reason, actor_id, record_id}, `revert_reason` {reason, record_id, detail}, `source_record_ids`; IDs only). The outcome is read through the store APIs (`getWorkItemByPr`, `listStateChanges`): `rejected` (closed with `close_reason: rejected`), `reverted` / `fixed_forward` (merged, then the §6 revert-tracking row), `clean_merge` (merged, neither row), `held` (anything else). A `should_pass` case comes only from a clean merge and only with an explicit `--expect should_pass`; a clean merge is never `should_flag`. Without `--expect`, rejected, reverted and fixed-forward PRs default to `should_flag`; a held PR must say which. An existing case directory is refused without `--force`. Every file is G5-scanned (channel `commit`) before anything is written; any finding writes nothing and prints rule names only. The human verdict form (severity + reason, BACKLOG #3) is not built yet: `human_verdict` is the human's merge or close row until it is. Choosing which PRs become cases is a human decision; none are seeded.
  - `factory golden run --agent reviewer` (only `reviewer` is accepted) replays every case through the `runner` plugin in a fresh detached sandbox (`branch: null`) with the worker's review system prompt, `REVIEW_SCHEMA`, the same harness tools, and the stored spec plus diff as the prompt (no doc index, so a replay does not depend on the docs). It builds no `ToolBroker`, opens no store, pushes nothing and posts nothing. With the `noop` sandbox the agent has the host user's access, so run it in the test environment only (§5).
  - **Rates:** a case is flagged when the parsed review has `verdict: "bug"`. `catch_rate` = flagged / completed `should_flag` runs; `false_alarm_rate` = flagged / completed `should_pass` runs; each is printed with numerator and denominator, and a zero denominator prints `n/a`. **Errored runs** (any runner status other than `completed`, or output that fails `parseReview`) are counted and shown separately and excluded from both rates.
  - `factory golden compare --base <file> [--agent reviewer] [--since <ref> | --all]` **(new decision, 2026-11-08, issue #338)** compares a prompt change, locally only (no CI job, no credential in GitHub; [05-ci-gate.md](05-ci-gate.md)). It replays the same cases twice through `runCases`, the one replay path: once with the base prompt read from `<file>`, once with the repo's `prompts/review.md`, and prints both sides' `catch_rate` and `false_alarm_rate` with numerator and denominator as Markdown (fit for a job summary). **Rule:** it fails (exit 1) when the catch rate drops by more than `GOLDEN_MARGIN`, or the false-alarm rate rises by more than it; a change of exactly the margin passes. `GOLDEN_MARGIN` (`src/golden.ts`) is a proposed default of 0.05, coarse because each case runs once. **Only when needed:** the changed paths are read from git (the diff from the merge base with `<ref>`, default `repo.base_branch`, plus uncommitted and untracked files; `--all` skips this). A change under `prompts/` affects that prompt; a change to the code that fills or sends prompts (`PROMPT_CODE_PATHS`: `src/golden.ts`, `src/core/outputs.ts`, `src/core/model-choice.ts`, `src/core/worker.ts`, `src/impl/runner/`, `src/impl/claude/`, `src/impl/openai/`, `src/impl/llm/`) affects every prompt. **Cases are tagged by prompt:** an optional `prompts` list in `case.json` (prompt file names, e.g. `["review.md"]`); without it a case uses its agent's prompt (`AGENT_PROMPT`: reviewer → `review.md`), so `golden add` keeps writing no tag. Only the cases tagged with an affected prompt replay. **Skips** (exit 0, the output says "Comparison skipped" and why): the change affects no prompt of the agent (no replay), no case is tagged with an affected prompt (no replay), or any of the four rates is `n/a`. Every outcome, skipped included, is recorded in `<state_dir>/golden/results/compare-<timestamp>/compare.json` (G5-scanned, `run_outcome`), beside each side's own results file under `base/` and `head/`. Like `golden run` it opens no store, builds no `ToolBroker` and writes nothing to GitHub.
  - **Cases belong to a role (new decision, 2026-11-08, RFC 0015 M10).** `case.json` may name its run role (`role`: `triage`, `implement`, `review`, `resolve`); a case without one is a `review` case, so every existing case and `golden add` stay as they are. Each role declares its minimum golden cases (`src/worker/roles/<name>.role.ts`); `tests/architecture/rule-of-two.test.ts` lists the roles still short of theirs (today triage, implement and resolve) in a ratchet that may only shrink. `golden/` is on the gate list.
  - **Results** go to `<state_dir>/golden/results/<timestamp>.json`, not the store: case IDs, expect, verdicts, findings, counts and rates only. The file is G5-scanned (channel `run_outcome`) first; a finding writes nothing. Not yet: comparing two agents automatically, repeated runs per case, shadow mode.

## History

- **Implicit verdicts in the numbers** (decision changed 2026-11-08, issue #316). Before: stats counted explicit `/verdict` verdicts only, and nothing else wrote one.

- **Golden compare** (new decision, 2026-11-08, issue #338). Before: `golden run` printed one prompt's rates and compared nothing, so a prompt change had no before/after number.

- **Run attempts** (new decision, 2026-11-07, issue #207). Before: one `worker_runs` row per run held only the latest claim: every claim overwrote `started_at`, a resumed paused run reused it, and an earlier claim's end, tokens and error had no record of their own.
- **`factory stats`** (new decision, 2026-11-01). Before: the feedback rate above had no read path, and `factory status` lists only the 50 newest items.
- **Golden set for the reviewer** (decision changed 2026-11-01: measurement now has a golden-set step). Before: "golden PRs" above was a plan with no cases, no runner and no numbers.
- **Revert and fix-forward tracking** (new decision, 2026-11-01). Replaces "revert rate (webhook)".
