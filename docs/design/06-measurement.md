# 6. Measurement

- Raise auto-merge: severity-weighted human feedback rate < per-tier threshold over a per-tier min sample.
- Keep it raised: revert rate, fix-forward links, *sampled human audits*. Lower automatically when escapes cross the threshold.
- **Per-tier merge record and the auto-merge rule, read-only (new decision, 2026-11-22, wi_338a8c26, phase 1 of 2 of "per-tier auto-merge drop-back"; current; replaces none).** Why: raising auto-merge for a tier needs that tier's record after merge, and the rule that would drop a tier back must be written once so the live check (phase 2) and the numbers people read cannot drift. **Figures**, per tier 1–5 plus untiered (the tier stored at merge time), over the merge evaluations below: `merged` (merges in the last 30 days), `reverted_or_fixed` (of those, merges with a `reverted` or `fixed_forward` row) and `not_accept` (owner verdicts other than accept on those merges: explicit `/verdict` comments only, implicit verdicts never count, owner's answer). **The rule** is one pure function, `tierRule` in `src/core/stats.ts`: a tier qualifies when its last 50 merges (of any age) have at most 1 reverted or fixed-forward merge and no critical verdict (an explicit `/verdict` with severity `critical`). Fewer than 50 merges never qualify (`too_few`); tiers 4 and 5 show `never` and never qualify. Results: `met`, `not_met`, `too_few`, `never`, plus `qualifies` (true only for `met`) and the sample's size, bad merges and critical verdicts. A merge is one evaluation row, so an item merged twice counts twice. **Reads:** `listMergeEvaluations` now also returns each merge's explicit verdicts by kind (`explicit`) and its explicit critical count (`critical`), from the same verdict query (grouped by kind, severity and `implicit`), and takes a window `{ within_ms }` of the store's clock beside a time or null, so no caller reads a clock. `collectTierMerges(store)` (two reads: all merges, and the last 30 days) builds the rows with pure `aggregateTierMerges`. **Shown:** `factory stats` prints a second table (`tier`, `merged_30d`, `reverted_or_fixed`, `not_accept`, `rule`) under the existing one, and `--json` carries the rows as `merges`; `GET /api/v1/efficiency` carries the same rows as `merges`, shown in Health > Efficiency ([06-efficiency.md](06-efficiency.md)). **Read-only here:** no setting, no write, no migration, and `auto_merge_max_tier` is unchanged. Phase 2 (2026-11-22, wi_f9e6887d) reads `tierRule` and the 20-merge drop-back (`droppedBack`) at each auto merge and refuses a tier's merge when its last 50 fail the rule or 2 of its last 20 are bad ([03-risk.md](03-risk.md), Per-tier rule and drop-back).
- **Revert and fix-forward tracking (new decision, 2026-11-01):** reverts are found by polling base-branch commits, not by webhook. The `github-issues` source reads `origin/<base_branch>` commits (cursor: commit date, `since` inclusive; the first poll reads at most the newest 500, and a window over 500 drops the oldest) and emits `base_commit` {sha, message}. The controller (matchers in `src/core/links.ts`) records a `reverted` state_changes row on a factory item when a commit body says `This reverts commit <merge_sha>`, or when a subject starting with `Revert` names its PR `#N` (the squash suffix `(#M)` at the end is the reverting PR, not a candidate). A new issue whose title or body says `Fixes #N` or `Follow-up to #N`, N a factory PR, gets `fixes_pr = N` (row reason `fixes_pr_linked`) and the item with PR N gets a `fixed_forward` row. Only factory PRs are linked; other numbers are ignored. These rows change no field: `reverted` and `fixed_forward` are state_changes reasons only, not stages or close reasons, and nothing about gates or auto-merge changes. What the reason code cannot hold goes in the new nullable `state_changes.detail` (JSON, IDs and shas only): `reverted` → `{reverting_commit, reverting_pr}`, `fixed_forward` → `{fix_work_item_id}`, `fixes_pr_linked` → `{original_work_item_id}`. Dedupe key (checked inside the conditional transition, so a conflict re-reads): (item, `reverted`, reverting commit), so two commits that revert the same merge are two rows; (original item, `fixed_forward`, fix item). Rows written before the column existed have `detail` NULL. Since 2026-11-11 the per-merge evaluation below counts these rows for each merge.
- **Per-merge evaluation (decision changed 2026-11-11, issue #512; replaces "stats over the revert and fix-forward rows are not built yet"):** every merge stores one evaluation row in `controller_merge_evaluations` (SQLite migration 42; solo default and enterprise setting use the same table, the solo default needs no setup). The key is (`work_item_id`, `merge_sha`). It holds the tier, the id of who made the merge (a user, agent or `system:*` id, never a display name), the item's `token_cost` and the time, all at merge time. **One write:** the store's `transition`, in the same transaction as the merge (the item moves to CLOSED with `close_reason` completed and a `merge_sha`), runs one conditional insert (`INSERT … SELECT … WHERE NOT EXISTS`, backed by the primary key). A second run, or a second replica, inserts nothing and changes nothing. Every merge path goes through that transition: the merge queue's local merge, a PR merged on the forge, and auto mode. **One read:** `FactoryStore.listMergeEvaluations(since)`, implemented once in `SqlFactoryStore` (`src/impl/store/sql/merge-evaluations.ts`), returns each merge oldest first with the title, the project and what followed it: the counts of its `reverted` and `fixed_forward` state changes and of its verdicts by kind (explicit and implicit). Three plain reads. Store data only, so a GitHub, Slack or Jira outage does not stop it. `digestMerges` (pure, `src/core/merge-evaluation.ts`) sums them: merged, reverted (merges with a revert), fixed forward, verdicts by kind, tokens. **No backfill:** merges made before the table existed get no row. The status page shows the digest ([09-status-page.md](09-status-page.md)). No weight or dial is written from it; auto mode's merge reads it through the per-tier rule and drop-back ([03-risk.md](03-risk.md)).
- **Implicit verdicts in the numbers (decision changed 2026-11-08, issue #316):** a merge with no commits by people, a person's push and a revert of a factory PR each store an implicit verdict ([04-gate-commands.md](04-gate-commands.md)), one per PR head. `listStatsRecords` returns each item's explicit severities and its implicit count apart, and `factory stats` shows the two counts in their own columns (`explicit`, `implicit`; the same keys in `--json`). The feedback weight and the rate still read explicit verdicts only: the weighted rate that gates auto-merge, and how implicit verdicts weigh in it, are a later decision. No weight or `min_sample` changed.
- **Autonomy (new decision, 2026-11-11, issue #522):** Autonomy is the share of merged factory items that merged with no person's push to their PR: (merged − with_push) ÷ merged. A merged factory item is one not adopted, CLOSED with `close_reason` completed; rejected and other closes are not counted, and neither are open items. A push is a stored implicit `changes` verdict (a merge is `accept`, a revert `reverted`, [04-gate-commands.md](04-gate-commands.md)). `listStatsRecords` returns two more per-item flags read in its existing queries, `pushed` (an implicit `changes` verdict is stored) and `merged`; no new query, table, schema or migration, and nothing is backfilled, so an item merged before push verdicts were stored counts as merged with no push. The rule lives once in `src/core/stats.ts`: pure `aggregateAutonomy(records)` and `collectAutonomy(store)`, one store read. `factory stats` prints one line under the table, `autonomy: 0.60 (3 of 5 merged factory items with no person's push)`, or `autonomy: not enough data (no merged factory items)` with none; `--json` has a top-level `autonomy` {`merged`, `with_push`, `autonomy` (null when `merged` is 0)}. The dashboard reads the same function through `GET /api/v1/data/autonomy` ([09-dashboard-app.md](09-dashboard-app.md)). One number, no tier split, no `min_sample`. Solo and enterprise get the same number: identity does not enter the count. Read-only, and like every stat it changes no dial, gate or auto-merge rule.
- **`factory stats`:** `npm run factory -- stats` prints one row per tier 1–5 plus `untiered` (`tier` null) over **CLOSED** items (merged, rejected or otherwise closed; the item's current tier): `items`, `explicit` and `implicit` (the counts of `/verdict` verdicts and of implicit verdicts on those items, since 2026-11-08), the feedback weight sum (the configured weight of every explicit `/verdict` severity on those items; implicit verdicts weigh nothing yet), `rate` = weight sum ÷ items, `/reject` (applied `spec_rejected` state changes), `/retry` (applied `retry_requested` state changes) and total `token_cost`. A refused command writes no state change, so it is not counted; a `/reject` on a floor block (`floor_rejected`) is not counted as `/reject` either. `--json` prints the same numbers plus the config used as one object, with no IDs or display names. Config: a required `stats` key in `factory.config.json`, `weights` {`none`, `minor`, `major`, `critical`} (each a number ≥ 0; checked-in 0 / 1 / 3 / 10) and `min_sample` (integer ≥ 1, default 10); anything else fails startup. There are no weights in code. A tier with fewer than `min_sample` items shows `not enough data` instead of the rate (JSON: `rate` null, `sufficient` false); its counts still print. **Read-only:** it reads through one new store method, `listStatsRecords(reasons)` (every item's tier, stage and `token_cost`, its state-change reasons from that list and its verdict severities, with no cap), and is built through `buildStatsStore`, which never calls `migrate()` (unlike `build()`) and never calls `transition`. **Stats changes no dial:** `auto_merge_max_tier` stays 0, and moving a dial on these numbers stays a human decision. **Adopted row (decision changed 2026-11-01, issue #113):** adopted items (§5, [05-sources.md](05-sources.md)) are left out of the tier rows and counted in one more row, `adopted` (CLOSED adopted items of any tier, same columns; `adopted` in `--json`).
- **Run attempts (new decision, 2026-11-07, issue #207):** every claim of a run writes one record in `worker_run_attempts`, in the claim's transaction: run id, attempt number, worker id, start, status `running`, and the claim's lease token (kept in the store, never returned). Attempt numbers count the run's claims (1, 2, 3 …), so the claim that resumes a paused run gets its own record; `Run.attempt` keeps its meaning (a resume adds nothing to it). The record is closed once, by what ends the claim: `completeRun` (conditional on the same lease token) as `succeeded` or `failed`, with the failed outcome's error code, `failureClass()` (`task`, `infra`, `rate_limited`, `stalled`) and `outcomeTokens()`; `pauseRun` as `paused`; a close with `cancel_running_runs` as `cancelled`; the reaper (`expireLeases`, whether it requeues, fails or cancels the run) as `lease_expired`, error code `lease_expired`, failure class `infra`, tokens 0, except an expired interactive session, which closes as `failed` with `session_lost` (§5 Interactive sessions). `session start` opens the session run's one record, like a claim. Succeeded, paused and cancelled records have no error code and no failure class; records closed with no outcome have tokens 0. Read through `listRunAttempts(item)` (runs in `listRuns` order, attempts in order). Retries, `max_attempts`, backoff and run statuses are unchanged: a factory retry is still a new run row (§5 Restarts), so a step that failed twice and then succeeded shows three runs with one attempt each. **Backfill:** SQLite migration 20 (applied on open) gives every run with attempt ≥ 1 one record numbered by its `attempt`, from the run row: status (a queued run with attempt ≥ 1 is `paused` when `paused_at` is set, else `lease_expired`), `started_at`, `finished_at` (else `paused_at`, else `updated_at`; null while running), the lease owner as worker id (null once the lease was cleared), error code, failure class and tokens as above. Queued runs with attempt 0 and manual runs get none. **Rollout:** stop old workers before the new code starts: a claim by old code writes no record.
- Compare agents: golden PRs (bad + good) → catch rate up without false-alarm rate up → shadow mode → human decides on cost.
- **Eval on change: a per-entity golden gate (decision changed 2026-11-18, issue #493; changes "Results … not the store", "Not yet: repeated runs per case" and the implement role's missing cases below; before: see History).** `src/controller/golden-gate/golden-gate.ts`, `checkChange(deps, item, entities)`. **Entities:** an entity is an id and its content (built now on these two, before the entity model of #491 exists): `role:<name>`, `prompt:<file>`, `skill:<name>` and so on. Its **fingerprint** is the SHA-256 of its content. **Which cases run:** an entity's own cases (`role:<name>`: every case of that role) and its dependents' cases: every case whose `case.json` has an optional `uses` list (entity ids) that names it. A case listed by several changed entities runs once per change. An entity with no case runs nothing and stores nothing. A malformed `uses` fails before any replay. **Replays:** each due case replays `golden.replays` times through `runCases` in `src/golden.ts` (the gate's `replay` dep returns its report; a replay passes when its verdict is what the case expects): a review case as `golden run` replays it, an implement case as below. **Rule:** an entity's pass rate is its cases' passing replays over all its replays (an errored replay fails). Its **base** is the pass rate of its last passing verdict. A drop of more than `golden.regression_margin` from the base is a regression; a change of exactly the margin passes (with the same epsilon as `golden compare`). With no base yet, the run passes and becomes the base. **Store, not memory:** each evaluated entity's fingerprint, verdict (`pass` or `regression`), pass rate and failing case ids, and its base fingerprint and rate, live in `controller_golden_fingerprints` (SQLite migration 44; one row per entity id), written through `FactoryStore.recordGoldenVerdict` and read through `getGoldenFingerprint`. A `pass` moves the base; a `regression` keeps it. Nothing is kept in process memory or the state dir, so another worker sees the same verdicts. **Not re-run:** an entity whose fingerprint equals its base fingerprint (its last passing run) runs nothing. **Block:** any regression posts one comment on the item (keyed by the regressed entities' fingerprints) naming each regressed entity, its pass rate against its base and its failing cases as `<role>/<case id>`, then moves the item to `blocked_on: human`, `blocked_reason: eval_regression` (state change reason `eval_regression`, detail `failing_cases`). The human decides: fix the entity, or revise the case into a new version. Run twice, an item already blocked on `eval_regression` is left as it is. No new gate command. **Config:** an optional `golden` block in `factory.config.json` (`goldenConfig` in `src/core/config.ts`, listed in `src/config-keys.ts`): `replays`, an integer ≥ 1 (default 1), and `regression_margin`, a number from 0 to 1 (default 0.05). Any other value, or an unknown key in the block, fails startup. **Absent, the gate is off:** no eval runs and nothing blocks. File-only, so no settings catalog entry. **Callers:** the entity model (#491) names a change's entities and calls the gate; until it lands no controller step calls it. SQLite only: no MySQL store exists, and a follow-up issue covers one. Out of scope here: triage and resolve replays, shadow mode, comparing agents, backfilling fingerprints.
- **Golden sets per role (decision changed 2026-11-18, issue #492; changes where cases live, how `golden run` picks them, and what it prints; before: see History).** `src/golden.ts`, three CLI commands.
  - **Layout.** Each case belongs to one role and lives in that role's folder: `src/worker/roles/<name>/golden/<case-id>/` with `instruction.md` (the work item spec, in the worker's review layout), `environment/diff.patch` (the PR's unified diff) and `case.json`. The folder names the role, so `case.json` names none and no code reads a role from it. The 15 cases that lived in one shared top-level folder (all reviewer cases) moved to `src/worker/roles/review/golden/` with no content change; each replays the same prompt as before. **Discovery:** `goldenCasesByRole` (`src/runtime/run-roles/run-roles.ts`) scans every role folder under `src/worker/roles/` with no list of roles in code; `run`, `compare`, `add` and the minimum check all use it, so a new role's cases are found with no engine change. Each role declares its minimum golden cases (`golden: { min_cases }` in `src/worker/roles/<name>.role.ts`); `tests/architecture/rule-of-two.test.ts` counts the cases in the role folders and lists the roles still short of theirs (today triage and resolve; implement got its first case, `643`, with eval on change) in a ratchet that may only shrink. The cases stay protected as part of `src/worker/roles/` (the permissions category of the gate list); `golden/` left the prompts category. Solo and enterprise use the same repo files; no setting.
  - `factory golden add <pr> [--role <name>] [--expect should_flag|should_pass] [--force]` writes `src/worker/roles/<name>/golden/<pr>/` (no `--role`: `review`, the only review default): `environment/diff.patch` (one read-only GET), `instruction.md` and `case.json` (`expect`, `outcome`, `human_verdict` {reason, actor_id, record_id}, `revert_reason` {reason, record_id, detail}, `source_record_ids`; IDs only). The outcome is read through the store APIs (`getWorkItemByPr`, `listStateChanges`): `rejected` (closed with `close_reason: rejected`), `reverted` / `fixed_forward` (merged, then the §6 revert-tracking row), `clean_merge` (merged, neither row), `held` (anything else). A `should_pass` case comes only from a clean merge and only with an explicit `--expect should_pass`; a clean merge is never `should_flag`. Without `--expect`, rejected, reverted and fixed-forward PRs default to `should_flag`; a held PR must say which. An existing case directory is refused without `--force`. Every file is G5-scanned (channel `commit`) before anything is written; any finding writes nothing and prints rule names only; files go to a temp sibling first, so a failure leaves no partial case. The human verdict form (severity + reason) is not built yet: `human_verdict` is the human's merge or close row until it is. Choosing which PRs become cases is a human decision.
  - `factory golden run role/<name>` replays one role's cases (no `--agent`) through the `runner` plugin in a fresh detached sandbox (`branch: null`) with the role descriptor's prompt (its file under `prompts/`) and tools, `REVIEW_SCHEMA`, and the stored instruction plus diff as the prompt (no doc index, so a replay does not depend on the docs). A role with no descriptor, or with `prompt: null`, is refused. The run kind is the role's name; a role with no `model_by` entry replays on the `standard` class. It builds no `ToolBroker`, opens no store, pushes nothing and posts nothing. With the `noop` sandbox the agent has the host user's access, so run it in the test environment only (§5). It prints, per case and in total, the input and output tokens (the runner's usage) and the wall time (the clock, sandbox create to destroy), then `pass_rate`, `catch_rate` and `false_alarm_rate`.
  - **Rates:** `pass_rate` = completed runs whose verdict matches `expect` (`bug` for `should_flag`, `pass` for `should_pass`) / completed runs (decision 2026-11-18, issue #492). A case is flagged when the parsed review has `verdict: "bug"`. `catch_rate` = flagged / completed `should_flag` runs; `false_alarm_rate` = flagged / completed `should_pass` runs; each is printed with numerator and denominator, and a zero denominator prints `n/a`. **Errored runs** (any runner status other than `completed`, or output that fails `parseReview`) are counted and shown separately and excluded from both rates.
  - `factory golden compare --base <file> [--agent reviewer] [--since <ref> | --all]` **(new decision, 2026-11-08, issue #338)** compares a prompt change, locally only (no CI job, no credential in GitHub; [05-ci-gate.md](05-ci-gate.md)). `--agent reviewer` (the only agent) replays the `review` role's cases; replacing `--agent` with `role/<name>` is a later change. It replays the same cases twice through `runCases`, the one replay path: once with the base prompt read from `<file>`, once with the repo's `prompts/review.md`, and prints both sides' `catch_rate` and `false_alarm_rate` with numerator and denominator as Markdown (fit for a job summary). **Rule:** it fails (exit 1) when the catch rate drops by more than `GOLDEN_MARGIN`, or the false-alarm rate rises by more than it; a change of exactly the margin passes. `GOLDEN_MARGIN` (`src/golden.ts`) is a proposed default of 0.05, coarse because each case runs once. **Only when needed:** the changed paths are read from git (the diff from the merge base with `<ref>`, default `repo.base_branch`, plus uncommitted and untracked files; `--all` skips this). A change under `prompts/` affects that prompt; a change to the code that fills or sends prompts (`PROMPT_CODE_PATHS`: `src/golden.ts`, `src/core/outputs.ts`, `src/core/model-choice.ts`, `src/worker/`, `src/impl/runner/`, `src/impl/claude/`, `src/impl/openai/`, `src/impl/llm/`) affects every prompt. A path under a role's golden folder (`src/worker/roles/<name>/golden/`) is a case, not prompt code: a change that touches only cases skips. **Cases are tagged by prompt:** an optional `prompts` list in `case.json` (prompt file names, e.g. `["review.md"]`); without it a case uses its role's prompt (the role descriptor's `prompt`), so `golden add` keeps writing no tag. Only the cases tagged with an affected prompt replay. **Skips** (exit 0, the output says "Comparison skipped" and why): the change affects no prompt of the agent (no replay), no case is tagged with an affected prompt (no replay), or any of the four rates is `n/a`. Every outcome, skipped included, is recorded in `<state_dir>/golden/results/compare-<timestamp>/compare.json` (G5-scanned, `run_outcome`), beside each side's own results file under `base/` and `head/`. Like `golden run` it opens no store, builds no `ToolBroker` and writes nothing to GitHub.
  - **Implement cases (2026-11-18, issue #493):** an implement case has the same three files plus two `case.json` keys: `base_sha`, the commit its change started from, and `uses`. Its replay is a runner wrapper, `implementReplayRunner` (`src/controller/golden-gate/implement-replay.ts`, applied in `buildGoldenRunDeps`; `runCases` itself has no implement branch). It checks out `base_sha` (detached) in the sandbox, runs the implement role with the role's prompt as system prompt and `instruction.md` alone as the prompt (no review schema), then passes when the tree differs from `base_sha` in every file `environment/diff.patch` changes; each file missed is a finding (`not changed: <path>`), and a failed git step errors the replay. The wrapper answers in the review output's shape (`pass` or `bug` with its findings), so `runCases` scores it like a review case. Its `expect` is `should_pass`. The seeded case `src/worker/roles/implement/golden/643/` is PR #643 (stop compiling the migration steps), taken from git history; its `uses` is `["prompt:implement.md"]`.
  - **Results** of `golden run` and `golden compare` go to `<state_dir>/golden/results/<timestamp>.json`: the role, case IDs, expect, verdicts, findings, `input_tokens`, `output_tokens` and `wall_ms` per case and in total, counts and rates only. The file is G5-scanned (channel `run_outcome`) first; a finding writes nothing. The gate's verdicts are in the store (eval on change, above). `runCases` takes the case ids to replay and a replay count; one replay per case without them. Not yet: comparing two agents automatically, shadow mode, a `checks/` folder per case.
