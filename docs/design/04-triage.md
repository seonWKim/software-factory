# 4. Agents: triage paths and companions

**A spec's quoted strings name the base tests that pin a change (decision changed 2026-11-25, wi_0961f7f7; replaces "only triage's own grep finds the tests asserting a changed string", see History).** Triage has no clone, so specs missed tests asserting a renamed string. The triage run (`src/worker/runs/triage/triage.run.ts`) reads each double-quoted string of four or more characters in the answer's `problem`, `done_criteria` and `desired_output` (`quotedStrings` in `src/core/triage-pins.ts`) and searches it with `git grep --cached -l -F` over `tests/` of its base checkout. Each matching file joins `allowed_paths` and `files_to_change` and is listed as `pinned_tests`, before `checkTestFiles` and `parseTriage`; no match adds nothing. `parseTriage` keeps `pinned_tests` (each in `files_to_change`); the spec comment lists them under "### Tests that pin this". `prompts/triage.md` says to quote the old text of a string the change renames or removes. Not changed: `checks_failed`, the companions, items triaged before.

**A done-check test file exists on the base or is marked new (decision changed 2026-11-24, wi_d833ac62; replaces triage's swap of a missing done-check file, see [history/04-pre-push-gates.md](history/04-pre-push-gates.md)).** Specs named check files that did not exist without saying to create them (one item: 5 files, 5 failed attempts). A `done_checks` `test_file` entry may carry `new: true`. `checkTestFiles` (`src/core/done-checks.ts`) also returns `checkFileRefusal`: each done-check file the triage run's base `tests/` lacks and that is not marked, and each marked one `allowed_paths` does not cover (a base with no tests/ files checks nothing: fixture repos would refuse every spec). It is sent back once in the same step (`check-files-retry`), like markup; a second such answer fails `invalid_output` naming them. A done-check file is never swapped. The spec comment shows ``(check: `tests/x.test.ts`, new file)``; the implement prompt's "New check files" lists each marked file with its line. Items triaged before keep their data.

**A new migration is named by slug with `<stamp>`; a taken timestamp moves to the next free minute (decision changed 2026-11-25, wi_b9b801b3; replaces "a build that finds a clash may use a later stamp", see History).** The prompt names a new migration and its test as `src/<c>/migrations/<stamp>-<c>-<slug>.migration.ts` and `tests/<stamp>-<c>-<slug>.test.ts`; the implementer takes the next free timestamp, and the scope rule covers any timestamp of that folder, component and slug (04-pre-push-gates). `parseTriage` accepts `<stamp>`; a done check on a `<stamp>` test file is refused and the test-file swap skips `<stamp>` paths. A concrete stamp (wi_27e56806): triage runs `freeMigrationStamps` (`src/core/migration-stamps.ts`) before the companions and `parseTriage`. Taken: every `src/*/migrations/` name at `refs/heads/<base_branch>` (`Sandbox.listLocalFiles`). A migration whose `yyyyMMddTHHmm` another file uses gets the first later free minute, same component and slug; its test moves with it, everywhere in the answer.

**Each done-when line carries a check: a repo check command, a test file, or a manual reason (decided 2026-11-22, RFC 0024 WP3 phase 1, wi_eb94310a; a new decision, none replaced).** Before it, triage wrote done-when lines as plain text and nothing recorded how a line is checked.

- **Shape.** The triage answer has `done_checks` (`DONE_CHECKS_SCHEMA` in `src/core/done-checks.ts`, required by `TRIAGE_SCHEMA`): one entry per `done_criteria` line, in order, `line` equal to that line. An entry is `{line, command}`, `{line, test_file}` or `{line, manual: true, reason}`. `parseTriage` refuses any other shape, a line with neither a check nor a manual reason, and a count or order that does not match, naming the entry `done_checks[i]`. A reason is checked for tool-call markup like the other text fields.
- **Which commands (owner answer 1, binding).** Only the repo's own check commands (`repo.check_commands`, else `test_command`), compared as the command text the spec shows (`doneCheckCommands`), plus test files: a safe repo-relative path under `tests/`.
- **Strict where an answer is applied (decision 1, default: strict).** The controller's triage branch passes the repo's check commands to `parseTriage`; with them, a missing list is refused and a command outside them is refused, and the item is retried like any invalid triage output. Without them (a stored triage output read again for `/approve` or a split, the worker's first parse, a session's `--spec` file) a missing list parses as none, so items and runs from before the change keep working; a list that is there must still pass every shape rule.
- **Stored.** The triage branch writes the list to the item's new nullable column `done_checks` (JSON text, migration `20261121T1000-controller-done-checks`, additive). Items triaged before keep null; nothing is backfilled.
- **The spec comment.** Under "Done when", each line ends with `(check: <command or test file>)`, the command or file in backticks, or `(manual: <reason>)`. A spec with no list shows the lines as before.
- **The prompt.** `prompts/triage.md` asks for `done_checks`, names the three forms and lists the project's check commands (`{{check_commands}}`).

Not changed: running the checks (a later phase of WP3), checks on the phases of a split spec (a phase keeps only its done criteria), the dashboard, and the implement, review and resolve outputs.

**Each decision option names its extra paths and done-when changes, and a revise instruction is the default of the decision it answers (decision changed 2026-11-21, wi_80ba9d05; replaces "a decision option is a plain string with no record of what it needs, and options stay off the spec comment", and adds a revise rule the prompt did not have, see History).** The decision that changed: what a decision option tells the owner before approval, and how a `/revise` binds the revised spec. **Decisions are questions with a reason, a default and options (decision changed 2026-11-10, issue #526; replaces "each decision is one line with its default, `{ text, default, owner_only }`").** Triage writes each entry of `decisions` as `{ question, reason, options, default, owner_only }` (`TRIAGE_SCHEMA` in `src/core/outputs.ts`; `prompts/triage.md` asks for each field):

- **Shape.** `question` and `reason` are non-empty strings; `options` is `[]` (a free answer) or 2 to 4 non-empty strings (`MIN_OPTIONS`, `MAX_OPTIONS`); `default` is the proposed answer and, when there are options, one of them. `parseTriage` refuses any other shape of a decision with a `question` and names the field (`decisions[1].options: must be [] or 2 to 4 non-empty strings`, `decisions[0].default: must be one of the options`). Reasons and options are checked for tool-call markup with the `decisions` field.
- **Stored.** The parsed `SpecDecision` keeps the question as `text` (the name auto mode and the stored outputs already use) and adds `reason` and `options`. Older stored decisions still parse: a plain string is an owner-only question with no default, and a `{ text, default, owner_only }` object is read as before. Items already triaged keep their decisions as stored (no backfill).
- **The spec comment.** "Decisions for you" keeps each line's wording (the question, `Proposed default: ...`, `(owner only)`) and numbers the decisions 1, 2, ... after the tier-raise bullet, so `/approve` can answer decision N with an `N: <answer>` line (design 04-gate-commands). Reasons and the option list stay off the comment; the dashboard shows them (design 09-dashboard-app). Since 2026-11-21 each option's changes show under its decision (the decision at the top).

**Path companions (decided 2026-11-07, issue #224).** Triage writes `allowed_paths` and `files_to_change` from the files it expects to change, so a spec often missed a companion file: the migration step for a schema change, or the design topic file for a decision. The implementer could not write it (`parseTriage` rejects an uncovered `files_to_change` entry, and the pre-push scope gate fails a push outside `allowed_paths` without a retry). Now the repository declares its companions, and the controller adds them:

- **Config.** `path_companions` in `factory.config.json` (optional, top level; listed in `TOP_LEVEL_KEYS`) is a list of `{ when, also }`: `when` one repo-relative path, `also` a non-empty list of repo-relative paths; a path ending in `/` names a folder. It is checked at load (`pathCompanionProblems` in `src/core/companions.ts`, run by `checkConfigKeys`): a value that is not a list, an entry without a non-empty `when`, an empty or non-string `also`, or an unknown key in an entry stops startup, each message naming the key and the entry index. Absent: no companions. The checked-in config declares the store schema, both doc indexes (`also`: their topic folder), and since issue #315 three more pairs: the store interface `src/interfaces/factory-store.ts` (`also`: the SQL store `src/impl/store/sql/sql-factory-store.ts`, the schema file, `tests/store-contract.test.ts`), `src/config-keys.ts` (`also`: `tests/config-keys.test.ts`), and any `docs/design/` topic file (`also`: `docs/design.md`).
- **Matching.** A `when` matches the answer's `files_to_change` only, never `allowed_paths`: equal, under a `when` folder, or a `when` under a named folder. Each `also` path is added to `allowed_paths` unless an allowed path already covers it.
- **Doc indexes.** Built in, apart from the config, with the rules of the 2026-11-18 decision above: an answer naming `docs/design.md` or `docs/plugins.md` in `files_to_change` or `allowed_paths` gets `docs/design/` or `docs/plugins/` added. The index stays allowed, so a new topic file's index line can still be written.
- **Where it runs.** In the controller's triage branch, on the raw answer, before `parseTriage` (so a companion listed only in `files_to_change` is accepted, not rejected as uncovered) and before the tier floor (so a config companion under a floor raises the tier like any other path; a built-in rule's path under a floor is refused instead). The stored `allowed_paths` include the added paths, so the scope gate allows them.
- **The spec.** The Files section lists each added path under "Added by `path_companions`", with the `when` path that caused it, in every spec comment the triage branch renders (the spec gate and the phase approved by its parent). An answer that matches nothing is unchanged: the same `allowed_paths` and the same spec text.
- **Split specs.** Only the top-level `allowed_paths` gain companions. Each phase's `allowed_paths` stay as triage wrote them; the phase's own triage run applies the rule when it runs.
- **The prompt.** `prompts/triage.md` asks which other files a change to the allowed paths requires, and names the topic files as the documentation targets, not the index, when the repository's docs are an index of topic files.

**Owner defaults and applied defaults (decided 2026-11-07, issue #315).** Triage used to ask the same questions on every item, and the owner accepted most as proposed. Now the owner's standing answers are checked in, and triage applies them instead of asking:

- **The file.** `prompts/owner-defaults.md` holds one rule per line, each followed by its source issue. No rule repeats what `CLAUDE.md` already decides. Solo default: the file is checked into the repo, so every run on that clone reads the same answers, and no account is needed. Enterprise setting: the same file, changed only through a reviewed merge. Per-person or per-project defaults are not supported.
- **Loading.** `loadConfig` in `src/load-config.ts` reads the file from the prompts folder and appends it to the triage prompt. A missing file means no defaults. It is not an error, the same as the optional resolve prompt.
- **The prompt.** `prompts/triage.md` says that a point `CLAUDE.md` decides is not a decision. Triage applies an owner default instead of asking, and lists each one it applied under `applied_defaults` as the rule it followed. It asks under `decisions` only for a choice that changes behaviour and that no default covers.
- **The output.** `applied_defaults` is an optional list of strings in `TRIAGE_SCHEMA` (at most `MAX_APPLIED_DEFAULTS`). `parseTriage` reads a missing list as empty, and rejects a value that is not a list or that has a non-string entry.
- **The spec.** `renderSpec` shows "### Applied defaults" right after "### Decisions for you", with one bullet per rule. It leaves the section out when the list is empty, so a spec with only applied defaults has no "Decisions for you" section.

Not changed: the floors and tier rules, the CI scope gate, the merge gate, per-project companions in the settings layers, and items already triaged (they keep their paths until a `/revise`).

**Tool-call markup is refused (decided 2026-11-08, issue #454).** A triage answer could carry the runner's tool-call markup (a `<parameter name="decisions">` tag inside a decisions entry, issue #446; the same in the Problem text) as an ordinary string, and the spec showed it raw. Now `parseTriage` in `src/core/outputs.ts` refuses an answer whose text holds bare tool-call markup: an opening or closing `parameter`, `invoke` or `function_calls` tag, or any tag in the runner's `antml` namespace. It checks every text field. The error names the field (`problem: tool-call markup outside code`, `phases[1].title: ...`). Markup inside backticks or a fenced code block is quoted, not checked, so a spec about this parser can still quote a tag.

**A markup refusal gets one re-prompt (decision changed 2026-11-10, issue #488).** The decision that changed: how a refused answer is retried. When `parseTriage` refuses an answer for tool-call markup (`<field>: tool-call markup outside code`), the triage run (`src/worker/runs/triage/triage.run.ts`) calls the agent once more inside the same journaled `run-agent` step. The new prompt is the same work item, then the exact error text, then "Answer with the JSON only." The second call keeps its own transcript (`<run>.markup-retry.json`). If the second answer is refused too, for any reason, the run fails as `invalid_output` with the second error; there is no third call. Any other `invalid_output` gets no re-prompt, except a done-check file the base lacks (2026-11-24, above), which shares this one re-prompt; an answer that parses on the first try makes one call.
