# 4. Agents: triage paths and companions

**Path companions (decided 2026-11-07, issue #224).** Triage writes `allowed_paths` and `files_to_change` from the files it expects to change, so a spec often missed a companion file: the MySQL migration step for a schema change, or the design topic file for a decision. The implementer could not write it (`parseTriage` rejects an uncovered `files_to_change` entry, and the pre-push scope gate fails a push outside `allowed_paths` without a retry). Now the repository declares its companions, and the controller adds them:

- **Config.** `path_companions` in `factory.config.json` (optional, top level; listed in `TOP_LEVEL_KEYS`) is a list of `{ when, also }`: `when` one repo-relative path, `also` a non-empty list of repo-relative paths; a path ending in `/` names a folder. It is checked at load (`pathCompanionProblems` in `src/core/companions.ts`, run by `checkConfigKeys`): a value that is not a list, an entry without a non-empty `when`, an empty or non-string `also`, or an unknown key in an entry stops startup, each message naming the key and the entry index. Absent: no companions. The checked-in config declares both store schemas (`also`: `migrations/mysql/` and `src/impl/store/mysql/migrations.ts`), both doc indexes (`also`: their topic folder), and since issue #315 three more pairs: the store interface `src/interfaces/factory-store.ts` (`also`: the SQL store `src/impl/store/sql/sql-factory-store.ts`, both schema files, `tests/store-contract.test.ts`, `migrations/mysql/` and `src/impl/store/mysql/migrations.ts`), `src/config-keys.ts` (`also`: `tests/config-keys.test.ts`), and any `docs/design/` topic file (`also`: `docs/design.md`).
- **Matching.** A `when` matches the answer's `files_to_change` only, never `allowed_paths`: equal, under a `when` folder, or a `when` under a named folder. Each `also` path is added to `allowed_paths` unless an allowed path already covers it.
- **Doc indexes.** Built in, apart from the config: an answer naming `docs/design.md` or `docs/plugins.md` in `files_to_change` or `allowed_paths` gets `docs/design/` or `docs/plugins/` added. The index stays allowed, so a new topic file's index line can still be written.
- **Where it runs.** In the controller's triage branch, on the raw answer, before `parseTriage` (so a companion listed only in `files_to_change` is accepted, not rejected as uncovered) and before the tier floor (so an added path under a floor raises the tier like any other). The stored `allowed_paths` include the added paths, so the scope gate allows them.
- **The spec.** The Files section lists each added path under "Added by `path_companions`", with the `when` path that caused it, in every spec comment the triage branch renders (the spec gate and the phase approved by its parent). An answer that matches nothing is unchanged: the same `allowed_paths` and the same spec text.
- **Split specs.** Only the top-level `allowed_paths` gain companions. Each phase's `allowed_paths` stay as triage wrote them; the phase's own triage run applies the rule when it runs.
- **The prompt.** `prompts/triage.md` asks which other files a change to the allowed paths requires, and names the topic files as the documentation targets, not the index, when the repository's docs are an index of topic files.

**Project-neutral prompts (decided 2026-11-07, issue #335).** The four core prompts serve every project the factory works on, so they name no tool (`npm`, `npx`) and no path of this repo (the doc indexes, `src/core/`, the MySQL migration paths). The implement, review and resolve prompts name the configured checks through the `{{check_commands}}` placeholder, filled once when the prompts are loaded (`fillPrompt` in `src/compose.ts`) from the same list as `checkCommands` in `src/core/checks.ts`: `repo.check_commands`, else `test_command`. The triage prompt checks a design against the principles in the repository's agent instructions (AGENTS.md or CLAUDE.md) and says a store schema change needs a migration for every store the repository ships, with neutral example paths. This repo's own rules (run tests through the npm scripts and never `npx`, the MySQL migration paths, solo and enterprise in the desired output) live in the "Rules for agents working on this repo" section of `AGENTS.md`, which reaches agents through `CLAUDE.md`, a symlink to it.

**Owner defaults and applied defaults (decided 2026-11-07, issue #315).** Triage used to ask the same questions on every item, and the owner accepted most as proposed. Now the owner's standing answers are checked in, and triage applies them instead of asking:

- **The file.** `prompts/owner-defaults.md` holds one rule per line, each followed by its source issue. No rule repeats what `CLAUDE.md` already decides. Solo default: the file is checked into the repo, so every run on that clone reads the same answers, and no account is needed. Enterprise setting: the same file, changed only through a reviewed merge. Per-person or per-project defaults are not supported.
- **Loading.** `loadConfig` in `src/compose.ts` reads the file from the prompts folder and appends it to the triage prompt. A missing file means no defaults. It is not an error, the same as the optional resolve prompt.
- **The prompt.** `prompts/triage.md` says that a point `CLAUDE.md` decides is not a decision. Triage applies an owner default instead of asking, and lists each one it applied under `applied_defaults` as the rule it followed. It asks under `decisions` only for a choice that changes behaviour and that no default covers.
- **The output.** `applied_defaults` is an optional list of strings in `TRIAGE_SCHEMA` (at most `MAX_APPLIED_DEFAULTS`). `parseTriage` reads a missing list as empty, and rejects a value that is not a list or that has a non-string entry.
- **The spec.** `renderSpec` shows "### Applied defaults" right after "### Decisions for you", with one bullet per rule. It leaves the section out when the list is empty, so a spec with only applied defaults has no "Decisions for you" section.

Not changed: the floors and tier rules, the CI scope gate, the merge gate, per-project companions in the settings layers, and items already triaged (they keep their paths until a `/revise`).

**Tool-call markup is refused (decided 2026-11-08, issue #454).** A triage answer could carry the runner's tool-call markup (a `<parameter name="decisions">` tag inside a decisions entry, issue #446; the same in the Problem text) as an ordinary string, and the spec showed it raw. Now `parseTriage` in `src/core/outputs.ts` refuses an answer whose text holds bare tool-call markup: an opening or closing `parameter`, `invoke` or `function_calls` tag, or any tag in the runner's `antml` namespace. It checks every text field: `in_short`, `problem`, `desired_output`, `tier_reason`, `scope` or `in_scope` and `out_of_scope`, `done_criteria`, `decisions`, `applied_defaults`, and each phase's `title`, `problem` and `done_criteria`. The error names the field (`problem: tool-call markup outside code`, `phases[1].title: ...`). Markup inside backticks or a fenced code block is quoted, not checked, so a spec about this parser can still quote a tag. Nothing is repaired or parsed out of the markup, so no spec shows raw markup. A `decisions` or `applied_defaults` value that is not a list of strings (for example a JSON string) gets an error that names it, and so does a missing text field. Solo and enterprise behave the same. Not changed: the triage prompt and schema, the spec renderer, items already stored, and the implement, review and resolve outputs.

**A markup refusal gets one re-prompt (decision changed 2026-11-10, issue #488).** The decision that changed: how a refused answer is retried. When `parseTriage` refuses an answer for tool-call markup (`<field>: tool-call markup outside code`), the triage run (`src/worker/runs/triage/triage.run.ts`) calls the agent once more inside the same journaled `run-agent` step. The new prompt is the same work item, then the exact error text, then "Answer with the JSON only." The second call keeps its own transcript (`<run>.markup-retry.json`). If the second answer is refused too, for any reason, the run fails as `invalid_output` with the second error; there is no third call. Any other `invalid_output` gets no re-prompt and fails as before; an answer that parses on the first try makes one call. `prompts/triage.md` says to answer with plain JSON only and never to write tool-call tags (parameter, invoke, function_calls or antml tags) inside a field value. Why: the controller's retry was a fresh call with the same prompt and no note of the error, so the same mistake repeated (issue #488: three runs). Solo and enterprise behave the same. Not changed: the output schema, the runner, refusal over repair, and the implement, review and resolve outputs.

## History

- **Prompt rules** (decision changed 2026-11-07, issue #335). Before: `prompts/triage.md` named this repo's principles from AGENTS.md, the MySQL migration paths (`migrations/mysql/`, `src/impl/store/mysql/migrations.ts`) for a store schema change, the topic files `docs/design/<topic>.md` and `docs/plugins/<interface>.md`, and `src/core/` in its example; the implement and review prompts named `npm test` and the `npx` rule.
- **Triage text check** (decision changed 2026-11-08, issue #454). Before: `parseTriage` checked only that each text field was a string or a list of strings, so tool-call markup passed into the spec, and a bad value got a bare error (`decisions`, `missing text field`) that did not say what was wrong.
- **Markup refusal retry** (decision changed 2026-11-10, issue #488). Before: a triage answer refused for tool-call markup was retried like any other invalid output: the controller ran a fresh triage with the same prompt and no note of the error, and the triage prompt said nothing about tags in field values.
