# 4. Agents: triage paths and companions

**Each decision option names its extra paths and done-when changes, and a revise instruction is the default of the decision it answers (decision changed 2026-11-21, wi_80ba9d05; replaces "a decision option is a plain string with no record of what it needs, and options stay off the spec comment", and adds a revise rule the prompt did not have, see History).** The decision that changed: what a decision option tells the owner before approval, and how a `/revise` binds the revised spec. In the EventBus item (wi_208c) the owner picked two options the spec offered: one needed a file outside the allowed paths and the other contradicted a done-when line, so the implement run stopped with `spec_conflict`. Earlier, the revise "make subscribers an EventBusActor" came back as a decision whose default was the opposite (plain threads).

- **Shape.** Each entry of `decisions` adds `option_changes` (`TRIAGE_SCHEMA` in `src/core/outputs.ts`): one `{ option, extra_paths, done_when }` per option that changes anything, `[]` when none. `option` is one of the options, named once; `extra_paths` are safe repo-relative paths (never `.claude/`) the option needs beyond `allowed_paths`; `done_when` are the done criteria it changes, each as the line it becomes. `parseTriage` refuses any other shape and names the field (`decisions[1].option_changes[0].option: must be one of the options`); an entry that changes nothing is dropped; `done_when` lines are checked for tool-call markup with the `decisions` field. The default's paths belong in `allowed_paths`.
- **Stored.** The parsed `SpecDecision` keeps them as `option_changes` (absent when empty). Older decisions, with plain-string options and no changes, parse unchanged; nothing is backfilled.
- **The spec comment.** Under each decision's line, one nested bullet per option that changes anything: `If you answer "<option>": needs `<path>` (add with `+paths`); changes done when: <line>`, before the answer block. The approve gate refuses an uncovered path (design 04-spec-gate-commands); the dashboard shows the same (design 09-dashboard-item-commands).
- **Revise feedback.** `prompts/triage.md` tells triage that an explicit instruction in the revision feedback sets the default of the decision it answers, never its opposite, or better is not asked again. It is a prompt rule only: the factory cannot tell by itself which decision an instruction answers, so the owner checks the revised spec comment. A change to this prompt needs a human merge, like every gate prompt.

**Built-in companion rules: a design topic's History file, a web view's i18n area file and the catalog barrel, a source file's test, a migration's table-docs file (decision changed 2026-11-18; the i18n rule also adds the generated barrel `web/src/i18n/en.ts`, replacing "the area file only"; the table-docs rule is added to the three built-in rules, which replaced "only the doc indexes are built in; every other companion comes from `path_companions` in the config", see History).** The decision that changed: which companions the controller adds without a config entry. Since 2026-11-14 most `spec_conflict` stops and `agent_needs_human` questions asked for one more path of these kinds; on 2026-11-18 wi_028251d5 stopped because a new migration's table needs its line in the owner's table-docs file (`tests/data-table-docs.test.ts`). `applyCompanions` in `src/core/companions.ts` now applies four rules to each `files_to_change` path, after the config entries and the doc index folders, and nowhere else:

- **Design History.** `docs/design/<topic>.md` adds `docs/design/history/<topic>.md`.
- **i18n area and barrel.** A web view or component adds the area file its name maps to (owner decision 2 of the work item) and the catalog barrel `web/src/i18n/en.ts`: `web/src/views/<area>.tsx` and `web/src/components/<area>.tsx` add `web/src/i18n/en/<area>.ts` and `web/src/i18n/en.ts`; a view named `<area>-<part>.tsx` or under `web/src/views/<area>/` maps to the same area. The barrel is generated from the area files (`npm run i18n:catalog`, design 09-dashboard-shell), so a change whose area file is new can regenerate it; triage cannot tell a new area from an existing one, since it has no clone, so the barrel comes with every area. A web file that names no area (`web/src/App.tsx`, `web/src/components/ui/*`) adds neither. No key is read.
- **Covering test.** A `.ts` or `.tsx` file under `src/` adds the test named after it (owner decision 1): `src/a/b.ts` adds `tests/b.test.ts`, `b.tsx` adds `tests/b.test.tsx`; the name is the file name up to its first dot (`plugins.command.ts` adds `tests/plugins.test.ts`). A `.d.ts` file and an `index` file add none. The path is added whether or not the test exists yet, so the implementer may create it.
- **Table-docs.** A `.ts` file directly under `src/<owner>/migrations/` adds `src/<owner>/table-docs.ts` (`src/worker/migrations/x.ts` adds `src/worker/table-docs.ts`), so the implementer can add the new table's line. A file elsewhere, in a subfolder or of another type adds none. The refusal below applies: `src/controller/table-docs.ts` and `src/identity/table-docs.ts` are protected gate paths, so controller and identity migrations still stop as `spec_conflict` (owner decision 1 of wi_227e8c5b, the default).
- **Never a gate path.** `refusedCompanion` drops a rule's path that is on `GATE_PATHS` (which holds every `PROTECTED_PATHS` entry) or under one of the project's tier floors. `applyCompanions` takes the floors as a required argument, and the controller's triage branch passes the item's project floors (`settings(it.project).floors`), so no caller skips the refusal. The refusal is the built-in rules' only: a config entry is the owner's own choice and is added as before.
- **The spec.** Each rule-added path is listed under "Added by `path_companions`" with the `files_to_change` path that caused it, like a config companion. An answer that matches no rule keeps the same `allowed_paths` and the same spec text.

Not changed: the config key and its entries, the gate lists, the floors and the scope gate, phases' `allowed_paths`, and items already triaged (no backfill).

**Generated files, shrinking ratchet lists and asserting tests need no stop (decision changed 2026-11-16; replaces "only the doc indexes, the store interface and the config keys have companions, and every path, ratchet lists included, must be in `allowed_paths`").** The decisions that changed: which companions the checked-in config declares, which paths the coverage rule always allows, and what the triage prompt asks for tests. On 2026-11-16 four items (wi_2e3d55f8, wi_c4ba8d7b, wi_c783c830, wi_477cf2a9) each stopped for a person only to get a path every such change needs.

- **Generated files.** `path_companions` in `factory.config.json` adds `schema/sqlite.sql` (regenerated by `npm run schema:snapshot`) when `files_to_change` names a file under `src/controller/migrations/` or `src/impl/store/sqlite/schema.ts`, and `docs/settings.md` (regenerated by `npm run settings:catalog`) when it names a file under a settings folder: `src/controller/settings/`, `src/guards/settings/`, `src/inbound/settings/`, `src/outbound/settings/`, `src/runtime/settings/`, `src/state/settings/`, `src/worker/settings/`. Triage only allows the paths; the implementer regenerates the files.
- **Ratchet lists.** `isCovered` in `src/core/policy.ts` always covers a `*.json` file directly in `tests/architecture/known-violations/`, whatever `allowed_paths` says. It is the rule of the scope gate (`scopeViolations`), the edit hook (`editCovered` in `src/impl/runner/gate-hooks.ts`) and the `files_to_change` check, so a run that lowers a count in `file-budget.json` or drops a fixed entry from `dependency-direction.json` never asks for the path. No other path is covered by it: not the folder itself, a subfolder, another file type, or `tests/architecture/lib.ts`. Growth stays refused: the architecture tests (`ratchet` and `countDrift` in `tests/architecture/lib.ts`) fail on a new violation and on a list entry the code no longer has. `pathsOverlap` keeps the plain rule, so a ratchet list overlaps only a list that names it or its folder. Not changed: `GATE_PATHS` (the folder is on it, so such a change still needs a human merge), `PROTECTED_PATHS`, the tier floors and the growth checks.
- **Asserting tests.** `prompts/triage.md` tells triage to grep the tests for each string the change removes or changes, and to list each matching test file in `allowed_paths` and `files_to_change`.

Not changed: items already triaged (no backfill).

**Triage refuses `.claude/` paths, owner-only (decision changed 2026-11-15; replaces "triage accepts any safe relative path").** The decision that changed: which paths a spec may name. `parseTriage` in `src/core/outputs.ts` refuses an answer whose top-level `allowed_paths`, a phase's `allowed_paths`, or `files_to_change` names a path under `.claude/`, written as `.claude/...`, `./.claude/...` or `.claude` alone. The error names the field and the path and says `.claude/ paths are owner-only` (`allowed_paths: .claude/agents/x.md: .claude/ paths are owner-only; ...`). Why: the repo already treats `.claude/` as owner-only (the tier 4 floor in `factory.config.json`, `GATE_PATHS` in `src/core/improver.ts`, the protected list in `src/core/standing.ts`) and the agent sandbox refuses every write there, so a spec naming one stopped its implement run and waited on a person (seen twice on 2026-11-15). The refusal goes through the existing invalid-output path. Not changed: the sandbox and runner rules, the floor and gate path lists, the triage prompt, and items already triaged (no backfill).

**Decisions are questions with a reason, a default and options (decision changed 2026-11-10, issue #526; replaces "each decision is one line with its default, `{ text, default, owner_only }`").** Triage writes each entry of `decisions` as `{ question, reason, options, default, owner_only }` (`TRIAGE_SCHEMA` in `src/core/outputs.ts`; `prompts/triage.md` asks for each field):

- **Shape.** `question` and `reason` are non-empty strings; `options` is `[]` (a free answer) or 2 to 4 non-empty strings (`MIN_OPTIONS`, `MAX_OPTIONS`); `default` is the proposed answer and, when there are options, one of them. `parseTriage` refuses any other shape of a decision with a `question` and names the field (`decisions[1].options: must be [] or 2 to 4 non-empty strings`, `decisions[0].default: must be one of the options`). Reasons and options are checked for tool-call markup with the `decisions` field.
- **Stored.** The parsed `SpecDecision` keeps the question as `text` (the name auto mode and the stored outputs already use) and adds `reason` and `options`. Older stored decisions still parse: a plain string is an owner-only question with no default, and a `{ text, default, owner_only }` object is read as before. Items already triaged keep their decisions as stored (no backfill).
- **The spec comment.** "Decisions for you" keeps each line's wording (the question, `Proposed default: ...`, `(owner only)`) and numbers the decisions 1, 2, ... after the tier-raise bullet, so `/approve` can answer decision N with an `N: <answer>` line (design 04-gate-commands). Reasons and the option list stay off the comment; the dashboard shows them (design 09-dashboard-app). Since 2026-11-21 each option's changes show under its decision (the decision at the top).

**Path companions (decided 2026-11-07, issue #224).** Triage writes `allowed_paths` and `files_to_change` from the files it expects to change, so a spec often missed a companion file: the migration step for a schema change, or the design topic file for a decision. The implementer could not write it (`parseTriage` rejects an uncovered `files_to_change` entry, and the pre-push scope gate fails a push outside `allowed_paths` without a retry). Now the repository declares its companions, and the controller adds them:

- **Config.** `path_companions` in `factory.config.json` (optional, top level; listed in `TOP_LEVEL_KEYS`) is a list of `{ when, also }`: `when` one repo-relative path, `also` a non-empty list of repo-relative paths; a path ending in `/` names a folder. It is checked at load (`pathCompanionProblems` in `src/core/companions.ts`, run by `checkConfigKeys`): a value that is not a list, an entry without a non-empty `when`, an empty or non-string `also`, or an unknown key in an entry stops startup, each message naming the key and the entry index. Absent: no companions. The checked-in config declares the store schema, both doc indexes (`also`: their topic folder), and since issue #315 three more pairs: the store interface `src/interfaces/factory-store.ts` (`also`: the SQL store `src/impl/store/sql/sql-factory-store.ts`, the schema file, `tests/store-contract.test.ts`), `src/config-keys.ts` (`also`: `tests/config-keys.test.ts`), and any `docs/design/` topic file (`also`: `docs/design.md`).
- **Matching.** A `when` matches the answer's `files_to_change` only, never `allowed_paths`: equal, under a `when` folder, or a `when` under a named folder. Each `also` path is added to `allowed_paths` unless an allowed path already covers it.
- **Doc indexes.** Built in, apart from the config, with the rules of the 2026-11-18 decision above: an answer naming `docs/design.md` or `docs/plugins.md` in `files_to_change` or `allowed_paths` gets `docs/design/` or `docs/plugins/` added. The index stays allowed, so a new topic file's index line can still be written.
- **Where it runs.** In the controller's triage branch, on the raw answer, before `parseTriage` (so a companion listed only in `files_to_change` is accepted, not rejected as uncovered) and before the tier floor (so a config companion under a floor raises the tier like any other path; a built-in rule's path under a floor is refused instead). The stored `allowed_paths` include the added paths, so the scope gate allows them.
- **The spec.** The Files section lists each added path under "Added by `path_companions`", with the `when` path that caused it, in every spec comment the triage branch renders (the spec gate and the phase approved by its parent). An answer that matches nothing is unchanged: the same `allowed_paths` and the same spec text.
- **Split specs.** Only the top-level `allowed_paths` gain companions. Each phase's `allowed_paths` stay as triage wrote them; the phase's own triage run applies the rule when it runs.
- **The prompt.** `prompts/triage.md` asks which other files a change to the allowed paths requires, and names the topic files as the documentation targets, not the index, when the repository's docs are an index of topic files.

**Project-neutral prompts (decided 2026-11-07, issue #335).** The four core prompts serve every project the factory works on, so they name no tool (`npm`, `npx`) and no path of this repo (the doc indexes, `src/core/`). The implement, review and resolve prompts name the configured checks through the `{{check_commands}}` placeholder, filled once when the prompts are loaded (`fillPrompt` in `src/compose.ts`) from the same list as `checkCommands` in `src/core/checks.ts`: `repo.check_commands`, else `test_command`. The triage prompt checks a design against the principles in the repository's agent instructions (AGENTS.md or CLAUDE.md) and says a store schema change needs a migration for every store the repository ships, with neutral example paths. This repo's own rules (run tests through the npm scripts and never `npx`, solo and enterprise in the desired output) live in the "Rules for agents working on this repo" section of `AGENTS.md`, which reaches agents through `CLAUDE.md`, a symlink to it.

**Owner defaults and applied defaults (decided 2026-11-07, issue #315).** Triage used to ask the same questions on every item, and the owner accepted most as proposed. Now the owner's standing answers are checked in, and triage applies them instead of asking:

- **The file.** `prompts/owner-defaults.md` holds one rule per line, each followed by its source issue. No rule repeats what `CLAUDE.md` already decides. Solo default: the file is checked into the repo, so every run on that clone reads the same answers, and no account is needed. Enterprise setting: the same file, changed only through a reviewed merge. Per-person or per-project defaults are not supported.
- **Loading.** `loadConfig` in `src/compose.ts` reads the file from the prompts folder and appends it to the triage prompt. A missing file means no defaults. It is not an error, the same as the optional resolve prompt.
- **The prompt.** `prompts/triage.md` says that a point `CLAUDE.md` decides is not a decision. Triage applies an owner default instead of asking, and lists each one it applied under `applied_defaults` as the rule it followed. It asks under `decisions` only for a choice that changes behaviour and that no default covers.
- **The output.** `applied_defaults` is an optional list of strings in `TRIAGE_SCHEMA` (at most `MAX_APPLIED_DEFAULTS`). `parseTriage` reads a missing list as empty, and rejects a value that is not a list or that has a non-string entry.
- **The spec.** `renderSpec` shows "### Applied defaults" right after "### Decisions for you", with one bullet per rule. It leaves the section out when the list is empty, so a spec with only applied defaults has no "Decisions for you" section.

Not changed: the floors and tier rules, the CI scope gate, the merge gate, per-project companions in the settings layers, and items already triaged (they keep their paths until a `/revise`).

**Tool-call markup is refused (decided 2026-11-08, issue #454).** A triage answer could carry the runner's tool-call markup (a `<parameter name="decisions">` tag inside a decisions entry, issue #446; the same in the Problem text) as an ordinary string, and the spec showed it raw. Now `parseTriage` in `src/core/outputs.ts` refuses an answer whose text holds bare tool-call markup: an opening or closing `parameter`, `invoke` or `function_calls` tag, or any tag in the runner's `antml` namespace. It checks every text field: `in_short`, `problem`, `desired_output`, `tier_reason`, `scope` or `in_scope` and `out_of_scope`, `done_criteria`, `decisions`, `applied_defaults`, and each phase's `title`, `problem` and `done_criteria`. The error names the field (`problem: tool-call markup outside code`, `phases[1].title: ...`). Markup inside backticks or a fenced code block is quoted, not checked, so a spec about this parser can still quote a tag. Nothing is repaired or parsed out of the markup, so no spec shows raw markup. A `decisions` or `applied_defaults` value that is not a list of strings (for example a JSON string) gets an error that names it, and so does a missing text field. Solo and enterprise behave the same. Not changed: the triage prompt and schema, the spec renderer, items already stored, and the implement, review and resolve outputs.

**A markup refusal gets one re-prompt (decision changed 2026-11-10, issue #488).** The decision that changed: how a refused answer is retried. When `parseTriage` refuses an answer for tool-call markup (`<field>: tool-call markup outside code`), the triage run (`src/worker/runs/triage/triage.run.ts`) calls the agent once more inside the same journaled `run-agent` step. The new prompt is the same work item, then the exact error text, then "Answer with the JSON only." The second call keeps its own transcript (`<run>.markup-retry.json`). If the second answer is refused too, for any reason, the run fails as `invalid_output` with the second error; there is no third call. Any other `invalid_output` gets no re-prompt and fails as before; an answer that parses on the first try makes one call. `prompts/triage.md` says to answer with plain JSON only and never to write tool-call tags (parameter, invoke, function_calls or antml tags) inside a field value. Why: the controller's retry was a fresh call with the same prompt and no note of the error, so the same mistake repeated (issue #488: three runs). Solo and enterprise behave the same. Not changed: the output schema, the runner, refusal over repair, and the implement, review and resolve outputs.
