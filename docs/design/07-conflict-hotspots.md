# 7. Self-improvement: conflict hotspots

- **The improve run files conflict hotspots (decision changed 2026-11-18; current; changes "File each recurring failure pattern" below, and "Claim and work" under the daily improve run). Changed again on 2026-11-18: the count skips files a merge halved and files gone from the base head, and the task dates each count (see History).** A conflict's detail names a different file set each run, so files never grouped.
  - **Record.** A `merge_conflict` failure (implement run) and a failed resolve run store the conflicting files as the outcome's `conflicts` (a succeeded resolve run stores `data.conflicts`). The count reads only that field (`conflictFiles`, `src/core/hotspots.ts`); no detail text is parsed, nothing is backfilled.
  - **Count.** Each improve run counts, per file, over the 7 days before its window's end (`HOTSPOT_WINDOW_MS`): the project's merge_conflict and resolve runs naming the file, and the items a coordination hold kept back on it, each once per file. Holds are claim decisions (`listClaimDecisionsSince`) `held`, `approved` or `timed_out`, files in `shared[].path`.
  - **Halving cut.** A merge halves a file when 2 × its deleted lines ≥ the file's lines at the merge's first parent (a split or move). Per file, runs finished and decisions written before the project's last such merge in the 7 days (`listMergeEvaluations`) are not counted; later ones are. A file not at `refs/heads/<base_branch>` is not listed.
  - **Git.** `src/core` runs no git: `runImprove` takes an optional `MergeGit`, built in `src/worker/runs/improve/improve.run.ts` with `factoryGit` (no checkout): `diff --numstat --no-renames` at `<sha>^1`, numstat from the empty tree for line counts, `ls-tree` at the head. A git failure fails the run before any model call, no report stored, retried. No reader: no cut, no head check.
  - **Threshold.** A file whose run plus held-item count reaches the live setting `conflict_hotspot_threshold` (integer ≥ 1, default 3; design 08-settings) is hot: the right number depends on how many workers run.
  - **Report.** Each hot file is one `hotspot` row in the report's patterns JSON: detail the file, `run_ids`, `held_item_ids`, `work_item_ids` every item named, optional `counted_at` (each run's finish and held item's decision time). Never drafted, never in `failure_groups`; no migration. The Rules page lists them.
  - **File.** `fileReport` files each row after the groups, same caps and `fileGroup`: pattern key the cyrb53 of `hotspot` plus the path, claimed in `controller_filed_patterns`. Title "Reduce conflicts on <file>"; the body (`hotspotBody`) lists the counts and each run and held item ID with its date, after the G5 `comment` scan. While open, a later report comments once with unlinked runs (the linked scan reads the 7-day window's reports); after it closes, refiled only after 30 days. A gate-list file is filed too (no draft, so never `needs_person`); its fix still needs a person's merge.
