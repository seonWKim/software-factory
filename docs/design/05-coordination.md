# 5. Coordination

- **Worker slots reported per process (decision changed 2026-11-07, issue #209; before: see History).** Each `WorkerPool` logs one `worker slots` line (`pid`, `slots` = the live count, `from` = the previous count or null, `reason`) when its live count changes: `start` when the pool starts, `settings change` on the first tick after `factory settings set workers <n>` changes it (lowering by three is one line, not three), and `drain` with `slots` 0 when the pool stops for any reason, shutdown included. A tick with an unchanged count logs nothing; the per-slot "worker slot stopping: workers lowered" line is gone. Each tick the pool also writes its own store row (`worker_processes`, keyed by `process_id` = `<host>:<pid>`, so a repeat write replaces it): `pid`, `host`, `slots`, `max_slots` (the slot count, the file's `max_workers`, else `workers`), `busy` (slots holding a run at that moment, from claim to release), `index_base`, `started_at` and `reported_at` (store clock). While draining it keeps writing with `slots` 0 until the last in-flight run ends, then deletes its row. A row a dead process left behind stays in the table but is not listed once its `reported_at` is older than `lease_ms` (`listWorkerProcesses(lease_ms)`). The row is a report, never a gate: a failed write is logged once per failure streak (`worker process report failed`) and no slot stops. The data goes in the store, not a status file, because a status file covers one host and MySQL installs run on several. `GET /api/v1/workers` returns it as `processes` (design §9). The supervisor's `child started` line, which logs the config block size, is unchanged, as are scheduling, claiming and `/api/health`. Schema: SQLite migration 19; MySQL step `migrations/mysql/0019-worker-processes.sql` (`CREATE TABLE IF NOT EXISTS`), run by `npm run migrate`. `tests/store-contract.test.ts` checks the step has the same columns as SQLite 19, and with `SF_TEST_MYSQL_URL` set it upgrades a state-18 database through `npm run migrate`'s path and checks the earlier rows are kept.
- Judgment calls default to humans (form + reason). Recurring decisions → proposed rules → human approves.
- Isolation: a worktree + branch per run (container later); ports and test DB per worker, chosen from `SF_WORKER_INDEX` (unique within one process only); shared pool mounted read-only with one updater. An item never has two implement-type runs at once; items with overlapping paths do, below the coordination cost threshold (Parallel workers and Coordination, below).
- **Parallel workers.** `workers` in `factory.config.json` (integer ≥ 1, default 1, anything else fails at startup) sets how many worker loops `factory dev` and `factory worker` run in one process (`WorkerPool`). Each has its id `<host>:<pid>:<n>` and passes `SF_WORKER_INDEX=n` to the agent and to the update run's test command. They share one counted `KeepAwake` (held while any run is in progress) and one drain (no claims after it, acknowledged after the last in-flight run). **One branch writer per item:** a claim skips an implement-type run (`implement`, including a review fix, and `update`) only while the same item has one running. Overlapping paths no longer hold runs back; their conflicts are handled at merge (sync before push, the update run, `/resolve`). Triage and review are never skipped. The check and the claim are one store transaction that first takes the lock row in `claim_locks` (migration 7), so two claimers on MySQL cannot both start one item's run; a skipped run stays queued and is claimed after its item's run completes. **Claim order:** a claim takes queued runs by kind rank, then `created_at`, then insertion order. The rank is review, triage, update, implement, resolve: runs that lead to a human decision first (review takes a PR toward ready-to-merge, triage gives the owner a spec to approve), then the branch writers, and `resolve`, a long branch-writing agent run, last. Within one kind the oldest run still goes first. A held run (its item has a branch writer running, or its `not_before` has not passed) blocks nothing behind it. Retry backoff, the rate-limit pause and the one-branch-writer rule are unchanged. Not in this change: aging or fairness, so a steady stream of review and triage runs can delay implement runs. Not in this decision: pausing every worker on a usage limit across processes (after #41), a status page panel of which worker runs what (the data is in `/api/v1/workers`, see Worker slots reported per process), splitting one item across workers, automatic scaling, and an index unique across processes or hosts.
- **Mechanical paths and mechanical merges (decision changed 2026-11-07, issue #297; before: every shared path weighed at least 1.0, see History).** What changed: a new class of paths, `mechanical_paths`, that two items usually change only by adding lines or new files: the MySQL migration runner (`src/impl/store/mysql/migrations.ts`), `migrations/mysql/`, `docs/design/`, `docs/design.md`, `docs/plugins.md`, `docs/plugins/` (the default). A shared path that equals one or lies under a mechanical folder weighs `mechanical_weight` (**0.25**) and is never a hotspot, even when `hotspot_paths` lists it (so `docs/design.md` no longer weighs 3.0); a learned weight wins when higher (from two recorded conflicts, which only real resolutions add). A folder that merely holds mechanical files (`docs/`) is not mechanical. So two items that each add a MySQL step, a History line in the same topic file and an index line cost 0.5 and run side by side; two items that both change `src/core/controller.ts` still cost 3.0 or more and are held. Hold reasons and the stored claim decision (`claim_decisions.shared`, `mechanical: true`) name each mechanical path with its weight: `docs/design.md (mechanical, 0.25)`.
  - **Appended-line merge, in code** (`src/core/mechanical.ts`). When a base merge conflicts and every conflicting file has, on both sides, only lines added to the common ancestor (index stages 1, 2, 3; regular files only), the worker merges each file as the base's added lines, then the branch's, at each place (one copy when both added the same lines), writes it through git (blob, index entry, `checkout-index`; never through a working-tree path), and goes on with no model call. All or nothing: one file with a removed or changed line, a file added on both sides or deleted on one, keeps the old path for every file (an agent step in the implement sync; the automatic resolve run after an update). It runs in the implement sync before push (then the merge commit, the scope gate, the size gate and the check list, before any push), in the update run (merge commit, then the check list; a failure is `tests_failed` as before) and in the resolve run (no agent step; the marker check, the worker's commit and the gates still run). A file merged this way is not recorded with `recordConflicts`, so it adds no learned weight.
  - **Migration renumbering, in code.** After a base merge is committed (implement sync, update run), when a MySQL step file the branch adds (`migrations/mysql/NNNN-<name>.sql|ts`) has a number the base already has, every step the branch adds moves, in number order, to the next numbers after the base's highest (`git mv`), literal references to the old name (`0025-name`) in the files the branch changed follow, and the worker commits that, before the scope gate and the checks. A moved step from an allowed path passes the scope gate. Skipped (logged) when the branch also changes a SQLite schema file: SQLite numbers its migrations in `schema.ts`, so that collision is real and the gates report it. The migration runner is unchanged.
  - **Config:** `mechanical_paths` (a list of non-empty paths) and `mechanical_weight` (a number above 0 and below 1.0, else startup fails), in `factory.config.json` and checked by `checkConfigKeys`. `src/compose.ts` now passes all five coordination keys into `FactoryConfig.coordination` (closing the known gap below). One global value until per-project settings (#99).
  - Not in this decision: SQLite migration renumbering, the resolve prompt, renumbering in the resolve run, references beyond a literal step name, hand-resolution weights (#113).
- **Dependency reads only when the source changed (decision changed 2026-11-07, issue #254; before: edges re-read from the forge on every poll, see History).** What changed: the coordination step on each poll applies the **stored** edges (`dependency_edges`) and no longer reads each item's links from the forge. The links (issue body for `Depends on`, `sub_issues`, `blocked_by`: three GETs on GitHub) are read when the poll delivers the issue (`item_requested`), which it does at intake and again only when the issue's `updated_at` moved past the intake cursor, for an item that is not closed and has no PR. Two bounded refreshes cover what an issue update may not show: an item's links are read again by the coordination step once this process's last read of them is **30 minutes** old (a sub-issue or blocked-by link added without the issue counting as updated), and the state of a dependency outside the factory (not a work item) is read at most once per **10 minutes** per dependency, shared by every item that waits on it (a factory item's state still comes from the store). The read times are kept in the controller's memory, a cache only, like the GitHub ETag cache (§5 Sources): a new process or another replica uses the stored edges and reads links only after its own 30 minutes (so a restart makes no burst of link reads), and reads an outside state once on first sight. A forge failure (outage, rate limit) stops no coordination: the read is logged once (`dependency links not read` / `dependency state not read`), the stored edges and states apply, and it is retried only after the interval. The local source offers no dependency links, so local items use their stored edges with no network call. Constants, not settings (`EDGES_REFRESH_MS`, `DEPENDENCY_STATE_REFRESH_MS` in `src/core/controller.ts`), since nobody has needed to tune them. With 10 queued implement items and nothing changed, a poll makes no issue body, `sub_issues` or `blocked_by` call (`tests/coordination-flow.test.ts`). Not in this decision: storing the read times in the store (so replicas share them), skipping the 30-minute refresh under `lowBudget()`, and a draining process running no controller (#294).
- **Coordination: dependencies and a cost threshold (decision changed 2026-11-03, issue #115; before: the claim held an implement-type run only while its own item had one running, so a dependent item could start before the work it needs merged, overlapping items always ran side by side, open PRs held nothing, and a file that conflicted again and again weighed the same as any other).** What changed: a claim now also holds an `implement` run (it stays queued, with a stored reason) for two reasons, both read from the store inside the same `claim_locks` transaction, never from the network.
  - **Dependencies.** An item depends on every issue named on a `Depends on: #N` line of its issue, on its GitHub sub-issues (a parent waits for its sub-issues) and on its blocked-by links (the GitHub source reads all three; a list GitHub has switched off gives none). Edges are stored per item (`dependency_edges`, with the source id even for an issue outside the factory) when the poll delivers the issue (at intake and again each time it changed; see Dependency reads below for when the forge is read). The controller writes each edge's state outside the claim lock: from the store for a factory item (merged = closed `completed` with a merge sha), else from the forge (an issue closed as completed or a merged PR is merged). Open: the item gets `blocked_on: dependency` and a `blocked_reason` naming the items (`waiting for #92 to merge`, one comment), stage `RUNNING`, status label "implementing". Merged: when the dependency's PR merges, the controller clears the hold in the same event, and the next claim takes the run (for an item outside the factory, on the first poll after its state is read again, at most 10 minutes later). Closed without a merge: `blocked_on: human`, `dependency_closed:#N`, queued runs cancelled, one comment. A cycle: refused, `blocked_on: human`, `dependency_cycle: #a → #b → #a`, queued runs cancelled, one comment keyed `dependency-cycle:<id>`. `/approve` never lifts a dependency hold; its refusal says so (new command phase `dependency_hold`, "waiting for a dependency to merge").
  - **Cost.** For an item without a PR, the cost of running it next to another item is the sum of the weights of the paths both change (the shared-path test is the scope gate's `isCovered`): 1.0 per shared path (a mechanical path 0.25, see Mechanical paths above); a file with two or more recorded conflicts 1.0 + 0.5 per conflict, at most 4.0; a hotspot (`hotspot_paths`: both schema files, `src/core/controller.ts`, `src/core/worker.ts`, `docs/design.md`, `SET_UP.md`) the fixed `hotspot_weight` 3.0 (a higher learned weight wins). A cost at or above `max_coordination_cost` (**2.5**, raised from the 1.5 first proposed) holds the run. Holders: items with an implement-type run running, items with an open PR even with no run (its stored diff file list `pr_files`; a PR opened before this change has none and falls back to `allowed_paths`, and the comment says so), and other claimable queued implement runs. Each side's files: `pr_files`, else triage's `files_to_change` (now stored), else `allowed_paths`. **This replaces the plain overlap view:** one or two ordinary shared files (1.0 or 2.0) run in parallel, a hotspot or a file with three or more recorded conflicts serializes. Deadlock rule: a run held only by other queued runs is claimed in claim order, so the oldest of a group that holds each other goes first. Each decision is stored per run (`claim_decisions`: shared paths with weights, total cost, threshold, holder item or PR, whether the holder fell back to `allowed_paths`), rewritten only when it changes. A cost hold keeps `blocked_on: none` (status "implementing"); the controller posts one comment per (run, holder) on the poll: `The implement run is held: waiting for #92 to merge: both change src/core/worker.ts (conflicted 6 times), cost 4.0 > 2.5.` `/approve` on such an item records `coordination_approved` (the approver's user ID as actor) and the next claim takes the run.
  - **Never held:** triage, review, update and resolve runs, and implement runs of an item that already has a PR (review fixes: their conflicts are the PR's, handled at merge).
  - **Learned weights:** the worker records one conflict per file at each base merge that conflicts and is not merged in code (sync before push, the update run, the resolve run), keyed by item and base sha, so an update and its automatic resolve on one base count once (`file_conflicts`, `recordConflicts`). A later hand-resolution record (#113) can use the same call.
  - **Config:** `max_coordination_cost` (number above 0, default 2.5), `hotspot_weight` (default 3.0), `hotspot_paths` in `factory.config.json`; a zero or non-numeric value fails at load (`checkConfigKeys`). One global value until per-project settings (#99). `src/compose.ts` passes them into `FactoryConfig.coordination` since 2026-11-07 (issue #297); before, the worker used the defaults, which equal the checked-in values.
  - **Schema:** migration 16 (SQLite) adds `work_items.files_to_change` and `pr_files` and the tables `dependency_edges`, `file_conflicts`, `claim_decisions`. MySQL: step `migrations/mysql/0016-coordination.sql`, the same tables plus `seq` for insertion order. No shipped migration changed.
  - Not in this decision: per-project thresholds (#99), sources other than GitHub, a command to resume an item blocked by a closed dependency or a cycle (a human closes or edits it), showing a cost hold on the status page (it shows `blocked_on` and `blocked_reason`, and a cost hold keeps both clear).
- Lease + heartbeat; expired leases released by code. Each claim bumps a **fencing token**; heartbeats, completions, handoff rows and broker calls carry it, so a worker that lost its lease can't write (decided 2026-10-31).
  - Host sleep: **status and token decide whether a lease is held, not the clock.** Heartbeat, completion, handoffs and broker calls are accepted while the run is `running` with the caller's token, even after `lease_expires_at` passed. So a worker that wakes from a sleep renews its unreclaimed lease and finishes on the same attempt. Expiry only makes a run eligible for the reaper. Once the reaper requeues or fails it, or another worker reclaims it (token + 1), the old token is refused everywhere. The reaper keeps its previous tick time in memory (per process, not shared between replicas). If more than `lease_ms` passed since then, it skips expiring leases for one `heartbeat_ms`, so workers that slept on the same host can renew first. Residual gap: a reaper on a host that did not sleep still requeues a sleeping worker's run once `lease_ms` passes. Closing that needs a human decision (longer lease, or host liveness in the store).
- **Budget checkpoints (new, 2026-11-01; §6):** the controller checks an item's token budget only where it queues an implement or review run, in the same conditional transition as the outcome it applies, never mid-run. At the budget the run is held on a `budget_checkpoints` row instead of queued, and `/budget` queues it later under the same key.
- Runs: the controller enqueues, workers claim. A transition can **ack a finished run and enqueue the next one in the same transaction**, so a crash between "decide" and "enqueue" can't strand an item (decided 2026-10-31).
- Store backend (D3 changed 2026-10-31): **MySQL** by default, because several workers and machines are planned. SQLite stays for tests and single-machine use. `factory.config.json` → `store.type` picks one (a plugin name, D6; `docs/plugins.md`). The store logic exists once (`SqlFactoryStore`); a backend is only a `SqlDriver` (transactions, statements, lock syntax), and both pass the same store contract tests. MySQL claims runs in READ COMMITTED transactions; since parallel workers (2026-11-01, below) every claim first locks the `claim_locks` row instead of using `FOR UPDATE SKIP LOCKED`, so the same-item check cannot race.
- **MySQL schema steps.** Now each schema or data change is one numbered file in `migrations/mysql/` (`NNNN-<name>.sql` or `NNNN-<name>.ts`, contiguous, never edited once shipped; README there), run only by `npm run migrate` (`src/impl/store/mysql/migrations.ts`). The state is one number in `schema_state`; step `NNNN` moves it from `NNNN-1` to `NNNN`, and the runner refuses, changing nothing, when the recorded state is not the next step's starting state (e.g. ahead of the newest file). The eleven old groups stay in code as a frozen baseline (state 11): they build an empty database; an existing database (legacy `schema_migrations` at 11) is only stamped 11, with no schema or data statement. `npm run migrate -- --status` lists the state and pending steps; `-- --dry-run` prints each `.sql` step's statements and the rows a `.ts` step's `plan` would change (READ ONLY transaction), changing nothing; the plain run prints a backup reminder, then applies steps in order under a named lock, recording the state after each. A `.sql` step is not atomic (MySQL DDL commits on its own; a failure leaves the previous state and the next run starts that step again, so steps must be safe to rerun); a `.ts` step's `apply` runs in one transaction with its state update. `.ts` steps are compiled by `npm run build` through `tsconfig.migrations.json` into `dist/migrations/mysql/`. `MysqlDriver.migrate()` (the `FactoryStore.migrate()` callers in `build()`, `buildUiParts()` and `golden add`) is now a check: it throws "… run `npm run migrate`" while steps are pending and applies nothing, so `dev`, `worker`, `controller`, `status`, `ui` and `golden add` refuse to start; a database ahead of the code still starts. `schemaVersion()` throws the same message, so doctor's MySQL check (and the Health panel) shows pending steps as a FAIL line, not the warn of the 2026-11-01 read-only probe decision (§9). Steps load from the code root, so the updater's runtime copy carries `migrations/`. SQLite is unchanged: it builds the latest schema on open, and `npm run migrate` on SQLite exits non-zero ("SQLite has no migration scripts"). No down-migrations. Rollout: every existing MySQL install runs `npm run migrate` once (it only stamps 11) before the factory starts again.
- Time is injected through a `Clock` interface: `SystemClock` in prod, `FakeClock` in tests (decided 2026-10-31). Crash → resume from branch + latest handoff, `restart_count` (not `loop_count`).

## History

- **Dependency reads only when the source changed** (decision changed 2026-11-07, issue #254). Before: edges re-read from the forge on every poll: each poll, for each item with a queued implement run or a dependency hold (up to 50 each), the controller read the issue body, its `sub_issues` and its `blocked_by` (three GETs), plus one GET per dependency outside the factory, so about 40 calls a poll with ten such items; on 2026-11-07 this used up the GitHub App's hourly limit, which also kept `/approve` and `/retry` comments from being read. A failed read failed the whole item's coordination pass, so stored edges did not apply during an outage.
- **Mechanical paths** (decision changed 2026-11-07, issue #297). Before: every shared path weighed at least 1.0, and `docs/design.md` was a hotspot at 3.0, so two items that each added an index line and a migration step reached the 2.5 threshold and ran one after the other; every base-merge conflict went to an agent step or a resolve run, even when both sides only added lines, and was recorded as a learned weight; a MySQL step number both branches took was left for the tests to fail on.
- **Worker slots reported per process** (decision changed 2026-11-07, issue #209). Before: the pool re-read `workers` each tick and logged "worker slot stopping: workers lowered" once per slot that stopped, never the count itself; the only count in the logs was the supervisor's `child started` line (`workers: <block size>`, the config, not the live value); the store kept no per-process record, so an idle process appeared nowhere and no host could see another host's slots.
- **Parallel workers** (new decision, 2026-11-01). Before: one worker loop per process, so approved items were built one at a time.
- **One branch writer per item** (decision changed 2026-11-01). Before: the overlap rule skipped an implement-type run while any item with overlapping `allowed_paths` had one running, later with shared docs exempted; nearly every spec lists a whole folder, so one implement run ran at a time whatever `workers` said.
- **Claim order** (decision changed 2026-11-01). Before: FIFO, the oldest queued run first whatever its kind, so a short triage or review run that a person waits on could sit behind older implement runs for about 45 minutes while every worker was busy.
- **MySQL schema steps** (decision changed 2026-11-01, issue #97). Before: the MySQL schema was a positional array of statement groups in `src/impl/store/mysql/schema.ts`, applied silently by `store.migrate()` on every store open, so nobody could see or check pending changes, a data change could not run on its own, and parallel PRs collided on the same array position.
- **Host sleep** (fencing rule changed 2026-11-01). Before, `lease_expires_at` was also a hard deadline for every write.
