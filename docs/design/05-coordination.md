# 5. Coordination

- **The shared store is paused; `SqlDriver` stays the SQL seam (decision changed 2026-11-13, issue #663, phase 1 of 2 of #659; before: see History).** The decision that changed: the refusal of an unsupported store in the first store decision below, and the shared store it kept in the code. The SQL dialect is `sqlite` only, and no SQL code branches on another dialect. A config whose `store.type` names no registered FactoryStore plugin fails at startup through the generic unknown-plugin error, `unknown FactoryStore plugin "<name>" at store.type`. A shared store (several hosts on one database) is paused: nothing derives one from the store type, so an external config (`--config`) may set any key, and the pack loaders get `sharedStore: false` until phase 2 of #659 removes that option. `SqlDriver` stays the SQL seam: the store logic exists once (`SqlFactoryStore`) over it, so a later SQL backend is a driver, not a new store. SQLite behaviour does not change.
- **`max_coordination_cost`, `hotspot_weight` and `mechanical_weight` are settable live (decision changed 2026-11-12, phase 1 of "Settings without editing factory.config.json"; before: all three were `factory.config.json` keys only, read once at startup, see History).** Each is a `factory settings set` key (and a Settings page key), global only, checked with the config loader's own message (`coordinationProblems`) and applied at the next claim with no restart: `LiveSettings` puts the effective values into `FactoryConfig.coordination`, which each worker passes to `claimRun`. They are tighten-only in the direction that holds more runs: a lower `max_coordination_cost` or a higher `hotspot_weight` or `mechanical_weight` needs no grant; a loosening asks `approve_merge` (`08-settings.md`). The file value still applies when no override is stored, and the defaults (2.5, 3.0, 0.25) when neither sets them. `hotspot_paths`, `mechanical_paths` and `hotspot_mode` still change by PR only.
- **The store is SQLite only (decision changed 2026-11-11, issue #590, phase 1 of 4 of #576; before: see History).** The decision that changed: **store backend D3**. The factory serves one owner (`08-permissions.md`), and SQLite on one machine carries every worker process of that owner, so nothing selects another store. `factory.config.json` has `"store": { "type": "sqlite" }` (no `store` key means the same). Setup asks no store question; `factory migrate` and `factory migrate --contract` run on SQLite only. The store logic still exists once (`SqlFactoryStore`) over a `SqlDriver`. Solo default and enterprise setting are the same: SQLite.
- **Default hotspots follow the RFC 0015 moves (decision changed 2026-11-09, owner decision; before: the default `hotspot_paths` named `src/core/controller.ts` and `src/core/worker.ts`, both removed by RFC 0015 M5/M6, so they matched nothing, see History).** The default `hotspot_paths` (`DEFAULT_HOTSPOTS`, `src/core/coordination.ts`) is both schema files, `src/controller/`, `src/worker/`, `docs/design.md` and `SET_UP.md`. `src/controller/` (folder form, owner decision) replaces `src/core/controller.ts`: every file under it weighs `hotspot_weight` (3.0), so two items that both change any controller unit, the router or the state tables are held. `src/worker/` replaces `src/core/worker.ts` the same way (the worker runner, run kinds, pool and roles). `tests/coordination.test.ts` fails when a default hotspot or mechanical path names nothing that exists. A config that sets `hotspot_paths` is unchanged.
- **One GitHub sync per project (decision changed 2026-11-08; before: every replica polled GitHub, budget per process; see History).** What changed: a store lease, `sync:<type>:<project>` (`inbound_sync_leases`: name, owner, token, expires_at; SQLite migration 40), decides which replica syncs a project with GitHub. Its holder alone polls the GitHub source and the GitHub forge, delivers the outbox rows of the GitHub source type (issue comments and PR comments), finishes source closes and phases, and stores the `github:budget` report; every other replica skips those steps and treats the optional reads (status catch-up, check reads, dependency reads) as waiting, so N replicas make the GitHub calls one makes. The lease reuses `lease_ms` and `heartbeat_ms` (no new setting). The controller holds it from its tick (`TickLease`): at most one store call per `heartbeat_ms`; the holder renews, another replica tries to take it each `heartbeat_ms` and at once when the holder's `expires_at` has passed, so a takeover comes within `lease_ms` of the holder's last renew; a controller that stops releases it. The same owner taking it again keeps its token (a controller with no `replica_id` uses the owner `controller`, so controllers in one test process act as one replica). Every write of the sync is fenced with the token, checked `FOR UPDATE` in the write's own transaction: cursor writes through `advanceSyncCursor`, delivery claims through `claimDelivery(seq, lease_ms, fence)`; a stale token writes nothing, so a replica whose lease was taken over posts no comment twice. Logs name the lease by its source type, never the project key. The lease logic is one copy, `src/core/lease.ts` (`StoreLease`), used by the stream listener too; `inbound_listener_leases`, keyed by source type only, keeps its table, store code and tests. The Health page shows `GitHub: 812/5000 left, resets 09:12, synced by replica <id>` (reset in UTC; a warn under 10% left or with no live holder), read from the store, no GitHub call. Solo default: one process, so the lease is always held and nothing else changes. With no GitHub plugin selected, no lease row is written. Several replicas on one store: exactly one syncs. Why a new table and not `inbound_listener_leases`: that lease is keyed by source type and leaves the project out, and the stream listener keeps it as it is.
- **Worker slots reported per process (decision changed 2026-11-07, issue #209; before: see History).** Each `WorkerPool` logs one `worker slots` line (`pid`, `slots` = the live count, `from` = the previous count or null, `reason`) when its live count changes: `start` when the pool starts, `settings change` on the first tick after `factory settings set workers <n>` changes it (lowering by three is one line, not three), and `drain` with `slots` 0 when the pool stops for any reason, shutdown included. A tick with an unchanged count logs nothing; the per-slot "worker slot stopping: workers lowered" line is gone. Each tick the pool also writes its own store row (`worker_processes`, keyed by `process_id` = `<host>:<pid>`, so a repeat write replaces it): `pid`, `host`, `slots`, `max_slots` (the slot count, the file's `max_workers`, else `workers`), `busy` (slots holding a run at that moment, from claim to release), `index_base`, `started_at` and `reported_at` (store clock). While draining it keeps writing with `slots` 0 until the last in-flight run ends, then deletes its row. A row a dead process left behind stays in the table but is not listed once its `reported_at` is older than `lease_ms` (`listWorkerProcesses(lease_ms)`). The row is a report, never a gate: a failed write is logged once per failure streak (`worker process report failed`) and no slot stops. The data goes in the store, not a status file, because a status file covers one host and the store covers every host. `GET /api/v1/workers` returns it as `processes` (design §9). The supervisor's `child started` line, which logs the config block size, is unchanged, as are scheduling, claiming and `/api/health`. Schema: SQLite migration 19.
- Judgment calls default to humans (form + reason). Recurring decisions → proposed rules → human approves.
- Isolation: a worktree + branch per run (container later); ports and test DB per worker, chosen from `SF_WORKER_INDEX` (unique within one process only); shared pool mounted read-only with one updater. An item never has two implement-type runs at once; items with overlapping paths do, below the coordination cost threshold (Parallel workers and Coordination, below).
- **Parallel workers (decision changed 2026-11-07: test runs get a CPU share; before: see History).** `workers` in `factory.config.json` (integer ≥ 1, default 1, anything else fails at startup) sets how many worker loops `factory dev` and `factory worker` run in one process (`WorkerPool`). Each has its id `<host>:<pid>:<n>` and passes `SF_WORKER_INDEX=n` to the agent and to the gate commands of the update and resolve runs and the check list. **CPU share for tests:** each loop also passes `SF_TEST_WORKERS` there, the host's CPUs (`os.availableParallelism()`) divided by the live claiming slot count (`workers`, capped at `max_workers`), rounded down, at least 1 (`testWorkerShare` in `src/worker/support.ts`); ten slots on a 10-CPU host give 1 each. This repo's `vitest.config.ts` uses it as `maxWorkers`; unset (a developer's `npm test`, solo or enterprise) vitest keeps its default. Derived, not a setting: no new config key. Another repo's test command uses it only if its test runner reads it. Each host computes its own share from its own CPUs and slots, so replicas on several hosts need nothing shared; two processes on one host while an old one drains can briefly oversubscribe. They share one counted `KeepAwake` (held while any run is in progress) and one drain (no claims after it, acknowledged after the last in-flight run). **One branch writer per item:** a claim skips an implement-type run (`implement`, including a review fix, and `update`) only while the same item has one running. Overlapping paths no longer hold runs back; their conflicts are handled at merge (sync before push, the update run, `/resolve`). Triage and review are never skipped. The check and the claim are one store transaction that first takes the lock row in `worker_claim_locks` (migration 7), so two claimers cannot both start one item's run; a skipped run stays queued and is claimed after its item's run completes. **Claim order:** a claim takes queued runs by kind rank, then `created_at`, then insertion order. The rank is review, triage, update, implement, resolve: runs that lead to a human decision first (review takes a PR toward ready-to-merge, triage gives the owner a spec to approve), then the branch writers, and `resolve`, a long branch-writing agent run, last. Within one kind the oldest run still goes first. A held run (its item has a branch writer running, or its `not_before` has not passed) blocks nothing behind it. Retry backoff, the rate-limit pause and the one-branch-writer rule are unchanged. Not in this change: aging or fairness, so a steady stream of review and triage runs can delay implement runs. Not in this decision: pausing every worker on a usage limit across processes (after #41), a status page panel of which worker runs what (the data is in `/api/v1/workers`, see Worker slots reported per process), splitting one item across workers, automatic scaling, and an index unique across processes or hosts.
- **Hold policy: a cost hold may time out or be allowed (decision changed 2026-11-07, issue #314; before: a cost hold kept the run queued until `/approve`, see History).** What changed: a run the cost rule holds (`held`: a running item or an open PR at or above `max_coordination_cost`) now follows `hold_policy`, read by the claim inside the same `worker_claim_locks` transaction. Modes: `{ "mode": "hold" }` (the default, also when the key is absent: today's behaviour, the run waits for `/approve` or for the holder to merge); `{ "mode": "run_after_minutes", "minutes": 20 }` (the run is claimed once it has been held `minutes`, a positive integer, default 20; decision `timed_out`); `{ "mode": "run" }` (claimed at once; decision `overlap_allowed`). Both new decisions keep the holder, shared paths, cost and threshold, as `held` does, so a person can see what ran side by side. The timer counts from `claim_decisions.held_since`: set when a run is first held, kept while it stays `held` whichever holder the decision names (the row's `at` still moves on every change), so a holder change never restarts it; a row from before the column has none and counts from its `at`. `hotspot_mode`: `policy` (default) lets a hold that shares a hotspot follow `hold_policy`; `hold` keeps any hold where a running item or open PR shares a hotspot path held under every mode (any shared hotspot counts, with no weight rule). Not changed: dependency holds (never time out or become `overlap_allowed`: the dependency check comes first), the deadlock rule, `/approve` and its refusals (it still lifts a `held` decision under any mode), the hold comment text, cycle handling.
  - **Config and setting:** `hold_policy` and `hotspot_mode` are top-level keys of `factory.config.json`, checked at load by `coordinationProblems` (an unknown mode, `minutes` that is not a positive integer, a key a mode does not take, an unknown `hotspot_mode` fail startup) and passed by `src/compose.ts` into `FactoryConfig.coordination` with the other coordination keys. `hold_policy` is also a settable key (`factory settings set hold_policy '{"mode":"run"}'`, design 08-settings.md), refused with the same messages and applied at the next claim with no restart: `LiveSettings` puts the effective value into the claim's coordination settings. `hotspot_mode` changes by PR only. One global value until per-project settings (#99). Solo and enterprise alike: the default keeps every run held until a person acts; a team that prefers throughput sets a timer.
  - **Schema:** SQLite migration 30 adds `claim_decisions.held_since` (NULL on older rows).
  - Not in this decision: showing on the Queue and Items pages when a held run will start (a follow-up issue), per-project hold settings (#99).
- **Mechanical paths and mechanical merges (decision changed 2026-11-07, issue #297; before: every shared path weighed at least 1.0, see History).** What changed: a new class of paths, `mechanical_paths`, that two items usually change only by adding lines or new files: `docs/design/`, `docs/design.md`, `docs/plugins.md`, `docs/plugins/` (the default). A shared path that equals one or lies under a mechanical folder weighs `mechanical_weight` (**0.25**) and is never a hotspot, even when `hotspot_paths` lists it (so `docs/design.md` no longer weighs 3.0); a learned weight wins when higher (from two recorded conflicts, which only real resolutions add). A folder that merely holds mechanical files (`docs/`) is not mechanical. So two items that each add a History line in the same topic file and an index line cost 0.5 and run side by side; two items that both change a file under `src/controller/` (before 2026-11-09, `src/core/controller.ts`) still cost 3.0 or more and are held. Hold reasons and the stored claim decision (`claim_decisions.shared`, `mechanical: true`) name each mechanical path with its weight: `docs/design.md (mechanical, 0.25)`.
  - **Appended-line merge, in code** (`src/core/mechanical.ts`). When a base merge conflicts and every conflicting file has, on both sides, only lines added to the common ancestor (index stages 1, 2, 3; regular files only), the worker merges each file as the base's added lines, then the branch's, at each place (one copy when both added the same lines), writes it through git (blob, index entry, `checkout-index`; never through a working-tree path), and goes on with no model call. All or nothing: one file with a removed or changed line, a file added on both sides or deleted on one, keeps the old path for every file (an agent step in the implement sync; the automatic resolve run after an update). It runs in the implement sync before push (then the merge commit, the scope gate, the size gate and the check list, before any push), in the update run (merge commit, then the check list; a failure is `tests_failed` as before) and in the resolve run (no agent step; the marker check, the worker's commit and the gates still run). A file merged this way is not recorded with `recordConflicts`, so it adds no learned weight.
  - **Migration renumbering is removed (decision changed 2026-11-13, #659 phase 2; before: see History).** The decision that changed: Migration renumbering, in code. Its code (`renumberSteps`, `stageRenumbering` and the helpers in `src/core/mechanical.ts`), its tests and the resolve run's renumbering are removed. The implement sync, the update run and the resolve run keep only the appended-line merge. An agent still renumbers a clashing migration by hand, as `prompts/implement.md` and `prompts/resolve.md` say. A SQLite schema collision is a real conflict: SQLite numbers its migrations in `schema.ts`, and the gates report it.
  - **Config:** `mechanical_paths` (a list of non-empty paths) and `mechanical_weight` (a number above 0 and below 1.0, else startup fails), in `factory.config.json` and checked by `checkConfigKeys`; `mechanical_weight` is also settable live since 2026-11-12 (above). `src/compose.ts` now passes all five coordination keys into `FactoryConfig.coordination` (closing the known gap below). One global value until per-project settings (#99).
  - Not in this decision: SQLite migration renumbering, the resolve prompt, renumbering in the resolve run, references beyond a literal step name, hand-resolution weights (#113).
- **A held run names the holder that decides; a closed holder stops holding at once (decision changed 2026-11-07; before: the stored decision named the highest-cost holder, and a closed holder stayed named until the next claim, see History).** What changed: (1) In a claim's holds, running items and open PRs come first, then queued runs, each group highest cost first (`holdsOn`), so a `held` decision names a running item or PR, the one that keeps the run queued, even when a queued run shares more files. The rule itself is unchanged: a queued run cannot make progress before it is claimed, so it never holds on its own; a run held only by queued runs is claimed in claim order (the oldest of a group that holds each other goes first, and a run held only by a queued run that an open PR holds goes ahead of it), and only a running item or an open PR keeps a run queued. (2) When an item closes (the merge path's `pr_merged` / `pr_closed` transition, or any other close), the same transaction deletes the claim decisions of queued runs that name it as holder and have no approval, so no comment, `/approve` refusal or status page names a merged PR from that commit on, even while claims are paused; the next claim records what holds each run now. No new forge read: the merge path is still the poll that sees the merge. Found 2026-11-07 10:43Z: 15 queued implement runs, 8 of 10 slots idle, decisions showing pairs held by each other (#254 / #316); each run of those pairs was also held by an open PR (#353, #355, #357, waiting for a merge) or a running item, which the decision did not name.
- **Split parents count as merged; `/retry` re-checks a closed dependency (decision changed 2026-11-07, issue #246; before: a factory item counted as merged only with a merge sha, and nothing lifted `dependency_closed`, see History).** What changed: (1) A dependency that is a factory item counts as merged when it is closed `completed` with a merge sha, **or** when it is a split parent (never implemented itself, so it has no sha) closed `completed` whose recorded phases are all closed `completed`, the same rule that closes the parent (`closeSplitIfDone`). When the split closes, its dependents are re-checked from the store in the same pass, as after a PR merge. A dependency outside the factory is unchanged: an issue closed as completed or a merged PR is merged; a PR closed unmerged and an issue closed as not planned stay `closed_unmerged`. (2) `/retry` (new command phase `dependency_closed`, "blocked: a dependency was closed without a merge") on an item blocked `dependency_closed:#N` reads its links and the states of the dependencies outside the factory from the forge at once, whatever the refresh intervals (one read per edge, only on a human command), and stores them. A dependency still closed unmerged, or a cycle, refuses it with a reply naming it, and nothing changes. Otherwise the block is lifted with the human as actor (state change `retry_requested`, detail `released: dependency_closed:#N`) and a new implement run is queued (restart_count + 1, since the block cancelled the old run); a dependency still open then holds it as usual (`blocked_on: dependency`). `/retry` fits because, as at a failed run, it starts the step the block stopped; `/approve` keeps its meaning (the spec or the floor) and still never lifts a dependency hold. `+paths` is refused there. A dependency cycle still needs a human to edit or close the item.
- **Dependency edges re-read only when the issue changed (decision changed 2026-11-07, issue #254; replaces the in-memory 30-minute link refresh of the same day, and before that edges re-read from the forge on every poll; see History).** Coordination reads an item's dependency edges from the store. They are read from the forge again only when the issue's `updated_at` moved past the time they were read at. The open-issue intake poll reports edits: `item_requested` carries the issue's `updated_at`. For an item the store already has, the controller compares it with the item's read time (`work_items.edges_source_updated_at`). When it is newer, or there is no read time, the controller reads the links once (issue body, sub-issues, blocked-by) and stores them. Every edge and the item keep that `updated_at` (`dependency_edges.source_updated_at`, so an issue with no links has a read time too). The same or an older time (the poll's `since` is inclusive, so the newest issue comes back every poll) reads nothing. A new item's links are read at intake, as before, with its `updated_at`. A failed read clears the item's read time, and so does an item from before this change. The next coordination pass then reads the links once and records the store time; after a failed read, that pass waits 10 minutes, so links that keep failing (a 403 or 5xx outage) cost one read per item per 10 minutes, not one per poll. A failed read stops no coordination: it is logged (`dependency links not read` / `dependency state not read`) and the stored edges and states apply; a failed outside-state read is not tried again for 10 minutes. A `/retry` at `dependency_closed` reads the links and every edge's state again at once (see Split parents above). Items with a PR or closed are not re-read. There is no timed link refresh: a sub-issue or blocked-by link added without the issue counting as updated is read on the issue's next edit or `/retry`. The factory's own label and comment writes also move an issue's `updated_at`, so they cost one read each, not one per poll. A dependency the store does not track is read from the forge at most once per 10 minutes (`DEPENDENCY_STATE_TTL_MS`). This is an in-process cache, like the ETag cache (design §5 Sources): a replica without it asks once. A dependency that is a factory item is still read from the store each pass. **Request budget:** while a source reports `lowBudget()`, the optional reads wait for the reset. Those are the forge state of untracked dependencies (the stored state stays), the coordination re-read of unread links, and the start-up status catch-up, which runs on the first tick whose budget is back. GitHub's `lowBudget()` is now also true under 10% of the reported limit, not only under `github.min_remaining`. It still logs one line on entering and one on leaving, and the budget is per process, in memory. Schema: SQLite migrations 33 (`dependency_edges.source_updated_at`) and 34 (`work_items.edges_source_updated_at`). Not in this decision: webhooks as a trigger for edge reads, a store-backed budget shared between processes, and a draining process stopping its controller (#294).
- **Coordination: dependencies and a cost threshold (decision changed 2026-11-03, issue #115; before: the claim held an implement-type run only while its own item had one running, so a dependent item could start before the work it needs merged, overlapping items always ran side by side, open PRs held nothing, and a file that conflicted again and again weighed the same as any other).** What changed: a claim now also holds an `implement` run (it stays queued, with a stored reason) for two reasons, both read from the store inside the same `worker_claim_locks` transaction, never from the network.
  - **Dependencies.** An item depends on every issue named on a `Depends on: #N` line of its issue, on its GitHub sub-issues (a parent waits for its sub-issues) and on its blocked-by links (the GitHub source reads all three; a list GitHub has switched off gives none). Edges are stored per item (`controller_dependency_edges`, with the source id even for an issue outside the factory) at intake and again only when the issue changed (see Dependency edges re-read only when the issue changed above). The controller writes each edge's state outside the claim lock: from the store for a factory item (merged = closed `completed` with a merge sha, or a split parent whose phases closed `completed`; see Split parents above), else from the forge (an issue closed as completed or a merged PR is merged). Open: the item gets `blocked_on: dependency` and a `blocked_reason` naming the items (`waiting for #92 to merge`, one comment), stage `RUNNING`, status label "implementing". Merged: when the dependency's PR merges, the controller clears the hold in the same event, and the next claim takes the run (for an item outside the factory, on the first poll after its state is read again, at most 10 minutes later). Closed without a merge: `blocked_on: human`, `dependency_closed:#N`, queued runs cancelled, one comment; `/retry` re-checks it (see Split parents above). A cycle: refused, `blocked_on: human`, `dependency_cycle: #a → #b → #a`, queued runs cancelled, one comment keyed `dependency-cycle:<id>`. `/approve` never lifts a dependency hold; its refusal says so (new command phase `dependency_hold`, "waiting for a dependency to merge").
  - **Cost.** For an item without a PR, the cost of running it next to another item is the sum of the weights of the paths both change (the shared-path test is the scope gate's `isCovered`): 1.0 per shared path (a mechanical path 0.25, see Mechanical paths above); a file with two or more recorded conflicts 1.0 + 0.5 per conflict, at most 4.0; a hotspot (`hotspot_paths`: both schema files, `src/controller/`, `src/worker/`, `docs/design.md`, `SET_UP.md`; see Default hotspots above) the fixed `hotspot_weight` 3.0 (a higher learned weight wins). A cost at or above `max_coordination_cost` (**2.5**, raised from the 1.5 first proposed) holds the run. Holders: items with an implement-type run running, items with an open PR even with no run (its stored diff file list `pr_files`; a PR opened before this change has none and falls back to `allowed_paths`, and the comment says so), and other claimable queued implement runs. Each side's files: `pr_files`, else triage's `files_to_change` (now stored), else `allowed_paths`. **This replaces the plain overlap view:** one or two ordinary shared files (1.0 or 2.0) run in parallel, a hotspot or a file with three or more recorded conflicts serializes. Deadlock rule: a run held only by other queued runs is claimed in claim order, so the oldest of a group that holds each other goes first. (See A held run names the holder that decides, above, for which holder a decision names.) Each decision is stored per run (`controller_claim_decisions`: shared paths with weights, total cost, threshold, holder item or PR, whether the holder fell back to `allowed_paths`), rewritten only when it changes. A cost hold keeps `blocked_on: none` (status "implementing"); the controller posts one comment per (run, holder) on the poll: `The implement run is held: waiting for #92 to merge: both change src/worker/runner.ts (conflicted 6 times), cost 4.0 > 2.5.` `/approve` on such an item records `coordination_approved` (the approver's user ID as actor) and the next claim takes the run.
  - **Never held:** triage, review, update and resolve runs, and implement runs of an item that already has a PR (review fixes: their conflicts are the PR's, handled at merge).
  - **Learned weights:** the worker records one conflict per file at each base merge that conflicts and is not merged in code (sync before push, the update run, the resolve run), keyed by item and base sha, so an update and its automatic resolve on one base count once (`controller_file_conflicts`, `recordConflicts`). A later hand-resolution record (#113) can use the same call.
  - **Config:** `max_coordination_cost` (number above 0, default 2.5), `hotspot_weight` (default 3.0), `hotspot_paths` in `factory.config.json` (the first two also settable live since 2026-11-12, above); a zero or non-numeric value fails at load (`checkConfigKeys`). One global value until per-project settings (#99). `src/compose.ts` passes them into `FactoryConfig.coordination` since 2026-11-07 (issue #297); before, the worker used the defaults, which equal the checked-in values.
  - **Schema:** migration 16 (SQLite) adds `work_items.files_to_change` and `pr_files` and the tables `controller_dependency_edges`, `controller_file_conflicts`, `controller_claim_decisions`. No shipped migration changed.
  - Not in this decision: per-project thresholds (#99), sources other than GitHub, a command to resume an item blocked by a cycle (a human closes or edits it), showing a cost hold on the status page (it shows `blocked_on` and `blocked_reason`, and a cost hold keeps both clear).
- Lease + heartbeat; expired leases released by code. Each claim bumps a **fencing token**; heartbeats, completions, handoff rows and broker calls carry it, so a worker that lost its lease can't write (decided 2026-10-31).
  - Host sleep: **status and token decide whether a lease is held, not the clock.** Heartbeat, completion, handoffs and broker calls are accepted while the run is `running` with the caller's token, even after `lease_expires_at` passed. So a worker that wakes from a sleep renews its unreclaimed lease and finishes on the same attempt. Expiry only makes a run eligible for the reaper. Once the reaper requeues or fails it, or another worker reclaims it (token + 1), the old token is refused everywhere. The reaper keeps its previous tick time in memory (per process, not shared between replicas). If more than `lease_ms` passed since then, it skips expiring leases for one `heartbeat_ms`, so workers that slept on the same host can renew first. Residual gap: a reaper on a host that did not sleep still requeues a sleeping worker's run once `lease_ms` passes. Closing that needs a human decision (longer lease, or host liveness in the store).
  - **Host sleep record (decision changed 2026-11-07, issue #218; before: see History).** Each worker checks every wait of its idle tick, its pause watch and its heartbeat with one shared check: a wait that ended more than **60 s** (`HOST_SLEEP_MS` = 60 000 ms) after it was due means the host slept, and the worker records one `host_slept` row in the store (`recordHostSleep`): its worker id, the wake time (`woke_at`), how late the wait ended (`gap_ms`, the time since the wait started minus the time it asked for) and the run it held (`run_id`, null on an idle tick). Late by 60 000 ms or less records nothing. One sleep wakes several loops of the same worker; a late wait whose span (due → woke) overlaps the last one that worker recorded is the same sleep and records nothing (in-process, per worker: it dedupes only its own loops). The row is keyed by (`worker_id`, `woke_at`), so a repeat write keeps one row. The heartbeat records after its renewal, so a late wake still renews first. A failed write is logged (`host sleep record failed`) and never stops the loop or the run. The `heartbeat late; renewing now` warning (gap over 2 × `heartbeat_ms`) is unchanged. Each worker records its own row: two workers on one host that slept give two rows, and the worker id shows which. `/api/v1/health` lists the 10 newest, the item detail those of the item's runs (design §9). Schema: SQLite migration 28 (`worker_host_sleeps`). Not in this decision: pruning old rows, a per-host dedupe across workers, sleeps of the controller or the listener, any change to lease, fencing, claim or reaper rules.
- **Budget checkpoints (new, 2026-11-01; §6):** the controller checks an item's token budget only where it queues an implement or review run, in the same conditional transition as the outcome it applies, never mid-run. At the budget the run is held on a `controller_budget_checkpoints` row instead of queued, and `/budget` queues it later under the same key.
- Runs: the controller enqueues, workers claim. A transition can **ack a finished run and enqueue the next one in the same transaction**, so a crash between "decide" and "enqueue" can't strand an item (decided 2026-10-31).
- **SQLite builds its schema on open (decision changed 2026-11-12, #576 phase 3, wi_3bb50eea9fda47638735d4b569f55b1e; before: see History).** SQLite builds its schema on open.
- Time is injected through a `Clock` interface: `SystemClock` in prod, `FakeClock` in tests (decided 2026-10-31). Crash → resume from branch + latest handoff, `restart_count` (not `loop_count`).
