# 5. Coordination

- Judgment calls default to humans (form + reason). Recurring decisions → proposed rules → human approves.
- Isolation: a worktree + branch per run (container later); ports and test DB per worker, chosen from `SF_WORKER_INDEX` (unique within one process only); shared pool mounted read-only with one updater. An item never has two implement-type runs at once; items with overlapping paths do (Parallel workers, below).
- **Parallel workers.** `workers` in `factory.config.json` (integer ≥ 1, default 1, anything else fails at startup) sets how many worker loops `factory dev` and `factory worker` run in one process (`WorkerPool`). Each has its id `<host>:<pid>:<n>` and passes `SF_WORKER_INDEX=n` to the agent and to the update run's test command. They share one counted `KeepAwake` (held while any run is in progress) and one drain (no claims after it, acknowledged after the last in-flight run). **One branch writer per item:** a claim skips an implement-type run (`implement`, including a review fix, and `update`) only while the same item has one running. Overlapping paths no longer hold runs back; their conflicts are handled at merge (sync before push, the update run, `/resolve`). Triage and review are never skipped. The check and the claim are one store transaction that first takes the lock row in `claim_locks` (migration 7), so two claimers on MySQL cannot both start one item's run; a skipped run stays queued and is claimed after its item's run completes. **Claim order:** a claim takes queued runs by kind rank, then `created_at`, then insertion order. The rank is review, triage, update, implement, resolve: runs that lead to a human decision first (review takes a PR toward ready-to-merge, triage gives the owner a spec to approve), then the branch writers, and `resolve`, a long branch-writing agent run, last. Within one kind the oldest run still goes first. A held run (its item has a branch writer running, or its `not_before` has not passed) blocks nothing behind it. Retry backoff, the rate-limit pause and the one-branch-writer rule are unchanged. Not in this change: aging or fairness, so a steady stream of review and triage runs can delay implement runs. Not in this decision: pausing every worker on a usage limit across processes (after #41), showing which worker runs what on the status page, splitting one item across workers, automatic scaling, and an index unique across processes or hosts.
- Lease + heartbeat; expired leases released by code. Each claim bumps a **fencing token**; heartbeats, completions, handoff rows and broker calls carry it, so a worker that lost its lease can't write (decided 2026-10-31).
  - Host sleep: **status and token decide whether a lease is held, not the clock.** Heartbeat, completion, handoffs and broker calls are accepted while the run is `running` with the caller's token, even after `lease_expires_at` passed. So a worker that wakes from a sleep renews its unreclaimed lease and finishes on the same attempt. Expiry only makes a run eligible for the reaper. Once the reaper requeues or fails it, or another worker reclaims it (token + 1), the old token is refused everywhere. The reaper keeps its previous tick time in memory (per process, not shared between replicas). If more than `lease_ms` passed since then, it skips expiring leases for one `heartbeat_ms`, so workers that slept on the same host can renew first. Residual gap: a reaper on a host that did not sleep still requeues a sleeping worker's run once `lease_ms` passes. Closing that needs a human decision (longer lease, or host liveness in the store).
- **Budget checkpoints (new, 2026-11-01; §6):** the controller checks an item's token budget only where it queues an implement or review run, in the same conditional transition as the outcome it applies, never mid-run. At the budget the run is held on a `budget_checkpoints` row instead of queued, and `/budget` queues it later under the same key.
- Runs: the controller enqueues, workers claim. A transition can **ack a finished run and enqueue the next one in the same transaction**, so a crash between "decide" and "enqueue" can't strand an item (decided 2026-10-31).
- Store backend (D3 changed 2026-10-31): **MySQL** by default, because several workers and machines are planned. SQLite stays for tests and single-machine use. `factory.config.json` → `store.type` picks one (a plugin name, D6; `docs/plugins.md`). The store logic exists once (`SqlFactoryStore`); a backend is only a `SqlDriver` (transactions, statements, lock syntax), and both pass the same store contract tests. MySQL claims runs in READ COMMITTED transactions; since parallel workers (2026-11-01, below) every claim first locks the `claim_locks` row instead of using `FOR UPDATE SKIP LOCKED`, so the same-item check cannot race.
- **MySQL schema steps.** Now each schema or data change is one numbered file in `migrations/mysql/` (`NNNN-<name>.sql` or `NNNN-<name>.ts`, contiguous, never edited once shipped; README there), run only by `npm run migrate` (`src/impl/store/mysql/migrations.ts`). The state is one number in `schema_state`; step `NNNN` moves it from `NNNN-1` to `NNNN`, and the runner refuses, changing nothing, when the recorded state is not the next step's starting state (e.g. ahead of the newest file). The eleven old groups stay in code as a frozen baseline (state 11): they build an empty database; an existing database (legacy `schema_migrations` at 11) is only stamped 11, with no schema or data statement. `npm run migrate -- --status` lists the state and pending steps; `-- --dry-run` prints each `.sql` step's statements and the rows a `.ts` step's `plan` would change (READ ONLY transaction), changing nothing; the plain run prints a backup reminder, then applies steps in order under a named lock, recording the state after each. A `.sql` step is not atomic (MySQL DDL commits on its own; a failure leaves the previous state and the next run starts that step again, so steps must be safe to rerun); a `.ts` step's `apply` runs in one transaction with its state update. `.ts` steps are compiled by `npm run build` through `tsconfig.migrations.json` into `dist/migrations/mysql/`. `MysqlDriver.migrate()` (the `FactoryStore.migrate()` callers in `build()`, `buildUiParts()` and `golden add`) is now a check: it throws "… run `npm run migrate`" while steps are pending and applies nothing, so `dev`, `worker`, `controller`, `status`, `ui` and `golden add` refuse to start; a database ahead of the code still starts. `schemaVersion()` throws the same message, so doctor's MySQL check (and the Health panel) shows pending steps as a FAIL line, not the warn of the 2026-11-01 read-only probe decision (§9). Steps load from the code root, so the updater's runtime copy carries `migrations/`. SQLite is unchanged: it builds the latest schema on open, and `npm run migrate` on SQLite exits non-zero ("SQLite has no migration scripts"). No down-migrations. Rollout: every existing MySQL install runs `npm run migrate` once (it only stamps 11) before the factory starts again.
- Time is injected through a `Clock` interface: `SystemClock` in prod, `FakeClock` in tests (decided 2026-10-31). Crash → resume from branch + latest handoff, `restart_count` (not `loop_count`).

## History

- **Parallel workers** (new decision, 2026-11-01). Before: one worker loop per process, so approved items were built one at a time.
- **One branch writer per item** (decision changed 2026-11-01). Before: the overlap rule skipped an implement-type run while any item with overlapping `allowed_paths` had one running, later with shared docs exempted; nearly every spec lists a whole folder, so one implement run ran at a time whatever `workers` said.
- **Claim order** (decision changed 2026-11-01). Before: FIFO, the oldest queued run first whatever its kind, so a short triage or review run that a person waits on could sit behind older implement runs for about 45 minutes while every worker was busy.
- **MySQL schema steps** (decision changed 2026-11-01, issue #97). Before: the MySQL schema was a positional array of statement groups in `src/impl/store/mysql/schema.ts`, applied silently by `store.migrate()` on every store open, so nobody could see or check pending changes, a data change could not run on its own, and parallel PRs collided on the same array position.
- **Host sleep** (fencing rule changed 2026-11-01). Before, `lease_expires_at` was also a hard deadline for every write.
