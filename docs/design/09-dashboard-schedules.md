- **The Schedules page lists schedules with a Switch and a row menu, shows the selected one's runs, and creates or edits one in a Dialog (decision added 2026-11-24, local-task-tk_0ae5a8e9 phase 2 of 2, wi_85d730fa1f614affaa897cbd9cbe6aa0; current; replaces none).** `web/src/views/schedules.tsx` (the form in `web/src/views/schedules/form.tsx`, the catalog keys of each word in `schedules/labels.ts`), route `/app/schedules`, `PAGES` entry `schedules` (icon CalendarClock, group `tasks`, after Calendar), text in `web/src/i18n/en/schedules.ts`. The page calls the phase 1 routes of [08-schedules.md](08-schedules.md) through `web/src/api/schedules.ts`; it changes no route and no core function.
  - **Layout.** `PageHeader` (title Schedules, a one-line description) with one primary action, New schedule, in `actions`. Under it two Cards, siblings after the header spaced by the Card's own top margin as on Health, Settings and Routines (a flex column with `gap-6` on top of that margin doubled the space; fixed 2026-11-24, see history): the schedules, and the selected schedule's runs. Header, Card and table structure follow `web/src/views/tasks.tsx`; the design-system "Stays fixed" list is kept (celadon palette, one primary action, header and Card structure, no raw IDs).
  - **Schedules Card.** A `DataTable` (`GET /api/v1/schedules`, polled like the other pages; the schedule's title leads each row) with the columns Schedule, Repeats (plain words, see the first decision), Next run (local time; "Paused" for a paused schedule), State (a Badge: Paused, Running, Waiting), Does and On, then a "⋯" `OverflowMenu`. The title selects the row (see the decision above). **On** is a `Switch`: on while `next_due_at` is set, off while it is null. Turning it off posts pause, on posts resume (`POST /api/v1/schedules/pause`, `/resume`); the schedule is paused exactly when it has no next run, so no new field holds it (owner answer 1: pause clears the next due time, no migration). The menu holds Run now (posts `/run`; off while paused, as `schedule run` refuses a paused schedule) and Edit. A refusal of any write (the core's reason, the owner check) shows in one `Notice` (tone bad) above the table; the Switch and the menu send nothing while the session token is unread or a write is in flight. No raw ID is shown anywhere: the table has no ID column, and the page makes a new schedule's ID from its title (lower-case words joined by `-`, a number after it when taken), never shown.
  - **Runs Card.** Titled "Runs of <title>" for the selected schedule, else "Runs" with "Select a schedule to see its runs." A `DataTable` of the rows of `GET /api/v1/schedules/runs?schedule=<id>` (read only while a schedule is selected), newest first, with Started (the run's `occurrence_at`, the slot it was due for, not the time it was claimed), Result (Ran, Skipped: still running, Skipped: factory busy, Held: waiting for your approval, Rejected), Cost (USD) and Output; a column empty in every row is left out, as `DataTable` does.
  - **New schedule and Edit.** One `Dialog` (`ScheduleDialog`), built from `Field`, `Input`, `Select`, `Textarea`, `Switch` and the Dialog's `ButtonRow`, so a row's input opens a modal and never changes the row's height. Fields as the CLI's flags: Title, Repeats (interval, daily, weekly, cron), When (the cadence's spec, with a help line per kind), Time zone (the browser's zone to begin with), Does (build, agent, feedback: owner answer 2), Text (the build's description, or the agent's and feedback's prompt), Skip while the factory is busy (`Switch`) and Token limit (a number; blank means the default and is left out). New posts `/add` with every field. Edit posts `/edit` with only the fields the owner changed (so an unchanged cadence does not move the next run), a changed kind always with its text, and closes with no request when nothing changed. A refusal stays in the Dialog with its reason. Deleting a schedule is not offered: no route or command exists.
