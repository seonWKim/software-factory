# 5. Coordination: Slack intake and messages

- **Slack reads Good, Bad and Feedback presses and the Feedback modal itself** (decision changed 2026-11-12, one-tap verdicts; current; replaces "a Slack button press is either a command (an inbox event or a stored command row) or a proposal press, and the source opens no modal", see History). What a tap means is design 04-gate-commands ("One-tap verdicts"). A press of `sf_verdict:good|bad|feedback`, and a `view_submission` of the Feedback modal (`sf_feedback`), are handled inside the Slack source (`src/impl/source/slack-verdicts.ts`), as chat commands are: the message is found by its ts in the store's posted-message records (`listPostedCommentsById`, a result marker in a configured channel, in a work item's thread; the modal's metadata only names the ts, which is checked again), the presser's linked user is checked for `record_verdict` through the source's `auth` (the local auth plugin), and the verdict is stored with `recordVerdict` (`replace`) before the envelope is acked. Nothing goes to the inbox. Feedback opens the modal with `views.open` (the press's `trigger_id`; a redelivered press's expired trigger is logged, not retried). After the store write the source edits the message once per stored verdict. A waiting spec's short message (below) ends with Good, Bad and Feedback after Reject…, and its edit shows the verdict line in it. A `view_submission` with the Feedback callback goes to the verdicts; any other goes to the spec and item modals. No new Slack scope: buttons and modals use the app's interactivity over Socket Mode. No schema change; solo and enterprise run the same path.
- **Slack spec messages: short, with decision buttons** (decision changed 2026-11-12; current; replaces "a spec is posted whole to Slack, after a separate `Status: needs approval` message", see History). The decision that changed: **in Slack, a spec waiting for approval is one short message whose decisions are answered with buttons.** The Slack source reads the spec comment by its headings (`## Factory spec`, `### In short (AS-IS → TO-BE)`, `### Decisions for you`, whose lines carry their `Proposed default:`) and posts: "Needs your approval: <item title>" (the title from the store), In short (at most 3 lines), Decisions (one line each with its proposed default), and a Full spec link to `<base>/app/items/<id>`, the base `slack.dashboard_url` when set, else the local dashboard `http://127.0.0.1:<ui.port>` (only the owner's machine opens it). Problem, Applied defaults, Done when and the rest stay in the store and on the dashboard. Buttons: Approve with defaults, Other… (when there is a decision: a modal with one field per decision, up to Slack's 99, prefilled with its default; its submit stores one `/approve` with an `N: <answer>` line per non-blank field) and Reject… (a modal with one reason field; its submit stores one `/reject <reason>`). Presses and submits follow the proposal press rules: the linked user, stored first as the typed command's row (keyed on the press or the view ID), applied through the controller's `AuthProvider` check; an unlinked account gets the one refusal, a spec no longer waiting the stale reply, and neither opens a modal. A modal opens from the press itself, before the ack (a `trigger_id` lasts about 3 seconds), after the egress scan; a failed `views.open` is logged once and not retried. The spec message keeps its buttons after approval (a press then gets the stale reply). No status message is posted just to say a spec needs approval: a thread with no status message yet gets none then, and a later status posts or edits the one message in place. A spec approved with no reply (auto mode) is still posted whole. Why: on a phone, the whole spec was a wall of text with the decisions, the one thing to act on, in its middle; one message per spec now carries the ask and the answers. Core, the controller, the other sources and the spec text are unchanged.
- **Slack: items are viewed in Slack, not on 127.0.0.1** (decision changed 2026-11-12, owner in Slack: "not possible to click the link in my phone"; current; replaces "with no `slack.dashboard_url`, the Full spec link and the notice title links go to the local dashboard `http://127.0.0.1:<ui.port>`", see History). The decision that changed: **with no https `slack.dashboard_url`, the Slack source posts no dashboard link; a View button opens the item in a Slack modal instead.** The View button (`sf_view`, value the item ID) is the first section's accessory on a waiting spec message (in place of the Full spec link) and the accessory of each owner notice line (one section per line, the title kept as plain text). A View press by a linked Slack account, in a listed channel or in `slack.notify_channel` even when that channel is not in `slack.channels` (owner answer 1), reads only the store and makes one Slack call, `views.open`: a read-only modal with the item's title, its state, the one-line reason it needs the owner (the notices' reason), and the waiting spec, or else the latest factory message, as mrkdwn with its command footer dropped; sections of at most 3000 characters and at most 45 of them (under Slack's 100 blocks), a longer body cut with the note naming `factory task show <id>`. Its buttons are the ones that apply now: Approve, Other… and Reject… for a waiting spec; Merge (`sf_merge`, its own action ID, not a thread footer button) for an item waiting for a human merge. The whole modal passes the egress scan before `views.open`; a withheld one shows the withheld notice and none of its text. An unlinked presser gets no modal. Presses inside the modal take the thread buttons' paths: the same link, state and stale checks, the same command rows (Merge stores the `merge` command as the linked user); Other… and Reject… open their modal with `views.push`. For an item from a Slack thread the answer is posted in that thread, as for its own buttons. For any other item (local, GitHub) the command runs with nothing posted in a Slack channel, its answer stays in the item's own thread, and the open modal is replaced with `views.update` by one line: the result (e.g. `Approved.`) or the refusal (owner answer 2). `views.update` and `views.push` need no new scope. With an https `slack.dashboard_url` (a tunnel the owner set up) the links stay as before and no View button is posted. The flow lives in `src/impl/source/slack-modals.ts`. Messages already posted are not edited. Why: a phone cannot open the owner's local dashboard, so the owner could not read a spec away from the Mac; nothing of the dashboard is exposed to the network.

- **Slack: no mention needed in a thread the factory owns** (decision changed 2026-11-12, issue #585; current; replaces "a reply in an item's thread with no mention still needs the slash", from the #541 decision below, see History). The decision that changed: **in a Slack thread that is a work item's (the factory owns it), a person's reply with no mention is read; in any other thread it is not.** In an owned thread a reply with no mention is kept on the item's thread, as before; a command typed with its slash is that command; any other reply, a bare command word included, is a plain comment that the plain-words reader reads (04-gate-commands): it answers once with proposed commands stored as pending, with a button each, Confirm all and Cancel, and changes no state until a press or a typed command. In a thread the factory does not own, a reply with no mention is other people's conversation: not stored, no model call, no reply; a mention there still works. No code change: the Slack source already did this (`fromEventsApi`), and tests/slack-source.test.ts now holds both halves. Why: the line that said a plain reply needs the slash no longer matched the reader, and the owner should not have to mention the bot in their own item's thread. Solo and enterprise are the same: one code path; the reply's author needs `approve_spec`, as before.
- **A Slack top-level work request becomes one item** (decision changed 2026-11-26, phase 1 of local-task-tk_dd036ba7; current; replaces "a Slack top-level mention becomes an item only on a press", see History). The decision that changed: **a top-level mention the model reads as one work request (`request`) is made a work item at once.** The Slack source still marks the `item_requested` of a top-level mention (one outside any thread) with `classify`; a mention inside a thread that is not an item, and every other source (local CLI, GitHub), are taken in as before. The intake unit reads a classified message once (`readMessage`); for a `request` answer it makes the item with the same `createWorkItem` call a press makes (the requester's `submit_work` check, keyed on the message's source id, the problem holding the message text), then posts one line naming it, `Task created: <item ID> <title>` (the ID in code font), keyed on the source id (`factory:task-created:<source id>`), so a redelivery finds the item and makes no model call, no second item and no second reply. Slack events carry no files, so a pasted image is not fetched: the item is made from the message text. A chat message still gets one answer; an unsure message, and one it does not read (no model, a sender without `approve_spec`, too long, a failed or malformed answer) get a short reply with a **Make this a task** button; an empty one gets `I couldn't read that.` and one the egress scan flags gets one fixed line, both with no button and no item; a model answer the scan flags posts nothing and makes no item. The button and its press are unchanged: an `item_requested` from the presser, marked `offered`, keyed on the message's source id, that creates the item and posts `Task created: <title>`, with no model call (04-chat-commands.md has the reading). No schema change, no new state; solo and enterprise run the same path on their store.
- **The sources read reactions on the factory's messages** (decision changed 2026-11-11, issue #524; current; replaces "a source reads comments and adds 👀, and reads no reactions", see History). What each reaction means is design 04-gate-commands ("A 👍 or 👎 on a factory message is a verdict"). **GitHub:** GitHub has no batched reaction read, so inside its poll the GitHub source lists the comments the store records as posted on a PR of its repository in the last 7 days (`listPostedComments`: the posted-message record's URL names `/pull/`) and reads each one's reactions with one GET per poll; every GET is conditional, so an unchanged list is a 304 that GitHub does not count. The cursor keeps, per comment still in the window, the highest reaction id delivered, so a reaction is delivered once. Under `lowBudget()` no reaction is read and the marks are kept; with no store there are no records and nothing is read. **Slack:** the app needs `reactions:read` and the `reaction_added` event (slack/manifest.json; an installed app must be reinstalled to get them). A reaction event names the message ts but not its thread, so the source finds the message in the store's posted-message records by its ts (`listPostedCommentsById`), which name the thread; the status message, a message with no record, a thread that is no work item, a channel not configured and a message older than 7 days (message ts against `event_ts`) mean nothing. Without the scope no such event arrives and nothing else changes; GitHub reactions are read whether Slack is on or not. **No schema change:** the two store reads are read-only, on the existing records (`outbound_deliveries`, whose `updated_at` is the post time once a comment is recorded), in the SQL store (`src/impl/store/sql/posted-comments.ts`; the interface is `PostedCommentReads` in `src/core/reaction-verdict.ts`, which `FactoryStore` extends).
- **Slack buttons follow the item's state** (decision changed 2026-11-11, issue #586; current; replaces "a message's buttons are built once from the command footer the controller wrote when it posted the message, and never change", see History). On each status write (one per state change, delivered by outbound) the Slack source also edits each earlier factory message of the item's thread whose footer buttons no longer all apply (`settle` in `src/impl/source/slack-source.ts`): one `chat.update` that keeps only the buttons that still apply, drops the footer's command list and ends with the Done line (`Done: <what happened> by <actor ID> at <time>. The item is now <phase>.`). It reads the store only: the thread entries' bodies give each message's buttons, the posted-message records its ts. Each update is recorded under `slack:done:<ts>:<buttons kept>` in the same posted-message records, so running it again makes no second call, and a later change that drops more buttons edits once more. A message posted before the records, a deleted one, or one the egress scan blocks is left as it is; Slack messages posted before this change are not backfilled. A press of a button that no longer applies gets one reply saying what already happened, with the current buttons (04-gate-commands.md). **Order:** the spec comment of a transition is stored before the transition commits and its status after; one announce lists thread entries before actions, and outbound sends a destination's batches one at a time in intent order, so the status is never posted before that spec is delivered (a failing spec delivery holds it). No schema change, no new state; solo and enterprise run the same path on their store.
- **Where intake runs** (since 2026-11-08, RFC 0015 M4): the polls, cursors, stream relay and command reads below now run in `src/inbound/` and reach the controller over the bus; the order and dedupe rules below are unchanged. See 10-event-driven.md, "Intake runs in inbound, on the bus".

- **Slack commands need no slash after a mention in an item's thread** (decision changed 2026-11-11, issue #541; current; replaces "after a mention, only `approve` works without its slash (issue #528); every other command needs it", see History). Slack takes a message that starts with `/` for its own slash commands, so the factory's commands follow a mention. In an item's thread, a mention whose first word is a command word with no slash is that command, with the same text: `@software-factory revise <feedback>` stores and applies exactly what `@software-factory /revise <feedback>` does, through the same role check, keyed once on the Slack event ID. It covers every command the Slack source takes with a slash after a mention: `approve`, `retry`, `revise`, `reject`, `resolve`, `budget`, `verdict`, `standing`, `link`, and `merge` (bare already). The Slack source adds the `/` (`withSlash` with `THREAD_BARE_COMMANDS`, src/core/commands.ts) before the same parsers read it; `help` is read bare anywhere, as before. The slash form after a mention keeps working. Outside an item's thread nothing changes: a bare command word is a request in plain words (`@software-factory reject duplicate emails` is answered with the offer to make it a task), and the slash form of an item command gets the reply naming where it works. A reply in an item's thread with no mention is read by the plain-words reader (see the no-mention rule above); its bare command word is never applied by itself. What Slack shows: the hint under a factory message, the `help` reply in a thread and the refusal outside a thread name each command without its slash (`chatForm`); SET_UP.md's Slack list does too. Outside an item's thread `link` keeps its slash in `help` and the unlinked reply, since a bare `link <code>` there is a request. GitHub's parser, footers, the shared refusal text and the dashboard are unchanged. Why: Slack users type the bare word; storing it as a plain comment did nothing. Solo and enterprise are the same: one code path, the linked user's stored role decides.

- **The command cursor starts at `commands` only** (decision changed 2026-11-11, issue #467; current; before: the relay read `intake:local` whenever `commands` was missing, see History). The command relay reads one cursor, `commands`; no row means it starts at seq 0. A one-time data step copied the old `intake:local` value into `commands` when `commands` was missing (one guarded INSERT, never an overwrite; `intake:local` itself is left as it was). Solo (SQLite): the inbound migration `20261111T1200-inbound-commands-cursor` runs once when the store opens, after the cursor table rename, in the same transaction as the other steps. Why: the fallback cost a second cursor read on every tick until a store's first command was relayed, and was a second way to start the same cursor that only an upgrade needed.

- **Slack replies on the item's thread** (new decision, 2026-11-10, issue #480; current). The decision that changed: **a person's reply in a Slack work item's thread is stored on the item's thread**, as the GitHub source stores a comment; before, the Slack source held the store read-only and a reply was only an event the controller used for `/link` and commands, so the item page showed only the factory's messages for a Slack thread. The Slack source (src/impl/source/slack-source.ts) now holds `getWorkItemBySource` and `recordItemMessage`. A reply in an item's thread (a plain `message` reply, or an `app_mention` in the thread), a command included, is written with `recordItemMessage` before its event is returned or its command runs: marker `slack:<message ts>`, actor `slack:<Slack user ID>` (never a display or real name), body the reply text with the bot mention removed, and no delivery, so no outbox row (it is already in Slack). The command still runs once, as before. The store ignores a repeat marker, so a redelivered envelope or a restarted listener stores nothing more. A failed write throws: the envelope yields no event and is not acked, so Slack sends it again (ack after store). Not stored: a reply in a thread that is not a work item, the mention that creates an item (its request text is the item's body), an empty reply, button presses. Entries keep the order the store received them in, which is the order Slack sent them. No migration, no schema change. Solo default: the entry goes to the local store. Enterprise setting: the same call on the shared store, so every replica sees it. Not built: backfilling replies received before this change, following Slack edits and deletes of a stored reply.

- **Slack intake and source routing.** The decision that changed (2026-11-01 decision, built 2026-11-07, issue #109): **Slack threads are a real-time source**, the `slack` stream plugin, next to GitHub through the existing per-type routing. A mention of the bot (`app_mention`) in a channel listed in the `slack` block of factory.config.json (`channels`: channel IDs, checked at load; an unknown key, a name instead of an ID, or a missing block while selected fails startup) is read from its thread (a top-level one becomes a work item only on a press of its Make this a task button, see the 2026-11-12 decision above), source id `slack:<team>:<channel>:<thread ts>`; `createWorkItem` is idempotent on it, so the `message` + `app_mention` pair Slack sends for one mention, and any redelivery, is one item. Only `app_mention` starts or commands with a mention; a thread reply without one is a command or a plain comment for an item thread; top-level messages without a mention, the bot's own messages, other bots and `subtype` events are ignored. Inbox dedupe is on Slack's `event_id` (a button press: team, user, `action_ts`). People are Slack user IDs (provider `slack`), linked to factory users with `/link`; an unlinked account's command is refused with one reply, and an unlinked mention gets one reply instead of the silence a GitHub issue gets (the label is GitHub's gate; Slack has none). Replies: the controller's comments, converted to mrkdwn, with a button for each footer command that takes no text (`approve`, `retry`, `resolve`, `budget`, `help`; reject, revise, verdict stay typed) and Confirm/Cancel under a suggestion; a press is the typed command by the presser, through the same `authorize`. Each post carries its marker's hash in Slack message metadata, and the store's posted-message record is checked first (decision changed 2026-11-11, issue #484; before: the thread was read first, see History): the Slack source writes the same `outbound_deliveries` record the GitHub source writes (`recordPostedComment`: the message ts as the comment ID, the Slack link as the URL), so a recorded marker returns its link with no Slack call. Only a marker with no record reads the thread once (`conversations.replies`), to find a message posted before the records; what it finds is recorded. So a marker is posted once. Everything posted is egress-scanned in the plugin; a blocked message is replaced, under the same marker, by one notice naming the rules, and is never retried in any form. Status is one thread message edited in place, with the PR link once there is one; its ts is recorded under the marker `slack:status`, so each later status is one `chat.update` and no thread read (the first status with no record reads the thread once, and records a status message posted before this change). A status message someone deleted (`message_not_found`) is replaced by a new one, recorded under `slack:status:after:<deleted ts>`, because a stored record keeps its first ts and no store method may change it; the source follows that chain with store reads only. A status or message the egress scan blocks is not posted or edited and leaves no record (a withheld notice is marked in its metadata and never recorded). Solo default: the records are in the local store, with no setting. Enterprise setting: they are in the shared store, so a second replica reads no thread for them. No new table, column, migration or store method. A repeated status with the same text still sends its `chat.update`. Not built: backfilling records for messages posted before this change (each is recorded the first time its thread is read). No Slack SDK (spec decision 5 changed): the listener already owns reconnects and the ack-after-store rule, so the plugin uses Node's WebSocket and the Web API over `fetch`, with no new dependency. `SUGGEST_MIN_CONFIDENCE` is 0.85 (was 0.7). Not built: DMs, reactions (no `reactions:write` scope, so `markSeen` does nothing), a channel check against the API (no `channels:read`), Slack token patterns in the egress scanner (the known-value check covers the configured tokens). Details: [docs/plugins/source-adapter.md](../plugins/source-adapter.md).
