# 5. Coordination: runs that ask for paths or wait for a dependency

- **An implement run that asks only for paths already allowed runs again, without the owner, and the prompts say ratchet lists are editable (decision changed 2026-11-16; changes the test-path grant below and "Agent asks a human"; owner's words: "agents don't know ratchet lists are always editable, so they stop to ask").** When an implement run returns `needs_human` and every path it names is already covered (`isCovered`: under `allowed_paths`, or a ratchet list `tests/architecture/known-violations/*.json`), the controller retries the implement run itself: `retry` in `src/controller/units/support.ts` with the system actor and no widening, so `allowed_paths` is unchanged, in the transition that acknowledges the run, with `detail.auto_grant: true` and the stopped run's id. The retry's note starts `already allowed: <paths>`, so the next implement prompt shows it under the approver notes; one thread comment (keyed on the run, as the test-path grant's) and a run log line say the same. It shares the test-path grant's budget and switch: at most one automatic action per item of either kind (`MAX_AUTO_GRANTS`, counted from the stored state changes), and `auto_grant_test_paths` off asks the owner instead. An ask that also names an uncovered path is not this case: test paths only go to the test-path grant, anything else to the owner, whose reply names only the uncovered paths. Review, resolve and update asks are never requeued this way, and items already held are not backfilled. `prompts/implement.md` and `prompts/resolve.md` say, next to the allowed-paths rule, that known-violations lists are always editable to shrink (never to grow); there is no update prompt. A `+paths` that adds nothing replies `already allowed: <paths>` (design 04-gate-commands).
- **An implement run that asks only for test paths gets them once, without the owner (decision changed 2026-11-15; changes "Agent asks a human" below; owner's words: "fix the failing tasks automatically").** When an implement run returns `needs_human` and every path it names outside the allowed paths is a test file (`test_globs`, default `tests/**` and `**/*.test.*`) and none is on the gate list (`isGatePath` over `GATE_PATHS`), `CLAUDE.md` or `AGENTS.md` (at any depth; refused by this check only, `GATE_PATHS` is unchanged), the controller applies the owner's `/retry +paths <those paths>` itself: the same transition (`retry` in `src/controller/units/support.ts`, the paths widened as `/retry +paths` widens them) with the system actor, in the transition that acknowledges the run, with `detail.auto_grant: true` and the stopped run's id. The item does not wait on the owner. The thread comment (keyed on the run) and the run log line name the granted paths and say they were granted automatically because the ask named test paths only; the retry's note says so too, so the review run sees it, and the reviewer prompt checks that the test edits only follow the change. At most one automatic grant per item (`MAX_AUTO_GRANTS` in `src/controller/units/run-results/auto-grant.ts`; the path check is `testPathsOnly` in `src/core/auto-grant.ts`), counted from the item's stored state changes, so a restart or another worker sees it; no new column and no migration. Two workers on the same result: the second transition is refused by the version fence, and its re-read finds this run's grant and changes nothing. A second ask (a covered-path requeue counts too, 2026-11-16 above), any non-test or gate-list path, or an ask the egress scan flags goes to the owner as before. `auto_grant_test_paths` (default on, per project, tighten-only: a project may only turn it off) switches it; review, resolve and update runs, `/approve +paths` and `/resolve +paths` are never granted automatically. Items already stopped are not backfilled.
- **An implement run that asks about an unmerged dependency waits for it (decision changed 2026-11-12; changes "Agent asks a human" below for this one case).** When an implement run returns `needs_human` and its reason names one of the item's stored open dependency edges (`listDependencyEdges`, each matched by its `shortRef` as a whole reference: `#9` does not match `#92`), and the item has no PR, the controller records a dependency hold instead of `agent_needs_human`: `blocked_on: dependency`, `blocked_reason` from `dependencyReason` (`waiting for #N to merge`), state change `dependency_hold`. In the same transition it queues one implement run keyed `<item>:implement:after-dependency:<stopped run>`, so applying the result twice queues one run. The store keeps a queued run of a dependency-held item from being claimed; coordination's release (`clear`) lifts the hold when the edge merges and the run starts by itself (the release itself queues nothing). One comment says what the run waits for, with no retry footer. A reason that names no open edge, and every review or resolve stop, is `agent_needs_human` as before. Items already stored as `agent_needs_human` are not backfilled.
