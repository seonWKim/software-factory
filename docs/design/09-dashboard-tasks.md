# 9. Status page: dashboard Tasks and Calendar pages

- **Every row is one `ListRow` with its actions in the "⋯" menu (decision changed 2026-11-20, wi_a2e1243f; current; replaces "action buttons beside the row" and "a row shows its raw ID", see History).** Needs you, task, done and Check rows use `ListRow` (`web/src/components/ui/list-row.tsx`): title on one line (ellipsis, full text on hover), details under it, every action in `OverflowMenu`. No raw ID; a built task's title opens its work item. Tests: `tests/ui-tasks-needs.test.tsx`, `tests/ui-needs-you.test.tsx`.
- **Needs you shows a claim pause once, in plain words (decision changed 2026-11-20, wi_cec6cd18; current; replaces "a pause in the notice, a Claim pauses section and a Check row", "an alarm's full text behind a toggle" and "a failed item reads `failed: <code>`", see History).**
  - **Pause row.** The `claim_pause` action carries `pause` and `until`; `text` is the plain name ("Model not answering"; `PAUSE_NAMES`, `src/ui/system-actions.ts`); `command` (the CLI fallback) is not drawn (decision 3). The Check row (`PauseCheckRow`, `ListRow`): name, "next check in 1m" or "ends in 1h" in a `time` whose title is the local time, and Resume now. Tasks has no Claim pauses section, and its notice names no pause.
  - **One Resume now.** `ResumeNow` (`web/src/views/system-banner.tsx`), shared with Health's pause list, posts `{ name }` with the CSRF token, then reloads the pauses and the overview; a refusal shows beside it. The 403 points to Needs you on Tasks.
  - **Alarm and failed item.** The zero-token detail says only how the last run ended, and the Full text toggle is gone (decision 2). A failed item's reason is the first line of its latest failed run's message (Withholder, run-outcome, 80 characters), else "The last run failed with no message."
- **Tasks and Calendar sit in Cards under their PageHeader (decision changed 2026-11-19, wi_de565ffb, "Professional polish: shared page header and cards"; current; replaces the Needs you and open-task `Section`s and the Calendar's bare period heading, see History).** Tasks: Needs you is a `Card` titled "Needs you" with its count, the open tasks a `Card` named "Open tasks" with no title; the empty list is an `EmptyState` with the calendar-check icon. Calendar: the period ("Nov 9 – 15, 2026") is the title of the `Card` that holds the week or month (`live`, so a change is announced), below the view switcher and the period buttons; no calendar connected is an `EmptyState` with the calendar icon. Item states on rows are the one `Badge` (09-dashboard-shell).

- **A Tasks row's title opens its description dialog (decision changed 2026-11-19, wi_6fee2cb6, "Plain tasks get a description"; current; replaces "on a Tasks row the ID and the title are both links", see History).** On an open task, when the page has a commands actor, the title is the row's text with the shared `Button` (ghost, no padding or least height, so the row keeps its height) laid over it, named "Description: <title>"; clicking it opens `DescriptionDialog` (`web/src/views/tasks/dialogs.tsx`): the shared `Dialog` titled with the task's title, one `Textarea` labelled Description holding the stored description, Save and Cancel. Save posts `{ id, body }` to `POST /api/v1/tasks/body` (`postTaskBody`, `web/src/api/tasks.ts`), reloads the tasks and closes; a refusal stays in the dialog with its reason. Cancel, Esc or the backdrop close it and post nothing. The dialog renders into `document.body`, so no row changes height (the learned rule: input in a list opens a modal). Its line under the field says Build this sends the title and the description; on a built task it says the work item keeps the text it was built with (decision 1: the title opens the dialog on a built task too, and the item link stays on the state and the mono ID, `ID_CLASS`). A done task's title, and every title with no actor, keeps the old rendering: a built task's title links to its item (`LINK_CLASS`), an unbuilt one is plain text. No new colours. Strings: `tasks.description`, `tasks.descriptionLabel`, `tasks.descriptionHint`, `tasks.descriptionBuilt`, `tasks.descriptionSaved` (`web/src/i18n/en/tasks.ts`).
- **Tasks is the landing page and holds the Needs you section (decision changed 2026-11-15; who is in the section and its Check group changed 2026-11-16, design 09-status-page; current; replaces "the Needs you page: a header, three groups, one action per row" (2026-11-13, wi_fc2c), and "Factory work" as a section of its own, see History).** The decision that changed: **there is no Needs you page; the owner's to-dos and what waits on them are one page.** `/app/` leads to `/app/tasks` (`"": "tasks"` in `REDIRECTS`, `web/src/pages.ts`), which is also where an unknown path lands. `PAGES` has no Needs you entry, no `needs` route key and no Factory group: the sidebar reads Tasks, Calendar, Plugins (its own group, the Plugins page decision above), then System. The Tasks entry carries a badge with the count of Needs-you rows (`needs_you` of the overview: the waiting items and the system actions, whatever the project tab); the top bar's "Needs you (N)" stays and links to `/app/`; the tab title reads the page, "(N) Tasks". `g n` is removed from `SHORTCUTS` and `GO_KEYS` (`web/src/keys.ts`) with `keys.goNeeds`; `page.needs` stays as the section title and the Work filter label.
  - **The section.** `NeedsYou` (`web/src/views/task-work.tsx`) is a `Card` titled "Needs you" with its count, above the selected view and below Quick add (the order decision below), shown only when an item waits. Its rows are the compact list per group (Merge, Approve, Answer or fix, then **Check**; `NeedsList`), its count the number of rows. Each item row has one primary action (Merge, Approve, Retry, Answer, or Open when the row has no command) and the overflow menu (`NeedActions`, unchanged); an Answer-or-fix reason links to the item's latest thread entry when the need names one. The Check group (All projects only) holds the overview's `system_actions`, one row each (`CheckRow`, `system-banner.tsx`, marked `data-check`, so `j`/`k` keep moving over the item rows): a non-alarm action shows its sentence and command; an alarm row shows its text on one line, the full text behind a "Full text" toggle and "Open on Failures" as its one primary action, and the auto-mode stop's alarm "Turn auto back on" with a Failures link; no dismiss. The table, its Why, Since and Issue columns, `WhyText` links in rows and the header's factory indicator are gone with the page (`NeedsYouPage` and `NeedsGroups` are deleted).
  - **Who is in it.** Every item that waits on a person or the budget (`needsYou` in `common.tsx`, the server's `NEEDS_YOU` levels; a stuck item is not in it), also one an open task in the Tasks read links through its work item ID: that task's row keeps its state badge and primary action (`WorkState` in `task-work.tsx`; an item that does not wait keeps the state button), and the item is a section row too, listed once. A done task's row keeps the plain state button. The section reads the same Tasks read and project filter as the rows: with a project tab it lists the waiting items built from that project's tasks (`useItems`, the Factory work decision below), with All projects all of them. Until the Tasks read arrives the section is not drawn.
  - **The factory's notes.** Under All projects only, after the section: the factory `Notice` (paused, stopped or failing, `factoryView`) and the claim pauses (`ClaimPauses`), drawn by `FloorStatus` (`pages.tsx`) whether or not an item waits. A project tab shows none of them. The red system-action lines and the "Open alarms: N." banner (`FloorNotes`) are gone: those are Check rows.

  - **Empty state.** One `EmptyState` message pointing to the quick-add field, with no button and no count: `tasks.emptyAll`. `tasks.today`, `tasks.upcoming`, `tasks.all`, `tasks.viewLabel`, `tasks.emptyToday` and `tasks.emptyUpcoming` are removed.
  - **Project tabs and timeline.** The project tabs filter the list, done rows as open ones. Today's timeline shows once, collapsed, above the list.
- **The Tasks page is stacked project tabs, Quick add, Needs you, list; Calendar is its own page (decision changed 2026-11-14; current; replaces "the Tasks page stacks the view tabs and the Project switcher on one row, then Quick add, Factory work, the view", see History).** The decision that changed: **the projects are a tab row under the title, above the view tabs, instead of a select on the view tabs' row.** The sidebar's Tasks group lists Tasks (`/app/tasks`) and then Calendar (`/app/calendar`), and the Tasks views show tasks only.
  - **Order and spacing.** Top to bottom under the page title: the project tabs (their own row, `Tabs`), Quick add, the Needs you section (the Factory work section until 2026-11-15), the list (the view tabs that once sat below the project tabs are removed, the one list decision above). One flex gap (the Section gap) separates the blocks; no block carries an `mb-*` or `mt-*` class. Quick add's error and a refused ⌘Z stay under the field.
  - **Factory work** is one compact list per group (Merge, Approve, Answer or fix: the `needs.group*` labels), no table header. A row has the item (and PR), its state as one `Badge`, a merge check only when it is not "mergeable", the reason only for an Answer-or-fix item (the badge already says it for Merge and Approve), and the primary action (Merge, Approve, Retry, Answer or Open) with the overflow menu. Since 2026-11-15 this list is the Needs you section (the decision at the top), with its count, and nothing shows when no item waits. It still follows the Project switcher (the decision below).
  - **Timeline.** Today's timeline (Inbox and Today) is collapsed until its control (`aria-expanded`) is pressed, and draws scheduled tasks only. Dropping a task on a half-hour slot and typing a time in the row still schedule it. Why collapsed: it filled the page with 48 empty slots; it belongs with scheduling, not with reading the list.
  - **Events leave the Tasks views.** Inbox, Today, Upcoming, List and Done show no calendar event row and no stale-sync notice. The empty states are a message that says to add a task in the field above, with no button; the Tasks section shows no count (a bare "0" removed).

- **A Tasks page (new decision, 2026-11-12, issue #607; current; replaces "the dashboard has no view of plain tasks", see History).** The one link in the sidebar's Tasks group, `/app/tasks` (`web/src/views/tasks.tsx`), reads `GET /api/v1/tasks` (`src/ui/tasks-api.ts`, served beside the notices and rules reads in `server.ts`) and shows four tabs: Inbox, Today, Upcoming and Project (design 02-tasks: the server places each task by its due date at its own local midnight; the page does no date arithmetic). Today lists the overdue tasks first under an Overdue heading, each title and due date in the bad-pill red token with an Overdue badge, then today's. Upcoming shows one group per day of the next 7 that has a task, headed by the viewer's short weekday and date. Project groups by `#list`, "No list" last. Each task is a card at every width (title, due, priority, `#list`, recurrence). An unbuilt task has Build this when the page has a commands actor: it posts `{ id }` to `POST /api/v1/tasks/build` with the token from the read, refreshes the read on success, and keeps a refusal beside the button; a built task shows a link to its work item instead. No quick-add form (the CLI, chat and the desktop shell add tasks).

One `listItemMessages` read per Needs-you row. Failed: the run's message (see the top) with `/retry`. Waiting for approval: `spec ready` with `/approve or /reject <reason>`. Ready to merge: the merge check (`mergeable`, `merge check running` or `N conflicting files`), with the Merge button beside it in the app; the command is `factory merge <id>` for a local item and none for a PR (changed 2026-11-08, issue #451). Other reasons in plain words. It never repeats the State label. Store reads only, no forge call. Rows without `need` fall back to the `why` sentence.
